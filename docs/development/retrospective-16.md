## Keep（続けること）

### K1. 途中レビューが、そのイテレーション自身の違反を捕まえた

T6（実装の途中でレビューを 1 度入れる）は **IT14・IT15 と 2 IT 連続で落としていた**。IT16 で初めて実施したところ、**IT16 自身が定めた T3 を IT16 の実装が破っている**ことが分かった。

C1 で `findPendingDischarges` という新しい一覧クエリを足しながら、`QueryCounter` のテストを書いていなかった。Javadoc には「まとめて 1 回で引く」と主張が書かれているだけだった。

**クローズ時のレビューでは、直す幅が広がっていた。** 途中で回したから、その場で直せた。

### K2. 破壊検証が空振りを 3 回見つけた

「テストがあること」と「テストが判別すること」は別である。本 IT で 3 回踏んだ。

| # | 空振り | 実際に守っていたもの |
| :--- | :--- | :--- |
| 1 | 荷降し手配のステータス絞り込み | `location` への JOIN（`LEFT JOIN` にした瞬間に却下が現場へ流れる） |
| 2 | 手配の並び順 | 行の物理的な並び（登録順と承認順がたまたま一致していた） |
| 3 | 名簿の逆方向 | 何も守っていなかった（カードを消して名簿に残すと白紙のダッシュボードが出る） |

**3 件とも、判別できる形にテストを書き直して初めて赤になった。**

### K3. 実測が判明するたびに順序を組み替えた

「落としたもの 0」は IT10・IT11 以来である。ただし**見積もりは大きく外している**。落とさずに済んだのは、実測が出るたびに順序を変えたためである。

- タスク 3（T3）と 5（C2）を入れ替えた — T3 を先に書くと C2 の重複が 7 → 最大 14 クラスに増える
- C1（受入基準）を C2 の途中で前倒しした — 落とさない対象を後ろに置くと、超過時に真っ先に危うくなる

### K4. 検査の無い規則を「守らない」と名前で残した

ADR 19 件に守り手を書き出し、**検査を書けないものは「守り手: 守らない」と明記した**。13 件が該当した。

書けない検査を書いたふりをするより、**どこが人の注意に預けられているかを残す**ほうが安全である。

## Problem（問題だったこと）

### P1. 記録された負債は、実態の 5 分の 1 から 10 分の 1 だった（最大の発見）

| 項目 | 引き継ぎの記録 | 実測 |
| :--- | :--- | :--- |
| C2（テストの貨物準備） | 7 クラス | **39 クラス・41 箇所** |
| C3（ビューの引数） | 2 件 | **21 件・最大 35 要素** |

**どちらも「落とす判断」がその小さい数字の上に立っていた。** C2 は IT14・IT15 と 2 度落とされ、C3 も同様である。「5 → 7 クラスに増えた」という記録を見て「まだ小さい」と判断していた。

**数え方が違えば、落とす判断の前提も違う。**

### P2. 検査を書く作業が、最も多く誤りを生んだ

| 誤りの種類 | 回数 |
| :--- | :--- |
| **自己参照**（検査が自分を違反として数える） | 3 |
| 品質ゲート違反（Checkstyle 2・SpotBugs 1） | 3 |
| **名簿方式の穴**（T4 で戒めた形を、T4 の後に自作した） | 1 |
| 走査条件の絞りすぎ（「インターフェース」に限定して 2 件を取りこぼした） | 1 |

とくに重いのは名簿方式である。`PersistenceMarkerCallerTest` は「版を進めるメソッド」を名前の一覧で持っていた。**別名で足したものは検査の外側に生まれる** — T4 でまさにそれを戒めた直後だった。

**守るものを増やすと、守られる対象も増える。**

### P3. 宣言された規則が、対象に届いていない形を 3 度見た

| # | 規則 | なぜ届かなかったか |
| :--- | :--- | :--- |
| 1 | ADR-009 の規則 1（購読は `AFTER_COMMIT`） | 既存の検査が `@TransactionalEventListener` を含むファイルだけを探していた。素の `@EventListener` に戻すと**対象から消えて緑になる** |
| 2 | Checkstyle の `ParameterNumber`（7 個まで） | **レコードのヘッダを見ない**。`InvoiceView` は 21 → 27 個まで誰にも止められずに育った |
| 3 | ADR-003「SQL を検証する唯一の場所」 | `*RepositoryTest` の基底を差し替えても何も落ちなかった |

**宣言はされているのに、対象が検査の視野の外にある。** 3 件とも別の理由で起きており、共通するのは「規則を書いた人が、その規則が届く範囲を確かめていない」ことである。

### P4. 自動化が US22 の保証を静かに消しかけた

C2 の移行スクリプトが、`ChargeCalculationScenarioTest` の**法人／割引率の引数を黙って落とした**。荷主の種別を `corporate ? "CORPORATE" : "INDIVIDUAL"` で切り替えており、スクリプトの判定が「リテラルの `CORPORATE`」しか見ていなかった。

**全緑を確認せずに進んでいれば、割引のテストが「個人荷主として通る」形で緑になっていた。** 気づいたのはバッチごとにテストを回していたからである。

### P5. 認可の食い違いを決められないまま閉じる

`ui_design.md` は荷役作業一覧を `ROLE_HANDLER, ROLE_TRACKER` とし、`SecurityConfig` は `ROLE_HANDLER` のみに絞って「現場が使う唯一の画面である」と理由を書いている。**どちらかが古い。**

C1 のテストで追跡管理者の到達性を主張したところ 403 で判明した。**認可を広げるのはテストで既成事実にしてよい変更ではない**ため実装は動かさず、両文書に食い違いを明記した。**決着はしていない。**

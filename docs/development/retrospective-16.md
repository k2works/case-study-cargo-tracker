## Keep

### 1. 「壊して赤を見る」を全項目でやった

TD-02 の絞り・TD-04 の `replicas`・US38 の検索条件・TD-03 の日付絞り込み・
US39 の既読の位置——**足した検査を 1 つずつ壊して赤を確かめた**。所要は 1 件あたり
1〜2 分である。

IT15 で「空の一覧に対する `doesNotContain` が何も判別していなかった」を踏んだため、
今回は**実業務の案件を 1 件置いた状態**で `contains(実業務).doesNotContain(SIM)` と
書いた。書いた後に絞りを外し、実際に赤になることまで見ている。

### 2. 検査が 5 回、実際に働いた

| 何が捕まえたか | 何を捕まえたか |
| :--- | :--- |
| 方言スモーク | `ON CONFLICT` が H2 で構文誤り（PostgreSQL では通る） |
| `SchemaDesignConsistencyTest` | `data-model.md` に `simulated` が無い |
| JaCoCo のカバレッジ検証 | `CargoSnapshot` の 4 引数コンストラクタが**誰も通らない道**になっていた |
| Checkstyle の FileLength | `BillingControllerTest` の肥大。**変わる理由が違う**検索 API のテストを分ける契機 |
| oxlint | 種の受け渡しを effect で同期していた（描画中に導く形へ） |
| E2E（CI） | 新しい区画が既存の指し方を曖昧にした（`SES-`・「種」が二重に一致） |

**いずれも「実装が正しいつもり」の状態で赤くなった。**

### 3. 見つけた欠陥を、見つかった場所に置いた

利用者からの申告（「利用者を切り替えると入った直後に断られる」）に対し、
判断そのものを単体テストで固定した。ナビゲーションの定義を判定に使い、
**写しを作らなかった**。

## Problem

### 1. 自分が入れた退行を、レビューが見つけた

**取り消した請求書（赤伝）が検索から消えていた。** US38 の絞り込みで
`voided_at IS NULL` を**一覧にも**掛けたためである。

受入基準は「取り消し済みの請求書は**合計に**含めない」だった。**「合計から外す」と
「一覧から消す」を取り違えた。** 赤伝こそ後から引かれる——「先月出し直した請求の、
元の番号は」「監査で取消理由を見せてほしい」は請求番号で引かれる。

しかも**自分で書いたテストが、その誤りを固定していた**
（`doesNotContain(voided)` と書いた）。テストは実装ではなく**私の理解**を写していた。

### 2. マニュアルが 2 か所、実装より古いまま残った

- 15 章の「出るか」の表と「夜間に回さないでください」が **TD-02 前のまま**
- 12 章の「いまはまだできないこと」に「発行済みの請求書を検索できません」が残り、
  **同じ章の手順と矛盾**

どちらも自分の変更で古くなった記述である。**新しい節を足すことには気を配ったが、
古い記述を探しに行かなかった。**「同じ章の中で矛盾している」のは、書いた直後なら
気づけたはずである。

### 3. 「読める場所」を作らずに「既読」を自動化した

ポップアップは出した時点で既読にする（[ADR-032] 決定 4）。**読み直せる場所を
同じ変更で作らなかった。** 回線が切れた・タブを閉じた・見落とした荷主は、
その知らせに二度と到達できない。

しかも**マニュアルには「14.3 のお知らせ欄を見てください」と書いていた**
——存在しない欄を案内していた。[記憶]「コメントは仕様として読み実装と突き合わせる」
と同じ形を、マニュアルでやった。

### 4. 5 視点レビューが 3 回連続で返らない

IT15（4 体）・IT16 の計画時（2 体）・IT16 のクローズ（4 体）と続いている。
今回は**待ち時間の上限を先に決めた**（Try 4）ので判断は速かったが、
**上限を決めても、独立したレビューが得られない事実は変わらない。**

利用者代表 1 体だけが返り、そこに**高 5 件**があった。うち 1 件は自分が入れた退行で、
**自己レビューでは見つけられていない。**

## Try

### 1. 「除く」と決めたら、除く先を名指しする（Problem 1）

「取り消し済みを除く」と書いたら、**どこから除くのかを列挙してから実装する**
——一覧・件数・合計のどれか。列挙せずに条件へ足すと、掛かる範囲が広がりすぎる。

**期待効果**: 「合計から外す」と「一覧から消す」の取り違えを、実装前に潰す。

### 2. 変更した機能の説明を、同じ章の中で読み直す（Problem 2）

節を足したら、**その章の「できないこと」「今後の課題」を必ず読む**。
自分の変更で古くなる記述は、たいてい同じ章の中にある。

IT17 の DoD に「機能を足したら、その章の制約・課題の記述を読み直す」を入れる。

**期待効果**: 「同じ章の中で矛盾している」を無くす。

### 3. 消える情報を作ったら、読み直せる場所を同じ変更で作る（Problem 3）

既読・自動削除・上限で切るなど、**情報が見えなくなる仕組みを入れたら、
その情報へ戻る道を同じ変更で用意する**。用意できないなら、その仕組みを入れない。

**期待効果**: 「知らせたことにしたのに読めない」を作らない。

### 4. レビューが返らない前提で、自己レビューの観点表を持つ（Problem 4）

3 回連続で返っていない。**次は「返らない」を既定として計画する。**
利用者代表が挙げた観点（その人の仕事が進むか・気づく手段が次の行動へ繋がるか・
ロール別と状態別の到達性・言葉づかい・マニュアルと画面の一致）を**観点表**にし、
自己レビューで機械的に当てる。

**期待効果**: 独立したレビューが得られないときの取りこぼしを減らす。
ただし**自己レビューは独立したレビューより弱い**——観点表があっても、
自分が入れた退行は見つけにくい。

### 5. 実環境の確認を、締めの日に依存しない形にする（残作業）

TD-02 の検収は「継続実行を一晩回した翌朝、4 つの一覧が実業務だけ」である。
**クローズの日には確かめられない。** 夜間の禁止を外した以上、この確認は
IT17 の初日に行う。

**期待効果**: 「運用で守る」から「確かめて外す」への切り替えを、宙に浮かせない。

# イテレーション 2 ふりかえり（KPT）

- 実施日: 2026-07-09
- 対象: IT2（2026-07-21 〜 08-01）／US04・US05・US06（10 SP）+ 技術的負債返済（M1/M3/M4/M5・ArchUnit 拡張）

| 指標 | 計画 | 実績 |

局面（開発戦略）: **序盤 = アウトサイドイン**。IT1 のウォーキングスケルトンのスタブ（予約ルート）を実画面へ差し替え、Booking BC を縦切りで立ち上げた。序盤（IT1-2）を計画どおり完走。

## Keep（継続すること）

### 技術的成功

- **テックリード（Claude Code）＋実装担当（Codex）の分業が高速かつ安定して機能した**。TDD サイクル単位で指示し、生成物をビルド・全テスト・設計レビューで検証してからコミットする流れを 6 コミット通して維持。
- **集約の不変条件で業務ルールを一元化**。危険物・冷凍の必須検証を `Cargo.ValidateSpecialRequirements` に集約し、UI は表示制御のみに限定。種別別の必須/禁止を単体テストで網羅した。
- **version 楽観ロックを更新系（US06）で正しく導入**（IT1 注153 の持ち越しを履行）。集約が version をインクリメントし、UPDATE の影響行 0 を並行更新競合として扱う設計を統合テストで実証。
- **M1（永続化ポートの IDbTransaction 依存除去）を AmbientTransaction 方式で完遂**。ドメイン/アプリケーションポートから System.Data を排除し、ヘキサゴナルの依存純度を回復。ArchUnit で継続検証。
- **ACL の境界厳守**。ShipperExistenceChecker を shipper テーブルへの SQL 直接参照に限定し、Booking→Shipper のドメイン型依存を持ち込まなかった。ArchUnit ルール 4 を Booking BC に拡張して固定線化。

### プロセス的成功

- **計画着手前の 2 段階検証（validating-iteration-plan → validating-design）が有効**。序盤アプローチの取り違え（インサイドアウト的手順）や IT1 パターンとの不整合（ポート配置・楽観ロック持ち越し）を開発着手前に是正できた。
- **技術的負債を計画的に返済**。ふりかえり Try を計画タスクに落とし込み、ストーリーと同じ品質ゲートで消化した。
- **ストーリー単位のコミット規律**を維持し、各コミットで全テスト緑・警告 0 を担保した。

## Problem（問題点）

- **イテレーション計画ファイルの編集中に構造破損が発生**した（ストーリー詳細・タスク節の重複/欠落）。validating-design の修正過程で Edit の適用が乱れ、最終的に Write で全面再構築して復旧。大きめの構造変更は部分 Edit より慎重に行うべきだった。
- **サンドボックス制約で Codex 側が `dotnet test` を実行できず**（ソケット bind 拒否）、テスト実行をすべてテックリード側で担う運用になった。ビルドは Codex 側で確認できたため致命的ではないが、フィードバックループが一段増えた。
- **設計ドキュメントの軽微なドリフトが実装で判明**（403 画面パス `/error/403` vs 実装 `/forbidden`、email の UNIQUE が「アプリ層で担保」表記のまま）。T1 で是正したが、ui_design/data-model の記述と実装の突合は継続課題。
- **CargoType が Booking と Estimation で二重定義**になった（BC 独立を優先）。domain-model は「共通」意図のため、将来の共通化是非は ADR で判断する必要がある（コード内にコメントで明記済み）。

## ベロシティと計画への反映

- IT2 実績 **10 SP**（計画どおり）。IT1=13・IT2=10 で平均 **11.5 SP/IT**。想定（10-12 SP）の範囲内で安定しつつある。
- 残 SP: **62 SP**（Release 1.0 MVP まで IT3-5）。バーンダウンは計画線に追従。
- 次イテレーション（IT3）から**中盤・インサイドアウト**に局面が切り替わる。航海スケジュール（US24/25/07）と経路候補算出（US08・外部サービス ACL の実データ化）が主戦場。

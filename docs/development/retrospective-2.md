## Keep（うまくいったこと）

### 技術的成功

1. **型駆動での不正状態排除の継続**: `CargoType` DU（Hazardous/Refrigerated に申告・温度データを埋め込み）と `BookingState` DU（Preliminary/RoutingRequested/Cancelled）で、必須制約と状態整合を型に昇格。危険物・冷凍の必須入力をコンパイル時＋サーバー側検証の二重で担保できた。
2. **ACL ポート＝関数レコードの一貫適用**: `ShipperExistenceChecker`・`RoutingRequestNotifier` を関数レコードとし、アプリケーション層テストはスタブ関数リテラルで差し込み、モックライブラリなしで検証できた（IT1 パターンの横展開）。
3. **BC 分離を保った横断参照（ADR-0008）**: 荷主の ShipperId（Guid）を `shipper_uuid` に永続化し、Booking からは Shipper プロジェクトを参照せず生 SQL アダプタで存在確認。ArchUnitNET の BC 分離ルールを緑に保ったまま実データ照会を実現した。
4. **Save/Update の責務分離**: `CargoRepository.Save`（INSERT）と `Update`（状態更新）を分離し、経路設計依頼時の再保存で UNIQUE 制約違反が起きる不具合を設計段階で解消した。
5. **カバレッジゲートの確立**: coverlet + ReportGenerator のマージと `classfilters` によるドメイン層抽出で、全体 80% / ドメイン 85% を機械判定する gate スクリプトと Backend CI を整備。ドメイン被覆の穴（未テスト値オブジェクト）を可視化して埋められた。

### プロセス的成功

1. **設計判断の先行決着**: 実装着手前に ADR-0007（経路設計中状態）・ADR-0008（荷主参照キー）を起票し、`validating-iteration-plan` / `validating-design` で整合を取ってから縦切りに入ったため、実装中の手戻りがなかった。
2. **レイヤー単位の小さな増分**: ドメイン → アプリ → インフラ → Web → 品質基盤の順に 1 増分 1〜2 コミットで進め、各コミットで全テスト緑・警告 0・フォーマット済みを維持した。

## Problem（課題）

1. **見積整合性チェック未実装（US04 AC6・任意）**: 見積番号の任意紐付けと出発地・目的地・貨物種別の一致検証（タスク 1.4 の一部）が未実装。Booking→Estimation の ACL 追加を要するため、駆動要因が明確になる時点まで保留した。
2. **post-commit イベントが Web 層で未結線（タスク 3.2）**: ワークフローは `CargoBooked`/`RoutingRequested` を戻り値で返すが、UnitOfWork の post-commit ディスパッチには未結線。消費者（Routing Context）が IT3 のため実害はないが、イベント基盤の実利用は先送り。
3. **Playwright E2E 継続未実施**: IT1 からの繰り越し（実ブラウザ・htmx 挙動の検証）は本 IT でも環境未整備のため未着手。種別連動フォームのクライアント表示切替は受け入れテスト（サーバー側）で代替検証にとどまる。
4. **設計ドキュメントへの反映残**: ADR-0007（BookingState に RoutingRequested）・ADR-0008（shipper_uuid）・Weight 値オブジェクト追加・cargo.shipper_id を Guid 参照とした判断を、domain-model.md / data-model.md 本体へ取り込む作業が残っている（計画に注記済み）。

## 局面移行の確認（IT2 → IT3）

開発戦略では IT2 が序盤（アウトサイドイン）の最終 IT、IT3 から中盤（インサイドアウト・Routing/Tracking/Handling）へ移行する。移行にあたり以下を確認した。

- 序盤の完了条件（歩けるスケルトン・基盤の妥当性検証）は IT1-IT2 で充足。
- IT3 は Routing の複雑ドメイン（経路候補算出・航海スケジュール）をドメイン層 FsCheck から作り込む（Try#4）。
- 序盤で確立した ACL＝関数レコード・UoW・Web スライスのパターンは中盤も踏襲する。

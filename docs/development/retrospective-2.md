# イテレーション 2 ふりかえり

## 概要

| 項目 | 内容 |
|------|------|
| イテレーション | 2 |
| 期間 | 2026-08-17 〜 2026-08-28（2 週間） |
| 計画 SP | 17 |
| 実績 SP | 17（達成率 100%。ただしタスク 2 件を IT3 へ送付） |
| 局面 | 序盤（アウトサイドイン） |

本イテレーションのゴールは「公開貨物追跡を US18 の受入基準まで作り込み、品質ゲートを機能させる」。
ゴール自体は達成したが、**品質ゲートそのものに穴があった**ことがレビューで判明し、
それを塞ぐところまでを本イテレーションの成果とした。

---

## Keep（うまくいったこと）

### K1. CI の前倒し（Try T5）が正しい判断だった

IT1 のふりかえりで「CI を IT3 から IT2 へ前倒しできないか」と挙げた TS05a を実施し、
**47 秒で完走する CI** が手に入った（受入条件は 8 分以内）。キャッシュを最初から入れたことで、
「遅いから回さない」という将来の劣化経路を潰せている。IT1 の「ローカル緑のみ」という
品質判断の弱さが 1 イテレーションで解消した。

### K2. 実装前に規約仕様を確定させた（Try T4）

`arch-lint` を実装する前に `docs/design/arch_lint_rules.md` で 9 規約の検出方法・既知の例外・
メタテストの仕様を確定させた。IT1 のレビューで見つかった「規約 5 の定義矛盾」を実装前に解消でき、
偽陽性による大量の手戻りを避けられた。**仕様を先に書く**というやり方は、
検査器のように「間違った仕様のまま実装すると全体が無価値になる」対象で特に効く。

### K3. 効果ハンドラによるテストダブルが UI 層でも効いた

画面関数を `Html` を返す純粋関数に保った結果、`ComponentsTest`（14 件）・`LayoutTest`（10 件）・
`TrackingPublicPagesTest`（21 件）が DB もサーバも起動せずに回る。61 件のテストが 2 秒で終わる。
IT1 で確立した構造が、画面が増えても素直に伸びることを確認できた。

### K4. 起動して実画面を見たことでバグを 1 件発見した

テストが全緑になった後にアプリを起動して HTML を確認したところ、推定到着日が
`2026-08-10 00:00:00` と表示されていた。テストは自分が書いた値（`"2026-08-10"`）を
渡していたため通っていた。**緑のテストは「実データで正しい」ことを意味しない。**

### K5. レビューが品質ゲート自体の欠陥を捕まえた

5 視点のレビューで、`arch-lint` が複数行に分けた違反を検出できないことが判明した
（プログラマとアーキテクトが独立に指摘）。実測で検出 0 件を確認している。
レビューを「コードの粗探し」ではなく「保証の仕組みが本当に保証しているか」に向けると、
単体では見つからない欠陥が出る。

## Problem（うまくいかなかったこと）

### P1. メタテストが緑でも検査器は信用できなかった

IT1 の ADR-0002 で「`arch-lint` にメタテストを設ける」ことを補償策としたが、
フィクスチャが**単一行に書いた違反**しか持たなかった。本プロジェクトの SQL は
`"SELECT ... " +` で改行して連結するスタイルであり、その形の違反は素通りしていた。
17 件のメタテストが緑であることが、検査器を信用する根拠になっていなかった。

**フィクスチャは「規約に違反する最小の例」ではなく「このコードベースで実際に書かれる形の違反」で
作らなければならない。**

### P2. テストが実装に追従し、書式バグを 2 度すり抜けた

日付書式のバグは、(1) 画面のユニットテストが自分の書いたきれいな値を渡していた、
(2) 統合テストが `String.contains("2026-08-10")` の部分一致だった、という 2 段で見逃された。
修正時もユニット側しか固めておらず、レビューで「縦断経路は無防備なまま」と指摘された。

原因は**インメモリのフィクスチャが JDBC の返す実データ形と違っていた**こと。
テストの入力が現実と違えば、変換のテストは何を書いても保証にならない。

### P3. 利用者にとっての価値が成立していなかった

Bootstrap の CSS が読み込まれておらず、バッジ・カード・表の体裁がまったく効かない状態で
「UI 基盤が揃った」としていた。設計（`architecture_frontend.md`）には `resources/static/` が
あるのに実装が存在しない。**受入条件をコードのインタフェースで書くと、
「利用者が見て価値があるか」が抜け落ちる。**

### P4. 「現在地」という言葉を疑わなかった

最新イベントの発生場所を「現在地」と表示していた。輸送中の貨物では積込港が表示され、
荷受人は「まだ出港していない」と読み違える。データモデル上の名前（`currentLocation`）を
そのまま画面の言葉にしてしまった典型で、ユーザー代表の視点がなければ気づけなかった。

### P5. ドキュメントが実装に追いつかない箇所が複数残った

CI と `arch-lint` は実装済みなのに手順書は「未整備」のまま、トレーサビリティ表は
テスト件数も E2E の状況も古いまま、規約数の数え上げは 8 と 9 が混在——といったずれが
レビューで 6 件見つかった。**IT2 で 2 度目**（IT1 でも同種の指摘があった）。

### P6. 見積もりが実績と乖離した（3 イテレーション目の課題）

計画は 61.5h（稼働 40h に対し 54% 超過）で、実際は E2E とフィクスチャ共通化を IT3 へ送って
着地した。SP は 17/17 で 100% だが、これは**タスクを落として達成率を保った**形であり、
ベロシティの信頼性という点では正直に記録しておく必要がある。

### P7. `Principal` と合成ルートの置き場所が構造的な負債になった

`Principal`（認証主体）を HTML 描画モジュールに置いたため、IT3 で認証基盤を作ると
依存の向きが逆転する。また合成ルートが `shared/` 配下にあるため、`arch-lint` の規約 4 が
`shared` を一律免除しており「shared → BC 依存」を検査できない。
どちらも**今なら安く直せるが、BC が増えると高くなる**。

## Try（次イテレーションでの改善アクション）

| # | アクション | 担当 | 期限 | 期待効果 |
|:--:|-----------|------|------|---------|
| T1 | **フィクスチャは「実コードで書かれる形」で作る**。新しい規約を追加するときは、既存コードから同種の記述を 1 つ探して負例の形に使う | 開発チーム | IT3 以降の常時 | P1 の再発防止。検査器の偽陰性を構造的に減らす |
| T2 | **テストのフィクスチャ生成を 1 箇所に集約し、JDBC が返す形式のみを源とする**（IT2 タスク 3.7 の再定義）。「ETA あり」「ETA なし」を名前付きフィクスチャにする | 開発チーム | IT3 | P2 の再発防止。重複除去ではなく「実データ形の一元化」が目的 |
| T3 | **受入条件に「利用者が画面で確認できること」を 1 行入れる**。UI を含むストーリーでは、起動して実画面を見ることを DoD に加える | 開発チーム | IT3 | P3・K4 の制度化。関数シグネチャの受入条件だけにしない |
| T4 | **静的ファイル配信と Bootstrap の導入を IT3 の独立タスクとして先頭に置く**（余力次第にしない） | 開発チーム | IT3 序盤 | P3 の解消。「余力次第の返済枠」が固定化する典型を避ける |
| T5 | **`Principal` / `Role` の移設と合成ルートの位置を IT3 の認証実装と同時に行う**。規約 10（shared → BC 依存の禁止）もこのとき追加する | 開発チーム | IT3 | P7 の解消。BC が増える IT4 の前に構造を正す |
| T6 | **ドキュメント整合の機械検査（`trace-lint`）を実装し CI に載せる**。US 番号とトレーサビリティ表の突合から始める | 開発チーム | IT3 | P5 の解消。人手の維持をやめる |
| T7 | **見積もりを稼働時間の範囲に収める**。計画時点で 40h を超える場合は、超過分を「IT3 送り」と明示してから着手する | 開発チーム | IT3 計画時 | P6 の緩和。達成率ではなく「計画どおりか」で見る |
| T8 | **新しい表示ラベルを決めるときは、業務の言葉として読み上げてみる**（「現在地」「例外」のような内部語をそのまま出さない） | 開発チーム | IT3 以降の常時 | P4 の再発防止 |

3 点で、SP ではなく「計画時間 vs 実時間」で見直す。

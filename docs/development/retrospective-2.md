## Keep（継続すること）

### 技術的成功事項

- **インサイドアウトの徹底**: ドメイン層（Voyage 集約・値オブジェクト）→ infra（SqlxVoyageRepository）→ app（ユースケース）→ interface（画面）の順で積み上げ、貧血ドメインモデルを回避できた。中盤局面のアプローチが機能した。
- **newtype + スマートコンストラクタ**: `VoyageNumber`/`VesselName`/`Carrier`、`CarrierMovement`（出発地≠到着地・出発<到着）、`Schedule`（時系列順・非空）の不変条件を生成時点で型に落とし込み、不正状態を生成時に排除した。
- **認可 extractor（`RoleGuard<R>`）**: `require_user` + `has_role` の 3 行重複（9 箇所）を型安全な extractor に集約し、認可の書き忘れをコンパイラが構造的に防ぐ設計に。5 視点のレビューで最も高く評価された。
- **BC 独立の維持**: `CargoType` を Routing 固有型として定義し、domain-booking を直接参照しない設計をコンパイラ（Cargo.toml 依存宣言）で強制した。
- **DIP 回復を ADR で明文化**: composition root への注入を ADR-0003 として記録し、意図的な設計判断として残した。

### プロセス的成功事項

- **計画前の整合性検証**: `validating-iteration-plan` + `validating-design` を着手前に実施し、ドメイン/データ/UI 設計との不整合（CarrierMovement の種別・船名欠落・`/voyages` 閲覧専用）を事前に検知して計画に注記できた。
- **developing-review の活用**: 中核実装完了後に 5 エージェント並列レビューを実施し、高優先度の受入基準テスト漏れを即座に補完（5 本追加）。レビュー→改善のループが機能した。
- **小さく頻繁なコミット**: 層ごと・目的ごとに分割し、pre-commit の fmt/clippy ゲートで品質を維持した。

## Problem（問題点）

### スコープ・計画の課題

- **US07 の受入基準の一部が未実装のまま完了扱いになった**: 「出発期間での検索」「予約番号からの貨物仕様確認」は受入基準にあるが実装されず、レビュー（user-representative）で発覚。計画時に検索条件を「出発港・到着港・貨物種別」に暗黙で絞っており、受入基準との差分が明示されていなかった。
- **異常系・境界のテストが計画に明示されず、レビューで漏れ発覚**: 寄港地複数区間・0 件時・更新キャンセル・日付逆転の HTTP 経路テストが初期実装で欠落。ドメイン単体は緑でも受入基準の異常系が HTTP で未実証だった（tester 指摘、後で 5 本補完）。

### 技術的課題

- **`search` の三重 N+1**: 全件ロード後に Rust 側フィルタ ＋ voyage ごとに子テーブルを個別クエリする実装で、件数増に対し線形劣化する。US07 の検索は本来 SQL WHERE で絞るべきだった（architect・programmer が指摘）。
- **設計ドキュメントが実装に先行して取り残された**: `/voyages` 登録・更新画面を実装したが ui_design.md への反映が後追いになった（クローズ直前に反映）。data-model.md は同時反映できていた。
- **実ブラウザ動作確認が未実施**: HTTP フローテストで代替したが、IT1 の教訓（セッション Cookie・DB 認証情報などの設定系ランタイム不具合は oneshot テストで漏れる）に対する実ブラウザ確認をこのイテレーション内で行えていない。

## 次イテレーション（IT3）への引き継ぎ

- **US07 の未実装分を IT3 スコープに統合**: 「出発期間での検索」「予約番号からの貨物仕様確認」は、US08（経路候補算出）が予約起点の経路設計フロー（`/bookings/{bookingId}/route`）で貨物仕様を扱うため、IT3 でまとめて実装する。
- **`search` の N+1 を SQL 絞り込みへ**: IT3 で経路探索を実装する際、Voyage 検索の Repository を SQL WHERE ベースに作り直す。
- **`CurrentUser.roles` の Vec<Role> 型化**: ADR-0003 でスコープ外とした型化を、セッションシリアライズ仕様への影響を確認しつつ別途対応する。
- **infra-eventbus 骨格**: IT1 から持ち越したイベントバス骨格は、Booking/Tracking 連携が始まる IT4-5 で完成させる方針を維持する。

# イテレーション 2 ふりかえり

対象: US03（法人荷主）・US04（貨物予約）・US05（危険物・冷凍）= 8 SP
期間: 2026-08-20（IT2）

## 実績

| 項目 | 計画 | 実績 |
| :--- | :--- | :--- |
| ストーリーポイント | 8 SP | 8 SP（100%） |
| 理想時間 | 75h（うち返済枠 22h・マニュアル 7h） | 計画どおり |
| ベロシティ | 9 SP（IT1 実績） | **8 SP** |

> 返済枠とマニュアルは SP に含めない。純粋なストーリー実装の実績（8 SP / 46h）で見る。
> 1 SP あたり 5.75h で、IT1（5.2h）とほぼ同水準。

### 満たしていない受入基準

依存先が未実装のため、**IT2 のスコープ外**として正直に記録する。

| 受入基準 | 依存先 | 状態 |
| :--- | :--- | :--- |
| US03「登録した法人情報は US22 で参照される」 | US22（IT11） | 参照される側のデータは用意済み |
| US04「経路設計者に予約登録の通知が送信される」 | US06（IT3） | 仮受付での保存までを完了とした |
| US04「見積情報との整合性が確認される」 | US01（IT12） | 見積が無いため確認しようがない |
| US05「経路設計時に対応可能な航海・ルートのみが候補として表示される」 | US08（IT4）・US09（IT5） | 特別情報を保存し、経路設計が読める形にするところまで |

## Keep

### 判断を先に決めて ADR に落とした

IT2 の冒頭で 9 件の判断を決め、ADR-007〜013 として記録した。とくに次の 3 件は、
決めずに進めていれば実装をやり直すことになっていた。

- **ADR-008（利用者と荷主を紐付けない）**: 紐付けが無い状態で `ROLE_SHIPPER` に予約参照を開くと、
  絞り込めないため**全荷主の予約が見える**。機能の不足ではなく情報漏洩であり、「後で足す」で守れない
- **ADR-009（状態列は最初から NOT NULL、料金列は NULL 許容）**: 後から NOT NULL を足すと IT2 で
  入った行が読めなくなる。一方で料金に 0 を置くと、算出漏れが「無料の予約」として通る
- **ADR-011（予約番号は DB シーケンス・形式はマイグレーションに置く）**: 5 サービスが論理参照する
  キーであり、値そのものが契約になる

### 「壊して赤」を全件で回した

IT1 の Try 1・2 を守り、追加した検査すべてについて対象を壊して赤になることを確認した。
このうち **CAS による失敗回数の記録**は、修正前の赤（同時 5 リクエストでロックが成立しない）を
先に見てから直しており、欠陥の実在が確かめられている。

### 方言スモークが両方向で働いた

`V3` の `booking_id` に置いた `DEFAULT` を制約より後ろに書いたところ、**PostgreSQL では通り
H2 だけが落ちた**。IT1 で「方言差は両方向に起きる」と記録した形がそのまま再現し、検査が捕まえた。

### 検査が導線の食い違いを捕まえた

ADR-008 で貨物予約を `ROLE_SALES` に絞った結果、荷主ダッシュボードの
「自分の貨物予約を見る」が **403 になる画面**を指す状態になった。ロール別到達性のテストを
足していたため、実装と同じ変更の中で気づけた。

## Problem

### 適用したはずの修正が当たっていなかった

荷主登録画面のクライアント側検証（`localInvalidMessage`）と、`max="30"` の除去は、
一度「書いたつもり」で先へ進んでいた。E2E が緑に見えたのは、MSW が同じ 400 を返していた
ためで、**別の経路がたまたま同じ結果を作っていた**。E2E が後で赤くなって初めて発覚した。

- **原因**: 一括置換の結果を確認せず、テストの緑だけを見た
- **影響**: US03 の E2E が 2 本、原因不明のまま数回落ちた

### 開発サーバの再利用で古い成果物を見ていた

Playwright の `reuseExistingServer` により、停止済みのサーバが再利用され、修正が
反映されていない状態でテストを流していた。IT1 でも同じ形（`dev:mock` を呼ぶ webServer が
ローカルでは露見しない）を踏んでいる。

### ネイティブ検証が自前のメッセージを覆い隠した

`type="number"` の `step="0.1"` は、`30.1` を**ステップ不一致**として弾く。ブラウザは吹き出しで
知らせるだけで画面には何も残らないため、「押しても何も起きない」状態になっていた。
`required` / `max` も同じで、いずれも**利用者に理由が届かない**。

### 作業機の資源が足りず、検査を同時に走らせられない

Testcontainers（PostgreSQL を立てる結合テスト）と kind 統合環境は、どちらも Docker の
資源を使う。作業機の Docker に割り当てられているのは 7.75 GB で、両方を同時に動かすと
**片方が「起動できない」という形で赤になる**。

赤の見え方が「方言スモークの初期化エラー」であるため、方言そのものの問題と紛らわしい。
実際には Docker がコンテナを立てられなかっただけで、コードは変わっていない。

- **影響**: バックエンドのフルビルドが 2 回続けて赤になり、原因の切り分けに時間を使った
### 健全なコンテナを「起動できていない」と判定していた

kind で新しいイメージの Pod が 10 分以上 Ready にならなかった。資源不足だと考えて
サービスを減らしたが、**本当の原因は起動プローブの `timeoutSeconds` が既定の 1 秒**
だったことだった。負荷のかかった作業機では JVM の actuator が 1 秒で応答しきれず、
正常に起動しているコンテナが繰り返し「異常」と判定されていた。

IT1 の「横断的な防御はヘルスチェックを除外する」と同じ family で、
**安全装置が正常なものを殺す**形である。7 サービスすべての probe を 5 秒に緩めた。

### MSW の状態がページ遷移で消えることを前提にしていなかった

`page.goto` は全体を読み直すため、MSW のメモリ上の状態が失われる。「前のテストが作ったもの」
「前の画面で登録したもの」に頼ったテストは、単体で流したときだけ落ちる。

## Try

| # | 改善アクション | 期待効果 | 反映先 |
| :--- | :--- | :--- | :--- |
| 1 | **置換したら置換後を読む**。一括置換の後は対象行を grep で確認してから次へ進む | 「書いたつもり」の修正が緑をすり抜けない | IT3 の作業手順 |
| 2 | **E2E を流す前に、開発サーバが今のコードを配っているか確かめる**（配信中のモジュールを 1 つ grep する） | 古い成果物に対する検査で判断しない | IT3 の DoD |
| 3 | **入力の拒否は自前のメッセージで行う**。`required` / `max` / `step` はブラウザに任せず、画面に残る形で理由を出す | 利用者が何を直せばよいか分かる | `ui_design.md` の入力規約 |
| 4 | **E2E は自分が使うデータを自分で用意する**。他のシナリオや前の画面の状態に頼らない | 単体で流しても通る | IT3 の E2E |
| 5 | **モックにも本物と同じ規則を書く**。モックだけが甘いと、画面は「動く」まま本番で落ちる | 写し間違いを早く見つける | IT3 の作業手順 |
| 6 | **免除は理由と解消時期を添えて一覧にし、一覧自体を検査する**（ロール別入口の免除で実施した形を広げる） | 「まだ作っていない」と「開かないと決めた」を取り違えない | IT3 の検査 |
| 7 | **Docker を使う検査は同時に走らせない**。結合テストと kind は順番に流し、赤が出たら「コンテナが立ったか」を先に見る | 環境の赤をコードの赤と取り違えない | IT3 の作業手順 |
| 8 | **kind は必要なサービスだけ立てる**。IT で触らないサービスは 0 レプリカにする | 作業機で統合環境の確認が完了する | `operating-deploy` の手順 |

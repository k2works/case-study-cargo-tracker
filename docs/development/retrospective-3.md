## Keep（うまくいったこと）

### 技術的成功

1. **インサイドアウトの徹底でドメインを堅牢化**: Schedule の連結制約（前区間到着港 = 次区間出発港）・時系列・非空を `create` で型保証し、経路候補算出（RouteComputation）を純粋関数の深さ優先探索として FsCheck 込みで固めてから外へ展開。複雑ドメインをドメイン層に凝集でき、貧血モデルを回避した（開発戦略 中盤の狙いを達成）。
2. **ADR による設計判断の明確化**: US08 の算出方式を ADR-0009 で「Routing 自コンテキスト構成」に確定。案 B（外部 ACL 委譲）・案 C（Estimation RouteCandidate 共用）を却下理由込みで記録し、実装の置き場所（ドメインサービス）が一意に定まった。
3. **親子集約の永続化パターン確立**: VoyageRepository で voyage + carrier_movement を単一トランザクションで保存し、更新は子の総入れ替え。集約復元時に seq_number 順で連結制約を再検証する往復を統合テストで実証。
4. **BC 分離を保った横断連携**: 経路設計依頼一覧は Booking の CargoQueries（ROUTING_REQUESTED 状態）を Web 合成層で結合し、Routing は Booking を直接参照しない。ArchUnitNET の BC 分離を緑に維持。
5. **VoyageNumber の型分離**: Routing 固有の VoyageNumber を Booking 固有型（Leg.Voyage 用）と別型として定義し、コンテキスト跨ぎの取り違えをコンパイルエラー化（設計レビュー #33 に整合）。

### プロセス的成功

1. **横断検証で戦略矛盾を早期発見**: `validating-design` で「開発戦略の US08 記述（外部 ACL スタブ駆動）」と ADR-0009 の矛盾を着手前に検出し、判断を仰いで戦略側を修正。実装中の手戻りを防いだ。
2. **設計ドキュメントの即時反映**: IT2 の retro Try#1 を踏襲し、Voyage 拡張（0006）と Routing 新規要素を data-model / domain-model へ完了時に反映。ドキュメントドリフトを持ち越さなかった。

## Problem（課題）

1. **費用が暫定ヒューリスティック**: US08 AC3 の費用は区間所要日数ベースの簡易計算にとどまる。正式な料金計算は Billing（IT7）に依存するため、経路候補の費用は暫定値である旨が UI で明示されていない。
2. **経路探索の深さ制限**: RouteComputation は発散防止のため最大 3 区間に制限。多段乗継が必要な稀なケースは候補に出ない。現実的な航路では十分だが制限は明示的ドキュメント化が薄い。
3. **post-commit イベント dispatch の未結線（継続）**: 経路設計依頼一覧は booking_status クエリで実現したが、ADR-0002 の post-commit イベント dispatch（UnitOfWork 結線）は消費者が引き続き不在のため未実施（IT2 H6 からの継続）。
4. **WireMock 契約テストのデスコープ**: ADR-0009 で ExternalRoutingServicePort が US08 で不使用となり、実 HTTP 実装が無いため WireMock.Net 契約テスト（タスク 4.1）を延期した。tech_stack の「外部システムは WireMock で契約固定」方針の実証が未達。
5. **US25 の差分確認 UI が簡易**: 更新画面は既存内容をフォームに復元するが、「変更前後の差分表示」（受入条件 2）はフォーム上の再編集に留まり、明示的な差分ビューは未実装。

### ベロシティ較正の結論

- **実効ベロシティ**: IT1-3 の平均は 11.3 SP/IT。ただし局面差が大きく、序盤（縦切り + 基盤）は 10 SP/IT、中盤（複雑ドメイン）は 14 SP を計画どおり消化した。
- **AI エージェント協働**により、当初想定（10-12 SP/IT・実効）を上回るスループットを 3 イテレーション連続で維持。基盤・パターンが確立し、IT2 のカバレッジゲート・IT3 の親子集約パターンなど再利用資産が増えている。
- **残リリース計画の妥当性**: Release 1.0 は IT5 完了時。残り IT4（12 SP）・IT5（17 SP）。IT5 の 17 SP は過積載リスク（リリース計画のスケジュールリスクにも記載）。IT1-3 の 100% 達成を踏まえても、IT5 は US17（手動更新）を切り出し候補として維持する。
- **改訂要否**: 現時点で IT 割り当て・リリース日の改訂は不要。IT4 完了時に IT5 の過積載を再評価する。

## 局面の継続（中盤 IT3 → IT4）

IT3・IT4・IT5 は中盤（インサイドアウト）。IT4 は Routing の経路確定（US09-11）と Booking の予約確定（US12/US13）で、Routing と Booking をまたぐ。IT3 で確立したパターンを継続する。

- Routing の経路候補（IT3）を Booking の CargoItinerary へ紐付ける（US11）。ここで Booking の `RouteProposed` 状態（IT2 スコープ外だった後続状態）を実装する。
- post-commit イベント dispatch を IT4 で結線する（Try#1）。
- BC 間連携は ACL / Event 経由に限定し、ArchUnitNET で直接参照禁止を維持する。

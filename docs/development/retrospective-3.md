# イテレーション 3 ふりかえり

対象: US24（航海登録）・US25（航海更新）・US07（航海検索）・US06（経路設計への引き渡し）= 10 SP
期間: 2026-08-20〜2026-08-21（IT3）

## 実績

| 項目 | 計画 | 実績 |
| :--- | :--- | :--- |
| ストーリーポイント | 10 SP | 10 SP（100%） |
| 理想時間 | 97h（うち返済枠 20h・マニュアル 8h） | 計画どおり + レビュー手直し |
| ベロシティ | 8 SP（IT2 実績） | **10 SP** |
| IT1〜IT3 の平均 | — | **9 SP / イテレーション** |

> 返済枠とマニュアルは SP に含めない。純粋なストーリー実装の実績（10 SP / 69h）で見ると
> 1 SP あたり 6.9h で、IT1（5.2h）・IT2（5.75h）より **2 割ほど重い**。新しいマイクロサービス
> （routingms）の立ち上げ分が上乗せになった。IT4 は既存サービスへの追加なので IT2 水準に戻る想定。

> **クローズ時のレビュー手直しは SP に計上していない。** 高優先度 10 件の対応に相応の工数が
> かかっている。ベロシティが計画どおりに見えることを「余力があった」と読み替えない。

### 満たしていない受入基準

依存先が未実装のため、**IT3 のスコープ外**として正直に記録する（計画で宣言したとおり）。

| 受入基準 | 依存先 | 状態 |
| :--- | :--- | :--- |
| US07「制約条件（港湾制約）に基づいて利用可能な航海が表示される」の**港湾制約** | 設計にモデルが無い | 航海スケジュール・寄港地接続・貨物種別対応の 3 つで絞るところまで。**「対応した」とは書かない** |
| US06「経路設計者に経路設計依頼の通知が送信される」 | メール送信が設計に無い | 画面上の気づく手段（ダッシュボードの件数 → 絞り込み済み一覧 → 詳細）で代替 |
| US06「予約情報に不備がある場合、修正してから引き渡せる」の**修正** | 予約の訂正（未着手） | 不備を見つけられるところまで。訂正は起票済み |

## Keep

### ADR の決定を同じ IT の中で実行される検査に落とした

IT2 の最大の指摘は「ADR-007 が承認済みなのに実装も検査もゼロ」だった。IT3 では
ADR-014（地点マスタの複製）・ADR-015（経路依頼状態）とも、決定と同じ IT の中で
検査に落ちている。レビューでも architect が「観点 1 は達成」と評価した。

### 「名簿を持たず実体から検出する」形を 3 つ作った

`LocationSeedReplicaTest`・`AuthenticatedUserFilterRegistrationTest`・`SharedKernelScopeTest` の
いずれも、対象を `settings.gradle` とマイグレーションの実体から導き、**除外の側だけを一覧**にした。
さらに 3 つとも「1 件も読み取れていなければ赤」を明示した。名簿方式は載せ忘れたものほど
無検査になるため、この形が効く。

### 新しいサービスに、前の IT で学んだ形が最初から入っていた

`MyBatisVoyageRepository.save` は最初から INSERT / UPDATE を分岐している。同じ IT の中で
bookingms の「常に INSERT」を直した学びが、新規コードに反映されていた。

### 検索の上限と 0 件を、黙らずに伝えた

50 件で切ったことを総件数つきで出し、0 件のときは「どの条件が強く効くか」まで書いて
条件を外す操作を置いた。レビューで user-representative が唯一「ここは合格」と書いた箇所。

## Problem

### US25 の中核シナリオが、全緑のまま動いていなかった

差分の比較が**先頭区間の出発日時しか見ていなかった**。実務でいちばん多い差し替えは
「本船が遅れて到着が 2 日ずれた」で、この場合 `hasChanges` が false になり、画面は
「変更はありません」と言って上書きを選ばせない。**運航管理者は正しい予定を入れたのに
更新できない**状態だった。

原因は、差分算出が項目ごとの比較の積み上げになっていて、`Voyage` の全項目を
網羅していることを誰も守っていなかったこと。テストは船名・寄港地・貨物種別の 3 つを
比較していたが、いずれも時刻を動かしていなかった。

### 実環境でだけ見つかる欠陥が、この IT で 3 件出た

| 欠陥 | いつ見つかったか | 覆い隠したもの |
| :--- | :--- | :--- |
| 更新のはずの保存が新しい予約を作る | kind で業務を通したとき | 単体は偽の保存先、統合は新規保存のみ |
| 権限の検査より入力の検査が先に走る | kind で業務を通したとき | どのレベルも順序を判別していなかった |
| 出発日の絞り込みが実バックエンドに通らない | **クローズのレビュー中** | モックが日付と日時を文字列で前方比較して通していた |

3 件目は、日付（`YYYY-MM-DD`）をそのまま送っているのにサーバは日時（`Instant`）で受け取る、という
型の食い違い。モックが `voyage.departureTime < '2026-10-01'` という文字列比較で「たまたま動く」
挙動を返していたため、単体も E2E も緑だった。**モックが本物より甘いと、画面は動いたまま本番で落ちる**
（IT2 Try 5 と同じ形が再発した）。

### 欠陥を直した場所と、テストを足した場所が違った

「認可より入力検証が先」は bookingms で見つかったのに、回帰テストは routingms にしか
無かった。レビューで tester が実測し、**bookingms 側は順序を戻しても全緑**であることを
確認している。実環境で見つけた欠陥は、見つかった場所に固定しなければ意味がない。

### 境界の包含を、境界のデータで検査していなかった

`CarrierMovement`（出発 = 到着を拒否）と `Schedule`（前の到着 = 次の出発を許可）は
隣接する 2 つの時刻境界で包含が逆向きだが、テストデータが常に「厳密に前 / 厳密に後」
しか使っていなかったため、**両方を反転しても全緑**だった。そしてどちらが正かは
業務の判断（滞船 0 分を認めるか）であり、決めていなかった。

### ADR の決定が 2 つあるのに、検査が 1 つしかなかった

ADR-014 は「同じ INSERT」と「テーブルの形も同じ」の 2 つを決めているが、検査は
種データしか見ていなかった。**列だけ足して種データを変えない `ALTER` は素通り**する。
「ADR を検査に落とした」と言えるのは、決定の数だけ検査がある場合に限る。

### 更新の導線が、画面としては成立していても業務としては使えなかった

一覧の「更新する」は航海番号しか引き継がず、実質「入力し直し」だった。10 区間ある
航海の到着を 1 日ずらすために全部打ち直すのは、その過程で別の項目が変わる。
受入基準（「既存の航海を更新できる」）は満たしていたが、業務では使えない。

### 一覧の既定に、もう出てしまった船が混ざっていた

出発日の昇順なので、絞らないと過去の便が先頭を占める。経路設計者が朝いちばんに開いて
最初に目に入るのがそれでは、一覧そのものが信用されない。IT2 でも同じ議論をしている
（[「一覧は『毎朝どう使うか』から確かめる」](../review/イテレーション2_review_20260820.md)）。

### 差分を、機械の表記のまま利用者に見せていた

日時が `2026-09-01T01:00:00Z`、貨物種別が `GENERAL, HAZARDOUS`、寄港地が UN/LOCODE のみ。
09:00 と入力した相手に 01:00 と見せて「上書きしますか」と問うのは、**判断させているように
見えて判断できない**。

### マニュアルの構成図に同じ行が 2 回あった

マニュアルの構成図そのものが信用を落とす。加えて、実際に出るのに書かれていない
メッセージが 6 件あった（とくに日時の未入力は最も踏みやすい）。

## Try

| # | 改善アクション | 期待効果 | 反映先 |
| :--- | :--- | :--- | :--- |
| 1 | **「全項目を比べる」は、項目を並べずに 1 つの表現にまとめて丸ごと比べる**。項目ごとの比較を積み上げると、属性が増えるたび同じ穴が空く | 比較漏れが構造的に起きない | IT4 の作業手順 |
| 2 | **更新のシナリオは「変えたい 1 項目だけを変える」形でテストする**。全項目を変えるテストは、比較漏れを判別しない | 中核シナリオが全緑のまま動かない状態を作らない | IT4 の DoD |
| 3 | **モックは「本物より甘い」ほうへ寄せない**。型が違う値を比較しているモックは、本物が断る入力を通す | モックが本番の欠陥を覆い隠さない | IT4 の作業手順 |
| 4 | **画面が送る値の型を、サーバが受け取る型と 1 度は突き合わせる**（日付 / 日時、数値 / 文字列） | 実環境でしか出ない型の食い違いを先に見つける | IT4 の DoD |
| 5 | **実環境で見つけた欠陥は、見つかった場所に回帰テストを置く**。他の場所に真似た実装を入れて終わりにしない | 直した場所と守られている場所がずれない | IT4 の作業手順 |
| 6 | **境界の包含は、境界のデータで検査する**。「厳密に前 / 厳密に後」だけのデータは包含の向きを判別しない。どちらが正かを業務判断として決めてから書く | 反転しても緑のテストを残さない | IT4 の DoD |
| 7 | **ADR は決定の数だけ検査を用意する**。決定が 2 つで検査が 1 つなら、片方は文章のまま | 「ADR を検査に落とした」を半分で名乗らない | `creating-adr` の手順 |
| 8 | **一覧は既定の絞り込みと並び順を「毎朝どう使うか」で決める**。終わったものが先頭に来ないか、必ず確かめる | 一覧そのものが信用されない状態を作らない | `ui_design.md` の一覧規約 |
| 9 | **編集の導線は「今の内容が入った状態」で開く**。番号だけを引き継いで空のフォームを出さない | 打ち直しの過程で別の項目が変わる事故を防ぐ | `ui_design.md` の入力規約 |
| 10 | **利用者に判断させる表示は、利用者の言葉と時刻で出す**。列挙名・UTC・コードのまま出さない | 判断できない問いを投げない | `ui_design.md` の表示規約 |
| 11 | **マニュアルは「表に無いメッセージ」を実装から機械的に洗い出してから閉じる** | 読者が表から探せない状態を作らない | `creating-manual` の手順 |
| 12 | **レビューの指摘は裏を取ってから直す**。今回、高優先度 1 件は指摘のほうが誤りだった（値は境界で切られていた） | 直さなくてよいものを直して壊さない | IT4 の作業手順 |

### 残した負債

| # | 内容 | 返済の目安 |
| :--- | :--- | :--- |
| 1 | `MyBatisShipperRepository.save` が常に INSERT（しかも荷主コードを再採番する） | **荷主編集（[#550](https://github.com/k2works/case-study-cargo-tracker/issues/550)）に着手するとき。** IT3 で `Cargo` を直したのと同じ形 |
| 2 | `Schedule.callingOrderOf` が最初の出現位置しか返さず、往復航海で SQL と集約の答えが食い違う | **US08（経路候補算出）に着手するとき。** `connects()` を使うため |
| 3 | `Shipper.email` が `String` のまま（[ADR-012](../adr/012-value-object-granularity.md)） | 荷主編集のストーリーに着手するとき |
| 4 | 利用者と荷主の紐付け（[ADR-008](../adr/008-no-user-shipper-link-in-it2.md)） | US18（IT6） |
| 5 | 方言スモークが名簿方式のまま（handlingms・trackingms・billingms に無い） | IT4 で handlingms がクエリを書くとき |
| 6 | `AuthenticatedUserFilter` の登録検査がテキスト一致にとどまる（公開パスを広げても緑） | IT4 |
| 7 | 公開追跡経路（`/api/v1/public/tracking/*`）とポータルの追跡番号欄 | US18（IT6） |

> **落とした負債は育つ。** 1 と 2 は「着手条件が来た IT で必ず対象になる」ため、その IT の
> 見積もりに最初から入れる。5 は対象サービスが増えるほど後から足すコストが上がる。

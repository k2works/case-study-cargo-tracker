局面（開発戦略）: **中盤 = インサイドアウト**。序盤（IT1-2・アウトサイドイン）から移行し、データ→ドメイン→アプリ→プレゼンの順で Routing BC を作り込んだ。経路候補算出（US08）を中盤の主戦場としてドメイン層で厚くテストした。

## Keep（継続すること）

### 技術的成功

- **インサイドアウトへの局面移行が円滑に機能した**。全ストーリーでデータ層（マイグレーション）→ドメイン（値オブジェクト・集約・不変条件）→アプリ→プレゼンの順に作り込み、ドメインロジックをテストで固めてから外側へ展開できた。
- **経路候補算出（US08）を純粋ドメインサービスに凝集**。`RouteCandidateCalculator` を永続化・外部サービス非依存の純粋ロジックとし、寄港地接続評価・時刻接続・期限フィルタ・直行優先ソートを 8 ユニットテストで網羅。中盤の主戦場をドメイン層で堅牢化できた。
- **BC 独立原則を貫き ADR で明文化**。Routing の `CandidateRoute`/`IRouteCandidateService` を Estimation の `RouteCandidate`/`IExternalRoutingServicePort` と分離し、ADR-0007 で判断基準（再判断トリガー）を記録。ArchUnit で Routing の BC 独立（Booking/Estimation/Shipper 非依存）を継続検証。
- **確立パターンの再利用が加速した**。AmbientTransaction・version 楽観ロック（ドメイン先行）・ACL（SQL 直接参照）・二方言 SQL・post-commit イベントを Routing でそのまま再利用し、US25 更新・US07 検索を短時間で実装。
- **IT2 レビューの高優先負債を計画的に返済**。M1 の AmbientTransaction を ADR-0006 化＋ネスト非対応ガードでテスト固定、H3 過去日ガード、H4/T3 の CargoType を ADR-0007 化。設計ドキュメント（domain-model/data-model/ui_design）とコードの矛盾も Day1 タスク 1.0 で解消。

### プロセス的成功

- **計画着手前の 3 段階検証（validating-iteration-plan → validating-design → Day1 docs 反映）が有効**。voyage 物理定義の不足・経路サービスの BC 所属・楽観ロック方式の乖離を開発着手前に確定し、docs/design に反映してから実装した。
- **ストーリー単位のコミット規律**を維持し、各コミットで全テスト緑・警告 0 を担保。SQL 方言コンプライアンステスト（`RETURNING` 禁止）が Voyage リポジトリの方言混入を早期検出した。

## Problem（問題点）

- **Codex が利用上限に達し US08 以降はテックリードが直接実装**することになった。分業体制が途中で崩れ、実装負荷がテックリードに集中した。US08 の探索アルゴリズム・DI 配線・ビュー・テストを一手に実装したため、レビューの独立性（実装者≠レビュアー）が一部失われた。
- **外部経路サービスの WireMock.Net 契約固定が未実施**。実 HTTP の外部サービスが存在しないため、経路候補算出をローカル算出（`VoyageRouteCandidateService`）で代替した。計画の「WireMock.Net で契約固定」は実連携時に持ち越し。IT1 の StubExternalRoutingService と同方針だが、成功基準の一部が未達のまま。
- **T4（ドメイン層 85% カバレッジのハードゲート）が未設定**。coverlet 収集は CI・develop.js に組込済みだが、実測ベースラインを確定していないため、閾値ゲートを CI に追加すると検証不能なままパイプラインを壊すリスクがあり見送った。
- **H5（Playwright E2E 拡張）が IT4 繰り越し**。予約/航海フローは Web.Tests（WebApplicationFactory）で機能担保したが、E2E.Tests（Playwright）への追加は時間都合で繰り越した。
- **一覧サマリの表現とテストの粒度がずれた**（US25）。航海一覧の区間列を起点→終点サマリとしたため、中間港を期待した受入テストのアサートを調整した。表示設計とテスト期待の初期すり合わせが不足していた。

## Try（次に試すこと）

| # | 改善アクション | 責任者 | 期限 | 期待効果 |
|---|--------------|--------|------|---------|
| T1 | **Codex 利用上限を前提に作業を分割**する。上限到達時はテックリードが小さな単位で実装を継続し、後続イテレーションで Codex 復帰時に独立レビュー（developing-review）を必ず挟む | 開発チーム | IT4 | 実装者≠レビュアーの独立性回復・レビュー品質維持 |
| T2 | **US08 の経路候補算出を IT4 の developing-review で重点レビュー**する（テックリード自作のため）。探索アルゴリズムの網羅性・費用計算の妥当性・パフォーマンス（区間展開の計算量）を第三者視点で検証 | 開発チーム | IT4 着手時 | 自作ドメインロジックの盲点解消 |
| T3 | **T4 カバレッジハードゲートを実測ベースライン確定後に設定**。まず reportgenerator で現行カバレッジを可視化し、ドメイン層の実測値を確認してから 85% ゲートを CI に追加（壊さないよう段階導入） | 開発チーム | IT4 | 品質目標の定量ゲート化 |
| T4 | **H5 Playwright E2E を IT4 で拡張**（予約フロー・航海フロー・経路確定フロー）。IT4 の予約確定（US13）と合わせて業務シナリオ E2E を追加 | 開発チーム | IT4 | 主要業務フローの E2E 担保 |
| T5 | **外部経路サービスの契約方針を IT4 で判断**。実外部サービス連携の要否を確認し、必要なら WireMock.Net 契約テストを追加、不要ならローカル算出を正式方針として ADR 化 | 開発チーム | IT4 | 経路候補算出の外部依存方針の確定 |
| T6 | **一覧/画面の表示粒度を受入テスト設計時にすり合わせ**る。サマリ表示か詳細表示かを US の受入条件と対応付けてからテストを書く | 開発チーム | IT4 以降 常時 | 表示設計とテスト期待の初期不一致の防止 |

## ベロシティと計画への反映

- IT3 実績 **14 SP**（計画どおり）。IT1=13・IT2=10・IT3=14 で平均 **12.3 SP/IT**。3 イテレーション実績が揃い、想定（10-12 SP・実効）とほぼ整合。**計画（IT 割り当て・リリース日）は現状維持**とする。
- 残 SP: **48 SP**（Release 1.0 MVP まで IT4-5）。バーンダウンは計画線に追従。
- 次イテレーション（IT4）は**中盤・インサイドアウト継続**。経路選択・再算出・紐付け・通知・予約確定（US09-13）。Routing の CandidateRoute を Booking の CargoItinerary に紐付ける BC 連携が焦点。

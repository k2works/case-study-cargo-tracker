- 対象: IT4（2026-08-18 〜 08-29）／US09・US10・US11・US12・US13（12 SP）+ IT3 レビュー指摘（H2/M1/M2/M9）消化

局面（開発戦略）: **中盤 = インサイドアウト**（IT3-5）。データ層 → ドメイン層 → アプリ → プレゼンの順で US09-13 を作り込み、予約フロー全体（算出→選択→紐付け→通知→確定）を一気通貫で結合した。

## Keep（継続すること）

### 技術的成功

- **インサイドアウトの局面リズムを維持できた**。全ストーリーでドメイン（Cargo 集約の旅程割当・状態遷移、SelectedRoute、RouteNotification）→ 永続化（leg/selected_route/route_notification）→ アプリ（各 CommandService）→ プレゼン（経路設計画面・予約詳細のアクション）の順に作り込み、内側をテストで固めてから外側へ展開できた。
- **BC 独立を最後まで貫いた**。Routing↔Booking の連携をすべて ACL 経由（`ISelectedRouteLookup` で確定経路を Booking プリミティブとして受領、`RouteCargoCommand` は `RouteLegInput` で受ける）とし、Booking→Routing の型依存を作らなかった。ArchUnit（6 件）が終始グリーンで、CargoType/CandidateRoute（ADR-0007）に続く BC 独立パターンを踏襲できた。
- **状態遷移の設計乖離を実装着手前に確定した**。UC フローの「経路設計中/経路提案中」と domain-model のコマンド定義（`RouteCargoCommand`/`ConfirmBookingCommand` の遷移元）の内部矛盾を Day1 で解消し、US06 で既に `RouteProposed` に遷移済みという実コードの実態に合わせて「US11=旅程割当のみ・US13=Confirmed 遷移」に確定してから実装した。手戻りゼロ。
- **確立パターンの再利用が加速した**。AmbientTransaction・version 楽観ロック（ドメイン先行）・二方言 SQL・post-commit イベント・`ToDatabaseTimestamp`（UTC DateTime 永続化）を Booking/Routing でそのまま再利用し、5 ストーリーを短時間で実装できた。
- **IT3 レビューの UI 指摘を計画的に消化した**。H2（US09 導線）は機能実装で解消、M1（状態バッジ日本語化）・M2（費用単位/概算）・M9（航海更新の差分ハイライト）を UI 一括対応として返済。いずれも Web テストで検証した。

### プロセス的成功

- **計画着手前の 3 段階検証（validating-iteration-plan → validating-design → Day1 docs 反映）が再び有効だった**。状態遷移・コマンドの乖離、URL の ui_design 準拠、レビュー指摘の反映漏れを開発着手前に検知・修正できた。
- **ストーリー単位・層単位の小さなコミット規律**を維持し、各コミットで全テスト緑・警告 0 を担保。UTC オフセット問題（PostgreSQL `TIMESTAMP` への DateTimeOffset 書き込み）を統合テストが早期検出し、`ToDatabaseTimestamp` 方式に統一して解決できた。
- **Ralph Loop による反復消化**で、機能実装 → レビュー指摘返済 → 進捗反映まで小さな単位で着実に前進できた。

## Problem（問題点）

- **US10（経路条件調整）は計画の専用コマンド・永続化を作らず、検索フォーム再送＋算出ロジック再利用で実現した**。受入条件は満たすが、計画（`AdjustRouteConditionCommand`・調整条件の記録）と実装に差異が生じた。UC08 の「調整条件と再算出結果が記録される」を厳密には満たしておらず、記録要否の判断を計画段階で詰め切れていなかった。
- **ドメイン層カバレッジ 85% のハードゲートが未達（繰り越し）**。198 テスト全緑だが、reportgenerator による実測ベースライン確定と CI ゲート追加は未実施。IT3 から 2 イテレーション連続の繰り越しとなった。
- **SonarQube 指摘（SQ-1〜SQ-5）が未消化（繰り越し）**。SonarQube スキャン実行（`operating-qt`）が前提のため、Ralph Loop 内では着手できず繰り越した。UI レビュー系（M1/M2/M9）は消化したが、静的解析ベースの指摘は残った。
- **Playwright E2E が IT3 から連続繰り越し**。予約フロー全体は Web.Tests（WebApplicationFactory）で担保したが、E2E.Tests（Playwright）への移植は未実施。
- **経路候補の選択がインデックス依存**。候補は都度算出のため、選択 POST で同一条件を再算出しインデックスで確定対象を特定している。航海データが選択操作の合間に変わると別経路を確定するリスクがある（実運用では稀だが設計上の弱点）。

## ベロシティと計画への反映

- IT4 実績 **12 SP**（計画どおり）。IT1=13・IT2=10・IT3=14・IT4=12 で平均 **12.25 SP/IT**。4 イテレーション連続で計画=実績が一致し、想定（10-12 SP・実効）と整合。**計画（IT 割り当て・リリース日）は現状維持**とする。
- 残 SP: **36 SP**（Release 1.0 MVP まで IT5）。バーンダウンは計画線に追従。
- 次イテレーション（IT5）は**中盤・インサイドアウト継続**。追跡番号発行・荷役/引取記録・状態更新・追跡照会（US14-18）で Release 1.0（MVP）を出荷する。IT4 からの繰り越し（カバレッジゲート・SonarQube・Playwright E2E・外部経路サービス ADR）を IT5 の品質タスクとして先に消化する。

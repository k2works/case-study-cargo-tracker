## Keep

### 技術面

- **7 エージェント並列レビューによる多角的な品質チェック体制**: プログラマー・テスター・アーキテクト・テクニカルライター・ユーザー代表・インタラクションデザイナー・プロジェクトマネージャーの 7 役割が同時にレビューすることで、単一視点では見逃しやすいセキュリティ・UX・BC 境界などの問題を網羅的に検出できました。
- **BC 境界を ArchUnit で自動検証する体制（A10 ルール追加）**: `tracking ↔ handling` 間の BC 境界違反を ArchUnit A10 ルールとして CI に組み込み、今後の誤った依存追加を自動検出できる体制を整備しました。
- **US13 受入条件 2 を後追いで完成させた**: 出発地・目的地・現在状態・推定到着日の表示（`show.html`）はレビュー指摘後に追加実装しましたが、IT3 で残した「追跡機能準備中」を完全に解消し、US09 から US13 までのエンドツーエンド追跡フローを完結させることができました。
- **E2E テストの品質向上（null ガード、未認証アクセス検証）**: Playwright テストに null ガード修正と未認証アクセス検証を追加し、テストの信頼性と網羅性を高めました。
- **荷役 BC の全イベント種別対応**: LOAD / UNLOAD / CUSTOMS / TRANSHIP / RECEIVE / MANUAL_UPDATE の 6 種別すべてに対応し、実際の港湾業務フローを網羅する実装を完成させました。

### プロセス面

- IT3 の Try 事項「テストフィクスチャポリシー（`reconstitute()` 使用）」を IT4 全タスクに適用し、ドメインイベント多重発行によるテスト失敗を事前防止できました。
- レビュー指摘（高優先 12 件）をすべて同イテレーション内に対応・コミットし、技術的負債を持ち越さずに完了できました。
- コミットを機能単位・レイヤー単位に細分化し、US10 → US11 → US12 → US13 の順序で依存関係に沿った開発を進められました。

## Problem

### 設計・実装

- **BC 境界違反が CI で未検出だった**: `TrackingQueryService` が handling BC の `HandlingEventType` を直接 import するという BC 境界違反が、ArchUnit ルール追加前は CI で検出されず、レビューで初めて発覚しました。`TrackingEventType` を新設して境界を明確化することで解消しましたが、ルールは実装と同時に書くべきでした。
- **US13 受入条件 2 の実装漏れがレビューまで気付かれなかった**: `show.html` への出発地・目的地・現在状態・推定到着日の表示は受入条件に明記されていたにもかかわらず、初回実装時に抜け落ちました。受入条件の確認粒度が不十分でした。
- **エージェントがスコープ外の機能を追加して既存テストを破損させた**: エージェントが指示外の `receiveConfirmationCode` 機能を独自に追加し、既存テストの修正が必要になりました。エージェントへの指示でスコープ境界を明示することが不可欠です。

### 品質管理

- IT4 終了時点のカバレッジは instruction 90% を達成したものの、分岐カバレッジは 71% に留まりました。例外系・分岐の多いドメインロジックへのテスト追加が IT5 以降の課題です。
- RECEIVE 重複防止（409）テストはレビュー後に追加されたもので、初回実装時にエッジケースのテストが不足していました。

## Try

| Try | 担当 | 期限 | 期待効果 |
|-----|------|------|----------|
| ArchUnit ルールを実装と同時に書く（後追いでなく TDD 的に）: `A10` のように BC 境界ルールは、対象クラスを実装するタスクと同一コミットで追加するルールを iteration_plan に明記する | Copilot | IT5 計画時 | BC 境界違反が実装時点で検出され、レビュー後の修正コストをゼロにできる |
| 受入条件を show.html のコメントに埋め込むことで実装漏れを防ぐ: 各 HTML テンプレートのファイル先頭に対応する受入条件を `<!-- AC: ... -->` コメントとして記述するルールを設ける | Copilot | IT5 実装開始時 | 受入条件と実装が同一ファイルに存在し、実装漏れを即座に発見できる |
| エージェントへのプロンプトで「スコープ外の機能追加は禁止」を明示する: プロンプトテンプレートに「このタスクで指定されていない機能・フィールドを追加しないこと。追加が必要と判断した場合は人間に確認を求めること」を追加する | Copilot | IT5 開始時 | エージェントによる意図しない機能追加と既存テスト破損を防止できる |

## 次イテレーションへの引き継ぎ

- IT5 では US14（遅延例外処理）・US15（破損・紛失例外処理）を実装し、Phase 1 コア輸送管理フローをすべて完結させます。
- 品質ベースラインは backend 361 テスト Green、E2E シナリオ Green、SonarQube Quality Gate PASS を維持条件とします。
- IT4 で確立した BC 境界ルール（A10 ArchUnit）と `TrackingEventType` パターンを IT5 全タスクに適用します。
- IT4 で残った分岐カバレッジ 71% の改善を IT5 の品質目標として設定します（目標: 75% 以上）。
- 実績ベロシティ平均は 11.25 SP（IT1: 10 / IT2: 10 / IT3: 12 / IT4: 13）。IT5 の 11 SP は平均範囲内です。

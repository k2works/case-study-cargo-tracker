書いていた。いずれも読めば守っている気になる状態だった。

## 技術的成果

### Booking Context の確立

- `Cargo` 集約（`book` / `cancel` / `canCancel`）。Setter を持たず、状態は保存値をそのまま復元する
- `BookingStatus`：**遷移表の全 64 セル（8 状態 × 8 コマンド）を網羅**。許可セルのみ列挙し
  拒否側を自動生成するため、状態やコマンドが増えても書き忘れない
- `CargoSpecification` を導入（設計図には無い）。種別・重量・寸法・個数・品名は画面でも
  1 つの入力ブロックとして現れる

### BC 間の境界

`ShipperExistenceChecker` ACL ポートを Booking 側に定義し、実装を Shipper 側に置いた。
ArchUnit ルール 4 は **ACL ポートのパッケージだけ**を越境の許可地点として除外している
（BC 単位で緩めると ACL を通す動機が消えるため）。

### CQRS のクエリ側（Try T6）

ArchUnit ルール「画面層はリポジトリを直接参照しない」を**先に置いて赤を確認してから**実装した。
一覧は JOIN 済みの 1 クエリで取り、予約ごとに荷主を引き直さない。
状態の表示名とキャンセル可否は SQL ではなく `BookingStatus` から導く。

### スキーマ

| バージョン | 内容 |
| :--- | :--- |
| `common/V3` | `cargo` に寸法・個数・品名を追加。**V1 で作られておらず、`data-model.md` には記載があったため誤認しやすい状態だった** |
| `common/V4` | 荷主コードの採番シーケンス（IT1 持ち越し C5） |
| `postgresql/V102` | シーケンスの既存データ整合。**`setval` は H2 に無く、common に置くとローカル起動が落ちる** |

## 課題と残作業

### 今回の地ならし（計画外の作業。Try T5）

| 内容 | 理由 |
| :--- | :--- |
| `setval` の H2 非対応によるマイグレーション分割 | 実 DB のテストは全緑で、ローカル起動でしか露見しなかった |
| テストデータの採番をシーケンスに揃える | 自前採番が本番経路と衝突し、原因でない他テストが落ちた |
| SonarQube の前処理（`sonarLibs` / `jacocoTestReport`）を設定に組み込み | 手順書の記述では忘れられ、スキャンが落ちた |
| ReDoS 修正が生んだ 2 種の指摘への追随 | 1 回のスキャンでは終わらない |
| `Shipper` の引数数超過に伴う `ShipperContact` の抽出 | Checkstyle が設計の匂いとして検出した |

# イテレーション 8 完了報告書

作成日: 2026-08-04

## エグゼクティブサマリー

IT8 は **計画 11 SP を全消化し、縮退 0 件**で完了した（IT5 から 4 イテレーション連続）。

3 つのストーリーはいずれも性格が異なる。

- **TS14（5 SP）** — レビューの返済。合成ルートを BC 別に畳み、予約一覧に絞り込みを入れ、
  IT6・IT7 の未返済 12 件を返した
- **US01（5 SP）** — 新規 BC（Estimation）。輸送見積を作成し、経路候補ごとに
  運賃と所要日数を出せるようにした
- **TS12b（1 SP）** — 負荷試験。**測ったうえで、検討していた対策を 2 つとも入れないと決めた**

本 IT の性格を一言で言えば「**書いたことを自分で使えたか**」である。
ADR-0010 は「合成ルートに置くと `arch-lint` が検出できない」というリスクを自分で書きながら、
**そこから導かれる手当て（テストを義務づける）をせず、書いた当日にそのリスクを踏んだ**。
IT8 計画は着手前に「未知の状態語は 0 件」と決めながら、**実装時にその表を読まず逆に実装した**。
いずれもクローズ時のレビューで検出し、対応した。

## 技術的成果

### 1. 合成ルートを BC 別に畳んだ（TS14-1）

IT7 レビュー M11 の返済。`Composition.flix` は 560 → 486 行になった。

**触る箇所の数（4）は減らせない**。効果は静的な型であり、ハンドラのリストを
畳み込むことはできない。減らせたのは**1 箇所あたりの分量**である。

| | IT7 まで | IT8 以降 |
| :--- | :--- | :--- |
| `AppEff` | 13 効果を 1 行に列挙 | BC 別名を 5 つ |
| `touchAll` | 13 行の `discard` | BC ごとに 1 行 |
| `runWithoutDb` | BC ごとに 5-7 行の `bug!` ハンドラ | BC ごとに 1 行 |

効果は Estimation の追加で実測できた。**新規 BC の配線で `Composition.flix` に
加えた変更は 25 行**であり、うち翻訳ロジックは 1 行も無い（BC の配線ファイルに閉じた）。

### 2. Estimation Context（US01）

| 要素 | 内容 |
| :--- | :--- |
| 集約 | `Estimate`（`EST-XXXXXXXX`・候補は値オブジェクト） |
| ポート | `EstimateRepo`（永続化）・`RouteSearch`（ACL） |
| 永続化 | V9（`estimate` / `route_candidate`。着手前に V1-V8 への不在を確認） |

**経路探索は Routing の `RouteFinder` を再利用する**（ADR-0010）。
再実装すると **見積で出した候補と経路割り当てで出る候補が食い違う**——
営業が「3 日で着きます」と答えた後、経路設計者の画面には該当する便が無い。
どちらの画面も単体では正しく動くため気付けない。

### 3. 共有カーネルの追加 3 件

| モジュール | 理由 |
| :--- | :--- |
| `Money` | 銭（1/100 円）の整数。DB の `NUMERIC(12,2)` と往復して値が変わらない（ADR-0006） |
| `FreightTariff` | **運賃表は全社で 1 つ**。見積と経路割り当てで違う金額を見せることはあり得ない |
| `Sql` | `escapeLike` が 3 箇所に複製されていた（IT6 レビュー M6）。**どの複製にもテストが無かったから 3 つに増えた** |

`FreightTariff` は当初 Estimation に置いた。US08 の費用列を実装する段で
Routing からも要ることが分かり、**合成ルートに 2 件目の翻訳を足す案を却下して**
共有カーネルへ移した（ADR-0010 自身が「2 件目なら置き場所を見直す」と書いている）。

### 4. 負荷試験と、そこから導いた「入れない」判断

| 目標（非機能要件 2.2） | 実測 |
| :--- | :--- |
| 平常時 50 RPS | 達成（同時実行 50 で 1,915 RPS・p95 48ms） |
| ピーク 200 RPS | 達成（同時実行 200 で 1,468 RPS・p95 394ms） |
| 追跡 API 1,000 RPS | 達成（最大 **2,306 RPS**・同時実行 100） |

**この数値を本番の見込みとして扱わない**。負荷生成とアプリが同一マシンで
CPU を奪い合い、DB は H2 のファイルで PostgreSQL のネットワーク往復が無い。

既定の同時実行 200 で `503` が 1 件も出なかったため、上限を 5 に落として再測定した。
4,000 件の一斉送信で 2,285 件の `503` を観測し、**防御は正しく働いていて
枠に達していないだけ**だと確認した（Try T6 の適用）。

その結果、検討していた対策を**2 つとも入れないと決めた**。

- 追跡 API のキャッシュ — 目標の 2.3 倍が出ている段階で足すのは、測って要らないと分かったものを足すこと
- タイムアウト時の枠返却を遅らせる案 — `504` を起こす条件自体が作れず、**測っていない問題を防ぐために測って分かっている可用性を犠牲にする**取引になる

いずれも再検討の条件を `architecture_backend.md` に明記した。

## レビュー結果

5 視点の並列レビューで **高 12 件・中 9 件・低 8 件**。高は全件対応した。

### 実バグ 2 件

| # | 内容 | 影響 |
| :--: | :--- | :--- |
| 1 | 重量表記が小数位を取り違える（`1050 g` → `1.50 kg`。実際は 1.05） | 荷主に 45% 重い値が伝わる。見積の重量が違えば運賃も違う |

| # | 内容 | 対応 |
| :--: | :--- | :--- |
| 1 | 受入基準 3 の検証が `contains("円")` で、運賃が 0 円でも緑 | 実額（194,000 円）・実日数（15 日）で突合 |

## 限界と課題

### 意図的に受け入れた限界

| # | 限界 | 理由 |
| :--: | :--- | :--- |
| 1 | **合成ルートに置いた翻訳を `arch-lint` が検出できない** | 代替（探索の再実装）は見積と経路割り当てで候補が食い違う欠陥を生む。穴に名前を付けて `arch_lint_rules.md` に記録し、固定するテストを対応付けた |
| 2 | 負荷試験の数値は**サーバ能力の下限**しか言えていない | 負荷生成が単一プロセスで飽和している可能性がある。複数プロセス化は IT9 |
| 3 | 同時実行の上限 200 は追跡 API では到達しない | **枠は最も重い経路のために存在する**。軽い経路の実測だけを根拠に下げない |

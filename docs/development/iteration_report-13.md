## エグゼクティブサマリー

**荷主が、自分で自社の貨物を見られるようになった。** [ADR-024](../adr/024-tracking-manual-update-and-exceptions.md) で
公開追跡を認証不要にしたとき、残っていたのは「**荷主が自社の貨物を横断して見る手段が無い**」ことだった。
追跡番号を 1 件ずつ控える運用は、貨物が増えるほど控え漏れを生む。IT13 で、
`ROLE_SHIPPER` の担当者はログインするだけで自社の貨物が並ぶ画面を持つ。

**境界は「見せない」ではなく「存在を知らせない」で引いた。** 他社の貨物は一覧に出ないだけでなく、
**追跡番号を知っていても荷主向け詳細では 404** になる。403 にすれば「その番号は在る」と教えることになる。
公開追跡（`/tracking/:trackingNumber`）とは URL・API・認可をすべて分けた（[ADR-029](../adr/029-shipper-tracking-boundary-and-inactivity-timeout.md) 決定 C）。

**紐付けは authms に置き、bookingms へ利用者 ID を混ぜなかった。** `user_shipper_link` は
authms が持ち、trackingms は authms（紐付け）と bookingms（`CargoSnapshot`）の
**2 本の ACL** を通して自社判定する。サービス境界に DB の外部キーを張らずに済んだ。

**9 イテレーション棚上げだった TD-01 を消化した。** IT2 のふりかえりで起票して以来、
どのイテレーションにも属していなかった無操作タイムアウトを、**15 分警告・20 分ログアウト**として
ADR で固定した。「余力次第」に置いたものは固定化する——居場所を決めて閉じた。

**これで計画した 13 イテレーションがすべて終わった。** 33 US・110 SP に
バッファの TD-01 2 SP を加えた 112 SP を、13 イテレーションで消化した（**平均 8.6 SP**）。

### 果たせなかったこと

#### 1. 自社貨物の判定が「直近 100 件」の中でしか働かない

`findRecent(100)` で取ってから所有判定しているため、**自社の貨物が直近 100 件から落ちると
荷主の一覧から消える**。IT13 の業務量では起きないが、**いつ壊れるかは件数だけで決まる**。
Read Model へ `shipperId` を取り込む形が正解であり、Release 2.2 の候補に送った
（[レビュー](../review/イテレーション13_review_20260828.md) 中 6）。

#### 2. 1 荷主に複数の担当者を置けない

`user_shipper_link.shipper_id` を UNIQUE にしたため、**1 荷主 1 利用者**である。
法人荷主では複数担当者が普通に起きる。IT13 は最小スコープとして意図的に選んだが、
**受入基準としては切り出していない**。Release 2.2 の候補に送った（同 中 7）。

#### 3. SonarQube の Backend ゲートが、クローズ作業中に ERROR へ戻っていた

**クローズ作業での再スキャンで、Quality Gate が ERROR に戻っていた。**
IT13 の品質ゲートを記録した 2026-08-28 の後に入れた**パッケージ構成リファクタ 3 件**が、
新規違反 14 件と Security Hotspot 1 件を持ち込んでいた。

- **違反 14 件は直した**（コミット `667516f5`）。Backend / Frontend とも `new_violations` は 0 になった
- **Security Hotspot 1 件は、利用者が UI で承認して PASS になった。** 走査トークンでは
  `api/hotspots/search` も `api/issues/do_transition` も `Insufficient privileges` を返し、
  **列挙も承認もできなかった**。**承認できるのは利用者だけ**という形が残っている

> **これは IT5・IT6・IT12 と同じ形で、4 度目である。** 本 IT でしたのは
> ゲート条件を `new_security_hotspots_reviewed=100.0` の自動判定に固定すると**決めた**ことだけで、
> **走査トークンの権限は解いていない**。決めただけでは同じ待ちがまた起きることを、
> クローズ当日に自分で実演した。

#### 4. 請求書検索は入れなかった（3 IT 連続の指摘）

経理担当者から IT11・IT12 と 2 度指摘され、本 IT でも Day 2 に判断して**送った**。
7 SP を US33 / TD-01 で使い切っており、触る画面もサービスも異なる。
Release 2.2 候補バックログの先頭に置いてある。**送るのは 3 度目である。**

### 主な設計判断（ADR-029）

- **紐付けは authms に持つ**（決定 A）。bookingms の `shipper` に authms の利用者 ID を混ぜない。
  混ぜた瞬間、認証の都合が予約のスキーマに漏れる
- **荷主向け Read API は trackingms が返す**（決定 B）。自社判定に要る荷主 ID は bookingms の
  `CargoSnapshot` を ACL で参照する
- **公開追跡と URL を分ける**（決定 C）。公開は「追跡番号を知る人向け」、荷主向けは「自社境界を守る画面」で、
  守るものが違う以上、同じ経路に載せない
- **未紐付けは 403 ではなく `200 + linked=false`**（決定 D）。認証は通っており、
  欠けているのは業務上の紐付けである。403 では利用者が何をすればいいか分からない
- **15 分警告・20 分ログアウト**（決定 E）。荷役・通関のような**作業中に切れると危険な画面**があるため、
  予告なしには落とさない

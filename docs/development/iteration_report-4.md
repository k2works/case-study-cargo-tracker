# イテレーション 4 完了報告書

対象: US08（経路候補算出）= 8 SP
期間: 2026-08-21（IT4）
局面: 中盤（インサイドアウト）の 2 本目。本システムで最も複雑なドメイン（グラフ探索 + 制約充足）を作るイテレーション。

## エグゼクティブサマリー

経路設計者が、引き渡された予約に対して**期限内に着く経路の候補を推奨順で受け取れる**ようになりました。
直行便が最優先で並び、候補ごとに航海番号・経由港・輸送日数・費用の概算が出ます。候補が無いときは
何で絞ったかを示し、条件を緩める操作へ繋ぎます。**選択・確定は US09（IT5）**であり、IT4 では
往復が閉じません（計画どおり）。

計画 8 SP を全量完了し、IT3 から持ち越した返済枠 8 件もすべて片付けました。設計ドキュメントの
欠落 16 件は着手前の検証で洗い出し、すべて同じイテレーションのうちに反映しています。

一方で、**クローズのレビューで全緑のまま通っていた欠陥が 6 件**見つかりました。IT3 の教訓
（安全装置は破るテストで固定する）を DoD に入れて臨みましたが、テスターが変異テストで実測すると
**4 つの安全装置が壊しても赤になりません**でした。

| 欠陥 | 見つかった場面 | 覆い隠したもの |
| :--- | :--- | :--- |
| すでに出港した便が候補の上位に出る | クローズのレビュー | そもそも実装されていなかった |
| 同じ航海が「直行」と「1 回積み替え」の 2 候補になる | クローズのレビュー | 出発も到着も船も同じ 2 行を、誰も比べていなかった |
| 積み替えの最低 6 時間が探索側で無防備 | クローズのレビュー（変異テスト） | 値オブジェクト側の検査が二重に見えた |
| 積み替え上限の 2 つのガードが互いを隠す | クローズのレビュー（変異テスト） | 片方が生きていれば結果が変わらない |
| 認可より先に型変換が走る | クローズのレビュー → 実バックエンドで裏取り | MockMvc では再現しない |
| ADR に存在しない決定をコードが引用 | クローズのレビュー | 決定の数だけ検査を、の逆向きを見ていなかった |

高優先度 14 件はすべて IT4 のうちに対応し、**壊すと赤になることを実測で確認**しています。

## 技術的成果

### 経路探索のドメイン

`TransitEdge`（経路区間）・`TransitPath`（経路候補）・`RouteSearchSpecification`（経路探索条件）・
`TransitPathFinder`（経路候補算出）・`RouteRecommendation`（推奨順と費用）を routingms に置きました。
いずれも Booking Context の類似型とは**別の型**で、変換は US09 の ACL で行います。

`RouteSpecification` は Booking Context に同名で存在するため、**着手前に改名を決めました**
（Routing 側は `RouteSearchSpecification`）。IT5 の ACL で変換の両端が同じ名前になる事故を避けています。

### 決めた業務判断（ADR 3 本）

| ADR | 決定数 | 内容 |
| :--- | :--- | :--- |
| [ADR-016](../adr/016-authorize-before-validate.md) | 2 | 入力の検査は認可のあとに、メソッド本体で行う |
| [ADR-017](../adr/017-route-candidates-api.md) | 3 | 複数候補を推奨順で返す・永続化しない・期限は日付で受ける |
| [ADR-018](../adr/018-route-search-rules.md) | 5 | 推奨順・費用の概算・港湾制約を持たない・積み替えの上限・積み替えの最低時間 |

**決定の数だけ検査を用意しました。** 否定の決定（港湾制約を持たない・候補を永続化しない）も、
許可リスト方式で「足したこと」を検出する形にしています。ADR-018 は当初「否定の決定であり
検査に落とせない」と書いていましたが、**誤りだったので撤回し、その経緯ごと ADR に残しました**。

### 実バックエンドでのみ再現する欠陥への対処

認可より先に型変換が走る欠陥は MockMvc では再現しません。パラメータを `String` で受けて
メソッド本体で変換する形に直し、**回帰は見つかった場所（kind 統合環境に対する検査）に置きました**。

## US10 のバッファ判断

[リリース計画](release_plan.md)が「US10（経路条件調整）の代替手段が画面上に実在するかを IT4 で確認する」と
定めていました。**実在することを確認しました。**

経路設計画面で到着期限と積み替えの上限を変えるとその場で算出し直します。候補が 0 件のときは
「到着期限を 1 週間延ばす」「積み替えを 3 回まで許す」の操作を出します。したがって
**バッファの順位は据え置きます**。ただし US10 の本体は「調整した条件を保存して再算出を繰り返す」ことで
あり、IT4 が用意したのは 1 回かぎりの手動調整です。

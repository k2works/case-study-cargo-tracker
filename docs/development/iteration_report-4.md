# イテレーション 4 完了報告書

## エグゼクティブサマリー

イテレーション 4 は **14 SP 中 12 SP を完了**（達成率 86%）し、ゴールである
「Shipper・Booking の 2 コンテキストを立ち上げ、書き込み経路を初めて通す」と
「ルーティング表の負債を BC が増える前に返済する」を達成した。

技術的な中心は **TS08（ルーティング表の単一化）**である。IT3 で効果集合ごとに 4 分割していた表は
「ルート表が認可の唯一の正典」という設計そのものを壊しており、BC が 2 つ増える本イテレーションが
最後の安価な返済機会だった。Flix の「効果は構文上使われていれば宣言でき、実行される必要はない」という
性質を用いて単一表へ戻し、判断を [ADR-0005](../adr/ADR-0005-single-routing-table.md) に記録した。

一方で、マルチパースペクティブレビューにより**テストが全緑のまま存在していた欠陥が 6 件**見つかった。
うち 3 件は「利用者に応答が返らない」種類である。**IT3 のふりかえり P1 と同じ問題が形を変えて再発**しており、
これが本イテレーション最大の学びとなった（[ふりかえり](retrospective-4.md) P1）。

また利用者代表のレビューで、**受入基準の文言は満たすが業務では使えない**箇所が複数指摘された。
US02・US04 の受入基準を「部分充足」として正直に記録し、IT5 へ引き継ぐ。

## 3. 技術的成果

### 3.1 ルーティング表の単一化（TS08）

IT3 の 4 分割表が抱えていた問題と、その解消。

| 問題 | 解消 |
| :--- | :--- |
| 同一パスが 2 表にあると先勝ちで片方の認可が静かに消える | 単一表 + `duplicateKeys` による検出（起動時とテスト） |
| パス一致・メソッド不一致で 404 を返す | `Resolution` を `Found` / `MethodMismatch` / `NotFound` に分け 405 を返す |
| ネストが線形に深くなる | ディスパッチの入れ子が消えた |
| 全リクエストを書き込みトランザクションで包む | ルート定義に `TxMode` を持たせ、読み取り専用でコミットしない |
| ルート定義と設計の可否表を突き合わせるテストがない | `AppRoutesTest.testRouteRolesMatchDesignTable` で機械照合 |

**採用した仕組み**: 実行されない枝（`touchAll(false)`）で全効果に構文上触れ、
表へ載せる時点で `lift` により効果集合を揃える。ポートに no-op 操作を足す案は、
成立するにもかかわらず**ドメインにランタイムの都合が漏れる**ため採らなかった。
言語の制約による税は避けられないが、**税の所在は選べる**。

### 3.2 新設したコンテキスト

| コンテキスト | 集約 | ポート | 実装 |
| :--- | :--- | :--- | :--- |
| Shipper | `Shipper` | `ShipperRepo` | `JdbcShipperRepo` |
| Booking | `Cargo` | `CargoRepo`・`ShipperExistenceChecker`（ACL） | `JdbcCargoRepo`・`JdbcShipperExistence` |

**BC 独立性**: Booking の domain は Shipper の domain を参照しない。ACL の実装は
インフラ層に置き、`shipper` テーブルを SQL 1 文で引く。コンテキスト間の結合を
そこに閉じ込めることで、ドメイン層とアプリケーション層は相手のモデルを知らずに済む。

## 6. 課題と残作業

### 6.1 未解決（最優先で追跡）

**公開追跡の間欠 403**。IT4 の実装中に 1 度だけ観測し、以後再現していない。

アーキテクトの分析により、403 の生成箇所は本番コード中に 1 つしかなく、
`Anonymous` の GET では**両分岐とも到達不能**であることが確認された。
したがって認可の誤りではありえず、**応答の取り違え**が疑われる。
サーバは仮想スレッドで並行処理しており、これが並行時の応答交差なら
**認証済み画面が別利用者へ返る可能性を含む重大欠陥**である。

IT4 では並行スモークテスト（50 本同時）を 2 件追加した。再現していない。
IT5 で認証あり・なしの混在版を追加し、原因に到達する（Try T7）。
**再現しないことを理由にクローズしない。**

### 6.2 意図的に残した負債

| 項目 | 理由 | 返済時期 |
| :--- | :--- | :--- |
| 荷主コードの衝突（約 77,000 件で 5 割） | 件数が桁違いに増えるまで実害がなく、再試行は生成責務の移動という設計変更を伴う | 荷主が数万件規模になる見込みが立った時点で ADR |
| `runWithoutDb` の 8 段ネスト・20 スタブ | IT4 クローズ直前の構造変更は危険 | IT5 で ADR-0005 の補遺として判断 |
| 統合テストの接続先切り替え | 日次ジョブが検出できるのはスキーマの方言差まで | IT5 |
| `afterCommit` が例外時に失われる | IT8 でイベント基盤を構築する前に記録が必要 | IT5 で記録 |

### 6.3 IT5 への繰越

[ふりかえり](retrospective-4.md) の「持ち越しタスク」に 21 項目を記載した。とくに重いものは次の 4 つ。

## 8. 総括

IT4 は**構造的負債の返済と 2 コンテキストの立ち上げを同時に行い、いずれも達成した**。
とくに TS08 は、IT3 のふりかえりで「BC が 8 個になる IT4 以降では持たない」と判断した負債を、
BC が 2 つ増える直前に返済できた。**返済の時機を計画で押さえたことが効いている**。

一方で、レビューが見つけた 6 件の「緑のまま存在していた欠陥」は、IT3 と同じ問題の再発である。
Try T2（受入基準に壊れ方を書く）は実行し、書いた壊れ方はすべて守られていた。
**書かなかった壊れ方が全部残った**という結果は、Try が「書く」ことしか求めておらず
「洗い出す方法」を与えていなかったことを示している。IT5 の Try T1 で観点表を作る。

もう一つの学びは「動く」と「使える」の区別である。受入テストが通る実装が、
利用者代表の目には「Excel の台帳を横に置く運用になる」と映った。
受入基準の文言を満たすことと、業務で使えることは別である。

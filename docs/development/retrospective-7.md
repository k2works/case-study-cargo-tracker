## Keep（続けること）

### K1. Try を「着手前」と「DoD」に置いたことが実装に効いた

IT6 のふりかえりは「**IT6 でその学びはレビュー依頼には適用できたが、実装には適用できなかった**」
という反省で終わっていた。そこで T1-T8 をすべてタスク 0（着手前）または実装タスクの DoD に置いた。

結果として、**レビューより前に自分で捕まえたものが 3 件**ある。

| # | 捕まえたもの | どの Try か |
| :--: | :--- | :--- |
| 1 | 引き継ぎ M2（管理者ロールが全業務画面で 403）が**誤指摘**だった | T8（設計にあるものを実物で確認する）の鏡像 |
| 2 | `route_candidate` の親が `estimate` であり本 IT の対象外だった | T8 |
| 3 | ACL の `capabilityOf` が未知の種別を `General` へ倒しかけた | IT6 の温度単位の判断を写した |

1 は特に大きい。**そのまま計画に載せていれば、存在しない欠陥に 1 SP と ADR 1 本を使っていた。**
レビューの指摘であっても実物で確かめる、という規律が働いた。

### K2. 「破ろうとするテスト」が実際に設計を変えさせた

`RuntimeGuardTest` は上限を 1 に落として同時到達させ、**503 の後に後続が成功する**ところまで見る。
この形にしたことで、レビューで 2 つの穴が具体的に指摘できた（`submit` が `try` の外・
タイムアウト時の過剰入場）。「入れたこと」しか見ないテストなら、どちらも緑のまま残った。

対称のテスト（`testAllowsRequestsBelowLimit` / `testFastRequestIsNotTimedOut`）を
意図的に添えたのも効いた。**「503 が出ること」だけを求めるテストは、常に 503 の実装でも緑になる。**

### K3. 導線の欠落を機械検査へ落とした

IT4・IT6 と 2 回再発した「画面単体は正しいがロールをまたぐと切れる」に対し、
`NavigationReachabilityTest` で `navItems` とルーティング表を双方向に突合した。

`Implemented` → ルートがある、`Planned` → ルートがない、の**両方向**を見るのが要点である。
片方向だと「実装したのに準備中のまま」を見逃す。

### K4. 未実装を「消す」でも「リンクのまま」でもない第三の解を採れた

navbar の行き止まり 5 件に対し、**消すと荷受人・荷役作業員・経理の項目が全滅**し、
**残すと押して 404** になる。実装状態を属性として持たせ「準備中」として押せなくすることで、
どちらの弊害も避けた。利用者代表から「押せて 404 になるより、見えて押せない方が業務上ずっとよい」
という評価が得られた。

## Problem（問題だったこと）

### P1. 【最重要】防御を足したことが、新しい単一障害点を作っていた

同時実行の枠を**全リクエストに適用**した。`/health/live` も例外ではなかった。

過負荷で liveness が `503` を返すと、オーケストレータは「混んでいるだけで生きている」
インスタンスを**再起動する**。負荷が高いときにインスタンスが落ちるため、事態は必ず悪化する。

**IT3 で全く同じことを学んでいる。** 「`/health/live` が DB を見ると DB 障害時に
再起動ループになる」（レビュー H4）。そのとき `TxMode.NoTx` という仕組みで防いだ。
今回は DB ではなく**セマフォ経由で同じ障害が再現した**。

`Server.handleDynamic` には「liveness が DB を見ると再起動を繰り返す」というコメントが
実際に書かれている。**教訓は文書にもコードにも残っていたのに、新しい防御を書くときに参照しなかった。**

> 防御を足すときは「この防御が働いたとき、**誰が困るか**」を経路ごとに数えるべきだった。
> 全経路に一律に適用したのは、**適用漏れを防ぐ**という正しい動機からだったが、
> 一律であること自体がリスクだという視点が抜けていた。

### P2. 最も重い設計判断を ADR にしなかった

IT7 は ACL の方向を反転させた（Booking → Routing から Routing → Booking へ）。
`domain-model.md` のイベントフロー図は反転前の形を正典としており、
**実装と正典が逆を向いた状態**が生まれた。

判断の理由はモジュールコメントに良質な形で書いてある。だから「書いてある」つもりでいた。
しかし**コメントはコードと一緒に消える**。ADR は決定が生き残るための形式である。

より実害があるのは、US09（経路の確定）の設計を直接ブロックしていた点である。
「確定して `CONFIRMED` へ遷移させる」のがどちらの BC の責務か、**2 通りに読めた**。
書き込みの越境を許すと、ここまでの BC 独立性の投資が一気に無駄になる。

### P3. 新しく作った共有カーネルにテストを 1 件も書かなかった

`SharedCalendarText` に `dateOf` / `toEpochDay` / `daysBetween` を足した。
`toEpochDay` は Hinnant の `days_from_civil` を手写ししたもので、整数除算と
100 年・400 年ルールを含む**自明でない式**である。`dateOf` は
**期限当日問題の根治点そのもの**である。

にもかかわらず、これらに触れる唯一のアサートは `testTransitDaysSpanTheWholeJourney` の
`expected = 11` **一点**だった。しかも 4/2 → 4/13 は月をまたがない。
つまり「**文字列の引き算では月をまたげない**」という、この関数を作った理由そのものが未検証だった。

「暦法を 1 箇所に閉じた」判断は正しい。**その 1 箇所を固定しなかった**のが問題である。

### P4. 業務の前提を確かめずに「候補」を作った

候補一覧に**出発日の絞り込みが無く、既に出港した便が並びうる**状態だった。

`connects` は先頭区間で無条件に真、`arrivesBy` は期限側しか見ない。
到着期限が先であれば、先月出港した便でも「利用可能な航路」として出る。

利用者代表の評価は厳しい。**「過去の便が 1 本でも並んだ瞬間、この一覧全体が
『信用できない参考情報』に格下げされ、結局これまでどおり船社サイトと表計算を開くことになる」**。

受入基準には書かれていなかった。しかし**受入基準に書かれていないことが「不要」を意味しない**。
「経路設計者は毎朝どう使うか」を一度も想像しなかったのが原因である。
同じ理由で船名も出していなかった（US07 受入基準 4 には明記されていた）。

### P5. 計画書に実績を書き足し続けた

`iteration_plan-7.md` に実績表・計画になかった対応・デモ結果・ロール × 画面の表を
追記したが、更新履歴は「初版作成」の 1 行のままだった。
読み手は「計画時点の判断」と「実施後の結果」を区別できない。

IT6 でも「更新履歴が時系列になっていない」と指摘されている。**形を変えた再発である。**

### P6. テストクライアントの取りこぼしが「送っていない」と見分けられなかった

`RuntimeGuardTest` が「503 に `Retry-After` が付いていない」と落ちた。
調べると**サーバは送っていた**。テストクライアントが 4 種のヘッダしか写し取っていなかった。

収集を列挙にしているのは「使わない値を運ぶ意味がない」という正しい理由からだが、
**列挙から漏れたヘッダは「送っていない」と区別が付かない**。
テストダブルの取りこぼしが、実装の欠陥に見えた。

### Try の書き方について（IT5・IT6 からの継続）

IT5 で「手順として書くと守られるが原理が及ぶ別の場所が漏れる」、
IT6 で「レビュー依頼には適用できたが実装には適用できなかった」と学んだ。

IT7 は**着手前と DoD に置いた**ことで、レビューより前に 3 件を自力で捕まえられた（K1）。
一方 P1 は「**過去の教訓がコードのコメントにまで書いてあったのに参照しなかった**」形である。

T1 はこれに対する打ち手だが、**「思い出す」に頼る Try は弱い**。
`NavigationReachabilityTest` のように機械検査へ落とせないかを、IT8 で一度検討する。

### 判断が要る事項

| # | 事項 | 備考 |
| :--: | :--- | :--- |
| 1 | **US09（経路確定）と US01（見積・運賃）の順序** | 利用者代表から「**確定は費用を見ずに行う操作ではない**。運賃が先か同時であるべき」。開発の都合ではなく業務の順序 |
| 2 | **最低接続時間**（同一港 24 時間・危険物 48 時間） | 業務からの回答が得られた。設定として外へ出せる形で入れる |

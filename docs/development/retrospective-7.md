# イテレーション 7 ふりかえり（KPT）

日付: 2026-08-23
対象: IT7（US15 荷役作業の記録・US16 引取作業の記録、10 SP／返済枠 12 件）

## サマリー

計画 10 SP を計画どおり達成し、**貨物が実際に動き出した**（追跡番号の入力 → 受領 → 積込 → 荷降し → 引取 → 追跡状態の反映）。あわせて **handlingms の初実装**と**サービス間の非同期連携 2 本目**（handlingms → trackingms）を通した。

**返済枠は 12 / 12 完了**。IT5 から 3 IT 持ち越していた SonarQube のホットスポットも、依頼ではなく**修正で閉じた**——中身を読んだら本物の弱点（ReDoS）だった。

一方で、クローズレビューで **11 件の高優先度**が出た。件数は IT6（9 件）より増えたが、**形が変わっている**。IT6 は「決定はあるが検査か配線が片側だけ」に集中していたのに対し、IT7 は次の 3 つに分かれる。

1. **コメントが宣言した性質を、コードが持っていない**（3 件）
2. **検査が届いていない層がある**（4 件）
3. **メニューに出しておきながら、そのロールで何もできない**（2 件）

最も重いのは**追跡の巻き戻り**で、5 視点のうち 3 つが独立に指摘した。

## Keep（続けること）

### 1. 規則の適用側を、機械的に導く（Try 1）

各サービスが規則を 1 つずつ呼ぶ形をやめ、`ServiceArchitectureTest` を継承する形にした。サービスが申告するのは「自分は誰か」だけで、規則の一覧は持たない。**規則を足せばその瞬間に 7 サービス全部へ掛かる。**

メタテストも作り直した。旧版は「ソースが規則名を含むか」を見ており、Javadoc に名前が出ているだけでも通った。IT6 で「名簿方式の弱点を防ぐためのメタテスト自身が名簿方式だった」という指摘に、構造で答えられた。

### 2. 「余力次第」にせず、返済枠を先に置く

Day 1-3 に固めて置き、独立したコミットで済ませた。**12 / 12 完了**。IT6 は 12 件中 11 件（1 件は権限の壁）だったので、初めて全部返せた。

「余力次第」にしていたら、Phase 1 の着手が Day 4 だった今回は確実に繰り越していた。

### 3. ゲートを有効にすると、隠れていたものが出る

`ignoreFailures = true` を外したところ、**SpotBugs は Java 25 のクラスファイルを読めておらず、1 クラスも解析していなかった**。ツール版を上げて初めて中身が見えた。**「検査を入れたこと」と「検査が働いていること」は別**という IT6 Keep 1 と同じ形が、静的解析側でも出た。

### 4. 検査が実際に働いた場面が 5 回あった

- 方言スモークを入れた途端に `ON CONFLICT`（H2 が解釈できない）が出た
- shared のメタテストが、handlingms のヘッダ検査の欠落を検出
- ナビの検証テストとマニュアル整合の検査が、期待の古さを 2 件検出
- マニュアル整合の検査が、章名とメニュー名の食い違いを検出

**どれも、書いた本人が気づいていなかった。**

### 5. 指摘の再現性を確かめてから直す

レビューで「空欄の日時が `RangeError` になる」と報告されたが、実測すると**別の（もっと悪い）壊れ方**だった——`new Date(':00Z')` は例外にならず **2000 年**として読まれ、「2000-01-01 の作業」が記録される。報告をそのまま信じて直していたら、この形は残っていた。

## Problem（問題だったこと）

### 1. コメントが宣言した性質を、コードが持っていない ★最重要

3 件出た。いずれも**書いた本人が「そう書いたから、そうなっている」と思い込んでいた**。

- `TrackingActivity#afterHandling` の「**戻せる遷移は作らない**」——実装は現在の状態を見ておらず、引取済のあとに古い受領が再配送されると `RECEIVED` へ巻き戻る。**しかも送り直す手段は同じ IT で自分が用意した**（`dev:k8s:events:redeliver`）ので、この経路は実在する
- `AdvanceTrackingUseCase#saveIfChanged` の「**同じ内容の更新で行を触らない**」——無条件に書き込んでいた
- マニュアルの「**追跡管理者は記録を見ることだけできます**」——履歴は記録に成功したときだけ出るので、記録できない追跡管理者は履歴を一度も見られなかった

IT10 の学び「コメントは仕様として読み実装と突き合わせる」を知っていながら、**自分が書いたコメントには適用していなかった**。

### 2. 検査が「1 つの層」で止まっている

`offRoute`（予定外だったか）は集約と DB のあいだでは守られていたが、**応答とイベントで潰しても全テストが緑**だった。画面はこの値で警告を出すため、潰れると警告が一切出なくなる。

同じ形で、**追跡番号から貨物を引く SQL が実 DB で一度も実行されていなかった**。旅程の join を落とすと handlingms 側は「照らす相手が無い」として全作業を予定外に倒す——安全側に倒す設計なので例外にならず、**すべての記録に「予定外」が付いたまま誰も気づかない**。

### 3. 「否定の決定」を 2 件、文章のまま置いていた

ADR-023 のコンプライアンス表に「bookingms が購読していないことを確かめる」「`RoutingStatus` を動かしていないことを対で確かめる」と書きながら、検査が無かった。IT6 で「決定の数だけ検査を用意する」を Keep に挙げた直後である。

**表に書いたことで、確かめた気になっていた。**

### 4. メニューに出しておきながら、そのロールで何もできない

`navigation.ts` に「メニューに出すのは、そのロールで**何かできる**画面に限る」と自分で書いておきながら、追跡管理者に `/handling` を開放して履歴を見せていなかった。追跡管理者のダッシュボードは他が全部準備中なので、**ログインすると「担当の画面は次のリリースで使えるようになります」だけが出る**状態だった。

「ロール別到達性」は IT6 で学んだはずだが、**到達したあとに何ができるか**は見ていなかった。

### 5. コンテナ起動の競合で、ビルドが不定期に落ちた

クローズ作業中に 4 回踏んだ。サブプロジェクトを並列に走らせると Testcontainers が同時に何個も立ち上がる。**再実行すると通るため、3 回目まで「環境の都合」として流していた**。

症状は毎回違うテストの `initializationError` で出るため、原因が資源だと分かりにくい。**「たまに落ちるテスト」を許すと、本物の赤も見逃す。**

## 次イテレーションへの引き継ぎ

### 持ち越し（IT8 で扱う）

| # | 内容 | 理由 |
| :--- | :--- | :--- |
| 1 | **本番コードを契約から導く**（パス・システム主体がリテラルのまま） | 契約は 1 つになったが、本番と契約が同時にずれても緑のまま |
| 2 | **交換機の引数を契約に含める** | 一致を保証しているのがコメントだけ。作り直す手順は用意したが、それは事後の復旧手段 |
| 3 | **認可を呼んでいることの検査** | 書き忘れは 401 に倒れるが、ロール違いは素通りする。8 サービス目で忘れたときに落ちる仕組みが無い |
| 4 | **種別の妥当性検査が 2 か所**（入口とユースケース） | 入口が増えた日に、種別不正が別の見え方をする |
| 5 | **`TrackingEventRoundTripTest` を契約ごとに割る** | 2 契約で 330 行。US17 で 3 契約目が入る |
| 6 | **`CargoSnapshot` の正準コンストラクタが public** | `of` の検査を素通りして生成できる |
| 7 | **`restore` が null を返す静的ファクトリ** | 呼び出し側から null 可能性が見えない |
| 8 | **引取の確認ダイアログ** | 種別が残るため、別の貨物に「引取」のまま記録する事故が起きうる。1 日数十件の画面なので、確認の入れ方は慎重に決める |

### IT8 の着手前に決めること

- **追跡管理者の画面（`/tracking/manage`）が準備中のまま。** IT7 で荷役の履歴だけは見られるようにしたが、担当画面の本体は US17・US20（IT8）である。**このロールに人を割り当てるなら、IT8 の完了までは荷役の履歴しか使えない**ことを伝える
- **予定外の作業が業務として処理されない。** 記録には残り、追跡管理者へ連絡する導線も書いたが、**待ち行列は US28（IT10）**である。それまでの予定外案件をどう扱うかを、運用ルールで決める
- **引取済の貨物が精算に乗らないまま溜まる**（US26・IT12 まで）。引取済の一覧が US26 の前提として要る

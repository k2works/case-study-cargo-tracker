# イテレーション 7 ふりかえり（KPT）

- **対象**: IT7（輸送見積作成 US01・輸送料金算出 US21・法人割引適用 US22・精算処理 US23・Estimation/Billing の 2 BC 新設・Phase 4 完了）

- **実績**: 18 SP 完了（目標 18 SP・達成率 100%・Phase 4 完了）／ RSpec 397 examples 0 failures ／ 全体カバレッジ 96.01%・新規 94.4% ／ SonarQube Quality Gate PASS ／ CI success ／ Release 1.0 はクローズ手順で発行

## Keep（うまくいったこと）

- **終盤アウトサイドインで新規 2 BC（Estimation/Billing）をゼロから貫通**。`FreightCalculationService` などの中核ドメインをインサイドアウトで先に固め、業務シナリオ E2E（料金算出→割引→精算→SETTLED 同期）で上位結合する、局面内のハイブリッド戦略が機能した。
- **BC 独立性を非循環 DAG で維持**。Estimation→{Routing,Billing}・Billing→{Booking,Shipper} をすべて公開 API + ADR-0003 越境識別子・プリミティブ受け渡しで統一し Packwerk privacy ゼロ違反。両 BC が同名 `RouteCandidate` を各 BC 内別型として持ち ACL 変換する ADR-0004 決定4 の設計が実装で確定した。
- **T33（状態の再導出禁止）を実装で実践**。IT6 の学び（[[feedback_domain-state-no-rederivation]]）を活かし、Invoice の base_amount を永続化（total からの逆算を排除）。レビューで割引額・shipper_id も同原則に統一した。
- **クローズ前レビューで高優先度 6 件を全対応**。programmer と architect が独立に同一の高指摘（shipper_id 消失）へ収束。tech-writer と user-rep が独立に同一の高指摘（請求明細のサーチャージ欠落＝経理が承認不能）へ収束し、確度の高い欠陥を早期是正できた。
- **設計反映を実装と近接して同期**。Money→MoneyAmount 命名統一・invoice イベント・ADR-0004 決定4 を実装コミットと近接して正典へ反映（[[feedback_scope-change-canon-sync]]）。

## Problem（課題・負債の発生源）

- **請求明細の不完全さをレビューまで見落とした**。FreightCalculationService は燃油サーチャージを合計に含めるが、請求書明細に行がなく合計が検算できない（経理が承認不能）状態だった。ドメイン計算と UI 表示の整合を実装 DoD に落とし切れていなかった。tech-writer と user-rep が独立に検出。
- **SettleInvoice の複数集約更新に partial-apply が再発**。決済ゲートウェイ呼び出しが状態ガードの前にあり再精算で二重課金の恐れ・`mark_settled` 失敗を無視して Invoice=精算済/Booking=未精算の不整合。IT5 の一貫性ギャップと同型で、レビューで初めて検出。
- **越境識別子 shipper_id の永続化漏れ**。集約が保持する越境識別子を保存せず再構成時に nil 化し、通知が固定アドレスに退化していた。T33（再導出禁止）の隣接ケースで、集約状態の「消失」という更に悪い形。
- **18 SP・2 BC 新設のスコープが大きく、受入基準の一部が未達**。US23 未払い通知の駆動バッチ・US21 料金調整（減額・補償）が未実装のままクローズ（正直に記録）。

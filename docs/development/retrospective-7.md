# イテレーション 7 ふりかえり（KPT）

| 項目 | 内容 |
| :--- | :--- |
| 対象 | IT7（US18 追跡情報の照会 / US16 引取作業の記録 / US03 法人荷主の登録） |
| 計画 SP | 8 |
| 完了 SP | 8 |
| 実施日 | 2026-08-08 |
| 局面 | **終盤（アウトサイドイン）** |

**本 IT で「作った人以外が初めて使う」段階に入った。** IT1〜IT6 の画面はすべて社内ロール向けだったが、
US18 の公開追跡は認証を持たない相手に見せる最初の画面である。

**返済枠 5 件をすべて完済した。** IT2〜IT6 で「余力次第」にせず時間で確保する運用が定着している。

## Keep（続けること）

### K1. 着手前の突合が 13 件の欠落を見つけた

開始準備（`opening-iteration`）の 2 つの検証で、**設計ドキュメント・スキーマ・シードデータの欠落を 13 件**見つけた。
そのうち実装をブロックしたのは 3 件である。

| 欠落 | 見つからなかったら何が起きたか |
| :--- | :--- |
| `/tracking` の認可規則が設計と実装で食い違う | **発行待ち一覧（他社を含む確定済み予約）が荷主に見える** |
| ROLE_SHIPPER・ROLE_CONSIGNEE の利用者が存在しない | 開いてよいと定めた画面を、誰も開けない |
| 引取確認を保存する列が無い | 引き渡し証明を記録する先が無い |

**IT5 は「実行できる人」、IT6 は「実行する人の入口」、IT7 は「その人自体の不在」。**
6 IT 連続で「作ったが使えない」型であり、**着手前の突合でしか見つからない**。

### K2. Checkstyle と ArchUnit が設計の誤りを 4 回捕まえた

| 検査 | 捕まえたもの | 直した形 |
| :--- | :--- | :--- |
| Checkstyle（パラメータ数 7） | 荷役に読み取った番号を足した | `HandledCargo`（番号と予約のひと組） |
| Checkstyle（パラメータ数 7） | 引取確認を足した | `HandlingDetails`（種別と、種別に応じて要る詳細のひと組） |
| Checkstyle（複雑度 10） | `apply` の boolean が 3 個 | 種別名 1 つに変え、誤配の反映と状態遷移を分けた |
| ArchUnit（レイヤ依存） | アプリケーション層がインフラの Mapper を直接参照 | 出力ポート `PortNames` を抽出 |

**いずれも上限を緩めなかった。** IT6 の K3 で確立した「上限に当たったことを、概念を見直す合図として使う」が
そのまま働いた。`HandlingDetails` は「受領なのに荷受人確認が付いている」という
**意味の定まらない組み合わせ**を型で防いでおり、DB の CHECK 制約とも対応している。

### K3. 安全装置を 11 件、入口と出口の両方で壊した

IT6 の Try T1 への対応である。**判定だけでなく、判定の結果が書かれる先まで壊した。**

| 装置 | 壊し方 | 結果 |
| :--- | :--- | :--- |
| 方言スモーク（採番） | `nextval` を PostgreSQL 専用構文に | 赤 1 件 |
| 購読側の取りこぼし計測 | 記録を握りつぶす | 赤 2 件 |
| 確定の衝突 | `CONFLICTED` を返さない | 赤 1 件 |
| 荷役種別の網羅 | 種別を 1 つ追加 | **コンパイルエラー**（実行時より強い） |
| 追跡番号の検索 | 絞り込みを無効化 | 赤 7 件 |
| 公開画面の情報制限 | 荷主名を画面に足す | 赤 1 件 |
| ヘルスチェックの除外 | 除外条件を外す | 赤 3 件 |
| 引取による配送完了 | `CLAIM` の伝播を止める | 赤 5 件 |
| 引き渡し後の荷受人保護 | 守りを外す | 赤 1 件 |
| E2E の経路 | 遷移表から `COMPLETE_DELIVERY` を削除 | 赤 1 件 |
| 港湾名の表示 | 名前の取得を空に | 赤 1 件 |

### K4. 規律を人手から自動へ移した

IT5 の Try「例外を投げる経路を `grep` で数える」は例外については守れていたが、
**戻り値で結果を返す安全装置には適用されていなかった**（IT6 の P2）。

本 IT では `@CheckReturnValue` を付けて **SpotBugs に数えさせる形**にした。
導入した瞬間に、**テストの Arrange 11 件が楽観的ロックの結果を握りつぶしていた**ことが分かった。
失敗した準備の上でアサートしていたのであり、**人が `grep` していたら気づけなかった**。

**規律は覚えているうちは守れるが、覚えている範囲しか守れない。**

### K5. 返済枠 5 件を完済した

`C1`（追跡番号での引き当て）・`C3`（荷役一覧とスキャナ入力）・`C5`（採番の置き場）・
`C6`（確定の衝突と種別の網羅）・`C10`（購読側の失敗を見る手段）。

**IT2 から 6 IT 連続で、返済枠を「時間」で先に確保する運用が守られている。**

## Problem（問題点）

### P1. 「宣言はしたが実装が無い」形が 6 件出た（最も重い）

レビューと自己検証で、**宣言と実装が食い違う欠陥が 6 件**見つかった。

| 宣言した場所 | 宣言の内容 | 実際 |
| :--- | :--- | :--- |
| `handling/form.html` のコメント | 「予約の荷受人と違えば警告を出し、メモへの理由記入を求める」 | **照合は場所しか見ていない。メモ欄も無い** |
| `handling/form.html` の案内文 | 「担当者メモに理由を記入してください」 | **メモ欄が画面に無い** |
| `handling/form.html` の案内文 | 「荷受人へ事前に送付した確認コード」 | **送付する手段が無い**（ADR-006）。照合もしない |
| `tracking/index.html` の案内文 | 「予約詳細から確認できます」 | **この画面を使う荷主・荷受人は予約詳細を開けない** |
| `iteration_plan-7.md` タスク 1-4 | 「作業日時の下限を追跡番号の発行日時とする」 | **実装していない** |
| `ClaimConfirmation.matchesConsignee` | 荷受人を照合するメソッド | **テストからしか呼ばれていない**（配線漏れ） |

**IT6 の P3（Javadoc が防ぐと宣言した故障モードを実装が守っていなかった）と同じ形である。**
今回は場所が Javadoc から**画面のコメント・利用者への案内文・計画**へ移った。

**とくに最後の 1 件は形として分かりやすい。** 「定義したがどこからも呼ばれないドメインメソッド」は
**配線漏れのサイン**であり、機械的に検出できたはずである。

### P2. 前 IT のレビュー指摘が 2 件、そのまま再発した

| 再発した指摘 | IT6 | IT7 |
| :--- | :--- | :--- |
| **付録 B に当該 IT の症状が 1 件も無い** | H8 | H8（同じ） |
| **マニュアルの項目表が実画面とずれている** | H7（7.1 が 9 列とずれ） | H9（担当者メモを足して 8 番目以降がずれ） |

**IT6 の Try には「マニュアルの索引 3 点同期」（T5）は入っていたが、
「項目表と付録 B」は入っていなかった。** ふりかえりで Try にしなかった指摘は、次の IT で同じように出る。

項目表のずれは**画面を後から直したときに起きている**。レビュー対応で欄を 1 つ足した結果、
丸数字が 1 つずつずれた。**マニュアルを書いた時点では正しかった。**

### P3. レビューエージェントが 5 視点中 4 視点で回答を返さなかった

`developing-review` は 5 つの XP 視点を並列に起動する。今回、**回答が返ったのは利用者代表のみ**で、
残る 4 視点は調査を終えたと見られる状態でアイドルに戻り、レポートを返さなかった。

フォールバック手順（本セッションで順次実施）に切り替えて 4 視点を自分で行い、
**高優先度 3 件（H6・H7・H8）を追加で見つけた**ため結果的には成立したが、
**「エージェントを起動した」ことと「レビューが行われた」ことは別である。**

### P4. 利用者代表の指摘が、他の視点より一貫して重かった

高優先度 9 件のうち **6 件が利用者代表**である（IT6 も 6 件）。
残りは自己レビューの tester / technical-writer 視点で見つけたものであり、
**プログラマ・アーキテクトの視点からは高優先度が出ていない。**

コードとアーキテクチャは整っているが、**「その画面の前に座った人が何をできるか」で見ると穴がある。**
2 IT 連続で同じ傾向であり、偶然ではない。

### P5. 引取確認が「記録はできるが証明にならない」状態で完了とした

確認コードは**発行も照合もされない**。ADR-006 により通知を送らないため、送付する手段が無く、
システムが持つ正解も存在しない。作業員は荷受人が口頭で言った数字を打つだけである。

文言を実態に合わせた（「提示されたコードを記録する。照合は行わない」）のは正しい対応だが、
**US16 の「引き渡しを証明する」という目的は、まだ半分しか達成していない。**

### ベロシティ

7 イテレーションの実績は **9 / 7 / 8 / 8 / 7 / 8 / 8** で、平均 **7.86SP**。
採用値 8SP との差は 0.14SP であり、**再調整はしない**。

**7 IT 連続で計画 SP = 実績 SP である。** ただしこれは「8SP に収まる量を計画している」ことの結果でもあり、
**上限は依然として測れていない**（IT1 からの持ち越しの問い）。

### CI が 3 IT 連続で緑だった

依存の更新を開始時に置く運用が定着している。

### レビューの重さについて

IT5 は 0 件、IT6 は 14 件、IT7 は 9 件。**IT6 と IT7 に共通するのは「新しい種類の相手に開いた」ことである。**
IT6 は Tracking Context の初出で BC 間 ACL が 3 つ増え、IT7 は認証を持たない相手に画面を開いた。

**境界が増えると、そこを渡る約束（合図・文言・証明）の扱いが問題になる。**
IT6 の P1〜P3 は「戻り値と例外」に帰着したが、**IT7 の P1 は「宣言と実装」に帰着する。**
どちらも**約束したことを守っているかを、機械が確かめていない**という点で同じである。

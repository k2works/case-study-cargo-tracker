# イテレーション 8 ふりかえり（KPT）

- **対象**: IT8（予備イテレーション・US23-5 支払期限超過の未払い通知・US21-6 例外時の料金調整・T37 遅延の新到着予定日構造化・業務全体シード）
- **期間**: Week 15（〜2026-07-29 クローズ）
- **実績**: 9 SP 完了（目標 9 SP・達成率 100%）／ RSpec 416 examples 0 failures ／ 全体カバレッジ 95.94%・新規 91.5% ／ SonarQube Quality Gate PASS ／ CI success ／ Release 1.1 はクローズ手順で発行

## Keep（うまくいったこと）

- **IT7 で正直に記録した受入基準の残を予備 IT で確実に消化**。US23-5（未払い通知の駆動バッチ）・US21-6（料金調整）を実装し、IT7 で「未達」と明記した 2 基準を完全充足。「正直な残記録 → 予備 IT で回収」のサイクルが機能した。
- **IT6 の T37 も同時に回収**。遅延対応の新到着予定日を構造化し公開追跡に反映。過去 IT の Try が繰越の連鎖にならず消化された。
- **クローズ前レビューで最重要欠陥を早期検出**。programmer と user-representative が独立に「OVERDUE 請求書の塩漬け」（期限超過後の遅延入金という典型業務が停止）へ収束。受入基準の文面は満たしても実業務を止める欠陥をクローズ前に是正できた。
- **業務全体のシードデータで動作確認が容易に**。航海・見積・フルライフサイクル（予約→追跡→荷役→請求→精算）・遅延例外・未払い請求を投入し、各ロールで全機能を画面から辿れる状態を用意。curl で全画面の描画も検証。
- **T33 の実践を継続**。InvoiceAmounts の専用ファイル抽出・revised_arrival_date の永続化・未払い通知を状態遷移に紐づけ（候補抽出との分離）。

## Problem（課題・負債の発生源）

- **状態機械のガードが受入基準の文面に引きずられ実業務を見落とした**。`confirm_payment`/`add_adjustment` を `pending?` のみに絞った結果、OVERDUE（期限超過）後の遅延入金・減額ができない塩漬けを生んだ。「期限を過ぎてから払われる」という現場の典型ケースをドメイン設計時に洗い出せていなかった。
- **符号正規化というドメイン不変条件をアプリ層に置いた**。REDUCTION 負/COMPENSATION 正の規約が AdjustFreight にあり、VO を直接生成すると不整合な明細が作れる状態だった。ドメインの単一の真実点を外していた。
- **開発シードで BC privacy をバイパス**。デモ未払い請求の期限超過を作るため生 SQL で invoices を直接更新。Packwerk 非検知の越境で、コメントの「privacy を尊重」と実態が矛盾。
- **業務意味の確認不足**。「補償費用」の増減方向（当社が荷主へ負担するなら請求減額のはず）が実装（追加請求＝正値）と食い違う疑いをレビューで指摘され、業務判断が保留に。

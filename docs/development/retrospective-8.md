## Keep（続けること）

### K1. 受入テストを先に書いたことが、識別子の設計を変えさせた

US01 は終盤の局面（アウトサイドイン）に従い、受入テストから書いた。
その過程で **URL に UUID が現れ、利用者が電話口で読み上げる番号と一致しない**
ことに気付き、`EstimateId` を採番の時点で `EST-XXXXXXXX` にする形へ変えた。

これは IT4 で「予約フォームが画面上どこにも出ていない UUID を要求していた」のと
同じ形の発見である。**単体テストでは決して現れない**——ドメインは識別子の中身を
知らなくてよく、画面は渡された値を出すだけだからである。

外側から書くことの価値は「網羅」ではなく、**利用者が辿る経路を歩くと
設計の行き止まりに当たる**ことにある。

### K2. 「値ではなく、あり得ない結果が出ないこと」を固定した

`FreightRateTest` は運賃の値を固定しない。固定したのは次の 3 つである。

- 積替が増えるほど高くなる（直行より積替 2 回が安い結果は業務上あり得ない）
- 重い貨物のほうが高い
- 危険物・冷凍は一般貨物より高い

単価そのものを固定するテストは **1 件だけ**置いた。値を変えたときに
「意図せず変わったのか、意図して変えたのか」が分かるようにするためである。

概算のように**唯一の正解が無い計算**では、値を全部固定すると
テストが仕様の写経になり、変更のたびに機械的に期待値を書き換える習慣がつく。

### K3. 測ってから「入れない」と決めた

TS12b は IT7 の Try T7（数値を持つ防御は、その数値が守られているか測ってから
恒久化する）への返答である。**測った結果、検討していた対策を 2 つとも入れないと決めた**。

- 追跡 API のキャッシュ（TTL 30 秒）— 目標の 2.3 倍が出ている段階で足すのは、
  **測って要らないと分かったものを足す**ことになる
- タイムアウト時の枠返却を遅らせる案 — 30 秒を超える処理が 1 つも無く、
  **`504` を起こす条件自体が作れなかった**。測っていない問題を防ぐために、
  測って分かっている可用性を犠牲にする取引になる

いずれも**再検討の条件**を書いた。「今は入れない」が期限のない先送りにならない。

### K4. 観測手段そのものを疑った

既定の同時実行 200 で `503` が 1 件も出なかったとき、「防御が壊れている」と
結論づけずに上限を 5 に落として再測定した。4,000 件の一斉送信で 2,285 件の
`503` を観測し、**防御は正しく働いていて、枠に達していないだけ**だと分かった。

IT7 の Try T6 がそのまま効いた場面である。

### K5. テストを消さずに「向き」を変えた

IT7 の `testDoesNotShowCostColumn`（費用の列を出さないこと）は、
IT8 で運賃モデルが入って条件が逆になった。削除せず
`testCostColumnIsNotAPlaceholder` に置き換えた——**守りたいのは
「数字の入っていない列を見せない」ことであり、それは変わらない**。

条件が変わったテストを消すのは、守っていたものごと捨てることになりやすい。

## Problem（問題だったこと）

### P1. 【最重要】返済したはずの欠陥を、同じ IT の中で自分で再発させた

IT7 レビュー M17（所要日数の `0` が「同日到着」と「読めなかった」を区別できない）を
Routing 側で直した。**その同じ IT で書いた Estimation 側の翻訳では、
同じ `0` 埋めを書いていた**。しかもドキュメントコメントには
「読めなければ**候補ごと落とす**」と、実装と逆のことを書いていた。

原因は明確である。**合成ルートに置いた翻訳（`EstimationWiring.toFoundRoute`）に
テストが 1 本も無かった**。`RouteSearch` に触れるテストは呼び出し回数を数える
スタブだけで、翻訳そのものを通るものが無かった。

ADR-0010 は「合成ルートに置くと `arch-lint` が検出できない」というリスクを
自分で書いていた。**そのリスクが、ADR を書いた当日に顕在化した**。
書いて満足し、そこから導かれる手当て（テストを義務づける）をしなかった。

### P2. 「全部見る」と宣言したテストが、最も新しいものを見ていなかった

`WiringTest.testEveryGetRouteResponds` は「**全ルートが 1 度ずつ通ること**」を
宣言しながら、パスは手書きの 18 件だった。本番の GET ルートは 21 件あり、
**IT8 で足した `/estimates` 系 3 本がすべて漏れていた**。

このテストの目的は「BC の `withDb` を適用し忘れた実装を捕まえる」ことである。
**最も新しい BC が対象外**では、目的をまったく果たしていない。

P1 と合わせて、**宣言と実態の乖離が 2 件重なった**。どちらも
「書いた本人が正しいと信じている」ため、レビューでしか見つからない種類である。

### P3. 計画の「壊れ方の観点」を読まずに実装し、逆の判断をした

IT8 計画は着手前に軸 1 として「未知の状態語は**全件へ倒さず 0 件**（黙って広げない）」
と決めていた。実装時にこれを確認せず、**「絞らない」に倒した**。
自分で書いた計画の、しかも壊れ方の観点の表を読まなかった。

コミット `9bdf186a` で戻したが、**計画を書くことと計画を使うことは別の行為**である。
着手前に決めたことは、着手時に読み返さなければ意味がない。

### P4. 実バグを 2 件、レビューまで見つけられなかった

- 重量表記が小数位を取り違える（`1050 g` → `1.50 kg`。実際は 1.05）
- 未知の貨物種別が `Standard` 運賃へ倒れる（同ファイルの `capabilityOf` は
  「未知は `None`」としており、判断が割れていた）

どちらも**単体テストを書いていれば即座に落ちる**性質のものだった。
`weightText` は画面（`EstimatePages`）に置いたためテストの対象外になっていた——
**桁の扱いは業務上の意味を持つのに、画面に置いたから誰も見なかった**。

IT7 の P3（新しく作った共有カーネルにテストを 1 件も書かなかった）と同じ形が、
今度は「ドメインに置くべきものを画面に置いた」という形で出た。

### P5. 受入テストのアサーションが弱く、壊れても緑だった

US01 の受入基準 3（候補ごとに経由港・所要日数・概算料金・航海番号が表示される）の
検証が `contains("V-")` / `contains("日")` / `contains("円")` だった。
**運賃計算が壊れて 0 円になっても緑**であり、`contains("日")` に至っては
日付表記でも通る。

`FreightRateTest` が「1,200 kg × 1 区間 = 194,000 円」を単価として固定しており、
受入テストのフィクスチャはまさにこの条件だった。**実額で突き合わせられたのに、
文字が含まれることしか見ていなかった**。

### P6. 負荷試験の測定が 1 回で、「ばらつき」と書いた

同時実行 100 で 2,306・200 で 1,468・400 で 2,246 という非単調な結果を
`non_functional.md` に「測定のばらつきの範囲」と書いた。**各条件 1 回しか
測っていない以上、それは測定ではなく推測である**。

さらに負荷生成が単一 Node プロセスであり、同時実行 100 と 400 で RPS が
同じ ~2,300 で頭打ちになるのは**送信側が飽和しているときの典型的な形**である。
「最大 2,306 RPS は目標の 2.3 倍」は、**サーバ能力の下限しか言えていない**。

### Try の書き方について（IT5-IT7 からの継続）

Try は「気をつける」ではなく**手順**として書く。T3 の「コミットメッセージに引用する」、
T2 の「見つけたらその場で変える」は、いずれも実行したかどうかが後から分かる形である。

IT7 の T4（画面を作る前に「毎朝どう使うか」を 3 行で書く）は US01 の計画に
書いてあり、**電話口の即答という利用場面が実装判断を 3 回変えた**
（危険物申告欄を出さない・最安概算を一覧に出す・見積番号をフラッシュで返す）。
継続する。

## 次イテレーション（IT9）への引き継ぎ

### 判断が要る事項（着手前に決める）

| # | 事項 | 背景 |
| :--: | :--- | :--- |
| 1 | **ADR-0010 の適用範囲を「読み取りに限る」と明記し、書き込み方向は別 ADR で扱うか** | IT9（US09・US11・US13）は Routing が Booking の状態を変える。読み取りの取り違えは「候補が出ない」で済むが、**書き込みの取り違えはデータが壊れる**。BC 間の意味的な結合は既に 3 件あり、4 件目が書き込みなら `composition/acl/` の導入を払う妥当なタイミング |
| 2 | **`POST /login` の CSRF 検証**（セキュリティ） | `anonymous()` として登録されており `requiresCsrf` が `false` を返す。一方フォームには `_csrf` を描画している——**出しているが検証していない**。ログイン CSRF が成立する |
| 3 | **見積の有効期限を業務として決めるか** | 利用者代表いわく「実務では有効期限 2 週間を必ず添える」。運賃が変動すると画面自身が書いている以上、業務上必要。値の定義は利用者側の判断 |

### 本 IT で対応しなかったレビュー指摘（中 6 件・低 8 件）

[IT8 実装レビュー](../review/IT8実装_review_20260804.md)の中 M4-M9・低 L1-L8。
とくに次の 2 件は IT9 で扱う価値が高い。

- **M4**: `transitDays = Int32` が「読めない」を表現できず、境界で必ず嘘をつく（DB 列の nullable 化を伴う）
- **M8**: 負荷生成の複数プロセス化（現状はサーバ能力の下限しか言えていない）

### 利用者代表からの機能要望（9 件）

見積は「電話口で答える」場面は成立するが、**「あとで見返す」場面が成立しない**。
U1（作成日・引き合い元）・U2（出発予定日・到着予定日）・U3（候補の時点表示）は
いずれも**受入基準に無いが業務上必要**なものである。
詳細は[レビュー](../review/IT8実装_review_20260804.md)の該当節。

**U7（見積から予約への導線）は US01 の価値を半分にする**という指摘であり、
ストーリーとして起票を推奨する。

### 未充足の受入基準（意図的・1 件）

US01 受入基準 6「危険物が含まれる場合、危険物申告情報の入力フォームが表示される」は
**実装していない**。見積の段階で必要なのは種別だけであり、申告情報は予約時に要る
（US05 で実装済み）。利用者代表も「見積段階で UN 番号を聞かれたら電話は切れる」として
**受入基準そのものを落としてよい**と述べている。ストーリーの修正を推奨する。

### 品質ゲートの未達（1 件）

**SonarQube の Quality Gate を確認できていない**。`.env` が無く、
`.env.vault` の復号にパスワードが要るため、スキャンを実行できなかった。
`sonar.sources` は `ops/scripts` のみ（Flix は非対応）であり、
本 IT で追加した負荷試験スクリプト 2 件が対象になる。**IT9 の着手前に実行する**。

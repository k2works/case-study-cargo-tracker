# IT10 完了報告書（2026-08-05）

## エグゼクティブサマリー

**計画 12 SP をそのまま消化し、縮退 0 件で完了しました**（IT5-IT10 で 6 イテレーション連続）。

本イテレーションで、**貨物が予約から現場まで通りました**。営業が予約を確定し（US13・IT9）、
経路設計者が追跡番号を発行し（US14）、荷役作業員が現場で受領・積込・荷降しを記録すると
（US15）、その結果が荷主の追跡画面に反映されます。予定と違う港で積み込めば
経路逸脱として予約へ報告され、経路設計者の画面に警告が出ます。

**Handling Context を新規に立ち上げました**（6 つ目の BC）。本プロジェクトで初めて
コンテキストをまたいで状態が伝播するイテレーションであり、その形を
**ADR-0012**（BC をまたぐ書き込みは相手の集約を同期に通す）として一般化しました。

一方、クローズ時レビューで**高優先度 9 件**が出ました。最も重かったのは
**ADR-0012 の中心的主張が、書いた当の IT で成立していなかった**ことです
（Handling → Tracking の書き込みが集約を通っていなかった）。高 7 件・中 3 件を返済し、
残る高 2 件は設計判断を伴うため理由を明記して IT11 へ送りました。

**もう 1 つ重要な発見がありました**。IT8・IT9・IT10 が 3 回連続で記録していた
「SonarQube 品質ゲート未達」は、**IT5 で既に品質ゲートから外れていた条件に対する
誤った記録**でした。**ADR-0013** で品質ゲートの正典を一本化しています。

## 技術的成果

### ADR-0012: BC をまたぐ書き込みは相手の集約を同期に通す

ADR-0011 は US09/US11 という**特定のストーリー**について書かれていたため、IT10 で
同じ議論をやり直しました。IT11（US16）でも 4 回目が来ます。**一般形として決めました**。

書き込みが越境する 3 箇所（Tracking → Booking、Handling → Tracking、Handling → Booking）は
いずれも同期の ACL ポートで、相手の集約を通ります。翻訳は `composition/acl/` にのみ置きます。

設計ドキュメントは `HandlingActivityRegisteredEvent` でイベント方式を描いていたため、
**未採用として同一の変更で是正**しました（イベント表・コンテキストマップ・
UI の「最大 30 秒の反映遅延」注記）。

### ADR-0013: 品質ゲートの正典はテスト戦略とする

IT8・IT9・IT10 が 3 回連続で「SonarQube 未達」と記録していましたが、
**IT5 のふりかえり Try T9 で既に品質ゲートから外れていました**。
IT5 は「3 回目の未実施にする前に決める」という正しい判断をしたのに、
**書き写された DoD が正典に追随せず、同じことが 3 回繰り返されました**。

品質ゲートの条件は 5 つで、**すべて CI で走ります**。

| 検査 | 対象 |
| :--- | :--- |
| 全テスト緑 | Flix 本体（単体・統合・HTTP） |
| `arch-lint` | アーキテクチャ規約（11 件 + メタテスト 32 件） |
| `trace-lint` | ビジネスルール ⇄ テストの対応 |
| `script:lint`（ESLint） | 運用スクリプト（検査器を含む） |
| `test:dbnames` | テスト用 DB 名の重複 |

### Handling Context の立ち上げ

終盤（アウトサイドイン）の局面ですが、**新 BC のドメインは中盤の規律**で組みました
（効果を要求しない・現在時刻は引数）。IT8 の Estimation と同じ形です。

`isValidFor` のデシジョンテーブル（種別 × 場所の一致 = 6 セル）を表駆動で網羅しました。
**受領の不一致は警告、積込・荷降しの不一致は MISROUTED** という書き分けは表を見ないと守れません。
`matchesLeg` は**航海番号で区間を特定してから港を比べます**——港だけで比べると、
同じ港を 2 度通る旅程（積替で戻る）で誤って一致します。

### 追跡番号の採番と一意性

形式は `TRK-YYYYMMDD-NNNN`。**日付を含むため同一日内の連番が競合点**になります。
一意性を保証するのは DB の UNIQUE 制約であり、アプリケーション側の
「読む → 決める → 書く」ではありません。

**制約を外すと赤くなることを実測しました**（IT9 の Try T3）。同時発行テストのほうは
外しても緑のままであり、その事実を doc に明記しています。

## 課題と残作業

### 1. `Cargo` のハブ化（IT11 の着手前に見直す）

`composition/acl/` が 6 本になり ADR-0011・ADR-0012 の再検討条件に到達しました。
ただし**見直すべきは本数ではありません**。6 本の内訳を向きで見ると、
**書き込み 4 本のうち 3 本が Booking へ向いています**。

これは「連携が増えた」のではなく **`Cargo` がハブ化している**ことを示します——
`BookingStatus`・`RoutingStatus`・`trackingNumber`・旅程を 1 集約で抱えるため、
Routing も Tracking も Handling も自分の仕事の印を `Cargo` に付けに来ます。

IT11 では条件を「**単一 BC へ向かう書き込みアダプタ数**」へ置き換えることを検討します。
`trackingNumber` は `Cargo` の不変条件にほとんど参加しておらず、自然な切れ目の候補です。

### 2. 間欠失敗（未解決・IT9 から継続）

ログインが 503 / 404 を返す事象が本 IT でも 2 度再現しました（いずれも単発で、
再実行では緑）。原因は特定できていません。

診断（`assertStatus` にルート・インスタンス・本文）は入っていますが、
**残る仮説（別インスタンスが応答する）を検出できるのは `withAppInstance` で
突合したときだけ**であり、IT10 の新規テストはすべて `withApp` 系です。
テスト本数が最も増えた領域が仮説検証の対象外になっています。

### 3. 規約 12 が 6 イテレーション未着手

IT4 レビュー M1 由来。ふりかえり Try T4（ポートの書き込みメソッドは集約型を取る）を
候補に加えます。

### 4. `operator_name` 列が常に NULL

`V12` で定義しましたが一度も書いていません。荷役は責任の所在がはっきりしている作業であり、
「誰が記録したか」は監査で最初に聞かれます。**定義されているのに常に NULL が
一番読みにくい状態**です。書くか落とすかを IT11 で決めます。

## 次イテレーション（IT11）への引き継ぎ

### 着手前に必ず行うこと

1. **BC 間連携の設計の見直し**（`Cargo` のハブ化。上記課題 1）
2. **US16 より先に H8 を扱う**（荷役が荷主のタイムラインに出ない）
3. **間欠失敗の診断強化**（`withApp` 系でもインスタンス突合を有効にする）

### 計画に織り込む改善（ふりかえりの Try）

1. **DoD に条件を書き写さない**。正典を 1 行で引用する（T1）
2. ADR を書いたら、**その ADR の再検討条件を自分の実装で満たしていないか**を起票時に確認する（T2）
3. **コメントが規律を宣言したら、実装がそれを守っているかをその場で読み直す**（T3）
4. **ポートの書き込みメソッドは集約型を引数に取る**（T4。規約 12 の候補）
5. 受入基準を満たしたら、**利用者代表の観点で「毎朝どう使うか」を通す**（T5）
6. 間欠失敗の診断を `withApp` 系でも有効にする（T6）
7. 新規 BC を立ち上げたら、**既存 BC が持つ共有の道具を先に探す**（T7）

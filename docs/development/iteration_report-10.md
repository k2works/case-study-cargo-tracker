# イテレーション 10 完了報告書

日付: 2026-08-26
対象: IT10（US28 誤配の検知と経路の再設計）
計画 SP: 7 ／ 実績 SP: 7（達成率 100%）

## エグゼクティブサマリー

**貨物が予定ルートから外れたことに、システムが自分で気づくようになった。** IT9 まで、
予定外の港での荷役は「警告が出る」だけで、そのあと誰かが遅延として起票する運用に委ねて
いた。IT10 では荷役の記録そのものから誤配を検知し、予約の経路の状況を「誤配」にして、
追跡の例外を自動で起票する。**判定は 1 か所（handlingms）にあり、新しいイベントは
増やしていない**（[ADR-026](../adr/026-misroute-detection-and-rerouting.md) 決定 1）。

設計の中心は、**誤配を「状態」ではなく「起きた事実」として別に持った**ことである。経路の
状況は組み直せば `ROUTED` へ戻るが、`Misroute`（いつ・どこで外れたか）は戻らない
——料金調整の根拠として参照されるためである（受入基準 28-8）。

**返済枠は 11 / 11 完了**（4 IT 連続で全返済）。

本 IT の特徴は、**ドメイン層・ユースケース・実環境 API がすべて緑のまま、画面から踏むと
US28 の中核が成立していなかった**ことである。マルチパースペクティブレビューが高 8 件を
挙げ、**すべてが実欠陥だった**。うち 6 件は自分では見つけていない。

> **決定を書いて検査も置いたのに、その決定が効く経路を一度も通していなかった。**
> ADR-026 決定 4 は「期限で弾くと組み直す手段そのものが無くなる」と明記し、集約から
> 期限検査を外して検査も置いた。しかし期限による絞りは routingms 側にもう 2 つ
> （SQL の航海取得・探索の枝刈り）あり、**期限に間に合う便が残っていない誤配貨物は
> 組み直せなかった**——決定 4 が避けようとした事態そのものである
> （[ふりかえり](retrospective-10.md) Problem 2）。

### 返済枠（11 件・35h）

IT9 のふりかえりと遅着レビューから引き継いだ 11 件をすべて消化した。主なもの:

- 通関申告一覧を「毎朝の待ち行列」にした（既定を未決着だけに・件数と切り捨ての明示）
- キャンセル申請の履歴を全件出した（却下後に再申請すると前回の理由が消えていた）
- 荷役側に「陸揚げ待ち」の入口を置いた（作業指示は自動で作られないため）
- 型検査のコマンドを塞いだ（`tsc --noEmit` はプロジェクト参照構成では何も検査しない）

## 技術的成果

- **`Misroute`（値オブジェクト）** — 誤配の事実。状態と別の軸に置き、2 回目以降の誤配でも
  最初に外れた場所と日時を残す。キャンセル済みの貨物は動かさない
- **`DetectMisrouteUseCase`（trackingms）** — 例外の自動起票。**判定はしない**——
  handlingms が付けた `offRoute` を受け取るだけで、旅程を一切持たない（BC 独立性）
- **`RouteSearchSpecification#forReroute`（routingms）** — 期限で弾かない探索。
  緩めるのは期限だけで、出発地・目的地・貨物種別・積み替えの上限は今までどおり効く
- **予約詳細の読み取り開放** — 追跡管理者・荷役に開いた（一覧は広げない）。例外一覧・
  キャンセル承認・陸揚げ待ちのいずれからも予約詳細へ渡す導線があり、**押すと 403 だった**

## レビュー結果

[イテレーション 10 レビュー](../review/イテレーション10_review_20260826.md)（5 視点並列）

| 重要度 | 件数 | 対応 |

| 誤りだった指摘 | 1 | 確認結果を記録。ただし検査が無かったため 1 本追加 |

**3 視点（architect / technical-writer / user-representative）が独立に同じ 2 つの根を
指摘した。**

1. **「一度でも外れた」と「いま外れている」を区別していなかった** — 記録の有無で分岐して
   いたため、組み直したあともバナーが「組み直してください」と言い続け、ユースケースは
   以後**永久に**再設計側へ分岐していた。**宣言（Javadoc・設計文書）は正しく、使い方が
   誤っていた**形で、コメントを読むだけでは気づけない
2. **期限による絞りが 3 か所に分かれていた** — 集約から外しただけでは効かず、SQL と
   探索の枝刈りが残っていた

どちらも、実環境テストが API を直接叩いていたため空振りしていた。

## 課題と残作業

### 次イテレーションへ送るもの

1. **レビューの低指摘 4 件** — 誤配バナーの港名表示・`RoutingStatus` の述語を `switch` 式へ・
   ADR-026 コンプライアンス表の決定 7 の行・trackingms の完全修飾名
2. **2 回目の誤配の扱い** — `Misroute` は 1 件しか持たない。**料金調整は回数で変わる**ため、
   US21（Release 2.0）の前に決める
3. **陸揚げ待ちが「未着手」を区別しない** — 手配が済んだ行を消す手段がない

### 仕組みで埋めていない部分

- **通知は代替**（US28-6・US29-4・US30-6・US30-7）。運用で回す約束が 4 つになった
- **誤配の記録を経理が読む手段がない** — 予約詳細にしか出ず、経理担当者は開けない。
  「残っている」と「読める」は別である。料金調整の実装（US21）で参照経路を作る
- **陸揚げの作業指示は自動で作られない**（ADR-025 決定 5・IT9 から継続）

### 運用手順の課題

**`dev:k8s:rollout:image` の `--tag` / `DEV_K8S_IMAGE_TAG` が効かない。** `dev:k8s:images` を
実行してもノード上のイメージが更新されず、コンテナ内の jar が 6 日前のままで**最初の実環境
確認が誤った赤を出した**。今回は `kubectl set image` を直接使って進めた。反映後は
**Pod の起動時刻とコンテナ内 jar の日時**で確かめること。

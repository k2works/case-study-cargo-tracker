# リリース完了報告書 Release 2.0（精算）- 国際貨物輸送管理システム（java/take-6）

**報告書作成日**: 2026-08-11

## 概要

Release 2.0（精算）の完了報告書です。IT13〜IT15 の 3 イテレーション、**16 ストーリーポイントを 100% 達成**し、対象 4 ストーリー（US21 / US22 / US23 / US30）をすべて完了しました。

**Release 2.0 で「運んだのに請求できない」が解消されました。** v1.1.0 は予約から引取までを通しましたが、引取が済んだ貨物は「配送完了」のまま止まり、経理担当者にはダッシュボードのカードすらありませんでした。本リリースで**引取 → 料金算出 → 確定 → 請求書の発行 → 督促 → 入金確認 → 精算完了**が画面だけでつながります。加えて、**輸送中の予約キャンセルが承認を伴う業務**になりました。

## 技術的成果

### 新しい Bounded Context

**Billing Context を新規に立ち上げました。** Release 2.0 は BC 間の越境が最も多いリリースであり、ACL ポートが 7 本増えています。

| ポート | 向き | 役割 |
| :--- | :--- | :--- |
| `ShipperDiscountPort` | Billing → Shipper | 契約割引率 |
| `TrackingStatusPort` | Billing → Tracking | 引取まで完了したか（**9 値の状態を 1 ビットに変換**） |
| `BillableCargoPort` | Billing → Booking | 請求対象と輸送実績 |
| `CargoExceptionRecordsPort` | Billing → Tracking | 減額の根拠となる例外の記録 |
| `BookingSettlementPort` | Billing → Booking | 入金確認後に予約を `SETTLED` へ |
| `InvoiceNotificationPort` | Billing → Booking | 発行を荷主へ伝えた記録 |
| `ShipperContactPort` | Billing → Shipper | 督促のための**いまの**連絡先 |
| `CargoCurrentLocation` | Booking → Tracking | 陸揚げ地の候補を絞るための現在地 |

### 金額の扱い

- **丸めは切り捨て**（`RoundingMode.DOWN`）。荷主に不利な方向へ丸めない
- **段階丸め**（基本料金 → 調整 → 割引 → 消費税）。総額での一括丸めをしない
- **最小通貨単位の整数で保持**する
- **丸め後の値と税率を永続化**する。**税制改正の日に過去の請求書が書き換わらない**
- **キャンセル料に割引も調整も適用しない。** 割引は「運びきったこと」への取引条件である

### アーキテクチャ上の判断（ADR）

| ADR | 判断 |
| :--- | :--- |
| ADR-016 | 明細テーブルを作らず、料金調整を精算書の列で持つ（要求元のないものは作らない） |
| ADR-017 | 料金の状態を支払いの状態と分ける（督促の対象を選べるようにする） |
| ADR-018 | 一部入金を認めない（差額の扱いは業務であり、黙って受けると帳簿と合わない） |
| ADR-019 | 支払期限の超過は画面を開いたときに判定する（バッチは止まっても誰も気づかない） |
| ADR-020 | 請求書に種別を持たせ、二重請求は予約と種別の組で防ぐ |
| ADR-021 | BC 越しに状態を変えるポートは、失敗が届く先を名簿に登録する |

## レビュー結果

| IT | 高 | 中 | 低 | IT 内対応 |
| :--- | :--- | :--- | :--- | :--- |
| IT13 | 13 | 10 | 8 | 高 9 件 |
| IT14 | 18 | 19 | 8 | 高 13 件 |

**3 イテレーションとも、全緑の状態からレビューが高優先度の指摘を出しました。** 自動チェックが原理的に見ない領域（業務としてどう使うか・コメントと実装の一致・記録の有無・ADR との整合）に集中しています。

Release 2.0 で見つかった最も重い 3 件:

1. **「例外にしない」が「記録しない」に滑っていた**（IT14）。入金確認後に予約を精算済みにできなかったことが、ログにも画面にも残らなかった。**その予約は精算後も引取記録を訂正できた**
2. **ADR-009 の規則を、コードの半分が守っていなかった**（IT15）。「購読側は `REQUIRES_NEW`」と明記した後も、半分は守られないまま増えていた
3. **コメントが仕様を語りながら実装が守っていなかった**（IT15）。遷移表が #9 と #10 を分けて説明しながら、同じループで登録していた

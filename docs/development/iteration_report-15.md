## エグゼクティブサマリー

**業務シミュレーションが、例外を含めて自動で通り、実運用に近い状態を作り続けられる
ようになった。** Release 2.2 が完了した。

本 IT の価値は、機能そのものより**この仕組みが実際に欠陥を捕まえたこと**にある。
乱数が入力を選ぶようになった結果、実環境で **5 つの欠陥**が出た——いずれも
ユニット・結合・モック・E2E がすべて緑の状態からである。

とりわけ大きいのは、**生成器が選んだ入力が業務 API まで届いていなかった**ことが
分かった点である。IT14 まで緑だった実行は「一般貨物・同じ港・同じ期限」の 1 本しか
通しておらず、**冷蔵と危険物は一度も通っていなかった**。修正後、実環境で 55 件を
流して失敗 0 件になり、いま初めて「業務が通っている」と言える状態になった。

あわせて、IT14 から送った負債 10 件をすべて返済した。

## 達成状況

### US36: 例外を含む業務シナリオを自動実行する（3 SP）

| # | 受入基準 | 判定 |
| :--- | :--- | :--- |
| 36-1 | 例外シナリオ（遅延・破損・誤配・税関保留・輸送中キャンセル）を選んで実行できる | 達成 |
| 36-2 | 例外が記録され、対応（解決・組み直し・承認）まで含めて実行される | 達成 |
| 36-3 | 誤配シナリオでは、現在地からの経路が組み直されて輸送が再開する | 達成（**組み直し用の航海の登録が要ることは実環境で分かった**） |
| 36-4 | 例外シナリオの結果も、US35 と同じ形式で工程ごとに確認できる | 達成（**分母が選択中シナリオ固定だったのをレビューで指摘され修正**） |

### US37: ランダムな業務シナリオをバックエンドが継続実行する（5 SP）

| # | 受入基準 | 判定 |
| :--- | :--- | :--- |
| 37-1 | 乱数でシナリオ・出発地・目的地・貨物種別・重量・期限を選び、一定間隔で実行し続ける | 達成（**選んだ入力が届いていなかったのを自己レビューで発見。間隔もレビュー指摘で実装**） |
| 37-2 | 実行間隔・同時実行数・例外比率を設定でき、上限を超えて実行しない | 達成（**画面から設定できなかったのをレビューで指摘され修正**） |
| 37-3 | 種が記録され、同じ種を指定すると同じ並びを再現できる | 達成（**停止後に種を読む手段は IT16**） |
| 37-4 | 管理者が開始・停止でき、停止すると進行中は最後まで終えてから止まる | 達成 |
| 37-5 | 生成データは US34 と同じ印で識別できる | **一部**——荷主一覧・予約一覧・精算の締め対象・発行済み精算書・未解決例外からは外れる。**キャンセル承認待ち・荷役・通関の一覧はまだ混ざる**（IT16） |
| 37-6 | 本番環境では起動しない | 達成 |
| 37-7 | 実行中もヘルスチェックと実利用者の操作は劣化しない | **一部**——ヘルスチェックは達成（実環境で再起動 0）。**実利用者の一覧への混入が 3 か所残る**（IT16） |
| 37-8 | 実行の統計が US35 と同じ形式で確認できる | 達成（**分布から対象へ辿れなかったのをレビューで指摘され修正**） |

## 技術的成果

### ADR-031（ランダム継続実行）の 6 決定

| 決定 | 内容 |
| :--- | :--- |
| 1 | 種は実行に保存し、**乱数器は種から作り直す**（共有すると並行実行で並びが変わる） |
| 2 | スケジューラは simulationms の中に置く（外に出すと停止・再現・上限が別の場所で管理される） |
| 3 | 同時実行数は上限で守り、**ヘルスチェックは対象外**（IT7 の再発防止） |
| 4 | 停止は**新規の開始だけ**を止める（進行中は最後まで走る） |
| 5 | 例外は**実際に起きる操作**で起こす（専用 API を作らない） |
| 6 | 二重実行の拒否は**手で押す実行にだけ**効かせる |

**6 件すべて、実装を壊すと検査が赤になることを確認した**（[レビュー](../review/イテレーション15_review_20260901.md)）。

### 途中で見つけた、計画になかった問題

| 内容 | 影響 |
| :--- | :--- |
| **方言スモークが 2 サービスに無かった** | テスト戦略に「全サービスに置く」と書いてあったが検査が無く、billingms と simulationms が素通り。マイグレーションを持つ全サービスに要ることを検査にした |
| **マニフェストを読む検査が、マニフェストだけの変更では走らない** | Gradle の up-to-date 判定。IT14 が実際に踏んだ形の変更で安全装置が働かなかった |

| 運用手順書に simulationms が反映されていなかった | 手順どおりに構築すると 8 つ目のサービスだけ起動しない |
| `data-model.md` の列幅が実スキーマと 4 件食い違い | 設計側を実態へ修正 |

### Quality Gate が PASS にならない理由

未レビューの Security Hotspot 2 件（java:S2245・乱数の使用）が残る。
**中身を読んだうえで安全と判断している**（[ADR-031](../adr/031-random-continuous-simulation.md)
に根拠を記載）——`SecureRandom` に替えると決定 1（同じ種 → 同じ並び）が成立せず、
US37-3 の受入基準を満たせなくなる。

承認の記録には「Administer Security」を持つ利用者のトークン（`SONAR_ADMIN_TOKEN`）が
要り、**IT14 から未設定のまま**である。認証情報の問題であって、コードの問題ではない。

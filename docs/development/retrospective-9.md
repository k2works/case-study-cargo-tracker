# イテレーション 9 ふりかえり（KPT）

日付: 2026-08-25
対象: IT9（US29 通関申告の登録・管理／US30 輸送中の予約キャンセル承認、10 SP／返済枠 14 件）

## サマリー

計画 10 SP を達成し、**通関という関門が引取の前に立った**。US16 の引取は IT7 以来
「荷受人の確認」だけが歯止めで、通関書類は目視に委ねられていた。あわせて輸送中の予約に
承認フローが入り、船の上の貨物が行き先を失ったままキャンセルされる経路を塞いだ。

**返済枠は 14 / 14 完了**（3 IT 連続で全返済）。

本 IT で最も重かったのは、**サービス単体のテストが全部緑のまま、画面と実環境でだけ
成り立たない**欠陥が 3 件出たことである。

1. **営業の画面にキャンセル申請の入口が出なかった** — 集約に述語はあるのに、応答の操作
   一覧に載せていなかった。モックだけがその操作を返していた
2. **`/api/v1/cancellations` が Gateway のどこにも振られていなかった** — 画面からは 404、
   サービス側は無実。**本番プロファイルでは公開追跡とロック解除も同じ状態だった**
3. **E2E が新しいガードの手前で止まり、以前からの守りを踏まなくなっていた** — 通関ガードが
   先に立ったため、「荷受人の確認」を外しても緑のままになる状態になっていた

## Keep（続けること）

### 1. 実環境で通す枠（Phase 6）を計画に置く

IT8 の Try がそのまま効いた。上の 1・2 は**この枠が無ければ IT10 以降に持ち越されていた**。
どちらも「API のテストは 200 を返すので緑」「サービスのテストは自分の中では正しいので緑」
であり、**画面と Ingress を通して初めて姿を現す**。

IT8 はこの枠で 1 件、IT9 は 3 件を捕まえた。**枠の価値は上がっている。**

### 2. ADR の決定ごとに検査を置き、1 件ずつ壊して赤を確認する

ADR-025 の 10 決定すべてで実施した（IT8 は 11 決定のうち 3 件が空振り）。**壊した記録を
表に残す**ことを完了条件にしたのが効いた——「検査名を書いた時点では未完了」と決めていな
ければ、また同じ空振りが残っていた。

### 3. 設計との突合を検査に落とす（返済枠 0.1）

`data-model.md` の DDL と Flyway のマイグレーションを突き合わせる検査は、**置いた直後に
13 件の実ドリフト**を指した。列挙して約束する形（IT8 は 13 件中 12 件が未反映）とは、
残るものが違う。

## Problem（問題だったこと）

### 1. 画面を通す検査が、API を通す検査より薄い

上の Keep 1 で捕まえた 3 件は、いずれも**画面を通していれば早く出た**。IT9 の受け入れ
テストは API を直接叩く形が中心で、画面から踏む形は限られていた。

`availableActions` に依存する画面は今後も増える。**サーバが値を載せ忘れると画面には何も
出ないが、API は 200 を返す**——この形は構造的に再発する。

### 2. 検査の入力を宣言し忘れると、壊しても緑になる

`BookingActionRosterTest` は画面の型とモックを読むが、Gradle の入力に宣言していなかった
ため、**モックだけを壊しても検査が動かなかった**。返済枠 0.1 で同じ落とし穴を踏み、
対処法まで分かっていたのに、**新しい検査を書くときに再現した**。

### 3. 型検査が何も見ていなかった

`tsc --noEmit` は、プロジェクト参照構成（`files: []` + `references`）では**何も検査せず
終了 0 を返す**。未定義の関数を呼んでも通る。IT9 のクローズで初めて気づいた。

**緑を見て安心していた分、検査が無いより危ない。** 型検査は `tsc -b` である。

### 4. 5 視点の独立レビューが実施できなかった

クローズのステップ 1 で 5 エージェントを並列起動したが、**いずれも結果を返さずに終了**
した（再試行した 2 体も同じ）。5 つの観点を単一のレビュアーが順に通す形に切り替えている。

IT7・IT8 では**複数視点が独立に指摘したものが最も重い欠陥**だった。その効果が今回は
働いていない。見落としの可能性は通常より高いと考えるべきである。

### 5. 新しいガードが、以前からの検査を空振りにする

通関ガードを引取の手前に置いたことで、「荷受人の確認がない引取は断られる」テストが
**通関の段階で止まる**ようになった。テストは緑のまま（断られること自体は変わらない）
だが、**確かめたかった守りには一度も届いていない**。

守りを 1 段足すたびに、その後ろにあった守りの検査は同じ形で空振りしうる。

## Try（次に試すこと）

| # | アクション | 期待効果 | 反映先 |
| :--- | :--- | :--- | :--- |
| 1 | **応答の一覧に依存する画面は、画面から踏む受け入れテストを 1 本持つ**（Problem 1）。API のテストだけで済ませない | 「サーバが載せ忘れ → 画面に何も出ない」を、実環境の枠を待たずに捕まえる | IT10 の DoD |
| 2 | **検査がリポジトリのファイルを読むなら、その場で入力に宣言し、壊して赤を確認する**（Problem 2）。検査を書いた直後に必ず 1 回壊す | 「壊しても緑」の検査を作らない。**壊して赤を確認する手順に、入力の宣言確認を含める** | IT10 の DoD・`ai-agent-guidelines` |
| 3 | **新しい検査コマンドを使い始めたら、一度壊して赤になることを確かめる**（Problem 3） | 何も見ていないコマンドを「緑」と読み違えない | IT10 の DoD |
| 4 | **ガードを 1 段足したら、その後ろにある守りの検査が今も踏まれているか確かめる**（Problem 5）。前提を作ってから確かめる形に直す | 守りを足すたびに、以前の守りが静かに無検査になるのを防ぐ | IT10 の進め方 |
| 5 | **5 視点レビューが動かない場合の代替手順を決める**（Problem 4）。単一レビュアーで通したことを報告書に明記し、少なくとも「実装者以外の視点」を 1 つは独立に回す | レビューの独立性が失われたことを、静かに見過ごさない | `closing-iteration` の運用 |

## 次イテレーション（IT10）への引き継ぎ

1. **通関一覧の既定の絞り込み**（レビュー低 11）。いまは全件・申告日時の新しい順で、決着済み
   の申告も混ざる。留置 3 日超の件数から絞る導線はあるため仕事は進むが、「毎朝どう使うか」
   では未決着を先に出すほうが自然
2. **US33（荷主の担当者が自分の貨物だけを追跡する）の配置**。IT9 で起票した
   （[Issue #555](https://github.com/k2works/case-study-cargo-tracker/issues/555)）が、
   リリースへの配置は未定
3. **通知は依然として代替**（US29-4・US30-6・US30-7）。画面が「送られていない」と言う形で、
   仕組みでは埋めていない。Release 2.0 以降
4. **キャンセル料の算定は US21（Release 2.0）**。IT9 時点で billingms に受け口が無い
5. **陸揚げの作業指示は自動で作られない**（[ADR-025] 決定 5）。承認した追跡管理者から荷役の
   担当者へ連絡する運用ルールを添えている

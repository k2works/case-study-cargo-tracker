# リリース計画 - 国際貨物輸送管理システム (Haskell 版)

## 概要

本ドキュメントは、国際貨物輸送管理システム (Cargo Tracker) Haskell 版 take-1 のリリース計画を定義する。
Scala 版 take-1 の実績データ (26 ストーリー / 8 イテレーション完了) と Java 版 take-2 の実績をベースに、Haskell / 純粋関数型パラダイムへの再実装に伴う学習コスト (係数 1.20) を織り込んで策定する。

参照: [ADR 0001 Haskell + Servant スタック採用](../adr/0001-haskell-servant-stack.md)

### プロジェクト情報

| 項目 | 内容 |
| :--- | :--- |
| プロジェクト名 | 国際貨物輸送管理システム (Cargo Tracker) Haskell 版 |
| 目的 | DDD・純粋関数型パラダイム (Servant + ReaderT) による貨物予約・経路設計・追跡・精算機能の提供と、Java/Scala 版との比較学習 |
| 対象ユーザー | 荷主・予約担当・経路設計者・追跡担当・精算担当・マスタ管理者 |
| 開発チーム | 1 名 (AI ペアプログラミング) |
| 想定稼働時間 | 20 時間 / 週 |

## 満足条件

### スコープ

ユーザーストーリー 25 件 ([US01〜US25](../requirements/user_story.md)) を 4 フェーズに分けて段階的にリリースする。
真の MVP は **Release 1.0 (追跡照会まで)** とし、Release 0.1 は内部デモ用の予約受付基盤、Release 0.2 は経路設計フロー、Release 2.0 を例外処理・精算を含む GA とする。
認証 (フォームログイン + JWT/Cookie) は全機能の前提として IT1 で実装する (横断要件、US 番号なし)。

| フェーズ | 内容 | 対応 US 数 | リリース |
| :--- | :--- | :---: | :--- |
| Phase 1 | 認証 + 予約・荷主基盤 + 航海スケジュールマスタ | 9 | 0.1 Internal Alpha |
| Phase 2 | 経路設計・確定 | 5 | 0.2 |
| Phase 3 | 追跡・状態更新 + 料金算出 | 5 | 1.0 MVP |
| Phase 4 | 例外処理・割引・精算 | 6 | 2.0 GA |
| 合計 | | 25 | |

### スケジュール

- **開発期間**: 18 週間 (2026-07-06 〜 2026-11-06、予備 IT9 含む)
- **イテレーション**: 2 週間 × 8 イテレーション + 予備 IT9 (バッファ・ふりかえり改善)
- **リリース**:
  - Phase 1 完了 → **Release 0.1 Internal Alpha** (IT2 末)

  - Phase 3 完了 → **Release 1.0 MVP** (IT6 末)
  - Phase 4 完了 → **Release 2.0 GA** (IT8 末)

## 学習コスト係数の適用

Java 版 take-2 実績ベースに対し、Haskell の純粋関数型・型クラス・ReaderT パターン学習の影響を織り込み **係数 1.20** を主要ストーリーに適用する。
Scala 版より高めの係数とする理由:

- 型クラスポート (`class Monad m => CargoRepository m`) の設計判断が初期に集中
- postgresql-simple の `FromRow` / `ToRow` 手書きマッピング (ORM なし)
- Lucid の Haskell コードベース HTML 構築の慣れ
- hedgehog プロパティテストの設計コスト

特に経路候補算出 (US08) は最大リスク要素として **8 SP** (Java 版 5 SP の 1.6 倍)。

### 優先順位マトリックス

4 軸評価で優先順位を決定:

1. **金銭価値 (BV)**: ビジネス価値
2. **コスト (C)**: 開発コスト
3. **知識習得 (KA)**: 技術的学習価値
4. **リスク軽減 (RR)**: リスク軽減効果

## イテレーション計画

### 想定ベロシティ

- 初期 (IT1-IT2): 8 SP / イテレーション (技術スタック立ち上げのため)
- 中期 (IT3-IT6): 10 SP / イテレーション (定常運用)
- 後期 (IT7-IT8): 10 SP / イテレーション (例外処理の追加複雑性で相殺)

### イテレーション割り当て

| IT | 期間 | 含む US | 目標 SP | リリース |
| :---: | :--- | :--- | :---: | :--- |
| IT1 | 2026-07-06 〜 07-19 | 認証 + US02 + US03 + US04 + US24 | 13 | - |
| IT2 | 2026-07-20 〜 08-02 | US01 + US05 + US06 + US25 | 10 | **0.1 Internal Alpha** |
| IT3 | 2026-08-03 〜 08-16 | US07 + US08a + US27 | 11 | - |
| IT4 | 2026-08-17 〜 08-30 | US08b + US09 + US11 + US13 | 11 | **0.2** |
| IT5 | 2026-08-31 〜 09-13 | US14 + US15 + US16 + US18 | 10 | プレ MVP |
| IT6 | 2026-09-14 〜 09-27 | US21 + US26 | 5 | **1.0 MVP** |
| IT7 | 2026-09-28 〜 10-11 | US17 + US19 + US20 + US22 | 10 | - |
| IT8 | 2026-10-12 〜 10-25 | US23 + (ストレッチ: US10 + US12) | 3 + 5 | **2.0 GA** |
| IT9 (予備) | 2026-10-26 〜 11-08 | バッファ・改善・ふりかえり・低優先度指摘 | - | - |

> 78 SP を 8 IT で消化 = 平均 9.75 SP/IT。学習による IT1-IT2 のスループットを 10-13 SP、安定期 IT3-IT8 を 10-11 SP で見積もる。
> IT5 で US18 を前倒し配置 (M-01 反映) し、IT5 末でプレ MVP デモを実施して荷主フィードバックを早期取得する。
> IT8 は確定 US23 (3 SP) + ストレッチ US10/US12 (5 SP) = 最大 8 SP。ストレッチ消化が困難な場合は IT9 へ。

## リリース判定基準

各リリースで以下を満たすこと。

### Release 0.1 Internal Alpha (IT2 末)

- [ ] 認証 (ログイン・ログアウト・ロール RBAC)
- [ ] 荷主登録 (個人・法人)
- [ ] 貨物予約登録 (一般・危険物・冷凍)
- [ ] 航海スケジュール CRUD
- [ ] 内部デモ可能 (Internal Alpha)
- [ ] 単体テストカバレッジ Domain ≥ 95%
- [ ] 単体テストカバレッジ Application ≥ 80% (M-02 反映)

### Release 0.2 (IT4 末)

- [ ] Release 0.1 の全機能
- [ ] 経路設計フロー (検索・候補算出・選択・紐付け・制約評価)
- [ ] 予約確定フロー
- [ ] 通関情報の予約紐付け (US27)
- [ ] hspec-wai による API 統合テスト整備

### Release 1.0 MVP (IT6 末)

- [ ] Release 0.2 の全機能
- [ ] 追跡番号発行・追跡情報照会 (公開ページ含む)
- [ ] 荷役作業登録 (引取確認含む)
- [ ] 輸送料金算出
- [ ] 荷受人への引取通知 (US26)
- [ ] **MVP として外部公開可能**
- [ ] E2E (Playwright) 主要 3 シナリオ Pass
- [ ] 非機能要件チェックリスト (P95 < 500ms / RTO 1h / SLA 99.5%) 達成
- [ ] CI で負荷スモークテスト (k6/wrk) 実行 (H-08 反映)

### Release 2.0 GA (IT8 末)

- [ ] Release 1.0 の全機能
- [ ] 例外処理 (遅延・破損・紛失)
- [ ] 割引適用・精算処理
- [ ] 経路再設計 (US10) と経路通知 (US12) — ストレッチ目標
- [ ] 監査ログ 7 年保持
- [ ] 全 27 US (US01-US27) の受け入れ基準を満たす
- [ ] 運用要件チェックリスト全項目達成

## リスクと対策

| リスク | 影響 | 対策 |
| :--- | :--- | :--- |
| Haskell 学習コスト超過 | スケジュール遅延 | IT1-IT2 に重点学習時間配分。型クラスポート・ReaderT パターンを最初に確立 |
| 経路候補算出 (US08) の複雑度 | IT3-IT4 のオーバラン | IT3 で前半着手、IT4 で残りを完了する 2 イテレーション分割 |
| postgresql-simple 手書きマッピングのコスト | 各 IT のリポジトリ実装遅延 | 共通変換ヘルパー (`enumFromText`, `parseStatus` 等) を IT1 で整備 |
| 外部 ACL ポートのモック整備 | 統合テスト着手遅延 | IT2 で WireMock スタブ + 型クラステストダブルパターンを確立 |
| GHC / Stack の CI 環境問題 | デプロイ遅延 | IT1 で GitHub Actions + Stack キャッシュを動作確認 |
| ベロシティの過大評価 | スコープ未消化 | 予備 IT9 で吸収。Phase 4 の中優先度ストーリーを IT9 候補に |

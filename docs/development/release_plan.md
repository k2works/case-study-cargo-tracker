# リリース計画 - 国際貨物輸送管理システム（java/take-6）

## 概要

本ドキュメントは、国際貨物輸送管理システムのリリース計画を定義します。

**スコープの区切り（どの US をどのリリースに入れるか）の正典は [リリーススコープ定義](release_scope.md) です。** 本ドキュメントはそこに**ストーリーポイント・イテレーション分割・スケジュール**を与えるものです。スコープを変更する場合は先に `release_scope.md` を更新してください。

### プロジェクト情報

| 項目 | 内容 |
|------|------|
| **プロジェクト名** | 国際貨物輸送管理システム（Cargo Tracker） |
| **目的** | 国際貨物輸送の予約から追跡・精算までを一貫して管理し、予約業務の効率化・最適ルート設計・リアルタイム追跡・例外対応の迅速化を実現する |
| **対象ユーザー** | 荷主・荷受人・営業担当者・経路設計者・追跡管理者・荷役作業員・経理担当者 |
| **開発チーム** | 1 名（AI ペアプログラミング） |
| **ブランチ** | `java/take-6` |

> 唯一のリリース**であり、`ShipperDiscountPort` / `TrackingStatusPort` / `BookingSettlementPort` の

> 「丸め後の値を永続化し、再計算で導出しない」と定めています。**発行済み請求書の金額は
> 税率が変わっても変わってはならない**ためであり、ここを取り違えると過去の請求が書き換わります。

> **US22 の設計是正は完了しています。** 旧版の `DiscountPolicy.calculateRate(shipperType, amount)` は
> 荷主種別と金額から割引率を算出する設計で、US03 / US22 が要求する「荷主ごとの契約割引率」を
> 参照していませんでした（レビュー H15）。`domain-model.md` で `ShipperDiscountPort` 経由に改めてあり、
> **契約割引率を保持する `CorporateContract` は IT7 で実装済み**です。US22 は設計どおりに実装できます。

#### 5SP の根拠（他ストーリーとの突き合わせ）

**感覚ではなく、実績のあるストーリーと並べて決めます。**

| 比較対象 | SP | US01 との違い |
| :--- | ---: | :--- |
| US29 通関申告を登録・管理する | 5 | **同じ形**（集約 1 つ＋一覧 / 登録 / 詳細の 3 画面）。US01 は BC 新設の分だけ重い |
| US30 輸送中の予約キャンセルを承認する | 5 | 集約新設＋ACL 2 本＋イベント発行で 5。**US01 はイベントを持たない分だけ軽い** |
| US08 経路候補を算出する | 8 | **探索そのものを作る**回。US01 は Routing の探索を再利用するため、ここまでは要らない |
| US04 貨物予約を登録する | 5 | 集約＋1 画面＋検証。US01 は画面が 3 つある分だけ重い |

**5SP とします。** BC 新設で重くなる分と、探索・料金算出を再利用できる分が相殺します。

#### 見積が軽く済む理由（**着手前に確認済み**）

| 要素 | 状態 |
| :--- | :--- |
| `estimate` / `route_candidate` テーブル | **V1 から存在する**（マイグレーション不要） |
| ドメインモデル（`Estimate` / `RouteCandidate` / `EstimateStatus`） | `domain-model.md` に定義済み |
| 画面（一覧 / 作成 / 詳細）と遷移 | `ui_design.md` に定義済み（`/estimates`） |
| ナビゲーション「見積管理」 | `ui_design.md` の構成表に ROLE_SALES で記載済み |
| 経路の探索 | Routing に実装済み（US08） |
| 概算料金 | Routing の `FreightEstimator` に実装済み（ADR-008） |

**未実装なのは Java のコードだけ**です（`estimation/` は `package-info.java` のみ）。

#### 着手前に決着させること（**IT17 の Try T6**）

**正典が食い違っています。着手前に決めます。**

`domain-model.md` の Estimation Context は「**ルート候補はスタブ実装（固定値）で生成される。
将来、外部ルーティングサービスとの連携時に置換予定**」と書いています。これは Routing に本物の
探索が無かった時期の記述です。

- **ADR-006 は外部連携を採らないと決めています。** 「将来の外部サービス」は来ません
- **Routing には US08 で本物の探索が入りました。** 固定値を返す見積は、**画面は動くのに数字が
  現実と無関係**という状態になります

**ACL ポートで Routing に問い合わせる形を第 1 案とします。** ただしこれは設計判断であり、
`domain-model.md` の記述の改訂と ADR を伴います。**IT18 の開始準備で決着させ、
決めてから着手します**（IT17 の A1 と同じ手順）。

> **決着が「スタブのまま」になった場合、SP は 3 に下がります。** 逆に Estimation 側に独自の
> 探索を作る判断になれば 8 です。**5SP はこの決着が第 1 案どおりになる前提の数字です。**

### ベロシティの再計算（IT3 終了時 / IT4・IT5 で再確認）

**初期値 12SP は過大でした。実績の平均 8SP を新しいベロシティとします。**
**IT9 終了時点の平均は 7.89SP で、採用値 8SP との差は 0.11SP です。再調整はしません。**
9 イテレーション連続で計画 SP = 実績 SP であり、**8SP は安定した見積もりの単位**になっています。

> **IT10・IT11 の 10SP は据え置きます。** IT9 終了時の実績で見直すと決めていましたが、
> 8SP が安定しているのは「計画分 ＋ 想定外」を吸収した結果であり、**上限を測れた
> わけではありません**。IT9 は計画 74.5h に対し、レビューの高優先度 9 件と
> SonarQube 7 件が計画外で乗りました。10SP は据え置き、**超過が見えた時点で
> ストーリーを落とす順序を計画に先に書く**という IT9 のやり方を続けます。

ただし 10 イテレーションとも「計画どおり完了」であり、**上限は測れていません**。

> **IT10 で初めて 10SP を達成しました。** ただしこれは「8SP が過小だった」ことを
> 意味しません。**計画に書いた順序どおり C9（3.0h 相当）を落として達成しています**。
> 落とす順序を先に決めておいたことが効いた、というのが正しい読み方です。
> IT11 も 10SP を据え置き、同じやり方を続けます。
各 IT で計画外の作業（地ならし・実バグの修正）が毎回発生しており、**8SP は
「計画分 ＋ 想定外」を吸収した結果**です。IT1 の時点で立てた
「地ならしが一度きりか毎回起きるか」という問いの答えは**毎回起きる**でした。

**したがって 8SP を上限として扱い、これを超える計画は立てません。**

> IT1 では計画外の作業が発生しました。マルチパースペクティブレビューで見つかった
> 高優先度 10 件の修正、SonarQube の整備、脆弱性 30 件の解消です。**これらは SP に
> 計上していません。** 見積もりの対象はユーザーストーリーであり、品質を満たすための
> 作業はストーリーの一部だからです。ただし**次の IT の計画では、この地ならしが
> 一度きりだったのか毎回起きるのかを見る必要があります**。

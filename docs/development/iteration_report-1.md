# イテレーション 1 完了報告書

## エグゼクティブサマリー

計画した 4 ストーリー（9 SP）をすべて実装し、ローカル統合（kind）と開発環境（Heroku）で動作を確認しました。あわせて以降 11 イテレーションが乗る**品質ゲートを実配線**しました（ArchUnit の全サービス適用・カバレッジ検証・CI・E2E・方言スモーク）。

この基盤投資が早々に効き、実装中に **5 件の実欠陥**が自動で検出されました。一方、クローズ時のレビューで**全テストが緑のまま素通りしていた欠陥が 3 件**見つかっており、「検査を入れたこと」と「検査が働くこと」の差、およびモックが安全網を無効化する構造が課題として残りました。

## 実施内容と評価

### 達成したこと

- **品質ゲートの実配線**。ArchUnit を共有配置で全サービスに適用し、未適用サービスを落とすメタテストを設置。カバレッジ検証を `check` に紐付け、CI と E2E 基盤を整備
- **アウトサイドインの徹底**。UI のニーズから API 契約を導出し、同じ変更で設計ドキュメントに反映。契約の手戻りは 1 度も発生しませんでした
- **破壊検証の習慣化**。安全装置を入れたら壊して赤を確認する運用により、「入れたのに働いていない」検査を 3 つ発見しました
- **実機確認**。kind と Heroku の両方で、認証・認可・ロック・荷主登録の全経路を確認

### 実装中に検査が見つけた実欠陥（5 件）

| # | 欠陥 | 検出した検査 |
| :--- | :--- | :--- |
| 1 | 公開経路 `/api/v1/tracking/**` が追跡管理者専用 API まで無認証で通していた | public-paths の破壊検証 |
| 2 | JWT フィルタがヘルスチェックまで 401 にし、再起動ループに入った | kind 統合の実機確認 |
| 3 | `#{keyword} IS NULL` が PostgreSQL でのみ実行時エラー | 方言スモーク（強化後） |
| 4 | シードの BCrypt ハッシュが実際のパスワードと不一致 | 結合テスト |
| 5 | 未実装メニューが行き先のないリンクだった | マニュアルのキャプチャ生成 |

### 検査自体が空振りしていた（3 件・いずれも破壊検証で発見）

- メタテストが Gradle の up-to-date でスキップされ、実行されないまま緑になっていた
- 方言スモークが `prepare` だけで、パラメータ型が決まらない欠陥を素通りさせていた
- 破壊検証の違反例（`~` 演算子）が H2 の互換モードでも解釈され、違反になっていなかった

## イテレーションレビュー

XP 5 視点で 137 ファイルをレビューし、**高 14 件・中 10 件・低 6 件**を検出しました（[統合レポート](../review/イテレーション1_review_20260819.md)）。

**高 14 件はすべてクローズ前に対応済み**です。特に重いものは次の 3 件で、いずれも全テスト緑をすり抜けていました。

1. **認証トークンが一度も API 呼び出しに載っていなかった**（`configureAuth` 未配線）。実バックエンドに対しては荷主機能が必ず 401 になる状態でした。フロントの検証が MSW モック越しであることが原因です
2. **ロック解除が名目だけだった**。失敗回数が持ち越されるため、15 分経って解除されても 1 回の誤入力で即再ロックされ、正規の利用者は事実上パスワードを 1 回も間違えられませんでした
3. **担当外ロールのダッシュボードが全部行き止まりだった**。押すと公開トップに戻され、利用者には「勝手にログアウトされた」と見えます

中 10 件は IT2 の返済枠として[ふりかえり](retrospective-1.md)に計上しました。

## 課題と残作業

### クローズ時点で未完了の項目

| 項目 | 状況 | 対応 |
| :--- | :--- | :--- |
| CI の緑確認 | **未実行**。ブランチが 19 コミット ahead で未 push | push 後に確認する。DoD の唯一の未達項目 |
> クローズ作業の途中で Docker Desktop が応答しなくなり（API 500）、Testcontainers・SonarQube・
> ドキュメントサイトのビルドが一時的に確認できませんでした。Docker Desktop の再起動で復旧し、
> **結合テストと SonarQube の品質ゲートはいずれも確認済み**です。

> あわせて、この過程で SonarQube のスキャン設定自体が未整備であることが分かりました
> （スキャン対象の定義が無く、既定の架空プロジェクトを見ていた）。バックエンド（Gradle）と
> フロントエンド（scanner）の 2 プロジェクトを定義し、カバレッジとテスト結果の連携まで
> 整備しました。

> **Docker 再起動後の一斉起動で 7 サービスが再起動ループに入る欠陥も見つかりました。**
> Spring Boot の初期化が liveness の猶予を超え、正常に起動中のコンテナが繰り返し
> 殺されていました（殺されるたびに負荷が増える悪循環）。`startupProbe` を入れて解消し、
> 全 10 Pod が Ready・再起動 0 で安定することを確認しています。これは IT1 で踏んだ
> 「ヘルスチェックを認証の対象から外す」と同型の失敗で、今回は防御ではなく probe の猶予が
> 実態に合っていませんでした。

### 技術的負債

- レビューの中 10 件（IT2 の返済枠）
- Gateway をバイパスできないことが、どこでも検査されていない（ADR-004 の前提）
- E2E がモック相手である限界の線引きが test_strategy に明文化されていない

## KPT 分析

### Keep（継続すること）

#### 技術的成功

- **CQRS パターンの導入（TrackingQueryService）**: trackingms に読み取り専用のクエリサービスを分離し、コマンドとクエリの責務を明確化した。SonarQube の Code Smell も発生せず、保守性の高い設計を実現できた

- **DB SEQUENCE による追跡番号一意性保証**: Flyway マイグレーション（`V2__add_sequence.sql`）で PostgreSQL SEQUENCE を導入し、`TrackingNumber` 生成の一意性を DB レベルで保証した。IT4 コードレビューの高優先度指摘（H1）を根本的に解決できた

- **専用例外クラスの導入**: `TrackingActivityNotFoundException` を `domain.exceptions` パッケージに新設し、文字列比較による分岐を排除した。ドメイン層のエラーハンドリングが型安全になり、コンパイル時にエラーを検出できるようになった

- **SonarQube Quality Gate PASS の継続（5 イテレーション連続）**: new_violations: 0、重複率 1.06% と高い品質水準を維持。`CargoCommandServiceTest` の Code Smell も同イテレーション内で解消した

- **フロントエンドテストの着実な増加**: IT4 の 26 件から 35 件へ +9 件増加。`TrackingPage` の照会画面テスト（正常・404・自動更新・例外バッジ）を網羅的にカバーした

#### プロセス的成功

- **IT4 コードレビュー指摘の計画的解消（TI02）**: IT4 と同様に、高優先度指摘を最初のタスクとして配置し技術的負債を早期解消してから新機能開発に着手するパターンが定着した

- **イベント駆動設計の踏襲**: `CargoAssignedForRoutingEvent` を IT2 で確立した `CargoRoutedEvent` パターンに倣って実装。マイクロサービス間の疎結合を維持しながら予約引渡し機能を実現できた

- **stub 実装によるインターフェース分離**: `ShipperNotificationPort` をインターフェースとして定義し、stub 実装（ログ出力のみ）で IT5 の受入条件を満たした。将来のメール通知実装への差し替えが Open/Closed 原則に沿って容易に行える

### Problem（課題）

- **IT5 計画の一部タスクが未完了**: イテレーション計画のタスク 1.5（リグレッションテスト・SonarQube 確認）、4.4（通知サービステスト）、4.6（通知バッジテスト）が未完了のままイテレーション完了とした。テスト結果・SonarQube 結果は確認済みだが、チェックリスト上の漏れは課題

- **Playwright E2E テストの先送り継続**: IT4 から持ち越した E2E テスト整備が IT5 でも実施できなかった。IT6（MVP 統合・E2E）で本格的に着手する必要がある

- **bookingms → trackingms 状態連携の未完了**: IT4 から持ち越した US14 受入条件 4（TRACKING_ISSUED 遷移の RabbitMQ イベント連携）が IT5 でも未実装のまま。IT6 以降で対応が必要

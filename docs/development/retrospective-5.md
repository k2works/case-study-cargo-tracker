## Keep（うまくいったこと）

### 技術的成功

1. **導出状態（`currentStatus`）の徹底**: Tracking の状態を保持フィールドにせず、イベント履歴から純粋関数で導出。状態の二重管理と復帰バグを構造的に排除し、`transport_status` はクエリ用の非正規化キャッシュと明示。domain-model の意図に忠実。
2. **不正状態の型排除**: `HandlingType` の `Load`/`Unload` にのみ `VoyageNumber` を型で埋め込み、Receive/Claim には持たせない。優れた ADT モデリングで「LOAD なのに航海番号なし」を表現不能にした。
3. **BC 間イベント駆動の完成**: 合成層（`BookingEventConsumer`・`HandlingAcl`）に BC 連携を閉じ、各ドメインは他 BC を参照しない。ArchUnit に Tracking/Handling の BC 分離ルールを追加し常時緑を維持。
4. **ADR-0002 の負債返済**: IT2-IT4 で 3 イテレーション放置された「ADR と実装の三重不整合」を、実装実態（BC ローカル DU + アプリ/合成層 post-commit）へ ADR を改訂して決着。デッドコード（UnitOfWork）を削除し、負債を可視な形で清算した。
5. **一気通貫 E2E**: 予約確定→追跡番号自動発行→荷役→照会を単一テストで縦貫通させ、BC 連携の意味的完全性を保証。

### プロセス的成功

1. **セルフレビューの中間適用が有効**: xp-tester が「Misrouted フィードバックが計算されるが画面に届いていない（テスト欠如で素通り）」を検出。正式レビュー前に受入テスト込みで是正でき、テストファーストの価値が出た。
2. **設計判断の即時ドキュメント化**: TrackingStatus 導出値・access_token・ADR-0002 改訂を計画・data-model・domain-model・ADR へ完了時反映。ドリフトを持ち越さなかった。

## Problem（課題）

1. **荷役→追跡の原子性欠如**: 荷役登録（別トランザクション・自前コミット）成功後に追跡イベント記録を別トランザクションで行うため、追跡記録が失敗すると乖離しうる。ベストエフォート＋ログ化で緩和したが、完全な原子性（単一トランザクション）は未達。
2. **US14 通知の recipient が追跡番号**: `notification_log` の recipient に追跡番号を流用しており、荷主軸で通知履歴を引けない。実送信・荷主メール解決は未実装（IT4 から継続）。
3. **Web ハンドラの通知方針の不統一**: 手動更新・荷役連携は no-op notifier、番号発行は notification_log 記録と経路ごとに異なる。`TrackingNotifier` の doc と実挙動が乖離。
4. **追跡照会の所有者チェックなし（設計判断）**: 追跡番号を知れば他人の貨物を閲覧可能。US18「追跡番号があれば照会できる」に沿った capability ベース設計だが、認証あり経路での追加防御はゼロ。
5. **`syncEvents` の全置換**: 追跡イベントを毎回全削除→全挿入するため、イベント数増加で書き込みが O(n)。append-only にできる余地。

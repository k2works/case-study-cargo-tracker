## Keep（継続すること）

### 技術的成功

- **イベント駆動の BC 連携で疎結合を実現した**。予約確定→追跡番号発行（`BookingConfirmedEvent`）、荷役登録→追跡イベント追記・予約状態同期（`HandlingActivityRegisteredEvent`）を post-commit ドメインイベント＋各 BC のハンドラで実装。BC 間を同期呼び出しで密結合させず、各コンテキストが自分の状態を自分で更新する形にできた。ArchUnit（6 件）も終始グリーン。
- **ACL パターンをプリミティブ DTO で一貫させた**。`ISelectedRouteLookup`（IT4）に続き、`ICargoSnapshotProvider`（荷役の妥当性検証）・`ITrackingNumberResolver`（追跡番号→予約番号）を SQL 直接参照＋Handling 側プリミティブで実装。Booking/Tracking の内部型に依存せず BC 独立を保った。
- **UnitOfWork を post-commit ハンドラ対応に修正した**。イベント発行前にトランザクション・アンビエントを解放することで、ハンドラが自身の UoW（新トランザクション）を開始できるようにし、ADR-0006 のネスト前提を侵さずに複数 BC を跨ぐ状態同期を成立させた。基盤の一手が US14-16 の連鎖を可能にした。
- **中盤の主戦場（荷役の妥当性検証）をドメインに凝集した**。`HandlingActivity.IsValidFor` に場所判定デシジョンテーブル（RECEIVE=出発港/LOAD=積込港/UNLOAD=荷降港/CLAIM=目的港、積込荷降しの不一致は MISROUTED）を凝集し、6 ユニットテストで網羅。ドメインロジックが薄いコントローラに漏れなかった。
- **IT4 レビュー高優先 H1-H7 を Week 1 前半で先行消化**。技術的負債を新規実装に持ち込まず、経路選択のインデックス依存の是正（候補キー照合）・確定経路の予約詳細表示・真実の源泉明文化などを完了。副次的に潜在バグ（BookingStatus の永続化 SCREAMING_SNAKE 不一致）も発見・是正した。

### プロセス的成功

- **計画着手前の 2 段階検証（validating-iteration-plan → validating-design）が再び有効**。コマンド名・HandlingType・CargoSnapshot・TransportStatus 9 段階の乖離を開発着手前に確定し docs/design を正に修正してから実装した。
- **Ralph Loop による層単位の反復消化**で、各コミットで全テスト緑・警告 0 を担保しながら 17 SP＋レビュー是正を着実に消化できた。
- **繰り越しの AI 完結分（ADR-0008・US10 記録要否）を確実に処理**し、3 イテレーション跨ぎの積み残しを減らした。

## Problem（問題点）

- **BookingStatus の永続化バグが長く潜在していた**。enum `RouteProposed` を `ToString().ToUpperInvariant()` で永続化すると "ROUTEPROPOSED"（アンダースコアなし）になり、ビュー・ラベルの "ROUTE_PROPOSED" 比較が一度も一致していなかった（ボタンが表示されない）。US14-IT4 のテストが「直接 POST」で操作していたため画面表示を検証しておらず、H6/H7（予約詳細 UI）の実装で初めて露見した。列挙型と DB 文字列の変換規約が明文化されていなかったことが根因。
- **プレースホルダ実画面化時のルート衝突が 2 回発生**。/tracking・/handling・/public/tracking の IT1 スタブが実コントローラと重複し 500（AmbiguousMatch）になった。実画面化のたびに対応スタブを撤去するチェックが手順化されていなかった。
- **ステータス表現変更のテスト seed ドリフト**。BookingStatus を SCREAMING_SNAKE に統一した際、統合テストが直接 SQL で 'ROUTEPROPOSED' を seed していた箇所が全テスト実行で初めて失敗した。個別フィルタ実行では気づけなかった。
- **品質ゲートが 3 イテレーション連続で繰り越し**。カバレッジ 85% ハードゲート・SonarQube SQ-2〜5・Playwright E2E が IT3/IT4 から IT5 まで持ち越された。いずれも環境操作（`operating-qt`・CI 設定・ブラウザ）が前提で Ralph Loop 内では着手できなかった。
- **US15 の荷役→追跡状態同期の実イベント経由 E2E を完全にはアサートできていない**。ハンドラ単体・リポジトリ往復・コマンドは検証したが、実 MediatR 発行を通した End-to-End（荷役登録→追跡照会で状態反映）の Web テストは US18 の追跡表示が揃うまで見送った。

## ベロシティと計画への反映

- IT5 実績 **17 SP**（計画どおり・過去最高）。IT1=13・IT2=10・IT3=14・IT4=12・IT5=17 で平均 **13.2 SP/IT**。超過リスク（US17 調整候補）を懸念したが、IT4 レビュー是正の先行消化を含めても計画内に収まった。
- 残 SP: **19 SP**（Release 1.1 まで IT6-7）。バーンダウンは計画線に追従。
- **Release 1.0（MVP・Phase 1・66 SP）の機能実装が完了**し出荷条件を充足。次は終盤（IT6-7・アウトサイドイン）で例外対応・請求精算を業務シナリオ起点で結合する。局面移行（IT5→IT6）に際し、中盤で作り込んだドメイン中核（Booking/Routing/Tracking/Handling）を終盤で再利用する。

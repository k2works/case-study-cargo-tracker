# イテレーション 13 ふりかえり

| 項目 | 内容 |
| :--- | :--- |
| イテレーション | IT13（2026-11-02 〜 2026-11-15 想定・**Release 2.1・予備 IT**） |
| 対象 | US33（5 SP）・TD-01（2 SP）= **7 SP** |
| 実績 | **7 SP（達成率 100%）** |
| レビュー | [高 3 件・中 7 件・低 3 件](../review/イテレーション13_review_20260828.md)。高はすべて対応 |

## Keep

### 1. 決定どうしが出会う筋を、着手前に書き出した（IT12 Try 1）

IT12 の Problem 1 は「決定は単体では正しく、誤りは組み合わせに出た」だった。本 IT は
「着手前に決めること」の表に**組み合わせて効く既存決定の列**を置き、A〜E の 5 件すべてで
既存決定（[ADR-008](../adr/008-shipper-role-scope.md) の紐付け前提・[ADR-024](../adr/024-tracking-manual-update-and-exceptions.md) の公開照会・[ADR-005](../adr/005-token-storage-in-session-storage.md) の `sessionStorage`）と突き合わせてから決めた。

- 公開追跡（認証不要）と荷主向け追跡（認証あり）が**同じ URL を共用しない**ことを、
  実装前に決められた（決定 C）。共用していれば、他社貨物の 404 は後から足す話になっていた
- 未紐付け利用者を 403 ではなく `200 + linked=false` にする判断（決定 D）も、
  「認証は通っているが業務上の紐付けが無い」という状態を先に言語化したから出た

### 2. ADR に書いた検査名を、機械で実在確認した（IT12 Try 2）

IT12 では ADR-028 のコンプライアンス表が挙げる 5 クラスが 1 つも実在しなかった。
本 IT は `AdrComplianceTableTest` を ADR-029 にも適用し、**表に名前を書いた時点で実在が
確かめられる**状態にした。作文に戻る余地を機械で塞いだ。

### 3. 「翻訳する」と書いた先を、同じ変更の中で書いた（IT12 Try 3）

「自社貨物だけ」を 3 つに翻訳し、**それぞれに検査を置いた**——API 認可（`system:trackingms`
だけが CargoSnapshot を読める）・Repository の絞り込み・E2E（他社追跡番号で 404）。
翻訳したところで満足する形（IT12 Problem 3）を繰り返さずに済んだ。

### 4. 3 度目の負債を、返済枠ではなく SP 付きタスクで返した

「例外の実績を trackingms から引く」は IT11・IT12 と 2 度落としていた。本 IT は Phase 0.2 に
**赤いテストとして**置き、US33 の一覧が例外を出すために必要であることを先に確かめた。
「余力次第の返済枠」に置いていれば、3 度目も落ちていた。

### 5. 実バックエンドを通し、手順書に順序を書き戻した

`IT13 実環境` の E2E を kind の実クラスタで通した。ここで踏んだ
`dev:k8s:apply -> dev:k8s:rollout:image` の順序を
[アプリケーション開発環境セットアップ手順書](../operation/アプリケーション開発環境セットアップ手順書.md)に書き、
前提サービス（frontend / Gateway / 全 backend / PostgreSQL / RabbitMQ）も明記した。
次に実 E2E を流す人が同じ 500 を踏まない。

## Problem

### 1. クラスタへの反映順序を間違え、実環境だけが 500 になった

`apply` の前に `rollout` したため、trackingms → authms の内部 REST が **`localhost` を向いたまま**
起動し、荷主向け一覧が 500 を返した。ユニット・結合・モック E2E はすべて緑だった。

> **同型は IT5（経路の確定）・IT12（見積の試算先）でも起きている。3 度目である。**
> 本 IT の対処は手順書への記載であり、**検査にはなっていない**。

### 2. 実行済みの証跡と、計画の状態表がずれていた（レビュー高 1・2）

Phase 6.1〜6.4 を実行し終えたのに、計画書の DoD とカバレッジの成功基準は未チェックのまま
だった。レビューの高優先度 3 件のうち 2 件が**この記録のずれ**である。
実装の欠陥ではないが、「どこまで終わっているか」を計画書から読めない状態を作っていた。

### 3. SonarQube の Hotspot は、形そのものを解いていない

IT12 から送った「毎回 UI 操作を要する形」（3 度目）に対し、本 IT でしたのは
**ゲート条件を `new_security_hotspots_reviewed=100.0` で自動判定すると決めた**ことだけである。
新しい Hotspot が出れば、また利用者に UI 操作を頼む。走査トークンの権限問題は残っている。

### 4. 保留にした中優先 3 件は、実データが増えると壊れる形をしている

スコープ判断として送ったが、性質が違うものが混ざっている。

- `findRecent(100)` の後で所有判定している——**自社貨物が直近 100 件から落ちると、
  荷主の一覧から消える**。件数が増えたときに初めて出る
- `user_shipper_link.shipper_id` が UNIQUE——**1 荷主に複数の担当者を置けない**。
  法人荷主では普通に起きる
- E2E helper の `E2E_API_BASE_URL` 利用と相対 URL が混在——検査の再現性の問題

「IT13 の業務量では許容」は正しいが、**いつ壊れるかを受入基準に落としていない**。

## Try

| # | Try | 理由 | 次イテレーションでの扱い |
| :--- | :--- | :--- | :--- |
| 1 | **実環境確認は `apply` → `rollout:image` → `rollout:restart` の 3 手を必ず踏む** | Problem 1。3 度目である | 手順書に書いた順序を、実 E2E タスクの前提として計画の Phase に明記する |
| 2 | **設定の向き先が実クラスタのマニフェストに現れることを、新サービス経路ごとに検査する** | Problem 1。IT12 で `APP_*_SERVICE_BASE_URL` の検査を作ったが、**trackingms → authms の新経路は検査に載っていなかった** | 内部 REST の呼び先を足したら、同じ変更でマニフェスト検査の対象に加える |
| 3 | **Phase を終えたら、同じコミットで DoD と状態表を更新する** | Problem 2。レビュー高 3 件のうち 2 件が記録のずれ | 進捗コミットの単位を「実装 + 計画書の状態」にする |

| 5 | **Hotspot は出た時点で中身を読み、実欠陥かを先に判定する** | Problem 3。過去 take では 3 IT 持ち越した 1 件が実際の欠陥だった | UI 承認を依頼する前に内容を読む運用を続ける |
| 6 | 着手前の整合性検証を続ける | 本 IT でも設計反映 5 件を着手前に潰した | 継続 |

| 8 | レビューは 5 視点そろうまで待つ | 本 IT も 5 視点そろえた | 継続 |

## 次イテレーション（Release 2.2）への引き継ぎ

**Release 2.1 は完了し、計画した 13 イテレーション（110 SP + バッファ 2 SP）をすべて消化した。**
以降は Release 2.2 候補バックログから選ぶ。

| # | 内容 | 見積 | 送るのは何度目か |
| :--- | :--- | :--- | :--- |
| 1 | **請求書の検索（請求番号・荷主名・予約番号）と発行月の絞り込み・合計** | 5h | **3 度目。** 経理担当者から 3 IT 連続。月末の締めが表計算に落ちたまま |
| 2 | 見積に荷主を入れる（割引後・荷主で探す・突き合わせに含める） | 4h | 2 度目 |
| 3 | 荷主向け一覧の所有判定を Read Model へ降ろす（`findRecent(100)` の外に自社貨物が落ちる） | 4h | 1 度目 |
| 4 | 1 荷主に複数担当者を紐付ける（`user_shipper_link` の UNIQUE を外す） | 3h | 1 度目 |
| 5 | `overdue()` の全件走査と `billable()` の N+1 を SQL に降ろす | 4h | 2 度目 |
| 6 | 「請求書」と「精算書」の混在 | 4h | 3 度目 |
| 7 | `cancellation` を本番の変換器に通す | 2h | 3 度目 |
| 8 | `V5` マイグレーションのスキーマ絞り・`invoice` の `CHECK` 制約 | 2h | 2 度目 |
| 9 | E2E helper の URL 解決を統一する | 2h | 1 度目 |
| 10 | SonarQube Hotspot の走査トークン権限 | 1h | **4 度目**（IT5・IT6・IT12・IT13）。ゲート条件は決めたが、権限は解いていない |

> **3 度目・4 度目が 4 件ある。** Release 2.2 を計画するなら、
> 請求書検索（3 度目）と Hotspot の権限（4 度目）は**返済枠ではなく SP 付きのタスク**で置く。

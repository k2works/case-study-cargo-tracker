## Keep

### K1. ADR を先に決めたことで、実装が判断に従った

ADR-0012（BC をまたぐ書き込みは相手の集約を同期に通す）を Day 1 に決めてから実装した。
ADR-0011 が US09/US11 という**特定のストーリー**について書かれていたため IT10 で
同じ議論をやり直したことが動機であり、**一般形にすれば IT11 で 4 回目を繰り返さない**。

副産物として、設計ドキュメントのイベント表・コンテキストマップ・UI の遅延注記を
**同一の変更で是正**できた。「設計図に描かれたまま実装しない矢印を残さない」を
決定 3 として ADR に書いたことが効いている。

### K2. 安全装置を「破るテスト」で固定できた（Try T3 の達成）

IT9 の P3 は「行ロックを入れたが、外しても緑のままだった」という空振りだった。
IT10 では同じことが起きたとき——UNIQUE 制約を外しても同時発行テストが緑——
**識別できる形を探し直した**。制約そのものを破りにいく形
（発行済みの番号を別の予約へ直接 UPDATE）なら赤くなることを実測できた。

空振りだった側のテストには「**このテストが識別できないこと（正直に書く）**」を
doc に明記した。これがあったから、クローズ時レビューで
「安全装置の検証水準がばらついている」という指摘が成立した。

### K3. 見送りの判断を、根拠が崩れた時点で撤回できた（Try T2 の達成）

M8（`leg` の全削除・再挿入）は IT9 で「実害が無い」として見送った。
IT10 で荷役が `leg` を参照するようになり前提が崩れたため、US15 のタスクの中で返した。

**Try T2 が定めた「見送りの根拠を壊すタスクが同じ IT に来たら撤回する」がそのまま働いた**。

### K4. 荷役作業員に 3 イテレーションぶりに入口ができた

IT7 から「押せる入口を 1 つも持たないロール」だった。
`NavigationReachabilityTest` の `knownStranded` から荷役作業員を外せたのは、
**テストが「縮んだ＝前進」を区別して落ちる形**になっていたからである（IT8 の Try）。

### K5. テストが実在の業務欠落を暴いた

レビュー H2（MISROUTED の統合テストが Booking を見ていない）を返済してアサーションを
足したところ、**赤くなった**。予約詳細にも一覧にも経路状態を出す欄が無く、
荷役作業員には「経路設計者へご連絡ください」と出るのに**受け手に受け皿が無かった**。

テストを直すつもりが業務の穴を見つけた——これは受入テストが機能した形である。

## Problem

### P1. 「品質ゲート未達」を 3 イテレーション連続で誤って記録していた（最重要）

IT8・IT9・IT10 の DoD は「SonarQube Quality Gate が PASS」を条件として持ち、
3 回とも「未達」と記録していた。IT9 は Problem P4 として挙げ、IT10 は Try T4 として
「実行方法を着手前に決める」を立てた。

**クローズ時に前提が誤っていたことが判明した**。SonarQube は
**IT5 のふりかえり Try T9 で既に品質ゲートから外れていた**（`test_strategy.md` 6.4）。
IT5 は「3 回目の未実施にする前に決める」という正しい判断をしたのに、
**同じことが IT8-IT10 で 3 回繰り返された**。

原因は明白で、**イテレーション計画の DoD がテスト戦略を参照せず、独自に条件を列挙していた**。
正典が変わっても、書き写された条件は追随しない。

[ADR-0013](../adr/ADR-0013-quality-gate-canon-is-the-test-strategy.md) で
品質ゲートの正典を `test_strategy.md` 6.4 に一本化した。

**未達が常態化すると、本当の未達が埋もれる。**

### P2. ADR が自分の再検討条件に到達していることに気付いていなかった

ADR-0012 は 2 つの再検討条件を自ら発火させていた。

- `composition/acl/` を「2 本 → 5 本。境界に到達」と書いたが実際は **6 本**
  （US14 の 1 本を数え落とした）。同じ IT で更新した `arch_lint_rules.md` は
  6 本と正しく書いており、**ADR と設計が矛盾**していた
- US15 は 1 トランザクションで **3 集約**を更新する。「3 つ以上」を対象外と定めた
  §2 を、**ADR を書いた IT で超えていた**

条件を書いた本人が、同じ文書の別の節で条件を超える実装を許容していた。
**条件と実装を別の節で書くと突き合わせない。**

### P3. コメントが規律を宣言し、実装が守っていない箇所が 4 つあった

- 「規則は共有カーネルが持つ。書き写すと片方だけ緩む」と書いて**書き写していた**（時刻検証）
- 「予約の経路状態が MISROUTED になることまで確かめる」と書いて**確かめていなかった**
- 「判定前は `Valid` に倒さない」と書いた直後に **`Valid` を代入**していた
- 共有の `withPreparedStatement` があるのに**私物コピーを新設**していた（例外時に閉じない）

**コメントは安全網として読まれる**ぶん、宣言と実装のずれは普通のバグより害が大きい。

### P4. ADR-0012 の中心的主張が、書いた当の IT で成立していなかった

Handling → Tracking の書き込みは、集約を読んで捨て、列単位のポートを呼んでいた。
`TrackingModel` に遷移メソッドは存在せず、**ADR が却下した選択肢 B（直接 SQL）と
保証されるものが同じ**だった。

`ApplyHandling` のコメントが「遷移の妥当性は見ない」と宣言していたため、
**集約を通しても通さなくても同じ**という状態でもあった。

**規則が無いことと、規則を書く場所が無いことは違う。**

### P5. 業務として回らない状態で「完了」にしかけた

利用者代表が High を 4 件挙げた。うち 2 件は機能が入っているのに業務が回らない。

- **荷役の記録が荷主のタイムラインに出ない**（`handling_activity` と
  `tracking_handling_event` が別テーブル）。US15 の「なぜ」は荷主がリアルタイムで
  確認できることなのに、荷主にはバッジが変わるだけ
- **荷役履歴が全件無制限**。追跡管理者が「この番号の貨物は今どこか」に答えるために開くが、
  全貨物が時系列で混ざる

受入基準は満たしているが、**受入基準は正常系しか書かない**。

### P6. 間欠失敗が IT9 から未解決のまま、診断が新規テストで有効になっていない

`assertStatus` の診断は良いが、残る仮説（別インスタンスが応答する）を検出できるのは
`withAppInstance` で突合したときだけである。**IT10 の新規テストはすべて `withApp` 系**であり、
テスト本数が最も増えた領域が仮説検証の対象外になっている。

本 IT でも 503 が 2 度再現した（いずれも単発で、再実行では緑）。

| **T5** | **受入基準を満たしたら、利用者代表の観点で「毎朝どう使うか」を通す**。受入基準は正常系しか書かない。とくに**一覧**と**通知の受け手**は、機能があっても業務が回らない形になりやすい | 全ストーリー | 常時 | P5。IT9 の「一覧は毎朝どう使うかから確かめる」を通知の受け手にも広げる |
| **T6** | **間欠失敗の診断を `withApp` 系でも有効にする**。起動時のインスタンス ID を暗黙に保持し、`assertStatus` の失敗メッセージに期待インスタンスを出す（呼び出し側の書き換え不要な形）。503 については同時実行セマフォの残数も診断ヘッダに載せる | IT11 タスク 0 | IT11 着手時 | P6。3 イテレーション未解決であり、切り分けられる形にしないと次も同じ |
| **T7** | **新規 BC を立ち上げたら、既存 BC が持つ共有の道具を先に探す**（`withPreparedStatement`・`isIsoDateTime`・正規化）。新しい場所では「無いから書く」が起きやすい | 新 BC の立ち上げ | 常時 | P3 の 2 件（私物 helper・書き写した検証）はどちらもこの形 |

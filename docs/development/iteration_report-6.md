## エグゼクティブサマリー

**Release 1.0 が完成した。** 「予約 → 経路 → 確定 → 追跡番号 → 荷役 → 輸送中」が一本つながり、
E2E がその 1 本を 4 つのロールをまたいで通している。ウォーキングスケルトンが端から端まで到達した。

本 IT は **Tracking Context の初出**であり、集約 2 件・リポジトリ 2 件・BC 間 ACL ポート 3 件・
画面 3 つを新設した。これまでで最もトランザクション境界が広いイテレーションになった
（荷役の登録は 1 トランザクションで 2 BC・3 集約を書く）。

**その広がりが、そのままレビューの指摘に現れた。** 5 視点のうち 3 視点が独立に同じ型の欠陥を
指摘している — 「安全装置を書いたが、その結果を誰も確かめていない／使っていない」。
高優先度 14 件のうち 8 件を本 IT 内で修正し、6 件は新規ストーリー相当として次 IT 以降へ送った。

## 技術的成果

### 実装

| 分類 | 内容 |
| :--- | :--- |
| Booking | 確定・追跡番号発行・輸送開始（遷移表 #4・#5・#6）。`CargoProgress` / `BookingTrackingNumber` |
| Tracking | `TrackingActivity` 集約・`TransportStatus`・`TrackingNumber`（業務 TZ で採番） |
| Handling | `HandlingActivity` 集約・妥当性検証（デシジョンテーブル）・誤配の反映 |
| ACL | `TrackingPort` / `CargoSnapshots` / `HandlingProgressPort` / `VoyageCapacityPort` |
| 画面 | 予約詳細のボタン 2 つ・`/tracking/queue`・`/handling`・`/handling/new`・navbar・ダッシュボード |
| スキーマ | V10（区間の添字）・V11（追跡番号の採番と一意性）・V12（追跡レコードの一意性） |
| E2E | Playwright を有効化（開発戦略の品質ゲート表が定める IT6）。クリティカルパス 1 本 |

### 設計上の判断

| 判断 | 理由 |
| :--- | :--- |
| **確定の瞬間に空き容量を数え直す** | 算出時の判定を信じると、算出から確定までの間に満船になった便を確定できる（IT5 レビュー M3）。実際にその順序を再現するテストで固定した |
| **ACL が運ぶ値はポートのパッケージに置く** | 相手の `domain.model` に置くと、実装する BC がそこを参照する。ArchUnit ルール 4 の除外は ACL ポートのパッケージだけであり、**そこが唯一の越境点**である |
| **確定の可否を `CargoProgress.confirmable` に 1 か所だけ置く** | 集約と画面が同じ判断を呼ぶ。2 か所に書くと「押せるのに実行すると失敗するボタン」が生まれる |
| **追跡番号の桁あふれは丸めない** | 剰余で丸めると、発行済みの番号と重複した番号を黙って返す。形式検査で落とす |
| **予定と違う作業も登録を拒否しない** | 拒否すると、実際に起きた作業がどこにも残らない。伝えるのは警告である |
| **BC 間 ACL は同期・同一トランザクション** | 片方だけ成功する状態が業務上あり得ない。**その代償として、楽観的ロックの失敗を握り潰してはならない**（レビューで 3 か所見つかった）。判断は ADR-009 として IT7 で起票する |

### 本 IT 内で修正した高優先度（8 件）

3. **誤配の反映を検証していなかった**（消しても全テストが緑だった）
4. **作業日時のタイムゾーン変換を検証していなかった**（UTC に戻しても緑だった）
5. `architecture_backend.md` が未更新（**イベント駆動設計が実装と食い違っていた**）
6. マニュアルの索引 3 点同期が未完
7. 追跡番号発行待ちの項目表が実画面とずれ
8. 付録 B に IT6 の症状が無かった

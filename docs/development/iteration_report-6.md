## エグゼクティブサマリー

**Routing Context という 3 つ目の Bounded Context を立ち上げ、航海スケジュールの
登録・更新・検索を利用者が使える状態にした。** あわせて IT5 のレビューで
高優先度として残した負債（予約一覧の絞り込み・荷主の可視範囲）を返済した。

計画 11 SP を縮退 0 件で消化した。テストは 481 → **570 件**（+89）。
CI（build/test/arch-lint・E2E・Trivy）は全ジョブ緑。

**本イテレーションの最大の収穫は、レビューの依頼方法を変えたことで
「他になし」と確定できた調査が 4 件出たことである。** IT5 のふりかえりで
「Try を手順として書くと、その手順は守られるが同じ原理が及ぶ別の場所が漏れる」
と学び、5 視点すべてに「この原理が及ぶ他の場所はどこか」を必須条件として課した。

**最大の課題は、新規に導入した 2 つの安全装置がいずれも守りたいものを
守れていなかったことである**（楽観的ロック・`X-App-Instance`）。
どちらも全緑のテストを伴っており、「入れたこと」の検証はあったが
「働くこと」の検証が無かった。レビューで発見し、本 IT 内で修正した。

## 技術的成果

### 1. Routing Context の立ち上げ（US24・US25・US07）

| 層 | 成果物 |
| :--- | :--- |
| ドメイン | `Voyage` 集約・`CarrierMovement`・`CargoCapability`・`VoyageError`（14 → 15 ケース） |
| ポート | `VoyageRepo`（`save` / `findByVoyageNumber` / `findForUpdate` / `findAll` / `replace` / `search`） |
| アプリケーション | `RegisterVoyage`（`register` / `update` / `search` / `versionOf`） |
| インフラ | `JdbcVoyageRepo`（N+1 を避ける単一 JOIN・行ロック） |
| インターフェース | `VoyagePages`（455 行）・`VoyageRoutes`（htmx による区間追加） |
| DB | `V8` で `voyage` / `carrier_movement` を新規作成（**定義はあったが実物が無かった**） |

**BC 独立性は守られた**。`routing/**` から他 BC への参照は 0 件。
`CargoCapability` を `Booking.CargoType` と分ける判断も、「同じ語だが文脈が違う」
という理由がコメントに残っている。

### 2. 可視範囲（TS11）

`VisibleScope`（`All` / `Owned` / `Nothing`）を導入し、`listVisible` / `findVisible` が
1 箇所で絞る形にした。他人の予約は 403 ではなく **404**（存在の有無を漏らさない）。
`users.shipper_id` は**認可の関心**として扱い、ドメインへは持ち込んでいない。

### 3. 楽観的ロック（ADR-0008）

内容から導いた版を隠しフィールドで往復させ、食い違えば現在の内容との差分を見せる。
**レビューで 2 つの欠陥が見つかり、いずれも本 IT で修正した。**

| 欠陥 | 修正 |
| :--- | :--- |
| 版の照合がアプリ側だけで、同時到達で両方が書ける | `findForUpdate`（`SELECT ... FOR UPDATE`）で読む時点に行を押さえる |
| `Stale` で版だけを最新へ差し替えるため、押し直すと相手の変更が黙って消える | 現在の内容との差分を見せてから押させる |

### 4. 観測手段（`X-App-Instance`）と間欠異常の新仮説

ADR-0005 に**仮説（H1-H7）と観測手段の対応表**を作った。手段を足す前に仮説を並べ、
どの手段がどの仮説を切り分けるかを対応付けた（IT5 Try T5）。

**行ロックの検証中に新しい事実を観測した。** 行ロックを外すと、並行更新テスト自体は
通る一方で**無関係な `ShipperHttpTest` のログインが `Set-Cookie` を得られずに落ちる**
（2 回再現）。書き込み競合がコネクションプールを占有する形で波及する。

これを **H7（書き込み競合による資源枯渇）** として記録した。
IT4・IT5 の 2 例は「そのルートでは起こり得ない応答」であり、
H7 は「アプリケーションの論理ではなく**実行環境の資源**が原因」という
これまでと別の系統の仮説である。**観測された事実に基づく点で H5/H6 より確度が高い。**

### 5. 自作 lint の穴を塞いだ

`arch-lint` 規約 9（SQL への文字列補間）が、**骨格を関数へ切り出して連結する形**
（本リポジトリの JDBC アダプタが実際に採る書き方）を素通しにしていた。
規約が守らせたい書き方をしているファイルほど検査から外れるという逆転が起きていた。
実コードの形のフィクスチャを追加して塞いだ（メタテスト 26 → 27 件）。

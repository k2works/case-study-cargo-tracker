# IT9 完了報告書（2026-08-05）

## エグゼクティブサマリー

**計画 12 SP をそのまま消化し、縮退 0 件で完了しました**（IT5-IT9 で 5 イテレーション連続）。

本イテレーションで、**予約が業務として一巡する形になりました**。営業が予約を登録し
（US04・IT4）、経路設計者へ引き渡し（US06・IT5）、航海スケジュールから経路候補を
算出し（US07/US08・IT7）、**候補を選んで予約に紐付け**（US09・US11・本 IT）、
**営業が荷主の承認を得て確定する**（US13・本 IT）——ここまでが画面から通ります。

技術的には 2 つの決定が中心にありました。1 つは **ADR-0011**（Routing は Booking の
集約を通して同期に書く）で、IT8 の ADR-0009 と食い違っていた方針を**書き始める前に**
決め直しました。もう 1 つは **TS16**（ログインの CSRF 検証）で、IT3 の先送り判断の
前提が IT8 で崩れていたことを名指しで認めて撤回しました。

一方、クローズ時のレビューで**高優先度 6 件**が出ました。とくに深刻だったのは、
**差し戻しとキャンセルに画面からの入口が無く、テストが緑のまま US13 の受入基準 4・5 が
実質未達だった**ことです（受入テストが URL を直接 POST していたため見逃していました）。
高 6 件と中 5 件はクローズ前に返済しています。

**SonarQube 品質ゲートは 2 イテレーション連続で未達**です。実行方法を IT10 の
着手前に決めます。

## 技術的成果

### ADR-0011: Routing は Booking の集約を通して書く

計画段階の `validating-design` が、IT9 計画の方針（同期の ACL ポート）と
**IT8 の ADR-0009**（ドメインイベントで知らせる）の食い違いを検出しました。

決め手は事実の確認でした。US09 で**書き込む集約は `Cargo` 1 つだけ**であり、
`Voyage` は読むだけ、経路候補は永続化しません。したがって
「1 トランザクションで更新する集約は 1 つ」という規約は**そもそもかかっていません**。

保護は「誰が呼ぶか」ではなく「**集約を通ること**」から来ます。
`BookingModel.attachItinerary` を不変条件の唯一の関門とし、
`ItineraryTest` は呼び出し元を介さず集約を直接叩いて、
保護が呼び出し元の行儀の良さに依存していないことを確かめます。

### `arch-lint` 規約 11: BC 間の翻訳は `src/composition/acl/` にのみ置く

規約 4（BC 間の直接参照）は `src/composition/` を対象外にしているため、
**ADR-0010 で合成ルートに置いた翻訳は検出できない穴**になっていました。
IT8 のレビューで、まさにその穴に置いたコードのコメントと実装が食い違っていた
（所要日数が読めない候補を「落とす」と書きながら 0 で埋めていた）ことが見つかっています。

規約 11 は翻訳を禁じません。**置き場所を 1 箇所に限定します**。
`src/composition/acl/` のファイル数が、そのまま BC 間の翻訳の件数になります。

### TS16: ログイン CSRF を二重送信 Cookie で防ぐ

IT3 は「未認証で状態を変える経路が存在しない」を根拠に見送っていました。
IT8 が見積機能（未認証で作成できる）を足した時点で、この前提は崩れていました。

セッション前の保護なのでセッションにトークンを置けません。
`LOGIN_CSRF` Cookie（`HttpOnly; SameSite=Strict`）とフォームの隠しフィールドに
同じトークンを置き、一致を見ます。`requiresCsrf` による分岐そのものをやめ、
**状態を変えるメソッドは常に CSRF を検証する**形にしました。

### 2 軸の状態（BookingStatus × RoutingStatus）

経路の割り当ては `BookingStatus` を動かさず `RoutingStatus` だけを `ROUTED` にします。
2 つの軸を 1 つの列挙に畳むと「**荷主が承認していないのに予約確定**」になるためです。
確定するのは営業が荷主の承認を得たとき（US13）だけです。

画面の表示ラベルは 2 軸から導出します（`ROUTE_PROPOSED` × `NOT_ROUTED` → 経路設計中、
`ROUTE_PROPOSED` × `ROUTED` → 経路提案済）。

## 課題と残作業

### 1. SonarQube 品質ゲートが 2 イテレーション連続で未達

`.env` が存在せず、`.env.vault` の復号に対話的なパスワード入力が要るため、
AI エージェント単独で実行できません。IT8 でも同じ理由で未達でした。

**「実行できない」と「実行していない」を区別せずに 2 回繰り越した**のが問題です。
IT10 の着手前に (a) 利用者に手順を依頼する、(b) `.env` の配置手順を運用ドキュメントに書く、
(c) DoD から外して別の静的解析に置き換える——のいずれかを選びます。

利用者に実行を依頼する場合の手順は次のとおりです。

```
npx gulp vault:decrypt     # .env.vault のパスワード入力が要る
npx gulp sonar-local:check # scan → gate
```

### 2. 行ロックが働いていることを検証できていない

`findForUpdate` を追加したあと、**それを外しても受入テストが緑のまま**であることを
実測しました。テスト用の構成では要求が実質的に直列化されており、
ロックの有無が観測に現れません。

いま入っている行ロックは「正しいはずだが、働いていることを示せていない」状態です。
テストの doc コメントにその旨を明記し、IT10 の課題としました。
**「入れたこと」を「働くこと」と言い換えない**ためです。

### 3. 間欠失敗（未解決・IT8 から継続）

ログインの `Set-Cookie` 欠落・`RuntimeGuardTest` の 404。
H5（後片付けを全経路へ）と H6（診断の強化）で発生確率と診断力は改善しましたが、
**原因は特定できていません**。本 IT の実行では再現していません。

### 4. 規約 12（BC の SQL に現れるテーブル）が 5 イテレーション未着手

IT4 レビュー M1 由来。番号の衝突（ADR-0011 が 11 を取った）は改訂履歴で解消しましたが、
実装は未着手です。

### 5. CI 未確認のコミットが 4 件

設計同期・レビュー記録・返済・本更新の 4 コミットが未 push です。
push して CI の緑を確認するまで、クローズは**暫定**です。

## 次イテレーション（IT10）への引き継ぎ

### ストーリーとして起票を推奨するもの

| 内容 | 出所 | 理由 |
| :--- | :--- | :--- |
| 経路割り当て画面に「現在の経路」を表示・候補の並べ替えと件数上限 | レビュー M10・M11（IT7 から継続） | 候補が 20〜30 件になると目視では回らない |
| 差し戻しの記録（日時・理由・外した経路） | レビュー M13 | 理由が無いと経路設計者は同じ経路を選び直す。スキーマ変更を伴う |
| 見積 → 予約の導線 | IT8 利用者代表 U7 | US01 の価値を半分にする指摘 |

### 計画に織り込む改善（ふりかえりの Try）

1. 状態を持つ画面は **DoD に状態ごとの到達性**を入れる。受入テストは URL 直叩きをやめる（T1）
2. 見送りの判断には、**その根拠を壊しうる同 IT のタスク名**を併記する（T2）
3. 同時実行の安全装置は、**外したテストが赤くなることを実測してから**コミットする（T3）
4. **SonarQube の実行方法を着手前に決める**。3 回目の繰り越しにしない（T4）
5. 自作 lint の**例外は許可リストで書く**。フィクスチャは差分 1 行の対にする（T5）
6. 設計同期は実装コミットに同梱し、**上位の図（コンテキストマップ・規約一覧）も開く**（T6）
7. 検査器を作るタスクの DoD に「**CI のどのステップから呼ばれるか**」を書く（T7）

### 表示ラベルの継続指摘

「確認済」は現場では**「予約確定」**と呼びます（US13 の受入基準もそう書いています）。

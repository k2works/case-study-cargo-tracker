## エグゼクティブサマリー

IT9 は計画 8SP を実績 8SP で完了した（達成率 100%、9 イテレーション連続）。

本イテレーションの成果は 3 つある。

1. **IT2 から 7 イテレーション積み上がった制約に決着をつけた。** 貨物予約一覧を荷主に開放したとき、利用者アカウントと荷主を結びつける手段が無く他社の予約まで見えていた。以来 4 か所で「US34 で紐付けを作ってから開放する」と書き続けてきた。US34 でその紐付けを作り、予約一覧を開放した。**同時に、追跡番号の末尾 4 桁検索は「開かない」と決めた** — 紐付けができたことは開放してよいという意味ではない。
2. **設計にあってスキーマに無い状態を解消した。** 危険物・温度管理の 6 列は `data-model.md` に IT1 から定義されていたが、マイグレーションに存在しなかった。US05 で追加し、種別と申告の整合をドメインで守るようにした。
3. **「全緑」が到達点ではないことを 3 つの独立した経路が示した。** テスト 926 件・E2E 8 本・静的解析すべてが緑の状態から、安全装置の破壊検証が 2 件、E2E とキャプチャ生成が 5 件、レビュー 5 視点が 9 件の欠陥を出した。**合計 16 件はすべてクローズ前に解消した。**

## 技術的成果

### ドメイン

| 要素 | BC | 内容 |
| :--- | :--- | :--- |
| `HazardousDeclaration` / `TemperatureRequirement` | Booking | 危険物申告と温度管理条件。**種別との整合は `CargoSpecification` が守る**（DB の CHECK に書かない） |
| `CargoSpecification.create` / `.reconstruct` | Booking | **新規受け入れは検査し、復元は検査しない。** 列が無かったころの予約が読めなくなると、その予約の追跡もキャンセルもできない |
| `ScheduleChange` | Routing | 運航変更の差分（変わった項目だけ）。**画面で 2 つの航海を突き合わせない** |
| `Voyage.reschedule` | Routing | 航海番号は変えられない。**出港済みの区間も変えられない** |
| `TrackingActivity.updateManually` | Tracking | 引取済みへの更新・未来日時・時系列の逆行を拒否（C4 / C10） |
| `ShipperScopedPrincipal` / `CurrentUser` | shared | 画面が Security Context を参照せずに紐付けを読む「共有の約束」 |
| `AffectedBookings` | Routing → Booking の ACL | 運航変更が影響する予約。**パッケージの辺は 1 本も増えていない** |

### スキーマ

| # | マイグレーション | 内容 |
| :--- | :--- | :--- |
| V20 | `user_shipper_link` | `users.shipper_id`（NULL 可・FK）。社内ロールは紐づかない |
| V21 | `cargo_special_handling` | 危険物 3 列・温度 3 列。CHECK は**値の形だけ**（単位の列挙、最低 ≦ 最高） |
| V904 / V905 | demo | 動作確認用の紐付けと、**荷主コードの採番をデモデータの分だけ進める** |

V905 は E2E が見つけた欠陥への対処である。デモデータが荷主コードを直接書いて採番を進めていなかったため、**動作確認環境で最初の荷主登録が必ず 500 になっていた**。入力をやり直しても直らない種類の失敗だった。

### 判断の記録

**ADR-013: 利用者と荷主の紐付けは Security Context が共有カーネルの ShipperId だけで持つ**

Security Context は Shipper Context のモデルを参照しない。運ぶのは `ShipperId` だけで、表示に要る値は CQRS のクエリ側が読む。採らなかった 5 案（Shipper 側に利用者を持つ / 独立した紐付け BC / 荷主コードを持つ / 毎回引く / 共有カーネルに置く）とその理由を記録した。

## 検証で得られたこと

### 安全装置の破壊検証（10 件中 2 件が空振り）

| 空振りした装置 | 理由 |
| :--- | :--- |
| 航海番号は変更できない（集約） | 画面が先に 400 を返すため、集約の守りを消しても誰も気づかない |
| 航海更新の楽観的ロック | 画面のテストでは先行更新を起こせないため、1 度も働いていなかった |

**画面で先に弾かれる条件、画面のテストでは起こせない状況は、集約の守りを判別しない。**
どちらも判別できるテストを足して赤を確認した。

レビューはこの**裏返し**を突いた。集約の単体テストは、**画面から踏んだときに何が起きるか**を判別しない。両方が要る。

### E2E とキャプチャ生成が出した 5 件

| # | 欠陥 | 見つからなかった理由 |
| :--- | :--- | :--- |
| 1 | 差し戻し時に特別な入力欄が消え、指摘された利用者が直す場所を失う | 入力欄を htmx でしか描画していなかった |
| 2 | ダッシュボードにカードが並ぶのに「利用できる機能はありません」と表示 | 画面の**内部の矛盾**は個別要素のテストに現れない |
| 3 | 動作確認環境で最初の荷主登録が必ず 500 になる | テストの DB にデモデータが無い |
| 4 | 既存の便を編集で開くと発着日時が消える | `datetime-local` の受け付ける形式はブラウザを通さないと分からない |
| 5 | 危険物・冷凍の列が無かったころの予約が読めなくなった | 既存データを持つ環境でしか現れない |

**4 と 5 は「今あるデータ」を壊す種類である。** 新しく作るデータだけを扱うテストでは原理的に見つからない。

## 課題と残作業

### 本イテレーションで解消したもの

- IT2 から 7 IT 積み上がった「US34 で紐付けを作ってから開放する」（4 か所）
- 危険物・温度の 6 列が設計にあってマイグレーションに無い状態（IT1 から 8 IT）
- C4 / C10（手動更新の時系列検査）

### 次イテレーションへの引き継ぎ（17 件）

ふりかえりの C1〜C17 に記録した。重いものは次の 3 件である。

- **C9: 荷主が予約詳細で古い到着日時を見る可能性。** 経路の区間は割り当て時の写しであり、航海を更新しても書き換わらない。**荷主に開いたことで、確かめようのない日付を確かめられるように見せる形が生まれた**（US25 と US34 を同じ IT で出したことによる）
- **C10: 運航変更に気づけるのが経路設計者だけ。** 営業担当者は担当荷主の日程が変わったことを知る手段が無い
- **C1: `shared.application` が ArchUnit のどのルールにも守られていない。** ADR-005 が「共有カーネルは放置すれば肥大化する」として設けた検査が、新しい場所で効いていない

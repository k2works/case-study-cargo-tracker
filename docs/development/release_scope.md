# リリーススコープ定義

本ドキュメントは「何を最初に出すか」を定める**スコープの正典**である。設計ドキュメント（`docs/design/`）は全リリースを通じた目標設計を記述しており、そのどこまでが初回リリースの約束かは本ドキュメントでのみ定義する。

日付: 2026-08-06

## 背景

2026-08-06 の設計レビューで、次の問題が指摘された。

- `docs/design/` の主要 6 文書のいずれにも「何を最初に出すか」の記述がない
- ユーザーストーリー 27 件のうち 20 件が優先度「高」であり、優先順位として機能していない
- `architecture_backend.md` は routing / tracking / handling / billing を「package-info のみ（将来実装予定）」とする一方、`non_functional.md` と `operation.md` は全機能が完成した状態を前提に非機能目標と運用手順を記述している
- その結果、**非機能目標がすべて初回リリース要件として読める**状態になっており、これが最大のコストリスクとなっていた

本ドキュメントはこの空白を埋める。

## 原則

1. **Release 0.1〜1.0 は「予約から追跡までが一本つながる」ことを最優先とする。** 幅を広げるより、細くても端から端までつながっていることを優先する（ウォーキングスケルトン）
2. **非機能目標はリリースごとに定義する。** 全リリース共通の目標を置かない
3. **要求元のないものは作らない。** `docs/requirements/user_story.md` の US01〜US36 に紐づかない機能は、US を起票するか設計から落とすかの二択とする

> **US35 / US36 は IT8 の開始準備で追加した。** どちらもレビューが「US 化して次の IT へ」と
> 求めながら **US 化されないまま 1〜2 イテレーション繰り越されていた**。
> 記名のない引き継ぎは「余力次第の返済枠」と同じ形で固定化するため、SP とイテレーションを
> 与えて起票した（`retrospective-7.md` C1・C2）。

## リリース構成

> **画面設計の状況（2026-08-06 時点）**: 全 31 US に対応する画面の設計は完了している（`ui_design.md` の「US と画面のトレーサビリティ」を参照）。本ドキュメントが定めるのは**実装の順序とリリースの区切り**である。

> **リリース呼称は版番号（0.1 / 0.2 / 1.0 / 1.1 / 2.0）に統一した（2026-08-10）。** 本ドキュメントは
> 序数（Release 1 / 2 / 3）、`release_plan.md` と `docs/design/domain-model.md` は版番号を使っており、
> **同じリリースが二通りの名前で呼ばれていた**。実際に打たれたタグが `java/take-6/v1.0.0` /
> `java/take-6/v1.1.0` である以上、**タグと一致する側が正しい**。対応は次のとおり。
>
> | 旧呼称（本ドキュメント） | 新呼称 |
> | :--- | :--- |
> | Release 1 | Release 0.1〜1.0 |
> | Release 2 | Release 1.1 |
> | Release 3 | Release 2.0 |

### Release 0.1〜1.0: 予約から追跡までの一気通貫

貨物を予約し、経路を割り当て、確定し、荷役を記録し、荷主が追跡できる。この一連が途切れずに動くことを唯一の成功条件とする。

| US | タイトル | 備考 |
| :--- | :--- | :--- |
| US26 | システムにログインする | 全機能の前提 |
| US27 | システムからログアウトする | US26 と対で扱う |
| US31 | 認証失敗が続いたアカウントを保護する | US26 の分割。総当たり攻撃の防止 |
| US33 | ロックされたアカウントを解除する | **US31 の分割**。ロックの自動解除待ちは現場の作業停止時間になる。荷役・追跡が入る IT6 までに必須 |
| US02 | 荷主を登録する | **US04 の前提**。荷主 ID を作る唯一の手段 |
| US32 | 荷主情報を訂正する | **IT1 レビューで追加**。訂正手段が無いと誤った荷主情報が請求書と通関書類に流れる |
| US24 | 航海スケジュールを新規登録する | **US07・US08 の前提**。経路候補の入力データを作る唯一の手段 |
| US04 | 貨物予約を登録する | |
| US06 | 予約情報を経路設計者に引き渡す | |
| US07 | 航海スケジュールを検索する | |
| US08 | 経路候補を算出する | 経路算出は内部シミュレーション（ADR-006） |
| US09 | 経路を選択・確定する | |
| US11 | 経路情報を予約に紐付ける | |
| US13 | 予約を確定する | |
| US14 | 追跡番号を発行する | |
| US15 | 荷役作業を記録する | 最も頻度の高い操作 |
| US18 | 追跡情報を照会する | 公開追跡（認証不要ページ）を含む |

**依存順序**（この順に着手する）:

```text
US26/US27 → US02 → US04 → US06 → US24 → US07 → US08 → US09 → US11 → US13 → US14 → US15 → US18
```

US02 と US24 は他ストーリーの入力データを作るため、**先行して着手しなければ後続が動作確認できない**。レビューで「荷主登録が無いため予約フローが成立しない」と指摘された箇所である。

### Release 2.0: 精算

料金を算出し、請求し、入金を確認して精算を閉じる。ここまでで「予約 → 追跡 → 精算」の業務が全部つながる。

| US | タイトル | 備考 |
| :--- | :--- | :--- |
| US21 | 輸送料金を算出する | 消費税の丸め規則を仕様として確定させること |
| US22 | 法人割引を適用する | 荷主の**契約**割引率を参照する設計に是正済み（`domain-model.md` の `ShipperDiscountPort`。レビュー H15） |
| US23 | 精算を処理する | 支払期限超過の督促は業務運用として定義すること |
| US30 | 輸送中の予約キャンセルを承認する | 陸揚げ地の判断とキャンセル料を伴う。**キャンセル料の算定が US21 に依存する**。UC22、BUC24 |

**依存順序**（この順に着手する）:

```text
US21 → US22 → US23 → US30
```

US21 が料金算出の土台であり、US22（割引）・US30（キャンセル料）はいずれもその上に乗る。US23 は請求と入金であり US21 / US22 の確定金額を必要とする。

## リリース別の非機能目標

`docs/design/non_functional.md` の目標値は**最終形**であり、初回リリース要件ではない。事業ボリューム（年 10,000 予約 ≒ 1 日 30 件）に対して過大な目標は、達成手段（Read Replica・RDS Proxy・マルチリージョン）のコストを芋づる式に発生させる。

| 項目 | Release 0.1〜1.0 | Release 1.1 | Release 2.0 以降（最終形） |
| :--- | :--- | :--- | :--- |
| 公開追跡 API スループット | 50 RPS | 100 RPS | 要再評価（現行 1,000 RPS は事業規模に対し過大） |
| 追跡機能の可用性 | 99.9% | 99.9% | 99.95%（99.99% は単一 ECS + 単一 RDS では構造的に達成不能） |
| 全体 SLO | 99.5% | 99.9% | 要再評価（現行 99.995% = 月 2.2 分は達成手段が未定義） |
| Read Replica | 導入しない | 読み取り 500 RPS 超過時に検討 | 同左 |
| 負荷試験 | **追跡 API に 1 本のみ実施**（壊れるならここ） | 主要 API に拡大 | 全面 |

> **注**: Release 0.1〜1.0 で追跡 API の負荷試験を 1 本だけ実施するのは、アーキテクチャのストレスポイントを早期に叩くためである。HikariCP 20 接続 × 最大 10 タスク = RDS `max_connections` 200 ちょうどという上限に張り付いた設計であり、`db.t3.medium`（バースト可能インスタンス）で目標を捌けるかは検証されていない。

## リリース別の運用要件

`docs/design/operation.md` の運用手順（日次 15 分 + 週次 30 分 + 月次 2 時間 + 年次 DR 訓練 4 時間、PagerDuty 5 分ページングの L1/L2/L3 オンコール、月次リストア訓練）は**常設 SRE 体制を前提としている**。担い手が定義されていない運用計画は実行されず、実行されない計画は「やっているつもり」を生む。

| 項目 | Release 0.1〜1.0 | Release 1.1 以降 |
| :--- | :--- | :--- |
| 日次点検 | 自動チェック + アラート通知のみ（人手の定時作業なし） | 手順書に沿った点検を追加 |
| オンコール | 業務時間内のベストエフォート | L1/L2/L3 体制を体制確保後に導入 |
| リストア訓練 | リリース前に 1 回 | 四半期ごと |
| DR 訓練 | 実施しない | 体制確保後に年次 |

体制が確保できていない運用要件は、確保できた時点で有効化する。**体制の裏付けなく運用手順だけを定義しない。**

## 業務運用（未定義）

`operation.md` は 1,100 行すべてが ECS・RDS・監視・デプロイの基盤運用であり、現場が必要とする業務運用カレンダーが存在しない。**Release 1.1 までに定義するとしていたが、IT12 で Release 1.1 を完了した時点で未定義のままである。** Release 2.0 で次を定義する。ROLE_BILLING の月次業務は US21〜US23 の実装と同時に決めなければ、機能はあるが誰がいつ回すかが無い状態になる。

| 頻度 | 内容 | 担当ロール |
| :--- | :--- | :--- |
| 日次 | 未解決例外の棚卸し、通関留置の督促 | ROLE_TRACKER |
| 月次 | 締め、請求書一括発行、未入金の督促 | ROLE_BILLING |
| 随時 | 船会社スケジュール変更の反映（US25） | ROLE_ROUTER |

## 更新のルール

- 本ドキュメントはスコープの**正典**である。`docs/design/` 側にスコープの記述を書かない
- リリース内容を変更する場合は本ドキュメントを更新し、変更理由を記録する
- イテレーション計画（`docs/development/`）は本ドキュメントの Release 区分に従う

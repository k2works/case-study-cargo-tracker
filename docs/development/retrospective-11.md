## Keep（続けること）

### 1. 着手前の整合性検証が、実装前に 15 件の食い違いを潰した

`opening-iteration` のステップ 3・4（`validating-iteration-plan` / `validating-design`）を
実施したところ、計画と正典のあいだに 15 件の不整合が出た。**うち 11 件は正典を読まずに
計画を書いた形**である。

最も重かったのは **`PaymentStatus` に `DRAFT` を足そうとしていたこと**。正典の 4 値は
支払いの状態であり、そこへ「金額を確定したか」を混ぜると `CONFIRMED` が
「支払い確認済み」と「金額確定済み」の 2 つの意味を持つ。**US23（IT12）で支払いを扱う段に
なって初めて破綻し、そのときには請求書がすでに発行されている。** 着手前に潰せた。

### 2. 返済枠を IT 序盤の独立コミットで片付けた（6 IT 連続）

9 件・26h を Day 1-3 相当で消化した。うち 3 件は**指摘の見立てと違う原因**が見つかった。

- 0.1: `oxlint` が警告を exit 0 で返しており、`verify` に入れても品質ゲートとして
  働かなかった（`--deny-warnings` を足した）
- 0.2: `--tag` の解釈ではなく `kubectl set image` の性質だった。既定タグが base に
  直書きされているため spec が変わらず、Pod が作り直されない
- 0.4: ADR-026 決定 2 が「述語がすべての値を明示的に扱う」と決めていながら、実装は
  否定リストで**足した値が自動的に開く方向へ倒れて**いた

**返済枠は「前 IT の指摘を消す作業」ではなく、原因を確かめ直す作業である。**

### 3. 横断的な検査が、フルビルドでしか出ない欠陥を 3 つ捕まえた

Port を追加したらフルテストを回す規律（IT8 の教訓）がそのまま効いた。

- `SchemaDesignConsistencyTest` — data-model.md との乖離、実装済みなのに未実装一覧に
  残っていたテーブル
- `AuthenticatedUserFilterRegistrationTest` — billingms にヘッダ無し拒否の検査が無い
- `ArchitectureTest` — `BillableCargo` を `interfaces` に置いたこと（application が
  interfaces に依存していた）

### 4. 撮った絵がまた欠陥を見せた（3 IT 連続）

マニュアルのキャプチャを撮って 2 件見つかった。

- **キャンセルされた予約に「引取日時」が出ていた。** 引き取っていないのに引取日時があると、
  「引き取ったのにキャンセルされた」と読まれる。並びに使っているのは最後に荷役があった
  日時であり、引取日時とは別のものである
- JSX の改行が半角空白になり、句点の直後に空きができていた（3 か所）

### 5. 実 DB のテストが、ユニットでは出ない 2 件を捕まえた

- **同じ重量なのに等しくない。** `BigDecimal.equals` は桁数まで見るため、
  `NUMERIC(10,3)` から読み戻した `4200.000` が `4200` と別物になっていた
- **発行時点の社名を残していなかった。** 荷主 ID で埋めるバグで、請求書の宛名が読めなかった

## Problem（困ったこと・繰り返したこと）

### 1. 例外（遅延・破損）の根拠が空のまま残った

受入基準 21-6 は「例外（遅延・破損等）が発生している場合、料金調整（減額・補償費用）の
入力ができる」である。**誤配（IT10 の `Misroute`）は根拠として出せるようになったが、
例外は `ChargeCalculation.exceptions()` が常に空リストを返す。**

計画の Phase 3.4 に「例外の実績を trackingms から引く（21-6 の根拠）4h」と書いてあったが、
**実装しないまま Phase を完了扱いにした。** 調整の入力そのものはできるので受入基準の
字面は満たすが、**根拠を出す側が片肺である**。

### 2. CI の E2E が毎回初回失敗している（4 回目）

`tracking.spec.ts` の 2 件（IT8 のデモ項目）が、**過去 4 回の CI すべてで初回失敗し
リトライで通っている**。本 IT の変更とは無関係だが、「たまに落ちる」ではなく毎回である。

**再実行で通ることを理由に 4 回見過ごした。** リトライがあると赤が見えなくなる。

### 3. 編集が適用されないまま「完了」と報告しかけた

`InvoiceCharges` へのリファクタと `shipperName` の集約を、**2 回とも「適用した」と
思い込んだまま次に進んだ**。実際にはファイルが変わっておらず、SonarQube の指摘が
消えないことで気づいた。

出力が失われたターンのあと、**結果を確かめずに次へ進んだ**のが原因である。

### 4. 距離を持っていないことに、着手してから気づいた

受入基準 21-2 は「輸送実績（経路・**距離**・重量・貨物種別・荷役作業実績）が表示される」。
港のマスタに緯度経度が無く、航海も距離を持たない。**ADR を書く段で初めて分かった。**

計画では「距離を除く」と書いていたが、**なぜ除くのか（持っていないから）を確かめたのは
着手後**である。IT10 の「決めること」に相当する確認が足りなかった。

## エグゼクティブサマリー

**経路を確定して予約に紐付けられるようになり、Release 0.2 が完成した。**
予約 → 引き渡し → 候補算出 → **確定** → 紐付けが一本つながり、
IT6 の「予約確定・追跡番号・荷役」へ進める状態になった。

あわせて **US33（ロック解除）を実装した。** ロックの自動解除を待つ間、
その担当者は作業できない。輸送は待ってくれないため、待ち時間がそのまま
業務の停止時間になる。荷役が入る IT6 の前に手当てできた。

**IT4 で先送りにした空き容量の判定を、今回は「壊すと赤になる」形で実装した。**

## 技術的成果

### 旅程と経路状態

- `CargoItinerary` が守るのは**区間をまたぐ 2 つの制約**（連結・時系列）。
  **どちらも行をまたぐため DB の CHECK では守れない**（`Schedule` と同じ理由）
- **旅程の端点は予約の出発地・目的地と一致する。** 違う旅程を割り当てると、
  荷主が頼んだ場所と違う場所へ運ぶことになる
- `CargoRouting` として経路状態と旅程を**ひと組**で持つ。「割り当て済なのに区間が無い」
  組み合わせを型が作らせない
- `CargoRoutingStatus` は Booking が自前で持つ（`RoutingCargoType` と同じ扱い）

### 空き容量（IT4 からの持ち越し）

`voyage.capacity_weight_kg`（V9）と**確定済み貨物の重量合計**から判定する。
IT4 では判定の材料が無く「常に真を返す装置」になるため画面に出さなかった。
**確定を実装した本 IT が、初めて壊して赤にできるイテレーションだった。**

### BC の分離

確定は Routing と Booking の両方に書き込む。ACL ポート `CargoRouteAssignments` を
Routing が定義し、Booking がアダプタを実装する。**境界では素の値だけを渡す**
（IT4 で ArchUnit に捕まった形を繰り返さない）。

**BC をまたぐ受け入れシナリオの置き場（`scenario`）を新設した。** どちらの BC 配下に
置いても相手の型を参照してルール 4 を破る。またぐのが仕事である。

### スキーマ

`leg` テーブルは V1 で作成済みであり、**本 IT が最初の利用者**である。

## レビュー結果

[IT5 実装レビュー](../review/IT5実装_review_20260807.md)（高 4 件 / 中 4 件 / 低 3 件）。
**高の 4 件と中の 1 件は本イテレーション内で修正済み。**

| # | 指摘 | 対応 |
| :--- | :--- | :--- |
| H1 | **経路を確定すると、経路割り当て画面が 404 になった** | 「読める」条件と「割り当てられる」条件を分けた。読み取りは引き渡し済みまでとし、割り当ての可否は集約が判断する |
| H2 | **確定時の楽観的ロック衝突だけが 500 になった** | 算出と同じ扱いに揃えた。片方だけ 500 になると、利用者から見て振る舞いが揃わない |
| H3 | **動作確認用のログイン一覧に管理者が無かった** | `application-{local,dev}.yml` に追加。一致を検査するテストが `V800` だけを読んでいたため、`db/seed` 配下のすべてを読むよう直した |
| H4 | **権限の無い POST が 405 になっていた** | 403 の画面への forward 先を GET 限定にしていた。**Heroku 上で実測して発見**（MockMvc では 403 で通る） |
| M1 | Jig が `RouteProposalMapper` を読み飛ばしていた | UUID の型ハンドラを明示した。**同じ値を 2 通りに扱っていた**ことが原因 |

| 内容 | 理由 |
| :--- | :--- |
| 積載可能重量を航海の属性に追加（集約・V9・登録画面） | 容量が分からない便を作れると、空き容量の判定が形骸化する |

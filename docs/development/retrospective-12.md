# イテレーション 12 ふりかえり

| 項目 | 内容 |
| :--- | :--- |
| イテレーション | IT12（2026-10-19 〜 2026-11-01 想定・**Release 2.0 の最終**） |
| 対象 | US23（3 SP）・US01（5 SP）・US21 の未達返済（3 SP）= **11 SP** |
| 実績 | **11 SP（達成率 100%）** |
| レビュー | [高 14 件・中 27 件・低 12 件](../review/イテレーション12_review_20260827.md)。高はすべて対応 |

## Keep

### 1. 着手前に「データはあるか」を確かめた（IT11 Try 5）

IT11 は着手後に「距離を持っていない」と分かった。本 IT は決定表に**「データはあるか」列**を
置き、`location.country_code` があること・地域区分は無いことを**着手前に**確かめた。
結果、輸出免税は列を足さずに実装でき、地域区分は 1 列で足りると判断できた。

### 2. 受け入れテストを先に赤で置いた（アウトサイドイン）

デモ項目 14 件のうち 13 件を先に E2E へ翻訳し、**新規 15 件が赤・既存 12 件が緑**を
確認してから実装に入った。「実演で緑になる」と「固定されている」を取り違えずに済んだ。

### 3. 検査が 4 回、実装より先に誤りを見つけた

- **網羅 switch** が `BookingStatus.SETTLED` の表示名の追加漏れをコンパイルで止めた
- **`SchemaDesignConsistencyTest`** が data-model.md との食い違いを 2 度落とした
- **Gateway の振り分け検査**が `/api/v1/estimates` の登録漏れを落とした
- **`LocationSeedReplicaTest`** が「マイグレーションを文字列順で読む」欠陥を露わにした
  （`V10` が `V2` より前に来る）

### 4. 実環境を通したことで、実環境でしか出ない欠陥を捕まえた

bookingms が `localhost:8086` を見ており、**見積の候補を探す操作だけが 500** だった。
IT5（経路の確定）と同型で、**3 度目**である。今回は再発防止として
**設定が読む `APP_*_SERVICE_BASE_URL` がすべて k8s マニフェストに現れることを検査**にした。

### 5. キャプチャの目視を続けた（4 IT 連続で欠陥が出た）

サイドバーで「見積管理」と「貨物予約」が**同時に選択状態**になっていた。
`NavLink` の既定が前方一致であることに、画面を見るまで気づかなかった。

## Problem

### 1. 自分で書いた 2 つの決定が噛み合っていなかった（レビュー高 1・2）

**キャンセル料の請求書に入金確認すると、永久に記録できない**経路があった。

- ADR-027 決定 5: 精算の対象には**キャンセル済みの予約も並ぶ**（キャンセル料を締めるため）
- ADR-028 決定 1: 予約は**引取済からしか**「精算済」へ進めない（運んでいない予約に精算済は無い）

この 2 つを繋ぐと、キャンセル料の入金確認で相手が 409 を返し、`@Transactional` が
**入金の記録ごと巻き戻す**。全テストが緑、実環境 E2E も緑だった——
**キャンセル済みの予約を精算する筋を、1 度も通していなかった**。

> **決定は単体では正しかった。** 誤りは「2 つの決定が出会う筋」を通していないことにあった。

### 2. ADR のコンプライアンス表が作文だった（レビュー中）

ADR-028 の表が挙げる **5 クラスすべてが実在しなかった**。中身は別の名前で守られていたが、
**表からは辿れなかった**。ADR-027 でも 1 件（`TaxRateTest`）見つかった。
「決定ごとに検査を置く」という規律の要が、名前だけの表になっていた。

### 3. 「循環しないことを層内依存禁止に翻訳する」が空約束だった（レビュー高 5）

計画で「ArchUnit は HTTP の向きを見ないから、層内依存禁止に翻訳する」と書き、ADR にも
書いたが、**その検査を実装していなかった**。しかも既存の「application は infrastructure に
依存しない」は `RestClient`（どの層にも属さない）を素通りする。
**翻訳したところで満足して、翻訳先を書かなかった。**

### 4. 改訂は新設より漏れる（レビュー高 10・11・12）

12 章に新設節（12.3〜12.5）を足しながら、**既存の 12.1 が IT11 のまま**残った
——「区間数で代替」「東京 → 横浜と東京 → ロサンゼルスはどちらも 1 区間」。
ADR-027 の追補が直したはずの誤りを、同じ章の前半が説明していた。
料金算出画面の「訂正する手段はありません」も同じ形である。

### 5. 業務として使えない実装が 2 件あった（レビュー高 3・4）

- **¥1 の入金でも「入金済・精算済」で閉じた。** 振込手数料の差引は日常的に起きる
- **印刷した紙が請求書になっていなかった。** メニュー・社内向け注記・操作ボタンが載り、
  宛名が無い。「印刷できる」を満たしても、**荷主に出せる紙**にはなっていなかった

### 6. 検索が無いことを 2 度指摘された

IT11 に続き、経理担当者から「探す・まとめる」が無いことを指摘された。
IT12 では印刷（出す）と赤伝（直す）を入れたが、**月末の締めは表計算に落ちたまま**である。

| 3 | **「〜に翻訳する」と書いたら、翻訳先を同じ変更の中で書く** | Problem 3。翻訳したところで満足していた | ADR の決定に「検査」欄がある以上、**その IT のうちに実装する**。Try 2 の検査が名前の実在までは守る |
| 4 | **改訂したら、その決定に言及している既存の記述を grep で洗う** | Problem 4。新設は書くが改訂は漏れる | クローズの文書同期に**「grep で洗い出す」手順**を足す（今回は `区間数で代替`・`訂正する手段` で 4 か所見つけた） |

## 次イテレーション（IT13）への引き継ぎ

Release 2.0 は完了し、**残るのは US33（荷主の担当者が自分の貨物だけを追跡する・5 SP）と
予備枠**である。加えて本 IT から送る負債がある。

| # | 内容 | 見積 | 送るのは何度目か |
| :--- | :--- | :--- | :--- |
| 1 | **請求書の検索（請求番号・荷主名・予約番号）と発行月の絞り込み・合計** | 5h | **2 度目。** 経理担当者から 2 IT 連続で指摘。**月末の締めが表計算に落ちたまま** |
| 2 | **見積に荷主を入れる**（割引後を出す・荷主で探す・突き合わせに含める） | 4h | 1 度目（IT12 レビュー高 14） |
| 3 | **例外の実績を trackingms から引く**（21-6 の片肺） | 4h | **3 度目。IT13 の計画に SP 付きで載せる** |
| 4 | `overdue()` の全件走査と `billable()` の N+1 を SQL に降ろす | 4h | 1 度目（同型の負債・請求書が増えるほど悪化する） |
| 5 | 「請求書」と「精算書」の混在 | 4h | 2 度目（画面が増えて広がった） |
| 6 | `cancellation` を本番の変換器に通す | 2h | 2 度目 |
| 7 | 完全修飾名の混在を揃える（本 IT で作り込んだ差分） | 1h | 1 度目 |
| 8 | `V5` マイグレーションのスキーマ絞り・`invoice` の `CHECK` 制約 | 2h | 1 度目 |
| 9 | **SonarQube の Hotspot が毎回 UI 操作を要する形を解く**（資格情報の受け渡しか、ゲート条件の見直し） | 1h | **3 度目**（IT5・IT6・IT12）。IT12 の 1 件は利用者が手動承認して PASS になったが、**同じ待ちがまた起きる**。`// NOSONAR` は Hotspot に効かないことを実測済み |

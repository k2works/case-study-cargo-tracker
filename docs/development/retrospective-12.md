## Keep

### K1. 「壊れる経路を塞ぐ」判断が、取り消し機能より先に効いた

IT11 のレビューは「誤登録した荷役を戻せない」（M10）を挙げていた。
取り消し機能を作る選択もあったが、**引取済への荷役登録そのものを拒む**ことで
壊れる経路を塞いだ。

引取は所有権の移転であり、その後に荷役は起きない。**業務としてありえない操作を
許していたこと自体が誤り**であり、戻す機能はその後の話である。
判定は自分の記録（`CLAIM` の有無）から分かるため、BC をまたぐ読みも増えていない。

### K2. ADR-0014 の再検討条件を、機械が数える形にできた

ADR-0011・ADR-0012 は「`composition/acl/` の総数」を条件にしていたが、
総数は「連携が増えた」と「単一の集約がハブ化している」を潰していた。
ADR-0014 で条件を置き換えたが、**散文にしかなく誰も数えていなかった**。

規約 13 として実装し、**4 本目で実際に赤くなることを実測**した。
現時点は Booking へちょうど 3 本で、1 本足せば発火する。

**条件を測れる形にしたなら、測る道具まで含めて 1 セットである。**

### K3. E2E が UI の欠陥を捕まえ、下の層に固定できた

追跡詳細に `id="location"` が 2 つあり、自動操作が最初の 1 つを掴んでいた。
結果、例外の記録が場所を空のまま送られて失敗していた。

HTTP テストはフォームを組み立てず直接 POST するため**原理的に見えない**。
同じ形を HTTP テスト（`id` の出現回数を数える）としても固定した——
E2E だけに頼ると、落ちたときの原因の切り分けが遅くなる。

### K4. 状態の再導出禁止が、今回は最初から守られた

例外の解決で戻る先（`statusBeforeException`）を**カラムに永続化**した。
IT10 で記録した教訓（履歴から再導出するとユニット緑でもクロスリクエストで誤復帰する）
が、設計の時点で適用されている。

## Problem

### P1. 安全装置の空振りが 4 イテレーション連続した（最重要）

IT9（行ロック）・IT10（UNIQUE 制約）・IT11（時刻の逆行）に続き、
IT12 は **`escalated`** だった。`grep escalat` すると**書き込み側しか存在しない**——
読む SQL も画面もビューも無く、48 時間ルールは純関数のユニットテストしか無かった。
判定を `false` に固定しても全テストが緑だった。

過去 3 回とは形が違う。IT9-IT11 は「守るはずの条件が効いていない」だったが、
今回は**計算した結果を誰も受け取っていない**。書いた列を読む先が無い。

**「保存する」と「読む」はセットで実装しないと、片方だけが残る。**

### P2. 荷主の画面が実態と食い違ったまま出荷されかけた

解決しても「遅延が発生しています」が残り、解決の瞬間に対応方針が消えていた。
どちらも**公開画面のコメント自身が警戒していた形**である
（「解決した瞬間に理由が消えると問い合わせが増える」）。

原因は明確で、**記録と解決を別々のテストで確かめていた**。
それぞれは緑だが、連鎖は誰も通していなかった。

**業務は 1 本の線であり、テストも 1 本で通さないと切れ目が見えない。**

### P3. 追跡管理者の画面が、荷主の画面より情報が少なかった

例外を記録するフォームだけがあり、記録した内容が一切出ていなかった。
荷主の公開画面には出ているのに、である。

追跡管理者は**荷主からの問い合わせに答える立場**であり、
荷主より情報が少ないと答えられない。IT10 の H8（荷役が荷主に出ない）と
向きが逆の、同じ形の欠落である。

### P4. 番兵（`Some("")`）が、宣言した不変条件を自分の手で破っていた

`ExceptionRecord` の doc は「`resolvedAt` が入っていれば解決である——別の型にすると
『発生していない解決』が型として作れてしまう」と書いていたのに、
`withResolutionNotes` が `Some("")` を「解決でない」の合図に使っていた。

さらに解決の指示を作るために、集約が `description = ""`
（`raiseException` 自身が拒む値）を組み立てていた。
**集約が自分の検証を通らない値を作っている**状態だった。

### P5. 「この IT で塞いだ穴」の照合（Try T1）が、例外フォームで漏れた

計画のタスク 0.1 に置いた照合が、**US19 で作った新しい入口には適用されなかった**。
拒否時の入力保持が例外フォームに効かず、しかも入力した値が隣の
状態更新フォームへ回るという、IT11 の M12 と同型の欠陥が残っていた。

**一覧を作っただけでは照合されない。** 新しい入口を作った瞬間に開く作業として
タスクに埋め込まないと、計画に書いただけで終わる。

### P6. ローカルで E2E を実行できないまま v1.0.0 を終えた

fat JAR のビルドが収束せず（1 GB を超えて増え続ける）、
本 IT でも**タスク 0.3 は未着手**である。CI では緑だが、
E2E が落ちるたびに CI を待つ往復が発生した（IT11 で 3 往復・IT12 で 1 往復）。

| **T1** | **「保存する」と「読む」をセットで実装する**。列を足したら、その列を読む画面・ビュー・SQL を同じコミットで作る。作らないなら**列を足さない**。DoD に「この IT で追加した列を読む箇所がある」を入れる | 全実装タスク | 常時 | P1。4 イテレーション連続の空振りのうち、今回は「計算したが誰も受け取らない」形だった |

## v1.0.0 の総括

### 達成

**全 12 イテレーションを縮退 0 件（IT5 以降 8 連続）で完了した。**

| 指標 | 値 |
| :--- | :--- |
| ユーザーストーリー | 20 本（US01-US09・US11・US13-US19・US24-US27） |
| SP | 149 / 160（93%。残 11 SP は将来リリース分の一部） |
| テスト | 894 件（単体・HTTP 統合）＋ E2E 3 本 |
| `arch-lint` | 規約 13 件・メタテスト 36 件・違反 0 件 |
| ADR | 14 件 |

業務フローは**端から端まで通る**——見積 → 予約 → 経路 → 確定 → 追跡番号 →
荷役 → 通関 → 引取。乱れたとき（経路逸脱・遅延）の処理も入っている。

### 既知の制約（v1.0.0 として受け入れる）

| # | 制約 | 当座の運用 |
| :--- | :--- | :--- |
| 1 | **荷主への通知が無い**（US12） | 荷主が公開追跡で自分で確認する。予約詳細に貼れる案内文を用意した |
| 2 | **記録の取り消しができない** | 壊れる経路は塞いだ。誤登録は追跡管理者へ連絡する運用 |
| 3 | **未解決例外の一覧が無い** | 追跡番号で個別に開く |
| 4 | **精算が無い**（Phase 5） | [ADR-0007](../adr/ADR-0007-defer-external-acl-and-scope-v1.md) でスコープ外 |
| 5 | **外部システム連携が無い**（TS07） | 通関は荷役の記録で表す（[ADR-0014](../adr/ADR-0014-customs-clearance-is-a-handling-record.md)） |
| 6 | **間欠失敗が残る** | 診断は明確（「アプリ以外が応答しました」）。再実行で緑 |

### 次リリースへの引き継ぎ

将来リリースのスコープは **21 SP**（US21・US22・US23・US10・US12・US20）。
これに IT12 レビューの中 6 件・低 5 件が加わる。着手前に決めるべきは次の 3 つ。

1. **記録の取り消しの設計**（M7）。US20（破損・紛失）と同じ土俵で決める
2. **未解決例外の一覧**（M8）。追跡管理者は「今どれが困っているか」から入る
3. **ローカルの E2E 実行環境**（Try T6）。2 イテレーション連続で未着手

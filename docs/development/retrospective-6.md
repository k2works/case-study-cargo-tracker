## Keep（うまくいったこと）

### 技術的成功

1. **導出状態設計の一貫性を例外にも徹底**: `InException` を保持フィールドにせず、アクティブな未解決例外の有無から `currentStatus` で導出。ビジネスルール 5（解決後の状態復帰）を「導出値なので自動的に成立」という形で実装レスに達成した。往復性（登録→解決→復帰）を FsCheck 含むユニット・統合・受け入れの 3 層で検証。
2. **不正状態の型排除（ExceptionResolution DU）**: 「解決済みなのに resolvedAt が null」という C# nullable 由来の不正状態を DU で表現不能にした。永続化では 2 カラムへ写像しつつ、ドメインは型安全を保った。
3. **BC 越境の実態を実装で発見し設計に反映**: 「例外→Booking Delivery 同期」を計画していたが、Booking の `transport_status` が未実体化（将来追加予定）と判明。架空の越境同期を作らず、InException は Tracking 自身のキャッシュで往復保証し、`TrackingExceptionDetected` は将来消費用の発行イベントとして残すと計画へ明記した。憶測でなく事実を確認して設計判断した。
4. **ETA の BC 分離**: 推定到着日を Tracking の読み取りモデルに cargo テーブルを join せず、合成層（App.fs）で `CargoQueries.findArrivalDeadline` を呼んで解決。ArchUnit の BC 分離を緑に維持した。
5. **append-only 化**: `syncEvents` を全置換（DELETE→INSERT）から未永続分のみ追記へ変更。イベントソースの追記原則・監査整合を守り、書き込みコストを一定化（retro-5 Try#5／レビュー中#2）。

### プロセス的成功

1. **Ralph Loop による小さな緑の連鎖**: ドメイン→アプリ→永続化→Web→技術的負債を 8 ターンに分割し、各ターンでビルド緑・テスト緑・コミットを徹底。回帰（consumer テストの DDL 不足・通知先の不一致）を都度検出・即修正できた。
2. **過去レビュー・ふりかえりの反映を計画表で追跡**: IT5 レビュー IT6 送り（高2・中6）を「過去レビュー・ふりかえりの反映」表でタスクへ紐付け、消化状況を可視化。暗黙の未対応をゼロにした。
3. **設計判断の即時 ADR 化**: 所有者制御（ADR-0011）・荷役→追跡整合（ADR-0012）を、コード変更が小さくても方針として明文化。「原子性が未達」を負債でなく意図的判断として清算した。

## Problem（課題）

1. **通知の実送信・荷主メール解決が未達（継続）**: recipient を追跡番号から予約 ID へ是正（中#3）したが、実メール送信・荷主連絡先モデル化（retro-5 Try#2）は「通知強化 IT」に持ち越し。notification_log 記録に留まる。
2. **Web ハンドラの通知方針がまだ不統一（継続）**: 例外登録は notification_log 記録、荷役連携・手動更新は no-op notifier のまま。retro-5 Try#3（通知の合成層ヘルパ集約）は未着手。
3. **荷役→追跡の原子性は方針確定に留まる**: ADR-0012 で「ベストエフォート＋冪等の結果整合」を正式方針としたが、自動再試行（アウトボックス）は未実装。取りこぼし時はログ監視＋手動/バッチ再記録に依存。
4. **US16 確認ステップはクライアント側のみ**: 誤登録防止の確認チェックボックスは `required`（HTML 検証）で、サーバー側の強制はしていない。UX 改善としては足りるが、堅牢性は限定的。
5. **例外の Description に対応方針を含める設計の曖昧さ**: ui_design では対応方針を登録フォームに含め、解決画面を別に持たない。IT6 では追跡詳細から解決アクションを追加したが、ui_design への「例外解決 state」追記は完了時反映事項として残る。

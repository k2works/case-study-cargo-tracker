## Problem（問題点）

### P1. 「壊して赤」を回した対象が偏っていた（最も重い）

実装時に 14 件の装置を壊して赤を確認した。**それでもレビューで 4 件の空振りが見つかった。**

| 見落とした装置 | なぜ回さなかったか |
| :--- | :--- |
| 誤配の反映（`markMisrouted`） | **判定そのものは 3 件回した。** 判定の結果を「どこに書くか」は回していない |
| 作業日時のタイムゾーン変換 | 画面のテストが緑だったため、変換も確かめたつもりになっていた |
| 追跡更新の衝突 | リポジトリ単体では回した。**その結果を呼び出し側が使うか**は回していない |
| 発行の衝突 | 同上 |

**共通するのは「入口は回したが、出口を回していない」ことである。**
判定・保存・変換の**結果がどこへ行くか**を、一度も壊していなかった。

### P2. 楽観的ロックの戻り値を 3 か所で捨てていた

IT5 の Try T2 で「例外を投げる経路を `grep` で数える」を実施し、**例外については守れていた**。
しかし**戻り値 `boolean` で結果を返す安全装置には、同じ数え方が適用されていなかった**。

`grep -rn "Repository\.\(update\|updateRouting\|updateTrackingNumber\)(" ` を一度実行するだけで
3 件とも見つかった。**規律はあったが、適用範囲が狭かった。**

### P3. 発行が原子的でなかった

`return` はコミットである。Spring がロールバックするのは非検査例外のときだけであり、
**戻り値でエラーを返す設計と `@Transactional` は相性が悪い**。

同じクラスの Javadoc が「1 つのトランザクションで書く。追跡レコードだけが作られて予約に
番号が付かないと…」と、**まさにこの故障モードを防ぐと宣言していた**。宣言と実装が食い違っていた。

### P4. 設計ドキュメントの一部だけを更新した

`domain-model.md` / `data-model.md` / `ui_design.md` は実装と同じ IT で直したが、
**`architecture_backend.md` を忘れていた**。

しかもそこには**イベント駆動設計が `AFTER_COMMIT` の結果整合を前提**に書かれており、
実装（同期・同一トランザクション）とは**故障モードがまるで違う**。次に読む人は存在しない
基盤の上に設計を積むところだった。

### P5. マニュアルの索引 3 点同期が守られなかった

`docs/manual/index.md` 自身が「章を追加したら index.md・00-はじめに.md・mkdocs.yml の
**3 箇所を必ず揃える**」と定めているのに、`00-はじめに.md` だけが漏れた。
**規約を書いた本人が、その規約を読まずに作業した。**

### P6. E2E が誤配経路を通ったまま緑だった

航海番号を `V0001` と決め打ちしていたため、実際に確定した便と違う便に積み込んでいた。
それは**誤配**だが、最終アサートは「輸送中」バッジだけを見ており、
**意図した経路を通ったかどうかを区別しなかった**。

「一本つながった」と主張しているテストが、**別の道を通っていた**。

### P7. レビューの後に設計を変えた

順序としては理想的でない。レビューはレビュー時点のコードに対するものであり、
**その後に BC 構成と連携方式を変えたため、指摘の前提が一部消えた**（レビュー報告に
追補として記録した）。

ただし変更の起点はレビュー指摘そのものであり、**レビューが機能した結果でもある**。
問題は「変えたこと」ではなく、**変えた後の扱いを決めていなかった**ことである。

### P8. 結果整合にしたことで、失敗が利用者に返らなくなった

購読側で楽観的ロックが衝突しても、**ログにしか残らない**。同期のときは画面に
「他の操作が先に行われました」と出せていた。

**これは結果整合を選んだ以上、避けられない代償である。** 問題は代償そのものではなく、
**ログを見る運用を用意していない**ことである。

### ベロシティ

6 イテレーションの実績は **9 / 7 / 8 / 8 / 7 / 8** で、平均 **7.83SP**。
採用値 8SP との差は 0.17SP であり、**再調整はしない**。

**CI が 2 IT 連続で緑だった。** 依存の更新を開始時に置く運用が定着している。

### レビューの重さについて

IT5 は高優先度 0 件、IT6 は 14 件だった。**IT6 が急に雑になったわけではない。**
Tracking Context の初出で BC 間 ACL を 3 つ追加し、トランザクション境界が
これまでで最も広くなったためである（1 トランザクションで 2 BC・3 集約）。

**境界が広がると、そこを渡る合図（戻り値・例外）の扱いが問題になる。**
P1・P2・P3 はすべてこの 1 点に帰着する。

そして**その合図の扱いを詰めた結果、境界の引き方そのものを変えることになった**
（ADR-010・ADR-009 改訂 1）。指摘が実装の修正で終わらず、設計判断まで遡ったのは
本 IT が初めてである。

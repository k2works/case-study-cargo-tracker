## Keep（続けること）

### K1. Try を「原理」として書き直したことが実際に効いた

IT5 の Try T1 は「レビュー依頼時に**この原理が及ぶ他の場所はどこか**を各指摘へ問う」だった。
5 視点すべてにこれを必須条件として課した結果、**「他になし」と確定できた調査が 4 件**出た。

| 調査 | 結果 |
| :--- | :--- |
| `CAST` を含む SQL の全数確認 | 無防備は検索の 2 箇所だけ |
| 「認可はあるが導線が無い」ずれの全ルート突合 | `/voyages` の 1 件。**逆向きのずれが 5 件**あることも判明 |
| 港コードで機能判定している箇所の走査 | 空虚なアサートは 1 件だけ |
| doc コメントの誤配置（空 `///` の 2 連続） | 3 件 |

**「他になし」と書けること自体に価値がある。** 次に同じ疑いが出たとき、調査済みだと分かる。
IT5 までは 1 箇所を直して終わり、次の IT で同じ形が別の場所から出ていた。

`CalendarText` の共有カーネル移設も、**置換ではなく委譲**で行ったため呼び出し側の変更が 0 だった。

### K3. 縮退順序を着手前に決めておいたが、使わずに済んだ

IT5 に続き縮退 0 件。計画時に理想時間を 63h（直近の超過率で割り戻すと 33h）へ絞ったことが効いた。

## Problem（問題だったこと）

### P1. 【最重要】安全装置を入れたのに守れていない、が 2 件同時に出た

楽観的ロック（ADR-0008）も `X-App-Instance` も、**設計の意図は正しく、テストも緑**だった。
にもかかわらず、いずれも守りたいものを守れていなかった。

| 装置 | 意図 | 実際 |
| :--- | :--- | :--- |
| 楽観的ロック | 失われた更新を防ぐ | 逐次実行でしか成り立たない。`Stale` の扱いは**1 回の衝突で無効化**される |
| `X-App-Instance` | 別インスタンスの応答を切り分ける | 期待値が無く、値を見ても判断できない |

共通しているのは、**「入れたこと」を検証するテストはあるが、「働くこと」を検証するテストが無かった**点である。

- `testRejectsStaleUpdate` は 1 人目の確定を待ってから 2 人目が送る**逐次**テスト
- `testInstanceIdentifierDiffersPerStartup` は**値が変わること**しか見ていない

さらに悪いことに、**同じ IT で `postConcurrently` を新設しておきながら、新設した安全装置の側には
適用していなかった**。IT5 で予約の引き渡しについて「連打・二重送信という実際の壊れ方を通っていない」と
指摘し、その手段まで作ったのに、**その手段を今回の新機能へ向けなかった**。

これは Try T1 が指摘した「原理が及ぶ他の場所」の、最も痛い形の再現である。
原理を理解して Try を書き、レビュー依頼にも書いたのに、**自分が実装する側に回ると適用が漏れた**。

### P2. 「画面単体は正しいがロールをまたぐと切れる」が 3 件

| # | 欠陥 |
| :--: | :--- |
| 1 | `/voyages` は営業へ開いているのに navbar が経路設計者のみで、営業はどこからも到達できない |
| 2 | 荷主に「新規予約登録」「経路設計へ引き渡す」が出る（押すと 403） |
| 3 | `operation.md` に書いた暫定運用が実行できない（経路設計者は `/bookings` を開けない） |

`VoyagePages` は `canManage` でボタンを丁寧に出し分けている。**その同じ判断が `BookingPages` に及んでいない。**
記憶にある IT4 の教訓（ロール別の作業入口ナビ導線の欠落）が、形を変えて再発した。

3 の運用手順は特に重い。**書いた手順が実行できるかを確かめずに運用へ載せると、
安全網があるつもりで何も見ていない状態になる。**

### P3. 検索の日付を無検証で `CAST` へ渡した（IT4 の障害と同型）

`?departureFrom=abc` で DB 例外となり、利用者には 500 ですらなく**応答が返らない**。
IT4 で `2026-02-30` によって同じことが起き、`isIsoDate` を作って直したのに、
**新しい入力経路でその関数を通さなかった**。

`<input type="date">` はブラウザ経由の入力しか守らない。クエリ文字列は誰でも書ける。
「画面が制限しているから安全」という思い込みが、境界の検証を飛ばさせた。

### P4. 空虚なアサートが再発し、ヘルパーが量産できる状態になっていた

寄港地の検証が検索フォームの `<select>`（港マスタ全件）に一致しており、**常に真**だった。
US24 受入基準 2 の唯一の HTTP 検証が何も見ていなかった。

さらに `probeConcurrently` は期待本文に `""` を渡すと本文検証が黙って無効になる設計で、
**空虚さを API の契約として制度化していた**。IT5 で 5 件見つけた空虚なアサートを、
ヘルパーが再生産できる形にしていた。

**そして、その修正として書いた `VoyagePagesTest` で自分が同じ罠を踏んだ**
（`not contains "GENERAL"` が `<select>` の `value` に当たって落ちた）。
原理を理解していても踏む。

### P5. `VoyagePages`（455 行）に描画テストが 1 件も無く、XSS の検証がどのレベルにも無かった

`ShipperPages` 等には描画単体テストがある。新しい BC を立ち上げるとき、
**既にある層の構成を写さなかった**。結果として、エスケープの検証が
統合テストを含めてどこにも無い状態で 1 イテレーション動いていた。

### P6. 設計にあるものが実装にあると考えていた

`voyage` / `carrier_movement` テーブルは `data-model.md` に定義があったが、
**V1 で作られていなかった**。マイグレーションが失敗して初めて気付いた。

### Try の書き方について（IT5 Try T1 の継続）

IT5 で「Try を手順として書くと、その手順は守られるが同じ原理が及ぶ別の場所が漏れる」と学んだ。
**IT6 でその学びはレビュー依頼には適用できたが、実装には適用できなかった**（P1）。

そこで T1-T8 はいずれも**実装タスクの DoD またはタスク 0（着手前）に置く**。
レビューは最後の関門であり、そこでしか効かない Try は「作ってから直す」ループを固定する。

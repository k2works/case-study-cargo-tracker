## エグゼクティブサマリー

**貨物が実際に動き出した。** 荷役作業員が追跡番号で貨物を特定し、受領・積込・荷降し・引取を記録すると、その結果が追跡の状態に反映される。IT6 までは追跡番号を発行しただけで、貨物はどこにも動いていなかった。

あわせて **handlingms（7 つ目のサービス）の初実装**と、**サービス間の非同期連携 2 本目**（handlingms → RabbitMQ → trackingms）を通した。REST の ACL（handlingms → bookingms）も 2 本目である。

**返済枠は 12 / 12 完了。** IT5 から 3 IT 持ち越していた SonarQube のセキュリティホットスポットも、**依頼ではなく修正で閉じた**——中身を読んだら本物の弱点だった。

クローズレビューで高優先度 **11 件**が出た。**すべてクローズ前に対応した。**

### 返済枠（12 件・SP 対象外）

**12 / 12 完了。** とくに次の 3 件は、実施したこと自体より**見つかったもの**に意味があった。

- **0.11**: `ignoreFailures = true` を外したところ、**SpotBugs は Java 25 のクラスファイルを読めておらず、1 クラスも解析していなかった**。ツール版を上げて初めて中身が見えた
- **0.1**: 3 IT 持ち越していたホットスポットは、**指摘どおりの弱点だった**（`EmailAddress` の正規表現。区切りの取り方が一意に決まらず、長い入力で長さの 2 乗に比例する時間がかかる）。曖昧さを消す代替も実測したところ、2000 文字で `StackOverflowError` になった。正規表現をやめて線形の判定にし、上限を設けた
- **0.6**: 冪等を一意制約に決めさせる形に変えたが、その `ON CONFLICT` を **H2 が解釈できない**ことを、後から入れた方言スモークが検出した（ローカルの手軽な起動先が挿入の瞬間に落ちる形）

## レビュー結果

高優先度 **11 件**。**すべてクローズ前に対応した。**

| # | 何が起きていたか |
| :--- | :--- |
| 1 | **追跡が巻き戻る。**「戻せる遷移は作らない」と書いてあるのに、現在の状態を見ていなかった。**送り直す手段は同じ IT で自分が用意した**ので、この経路は実在する |
| 2 | 「同じ内容の更新で行を触らない」と書いてあるのに、無条件に書き込んでいた |
| 3 | `offRoute` を応答・イベントで潰しても全テストが緑だった |
| 4 | 追跡番号で貨物を引く SQL が実 DB で一度も実行されていなかった |
| 5 | **追跡管理者が `/handling` を開いても何もできなかった**（メニューには出ていた） |
| 6 | 契約に値の語彙が無く、種別を足すと受け手が黙って何もしない |
| 7・8 | 「購読しない」「動かさない」という否定の決定 2 件が、表に書かれただけで検査が無かった |
| 9 | 述語と操作が同じ条件を二度書いていた（`Cargo` の 4 か所） |
| 10 | testFixtures に範囲の検査が無かった（契約を置くと決めたのに） |
| 11 | 設計正典が ADR-023 に追随しておらず、決定と正面から矛盾していた |

**5 視点のうち 3 つが独立に #1 を指摘した。** 1 視点だけなら見落としていた可能性がある。

対応の過程で 2 件見つかった。

- **空欄の作業日時が「2000-01-01 の作業」として記録される。** レビューは `RangeError` と報告したが、実測すると誤った値が記録される形だった。**報告をそのまま信じて直していたら残っていた**
- **コンテナ起動の競合でビルドが不定期に落ちる。** クローズ作業中に 4 回踏み、3 回目まで「環境の都合」として流していた

中・低優先度は方針を明記して[レビュー結果](../review/イテレーション7_review_20260823.md)に記録し、大半を IT8 に送った。

## 次イテレーションへの引き継ぎ

IT8 は US17（貨物状態の手動更新）・US18（追跡情報の照会）・US19（遅延例外）・US20（破損・紛失例外）で 9 SP。

- **荷主が初めて自分で状態を見る。** IT7 まで追跡の状態を見られるのは DB とデモだけだった。US18 で外から見えるようになると、**IT7 に潜んでいた状態の誤りが荷主に見える**
- **通知の仕組みが入る。** US17・US19・US20 がいずれも「荷主に通知が送信される」を受入基準に持つ。US15-5（荷役の状態変更通知）はここで代替から本物になる
- **ふりかえりの Try 7 件**（とくに Try 1「〜しないと書いたコメントは、その場で壊して赤を確認する」・Try 3「ADR のコンプライアンス表に検査の場所を書く」）を計画のタスクと DoD に落とす
- **`ONBOARD_CARRIER` / `EXCEPTION` の扱いを先に決める。** US17・US20 を入れるとき、「未知の種別」と「到達不能な値」が同じ「何も起きない」に落ちる状態を解消してから着手する

> **US19 を「通知基盤」と呼んでいたのは誤りでした**（IT6 の [ADR-021](../adr/021-shipper-notification-and-confirmation-transitions.md) 以来）。US19 は**遅延例外の処理**で、通知はその受入基準の 1 つです。「通知が入るのは IT8」という時期の読みは合っていましたが、ストーリーの名前が違いました。IT8 の計画時に気づき、設計・ADR・過去の計画の記述を直しました。

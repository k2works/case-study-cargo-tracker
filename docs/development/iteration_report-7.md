## エグゼクティブサマリー

**経路設計者が、引き渡された予約に対して「期限内に運べる経路の候補」を画面で得られるようになった。**
候補は Flix の Datalog による到達可能性判定から自動算出され、直行便を最優先に推奨順で並ぶ。
これにより IT8 の「経路の選択・確定（US09）」が入力を得られる状態になった。

併せて、設計に定めながら IT1 から未実装だった **HTTP ランタイムの防御**（同時実行上限・
バックプレッシャ・タイムアウト）を実装し、**3 IT 連続で再発していた導線の欠落**を
機械検査へ落とした。

計画 11 SP をすべて完了し、縮退は 1 件も行っていない。ベロシティは 2 イテレーション連続で 11 SP。

一方で、**レビューで高優先度 14 件**が挙がった。最も重いのは
**「防御を足したことが新しい単一障害点を作っていた」**（過負荷時に liveness が 503 を返し、
オーケストレータがインスタンスを再起動する）である。IT3 で DB について学んだ再起動ループが、
セマフォ経由で同型再現していた。12 件はクローズ前に対応し、2 件は限界として明文化した。

## 技術的成果

### 1. Datalog による到達可能性判定（US08）

Flix 固有の Datalog 制約解決を**設計どおり初めて実装に使った**
（[バックエンドアーキテクチャ](../design/architecture_backend.md)「Routing Context における Datalog の活用」）。

**2 段構えとした**。推移閉包が答えるのは「港がつながっているか」だけであり、
実際に乗れるかは時刻と対応貨物種別に依存する。

1. Datalog で「出発地から仕向地へそもそも到達しうるか」を判定し、到達し得ない依頼を打ち切る
2. 到達しうる場合のみ深さ優先で辿り、時刻・種別・航海の重複を検証する

**Datalog はモジュール内部に閉じ、公開型に Datalog の型は現れない**（`arch-lint` で担保）。

航海 1 本から「乗れる区間」を i ≤ j の全組み合わせで展開することで、
**寄港地からの積み込み・寄港地での荷降ろし**が探索対象に入った（IT6 引き継ぎ M1）。

### 2. 境界の扱いを 3 点固定

| 境界 | 判断 | 理由 |
| :--- | :--- | :--- |
| 到着期限 | **日付単位**で比較 | 期限は `DATE`、到着は `TIMESTAMP`。素朴に比べると期限当日着が全滅する |
| 接続 | **同時刻を成立**とする | `Voyage` のビジネスルール 6 と揃える。最低接続時間は業務ルール未定義であり実装が決めない |
| 出発日 | **出発可能日（今日）以降**に限る | 過去の便が 1 本混ざると一覧全体が信用できなくなる（レビューで是正） |

暦法（`toEpochDay` / `daysBetween`）は共有カーネルの 1 箇所に閉じた。

### 3. HTTP ランタイムの防御（TS12）

IT1 から未実装だった 3 項目を実装した。**全リクエストが必ず通る 1 点**（`Server.start`）で適用する。
ルートごとに書くと書き漏らしたルートが無防備になる——認可をルーティング表の宣言にしたのと同じ判断である。

| 項目 | 実装 |
| :--- | :--- |
| 同時実行の上限 | セマフォ（既定 200・`APP_MAX_CONCURRENT_REQUESTS`）。**待たずに断る** |
| バックプレッシャ | `503` + `Retry-After`。画面を返し、ダッシュボードへの導線を置く |
| タイムアウト | 30 秒（`APP_REQUEST_TIMEOUT_SECONDS`）。別スレッドで処理し `cancel(true)` で割り込む |

**ヘルスチェックは枠を通さない**。過負荷で liveness が `503` を返すと、
オーケストレータが「混んでいるだけで生きている」インスタンスを再起動する
（レビューで是正。詳細は「限界と課題」）。

### 4. 導線の機械検査（TS13）

`navItems` に実装状態（`Implemented` / `Planned`）を持たせ、
`NavigationReachabilityTest` がルーティング表と**双方向に**突合する。

- `Implemented` → ルートがある（行き止まりを作らない）
- `Planned` → ルートがない（実装したのに準備中のままを作らない）
- 項目を見られるロールは、そのルートを通れる

未実装の項目は**消さずに「準備中」として押せなくした**。
消すと荷受人・荷役作業員・経理は項目が全滅し、「担当する業務がありません」とだけ表示される。
権限は正しいので問い合わせても解決しない。

### 5. ACL の方向を確定（ADR-0009）

Routing が Booking から依頼を引く（pull）。実装が `cargo` テーブルを 1 文で引き、
**Routing の言葉へ翻訳する**（`cargo_type` → `CargoCapability`）。
`BookingJdbcShipperExistence`（Booking → Shipper）と対称であり、
本プロジェクトの ACL の一般形は「**必要とする側が、必要な形に翻訳して引く**」となった。

**未知の貨物種別を `General` へ倒さない**。危険物を一般貨物として読むと、
危険物を運べない航海が候補に出る（IT6 の温度単位と同じ判断）。

## 限界と課題

### 明文化して残した限界（2 件）

| # | 限界 | 判断 |
| :--: | :--- | :--- |
| 1 | **タイムアウトで枠を返した時点で、処理はまだ走っている可能性がある**。`cancel(true)` は割り込み要求にすぎず、JDBC の待機や純粋な計算ループは応答しない。したがってタイムアウトが多発する状況では「同時実行 ≤ N」が破れる | 恒久対策 2 案（枠の解放をタスク側へ移す／`setQueryTimeout` の併用）はいずれも「同時実行 200」の意味を変える。**TS12b（IT8）の実測を見てから決める**。測らずに設計を変えない |
| 2 | **`booking_status = 'ROUTE_PROPOSED'` のリテラル結合を `arch-lint` が検出できない**。Booking が状態名を変えると Routing は静かに `None` を返す | ACL をインフラ層に置く設計の代償である。[arch-lint 規約仕様](../design/arch_lint_rules.md) に既知の穴として記載し、守るのは統合テストとした |

**成功基準 6（「タイムアウトで `504` が返り、スレッドと接続が解放される」）は部分達成である。**
`504` は返るが「解放される」は保証できていない。基準の書き方が実態より強かった。

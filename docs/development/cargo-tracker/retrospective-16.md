## Keep

### 「実物を通す」ことでしか出ない欠陥が、また 8 件出た

層ごとの検査はすべて緑でした。出たのは次の場所です。

- クラスタ E2E の**準備だけ**で 3 件——Dockerfile 7 本のモジュール写し忘れ（全イメージが作れない）、既存クラスタの DB 不足、管理者が業務画面を開けない
- 受け入れスイート（8 サービスを単一 JVM）の実装で 5 件——識別子が列にあふれる、**応答コードの無い失敗が成功として通る**、発行直後の読み取り、状態コードの推測（`ISSUED`／`INVOICED`）、必須項目の欠落

**「クラスタ E2E はモックが通す欠陥を捕まえる」は、E2E を書く前の準備段階でも効きました。** イメージを作る・DB を用意する・画面から踏む、のどれもが検査です。

### 待ちを読み口の値で判別する形が、設計の中心になった

`ChainReadiness` は工程ごとに「何が読めたら次へ進めるか」を宣言し、**待たない工程も宣言します**。既定を「待つ」にすると、読み口を持たない工程が上限まで待ってから失敗します。

`ChainWaitTest` は経過時間ではなく「何回読み直したか」で判別するので、脆弱な実装に戻すと必ず赤くなります。IT7 の「時間で守るテストは判別しない」がそのまま形になりました。

### 名簿を数え上げる検査が、その場で欠陥を捕まえた

`DockerfilesCopyEveryModuleTest` は `settings.gradle.kts` の include を出典に照合します。「足したら 8 か所を直す」という約束は、**8 か所あるという事実そのものが忘れられる**——実際に 7 本が壊れていました。

### 往復の契約テストが、発行側も集約も見逃した欠陥を捕まえた

個人情報を暗号化する Converter がイベントを組み直すときに `simulated` を数え落とし、常に `false` に潰していました。印は契約にも集約にも載っているのに、投影には「本物」として届いていた。**組み直す変換は、運ぶ項目を数え落とします。**

## Problem

### この IT で、自分でセキュリティの穴を作り込んだ

`simulated` を誰でも立てられる形にしていました。営業ロールの利用者が本物の荷主を「シミュレーション由来」で登録すると、**営業の一覧にも経理の一覧にも出なくなり、消えたことに誰も気づきません**。

原因は、**印を「付ける側の都合」だけで設計した**ことです。「シミュレーションは人と同じ API を叩く」（ADR-0020 決定 2）を守ることばかり考え、「同じ API を人も叩ける」ことを考えていませんでした。**開いた入口は、意図した相手以外も通ります。**

### 受入基準を 2 件、「書いてあるが満たしていない」まま全緑にした

- US34 §5（識別子から業務画面へ）——行き先 3 つのうち 2 つが**引数を読まない一覧**へ飛び、しかも請求一覧は除外対象なので絶対に出ない
- US33 §3（実データに混ざらない）——経路設計の作業一覧が外れておらず、失敗シナリオを流すたび偽の依頼が滞留する

どちらも検査はありました。US34 §5 は**行き先 1 つだけ**を確かめていたので、残り 2 つが壊れていても緑でした。

### 検査を書いたことと、検査が働くことを、また混同した

レビューで 4 件出ました。

- 「要確認一覧に出ない」——除外が未実装で、成功経路では項目が 1 件も作られないため**常に空で緑**
- `ScenarioTest` が `contains` で順序を見ていない——工程を入れ替えても緑
- 「精算済」を待っていない——最後の工程は請求書までしか待たない
- `StepRole.of()` が本番からほぼ呼ばれていない——**本番が参照しない表**を固定していた

`DockerfilesCopyEveryModuleTest` も、最初は入力を宣言し忘れて UP-TO-DATE で走らず、**赤を 1 度も見られませんでした**。

### 前 IT の Try を採点しなかった（Try T7 そのものを落とした）

IT15 の Try 7 件を採点する約束（T7）だったのに、**ふりかえりを書くときに採点表を作りませんでした**。気づいたのは、利用者から「イテレーション計画 16 の成功基準にチェックがついていない」と指摘されたときです。

**成功基準を埋める作業そのものを飛ばしていました。** DoD は埋めたのに成功基準は空のまま「クローズ確定」と報告しています。DoD と成功基準は別の表で、**片方だけ埋めても採点したことにならない**——しかも成功基準のほうに Try の採点が入っていました。

採点してみると、7 件中 4 件が達成・2 件が一部・1 件（T7 自身）が未達でした。**採点しなければ「全部できたつもり」のまま次へ進んでいました。**

### 監視ループが自分自身に一致して 40 分止まった

`pgrep -f "gulp k8s:images"` が監視コマンド自身の文字列に一致し、永久に終わらない待ちが 3 本できました。**待ち条件が自分を数えていないか**を確かめていませんでした。

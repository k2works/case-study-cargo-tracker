## 技術的成果

### 既存集約への不変条件の追加（中盤の型）

- `Voyage.updateSchedule`：未登録の拒否・キャンセル済みの拒否（不変条件 5）・登録と共有する `validate`
- `Cargo.updateSpecification`：遷移表の述語（`BookingStatus.canUpdateSpecification`）・**期限は「変えたときだけ」検査**
- `VoyageCancelledEvent` を発行側コマンド無しで先に置いた（不変条件 5 に到達する手段が要るため）。発行側は IT5

### 導出を 1 か所へ寄せた（R.1・R.2）

要確認一覧の識別子を、共有カーネルの `AttentionItemId`（事実から導く 16 進 32 文字）に統一しました。**返済の過程で、2 つの BC が区切り文字ごと違う導出をしていたことが分かりました。**

既存行を付け替えるマイグレーション（booking `V005`・routing `V006`）を置き、**SQL の導出と Java の導出が同じ値になること**を統合テストで固定しています。片方だけ直すと、既存クラスタの行だけが新しい導出と食い違い、同じ事実が 2 行に並びます。

### 認可の宣言に HTTP メソッドを入れた（ADR-0006 決定 6）

`PUT /bookings/{id}` は `GET /bookings/{id}` と同じ経路です。経路だけの宣言では「読めるが直せない」を表せないため、`RoleAuthorization` を `List<Rule>`（メソッド・パターン・ロール）に変えました。ADR-0006 に決定 6 として追補し、**宣言されていない経路とメソッドの組は通さない**検査を同じ変更で置いています。

### 判定を正典から読むテスト

`voyageRules.canon.test.ts` を追加しました（`transitions.canon.test.ts` と同じ形）。フロントの述語が Java の集約とずれたら赤になります。

## Keep

### 判定を 1 か所に寄せる形が、初めて「構造で効いた」

陸揚げ地の候補は `DischargeCandidates` というドメインサービス 1 本に寄せ、**集約（断る側）と読み口（出す側）の両方がそこを呼ぶ**形にした。`DischargeCandidatesTest#everyCandidateIsAccepted` が候補全件を集約の断る側に通すので、「画面に出ているのに押すと断られる港」は構造上つくれない。

レビューでは programmer・tester・architect の 3 視点が独立にこれを良い点として挙げた。**今まで「片方だけ直る」形で繰り返し失敗してきた場所**なので、効いたことを記録しておく。

### 名簿を手書きしない検査が、2 IT 後に働いた

`RateTableParityTest#everyCancellableStatusHasAFeeRate` は `BookingStatus` の列挙から回して料率の漏れを見つける。名簿を手で書いていたら、状態を足したときに名乗り出ない。

同じ形で、IT13 の負債枠で置いた `AcceptanceFixturesAreNotTimeBombsTest`（受け入れフィクスチャの固定日付を赤にする）が、**本 IT で私が書いた 5 か所を実際に捕まえた**。置いた検査は 2 IT 後に働くことがある。

### 承認しても追跡を閉じない、という判断を 3 か所で同じ言葉にした

業務上いちばん誤解されやすい点なので、画面の説明文・一覧の見出し・マニュアルで同じ言葉を使った。レビューの user 視点が「繰り返し書いてあるのは正しい」と挙げた。

### 「余力次第」を使わなかった

IT13 から 3 IT 続いた 7 件は、6 件を返し、**残る 1 件は行き先（Release 3.0）と理由を書いて送った**。引き継ぎ 2（Processing Group の分け直し）も「やらない」と決めたうえで、token の移行手順と着手の引き金を手順書に書いた。

## Problem

### 層が全部緑でも、業務が回っていなかった（最重）

レビューの高 13 件のうち **4 件は「記録はあるのに読み口が無い」形**だった。

| 何が欠けていたか | 気づけなかった理由 |
| :--- | :--- |
| 承認した陸揚げ地が荷役の現場に届かない | クラスタ E2E が**追跡番号を持って API を直接叩いた**ので、現場が対象を見つけられないことを踏まなかった |
| 却下の理由が申請した営業に届かない | 受入基準 §7 の落とし先は正典（`ui_design`）に書かれていたが、実装の受入テストは集約と履歴までしか見ていない |
| 陸揚げ待ちがどの画面にも出ない | 列は T5 で足した。読み口に載せる作業を別タスクにしなかった |
| 承認待ちの件数（§4 の落とし先）に検査が無い | 件数ブロックを丸ごと削っても全テストが緑だった |

**集約・投影・往復テスト・受け入れテスト・クラスタ E2E がすべて緑のまま**残っていた。層ごとの検査は自分の層しか見ず、E2E も「自分が書いた道」しか通らない。

### 正典が実装より先に正しいことがある

却下の知らせも陸揚げ待ちも、`ui_design.md` には最初から書かれていた。**実装が正典に追いついていないことを、クローズのレビューまで誰も見ていなかった。** 逆に正典が古かった箇所も 1 件あった（キャンセル料の受け皿）。どちらの向きにもずれる。

### 名簿方式の検査が、次に足すものを守らなかった

承認待ち一覧の認可が `GET /bookings/*` に吸われ、営業・経路設計・経理にも開いていた。**同じ形の実測がコードのコメントに残っている場所での再発**である（「経路設計者の作業一覧が営業にも見えた」）。個別の経路を 1 本ずつ検査する形では、次に足す一覧が名簿から漏れたときに誰も気づかない。

### 検査を書いたが、判別していなかった

取り消した荷役の現在地を検査するテストを 1 本書いたが、**最初の版は壊れた実装でも緑**だった（取り消しても同じ港が候補に残るので承認が通る）。「赤にする」と決めていても、**赤にしてみるまで判別するかは分からない**。

### 申請と判断のあいだの時間を考えていなかった

§8（引取以降はキャンセル不可）は申請の時点でしか見ておらず、申請中に引き取られると承認が通った。**2 段階の操作では、1 段階目の検査は 2 段階目を守らない。**

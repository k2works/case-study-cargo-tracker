# リリース完了報告書 2.0 - Cargo Tracker（CQRS / Event Sourcing 版）

**報告書作成日**: 2026-09-14

## 概要

Cargo Tracker v2.0「精算とキャンセル」のリリース完了報告書です。全 3 イテレーション（IT13〜IT15）、**22 ストーリーポイントを消化しきり**、貨物輸送の業務の輪が閉じました——見積 → 予約 → 経路設計 → 確定 → 追跡 → 荷役 → 引取 → 請求 → 発行 → 入金 → 精算済、そして**止めるとき**（キャンセルと返金相当のキャンセル料）まで。

**本リリースで初めて「お金」を扱いました。** 料金の算出・割引・税・調整・発行・入金・取消・キャンセル料は、いずれも間違えると業務上の損害に直結します。そのため本リリースでは「**黙って 0 円にしない**」「**取りこぼした請求はあとから取り返せない**」を繰り返し判断の軸にし、算出できない場合は必ず経理宛の要確認へ落とす形に統一しました。

**局面は終盤（アウトサイドイン）のままです。** 新しい集約は `Invoice` の 1 つだけで、あとは既にある集約を業務シナリオ起点で束ねています。US30（輸送中のキャンセル）は 4 サービスの連鎖（予約 → 追跡・荷役・請求 → 陸揚げの荷降し → 追跡を閉じる）で、本プロジェクトで最も長い連鎖になりました。

### IT14 の未達がリリース内で閉じた理由

未達の中身は「`PaymentRecordedEvent` を bookingms が処理しない」——BC をまたぐ配送の欠落でした。**1 サービスの中で完結する検査はすべて緑**で、往復の検査だけが無かった。IT15 の T-1 で調べたところ、当初の見立て（「token は追いついているのに配送されていない」）は誤りで、**投影に `BookingSettledEvent` のハンドラが無かった**ことが原因でした。

この経験から IT15 では「**BC をまたぐ契約イベントに、向きごとの往復テストを置く**」を Try に立て、`CancellationRoundTripIT` として実装しています（3 つの購読先の表を 1 本で見る）。

### 技術的な成果

- **`Invoice` 集約**（本リリース唯一の新設）。算出・調整・発行・入金・取消・キャンセル料を 1 つの集約で扱い、状態は `BillingStatus` が正典（ADR-0017）
- **料率を設定に外出しした**（ADR-0016）。`cargo-rates.yml` に置き、名簿を手書きしない検査（`RateTableParityTest`）が列挙から回して漏れを見つける
- **営業日の数え方を共有カーネルに置いた**（ADR-0015）。留置日数と支払期限で同じ数え方を使う
- **処理の列を貨物ごとに分けた**（`@SequencingPolicy`）。IT12 で「この版に手立てが無い」と書いた判断が誤りだったと IT13 で分かり、1 件の毒が無関係の貨物を巻き添えにする形を解消
- **判定を 1 か所に寄せる形が構造で効いた**（IT15 の `DischargeCandidates`）。集約（断る側）と読み口（出す側）が同じ関数を呼ぶので、「画面に出ているのに押すと断られる港」は構造上つくれない
- **認可の名簿そのものを固定する検査**（IT15 の `RoleAuthorizationDeclarationTest`）。個別の経路を 1 本ずつ検査する形をやめた

## 総評

### よかったこと

**「余力次第」を一度も使いませんでした。** 引き継ぎと負債は毎 IT で行として立て、返せないものは行き先と理由を書いて送りました。繰越ゼロは IT15 で 11 回連続です。IT13 から 3 IT 続いた 7 件も、6 件を返して 1 件を明示的に送っています。

**置いた検査が、あとの IT で働きました。** IT13 の負債枠で置いた「受け入れフィクスチャの固定日付を赤にする」検査は、2 IT 後に私が書いた 5 か所を実際に捕まえました。IT13 で入れた `@SequencingPolicy` も、IT15 のキャンセルの連鎖でそのまま効いています。

**クラスタ E2E が、モックでは出ない欠陥を毎 IT で捕まえました。** IT13 は請求書 ID の桁あふれと調整明細の重複、IT14 は見積と請求の差額、IT15 はマニュアルの文言の食い違い。

### 学んだこと（次のリリースへ）

**層が全部緑でも、業務が回らないことがあります。** IT15 のレビューで出た高 13 件のうち 4 件は「記録はあるのに読み口が無い」形で、集約・投影・往復テスト・受け入れ・クラスタ E2E がすべて緑のまま残っていました。**クラスタ E2E ですら、追跡番号を持って API を直接叩いたので現場の穴を踏みませんでした。**

**正典が実装より先に正しいことがあります。** 却下の知らせも陸揚げ待ちも `ui_design.md` には書かれていましたが、実装が追いついていませんでした。逆に正典が古かった箇所も 1 件ありました。**どちらの向きにもずれます。**

**成功基準の一覧は、事実と食い違うことがあります。** IT14 では受け入れテストのステップ定義が 1 つも無いまま「緑」と記録され、フルビルドも前のコミットから赤のままでした。IT13 では Try で置いた規約検査 3 本が 1 件も走っていませんでした（入力宣言のパス誤り）。**一覧の上では揃って見えます。**

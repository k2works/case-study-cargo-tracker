## Keep（続けること）

### 引き継ぎ枠を Day 1 の独立コミットで消化した

IT4 のふりかえりで出た高 2 件を含む 6 件を、**Day 1 にまとめて返しました**。IT4 の学び（「余力次第の返済枠は毎 IT 繰越されて固定化する」）をそのまま形にしたもので、**繰越ゼロ**で終わっています。返済を後ろに置かなかったので、US08 の実装が返済に押し出されることもありませんでした。

### 並列レビューをクローズの最初に起動した（IT4 の T8）

3 イテレーション連続で有効でした。今回は **約 4〜5 分**で 5 通とも届いています（IT3 は 4〜6 分、IT4 は約 45 分）。**所要は回によって大きく振れる**ので、「何分で返る」を前提にした運用は作れません。「クローズの最初に起動して待つ」だけが、どちらに振れても成立します。

**本 IT で最も重い欠陥（打ち切りの順序）を見つけたのはレビューです。** 単体・統合・受け入れ・クラスタ E2E のすべてが緑の状態でした。

### インサイドアウトで、探索から画面へ順に組んだ

routingms の探索（純粋なドメインサービス）→ `@QueryHandler` → 契約 → ACL → Controller → 画面の順で組みました。探索の判断を単体テストだけで詰められたので、グラフの組み立て（実 DB）と分けて考えられています。**打ち切りの欠陥を直したときも、直した場所は探索の 1 か所だけ**で済みました。

### 契約クエリを「ゴールデン一致」と「往復」の両方で固定した

計画時のレビューで「片側だけでは購読側の期待ずれを捕まえられない」と指摘され、両方を置きました。ゴールデンは壊して赤を見ています。

## Problem（うまくいかなかったこと）

### P1: 実環境で症状を見ながら、実装ではなくテストを直した

**本 IT で最も重い問題です。** クラスタ E2E で「登録した直行便が候補に出ない」症状に当たり、`cluster.spec.ts` のコメントに「既存の 16 日の便 20 件に押し出された」と**実測を書きながら**、原因を「同着の並び」と読んでテスト側を回避しました。実際は候補 20 件の打ち切りが並べ替えの前に効いており、**US08 §受入基準 4・5 が破れていました**。

レビューの 4 視点が同じ欠陥を指すまで、全緑のまま残っていました。ADR-0007 に「決定 2 の訂正」として経緯を記録しています。

### P2: 書いた保証が 3 件、空手形だった

- `RoutingQueryHandler` の javadoc と `architecture_backend.md` の規則表が「知らない港・種別は断る」と書いていたが、断っていたのは種別だけ
- `findEdgesFrom` の javadoc が「一覧と同じ絞り込みを共有する」と書いていたが、共有しておらず、しかも XML のコメントは**意図的に違う判断**であることを説明していた
- 受け入れシナリオ「設計し直すと古い区間は残らない」が、設計し直していなかった

いずれも javadoc・規則表・テスト名という「読めば守られていそうな形」でした。IT4 の学び（書いた保証は赤で固定する）が、同じ形で再現しています。

### P3: REST の層が丸ごと空いていた

`GET /bookings/{id}/route-candidates` と 503 の応答は、フロントの自作モックとクラスタ E2E だけが通していました。**`./gradlew build` では 1 度も通りません。** 層の分担は概ね妥当でしたが、ここだけ穴が空いていたのをテスターの視点が指しています。

### P4: 品質ゲートを「ストーリー完了ごと」に回さなかった（IT4 の T4 が守れていない）

層別カバレッジと SonarQube をクローズまで回さず、**CI が JaCoCo の分岐閾値で 2 回落ちました**。値オブジェクトの「断る側」の分岐が一度も踏まれていない状態で、クローズに入っています。T4 は IT4 で立てた Try で、今回守れていません。

### P5: 受入基準の未達を 1 件、計画時に見落とした

US09 §受入基準 4「最適な候補がない場合、経路条件調整（US10）に進める」は、US10 が本 IT のスコープに無い以上、着手前から未達が確定していました。費用の 2 件は計画時に明記していたのに、この 1 件は挙がっていません。**テスターの視点が指すまで気づいていません。**

### P6: 経路設計者以外の画面が、経路の進み具合を映していなかった

予約詳細に経路設定状態が無く、営業は「経路が決まったか」を予約詳細から読めませんでした。ロール別の到達性は確かめていましたが、**同じ画面を別のロールが見たとき何が読めるか**は見ていません。

### P7: 断りの文に内部の列挙名が出ていた

`経路設計を依頼していない予約には経路を確定できません（NOT_ROUTED）`。業務担当者には読めず、マニュアルとも照合できません。マニュアルに「括弧の中は内部の記録用の名前です」という**注釈を足して済ませていた**のが、実装で直すべき問題でした。

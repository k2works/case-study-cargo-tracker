## Keep

### 手立てを機械に移すと守れる——3 IT 続けて守れなかった Try が今回は守れた

Try T4「重い検証は 1 本ずつ」は IT9・IT10・IT11 と **3 IT 続けて守れませんでした**。文章で
「気をつける」と書いていたからです。今回は `npx gulp dev:backend:guard` を序盤に作り、
**走っている Gradle があれば断る入口**からしか回さないようにしました。IT11 の `.gitmessage`
（品質ゲートの結果を書く欄）と同じ形です。

Try T5「フルビルドは分けて回す」も `dev:backend:full:split` に落とし、5 群の単位を
`operation.md` に書きました。**この環境では 10 分を超える通しが完走しない**という制約を、
手順の文章ではなくタスクの形にしたので、以降どのセッションでも同じ分け方になります。

### 正典が実装不能なとき、正典を直した

3 か所あります。

1. **履歴を Event Store から読む**（`data-model.md`）。`@QueryHandler` から
   `EventStore.transaction(ctx).source(...)` を回すと、タグを指定しても `havingAnyTag()` でも
   **0 件**になります（実測。集約の復元は同じ API で動くので、クエリの `ProcessingContext` が
   この読み方を支えていない）。`customs_status_history` 投影にし、主キーを元イベントの識別子に
   しました（リプレイで積み上がらない。ADR-0012 の前例）
2. **`held_business_days` に確定値を写す**（V006 のコメント）。写す相手は契約イベントですが、
   投影は内部イベントだけを読みます。**列は常に 0** で、読むときに数えます
3. **`HolidayCalendar` を共有カーネルに置く**（当初案）。ADR-0001 決定 4 の名簿は「全 BC で
   同じでなければならない業務上の理由」を求めます。営業日を数えるのはいま handlingms だけ
   なので handlingms に置き、US21（IT13）で billingms が保管料を数え始めたら移します

**数を合わせるために「実装した」ことにしていません。** どれも理由と代替を書いて残しました。

### イベントの形をいま決めた（購読側がまだ無くても）

`CustomsStatusChangedEvent` に `bookingId` と `heldBusinessDays` を載せました。購読するのは
trackingms（例外の自動起票）だけで、billingms は US21（IT13）からです。

**受け皿だけを置くことはしませんでした**——記録を積んで誰にも読めない状態になり、IT10 で
2 回踏んだ形です。一方で**項目はいま決めます**。イベントは追記専用で、後から足しても過去の
イベントには入りません。

## Problem

### P1: 「記録はあるのに読み口が繋がっていない」を 2 か所で作った

クローズのレビューで出た高 3 件のうち 2 件がこれです。

- **S02 の「督促してください」が全件の一覧に着いた。** `?overdueOnly=true` を渡していたのに、
  S52 が URL を読んでいませんでした。件数から来た人が、どれが督促の対象かをもう一度自分で
  絞ることになります。`DashboardPage.test.tsx` は href を検査していましたが、**着いた先の
  挙動は誰も見ていません**でした
- **留置から出ると営業日数が 0 に落ちた。** 列を返していましたが列は常に 0 です。5 営業日
  留置されて通関済になった申告が「留置 0 営業日」に見え、US21 の調整根拠がそこで消えます

IT10 の P1（記録したが読めない）と同じ形です。**今回は記録と読み口を対で出したつもりでした**
——実際、S53 の履歴も S52 の一覧も作りました。抜けたのは**画面から画面への繋ぎ目**です。

### P2: 自分が書いた保証形を疑えなかった

`heldBusinessDaysOf` の javadoc は「留置から出たあとは列の確定値を返す」と書いていました。
その列を書いているのは自分で、**0 のままにする判断も自分でした**。V006 のコメントも
「`CustomsStatusChangedEvent.heldBusinessDays` から写す」と書いたままでした。

「履歴はイベント列から読む」も 4 か所に残っていました（`HandlingQueries` の javadoc・
`architecture_backend.md`・受け入れ feature のコメント・計画の ER 図の note）。正典は注 N3 で
直したのに、**書いた側の文が古いまま**です。IT11 の P（「〜しない」コメントは赤で固定する）が
再現しました。

### P3: 引取待ちが IT11 の文言のまま「分かりません」と言い続けた

`AwaitingClaimPage` は「通関の状態はこの画面では分かりません。荷主または通関業者に確かめて
から引き渡してください」と出していました。コメントには「通関の記録は US29（IT12）で作る」と
書いてあり、**その IT が今回**です。

しかも US29 で引取のガードが有効になったので、通関済でなければ引取そのものが断られます。
**現場が確かめる先を間違えたまま、荷受人を窓口で待たせる**ことになります。

「後の IT で作る」と書いたコメントは、その IT で回収する対象として拾えていませんでした。

### P4: 「返らない」と判断したが、返っていた

Try T7「5 通そろうまでクローズしない。返らない視点には再送する」を守ろうとしましたが、
48 分待っても 1 通も届かず、催促 5 通も無応答だったので逐次フォールバックに切り替えました。

**その後、5 通すべてが届きました。** 実際には起動から約 40 分で完了しており、通知が遅れて
いただけです（4 通は長さ制限で切れており、続きを個別に求めました）。

**遅着分に実欠陥が 5 件入っていました。** 逐次で回した分では出なかったものです。

- **再留置が誰にも見えない**（`containsKey` で黙って捨てていた）
- **「不可」でも税関保留を解決していた**（誰も追わない貨物が港に残る）
- **申告日時がブラウザの時間帯で送られていた**（コメントは「業務タイムゾーンで送る」）
- **決着した申告にも更新フォームが出ていた**（モックが本物より甘く、テストは緑）
- **宣言した安全網が 2 つ実在しなかった**（`portTimeZone.canon.test.ts`・通関の呼び名の canon）

IT11 のふりかえりでも「user 視点が 1 時間後に高 3 件を持って返った」と書いています。
**2 IT 続けて、遅着分にしか出ない欠陥がありました。** 待ち方の上限を決めるのは正しいの
ですが、**切り替えたあとに返着を捨てない**ことが要点です。

### P5: CI が時限式のフィクスチャを出した

クローズ確定前の push で CI が赤（routing の受け入れ 13/20）。**コードの後退ではありません**
——CI が緑だったコミットに戻しても同じ 13 件が落ちました。

航海の出発日時が `2026-09-10T09:00:00Z` **固定**で、一覧は既定で出港済みを外すため、
**現実の時刻がその時刻を追い越した瞬間に登録した航海が一覧から消えます**。同じ日の
08:00 UTC の CI は緑、09:51 UTC の CI は赤。テストの意図（登録が投影に届くか）とは関係の
ない赤です。

IT8 の教訓「テストも同じ Clock で『今日』を決める」は**書いた日付そのもの**には及んで
いませんでした。同型が handling・tracking の suite に残っています。

### P6: 引き継ぎ枠 A が一部未達（この版に手立てが無い）

DLQ は入り、毒イベントは退避されて処理は続きます（[ADR-0014](../../adr/cargo-tracker/0014-poison-events-are-parked-not-blocking.md)）。
しかし**処理の列が全体で 1 本**のままで、同じ列の後続イベントは届きません。
`SequentialPolicy.FULL_SEQUENTIAL_POLICY` が既定で、プロパティは読まれず、注釈は構築される
だけで `sequenceIdentifierFor` が呼ばれません（プローブで確認）。

T7e のクラスタ E2E で**実際に起きました**——退避された 4 件のうち **3 件は巻き添え**です。
ADR の「引き受けていないこと」に書き、IT13 へ送りました。

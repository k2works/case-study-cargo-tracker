# イテレーション 3 完了報告書

## エグゼクティブサマリー

イテレーション 3 は **15 SP 中 14 SP を完了**（達成率 93%）し、ゴールである「自作の認証・認可基盤を
確立し、ログイン・ログアウトを通す」を達成した。序盤（IT1-IT3）の最終イテレーションとして、
アーキテクチャの成立に必要な機構はすべて実装済みとなった。

本イテレーションの主題は**本プロジェクト最大のリスクである自作セキュリティ**である。
機能としては US26・US27 の受入基準をすべて満たしたが、より重要な成果は
**「テストが緑でも運用と安全性で破れる欠陥」を 5 件発見・修正したこと**にある。

| 欠陥 | 発見されなければ何が起きたか |
|------|---------------------------|
| `user_roles` が複数行を許し、認可が非決定的 | 兼務ユーザーを 1 人登録した瞬間、権限がリクエストごとに変わる |
| 環境判定がフェイルオープン | 本番の環境変数注入に失敗すると、ログイン画面に開発用の資格情報が印字される |
| 存在しない利用者でハッシュ照合を省略 | 応答時間の差で、在籍者のユーザー名を総当たりで特定できる |
| `/health/live` が DB トランザクションを開く | DB 障害時にコンテナが再起動ループに入る（防ごうとした事象そのもの） |
| BCrypt が DB コネクションを占有 | ログインの同時実行でコネクションプールが枯渇する |

いずれもテストは緑で、受入基準も満たしていた。**「動作の正しさ」ではなく「壊れ方の設計」**に
属する欠陥であり、正常系のテストをいくら足しても見つからない。

TS05b（CI/CD の残り）は部分完了である。**SonarQube が Flix を解析できない**ことが判明し、
適用範囲を運用スクリプトに限定した。代わりに IT4 送りの予定だった `trace-lint`
（ドキュメント整合の機械検査）を実装し、CI の品質ゲートを 4 段にした。

### 未達項目についての説明

**SonarQube は Flix を解析できない**（サポート言語に含まれない）。IT2 のクローズで
「未実施＝未達」としたが、その実態は「JS 側の静的解析が未実施」であり、Flix 本体の品質判断が
欠けていたわけではない。IT3 で適用範囲を確定し、`sonar-project.properties` を用意した
（対象は `ops/scripts`。`arch-lint` を含めるのは、検査器のバグが「検査をパスしているのに
違反している」状態を生むため）。

実行には SonarQube のトークン（`.env` の `SONAR_TOKEN`）が必要で、本イテレーションでは
設定されていなかったため実施していない。**Flix 本体の品質は `arch-lint`（規約 10 件）・
セキュリティ回帰テスト・トレーサビリティ表の 3 つで担保する**（テスト戦略 6.4）。

### クローズ前に対応した主な指摘

冒頭のエグゼクティブサマリーに挙げた 5 件（非決定的な認可・フェイルオープン・タイミング差・
liveness の DB 依存・コネクション占有）に加え、次を対応した。

| # | 指摘 | 対応 |
|:--:|------|------|
| H6 | セッションタイムアウトが絶対タイムアウトで、非機能要件の「最終アクセスから」と乖離 | `lookup` 成功時に失効時刻を延長 |
| H7・H8 | `AuthService` の単体テストがなく、ロック解除の境界値が未検証 | 単体テスト 9 件を追加（判定の順序・境界値・ユーザー列挙） |
| H9 | テストヘルパーが失敗を握りつぶし、ログインが壊れていても緑になる | `Assert.fail` で停止 |
| H11 | 締め出された利用者に事実と違う案内が出る | 終了理由を区別し `/login?superseded` を追加 |
| H12・H13 | パスワード再設定の導線・ロック時の管理者連絡がない | 文言を改訂 |
| H14・H15 | 手順書だけではログインできない・`APP_SECURE_COOKIE` の記載が皆無 | ログイン確認手順と環境変数一覧を追加 |

### 次イテレーションへ送る高優先度の指摘

| # | 指摘 | 理由 |
|:--:|------|------|
| H16 | **ルーティング表の単一化（lift 案の実験）** | BC が 8 個になる IT4 で破綻する。認可の正典が「N 個の表 + 試行順序」になっており、同一パスが 2 表にあると片方の認可が静かに消える |
| H17 | CSRF のクロスセッション統合テスト | 純粋関数のテストのみで、配線を取り違えても緑になる |
| M9 | `/health/ready` がルート表の外 | 認可の正典に対する例外。lift 案と同時に解消 |

### 受容した判断

**ロック・無効化の文言によるユーザー列挙**を受容した。テスターは「存在するユーザー名だけに
『ロック』『管理者に連絡』が出るのは列挙経路である」と指摘し、ユーザー代表は「締め出された
利用者が次の行動を取れることが優先」と指摘した。**利用者側を採る**。

存在するユーザー名が判別できる代償より、締め出された利用者が管理者へ辿り着けることを優先する。
この受容は IT4 で ADR-0002 の補足として記録する。

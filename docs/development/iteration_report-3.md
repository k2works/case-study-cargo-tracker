# イテレーション 3 完了報告書

対象: US24（航海登録）・US25（航海更新）・US07（航海検索）・US06（経路設計への引き渡し）= 10 SP
期間: 2026-08-20〜2026-08-21（IT3）
局面: 中盤（インサイドアウト）の 1 本目。2 つ目のマイクロサービス（routingms）を業務で使い始める最初のイテレーション。

## エグゼクティブサマリー

経路設計者が**航海スケジュールを自分で登録・更新し、予約に合う航海を探せる**状態になりました。
営業担当者は仮受付の予約を経路設計者へ引き渡せ、経路設計者はダッシュボードの件数から
その予約へ辿り着けます。計画 10 SP を全量完了し、IT2 から持ち越した返済枠 7 件も
すべて片付けました。

IT3 の技術的な要点は、**ADR の決定を同じイテレーションの中で実行される検査に落とした**ことです。
IT2 の最大の指摘（ADR-007 が承認済みなのに実装も検査もゼロ）に正面から答え、
新設した ADR-014・015 はいずれも検査を伴っています。加えて「名簿を持たず実体から検出する」
形の検査を 3 つ作りました。名簿方式は載せ忘れたものほど無検査になるためです。

一方で、**実環境でだけ見つかる欠陥がこの IT で 3 件出ました**。いずれもモックと単体テストでは
緑でした。3 件目はクローズのレビュー中に見つかったもので、開発フェーズの終了時点では
気づけていません。

| 欠陥 | 見つかった場面 |
| :--- | :--- |
| 更新のはずの保存が新しい予約を作る | kind 統合環境で業務を 1 本通したとき |
| 権限の検査より入力の検査が先に走る | kind 統合環境で業務を 1 本通したとき |
| 出発日の絞り込みが実バックエンドに通らない（日付を送り、日時で受け取る） | **クローズのレビュー中** |

さらにクローズ時のレビューで、**US25 の中核シナリオが全緑のまま動いていない**ことが分かりました
（下記「レビュー結果」）。受入基準は満たしていましたが、実務でいちばん多い差し替えができない
状態でした。

## 技術的成果

### 判断を ADR に落とし、同じ IT の中で検査にした（ADR-014・015）

| ADR | 決定 | 検査 |
| :--- | :--- | :--- |
| [ADR-014](../adr/014-location-replica-sync.md) 地点マスタの複製 | 正は bookingms。同一の種データを配り、実行時のイベント同期は行わない。テーブルの形も揃える | `LocationSeedReplicaTest`。`location` を作るサービスをマイグレーションの実体から検出し、**種データとテーブルの形の両方**を正と比べる |
| [ADR-015](../adr/015-routing-requested-state.md) 経路依頼状態 | `RoutingStatus.ROUTING_REQUESTED` を足す。引き渡しは `BookingStatus` を変えない。二重依頼を許さない。経路設計者には依頼済みだけを見せる | `Cargo` の単体テストと `CargoBookingControllerTest`。とくに「絞り込みの指定で範囲を広げられない」ことまで固定 |

ADR-007（利用者ヘッダの必須化）も IT2 で承認だけしていたものを実装し、
**除外に無いサービスは必須**という形の登録検査を付けました。

### 「名簿を持たず実体から検出する」検査を 3 つ作った

`LocationSeedReplicaTest`・`AuthenticatedUserFilterRegistrationTest`・`SharedKernelScopeTest` は
いずれも対象を `settings.gradle` とマイグレーションの実体から導き、**除外の側だけを一覧**にしています。
3 つとも「1 件も読み取れていなければ赤」を明示しており、検査が空振りで緑になる経路を塞いでいます。

### 型を安易に共有カーネルへ引き上げなかった

routingms の `CargoType` は bookingms と同名・同値ですが、別の型として定義しました。
予約側は「その貨物が何か」、経路側は「その船が何を運べるか」で意味が違い、片方に値が
増えたときにもう片方が必ず追随するとは限らないためです。この判断は
`SharedKernelScopeTest`（共有カーネルに置けるパッケージの列挙）によって守られています。

### 検査が捕まえた実欠陥

| # | 欠陥 | どう捕まえたか |
| :--- | :--- | :--- |
| 1 | 更新のはずの保存が新しい予約を作る（`save()` が常に INSERT） | kind で業務を 1 本通したとき。先に赤い統合テストを置いてから直した |
| 2 | 権限の検査より入力の検査が先に走る（`@Valid` が引数解決時に走る） | kind で業務を 1 本通したとき |
| 3 | 出発日の絞り込みが実バックエンドに通らない | クローズのレビュー中。モックが日付と日時を文字列で前方比較していた |
| 4 | 差分が先頭区間の出発日時しか比べず、時刻だけの変更で更新できない | クローズのレビュー（3 視点が独立に指摘） |
| 5 | `CarrierMovement` と `Schedule` の時刻境界が、反転しても緑 | クローズのレビュー（tester が実測） |

## レビュー結果

[イテレーション 3 開発成果物レビュー](../review/イテレーション3_review_20260821.md)（XP の 5 役割による並列レビュー）。

指摘件数: **高 11 件 / 中 20 件 / 低 10 件**。

高優先度のうち **10 件を本イテレーションで対応**しました。1 件（メッセージに入力値が続くという指摘）は
裏を取った結果レビュー側の誤りで、値は `UserFacingMessage` が境界で切っており画面には出ません。
その旨をレビュー結果に記録し、あわせてマニュアルにも同じ宣言を明記しました。

### 最も重い指摘

**US25 の中核シナリオが、全緑のまま動いていなかった。** 差分の比較が先頭区間の出発日時しか
見ていないため、実務でいちばん多い「本船が遅れて到着が 2 日ずれた」が差分に現れず、画面は
「変更はありません」と言って上書きを選ばせません。運航管理者は正しい予定を入れたのに
更新できない状態でした。programmer・user-representative・tester が独立に指摘しています。

日程を全区間の 1 つの表現にまとめて丸ごと比べる形に直しました。項目ごとの比較を積み上げると、
航海に属性が増えるたび同じ穴が空くためです。

### 対応で業務価値が上がった点

| 対応 | 業務上の意味 |
| :--- | :--- |
| 差分を業務タイムゾーン・港名・日本語の種別で出す | 09:00 と入力した相手に 01:00 を見せて「上書きしますか」と問わない |
| 一覧の「更新する」が今の内容を引き継ぐ | 10 区間の到着を 1 日ずらすために全部打ち直させない（打ち直しの過程で別の項目が変わる） |
| 一覧の既定を本日以降に絞る | 朝いちばんに開いて最初に目に入るのが、もう出てしまった船にならない |

## 次イテレーションへの引き継ぎ

[イテレーション 3 ふりかえり](retrospective-3.md)に KPT と引き継ぎをまとめています。要点は次の 3 つです。

1. **モックを本物より甘いほうへ寄せない。** 型が違う値を比較しているモックは、本物が断る入力を通す。
   IT3 の 3 件目の欠陥はこの形で、IT2 の Try 5 が再発している
2. **実環境で見つけた欠陥は、見つかった場所に回帰テストを置く。** 他の場所に真似た実装を入れて終わりにしない
3. **ADR は決定の数だけ検査を用意する。** 決定が 2 つで検査が 1 つなら、片方は文章のまま

ベロシティは IT1〜IT3 の実測平均 **9 SP / イテレーション**。実効 8 SP（バッファ込み）は妥当なため
据え置きます。ただし IT3 は 1 SP あたり 6.9h と過去 2 IT より 2 割重く、新しいマイクロサービスの
立ち上げ分が上乗せになっています。IT4 は既存サービスへの追加なので IT2 水準に戻る想定です。

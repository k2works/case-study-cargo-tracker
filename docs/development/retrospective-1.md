# イテレーション 1 ふりかえり

対象: US26（ログイン）・US27（ログアウト）・US31（アカウント保護）・US02（荷主登録）= 9 SP
期間: 2026-08-19（IT1）

## 実績

| 項目 | 計画 | 実績 |
| :--- | :--- | :--- |
| ストーリーポイント | 9 SP | 9 SP（100%） |
| 理想時間 | 74h（うち基盤投資 24h） | 計画どおり |
| ベロシティ | — | **9 SP**（初回のため基準値とする） |

> 基盤投資（品質ゲート 15h + マニュアル 9h）は SP に含めない。IT2 以降のベロシティ比較を歪めないため、
> 純粋なストーリー実装の実績（9 SP / 50h）で見る。

## Keep（続けること）

- **検査を Day 1 に置いた**。ArchUnit・カバレッジ検証・CI・E2E を先に配線したことで、実装中に 5 件の実欠陥が自動で見つかった。後から入れていれば、どれも本番か次 IT まで残っていた
- **破壊検証を毎回行った**。安全装置を入れたら必ず壊して赤を確認する。この習慣が「入れたのに働いていない」検査を 3 つ見つけた
- **アウトサイドインの順序を守った**。UI のニーズから API 契約を導出し、同じ変更で設計ドキュメントに反映した。契約の手戻りが 1 度も起きなかった
- **実機で確認した**。kind 統合と Heroku デプロイまで通す。ユニット全緑でも実機だけが落ちる欠陥（ヘルスチェックの 401）はここでしか見つからない

## Problem（問題だったこと）

- **検査が 3 つ空振りしていた**
  - メタテストが Gradle の up-to-date 判定でスキップされ、実行されないまま緑になっていた
  - 方言スモークが prepare だけで、`#{keyword} IS NULL` のような型未決定の欠陥を素通りさせた
  - 破壊検証の違反例（`~` 演算子）が H2 の互換モードでも解釈され、違反になっていなかった
- **設計に書かれていない判断が実装中に露出した**。トークンの保管先は設計に記載がなく、E2E の失敗という形で判断を迫られた（ADR-005 として起票）
- **正典ドリフトが 2 件見つかった**。data-model のロール一覧に `ROLE_ROUTING` が欠けていた。`users.display_name` が設計に無かった
- **画面を見るまで気づけない欠陥があった**。未実装メニューが行き先のないリンクになっていたのは、マニュアルのキャプチャを撮って初めて分かった
- **全テストが緑のまま素通りした欠陥が 3 件あった**（クローズ時のレビューで検出）
  - 認証トークンが一度も API 呼び出しに載っていなかった（`configureAuth` が未配線）。実バックエンドに対しては荷主機能が必ず 401 になる状態
  - ロック解除後に失敗回数が持ち越され、1 回の誤入力で即再ロックされた。US31 の「自動解除」が名目だけになっていた
  - 担当外ロールのダッシュボードのリンクが全部行き止まりで、押すと公開トップに飛ばされた
- **モックが安全網を無効化していた**。フロントの検証が MSW で完結しているため、上の 1 件目は 137 ファイル・全テスト緑をすり抜けた
- **自分で作った検査にも空振りがあった**。ArchUnit のメタテストはファイルの存在しか見ておらず、規則を書き忘れたクラスでも緑だった

## Try（次イテレーションで試すこと）

| # | アクション | 狙い | IT2 での組み込み先 |
| :--- | :--- | :--- | :--- |
| 1 | **検査を追加したら、その場で壊して赤を確認する**（緑を見て終わりにしない） | 空振りする検査を作らない | 各タスクの完了条件に明記 |
| 2 | **破壊検証の違反例が「本当に違反か」を先に確かめる** | 赤にならないとき、検査の欠陥と違反例の欠陥を切り分ける | 同上 |
| 3 | **新しい Mapper を書いたら方言スモークを同じコミットで通す** | 本番相当 DB でしか落ちない SQL を残さない | タスク 2.x の完了条件 |
| 4 | **設計に書かれていない判断に出会ったら、その場で ADR に起こす** | 「実装を読まないと分からない決定」を残さない | 着手時のチェック項目 |
| 5 | **画面を追加した IT では、キャプチャを撮って目視する** | 実装は正しいが利用者には壊れて見える状態を検出する | マニュアル更新タスク |
| 6 | **正典（設計ドキュメント）を先に読み、差分があれば同じ変更で直す** | 実装と設計の乖離を溜めない | 各ストーリー着手時 |
| 7 | **「定義したが呼んでいない」関数を疑う**。定義済み未使用は配線漏れのサイン | モック越しの緑をすり抜ける配線漏れを止める | 実装レビュー時のチェック |
| 8 | **モックで検証した機能は、実物を 1 本通すまで「動く」と言わない** | E2E がモック相手である限界を明示する | 各ストーリーの完了条件 |
| 9 | **時間で変わる振る舞いは可変 Clock でテストする**。固定 Clock では「◯分後にどうなるか」を通れない | 期限・解除・締切の受入基準を実際に確かめる | 期限を扱うタスク |

- **中 10 件は IT2 の返済枠に計上する**（下記の引き継ぎを参照）
- 低 6 件は記録のみとし、該当箇所を触る IT で合わせて直す

## 次イテレーションへの引き継ぎ

- **US03（法人荷主）で `contract_number` / `discount_rate` を使う**。列は IT1 の `V2__init_booking.sql` で用意済み。荷主登録画面に「法人」を選んだときの追加項目を足す
- **`/api/v1/public/tracking/*` は経路のみ確保済み**。US18（追跡照会）の実装時にハンドラを作る。ポータルの追跡番号欄も同時に活性化する（IT1 では非活性）
- **ナビゲーションの `available: false` を、画面を実装した IT で true にする**。忘れるとメニューから到達できないまま実装が終わる
- **バックエンドの API モック（MSW）を実物に差し替える**。IT1 では E2E がモック相手のため、Gateway・authms・bookingms を通した E2E は kind でのみ確認している

### IT2 の返済枠（レビューの「中」10 件）

「余力次第」にすると固定化するため、**IT2 序盤の独立コミット枠**として確保する。

| # | 内容 | 理由 |
| :--- | :--- | :--- |
| M1 | `GET /api/v1/auth/me` を削除するか正しく実装する | 現状 `displayName` に利用者 ID を返す。画面が使い始めた瞬間に「sales01」が出る |
| M2 | 失敗回数の更新を DB 側の加算に寄せ、並列でロックが成立することを検証 | 総当たりは並列で来る。いまは同時 5 リクエストでロックが成立しない可能性 |
| M3 | US31 のシステムレベル受入テスト（MSW に失敗回数を持たせる） | 「画面で 5 回間違えるとどうなるか」を誰も確かめていない |
| M4 | `RegisterShipperUseCase` の責務分割と boolean 引数の解消 | 呼び出し側で意図が読めない |
| M5 | フロントの `pages/` と `features/` の関係を決める | 画面が 6 枚のいまが最も安い。決めずに増やすのが最も高くつく |
| M6 | 荷主一覧に上限とページング | 荷主が育つ前提の画面 |
| M7 | `enabled` の判定を集約の述語に寄せる | いま二重にあり、意味が変わったとき片方だけ直る |
| M8 | CORS プリフライト（OPTIONS）の扱いを決めテストで固定 | 別オリジン配置時にブラウザからログインできなくなる |
| M9 | 追加した npm script を運用手順書に記載 | `test:e2e:production` は ADR-006 の唯一の検査 |
| M10 | IT2 計画作成時にマイグレーション名を実装に合わせる | 計画は `V1__init_booking`、実装は `V2__init_booking` |

### IT2 冒頭で判断が要ること

- **Gateway をバイパスできないことをどう担保・検査するか**。ADR-004 の前提でありながら、いまどこでも確かめられていない。サービスが 2 → 6 に増える前に決める
- **荷主の編集ストーリーを起票するか**。実務で最も頻度が高いのは新規登録ではなく打ち間違いの修正
- **法人荷主を US03 まで登録させるか**。契約番号・割引率が空の法人が溜まると US03 で全件の追加入力が発生する
- **共用端末の無操作タイムアウトの要否**

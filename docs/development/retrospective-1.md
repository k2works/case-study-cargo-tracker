局面（開発戦略）: **序盤 = アウトサイドイン**。技術基盤 → 認証 → ウォーキングスケルトン → 荷主/見積の縦切りを一巡し、序盤の骨格が完成した。

## Keep（継続すること）

### 技術的成功

- **ドメイン先行 TDD + 二方言（SQLite/PostgreSQL）運用が機能した**。値オブジェクトで不変条件を前倒しし、Testcontainers（実 PostgreSQL）を「正」として統合検証。SQLite の型アフィニティ差異（decimal→TEXT、UUID/DateOnly の TypeHandler）を `DapperConfiguration` の一箇所に封じ込めた。
- **post-commit イベント基盤（AggregateRoot + UoW）が「事故を構造で防ぐ」形になった**。ロールバック時イベント非発行を統合テストで実証（ADR-0002 コンプライアンス）。
- **ウォーキングスケルトン戦略が奏功**。認証後に画面遷移図準拠のロール制御ナビ + 全ルートのプレースホルダを一括作成し、以降の US を「スタブ→実画面の差し替え」に落とせた。
- **設計ドキュメントを「正」とする規律**。実装で判明した乖離（認証方式・per-story スキーマ・住所）を ADR 起票と docs 修正で追従した。

### プロセス的成功

- **マルチパースペクティブレビュー（XP 5 エージェント並列）が高い ROI を発揮**。ArchUnit 未実装・住所ドリフト・危険物申告など、単独では見落としがちな課題を体系的に検出。高優先 5 件をイテレーション内でほぼ解消した。
- **validating-design による設計整合検証**を計画着手時に実施し、開発着手前に不整合を潰せた。
- **品質ゲートの自動化**（pre-commit の format/build、CI の全テスト実行）が壊れたコードのコミットを防いだ。

## Problem（問題点）

- **設計ドキュメント（domain-model・data-model・iteration_plan）のドリフトが複数発生**。住所カラム、ShipperCode 桁数、DDL の NOW()/version など。SoT である domain-model が一時的に信頼できない状態になった。
- **計画の前提が実装で複数覆った**。「0001＝5 テーブル一括」→ per-story、full Identity → 軽量認証、user_roles → 単一 role。計画作成（07-04）と開発（07-08）の間で判断が動いた。
- **E2E のデバッグに時間を要した**。navbar のログアウトボタンが DOM 先頭にあり `button[type=submit]` セレクタが誤クリック、htmx の hx-include 漏れ、Cookie/antiforgery の切り分けなど、実ブラウザ特有の落とし穴に嵌った。
- **アーキテクチャの規律（ArchUnit）が当初未実装**で、Application→Infrastructure の依存（具象 UnitOfWork 直接 new）が混入していた。レビューで検出し是正。
- **見積の受入条件の一部（期限に間に合うルートなし通知）が未実装**。スタブ段階のため IT3 の実データ化まで持ち越し。

## ベロシティと計画への反映

- IT1 実績 **13 SP**。計画の想定（10-12 SP）を上回ったが、初回かつ基盤タスク（SP 外）を多く含むため、IT2 も計画どおり 10 SP で進め、**IT3 終了時に 3 イテレーション実績で再較正**する（ADR/リリース計画の方針を維持）。
- 残 SP: 72 SP（Release 1.0 MVP まで IT2-5）。バーンダウンは計画線に追従。

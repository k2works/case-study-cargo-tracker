## Keep（継続すること）

- **序盤アウトサイドイン + ウォーキングスケルトン先行**が奏功。最初の 2 週間で TSX SSR + htmx + NestJS + Kysely の非典型構成の妥当性を E2E で早期検証できた。
- **判別可能ユニオンによる認証結果表現**（`AuthenticationResult`）と**ロックポリシーの純粋関数化**（`account-lock-policy`）でテスト容易性が高い。
- **pg-mem による統合テスト**が Docker 不要で高速。リポジトリ層を実 SQL で薄く検証できた。
- **スケルトン判定 E2E のマトリクス駆動**（8 画面 × 6 ロール = 49 ケース）でロール別到達性を機械的に網羅。
- **設計ドリフトの都度是正**（data-model へのロックカラム反映・ui_design への荷主登録画面追記）で実装と設計を同一変更で同期。
- **SonarQube 品質ゲートをクローズ前に通す**規律で、Bug/Code Smell を残さず締められた。

## Problem（問題点）

- **受入基準の入力項目漏れ**（US02 の住所・連絡先）を初回実装で落とし、レビューで検出（`Address` 幽霊フィールド化）。フォーム項目を受入基準と 1:1 で突き合わせる工程が不足していた。
- **登録後の荷主 ID 非表示・Email 重複時の既存提示未実装**など、受入基準の「利用者に見える結果」を初回で満たせていなかった。
- **CI の npm ci が lock ドリフトで失敗**。ローカル macOS の `npm ci --dry-run` は通るが Linux でプラットフォーム別 optional 依存（@emnapi）欠落で赤。多数の install/uninstall で lock が部分ドリフトしていた。
- **tsx が emitDecoratorMetadata 非対応**で NestJS DI が実行時に壊れる問題に実装途中で遭遇（SWC へ切替で解決）。事前の技術検証で拾えていれば手戻りが減った。
- **設計ドキュメントに他 take 由来のドリフト**（「IT1 実装状況（2026-04-04 完了）」等）が残存。移植時のクリーンアップが不足。

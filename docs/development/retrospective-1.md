## KPT 分析

### Keep（継続すること）

#### 技術的成功

- **TDD サイクルの確立**: BE（Spring Boot + JUnit 5）と FE（Vitest）の両方で Red-Green-Refactor サイクルを実践できた。1 SP あたり約 2.1h の実績値が得られた
- **ArchUnit によるアーキテクチャ検証**: ヘキサゴナル依存ルールを自動テストで担保する基盤を確立。IT2 以降も同じパターンを継続する
- **E2E テストの早期追加**: Playwright テストを 14 件まで拡張し、実際のブラウザ操作でエンドツーエンドの動作を確認できた。ナビゲーションバグの再発防止テストも追加
- **SonarQube Quality Gate**: カバレッジ目標 80% に対して 86.7% を達成。コード品質の定量的な可視化が機能している
- **AI ペアプログラミング（Codex 分業）**: 実装を Codex に委譲し、Claude が設計・受入を担う分業体制が IT1 で機能した

#### プロセス的成功

- **インサイドアウト開発**: BE API → FE 画面の順序で開発し、API が確定してから画面を構築する流れが安定した
- **イテレーション計画書の活用**: `iteration_plan-1.md` を作業の基準として使い、進捗率を随時更新できた

---

### Problem（改善が必要なこと）

#### 技術的課題

- **API パスと Gateway ルーティングの不一致**: VoyageController のパスを `/api/v1/voyages` で実装したが、Gateway の Route 設定が `/api/routing/**` だったため E2E テストで 404 が発生した。設計段階でパス設計を Gateway ルートと一致させる必要があった
- **DB の VARCHAR 制約とテストデータの不整合**: `voyage_number` を VARCHAR(20) で設計したが、E2E テスト用タイムスタンプ付き値（`E2E-LIST-<13桁>`= 22 文字）が制約違反になり 500 エラーが発生した。テストデータの命名規則を事前に考慮していなかった
- **UI スタイルが仕様（ワイヤーフレーム）と乖離**: `iteration_plan-1.md` の PlantUML salt ワイヤーフレームを参照せずに実装したため、スタイルが未適用のままになっていた。E2E 通過後に別途 Tailwind CSS を適用する追加作業が発生した
- **ナビゲーションパスのミスマッチ**: `AppLayout.tsx` に `/routing/voyages` と誤ったパスを設定し、「航海スケジュール」リンクが機能しなかった。ナビゲーションの E2E テストがなかったため発見が遅れた

#### プロセス的課題

- **IT1 の SP 過負荷**: 計画 35 SP（採用ベロシティの 194%）は認証基盤構築の特殊要因とはいえ、実際に完了まで複数セッションにまたがる長期作業となった
- **UI 仕様との照合タイミング**: FE 実装時にワイヤーフレームを確認する工程が抜けており、UI スタイル適用が後回しになった

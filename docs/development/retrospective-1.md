| 項目 | 内容 |
|------|------|

## Keep（続けること）

### K1: TDD による高品質な実装

バックエンド 67 件、フロントエンド 35 件、合計 102 件のテストが ALL PASSED。テストファーストのアプローチにより、実装完了時点でリグレッションのない状態を維持できた。

### K2: 計画的な持越し判断

E2E テスト（5.8）を IT2 に持越す判断を事前にリスクテーブルで明記していた。超過見込みが出た時点で計画的にスコープを調整し、コア機能の完成度を優先した。アカウントロック（2.7）・ログアウト（2.8）も優先度調整で持越しとし、ログイン・JWT 発行というコア認証を先に完成させた判断は適切だった。

### K3: ADR による意思決定の記録

ADR-0004（マイクロサービス分割方針）、ADR-0005（shared モジュールの役割）、ADR-0006（Heroku デプロイ構成）を作成し、アーキテクチャ上の意思決定を記録に残した。レビュー指摘への対応も含め、設計判断のトレーサビリティが確保された。

### K4: Phase 0 レビュー指摘の即時対応

PingControllerIntegrationTest 追加、DisplayName 追加、ADR 作成など、レビュー指摘 4 件を IT1 冒頭で全件対応完了した。技術的負債を溜めない姿勢を維持できた。

### K5: 計画外タスクへの柔軟な対応

gatewayms 追加、Heroku デプロイ環境構築、SonarQube 品質対応、CI ワークフロー構築など、多数の計画外タスクを SP 外として処理しつつ、計画ストーリーの大部分を完了させた。

## Problem（問題点）

### P1: 計画外タスクの多さ

SP 外で実施した計画外タスクが 9 件に上った（gatewayms、Heroku デプロイ、SonarQube、Checkstyle/SpotBugs、Git Hooks、CI、CORS、nginx 修正、セットアップ手順書更新）。これらはインフラ・運用基盤として必要だったが、見積もりに含まれていなかったため、本来の計画ストーリーに充てる時間が圧迫された。

### P2: Axon Aggregate の CRUD 切替え

bookingms の ShipperAggregate を Axon Event Sourcing で実装する計画だったが、工数超過のリスクから CRUD 実装に切り替えた（タスク 4.3〜4.5 未完了）。リスク対策として計画に記載していたものの、Event Sourcing の学習機会を IT1 で得られなかった。

### P3: Definition of Done の未達項目

以下の DoD 項目が未達のまま IT1 を完了した。

- テストカバレッジ 80% 以上（未計測）
- Checkstyle / SpotBugs エラーなし（セットアップは完了したが全項目クリアの確認なし）
- `local-docker` プロファイルでの動作確認（API・画面）
- Swagger UI での全 API 確認
- フロントエンド E2E テスト

DoD を満たさないままイテレーションを完了と判断したことで、品質基準が曖昧になるリスクがある。

### P4: SP 見積もりの精度

計画 16 SP に対し実績 14 SP で、2 SP 分の持越しが発生した。UI 実装（US-UI: 2 SP）は「完了（部分）」であり、E2E テストが未完了。US00 も「完了（部分）」でありロック・ログアウトが残っている。「部分完了」のストーリーが 2 件あり、完了の定義が曖昧になった。

### P5: 1 SP あたりの理想時間の乖離

計画では 1 SP = 約 5.5h（合計 87.5h / 2 週間）と見積もったが、計画外タスク 9 件の工数を含めると実際の作業量は見積もりを大幅に超過していた可能性がある。週 20 時間（2 週間 40 時間）の想定稼働に対し、87.5h の理想時間は持続可能なペースを超えている。

## Try（次に試すこと）

### T1: 計画外タスクのバッファを明示する

IT2 以降、計画 SP の 20% 程度をインフラ・運用タスク用のバッファとして確保する。具体的には、14 SP の計画であれば 11〜12 SP をストーリーに、2〜3 SP 相当を計画外タスク用に割り当てる。

### T2: DoD の段階的導入

IT2 では以下の DoD 項目を必須化する。

1. テストカバレッジの計測と報告（80% 未達でも計測は必須）
2. Checkstyle / SpotBugs の CI 統合（PR 単位で自動チェック）
3. E2E テストの最低 1 シナリオ実装（IT1 持越し分）

全項目を一度に必須化するのではなく、段階的に基準を引き上げる。

### T3: ストーリーの完了定義を厳格化する

「部分完了」を認めず、ストーリーは「完了」か「未完了」の二値で判定する。IT1 で「部分完了」となった US00 は、残タスク（ロック・ログアウト）を独立したストーリーとして IT2 に起票する。これにより、ベロシティの正確性が向上する。

### T4: Event Sourcing のスパイクを IT2 で実施する

IT2 の貨物予約（US04）で Axon Event Sourcing を本格導入する前に、タイムボックス（4h）のスパイクを設け、BookingAggregate のプロトタイプを作成する。IT1 で得られなかった学習機会を早期に確保する。

### T5: 持続可能なペースの見直し

1 SP = 5.5h の見積もりを見直す。IT1 の実績から、計画外タスクを含めた実際の作業時間を計測し、IT2 の計画に反映する。週 20 時間の稼働制約を前提に、1 イテレーションで消化可能な SP 数を再評価する。

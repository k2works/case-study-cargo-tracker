## エグゼクティブサマリー

**予約から精算までが、1 回の指示で通るようになった。** これまで端から端まで確かめるには、
5 つのロールでログインし直して 20 以上の画面を操作する必要があり、実演のたびに手順が揺れ、
配備直後に「どこが切れているか」を切り分ける手段も無かった。IT14 で、システム管理者は
`/admin/simulations` から 14 工程を自動で通し、工程ごとの成否・所要時間・生成した識別子・
失敗理由を読める。

**確かめる仕組みを、確かめられる形で作った。** この種の仕組みは作り方を誤ると
**確かめているつもりで何も確かめていない**状態になる。[ADR-030](../adr/030-business-simulation-execution.md)
決定 2 で「専用の書き込み経路を作らない」を先に決め、出口を 1 ポートに絞り、
内部 API を参照していないことをソースを読む検査で固定した（ArchUnit には文字列で書かれた
URL の向き先が映らないため）。**工程ごとに、その工程を踏むロールの利用者としてログインし直す。**

**8 つ目のサービスを足した。** simulationms（8087）は業務ではなく業務の**呼び出し元**であり、
既存 6 サービスとは変わる理由が違う。依存は `shared` のみで、業務サービスへの型依存は
物理的に不可能である。

**実環境の枠が、また実環境でしか出ない欠陥を捕まえた。** 接続先が他サービスのデータベース
（`billing_db`）を向いていた——ユニット・結合・モックはすべて緑だった。IT5・IT12・IT13 と
同じ族の欠陥であり、マニフェストから接続先を読む検査に落とした。

**レビューが、緑の状態から「運用で確実に起きる壊れ方」を 5 つ見つけた。** 実環境で 14 工程が
成功し、CI も SonarQube も緑になった後の話である。うち 4 件は、自分が書いたコメントや決定が
「守られているつもり」だった箇所だった。

## 達成状況

### US34: 業務シナリオを選んで自動実行する

| # | 受入基準 | 状態 |
| :--- | :--- | :--- |
| 34-1 | 予約登録 → 経路確定 → 予約確定 → 追跡番号発行 → 荷役 → 通関 → 引取 → 料金算出 → 精算までが順に実行される | **満たす**（14 工程。実環境で全工程成功を確認） |
| 34-2 | 各工程は**本番と同じ API** を通る（専用の書き込み経路を作らない） | **満たす**（Gateway 経由・工程ごとにログイン。内部 API 不使用と出口 1 ポートを検査で固定。**壊すと赤になることも確認**） |
| 34-3 | 生成された荷主・予約・請求書がシミュレーション由来と識別できる | **一部**（荷主コードの `SIM-` 帯。営業の荷主一覧と精算の締め対象から除外。**追跡の未解決例外一覧は IT15**） |
| 34-4 | 本番環境では実行が拒否される | **満たす**（許可した環境以外は**起動そのものが失敗**。無効にした環境では実行を 503 で断る） |
| 34-5 | 同じシナリオの二重実行が拒否され、実行中の結果へ案内される | **満たす**（409＋実行中の実行への導線。**止まったきりの実行は 15 分で見切る**） |

> **34-1 の「選んで」について**: 実装したシナリオは「標準輸送」1 本で、輸送条件
> （JPTYO → USLAX・一般貨物・900kg）も固定である。疎通確認では条件を毎回変えると
> 失敗時に条件を疑うことになるため固定した。**顧客の航路で見せる**用途には足りておらず、
> US36（例外を含むシナリオ）と併せて IT15 で扱う。

| # | 受入基準 | 状態 |
| :--- | :--- | :--- |
| 35-1 | 工程ごとの成否が分かる | **満たす** |

### 果たせなかったこと

#### 1. 追跡管理者の未解決例外一覧に、シミュレーション由来が混ざる

trackingms は荷主コードを持たない（貨物の要約を bookingms へ問い合わせて解決している）。
外すには「この追跡番号はシミュレーション由来か」を問う経路が要る。**IT15 へ持ち越す**。

当座の手当てとして、実行画面とマニュアルの両方に「未解決例外一覧には出る・実行したら
追跡管理者に一報」を明記した（当初は画面が「経理の締めや荷主一覧には出ません」とだけ書き、
**例外一覧に出る事実を伏せていた**）。

#### 2. 実行が同期 HTTP 1 本で、進捗が見えない

14 工程を直列に回すため（実測 8 秒）、押した人は終わるまで待つ。一覧も自動更新しない。
US37（ランダム連続実行）では非同期が必須になるため、**IT15 で `202 Accepted` +
`GET /{runId}` の形に変える**。

#### 3. 由来のフラグは、実在の営業利用者本人なら今も送れる

要求本文だけで立てられる穴は塞いだ（設定で許した利用者だけが立てられる）が、
シミュレーションは実在の営業利用者としてログインするため（決定 2）、その利用者本人は送れる。
塞ぎ切るにはシミュレーション専用の利用者が要る。ADR に明記して IT15 へ。

## 技術的成果

### 1. 8 つ目のマイクロサービス（simulationms）

| 項目 | 内容 |
| :--- | :--- |
| ポート | 8087（Gateway 経由 `/api/v1/simulations/**`） |
| データベース | `simulation_db`（`simulation_run` / `simulation_step_result`） |
| 集約 | `SimulationRun`（状態は工程の結果から導く。結果は**足すだけ**） |
| 出口 | `BusinessGateway` の **1 ポート**のみ |

### 2. 検査が実装より先に誤りを見つけた回数：8 回

新サービスの ArchitectureTest 欠落、利用者ヘッダのフィルタ未登録、ヘッダ必須検査そのものの
欠落、`TIMESTAMPTZ` を H2 が解釈しない（＋動的 SQL が方言スモークから漏れていたこと）、
ドメイン層カバレッジ 90% 未達（未使用メソッド＝ TDD 違反）、環境変数の命名、
マニュアル 15 章の欠落、**接続先が他サービスの DB を向いていた**。

### 3. 決定を 1 つ改訂した

[ADR-030](../adr/030-business-simulation-execution.md) 決定 3 は当初「`SIM-` 帯**と**
`simulated` 列」だったが、**帯 1 本に絞った**。両方持つと食い違う行が生まれ、
どちらが正しいかを決める規則がまた要る。

## レビュー結果

[高 12 件・中 30 件・低 12 件](../review/イテレーション14_review_20260831.md)。高は 10 件対応、
2 件（未解決例外一覧の除外・実行の非同期化）を IT15 へ明示的に送った。

**実環境で全工程が成功し、CI と SonarQube が緑の状態から、運用で確実に起きる壊れ方が
5 つ見つかった。**

| 何が起きるか | なぜ緑をすり抜けたか |
| :--- | :--- |
| 中断した実行がシナリオを永久にブロックする | 想定外の例外を投げるテストが無かった |
| 由来のフラグを要求本文だけで立てられる | 「他の誰かが立てる」経路を考えていなかった |
| 本番判定が fail-open | 載せ忘れるのは**将来この場所を知らない人**である |
| 無効化の設定が何も無効化しない | 設定の名前が守っているつもりになっていた |
| 決定を固定する検査が何も固定していない | 名前の実在は機械で確かめたが、**中身が判別するか**は誰も見ていなかった |

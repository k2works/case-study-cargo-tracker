# 2026-08-04 IT7 の立ち上げから クローズまで

IT6 のクローズ直後から、IT7（経路候補算出・HTTP ランタイムの防御・導線の返済）を
立ち上げ、開発し、クローズするまでの記録である。

コミットログには載らない**判断の経緯と、そこで見つけた「前提の誤り」**を残す。

---

## 1. 立ち上げ — 指摘を実物で確かめたら、3 件の前提が崩れた

`opening-iteration` の 6 ステップを順に進めた。計画を書く前にふりかえりを読み、
書いた後に 2 種類の整合性検証（`validating-iteration-plan` / `validating-design`）を通す。

**この検証で 3 件、前提が実態と違うことが分かった。**

### 1.1 引き継ぎ M2 が誤指摘だった

IT6 のレビューは「管理者ロールが navbar の全項目を押せるが、ルート側の `RoleAnyOf` に
`Admin` が無いため**どの業務画面も 403**」と記録し、「認可設計の方針決定が要る」として
IT7 へ送っていた。計画時点では ADR-0009 を起票する予定にしていた。

着手前に実物を確認した。

| 確認先 | 内容 |
| :--- | :--- |
| `Auth.flix:38` | `case (_, Some(user)) if role(user) == Role.Admin => Decision.Allow` |
| `architecture_backend.md` | 「`Admin` は常に通す」と設計されている |
| `AuthorizationTest.flix:66` | `testAdminPassesEveryRoute` が全ルートで固定している |

**指摘そのものが事実と異なっていた。** ADR の起票を取りやめた。

IT6 のふりかえり Try T8 は「設計ドキュメントに定義がある DB オブジェクトは
着手前に実物の有無を確認する」だった。今回はその**鏡像**である——
レビューが「無い」と言ったものが、実際にはあった。

> そのまま計画に載せていれば、存在しない欠陥に 1 SP と ADR 1 本を使っていた。

### 1.2 `route_candidate` は本 IT の対象外だった

`data-model.md` に `route_candidate` テーブルの定義がある。US08 は「経路候補」を
算出するのだから、当然これを使うと考えていた。

親を確認したら `estimate_id` だった。つまり**見積（US01・IT8）に紐づくルート候補**であり、
経路設計者が経路割り当て画面で見る候補とは別の関心である。

「設計にあるから今作る」も、「設計にあるから実装にもある」と同じ誤りだった。
**誰が親か**を確認して初めて分かった。

### 1.3 設計の可否表が IT4 時点のまま止まっていた

`architecture_backend.md` の「認可の可否表」は IT5・IT6 で追加した 9 ルートを欠いていた。

不思議だったのは、`AppRoutesTest.testRouteRolesMatchDesignTable` という
「表と実装を突合する」テストが存在し、しかも緑だったことである。

読んでみると、このテストが比較しているのは**テストファイル内に書かれた可否表のリテラル**と
ルーティング表だった。つまり**コードとコードを比べており、Markdown の表は検査の対象外**である。

テストは「表を更新せずにルートを足すと落ちる」ことを保証するが、
**落ちたときに直す先はテスト内のリテラルであり、ドキュメントではない**。

この非対称は書き残した。IT7 では `navItems` の側を機械検査へ落としたが、
可否表は依然として人の規律に依存している。

## 2. 開発 — Datalog は「刈る」のではなく「門」だった

### 2.1 2 段構えにした理由

`architecture_backend.md` は Datalog を「到達可能性判定と積み替え制約の検証」に使うと定めている。
実装してみると、**推移閉包が答えるのは「港がつながっているか」だけ**だと分かった。

実際に乗れるかは時刻（前の船が着く前に次の船が出ていないか）と対応貨物種別に依存し、
これらは推移閉包の外にある。よって

1. Datalog で到達可能性を判定する
2. 深さ優先で辿り、時刻・種別・航海の重複を検証する

とした。当初のコメントには「1 で**刈った空間**を 2 で辿る」と書いた。

**レビューで、これが実装と違うと指摘された。** `isReachable` は
`origin → destination` の到達可否を返す**単一の Bool ゲート**であり、
`search` は刈られていない `hops` 全体を辿る。中間地点から仕向地へ到達不能な枝は、
最後まで展開されてから捨てられる。

コメントを「探索の要否を決める門である」と実態に合わせた。
枝ごとの刈り込みは `Reachable(y, destination)` を述語に使えば実現できるが、
積み替え上限が 2 回で深さが 3 に抑えられているため本 IT では行わない、と明記した。

> **書いた設計と、書いたコードが違っていた。** しかも書いた本人が気付かなかった。

### 2.2 境界を 3 つ決めた

| 境界 | 判断 | 決め方 |
| :--- | :--- | :--- |
| 到着期限 | 日付単位で比較 | メモリにあった教訓（DATE 期限 vs TIMESTAMP 到着）を最初から適用した |
| 接続 | 同時刻を成立とする | `Voyage` のビジネスルール 6 と揃えた。**最低接続時間は業務ルール未定義なので実装が決めない** |
| 出発日 | — | **決めなかった。これが後で問題になる** |

2 つ目の「実装が決めない」は正しい判断だったが、
利用者代表から**業務としての回答**が返ってきた——同一港 24 時間・危険物 48 時間。
決めなかったこと自体は正しく、決めるべき人に聞けば答えが出るという例になった。

### 2.3 TS12 は一度ハングした

タイムアウトを Java の `Future.get(timeout)` で実装した。
全テストが 600 秒を超えても終わらず、バックグラウンドへ落ちた。

原因の仮説を立てた。**`future.get` はハンドラ内の例外を `ExecutionException` に包んで
投げ直す。捕まえないとハンドラから例外が抜け、応答を書かないまま接続が閉じる。**
`TimeoutException` しか catch していなかった。

`Exception` の catch を足したら通った。この経験はコメントとして残した——
「捕まえないとハンドラから例外が抜け、**応答を書かないまま接続が閉じる**。
呼び出し側からは『応答が返らない』——最も診断しにくい壊れ方になる」。

**そのコメントが、後のレビューで別の穴を指摘する根拠になった**（`submit` が `try` の外）。

### 2.4 テストが「実装の欠陥」に見えた

`RuntimeGuardTest` が「503 に `Retry-After` が付いていない」と落ちた。
実装を疑って調べたら、**サーバは送っていた**。テストクライアントが
4 種のヘッダしか写し取っていなかった。

収集を列挙にしているのは「使わない値を運ぶ意味がない」という正しい理由からだが、
**列挙から漏れたヘッダは「送っていない」と区別が付かない**。

ふりかえりの Try にした——「テストが実装の欠陥を示したら、まず観測手段そのものを疑う」。

## 3. クローズ — レビューで 14 件の高優先度

5 視点の並列レビューを回した。高 14 / 中 18 / 低 9。

### 3.1 最も重かったもの: 防御が新しい単一障害点を作っていた

同時実行の枠を**全リクエストに適用**した。`/health/live` も例外ではなかった。

過負荷で liveness が 503 を返すと、オーケストレータは
「混んでいるだけで生きている」インスタンスを**再起動する**。

**IT3 で全く同じことを学んでいる。** 「`/health/live` が DB を見ると DB 障害時に
再起動ループになる」。そのとき `TxMode.NoTx` という仕組みで防いだ。
今回は DB ではなく**セマフォ経由で同じ障害が再現した**。

しかも `handleDynamic` には「liveness が DB を見ると再起動を繰り返す」という
コメントが実際に書かれている。**教訓は文書にもコードにも残っていたのに、
新しい防御を書くときに参照しなかった。**

全経路に一律に適用したのは「適用漏れを防ぐ」という正しい動機からだった。
**一律であること自体がリスクだ**という視点が抜けていた。

### 3.2 業務からの評価: 「この画面のまま日常業務は回らない」

利用者代表の指摘は、費用が無いことでも選択できないことでもなかった。

> **候補一覧に「もう出港した便」が混ざりうる**。経路設計者は毎朝
> 「今日から積める船はどれか」で見ている。過去の便が 1 本でも並んだ瞬間、
> この一覧全体が「信用できない参考情報」に格下げされ、結局これまでどおり
> 船社サイトと Excel を開くことになる。

受入基準には書かれていない。しかし**書かれていないことが「不要」を意味しない**。
「経路設計者は毎朝どう使うか」を一度も想像しなかったのが原因である。

同じ理由で船名も出していなかった（US07 受入基準 4 には明記されていた）。

`RouteSpec` に `earliestDeparture` を足し、`Clock.today()` をアプリケーション層で
注入する形で是正した。**ドメイン層は効果を要求しない**規約を守るため、
日付は引数で渡す。

### 3.3 ADR を書かなかったことの代償

IT7 は ACL の方向を反転させた（Booking → Routing から Routing → Booking へ）。
`domain-model.md` のイベントフロー図は反転前の形を正典としており、
**実装と正典が逆を向いた状態**が生まれた。

判断の理由はモジュールコメントに書いてある。だから「書いてある」つもりでいた。

アーキテクトの指摘は的確だった。

> 判断の理由はすべてソースコードのモジュールコメントに、非常に良質な形で
> 書かれています。しかしコメントは**コードと一緒に消える**もので、
> ADR は**決定が生き残るための形式**です。

より実害があるのは、US09（経路の確定）の設計を直接ブロックしていた点である。
「確定して `CONFIRMED` へ遷移させる」のがどちらの BC の責務か、2 通りに読めた。

ADR-0009 を起票し、**確定は Routing がイベントを発行し Booking が更新する**と決めた。
書き込みの越境を許すと、ここまでの BC 独立性の投資が一気に無駄になる。

### 3.4 新しく作った共有カーネルにテストが 1 件も無かった

`SharedCalendarText` に `toEpochDay`（Hinnant の `days_from_civil`）と
`dateOf`（**期限当日問題の根治点そのもの**）を足した。

これらに触れる唯一のアサートは `expected = 11` 一点だった。しかも 4/2 → 4/13 は
月をまたがない。つまり「**文字列の引き算では月をまたげない**」という、
この関数を作った理由そのものが未検証だった。

「暦法を 1 箇所に閉じた」判断は正しい。**その 1 箇所を固定しなかった**のが問題である。
18 件を追加した（閏年の 4 象限・世紀境界・年またぎ・全角の拒否）。

## 5. 今日いちばん学んだこと

**「書いてある」と「参照される」は別である。**

- 可否表は**ドキュメントに書いてあった**が、テストが見ていたのはコード内のリテラルだった
- 再起動ループの教訓は**コードのコメントに書いてあった**が、新しい防御を書くときに読まなかった
- ACL の方向は**モジュールコメントに書いてあった**が、正典の図は逆を向いたままだった
- Datalog の 2 段構えは**コメントに書いてあった**が、実装は書いたとおりになっていなかった

4 つとも「記録が無かった」のではない。**記録はあったが、必要な瞬間に参照されなかった**。

IT7 で `NavigationReachabilityTest` を作ったのは、導線の欠落が 2 回再発したからだった。
機械検査へ落とすというのは、「参照する」を人の規律から外すということである。

ふりかえりの Try T1（横断的な仕組みを足したら誰が困るかを表にする）は、
**まだ人の規律に頼っている**。それを承知で書いた——
「『思い出す』に頼る Try は弱い。機械検査へ落とせないかを IT8 で一度検討する」。

## 学び

- **並列エージェントへの共通指示には「正が 1 つの値」（バージョン番号・製品名）を明示的に固定する**。マッピング表を渡しても、指示にない周辺値はエージェントごとに揺れる
- **サブエージェントのセッション上限は fan-out の途中でも起きる**。部分適用状態を検出する術は「エージェントの完了報告を信じず grep で残存を数える」こと。今回 `grep -c "EF Core"` の残存カウントが復旧の起点になった
- **トレーサビリティのドリフトは複数視点レビューで初めて確定する**。3 エージェントが同じズレを別ルート（画面・テスト・業務）から指摘したことで、「旧採番の残骸」という診断に確信が持てた
- **ORM を外すと「フレームワークが暗黙に解決していた問題」が全部設計課題として現れる**（集約の子コレクション保存・イベント発行タイミング・監査カラム・楽観ロック）。マイクロ ORM 採用の見積りにはこの設計コストを含めるべき
- **二方言運用の穴はマイグレーションではなく実行時 SQL に開く**。DbUp のプロバイダ別スクリプトで安心してはいけない。`NOW()` / `RETURNING` のような手癖の方言は規約 + 機械検出で塞ぐ
- **PlantUML のコンポーネント名に角括弧を含めてはならない**。`[名前[入れ子]]` は構文破壊。`component "..." as alias` 形式が安全

## 運用フェーズ Skill 実行の時系列

### 1. `operating-setup` — 段階 1: アプリケーション開発環境

テンプレートから C# 版手順書を生成（.NET 10 / SQLite / Docker、Development と Production 互換の 2 プロファイル）。ローカルツール（dotnet 10.0.100 / Docker 29.6.1 / Node v24）の前提充足を確認。

### 2. `validating-operating-setup` — 監査 → A 対応 → B1〜B5 実施

初回監査は ✅12 / ❌13。「今すぐ可能」な A1〜A3（husky + lint-staged・.editorconfig・pre-commit）を実施後、ユーザー指示で B1〜B5（スキャフォールド）へ。

- **1 回目のスキャフォールドは設計不一致**でやり直しになった。レイヤー別 4 プロジェクト分割（CargoTracker.Domain/Application/Infrastructure/Web）で作ったが、architecture_backend.md のプロジェクト構造は「単一 Web ホスト + 名前空間ルート `CargoTracker` のコンテキスト優先構成」だった。設計ドキュメントの全体図（レイヤー別パッケージ図）だけ見て プロジェクト構造の章を精読しなかったのが敗因
- 途中で NU1903（Microsoft.Data.Sqlite の推移的依存に脆弱性 → SQLitePCLRaw.bundle_e_sqlite3 で上書き）、NU1603（実在しないパッケージバージョンを憶測で記載 → 実バージョンに固定。その際 MediatR が商用ライセンス世代の 14.x に上がり、tech_stack 指定の 12.5.0 へ固定し直し）を検出。**pre-commit フックが 2 回とも先に問題を止めた**

### 3. `operating-setup` — 段階 2: 開発環境（GHCR 構成 → Heroku 構成へ転換）

最初は SSH サーバー + GHCR 構成で手順書と Dockerfile を作成（`.dockerignore` がないと bin/obj 混入で `--no-restore` が壊れる問題を検出）。その後ユーザー指示で参照実装（dev_infa_instruction.md）に倣い **Heroku container stack 構成へ全面転換**。H2 インメモリの役割は SQLite（エフェメラル）が引き受け、ADR-0003 の開発 DB 方針とも噛み合った。

### 4. `operating-script` + 実デプロイ — deploy:dev / develop.js

`deploy:dev:setup` の実行で 2 つの Heroku 実地問題を踏んだ:

1. **`error from registry: unsupported`** — Docker Desktop の containerd イメージストアが OCI マニフェストを push する。`--provenance=false` だけでは不足で、buildx 直接 push（`--output type=image,oci-mediatypes=false,push=true`）で解決
2. **起動即 `Process exited with status 0`（H10）** — exec 形式 `ENTRYPOINT ["sh","-c",...]` が Heroku のコマンドラップと干渉。シェル形式 `CMD` に変更して解決

`develop.js`（dev:app / tdd:app / dev:db:* / dev:check）作成時には、**稼働中の同名 compose プロジェクトが別リポジトリ（haskell-take-1 の `apps/cargo-tracker`）由来**という衝突を発見。`name: cargo-tracker-csharp` の明示と `DEV_DB_PORT` 環境変数化で共存させた。

### 5. `operating-cicd` — Nix ベース CI + Heroku CD

`ops/nix/environments/dotnet/shell.nix` を `dotnet-sdk_10`（10.0.102）に固定し、CI はローカルと同一の nix-shell で format → build → test を実行する構成に。ローカル検証で **SDK 10.0.100 では通っていた build が 10.0.102 の Analyzers で CA1716（`Shared` は VB 予約語）により失敗**。名前空間は設計で規定のため .editorconfig で根拠付き抑止。HEROKU_API_KEY を GitHub Secrets に登録し（リポジトリ名は `case-study-cargo-tracker` — ディレクトリ名と異なる点に注意）、push で Backend CI 初回全緑。

## 学び（運用フェーズ）

- **スキャフォールドの前に設計の「プロジェクト構造」の章を精読する**。アーキテクチャ図（論理レイヤー）とプロジェクト構造（物理配置）は別物で、前者だけ見ると物理分割を誤る
- **パッケージバージョンを憶測で csproj に書かない**。`dotnet add package` に解決させる。憶測は NU1603 を、放置は意図しないメジャー昇格（MediatR 14 = 商用ライセンス世代）を招く
- **Heroku container stack の 2 大地雷**: (1) containerd ストアの OCI push は `oci-mediatypes=false` の buildx 直接 push で回避、(2) 起動コマンドはシェル形式 CMD 一択（exec 形式 ENTRYPOINT + sh -c は即死）
- **SDK のパッチバージョン差で Analyzers の検出が変わる**（10.0.100 で緑 → 10.0.102 で CA1716）。CI と ローカルのツールチェーン一致（今回の Nix 化）はこの問題の恒久対策になる
- **compose の `container_name` / 既定プロジェクト名はリポジトリ横断でグローバル**。同名ケーススタディを並行する環境では `name:` 明示とポートの環境変数化が必須
- **多リポジトリ運用では GitHub リポジトリ名とローカルディレクトリ名の不一致に注意**。`gh secret set -R` の 404 で気づいた

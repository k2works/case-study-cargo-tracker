## 学び

- **共有インメモリ SQLite は keep-alive 接続が必須**。`Mode=Memory;Cache=Shared` は「開いている接続が 0 本になると DB が破棄される」。接続プールを開閉するアプリでは、マイグレーション前に 1 本開いてプロセス終了まで保持しないと、リクエストごとに空 DB になる。keep-alive は早期 GC を避けるためシャットダウン後に明示 Dispose する参照点を作る。
- **file DB + forward-only マイグレーションはジャーナル不整合の温床**。DbUp の SchemaVersions と実テーブルがずれると「already exists」で起動不能になる。開発では毎起動まっさらなインメモリにするのが最も安全（過去にも journal 手挿入で対処した同種の罠）。
- **同名レコードフィールドは型推論が最後定義を選ぶ**。`RoutingRequestNotifier` と `ShipperNotifier` が両方 `Notify` を持つと、注釈なしのスタブが後発型に推論されて FS0001 が連鎖する。スタブに返り値型注釈を付けるのが F# の標準解（メモリ化済み）。
- **US10 の「期限調整」は探索専用と割り切ると設計が閉じる**。緩和期限は候補算出にのみ効かせ、確定はドメインが元の `RouteSpecification` 期限で検証して棄却（400）。実際の期限変更は営業経由の別アクションに委ね、その挙動を受入テストで固定した。レビューで潜在矛盾として指摘され、テストで先回りしていたことが奏功。
- **post-commit dispatch はベストエフォートを型/コメントで明示する**。`Async.Catch` で握り、確定済み結果を巻き戻さない意図をコードに書く。ただし架構視点では ADR-0002（UnitOfWork.execute + Shared Payload）と実装（Application 層ループ dispatch + BC ローカル DU）の乖離が 3 IT 継続しており、BC 間連携着手が decision の締切。
- **成功フィードバックの配線漏れは受入テストが素通りする**。View に `alert-success` 枠があっても呼び出し側が常に `None` だと無言。PRG の `?msg=` クエリで成功文言を出し、受入テストで `alert-success` を明示検証すると「動くが不親切」を捕捉できる。
- **イテレーション文書は数値・SP・US タイトルがズレやすい**。plan/retro/report で実測カバレッジや SP 配分が食い違うと報告の信頼性を損なう。release_plan.md を正として機械的に突合するのが吉。

### 1. `closing-iteration`（IT5）— 前回の締め

#### ハマったポイント

**`voyage` テーブルが存在しなかった。** `data-model.md` に定義があったので `ALTER TABLE` を書いたら
マイグレーションが落ちた。V1 で作られていたのは location / tracking 系だけで、`voyage_number` は
`tracking_handling_event` の一列として存在するだけだった。**「設計にあるから実装にもある」と考えていた。**

**Flix の落とし穴も複数踏んだ。**

| 症状 | 原因と対処 |
| :--- | :--- |
| `instance` を変数名に使うとパースエラー | 予約語。`appInstance` へ改名 |
| `List.groupBy` が `Nel` を返して型が合わない | `groupConsecutive` を自作 |
| 描画テストで `not contains "GENERAL"` が落ちる | 検索フォームの `<select>` が `value="GENERAL"` を持つ。**tester が指摘した罠を自分で踏んだ** |

### 4. `closing-iteration`（IT6）— 5 視点レビューと修正

5 視点を並列で起動し、**全視点に「この原理が及ぶ他の場所はどこか」を必須条件**とした（Try T1）。

| 調査 | 結果 |
| :--- | :--- |
| `CAST` を含む SQL の全数確認 | 無防備は検索の 2 箇所だけ |
| 「認可はあるが導線が無い」ずれの全ルート突合 | `/voyages` の 1 件。**逆向きのずれが 5 件**あることも判明 |
| 港コードで機能判定している箇所の走査 | 空虚なアサートは 1 件だけ |
| doc コメントの誤配置（空 `///` の 2 連続） | 3 件 |

高 14 / 中 15 / 低 7。**高は全件対応**した。

#### この日いちばん重い発見

**新規に導入した 2 つの安全装置が、どちらも守りたいものを守れていなかった。**

| 装置 | 意図 | 実際 |
| :--- | :--- | :--- |
| 楽観的ロック（ADR-0008） | 失われた更新を防ぐ | 版の条件が SQL に無く同時到達で両方が書ける。`Stale` は版だけ最新へ差し替えるため、押し直すと**相手の変更が黙って消える** |
| `X-App-Instance` | 別インスタンスの応答を切り分ける | **期待値が無く**、値を見ても判断できない |

どちらも全テスト緑だった。共通するのは「**入れたこと**を検証するテストはあるが、
**働くこと**を検証するテストが無い」点である。しかも同じ IT で `postConcurrently`（同時 POST ヘルパー）を
新設しておきながら、**新設した安全装置の側には向けなかった**。

### 5. 行ロックの検証中に間欠異常の手掛かりを得た

修正とテストを同時に入れたため、並行更新テストに実効性があるか確かめようと行ロックを外した。
すると予想外の結果になった。

| 構成 | 結果 |
| :--- | :--- |
| 行ロックあり | 570 件緑 |
| 行ロックなし | 並行更新テストは**通る**。代わりに**無関係な `ShipperHttpTest` のログインが `Set-Cookie` を得られず落ちる**（2 回再現） |

行ロック無しで同じ行へ 8 本の書き込みトランザクションが同時到達すると競合し、
待機がコネクションプールを占有する。IT4・IT5 の間欠異常はいずれも「そのルートでは起こり得ない応答」で、
これまでの仮説（応答の交差・ポート再割り当て）は**アプリケーションの論理**に原因を求めていた。
H7 は**実行環境の資源**に求める点で系統が違い、しかも観測に基づく。ADR-0005 へ記録した。

## 学び

- **検証手段を作ることと、それを新機能へ向けることは別の行為である。** IT6 は
  `postConcurrently` を新設しながら、同じ IT で新設した楽観的ロックへ向けなかった。
  着手前に「既に作った検証手段の一覧」を読み直す手順が要る
- **read-modify-write をアプリケーション側の比較だけで守れると考えてはいけない。**
  版の照合は「読む → 比べる → 書く」であり、この 3 つの間に別のトランザクションが書けば両方が通る。
  `SELECT ... FOR UPDATE` か `WHERE` 句の条件が要る
- **観測手段には必ず期待値との突合を付ける。** 応答へ添えて印字するだけでは、
  受け取った値が期待どおりか誰にも分からない。IT5 の `X-Route`（テスト実行で無効だった）と
  IT6 の `X-App-Instance`（期待値が無い）は、同じ失敗の 2 つの形である
- **「画面単体は正しいがロールをまたぐと切れる」は繰り返し起きる。** navbar の導線欠落・
  押せないボタン・実行できない運用手順の 3 件が同時に出た。画面を足したら
  **そのロール以外で開いたときに何が見えるか**を 1 つずつ確認する
- **書いた運用手順が実行できるかを確かめる。** 「経路設計者が予約一覧を状態で絞り込む」と書いたが、
  経路設計者はその画面に到達できず、状態で絞る手段も無かった。
  **安全網があるつもりで何も見ていない状態**が最も危ない
- **「他になし」と書けること自体に価値がある。** 1 箇所を直して終わりにすると、
  次の IT で同じ形が別の場所から出る。全数調査の結果を記録しておけば、次に同じ疑いが出たとき
  調査済みだと分かる
- **原理を理解していても同じ罠を踏む。** tester が指摘した「ページ全体の部分一致は常に真になる」を、
  その修正として書いたテストでそのまま踏んだ。理解は予防にならない。機械的な手順が要る
- **自作 lint は、守らせたい書き方をしているファイルほど検査から外れることがある。**
  `arch-lint` 規約 9 は SQL の骨格を要求していたが、骨格を関数へ切り出す
  （このリポジトリの JDBC が実際に採る書き方）と素通しだった。
  フィクスチャは**実コードの形**で作る

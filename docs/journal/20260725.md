`orchestrating-project --status` → `opening-iteration`（IT2 開始準備）→ `orchestrating-development`（US05/US13 実装）→ 追加要望対応（CSS・ナビ導線・既定ユーザー）→ `closing-iteration`（IT2 クローズ 7 ステップ）。IT2 で Phase 1 を完了し Release 0.1 MVP に到達した。

## 主要な意思決定と、なぜそうしたか

- **Try 返済を機能実装より先に**: T1（設計是正）・T2（ShipperCode 改称）を着手初期に実施。設計と実装がずれたまま US05/US13 を積むと二重の手戻りになるため、先に土台を揃えた。結果、新規コードは最初から `ShipperCode` を使え churn を抑えられた。
- **可否判定をドメインへ集約（レビュー起点）**: 当初ハンドラで `CanCancel = status != CANCELLED` としていたが、ドメインの `Cancel()` が許容するのは PRELIMINARY/ROUTE_PROPOSED/CONFIRMED のみ。Programmer レビューで UI/ドメイン不整合を指摘され、`Cargo.CanConfirm/CanCancel/CanSendBackToRouting` を単一情報源としてドメインに置いた。UI の可否表示とドメイン規則が二度と乖離しない。
- **ShipperId を Shipper BC へ移設**: Architect レビューで「BC 独立の意味目標は達成済みだが、UUID 型が共有カーネルに物理的に残る」と指摘。Booking 参照ゼロを確認し、コンパイラを安全網にして移設。ADR-0005 決定2 を完遂した。

## どこで詰まったか

- **SonarQube Quality Gate が一度 FAIL**: 新規コードカバレッジ 52%（要 80）。原因は infra（Repository・Query）が integration タグ配下で、`go test -coverprofile`（unit のみ）に含まれないこと。`go test -tags integration -coverprofile` で計測し直し、さらに handler の 422/404 異常系・application の特殊貨物異常系テストを追加して 84.2% まで引き上げ PASS。**学び**: クローズ時のカバレッジは必ず integration タグ込みで計測する（IT3 の Try に標準化を計上）。
- **引数過多の Code Smell**: `RegisterCargo`(8)・`Restore`(9) が SonarQube MAJOR。`domain.CargoParams` 構造体に集約して解消。値オブジェクトが増えるドメインでは最初から params 構造体を検討すべきだった。
- **numericFromFloat3 の負数丸めバグ**: `int64(f*1000+0.5)` が負の温度で誤差。round-trip の integration テストで検出し `math.Round` に修正。テストがなければ本番まで潜在した。

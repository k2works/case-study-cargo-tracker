# 2026-07-25 開発ジャーナル

## この日やったこと（Skill の流れ）

`orchestrating-project --status` → `opening-iteration`（IT2 開始準備）→ `orchestrating-development`（US05/US13 実装）→ 追加要望対応（CSS・ナビ導線・既定ユーザー）→ `closing-iteration`（IT2 クローズ 7 ステップ）。IT2 で Phase 1 を完了し Release 0.1 MVP に到達した。

## 主要な意思決定と、なぜそうしたか

- **Try 返済を機能実装より先に**: T1（設計是正）・T2（ShipperCode 改称）を着手初期に実施。設計と実装がずれたまま US05/US13 を積むと二重の手戻りになるため、先に土台を揃えた。結果、新規コードは最初から `ShipperCode` を使え churn を抑えられた。
- **可否判定をドメインへ集約（レビュー起点）**: 当初ハンドラで `CanCancel = status != CANCELLED` としていたが、ドメインの `Cancel()` が許容するのは PRELIMINARY/ROUTE_PROPOSED/CONFIRMED のみ。Programmer レビューで UI/ドメイン不整合を指摘され、`Cargo.CanConfirm/CanCancel/CanSendBackToRouting` を単一情報源としてドメインに置いた。UI の可否表示とドメイン規則が二度と乖離しない。
- **ShipperId を Shipper BC へ移設**: Architect レビューで「BC 独立の意味目標は達成済みだが、UUID 型が共有カーネルに物理的に残る」と指摘。Booking 参照ゼロを確認し、コンパイラを安全網にして移設。ADR-0005 決定2 を完遂した。

## どこで詰まったか

- **SonarQube Quality Gate が一度 FAIL**: 新規コードカバレッジ 52%（要 80）。原因は infra（Repository・Query）が integration タグ配下で、`go test -coverprofile`（unit のみ）に含まれないこと。`go test -tags integration -coverprofile` で計測し直し、さらに handler の 422/404 異常系・application の特殊貨物異常系テストを追加して 84.2% まで引き上げ PASS。**学び**: クローズ時のカバレッジは必ず integration タグ込みで計測する（IT3 の Try に標準化を計上）。
- **引数過多の Code Smell**: `RegisterCargo`(8)・`Restore`(9) が SonarQube MAJOR。`domain.CargoParams` 構造体に集約して解消。値オブジェクトが増えるドメインでは最初から params 構造体を検討すべきだった。
- **numericFromFloat3 の負数丸めバグ**: `int64(f*1000+0.5)` が負の温度で誤差。round-trip の integration テストで検出し `math.Round` に修正。テストがなければ本番まで潜在した。

## 次回に活かすこと

- カバレッジは integration 込みで計測（手順標準化）。
- 3+ 値オブジェクトを取る集約コンストラクタは params 構造体を初手から。
- マルチパースペクティブレビューは go-arch-lint 緑でも見えない構造/UI 不整合を確実に拾う。クローズ前レビュー→即対応のループは費用対効果が高い。

- BC 横断は合成ルート注入方式（ADR-0007）: `RouteSearcher` ACL ポートを Booking/Estimation の application に定義し、`cmd/server` の変換アダプタで Routing の `SearchRoutesService` を注入。`.go-arch-lint.yml` 無改変。
- Try 返済: shared `Clock` 注入（T3）、見積の実経路化・経由港表示（T3・`route_candidate.waypoints` 000010）、航海フォームの動的区間・edit 全区間表示（T2）、Estimate 到着期限の不変条件（T6）、境界テスト補強（T5）、設計本体同時反映（T1）。

## 判断と学び

- **開発中の中間 self-review が確証バグを捕捉**: programmer/tester が**独立に同時**、DATE 期限(00:00) vs TIMESTAMP 到着(時分) の齟齬で「期限当日に時刻付き到着する正当な候補を刈る」バグを指摘。2 観点一致は信頼性が高く、クローズ前に日付単位比較へ是正。Estimation の候補ゼロ誤通知にも波及していた。→ メモリ `feedback_date-vs-timestamp-deadline` に記録。
- **クローズ 5 観点で残る穴を回収**: technical-writer が data-model の物理カラム未同期（cargo.routing_status・route_candidate.waypoints）を、user-representative が経路割り当て画面の期限充足 UX 欠落（到着期限・到着予定日・残日数なし）を検出。中間 3 観点＋クローズ 5 観点の 2 段運用が機能した。
- **合成ルート注入方式の再利用性**: US09（Booking）と T3（Estimation）で同じ `RouteSearcher` パターンを 2 度適用。ACL ポートを消費側に置き cmd で変換注入する形は、BC 独立性を保ったまま探索ロジックを複数 BC で共有できる汎用解と確認。

## どこで詰まったか

- **確定後のリダイレクト先が 403**: US09 の経路確定（経路設計者ロール）後に予約詳細（営業ロール専用）へ PRG すると 403。detail 参照を分割登録（`RegisterDetail`）し経路設計者にも許可、状態操作ボタンはロールで出し分けた。E2E で発覚（handler 単体では気づけなかった）。
- **SonarQube 品質ゲート FAIL（引数7超 2 件）**: `CreateEstimate` の 8 引数（Task 0 で now 追加）とテストヘルパ mvt の 9 引数。params 構造体化（`NewEstimateParams`）と `time.Time` 化で解消し PASS。テスト緑だけでは締まらない好例。
- **feature ブランチ CI が自動起動しない**: main push/PR のみ自動・go/take-1 は workflow_dispatch 手動。クローズ時に手動トリガーが必要（Try T7 に計上）。

## 次回に活かすこと

- マイグレーション追加時は data-model 物理テーブル（カラム表・DDL・論理モデル）を同一コミットで更新（Try T1）。

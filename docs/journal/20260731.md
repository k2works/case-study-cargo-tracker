# 2026-07-31 開発ジャーナル

Release 1.0（全 27 ストーリー・IT7 クローズ）到達後のバッファ作業として、「ログインして業務フロー（予約 → 経路 → 荷役 → 追跡 → 精算）を手で回せる状態」を作るためのシードデータを整備した。荷主・航海マスタから着手し、実 PostgreSQL 向けのシードコマンド（`npm run seed`）を新設、最後にユーザーからの要望で見積・貨物予約のデモデータまで広げた。「pg-mem にデータが入っていない」という指摘は、実は荷主に一覧画面が無く自由入力だったことが原因で、稼働アプリを HTTP で直接照会して健在を確認した。

## ハイライト

- 業務フロー用シードを `seedShippers`（個人 2・法人 2）・`seedVoyages`（直行/経由）で追加し、`seedAll` に集約して pg-mem 起動時・実 DB 双方で共通化した
- 実 PostgreSQL 向けシードコマンド `npm run seed`（`seed-cli.ts`）を新設し、使い捨て Postgres コンテナで migrate → seed → 冪等再実行をエンドツーエンド検証した
- 「データが入っていない」指摘を、稼働中 dev サーバーへの HTTP 照会（`/voyages` に V-DEMO 航海、予約フォームの UN/LOCODE 候補）で「実は入っている」と切り分けた
- 見積 2 件・貨物予約 2 件（荷主 FK 解決・PRELIMINARY）のデモデータを追加し、見積管理・貨物予約一覧に表示データを供給した

## Skill 実行の時系列

このセッションは特定の Skill オーケストレーションではなく、Release 1.0 後のバッファ作業（シード整備）を対話的に進めた。作業単位で記す。

### 1. シードデータ追加（荷主・航海）

`seed.ts` に業務フローの起点となるマスタを追加した。

| 追加関数 | 内容 |
| :--- | :--- |
| `seedShippers` | 個人 2（割引 0）・法人 2（割引 15% / 30%）。US22 の法人割引を確認できる |
| `seedVoyages` | 直行 V-DEMO-001（JPTYO→USLAX）・経由 V-DEMO-002（JPTYO→HKHKG→SGSIN）。到着日は `now` 基準の相対日付 |
| `seedAll` | 全シードを集約。`main.ts`（pg-mem 起動時）と共通化 |

### 2. シードコマンド新設（`npm run seed`）

実 PostgreSQL にはシードが自動投入されない（`main.ts` は `!DATABASE_URL` 時のみ seed）ため、`seed-cli.ts` を新設し `npm run seed` を追加した。`DATABASE_URL` 未設定はガードで明示エラー。使い捨て Postgres 16 コンテナで `migrate:up` → `seed`（1 回目・2 回目）→ 行数照会（users 6 / location 10 / shipper 4 / voyage 2 / carrier_movement 3、冪等）を検証してからコンテナを破棄した。

### 3. 「データが入っていない」の切り分け

ユーザーから「pg-mem にデータが入っていない」との指摘。シード経路（`createPgMemDatabase` + `seedAll`）と Nest DI 経由（`app.get(DATABASE)` の同一インスタンス）の双方で件数を確認し、コードは正常と確定。稼働中 dev サーバー（port 8080）へ HTTP 照会し、`/voyages` に V-DEMO 航海、予約フォームの UN/LOCODE 候補に 10 ロケーションが出ていることを確認。原因は**荷主に一覧画面が無く、予約フォームの荷主 ID が自由入力テキスト**だったこと。seed 済み荷主コード（SHP-DEMO0001〜0004）を提示して解決した。

### 4. 見積・貨物予約のデモデータ追加

ユーザー要望で下流画面の表示データを拡張。`seedEstimates`（見積 2 件・CREATED）・`seedBookings`（貨物予約 2 件・PRELIMINARY・荷主 FK 解決）を追加し `seedAll` に組み込んだ。`/estimates`・`/bookings` に表示されることを HTTP で確認。

## 学び

- **「データが無い」の 9 割は「表示経路が無い」**。DB にデータはあるのに画面に出ない場合、まず一覧画面の有無・入力方式（ドロップダウン vs 自由入力）を疑う。DB 直照会 → DI 経路 → 稼働アプリ HTTP の順で切り分けると早い
- **`estimate_id` / `booking_id` は UUID 型**。読みやすい `EST-DEMO0001` 形式は `cannot cast type text to uuid` で弾かれる。デモ用でも有効な UUID を固定定数（`DEMO_ESTIMATE_IDS` 等）で持ち、テストから参照して可読性と冪等性を両立させる
- **冪等シードは「テーブルが空か」で判定**すれば、ID は非決定的でも安全。ただしテストで特定行を検証するなら ID は固定値にする
- **FK 順序に注意**。`carrier_movement`→`location`、`cargo`→`shipper` の FK があるため、seed 関数単体テストでは依存マスタを先に投入する。`seedAll` の呼び出し順（location → shipper → voyage → estimate → booking）がそのまま依存順
- **実 DB 検証は使い捨てコンテナで完結させる**。`docker run -p 55432:5432 postgres:16` で一時 DB を立て、`DATABASE_URL` を差して migrate/seed を通し、確認後に `docker rm -f`。SonarQube の DB（5432 常駐）とはポートを分けて衝突を避ける
- **`node --watch` の再起動を前提に稼働確認する**。dev サーバーはファイル保存で再起動し pg-mem は毎回新規なので、稼働中インスタンスの状態（今回は予約が PRELIMINARY から進んでいた）は長時間セッションの履歴を映す。正規初期状態はユニットテストで担保する

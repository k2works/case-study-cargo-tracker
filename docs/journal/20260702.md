## 学び

- **plan.md の設計詳細度はプロジェクト規約より運用者の裁量が優先する**。T5-17 で「plan.md は task list、設計は docs/design/」と決めたが、実際には設計セクションを plan.md 内に持つ IT5 の運用のほうが「1 ファイルで完結して読める」利点があり、ユーザーが後者を選好した。規約は絶対ではなく、成果物の使い勝手を都度確認する
- **`validating-iteration-plan` の NG 指摘は「設計セクション不足」がほとんど**。task list 中心で計画を書くと必ずこの検証で引っかかる。task list 派で通すなら T5-17 を明文化し validating skill 側にも「設計を docs/design/ に分離した場合は plan 側の詳細記述を要求しない」オプションを追加する必要がある
- **GitHub Issue のクローズは IT 完了報告書とは独立に忘れがち**。今回は `--status` で「Issue #273-277 が OPEN」を検出できたので、この観点を IT 完了報告書テンプレートの DoD に組み込むと再発防止になる
- **大規模な設計セクション書き下ろしは Explore ではなく general-purpose エージェントに委譲する**。Explore は read-only で Write/Edit ができないため、900 行規模の追記には不向き。委譲時のエージェント種別選択を型化する
- **markdownlint MD060 は既存 baseline に合わせる**。新規ファイルだけ厳格化すると差分レビューが煩雑になる。プロジェクト全体で lint 規約を決めるまでは「既存が通る範囲で書く」が実用的
- **ADR 骨子をコードブロックで plan 内に埋めるスタイル** (IT5 で採用、IT6 で継続) は、まだ提案段階の ADR に対して「案は plan に、正式化したら docs/adr/ に切り出す」という段階運用と親和する

#### 主要な意思決定と学び (実装フェーズ)

- **Verifier 注入の 3 phase 分解**: 平文比較 → 定数時間比較 → bcrypt hash 保存の直接切替は既存 6 テストを破壊するリスクがあったため、`type Verifier = Text -> Text -> Bool` を Shared に導入して `verifyWith checker` で戦略パターン化。既存テストを緑のまま bcrypt に完全移行できた。**この 3 phase パターンは今後の Domain 型の段階的移行の型として再利用したい**
- **TxRunner の配置は arch-check の T-01 で修正**: 当初 Infrastructure に置いたが T-01 (withTransaction は Application 層のみ) 違反で検出。Application 層に移設して解消。**Shared/Application/TxRunner という配置は Cross-BC で共有されるトランザクション境界抽象として自然だった** (以後の Pricing / Notification でも同じ場所を使う)
- **Rule 4 違反の予見**: Handling BC が Notification Domain (`LogChannel` コンストラクタ) を import した初期実装が Rule 4 で違反。修正時に `sendClaimLogNotificationText :: ... → Text → Text → Text → UTCTime → m ...` の Text-only helper を Notification.Application に追加して解消。**「他 BC の Domain 型をコンストラクタ経由で参照したくなったら、まず Text-only helper を用意する」というアンチパターン検知ルールを型化できた**
- **In-Memory Repository の残置価値**: Postgres 実装への移行後も InMemoryPricingRuleRepository / InMemoryNotificationRepository を残置。単体テストのフィクスチャや暫定デモ用途で有用。**「Postgres 実装ができたら In-Memory を消す」ではなく「両立させる」判断は Testcontainers 依存を減らす副次効果もあった**
- **Ralph Loop 30 反復は後半で粒度が粗くなる**: 前半 (T5-01〜T5-05) は 1 反復 = 1 phase = 1 コミットで密度が高かったが、後半の Postgres Phase は 1 反復に 2 モジュール (Repository) が入るなど粒度がぶれた。**5 反復ごとに `--status` で確認すると集中が保てそう** (Try に T6-10 として計上)

### 学び (統合)

- **「Domain / Application / Infrastructure / Interfaces / Views / Wire / Postgres の全レイヤ」を 1 ストーリーで完成させる粒度は、実は 5 SP 見積では過小評価**。US21 / US26 いずれも計画 5 SP → 実績 13 SP 相当。「全レイヤ完了」を DoD にするなら 10-15 SP 見積が妥当
- **Ralph Loop は「1 反復 1 commit / 1 テスト増分」の粒度を保つと消化率が高い**。IT5 の Ralph 21 反復 + IT6 の Ralph 32 反復ともにこの粒度で機能した
- **Postgres 実装は「migration + Repository + Main 切替」を 1 反復にまとめると arch-check / build / test の並行検証で自然に品質担保できる**。Postgres Phase 1-2 が典型例
- **CHANGELOG [Unreleased] の実績ベース整理 (T5-20) は IT 完了時にも継続効果**。実装物の Added / Changed / Fixed が並ぶことで、IT 完了報告書と CHANGELOG の内容が重複せず補完関係になる (完了報告書は指標、CHANGELOG はエンドユーザー向け機能一覧)
- **Ralph Loop 停止条件が明示的でない場合の判断**: `--max-iterations` も `--completion-promise` も指定なしで起動された Ralph Loop は「無限ループ」に見えるが、実際は「タスクが尽きるまで自然に終わる」という運用が成立した。IT6 の作業スコープ (T5-01〜T5-21 + US21 + US26 + Postgres + 完了報告書 + KPT) が実質的な完了促進として機能した

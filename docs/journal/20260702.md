## 学び

- **plan.md の設計詳細度はプロジェクト規約より運用者の裁量が優先する**。T5-17 で「plan.md は task list、設計は docs/design/」と決めたが、実際には設計セクションを plan.md 内に持つ IT5 の運用のほうが「1 ファイルで完結して読める」利点があり、ユーザーが後者を選好した。規約は絶対ではなく、成果物の使い勝手を都度確認する
- **`validating-iteration-plan` の NG 指摘は「設計セクション不足」がほとんど**。task list 中心で計画を書くと必ずこの検証で引っかかる。task list 派で通すなら T5-17 を明文化し validating skill 側にも「設計を docs/design/ に分離した場合は plan 側の詳細記述を要求しない」オプションを追加する必要がある
- **GitHub Issue のクローズは IT 完了報告書とは独立に忘れがち**。今回は `--status` で「Issue #273-277 が OPEN」を検出できたので、この観点を IT 完了報告書テンプレートの DoD に組み込むと再発防止になる
- **大規模な設計セクション書き下ろしは Explore ではなく general-purpose エージェントに委譲する**。Explore は read-only で Write/Edit ができないため、900 行規模の追記には不向き。委譲時のエージェント種別選択を型化する
- **markdownlint MD060 は既存 baseline に合わせる**。新規ファイルだけ厳格化すると差分レビューが煩雑になる。プロジェクト全体で lint 規約を決めるまでは「既存が通る範囲で書く」が実用的
- **ADR 骨子をコードブロックで plan 内に埋めるスタイル** (IT5 で採用、IT6 で継続) は、まだ提案段階の ADR に対して「案は plan に、正式化したら docs/adr/ に切り出す」という段階運用と親和する

## 学び

- **整合性検証は計画作成直後に必ず実施する**: HS コード 4 桁 vs 6-10 桁の誤り、`customs_info` vs `customs_declaration` の重複は実装着手後に発覚すれば DB マイグレーション + UI + Domain 全層の手戻りになる。21 件すべてを開始前に検出できたのは大きな投資効果
- **「同等水準で」の依頼には先行イテレーション計画のサブセクション網羅性を物差しにする**: IT2 計画の `^### ` を grep で抽出し、IT3 計画と差分を取って欠落 (シーケンス図 / トランザクション境界 / エラー処理戦略 / CI 統合) を機械的に拾えた
- **過剰計画の警告は必須**: 29 SP / IT2 実績 18 SP の 1.6 倍。**ストレッチ枠 4 SP を明示区分** + 「コミット必達 25 SP」を別表記することで、消化遅れ時の判断 (何を IT4 へ繰越すか) が事前に決まる
- **GitHub Issue 本文は「リンクのみ」より「Gherkin 受入基準」を直書きするほうが PR レビュー時に効率が良い**: 旧版の Issue は `user_story.md` への単純リンクのみで、HS 桁数誤りに気付けない構造だった。受入基準を本文に直書きすることで、Issue を見るだけで仕様の最新版が分かる
- **計画ドキュメントを Single Source of Truth とし、GitHub は同期先**: skill の運用方針に従い、Issue を直接編集せず計画ドキュメント側を修正してから sync を回す原則を堅持。今回は計画 → Issue の片方向同期で破綻なし
- **IT3 トラッカー Issue (#271) は IT2 まで存在しなかった新パターン**: 本体ストーリー Issue とは別に、ストーリー外のタスク (U-XX 繰越、H-XX レビュー対応、ADR 起票) を 1 つの Issue でチェックリスト化することで、Milestone レベルで「何が残っているか」が即座に見える

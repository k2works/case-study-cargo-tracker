## 学び

- **Milestone クローズは Issue クローズと別 API**: `gh issue close` は Issue を閉じるだけで milestone.state は open のまま。`gh api -X PATCH repos/OWNER/REPO/milestones/N -f state=closed` を明示的に叩く必要がある。「open:0 closed:N」の milestone を放置しない
- **取り残し Issue は Milestone クローズ時に発掘される**: US05 (#236) は IT2 で US04 と統合されたが、GitHub Issue は clone 元のテンプレから独立して作成されていたためクローズ漏れが半年残存。IT ごとの retrospective で「Issue のクロージング状況」を含めるとよい
- **DB 認証エラーは実装着手前の暗黙前提**: `dbmate status` が動く前提で `orchestrating-project --iteration N` は書かれているが、Postgres の user/password が local で未整備なケースがある。IT 開始 checklist に「Postgres up + credential 一致」を明示追加すべき (T5-16 の拡張)
- **計画の設計セクション深度は「IT6 パリティ」を基準にする**: IT6 の 900 行超は「新規 BC 2 個 + Tx 境界初導入」の特殊事情もあるが、Haskell 型定義 + PlantUML + シーケンス + Tx ルールの 4 点セットを新規 BC には必ず用意する運用にすると、実装フェーズの手戻りが減る
- **`validating-iteration-plan` の指摘は 2 種類ある**: (1) 計画側の欠落 (今回の US17 手動更新フォーム) → 上流ドキュメント側を修正、(2) 対応済だが計画未反映 (今回の IT6 レビュー #1) → 追記不要。8 ステップ全て NG=修正必須ではないので、指摘ごとに「どこを直すべきか」を判定する
- **Cross-BC 参照は Text DTO で統一**: IT6 で確立した `bookingId :: Text` / `trackingNumber :: Text` パターンを IT7 の `ExceptionToTrackingHelper` / `ShipperToPricingHelper` にも継承。arch-check Rule 4 で自動検証するので、helper の配置は `Shared/CrossBc/` に固定する規約を計画書に明記した
- **JSONB detail vs 垂直分割の判断**: DelayException / DamageException / LossException を 3 テーブルに分割するか単一 `exception_record` + `detail_json` にするかは早期に決めておく。ADR-0014 で「単一テーブル + JSONB + Application 層で property 検証」を採用し、検索性 (severity/type index) と柔軟性のバランスを取った

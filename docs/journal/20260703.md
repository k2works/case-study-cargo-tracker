## 学び

- **Milestone クローズは Issue クローズと別 API**: `gh issue close` は Issue を閉じるだけで milestone.state は open のまま。`gh api -X PATCH repos/OWNER/REPO/milestones/N -f state=closed` を明示的に叩く必要がある。「open:0 closed:N」の milestone を放置しない
- **取り残し Issue は Milestone クローズ時に発掘される**: US05 (#236) は IT2 で US04 と統合されたが、GitHub Issue は clone 元のテンプレから独立して作成されていたためクローズ漏れが半年残存。IT ごとの retrospective で「Issue のクロージング状況」を含めるとよい
- **DB 認証エラーは実装着手前の暗黙前提**: `dbmate status` が動く前提で `orchestrating-project --iteration N` は書かれているが、Postgres の user/password が local で未整備なケースがある。IT 開始 checklist に「Postgres up + credential 一致」を明示追加すべき (T5-16 の拡張)
- **計画の設計セクション深度は「IT6 パリティ」を基準にする**: IT6 の 900 行超は「新規 BC 2 個 + Tx 境界初導入」の特殊事情もあるが、Haskell 型定義 + PlantUML + シーケンス + Tx ルールの 4 点セットを新規 BC には必ず用意する運用にすると、実装フェーズの手戻りが減る
- **`validating-iteration-plan` の指摘は 2 種類ある**: (1) 計画側の欠落 (今回の US17 手動更新フォーム) → 上流ドキュメント側を修正、(2) 対応済だが計画未反映 (今回の IT6 レビュー #1) → 追記不要。8 ステップ全て NG=修正必須ではないので、指摘ごとに「どこを直すべきか」を判定する
- **Cross-BC 参照は Text DTO で統一**: IT6 で確立した `bookingId :: Text` / `trackingNumber :: Text` パターンを IT7 の `ExceptionToTrackingHelper` / `ShipperToPricingHelper` にも継承。arch-check Rule 4 で自動検証するので、helper の配置は `Shared/CrossBc/` に固定する規約を計画書に明記した
- **JSONB detail vs 垂直分割の判断**: DelayException / DamageException / LossException を 3 テーブルに分割するか単一 `exception_record` + `detail_json` にするかは早期に決めておく。ADR-0014 で「単一テーブル + JSONB + Application 層で property 検証」を採用し、検索性 (severity/type index) と柔軟性のバランスを取った

### Ralph Loop 運用の学び

- **反復ごとに 1 コミット原則**: 1 反復 = 1〜3 コミット。commit → status update commit
  → plan update commit の 3 段構えで進捗が明示化。stop hook 再投入時に「前回の
  最後のコミット」を起点に次の作業を判断できる
- **fourmolu の Haddock コメント位置ルール**: 引数の型注釈は `-- | ...` を引数の
  **前**に置く。 `-- ^` (後置) を使うと自動整形でエラー。今 Ralph 反復で 4-5 回踏んだ
- **hspec-wai app 引数の増減はテストのフィクスチャ調整が付随**: Interfaces に
  Repository を注入するたび既存の `costCalculationApp jpyRuleRepo emptyRateRepo`
  等が壊れる。`emptyShipperRepo` のような最小フェイクを事前に用意する
- **hedgehog `check :: IO Bool` パターン**: hspec の `it $ check property` は
  型エラー。`check property >>= assertTrue` に統一するヘルパを spec 末尾に置く
  (`assertTrue True = pure ()` / `assertTrue False = expectationFailure "..."`)
- **arch-check Rule 4 (BC 間 Domain 直接参照禁止) を Cross-BC helper 経由で回避**:
  Exception BC の Cross-BC 参照 (Tracking 状態遷移) は Text-DTO callback
  `(Text -> m (Either DomainError ()))` を Command 引数で受け取ることで、
  Exception.Application が Tracking.Application.Ports にすら依存しない設計を実現
- **Ralph Loop で ADR 起票と実装を交互に**: iter 18-22 は「ADR-0013 起票 →
  ADR-0014 起票 → Phase 1 実装 → Phase 3 property → Phase 2 統合」の順で
  ADR の Decision セクションを実装のガイドラインとして活用。実装しながら ADR を
  refine する動きも取れた
- **JSONB detail_json の暫定パーサ回避**: PostgresExceptionRepository.find 系は
  「暫定的に Nothing/[] 返却」として先送りし、Testcontainers 統合テスト (T6-05) と
  併せて aeson インスタンス整備するタスクに分離。JSONB → Domain 型の
  再構築を Ralph Loop 中に完璧に仕上げようとせず、READ 経路のカバレッジは後回しに
  した判断は Ralph 反復の速度維持に効いた
- **Ralph Loop 停止判断**: 完了 promise なしの無限ループなので、目的達成後の
  「上流ドキュメント同期」まで進めた段階で `/ralph-loop:cancel-ralph` を呼ぶ判断
  も必要。Ralph Loop iter 25 完了時点で「Domain / Application / Infrastructure /
  Migration / ADR / 上流ドキュメント」の一貫性が確保できた

### iter 38-58 の学び

- **View 骨組み → Servant → Main → hspec-wai の 4 分割**: US17 の 1 スライスを
  4 イテレーションに分けたことで、各コミット差分が読みやすく、pre-commit

  追加する誘惑を退けた

  として導入することで、既存の `mkNotification` / Postgres 復元コード /
  in-memory テストのすべてを一度に変更する必要がなくなり、Phase 別コミット
  (`Phase 1` migration → `Phase 2` VO → `Phase 3` Postgres → `Phase 3` Handling
  DI) を独立にレビュー可能な単位に分割できた
- **Ralph Loop 中は "小さく確実に" を厳守**: iter 38-58 は 1 コミット = 1 ロジック
  変更で、pre-commit を都度パスさせた。テストのないリファクタリングは避け、
  Postgres 変更もローカルビルドが通ることを確認してから push

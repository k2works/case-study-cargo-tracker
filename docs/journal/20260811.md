#### ハマったポイント 1: H2 の制約名が自動生成だった

X1 で `invoice.booking_id` の UNIQUE を落とす必要がありましたが、**V1 が制約に名前を付けずに書いていた**ため、PostgreSQL は `invoice_booking_id_key`、H2 は `CONSTRAINT_74D6` と別の名前を付けます。名前を書き写せば片方でだけ落ちる（ADR-003 が禁じた「方言の漏れ」）。

**名前ではなく形で探して落とす**ことにしました（「invoice の UNIQUE 制約のうち、列が `booking_id` 1 つだけのもの」）。PostgreSQL は `DO $$` ブロック、H2 は `EXECUTE IMMEDIATE` で書き、`h2/` に初めてファイルが増えました。**スキーマが分岐したのではなく、名前の付き方が違うだけ**であることを両方のファイルに書いています。

H2 側の実挙動は、一時的なテストで `INFORMATION_SCHEMA` を読んで確かめました（`CONSTRAINT_74D` = invoice_number、`CONSTRAINT_74D6` = booking_id）。

#### ハマったポイント 2: 自分の catch が自分のデバッグを止めた

タスク 3 の画面テスト 9 本が**すべて 404「予約が見つかりません」で落ちました**。予約は SQL で直接入れており、詳細画面の GET は通っている。原因が分からず、デバッグ出力を仕込む往復をしました。

原因は `findCargo` の catch でした。

```java
try {
    return cargoRepository.findById(new BookingId(UUID.fromString(id)));
} catch (IllegalArgumentException e) {
    return Optional.empty();   // 復元が投げた例外もここへ来る
}
```

テストデータの追跡番号が `TRK-CXL-0001` で形式違反（`TRK-YYYYMMDD-NNNN` が正）であり、集約の復元が `IllegalArgumentException` を投げていました。**それが「見つかりません」に化けて、ログにも何も残らない。** catch を UUID の解析だけに狭めた瞬間に本当の例外が出て、1 分で直りました。

**「形式の違う ID を例外にしない」という判断は正しく、`try` の範囲だけが誤っていた。** メモリに記録しました。

#### ハマったポイント 3: Cargo が 500 行を超えた

`canCancelImmediately` と `canRequestCancel` と `approveCancel` を足したら 523 行になりました。コメントを削るのではなく、**キャンセル可否の判定を `BookingStatus` に寄せました**。調べると**クエリサービスは元から遷移表を直接引いており、判断が 2 か所にあった**。1 か所に置いたことで 500 行ちょうどに収まりました。

`SecurityConfig.filterChain` が 150 行を超えたときも同じで、認可規則を `cancellationRules` に切り出しました。

#### ハマったポイント 4: 折りたたみが E2E で開かなかった

申請フォームを Bootstrap の `collapse` に入れたら、E2E で `#cancelReason` が見つからずに落ちました。**Bootstrap の JavaScript に依存する**うえ、そもそも**「申請できること」自体が画面から読めない**。常時表示のカードに変えました。

### 2. `closing-iteration` — IT15 のクローズ

レビューは 5 視点を**逐次に**実施しました（Agent ツールは利用者の指示が無い限り使わない）。

#### 最大の発見: ADR に書いた規則を、コードの半分が守っていなかった

既存の購読先サービスの伝播を確認したところ、5 本が `REQUIRES_NEW` を宣言していました。**自分が足した `ChargeCancellationFeeCommandService` は素の `@Transactional`** です。ADR-009 の規則 2 は「購読側は新しいトランザクションで書く」と明記しています。

直すついでに検査（`EventualConsistencyPropagationTest`）を書いたところ、**既存に 5 本の違反が出ました**。

```text
BookingExceptionNotificationHandler → RecordExceptionNotificationCommandService
BookingStatusNotificationHandler    → RecordStatusNotificationCommandService
BookingVoyageRescheduledEventHandler → SyncItineraryScheduleCommandService
TrackingCustomsEventHandler         → RaiseTrackingExceptionCommandService
TrackingMisrouteEventHandler        → RaiseTrackingExceptionCommandService
TrackingRoutedEventHandler          → RerouteTrackingCommandService
```

**5 本が守っていて 5 本が守っていない。** ADR を書いた後も、半分は守られないまま増え続けていました。テストが緑なのは Spring の内部挙動に依存しているためで、**依存していること自体が危うい**。呼び出し元がイベント購読とトランザクションを持たない画面だけであることを確認したうえで、6 本すべてに宣言を足しました。

**「ADR に書いた」と「守られている」の間に何も無かった。** ふりかえりの Try T1 は「ADR に規則を書いたら**その場で検査を書く**。書けないなら『守り手: 守らない』と明記する」にしました。

#### 2 つ目: C4 と同じ型を、C4 を返済した同じ IT で作った

**返済したことと、次に書くときに思い出すことは別**でした。

## 学び

- **`try` の範囲は「握り潰してよい失敗」だけに限る。** 症状が「全部同じエラーコードで落ちる」なら、まず catch の広さを疑う
- **ADR に規則を書いただけでは守られない。** 検査に落とすまでが 1 セット。落とせないなら「守らない」と書くほうが誠実
- **名簿方式の検査は「名簿に無い入力」を必ずテストする。** 素通りさせると、いちばん検査が要る新しいものが漏れる
- **落とした負債は育つことがある。** 0-5（テストヘルパー）は 5 → 7 クラス、0-9（ビューの引数）は 1 → 2 クラスに増えた。「落とす順序」を見積もりの大きさだけで決めない
- **制約に名前を付けずに書くと、後で落とせなくなる。** DBMS が自動命名するため、方言をまたいで消せない
- **折りたたみは「あること」を隠す。** 申請できること自体が読めなくなる

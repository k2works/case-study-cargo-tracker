## 学び

- **上流ドキュメントの欠落は「PARTIAL」評価で受け止め、計画側に補完タスク化して吸収する** — validating-iteration-plan で NG を出しても、上流ドキュメントを即座に補完するとスコープが肥大化する。「計画側で Day 1 に補完 → 以降タスクが参照」の順序を明示することで、依存関係を可視化しつつ計画完了状態を維持できる
- **ID 型・テーブル名・URL の揺れは「既存を正とする」原則を機械的に適用**: `trackingId` vs `trackingNumber`、`handling_events` vs `handling_activity`、`CargoStatus` vs `TransportStatus` のような命名衝突は、AI が新規に案を出す時ほど発生しやすい。ui_design.md / data-model.md / domain-model.md の既存名を検索して先に確認する規律が必要
- **T-03 (Domain no IO) を守りながら bcrypt を扱う型分離**: `ConfirmationCodeGenerator.generate` は純粋関数、`bcryptHash` / `randomDigits` は Application 層でラップ、と分離することで H-04 SEC-04 と T-03 を両立できる。同じパターンが JWT 署名・rate-limit などにも適用可能
- **設計セクションのサイズは「IT4 と同レベル」が実務的な最低ライン** — 130 行 (骨格のみ) では実装者が判断できず、910 行 (Haskell 型 + シーケンス + トランザクション + テスト戦略まで) で初めて Ralph Loop が自律実行できる。以降の IT 計画も iteration_plan-4.md/5.md 水準を基準とする
- **`gh project item-add` の stdout が silent なので `--format json` で確認する**: 通常の invoke は成功しても出力なし。PVTI ID を確認するには `--format json | python3 -c "..."` パターンが必要
- **Ralph Loop 適性分類 (AI 完結可 / Docker / Browser / 人手) を計画段階でテーブル化することが T4-01 の実装**: IT4 では計画時に分類せず終盤で「外部依存 1 SP が予期せず繰越」が発生した。IT5 では全 9 タスクグループに Ralph 適性列を追加し、Loop 対象範囲を事前明示

## 学び

- **上流ドキュメントの欠落は「PARTIAL」評価で受け止め、計画側に補完タスク化して吸収する** — validating-iteration-plan で NG を出しても、上流ドキュメントを即座に補完するとスコープが肥大化する。「計画側で Day 1 に補完 → 以降タスクが参照」の順序を明示することで、依存関係を可視化しつつ計画完了状態を維持できる
- **ID 型・テーブル名・URL の揺れは「既存を正とする」原則を機械的に適用**: `trackingId` vs `trackingNumber`、`handling_events` vs `handling_activity`、`CargoStatus` vs `TransportStatus` のような命名衝突は、AI が新規に案を出す時ほど発生しやすい。ui_design.md / data-model.md / domain-model.md の既存名を検索して先に確認する規律が必要
- **T-03 (Domain no IO) を守りながら bcrypt を扱う型分離**: `ConfirmationCodeGenerator.generate` は純粋関数、`bcryptHash` / `randomDigits` は Application 層でラップ、と分離することで H-04 SEC-04 と T-03 を両立できる。同じパターンが JWT 署名・rate-limit などにも適用可能
- **設計セクションのサイズは「IT4 と同レベル」が実務的な最低ライン** — 130 行 (骨格のみ) では実装者が判断できず、910 行 (Haskell 型 + シーケンス + トランザクション + テスト戦略まで) で初めて Ralph Loop が自律実行できる。以降の IT 計画も iteration_plan-4.md/5.md 水準を基準とする
- **`gh project item-add` の stdout が silent なので `--format json` で確認する**: 通常の invoke は成功しても出力なし。PVTI ID を確認するには `--format json | python3 -c "..."` パターンが必要
- **Ralph Loop 適性分類 (AI 完結可 / Docker / Browser / 人手) を計画段階でテーブル化することが T4-01 の実装**: IT4 では計画時に分類せず終盤で「外部依存 1 SP が予期せず繰越」が発生した。IT5 では全 9 タスクグループに Ralph 適性列を追加し、Loop 対象範囲を事前明示

## 追加の学び

- **Cross-BC helper (Text-based DTO) パターンは Rule 4 の実用解**: BC 内 Domain 型を外に漏らさず `Maybe Text` / `Either DomainError ()` で境界を切ると Interfaces 層は Domain 型を知らなくて済む。3 種 (`queryTrackingNumberText` / `verifyAndConsume` / `queryHandlingHistoryText`) 揃えば「新 BC 追加時のテンプレ」として使える。
- **サーバ側 migration 未適用は E2E に 500 で現れる**: 開発 DB (cargo_tracker_dev) に自動 apply する仕組みがないと、IT の切り替わりで確実に踏む。globalSetup で `dbmate up` を叩く / IT 開始 checklist に `dbmate status` を加える (T5-16) の両輪が必要。
- **E2E test isolation は「globalSetup + TRUNCATE + workers=1」の三点セット**: workers>1 化する時は worker ID を schema 名に混ぜる必要あり。今は fullyParallel:false + workers:1 なので TRUNCATE 一発で足りる。
- **`e2e-schema-setup.sh` の URL 結合子バグ**: `DATABASE_URL=postgres://user:pass@host/db?sslmode=disable` に `?options=...` を追記すると Postgres driver が「wrong sslmode value」で落ちる。既存 `?` がある場合は `&` に切替える条件分岐が必要。
- **Servant `Headers '[...]` は型で強制できる Set-Cookie の砦**: 発行漏れをコンパイラが弾いてくれる。Session Cookie を型に載せると「発行忘れ」バグが構造的にゼロになる。
- **`user_id BIGINT` ↔ `UserId Text` の橋渡しは INSERT-SELECT-JOIN で吸収可能**: `INSERT INTO session (...) SELECT ?, u.id, ?, ? FROM users u WHERE u.username = ?` はドメイン層に BIGINT を露出させずに INSERT できる postgres パターン。
- **Ralph Loop end-of-life + 手動集中実装フェーズの 2 段運用は 40 SP/日を実現する**: IT4 の 19 SP から 2 倍達成した要因は「Ralph で消化可能な範囲」と「手動で走らせるべき集中実装」を切り分けたこと。次回以降も本パターンを維持する。
- **マルチパースペクティブレビューは IT 完了直後が最も効く**: 記憶が新鮮で修正の判断が早い。1 日遅らせると priority 判定に迷いが出る。

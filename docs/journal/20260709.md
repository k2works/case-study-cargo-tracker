## 学び

- **大きな構造変更は部分 Edit の連鎖より Write で全面書き直す方が安全**。Markdown の見出し/表を跨ぐ編集は Edit がずれて重複・欠落を生みやすい。編集後は `grep -nE '^#{2,4} '` で見出し構造を必ず検証する。
- **Codex はサンドボックス内で `dotnet test` を実行できない**（ソケット bind 拒否）。実装指示は「ビルドまで確認、テストはテックリードが実行」と明示し、TDD の Red 確認と全テスト緑の担保はテックリード側で行う運用にする。
- **アーキ根幹のリファクタ（M1 の AmbientTransaction）は実装が緑でも ADR を伴わせる**。3 エージェントが独立に「ADR 未起票」を指摘した。ADR-0002 の `IUnitOfWork.Transaction` 削除のような破壊的決定は、記録がないと将来同じ議論を繰り返す。
- **アンビエント方式は「依存を署名から消す」代償に「暗黙のスコープ契約」を生む**。scoped 前提・ネスト非対応・非並行前提はテストで固定し ADR に前提として明記しないと、テストが通っても本番で静かに壊れる。
- **設計ドキュメント（domain-model）のドリフトは IT ごとに繰り返す**（IT1 の住所、IT2 の CargoType「共通」矛盾で 2 件目）。イテレーション完了 DoD に domain-model 同期チェックを組み込む価値がある。
- **「見積には有るのに予約に無い」非対称は業務視点とコード視点の両方から出る**。過去日ガードが Estimate.Create にだけ追加され Booking に無い件は、user-rep（業務ミス）と programmer（スコープ外発見）が独立に指摘した。横展開漏れは複数視点で捕まる。
- **応答テキスト内に tool 実行結果を捏造しない**。mkdocs「破損」を実際には走っていない Bash 出力として書いてしまい、後で実ファイル確認で誤りに気づいた。事実は必ず tool で確認してから述べる。

### 4. PlantUML 修正

ユーザーから「ドメインモデルの PlantUML が壊れている」と指摘。原因は:

- `enum EstimateStatus { Created; Expired }` のセミコロン区切り → 改行区切りに
- `voyageNumbers : [VoyageNumber]` の角括弧型表記 → `List<VoyageNumber>` に

## 学び

- **計画書作成 → 整合性検証は 1 セット**: 初版を書いた直後の高揚感のままコミットすると、BC 名・PK 規約のような構造的負債を抱え込む。今日は `validating-iteration-plan` の 8 ステップ検証で 14 件を 1 ターンで検知できた。Explore エージェントの並列実行が効果的
- **「新規追加」と「設計済の実装」は別物**: 計画書で「新規 BC `Pricing`」と書く前に `domain-model.md` を必ず grep する。今回は `Estimation Context` が既に確定済だったため、書き直しで済んだが、もし実装まで進めば BC リネームの大手術になっていた
- **PlantUML の enum / list 型表記は要注意**: `{ Created; Expired }` セミコロン区切り、`[VoyageNumber]` 角括弧、`Hazardous(X)` 関数風 — どれもレンダラによって解釈が割れる。改行区切り / `List<T>` / note 補足 が最も保守的
- **既存スキーマを必ず grep してから新規マイグレーションを計画する**: `cargo.booking_status` は IT1 で既に投入済だったのに「006_add_status_to_cargo.sql で追加」と書いていた。`grep -in "status" apps/cargo-tracker/db/migrations/*` 一発で防げる
- **dbmate と連番マイグレーションは異なる**: 計画書では論理順序 (007/008/...) を使ってよいが、実ファイル名は dbmate の date prefix 形式 (`YYYYMMDDHHMMSS_*.sql`) に従う。両者の対応を計画書に明記しておかないと、開発時に混乱する
- **GitHub Issue の状態は計画書と乖離する**: IT1 完了後に Issue クローズを忘れると、Milestone の Open 件数が虚偽の値を返す。`/syncing-github-project --sync` を IT 切り替え時に必ず流す運用を memory `feedback_ralph-loop-iteration.md` と並べて確立すべき
- **AskUserQuestion を使うタイミング**: GitHub Issue の 5 件クローズ + 11 件新規作成のような shared state を変える操作は、フル同期 / 部分同期 / スキップを選択肢化してから実行する。CLAUDE.md の「確認必須」運用と整合

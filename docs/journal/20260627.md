## 学び

- **計画書作成 → 整合性検証は 1 セット**: 初版を書いた直後の高揚感のままコミットすると、BC 名・PK 規約のような構造的負債を抱え込む。今日は `validating-iteration-plan` の 8 ステップ検証で 14 件を 1 ターンで検知できた。Explore エージェントの並列実行が効果的
- **「新規追加」と「設計済の実装」は別物**: 計画書で「新規 BC `Pricing`」と書く前に `domain-model.md` を必ず grep する。今回は `Estimation Context` が既に確定済だったため、書き直しで済んだが、もし実装まで進めば BC リネームの大手術になっていた
- **PlantUML の enum / list 型表記は要注意**: `{ Created; Expired }` セミコロン区切り、`[VoyageNumber]` 角括弧、`Hazardous(X)` 関数風 — どれもレンダラによって解釈が割れる。改行区切り / `List<T>` / note 補足 が最も保守的
- **既存スキーマを必ず grep してから新規マイグレーションを計画する**: `cargo.booking_status` は IT1 で既に投入済だったのに「006_add_status_to_cargo.sql で追加」と書いていた。`grep -in "status" apps/cargo-tracker/db/migrations/*` 一発で防げる
- **dbmate と連番マイグレーションは異なる**: 計画書では論理順序 (007/008/...) を使ってよいが、実ファイル名は dbmate の date prefix 形式 (`YYYYMMDDHHMMSS_*.sql`) に従う。両者の対応を計画書に明記しておかないと、開発時に混乱する
- **GitHub Issue の状態は計画書と乖離する**: IT1 完了後に Issue クローズを忘れると、Milestone の Open 件数が虚偽の値を返す。`/syncing-github-project --sync` を IT 切り替え時に必ず流す運用を memory `feedback_ralph-loop-iteration.md` と並べて確立すべき
- **AskUserQuestion を使うタイミング**: GitHub Issue の 5 件クローズ + 11 件新規作成のような shared state を変える操作は、フル同期 / 部分同期 / スキップを選択肢化してから実行する。CLAUDE.md の「確認必須」運用と整合

## 追加の学び (午後セッション)

- **Ralph Loop 21 反復で 1 日 1 IT 完結の再現性**: IT1 (20 SP) → IT2 (18 SP) いずれも 1 日完結。AI 単独で消化可能な範囲 (Domain 設計 + Application + Postgres + HTTP + テスト) を 1 反復 = 1 Try or 1 ストーリー層に圧縮するパターンが固定化
- **既存テストフェイクへのポート追加スタブはサクッと awk で**: Repository ポート拡張時、12 箇所の既存テストフェイクに `findAll* = pure []` を追加する作業を `awk '/, updateBooking = / {print; print "      , findAllCargos = pure []"; next} 1'` で機械化したが、Haskell の `do` ブロック直後にレコードフィールドを挟むと **layout 規則違反** で複数ファイル壊れた。手動で 4 箇所修正する羽目に。次回は record の閉じ `}` の直前に追加する `awk` パターンに統一する
- **ghcid hot-reload が Lucid View 部に効かない場合がある**: `stack ghci :main` モードでは複数モジュール変更時に再ロードがスキップされることがある。確実な動作確認には `stack build && stack exec` で別プロセス再起動が必要
- **postgresql-simple の `(:.)` 演算子は 7-tuple 限界の救済策**: 14 列 INSERT を 7-tuple × 2 で結合できる。`Database.PostgreSQL.Simple.Types` から import
- **macOS BSD awk の `match($0, regex, arr)` は通らない**: T-10 check-coverage.sh で踏んだ罠。sed `-n '/pattern/p' | grep -oE` への書き直しで安定
- **htmx `hx-trigger="keyup changed"` は `page.fill()` で発火しない**: Playwright で htmx 検索をテストする場合は `page.keyboard.type()` を使う必要がある。E2E US04 で踏んだ罠
- **登録直後の Cargo が Draft 状態であることが内部デモブロッカー**: IT1 設計時点での `Draft → submitBooking → Submitted` という二段階遷移が IT2 で表面化。`mkCargo` で初期状態を `Submitted` にするか、`SubmitBookingCommand` の UI を IT3 で追加するかは要設計判断
- **arch-check Rule 4 ALLOWLIST の単調増加リスク**: 「新規違反のみ fail」運用は安全だが ALLOWLIST が放置されると形骸化する。テスター指摘 (M-12) の「失効期限を frontmatter で付与」は IT3 で導入検討
- **`xp-technical-writer` がベロシティ表記の 3 ドキュメント間不一致を発見**: 完了報告書・ふりかえり・release_plan で同じ 18 SP を 100% / 180% / 180% と書き分けていた。ドキュメント間 cross-check は人間レビュー / AI レビュー両方で必須

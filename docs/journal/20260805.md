# 2026-08-05 開発ジャーナル

IT10 のクローズ、IT11 の計画・開発・クローズ、IT12 の計画・開発を 1 日で通した。
**v1.0.0 の業務フローが端から端まで開通**し（予約 → 経路 → 追跡番号 → 荷役 → 引取）、
そのフローが乱れたときの処理（遅延例外）まで入った。
道中で最も学びが多かったのは、**返済した直後に同じ穴を新しい入口で開けていた**ことと、
**E2E が 2 度、実装では見えない欠陥を捕まえた**ことである。

## ハイライト

- **業務フローが端から端まで繋がった**（IT11）。IT10 までは「荷役は記録できるが
  荷主のタイムラインに出ない」状態で、機能はあるのに業務が回らなかった
- **3 イテレーション未解決だった間欠失敗の正体が判明した**——
  **アプリ以外が応答していた**（本文が `Proxy key is incorrect`）。
  診断は IT9 から出ていたのに「(不明)」という表記が異常の名前になっていなかった
- **7 イテレーション未着手だった規約 12 を起票**し、続けて**規約 13**（ADR の
  再検討条件を機械が数える）まで入れた。「余力があれば」で先送りしない規律が効いた
- **E2E が実行環境の欠陥を 2 件、UI の欠陥を 1 件捕まえた**。いずれも
  HTTP 統合テストでは原理的に見えない形だった
- **ADR-0014 で「引取が永久にできない実装」を作る前に避けられた**。
  IT10 の P5（機能はあるが業務が回らない）と同じ形を、**作る前に**止めたのは初めて

## Skill 実行の時系列

IT5 は「3 回目の未実施にする前に決める」という正しい判断をしたのに、
**書き写された DoD が正典に追随せず**同じことが IT8-IT10 で繰り返された。
IT9 は Problem に挙げ、IT10 は Try を立てたが、どちらも誤った前提の上での改善だった。

`ADR-0013` で品質ゲートの正典を `test_strategy.md` 6.4 に一本化した。

| 成果物 | 内容 |
| :--- | :--- |
| `docs/adr/ADR-0013-...md` | 品質ゲートの正典はテスト戦略とする |
| `docs/review/IT10実装_review_20260805.md` | 高 9・中 16・低 9（高 7 件・中 3 件を返済） |

もう 1 つ重かったのは、**ADR-0012 の中心的主張が書いた当の IT で成立していなかった**
ことである。Handling → Tracking の書き込みは集約を読んで捨て、列単位のポートを

### 2. `opening-iteration`（IT11）— E2E 基盤の有無を取り違えた

計画の初稿に「E2E 基盤がまだない」と書いたが、**TS05b で導入済み**だった
（`playwright.config.js`・`e2e/booking.spec.js`・CI の `e2e` ジョブ）。
`find` で `tmp/` 配下の別リポジトリだけを見て判断したのが原因。
シナリオ③を IT11 に組み込む形へ修正した。

検証（`validating-iteration-plan` / `validating-design`）で設計の穴が 4 件出た。

- `domain-model.md` の `HandlingActivity` に**荷受人確認の属性が無い**
- `ui_design.md` の追跡詳細に**更新フォームが無い**
- 荷役種別の名前が正典どうしで食い違う（`CUSTOMS_CLEARANCE` / `CUSTOMS`）
- `data-model.md` の「`customs_declaration` は US16 まで作らない」の扱い

### 3. `orchestrating-development`（IT11）— 通関のゲートに通す者がいない

ADR-0014 を Day 1 に起票した。設計は通関の状態を**税関システムの ACL** から
受ける形だが、その TS07 は ADR-0007 で延期中である。
つまり `customs_declaration` を作ってゲートにすると、**CLEARED にできる者が
誰もいない**——引取が永久にできない。IT10 の P5 と同じ形になるところだった。

通関済は `CUSTOMS` 種別の荷役記録で表すことにした。現場で通関書類を受け取るのは
荷役の側であり、「通関が終わった」ことを最初に知る立場にある。

あわせて ADR-0011・ADR-0012 の再検討条件（`composition/acl/` の総数）を
**「単一 BC へ向かう書き込みアダプタ数」**へ置き換えた。総数は
「連携が増えた」と「`Cargo` がハブ化している」という異なる 2 つの事実を潰していた。

#### 間欠失敗の正体

テスト実行中に 503 が再現し、**本文が `Proxy key is incorrect`** だった——
我々のアプリが返す文字列ではない。**アプリ以外が応答していた**。

テストは `localhost` へ繋ぐが、`localhost` は環境によって `::1` を先に引く。
サーバは IPv4 のワイルドカードに束縛するため、同じ番号を握る別プロセスがいると
そちらへ届く経路があった。接続先を `127.0.0.1` に固定した。

診断は IT9 から出ていた（「処理したインスタンス: (不明)」）。
**出ていたのに 3 イテレーション誰も読み取れなかった**——
「(不明)」が異常の名前になっていなかったためである。現在は
「アプリ以外が応答しました」と名指す。

#### E2E が実行環境の欠陥を 2 件暴いた

シナリオ③（荷役 → 追跡反映）を書いたところ、**実装ではなく実行環境**が落ちた。

1. 開発シードの追跡番号に**対応する貨物が無く**、荷役の登録が必ず失敗した
2. シードが主キーを直書きしており、`GENERATED BY DEFAULT AS IDENTITY` は
   明示した値で採番列を進めないため、**利用者が予約を登録した瞬間に主キー衝突**で
   失敗した（E2E の予約シナリオが 4 本まとめて落ちて分かった）

どちらも HTTP 統合テストでは現れない——毎回まっさらな DB を使うため、
**シードと利用者の操作が同じ採番列を奪い合う形が存在しない**。

### 4. `closing-iteration`（IT11）— 4 視点が同じ箇所を指した

5 視点のレビューで高 11・中 17・低 8。**高は全件返済した**。

複数の視点が独立に同じ箇所を指した 4 件は、いずれも実際の欠陥だった。

| 指摘 | 何が起きていたか |
| :--- | :--- |
| 手動更新の場所が無検証 | **同じ IT で荷役登録に入れたマスタ照合が、同じ IT で新設した画面に無かった** |
| 荷主の画面に `ONBOARD_CARRIER` | 翻訳表の既定が `case other => other`（素通し）だった |
| 時刻の逆行が素通り | 画面は `T` 区切り 16 文字、DB は空白区切り 19 文字。辞書順で比べると**同日は必ず「前ではない」** |
| ロック外で読んだ値で判定 | 状態の巻き戻しは守られるのに時刻だけ守られない非対称 |

時刻の逆行が隠れていた理由は明確で、**`updateManually` にユニットテストが
1 件も無かった**。155 行の不変条件が HTTP 経由の 2 本でしか確かめられておらず、
`isBefore` を丸ごと `false` にしても緑だった。安全装置の空振りは
IT9（行ロック）・IT10（UNIQUE）に続き **3 イテレーション連続**である。

tester の指摘 1 件（履歴が古い順に返る）は**実装を追うと成立しなかった**。
反転で新しい順に戻っている。ただし並び順に依存する設計であること自体は
指摘のとおりで、`MAX` で取る形へ変えた。

### 5. `opening-iteration` / `orchestrating-development`（IT12）

TS18（IT11 レビューの返済）を先に置いた。**M10（誤登録した荷役を戻せない）は
US19 の設計判断と土俵が同じ**であり、別々に決めると食い違うためである。

US19（遅延例外）では、**発生前の状態をカラムに退避**して解決で戻す形にした。
履歴から再導出すると、ユニットテストが緑でもクロスリクエストで誤復帰する——
IT10 で記録した教訓が直接あたる。

**対応の記録と解決を別の操作に分けた**のは計画からの変更である。
新しい到着予定が決まっても遅延そのものが解消したとは限らない。

規約 13（単一 BC へ向かう書き込みアダプタ数）を実装した。ADR-0014 の診断は
「条件が代理指標として機能せず、到達に気付かなかった」だったが、
**置き換えた新条件も散文にしかなく、やはり誰も数えていなかった**。
現時点はちょうど 3 本で、1 本足せば発火する位置にある。

#### E2E が UI の欠陥を捕まえた

追跡詳細には「状態の更新」と「例外の記録」の 2 つのフォームがあり、
どちらも場所を選ばせる。**`id="location"` が 2 つ**あり、自動操作は最初の 1 つを
掴んでいた。結果、例外の記録が場所を空のまま送られて失敗していた。

HTTP テストはフォームを組み立てず直接 POST するため、**この形は原理的に見えない**。
同じ形を HTTP テストでも固定した（`id` の出現回数を数える）——
E2E だけに頼ると、落ちたときの原因の切り分けが遅くなる。

## 学び

- **「直した」という記憶は、次に書くコードには効かない。** 返済した内容は
  「この IT で塞いだ穴」の一覧として持ち歩き、**新しい入口を作るたびに照合する**。
  IT11 は荷役登録にマスタ照合を入れた直後、同じ IT で新設した画面に同じ穴を開けた
- **不変条件を書いたら、その IT のうちにユニットテストを書く。** HTTP 経由だけで
  確かめると、材料の**書式・順序といった内側の前提**が検証されない。
  安全装置の空振り 3 連続はいずれも「外側からしか見ていない」形だった
- **既定値が「素通し」の変換表は、値が増えた瞬間に漏れる。**
  `case other => other` / `case _ => value` は表示・翻訳・符号化のどこにでもある
- **文字列の大小比較は、2 値の書式が同じときにだけ意味を持つ。**
  「ISO 8601 は辞書順＝時刻順」は正しいが、`T` 区切りと空白区切りを混ぜた瞬間に崩れる
- **診断は「出す」だけでなく「異常の名前を与える」ところまでやる。**
  「(不明)」は 3 イテレーション読み取られなかったが、
  「アプリ以外が応答しました」は 1 度で伝わった
- **ADR で条件を置き換えたら、置き換えられる側の文書を同じコミットで触る。**
  「置き換えた」と書くだけでは、読む人は古い側にたどり着く
- **再検討条件は機械が数える形にする。** 散文の条件は ADR-0011・0012・0014 と
  3 度とも見落とされた。測れる条件へ書き換えたなら、**測る道具まで含めて 1 セット**
- **E2E は「実装の別レイヤ」ではなく「実行形態の別レイヤ」を見る。**
  今回捕まえたのはシードと採番列の衝突・DOM の id 重複であり、
  どちらも同一 JVM 内の HTTP テストでは現れない
- **主キーを直書きしたシードは、利用者の最初の操作を壊す。**
  `GENERATED BY DEFAULT AS IDENTITY` は明示した値で採番列を進めない
- **`from` / `to` は Flix の予約語**（`query` / `end` / `run` / `as` / `handler` に続く）

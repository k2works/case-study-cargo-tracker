## 学び

- **「単体テストは通るが配線されていない」は最も検出しにくい欠陥**。CheckOverdueService は tree-wide grep で自テスト以外の参照ゼロ＝実質デッドコードだった。DoD に「駆動元（HTTP ルート/バッチ/イベント）と HTTP/E2E 実証」を含めないと、受入基準のチェックは埋まっても業務上は未達になる。IT4-8 で 4 IT 連続、形を変えて再発した最頻の落とし穴。
- **状態変更系は必ず HTTP/E2E で 1:1 実証する（IT7 Try#1）**。domain 単体だけで満足すると、ルート未登録・権限漏れ・通知先誤りといった配線バグを取り逃す。
- **冪等に見えて不整合な中間状態が最も危険**（IT7 charge_id）。「新規採番＋upsert は status のみ更新」で、戻り値の ID が DB に存在せず redirect 先が 404。冪等化するなら既存 ID の再利用を明示的にテストで固定する。
- **E2E はテスト側の想定ミスも検出する**（IT7 割引デモ）。seed 実値 15% に対しテスト期待値 10% で失敗したが、実装は正しかった。テストの前提（seed 値）と期待値を一致させる。
- **文字列業務キーは長さ制約を最初に確認する**。`INV-` + UUID simple(32桁) = 36 文字で VARCHAR(30) 超過。生成時に制約を意識して 24 桁に短縮。
- **transitive advisory は「本番露出の有無」で判断する**。cargo audit の 3 件（rsa/tokio-tar/rustls-pemfile）はいずれも dev-dependency（testcontainers）or 未使用ドライバ（sqlx-mysql）経由で本番非露出。根拠コメント付きで ignore するのが正攻法。sqlx の `default-features = false` は `migrate!` マクロ（macros 機能）が壊れるので不可。
- **品質ゲートは CI と同じ `+stable` ツールチェーンで検証する**。ローカル stable が CI（`@stable`）より古いと新 clippy lint がすり抜ける（IT6 で実際に CI だけ赤になった前例）。
- **BC 独立は「逆方向の連携」でこそ試される**。Billing→Booking の settle 連動を domain 直接依存でなく `BookingSettlementPort` ACL 経由にすることで、全 IT 中もっとも厳格な BC 独立を達成。ACL は入力方向だけでなく出力方向（他 BC の状態を変える）にも一貫適用する。

## 学び

- **状態機械は「遷移表」だけでなく「前提条件」も設計時に洗い出す**。TrackingStatus と BookingStatus を別 BC で二重管理した結果、RECEIVE 直後の CLAIM で両者が乖離する穴をレビューで初めて検出した。集約ごとに precondition をユニット spec で固定するのを設計 DoD にする（→ IT6 の T30）。
- **1 イベント → N ハンドラのコレオグラフィは「N 個の副作用を 1 テストで同時検証」する**。`handling_activity_registered` の 3 ハンドラのうち通知永続化だけテストが抜け、レビューで指摘された。ファンアウトは結線した数だけ結合テストを書く。
- **越境の二段書き込み（Booking コミット → Tracking 保存）は宙吊りを生む**。後段失敗で「発行済みだが追跡不可・回復不能」になる。冪等回復パス（保持済みキーで復元）を最初から用意する。将来は Outbox（ADR-0002 既定）。
- **プレースホルダは「実装済み US に残っていないか」を毎クローズで突合する**。ナビ導線を追加しても遷移先がプレースホルダなら受入基準の入口が実在しない。system spec が「到達先の中身」まで見ていないと見逃す。
- **SonarQube の新規コード違反は「パラメータ数 >7」「case に default なし」「無名 default export class」が定番**。集約の多フィールドは `**attributes` splat・引数はハッシュ集約・case は明示 else で先回りできる。
- **サブエージェントの 529 Overloaded 中断でも生成物は残ることがある**。ファイル存在を確認し、末尾の不正タグだけ手当てすれば再実行不要。
- **負債返済枠は「序盤の独立コミット枠」に置くと本当に消化できる**。IT4 で繰越した T22 を IT5 序盤で先着手し、繰越連鎖を断てた。「余力次第」を排除した効果が実証された。

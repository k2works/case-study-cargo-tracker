# 2026-07-22 開発ジャーナル

Rust 版 Cargo Tracker の開発を一気に前進させた 1 日。午前に IT2（航海スケジュール）をクローズし、午後は IT3（経路算出・選択）と IT4（予約連携・確定）を「開く→実装→レビュー→クローズ」まで通しで回した。さらに `opening-iteration` / `closing-iteration` スキルを新設し、イテレーションのライフサイクル運用そのものを標準化した。最後に IT1〜IT4 のデモ項目を Playwright E2E としてナビ経由に統一し、動く成果物を担保した。

## ハイライト

- **3 イテレーションを 1 日で消化** — IT2 クローズ、IT3・IT4 をフルサイクル（計画→整合性検証→TDD 実装→マルチパースペクティブレビュー→ふりかえり→完了報告→ドキュメント同期）で完了。
- **予約状態機械を Cargo 集約に実装（US06/US11/US13）** — `CargoRepository::save` を upsert 化して状態遷移を永続化し、BC 跨ぎの書き込み一貫性を確保。
- **イテレーション運用スキルを新設** — `opening-iteration` と `closing-iteration` を追加し、開始準備・締め作業の順序依存工程をチェックリスト化。
- **ADR を 3 本整備** — interface 層 DIP 回復（ADR-0003）、BC 跨ぎ書き込み一貫性（ADR-0004）、予約状態機械（ADR-0005）。設計判断を追跡可能に。
- **デモ項目の E2E をナビ経由に統一** — IT1〜IT3 のデモを Playwright で navbar/dashboard 導線経由に揃え、ナビゲーション整合性を担保。

## 学び

- **イテレーション運用は「開始」と「締め」の両端が抜けやすい** — 計画作成だけで着手し、着手前の整合性検証や締めのドキュメント同期を省くと手戻りになる。`opening-iteration` / `closing-iteration` として順序依存工程をスキル化することで、抜けを構造的に防げる。
- **BC 跨ぎの書き込み一貫性は ADR で明示する** — 予約状態機械が routing / booking の境界を跨ぐため、暗黙の一貫性ルールを ADR-0004 として起票。後から「なぜこの整合方針か」を追跡できるようにした。
- **SQL 絞り込みは段階的に返済する** — `VoyageRepository::search` はまず SQL 絞り込み化（Try #2）で正しさを確保し、相関副問い合わせの読みにくさは後日 CTE 化（Try #5）で返済。Try を分割することで各コミットの意図が明確になる。
- **デモ E2E はナビ経由に統一する** — 個別画面への直リンクではなく navbar/dashboard 導線を通した E2E にすることで、画面実装とナビゲーションの 4 点一致（ui_design→navbar→dashboard→test）を自動テストで担保できる（[[feedback_navigation-integrity-check]]）。
- **`save` の upsert 化で状態遷移を永続化** — エンティティの状態機械を実装しただけでは永続化されない。リポジトリの `save` を upsert 対応にして初めて遷移が保存される。ドメインとインフラの両輪を揃える。

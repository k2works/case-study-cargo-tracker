# 2026-09-12 IT14 の開発とクローズ

## この日やったこと

IT14（US01 輸送見積を作成する・US23 精算を処理する）の開発とクローズを通しました。
見積 → 予約 → 輸送 → 引取 → 発行 → 入金 → 精算済、という**業務の輪が初めて閉じました**。

## 判断の記録

### 受け入れテストは「書いてあった」が、1 つも回っていなかった

この IT でいちばん重い欠陥です。`請求の精算.feature`（9 シナリオ）と
`輸送見積の作成.feature`（6 シナリオ）を書き、計画の受入基準の表からも名指ししていました。
成功基準「デモ項目の受け入れテストがすべて緑」にもチェックが付く見込みでした。

**ステップ定義が 1 つもありませんでした。**

未定義のステップが赤を出さない設定だったので、スイートは緑のまま通ります。一覧の上では
「受け入れテストがある」ようにしか見えません。レビュー（tester 視点）がこれを指し、
「**書いたが未定義は最悪の形**」と書いてきました。同意します——無いより悪いのは、
あると思わせることです。

実際に回るようにしたら、**実欠陥が 3 件**出ました。

1. **候補の経由港が候補ごとに違わない。** 画面が `出発地 → 目的地` を繋いでいました。
   どの候補も同じ経路に見えるので、営業担当者は案を選び分けられません。正典の S13 は
   `JPTYO > SGSIN > USNYC` と**候補ごとに違う並び**を描いていました
2. **見積と異なる項目を画面が捨てていた。** サーバは応答に載せており、集約の検査も
   値オブジェクトの検査も緑でした。**画面だけが受け取って捨てていた**ので、
   「断らずに知らせる」という不変条件は、画面の手前で消えていました
3. **見積の貨物種別が素の `valueOf`** で、知らない値が 500 になっていました

3 件とも、層ごとの検査では出ません。**「回す」ことに価値があります。**

### 列も読み口も画面もあるのに、書き込みだけが無かった

`quoted_amount`（見積時の概算）は、

- マイグレーションに列があり
- `InvoiceRow` に項目があり
- `InvoiceView` に項目があり
- S61 が「見積時の概算 → 請求 → 差額」の分岐を持っていて
- 画面のテストまで緑でした（モックが値を返すので）

**`INSERT` 文だけが、その列を書いていませんでした。** さらに `InvoiceCalculation` が
`null` を固定で渡していました。つまり**差額行は本番で永久に出ません**。

IT13 で「記録と読み口は対で出す」という規律を立てたのですが、**読み口の側ばかり見ていました**。
記録の側——実際に書いているか——も同じ検査で通す必要があります。今回は
「予約の時点で概算を写す → 引取で請求書を作る → 差額を読む」を 1 本の IT で通しました。

### 「不変条件はこれが守る」と書いたメソッドが、本番から呼ばれていなかった

集約 `Quotation` の Javadoc に「不変条件 3（予約との食い違いは断らず項目名で知らせる）は
`diffAgainst` が守る」と書いていました。**`diffAgainst` は本番から一度も呼ばれていません。**
実際に守っているのは `application/QuotationDiff`（投影を読む）でした。

`hasCandidate()` はもっと悪く、Javadoc が「**期限に間に合う**候補があるか」なのに
実装は総数を見るだけで、テストは「1 件 → 真 / 0 件 → 偽」しか見ないので
**この食い違いを判別しません**。

どちらも削除しました。すると SpotBugs が「読み出されないフィールド」を 6 件出しました——
集約が 5 項目を復元していたのは、その 2 つのメソッドのためだけだったのです。
**読まない状態を復元すると、次の書き手が「ここから読める」と思って使います。**
残したのは見積番号だけ（同じ番号で二度作らせないための判断に使う）です。

### 集約の守りが、画面からは絶対に踏まれなかった

見積の入口が空文字を `null` に寄せていませんでした。画面は貨物種別を切り替えたとき
空文字を送るので、`HazardousDeclaration` が先に 422 を投げます。集約の
「危険物には危険物申告が必要です」は、**画面経由では一度も踏まれません**。

予約側の `CargoSpecificationAssembler` は、同じ罠を警告するコメントまで持っていました。
**入口ごとに扱いが違っていた**だけです。正規化を共有し、集約の守りを画面から踏む検査を
足しました。

### フルビルドが、前のコミットから赤のままだった

成功基準「`TZ=UTC` でモジュールを分けて `build` が緑」も、事実に反していました。
`:bookingms:build` と `:routingms:build` のカバレッジゲートが落ちており、
`Cargo#settle`（US23 の中核）は**分岐カバレッジ 0**でした。

モジュール単位の `test` は緑です。`build` を回すまで気づけません。IT12 で
「ローカルの品質ゲートは CI と同じコマンドで」と学んだのに、**IT を締める直前にしか
実行していませんでした**。

### 正典のほうが実装より細かかった（逆向きの修正）

これまでは「実装が正典を追い越したら正典を直す」形でしたが、今回は逆が 2 件ありました。

- **Processing Group は「書くテーブルの単位」ではなくパッケージ**です。Axon 5 に
  `@ProcessingGroup` が無いので、`booking-shipper-projection` /
  `booking-cargo-projection` / `booking-quotation-projection` は**同じグループ・
  同じ token・同じ退避先**に同居します。つまりリプレイと退避の単位は正典より粗い
- `invoice_notification` は実体だけが増え、ER にも表にも載っていませんでした

どちらも実装のほうが自然なので、正典を書き直しました。「正典が正しい」と決め打つと、
実装不能な正典が残ります（IT9 で 2 件踏んだのと同じ形です）。

### レビューが切れて届き、続きに中優先が 13 件入っていた

5 本のうち 2 本が長さ制限で切れました。続きを求めて**1 時間半後に返着**し、そこに
`hasCandidate()` の食い違い、危険物ガードが踏まれないこと、`invoice_notification` が
正典に無いことが入っていました。

IT6 で「40 分待つ」、IT13 で「切れていたら続きを求める」と学んだことが、両方効きました。
次は**最初から出力形を指定します**——「高と中だけ・1 件 1 行の表で」。

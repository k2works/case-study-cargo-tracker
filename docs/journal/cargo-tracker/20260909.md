# 2026-09-09 IT10 の開発とクローズ

## この日やったこと

IT10（US16 引取・US19 遅延例外）の開発フェーズとクローズを通しました。32 コミット。

## 判断の記録

### 契約に載せるか、BC の内部に置くか

引取のとき荷受人の確認（署名または確認コード）を記録する必要がありました。素直に考えると
契約イベント `HandlingActivityRegisteredEvent` に項目を足すことになります。

しかしこのイベントは**すでに本番の Event Store にある**ので、項目を足すとゴールデン JSON を
書き換えることになります（過去のイベントが読めなくなる）。加えて、正典のイベント表を見ると
購読側（trackingms・bookingms）の投影は荷受人名を必要としていません。

**handlingms 内部の `ConsigneeConfirmationRecordedEvent` を新設**しました。契約は形を変えず、
増やす側を自分の BC に置く。レビューでもこの判断は妥当とされ、「集約 → 投影 → クエリ → 画面まで
全層が繋がっている」と評価されました。

皮肉なことに、**同じ IT で trackingms 側は同じことに失敗しました**（下記）。

### 「記録で満たす」の落とし穴

US19 §3「荷主に通知が送信される」は、送信基盤がスコープ外なので「通知した事実を記録する」で
満たす設計です。私は `ExceptionShipperNotifiedEvent` を作り、計画の受入基準表に「記録で達成」と
書きました。

**購読する投影を書いていませんでした。** Event Store に積まれるだけで、誰の画面にも出ません。
「記録で満たす」と宣言した以上、記録が読めなければ満たしたことにならない——にもかかわらず、
集約の単体テストも、HTTP の統合テストも、画面のテストも、クラスタ E2E さえ緑でした。
どれも「送った」ことしか見ていなかったからです。

レビューの programmer と tester が**独立に同じ結論**に達して見つかりました。

### 引取の取り消しをどうするか

アーキテクトから「`CLAIM` を取り消すと追跡だけ戻り、予約の配送完了と精算が残る」と
指摘されました。補償イベントを設計するか、経路を塞ぐかの選択です。

**塞ぐことにしました。** 補償は購読側（bookingms・billingms）の受け口設計が要り、
`Cargo` には引取済から戻る遷移がありません。設計を急いで入れるより、断って IT11 で
設計する方が安全です。これは IT9 が「引取そのもの」に下したのと同じ判断で、
**検査できない段階でその経路を開けない**という一貫した態度です。

## 詰まったところ

### クラスタが IT9 のコードを動かしていた

US16 のクラスタ E2E で「荷受人の確認なしの引取が 201 で通る」のを見て、実装を疑いました。
集約のテストは緑、統合テストも緑。1 時間ほど実装を読み直しました。

原因は `gulp k8s:images` がイメージを作り直していなかったことです。`docker images` の
作成時刻を見たら 7 時間前でした。**「作り直した」という出力を信じたのが誤り**でした。

さらに、自分で書いた `for s in ...; docker build -t cargo-tracker/$s:latest` が
zsh の `:l` 修飾子で `cargo-tracker/trackingmsatest` に化け、壊れたタグを 3 つ作りました。

### フルビルドを 5 回失敗させた

すべて実行の仕方です。クラスタ E2E と同時に走らせて CPU を奪い合わせ、`--stop` で
自分のビルドを止め、コミットフックとビルドを 1 本に繋いで詰まらせ、build ディレクトリを
3 度壊しました。**実装は正しいのに、検証の段取りで 1 時間以上**を失いました。

## 学び

### タスク行にすると守れる

Try T3（US ごとにクラスタ E2E を回す）は IT8・IT9 と 2 回続けて守れませんでした。IT10 は
計画の段階で **T2e・T6e という独立したタスク行**にしたら守れました。「気をつける」では
2 回とも守れず、行にしたら 1 回で守れた。

しかもその T2e が実際に 2 件の欠陥を出しました。守った甲斐がありました。

### 正典と突き合わせる検査は、書き写しのずれを見つける

予約の状態の呼び名を正典と突き合わせる検査を足したら、**4 件のずれ**が出ました。
既存の検査は「画面と実装が揃っているか」しか見ていません。**両方に同じ誤りを書き写せば
緑のまま**です。

正典を読んで突き合わせる形にして初めて、書き写しの誤りが見えました。

### 自分で作った検査に自分が捕まる

Try T6 で「適用済みマイグレーションを編集していない」検査を作りました。クローズの最中、
その検査が**私が足した V008 を台帳に載せ忘れている**ことを捕まえました。

作った日のうちに役に立つとは思っていませんでした。

# 2026-09-09（続き） IT11 の開始準備と開発

IT11（US20 破損・紛失例外・US28 誤配検知と経路の再設計）の開始準備から開発フェーズまでを通しました。

## 判断の記録

### 「読める記録」にするために、読み口を先に決めた

US20 §3 は「管理職への escalation 通知が送信される」です。送信基盤はスコープ外なので、IT10 の US19 §3 と同じく「記録で満たす」形になります。

**IT10 はここで失敗しました。** `ExceptionShipperNotifiedEvent` を出したが購読する投影が無く、受入基準は実質未達のまま「記録で達成」と書いていました。今回は**読み口を先に決めてから**記録を作りました——例外一覧（S42）を `ROLE_ADMIN` に開き、緊急なのに知らせた記録が無い行に「未連絡」と出す。これで「知らせた」が画面から確かめられます。

副産物として、**リンクの出し分け**という問題が出ました。管理者は S41（追跡詳細）も S43（起票）も開けないので、一覧の行にリンクを出すと 403 に当たります。読む側と手を動かす側を、同じ画面の中で分けました。

### 不変条件を「例外を許す」ではなく「別の規則」として立てた

US28 §6 は「再設計後の到着予定が期限を超える場合、差分が明示される」です。`Cargo` 不変条件 5（旅程は経路仕様を満たす）は期限を満たさない旅程を断るので、そのままでは誤配の再設計ができません。

`isSatisfiedBy` に「誤配なら期限を見ない」という分岐を足すこともできました。**そうしなかったのは、その分岐が増え続けるからです。** 代わりに `isSatisfiedByRedesign` という別の述語を立て、「再設計は出発地も期限も見ない。目的地だけ引き継ぐ」という**別の規則**として書きました。緩めた側だけでなく、**通常の設計で超過候補が出ないこと**も赤で固定しています——緩める側だけを検査すると、緩みすぎに気づけません。

### `appender.append()` はその場で集約へ適用される

引き継ぎ枠 B（例外の対応中に届いた荷役を、解決後に適用する）で 30 分ほど詰まりました。

```java
appender.append(new TransportStatusUpdatedEvent(..., statusBeforeException, RESOLVED, ...));
applyDeferredHandlings(statusBeforeException, appender, now);  // ← null
```

`append` した瞬間に `@EventSourcingHandler` が走り、`statusBeforeException` が null に戻ります。**引数はその後に評価される**ので、戻り先が消えていました。控えてから append する形に直しました。同じ理由で、預かりの map を反復しながら `append` すると反復中に要素が消えます（`List.copyOf` してから回す）。

### 実環境でしか出ない欠陥が、また 2 件

**Try T8（US ごとにクラスタ E2E を 1 度回す）は、今回も割に合いました。**

1 件目は**投影が止まっていた**ことです。誤配の自動起票で例外の識別子を `"MIS-" + activityId`（40 文字）にしていましたが、`exception_id` は `VARCHAR(36)` でした。集約のテストは投影の桁を知らないので緑のまま通ります。そして**書けないイベントが 1 つあると Event Processor はそこで止まり、後続のイベントが全部届かなくなります**。画面には「反映されない」としか出ません。

導き方を UUID に収める形（`TrackingException#misrouteIdFor`）へ直し、列も前提に寄りかからない幅へ広げました。**列を広げたのは、止まった投影を動かすためでもあります**——1 件の不正なイベントが入ってしまうと、直したコードだけでは動き出しません。

2 件目は**例外一覧が荷主にも開いていた**ことです。`/api/v1/tracking/trackings/**` の広い宣言に吸われており、他社の貨物の例外まで読めました。管理者に開く変更をしていなければ、気づかないままでした。

### 通しでしか出ない脆さを 6 か所直した

クラスタ E2E は単独では全部緑なのに、通しでは毎回 1〜4 件落ちました。落ちるテストは毎回違いました。原因は 2 種類です。

- **航海一覧の表示上限**。作り直さないクラスタでは同じ区間の便が積み上がり、絞り込んでも登録した便が 1 ページ目に載りません。名指しで探すのをやめ、詳細を URL で開く形にしました。**画面に「航海番号で探す」手段が無い**ことが分かったので、IT12 の候補として残します——経路設計者も同じ壁に当たります
- **投影の反映待ちが「押した直後の 1 回だけ」**だった箇所が 5 つ。読み直しながら待つ形に寄せました

### この環境では 10 分を超えるビルドが完走しない

`./gradlew build` の通しが、4 回とも途中で消えました。バックグラウンドに回した時点で殺されているようです。モジュールを分けて 5 回に分割し、それぞれ 10 分以内で回しました。

加えて、**走っているビルドの隣で別の Gradle を起こして build ディレクトリを 3 度壊しました**。IT10 のふりかえりで Try T3（重い検証は 1 本ずつ）を立てたのに、同じことを繰り返しています。手順書には書きましたが、書いただけでは守れませんでした。

## 学び

- **読める記録にするには、読み口を先に決める。** 記録を作ってから読み口を探すと、たいてい忘れる
- **不変条件を緩めるときは、別の述語を立てる。** 分岐を足すと、次に緩めたい人も分岐を足す
- **`append` は即座に適用される。** 集約の状態を引数に渡すなら、append の前に控える
- **投影は 1 件の不正なイベントで止まる。** 直したコードだけでは動き出さないので、入ってしまったものを通す手当てが要る

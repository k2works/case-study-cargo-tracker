## なぜそうしたか / 判断（追記分）

- **割引ポリシー管理を独立 BC にした**: Billing の `DiscountPolicy`（請求時の割引率算出 VO）を可変な永続集約に変えると、テスト済みの請求フローに影響する。有効期間付き CRUD のライフサイクルは責務が異なるため別 BC に分離し、同名 `DiscountPolicy` の二義性を ADR-0010 で明文化した。
- **ダッシュボードの横断集約は shared に SummaryProvider（DIP）で置いた**: 各 BC のクエリを合成ルート（cmd）で束ねるアダプタを注入し、BC 独立性を壊さずに横断サマリーを実現。`make arch` 無改変で通過。
- **高優先度レビュー指摘はクローズ前に全対応、金銭ドメインの重い設計課題は明示保留**: 期限境界バグ・E2E 欠落・正典未反映は即対応。金額 int32 クランプ・入金確認の部分失敗リカバリはスキーマ/整合性設計変更を伴うため Release 1.0 後バックログへ理由付きで保留。

## どこで詰まったか（追記分）

- **新 BC が正典 ADR-0002・domain-model と矛盾したまま実装していた**: architect/technical-writer レビューで「ADR-0002（BC 数ドリフト防止）の趣旨に反する 8 個目の BC を無記録追加」と高指摘。data-model.md だけ更新して ADR・domain-model・plan 注5 が取り残されていた。クローズ時に ADR-0010 起票・正典 7→8・plan 注5 更新で是正（メモリ [[feedback_scope-change-canon-sync]] 記録）。
- **支払期限の DATE/TIMESTAMP 境界バグがテストの盲点で潜在**: `MarkOverdue`・`IsActiveOn` を timestamp 比較で実装し、テストが全て 00:00 だったため「期限当日に時刻付きで払うと超過扱い」の偽陰性が隠れていた。既知の再発パターン（メモリ記録済み）を実装時に適用できず、レビューが安全網になった。日付単位比較へ正規化 + 当日時刻付き境界テストを追加。
- **SonarQube 初回 FAIL（new_violations 2）**: 割引ポリシーハンドラのテンプレートパスリテラル 3 回重複。定数化で PASS（new_coverage 81.1%）。sed での定数置換が const 宣言自体まで自己参照に書き換えてしまい、手で修正した小さな罠。

## 次回どう活かすか（追記分）

- **スコープ外→内の変更は正典 3 点（ADR・domain-model・該当 plan）を実装と同一変更で更新**（メモリ化済み）。data-model だけ直して満足しない。
- **日付比較の実装直後に「当日時刻付き」テストを必須化**: メモリ [[feedback_date-vs-timestamp-deadline]] を実装時チェックに組み込む。
- **金銭ドメインの整合性課題は独立コミット枠で先着手**: int32→BIGINT・入金確認の冪等化を「余力次第」にせず次サイクル序盤に固定枠で。

# 2026-08-07 開発ジャーナル

IT3（US24 航海スケジュール登録 / US07 検索 / US06 引き渡し、8SP）を計画から実装・クローズまで通した。**この日の裏テーマは「同じ型の失敗は繰り返す」だった。** 方言差を 3 回、タイムゾーンの取り違えを 2 回（実装とテストで）踏み、そのたびに「次はどう気づくか」を仕組みに変えた。

## ハイライト

- **局面が中盤（インサイドアウト）に切り替わった最初のイテレーション。** `Schedule` の連結制約は行をまたぐため DB の CHECK では守れず、画面から作っていれば「貨物が途中で消えるスケジュール」を登録できていた
- **実バグを 3 件見つけた。** いずれも「テストは緑なのに動かない」種類（UTC の業務日付 / 空の港マスタ / H2 が解釈できない `LATERAL`）
- **安全装置を 6 つすべて壊して赤を確認した**（業務時計・ページ送り・連結制約・区間の順序・H2 方言・ArchUnit）
- **CI が赤のままクローズに入りかけた。** 直したはずの不具合と同じ取り違えを、テストの側でしていた
- **ベロシティを 8SP に再計算した**（3 イテレーションの実績）。初期値 12SP は過大だった

## Skill 実行の時系列

### 1. `opening-iteration` — IT3 の開始準備

計画作成時の突合で**前提の欠落を 3 件**見つけた。

| 見つけたもの | 内容 |
| :--- | :--- |
| 港マスタが空 | `carrier_movement` は `location` への外部キーを持つため、**航海を 1 件も登録できない** |
| `voyage` にカラムが無い | 船名・運送会社・取扱貨物種別。IT2 の `cargo` と同じ型の欠落 |
| `domain-model.md` に要素が無い | `VesselName` / `CarrierName` / `RoutingCargoType` |

あわせて US06 の「通知が送信される」が ADR-006 により実体を持たないことを確認し、「経路割り当て待ち一覧に現れる」へ受入基準を修正した。**通知の実体が無いまま「送信される」と書き続けると、永遠に満たせない受入基準が残る。**

`release_plan.md` の SP 合計が 2 件ずれていたのもここで見つけた（US32・US34 を足したときに合計を更新していなかった）。

### 2. `orchestrating-development` — 実装

**返済枠から着手した。** ページ送り・バッジ色分け・荷主検索モーダル・キャンセル確認。IT2 の Try「返済枠を最初から時間で確保する」に従った。

途中で**日本時間 0〜9 時に当日着の予約が拒否される**バグを掘り当てた。アプリの時計が `Clock.systemUTC()` で、UTC ではまだ前日だったためである。たまたま日付をまたいだ時刻に作業していてテストが落ちた。

**正典のずれも 1 件。** `ui_design.md` の付録は「全 enum の日本語ラベルの正典」と宣言しているのに、実装は 3 件（仮受付 / 配達完了 / 精算済）が食い違っていた。**実装に合わせて正典を書き換えると、正典が正典でなくなる。** 宣言された正典に、実装・受入基準・マニュアル・要件定義を揃えた。

ドメインは中盤の規律どおり画面より先に固めた。`Schedule` の連結制約（区間 n の到着港 = 区間 n+1 の出発港）と時系列制約（着く前に次の船は出ない）は、**どちらも 1 行で完結せず行をまたぐため DB の CHECK 制約では守れない**。検証を外すと 4 件落ちることを実測してから採用した。

### 3. 方言差 3 回目 — 仕組みにする

キャプチャを撮ろうとして航路一覧が 500 になった。**`LATERAL` を H2 が解釈できない。** Testcontainers のテストは全部緑のままだった。

IT2 から数えて 3 回目である。

| 書いたもの | 症状 |
| :--- | :--- |
| `setval`（共通マイグレーション） | ローカル起動が Flyway で止まる |
| `INTERVAL 'N days'`（動作確認用データ） | 同上 |
| `LATERAL`（航路一覧のクエリ） | 画面が 500 |

ADR-003 は「H2 で緑だが本番で落ちる」方向だけを警戒していたが、**逆方向も同じ頻度で起きる**。人の注意に頼るのをやめ、全クエリサービスを H2 上で実行して「解釈できるか」だけを見る `H2DialectSmokeTest` を置いた。ADR-003 にも規律として追記した。

### 4. `closing-iteration` — CI が赤だった

クローズのステップ 2.5（CI 確認）で赤を見つけた。**ローカルは緑だった。**

原因は、**直したはずの不具合（UTC で業務日付を判断する）と同じ取り違えを、テストの側でしていた**こと。ローカル（JST）では一致するため見えず、CI（UTC）でだけ 1 日ずれた。しかも**同じ形が 4 ファイルに残っていた**。1 か所直して満足し、他を探さなかった。

Trivy も HIGH 2 件を検出していた。Checkstyle の推移的依存である。**ビルドツール自身の依存もスキャンの対象**であり、アプリの実行時に載らなくても CI のビルド環境で実行されるコードである。

### 5. レビューで行き止まりを見つけた

**経路割り当て待ち一覧から予約の内容を確認できなかった。** 一覧には出発地・目的地しか出ておらず、寸法や品名は見えない。経路設計者は一覧を見た後、何もできない状態だった。

IT2 の教訓（ロールへの開放を確かめる）は守れていたが、**「開いた画面から次に何ができるか」は別の観点**である。正典が定める残り日数の色分け（3 日以内は赤、7 日以内は橙）も実装していなかった。**画面遷移図は計画に載せたが、画面の中の要素表を突き合わせていなかった。**

予約詳細を経路設計者にも開放した（GET のみ。操作は営業担当者のまま）。**読むことと変えることは別である。**

## 学び

- **同じ型の失敗が 2 回続いたら、その場で仕組みにする。** 方言差は 3 回目でようやくスモークテストにした。1 回目の時点で「同じ型が続く」と読めたはずである
- **修正した層の「鏡像」を探す。** ある層の取り違えを直したら、`grep` で同じ形が他に無いか確認する。今回は `LocalDate.now()` が 4 ファイルに残っていた
- **クローズ前に CI と同じ条件で 1 度回す**（`TZ=UTC ./gradlew test`）。ローカルと CI の環境差は、環境差そのものを再現しないと見えない
- **ロール別の到達性と、画面から先への到達性は別の観点である。** 「開けるか」を確かめても「開いた先で何ができるか」は確かめたことにならない
- **正典が「自分が正典である」と宣言しているなら、実装をそちらに合わせる。** 実装に合わせて正典を書き換えると、正典が正典でなくなる
- **ビルドツール自身の依存も攻撃面である。** 本番に載らないことは、無視してよい理由にならない
- **品質ゲートの判定は「解析が処理され終わってから」読む。** スキャン直後のゲート照会は前回の解析結果（指摘 14 件）を返した。解析タスクの完了を待って読み直すと PASS だった。**待たずに読んだ赤は、赤ではなく古い**
- **業務日付は利用者の暦の上の概念である。** サーバの標準時で判断すると、時差の分だけ「当日」を拒否する時間帯ができる。日中しか動かさなければ一生気づかない

# 2026-08-07（続き）IT4 開発ジャーナル

IT4（US08 経路候補を算出する、8SP）を開始準備から実装・クローズまで通した。
**この日の裏テーマは「置いた気になっている装置」だった。** 装置そのものの不在は
IT3 までの規律で減ったが、**列だけある・保存のときだけ効く**という形が 2 件残っていた。

## ハイライト

- **本システム最大の 1 件を単独で扱った。** 経路探索・経路提案・概算費用をドメインから固めた
- **安全装置を 7 つ壊して赤を確認した。** うち 1 つ（逆走チェック）は**テストが判別していなかった**
- **ArchUnit が設計の誤りを実際に捕まえた。** ACL の戻り値に BC の型を置いた
- **実バグを 2 件見つけた。** 楽観的ロックの空振りと、読み戻しで落ちる貨物種別
- **利用者から「一覧を押すと拒否される」と報告を受けた。** 共有画面の中の元からあるリンク
- ベロシティは 4 回目も 8.0SP。IT3 で採用した値と一致した

---

## 判断の記録

### 費用に入力が無かった

US08 の受入基準は「費用が表示される」を求めているのに、**運賃表も港間の距離も
`voyage` の運賃カラムも無かった**。選択肢は 3 つあった。

| 案 | 採らなかった理由 |
| :--- | :--- |
| 運賃マスタを新設する | US24 の画面とマニュアルに波及し、8SP に CRUD が丸ごと乗る |
| 費用の列を出さない | 「提案時に最初に聞かれる」ものを出さない提案画面は使えない |
| **概算式で出す** | **採用**（ADR-008） |

**材料が無いことを認めた上で概算を出す**方針を ADR にし、単価を設定値として外に出した。
**ソースを変えずに調整できることが、この式が暫定であることの証拠**になる。
画面・マニュアル・ADR の 3 か所に「概算」と明示した。

### 空き容量の列を出さなかった

`ui_design.md` は候補テーブルに「空き」を定めているが、判定の材料が無い。
経路が確定して初めて容量は減るため、確定（US09）が無い IT4 では
**判定が常に「あり」を返し、壊しても赤にならない装置**になる。

**確かめていない「あり」を画面に出すことは、確かめたと言うことと同じ**である。
列ごと出さず、IT5 で US09 と同時に実装することにした。

### ACL の境界で BC の型を使わない

ポートの戻り値に Routing の値オブジェクトを置いたところ、ArchUnit ルール 4 が
「booking が routing に依存している」と落ちた。**実装する側が相手のドメインを
直接参照するなら、ACL を置いた動機そのものが消える。**

境界は素の値にし、翻訳は Routing 側で行う形に直した。
**ルールが「宣言」ではなく「検査」になっている**ことの価値が出た場面である。

## 踏んだもの

### 逆走チェックのテストが判別していなかった

装置（乗ってから降りる順序の判定）を外しても緑のままだった。
**出発地がそもそも航路上に無いだけ**で、順序を見ているかを確かめていなかった。

乗る港と降りる港が**どちらも航路上にある**形（目的地に着いた後に出発地を出る航海）に
差し替えて、判別することを確かめた。**「壊して赤」を実行しなければ見つからなかった。**

### 外部キーを張ったら予約が 500 になった

`cargo` の発着港に港マスタへの外部キーを追加したところ、形式は正しいが
マスタに無い港（`ZZZZZ`）での予約が `DataIntegrityViolationException` になった。

**制約を足すことは、入力の検証を足すこととセットである。** Booking にも
`KnownPorts` を置き、どの港が登録されていないかを画面に返すようにした。
IT3 の航海登録と同じ扱いに揃えた。

### 楽観的ロックの列を持ちながら使っていなかった

`booking_route_proposal` は `version` を持ち、`data-model.md` も
「楽観的ロック」と書いているのに、**更新の SQL が `WHERE` で見ていなかった**。

**列があるのに見ていなければ、持っていないのと同じ**であり、次に読む人は
守られていると誤解する。`shipper` には正しい書き方がすでにあったのに、
**新しい集約を作るとき、既存集約の書き方を見に行かなかった。**

### 読み戻しで貨物種別を落としていた

危険物の予約に、危険物を扱えない便が「選択可」として並んでいた。
選択可否は「この貨物は何か」と「この便は何を運べるか」の両方で決まるのに、
読み戻しで前者を `GENERAL` 固定にしていた。

**保存のときだけ効く安全装置は、安全装置ではない。**

### 「一覧を押すと拒否される」

利用者から報告を受けた。予約詳細は営業担当者と経路設計者の両方が開くが、
「一覧に戻る」の行き先（貨物予約一覧）は営業担当者のものだった。

IT2 は「開けるか」、IT3 は「開いた先で何ができるか」、IT4 は
**「置いてあるボタンを実際に押せるか」**。同じ主題の 3 番目の変奏である。
**新しく足したボタンは数えたが、元からあるボタンを数えていなかった。**

## 学び

- **装置は「置いたか」ではなく「働くか」で数える。** 列がある・宣言があるだけの箇所は、無いより悪い。次に読む人が守られていると誤解する
- **新しい集約を作るときは、既存集約の同じ操作を先に読む。** 保存・更新・読み戻しの書き方はすでにプロジェクトの中にある
- **「壊して赤」は読み戻しにも適用する。** 保存の経路だけを確かめると、読み直したときに落ちる値を見逃す
- **制約を足すことは、入力の検証を足すこととセットである。** 外部キーだけを張ると、業務のエラーが 500 になる
- **材料が無いことは、認めて記録する。** 概算であることを画面・マニュアル・ADR に書けば、暫定のまま使える
- **画面を追加ロールへ開放したら、その画面の中のリンクを全部数える。** 新しく足したものだけでは足りない
- **依存の脆弱性は毎イテレーション出る。** クローズ直前に出ると CI が赤のままクローズに入りかける。開始時の作業として先に置く

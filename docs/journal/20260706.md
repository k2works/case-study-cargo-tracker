## 学び

- **F# 移植の最重要レビュー観点は「ファイル順コンパイルと循環参照」**。C# では成立する「全集約型を参照する中央イベント enum」が F# ではコンパイル不能になる。移植設計では言語の依存解決モデルの差を最初に ADR 化すべき
- **大規模並列生成 → 並列レビュー → 並列修正のパイプラインは、各エージェントに「ファイル単位の排他担当」を割り当てると衝突しない**。同一ファイルを 2 体が触る構成にしなかったことで全フェーズ無事故
- **セッション上限で並列エージェントが全滅したら、grep で「何がどこまで反映されたか」を棚卸ししてから残作業だけ再投入する**。同じプロンプトの再実行は完了済み修正を壊すリスクがある
- **用語統一は「正とする側を宣言してから」一括修正し、最後に横断 grep で検収する**。エージェント別修正では担当外ファイルに漏れが必ず残る（今回 51 箇所）
- **トレーサビリティ表は欠落検出器として機能する**。ui_design に「対応 US」列があったからこそ US14/16/21/22 の画面欠落が 3 エージェントから独立に指摘された。domain-model に同じ列が無かったことも同時に露見した
- **移植ドキュメント生成時は「移植元」をエージェントに明示しても学習知識の別実装（Java 版 Cargo Tracker）に引っ張られることがある**。移行マッピング表など「元技術名を列挙する成果物」は生成後に元技術名を grep 検品する

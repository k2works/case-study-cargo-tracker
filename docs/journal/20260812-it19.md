# 2026-08-12 IT19（出荷と是正）

## この日やったこと

Release 2.1 を出荷として確定させ、`ui_design.md` に書いてあって実装に無かった 2 件を返した。あわせて IT18 の Try 5 件を検査に落とし、利用者の依頼で 2 件（開発環境のシード・ドメインモデルの分割）を追加で行った。

**全 36 ユーザーストーリーが実装完了した後の、最初のイテレーション。**

## 判断の記録

### 「整流 3 回目」と呼ばなかった

開発戦略は整流について「この局面を繰り返さないことが目的である」と書き、IT17 のふりかえりは「2 回目・**最終**」と宣言している。**その宣言を取り消さないことにした。**

中身が違う。整流の対象は自分たちが数え上げた技術的負債だが、今回の対象は**正典に届いていない実装**である。局面名を「出荷と是正」とした。

### 名簿方式をやめる、ではなく「叩き方は人が書き、載せ忘れだけを機械が見る」

H2 スモークの載せ忘れを止める方法として、計画では「Bean を自動で集めて全件叩く」としていた。だが引数の要るメソッドには値をこしらえる必要があり、**叩けなかったものを黙って飛ばす形になりやすい**。それは名簿方式に戻るのと同じである。

叩き方は人が書き、載せ忘れだけを機械が見る形にした。

### SQL では作れないものがある

開発環境をマニュアルと同じ状態にする依頼を受けて調べると、追跡の記録も請求書も**荷役を登録した結果としてドメインイベントが作る派生データ**だった。`handling_activity` だけを INSERT すると、一覧には出るのに追跡画面と状態バッジが食い違う。採番もシーケンスと衝突する。

本番と同じ経路（アプリケーションサービス）で投入する形にした。

## 詰まったこと

### 投入済みの判定を 3 回間違えた

- 「見積があれば投入済み」——見積を作る別のテストが先に走ると、投入が丸ごと飛ぶ
- 「動作確認用の荷主が居れば投入済み」——その荷主は SQL が作る。local を起動すると必ず先に居るため、**一度も走らなかった**
- 「その荷主に予約があれば投入済み」——予約も SQL が作る

**印にできるのは、投入する側しか作らないものだけである。**

### 検査そのものが走っていなかった

壊れた `@link` を入れて破壊検証をしたら、赤にならなかった。Javadoc だけの変更ではバイトコードが変わらず `compileJava` が UP-TO-DATE になり、**テストが実行されなかった**。

ソースを読む検査が、ソースを入力に宣言していなかった。**破壊検証をしていなければ気づかなかった。**

### 参照実装の構成を、意味を確かめずに写した

ドメインモデルの分割で、参照実装が `BookingId` を `aggregates` に置いているのをそのまま真似た。結果、**ADR が「集約ルートの数が目に見える」と書いた利得を、識別子の同居が最初の 1 回で壊した**（本文の「Booking は 4」も誤りだった）。`entities` も 8 件中 6 件が record（同一性を持たない）だった。

レビューで指摘され、同じイテレーションの中で直した。直した結果、`entities` に残ったのは 2 クラスだけである。

### 「名前で記録した」と書きながら、記録が無かった

ADR-024 は 2 か所で「次のイテレーションで ArchUnit ルールに落とす（名前で記録した）」と書いていた。`docs/development/` を grep しても **1 件もヒットしなかった**。

**ADR 本文が最も強い言葉で戒めている形を、その ADR 自身が踏んでいた。**

## 学び

**検査を足すイテレーションで、その検査自身に穴を 3 つ作った。**

| 検査 | 穴 |
| :--- | :--- |
| H2 スモークの載せ忘れ | 型単位でしか見ておらず、**メソッド 6 件を素通り** |
| ADR-022 の規則の置き場 | 数値リテラルしか拾わず、**移設先がまさに定数比較の形** |
| 型名の照合 | 部分一致で、接尾辞が重なる型を見分けられない |

IT17・IT18 で外したのは「新しいサービス」だった。だから検査もサービス単位で書いた。**だが次に増えるのはメソッドである。**

「2 回続けて外したなら方式の問題」と書いて方式を変えたのに、**新しい方式の粒度が事故の粒度と合っていなかった。** Red は「過去に起きた症状」ではなく「次に起きる症状」で書く必要がある。

## 学び

- **例外を握る try/with は「握りたい処理の全体」を包む** — `BookingEventConsumer` は `IssueTracking.issue` は try/with 内だったが、その手前の `alreadyIssued` COUNT クエリが try 外だった。post-commit ベストエフォートの設計意図は「dispatch 由来の失敗で確定済み予約を巻き戻さない」なので、事前チェックのクエリも含めて包む必要がある。「本命の処理だけ保護」は事前クエリの例外を見落とす。
- **ドキュメントの「改訂」は旧記述の置換まで含めて初めて完了する** — ADR-0002 は「決定の改訂（IT5）」節を追加したが、旧「決定」「影響」節が Payload 方式を現行仕様のように残し、3 イテレーション自己矛盾したまま生存した。改訂時は旧節に取り消し線・置換注記を付けて「どちらが正か」を読者が迷わない状態にする。architecture_backend.md のコード例も同じ罠。
- **設計判断が実装で変わったら ADR とアーキ設計書の両方を追う** — 「BC ローカル DU に変えた」は ADR だけでなく `architecture_backend.md` のコード例・図・移行マッピングにも波及する。1 箇所直して満足すると別箇所が矛盾源になる。
- **Markdown テーブルの区切り行重複・列順序乱れは自分の過去の雑な編集が起点になりやすい** — `perl -0pi` での行置換がテーブル行を壊した（本セッションでも計画表を 2 回破損）。構造を持つテーブルは Edit で厳密一致置換し、一括正規表現置換は避ける。
- **導出状態と非正規化キャッシュは役割を分けて設計する** — TrackingStatus はイベントから導出（保存しない）、transport_status は読み取り高速化のキャッシュ。syncEvents の全置換（DELETE→INSERT）はキャッシュ再構築としては妥当だが、イベント本体は append-only であるべき（IT6 で分離）。

# 開発ジャーナル 2026-07-27（IT7）

## 今日やったこと

IT7（US17 貨物状態手動更新・US19 遅延例外・US20 破損/紛失例外・13SP）を **opening → development → closing** まで一気通貫で実施。IT6 で「枠のみ」だった Tracking Context の例外処理を、追跡管理者の業務フローとして作り込んだ。Phase 3 の例外処理側が完成。

- **opening**: IT6 ふりかえり反映 → iteration_plan-7 作成 → 整合性検証 → Release 1.0 マイルストーン + Issue #380-382 → ドキュメント同期。設計ギャップ 4 件を注1〜4 として先出し。

- **closing**: developing-review（XP 5 視点）→ 高優先度対応 → SonarQube PASS → 進捗 → ふりかえり → 報告書 → GitHub → ドキュメント同期。

## なぜそうしたか / 判断

- **貨物状態 EXCEPTION を別カラムで持たず `HasActiveException()` から算出**: 状態の二重管理を避け、例外解決で発生前状態に自然復帰させた。IT6 の CurrentStatus（UNKNOWN 読み飛ばし）の延長で凝集を保った。
- **EscalationPolicy をステートレスドメインサービスに**: LOST 即時 / DELAY 48h の 2 系統を集約。判定基準時刻を引数（Clock 由来）で渡すことで、48h 境界をテーブル駆動で決定的に検証できた。
- **通知をベストエフォートに（レビュー後）**: 当初 Save 後の通知失敗をユースケース失敗として返していたが、programmer/architect が「永続化済みなのに 422 → 再送で二重登録」を指摘。ログ実装のうちに契約を正した。

## どこで詰まったか

- **フィードバック到達がまた弱かった**: IT6 の Try T1（検証結果フィードバックの DoD 化）を掲げていたのに、追跡詳細に対応報告を出しておらず、荷役作業員の破損登録導線も欠落。DoD 宣言だけでは不十分で、実装直後の確認手順が必要（IT8 Try T1）。
- **SonarQube 違反（開発時 3・レビュー後 0）**: リテラル重複（"2006-01-02 15:04"・"invalid form"）とパラメータ過多（8 引数）。定数化・params 構造体で解消。
- **返済枠 T3/T4（ADR-0008）を今回も見送り**: 採番原子化・履歴リプレイは核心ストーリー優先で 2 IT 連続の繰越に。負債が固定化しつつあるため、IT8 序盤で先に着手する運用に変える（Try T3）。

# 2026-06-26 開発ジャーナル

Haskell 版 Cargo Tracker のスキャフォルディング以降、**運用基盤** (環境構築 → 開発スクリプト → 監査 → CI) を Skills の組み合わせで一気通貫に整備した。

## ハイライト

- **Skills の連鎖で運用基盤を完成**: `operating-setup` → `operating-script` → `validating-operating-setup` (新規) → `operating-cicd` の流れで、スタブ実装にもかかわらず CI まで動く土台を構築
- **`validating-operating-setup` スキルを新規作成**: 「手順書を作っただけで実施が放置される」問題を防ぐため、`skill-creator` を使って監査スキルを新規追加
- **CI を 3 回の修正で安定化**: Nix ベースで lts-24 / GHC 9.10.2 のフル CI (Lint + Format + Build + Test + Security) が成功

### 2. `operating-script` — Gulp タスク `develop.js` の作成

| グループ | 主要タスク |

### 3. `validating-operating-setup` — スキル新規作成

手順書のステップ実施状況を **章別チェックリスト → サマリ → A/B/C/D 分類 → 着手提案** の順で監査する新スキルを `skill-creator` で作成。

`.claude/skills/validating-operating-setup/SKILL.md` (118 行)

設計判断:

- 証拠列を必須化 (`OK` だけでなくバージョン番号 / パス / 検出結果を残す)
- **A 今すぐ / B 実装と一体 / C 任意 / D 別フェーズ** の 4 バケツに分けて、ユーザーが短い決断で次へ進めるようにした
- 「新メンバーがこの手順書だけで進めて詰まるか?」を判定の迷い解消の基準に
- 手順書の改変はスコープ外 (`operating-docs` に委譲)

別の手順書 (`開発環境セットアップ手順書.md`) でテスト実施したところ、リモート/ローカルの判別まで自律的に補完できることを確認 (定性的に検証成功)。

`.github/workflows/ci.yml` を新規作成。`ops/nix/environments/haskell/shell.nix` に `hlint` / `fourmolu` / `weeder` / `ghcid` / `dbmate` / `postgresql` を追加して **ローカルと CI で同じツールセット** を使用。

ジョブ構成:

| ジョブ | 役割 |

| 試行 | 問題 | 修正 |

最終的に全 4 ジョブが ✅ で安定。

## 学び

- **Skills の役割分担** が想定通り機能した: 設定生成系 (`operating-*`) と監査系 (`validating-*`) を分けることで、各タスクの責務が明確化された
- **「手順書 vs 現状」のギャップ可視化** が IT 着手前のチェックリスト代わりになる。これは `tracking-progress` や `validating-iteration-plan` と同じ「ドキュメントを腐らせない」型のスキル
- **HLint の `within` は直感に反する** (ホワイトリスト) ので、依存方向の制約は HLint ではなく **arch-check 等の専用ツール** に乗せた方が安全
- **macOS の BSD `ar` + GHC 9.8 の組み合わせは地雷**。GHC 9.10 (lts-24+) に上げるだけで回避可能
- **`stack build --pedantic` はスタブ期間中は不適合**: 未使用 dep が大量に発生するため。IT1 で全 dep が使われるようになってから再有効化する

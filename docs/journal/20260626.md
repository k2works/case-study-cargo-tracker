## 学び

- **Scala 版を「参考」にして Haskell 版を「導出」する流れは効率的だが、忠実に写すと表現ミスマッチが発生する**: 例として「sum type で割引ポリシーを表現」「型クラスポートの境界」など、Haskell に翻訳する過程で得られた知見が中優先度指摘の半分以上を占めた。最初から純 Haskell ネイティブで設計し直せば回避できたかもしれない
- **マルチパースペクティブレビューは Sprint 0 の安全網として極めて有効**: 5 エージェントの並列レビューで 42 件指摘が発見でき、ユーザー単独レビューでは見落とされていたであろう「集約数が backend.md と domain-model.md で齟齬」「トランザクション境界が未定義」が拾えた
- **PlantUML の composite state は罠**: composite 内で同名要素を参照すると複製される。ER 図の概念モデルでも skinparam の一行記述やショートエイリアスは避け、フルネーム + `skinparam linetype ortho` が安全
- **Skills の役割分担** が想定通り機能した: 設定生成系 (`operating-*`) と監査系 (`validating-*`) を分けることで、各タスクの責務が明確化された
- **「手順書 vs 現状」のギャップ可視化** が IT 着手前のチェックリスト代わりになる。これは `tracking-progress` や `validating-iteration-plan` と同じ「ドキュメントを腐らせない」型のスキル
- **HLint の `within` は直感に反する** (ホワイトリスト) ので、依存方向の制約は HLint ではなく **arch-check 等の専用ツール** に乗せた方が安全
- **macOS の BSD `ar` + GHC 9.8 の組み合わせは地雷**。GHC 9.10 (lts-24+) に上げるだけで回避可能
- **`stack build --pedantic` はスタブ期間中は不適合**: 未使用 dep が大量に発生するため。IT1 で全 dep が使われるようになってから再有効化する

## 開発フェーズ Skill 実行の時系列 (IT1 完了後の追加セッション)

リリース計画策定後、Ralph Loop で IT1 を圧縮実装 (28 イテレーション + 後続改善 10 コミット)。Phase A (PRG/詳細画面) + Phase B (htmx) を計画と整合させた後、XP 5 エージェント並列レビューで全体を検証し、ふりかえり・報告書を整備した。

### 1. `ralph-loop` — IT1 圧縮実装

Ralph Loop で `IT1 --max-iteration 10` を入力に 28 イテレーション継続実行。計画 13SP に対し実績 20SP (達成率 154%) を圧縮 1 日で達成。4 BC × 4 層 + Lucid SSR + Postgres 永続化 + arch-check Phase 1 + 117 tests グリーンに到達。

主要な落とし穴と対処:

- `Char8` ByteString は Latin-1 のため日本語をトランケート → テストボディは ASCII へ
- レコードフィールド `id` が `Prelude.id` と衝突 → 早期に `shipperId` へ別名化
- HLint の `within` は whitelist セマンティクスのため "not within" 表現不可 → grep ベース shell スクリプト `scripts/arch-check.sh` で arch-check Phase 1 を実装
- `secondsToDiffTime` は 86400 超でオーバーフロー → `addUTCTime` で日付計算
- `postgresql-simple` の `execute` は RETURNING 不可 → `query` を使う
- macOS では `libpq` を Homebrew 導入 + `PKG_CONFIG_PATH`/`PATH` 設定

`creating-iteration-report` で `iteration_report-1.md` を作成、`iteration_plan-1.md` のタスクチェック状態を 35 件 `[x]` に更新、`release_plan.md` の IT1 実績 20SP/154% を反映。続いて Playwright E2E 雛形を `apps/cargo-tracker/e2e/` 配下に作成 (4 spec: home / shipper / voyage / booking)、Gulp/npm タスク統合。

### 3. 認証フロー改善とホットリロード

- ログイン画面に `admin@example.com` / `password` のデフォルト値と 8 ロールシードユーザー一覧を表示

### 4. 画面遷移・インタラクション計画とのギャップ修正 (Phase A + B)

`iteration_plan-1.md` の画面遷移図 (PRG + 詳細画面 + htmx) と実装 (結果ページ直接返却) の乖離を 2 フェーズで追従:

- **Phase A**: `ShipperRepository.findById/searchByQuery`, `BookingRepository.findCargoById` 追加 + Postgres 実装。`ShipperShowView` / `BookingShowView` / `VoyageShowView` 3 詳細ビュー作成。全 Form POST を `throwError err303 {errHeaders=[Location]}` に変更し PRG 化。JSON API を `/api/*` に分離
- **Phase B**: Layout に htmx 1.9.12 CDN。`GET /shippers/search?q=` で htmx 候補リスト部分 HTML、Booking フォームに 300ms デバウンスで統合。`GET /voyages/new/movement-row` で区間行部分 HTML、Voyage フォームに「+ 区間を追加」ボタン (beforeend 挿入)

ハマったポイント:

- Servant の `throwError` ローカルヘルパーは型推論で `MonadError ServerError m` 制約を解決できず GHC-80003 エラー → 明示的に `:: Text -> Handler a` シグネチャ付与

## 学び (IT1 完了後追加分)

- **Servant の `throwError` 内ローカルヘルパーは明示型必須**: `redirectErr = throwError ...` を `where` 句に置くと `MonadError ServerError m` の polymorphism で GHC-80003。`:: Text -> Handler a` を付ければ解消
- **Lucid の `makeAttribute` は `Lucid.Base` から import**: htmx の `hx-*` 属性を扱うときに毎回遭遇する罠
- **PRG パターンを後から導入すると Form/詳細の対称性が壊れる**: 詳細ビューと findById ポートは Domain 設計時に決めるべき。後追いだとリポジトリポート → 実装 → ビュー → ルーティング → テスト fake の 5 層に波及
- **htmx の hx-get に input が混じると query 名衝突**: フォームの `name="shipperId"` を hx-get で送信すると検索 API の `q` パラメータと不整合。検索 API 側で複数キーを許容する設計が現実的
- **Ralph Loop の「end-of-life」運用**: 完了済みタスクで Stop hook が再発火する状態は、最小応答 (`Simple made easy.` + 1 文) で抜ける運用が安定する (memory `feedback_ralph-loop-end-of-life.md` の更新)
- **XP 5 エージェント並列レビューは IT 規模の検証に有効**: 個別の指摘に矛盾はなく、補完関係で 30 件以上の改善点を網羅。「テスト・構造・UX・ドキュメント」の 4 軸を 1 セッションで横断できる
- **完了報告書は「成功基準ごとのエビデンス対応表」が本質**: 「113 tests passing」だけでは未達の発見が遅れる。HPC % / arch-check ログ / E2E spec 数を計画と対応付けて表化する
- **placeholder の文書化欠落は最大の罠**: `Shipper.name = email` のような暫定処置は、Haddock とドメインモデル設計書の両方に明示しなければ次担当がコードを開いた瞬間に詰む

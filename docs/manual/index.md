# ユーザーマニュアル

国際貨物輸送管理システムを日々の業務で使うための手引きです。読者は業務担当者であり、開発者ではありません。

このマニュアルの価値は網羅性ではなく、**画面の前に座った担当者がその場で手を動かせること**にあります。

## 公開の形

`docs/manual/*.md` が正典です。`npx gulp manual:build` が HTML へ変換し、
`apps/www/manual/` に出力します。ドキュメントサイトのイメージはポータル
（`apps/www/`）をまるごと配信するため、**出力した時点でポータルの
「ユーザーマニュアル」から読める**状態になります。

生成物は追跡しません（`.gitignore`）。ソースと出力を二重に持つと、
どちらが正かが分からなくなります。

> **置き場所と配信先を離さないこと。** 以前は存在しない `apps/manual/` を
> 参照していたため、書いたマニュアルが配信されず「まだ作成していません」という
> ダミーが出続けていました。

## 構成

```text
docs/manual/
├── index.md                 # 本文書（構成・テンプレート・キャプチャ方針）
├── 00-はじめに.md            # 読み方・表記規約・動作環境
├── 01-業務フロー.md          # 業務全体の流れと、各工程で使う画面（各章への入口）
├── 02-ログイン.md            # ログイン・ログアウト・ロックされたとき
├── 03-荷主管理.md            # 荷主の登録・検索・編集
├── 04-貨物予約.md            # 貨物予約の登録・確認（危険物・冷凍を含む）
├── 05-航海スケジュール.md     # 航海の検索・登録・更新・詳細（US24・US25・US07）
├── 06-経路設計.md            # 経路候補の算出・選択・確定・追跡番号の発行（US08〜US11・US14）
├── 07-アカウント管理.md       # ロックされたアカウントの解除（US32）
└── assets/*.png             # 画面キャプチャ（Playwright が自動生成）

apps/www/manual/             # manual:build が生成する HTML（追跡しない）
```

章番号は画面の並び順です。業務の順序ではありません。イテレーションが進むごとに章が増えます。

| 章 | 内容 | 追加した IT |
| :--- | :--- | :--- |
| 00 | はじめに（読み方・表記規約） | IT1 |
| 01 | 業務フロー（全体の流れと各工程で使う画面） | IT1 |
| 02 | ログイン（US26・US27・US31） | IT1 |
| 03 | 荷主管理（US02・US03） | IT1・IT2・IT5（編集） |
| 04 | 貨物予約（US04・US05・US12・US13） | IT2・IT5（割り当て経路の表示）・IT6（通知・確定・追跡番号の確認） |
| 05 | 航海スケジュール（US24・US25・US07。航海詳細は IT4） | IT3・IT4 |
| 06 | 経路設計（US08〜US11・US14） | IT4・IT5・IT6（追跡番号の発行） |
| 07 | アカウント管理（US32） | IT6 |

### 業務フローの章の位置づけ

01 は**各章への入口**です。読者は「自分の仕事がシステムのどこにあたるか」から探すため、
画面名を知らなくても辿り着けるようにします。

- 各画面の章は、冒頭で 01 のどの工程に対応するかを述べる
- 01 の対応表には**まだ使えない画面も載せ、「準備中」と示す**。載せないと、業務の流れに
  穴があるのか、システムが対応していないだけなのかが読者に判断できない
- **画面を追加した IT では、01 の対応表の「状況」も更新する**。ここを忘れると、使えるように
  なった画面を誰も探しに来ない

## 節の執筆テンプレート

画面ごとに 1 節を立て、次の順序で書きます。この順序は読者が実際に迷う順序です。

```markdown
## <章.節> <画面・機能名>

### この画面でできること

（業務上の目的を 1〜3 行）

### 画面の開き方

（メニュー名 → 画面名。URL も添える）

### 画面の説明

![<画面名>](assets/<章番号>-<slug>.png)

| 項目 | 必須 | 説明 |
| :--- | :--- | :--- |

（一覧画面では「| 列 | 説明 |」の表にする。ボタンも項目として並べる）

### 操作手順

1. （番号付き。クリック対象は「」で囲む）

### よくある入力の誤り

| 表示されるメッセージ | 直し方 |
| :--- | :--- |

（**画面に実在する文言をそのまま書く**。実装のメッセージと突き合わせて確かめる。
一部だけ入力したときにだけ出るメッセージも漏らさない）

### 注意・補足

（業務ルール上の注意、うまくいかないときの対処。引用ブロック `>` で書く）
```

> **様式は 04 章を正典とします。** IT2 のレビューで、章ごとに項目表の形と注意の書き方が
> 揃っていないと、読者が「どこに注意が書いてあるか」を毎回探し直すことが分かりました。

## 節へのリンク

**節見出しには英数字の ID を明示する**（`## 3.2 荷主を登録する {#register-shipper}`）。

日本語の見出しは、生成時に `#_3` のような機械的な ID に変換される。ID を書かずにリンクすると
アンカーが落ち、章の先頭に飛ぶ。読者は目的の節を自分で探すことになる。

- ID は英数字とハイフンで、節の内容が分かる語にする（`#register-shipper`）
- 章内の目次表からのリンクも同じ ID を使う
- 節を消すときは、その ID を参照している箇所も直す

## 表記規約

| 規約 | 例 |
| :--- | :--- |
| 文体はですます調 | 「〜します」「〜してください」 |
| ボタン・入力項目・選択肢は「」で囲む | 「検索」をクリックします |
| 画面の場所はメニュー → 画面の順 | メニュー「荷主管理」→「荷主を登録する」 |
| 種別・状態は画面の表示名で書く | 「個人」（`INDIVIDUAL` ではなく） |

書かないこと:

- テーブル名・カラム名・API パス・クラス名（読者は画面しか見ません）
- 実装都合の説明（「非同期で処理されるため」→「反映まで少し時間がかかります」）

業務ルールに関わる注意は本文に混ぜず「注意・補足」に集めます。読者が操作中に読むのは手順、つまずいてから読むのが注意だからです。

## 画面キャプチャの方針

キャプチャは **Playwright で自動生成します。手作業で PNG を置いてはいけません** — 次回の再生成で上書きされ、画面が変わったときの撮り漏れに気づけなくなります。

| 項目 | 内容 |
| :--- | :--- |
| 生成 spec | `apps/frontend/e2e/manual/manual-screenshots.spec.ts` |
| 設定 | `apps/frontend/playwright.manual.config.ts` |
| 実行 | `npm run screenshots:manual`（`apps/frontend` で実行） |
| 出力先 | `docs/manual/assets/` |
| 配信 | 本番相当ビルドをローカル配信（`vite preview`） |
| データ | API モック（バックエンド不要で、毎回同じ画面が撮れる） |
| 命名 | `<章番号>-<英字スラッグ>.png`（例: `02-login.png`） |

### 本番相当ビルドで撮る理由

開発サーバはビルドモードで見た目が変わることがあり、開発用の表示が写り込みます。一方で**本番環境そのものには接続しません**。マニュアルは Git 管理下に置かれるため、実在の顧客名や連絡先がリポジトリに残るのを避けます。**見た目は本番ビルド、データはモック**で揃えるのが原則です。

この理由から、通常の E2E 実行からキャプチャ spec は除外しています（`playwright.config.ts` の `testIgnore`）。開発サーバで動かすと違う見た目の PNG で上書きしてしまうため、除外は外さないでください。

### 画面を変えたとき

画面を変更したイテレーションの中で、該当する節の本文とキャプチャを同時に更新します。クローズ時にまとめて思い出そうとすると、計画外の作業がイテレーション末に積み上がり、更新自体が飛ばされます。

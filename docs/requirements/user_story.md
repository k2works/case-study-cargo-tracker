# ユーザーストーリー - 国際貨物輸送管理システム

システムユースケースから開発可能な粒度のユーザーストーリーを導出する。
「〜として、〜したい。なぜなら〜だからだ」の形式で記述し、各ストーリーに受入条件を定義する。

受入条件は人と AI の契約として、Given/When/Then で一意に判定できる形で書き、`AC-01` から番号を振る。元の基準に無い振る舞いを補った条件には「（AI の仮定）」と印を付ける。各ストーリーの「参照する成果物」は生成時に AI に渡すコンテキスト、「確認ポイント」は承認ゲートで人が判断する点、「AI の仮定」は未確認の前提を示す。用語は[用語集](../design/glossary.md)、AI に任せる範囲とリスク ID は[リスク台帳](risk_register.md)に従う。

## US01: 輸送見積を作成する

**として**: 営業担当者

**したい**: 荷主の輸送要件（出発地・目的地・希望期限・貨物種別・重量）を入力し、輸送料金と所要日数の見積を作成したい

**なぜなら**: 荷主が予算と納期を事前に把握でき、予約決定を迅速に行えるからだ

**対応 UC**: UC01

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 営業担当者が見積作成画面を開いている / When 出発地・目的地・希望期限・貨物種別・重量を入力して検索する / Then 航海スケジュールをもとにした経路の概算候補が表示される
- [ ] **AC-02** Given 経路の概算候補が表示されている / When 候補一覧を見る / Then 候補ごとに経由港・所要日数・概算料金・航海番号が表示される
- [ ] **AC-03** Given 経路の概算候補が表示されている / When 見積を保存する / Then 見積が保存され、見積番号が発行される
- [ ] **AC-04** Given 希望期限までに目的地へ到達できる航海が無い / When 見積の条件で検索する / Then 期限に間に合う経路が無いことが通知される
- [ ] **AC-05** Given 見積作成画面を開いている / When 貨物種別に「危険物」を選ぶ / Then 危険物申告情報の入力フォームが表示される

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: [UC01 輸送見積を作成する](system_usecase.md)
- 制約条件: [要件定義書「経路設計の制約条件」](requirements_definition.md)

**確認ポイント**: 概算料金の算出方法が未定義（US21 の輸送料金算出と同じ計算かどうか）。危険物申告情報の項目は要件に無い（R-05）

**AI の仮定**: 概算候補の抽出には US08 の経路候補算出と同じ制約条件を使う（要確認）

## US02: 荷主を登録する

**として**: 営業担当者

**したい**: 新規荷主の氏名/社名・住所・連絡先・メールアドレスをシステムに登録したい

**なぜなら**: 次回以降の予約で荷主情報の再入力を省略でき、顧客情報を一元管理できるからだ

**対応 UC**: UC02

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 入力するメールアドレスの荷主が登録されていない / When 氏名または社名・住所・連絡先・メールアドレス・荷主種別「個人」を入力して登録する / Then 荷主が登録され、荷主 ID が発行される
- [ ] **AC-02** Given 同じメールアドレスの荷主が登録済みである / When そのメールアドレスで登録しようとする / Then 既存の荷主が表示され、既存の荷主を使うか登録を続けるかを選べる

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: [UC02 荷主を登録する](system_usecase.md)

**確認ポイント**: 必須項目が未入力のときの振る舞いは受入条件に無い

**AI の仮定**: 「どちらを使用するか選択できる」を、既存の荷主を使うか新規登録を続けるかの選択と解釈した（要確認）

## US03: 法人荷主を登録する

**として**: 営業担当者

**したい**: 法人荷主の契約番号と割引率を含めて登録したい

**なぜなら**: 法人契約条件（割引率）を精算時に自動適用できるからだ

**対応 UC**: UC02

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 荷主登録画面を開いている / When 荷主種別「法人」を選ぶ / Then 契約番号と割引率の入力欄が表示される
- [ ] **AC-02** Given 荷主種別「法人」を選んでいる / When 割引率 0%〜30%（境界値 0% と 30% を含む）で登録する / Then 法人荷主が登録され、荷主 ID が発行される
- [ ] **AC-03** Given 荷主種別「法人」を選んでいる / When 割引率に 30% を超える値または負の値を入力して登録する / Then 登録できず、範囲外であることが示される（AI の仮定）
- [ ] **AC-04** Given 割引率を登録した法人荷主がいる / When その荷主の輸送料金に法人割引を適用する（US22） / Then 登録した割引率が使われる

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: [UC02 荷主を登録する](system_usecase.md)
- 関連ストーリー: US22 法人割引を適用する

**確認ポイント**: AC-03 は元の基準「0〜30% の範囲で設定できる」から導いた範囲外の振る舞い

**AI の仮定**: 範囲外の割引率は登録を拒否する（警告に留めない）（要確認）

## US04: 貨物予約を登録する

**として**: 営業担当者

**したい**: 荷主 ID・貨物仕様（種別・重量・寸法・個数・品名）・輸送条件（出発地・目的地・希望日）を入力して予約を登録したい

**なぜなら**: 荷主の見積承認後に正式な予約を受け付け、経路設計フェーズに引き継げるからだ

**対応 UC**: UC03

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 荷主が登録済みである / When 荷主 ID を入力する / Then その荷主が選択される
- [ ] **AC-02** Given 荷主を選択している / When 貨物種別・重量・寸法・個数・品名と、出発地・目的地・希望引渡日・希望着日を入力して登録する / Then 予約番号が発行され、予約状態が「仮受付」になる
- [ ] **AC-03** Given 予約の登録が完了した / When 完了を確認する / Then 経路設計者に予約登録が通知される
- [ ] **AC-04** Given 見積のある荷主の予約を登録する / When 登録する / Then 見積の内容との整合性が確認される

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: [UC03 貨物予約を登録する](system_usecase.md)
- 状態: [要件定義書「貨物予約の状態遷移」](requirements_definition.md)

**確認ポイント**: AC-04 の「整合性の確認」の中身（どの項目を比べるか、差異があるとき登録を止めるか警告に留めるか）が未定義で、Given/When/Then で一意に判定できない。「希望着日」は用語集の「希望期限」と同じか

**AI の仮定**: 見積番号を指定した場合に、出発地・目的地・貨物種別・重量を見積と比べ、差異を警告する（要確認）

## US05: 危険物・冷凍・冷蔵貨物の予約を登録する

**として**: 営業担当者

**したい**: 危険物や冷凍・冷蔵貨物の場合に、特別な追加情報（危険物申告・温度管理条件）を含めて予約を登録したい

**なぜなら**: 貨物種別に応じた法的要件と取扱い条件を正確に管理し、安全な輸送を保証できるからだ

**対応 UC**: UC03

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 予約登録画面を開いている / When 貨物種別「危険物」を選ぶ / Then 危険物申告情報の入力欄が表示され、未入力では登録できない
- [ ] **AC-02** Given 予約登録画面を開いている / When 貨物種別「冷凍・冷蔵貨物」を選ぶ / Then 温度管理条件の入力欄が表示され、未入力では登録できない
- [ ] **AC-03** Given 危険物申告情報または温度管理条件を登録した予約がある / When 経路設計で候補を表示する / Then その貨物種別に対応する航海・経路だけが候補になる

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: [UC03 貨物予約を登録する](system_usecase.md)
- 制約条件: [要件定義書「経路設計の制約条件」（貨物種別対応）](requirements_definition.md)

**確認ポイント**: 危険物申告情報と温度管理条件の項目が要件に無い（R-05）。AC-03 は経路設計（US07・US08）の振る舞いで、この予約登録のストーリーだけでは確かめられない（R-04）

**AI の仮定**: 危険物申告情報は国連番号と等級、温度管理条件は設定温度の範囲とする（要確認。R-05 により確認まで実装しない）

## US06: 予約情報を経路設計者に引き渡す

**として**: 営業担当者

**したい**: 仮受付された予約の出発地・目的地・期限・貨物仕様を確認し、経路設計者に引き渡したい

**なぜなら**: 経路設計者が正確な情報をもとに最適な経路設計を開始できるからだ

**対応 UC**: UC04

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 「仮受付」の予約がある / When 予約番号を指定する / Then 出発地・目的地・期限・貨物仕様が表示される
- [ ] **AC-02** Given 「仮受付」の予約がある / When 経路設計を依頼する / Then 予約状態が「経路提案中」になり、経路設計者に依頼が通知される
- [ ] **AC-03** Given 予約情報に不備がある / When 予約情報を修正してから経路設計を依頼する / Then 修正後の内容で経路設計者に引き渡される

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: [UC04 予約情報を引き渡す](system_usecase.md)
- 状態: [要件定義書「貨物予約の状態遷移」](requirements_definition.md)

**確認ポイント**: 「不備」の判定基準が未定義。US04 AC-03 の予約登録の通知と、AC-02 の依頼の通知が二重に届かないか

**AI の仮定**: 不備はシステムが検出するのではなく、営業担当者が確認して判断する（要確認）

## US07: 航海スケジュールを検索する

**として**: 経路設計者

**したい**: 予約の出発地・目的地・期限をもとに、利用可能な航海スケジュールを検索したい

**なぜなら**: 制約条件を満たす航海を特定し、経路候補算出の入力を準備できるからだ

**対応 UC**: UC05

**Unit**: [U-03 航海スケジュール・経路設計](units.md)

**受入条件**:

- [ ] **AC-01** Given 「経路提案中」の予約がある / When 予約番号を指定する / Then 出発地・目的地・期限・貨物仕様が表示される
- [ ] **AC-02** Given 航海スケジュールが登録されている / When 出発地・目的地（UN/LOCODE）・出発期間・貨物種別を入力して検索する / Then 制約条件（航海スケジュール・寄港地の接続・港湾制約・貨物種別対応）を満たす航海だけが表示される
- [ ] **AC-03** Given 検索結果が表示されている / When 一覧を見る / Then 航海ごとに航海番号・運送会社・出発日・到着日・寄港地が表示される
- [ ] **AC-04** Given 貨物種別が「危険物」または「冷凍・冷蔵貨物」の予約である / When 航海を検索する / Then その貨物種別に対応する航海だけに絞り込まれる
- [ ] **AC-05** Given 条件を満たす航海が無い / When 検索する / Then 該当する航海が無いことが表示され、条件を緩めて再検索できる

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: UC05 航海スケジュールを検索する（[システムユースケース](system_usecase.md)）
- 制約条件: [要件定義書「経路設計の制約条件」](requirements_definition.md)

**確認ポイント**: UN/LOCODE は実在するコードを使う（R-09）。貨物種別対応の判定に使う航海側の項目は US24 の「対応貨物種別」（R-04）

**AI の仮定**: 期限は出発期間の終わりではなく到着の期限として検索条件に使う（要確認）

## US08: 経路候補を算出する

**として**: 経路設計者

**したい**: 航海スケジュール検索結果をもとに、制約条件を考慮した経路候補を自動算出してほしい

**なぜなら**: 手作業の属人化を解消し、制約条件を漏れなく考慮した最適経路を効率的に見つけられるからだ

**対応 UC**: UC06

**Unit**: [U-03 航海スケジュール・経路設計](units.md)

**受入条件**:

- [ ] **AC-01** Given 航海の検索結果と、出発地・目的地・期限がある / When 経路候補を算出する / Then 寄港地の接続を評価した経路候補が自動で算出される
- [ ] **AC-02** Given 経路候補が算出された / When 一覧を見る / Then 候補ごとに所要日数・経由港・費用・航海番号が表示され、推奨順に並んでいる
- [ ] **AC-03** Given 出発地から目的地まで乗り継ぎの無い航海がある / When 経路候補を算出する / Then その経路が最優先の候補として提示される
- [ ] **AC-04** Given 期限内に目的地へ到達できる経路が無い / When 経路候補を算出する / Then その旨が通知され、経路条件の調整（US10）が促される

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: UC06 経路候補を算出する（[システムユースケース](system_usecase.md)）
- 制約条件: [要件定義書「経路設計の制約条件」](requirements_definition.md)

**確認ポイント**: 推奨順の基準（所要日数・費用・乗り継ぎ回数の優先順位）が未定義。費用の算出方法が未定義。制約条件を AI が追加・省略しない（R-04）

**AI の仮定**: 「直行便」は乗り継ぎ（経由港）の無い経路と解釈した。直行便の次は所要日数の短い順に並べる（要確認）

## US09: 経路を選択・確定する

**として**: 経路設計者

**したい**: 算出された経路候補から最適なものを選択し、経路を確定したい

**なぜなら**: 最適経路を正式に確定し、予約への紐付けに進めるからだ

**対応 UC**: UC07

**Unit**: [U-03 航海スケジュール・経路設計](units.md)

**受入条件**:

- [ ] **AC-01** Given 経路候補が算出されている / When 候補一覧を開く / Then 候補ごとに経由港・所要日数・費用・航海番号が表示される
- [ ] **AC-02** Given 経路候補一覧を開いている / When 候補を 1 件選んで確定する / Then その経路の状態が「確定」になる
- [ ] **AC-03** Given 最適な候補が無い / When 経路条件の調整を選ぶ / Then 経路条件の調整（US10）に進む

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)

**確認ポイント**: 「経路状態」（確定・誤配）は用語集と要件定義書の状態モデルに無い。経路に状態を持たせるかはドメインモデル設計で決める（R-06）

**したい**: 配送完了した予約に対して輸送実績（経路・重量・貨物種別・荷役実績）をもとに輸送料金を算出したい

**なぜなら**: 実際の輸送内容に基づく正確な料金を算出し、精算に進めるからだ

**対応 UC**: UC17

**Unit**: [U-05 精算](units.md)

**受入条件**:

- [ ] **AC-01** Given 貨物状態が「引取済」（予約状態が「配送完了」）の予約がある / When 料金算出を開始する / Then 輸送実績（経路・距離・重量・貨物種別・荷役作業実績）が表示され、基本料金が自動で計算される
- [ ] **AC-02** Given 基本料金が計算されている / When 算出結果を確認して確定する / Then 輸送料金が「確定」の状態で登録される
- [ ] **AC-03** Given 遅延・破損などの例外が発生した予約である / When 料金算出を開く / Then 料金調整（減額・補償費用）を入力できる

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: UC17 輸送料金を算出する（[システムユースケース](system_usecase.md)）
- 状態: [要件定義書「貨物予約の状態遷移」](requirements_definition.md)

**確認ポイント**: 基本料金の計算式（距離・重量・貨物種別の係数）が未定義で、AC-01 の計算結果を判定できない。「距離」は用語集に無い。輸送料金の状態（確定）が状態モデルに無い

**AI の仮定**: 基本料金の計算式は受入条件の追加で定義してから実装する。確定前の輸送料金は「算出済」の状態を持つ（要確認）

**確認ポイント**: インセプションデッキは「税関申告システム（連携は行うが、申告業務自体は対象外）」をスコープ外としている。本ストーリーは税関とは連携せず申告結果を手入力で記録するもので、スコープ外の申告業務そのものではないと読めるか。税関と電子連携しない判断は ADR が未記録。「貨物 ID」は用語集に無い。UC21 の「不可」時の返送・廃棄の判断と「3 日超の督促通知」が受入条件に無い

**AI の仮定**: 申告業務のうち記録だけをスコープ内とする。「貨物 ID」は予約番号を指す（要確認）

## US30: 輸送中の予約キャンセルを承認する

**として**: 追跡管理者

**したい**: 輸送中の貨物に対するキャンセル申請について、陸揚げ地を指定したうえで承認または却下したい

**なぜなら**: 輸送開始後のキャンセルは貨物が船の上にあるため「どこで降ろすか」の判断が必要であり、営業担当者の操作だけで完結させると貨物が宙に浮くからだ

**対応 UC**: UC22

**Unit**: [U-02 貨物予約](units.md)

**受入条件**:

- [ ] **AC-01** Given 予約状態が輸送開始前（仮受付・経路提案中・予約確定・追跡番号発行済）の予約がある / When 営業担当者がキャンセルする / Then 承認なしで即座にキャンセルされる
- [ ] **AC-02** Given 予約状態が「輸送中」の予約がある / When 営業担当者が予約詳細を開く / Then `[キャンセル（要承認）]` の申請ボタンだけが表示される
- [ ] **AC-03** Given 「輸送中」の予約でキャンセルを申請する / When 理由を入力せずに申請する / Then 申請できない
- [ ] **AC-04** Given 「輸送中」の予約で理由を入力して申請した / When 申請が完了する / Then 追跡管理者に通知され、承認待ちの一覧に表示される
- [ ] **AC-05** Given 承認待ちの申請がある / When 追跡管理者が陸揚げ地（現在地の港または次の寄港地）を指定して承認する / Then キャンセルが確定し、陸揚げ地への荷降しが手配され、荷主に通知される
- [ ] **AC-06** Given 承認待ちの申請がある / When 追跡管理者が却下する / Then 予約は「輸送中」のまま維持され、却下理由が申請者と荷主に通知される
- [ ] **AC-07** Given 予約状態が「配送完了」以降の予約がある / When キャンセルしようとする / Then キャンセルできない
- [ ] **AC-08** Given キャンセル料が発生する状態の予約をキャンセルする / When キャンセルが確定する / Then 状態に応じた料率でキャンセル料が算定され、精算に引き渡される
- [ ] **AC-09** Given キャンセルの申請・承認・却下があった / When 予約詳細を開く / Then 履歴（日時・実行者・理由）が表示される

**参照する成果物**:

- ドメイン用語: [用語集](../design/glossary.md)
- ユースケース: UC22 予約をキャンセルする（[システムユースケース](system_usecase.md)）
- 状態: [要件定義書「貨物予約の状態遷移」](requirements_definition.md)

**確認ポイント**: キャンセル料の料率が未定義で AC-08 を判定できない。AC-01 は営業担当者の振る舞いで、ストーリーの主語（追跡管理者）と異なるため分割の候補。US13 AC-04 と重複。予約状態に「キャンセル承認待ち」を持つか（R-06）

**AI の仮定**: 承認待ちの間も予約状態は「輸送中」のままとし、申請は別に記録する（要確認）

# 設計

設計ドキュメントです。実装言語は **Flix**（JVM 上の関数型言語）で、Web フレームワーク・ORM・モックライブラリを持たないという制約のもと、
出力ポートを代数的効果として表現するヘキサゴナルアーキテクチャを採ります。方針の全体像は [技術スタック選定](tech_stack.md) と [バックエンドアーキテクチャ](architecture_backend.md) を参照してください。

要件定義に基づき、バックエンド・フロントエンド・インフラのアーキテクチャから、データモデル、ドメインモデル、UI、テスト戦略、非機能要件、運用要件まで包括的に設計しています。

## 段階的実装方針（暫定）

8 つのコンテキストを同時に着手しない。以下の順序で縦に貫き、パターンを確立してから横展開する。
**本節は暫定であり、正式な定義は開発戦略（`docs/development/development_strategy.md`）で行う。**

| 段階 | 範囲 | 狙い |
| :--- | :--- | :--- |
| 1. ウォーキングスケルトン | 公開貨物追跡（US18・**認証不要**）を HTTP → ルーティング → クエリサービス → JDBC ハンドラ → 画面まで縦断 | 効果ハンドラ・`Tx`・`Html` DSL・`arch-lint` の 4 基盤を最小構成で確立する。認証を含めないことで最大リスクを後段に分離する |
| 2. 認証・認可 | US26/27 + ルーティング表の必須ロール + セッションストア（DB 実装） | 自作セキュリティ機構を早期に固め、以降の全画面で認可テストを回せる状態にする |
| 3. 中核業務 | Booking / Shipper / Estimation / Routing（US01-US14、優先度「高」） | DDD の主戦場。集約と状態遷移の TDD に集中する |
| 4. 荷役・追跡 | Handling / Tracking（US15-US20） | イベント駆動（after-commit 配信）の検証を含む |
| 5. 精算 | Billing（US21-US23、優先度「中」） | 金額計算をテーブル駆動で網羅する |

**段階 1・2 の完了時に必ず評価する項目**

- 効果の組み合わせがシグネチャをどこまで肥大化させるか（実測して許容範囲を判断する）
- `arch-lint` が実際に規約違反を検出できるか（違反フィクスチャによる検証）
- 追跡 API のスループット（[バックエンドアーキテクチャ](architecture_backend.md) の未検証項目）

## 1. 設計の前提

### 1.1 テスト戦略を左右する要件

| 要件・設計 | 出典 | テスト戦略への影響 |
| :--- | :--- | :--- |
| ドメインが純粋関数で、`Either[Error, (新状態, イベント)]` を返す | バックエンド 4.1 | 業務ルールの大半を Pekko も DB も無しで速く検査できる。ユニットテストに投資する |
| 状態モデルが貨物予約 8 状態・貨物状態 9 状態、遷移以外を許さない | 要件定義書、ドメイン D1・B1・T1 | 状態 × コマンドの全組み合わせを表から生成して検査できる |
| 例外・通関・キャンセルの履歴が残り、料金調整の根拠になる | US28 AC-06、US29 AC-09、US30 AC-09 | 履歴が「残ること」と「消えないこと」を検査する |
| 金額と端数処理 | U-05 NFR | 境界値と性質（プロパティ）で網羅する |
| 経路算出が制約条件 5 つをすべて満たす | U-03 NFR、R-04 | 制約の漏れを検出するテストを、制約を 1 つ足すごとに足す |
| 書き込みの結果が読み取りに遅れて現れる（結果整合） | バックエンド 6.4 | 画面から踏む検査で、更新直後の一覧に対象が見えることを確かめる |
| 5 つの Unit が契約（`contract`）でつながる。連携は 17 本 | バックエンド 7.2 | 連携の数だけ往復テストを置く（検査 A9） |
| 公開の追跡照会は認証なし | US18、R-02 | 推測・過負荷・個人情報の漏れを攻撃者の視点で検査する |
| 認証・認可、スキーマ変更、外部連携は確認必須 | リスク台帳 R-01〜R-03 | 該当ステップで止まり、テストの内容も人が承認する |
| 外部システムの仕様が不明 | R-01 | ポートとスタブ、契約テストで先行する。スタブを本物より甘くしない |
| 本プロジェクトは AI が TDD で生成し、人が全行を理解して承認する | CLAUDE.md、AI-DLC | テストは「契約」であり「次のコンテキスト」。AI が書いたテストを人が読める粒度と名前にする |

## 3. テストレベルの定義

重複する検証は実行時間と保守の負担を増やすだけです。**1 つの振る舞いは、それを最も安く判別できる層で 1 回検査し**、上の層は「つながっていること」だけを確かめます。

| # | レベル | 対象 | 使うもの | 外部依存 | 速度の目安 | 守る振る舞い |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| L1 | ドメイン単体 | 集約・値オブジェクト・ドメインサービス（`domain`） | ScalaTest | 無し（Pekko・DB・時計に依存しない） | ミリ秒 | 不変条件、状態遷移、計算、業務エラー |
| L2 | プロパティ | `RouteFinder`、金額計算、値オブジェクトの検証、状態遷移 | ScalaCheck | 無し | 秒 | 「どんな入力でも成り立つ性質」 |
| L3 | ユースケース | `use-case`（認可・冪等性・外部の事実の収集） | ScalaTest。出力ポートは手書きのフェイク | フェイク | ミリ秒〜秒 | 認可が入力検証より先、冪等性キー、ポートの呼び方 |
| L4 | アクター | 集約アクター、イベントシリアライザ（`command-adapter`） | pekko-actor-testkit-typed、pekko-persistence-testkit（インメモリの Journal） | インメモリ | 秒 | 永続化→返信の順、復元、イベントの往復と旧版 |
| L5 | 統合（DB） | 読み取りモデル、DAO、マイグレーション、冪等性キーの表 | ScalaTest + Testcontainers（PostgreSQL） | PostgreSQL の実物 | 秒〜数十秒 | SQL、制約、投影の冪等、マイグレーション |
| L6 | 統合（配信） | イベントストア→購読→読み取りモデル | Testcontainers（BE-03 が A なら LocalStack を加える） | 実物 | 数十秒 | 配信、再配信での冪等、順序の逆転 |
| L7 | 契約・往復 | Unit をまたぐ連携 17 本、外部ポートのスタブ | L5・L6 の上に構成 | 実物 | 数十秒 | 提供側のコマンド → 購読側の読み取りモデルに結果が現れる（検査 A9） |
| L8 | API | GraphQL（Mutation・Query・公開スキーマ） | ScalaTest + 実行中のアプリ | 実物 | 数十秒 | 業務エラーのコード、公開項目の固定、認可 |
| L9 | 適合性 | モジュール依存・import・イベント一覧（A1〜A9、F1〜F9） | sbt `dependsOn`、ArchUnit、ESLint | 無し | 秒 | 構造の規則 |
| L10 | E2E | 画面から踏む業務シナリオ | Playwright | ステージング相当の全体 | 分 | つながって動くこと、ロール別の到達性 |

- **L1 が主役**です。業務ルール（B・V・R・T・S・I の不変条件）は L1 で判別し、上の層で同じ条件を重ねて検査しません
- **L3 は Pekko を起動しません**。use-case が出力ポートを持つ設計（バックエンド 5.2）の目的がここにあります
- **L5 は PostgreSQL の実物だけで行います**。メモリ上の別 DB で代用しません（PostgreSQL 固有の型・制約・スキーマをデータモデルが使うため。TST-05）
- **L7 は連携の数だけ**置きます。1 つの Unit の内側で完結する検査は、購読側に届いていなくても緑になるためです

## 4. Unit 別の水準と技法

リリース計画の水準を、本書で次のように具体化します。

| 水準 | 意味 | 適用する技法 |
| :--- | :--- | :--- |
| **Standard** | 受入条件のすべてを判別し、異常系と境界値を押さえる | L1・L3・L4・L5・L8・L10（受入条件ごと）。状態 × コマンドの表。イベントの往復テスト。ロール × 操作の表 |
| **Comprehensive** | Standard に加え、性質で網羅し、守りが働くことを壊して確かめる | Standard + L2（プロパティ）+ **変異の確認**（[7.4](#74-守りを壊して確かめる)）+ 追加の異常系（攻撃者の視点・運用の視点）+ 監査証跡の検査 |

| Unit | 水準 | 重点 | 特記すべきテスト |
| :--- | :--- | :--- | :--- |
| U-01 認証 | **Comprehensive** | 認証失敗 5 回でロック（I1）、同一メッセージ、監査ログ、パスワード保存、セッションの破棄 | 方式が ADR で決まった後に具体化（BE-09）。**攻撃者の視点**：ユーザー列挙、総当たり、ロック中の正しいパスワード、戻る操作 |
| U-02 貨物予約 | **Standard** | 状態遷移（B1）、予約番号・追跡番号、キャンセル（承認・却下・料）、荷主の重複警告 | 状態 × コマンドの全組み合わせ。US30 の申請・承認・却下の履歴 |
| U-03 航海・経路設計 | **Comprehensive** | 制約条件 5 つ（R-04）、UN/LOCODE（R-09）、乗り継ぎ（R1）、航海番号の重複（V1） | `RouteFinder` のプロパティ。制約を 1 つ足すたびに、その制約を破る入力を拒むテストを足す |
| U-04 荷役・追跡 | **Standard** | 荷役種別と状態の整合（T1）、通関が引取の前提、例外の履歴、公開照会 | 反映時間の計測点（L6）。公開スキーマの項目の固定（A7）。存在しない番号と形式不正で同じ応答 |
| U-05 精算 | **Comprehensive** | 基本料金・割引・端数の計算（S1〜）、精算書、入金確認、二重請求の防止 | 金額のプロパティ（単調性・範囲・端数）。計算式が受入条件に定義されるまで実装しない（US21 AC-01） |

### 4.1 Unit ごとの重点の根拠

- **U-03 と U-05 が Comprehensive**なのは、誤りが業務上の損失に直結する（経路の誤りと金額の誤り）うえ、仕様が未確定の部分が多く、AI が推測で埋めやすいからです（R-04・U-05 の意図 HIGH）。例の検査だけでは「例が通る別の実装」を見逃すため、性質で網羅します
- **U-01 が Comprehensive**なのは、認証・認可がリスク HIGH（R-02）で、緑のテストと壊れ方の設計が別物だからです。守りは「入れたこと」でなく**「働くこと」**を検査します
- **U-02 と U-04 は Standard** です。ただし U-04 の公開照会（認証なし）だけは、U-01 に準じて攻撃者の視点の検査を加えます

## 5. カバレッジと数値目標

数値は**出発点の提案**で、ウォーキングスケルトン（Bolt 1）で実測してから確定します（TST-03）。カバレッジは「テストが足りているか」の十分条件ではなく、「触れていない場所」を見つける道具として使います。

### 5.1 カバレッジ目標（提案）

| 対象 | 行 | 分岐 | 根拠 |
| :--- | :---: | :---: | :--- |
| `domain`（全 Unit） | 90% 以上 | 85% 以上 | ガイドの目標。純粋で速く、投資効果が高い |
| `use-case` | 85% 以上 | 80% 以上 | ガイドの目標 |
| `command-adapter`・`query-adapter` | 70% 以上 | — | ガイドの目標。配線は L5〜L8 で確かめる |
| 全体 | 80% 以上 | — | ガイドの目標 |
| フロントエンド（`features/`） | 80% 以上 | — | ガイドに合わせた仮置き（要確認） |

- 閾値を下回ったらビルドを失敗にする（下げる方向のみ。閾値は**上げる一方**にして、緩めるには ADR を要する）
- **カバレッジの計測ツールは未確定**です。Scala 3 での対応状況を着手時に確認します（技術スタック 2.5。TST-03）
- 生成された DAO・Protobuf の生成コードは計測の対象外にする

### 5.2 変異テスト（Comprehensive の Unit のみ）

`domain` の守りが「通るテストがある」だけでなく「壊すと落ちる」ことを確かめるため、**Comprehensive の Unit（U-01・U-03・U-05）の `domain` に限って**変異テストを検討します。

- ツールは未選定です（Scala 向けの候補は着手時に確認。外部ツールの導入は承認が要る）。ガイドの目標値（変異を検出する割合 75%）を仮の出発点にします
- 導入しない場合の代替は、[7.4 の「守りを壊して確かめる」](#74-守りを壊して確かめる)を人手の規律として回す方法です
- **決定は Bolt 5（U-03 の経路算出）の前**。最初の Comprehensive の適用場所だからです（TST-04）

### 5.3 実行時間の目標（提案）

| 区分 | 目標 | 備考 |
| :--- | :---: | :--- |
| L1〜L4・L9（ユニット相当） | 1 分以内 | 開発者が TDD で手元で回す速さ。ガイドは 30 秒だが、Scala のコンパイルを含むため仮置き |
| L5〜L8（統合） | 5 分以内 | Testcontainers の起動を含む |
| L10（E2E） | 10 分以内 | ステージングで実行 |
| パイプライン全体 | 20 分以内 | 要確認 |

実測が目標を超えたら、検査を減らすのではなく**層を見直します**（重複する検査を下の層へ移す）。

## 6. 技法

### 6.1 ドメインの検査（L1）

集約の検査は、**「過去のイベント列を与え、コマンドを実行し、返るイベントまたは業務エラーを確かめる」**形に統一します。

```scala
// 形（疑似コード。命名・DSL は技術スタックの確定後に決める）
"予約確定" should "経路が紐付いた経路提案中の予約を確定できる" in {
  Given(events = bookingReceived, handedOver, routeBound)
    .When(ConfirmBooking(by = salesRep))
    .ThenEvents(BookingConfirmed(...))   // US13-AC02 に対応するテスト（確定が成功するケース）
}
"B1: 経路選択済でなければ予約の確定を拒む" in {   // 業務規則は B 番号で命名する
  Given(events = bookingReceived)
    .When(ConfirmBooking(by = salesRep))
    .ThenRejected(InvalidTransition(from = Received, command = "ConfirmBooking"))
}
```

- 状態を直接組み立てず、**イベント列から状態を作る**。状態の組み立てが本番の復元経路と同じになる
- 業務エラーは例外ではなく sealed な型で返るため、型で期待を書く
- **状態 × コマンドの全組み合わせ**は、ドメインモデルの遷移表から生成して検査する（[6.2](#62-状態遷移の網羅)）

### 6.2 状態遷移の網羅

貨物予約（8 状態）と貨物状態（9 状態）（受領待ち〜引取済・例外発生・対応中）は、**許される遷移だけ**を許します（D1）。

- 遷移表（状態 × コマンド → 次の状態または拒否）を**1 つのデータ**として持ち、そこから検査を生成する。許す遷移は成功を、表に無い組み合わせはすべて `InvalidTransition` を確かめる
- 表に載っていない状態やコマンドは**失敗にする**（載せ忘れが素通りしない。検査 A5 と同じ考え方）
- 状態モデルとの差分 11 件（[ドメインモデル 第 12 章](domain-model.md#12-状態モデルとの差分r-06)）は、差分ごとに遷移の検査を持つ。要件定義書の状態モデルを正とし、足した遷移は差分として明示されたものだけを許す（R-06）

### 6.3 プロパティテスト（L2）

| 対象 | 性質（例） | Unit |
| :--- | :--- | :--- |
| `RouteFinder` | 返る経路はすべて、区間が連続し（R1）、期限内に到着し、貨物種別に対応した航海だけを使い、港湾制約を満たす | U-03 |
| `RouteFinder` | 直行の経路があれば最優先候補になる。候補は推奨順に並ぶ（順序の基準は要確認） | U-03 |
| `RouteFinder` | 制約を緩めると候補は減らない（期限を延ばす、など） | U-03 |
| 基本料金 | 重量・距離が増えれば料金は減らない（計算式の確定後）。端数処理は常に 1 つの規則で決まる | U-05 |
| 法人割引 | 割引後の金額は 0 以上、基本料金以下。割引率 0〜30% の外は登録できない（US03 AC-03） | U-05 |
| UN/LOCODE | 実在する形式（国 2 文字 + 場所 3 文字）だけを受け付ける。標準の外は拒む | 共有 |
| 認証 | 失敗回数は 0 以上。5 回目でロックされ、成功で 0 に戻る | U-01 |

- **性質は例で補う**。例（境界値）で入口を固定し、性質で穴を探す
- ランダムな入力で港湾コードを作るときも、**実在する UN/LOCODE を使う**（R-09）

### 6.4 イベントと読み取りモデル（L4・L5・L6）

| 検査 | 内容 | 規則 |
| :--- | :--- | :--- |
| 往復 | 公開イベントをシリアライズ→デシリアライズして一致する | A5 |
| 旧版 | 固定した旧版のバイト列を読める | 9.2（バックエンド） |
| 一覧 | イベントの一覧から検査を生成し、載っていないイベントを失敗にする | A5 |
| 冪等な更新 | 同じイベントを 2 回、順序を入れ替えて流しても結果が同じ。追記専用の行（追跡イベントの履歴）が増えない | A6 |
| 再構築 | 読み取りモデルを捨て、イベントから作り直して同じになる | 6.2（バックエンド） |
| 載せ忘れ | 購読側が必要とする項目をイベントが運んでいる（読み取りモデルの列を並べて確かめる） | 6.2 |
| 反映時間 | イベントの発生時刻と反映時刻の差を測る点がある | 9.4（バックエンド）、R-08 |

### 6.5 結果整合（L8・L10）

コマンドが成功しても読み取りは遅れます（バックエンド 6.4）。

- L8：Mutation の応答の版を使い、Query が「その版以上になるまで」待つ検査（**同じ集約の読み取り**に限る）。上限を過ぎたときは「反映待ち」を返す
- **L6・L7（購読側・別の集約）の待ち方**：版は使えない。待つ条件は「**購読側に、元のイベント ID（causation）を持つ行が現れるまで**」とし、上限は NFR-P10 の p99（15 s）に揃える。時間切れのときは、**待避先の件数と購読の位置（オフセット）を出力**して原因を指す（時間切れだけを報告しない）
- **否定の検査**（二重に作られない・届かない）は時間待ちにしない。重複や不要なイベントを流した後に**目印のイベント（フェンス）を流し、その処理完了を待ってから**件数を確かめる。時間待ちだと、遅いだけで届いていない場合に偽の緑になる
- 順序逆転の検査（A6）は、バックエンド 6.2 の「版が飛んだら保留」と対で書く。期待値は「**後着で欠けが埋まった後に、順に適用される**」
- L10：**更新直後に一覧を開き、対象の行が見える**ことを画面から確かめる（F8）。識別子を握って API を叩かない

### 6.6 時刻と業務日付（BE-11）

- 現在時刻は `Clock` ポートから取る。テストは固定した `Clock` を差し込む。**「今日」を決めるのもテストの `Clock`** で、JVM の既定の時計を使わない
- 期限（日付）と到着（時刻付き）の比較は、**期限当日の時刻付き到着**を必ず入れる（日付と時刻付きを素朴に比べる境界の誤りを検出する）
- 業務タイムゾーンの基準が決まったら、その基準と異なる時刻帯（UTC）でも一度回す（F9）
- E2E の日時は共有のヘルパで作る。`toISOString()` を直接使わない

### 6.7 認可とロール

- ロール × 操作の表を 1 つ持ち、**全組み合わせを生成**して検査する（A8。画面の F5・F6 も同じ表から）
- 認可は入力検証より先。**権限の無いロールが不正な入力を送ったとき、入力の仕様でなく認可のエラーが返る**ことを確かめる
- 画面での出し分けは利便性で、権限の根拠はバックエンド。**画面で隠したボタンの操作を直接送って**、バックエンドが拒むことを確かめる

### 6.8 公開の追跡照会

| 検査 | 内容 | 規則 |
| :--- | :--- | :--- |
| 項目の固定 | 公開スキーマの項目一覧を固定し、増えたら失敗 | A7 |
| 個人情報 | 応答に荷主の氏名・住所・連絡先が無い | 8.2（バックエンド） |
| 同一の応答 | 存在しない番号と形式不正の番号で、応答が変わらない | US18 AC-03 |
| 回数制限 | 制限を超えると拒まれ、**ヘルスチェックは制限の対象外** | R-02 |
| 深さ・複雑さ | 深いクエリ・イントロスペクションが拒まれる | 8.2 |
| バンドル | 公開の入口が認証の仕組みと業務画面のコードを含まない | F7 |

### 6.9 マイグレーション（R-03）

- 空の PostgreSQL に全マイグレーションを数値順に適用できる
- **直前の版のスキーマにデータを入れたまま**、次の版を適用できる（既存行が読めなくなる不変条件の追加を検出する）
- 適用済みのマイグレーションを書き換えていない（チェックサムの検査）
- Unit ごとのスキーマをまたぐ外部キーが無い（`reference` への参照を除く）
- 適用前の差分は人が確認する。テストは「適用できること」を保証し、差分の妥当性は人が見る

### 6.10 外部ポート（R-01）

| 外部 | ポート | テスト |
| :--- | :--- | :--- |
| 通知 | `NotificationPort` | スタブが送信内容を記録し、**通知を伴うイベントごとに送信内容を確かめる**。送信の失敗が業務の状態を巻き込まないこと、失敗が記録されること |
| 決済機関 | `PaymentPort` | スタブ。入金確認をポート越しの通知として受け、**入金を二重に受けても精算が 1 回で完結する**こと |
| 港湾管理 | `PortFacilityPort` | 未使用（使う場面が出たら定義） |
| 税関 | なし | 手入力のため、ポートのテストは無い（UC21 の判断は ADR が未記録。BE-13） |

- スタブは**本物より甘くしない**。型が違う値を通すスタブは、本物が断る入力を通してしまう（F4）
- 実在サービスの API 仕様を想定したテストを書かない。仕様が決まったら契約テストを足す

## 7. AI-DLC と TDD の進め方

### 7.1 TDD の三原則は変えない

1. 失敗するテストを書くまで、本番コードを書かない
2. コンパイルが通らない、または失敗する範囲を超えてテストを書かない
3. 失敗しているテストを通す以上に本番コードを書かない

AI が回し、人が承認ゲートで検証します。**テストが先に失敗することを確認した記録**（Red の出力）を、Bolt の計画の各ステップに残します。

### 7.2 テストは「契約」として読める形にする

- 受入条件に対応するテストは、テスト名に**ストーリーと受入条件の番号**を含める（例：`US13-AC02 …`）。業務規則の検査（遷移の拒否など）は `B1`・`T1` のように**ドメインモデルの不変条件の番号**で命名し、AC 番号を付けない（付けると突き合わせが未検査の AC を「対応済み」と数える）。人が受入条件との対応を読める
- 1 テスト 1 振る舞い。Given/When/Then を分ける
- AI が書いたテストは、人が**全行を理解**してから承認する（ゲート）。分からないテストは受け入れない
- テストが緑でも、**テスト自体が正しい理由で緑か**を疑う（定義だけ書いて何も検査しないテスト、スタブが引数を捨てて組み立てを検査しないテストなど）

### 7.3 ゲート密度

リリース計画に従います。

| Unit | 既定のゲート | 下げる条件 |
| :--- | :--- | :--- |
| U-02・U-04（Standard、エントロピーに HIGH 無し） | 各サイクルで人が読む | Bolt 1 の変更依頼が少なければ「Green 完了時のみ」に下げる |
| U-01・U-03・U-05（Comprehensive、リスク HIGH） | 下げない。確認必須の操作（認証・スキーマ変更・外部連携）を含むステップで必ず停止 | — |

### 7.4 守りを壊して確かめる

**テストが緑であることは、守りが働いていることを意味しません。** 次の守りは、**壊して赤になる**ことを確かめます。

| 守り | 壊し方 | 赤になるべきテスト |
| :--- | :--- | :--- |
| 状態遷移の拒否（B1・T1） | 遷移表に許さない遷移を足す | 遷移の表の検査 |
| 通関済でなければ引取を拒む（US29 AC-04） | 条件を外す | 引取の拒否の検査 |
| 認可がユースケースの入口にある | 入口の検査を外す | 全組み合わせの検査（A8） |
| 冪等性キー | 検査を外して再送する | 二重登録の検査 |
| 読み取りモデルの冪等 | 重複を弾く条件を外す | 同じイベントを 2 回流す検査（A6） |
| 公開スキーマの項目の固定 | 項目を 1 つ足す | A7 |
| 経路の制約条件 | 制約を 1 つ外す | その制約を破る入力を拒む検査（R-04） |
| 金額の端数処理 | 切り捨てを四捨五入に変える | 端数の境界値 |

- **規律として回す**：Comprehensive の Unit の Bolt では、上の表の守りのうち、その Bolt が触れるものを**守りごとに 1 件**、壊して赤を確認した記録をステップに残す
- **記録の形**：(1) 壊した守り（表の行）、(2) 壊した差分（**本番コードだけ**を変え、テストファイルは変えていないことを示す）、(3) 赤になったテストと出力、(4) 元に戻した後の緑の出力。AI がテストの側を壊して赤にする誤りを防ぐため
- 変異テストのツールを導入した場合は、この確認を自動化する（TST-04）
- 「〜しない」と書いたコメントや設計の文は、書いただけで守れていない。**書いた保証は赤で固定する**

## 9. フロントエンドのテスト

| レベル | 対象 | 道具（技術スタック 3） | 守ること |
| :--- | :--- | :--- | :--- |
| 部品・フック | `components/`、各 feature の `hooks/` | Vitest + Testing Library | 表示、入力、状態の出し分け。サーバー状態は MSW で差し替える |

### 9.1 E2E の進め方

- **識別子を握って API を叩く検査にしない**。一覧から対象を選んで始める。一覧から辿れない欠陥を踏むため
- E2E は**業務シナリオ単位**で少数に絞る（下表）。受入条件ごとに E2E を書かない

| シナリオ | 通る Unit | 起点 | Bolt の目安 |
| :--- | :--- | :--- | :--- |
| 荷主登録 → 予約登録（仮受付） | U-02 | 営業担当者のホーム | 1（ウォーキングスケルトン） |

| 追跡番号の発行 → ログイン無しの照会 | U-02・U-04 | 公開の入口 | 8 |
| 荷役の記録 → 追跡情報の反映 → 引取（通関済） | U-04 | 荷役作業員のホーム（モバイル幅） | 10〜15 |

- 荷役作業員の E2E は**モバイル幅**で行う（UI 設計 P6）

## 10. テストデータ

| 方針 | 内容 |
| :--- | :--- |
| 架空の値 | 荷主・会社・船名・航海番号は架空でよい（リスク台帳）。ただし**港湾・都市のコードは実在する UN/LOCODE**（R-09）。出典を `reference` の初期データに示す |
| 作り方 | **Object Mother + ビルダー**。既定は妥当な値、検査したい項目だけを上書きする。ドメインの値オブジェクトを通して作り、**不正な状態を作れない**ようにする |
| 識別子 | ULID（集約）と業務番号（予約番号・追跡番号）を**本番と同じ採番の経路**で作る。テストだけの採番は、本番の採番との衝突や形式の違いを隠す |
| 時刻 | 固定した `Clock`。E2E は共有ヘルパ |
| 共有 DB | **自分が作った行だけを数え、名指しする**。全体の件数を数える検査は、別の変更で赤くなり原因を指さない |
| 分離 | 統合テストは Testcontainers の使い捨ての DB。テストごとにスキーマを初期化するか、独自の識別子で名前空間を分ける |
| 個人情報 | 実在の人物のデータを使わない |
| 失敗する条件 | 時間や期限で作らず、**構造で作る**（共有環境に溜まったデータでたまたま成功しない） |

## 11. 受入条件とのトレーサビリティ

### 11.1 対応のとり方

- ストーリーの受入条件（Given/When/Then、`AC-01`〜）は人と AI の契約です。**1 つの受入条件に 1 つ以上のテスト**を対応させ、テスト名にストーリーと AC の番号を含める（`US13-AC02`）
- 受入条件の番号から、どのレベルで検査するかを下表で決める。同じ振る舞いを複数の層で重ねない
- 対応の確認は**自動で行う**：ユーザーストーリーの AC 一覧と、テスト名の AC 番号を突き合わせ、**テストの無い AC を一覧にする**スクリプトを置く（Bolt 1 の計画に含める。TST-06）。書いただけで定義のない受け入れは何も検査しない

### 11.2 ストーリー別の対応

## 13. CI との連携と運用

[インフラ設計 6.1](architecture_infrastructure.md#61-パイプライン提案)のパイプラインに、レベルを次のように割り当てます。

```plantuml
@startuml
title テストの実行（パイプラインへの割り当て）

start
:プッシュ;
fork
  :バックエンド\nコンパイル・フォーマット\nL1・L2・L3・L4;
fork again
  :適合性 L9\n(A1〜A3, F1〜F3, F7);
fork again
  :フロントエンド\nlint・型生成・部品の検査;
end fork
:統合 L5・L6・L7・L8\n（PostgreSQL / LocalStack をコンテナで起動）;
:イメージのビルド・脆弱性走査;
if (main ブランチ?) then (yes)
  :ステージングへデプロイ;
  :E2E L10\n（一覧から対象を選んで始める）;
  :本番へのデプロイ【承認待ち】;
else (no)
endif
stop
@enduml
```

| 規則 | 内容 |
| :--- | :--- |
| 全体で通す | `sbt test` を**モジュールを絞らず全体で**通す。絞った実行だけで緑にしない（依存の規則の検査は全体で働く）。ローカルの品質ゲートも CI と同じコマンドで回す |
| 失敗の扱い | どの段階も失敗したらその先へ進まず、**失敗の段階が分かる通知**にする。赤は 1 つの意味にする（例：導入の失敗と検出を同じ赤にしない） |
| たまに落ちるテスト | 再実行で通ることを理由に進めない。**2 回目に見たら原因を追う**。待つのではなく、状態が整うまでの条件を明示する |
| 時間で守らない | 経過時間のアサートは、脆弱な実装に戻しても緑になる。**分岐の結果**（どの検査で落ちたか）で判定する |
| 配線 | 検査が走っていること自体を確かめる。入力を宣言しない設定読み取りの検査は、キャッシュで走らず、壊しても緑になる。シナリオ数・テスト数の下限で確かめる |
| 依存とイメージ | 依存ライブラリとイメージの脆弱性走査を CI に入れる（インフラ I） |
| 秘密情報 | 接続情報・鍵はリポジトリにもテストにも置かない。環境変数の値を AI は読まない（R-10） |
| ブランチ保護 | main へのマージは、必須の段階が緑のときだけ |

## 15. 未決事項と AI の仮定

### 15.1 人に確認する点

- テスト形状（TST-01）。特に U-01 をダイヤモンド型にすることと、全体の比率
- カバレッジの閾値（TST-03）。ガイドの値（ドメイン 90%、全体 80%）を出発点にしてよいか
- 変異テストを導入するか、手作業の規律で代替するか（TST-04）。ツールの導入は承認が要る
- 実行時間の目標（5.3）。パイプライン全体 20 分以内でよいか
- [11.3](#113-判定できない受入条件)の受入条件の確認。どれから先に解消するか（Bolt の順に従うのが自然）
- E2E をステージングで回すか、PR ごとに一時環境で回すか（運用要件定義と合わせて）
- 荷役作業員のモバイル端末の種類と、E2E で再現する画面幅
- 性能・負荷テストの目標値（非機能要件定義）

### 15.2 AI の仮定

- 比率（70/25/5）・カバレッジ・実行時間の数値は**仮置き**で、Bolt 1 の実測で確定する
- テストの道具（ScalaTest・ScalaCheck・Testcontainers・ArchUnit・Playwright など）は[技術スタック](tech_stack.md)の提案に従う。承認が済むまで確定でない
- 受入条件 120 件の数は、ユーザーストーリーの `**AC-nn**` の出現数に一致する
- 遷移表・ロール × 操作の表は、ドメインモデルとの整合を前提に、Bolt の中で作る
- 外部システムの実仕様が決まるまで、契約テストの中身は定義しない

### 15.3 次の設計活動

1. 運用要件（`analyzing-operation`）：E2E の実行環境、通知の送信先、ランブック
2. 非機能要件（[non_functional.md](non_functional.md)）の数値を 5.3・6.8 に反映する（合意後）
3. 承認後：ADR の作成（`creating-adr`）。BE・FE・IF・TS・TST・NF の各候補
4. 承認後：ウォーキングスケルトン（Bolt 1）の計画を `bolt_plan-1.md` に書く（TDD の最初の Red を含む）

# UI 設計：国際貨物輸送管理システム

[フロントエンドアーキテクチャ](architecture_frontend.md)が決めた構造（SPA、`features/` の Unit 対応、ロール別ナビゲーション、結果整合への対応、公開照会の分離）の上に載る、画面・遷移・操作を設計します。

- 入力: [ユーザーストーリー](../requirements/user_story.md)、[システムユースケース](../requirements/system_usecase.md)、[要件定義書](../requirements/requirements_definition.md)（状態モデル）、[Unit 定義](../requirements/units.md)、[リリース計画](../development/release_plan.md)、[バックエンドアーキテクチャ](architecture_backend.md)、[フロントエンドアーキテクチャ](architecture_frontend.md)、[用語集](glossary.md)
- 設計の方法は [UI 設計ガイド](../reference/UI設計ガイド.md)（オブジェクト指向 UI）に従います。画面遷移は PlantUML のステートチャート図、画面イメージは salt 図で書きます
- **画面の ID（SC-xx）は本書で採番した仮の識別子**です。ストーリーの受入条件（AC）を満たす画面を過不足なく置くことが目的で、レイアウトの細部（余白・色・文言）は実装の Bolt で詰めます
- 用語は[用語集](glossary.md)を正とします。画面の文言に、用語集が退けた語（ルート、経由地、見積り など）を使いません
- 承認前に実装へ進みません。本書にも AI の仮定と要確認を残してあります（[第 11 章](#11-未決事項と-ai-の仮定)）

## 1. 設計の方針

| # | 方針 | 理由 |
| :--- | :--- | :--- |
| P1 | **オブジェクトを中心**に画面を作る。メニューは「予約」「航海」「貨物追跡」のようなオブジェクト名で並べ、操作は一覧と詳細の中のボタンにする | ロールごとに業務は違うが、扱うモノは共通。UI 設計ガイドの原則 |
| P2 | 各ロールに**作業入口**（ホームの件数とリンク）を置く。件数や警告は、必ず対象の絞り込み済み一覧へのリンクを持つ | 気づいても、そこから行けなければ仕事が進まない |
| P3 | 状態によって出す操作を変える。出し分けの根拠は画面で再判定せず、読み取りモデルが返す「実行できる操作」の項目を使う | 集約の述語と画面の判定がずれると、押せるのに失敗するボタンが生まれる |
| P4 | 書き込み直後の画面は、反映の遅れ（結果整合）を前提にする。成功後に自分が作ったものが一覧に見える | バックエンド 6.4、フロントエンド 3.2 |
| P5 | 取り返しのつかない操作と、業務上の警告の承認は、確認を挟む。取り消す側（キャンセル・却下）には余計な確認を置かない | 誤操作を防ぎ、必要な判断は流れを止めない |
| P6 | 荷役作業員の画面はモバイルファーストで、最小の入力で完結する。他のロールは PC を主とし、モバイルでも崩れない | 要件定義書（モバイル対応の荷役作業記録） |
| P7 | 画面は**権限の根拠ではない**。隠すのは利便性のためで、直接 URL でも操作でも、拒否はバックエンドが行う | フロントエンド 5.1 |
| P8 | 公開の追跡照会は、業務画面と枠・コード・エンドポイントを分ける | フロントエンド 5.3 |

## 4. ロール別のナビゲーション

### 4.1 メニューとホームの作業入口

メニューはオブジェクト名で並べます（左サイドナビゲーション。荷役作業員のモバイルだけ下部のタブ）。ホームの件数は、対象の絞り込み済み一覧へのリンクです。

| ロール | メニュー | ホームの作業入口（件数 → リンク先） |
| :--- | :--- | :--- |
| 営業担当者 | 荷主（SC-20）、見積（SC-24）、予約（SC-25） | 仮受付の予約 → SC-25（状態＝仮受付）／経路が紐付き通知待ちの予約 → SC-25（状態＝経路提案中・経路選択済）／承認待ちの自分のキャンセル申請 → SC-25（絞り込み） |
| 経路設計者 | 予約（SC-25）、航海（SC-40） | 経路設計の依頼待ち → SC-25（状態＝経路提案中）／追跡番号の発行待ち → SC-25（状態＝予約確定）／誤配が起票された予約 → SC-25（誤配あり）。再設計の担当はこのロール |
| 追跡管理者 | 貨物追跡（SC-52）、例外（SC-56）、通関（SC-58）、キャンセル承認（SC-30） | キャンセル承認待ち → SC-30／例外発生中（誤配・紛失は緊急を先頭）→ SC-56／留置 3 日超 → SC-58（留置・超過）／対応中の貨物 → SC-52（状態＝対応中） |
| 荷役作業員（モバイル） | 荷役記録（SC-50）、通関（SC-57・SC-58）、例外報告（SC-55） | ホームは持たず、ログイン直後に SC-50 を開く（最小の操作で記録に着手するため） |
| 経理担当者 | 精算対象（SC-70）、精算（SC-73） | 料金算出待ち → SC-70／支払い期限超過 → SC-73（期限超過） |
| 荷主 | 追跡照会（SC-10） | 追跡番号の入力のみ。**予約・精算の閲覧をさせるかは要確認** |
| システム管理者 | アカウント（SC-04） | ロック中のアカウント → SC-04（状態＝ロック） |

## 6. 画面イメージ

ウォーキングスケルトン（Bolt 1）の画面から順に、主要な画面の配置を示します。情報の優先順位とグルーピングを表すもので、ピクセルの精度は持ちません。画面の例に使う港湾コードは実在する UN/LOCODE（東京 `JPTYO`、シンガポール `SGSIN`、ロッテルダム `NLRTM`）で、荷主名・番号は架空です。追跡番号と予約番号の**形式は未定**（バックエンド 4.4）のため、`T-XXXX` のように仮の表記にします。

## 7. インタラクション設計

### 7.1 主要シナリオ

**S1 荷主を登録して予約を仮受付にする（ウォーキングスケルトン。US02, US04）**

1. 営業担当者が SC-20 の「新規登録」から SC-21 を開く。
2. 荷主種別・氏名・住所・連絡先・メールアドレスを入力して「登録」を押す。
3. システムが荷主を登録し、荷主 ID を発行して SC-22（荷主詳細）を表示する。
4. 「予約を登録」で SC-26 を開く。荷主は選択済みで、貨物仕様と輸送条件を入力して「登録」を押す。
5. システムが予約番号を発行し、状態「仮受付」で SC-27 を表示する。画面は応答の版以上になるまで取得して表示する。
6. 営業担当者が SC-25 を開くと、登録した予約が一覧にある（結果整合の検査項目）。

**S2 経路を設計し、予約に紐付けて荷主に通知する（US07〜US12）**

1. 経路設計者がホームの「経路設計の依頼待ち」から SC-25 を開き、予約を選んで SC-27 から「経路を設計」で SC-44 を開く。
2. 検索条件を確認して検索する。候補が出たら 1 件選んで「確定」を押す。
3. SC-46 で確定経路と予約番号を確認し、「予約に紐付ける」を押す。SC-27 に戻る。
4. 営業担当者のホームに「経路が紐付き通知待ち」の件数が出る。SC-27 の「経路を通知」で SC-47 を開き、通知内容を確認して送信する。
5. 荷主が経路を承認したら、営業担当者が SC-27 で「予約を確定」を押す。

**S3 荷役作業を記録する（荷役作業員。US15, US28 AC-01・02）**

1. 荷役作業員がログインすると SC-50 が開く。追跡番号を入力する。
2. 作業種別・日時・場所を確認する。場所が予定経路外なら SC-51 の警告が出る。
3. 「承認して登録」を選ぶと、記録され、誤配が起票される。追跡管理者と経路設計者のホームの件数が増える。

**S4 輸送中の予約のキャンセルを承認する（US30）**

1. 営業担当者が SC-27 の「キャンセル（要承認）」で SC-29 を開き、理由を入力して申請する。
2. 追跡管理者のホームの「キャンセル承認待ち」が増える。SC-30 → SC-31 を開く。
3. 陸揚げ地を選んで承認するか、理由を入力して却下する。結果は SC-27 の履歴に残り、営業担当者に通知される。

**S5 通関を管理して引取に進める（US29）**

1. 荷役作業員が荷降しを記録した後、SC-57 で申告番号・申告日時を登録する（状態は「審査中」）。
2. 追跡管理者が SC-59 で理由を入力して状態を更新する。「留置」にすると例外が起票され、3 日を超えると SC-58 の行に警告が出てホームの件数に入る。
3. 「通関済」になった貨物だけ、SC-50 で「引取」を選べる。

**S6 料金を算出して精算する（US21〜US23）**

1. 配送完了（貨物状態「引取済」）の予約が SC-70 に現れる。経理担当者が選んで SC-71 を開く。
2. 基本料金と割引を確認し、例外があれば料金調整を入力して「確定」を押す。
3. SC-72 で精算書を発行する。入金が確認されると精算済になる。

### 7.2 操作パターンの統一

| 操作 | パターン | 適用 |
| :--- | :--- | :--- |
| 作成 | ブランクのフォームを開く。作成後は作成したオブジェクトの詳細へ移る | 荷主、予約、航海、見積 |
| 更新 | 詳細から編集に入り、確認画面（差分）を経て保存する。軽い更新は同じ画面で行う | 航海の更新は確認画面あり。貨物状態の更新は同じ画面 |
| 状態の遷移 | 詳細の操作ボタン。押せない状態では**ボタンを出さない**（無効表示にしない）。出す根拠は読み取りモデルの「実行できる操作」 | 予約の確定、追跡番号の発行、経路の確定 |
| 取り消し系 | 理由の入力が必須のダイアログ。確認の追加は置かない（理由の入力が確認を兼ねる） | キャンセル申請、却下、通関状態の更新 |
| 警告の承認 | 登録の前に警告のダイアログを出し、「中断」と「承認して続行」を並べる | 予定外の作業場所 |
| 一覧 | 検索・絞り込み、状態の列、行を選ぶと詳細。新規登録は一覧の右上 | すべての一覧 |
| 件数のリンク | 絞り込み条件を引き継いだ一覧を開く | ホーム |

### 7.3 コマンドの重複を防ぐ

- 送信ボタンは押した直後から応答まで無効にする（連打を防ぐ）
- 同じ画面から再送するとき、冪等性キーは同じにする（フロントエンド 4.2）。画面を開き直すと新しいキーにする
- 通信エラーで結果が分からないときは、「結果を確認する」ボタンで読み取りを取り直し、登録済みかを見てから再送を促す

## 8. エラー・フィードバックの設計

### 8.1 エラーの種類と表示

| 種類 | 例 | 表示の場所と文面 | 回復の方法 |
| :--- | :--- | :--- | :--- |
| 入力の検証（クライアント） | 必須項目の未入力、割引率の範囲外、出発日が到着日より後 | 欄の下に赤字で理由。送信時に最初のエラー欄へフォーカスを移す | 修正して再送 |
| 業務エラー（サーバー） | 不正な状態遷移、同じ航海番号、通関済でない貨物の引取 | 本文上端の帯に、原因と現在の状態を出す（例：「通関状態は『審査中』です」） | 帯のリンクから状態を確認する |
| 権限（403） | 権限の無い画面・操作 | SC-03 に移る。ホームへ戻る導線を置く | ホームへ戻る |
| 認証切れ（401） | セッション切れ | SC-01 へ。「ログインし直してください」を出す。入力途中の内容を失う旨 | 再ログイン |
| 通信エラー | 接続不能 | 帯に「通信できません。もう一度お試しください」と「再試行」。入力は保持 | 再試行（同じ冪等性キー） |
| タイムアウト | 応答が遅い | 通信エラーと同じ。ただし「処理は完了している可能性があります。結果を確認してください」を添える | 結果を確認する |
| 反映待ち | 書き込み後に読み取りが追いつかない | 帯に「反映を待っています」。上限時間を超えたら「反映に時間がかかっています。更新してください」と手動の更新を出す | 更新 |
| 回数制限（公開照会） | 短時間の多数の照会 | 「しばらくしてからもう一度お試しください」 | 時間をおく |
| 想定外のエラー | 500 など | 帯に「問題が発生しました」と問い合わせ用の相関 ID | 管理者に連絡 |

- 上限時間・再試行の間隔・タイムアウトの秒数は**非機能要件定義で決める**（本書では決めない。提案は[非機能要件 NFR-P11・P12](non_functional.md)：上限 15 秒、間隔 500 ms から 2 秒まで）
- 認証の失敗とロックでは、画面でも**同じ文面**にする。無効化だけ別の案内（管理者への問い合わせ）

### 8.2 バリデーションの規則

- 入力の検証は「その場で分かるもの」だけクライアントで行う（必須、範囲、形式）。**業務の規則はサーバーが判定し、画面は結果を表示するだけ**にする（画面に規則の写しを持たない）
- 期限と到着の比較など、日付と日時にまたがる判定は画面で行わない（バックエンドの判定を表示する）
- UN/LOCODE は選択式で入力させ、形式の誤りを画面で防ぐ。実在しないコードの判定はサーバーが行う

### 8.3 確認とフィードバックの原則

- 成功は帯で一言（「登録しました」＋次の操作へのリンク）。モーダルで止めない
- 状態が変わる操作の後は、詳細の状態表示が更新されるのを確認してから成功を出す（結果整合）
- 取り消せない操作（確定・発行）の前だけ、確認の文を添える。確定ボタンのラベルに結果を書く（「予約を確定」）

### 8.4 反映待ち（結果整合）の見せ方

```plantuml
@startuml
title 書き込み後の画面の流れ

actor 利用者
participant 画面
participant "command-api" as C
participant "query-api" as Q

利用者 -> 画面 : 「登録」
画面 -> C : Mutation（冪等性キー）
C --> 画面 : ID と最後の版
画面 -> 画面 : 「反映を待っています」の帯
loop 版が追いつくまで（上限時間まで）
  画面 -> Q : 取得
  Q --> 画面 : 読み取りモデルの版
end
alt 追いついた
  画面 -> 利用者 : 詳細を表示し「登録しました」
else 上限時間を過ぎた
  画面 -> 利用者 : 「反映に時間がかかっています」と［更新］
end
@enduml
```

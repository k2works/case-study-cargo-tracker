# 非機能要件定義 - 国際貨物輸送管理システム

## 概要

本ドキュメントは、国際貨物輸送管理システム（7 マイクロサービス + React SPA）の非機能要件を測定可能な形で定義する。ISO/IEC 25010 品質モデルに基づき、性能・セキュリティ・可用性・保守性・拡張性の 5 カテゴリで数値目標を設定する。

本定義は take-3 の非機能要件を基礎とし、本プロジェクトの要件差分
（アカウント保護 US31・通関監査 UC21・キャンセル承認 UC22・公開追跡照会・kind / Heroku / AWS の 3 環境構成）を反映している。

### 品質属性の優先順位

| 優先度 | 品質属性 | 根拠 |
| :--- | :--- | :--- |
| 1 | **セキュリティ** | 国際貨物輸送は規制産業。荷主情報・通関情報の保護と監査証跡（通関状態変更・キャンセル承認・認証試行）が最優先 |
| 2 | **可用性** | 荷役作業は 24 時間稼働。追跡情報のリアルタイム性が業務に直結 |
| 3 | **性能** | 追跡照会のポーリング（30 秒間隔）と荷役登録の応答速度がユーザー体験を左右 |
| 4 | **保守性** | 7 マイクロサービスの独立デプロイ・運用を持続可能にする |
| 5 | **拡張性** | 港湾・航路の追加、新規貨物種別への対応 |

## 2. セキュリティ要件

### 2.1 認証・認可

| 要件 | 仕様 | 実装方式 |
| :--- | :--- | :--- |
| 認証方式 | JWT Bearer Token | authms が発行、API Gateway が検証 |
| トークン有効期限 | アクセストークン: 1 時間、リフレッシュトークン: 7 日 | Zustand ストアで管理 |
| パスワードポリシー | 8 文字以上、英数字混在必須 | BCrypt (strength 12) でハッシュ化 |
| アカウントロック | 認証失敗 5 回連続で 15 分ロック。ロック中と認証情報誤りで**同一エラーメッセージ**を返す（列挙攻撃防止） | `users.failed_attempts` / `locked_until` カラム永続化（US31） |
| ロック解除 | ロック期限経過で自動解除。管理者（`ROLE_ADMIN`）による手動解除も可 | authms |
| 認可モデル | RBAC（Role-Based Access Control） | Spring Security `@PreAuthorize` |
| API エンドポイント保護 | 全 API に認証必須。例外は `GET /api/v1/tracking/**`（公開追跡照会）のみ | API Gateway JWT フィルタ |
| 公開エンドポイントの防御 | 追跡照会は追跡番号の推測困難性 + レートリミットで保護（ヘルスチェックはレートリミット対象外） | API Gateway |
| CORS | フロントエンドオリジンのみ許可 | Spring Cloud Gateway CORS 設定 |

### 2.2 ロールと権限

| ロール | 権限範囲 | 対応アクター |
| :--- | :--- | :--- |
| `ROLE_ADMIN` | 全操作 + ユーザー管理 + アカウントロック解除 | システム管理者 |
| `ROLE_SALES` | 見積・荷主登録・予約登録/確定・キャンセル申請 | 営業担当者 |
| `ROLE_ROUTING` | 航海スケジュール管理・経路候補算出・経路確定・追跡番号発行 | 経路設計者 |
| `ROLE_TRACKER` | 追跡情報更新・例外対応・通関状態管理・キャンセル承認/却下 | 追跡管理者 |
| `ROLE_HANDLER` | 荷役作業登録・通関申告登録 | 荷役作業員 |
| `ROLE_ACCOUNTANT` | 輸送料金算出・割引適用・精算処理 | 経理担当者 |
| `ROLE_SHIPPER` | 自身の予約照会・追跡照会・キャンセル申し出 | 荷主 |
| （認証不要） | 追跡番号による追跡照会のみ | 荷受人・荷主 |

### 2.3 データ保護

| 保護対象 | 対策 | 備考 |
| :--- | :--- | :--- |
| 通信経路 | TLS 1.3（ACM 証明書） | ALB 終端 + 内部通信は VPC 内。Heroku 開発環境は Heroku SSL、CloudAMQP は AMQPS |
| パスワード | BCrypt ハッシュ (strength 12) | 生パスワードを保存しない |
| DB 保存データ | RDS 暗号化（AES-256） | AWS KMS マネージドキー |
| S3 監査ログ | SSE-S3 暗号化 | バケットポリシーでアクセス制限 |
| 個人情報 | 荷主名・メールアドレスは最小限保持 | 不要になったデータは削除 |

### 2.4 監査ログ

| ログ種別 | 記録内容 | 保存先 | 保持期間 |
| :--- | :--- | :--- | :--- |
| 認証ログ（auth_audit_log） | ログイン成功/失敗・ロック発生/解除、IP アドレス、User-Agent。**追記専用** | auth_db + S3 | 1 年 |
| 通関状態変更履歴（customs_status_history） | 変更前後の状態・日時・変更者・**理由（必須）**。**追記専用** | handling_db | 7 年 |
| キャンセル承認記録 | 申請者・理由・承認/却下者・陸揚げ地・日時 | booking_db（cancellation_request） | 5 年 |
| 操作ログ | 誰が・いつ・何を操作したか | CloudWatch Logs | 1 年 |
| API アクセスログ | リクエストパス・ステータスコード・レスポンスタイム | CloudWatch Logs | 90 日 |

> 追記専用テーブル（auth_audit_log / customs_status_history）は UPDATE / DELETE を発行しないことを
> テストで固定する（「安全装置は破るテストで固定する」の規律）。

### 2.5 脆弱性対策（OWASP Top 10）

| 脅威 | 対策 |
| :--- | :--- |
| A01 アクセス制御の不備 | RBAC + API Gateway での一元的な認可チェック。公開エンドポイントは追跡照会のみに限定 |
| A02 暗号化の失敗 | TLS 1.3、BCrypt、RDS 暗号化 |
| A03 インジェクション | MyBatis パラメータバインディング（SQL インジェクション防止） |
| A05 セキュリティ設定ミス | Spring Security デフォルト拒否、不要なエンドポイント無効化 |
| A07 認証の不備 | JWT + リフレッシュトークン、アカウントロック（5 回失敗で 15 分）、同一エラーメッセージによる列挙防止 |
| A09 ログと監視の不足 | 構造化ログ + 追記専用監査テーブル + CloudWatch アラート |

## 3. 可用性要件

### 3.1 稼働率目標（SLA）

| 環境 | 稼働率目標 | 年間許容ダウンタイム | 計画停止 |
| :--- | :--- | :--- | :--- |
| 本番（AWS ECS） | 99.9% | 8.77 時間 | 月 1 回、深夜 2:00-4:00 |
| ステージング（AWS ECS） | 99.0% | 87.6 時間 | 随時 |
| 開発（Heroku） | 95.0% | 438 時間 | 随時。H2 メモリ DB のため再起動でデータ消失を許容 |
| ローカル（kind） | - | - | 開発者管理 |

### 3.2 障害復旧目標

| 指標 | 目標値 | 備考 |
| :--- | :--- | :--- |
| RTO（復旧時間目標） | 4 時間以内 | 重大障害（全サービス停止）の場合 |
| RPO（復旧時点目標） | 1 時間以内 | RDS 自動バックアップの頻度に依存 |
| MTTR（平均復旧時間） | 30 分以内 | 単一サービス障害の場合 |
| 障害検知時間 | 5 分以内 | CloudWatch アラート + ヘルスチェック |

### 3.3 障害許容性

| 障害シナリオ | 影響範囲 | 対策 | 復旧方法 |
| :--- | :--- | :--- | :--- |
| 単一サービス障害 | 該当サービスの機能のみ | ECS タスク自動再起動（ヘルスチェック） | 自動復旧（30 秒以内） |
| DB 障害 | 該当サービスの読み書き | RDS Multi-AZ フェイルオーバー | 自動復旧（1-3 分） |
| RabbitMQ 障害 | サービス間非同期通信 | Amazon MQ クラスター構成 + DLQ | 自動復旧 + メッセージ再送 |
| AZ 障害 | 該当 AZ のサービス | マルチ AZ デプロイ | ALB がヘルシーな AZ に振り分け |
| API Gateway 障害 | 全 API リクエスト | 最低 2 タスクの冗長構成 | ECS 自動再起動 |
| イベント消費失敗 | 追跡/請求の状態同期 | DLQ 滞留アラート（> 0 で通知） | 再投入手順書に従い手動再処理 |

### 3.4 ヘルスチェック

| サービス | エンドポイント | チェック間隔 | タイムアウト | 失敗閾値 |
| :--- | :--- | :--- | :--- | :--- |
| 全マイクロサービス | `/actuator/health` | 30 秒 | 10 秒 | 3 回連続失敗で再起動 |
| API Gateway | `/actuator/health` | 15 秒 | 5 秒 | 2 回連続失敗で再起動 |
| RDS | `pg_isready` | 10 秒 | 5 秒 | 5 回連続失敗でアラート |
| RabbitMQ | AMQP 接続確認 | 30 秒 | 10 秒 | 3 回連続失敗でアラート |

> ヘルスチェック（liveness / readiness）はレートリミット等の横断的防御の**対象外**とする。
> 一律適用すると過負荷時に liveness が 503 を返し再起動ループに陥る。

### 4.5 時刻の扱い

| 項目 | 方針 |
| :--- | :--- |
| 業務日付の判断 | 業務タイムゾーン（Asia/Tokyo）の `Clock` を DI し、UTC で日付判断しない |
| DB 保存 | TIMESTAMP は UTC で保存し、表示時に業務 TZ へ変換 |
| テスト | 本体と同じ `Clock` を注入して「今日」を決める。CI（UTC）でも一度回して検証 |

## 非機能要件サマリー

| カテゴリ | 主要指標 | 目標値 |
| :--- | :--- | :--- |
| **性能** | API レスポンスタイム p95 | 500ms-1.5s（操作による） |
| **性能** | 追跡照会（公開） p95 | 300ms |
| **性能** | 同時接続ユーザー数 | 100 名（ピーク 200 名） |
| **セキュリティ** | 認証方式 | JWT + RBAC（公開は追跡照会のみ） |
| **セキュリティ** | アカウントロック | 5 回失敗で 15 分・同一エラーメッセージ |
| **セキュリティ** | 監査ログ | 追記専用（認証 1 年・通関 7 年） |
| **可用性** | 稼働率 (SLA) | 本番 99.9% |
| **可用性** | RTO / RPO | 4 時間 / 1 時間以内 |
| **保守性** | テストカバレッジ | 80% 以上（ドメイン層 90%） |
| **保守性** | アーキテクチャ検証 | ArchUnit 違反 0 件 |
| **拡張性** | 水平スケーリング | CPU 70% で自動スケールアウト |

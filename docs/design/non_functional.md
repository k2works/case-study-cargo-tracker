# 非機能要件 - 国際貨物輸送管理システム

## 概要

国際貨物輸送管理システムの非機能要件を ISO/IEC 25010 品質モデルに基づき定義する。すべての要件は **測定可能** であり、テスト戦略（`test_strategy.md`）と運用要件（`operation.md`）で検証可能となるよう数値目標を明示する。

Axon Framework 5 + マイクロサービス + Event Sourcing アーキテクチャ固有の要件（コマンド処理レイテンシ・Projection 追従遅延・Event Store 書き込み TPS など）も含める。

## 業務上の想定規模

ビジネス目標（インセプションデッキ）と業務量を踏まえた前提値。

| 指標 | 値 | 根拠 |
| :--- | :--- | :--- |
| 同時利用者数（業務時間内） | 100 名 | 営業 30 + 経路設計 10 + 追跡管理 20 + 荷役 30 + 経理 10 |
| 同時利用者数（ピーク） | 300 名 | キャンペーン期・繁忙期想定 |
| 年間予約件数 | 100,000 件 | 1 日平均 274 件 |
| 1 予約あたりの平均イベント数 | 30 件 | 予約 → 経路 → 追跡 → 荷役 → 精算 |
| 年間ドメインイベント数 | 約 300 万件 | Event Store の容量目安 |
| 1 予約あたりの平均 Leg 数 | 2.5 | 直行 + 1 回中継 |
| 平均輸送期間 | 30 日 | 同時に追跡中の貨物 = 約 8,300 件 |
| 荷主数（5 年累計） | 30,000 | 個人 60% / 法人 40% |
| 航海スケジュール登録数 | 月 500 件、累計 30,000 件 | |

## 1. 性能効率性（Performance Efficiency）

### 1.1 応答時間（レスポンスタイム）

操作種別ごとに p50 / p95 / p99 を定義する。計測は本番に近いデータ量のステージング環境で実施。

| 操作種別 | 例 | p50 | p95 | p99 |
| :--- | :--- | :--- | :--- | :--- |
| 認証・JWT 発行 | ログイン | 200ms | 500ms | 1.0s |
| 単純な Read Model 照会 | 予約詳細・追跡照会 | 200ms | 500ms | 1.0s |
| 一覧 Query（最大 100 件） | 予約一覧・荷主一覧 | 300ms | 800ms | 1.5s |
| 経路候補算出（複雑な Domain Service） | UC06 経路候補算出 | 500ms | 1.5s | 3.0s |
| Command 受領（202 Accepted まで） | 予約登録・状態更新 | 200ms | 500ms | 1.0s |
| Command → Read Model 反映（結果整合性） | 予約登録後の一覧反映 | 1.0s | 3.0s | 5.0s |
| Saga 完了（予約 → 経路 → 追跡発行） | `BookingSagaManager` 全体 | 5.0s | 10s | 15s |
| ファイル添付なしの一般ページ初回表示（LCP） | ダッシュボード | 1.5s | 2.5s | 4.0s |
| ページ遷移（クライアントサイド） | SPA 内部遷移 | 100ms | 300ms | 500ms |

## 2. 信頼性（Reliability）

### 2.1 稼働率（SLA）

| 環境 | 稼働率目標 | 月間許容ダウンタイム | 年間許容ダウンタイム |
| :--- | :--- | :--- | :--- |
| 本番（営業時間内 平日 8:00–20:00 JST） | **99.9%**（フェーズ 1）／ **99.95%**（フェーズ 2） | 約 13 分 / 約 22 分 | 約 2.6 時間 / 約 4.4 時間 |
| 本番（24 時間） | **99.5%**（フェーズ 1）／ **99.9%**（フェーズ 2） | 約 3.6 時間 / 約 43 分 | 約 43.8 時間 / 約 8.8 時間 |
| 公開追跡照会（S15 / `/tracking/:tn`） | **99.9%**（フェーズ 1、24 時間）／ **99.95%**（フェーズ 2） | 約 43 分 / 約 22 分 | 約 8.8 時間 / 約 4.4 時間 |
| ステージング | 99% | 約 7 時間 | 約 88 時間 |
| 開発環境 | ベストエフォート | - | - |

計画停止（メンテナンス）は稼働率から除外する。月 1 回・夜間 1 時間以内を想定。

> **フェーズ別 SLA の根拠**: フェーズ 1 は Heroku 上の単一 dyno 前提で、再起動運用での MTTR は数分〜十数分。四半期 1 回の障害発生で 99.95% は破る確率が高いため、フェーズ 1 は **業務時間内 99.9% / 24 時間 99.5%** を上限とする。フェーズ 2 では冗長構成へ移行し 99.95% を目指す。詳細は [ADR-0001](../adr/0001-axon-framework-adoption.md) を参照。

### 2.2 障害許容性

| 観点 | 要件 |
| :--- | :--- |
| アプリ層単一サービスの障害 | Heroku dyno の自動再起動と Health Check で自動復旧、ユーザー影響 5 分以内 |
| サービス間連携の障害 | Circuit Breaker（Resilience4j）で fail-fast、Saga が補償処理を実行 |
| Aiven Kafka の障害 | マネージドサービスの冗長構成による自動回復。アプリ層のリトライ機構（指数バックオフ）で吸収。最大 5 分の Command/Event 受付不可は許容 |
| RDS の障害 | Multi-AZ 構成で自動フェイルオーバー、RTO < 60 秒 |
| 外部 ACL（決済機関・通知・税関）の障害 | リトライ + Circuit Breaker、業務継続性のため Saga の補償処理を準備 |

### 2.3 回復性

| 指標 | 値 |
| :--- | :--- |
| 検知時間（MTTD） | < 5 分 |
| 初期対応（一次切り分け） | < 15 分 |
| 軽微な障害の RTO | < 30 分 |
| 重大な障害の RTO | **< 4 時間** |
| RPO（Read Model） | **< 1 時間**（RDS 自動スナップショット粒度） |
| RPO（Event Store、フェーズ 1） | **< 1 時間**（Aiven Kafka のメッセージ保持 + S3 ストリーミングエクスポート） |
| RPO（Event Store、フェーズ 2） | **< 5 分**（Aiven Kafka の冗長レプリケーション） |
| データ整合性 | 集約単位で ACID、サービス間は結果整合性（Saga 補償） |

### 2.4 成熟性

| 指標 | 値 |
| :--- | :--- |
| 重大欠陥（Severity 1）発生率 | リリース後 30 日で 0 件 |
| 中程度欠陥（Severity 2）発生率 | リリース後 30 日で < 3 件 |
| 平均故障間隔（MTBF） | > 720 時間（30 日） |

## 3. セキュリティ（Security）

### 3.1 認証・認可

| 項目 | 内容 |
| :--- | :--- |
| 認証方式 | JWT（HS512 または RS256）+ リフレッシュトークン |
| アクセストークン有効期限 | **24 時間**（業務時間内の利便性） |
| リフレッシュトークン有効期限 | **7 日**（社内ツール想定） |
| 多要素認証（MFA） | 管理者ロール（`ROLE_ADMIN`）は必須、その他は推奨 |
| パスワードポリシー | 最低 12 文字、英大文字・小文字・数字・記号のうち 3 種類以上、漏洩リスト（HIBP）チェック |
| パスワードハッシュ | BCrypt（ストレッチ 12）または Argon2id |
| ロックアウト | 5 回連続失敗で 15 分ロック、ログ記録、管理者通知 |
| 認可モデル | RBAC（ロール: `SHIPPER`, `SALES`, `ROUTING`, `TRACKER`, `HANDLER`, `ACCOUNTANT`, `ADMIN`）+ リソースベース制約 |
| API 保護 | API Gateway での JWT 検証 + 各サービスでロール・スコープ確認 |
| 公開追跡照会 | 認証不要だが、追跡番号は推測困難（`TRK-` + 大文字英数 10 桁 = 約 1.5×10^17 通り） |

### 3.2 通信暗号化

| 区間 | 方式 |
| :--- | :--- |
| クライアント ↔ Heroku ルーター | TLS 1.3 強制（TLS 1.2 は当面互換維持） |
| Heroku ルーター ↔ アプリ層 | Heroku 内部通信、追加で mTLS 推奨（将来） |
| アプリ層 ↔ RDS | TLS 必須、サーバ証明書検証 |
| アプリ層 ↔ Aiven Kafka | TLS 1.3（SASL/SSL） |
| アプリ層 ↔ 外部 ACL（決済・通知・税関） | TLS 1.3、相手側証明書ピンニング検討 |
| 暗号スイート | AEAD のみ許可（AES-GCM、CHACHA20-POLY1305） |

### 3.3 保存データの暗号化

| データ | 暗号化方式 |
| :--- | :--- |
| RDS（PostgreSQL） | AWS RDS 暗号化（AES-256, KMS 管理） |
| Aiven Kafka（Event Store） | Aiven マネージド暗号化（AES-256） |
| S3（バックアップ・ログ） | SSE-KMS |
| 個人情報（メール・電話など）の項目暗号化 | アプリ層で AES-256 GCM、鍵は AWS KMS（年次ローテーション） |
| シークレット（DB 認証情報・API キー） | AWS Secrets Manager、自動ローテーション |

### 3.4 監査ログ（責任追跡性）

| 項目 | 内容 |
| :--- | :--- |
| 監査対象操作 | 認証成功・失敗、ロール変更、Command 全件、データ参照（個人情報・金額関連） |
| 監査ログの内容 | タイムスタンプ、ユーザー ID、IP アドレス、ユーザーエージェント、操作種別、対象リソース、結果 |
| 保持期間 | オンライン 1 年 + S3 アーカイブ 7 年 |
| 改ざん防止 | S3 Object Lock（コンプライアンスモード） |
| Event Store の活用 | すべての状態変更は Event Store に時系列で残るため、業務監査ログを兼ねる |

### 3.5 OWASP 対策

OWASP Top 10（2021）を網羅。

| カテゴリ | 対策 |
| :--- | :--- |
| A01 アクセス制御の不備 | RBAC + Spring Security `@PreAuthorize` + Aggregate 側での権限チェック |
| A02 暗号化の失敗 | TLS 1.3 強制、AES-256、強力なパスワードハッシュ |
| A03 インジェクション | MyBatis の `#{...}` バインド変数のみ使用（`${...}` の文字列連結禁止）、Bean Validation、テンプレート文字列禁止 |
| A04 セキュアでない設計 | 脅威モデリング（STRIDE）、ADR で記録 |
| A05 セキュリティ設定ミス | Terraform で IaC、設定の構成ドリフト検出 |
| A06 脆弱なコンポーネント | Snyk / Dependabot で週次自動スキャン、CVSS 7.0+ は即対応 |
| A07 認証の失敗 | 強力なパスワード・MFA・ロックアウト |
| A08 ソフトウェア・データの整合性 | コンテナイメージ署名（cosign）、Maven Central / npm の署名検証 |
| A09 ロギング不足 | 統一監査ログ + Event Store の二重保証 |
| A10 SSRF | 外部 URL は許可リスト方式、内部 IP へのアクセスを禁止 |

### 3.6 脆弱性管理

| 項目 | 頻度・閾値 |
| :--- | :--- |
| 静的解析（SonarQube・SpotBugs） | PR ごと |
| 依存関係スキャン（Snyk・OWASP DC） | PR ごと + 週次 |
| コンテナイメージスキャン（Trivy） | ビルドごと |

| CVSS 7.0-8.9（High） | 7 日以内に対応 |
| CVSS 4.0-6.9（Medium） | 30 日以内に対応 |

## 4. 使用性（Usability）

### 4.1 アクセシビリティ

WCAG 2.1 レベル AA に準拠。

| 項目 | 要件 |
| :--- | :--- |
| キーボード操作 | すべての機能がキーボードで操作可能 |

## 5. 保守性（Maintainability）

### 5.1 モジュール性

| 指標 | 目標 |
| :--- | :--- |
| マイクロサービス間の結合 | Axon Event Bus（疎結合）、同期呼出は ACL 経由のみ |
| 集約サイズ | 1 集約 < 500 LOC、Aggregate Root の `@CommandHandler` < 10 個 |
| 循環依存 | ArchUnit で禁止、検出時は CI 失敗 |
| パッケージ依存ルール | `domain → application → interfaces` 方向のみ、`infrastructure` は逆向き不可 |

### 5.2 試験性

テスト戦略（`test_strategy.md`）に詳細を譲るが、以下が必要条件：

| 指標 | 目標 | 位置付け |
| :--- | :--- | :--- |
| ミューテーション (PIT) | ドメイン層 75% 以上、全体 65% 以上 | **ドメイン層の主指標**（H21 反映） |
| カバレッジ（行） | ドメイン層 90% 以上、全体 80% 以上 | 副指標（Event Sourcing 集約は private setter で膨らむため補助的に計測） |
| Flaky テスト発生率 | 月 5 件以下 | - |
| CI のテスト実行時間 | PR 10 分以内、main マージ後 20 分以内 | - |

### 5.3 解析性（ログ・トレーシング）

| 項目 | 内容 |
| :--- | :--- |
| ログ形式 | JSON 構造化ログ（タイムスタンプ・レベル・MDC（traceId, userId, bookingId 等）） |
| ログレベル | 本番: INFO 以上、開発: DEBUG |
| ログ保持 | アプリ 30 日、アクセス 90 日、監査 1 年 + S3 アーカイブ 7 年 |
| 分散トレーシング | OpenTelemetry、サービス間 traceId 伝播 |
| メトリクス | Micrometer → Heroku ログ、業務メトリクス（予約数・例外数・売上）も収集 |
| ヘルスチェック | `/actuator/health/liveness`, `/actuator/health/readiness`（K8s 互換） |

## 6. 拡張性（Scalability）

### 6.1 水平スケーリング

| サービス層 | スケーリング戦略 |
| :--- | :--- |
| アプリ層（ステートレス、Heroku dyno） | CPU/メモリベース Auto Scaling、最大 dyno 数まで自動 |
| フロントエンド（Nginx 配信） | 同上 |
| Aiven Kafka | マネージドサービスとして水平スケール対応 |
| RDS（PostgreSQL） | Read Replica 追加、書き込みは単一プライマリ |
| Read Model（Projection） | 各マイクロサービスごとに DB を分離済み、ボトルネックを局所化 |

### 6.2 想定する拡張シナリオ

| シナリオ | 対応方針 |
| :--- | :--- |
| 利用者 3 倍（300 → 1,000 名） | Auto Scaling の上限引き上げ + Read Replica 追加 |
| 取扱量 10 倍（年 100K → 1M 件） | Aiven Kafka のパーティション追加、Read Model にパーティション追加 |
| 国際展開（多リージョン） | Multi-region 構成、Aiven Kafka のクロスリージョンレプリケーション |
| 新規業務領域追加 | 新マイクロサービスをコンテキストとして追加、既存サービスへの影響は最小 |
| 通知チャネル追加（SMS / Push） | `NotificationAcl` を介して追加（ドメインへの影響なし） |
| モバイルアプリ | 既存 REST API + JWT を再利用、画面のみ追加開発 |
| リアルタイム配信（SSE / WebSocket） | Tracking Context に SSE エンドポイントを追加し、Axon Event Bus を購読 |

### 6.3 容量計画

| 項目 | 6 ヶ月後 | 1 年後 | 3 年後 |
| :--- | :--- | :--- | :--- |
| 同時利用者（ピーク） | 200 | 300 | 500 |
| Read Model 容量 | 10 GB | 20 GB | 80 GB |
| Event Store 容量 | 15 GB | 30 GB | 120 GB |
| 月間 API リクエスト | 5M | 15M | 50M |
| 月次見直し対象 | 容量推移、Auto Scaling の上限、コスト | 同左 + 構成見直し検討 | Aiven Kafka スケールアップ・マルチリージョン検討 |

## 7. 互換性（Compatibility）

| 項目 | 要件 |
| :--- | :--- |
| 外部システム連携 | RESTful + JSON（API Gateway 経由）、SOAP 不採用 |
| UN/LOCODE | 国際標準コード（5 文字）の準拠 |
| 通貨 | ISO 4217（3 文字コード）+ 小数 2 桁、`NUMERIC(14,2)` |
| 日時 | ISO 8601 + JST 表示、内部は UTC で保存 |
| ファイル形式 | 添付は PDF/CSV/JPEG/PNG のみ許可、サイズ 10MB 以下 |
| 過去システムからのデータ移行 | CSV 入力経路を 1 度だけ用意（プロジェクト初期） |
| 同居システム | Heroku 環境内に他システムが存在しても影響しないよう、アプリを隔離 |

## 8. 移植性（Portability）

| 項目 | 要件 |
| :--- | :--- |
| クラウドプロバイダー依存 | Heroku デプロイを主軸とするが、Docker 化により他クラウドへの移植が可能な構成（Terraform 抽象化） |
| 開発環境 | macOS / Windows / Linux すべてで動作（Docker Compose）。WSL 2 を Windows で推奨 |
| Java バージョン互換 | Java 25 LTS 必須、次回 LTS（Java 29）への移行は半年以内に評価 |
| Node バージョン互換 | Node 22 LTS、`.nvmrc` で固定 |
| データベース | PostgreSQL 16 専用。SQLite/MySQL は非対応 |
| 文字コード | UTF-8（ファイル・DB・通信すべて） |
| 改行コード | LF（リポジトリ既定） |

## 11. トレードオフと優先順位

非機能要件には相反するものがある。優先順位を明示する。

| トレードオフ | 優先 | 理由 |
| :--- | :--- | :--- |
| 整合性 vs 可用性 | **可用性（結果整合性受容）** | Axon の CQRS + Saga が前提。整合性は Saga 補償で保証 |
| 開発速度 vs セキュリティ | **セキュリティ** | 物流データ・個人情報を扱うため、規定の対策は省略不可 |
| コスト vs 可用性 | **段階的引き上げ** | フェーズ 1 は 99.9%、フェーズ 2 で 99.95% を目標。99.99% はマルチリージョン化のタイミング |
| 機能拡張 vs パフォーマンス | **両立**（測定して回帰を検知） | k6 のパフォーマンステストを CI に組み込み |
| 監視の細かさ vs ノイズ | **シグナル重視** | アラート閾値は p99 ベース、トースト的アラートは出さない |

## 13. リスクと緩和策

| リスク | 影響 | 緩和策 |
| :--- | :--- | :--- |
| Aiven Kafka の障害 | 全 Command/Event/Query が停止 | Aiven マネージドの冗長構成、S3 エクスポート、復旧訓練 |
| Event スキーマ不整合（後方互換性破壊） | サービス起動失敗、Projection 破損 | Upcaster 実装、Contract テスト、Blue/Green 時の検証 |
| Read Model 不整合 | 表示と実体の乖離 | Token リセットによる再構築、定期的な整合性チェッカー |
| ピーク日の追跡照会スパイク | 502/503 エラー多発 | CDN キャッシュ（追跡 API は短期 TTL）、Auto Scaling アグレッシブ設定 |
| ベンダーロックイン（Heroku / Axon） | 移行コスト | Terraform で抽象化、Axon Framework のドメイン部はフレームワーク非依存に保つ |

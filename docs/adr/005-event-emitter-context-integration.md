# ADR-005: コンテキスト間連携は NestJS EventEmitter による同一プロセス内イベントとする

Bounded Context 間の連携は @nestjs/event-emitter（EventEmitter2）によるドメインイベントで行い、イベントはトランザクションコミット後に発行する。

日付: 2026-07-27

## ステータス

承認済み

## コンテキスト

7 つの Bounded Context は「BC 間直接参照禁止（ACL / イベント経由のみ）」の規律で分離している。参照元 Java 版は Spring Events（`@TransactionalEventListener(AFTER_COMMIT)`）で疎結合な連携を実現していた。本システムは単一プロセスのモジュラーモノリスであり、分散メッセージングの導入は初期フェーズでは過剰である。

- 例: `HandlingActivityRegisteredEvent` は Tracking（輸送ステータス更新）と Booking（配送状態更新）の 2 つのリスナーを持つ
- EventEmitter2 はデフォルトで同期実行のため、コミット前にリスナーが走ると未確定データを他コンテキストが読むリスクがある

## 決定

- コンテキスト間連携は EventEmitter2 のドメインイベントに限定する（`@OnEvent` ハンドラは presentation/events に配置）
- イベントは**トランザクション境界（Kysely `transaction()`）の完了後に emit** する（AFTER_COMMIT 相当）
- 複数リスナーの片方が失敗した場合の方針: リスナーは冪等に実装し、失敗はエラーログ + 監視アラートで検知して再処理する（結果整合）。初期フェーズでは Transactional Outbox は導入しない
- 高可用性・複数プロセス化が必要になった時点で Transactional Outbox パターン + メッセージブローカーへの移行を別 ADR で判断する

### 代替案

- **メッセージブローカー（SQS / RabbitMQ）**: プロセス障害に強いが、単一プロセスのモノリスにはインフラ・運用コストが過剰。却下（将来の移行先として留保）
- **Transactional Outbox を初期から導入**: 配信保証は高まるが、ポーリング・リレー機構の実装コストが初期スコープに見合わない。却下（移行パスとして記録)
- **BC 間の直接メソッド呼び出し**: 最も単純だが、コンテキスト境界が溶けて「BC 間直接参照禁止」の規律に反する。却下

## 影響

### ポジティブ

- コンテキスト間が発行/購読で疎結合になり、リスナー追加が既存コードに影響しない
- 同一プロセス内のためレイテンシ・運用コストが最小

### ネガティブ

- プロセスクラッシュ時、コミット済みだが未発行のイベントは失われる（結果整合の破れ）。監視と手動リカバリ手順（operation.md）で補う
- リスナーの冪等性・失敗時再処理の規律を実装者が守る必要がある

## コンプライアンス

- dependency-cruiser ルール「BC 間直接参照禁止」を CI で検証する
- イベント発行がトランザクション完了後であることをコードレビューと統合テスト（AFTER_COMMIT タイミング検証）で確認する

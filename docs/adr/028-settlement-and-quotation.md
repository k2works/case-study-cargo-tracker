# ADR-028: 精算の処理と輸送見積

発行した請求書の入金を確認し（US23）、営業担当者が輸送料金を先に見積もる（US01）ときに、
**どこで金額を決め、間違いをどう直し、予約の状態をどう閉じるか**を決める。

日付: 2026-08-26

## ステータス

承認済み（決定 1〜7）

## コンテキスト

IT11 で運賃を計算できるようになったが、**発行した請求書は `PENDING` のまま動かない。**
入金を確認する手段が無く、予約は引取済のまま残る。Release 2.0 はこの 1 本を通して閉じる。

同じ IT で US01（輸送見積）に戻る。**営業担当者が最初に触る画面でありながら、
料金の式に依存するため最後に置いた**——式が決まる前に作ると、見積は
「実料金と違う数字を出す機械」になる。

IT11 の完了報告書と経理担当者のレビューが、着手前に決めるべきことを 7 つ残した。
本 ADR はそれに答える。

> **決定ごとに「破られたら何が起きるか」を先に書く**（IT11 Try 8）。IT11 は決定 4 に
> 検査を置いていたが、その検査は明細の不変性だけを見ており、**金額そのものを一度も
> 見ていなかった**。何が起きるかを書かないと、検査は「決定の名前」に対して書かれる。

## 決定

### 決定 1: `CargoDeliveredEvent` は実装しない。実装するのは逆向きの 1 本（billingms → bookingms）

精算の起点は経理担当者の操作である（[ADR-027](027-transport-charge-calculation.md) 決定 5）。
US23 の受入基準にも自動起票は無い。**読む側の無い配線を先に敷かない**
（[ADR-025](025-customs-declaration-and-cancellation-approval.md) 決定 3 の継承）。

かわりに**逆向きの 1 本を実装する**。受入基準 23-4 は「入金確認後、精算状態が『精算済』に
更新され**予約状態も『精算済』になる**」と書いており、**こちらには読む側がある**
——予約の一覧と詳細が、その状態を出す。

**破られたら**: 引取済の予約が永久に引取済のまま残り、営業担当者は
「この案件は終わったのか」を予約の画面から判断できなくなる。

### 決定 2: 入金は `payment` テーブルに持つ。`invoice` に列を足さない

発行した請求書の金額は動かない（ADR-027 決定 4）。**入金は請求書に起きた別の出来事**であり、
請求書の属性ではない。1 通に対して複数回の入金（分割入金）が起こりうることも、
表を分ける理由になる——本 IT では 1 回だけを扱うが、**列に持つと分割入金は列の増設になる。**

金額の型は `NUMERIC(15,2)`（`invoice` 側に揃える。論理モデルの `INTEGER` から変更・注 6）。

**破られたら**: 入金の記録が請求書の行を書き換える形になり、ADR-027 決定 4 が
「金額は動かない」と言っている行を、入金のたびに UPDATE することになる。

### 決定 3: 発行した請求書は取り消して出し直す（赤伝）。`invoice` を書き換えない

経理担当者は「DB を直すのは監査に耐えない」と明言した。**間違いは消さずに取り消す。**

- `voided_at` / `void_reason` を足す。**理由は必須**——なぜ取り消したかが残らない取り消しは、
  あとから見て「二重発行の失敗」と区別できない
- 出し直しは**新しい請求番号**で発行する
- `booking_id` の UNIQUE 制約は**出し直しを妨げる**ため、取り消し済みを除く形に変える

> **落とし穴が 2 つある。** (a) `existsForBooking` の `COUNT(*)` が取り消し済みも数えるため、
> 制約だけを変えてもアプリ側が先に弾く。(b) H2 が部分 UNIQUE の `WHERE` を解釈しない公算が
> あり、**CI（PostgreSQL）は緑のままローカル起動だけが落ちる**。着手時に実測する。

**破られたら**: 金額を間違えた請求書が永久に残り、その予約には二度と請求できない。
あるいは経理担当者が DB を直し、監査の記録が実際の請求と食い違う。

### 決定 4: 「取消済み」を `PaymentStatus` に混ぜない

`PaymentStatus` は**支払いの状態**（未入金・入金済・期限超過・返金済）であり、
取り消しは**請求書そのものの状態**である。混ぜると `PENDING` が
「まだ払われていない」と「もう請求していない」の 2 つの意味を持つ。

ADR-027 決定 3 で `DRAFT` を混ぜなかったのと同じ理由である。

**破られたら**: 未入金の一覧に取り消し済みが混ざり、経理担当者が
「払われていない請求」として荷主に催促する。

### 決定 5: `OVERDUE` は永続化せず、日付から判定する

正典のビジネスルール 3 は「支払期限を超過したら `PaymentStatus` を `OVERDUE` に更新する」と
書いているが、**更新する相手（バッチ）が無い。** 書いた列は、書き込む人がいなければ
**いつまでも `PENDING` のまま**であり、期限を過ぎた請求が一覧に現れない。

`Invoice.overdue(today)` で判定する。**業務日付は業務タイムゾーンで決める**
（`Clock` を注入する。UTC で判定すると時差の分だけ「当日」がずれる）。

**破られたら**: 列を足したのに誰も書かないため、**期限超過の件数が常に 0 件**になる。
経理担当者は「未払いは無い」と読む——気づく手段が、気づかせない手段になる。

### 決定 6: 料金の式は billingms の 1 か所に置く。見積は ACL 経由で試算を問う

見積の概算料金（01-3）と実料金（US21）は**同じ式**を使う。**式を 2 つ持たない**
——持てば必ずずれる（IT11 のモックが現にそうなっていた。本 IT の返済枠 0.2）。

式の在り処は billingms である。bookingms は
`application/port/ChargeQuoteFinder` → `infrastructure/billing/RestChargeQuoteFinder` で問う。
**新しい結合方向であるため、ここで決定として起票する**——終盤で新しい結合方式を発明しない。

> **ArchUnit は HTTP の向きを見ない。** 経路はリテラルであり、構造に映らない。
> 「循環しないことを固定する」は書けない約束なので、**層内の依存禁止**に翻訳する
> ——見積のユースケースが `BillingSnapshotFinder` / `RestClient` に依存しないことを検査する。

**破られたら**: 荷主に出した見積と、運び終えたあとの請求が違う金額になる。
営業担当者は毎回「見積はあくまで概算です」と言うことになり、見積の意味が消える。

### 決定 7: 見積は UUID で識別し、人が読める見積番号を別に持つ

正典の `EstimateId` は UUID である。しかし受入基準 01-4 は「**見積番号が発行される**」と
書いており、**荷主と電話で読み合わせる番号**が要る。

- `estimate_id`（UUID）— URL と内部の識別子。**推測できないこと**に意味がある
- `estimate_number`（`EST-YYYY` + 6 桁）— 人が読む番号。採番は
  [ADR-011](011-invoice-numbering.md) と同じシーケンス方式

**破られたら**: UUID を電話で読み上げることになる。あるいは連番だけにすると、
URL を 1 つ増減させて他の荷主の見積が開ける。

## 影響

### 良い影響

- **予約から精算までが 1 本で閉じる。** IT1 から積んできた鎖の最後の輪が繋がる
- **間違いを直す手段ができる**（決定 3）。IT11 まで、発行した請求書は直す方法が無かった
- **見積と実料金が同じ式を通る**（決定 6）。営業と経理が同じ数字を見る

### 悪い影響・受け入れるリスク

- **外部連携を 3 つとも実装しない**（メール通知・決済機関・期限超過通知）。
  **代替であることを画面に書く**——書かないと、利用者は「壊れている」と受け取って待ち続ける
- **BC 間の結合方向が増える**（決定 6）。bookingms ⇄ billingms の双方向になる。
  片方が落ちると、もう片方の一部の画面が使えなくなる
- **基準運賃 50,000 円は依然として置いた数字である。** 見積にもそのまま伝染する。
  **暫定値であることをマニュアルに 1 行書く**（いまは ADR にしか無い）

## コンプライアンス

**決定ごとに「破られたら何が起きるか」→「それが起きないことの検査」の順に書く**（IT11 Try 8）。
決定の名前に対して検査を書くと、IT11 の決定 4 のように**検査が決定の一部分しか見ない**。

| 決定 | 破られたら何が起きるか | それが起きないことの検査 |
| :--- | :--- | :--- |
| 1 逆向きの 1 本 | 引取済の予約が永久に閉じない | `billing.spec.ts#デモ 2`（**予約の画面で**精算済を見る）・`BookingStatusTest`（`SETTLED` を扱う場所すべてを `values()` から回る）・`SettleBookingUseCaseTest` |
| 2 `payment` は別表 | 入金のたびに請求書の行を書き換える | `PaymentPersistenceIntegrationTest`（保存後に `invoice` の金額列が 1 つも変わらない）・`InvoiceTest.Immutability`（既存） |
| 3 赤伝 | 間違えた請求書が永久に残る / DB を直される | `InvoicePersistenceIntegrationTest#取り消したあと、同じ予約に出し直せる`（**新しい請求番号であることまで見る**）・`InvoiceTest#void_ は理由を要求する`・`billing.spec.ts#デモ 4` |
| 4 取消は状態に混ぜない | 取り消し済みに催促する | `PaymentStatus` の値の名簿（既存）・`InvoiceRepository#findUnpaid` が取り消し済みを含まないことの検査 |
| 5 `OVERDUE` は判定 | 期限超過が常に 0 件 | `InvoiceTest#overdue`（期限当日は超過でない・**日付単位で比べる**）・`OverdueCountIntegrationTest`（業務タイムゾーンの `Clock` を差し替えて件数が変わる）・`billing.spec.ts#デモ 3` |
| 6 式は 1 か所 | 見積と請求が違う金額になる | `QuoteMatchesInvoiceIntegrationTest`（**同じ条件で見積と実料金が一致する**）・`EstimateArchitectureTest`（見積のユースケースが `RestClient` / `BillingSnapshotFinder` に依存しない）・`RestChargeQuoteFinderTest` + プロバイダ側 |
| 7 UUID と見積番号 | UUID を読み上げる / 隣の見積が開ける | `EstimateIdTest`（UUID の形）・`EstimateNumberTest`（`EST-YYYY` + 6 桁・年をまたぐと 1 に戻る）・`estimate.spec.ts#見積番号が発行されて一覧から開ける` |

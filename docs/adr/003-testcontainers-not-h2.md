# ADR-003: テスト用 DB は Testcontainers に一本化し H2 を採用しない

テスト実行時も本番と同一の PostgreSQL を Testcontainers で起動し、H2 インメモリ DB は使用しない。

日付: 2026-08-06

## ステータス

承認済み

## コンテキスト

H2 の採否が設計ドキュメント間で正反対に分かれていた。

| 立場 | ドキュメント |
| :--- | :--- |
| 採用 | `tech_stack.md`（バージョン 2.x・接続 URL `jdbc:h2:mem:testdb;MODE=PostgreSQL;...` まで明記）、`architecture_backend.md`（統合テストで「Testcontainers, H2」） |
| 不採用 | `test_strategy.md`「H2 はインメモリ DB としては採用しない」、`data-model.md`「H2 は採用しない」 |

さらに深刻なのは `data-model.md` の**自己矛盾**である。同ファイルは冒頭で H2 不採用を宣言しながら、以下 3 つの設計判断を H2 互換性を根拠に下していた。

- 判断 4: 「テスト（H2）との互換性も維持できる」
- 判断 7: 「H2 との互換性を優先して」
- Flyway 方針: 「本番とテスト（H2）で同一マイグレーションスクリプトを使用するため…H2 互換形式で記述する」

つまり、H2 を捨てたのに H2 互換性を根拠にした制約（例: `BIGSERIAL` を避ける）だけが残っている状態だった。

## 決定

**テスト用 DB は Testcontainers（PostgreSQL 16.x）に一本化し、H2 を採用しない。** あわせて、H2 互換性を根拠にしていた設計判断を根拠ごと見直す。

判断根拠は次のとおり。

- H2 の PostgreSQL 互換モードは方言を完全には再現しない。特に本システムが多用する予定の型（`TIMESTAMPTZ`・`UUID`・`NUMERIC` の丸め挙動）と、楽観的ロック（ADR 検討中）・部分インデックス・`ON CONFLICT` の挙動に差がある
- 方言差があるということは、**H2 上で緑になったテストが本番で落ちうる**ということであり、これは安全網ではなく偽の安全網である
- Testcontainers はシングルトンコンテナ（`@Testcontainers` + `static` フィールド、または Spring Boot 3.1+ の `@ServiceConnection`）でテストクラス間の起動コストを 1 回に抑えられるため、「H2 のほうが速い」という利点は実運用上ほぼ消える

### 変更箇所

- `tech_stack.md`: データベース表から H2 の行を削除し、「テスト環境の DB 設定」節（`jdbc:h2:mem:testdb;MODE=PostgreSQL;...`）を削除して Testcontainers の記述に置き換える
- `architecture_backend.md`: 統合テストの記述から「H2」を削除する
- `data-model.md`: 判断 4・判断 7・Flyway 方針から H2 互換性の根拠を削除する。**根拠が失われた制約は制約ごと再検討する**。特に「H2 互換のため `BIGSERIAL` を避ける」は不要になるため、識別子戦略を PostgreSQL の機能を前提に引き直す
- `test_strategy.md`: 現行の記述（H2 不採用・Testcontainers 一本化）を維持する。本 ADR がその根拠となる

### 代替案

| 代替案 | 却下理由 |
| :--- | :--- |
| H2（PostgreSQL 互換モード）を使い高速化する | 方言差により偽の安全網になる。国際輸送でタイムゾーン付き時刻を多用する本システムでは、まさに差の出る領域を踏む |
| ユニットテストは H2、統合テストは Testcontainers の使い分け | 2 つの DB の方言差を両方把握し続けるコストがかかる。かつ「どちらで落ちたか」の切り分けが増える |
| ローカルに PostgreSQL を常駐させる | 開発者の環境構築手順が増え、バージョン差が生まれる。CI との一致も保証できない |

## 影響

### ポジティブ

- テストが本番と同一の DB 方言で実行され、方言差起因の本番障害が構造的に排除される
- `TIMESTAMPTZ`・`UUID`・部分インデックスなど PostgreSQL の機能を制約なく設計に使える
- Flyway マイグレーションを本番専用の 1 系統で書けるため、互換形式への配慮が不要になる

### ネガティブ

- テスト実行に Docker が必要になる。開発環境セットアップ手順と CI 定義に Docker の可用性が前提として加わる
- 初回のコンテナ起動（イメージ pull を含む）に時間がかかる。CI ではイメージのキャッシュが必要
- シングルトンコンテナを使う場合、テスト間のデータ独立性は自前で担保する必要がある（`@Transactional` ロールバックまたは明示クリーンアップ）。これは `test_strategy.md` のテストデータ準備規約で定める

## コンプライアンス

- `build.gradle` / `pom.xml` の依存に `com.h2database:h2` が存在しないこと（CI の依存チェックで検出可能）
- `application-test.yml` 等に `jdbc:h2:` を含む接続 URL が存在しないこと
- 統合テストが `PostgreSQLContainer` 経由で起動していること
- `data-model.md` に「H2 互換」を根拠とする記述が残っていないこと

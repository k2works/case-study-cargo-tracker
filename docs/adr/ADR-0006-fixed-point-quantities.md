# ADR-0006: 小数を伴う量は固定小数点整数で保持する

## ステータス

承認済み（2026-08-03・IT5）

## 文脈

業務上の量のうち、小数を伴うものが増えてきた。

| 量 | 内部表現 | DB の型 | 導入 |
| :--- | :--- | :--- | :--- |
| 割引率 | 万分率の `Int32`（`1500` = 15.00%） | `NUMERIC(5,4)` | IT4（US03） |
| 重量 | グラムの `Int64`（`1200500` = 1200.500 kg） | `NUMERIC(10,3)` | IT4（US04） |
| 寸法 | ミリメートルの `Int32` | `NUMERIC(10,3)`（cm） | IT4（US04） |
| 温度 | 千分の一度の `Int64`（`-25500` = -25.5℃） | `NUMERIC(10,3)` | **IT5（US05）** |

ドメインモデル設計は当初 `TemperatureRequirement` の温度を `BigDecimal` としていた。
IT5 の実装時に、既に確立していた 3 例と揃えるかどうかを判断する必要が生じた。

あわせて、IT4 のレビューで**同じ変換を 2 箇所に書いて同じバグを 2 つ作った**
経緯がある（`-0.5` の符号が消え `0.50%` になる。整数部の `-0` を数値化すると `0` になるため）。

## 決定

**小数を伴う量は、桁を固定した整数で保持する。浮動小数点型・`BigDecimal` は使わない。**

1. 内部表現は「最小単位の整数」とする（万分率・グラム・ミリメートル・千分の一度）
2. DB との変換は**境界（リポジトリ）で行う**
3. 文字列 ⇄ 整数の解釈は `SharedDecimal` に集約し、**量ごとに書かない**
4. 符号を許すかは量ごとに決める。`parseScaled`（非負）と `parseSignedScaled`（符号付き）を分ける

## 根拠

**誤差を業務判断へ持ち込まない。** 料金計算・積載判定・保冷条件は、いずれも
金銭や貨物の損害に直結する。`Float64` の 0.1 は 0.1 ではなく、加算を重ねると
表示上の値と計算結果が食い違う。「合計が 1 円合わない」は、原因を突き止めるまで
誰も納得しない種類の不具合である。

**`BigDecimal` を使わない理由は、誤差ではなく境界の数である。** `BigDecimal` は
正確だが、Flix から Java の値を扱うことになり、等価性・表示・シリアライズの
それぞれで Java 側の作法が漏れてくる。整数なら Flix の値として完結する。

**符号の扱いを量ごとに分けるのは、既定値へ倒す事故を防ぐため。**
割引率・重量・個数は非負であり、負の入力は打ち間違いである。これを 0 として
受け入れると「割引なしの法人」「重量 0 の貨物」が静かに通る。一方で温度は
ほぼ常に負であり、同じ関数に両方の意味を持たせると、どちらかの安全性が落ちる。

## 帰結

### よい点

- 誤差が原理的に発生しない。テストで境界値を直接書ける
- 変換が 1 箇所（`SharedDecimal`）に集まり、符号消失のようなバグを 1 度しか作れない
- Flix の値として完結し、等価比較・パターンマッチが素直に書ける

### 悪い点

- **単位を取り違えると桁がずれる**。`weightGrams` に kg を入れると 1000 倍になる。
  型ではなくフィールド名でしか区別できない
- 画面へ出すとき必ず変換が要る。`-25500` をそのまま出すと利用者には意味が分からない
- DB の型（`NUMERIC(s,p)`）と内部の桁数を**別々に決められてしまう**。
  ずれるとリポジトリの往復で桁が落ちる

### 対策

- 変換は必ず `SharedDecimal` を通す。「似ているが少し違う」変換を新しく書かない
- リポジトリの**往復テストを必須にする**（保存した値と読み出した値の一致）。
  片道だけのテストは「書けているが読めていない」を見逃す。IT5 で
  `JdbcCargoRepoTest` に重量・温度・寸法の往復を置いた
- 表示用の変換関数をドメインに置く（`weightKilograms`・`temperatureText`（いずれも `SharedDecimal.formatScaled` に委ねる））

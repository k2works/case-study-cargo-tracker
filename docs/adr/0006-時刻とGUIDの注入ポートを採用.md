# ADR-0006: 時刻・GUID の注入ポートを採用

非決定的な入力（現在時刻・GUID 生成）のドメインからの分離方式の決定

日付: 2026-07-14

## ステータス

2026-07-14 提案

## コンテキスト

ドメインロジックの一部は現在時刻や新規 GUID に依存します。具体的には以下です。

- `EstimateId.generate`（見積 ID = UUID の採番・US01）
- `Invoice.generate` / `MarkOverdue`（精算書発行日時・延滞判定・US21/US23）
- 追跡例外のエスカレーション時限判定（発生からの経過時間・US19/US20）

これらが `System.DateTimeOffset.Now` や `System.Guid.NewGuid()` を直接呼ぶと、ドメイン関数が非決定的になり、プロパティベーステスト（FsCheck）や状態遷移テストで結果を固定できません。設計ドキュメントレビュー（2026-07-06）でも xp-tester から「時刻・乱数依存に対する injection ポートが未設計」が高優先度指摘として挙げられています（domain-model.md のビジネスルールでは Clock ポートに言及があるが、型としては未定義）。

## 決定

**現在時刻・GUID を注入ポート（関数型）としてアプリケーション層から渡す方式を採用します。**

1. **Clock ポート**: `type Clock = unit -> System.DateTimeOffset`。現在時刻を要するドメイン関数は `Clock` から取得した値を**引数で受け取る**（ドメイン関数内で `Now` を呼ばない）。
2. **IdGenerator ポート**: `type IdGenerator = unit -> System.Guid`。GUID を要する採番（`EstimateId.generate` 等）は `IdGenerator` から取得した値を引数で受け取る。
3. **合成ルートでの結線**: 本番実装は `fun () -> DateTimeOffset.Now` / `fun () -> Guid.NewGuid()` を合成ルート（`CargoTracker.Web` の Composition Root）で束縛する。テストは固定値を返す関数リテラルを差し込む。
4. **配置**: ポート型は `CargoTracker.Shared` に定義し、全 BC から参照可能にする（ADR-0001 のファイル順規約に整合）。

根拠は以下のとおりです。

1. **ドメインの純粋性**: 時刻・乱数をドメイン関数の外へ追い出すことで、ドメインは入力から出力が一意に決まる純粋関数となり、FsCheck・状態遷移テストで検証可能になる。
2. **モックライブラリ不要**: ポートが関数型のため、テストは関数リテラルで差し替えられ、Moq 等のモックライブラリは不要（tech_stack.md の方針に整合）。
3. **軽量**: インターフェース・DI コンテナへの登録は最小限（合成ルートでの束縛のみ）。

## 代替案

- **`DateTimeOffset.Now` を直接呼ぶ**: 実装は簡素だが非決定的でテスト困難。レビュー指摘の対象。
- **アンビエントコンテキスト（`AsyncLocal`）**: 暗黙の依存となり、F# の明示的依存の思想と合わない。

## 影響

- 時刻・GUID を要するドメイン関数のシグネチャに `now: DateTimeOffset` / `id: Guid` 引数（またはポート）を追加する。
- IT1 でタスク 1.7 として Clock / IdGenerator の参照実装を作り、`EstimateId.generate`（US01）で最初に使用する。
- domain-model.md のビジネスルール（Tracking の Clock 言及）と整合する。

## コンプライアンス

- ドメイン関数内で `DateTimeOffset.Now` / `Guid.NewGuid()` を直接呼ばないこと（コードレビュー・FSharpLint で確認）。
- 時刻・GUID 依存のドメインロジックは固定値注入で決定的にテストすること。

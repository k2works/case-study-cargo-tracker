# ADR-004: 永続化に MyBatis を採用し JPA / Hibernate を採用しない

O/R マッパーとして MyBatis を採用し、SQL を明示的に管理する。

日付: 2026-08-06

## ステータス

承認済み

## コンテキスト

`tech_stack.md` は MyBatis を採用技術として挙げ、「MyBatis による SQL の明示的管理は CQRS の Read Model 最適化に適合する」と選定理由の総括で述べているが、**JPA を採らなかった理由が記録されていなかった**。Spring Boot の既定の選択肢は Spring Data JPA であり、そこから外れる判断は根拠を残さなければ後任者が「なぜ茨の道を選んだのか」を再検討することになる。

本システムの永続化には次の性質がある。

- DDD の集約（`Cargo` + `CargoItinerary` + `Leg`）を単一トランザクションで整合させる必要がある
- CQRS の読み取り側は複数テーブルを JOIN して画面向け DTO を直接返す設計（`architecture_backend.md`）
- 境界付けられたコンテキスト間に DB 外部キーを張らない方針（`data-model.md` 判断 5）
- 追跡 API に p95 200ms という性能要件（`non_functional.md`）

## 決定

**MyBatis を採用し、JPA / Hibernate は採用しない。**

判断根拠は次のとおり。

- **CQRS の読み取り側で SQL を直接書ける**。画面向けの JOIN クエリを DTO に直接マッピングでき、JPA のエンティティグラフや射影 DTO を介する必要がない。読み取り最適化が本システムの性能要件の中心にある以上、ここが素直に書けることの価値は高い
- **BC 間に FK を張らない方針と相性がよい**。JPA は関連を `@ManyToOne` 等のオブジェクト参照で表現するのが自然だが、その自然さが BC 境界を越えた参照を誘発する。MyBatis は識別子を識別子のまま扱うため、境界を越えないことがデフォルトになる
- **発行される SQL が予測可能**。JPA の遅延ロードによる N+1 は「動くが遅い」という形で現れ、性能要件に対する予測可能性を下げる。MyBatis では SQL がコードとして見えているため、性能問題がレビュー時点で検出できる
- ドメインモデルを永続化アノテーションから独立させられる。ヘキサゴナルアーキテクチャで集約を純粋な Java オブジェクトに保つ方針と整合する

### 代替案

| 代替案 | 却下理由 |
| :--- | :--- |
| Spring Data JPA / Hibernate | 遅延ロードによる性能の予測不能性、集約を越えたオブジェクト参照の誘発、ドメインモデルへのアノテーション混入。CQRS 読み取り側の JOIN を素直に書けない |
| Spring Data JDBC | 集約指向で DDD との相性はよいが、CQRS 読み取り側の複雑な JOIN には結局 `JdbcTemplate` を併用することになり、2 つの機構を抱える |
| jOOQ | 型安全な SQL 構築という点で魅力があるが、商用ライセンスが商用 DB で必要になる点と、コード生成をビルドに組み込むコストがある。PostgreSQL のみなら無償だが、学習コストに見合う差が MyBatis に対して大きくない |

## 何がどこで守るか

| 守るもの | 守り手 |
| :--- | :--- |
| JPA / Hibernate ORM を本番に持ち込まない | **ビルド**（`verifyProductionDependencies` の `org.hibernate.orm` / `jakarta.persistence`） |
| ドメインモデルに永続化アノテーションを混入させない | **`PackageStructureTest.ドメイン層はMyBatisに依存しない`** |

**`hibernate-validator` は対象外である。** Bean Validation の実装であり ORM ではない。
`org.hibernate` で一括除外すると誤検知するため、検査は `org.hibernate.orm` を見る。

## 影響

### ポジティブ

- 発行される SQL がコードとして可視化され、性能問題をレビューで検出できる
- ドメインモデルが永続化技術から独立し、ヘキサゴナルの依存方向が守りやすい
- CQRS の読み取り側を Read Model 用テーブルを作らずに JOIN で実現できる（`architecture_backend.md` の方針と整合）

### ネガティブ

- CRUD の定型コードを自分で書く必要がある。JPA の派生クエリのような自動生成がない
- マッピング XML またはアノテーションと DDL の対応を人間が維持する必要があり、カラム追加時の追随漏れが起きうる。統合テスト（ADR-003 の Testcontainers）で実 DB に対して検証することが前提となる
- 動的 SQL の組み立てが XML の `<if>` 等で複雑になりやすい。検索条件の多い一覧画面で可読性が落ちる

## コンプライアンス

- ArchUnit ルールにより、ドメイン層のクラスが MyBatis の型（`org.apache.ibatis..`）に依存しないことを検証する
- リポジトリ実装がアプリケーション層で定義された出力ポートを実装する形になっていること（DIP の遵守）
- すべての Mapper に対して Testcontainers 上の統合テストが存在すること（マッピングと DDL の対応を人間が維持する以上、実 DB による検証が唯一の防御線となる）

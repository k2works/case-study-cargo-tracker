# ADR-011: 予約番号は DB のシーケンスで採番し、`BKG-YYYYNNNNNN` の形式とする

貨物予約の予約番号（`booking_id`）は、bookingms のデータベースのシーケンスで採番する。形式は `BKG-` + 西暦 4 桁 + 連番 6 桁とする。追跡番号（IT6）は別の識別子であり、予約番号から導出しない。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

`booking_id` は 5 サービス（booking / routing / tracking / handling / billing）が論理的に参照するキーである。サービスをまたぐため外部キー制約が張れず、値そのものが契約になる。後から形式を変えると、既に発行した番号と新しい番号が混在し、5 サービスの照合が壊れる。

IT1 で荷主コードの採番について同じ問題に当たった。集約側で MAX+1 を計算する実装はシーケンスと衝突し、**原因でない他の登録が UNIQUE 制約で落ちた**。テストデータの採番も本番経路を通すという規律をそこで立てた。

決めるべき点が 3 つある。

- **どこで採番するか**（アプリ / DB / 外部の採番サービス）
- **形式**（利用者が電話口で読み上げる。長すぎても、紛らわしくてもいけない）
- **追跡番号との関係**（IT6 で追跡番号を発行する。同じものか、別か）

## 決定

1. **採番は bookingms のデータベースのシーケンス（`booking_id_seq`）で行う。** アプリ側で MAX+1 を計算しない。連続登録で衝突しないことを結合テストで確認する
2. **形式は `BKG-YYYYNNNNNN`**（例: `BKG-2026000001`）。`BKG-` で他の識別子と見分けがつき、西暦で発行年が分かる。連番は年をまたいでもリセットしない（リセットすると年をまたいだ重複が起きる）。全長 14 文字は `VARCHAR(20)` に収まる
3. **形式の組み立てをマイグレーションに書く。** シーケンスと形式を同じ場所に置き、アプリ側で文字列を組み立てない。アプリ側に置くと、別の経路（データ移行・運用スクリプト）が違う形式を作れてしまう
4. **追跡番号（IT6）は予約番号と別の識別子とする。** 予約番号は社内の識別子であり、荷主・受取人に渡すのは追跡番号である。同一にすると、追跡番号を知った第三者が予約番号を知ることになり、内部の照会経路に推測でアクセスできる。導出関係も作らない（`BKG-2026000001` から `TRK-...` が計算できてはならない）

### 代替案

- **UUID を使う**: 衝突しないが、電話口で読み上げられない。荷主との会話に出る識別子として不適
- **アプリ側で `年 + カウンタ` を組み立てる**: 複数インスタンスで採番が重なる。IT1 の荷主コードで踏んだ轍と同じ
- **予約番号を追跡番号として使う**: 発行が 1 つで済むが、社外に出す識別子と社内の識別子が同じになる。分離しておくほうが後から狭められる

## 影響

### ポジティブ

- 5 サービスが参照するキーの形式が、実装より先に固定される
- 採番の衝突が構造的に起きない（シーケンスが唯一の発行元）

### ネガティブ

- 予約番号から発行年が読めるため、年間の発行件数がおおよそ推測できる。社内識別子であり許容する
- IT6 で追跡番号の採番を別に作る必要がある

## コンプライアンス

- `V3__init_booking_cargo.sql` にシーケンスと形式の組み立てを置く
- 連続して複数件登録し、予約番号が重複しないことを結合テストで確認する
- IT6 の計画時に本 ADR を読み、追跡番号を予約番号から導出していないことを確認する

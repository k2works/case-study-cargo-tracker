# ADR-030: 業務シミュレーションは Gateway 経由で本番の経路を踏む

予約から精算までを自動で流す仕組みは、実利用者と同じ API・同じ認可を通り、
生成したデータは荷主コードで実データと区別する。

日付: 2026-11-16

## ステータス

提案（決定 1〜5）

## コンテキスト

Release 2.1 までで業務は端から端まで通った。しかし**それを確かめる手段は人手のまま**である。
予約から精算まで追うには 7 ロール分のログインと 20 以上の画面操作が要り、実演のたびに
手順が揺れる。

IT5（経路の確定）・IT12（見積の試算先）・IT13（荷主追跡）で **3 度**、
「接続先が `localhost` を向いていて実環境だけ 500」という同型の欠陥が出た。いずれも
ユニット・結合・モック E2E はすべて緑で、**実際の経路を踏んで初めて**分かった。

踏む作業を自動化する。ただし自動化の仕方を誤ると、**確かめているつもりで何も確かめていない**
仕組みになる。専用の書き込み経路を用意すれば実装は速いが、そのとき検出できなくなるのは
まさに「シミュレーションは通るのに実際の操作は通らない」という状態である。

> **決定ごとに「破られたら何が起きるか」を先に書く**（ADR-028・ADR-029 と同じ）。

## 決定

### 決定 1: シミュレーションは独立したサービス（simulationms）に置く

`simulationms` を新設し、既存 6 サービスには実行の仕組みを持ち込まない。

既存サービスのどれかに入れると、そのサービスだけが他の 5 サービスを呼ぶ**太い依存**を持つ。
シミュレーションは業務ではなく**業務の呼び出し元**であり、業務の BC とは変わる理由が違う。

**破られたら**: 業務サービスが「呼び出し元の都合」で変わる。たとえば bookingms に置くと、
予約の集約が荷役や精算の進め方を知ることになり、予約のテストが他サービスの状態に依存する。

### 決定 2: 呼び出しは Gateway 経由・実在のデモ利用者としてログインする

simulationms は **[ADR-004](004-gateway-jwt-verification.md) の Gateway を通し、実在の利用者として
ログインして**業務 API を呼ぶ。内部 API（`/api/v1/internal/**`・`shipper-snapshots`・
`by-tracking-number`）も `system:` principal も使わない。

**ロールは工程ごとに違うため、工程ごとにログインし直す。** 1 つの利用者に全ロールを与えると、
**本番には存在しない権限の持ち主**を作ることになり、認可の検査を素通りする。

出口は `BusinessGateway` の **1 ポート**に絞る。各サービスへ直接つなぐ ACL を 6 本作ると、
そのうち 1 本でも内部 API を向いた時点でこの決定は崩れる。

**破られたら**: 認可を素通りする経路が新設される。シミュレーションは通るのに実利用者の操作は
403 で止まる、という状態が検出できなくなる——**この仕組みを作る理由そのものが失われる**。

### 決定 3: シミュレーション由来は荷主コードの帯で識別する

荷主コードに `SIM-` の帯を設け、bookingms の `shipper` に `simulated` 列を持つ。
貨物・請求書・追跡はすべて荷主から辿れるため、**他サービスは荷主コードで判断する**。

`simulated` 列を全サービスへ伝播させない。伝播させると、**伝播漏れた 1 サービスだけが
実データに混ぜる**。列を持つのは bookingms の荷主 1 か所だけである。

除外は**除外する側**に検査を置く。精算の締め対象・未解決例外一覧・荷主向け一覧のそれぞれで
「シミュレーション由来を 1 件作り、出ないこと」を確かめる。

**破られたら**: 経理担当者の締めにシミュレーションの請求書が混ざり、追跡管理者の対応一覧に
存在しない貨物の例外が並ぶ。**実データが信用できなくなる**——業務が止まる。

> **荷主から辿れないものが 1 つある（IT14 Phase 3.2 で判明）**: **航海**である。
> まっさらな環境には航海が 1 本も無く、無いと経路候補が 0 件になる。「候補が無いので飛ばす」に
> すると何も運ばないまま全工程が成功で終わるため、シミュレーションは航海も登録する。
> 航海は荷主に紐づかないので、荷主コードでは識別できない。
> **航海番号を `V-SIM-` の帯にし、船名・運送会社も「シミュレーション」と名乗る。**
> ただし航海一覧からの除外は行っていない——経路設計者の一覧にシミュレーションの航海が
> 並ぶ。除外すると経路候補にも出なくなり、割り当てる相手が消えるためである。
> **見えることを選んだ**（名前で見分けられる）が、これは決定 3 の「荷主から辿れる」という
> 前提の外にある。運用で問題になれば別の決定を起こす。

### 決定 4: 本番環境では起動しない。設定ではなく起動時の検査で落とす

`app.simulation.enabled` が真かつ環境が本番なら、**アプリケーションの起動を失敗させる**。
設定値を読んで実行時に断る形にはしない。

**破られたら**: 設定の読み違いで、本番に `SIM-` の荷主と貨物が生まれる。決定 3 の除外が
効いていても、**実在しない輸送の記録が本番の DB に残る**こと自体が業務の事故である。

### 決定 5: 失敗しても巻き戻さない

工程ごとに独立したトランザクションで進め、失敗したらそこで止める。
**それまでに作られた業務データは取り消さない。**

IT12 では `@Transactional` が入金の記録ごと巻き戻し、経理担当者が何度押しても記録できない
経路があった。ここで巻き戻すと、**どこまで進んだかを追う材料が消える**——US35 の目的そのものを
失う。

**破られたら**: 「失敗しました」だけが残り、経路候補が 0 件なのか、サービス間の設定が
間違っているのか、通関で止まっているのかが分からない。原因の切り分けに結局手作業が要る。

## 影響

### 良い影響

- 実際の経路を人手なしで踏める。IT5・IT12・IT13 で 3 度出た同型の欠陥を、配備直後に検出できる
- 実演の手順が揺れない
- 認可の抜け道を作らないため、シミュレーションが通ることが**実利用者も通ること**を意味する

### 悪い影響・受け入れるコスト

- **サービスが 8 つになる**。立ち上げの型（Gradle・Flyway・ArchUnit・k8s・`APP_*_SERVICE_BASE_URL` の検査）を踏襲する分のコストがかかる
- Gateway 経由で呼ぶため、内部 API を直接叩くより**遅い**。実行時間は業務の実際の応答時間に依存する
- 工程ごとにログインし直すため、**認証の回数が増える**

いずれも決定 2 の代償であり、速さのために内部 API へ寄せると仕組みの意味が失われる。

## コンプライアンス

> **実在する検査だけを名前で挙げる。** IT12 のレビューで、ADR-028 の表が挙げる 5 クラスの
> **すべてが存在しない**ことが分かった。`AdrComplianceTableTest` が名前の実在を機械で
> 確かめるため、まだ置いていない検査は**名前を書かず、どの Phase で置くかを書く**。
> 本 ADR が「承認済み」になる条件は、この列がすべて名前で埋まることである。

| 決定 | 破られたら何が起きるか | それが起きないことの検査 |
| :--- | :--- | :--- |
| 1 simulationms を独立させる | 業務サービスが呼び出し元の都合で変わる | `ArchitectureTest`（simulationms も shared の `ServiceArchitectureTest` を継承し、BC 独立性ルールの対象になる）・`ArchitectureRuleCoverageTest`（settings.gradle の全サービスが対象であることを名簿なしで確かめる） |
| 2 Gateway 経由・実利用者として呼ぶ | 認可を素通りする経路が新設される | `SimulationArchitectureTest`（内部 API と `system:` 名乗りをどこからも参照しない／出口は `BusinessGateway` の 1 ポートだけ。**違反を入れて赤になることを確認済み**）・`ScenarioTest`（すべての工程が踏む人のロールを持つ） |
| 3 荷主コードで識別する | 実データに混ざり、締めと対応一覧が信用できなくなる | 未実装（Phase 4.1・4.3）: `SIM-` 帯の採番と、精算の締め対象・未解決例外一覧・荷主向け一覧のそれぞれで**除外する側**に置く検査 |
| 4 本番では起動しない | 本番に実在しない輸送の記録が残る | `SimulationDisabledInProductionTest`（本番プロファイル + 有効化で起動が失敗する・無効なら起動する・本番でなければ有効にできる） |
| 5 巻き戻さない | どこまで進んだかを追えない | `SimulationRunTest`（失敗した工程で止まり、それまでの結果と識別子が残る／失敗後は続きを記録できない）。実際の業務データが残ることは Phase 3.4 で統合テストにする |

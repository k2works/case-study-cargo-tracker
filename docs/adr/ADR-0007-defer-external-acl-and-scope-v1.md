# ADR-0007: 外部連携 ACL 基盤を延期し、v1.0.0 のスコープから精算を外す

## ステータス

承認済み（2026-08-03・IT6）

## 文脈

リリース計画は当初、v1.0.0 を「予約から精算まで」と定義し、
以下の 2 つを含んでいた。

| 対象 | 内容 | 見積 |
| :--- | :--- | :--- |
| Phase 5（精算） | US21-23。請求書の発行・支払い確認・入金消込 | 13 SP |
| TS07 | 外部連携の ACL 基盤（外部 API を叩くためのポート・スタブ・契約テスト） | 5 SP |

いずれも **IT4 から 2 回先送りしていた**。先送りの理由はそのつど
「今回のゴールに直結しない」であり、**判断そのものは一度も下していない**。

「余力次第の返済枠」は毎イテレーション繰り越されて固定化する。
判断を保留したまま計画へ残し続けると、残っていること自体が
「いつかやる」という合意に見えてしまう。

### TS07 の実態

現時点で**外部連携を必要とするストーリーが 1 つも無い**。

| 外部連携に見えるもの | 実態 |
| :--- | :--- |
| US08（経路候補の算出） | Datalog による自前実装。外部のルーティング API は使わない |
| 荷主の与信 | v1.0.0 のスコープに無い |
| 船社のスケジュール取込 | US24 は**画面から人が登録する**（IT6 で実装済み） |

ACL 基盤は「外部と話す必要が生じたときに、その相手に合わせて」作るものである。
相手が決まる前に基盤だけ作ると、実際の相手が来たときに作り直すことになる。

### 精算の実態

精算（請求・入金）は**会計システムとの境界**を持つ領域であり、
本ケーススタディが扱う「貨物の予約・経路・追跡」とは関心が異なる。
v1.0.0 に含めると、その境界の設計をリリース前に決め切る必要が生じる。

## 決定

**1. v1.0.0 の定義を「予約から荷役・追跡まで」に変更する。**
精算（Phase 5・US21-23・13 SP）は v1.0.0 のスコープ外とし、v1.1.0 以降で扱う。

**2. TS07（外部連携 ACL 基盤・5 SP）は、必要とするストーリーが立つまで着手しない。**
リリース計画からは削除せず「延期」として残し、**着手条件を明記する**。

着手条件: **外部システムと通信するストーリーが計画に入ったとき**。
そのストーリーの相手（プロトコル・認証・失敗時の振る舞い）が分かってから設計する。

## 根拠

**リリースは「動くものが出ること」に価値がある。** 予約 → 経路 → 荷役 → 追跡は
それだけで一連の業務として閉じており、荷主・営業・経路設計者・荷役担当者の
4 ロールが実際に使える。精算を待つ理由は無い。

**使われない基盤は負債である。** ACL 基盤を先に作ると、テスト・ドキュメント・
アーキテクチャ検査の対象になり、変更のたびに維持コストがかかる。
それに対して得られる価値は「将来の作業が少し楽になるかもしれない」だけである。

**判断を下すこと自体に価値がある。** 「余力次第」のまま残すと、
毎イテレーションの計画で同じ検討を繰り返し、そのつど時間を使う。
スコープ外と決めれば、以降その検討は発生しない。

## 帰結

### よい点

- IT6-IT10 の 59 SP が 12-13 SP × 5 に収まり、**縮退を前提としない計画**になった
- 精算の境界設計をリリース前に決め切る必要が無くなった
- TS07 の着手条件が明文化され、「まだやらない」理由を毎回説明しなくてよくなった

### 悪い点

- **v1.0.0 では売上が立たない**。請求できないため、実運用に投入するなら
  精算は別手段（既存の会計システムへの手入力）で回す必要がある
- 精算を後から足すとき、予約・貨物の集約に請求に必要な属性が
  足りない可能性がある。その時点で追加する。**集約のフィールドは `Option` で
  段階的に導入する**（既存データを読めなくせずに列を増やせる）

### この判断を見直す条件

- 外部システムと通信するストーリーが計画に入ったとき（TS07 の着手条件）
- v1.0.0 のリリース後、精算を v1.1.0 の最優先とするかを改めて決める

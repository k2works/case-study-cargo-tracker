# ADR-0011: 経路の割り当ては Booking の集約を通して書く

経路設計者が選んだ経路を予約へ紐付ける書き込みは、**ドメインイベントではなく
Booking のアプリケーションサービスを同期的に呼ぶ**。
[ADR-0009](ADR-0009-routing-pulls-booking-via-acl.md) の US09 該当節を supersede する。

あわせて、**合成ルートに置く BC 間の翻訳を `src/composition/acl/` に限定し、
`arch-lint` 規約 11 で機械検査する**。

日付: 2026-08-04

## ステータス

2026-08-04 承認されました（IT9・US09/US11 の着手前）

## コンテキスト

IT9 は US09（経路の選択・確定）・US11（予約への紐付け）を実装する。
**Routing 側の画面で選ばれた経路が、Booking の `Cargo` に書き込まれる**——
本プロジェクトで初めての、BC をまたぐ**書き込み**である。

### ADR-0009 は既に方式を決めていた

[ADR-0009](ADR-0009-routing-pulls-booking-via-acl.md) は次のように書いている。

> したがって US09 では **Routing が「選ばれた経路」をドメインイベントとして発行し、
> Booking の購読者が `Cargo` を更新する**。Routing が `cargo` / `leg` テーブルへ
> 書き込む形は採らない。
>
> **書き込み方向の越境を許すと、ここまでの BC 独立性の投資が一気に無駄になる**。
> 読み取りの ACL は「相手のスキーマに依存する」だけだが、
> 書き込みの ACL は「**相手の不変条件を壊しうる**」。

**この懸念は正しい。** 本 ADR は懸念を否定するのではなく、
**懸念が指す危険の正体を特定し、より小さい手段で同じ保護を得る**ことを述べる。

### 着手前に判明した 2 つの事実

**1. 更新される集約は 1 つだけである。**

[バックエンドアーキテクチャ](../design/architecture_backend.md)のトランザクション規約は
「1 トランザクションで更新する集約は 1 つとし、他集約への波及はドメインイベントで行う」
と定める。ADR-0009 がイベントを選んだのは、この規約に従ったためと読める。

しかし US09/US11 で**書き込まれるのは `Cargo` だけ**である。

| 集約 | 本操作での扱い |
| :--- | :--- |
| `Cargo`（Booking） | **更新する**（旅程の付与・`RoutingStatus` の変更） |
| `Voyage`（Routing） | 読むだけ（候補の算出に使う） |
| 経路候補 | **永続化しない**（IT7 の判断。都度算出） |

**波及先の集約が存在しない。** したがってトランザクション規約は本操作に適用されない。
イベントを挟む理由が、規約の側から見て無い。

**2. イベント基盤が実装に存在しない。**

BC 間の連携は現在すべて直接呼び出し（ACL ポート）である。
イベント方式を採るには、イベント型・発行・購読の登録・トランザクション内での
配送を新設する必要がある。US11 は 3 SP であり、**基盤の新設は収まらない**。

## 決定

### 1. Booking のアプリケーションサービスを同期的に呼ぶ

Routing は `BookingItineraryAssignment` ACL ポートを**自分の語彙で**宣言する。
実装は Booking の `BookingBookCargo`（アプリケーションサービス）を呼ぶ。

```
経路割り当て画面（Routing）
  → RouteAssignment ユースケース（Routing・候補の妥当性を検証）
    → BookingItineraryAssignment ポート（Routing の語彙）
      → [合成ルートの ACL] 翻訳
        → BookingAssignItinerary（Booking のアプリケーションサービス）
          → Cargo.attachItinerary（集約が不変条件を検証）
```

**`cargo` / `leg` テーブルへ直接書く形は採らない**——この点は ADR-0009 のとおりである。

### 2. 不変条件は集約が守る

ADR-0009 の懸念「書き込みの ACL は相手の不変条件を壊しうる」が指す危険は、
**相手のテーブルへ直接書くこと**である。集約を通す限り、この危険は生じない。

`Cargo.attachItinerary` は次を検証し、満たさなければ `Err` を返す。

- 予約が `ROUTE_PROPOSED` であること（仮受付・確定済みには割り当てない）
- 旅程の端点が `RouteSpecification` の出発地・仕向地と一致すること
- 区間が連結していること（前の荷降港＝次の積込港）
- 区間が 1 つ以上あること

**呼び出し元が誰であっても、これらは迂回できない。** Routing が壊れた値を渡しても
集約が拒む。**保護は呼び出し元の行儀の良さに依存しない**——ここが本 ADR の要点である。

### 3. 合成ルートの翻訳を `src/composition/acl/` に限定する（規約 11）

[ADR-0010](ADR-0010-estimation-reuses-route-finder-via-composition.md) は
BC 間の翻訳を合成ルートに置いたが、**`arch-lint` 規約 4 の対象外**であるため
検出できない穴になった。本 ADR で穴を**数えられる形**にする。

| 項目 | 内容 |
| :--- | :--- |
| 規約 11 | **BC 間の翻訳は `src/composition/acl/` にのみ置く**。`src/composition/*Wiring.flix` に 2 つ以上の BC への参照を書かない |
| 検出方法 | `*Wiring.flix` が参照するモジュールのコンテキストを数え、`shared` を除いて 2 つ以上あれば違反 |
| 例外 | `src/composition/acl/` 配下（翻訳の置き場所）。`Composition.flix` は**ルーティング表そのもの**であり全 BC の `Routes` を参照するのが役目のため対象外（翻訳は持たない） |

**「穴を塞ぐ」のではなく「穴に名前を付けて数えられるようにする」**。
`composition/acl/` にファイルが何本あるかが、BC 間の翻訳の件数そのものになる。

### 4. ADR-0010 の適用範囲を読み取りに限定する

ADR-0010 は Estimation → Routing の**読み取り**（経路探索）についての判断である。
書き込みは本 ADR が扱う。ADR-0010 側にその旨を追記する。

## 検討した選択肢

### A. ドメインイベントで連携する（ADR-0009 のとおり）

**却下。** 理由は 3 つある。

1. **波及先の集約が無い**（上記の事実 1）。イベントは「1 トランザクション 1 集約」を
   守るための手段であり、守るべき対象が無いところで使うと**手段だけが残る**
2. **基盤の新設が US11 の 3 SP に収まらない**（事実 2）
3. **同期配送するイベントは、間接層を 1 つ増やした同期呼び出しである**。
   非同期にする要求は US09/US11 に無い（経路を割り当てた瞬間に画面へ結果を返す）

> **将来イベントが要る場面は来る**。US13 の「経路設計者に追跡番号発行依頼の通知」
> （将来リリース）や Tracking との連携がそれである。**そのときに基盤を作る**。
> 今作ると、最初の利用者が「イベントを必要としない操作」になる。

### B. Booking のアプリケーションサービスを同期的に呼ぶ（採用）

上記のとおり。

### C. 画面を Booking 側へ移す

経路割り当ての POST を Booking のルートにすれば、書き込みの越境は消える。

**却下。** 画面が選んだ候補を Booking が再検証するには `RouteFinder` が要り、
**Booking が Routing へ依存する**——向きが逆になるだけで越境は残る。
候補の legs をフォームの hidden field で運ぶ案は、**利用者が改竄できる**。

## 帰結

### よい点

- **不変条件の保護が呼び出し元に依存しない**。集約を通す限り、
  誰がどう呼んでも壊れない
- イベント基盤という「まだ要らないもの」を作らずに済む
- **BC 間の翻訳が数えられるようになる**（規約 11）。
  ADR-0010 が残した穴が、`composition/acl/` のファイル数として可視化される
- Routing のドメイン・アプリケーション層は Booking の型を知らない。
  ポートの語彙は Routing のものである

### 悪い点・引き受けるリスク

- **合成ルートの ACL が「配線」以上のものを持つ状態は続く**。規約 11 で
  置き場所を限定したが、そこに書かれるコードの量は増えていく。
  **`composition/acl/` のファイルが 5 本を超えたら、BC 間連携の設計そのものを見直す**
- 同期呼び出しであるため、Booking の処理が遅いと Routing の画面応答が遅くなる。
  現時点で `attachItinerary` は 1 行の `UPDATE` と数行の `INSERT` であり問題にならない
- **ADR-0009 の記述と食い違う**。ADR-0009 側に supersede の注記を入れ、
  「US09 の該当節は ADR-0011 が置き換えた」と明記する

### 再検討する条件

次のいずれかが起きたら本判断を見直す。

- **波及先の集約ができたとき**（Tracking の `TrackingActivity` を同時に更新する要求など）。
  そのときは 1 トランザクション 1 集約の規約が効き、イベントが必要になる
- `composition/acl/` のファイルが **5 本を超えた**とき
- 非同期の要求が出たとき（通知・外部システム連携）

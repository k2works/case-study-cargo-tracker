# ADR-013: 利用者と荷主の紐付けは Security Context が共有カーネルの ShipperId だけで持つ

利用者アカウントと荷主を結びつける情報を **Security Context の `users` テーブルに置き、値としては共有カーネルの `ShipperId` だけを持つ**。Security Context は Shipper Context のモデルを一切参照しない。

日付: 2026-08-09

## ステータス

承認済み

## コンテキスト

IT2 で貨物予約一覧を荷主（`ROLE_SHIPPER`）に開放したとき、**利用者アカウントと荷主を結びつける手段が無く、他社の予約まで見える状態だった**。クローズ前のレビューで気づいて開放を取り消し、以来 7 イテレーションにわたって「US34 で紐付けを作ってから開放する」と書き続けてきた（貨物予約一覧・追跡の認証つき一覧・追跡番号の末尾 4 桁検索・自社貨物一覧の 4 か所）。

US34（荷主が自社の予約を照会する）は、この積み残しを解く。解くには「いまログインしている利用者はどの荷主か」を答えられる必要があり、**その答えをどの BC が持つか**が構造の判断になる。

### 制約

- **ADR-005**: 共有カーネルは `Location` と `ShipperId` の 2 つに限る。増やすと 1 つの変更が全 BC の再ビルドとレビューを強制する
- **ArchUnit ルール 4**: ドメイン層・アプリケーション層は BC をまたいでクラスを参照しない。またげるのは `infrastructure/acl` のアダプタだけである
- **ADR-012**: BC 間の依存の向きは一方通行に保つ。逆向きのポートを足す前に順方向を疑う

## 決定

**`users` テーブルに `shipper_id`（`UUID`、`NULL` 可、FK → `shipper.id`）を置く。** Security Context の集約 `UserAccount` はこれを共有カーネルの `ShipperId` として保持し、認証情報（`ShipperScopedUser`）に載せる。

画面（Booking Context）は **共有の約束 `ShipperScopedPrincipal` / `CurrentUser` 越しにだけ**これを読む。Security Context のクラスは参照しない。

```text
security/…/ShipperScopedUser  ──implements──▶  shared/application/security/ShipperScopedPrincipal
booking/…/BookingController   ──uses──────────▶  shared/application/security/CurrentUser
```

**運ぶのは `ShipperId` だけである。** 荷主の名前も連絡先も運ばない。表示に要る値は CQRS のクエリ側が SQL で読む（`shipper` を JOIN する既存の方式と同じ）。

### 絞り込みの規律

- **絞り込みは SQL で行う。** 画面側で絞ると、検索条件・ページング・並べ替えのどれか 1 つを変えたときに漏れる
- **絞るかどうかはロールで決め、紐付けの有無では決めない。** 「紐付けが無い = 絞らない」にすると、設定を忘れた荷主に全社の予約が見える。**設定漏れが情報漏洩に直結する形を作らない**
- **他社の予約は 404 を返す**（403 ではない）。403 は「存在するが見せない」と伝えてしまい、番号を変えながら叩けば他社の予約の有無を確かめられる。追跡照会（US18）で「存在しない番号と権限外の番号を区別しない」と決めたのと同じ判断である

## 結果

### よい影響

- 認証の 1 回の読み込みで紐付けが載る。**画面が予約を読むたびに利用者から荷主を引き直す形にならない**（引き忘れた経路が他社の予約を見せる、が起きない）
- Security Context は Shipper Context のモデルを知らないままである。ArchUnit ルール 4 に触れず、ACL ポートも増えない
- 7 イテレーション積み上がった「紐付けができてから開放する」の前提が解け、貨物予約一覧を荷主に開放できた

### 受け入れる代償

- **紐付けの設定手段は本 IT では画面に無い。** 動作確認環境はデモデータ（`V904`）で、本番は運用手順で設定する。画面からの設定は荷主管理（US32 の延長）で扱う
- **FK が Shipper Context のテーブルを指す。** テーブル間の参照は BC をまたぐ。コードの参照は無いが、スキーマ上の結合は残る。荷主が消えたときに宙に浮いた紐付けを残さない（「存在しない荷主の予約を探す利用者」を作らない）ことを優先した

## 検討したが採らなかった案

| 案 | 内容 | 不採用の理由 |
| :--- | :--- | :--- |
| Shipper 側に利用者 ID を持つ | `shipper` に `user_id` を置く | **引く向きが業務と逆である。** 必要なのは「この利用者はどの荷主か」であり、ログインのたびに荷主全件から逆引きすることになる。荷主 1 社に利用者が複数いる将来も表せない |
| 独立した紐付け BC を作る | `identity-link` のような BC を新設する | **BC が 1 つ増えて得るものが「1 列」しかない。** ACL ポートが 2 本増え、ADR-012 の依存の向きにも新しい辺が増える |
| `ShipperId` ではなく荷主コードを持つ | `users.shipper_code` にする | **荷主コードは表示のための識別子**であり、採番の都合で変わりうる。同一性は `ShipperId` が表す |
| 認証情報に載せず毎回引く | 画面ごとに利用者 → 荷主を引く | **引き忘れた 1 か所が他社の予約を見せる。** 認可の欠落は「動くが漏れる」形で現れ、テストが緑のまま残る |
| 共有カーネルに `UserAccount` を置く | 利用者そのものを共有する | **ADR-005 と矛盾する。** 認証の都合の変更が全 BC に波及する |

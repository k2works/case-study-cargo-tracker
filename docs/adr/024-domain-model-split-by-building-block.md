# ADR-024: ドメインモデルを構成要素ごとのパッケージに分ける

## ステータス

承認済み（2026-08-12。IT19）

## コンテキスト

各 BC の `domain/model` は 1 つのパッケージにすべてを入れていた。実測で **140 クラス**あり、最大の Booking は 35 クラスが 1 階層に並んでいた。

パッケージを開いたとき、**どれが集約ルートでどれが値オブジェクトなのかは、クラスを開くまで分からない**。JIG のパッケージ図でも 1 つの箱になり、構成要素の別が読み取れない。

参照実装（`practical-ddd-in-enterprise-java` の `bookingms`）は `domain/model` を **aggregates / entities / valueobjects / commands** に分けている。

## 決定

**各 BC の `domain/model` を、DDD の構成要素ごとのサブパッケージに分ける。**

| サブパッケージ | 入れるもの |
| :--- | :--- |
| `aggregates` | 集約ルートと、その識別子 |
| `entities` | 集約の内側で同一性を持つもの |
| `valueobjects` | 値オブジェクトと列挙 |
| `commands` | 業務の要求を 1 つの型にまとめたもの |

**ドメインサービスと例外は `domain/model` 直下に残す。** どのサブパッケージにも属さないためであり、参照実装もサービスの置き場を持たない。該当するのは 6 クラス（`RouteSearchService` / `FreightEstimator` / `FreightChargeCalculator` / `DischargeCandidates` / `ClaimCodeMatch` / `InvalidBookingStatusTransitionException`）である。

**サブパッケージにはすべて `package-info.java` を置く。** 説明の無いパッケージは JIG の図では名前だけの箱になる。

## 結果

### 得たもの

- **パッケージを開いた時点で構成要素が分かる。** 「この BC の集約ルートは何か」は `aggregates` を見れば足りる
- **JIG の用語集に構成要素ごとの説明が載る**（27 パッケージ分を追加）
- **集約ルートの数が目に見える。** Booking は 4、Handling は 3、Routing は 2 —— **多いことがひと目で分かる**

### 失ったもの（**重要**）

**パッケージプライベートで守っていた境界が壊れた。**

分割前、集約の内側だけに開いていた操作は「同じパッケージにいること」で守られていた。javac が越境を止めていたのである。サブパッケージに分けると同じパッケージではなくなるため、**7 つのメソッドを `public` にせざるを得なくなった**。

| クラス | 開いた操作 | 本来呼んでよいもの |
| :--- | :--- | :--- |
| `ProposedRoute` | `of` / `withPriority` | `RouteSearchService` |
| `TrackingExceptionEvent` | `raise` / `resolve` | 集約ルート（`TrackingActivity`） |
| `CargoProgress` | `withStatus` / `withRouting` / `issued` | 集約ルート（`Cargo`） |
| `NotificationDelivery` | `succeeded` | 集約ルート（`BookingNotification`） |

**これはコンパイラによる保証を、コメントによる約束へ格下げしたということである。** 各メソッドには「呼んでよいのは誰か」を書いたが、**書いてあることと守られていることは別である**（本プロジェクトが繰り返し踏んできた形そのものである）。

**この損失を検査で埋め合わせていない。** 埋め合わせるなら「集約ルート以外から `entities` の生成・変更メソッドを呼ばない」という ArchUnit ルールが要る。**IT19 では書いていない** —— 名前で記録し、次のイテレーションへ送る。

### 変えなかったもの

- **集約の境界そのもの。** どのクラスがどの集約に属するかは変えていない
- **BC 間の規律。** ArchUnit のルール 4（BC 間でクラスを直接参照しない）はパッケージ階層が深くなっても効く
- **共有カーネルの検査。** 対象を `shared.domain.model` から `shared.domain.model..` に広げた（**サブパッケージへ移した瞬間、ルールは「何も検査していない」状態になった**。`allowEmptyShould(true)` を使っていなければ、これは赤で気づける）

### 副次的に返した負債

`Cargo` が分割の import で 500 行を超え、Checkstyle が赤になった。**IT15 から 4 イテレーション持ち越していた D1**（「次に `Cargo` を触る IT で引取まわりを切り出す」）をここで返し、`claimCode` / `consignee` / `claimedAt` を `CargoClaim` にまとめた（498 行）。

## 代替案

### 分けない（現状維持）

**採らなかった。** 140 クラスが 9 つのパッケージに平らに並ぶ状態は、新しく読む人に構成要素の別を伝えない。

### `entities` を作らず、集約ルートと同じパッケージに置く

**カプセル化を失わずに済む案である。** 採らなかったのは、参照実装の構成に揃えることを優先したためである。**失ったものの節に書いたとおり、この判断には実費がある。**

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| すべてのパッケージに説明がある | **`PackageInfoPresenceTest`**（IT19 で追加） | `.java` を置いたディレクトリに `package-info.java` があること。**中身が正しいかは見ない** |
| トップレベルは BC と 1 対 1 | **`PackageStructureTest.すべてのクラスはBC集合のいずれかに属する`** | クラスの所属パッケージのみ。**サブパッケージの名前は見ていない**（`aggregates` を `roots` と書いても落ちない） |
| 共有カーネルは Location と ShipperId だけ | **`PackageStructureTest.共有カーネルはLocationとShipperIdのみ`** | `shared.domain.model..` 配下の単純名。**サブパッケージへ移した瞬間に「何も検査していない」状態になり、赤で気づけた** |
| BC 間でクラスを直接参照しない | **`PackageStructureTest.コンテキスト間でクラスを直接参照しない`** | Java のクラス参照のみ。パッケージが深くなっても効く |
| 集約ルート以外が `entities` の生成・変更を呼ばない | **守らない。** | **検査の外。** 分割前は javac が止めていたが、公開した 7 メソッドは**誰からでも呼べる**。コメントに「呼んでよいのは誰か」を書いただけである |

> **最後の 1 行が本 ADR の代償である。** 「書いてあること」と「守られていること」は別であり、
> 本プロジェクトはそれを繰り返し踏んできた。**次のイテレーションで ArchUnit ルールに落とす**
> （名前で記録した）。

# ADR-010: Handling Context を独立した境界付けられたコンテキストに昇格する

荷役コンテキストを Tracking Context 内のモジュールから、独立した境界付けられたコンテキスト（`handling/`）へ昇格する。**ADR-002 を置き換える。**

日付: 2026-08-08

## ステータス

承認済み（**ADR-002 を置き換える**）

## コンテキスト

ADR-002（2026-08-06）は、Handling を Tracking Context 内のモジュール（`tracking/handling/`）として実装することを決めた。その判断根拠は 3 つだった。

1. 荷役イベントの登録と輸送状態の遷移は**同一の不変条件**を共有する
2. 独立 BC にすると、最高頻度の操作に**BC 間の結果整合**という最も重い連携機構を課すことになる
3. 荷役作業員と追跡管理者で**ユビキタス言語が分岐していない**

IT6 で Tracking Context と Handling モジュールを実際に実装した結果、**根拠 2 と 3 の前提が変わった**。

### 根拠 2 の前提が変わった

ADR-002 は「独立 BC = 結果整合が必要」を前提にしていた。しかし IT6 では、**Handling → Booking をすでに ACL の同期呼び出し（同一トランザクション）で実装している**。ADR-009 はこれを全 BC 間連携の方針として明文化した。

**独立 BC にしても結果整合は要らない。** 根拠 2 が指していたコストは、もはや発生しない。

### 根拠 3 の前提が変わった

実装してみると、**言語は分岐していた**。

| 概念 | Handling | Tracking |
| :--- | :--- | :--- |
| 作業・出来事の種別 | `HandlingType`（受領・積込・荷降し・通関・引取） | `TrackingEventType`（同じ 5 値だが「追跡の上で何が起きたか」） |
| 航海番号 | `HandlingVoyageNumber` | `TrackingVoyageNumber` |
| 予約参照 | `CargoBookingId` | `TrackingBookingId` |

IT6 の実装では、**同じ BC の中にいながら 3 組の対応する型を別々に定義していた**。`TrackingEventType` の Javadoc は「荷役として何をしたかと、追跡の上で何が起きたかは**別の事実**である」と自ら述べている。

**別の事実を扱う 2 つのモデルが 1 つの BC に同居していた。** これは統合されている状態ではなく、**境界が引かれていないだけ**である。

さらに、実装は名前が一致していることに依存した `TrackingEventType.valueOf(handlingType.name())` という結合を持っていた（IT6 レビュー M2）。分離を宣言しながら、文字列で結合していた。

### 根拠 1 について

「荷役イベントが登録されたら輸送状態が必ず更新される」は正しい。しかし**それは同一トランザクションで担保できる**（ADR-009）。不変条件の共有は、BC を分けない理由にはならない。

### ADR-002 が挙げていたネガティブが現実になった

ADR-002 自身が「Tracking Context が肥大化する。追跡・例外イベント・荷役・通関申告の 4 領域を抱えることになり、将来 Tracking の分割が必要になる可能性がある」と記していた。IT6 で荷役だけが実装された時点で、`tracking/` 配下は 2 つの独立したモデル群に分かれていた。

## 決定

**Handling を独立した境界付けられたコンテキスト（`com.example.cargotracker.handling`）へ昇格する。**

- トップレベルパッケージを `tracking/handling/` から `handling/` へ移す
- Handling → Tracking の連携は **ACL ポート `TrackingEvents`** を通す（定義は Handling、実装は Tracking の `infrastructure/acl`）
- 呼び出しは**同期・同一トランザクション**（ADR-009）。結果整合は採らない
- ArchUnit の BC 集合に `handling` を加える。**BC 分離ルール（ルール 4）が Handling と Tracking の間でも効くようになる**

### 変更箇所

- `apps/cargo-tracker/src/main/java/com/example/cargotracker/handling/**`（パッケージの移動）
- `handling/application/internal/outboundservices/acl/TrackingEvents`（新設。荷役 → 追跡）
- `tracking/infrastructure/acl/TrackingEventsAdapter`（新設。**荷役種別 → 追跡イベント種別の翻訳はここで行う**）
- `PackageStructureTest`: BC 集合に `handling` を追加
- テストの置き場: 荷役のテストを `com.example.cargotracker.handling` へ移す（**ルールはテストにも等しく効く**）
- `architecture_backend.md` / `domain-model.md` / `data-model.md` / `test_strategy.md`: Handling を独立 BC として記述する
- `ui_design.md`: URL パス `/handling/*` は**変更しない**（ADR-002 の判断を維持する。URL は利用者から見た業務の区切りであり、内部構成に追随させない）

### 代替案

| 代替案 | 却下理由 |
| :--- | :--- |
| ADR-002 のまま維持する | 実装では既に 3 組の対応型を別々に定義しており、**境界が引かれていないだけの状態**だった。維持すると、名前の一致に依存した結合（`valueOf`）が残り続ける |
| 型の重複をやめ、本当に 1 つのモデルに統合する | 荷役種別と追跡イベント種別は**別の事実**である（同じ値でも、荷役は「作業として何をしたか」、追跡は「輸送の上で何が起きたか」）。統合すると、荷役に種別を足すたびに追跡の表示規則を触ることになる |
| 通関申告だけを別 BC に切り出す | ADR-002 が将来の候補として挙げた案。**荷役と追跡の分離が先**である。通関は US29（IT11）で実装するため、そのときに改めて判断する |

## 影響

### ポジティブ

- **BC 分離ルールが Handling と Tracking の間で効くようになる。** 実際に、昇格後に荷役から追跡の型を直接参照する変更を入れると ArchUnit が捕まえることを実測した
- 名前の一致に依存した結合（`TrackingEventType.valueOf(...)`）が、境界での明示的な翻訳（`switch`）に変わった。荷役に種別を足しても、対応を書き忘れればコンパイルではなく**翻訳の場所で**気づける
- Tracking Context の責務が「追跡・例外イベント」に絞られ、US19 / US20（例外処理。IT10）の実装余地が読みやすくなった

### ネガティブ

- **境界を越える翻訳のコードが増える。** `TrackingEvents` の引数は素の値であり、荷役側の型を組み立て直す手間がかかる。これは ACL の対価であり、意図的に受け入れる
- ADR-002 を 2 日で置き換えたことになる。**判断が早すぎたのではなく、実装しないと分からないことがあった**（言語が分岐するかどうかは、モデルを書いてみるまで分からない）
- 通関申告（US29）は現時点で未実装であり、その所属は Handling に置く前提だが、実装時に再検討の余地が残る

## コンプライアンス

- ArchUnit の BC 集合に `handling` が独立して現れること
- `handling/` 配下のクラスが `tracking/` の型を直接参照していないこと（ACL ポート経由のみ）
- 荷役種別と追跡イベント種別の対応が、文字列の一致ではなく明示的な写像で行われていること
- 荷役のテストが `com.example.cargotracker.handling` に置かれ、追跡の型を参照していないこと

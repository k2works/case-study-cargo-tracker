# ADR-019: 支払期限の超過は画面を開いたときに判定する

支払期限を過ぎた請求書に印を付ける処理を、定期実行のバッチではなく**画面を開いたときの判定**として実装する。

日付: 2026-08-10

## ステータス

承認済み

## コンテキスト

US23 は「支払い期限超過時、経理担当者に未払い通知が送信される」と定めている。

期限超過は**時間の経過だけで起きる**状態変化であり、誰かの操作では起きない。実装の選択肢は 2 つある。

1. 定期実行（夜間バッチ・スケジューラ）で全件を走査して印を付ける
2. 経理担当者が請求の画面を開いたときに判定する

本システムには定期実行の基盤がなく、導入すれば**動いているかを監視する仕組みも同時に要る**。

## 決定

**画面（請求書一覧・ダッシュボード）を開いたときに判定する。**

- 未入金かつ発行済みの請求書を引き、期限を過ぎていれば `payment_status` を `OVERDUE` にする
- 判定は**業務のタイムゾーンの今日**で行う（`Clock` から取る）
- **期限当日は超過にしない**

あわせて、US23 の「未払い通知が送信される」は**画面で気づける形**として実現する（ダッシュボードのカード＋督促対象一覧）。通知の自動送信は作らない。

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| 未入金かつ発行済みのみを超過にする | **ドメイン**＋ `InvoiceReminderTest` | **集約の判定**と一覧のテスト |
| 判定は業務のタイムゾーンの今日で行う | **`BusinessClockTest`**＋`InvoiceReminderTest`（`TZ=UTC` でも緑であることを CI が見る） | **業務時刻を注入した経路**のみ（`TZ=UTC` の CI でも緑であることを含む） |
| **期限当日は超過にしない** | **`InvoiceReminderTest`**（境界のテスト） | **境界の 1 日**（前日・当日・翌日）のみ |
| 通知の自動送信を作らない | **守らない。** | **検査の外。** 送信処理を足しても落ちない |

## 根拠

- **動いていないことに気づける。** バッチは止まっても誰も気づかない。気づくのは督促が半月遅れたときである。画面の判定は、経理担当者が仕事を始めた瞬間に走る
- **経理担当者は毎日この画面を開く。** 督促は画面を見た人が起こす行為であり、**見る前に印が付いている必要は無い**
- **監視の仕組みを増やさない。** バッチを入れると「バッチが動いているか」を見る場所がもう 1 つ増える
- **送信の仕組みを先に作らない。** 受け取る人が見る場所が無ければ、送っても届かない（IT13 の運用要件 R2 で「拾えなかった実績が出てから作る」と決めた形に揃える）

## 影響

### よくなること

- 追加の実行基盤・監視が要らない
- 判定のロジックが 1 か所（集約の `markOverdue`）に収まり、テストで日付を渡して確かめられる

### 気をつけること

- **誰も画面を開かなければ印は付かない。** ただし印が付いていても、見る人がいなければ督促は進まない。困り方は変わらない
- 請求書の件数が増えると、画面を開くたびの走査が重くなる。**未入金かつ発行済み**に絞っており、件数はそのまま「督促待ちの件数」である。膨らんだら、そのこと自体が業務の問題として先に見える
- 外部システムへ「期限超過になった」ことを能動的に伝える要求が出たら、本 ADR を見直す

## 代替案

| 案 | 却下の理由 |
| :--- | :--- |
| 夜間バッチで判定する | 実行基盤と監視が要る。**止まっても気づかない** |
| 判定せず、画面で毎回「期限 < 今日」を評価する | 状態が残らず、督促の対象を SQL で絞れない |
| 期限超過をメールで自動送信する | 受け取る場所（画面）が無いまま送信だけ作ると、届いたかどうかを誰も確かめられない |

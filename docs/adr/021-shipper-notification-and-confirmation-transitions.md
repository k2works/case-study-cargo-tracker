# ADR-021: 荷主への通知・予約の確定・追跡番号の発行で動く状態

経路が決まった予約を荷主へ提示し（US12）、合意を得て確定し（US13）、追跡番号を発行する（US14）ときに、予約のどの状態が動くか・誰の手番か・どこへ戻せるかを決める。

日付: 2026-08-22

## ステータス

承認済み

## コンテキスト

[ADR-020](020-itinerary-assignment-transitions.md) で経路の割り当てまでは決まった。IT6 はその先を閉じる。`BookingStatus` は実装上まだ `PRELIMINARY` と `ROUTE_PROPOSED` の 2 つしかなく、設計（`domain-model.md`）にある `CONFIRMED` / `TRACKING_ISSUED` は使えるようになっていない。

決めることが 6 つある。いずれも**永続化された行に現れる**ため、あとで直すと移行が要る。

- 「荷主へ通知した」を状態にするか、記録だけにするか
- 再通知を許すか
- 確定したあと戻せるか（US13-4 の射程）
- US13-4 の「経路設計中に戻す」が何を指すか（`BookingStatus` だけか、`RoutingStatus` も動かすか）
- `CANCELLED` をここで足すか
- 状態ごとに**誰の手番か**

加えて、[イテレーション 6 計画](../development/iteration_plan-6.md)の注 13 が「経路設計者は `CONFIRMED` の予約を開けないので US14 が 404 になる」と書いていた。**この読みは誤りである**（決定 7）。実装を確かめてから決める。

## 決定

### 1. `BookingStatus` に `ROUTE_NOTIFIED` を足す

遷移は `PRELIMINARY → ROUTE_PROPOSED → ROUTE_NOTIFIED → CONFIRMED → TRACKING_ISSUED` とする。

足す理由は 2 つある。

第一に、**通知していない予約を確定できてはいけない**。確定は「荷主の合意を得た」という業務上の事実であり、提示していない条件で合意は成り立たない。状態で表せば集約がその不変条件を守れる。記録（`RouteNotification`）の有無で代用すると、守るのは呼び出し側の作法になる。

第二に、営業から見て「提示できる」と「提示して返事を待っている」は別の手番である。同じ状態で兼ねると、営業は自分が動く予約と荷主待ちの予約を一覧で区別できない。[ADR-020](020-itinerary-assignment-transitions.md) の決定 2 が `RoutingStatus` と `BookingStatus` を分けたのと同じ理由で、**関心が違うものを 1 つの値で兼ねない**。

> **記録と状態は二重管理ではない。** 状態を動かすのは `notifyShipper` だけであり、その同じ操作が記録（いつ・誰が）を置く。集約の不変条件として「`ROUTE_NOTIFIED` 以降なら通知の記録がある」を検査する。**復元では検査しない**（[ADR-012](012-value-object-granularity.md)。列が無かったころの行が読めなくなる）。

### 2. 再通知を許す（`ROUTE_NOTIFIED → ROUTE_NOTIFIED`）

返事が無い・連絡先を間違えた・内容を補足したい、はいずれも実務で起きる。塞ぐと営業は予約を経路設計へ戻して割り当て直すという遠回りをするか、システムの外で連絡して記録が残らなくなる。

**記録は最新の 1 件だけ持つ。**「何回・いつ送ったか」の履歴は列では表せず、別テーブルが要る。通知の実体（メール送信）が US19（通知基盤）で入るまで、履歴を持っても送った証拠にはならない。**履歴を持たないことをここに明記する**——書かないと「実装漏れ」と読まれる。

### 3. 確定したあとは戻せない

US13-4（荷主がルート変更を希望したら経路設計中に戻せる）の射程は**確定前**（`ROUTE_NOTIFIED` から）に限る。

確定は追跡番号の発行（US14）と荷役の起点であり、そこから先は貨物が動き始める。戻せるようにすると、追跡番号が発行された予約の経路が黙って変わり、荷役の担当者と荷主が別の予定を見る。確定後に変更が要るなら、それはキャンセル（US30）または経路の差し替え（[ADR-020](020-itinerary-assignment-transitions.md) 決定 4）である。

### 4. 「経路設計中に戻す」は `RoutingStatus` も戻す

`BookingStatus` を `ROUTE_PROPOSED` に戻すだけでは足りない。荷主が変更を希望したのだから、**経路設計者にもう一度作業してもらう**必要がある。`RoutingStatus` を `ROUTING_REQUESTED` に戻し、経路設計者の「作業待ち」に現れるようにする。

**旅程は消さない。** 見直しの起点になる（どこが気に入られなかったかを、いまの経路を見ながら話す）。[ADR-020](020-itinerary-assignment-transitions.md) 決定 4 の差し替えがそのまま使える。

用語は画面もマニュアルも「**経路設計へ戻す**」で統一する。US13-4 の「経路設計中」は `RoutingStatus.ROUTING_REQUESTED`（画面の言葉は「経路設計を依頼済み」）を指す。**「経路提案中」（`ROUTE_PROPOSED`）とは別の言葉である**。

### 5. `CANCELLED` は US30（IT9）まで足さない

輸送開始前のキャンセルは承認を経ない（US30 受入基準 1）ので、承認フローと不可分だから落とすのではない。落とす理由は、**`CANCELLED` 状態・キャンセル理由の記録・キャンセル料の算定を一度に設計するほうが 1 回で済む**ためである。ここだけ先に状態を足すと、US30 で申請・承認・陸揚げ地・料率を入れるときに作り直しになる。

US13-5・US13-6 は IT6 のスコープ外とし、完了報告書に明記する。

### 6. 状態ごとに誰の手番かを定める

| 状態 | 手番 | 次にすること |
| :--- | :--- | :--- |
| `PRELIMINARY` | 営業 | 経路設計を依頼する（US06） |
| `ROUTE_PROPOSED` | 営業 | 荷主へ通知する（US12） |
| `ROUTE_NOTIFIED` | 荷主 | 返事を待つ。確定するか、経路設計へ戻す（US13） |
| `CONFIRMED` | 経路設計者 | 追跡番号を発行する（US14） |
| `TRACKING_ISSUED` | 荷役 | 貨物を受け取る（US15・IT7） |

手番は**画面に出す**。出さないと、一覧に並んだ予約のどれが自分の仕事か分からず、状態を足した意味が無くなる。

### 7. 経路設計者の可視範囲は広げない（計画の注 13 は誤り）

可視の判定は `RoutingStatus#visibleToRoutingPlanner()` 1 か所にあり、`NOT_ROUTED` 以外を開く（[ADR-020](020-itinerary-assignment-transitions.md) 決定 3 の後日談で一本化した）。**確定は `BookingStatus` を動かすだけで `RoutingStatus` は `ROUTED` のまま**なので、確定した予約は経路設計者に見えたままである。US14 は 404 にならない。

したがって範囲を広げる変更はしない。ただし**狭まらないことを検査で固定する**——「確定した予約が経路設計者に見える」ことを直接のテストにする。判定が 1 か所にあることは、そこを触れば全部が変わることでもある。

## 代替案

- **通知を記録だけにして状態を足さない**: 状態が 1 つ減る。しかし「通知していない予約を確定できない」を集約が守れなくなり、守るのは呼び出し側の作法になる。作法は増えた入口の数だけ破られる
- **確定から戻せるようにする**: 営業の手戻りは楽になる。しかし追跡番号が発行された予約の経路が黙って変わり、荷役と荷主が別の予定を見る。戻す必要が出た場面は、実際にはキャンセルか差し替えである
- **`ROUTE_NOTIFIED` から `RoutingStatus` を動かさずに戻す**: 変更が小さい。しかし経路設計者の「作業待ち」に現れないため、荷主が変更を希望したことが誰にも伝わらない。US13-4 の目的（戻したことが経路設計者に見える）を満たさない
- **通知の履歴を最初から別テーブルで持つ**: 何回送ったかが残る。しかし送信の実体が無い段階では「記録上の再通知」でしかなく、証拠にならない。US19（通知基盤）と同時に入れるほうが、持つ項目が決まる

## 影響

### ポジティブ

- 荷主の合意を経ていない確定が、集約の段階で成り立たなくなる
- 営業の一覧で「自分が動く予約」と「荷主待ちの予約」が分かれる
- 荷主が変更を希望したことが、経路設計者の作業待ちに現れる

### ネガティブ

- **`BookingStatus` が 5 値になり、`Cargo` の遷移が増える。** 肥大化の判断はタスク 1.5 で明示的に行う
- **通知の履歴が残らない。** 何回送ったかは分からない。US19 まで最新の 1 件だけである
- **確定後に経路を戻せない。** 荷主の気が変わった場合、キャンセル（US30・IT9）まで受け皿が無い。IT6〜IT8 のあいだ、確定後の変更は運用で吸収することになる
- **「通知した」は画面上の記録であり、荷主には何も届かない。** US12 と同じく代替であることを画面・マニュアル・完了報告書に明記する

## コンプライアンス

**決定の数だけ検査を用意する。**

| 決定 | 検査 |
| :--- | :--- |
| 1. `ROUTE_NOTIFIED` を足す | `ROUTE_PROPOSED` 以外からは通知できないこと、**通知していない予約は確定できない**ことを集約の単体テストで固定する。`ROUTE_NOTIFIED` 以降なら通知の記録があることを不変条件として検査し、**復元では検査しない**ことも対で固定する |
| 2. 再通知を許す | `ROUTE_NOTIFIED` から通知できること、**記録が最新で上書きされる**ことを固定する |
| 3. 確定後は戻せない | `CONFIRMED` / `TRACKING_ISSUED` からの `returnToRouting` が断られることを固定する。「戻せる状態から戻せる」だけを確かめると、どこからでも戻せる実装でも緑になる |
| 4. `RoutingStatus` も戻す | 戻したあと `RoutingStatus` が `ROUTING_REQUESTED` になり、**経路設計者の作業待ちの一覧に現れる**ことを確かめる。旅程が残っていることも見る |
| 5. `CANCELLED` を足さない | `BookingStatus` に `CANCELLED` が無いことを検査する。**列挙の要素を数える検査**にする（「足さなかった」は書かないと守られない） |
| 6. 手番を画面に出す | 状態ごとの手番の文言が画面に出ることをコンポーネントテストで固定する |
| 7. 可視範囲を広げない | **確定した予約が経路設計者の一覧と詳細に出る**ことを固定する。判定が 1 か所なので、そこを触ると全部が変わる |

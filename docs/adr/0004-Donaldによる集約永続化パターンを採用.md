# ADR-0004: Donald による DDD 集約の永続化パターンを採用

集約ルートの永続化方式（データアクセスライブラリ・マッピング・楽観的ロック）の決定

日付: 2026-07-14

## ステータス

2026-07-14 提案

## コンテキスト

Cargo Tracker F# 版は、DDD の集約（`Shipper`・`Cargo`・`Voyage`・`TrackingActivity`・`Invoice` 等）を不変レコード + 判別共用体で表現し、値オブジェクトはスマートコンストラクタで不変条件を保証します（domain-model.md）。これらをリレーショナル DB（PostgreSQL 本番 / SQLite 開発）へ永続化するにあたり、以下の設計判断が必要です。

1. **データアクセス方式**: EF Core のような O/R マッパーを使うか、手書き SQL の薄いラッパを使うか。F# のレコード・判別共用体・Option 型は O/R マッパーの規約（可変プロパティ・ナビゲーションプロパティ・遅延読込）と相性が悪く、Make Illegal States Unrepresentable の設計を崩す。
2. **マッピング方式**: 自動マッピングに委ねるか、`IDataReader -> 'T` を手書きするか。判別共用体（`ShipperKind` / `CargoType` / `BookingState`）と DB 列（文字列判別子 + ケース固有列）の相互変換は自動化が難しい。
3. **同時更新制御**: 更新系ストーリー（US25 航海更新・状態遷移）で失われた更新を防ぐ仕組み。

## 決定

**Donald（F# 向け ADO.NET 薄ラッパ）による手書き SQL + 手書きマッピング + version 列による楽観的ロックを採用します。**

1. **Donald + 手書き SQL**: リポジトリ実装（各コンテキストの `Infrastructure` モジュール）に SQL を直接記述する。接続は `IDbConnection` 抽象で受け、Npgsql（PostgreSQL）/ Microsoft.Data.Sqlite（SQLite）を透過的に扱う（ADR-0003）。
2. **手書き `ofDataReader`**: 自動マッピングは使用せず、`IDataReader -> 'T` を手書きする。判別共用体 ⇔ 文字列の変換はドメイン型モジュールの `toString` / `ofString`（スマートコンストラクタ）で行い、検証済みであることを型で保証する。判別子 + ケース固有列（他ケースは NULL）への展開・復元もこの層で行う。
3. **楽観的ロック**: 集約テーブルに `version BIGINT NOT NULL DEFAULT 0` を持ち、UPDATE 時に `WHERE version = @expected` で照合し `version + 1` に更新する。影響行数 0 は `DomainError` 相当の競合として扱う。登録のみのストーリー（US02/03）では列を用意するのみで照合しない。
4. **サロゲートキー + 業務キー**: PK は `BIGSERIAL`（または `GENERATED BY DEFAULT AS IDENTITY`）、業務キー（`shipper_code` / `booking_id` 等）は UNIQUE 制約。`RETURNING` は PostgreSQL 方言のため使わず、呼び出し側は業務キーで再参照する（ADR-0003）。

根拠は以下のとおりです。

1. **型駆動設計の維持**: 手書きマッピングにより、DB の可変・NULL 許容の世界とドメインの不変・型安全な世界の境界を明示でき、スマートコンストラクタ経由での復元で不変条件を再保証できる。
2. **テスト容易性**: Port が関数レコードのため、リポジトリはスタブ（関数リテラル）で差し替え可能。実 SQL の検証は Testcontainers（実 PostgreSQL）で行う。
3. **方言差異の局所化**: SQL がリポジトリに集約されるため、ANSI 標準への準拠と方言検出テスト（ADR-0003）で二方言互換を担保できる。

## 代替案

- **EF Core**: 変更追跡・マイグレーション・LINQ が使えるが、F# の不変レコード・判別共用体・Option と規約が合わず、可変モデルへの妥協を強いる。CQRS の Read Model を DTO へ直接射影する用途でも手書き SQL の方が最適化しやすい。
- **Dapper**: C# 版で採用。F# でも動作するが、Donald の方が F# の関数的マッピング・`SqlType` DU・CE との親和性が高い。

## 影響

- 各コンテキストに `Infrastructure` モジュール（`ofDataReader` + CRUD 関数）を持つ。
- 楽観的ロックの競合は `DataError`／`DomainError` として上位ワークフローへ伝播し、UI で再試行を促す。
- `version` 列を全集約テーブルに付与する（data-model.md で定義済み）。

## コンプライアンス

- リポジトリの SQL は ANSI 標準に準拠し、PostgreSQL 固有機能（JSONB・配列・`RETURNING`・`ILIKE`・`ON CONFLICT`）を使わないこと（方言検出テスト・ADR-0003）。
- 集約の更新系操作は version 照合を伴うこと（コードレビューで確認）。
- ArchUnitNET で「ドメイン層が Donald を参照しない（Port 経由のみ）」ルールを CI で常時実行すること。

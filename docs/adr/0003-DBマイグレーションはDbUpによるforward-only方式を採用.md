# ADR-0003: DB マイグレーションは DbUp による forward-only 方式を採用

データベーススキーマ変更をバージョン付き SQL スクリプト + DbUp の前進専用（forward-only）方式で管理する決定

日付: 2026-07-06

## ステータス

2026-07-06 承認済み

## コンテキスト

Cargo Tracker は開発環境で SQLite、ステージング・本番・テスト（Testcontainers）で PostgreSQL 16 を使用する二方言運用です。スキーマ変更を安全かつ再現可能に適用する仕組みが必要であり、マイグレーションツールの選定と運用方式（ロールバックスクリプトの有無、方言差の扱い）を決める必要があります。DbUp は C# 製ライブラリですが .NET ライブラリとして F# からそのまま利用できます。

## 決定

**DbUp によるバージョン付き SQL スクリプトの forward-only マイグレーションを採用します。**

1. **バージョン付き SQL スクリプト**: マイグレーションは連番付きの生 SQL ファイル（`0001_initial_schema.sql` 等）として管理し、DbUp がアプリケーション起動時（または CI/CD の専用ステップ）に未適用スクリプトを順次実行します。適用履歴は journal テーブル（`schemaversions`）で管理し、適用済みスクリプトの編集は禁止します。
2. **forward-only（前進修正）**: ロールバックスクリプトは作成しません。誤ったスキーマ変更は、新しいスクリプトで元の状態に戻す roll-forward 方式で対応します。
3. **プロバイダ別ディレクトリ**: `Scripts/postgresql/` と `Scripts/sqlite/` を同一バージョン番号で並行管理し、方言差（`BIGSERIAL` と `INTEGER PRIMARY KEY AUTOINCREMENT` 等）を吸収します。SQL は ANSI 標準の範囲を基本とし、PostgreSQL 固有機能は使用しません。
4. **破壊的変更は Expand-Contract**: 列のリネーム・削除などの破壊的変更は、追加（Expand）→ 移行 → 削除（Contract）の段階適用パターンで、新旧スキーマが共存できる状態を保ちながら進めます。

根拠は以下のとおりです。

1. **Flyway と同思想の実績あるモデル**: バージョン付きスクリプト + journal テーブル + forward-only は Flyway で確立された運用モデルであり、Down スクリプトの保守コスト（実際にはほぼ検証されず信頼できない）を排除できます。
2. **二方言運用への適合**: 開発 SQLite / 本番 PostgreSQL 16 の差異は、ANSI 標準 SQL を基本としプロバイダ別ディレクトリで最小限の方言差分のみを管理することで吸収できます。本番とテスト（Testcontainers による PostgreSQL）は同一スクリプトを使用するため方言差異が発生しません。
3. **生 SQL による透明性**: スクリプトはそのままレビュー可能であり、ORM のマイグレーション DSL に依存しない移植性を持ちます。

## 影響

- マイグレーション適用は `DeployChanges.To.PostgresqlDatabase(...).WithTransactionPerScript()` の構成で 1 スクリプト = 1 トランザクションとします（`docs/design/data-model.md` 参照）。
- シードデータ（UN/LOCODE マスタ等）もデータ専用スクリプトとして同じ仕組みで管理します。
- CI/CD ではデプロイ前の専用ステップでマイグレーションを適用してからアプリケーションをデプロイします。
- 開発者は PostgreSQL 固有機能（`ENUM` 型、配列型等）を使用できず、ANSI 標準の範囲で設計する規律が求められます（例: 状態列は `VARCHAR` + CHECK 制約）。

## コンプライアンス

- コードレビューで「適用済みスクリプトが編集されていないこと」「プロバイダ別ディレクトリのバージョン番号が同期していること」「PostgreSQL 固有機能を使用していないこと」を確認すること。
- Testcontainers による PostgreSQL 統合テストで、マイグレーションスクリプトが CI で常時適用・検証されること。

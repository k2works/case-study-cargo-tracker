# ADR-023: 荷役作業の記録と妥当性検証

荷役作業員が受領・積込・荷降し・引取を記録する（US15・US16）ときに、何を必須とするか・予定と違う場所の作業をどう扱うか・通関ガードが無い状態でどう引取を通すか・どのイベントを発行するかを決める。

日付: 2026-08-23

## ステータス

承認済み

## コンテキスト

IT7 で **handlingms を初実装**し、貨物が実際に動き出す。IT6 までは追跡番号を発行しただけで、貨物はどこにも動いていなかった。

決めることが 6 つある。荷役の記録は**実際に起きた作業の記録**であり、あとから「無かったこと」にはできない。記録を拒む判断も、記録を残す判断も、現場の作業を止めるか誤った記録を残すかのどちらかに直結する。

- 荷役の種別ごとに何を必須とするか
- 予定ルートと違う場所の作業を、拒むのか記録するのか
- 引取の通関ガードを、`CustomsDeclaration`（US29・IT9）が無い IT7 でどう扱うか
- どのイベントを発行し、どのイベントを発行しないか
- 誰が購読するか
- 貨物の情報をどう取るか

加えて、**設計に足りていないものが 3 つある**（[イテレーション 7 計画](../development/iteration_plan-7.md) の注）。追跡番号から貨物を引く経路が無い、予定外だったことを記録に残す場所が無い、Handling Context の追跡番号型が型の表に無い。この ADR と同じ変更で設計へ反映する。

## 決定

### 1. 種別ごとの要件は、種別そのものに持たせる

| 荷役の種別 | 航海番号 | 荷受人の確認 | 照合する港 |
| :--- | :--- | :--- | :--- |
| RECEIVE（受領） | 不要 | 不要 | 出発港 |
| LOAD（積込） | **必須** | 不要 | 旅程の積込港 |
| UNLOAD（荷降し） | **必須** | 不要 | 旅程の荷降港 |
| CLAIM（引取） | 不要 | **必須**（決定 5） | 目的港 |

積込・荷降しに航海番号が要るのは、**どの船に載せたかが分からないと貨物を追えない**ためである。受領と引取は船が関わらない。

要件を種別に持たせるのは、呼び出し側に `if (type == LOAD)` を書かせないためである。書かせると、種別が増えたときに書き換える場所が散らばり、書き換え忘れた場所だけが黙って通す。

### 2. 貨物の情報は ACL 経由で取り、Booking の型は持ち込まない

`CargoSnapshot` として、bookingms の REST から取る（[ADR-019](019-route-assignment-api.md) と同じ形）。相手の型をこちらのクラスパスに置かない。

**追跡番号で引く。** US15-1 は追跡番号を作業の起点にしており、荷役作業員は予約番号を知らない。bookingms 側に追跡番号での照会を足す。

> **設計への反映**: `domain-model.md` の `CargoSnapshot` は `bookingId` から始まっており、追跡番号から引く経路が無い。同じ変更で反映する。

### 3. 予定と違う場所の作業は、**拒まずに記録し、予定外だったことを残す**

現場ではすでに作業が終わっている。拒むと、**実際に起きたことがどこにも残らない**。作業員はシステムの外で連絡するか、嘘の場所を入れて通すことになる。どちらも記録としては後者のほうが悪い。

したがって**警告を出したうえで記録する**。あわせて `offRoute`（予定外だったか）を**行に残す**。

> **設計への反映**: `domain-model.md` の `isValidFor(): boolean` は真偽を返すだけで、判断が記録に残らない。US28（IT10）で誤配を扱うとき、過去の作業を判定し直すことになる。`data-model.md` の `handling_activity` にも `off_route` 列を足す。

**`RoutingStatus` を `MISROUTED` へ動かすのは US28（IT10）である。** IT7 は記録に残すところまでで、経路の状態は動かさない。**動かさないことをここに書く**——書かないと実装漏れと読まれる。

### 4. 引取は、通関ガードの代わりに**荷役作業員の明示的な確認**を必須とする

[ドメインモデル](../design/domain-model.md)の Handling Context ビジネスルール 2 は「`CustomsDeclaration` が CLEARED になるまで CLAIM できない」と定めているが、`CustomsDeclaration` は US29（IT9）であり **IT7 には無い**。

ガードが無いまま引取を通すと、「通関前の貨物を引き渡した」記録が残る。**空欄のまま通せる形にはしない。**

そこで IT7 は、`ConsigneeConfirmation`（荷受人の確認を誰から得たか）を必須とする。**空なら断る。** 確認は業務上の事実であり、荷役作業員が「確かに荷受人へ引き渡した」と記録することになる。

**これは代替である。** IT9 で `CustomsDeclaration` による本物のガードに置き換える。代替であることを画面・マニュアル・完了報告書に明記する——書かないと、IT9 で二重にガードを掛けるか、代替のほうを消し忘れる。

### 5. 発行するのは `HandlingActivityRegisteredEvent` の 1 種類だけ

[ADR-022](022-domain-event-contract.md) の型をそのまま写す。**新しい結合方式を発明しない。**

ペイロードは「受け手が自分の集約を進めるのに要るもの」に絞る——`bookingId` / `trackingNumber` / `type` / `locationUnLocode` / `completionTime` / `voyageNumber` / `offRoute` / `occurredAt`。

> **`CargoDeliveredEvent`（billingms へ）は IT7 では発行しない。** US16-4 は「引取済は精算の開始条件」と書いているが、精算は US23（IT12）である。**発行しないことをここに明記する**——書かないと実装漏れと読まれる（[ADR-022](022-domain-event-contract.md) 決定 1 の `CargoRoutedEvent` と同じ形）。

### 6. IT7 で購読するのは trackingms だけ

[ドメインモデル](../design/domain-model.md)のイベント一覧は処理先を「trackingms・bookingms」と書いているが、bookingms 側の処理は**誤配で `RoutingStatus` を動かす**こと（US28・IT10）であり、決定 3 で IT7 の範囲外にした。

交換機は将来 2 者が読める形（トピック交換機 + 購読側ごとのキュー）にしておく。IT6 で作った形をそのまま使う。

> **設計への反映**: イベント一覧の処理先に「trackingms（IT7）・bookingms（US28・IT10）」と時期を書き添える。

## 代替案

**予定外の作業を拒む。** 記録の正しさは保てるが、現場の作業はすでに終わっている。拒めば実際に起きたことが残らず、嘘の場所で通す動機を作る。記録を残すシステムとして本末転倒である。

**引取に何のガードも掛けない（IT9 まで素通りさせる）。** 実装は最小になるが、「通関前の貨物を引き渡した」記録が残る。しかも IT9 でガードを足すとき、**素通りで作られた過去の記録**をどう扱うかという問題が新しく生まれる。

**`CustomsDeclaration` を IT7 で前倒しする。** 本物のガードになるが、US29 は通関申告の登録・状態更新・監査履歴・督促まで含む。IT7 の 10 SP に収まらず、荷役の記録そのものが薄くなる。

**照合する港の判定を画面にも書く。** 入力中に警告を出せるが、判定が 2 か所になる。画面の判定だけが古い規則のまま残る形は IT6 で 5 件出た。判定はサーバに置き、画面は結果を出す。

## 影響

- handlingms が初めて業務を持つ。ヘキサゴナルの層・Flyway・MyBatis の配線を trackingms の形で写す
- サービス間の非同期連携が 2 本目になる。[ADR-022](022-domain-event-contract.md) の型を写すだけで済むかが、この IT の見積もりの前提である
- bookingms に追跡番号での照会が増える。**システム主体として名乗る**（[ADR-019](019-route-assignment-api.md) 後日談 3）
- `handling_activity` に `off_route` が入る。US28（IT10）はこの列を入力に使う
- 引取の確認は IT9 で置き換える。置き換えるときに**この決定を消す**

## コンプライアンス

**決定の数だけ検査を用意する。**

| 決定 | 検査 |
| :--- | :--- |
| 1. 種別ごとの要件 | デシジョンテーブルの 4 行すべてにテストを置く。**種別を 1 つ足したら赤になる**こと（種別から要件を導いているか、呼び出し側に分岐が残っていないかを、名簿ではなく列挙の網羅で見る） |
| 2. ACL 経由で取る | 追跡番号で貨物を引く契約テスト（コンシューマ + プロバイダ）。**名簿は DTO の要素から導く**。あわせて handlingms のクラスに Booking の型が現れないことを ArchUnit で見る（`serviceIsolationRule`） |
| 3. 予定外は記録する | 予定ルート外の港で記録したとき、**警告が出て、かつ `offRoute` が真で保存される**ことを固定する。警告を消す実装に変えると赤になること。**`RoutingStatus` を動かしていない**ことも対で確かめる |
| 4. 引取の確認 | 確認が空の CLAIM を断ることを、集約・API・画面の 3 層で固定する。**断りを外すと赤になる**こと |
| 5. 発行するイベント | 荷役を記録したときにだけ発行されることを固定する。**`CargoDeliveredEvent` が発行されていない**ことも対で確かめる（発行しないという決定も検査に落とす。[ADR-018](018-route-search-rules.md) 決定 3 と同じ許可リスト方式） |
| 6. 購読は trackingms だけ | 実 RabbitMQ で 1 往復させ、追跡の状態が進むことを確かめる。デッドレターへの到達も対で見る。**bookingms が購読していない**ことを、購読の宣言が無いことで確かめる |

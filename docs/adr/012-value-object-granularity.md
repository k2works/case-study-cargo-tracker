# ADR-012: 値オブジェクトは不変条件を持つ属性にだけ導入し、荷主は単一クラスのままとする

属性に検査すべき規則がある場合にのみ値オブジェクトを定義する。規則が「空でない」だけの属性は `String` のまま持つ。`Shipper` は法人・個人でサブタイプに分けず、単一クラスとして種別を属性で持つ。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

IT1 の `Shipper` は `name` / `email` / `address` / `phone` を `String` で持ち、検査は `register` の中に書いている。一方 `domain-model.md` は、これらを値オブジェクトとして描いている。設計と実装が割れた状態である。

IT2 で `ContractNumber` / `DiscountRate` / `BookingId` / `RouteSpecification` / `Dimensions` などを追加すると、**1 つの集約に値オブジェクトと素の `String` が混在する**。混在そのものは悪ではないが、混在の**理由が説明できない**状態は悪い。次に属性を足す人が、どちらにすべきか判断できない。

同時に `Shipper` の形も決める必要がある。法人だけが契約番号・割引率を持つため、`CorporateShipper` サブタイプにする案がある。

## 決定

1. **値オブジェクトを定義する基準を「不変条件を持つか」に置く。**
   - 定義する: 形式・範囲・複数属性間の関係など、**破りうる規則**がある（`DiscountRate` は 0〜30%、`RouteSpecification` は出発地 ≠ 目的地、`TemperatureRequirement` は下限 ≦ 上限）
   - 定義しない: 規則が「空でない」だけ（`name`、`address`、`phone`）。ラッパーを作っても守るものが増えず、変換のコードだけが増える
   - `email` は形式検査があるため本来は値オブジェクトだが、IT1 で `String` として永続化済みである。**IT2 では変えない**（変更は US03 の受入基準と無関係であり、移行のリスクだけが増える）。IT3 以降、荷主を編集するストーリーに着手するときに合わせて導入する
2. **`domain-model.md` を本 ADR の基準に合わせて修正する。** 設計に「すべて値オブジェクト」と描いたまま実装が違う状態を残さない
3. **`Shipper` は単一クラスのままとする。** 種別は `ShipperType` の属性で持ち、法人固有の契約情報は `Optional` 相当（null 許容）で持つ。理由は 2 つ
   - **種別は変わりうる**。個人事業主が法人成りする。サブタイプにすると、種別の変更が「別のオブジェクトへの作り替え」になり、識別子を引き継ぐ処理が要る
   - **多態が要る箇所が無い**。IT2 で法人・個人の振る舞いが分かれるのは検査（法人以外は契約情報を持てない）だけであり、これは集約の不変条件として書ける
4. **法人の契約番号は必須、割引率は任意とする。** 契約番号が無い法人を許すと、US22（法人割引）で全件の追加入力が発生する。割引率は交渉の結果であり、登録時点で決まっていないことがある。未設定は 0% ではなく「未設定」として扱う（0% にすると、設定漏れが「割引なしの契約」として通る）

### 代替案

- **すべての属性を値オブジェクトにする**: 一貫はするが、`Name` / `Address` / `Phone` は「空でない」以外に守るものが無い。型の数が増えるぶん、読む量が増える
- **`CorporateShipper` サブタイプにする**: 法人固有の属性が null にならない利点はあるが、種別変更と永続化（単一テーブル継承の判別列）のコストが上回る
- **契約番号も任意にする**: 契約番号の無い法人が溜まる。US22 で全件を追いかけることになる

## 影響

### ポジティブ

- 属性を足すときの判断基準が言語化され、混在の理由が説明できる
- 種別の変更が、識別子を保ったまま行える

### ネガティブ

- `email` が値オブジェクトになるのが IT3 以降にずれる。設計と実装の差が一時的に残る（本 ADR で明記して追跡する）
- 法人固有の属性が null を取りうるため、参照側で存在確認が要る

## コンプライアンス

- `Shipper` に「個人なのに契約情報を持つ」状態を作れないことをテストで固定する
- 「法人なのに契約番号が無い」状態を新規登録で作れないことをテストで固定する。ただし**復元では検査しない**（列が無かったころの行が読めなくなる）
- `domain-model.md` の `Shipper` / 値オブジェクト一覧が本 ADR と一致していることを、IT2 のレビューで確認する

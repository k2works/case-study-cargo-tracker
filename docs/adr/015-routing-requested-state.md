# ADR-015: 経路設計の依頼を `RoutingStatus` の状態として持ち、経路設計者に見せる範囲をそれで絞る

`RoutingStatus` に `ROUTING_REQUESTED` を追加する。営業担当者が予約を経路設計者へ引き渡した事実を、この状態で表す。経路設計者に開く予約一覧は、この状態のものに限る。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

US06（予約情報を経路設計者に引き渡す）の受け入れ基準は「経路設計依頼の通知が送信される」を含むが、**メール送信の仕組みはこのシステムに存在しない**（[リリース計画の技術リスク](../development/release_plan.md)）。通知が作れない以上、経路設計者が「自分に仕事が来た」ことに気づく別の手段が要る。

気づく手段として最小なのは、経路設計者のダッシュボードに「経路設計待ち N 件」を出すことである。ただし**件数を出すだけでは仕事は進まない**。そこから対象の予約へ行けなければ、経路設計者は一覧を自分で探すことになる（IT2 のレビューで同型の指摘があった）。

つまり必要なのは「依頼された予約だけを取り出せること」であり、そのためには依頼という事実がデータとして残っていなければならない。

現状の `RoutingStatus` は `NOT_ROUTED` だけを持つ（[ADR-009](009-cargo-status-columns-from-the-start.md) で「まだ動いていない」を意味のある状態として最初から NOT NULL にした）。「まだ経路が付いていない」と「経路設計を依頼した」は、経路設計者から見れば別の状態である。

## 決定

1. **`RoutingStatus` に `ROUTING_REQUESTED` を追加する。** あわせて、後続で使う `ROUTED` も定義する（US09 で経路を紐付けるときに使う）
2. **依頼は予約の状態（`BookingStatus`）を変えない。** 予約の確定は工程 6 の別の作業であり、引き渡しと混ぜない
3. **依頼できるのは仮受付の予約だけで、二重の依頼はできない。** 二重に通すと待ち行列に同じ予約が並び、経路設計者からは「同じ仕事が 2 件ある」ように見える
4. **依頼できるのは営業担当者だけとする。** 経路設計者が自分で依頼を立てられると、引き渡しの記録が「誰が渡したか」を表さなくなる
5. **経路設計者に開く予約は `ROUTING_REQUESTED` のものに限る（一覧・詳細の両方。IT4 で射程を明記）。** 経路設計者の仕事は「依頼された予約に経路を組む」ことであり、まだ引き渡されていない予約（営業が作業中のもの）は対象ではない。[ADR-008](008-no-user-shipper-link-in-it2.md) が「必要な範囲だけ開く」と決めた形をここでも守る。絞り込みの指定でこの範囲を広げることはできない。**入口ごとに判断を書かず、集約の述語（`Cargo#visibleToRoutingPlanner`）を各入口が呼ぶ。** IT3 では決定の文言が一覧しか指しておらず、詳細が絞られていなかった。一覧を絞っても、予約番号を順に試せば詳細から同じ範囲が読める。**入口を 1 つ塞いでも、同じ範囲を返すもう 1 つの入口が開いていれば、絞りは無いのと同じである**

### 代替案

- **別テーブル（`routing_request`）に依頼を記録する**: 申請・承認・却下のように**履歴が要る**なら妥当だが（[キャンセル申請](../design/data-model.md)がそう）、引き渡しに却下は無く、再依頼もできない。1 つの状態で足りる
- **`BookingStatus` に「経路設計中」を足す**: 予約のライフサイクル（仮受付 → 確定 → 追跡番号発行 …）に、経路設計側の進み方を混ぜることになる。同じ予約に対して 2 つの進み方があり、片方の遷移がもう片方を巻き込む
- **通知が作れるまで US06 を延期する**: 経路設計者が引き渡しに気づけない状態のまま IT4（経路候補算出）へ進むと、経路設計の入口が無いまま出口だけ作ることになる
- **経路設計者に予約一覧を全件開く**: 実装は簡単だが、経路設計者が見る必要のない予約（営業が作業中のもの）まで開く

## 影響

### ポジティブ

- 経路設計者が「自分に来た仕事」を一覧で取り出せる。ダッシュボードの件数から、その対象へそのまま行ける
- 依頼という業務上の出来事が、データとして残る（誰が渡したかまでは IT3 では持たない。下記）

### ネガティブ

- **通知の代わりであり、通知ではない。** 経路設計者が画面を開かない限り気づけない。メール送信の仕組みが入ったら、この状態を入力として通知を出す
- **「誰がいつ依頼したか」は残らない。** 状態だけを持つため、引き渡しの監査には足りない。必要になったら別テーブルに切り出す（そのときは本 ADR の代替案 1 を採る）
- `BookingStatus` が IT3 時点で `PRELIMINARY` だけであるため、決定 3 の「仮受付の予約だけ」という検査は**まだ働く場面が無く、破って赤にするテストも書けない**。US11（予約確定）・UC22（キャンセル）で状態が増えたときに、確定済み・キャンセル済みを弾くテストと対にする

## コンプライアンス

- 二重の依頼が拒否されることを集約の単体テストで固定し、検査を外すと赤になることを確認する
- 経路設計者の一覧が `ROUTING_REQUESTED` に絞られることを API のテストで固定し、絞りを外すと赤になることを確認する
- **経路設計者が、引き渡されていない予約の詳細を開けない**ことを API のテストで固定する（IT4 で追加）
- 依頼できない状態への依頼が 409（入力の誤りである 400 ではない）で返ることを確認する

# ADR-008: データストアの構成とスキーマ規約

PostgreSQL に Unit ごとのスキーマ + 共有の reference・platform を置き、列挙値は text + CHECK、実行できる操作を読み取りモデルの列に持つ。

## コンテキスト

- 読み取りモデルは Unit ごとに独立させたい（Unit の独立）。港湾などの参照データ（UN/LOCODE。R-09）は Unit 間で共有する。
- スキーマ変更・マイグレーションは確認必須で、適用前に人が差分を確認する（R-03）。
- 画面は「その状態で開ける操作」を集約の述語どおりに出す必要がある（フロントエンド 5.2）。

## 決定

**PostgreSQL に Unit ごとのスキーマ（`booking`・`routing`・`tracking`・`billing`・`identity`）+ 共有の `reference`（読み取り専用の参照データ）+ `platform`（冪等性キー・待避イベント）**を置く。**スキーマをまたぐ外部キー・結合は置かない**（`reference` への参照を除く）。**列挙値は `text` + `CHECK`**、**実行できる操作（`available_commands`）は読み取りモデルの列に持つ**。履歴の行はイベント ID を主キーにする。DAO は手書きの Slick 定義を基本とし、生成の採否は PoC で決める。PostgreSQL は 18（RDS が未提供なら 17）。

### 変更箇所

- `reference` の初期データは実在する UN/LOCODE の部分集合（取扱い貨物種別は架空の設定であることを明記）。
- マイグレーションは Flyway で数値順に適用し、適用済みのファイルを書き換えない。
- 公開照会は専用ビュー（`tracking.public_tracking_v`）だけを読む。

### 代替案

- **1 スキーマ／`reference` を Unit ごとに複製**：Unit 間の独立は強いが、参照データの重複と不整合が生じる
- **PostgreSQL の `ENUM`**：値の追加・削除のマイグレーションが重い
- **操作の可否を画面または API が状態から導く**：状態の再判定が画面に漏れ、集約の述語とずれる

## 影響

### ポジティブ

- Unit の独立とデータの共有を両立できる。
- 操作の出し分けが集約の述語と一致する。

### ネガティブ

- 読み取りモデルの列が増える（非正規化。DB-05）。
- マイグレーションの適用に人の承認が要り、スキーマ変更の速度が落ちる。

## コンプライアンス

- DB 統合テストは PostgreSQL の実物（Testcontainers）で行う（ADR-011）。

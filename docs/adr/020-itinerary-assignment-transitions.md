# ADR-020: 経路の割り当てで動く状態と、割り当てを許す条件

経路候補を予約に割り当てる（US09）ときに、予約のどの状態が動くか・どこからなら割り当てられるか・割り当てたあと誰が見られるか・差し替えを許すかを決める。

日付: 2026-08-21

## ステータス

承認済み

## コンテキスト

IT4 で経路候補を算出できるようになったが、**選んだ候補を予約に紐付ける先が無い**。US09（経路の選択・確定）と US11（予約への反映）で、経路設計者が選んだ旅程を予約に割り当てる。

このとき決めることが 5 つある。いずれも「実装してから考える」と、あとで直すのに永続化された行の移行が要る種類の判断である。

- `RoutingStatus` と `BookingStatus` のどちらが、どう動くか
- どの状態からなら割り当てられるか
- 割り当てたあと、その予約を経路設計者が引き続き見られるか
- 経路の差し替えを許すか
- 見えない予約と存在しない予約を、応答で区別するか

3 つ目は放っておくと事故になる。[ADR-015](015-routing-requested-state.md) の決定 5 が「経路設計者に開くのは `ROUTING_REQUESTED` のものに限る」と決めているため、**割り当てた瞬間に自分が開けなくなる**。確定画面に進む前に一覧へ弾き返される。

## 決定

1. **引き渡された予約にだけ割り当てられる**（`ROUTING_REQUESTED`。決定 4 により `ROUTED` からの差し替えも許す）。 `NOT_ROUTED`（まだ営業が引き渡していない）への割り当ては、営業が作業中の予約に経路設計者が手を出すことになる。引き渡しという業務上の受け渡しを飛ばせてしまうと、`RoutingStatus` が「誰の手番か」を表さなくなる
2. **割り当てで `RoutingStatus` は `ROUTED` に、`BookingStatus` は `ROUTE_PROPOSED` に動く。** 2 つ動かすのは、経路設計側の進み方（経路が決まった）と予約のライフサイクル（荷主に提示できる状態になった）が別の関心だからである。`CONFIRMED` にはしない。**確定は荷主の合意を経た別の作業**（US13・IT6）であり、経路が決まっただけで予約を確定にすると、荷主が見ていない条件で契約が成立したことになる

   > 設計のシーケンス図が `CONFIRMED` と書いているのは誤りで、UC09 が正である（IT5 開始準備の設計反映 #4）。

3. **`ROUTED` の予約も経路設計者に開く**（決定 7 の `CONSULTATION_REQUESTED` も同じ）（[ADR-015](015-routing-requested-state.md) 決定 5 の射程を広げる）。割り当てた直後に自分が開けなくなると、確定画面にも旅程にも辿り着けない。判定は集約の述語 `Cargo#visibleToRoutingPlanner` 1 箇所で行い、入口はこれを呼ぶ
4. **経路の差し替えは許す。ただし `ROUTED` からの再割り当てに限る。** 航海の遅延・欠航は実際に起こり、そのたびに予約を取り直すのは業務が成り立たない。**新しい旅程も決定 5（要件を満たすこと）の検査を通る**。差し替えても `BookingStatus` は `ROUTE_PROPOSED` のまま動かさない（提示できる状態であることは変わらない）。

   > **`CONFIRMED` 以降の差し替えは本 ADR では決めない。** 確定後の変更は荷主の再合意が要る可能性があり、US13 で予約確定を作るときに決める。いま決めると、確定の意味が決まる前に例外を作ることになる。

5. **旅程が予約の要件（`RouteSpecification`）を満たさなければ、割り当てを断る。** 端点が違う旅程を割り当てると、荷主は貨物を渡せない場所で待つ。期限を過ぎる旅程を割り当てると、約束を破ることが確定した状態で予約が進む。判定は `RouteSpecification#isSatisfiedBy(itinerary, destinationZone)` に置き、**画面と集約で別々に書かない**
6. **見えない予約と存在しない予約は、応答で区別しない**（404・同じ本文）。403 と 404 を打ち分けると、予約番号を順に試すだけでどの番号が実在するかが分かる。内容は隠れても、営業がいま何件抱えているかは漏れる。番号は連番であり総当たりは容易である（[IT4 の残作業 11](../development/iteration_report-4.md#課題と残作業)。本 ADR と同じ IT で実装済み）

7. **条件では経路が組めないとき、`RoutingStatus.CONSULTATION_REQUESTED` として営業へ差し戻す**（US10）。通知の仕組みが無いため、[ADR-015](015-routing-requested-state.md) が US06 で採ったのと**同じ形**（状態を持たせて一覧で気づかせる）で代替する。「見つかりませんでした」で終わらせると、経路設計者の画面の中で行き止まりになり、荷主との条件交渉が始まらない。

   差し戻せるのは `ROUTING_REQUESTED` のときだけである。経路が決まった予約に協議を頼むのは、差し替えるべき場面である（決定 4）。**差し戻した予約も経路設計者に開いたままにする**（決定 3 と同じ理由。差し戻した本人が営業と話したあとに続きができなくなる）。

   差し戻した予約は、荷主と条件が決まれば**営業がもう一度引き渡せる**（`requestRouting`）。ここを塞ぐと、差し戻した予約が誰の手番でもなくなる。

   > **差し戻しの理由は残らない。** 状態だけを持つため、「何が厳しかったか」は画面の条件から読むしかない。理由を残すには列が要る。必要になったら決定 4 の履歴と合わせて別テーブルに切り出す。

### 代替案

- **`BookingStatus` を動かさない**: 経路が決まったことは `RoutingStatus` だけで表せる。しかし営業から見ると「荷主に提示できる状態になったか」が読めず、`RoutingStatus` を営業が解釈することになる。関心が違うものを 1 つの状態で兼ねると、片方の都合で遷移を足したときにもう片方が壊れる
- **`NOT_ROUTED` からも割り当てられるようにする**: 経路設計者が自己判断で先回りできるが、引き渡しの記録が意味を失う。[ADR-015](015-routing-requested-state.md) 決定 4（依頼できるのは営業だけ）と同じ理由で採らない
- **差し替えを禁止する**: 実装は単純だが、遅延・欠航のたびに予約を取り直すことになる。予約番号が変わると、荷主・荷役・請求の側から見て別の貨物になる
- **`ROUTED` を経路設計者に開かない**: ADR-015 の文言をそのまま守る形だが、割り当てた本人が結果を確認できない。「絞る」と「見えなくする」は違う

## 影響

### ポジティブ

- 経路設計者の導線が閉じる。依頼された予約 → 候補 → 選択 → 確定 → 旅程の確認まで、同じ人が辿れる
- 要件を満たさない旅程が予約に入らないことが、集約の不変条件として保証される
- 予約番号の総当たりで、営業が抱える予約の件数が漏れなくなる

### ネガティブ

- **`ROUTED` を開くことで、経路設計者が見られる範囲は広がる。** 引き渡された予約であることは変わらないため、[ADR-008](008-no-user-shipper-link-in-it2.md) の「必要な範囲だけ開く」は守れているが、範囲が単調に増える方向であることは記録しておく
- **差し替えの履歴は残らない。** 「いつ・なぜ差し替えたか」は状態からは読めない。監査が要るようになったら別テーブルに切り出す（[ADR-015](015-routing-requested-state.md) の代替案 1 と同じ形）
- `BookingStatus` に `ROUTE_PROPOSED` が増えるため、**`PRELIMINARY` だけを前提にした検査が壊れる**。`requestRouting` の「仮受付の予約だけが依頼できる」は、これで初めて働く場面ができる（ADR-015 のネガティブに書いた「まだ働く場面が無い」が解消する）

## コンプライアンス

**決定の数だけ検査を用意する。** 文章だけの決定は守られない（[IT4 のふりかえり](../development/retrospective-4.md)）。

| 決定 | 検査 |
| :--- | :--- |
| 1. `ROUTING_REQUESTED` からのみ | **`NOT_ROUTED` からの**割り当てが拒否されることを集約の単体テストで固定し、検査を外すと赤になることを確認する（`ROUTED` からは決定 4 により許す） |
| 2. 2 つの状態が動く | 割り当て後に `RoutingStatus.ROUTED` かつ `BookingStatus.ROUTE_PROPOSED` になることを固定する。**`CONFIRMED` にしないこと**も明示的に確かめる |
| 3. `ROUTED` も開く | `visibleToRoutingPlanner` が `ROUTED` で真になることを固定し、API の詳細取得でも 200 が返ることを確かめる |
| 4. 差し替えを許す | `ROUTED` からの再割り当てが通ること、そのとき `BookingStatus` が動かないことを固定する |
| 5. 要件を満たさない旅程を断る | 端点違い・期限超過の旅程で割り当てが拒否されることを固定し、**壊して赤を確認する** |
| 6. 403 と 404 を揃える | 見えない予約と存在しない予約の応答が、状態も本文も区別できないことを API のテストで固定する（実装済み） |
| 7. 営業へ差し戻す | `ROUTING_REQUESTED` 以外から差し戻せないことを集約の単体テストで固定する。**差し戻した予約が経路設計者に見えたままである**ことも確かめる（決定 3 と同じ理由で外れやすい） |

## 後日談（IT5 のクローズ）

マルチパースペクティブレビューで、**決定 3 と決定 7 が詳細画面でだけ守られ、一覧では別の判定が書かれていた**ことが分かった。一覧は `ROUTING_REQUESTED` に固定されており、割り当てた予約も差し戻した予約も一覧から消えていた。

判定は `RoutingStatus#visibleToRoutingPlanner` に 1 つだけ置き、一覧の範囲は `RoutingStatus#openToRoutingPlanner()` から導く形に直した。**同じ規則を守る箇所が 2 つあると、互いを隠して両方とも無検査になる**（IT4 のふりかえりと同じ型の再発）。

また、**routingms が「遅い」だけの状態**（応答しない）を決定 2 の再検証が「候補に無い」と扱い、409「航海スケジュールが変わっている可能性があります」と誤診していた。相手の不調は 503 に分け、確認できなかったことと不成立だったことを区別する。

# ADR-0013: 品質ゲートの正典はテスト戦略とし、イテレーション計画は引用する

クローズ条件としての品質ゲートは
[テスト戦略](../design/test_strategy.md) 6.4 が定める 5 つの検査であり、
**イテレーション計画の DoD はそれを引用するだけとする**。

SonarQube は **IT5 で既に品質ゲートから外れていた**。
IT8・IT9・IT10 の DoD がその決定を反映しないまま
「SonarQube Quality Gate が PASS」を条件として持ち続け、
3 イテレーション連続で「未達」と記録していた。

日付: 2026-08-05

## ステータス

2026-08-05 承認されました（IT10 のクローズ時）

## コンテキスト

### 3 イテレーション連続で「未達」と記録していた

IT8・IT9・IT10 の完了報告書は、いずれも品質ゲートの表に
「SonarQube Quality Gate ❌ 未達」を記録している。
IT9 のふりかえりは Problem P4 として挙げ、IT10 の計画は Try T4 として
「実行方法を着手前に決める」を立てた。

IT10 のクローズでその実行方法を確定させようとして、**前提が誤っていたことが判明した**。

### IT5 で既に外していた

[テスト戦略](../design/test_strategy.md) 6.4 は次のように書いている。

> **IT5 での決着（ふりかえり Try T9）**: SonarQube を**品質ゲートから外し、
> ESLint に置き換えた**。
>
> 理由は検査内容ではなく**実行されるかどうか**である。SonarQube はローカルサーバの起動と
> トークン（`.env` の `SONAR_TOKEN`）を要するため、**IT3・IT4 と 2 イテレーション連続で
> 実行されなかった**。通していない条件を「品質ゲート」と呼び続けると、定義が形骸化する。
> IT5 で 3 回目の未実施にする前に決める、というのが Try T9 だった。

**IT5 が 3 回目の未実施を避けるために下した決定を、IT8-IT10 が知らずに 3 回繰り返した。**

理由は明白で、**イテレーション計画の DoD がテスト戦略を参照せず、独自に条件を列挙していた**。
IT5 で正典が変わっても、DoD は書き写された古い条件を持ち続けた。

### SonarQube は Flix を解析できない

そもそも SonarQube のサポート言語に Flix は無い。
アプリケーション本体の 100% は Flix であり、
**SonarQube が見られるのは Node.js の運用スクリプトだけ**である。

「本体の品質が測れていない」という懸念は正しいが、
それは SonarQube を実行しても解消しない。

## 決定

### 1. 品質ゲートの正典は `test_strategy.md` 6.4 とする

クローズ条件は次の 5 つである。**すべて CI で走る**。

| 検査 | 対象 | CI ステップ |
| :--- | :--- | :--- |
| 全テスト緑 | Flix 本体（単体・統合・HTTP） | `Test` |
| `arch-lint` | アーキテクチャ規約（11 件 + メタテスト） | `Architecture lint` |
| `trace-lint` | ビジネスルール ⇄ テストの対応 | `Traceability lint` |
| `script:lint`（ESLint） | 運用スクリプト（検査器を含む） | `Script lint` |
| `test:dbnames` | テスト用 DB 名の重複 | `Test database name lint` |

**「実行されること」を条件の一部とする**。サーバの起動や対話的な認証を要する検査は、
どれほど内容が優れていても品質ゲートに置かない——通していない条件は形骸化する。

### 2. イテレーション計画の DoD は正典を引用する

DoD に個別の検査名を書き写さない。次の 1 行にする。

```markdown
- [ ] 品質ゲートを通過（`test_strategy.md` 6.4 の 5 検査。CI で確認）
```

**書き写した条件は正典が変わっても追随しない**——本 ADR が扱っている問題そのものである。

### 3. SonarQube の道具立ては残す

`sonar-project.properties` と `npx gulp sonar-local:*` は消さない。
手元で深い分析をしたいときに使える手段を消す理由はない。
**ただし品質ゲートの条件ではない**（IT5 の決定を維持する）。

## 引き受けるリスク

### Flix 本体に外部の静的解析が当たらない

`arch-lint` は自作であり、**検査器自身のバグは検査されない**
（ESLint が `arch-lint` のコードを見るのが唯一の外部統制である）。
IT2 で実際に「検査をパスしているのに違反している」状態が発生した。

**緩和**: `arch-lint` にメタテスト（32 件）を置き、
フィクスチャは実コードの形で書く（IT9 レビュー M2 の返済）。
それでも「メタテストが緑でも実コードの違反を見逃す」ことは IT2 で起きている。

**見直す条件**: Flix を解析できる静的解析器が現れたとき。

### カバレッジを測っていない

テスト戦略は「カバレッジ計測が壊れているのと同義として扱う」として
`trace-lint`（ビジネスルール ⇄ テストの対応）を代わりに置いている。
これは**網羅の物差しであって、コードの実行率ではない**。

**見直す条件**: Flix にカバレッジ計測の手段ができたとき。

## 検討した選択肢

### 選択肢 A: `.env` をローカルに配置して自動化する

利用者が一度 `.env` を復号・配置し、以降は AI が実行できるようにする。

**採らない理由**: 復号済みの認証情報が作業ツリーに残る。
加えて、**解析対象が Node.js の運用スクリプトだけ**であり、
ESLint が CI で同じ対象をより確実に検査している——得られるものが重複する。

### 選択肢 B: クローズのたびに利用者へ実行を依頼する

IT10 の計画が Try T4 として一度選んだ案である。

**採らない理由**: 「実行されること」を条件にできない。
利用者が不在のセッションではクローズが止まる。
IT5 が外した理由（実行されない条件は形骸化する）がそのまま当てはまる。

### 選択肢 C: 品質ゲートから外すが DoD には残す（現状維持）

**採らない理由**: 3 イテレーション連続で「未達」と書き続けた状態そのものである。
未達が常態化すると、**本当の未達が埋もれる**。

## 帰結

### 良い点

- **品質ゲートの条件がすべて CI で走る**。ローカルの手順や利用者の在席に依存しない
- 正典が 1 箇所（`test_strategy.md` 6.4）になり、DoD の書き写しによるドリフトが止まる
- 「未達」の記録が本当の未達だけになる

### 悪い点

- Flix 本体に外部の静的解析が当たらない状態が続く（上記リスク）
- **カバレッジの数値が無い**。テスト件数と `trace-lint` で代替している

### 再検討する条件

1. Flix を解析できる静的解析器・カバレッジ計測の手段が現れたとき
2. `arch-lint` の見逃しが実コードで再び発生したとき（IT2 で 1 度）
3. 品質ゲートの検査が CI で走らなくなったとき（**条件の側を直す**。検査を諦めない）

## 学び

**書き写した条件は正典が変わっても追随しない。**

IT5 は「3 回目の未実施にする前に決める」という正しい判断をした。
にもかかわらず同じことが IT8-IT10 で繰り返されたのは、
決定が `test_strategy.md` に書かれ、DoD には書き写された条件が残ったからである。

`arch-lint` 規約 11 で「BC 間の翻訳を 1 箇所に限定する」判断をしたのと同じ形が、
プロセスの側にも要る——**条件は 1 箇所に置き、他は参照する**。

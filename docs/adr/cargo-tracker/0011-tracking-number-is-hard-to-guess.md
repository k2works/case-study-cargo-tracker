# ADR-0011 追跡番号は推測されにくい形式で採る

認証なしで照会できる追跡番号を連番から衝突検査つきの乱数へ改め、正典の形式（`TRK-` + 大文字英数字 10 桁）にそろえる。[ADR-0010](0010-reaction-handler-as-the-only-coordinator.md) 決定 2 の採り方を訂正する。

日付: 2026-09-07

## ステータス

2026-09-07 提案されました。[ADR-0010](0010-reaction-handler-as-the-only-coordinator.md) 決定 2 を訂正するもの。

## コンテキスト

IT8 は **US18（荷主が追跡番号で貨物を照会する）**を作る。この照会は**認証を要らない**。荷主は予約のたびに口座を作らず、渡された番号だけで見る。`ui_design.md` の S44 は「総当たり対策：推測しにくい形式」と書いている。

IT7 の実装はこれを満たしていなかった。

- 採り方は**連番**（`nextval('tracking_number_seq')`）で、形式は `T-2026-000001`
- クラスタの実データが `T-2026-000001`・`T-2026-000005`・`T-2026-000007` と並んでいた。**1 つ知れば前後がすべて推測できる**
- 正典（`domain-model.md:1431`）は `TRK-` + 大文字英数字 10 桁と定めており、**形式そのものが食い違っていた**

IT7 の時点では照会が認証の内側にしかなかったため、連番でも実害が出ず、テストも形式を見ていなかった。**US18 を作る前に直す。**公開してから直すと、外に出た番号を回収できない。

## 決定

### 決定 1: 形式は正典に合わせる（`TRK-` + 大文字英数字 10 桁）

`domain-model.md:1431` をそのまま実装にする。設計が正で、実装が追随する。10 桁・36 文字の集合で 36^10 ≒ 3.7×10^15 通り。総当たりは、ゲートウェイのレート制限（IT8 T6b）と合わせて成り立たなくする。

### 決定 2: 連番をやめ、衝突検査つきの乱数にする

`SecureRandom` で 10 文字を採り、**採るたびに投影テーブルへ問い合わせて空きを確かめる**。乱数は重なりうるので、確率に任せない——同じ番号が 2 つ出れば、別の貨物が同じ追跡に見える。`cargo_summary.tracking_number` の UNIQUE 制約が最後の砦として残る。

**採番の場所は投影側のまま**（ADR-0010 決定 2 / `data-model.md`「採番は投影側」）。集約は「発行してよいか」だけを判断する。変えたのは採り方だけで、場所ではない。

### 決定 3: ADR-0010 決定 2 の「シーケンスで採る」を訂正する

ADR-0010 に訂正の注記を入れ、`tracking_number_seq` を落とす。**訂正は文章だけでは守られない。**実装が連番へ戻ったら赤にする検査を、この変更と同じ中で置く。

### 決定 4: 既存の発行済み番号は書き換えず、開発データを作り直す

`T-2026-0000NN` 形式の行は**書き換えない**。追跡番号は trackingms の集約識別子でもあり、bookingms 側だけを書き換えるとイベントストアと食い違う。開発・クラスタのデータは `npx gulp e2e:data` で作り直す。**本番データはまだ無い**（US18 は IT8 で初めて公開する）。

## 検査

**決定の数だけ検査を対応させる。** 文章のまま残った決定は守られない。

| 決定 | 検査 |
| :--- | :--- |
| 1 | `TrackingNumberGeneratorIT#followsTheCanonicalFormat`（`^TRK-[0-9A-Z]{10}$` に一致する） |
| 2 | `TrackingNumberGeneratorIT#isNotSequential`（20 個採って隣が 1 文字違いで並ばない）・`#doesNotCollide`（200 個が重ならない） |
| 3 | `TrackingNumberIsNotSequentialTest#noSourceDrawsFromTheSequence`（`nextval('tracking_number_seq')` を読む場所が無い） |
| 4 | `TrackingNumberGeneratorIT#theSequenceIsGone`（マイグレーション後の DB に `tracking_number_seq` が無い＝V016 が効いている） |

## 代替案

| 案 | 内容 | 却下の理由 |
| :--- | :--- | :--- |
| 連番のまま照会に認証を課す | S44 をログインの内側に置く | 荷主は口座を持たない。US18 の「番号だけで見られる」がそのまま消える |
| UUID をそのまま使う | `550e8400-e29b-...` | 電話や紙で伝えられない長さ。正典の形式とも違う |
| 連番を暗号化して見せる | 内部は連番、表示だけ変換 | 鍵の管理が増え、同じ番号が 2 つ出ない保証は結局 DB に戻る。得るものが無い |
| 既存番号も新形式へ書き換える | `cargo_summary` を UPDATE | 追跡番号は trackingms の集約識別子。片側だけ書き換えるとイベントストアと食い違う |

## 影響

- 追跡番号の見た目が変わる（`T-2026-000001` → `TRK-8K2QX7M4RB`）。IT7 のマニュアル 11 章の画面キャプチャは撮り直す（IT8 T11）
- 採番のたびに投影テーブルへの問い合わせが 1 回増える。発行は 1 予約に 1 回なので、量は問題にならない
- 総当たりの防ぎは形式だけでは足りない。**ゲートウェイのレート制限（IT8 T6b / 429）と対で成り立つ**

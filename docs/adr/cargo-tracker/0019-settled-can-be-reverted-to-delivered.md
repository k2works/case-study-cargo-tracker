# ADR-0019 精算済は終端ではない——入金の取り消しで引取済へ戻す

予約の `SETTLED`（精算済）を**終端状態から外す**。入金を取り消したとき、予約は `DELIVERED`（引取済）へ戻る。

日付: 2026-09-14

## ステータス

2026-09-14 提案。IT15（引き継ぎ 3・入金の取り消し）で実装済み、IT16 で起票。

## コンテキスト

**入金は誤って記録されます。** 振込の消し込みは人が行う作業で、別の請求書に当ててしまうことがあります。IT14 のレビューで経理担当者から挙がり、IT15 で「入金の取り消し」を実装しました（請求書は `PAID` → `INVOICED` へ戻る）。

**そこで予約の側が問題になりました。** 入金を記録すると予約は `DELIVERED` → `SETTLED` へ進みます（US23 §受入基準 4）。入金を取り消したのに予約が `SETTLED` のままだと、**請求書は「未入金」で予約は「精算済」**という食い違いが残ります。BC をまたぐので、どちらかの画面だけを見ている人には気づけません。

**`SETTLED` は状態遷移図で終端（`SETTLED --> [*]`）でした。** 戻せるようにするということは、**終端状態は終端である**という前提を覆すことです。前提を覆す決定は、理由を残さないと次に精算後の処理を足す人が同じ議論をやり直します。

## 決定

1. **`SETTLED` から `DELIVERED` への遷移を認める。** 契機は入金の取り消し（`PaymentVoidedEvent`）だけ
2. **人の操作では戻せない。** 遷移表には載せるが、手で動かす画面の選択肢には出さない
3. **`CANCELLED` は終端のままとする。** キャンセルは契約の終わりで、戻す業務が無い
4. **戻ったことは記録に残す。** `BookingSettlementRevertedEvent` を出し、予約の履歴から追える

| 1 | `CargoSettlementTest`（入金の取り消しで `SETTLED` → `DELIVERED` へ戻る） |
| 1・2 | `transitions.canon.test.ts`（画面の遷移表が正典と丸ごと一致する。**手で動かせる先**は `TransportStatus#isSetByHand` 相当の述語で絞る） |
| 3 | `CargoCancellationTest`（キャンセル済の予約は二度キャンセルしない・状態は読める） |

## 代替案

**(a) 予約を `SETTLED` のままにする。** 請求書と予約が食い違ったまま残ります。**BC をまたぐ食い違いは、片方の画面だけを見ている人には見えません**——本プロジェクトで繰り返し出ている形です。

**(b) 入金の取り消しをやめ、赤伝（マイナスの入金）で相殺する。** 会計としては筋が通りますが、**誤りの記録が残り続ける**ので「この予約はいくら入金されたか」が読みにくくなります。IT15 では「入金の行は消さず取り消した印を付ける」形（不変条件 9）を採ったので、予約の側もそれに合わせます。

## 結果

**良い面.** 請求書と予約が食い違わなくなりました。取り消しの事実も両方に残ります。

**悪い面.** **終端状態が 1 つ減りました。** 「精算が済んだら何もしない」と読める設計ではなくなったので、精算後の処理（督促の停止・実績の集計）を足すときは「戻ることがある」を前提にする必要があります。

**残っている窓.** 戻せるのは入金の取り消しだけです。請求書そのものの取消（`VOID`）で予約がどうなるかは**決めていません**——現在は予約を動かしません。取消は「請求を出し直す」操作で、引取の事実は変わらないためですが、**出し直さないまま終わる場合**の扱いは未定です。

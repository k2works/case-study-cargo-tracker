# ADR-0006 ロールの認可を Gateway の 1 か所で宣言する

経路ごとに許すロールを Gateway の宣言表（`RoleAuthorization`）で定め、そこで通らないものは後段へ渡さない。宣言の無い経路は通さない。

日付: 2026-09-04

## ステータス

2026-09-04 提案されました

## コンテキスト

IT3 のマルチパースペクティブレビューで、**サーバ側にロールの検査が 1 つも無い**ことが分かった。

ロールによる出し分けはフロントの `RequireRole`（`routes.tsx`）だけにあり、Gateway は JWT の署名を検証して利用者とロールを後段へ伝えるところで止まっていた。後段のサービスにも `@PreAuthorize` は無い。つまり、認証さえ通れば誰でも

- `POST /api/v1/routing/voyages`（航海スケジュールの登録）
- `GET /api/v1/booking/bookings/routing-worklist`（**全荷主**の予約一覧）

を叩けた。画面の出し分けは誤操作を減らすためのもので、守りではない。ブラウザを介さずに叩けば素通りする。

`BookingController` の Javadoc には「経路設計ロールへの開放は Gateway の**ルートとロール**で行う」と書いてあり、前半（ルート）だけが実装されていた。**書いただけで守った気になっていた形**である。

置き場所の候補は 2 つあった。

1. **各サービスに置く**（`@PreAuthorize` / Spring Security）
2. **Gateway に 1 か所で置く**

## 決定

Gateway に 1 か所で置く（案 2）。

1. 経路パターン → 許すロールの対応を `RoleAuthorization` の宣言表に持つ
2. `JwtAuthenticationFilter` が署名の検証に続けて認可を見る。**入力検証より先**に置く
3. **宣言の無い `/api/` の経路は通さない**（403）。載っていないものを許す形にすると、載せ忘れた経路ほど無防備になる
4. 応答は `{"code":"FORBIDDEN"}` だけを返し、何が足りないかは書かない
5. 要確認一覧のように「宛先ロールでサービス側が絞る」ものは `ANY_AUTHENTICATED` と宣言する。ここで二重に絞ると、ロールが増えるたびに 2 か所を直すことになり、片方が置き去りになる
6. **宣言は HTTP メソッドも見る（IT4 追補・2026-09-05）。** 同じ経路でも読みと書きで許すロールが違う。予約詳細（`GET /bookings/{id}`）は営業・経路設計・追跡が読むが、修正（`PUT /bookings/{id}`）は営業だけである（US32）。経路だけで宣言すると、**読める人が全員書けることになる**。メソッドを絞る宣言は経路だけの宣言より**先**に置く（後ろに置くと広いほうに吸われる）

宣言の抜けは `EveryServiceEndpointIsRoutedAndProtectedTest` が赤にする。決定 6 は `JwtAuthenticationFilterTest`（経路設計者・追跡管理者の `PUT` が 403、営業は通る、`GET` は 3 ロールとも通る）が赤にする。各サービスの `@RequestMapping` を全部拾ってから、宣言があるかを見る形にした。

## 根拠

**分担を ADR-0001 決定 4 と揃えられる。** 署名の検証は Gateway 1 か所で、後段は `X-Auth-Roles` を信じる、と既に決めてある。認可だけを後段に置くと、「誰が守っているか」が経路ごとに変わる。

**表示ロールの正典（`ui_design.md` の画面一覧）と 1 対 1 で読み比べられる。** 各サービスに散ると、画面 1 つの権限を確かめるのに複数のリポジトリを歩くことになる。

**宣言表なので、増えたことも減ったことも差分に出る。** 注釈をコントローラに散らすと、付け忘れは差分に現れない（何も書かないのが既定になる）。

## 影響

- **後段サービスを Gateway 経由でしか公開しない**ことが前提になる。クラスタ内でサービスを直接叩けば認可を迂回できる。ネットワークの分離は k8s の Service（ClusterIP）に依存しており、その前提が崩れるならサービス側にも置き直す必要がある
- 新しい経路を足したら宣言も足す。忘れると **403 になって動かない**（黙って通るのではない）ので、気づける形の失敗になる
- 経路パターンは**上から順に最初に当たったものを使う**。細かい経路を先に置く。`Map.copyOf` にすると順序が失われるので使わない
- メソッドを絞る宣言（決定 6）は、経路だけの宣言より前に並べる。並び順が意味を持つので、宣言を `Map` で持たず `List<Rule>` で持つ

## 代替案

- **各サービスに `@PreAuthorize` を置く**: 権限の判断が業務コードの近くに来るのは利点だが、7 サービスに散ると画面 1 つ分の権限を読み解くのに全部を歩くことになる。付け忘れが差分に現れないのも欠点
- **フロントの出し分けだけで済ませる**: 守りではない。これが IT3 まで実際に起きていた状態

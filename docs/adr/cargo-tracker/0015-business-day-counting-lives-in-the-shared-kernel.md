# ADR-0015 営業日の数え方は共有カーネルが持つ

`HolidayCalendar` を handlingms から共有カーネル（`shared.domain.calendar`）へ移す。数える国は**輸入港の UN/LOCODE** から決める。

日付: 2026-09-11

## ステータス

2026-09-11 提案。IT13（US21）。

## コンテキスト

**移す条件は IT12 が先に書いていました。** `domain-model.md` の要素表は `HolidayCalendar` について「置き場は handlingms。**billingms が保管料を数え始めたら、そのとき移す**」と書いています。読む側の無い配線を先に敷かない、という IT9・IT10 と同じ判断です。

**US21 でその条件が満たされます。** 請求の調整行は、留置による保管料を `CustomsStatusChangedEvent.heldBusinessDays` を根拠に立てます（`domain-model.md` の料金計算の節）。つまり**同じ留置について、handlingms の画面が出す日数と billingms の請求の根拠が一致しなければなりません**。数え方が 2 か所にあると、片方だけ直ります（IT10 の「判定はテスト側に書き直さない」と同じ形）。

**国別分岐が本番で一度も踏まれていませんでした**（IT12 レビュー #L17）。`HolidayCalendar` は国コードで休日表を切り替えますが、呼び出しは 2 か所とも `new CountryCode("JP")` 固定でした。**切り替えているのは検査だけ**で、本番の経路はどの貨物でも日本の暦で数えていました。留置は輸入港の税関で起きるので、これは業務として誤りです。

## 決定

**決定 1. `HolidayCalendar` は共有カーネル（`shared.domain.calendar`）に置く。** 置ける場所は [ADR-0001](0001-cqrs-es-with-axon-in-microservices.md) 決定 4 の名簿が縛っており、足すには「全 BC で同じでなければならない業務上の理由」が要ります。理由は上のとおり——**同じ留置に対して 2 つの BC が違う日数を出してはならない**からです。`Money` を共有カーネルに置かないのと逆方向の判断ですが、理由が違います。金額の型は BC ごとに通貨も丸めも違いえますが、営業日は違ってはいけません。

**決定 2. 数える国は輸入港の UN/LOCODE の先頭 2 文字で決める。** 留置は輸入港の税関で起きます。輸入港は登録のときに application 層が持ち込み（集約は投影を読めません）、内部イベント `CustomsDeclarationRegisteredEvent` と読み取りモデルの両方に載せます。**集約（記録の時点）と読み取り（画面・請求）が同じ決め方を使う**ことが肝心で、違う決め方を置くと記録した日数と画面の日数が食い違います。

**決定 3. 輸入港が載っていない申告は日本の暦で数える。** イベントは追記専用なので、列を足す前に登録された申告には輸入港が入っていません。不変条件を足して既存の行を読めなくしない、という IT11 の判断と同じです。**足りないことは「早く点く」側に倒れます**（日本の休日を外して数えるぶん日数が小さくなり、督促は遅れません）。

## 検査

**決定の数だけ検査を用意する。** 検査に落とさなかった決定は守られません。

| 決定 | 検査 |
| :--- | :--- |
| 1 | ArchUnit：`SharedKernelScopeTest`（名簿に `shared.domain.calendar` を足した。名簿を狭めると赤になることも同じ検査が見る）。`HolidayCalendarTest` は移送先のパッケージで回る |
| 2 | `CustomsProjectionIT#countsBusinessDaysInTheImportCountry`（**同じ期間・違う輸入港で日数が変わる**。日本は 8/11 の山の日を外して 4 営業日、米国は 5 営業日。日本固定に戻すと赤になる） |
| 3 | `CustomsQueryHandlerTest`・`CustomsDeclarationTest`（輸入港が `null` の申告でも数えられる）。`CustomsProjectionIT#theRecordedAndTheReadCountAgree`（**記録の時点で載せた日数と読み取りが数える日数が一致する**——決定 2 の「同じ決め方」を固定する） |

## 代替案

| 案 | 内容 | 却下の理由 |
| :--- | :--- | :--- |
| billingms に写す | 同じ `HolidayCalendar` を billingms にも置く | **片方だけ直る。** 休日表は毎年変わるので、写した瞬間から食い違い始める |
| 日本固定のまま | 輸入港を持ち込まない | 留置は輸入港で起きる。国別分岐を持ちながら本番で切り替えないなら、その分岐は「あるつもり」でしかない |
| 外部の休日カレンダー API | 移動する休日（振替・旧正月）まで正しく数える | 本 IT のスコープ外。固定日だけでも**足りないことは「早く点く」側に倒れる**ので、督促は手遅れにならない。必要になったら `HolidayCalendar` の内側だけを差し替えられる |

## 結果

**よくなること。** 同じ留置について handlingms と billingms が同じ日数を出す。国別分岐が本番の経路で実際に踏まれる。休日表を直す場所が 1 か所になる。

**代償。** 共有カーネルが 1 パッケージ太る。休日表の変更が全サービスの再ビルドを要求する。

**守りきれなくなる兆し。** 国別の休日が「固定日だけ」で足りなくなったとき（振替休日を数え間違えた苦情が出たとき）。そのときは `HolidayCalendar` の内側を外部カレンダーに差し替える——置き場の決定はそのままでよい。

# ADR-0008 予約の修正内容は投影として持つ

US32 §受入基準 4「修正の履歴（いつ・誰が・**何を変えたか**）が残る」を読めるようにするため、修正イベントから決まりきった形で導く投影テーブル `cargo_revision` を置く。

日付: 2026-09-05

## ステータス

2026-09-05 提案されました。[ADR-0002](0002-event-store-axon-server-and-postgresql-read-models.md) の読み取りモデル方針の範囲内で、IT4 の判断を改めるもの。

## コンテキスト

IT4 で US32（仮受付の予約情報を修正する）を実装したとき、次の判断をした。

> 「修正の履歴が残る」は Event Store が持つ。投影には最終更新の 2 列だけを置き、変更内容の履歴テーブルは作らない。同じ事実を 2 か所で持つと必ずずれる。
> — `V007__add_cargo_summary_updated.sql`・`CargoSpecificationUpdatedEvent`

この判断は「ずれない」という点では正しかった。しかし **IT4 のクローズ時点で、何を変えたかを読む手段はどこにも無かった**（IT4 引き継ぎ 2・高）。画面にも API にも読み口が無く、Event Store を直接読む運用手順も無い。受入基準の「残る」を「記録した」とだけ解釈し、「読める」を落としていた。

記録だけして読み口を出さないと、記録は無いのと同じである。実際、IT4 の完了報告書はこの項目を**未達**として記録している。

### 検討した案

| 案 | 内容 | 判断 |
| :--- | :--- | :--- |
| A | Event Store を読み取り時に遡って差分を作る | 却下。Query 側が Event Store に依存する形を作ると、ADR-0001 の「読みは投影だけを見る」を崩す。集約のイベント列を毎回読むので、修正の多い予約ほど遅くなる |
| B | 修正イベントの本文に「変更前の値」も載せる | 却下。集約が変更前を知るために投影を読むか、イベントを肥らせることになる。契約イベントではないので互換性の縛りは無いが、同じ事実を 2 つの形でイベントに載せることになる |
| C | **投影として持つ**（採用） | 投影は「イベントから導けるもの」を置く場所である。差分は修正イベントと直前の投影行から決まりきった形で導けるので、投影の定義に収まる |

## 決定

1. **`cargo_revision` を置く。** 1 行 = 1 回の修正で変わった 1 項目（`booking_id`・`updated_at`・`field_label`・`field_seq`・`before_value`・`after_value`・`updated_by`）。
2. **主キーに修正時刻を含める。** 連番で採ると、リプレイのたびに新しい番号が振られて同じ修正が積み上がる。`ON CONFLICT DO NOTHING` で入れる。
3. **差分は丸ごと比べて作る。** `CargoSpecificationDiff` がレコード要素そのものを回す。項目を列挙した名簿は持たない（手で書くと、要素を足したときに書き忘れたものが黙って差分から消える）。**ラベルの無い要素は例外にする。**
4. **読み口を同じ変更で出す。** `GET /api/v1/booking/bookings/{id}/revisions` と S22 予約詳細の「修正履歴」。記録と読み口は対で出す。

## 結果

### 良い点

- US32 §受入基準 4 が満たせる。誤って直したときに、何を戻せばよいかが読める
- 投影なので、他の読み取りモデルと同じ規律（リプレイで増えない・実 DB のテストで固定する）がそのまま効く
- 変更前の値をイベントに載せないので、集約は今までどおり「これからの姿」だけを述べる

### 悪い点・受け入れるリスク

- 同じ事実が Event Store と投影の 2 か所にある。**投影が正でないことを守る**必要がある（食い違ったら Event Store から作り直す）
- 項目のラベルを投影に書く（`field_label`）。ラベルを変えると過去の行と新しい行で表記が混ざる。表示名の変更は業務用語の変更なので、そのときに移行を判断する
- 差分は「投影に入っていた値」との比較である。投影が遅れている間に 2 回続けて修正すると、2 回目の差分は 1 回目の結果と比べられる（イベントは順に処理されるので、通常は起きない）

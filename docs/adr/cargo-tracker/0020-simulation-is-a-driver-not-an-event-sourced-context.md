# ADR-0020 業務シミュレーションは独立サービスに置き、Event Sourcing は適用しない

業務シミュレーション（UC23 / US33〜US36）は **`simulationms`** という独立サービスに置く。各工程は **Gateway 経由の HTTP** で本番の API を叩く。実行の記録（`simulation_run` / `simulation_step`）は **Event Sourcing を適用せず**、現在状態だけを持つ。

日付: 2026-09-14

## ステータス

2026-09-14 提案。IT16（US33・US34）。

## コンテキスト

**予約から精算まで手で追うのに 7 ロール分のログインと 20 以上の画面操作が要ります。** 実演のたびに手順が揺れ、配備直後に「どこが切れているか」を切り分ける手段もありません（UC23）。

作るのは**業務ではなく、業務が成立していることを確かめる手段**です。ここで 3 つ決める必要がありました。

1. **どこに置くか。** 既存のサービスの中か、独立サービスか
2. **どうやって工程を実行するか。** 内部の API を直接呼ぶか、本番と同じ HTTP 経路を通るか
3. **実行の記録に Event Sourcing を適用するか**（ADR-0001 は全 BC の既定としている）

## 決定

### 1. 独立サービス `simulationms` に置く

業務サービスの中に置くと、**本番で起動しない仕組みを業務サービスが抱える**ことになります。業務サービスが環境で振る舞いを変えるのは、確かめたい対象そのものを不安定にします。

### 2. 各工程は Gateway 経由の HTTP で本番の API を叩く

**呼ばれる側は本番の実装そのものを使い、自動化するのは呼び出し元だけ**です。認可も本番と同じ経路（ロールごとのトークン）を通ります。

本システムの越境は**すべて Axon の契約イベント／コマンド／クエリ**で、HTTP で他サービスを呼ぶ本番コードは 1 件もありません（実測 0 件）。`simulationms` は**あえてその例外**になります——人が操作するのと同じ経路を踏むことが目的だからです。

**ArchUnit は名簿で緩めません。** 「`simulationms` だけが Gateway の URL を組み立てて HTTP で呼ぶ」ことを明示的に許し、それ以外のサービスが HTTP で越境したら赤にします。

### 3. Event Sourcing を適用しない

**実行の記録は業務の事実ではありません。** 監査の対象でもなく、リプレイして作り直す価値もありません。`authms` に適用していないのと同じ理由です（`architecture_backend.md`「authms の Event Sourcing: ユーザーとロックは現在状態だけが業務に要る」）。

加えて、**実行は長く走る処理**です。1 本のシナリオは連鎖の待ちを含めて数十秒かかります。コマンドハンドラの中で走らせるとコマンドバスを占有するので、実行はバックグラウンドで進み、工程が終わるたびに記録を書き足します。**コマンドバスをログとして使う形になる**なら、Event Sourcing を選ぶ理由が残りません。

### 4. 由来の印は契約イベントに載せ、除外は各 BC の読み口に置く

シミュレーションは**本番の API で本物の業務データを作ります**（決定 2）。何もしなければ、営業の予約一覧にも経理の請求一覧にも実データとして並びます。

**印は荷主に付けます。** `ShipperRegisteredEvent` に `simulated` を足し、貨物と請求はその荷主から引き継ぎます。専用の荷主種別にはしません——由来と荷主種別は直交し（シミュレーションでも法人割引を踏みたい）、`ShipperType` は割引の判断に使われています。

**項目は `Boolean` にします。** プリミティブの `boolean` だと、この項目が無い古いイベントを読めません（`ConversionException`。IT16 で実測）。`null` は「印が付く前に登録された荷主」＝本物です。

**除外は読み口の側に置きます。** 印を付けるだけでは混ざります。読み口ごとに外すので、**外していない読み口がある**ことを自覚して数えます（下表）。

**印を立てられる相手を絞ります。** 印は業務の一覧から荷主と貨物を消すので、誰でも立てられると本物の荷主を静かに見えなくできます。`bookingms` は**実行を許可した環境でだけ**印を受け付けます（既定は無効・本番では立てない）。ロールでは絞りません——シミュレーションは人と同じ利用者として登録するので（決定 2）、ロールで分けるとシミュレーションだけが通る道を作ることになります。

| 読み口 | 外す | 根拠 |
| :--- | :--- | :--- |
| 予約一覧・件数（S20） | 済 | `CargoSummaryMapper.xml` の `visible` |
| 経路設計の作業一覧（S30） | 済 | 同 `worklistVisible`。**失敗シナリオは必ずここで止まる** |
| 荷主一覧（S10） | 済 | `ShipperMapper` の投影に印を持つ |
| 請求一覧（S60） | 済 | `InvoiceMapper.xml` の `searchWhere` |
| 追跡一覧（S40） | 済 | `TrackingSummaryMapper` の `findAll` / `countAll`。IT17 |
| 荷役の作業一覧（S50）・ダッシュボード（S02）・引取待ち（S54） | 済 | `CargoSnapshotMapper` の 3 つの読み口。IT17 |
| 要確認一覧（S70・bookingms / billingms） | 済 | `AttentionItemMapper` の `findOpenByRole`。登録時に対象から解決する。IT17 |
| 例外一覧（S42） | 済 | `TrackingExceptionMapper` の `findOpen`。**US35 の例外シナリオ × 継続実行で一晩に数百件**。IT17 |
| キャンセル承認待ち（S23） | 済 | `CancellationRequestMapper` の `findPending`。陸揚げ地を決められるのは追跡管理者だけ。IT17 |
| 通関一覧（S52） | 済 | `CustomsDeclarationMapper` の `search`。留置が 3 営業日を超えたものを毎朝見る。IT17 |

**この 3 つは IT17 のレビューで見つかりました。** 表が「済」と「未」で埋まっていたので**完全に見えていた**——数え上げたつもりで、例外・キャンセル・通関の一覧が表に載っていませんでした。**表に無いものは、外していないことにも気づけません。**

**外さない読み口も書く。** 「まだ外していない」と「意図して外さない」は別である。

| 読み口 | 外さない理由 |
| :--- | :--- |
| 追跡・予約・請求・荷役の**単票** | US34 の実行結果が工程ごとにここへ辿る。外すと実行結果から何も開けない |
| 追跡一覧を**荷主で絞る**読み（S40 荷主 / S02 荷主） | 行はその荷主のものしか返らない。外すと確認用の利用者が自分の一覧から辿れない（US37 §6） |
| 自社予約一覧（S45・S46）・貨物の知らせ | 同上。荷主で絞る読みは外さない |
| 航海あての要確認（`routingms`） | 航海は共有の設備で、荷主に属さない。印が付く対象ではない |
| 航海スケジュール一覧（S31） | 同上。**シミュレーションは便を登録する**——便が 1 本も無い環境ではどのシナリオも「経路の確定」で止まるので、必要なデータ準備を工程に含めた（`PREPARE_VOYAGES`）。印を付けられないので**一覧には本物として並ぶ**。代わりに<b>同じ区間を同じ貨物種別で運べる便がすでにあれば足さない</b>——溜まる量を「使う区間の数」に抑える |

**引く先が無い対象は本物として扱う。** シミュレーションかどうかを引けない要確認
（写しがまだ無い・対象の種類を知らない）は一覧に出す。消す側に倒すと、いちばん
知らせたい「請求書を作れなかった」が黙って消える。

## 検査

| 決定 | 検査 |
| :--- | :--- |
| 1 | `SimulationServiceIsSeparateTest`（`simulationms` が他サービスのパッケージ・DB に依存しない） |
| 2 | `OnlySimulationCrossesByHttpTest`（HTTP クライアントを本番コードで使うのは `simulationms` だけ。**全サービスを走査してから**判定する） |
| 3 | `EventSourcedServicesHaveTheSameShapeTest`（`@EventSourced` を付けた集約だけを拾うので、付けなければ対象外。**付けたのに形が違えば赤**） |
| 4 | `SimulatedOriginRoundTripIT`（印が予約・請求・追跡・荷役の一覧まで届く・**表ではなく一覧の経路で見る**。BC をまたぐ配送を判別するのはここだけ）、`SimulatedOriginExcludedIT`（trackingms / handlingms。**読み口を数え上げた表を javadoc に置く**）、`SimulatedAttentionExcludedIT`（bookingms / billingms）、`ShipperDataEncryptingConverterTest`（組み直しで項目を落とさない）、`ShipperControllerIT`（許可していない環境では印を受け付けない）、受け入れ「生成した予約は、営業の予約一覧に出ない」 |

**決定 3 に専用の検査は要りません。** 既存の検査は「`@EventSourced` が付いた集約を全部拾ってから形を見る」形なので、付けなければ何も要求しません。**名簿に例外を足す必要がない**のは、この検査が名簿方式でないからです。

## 代替案

**(a) 既存サービス（たとえば gatewayms）に相乗りする。** 本番で起動しない仕組みを業務サービスが抱えます。Gateway は全リクエストの通り道なので、そこに負荷をかける側を置くのは特に危険です。

**(b) 内部の API（Axon のコマンド／クエリ）を直接叩く。** 認可を通らないので、**「シミュレーションは通るのに実際の操作は通らない」状態を検出できなくなります**。IT15 では層ごとの検査がすべて緑のまま業務が回っていなかったことが 4 件あり、いずれも呼び出し元を変えずに実際の経路を踏んで初めて見つかりました。

**(c) Event Sourcing を適用する。** ADR-0001 の既定には沿いますが、得るもの（履歴・リプレイ・監査）がどれも要りません。長く走る処理をコマンドで刻むことになり、**コマンドバスをログとして使う**形になります。

## 結果

**良い面.** 業務サービスは環境で振る舞いを変えません。シミュレーションが通ることと実際の操作が通ることが、同じ経路を踏むので一致します。

**悪い面.** **HTTP で越境する経路が 1 本できます。** `simulationms` は他サービスの API の形（パス・要求・応答）に依存するので、API を変えるとここも直ります——**契約イベントと違い、変更が検査で捕まりません**。受け入れシナリオとクラスタ E2E が唯一の安全網になります。

**残っている窓.** `simulationms` が Gateway の URL を組み立てるので、**Gateway の経路を変えたときに気づく手段が弱い**です。IT17 で「シナリオが叩く経路の一覧」と Gateway の宣言を突き合わせる検査を置くかどうかを決めます。

**印の解決には順序の窓があります。** 追跡・荷役・請求は「荷主の写しが先に届いている」ことを前提に投影の時点で印を解決します。写しがまだ無ければ本物として扱うので、荷主の登録と追跡の開始がごく短い間隔で起きると、その 1 件だけ一覧に残ります。シミュレーションは登録から追跡開始まで数十秒かかるので実害はありませんが、**印を消す側に倒さない判断の裏返し**として記録します。

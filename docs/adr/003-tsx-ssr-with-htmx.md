# ADR-003: フロントエンドを TSX SSR + htmx で構成する

テンプレートエンジンとして TSX（React 19 `react-dom/server` の `renderToStaticMarkup`）を採用し、クライアント側は htmx による部分更新のみとする（ハイドレーションなし）。

日付: 2026-07-27

## ステータス

承認済み

## コンテキスト

参照元の Java 版設計は Thymeleaf SSR + htmx + Bootstrap 5 を採用し、業務系 Web アプリとして「SSR + 最小 JS」の方針を取っていた。TypeScript 版の当初案は Nunjucks（文字列テンプレート）だったが、文字列テンプレートでは画面が要求するデータとドメイン層の DTO 型の整合を検査できず、変数名のタイプミス・渡し忘れが実行時まで顕在化しない。

- 画面数は 17 + α で限定的、リアルタイム要件は追跡ステータスのポーリング程度
- SPA の複雑さ（ビルドパイプライン・クライアント状態管理）を持ち込みたくない
- TypeScript エンジニアが一貫して開発できる構成にしたい

## 決定

- テンプレートは `.tsx` の関数コンポーネント（型付き props）とし、サーバー上で `renderToStaticMarkup` により静的 HTML へレンダリングする
- クライアント側 React・ハイドレーションは行わない。動的挙動は htmx 2.x（部分更新・ポーリング・PRG 支援）と最小限の vanilla JS が担う
- レイアウトは `Layout.tsx` + children 合成。ロール別 UI 制御は props の `user` / `roles` で型安全に分岐する
- Alpine.js 等のクライアントフレームワークは導入せず、必要になった時点で ADR で判断する

### 代替案

- **Nunjucks / EJS（文字列テンプレート）**: Thymeleaf の直訳として自然だが、テンプレートが型検査対象外となり、DTO 変更の影響が実行時までわからない。却下
- **React SPA（+ REST API）**: 型安全だが、限定的な画面数に対してビルド・状態管理・API 二重化のコストが過大。SEO・初期表示も不利。却下
- **Next.js**: SSR は得意だが、NestJS と分離したもう 1 つのサーバー実行系を持つことになり、構成が複雑化する。却下

## 影響

### ポジティブ

- テンプレートも TypeScript の型検査対象となり、画面とドメイン型の整合をコンパイル時に保証できる
- ハイドレーションがないためクライアント JS は htmx のみで軽量、初期表示が速い
- JSX の自動エスケープにより XSS 耐性が既定で高い

### ネガティブ

- React をレンダラーとしてのみ使う非典型的構成のため、React エコシステムの慣習（hooks 等）はほぼ使えないことを開発者が理解する必要がある
- htmx フラグメントとフルページの二重レンダリング分岐（HX-Request 判定）を Controller で規約化する必要がある

## コンプライアンス

- TSX コンポーネントの単体レンダリングテスト（Vitest + cheerio）と、Controller 統合テストでの HTML 断片・PRG 302 検証を test_strategy.md 3.5 に従い実装する
- `dangerouslySetInnerHTML` の使用禁止（例外は DOMPurify サニタイズ済みのみ）をコードレビューで確認する

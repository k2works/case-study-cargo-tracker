# ADR-012: BC 間の依存の向きを一方通行に保ち、残る循環はインフラ層に閉じ込める

境界付けられたコンテキスト間のパッケージ循環について、**断てるものは呼び出しの向きを一方通行にして断ち、断てないものは理由を記録したうえでインフラ層に閉じ込める**。

日付: 2026-08-08

## ステータス

承認済み

## コンテキスト

IT7 のクローズ後、JIG のパッケージ図で **Booking ⇄ Routing** と **Booking ⇄ Tracking** が循環していることが分かった。

### 測定した事実

BC 横断の `import` は本番コード全体で **6 ファイル**であり、**すべて `infrastructure/acl/` のアダプタ**である。ドメイン層とアプリケーション層には 1 件も無い（実測 0 件）。

| 依存 | 実体 | ADR-009 の分類 |
| :--- | :--- | :--- |
| Booking → Tracking | `CargoArrivalEstimatesAdapter` | **問い合わせ**（目的地・推定到着日） |
| Tracking → Booking | `TrackingPortAdapter` | **コマンド**（追跡番号の発行。番号を返す） |
| Booking → Routing | `CargoRouteAssignmentsAdapter` / `RoutableBookingsAdapter` | **コマンド**（割り当ての可否を返す）/ **問い合わせ** |
| Routing → Booking | `VoyageCapacityAdapter` | **問い合わせ**（確定時の空き再判定） |
| Booking → Handling | `CargoSnapshotsAdapter` | **問い合わせ** |

### 循環が生まれる仕組み

規約そのものが原因である。**ポートは呼ぶ側が定義し、アダプタは呼ばれる側が実装する**（ADR-005・ArchUnit ルール 4）。

この配置では、A が B を呼ぶたびに**パッケージ B が A に依存する**。したがって A と B が互いに呼び合えば、**呼び出しの内容にかかわらず必ずパッケージ循環になる**。

**アダプタの置き場所を変えても循環は消えない。** 依存を持つパッケージが入れ替わるだけである。

### Handling だけが循環していない

Handling → Booking は `CargoSnapshots`（問い合わせ）1 本だけであり、逆向きの状態伝播は
`HandlingActivityRegisteredEvent` で行っている（ADR-009）。**呼び出しが一方通行であるため循環しない。**

これが本 ADR の答えの形である。

### なぜ ArchUnit は緑で JIG だけが検出するのか

ArchUnit のルール 4 は `..outboundservices.acl..` を**依存先とする参照を除外**している（ポートのパッケージが唯一の越境点であるという設計意図の表明）。JIG にその除外は無いため、素のパッケージ依存が見える。

**JIG のほうが正直である。** ArchUnit の除外は「越境してよい場所」を宣言しているだけで、「循環していない」ことを主張していない。

### 各方向を断てるか

| 方向 | 断てるか | 理由 |
| :--- | :--- | :--- |
| Tracking → Booking（`CargoArrivalEstimates`） | **断てる** | 目的地と推定到着日は、**追跡番号の発行時に一緒に渡せる**。その呼び出しは既に Booking → Tracking の向きである。経路が変わった場合は `CargoRoutedEvent` で更新すればよく、ADR-009 が定める「状態の伝播はイベント」に沿う |
| Booking → Tracking（`TrackingPort`） | 断てない | **コマンドであり番号をその場で返す**。イベントにすると発行の可否と番号を利用者に返せない |
| Booking → Routing（`CargoRouteAssignments`） | 断てない | **コマンドである。** 戻り値（`NOT_FOUND` / `REJECTED` / `CONFLICTED`）を経路設計者の画面にそのまま返している。イベントにすると**拒否の理由を返せなくなる**（ADR-009 が明示的に避けた形） |
| Booking → Routing（`RoutableBookings`） | 断てなくはない | 経路割り当て待ちの一覧。Routing 側が読み取りモデルを持てば不要になるが、**イベント駆動の読み取りモデルを 1 つ増やす規模**であり、`CargoRouteAssignments` が残る以上この 1 本を消しても循環は解けない |
| Routing → Booking（`VoyageCapacityPort`） | 断てない | **確定の瞬間の空き容量**であり、古い値では意味を持たない（IT5 レビュー M3 の指摘そのもの）。結果整合の読み取りモデルにすると、この検査を入れた理由が消える |

**Booking ⇄ Routing は、両方向とも ADR-009 の基準に照らして同期が正しい。** 循環を消すには、業務上必要な即時性を捨てるか、読み取りモデルを増やして複雑さを買うかのどちらかになる。

## 決定

### 1. 断てる循環は断つ — Booking ⇄ Tracking

`CargoArrivalEstimates`（Tracking → Booking の問い合わせ）を**廃止する**。

- 追跡番号の発行時（`TrackingPort.issue`）に、**目的地と推定到着日を一緒に渡す**
- 経路が変わったときは `CargoRoutedEvent` を Tracking が購読して更新する

これにより Tracking → Booking の参照が 0 になり、**Booking ⇄ Tracking の循環は消える**。

### 2. 断てない循環は受け入れ、理由を記録する — Booking ⇄ Routing

**残す。** 両方向とも即時の答えを要するコマンド・問い合わせであり、イベント化すると
「拒否の理由を返せない」「古い空き容量で確定できてしまう」という**業務上の後退**になる。

**循環そのものより、循環を消すために失うもののほうが大きい。**

### 3. 循環をインフラ層に閉じ込める

**ドメイン層とアプリケーション層に BC 間の参照を作らない**ことを、ArchUnit で固定する。

現在この値は 0 件である。**0 件であることを検査で守る**（いま守れていることと、明日も守れることは別である）。

循環が `infrastructure/acl/` のアダプタに閉じている限り、次の性質が保たれる。

- ドメインとアプリケーションは**自分の BC のポート interface しか知らない**（依存性逆転が成立している）
- 循環はコンパイル単位の都合であって、**業務ロジックの相互依存ではない**
- BC を別モジュール・別デプロイに切り出すとき、**動かすのはアダプタだけで済む**

### 4. 新しい BC 間依存を足すときの規律

**逆向きのポートを足す前に、順方向の呼び出しでデータを渡せないかを先に問う。**

IT7 で `CargoArrivalEstimates` を足したときは、この問いを立てなかった。既に Booking → Tracking の呼び出しがあり、そこにデータを載せれば済んだ。**逆向きの問い合わせは、最後の手段である。**

## 影響

### 良い影響

- Booking ⇄ Tracking の循環が消える
- 「逆向きのポートを足す前に順方向を疑う」という規律ができ、循環の増加を止められる
- ドメイン層・アプリケーション層の無循環が検査で固定され、**将来モジュール分割するときの前提が守られる**

### 悪い影響・残る課題

| # | 内容 | 扱い |
| :--- | :--- | :--- |
| 1 | **Booking ⇄ Routing の循環は残る** | 受け入れる。JIG のパッケージ図には出続けるため、**図を見た人が毎回同じ疑問を持つ**。本 ADR がその答えである |
| 2 | Tracking が目的地・推定到着日の写しを持つ | **予約が経路を変えたときに古くなる**。`CargoRoutedEvent` の購読で追随するが、結果整合であり反映に間がある（ADR-009 の代償と同じ性質） |
| 3 | 発行時に渡す値が増える | `TrackingPort.issue` の引数が増える。**運ぶのは素の値だけ**という規約は維持する |
| 4 | `RoutableBookings` は残す | 単独で消しても循環は解けないため、複雑さに見合わない。Routing が読み取りモデルを持つ判断は別途 |

### 実施時期

| # | 内容 | 時期 |
| :--- | :--- | :--- |
| 1 | ArchUnit ルールの追加（ドメイン層・アプリケーション層の無循環） | **IT8 の返済枠**。小さく、いま 0 件であるため即座に固定できる |
| 2 | `CargoArrivalEstimates` の廃止と発行時のデータ受け渡し | **IT8**。US17（貨物状態の手動更新）で Tracking を触るため、同じイテレーションで行う |
| 3 | `CargoRoutedEvent` の購読による更新 | 上記 2 と同時。**片方だけ入れると古い値が更新されないまま残る** |

## 検討したが採らなかった案

| 案 | 内容 | 不採用の理由 |
| :--- | :--- | :--- |
| ポート専用パッケージ（`contracts/`）に集約 | 全 BC が `contracts` に依存し、BC 間は無依存になる | **ADR-005 と矛盾する。** 共有カーネルを `Location` と `ShipperId` の 2 つに限る判断は、「1 つ変えると全 BC の再ビルドとレビューを強制する」ことを避けるためである。ポートを共有すると同じ問題が起きる。`KnownPorts` を Booking と Routing で共有しなかった判断も同じ理由による |
| アダプタを呼ぶ側の `infrastructure` に置く | 依存の持ち主を入れ替える | **循環は消えない。** 依存を持つパッケージが変わるだけである |
| すべての BC 間連携をイベントにする | 循環が完全に消える | **拒否の理由を利用者に返せなくなる**（ADR-009 が明示的に避けた形）。追跡番号の発行も経路の割り当ても、可否をその場で画面に返す必要がある |
| ArchUnit の除外を外して循環を禁止する | 検査を厳しくする | 上記のとおり**業務上必要な同期呼び出しまで禁止される**。検査を実態に合わせるのではなく、実態を検査に合わせようとして設計を歪める |

# ADR-008: IT2 では利用者と荷主を紐付けず、貨物予約は営業担当者のみが扱う

authms の利用者と bookingms の荷主を紐付ける仕組みは IT2 では作らない。紐付けが無い間、貨物予約の登録も参照も `ROLE_SALES` に限る。`ROLE_SHIPPER` に予約参照を開くのは、紐付けを実装する US18（IT6）以降とする。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

`ui_design.md` の権限マトリクスでは、貨物予約の参照を `ROLE_SALES` と `ROLE_SHIPPER` の両方に開いている。荷主が「自分の予約」を見られることを意図した記述である。

しかし現時点で、**ログインしている利用者がどの荷主なのかを判定する手段が無い**。authms の `user` と bookingms の `shipper` は別のデータベースにあり（Database per Service）、両者を結ぶキーがどこにも無い。

この状態で `ROLE_SHIPPER` に予約参照を開くと、絞り込みができないため**全荷主の予約が見える**。荷主 A が荷主 B の出荷内容・数量・行き先を読めることになり、これは機能の不足ではなく情報漏洩である。

紐付けの設計は小さくない。「利用者 1 人が複数の荷主を担当しうるか」「荷主の担当者が交代したとき過去の予約が見えるか」を決める必要があり、US18（追跡照会）・US22（法人割引）・キャンセル申請者の判定にも波及する。IT2 の 8 SP に押し込むと、どれかが雑になる。

## 決定

1. **IT2 では紐付けを作らない。** 代わりに線を明示的に引く
2. **貨物予約の登録・参照はいずれも `ROLE_SALES` のみとする。** `ui_design.md` の権限マトリクスを本 ADR に合わせて更新する（設計が実装に追随するのではなく、**設計を先に直してから実装する**）
3. **`ROLE_SHIPPER` が予約を参照できないことをテストで固定する。** 「まだ作っていない」を「開いていない」と取り違えないため、荷主ロールが 403 を受けることを明示的に検証する
4. **紐付けの設計は US18（IT6）の着手時に行う。** そこで初めて荷主本人が画面を使うため、判断に必要な材料（何を見せ、何を見せないか）が揃う

### 代替案

- **`shipper` に `user_id` 列を足して IT2 で紐付ける**: 1 対 1 を前提に置くことになる。実務では 1 社に複数の担当者がいるため、後から 1 対多へ変えることになり、既に入ったデータの移行が要る
- **`ROLE_SHIPPER` に開いたうえで、絞り込みは後から足す**: 絞り込みが無い期間に情報が漏れる。「後で足す」で守れない種類の欠落である

## 影響

### ポジティブ

- 情報漏洩の経路を作らずに IT2 を閉じられる
- 紐付けの設計を、判断材料が揃う IT6 まで持ち越せる

### ネガティブ

- `ui_design.md` の権限マトリクスを一度狭め、IT6 で広げ直す。設計の履歴が 2 段になる
- 荷主ロールでログインしても IT2 の新機能に触れない。デモの見せ方が営業担当者中心になる

## コンプライアンス

- `CargoBookingController` のテストで、`ROLE_SHIPPER` が登録・参照とも 403 を受けることを検証する
- 認可設定を外すとそのテストが赤になることを確認する
- `ui_design.md` の権限マトリクスが本 ADR と一致していることを、IT2 のレビューで確認する

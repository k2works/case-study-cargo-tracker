# ADR-0008: 更新の衝突は内容から導いた版の照合で検出する

## ステータス

承認済み（2026-08-03・IT6）

## 文脈

US25（航海スケジュールの更新）で、既存のスケジュールを上書きする操作が入った。
航海スケジュールは**複数の経路設計者が同じ航海を編集しうる**。
運航変更は情報が入った担当者から順に反映するため、同時編集は珍しくない。

素朴に実装すると**後勝ち**になる。A が寄港地を追加し、B が船名を直したとき、
後に保存した方の内容で全項目が上書きされ、**先に保存した変更は痕跡なく消える**。
消えたことは誰にも通知されない。次に一覧を開いたときに「入れたはずの寄港地が無い」
という形で現れ、入力ミスと区別がつかない。

IT5 では予約の引き渡し（`assign`）が同じ read-modify-write の構造を持っていたが、
そこは**状態遷移**であり、集約側で「WAITING 以外からは遷移できない」と表明することで
二重実行を防いでいた。**任意の属性を書き換える更新には、この手が使えない**。

## 決定

**更新系は、更新前に見ていた版と現在の版を照合し、食い違えば保存しない。**

1. 版は**集約の内容から導く**（`RegisterVoyage.versionOf`）。全属性を連結した文字列のハッシュ
2. 版は**隠しフィールドで往復させる**（編集フォーム → 確認 → 保存）
3. 食い違ったときは `Stale(現在の値)` を返し、**現在値を見せて利用者に再度判断させる**。
   自動マージしない
4. 更新結果は列挙型（`Updated` / `NotFound` / `Stale` / `Invalid`）で表す。
   真偽値にすると「保存しなかった理由」が消える

### 版に更新日時を使わない

| 案 | 問題 |
| :--- | :--- |
| `updated_at` を版とする | 秒未満の更新が同じ値になりうる。**内容は同じだが保存し直した**場合にも食い違いとして扱う |
| 版番号のカラムを持つ | 増やす責務が保存経路すべてに乗る。1 箇所忘れると静かに効かなくなる |
| **内容から導く**（採用） | 同じ内容なら同じ版。カラムも増やさない |

## 根拠

**失われた更新は、失われたことが分からない。** これが後勝ちの本質的な悪さである。
エラーになるなら利用者は気付いて対処できる。静かに消えると、消えたことに
気付くのは業務が壊れたあとになる。

**自動マージしない。** 「船名は A の値、寄港地は B の値」と機械が決めると、
どちらの担当者も自分が保存した内容と違うものを見ることになる。
運航の変更は**それぞれに理由がある**。理由を知っているのは人であり、
機械が持っている情報では判断できない。

**版を内容から導くのは、忘れられない仕組みだからである。** 版番号のカラムを
持つ方式は、保存する側が毎回インクリメントしなければならない。
新しい更新経路を足した人がそれを忘れると、**衝突検出が静かに無効になる**。
内容から導けば、忘れるという操作自体が存在しない。

## 帰結

### よい点

- 失われた更新が起きない。衝突は必ず利用者に見える形で現れる
- 版のカラムもマイグレーションも要らない
- 「同じ内容を保存し直した」は衝突にならない（利用者を無用に止めない）

### 悪い点

- **ハッシュの衝突（異なる内容が同じ版になる）は理論上ありうる**。
  運航変更の同時編集という規模では実際上問題にならないが、ゼロではない
- 版の計算対象に含め忘れた属性は、**その属性だけ後勝ちになる**。
  属性を足すときは `versionOf` も直す必要がある（テストで固定する）
- 集約ごとに `versionOf` を書くことになる（共通化は集約の形が揃ってから判断する）

### 既存の更新系への適用

`updateStatus`（予約の状態遷移）には**適用しない**。状態遷移は
「遷移元の状態」が版の役割を果たしており、集約側で表明済みである
（`assign` の同時実行で成功が 1 本だけになることを `BookingHttpTest` で固定した）。

**任意の属性を書き換える更新系**を新設するときは、本 ADR に従う。

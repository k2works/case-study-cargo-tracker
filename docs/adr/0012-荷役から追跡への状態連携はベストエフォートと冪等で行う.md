# ADR-0012: 荷役→追跡の状態連携はベストエフォート＋冪等で行う

荷役作業登録（Handling）から追跡状態更新（Tracking）への BC 連携を、単一トランザクションではなく、荷役を正としたベストエフォート発火＋冪等な追跡記録で行う決定。

日付: 2026-07-17

## ステータス

2026-07-17 提案（IT6・retro-5 Try#1／IT5 レビュー中#5 の荷役→追跡原子性方針の確定）

## コンテキスト

IT5 で荷役作業登録（US15/US16）の成功後に、対応する追跡イベントを記録して追跡状態を更新する BC 連携を `handlingCreate`（合成層）に実装した。現状、荷役の永続化（Handling リポジトリのトランザクション）と追跡イベントの記録（Tracking リポジトリの別トランザクション）は**別トランザクション**であり、荷役は成功したが追跡記録が失敗する部分失敗があり得る。

IT5 レビュー（中#5）と retro-5 Try#1 で、この「別トランザクション更新失敗が `eprintfn` のみ」という原子性の欠如について、補償／再試行方針を定めることが求められた。

素朴には両更新を単一トランザクションに束ねれば原子性が得られる。しかし Handling と Tracking は別コンテキスト（別集約・別テーブル）であり、両者を 1 つの技術トランザクションに束ねることは、BC 分離（ADR-0001）と post-commit イベント駆動（ADR-0002）の設計方針に反する。分散した集約の即時強整合を求めることは、DDD の集約境界（1 トランザクション＝1 集約）の原則とも矛盾する。

## 決定

**荷役→追跡の連携は単一トランザクションで束ねず、荷役を「正」としたベストエフォート発火＋冪等な追跡記録による結果整合で行う。**

1. **荷役が正**: 荷役作業の登録が成功した時点で業務事実は確定する。追跡状態はその射影であり、追跡記録の失敗は荷役を巻き戻さない（post-commit のベストエフォート原則・ADR-0002 と同方針）。
2. **失敗は握り潰さずログ**: 追跡記録が失敗した場合は握り潰さずログ出力し、可観測性を確保する（レビュー中#1 と同方針・現行実装済み）。
3. **冪等な再記録で回復**: 追跡イベントは（追跡番号・イベント種別・時刻・場所）で冪等に扱えるため、再送・バッチ再記録で回復可能とする。TrackingStatus は Events からの導出値（保持しない）であり、同一イベントの重複記録があっても最終状態は収束する。
4. **将来の強化**: 恒久的な取りこぼしを防ぐ必要が生じた場合は、荷役側に「追跡未反映」フラグ or アウトボックス（Transactional Outbox）を導入し、post-commit ディスパッチャで再試行する（release_plan の将来移行項目）。本 IT では導入しない。

### 代替案

- **案 B: 荷役と追跡を単一トランザクションに束ねる**（却下）: 即時強整合は得られるが、BC 分離（ADR-0001）・post-commit イベント駆動（ADR-0002）・集約境界（1 Tx＝1 集約）に反する。Handling が Tracking の永続化詳細に結合し、両 BC の自律性を損なう。
- **案 C: 追跡記録の失敗で荷役登録も失敗（ロールバック）にする**（却下）: 荷役という確定した業務事実を、その射影である追跡の技術的失敗で取り消すことになり、業務的に不自然。荷役作業員の再入力を強いる。

## 影響

### ポジティブ

- BC 分離・集約境界・post-commit イベント駆動の設計方針と一貫する。
- 荷役という業務事実を追跡の技術的失敗で巻き戻さない。
- TrackingStatus の導出値設計により、冪等な再記録で最終状態が収束する。

### ネガティブ

- 追跡記録が失敗した場合、回復（再記録）まで追跡状態が荷役の実態から一時的に乖離する。
- 現状は自動再試行を持たず、ログ監視＋手動／バッチ再記録に依存する（アウトボックスは将来導入）。

## コンプライアンス

- 追跡記録失敗時に握り潰さずログ出力することを実装で確認する（`handlingCreate` の `eprintfn`）。
- 荷役登録の成否が追跡記録の成否に依存しない（追跡失敗でも荷役は確定）ことを受け入れテストで担保する。
- TrackingStatus が Events からの導出値であり、重複記録に対して収束することをドメインユニットで担保する（`currentStatus`）。

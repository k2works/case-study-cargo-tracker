# ADR-0014: 通関済は荷役の記録で表す／BC 間連携の再検討条件を向き先で測る

- **状態**: 承認
- **日付**: 2026-08-05
- **決定者**: 開発チーム
- **関連**: [ADR-0007](ADR-0007-defer-external-acl-and-scope-v1.md)・[ADR-0011](ADR-0011-routing-writes-booking-through-its-aggregate.md)・[ADR-0012](ADR-0012-cross-context-writes-go-through-the-target-aggregate.md)

## 文脈

2 つの主題を 1 本にまとめる。どちらも「**条件や設計の書き方が誤っていた**」ことへの
是正であり、根が同じである——**書いた条件が実態を測れていない**。

### (a) 通関のゲートに、通す者がいない

[ドメインモデル設計](../design/domain-model.md)の追加ルール 2 は
「CustomsDeclaration が CLEARED 状態になるまで CLAIM（引取）は実施できない」と定める。
US16（引取作業を記録する）を実装するには、この不変条件を実装する必要がある。

ところが設計は `CustomsDeclaration` の状態更新を**税関システムの ACL**
（`CustomsClearancePort`・`UpdateCustomsStatusCommand`）から受ける形で描いており、
その **TS07（外部 ACL 基盤）は [ADR-0007](ADR-0007-defer-external-acl-and-scope-v1.md)
で延期中**である。

つまり `customs_declaration` を作ってそのまま引取のゲートにすると、
**CLEARED にできる者が誰もいない**。引取が永久にできない状態になる。

これは IT10 の Problem 5（機能が入っているのに業務が回らない）と同じ形である。
受入基準は満たすが、業務は 1 件も完了しない。

### (b) 再検討条件が代理指標として機能していない

ADR-0011 は「`composition/acl/` が 5 本を超えたら見直す」、
ADR-0012 は「1 つの操作で 3 つ以上の集約を更新したら見直す」を条件としている。
IT10 終了時点で**どちらにも到達した**が、到達したこと自体に気付いていなかった
（ADR-0012 は自分の起票と同じ IT で 2 つの条件を発火させていた）。

さらに IT10 のレビューで、**本数は 2 つの異なる事実を潰している**ことが分かった。

| 見え方 | 実体 |
| :--- | :--- |
| ACL が 2 本 → 6 本に増えた | 連携が増えた（危険とは限らない） |
| **書き込み 4 本のうち 3 本が Booking へ向いている** | **`Cargo` がハブ化している**（危険） |

Handling の 3 本は読み 1・書き 2 の素直な形であり、粒度として問題ない。
一方 `Cargo` は `BookingStatus`・`RoutingStatus`・`trackingNumber`・旅程を 1 集約で抱えるため、
Routing も Tracking も Handling も**自分の仕事の印を `Cargo` に付けに来る**。

## 決定

### 1. 通関の完了は `CUSTOMS` 種別の荷役記録で表す

`customs_declaration` テーブルは**本リリースでは作らない**。

- `HandlingType` に **`CUSTOMS`（通関）** を加える（正典の 5 値のうち 4 値目）
- **`CUSTOMS` の記録がある貨物だけが引取できる**（追加ルール 2 の実装）
- 記録するのは荷役作業員である。現場で通関書類を受け取るのは荷役の側であり、
  「通関が終わった」ことを最初に知る立場にある

### 2. `CUSTOMS` は輸送状態を変えない

通関は貨物の位置も輸送の段階も変えない。**出来事としては残すが状態は進めない**。

これを表すため、荷役種別から輸送状態への写像を `Option` にする——
`resultingStatusOf(CUSTOMS) = None`。`None` のときタイムラインには 1 行増えるが
バッジは変わらない。**「変えない」を既定値（現在の状態）で表さない**
——同じ値を書き戻す実装は、書き戻しの競合を隠す。

### 3. 引取（`CLAIM`）は荷受人確認を伴わなければ構築できない

US16 の受入基準 1・2 は荷受人確認（署名または確認コード）を要求する。
**署名画像は扱わず確認コードとする**（画像の保管は本リリースの範囲を超える）。

確認コードは**集約の不変条件**とする。`register` が `CLAIM` を受けたとき
確認コードが空なら `Err` を返す。「後で入れる」余地を作らない——
引取は所有権の移転であり、証跡の無い引取は業務上成立しない。

### 4. 再検討条件を「単一 BC へ向かう書き込みアダプタ数」で測る

ADR-0011・ADR-0012 の再検討条件を次で置き換える。

> **単一の BC へ向かう書き込み ACL アダプタが 3 本を超えたら、
> その BC の集約の粒度を見直す。**

読みは数えない——相手の不変条件を壊さないため危険の質が違う。
総数も数えない——**増えたこと自体は危険ではない**。

現時点の値は **Booking へ 3 本**（旅程の割り当て・追跡番号の記録・経路逸脱の報告）であり、
**条件ちょうどで、超えていない**。次に Booking へ書き込む ACL が生まれた時点で
`Cargo` の分割を検討する。

## 検討した代替案

### 案 A: `customs_declaration` を作り、画面から状態を変えられるようにする

設計どおりのテーブルを作り、追跡管理者が `CLEARED` に変える画面を足す。

**採らない理由**: 実体のない業務手順を作ることになる。通関の可否を決めるのは税関であり、
社内の誰かが画面で `CLEARED` にするのは**記録ではなく創作**である。
外部連携が入ったとき、この画面は捨てるか、二重の真実になる。

### 案 B: 通関のゲートを実装しない（US16 の受入基準だけを満たす）

引取を無条件に記録できるようにする。

**採らない理由**: 通関前の貨物を引き渡すのは業務上の重大な逸脱であり、
リリース計画も IT11 の題に「通関未完了時の拒否」と書いている。
落とすなら計画の変更として明示すべきで、黙って落とす対象ではない。

### 案 C: `HandlingType` に `CUSTOMS` を足さず、引取の画面に「通関確認済」チェックを置く

**採らない理由**: チェックは記録として残らない。「誰が・いつ確認したか」が
追えなければ、後から通関前の引き渡しを検証できない。
`CUSTOMS` の荷役記録なら日時・場所・担当者がそのまま残る。

## 帰結

### 良い点

- **業務が回る**。荷役作業員が通関を記録し、その貨物を引き取れる
- 通関の記録が**タイムラインに出る**（H8 の形にそのまま乗る）。荷主は
  「通関中」であることを自分で確認できる
- 外部連携（TS07）が入ったときの移行先が明確である——`CUSTOMS` の記録を
  `customs_declaration` へ写し、記録の出どころを ACL へ変える

### 悪い点・引き受けるリスク

- **設計ドキュメントと構造が違う**。`CustomsDeclaration` エンティティは
  本リリースに存在しない。`domain-model.md` と `data-model.md` に
  本 ADR を参照する注記を入れ、**描いたまま作らないものを放置しない**
- 通関の状態が 2 値（記録がある / ない）に潰れる。`HELD`（留置中）・
  `REJECTED`（不可）は表現できない。**留置は例外として扱う**——
  US19/US20（例外処理）の範囲であり、そちらで扱う

### 再検討する条件

1. **外部税関システムとの連携が計画に入ったとき**（TS07 の着手条件）。
   `customs_declaration` を作り、記録の出どころを ACL へ移す
2. **通関の留置・却下を業務として扱う要求が出たとき**。2 値では足りなくなる
3. **単一の BC へ向かう書き込み ACL アダプタが 3 本を超えたとき**（決定 4）

> **本 IT の実装が上の条件に触れていないか**（IT10 ふりかえり Try T2）:
> 条件 3 は**現時点でちょうど 3 本**であり、超えていない。US16・US17 は
> Booking へ向かう書き込みアダプタを増やさない（US17 は Tracking を直接扱う）。
> 条件 1・2 はいずれも本 IT のスコープ外である。

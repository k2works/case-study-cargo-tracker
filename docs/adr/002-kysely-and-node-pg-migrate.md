# ADR-002: データアクセスに Kysely、マイグレーションに node-pg-migrate を採用する

ORM は採用せず、型安全な SQL ビルダー Kysely と node-pg-migrate による明示的な SQL / スキーマ管理を行う。

日付: 2026-07-27

## ステータス

承認済み

## コンテキスト

参照元の Java 版設計は MyBatis（XML マッパー）を採用し、「SQL を明示的に管理する」方針を CQRS の Read Model 最適化の根拠としていた。TypeScript 版でも以下を満たすデータアクセス手段が必要である。

- CQRS のクエリ側で読み取り最適化 SQL（JOIN・集計）を直接書ける
- ドメインモデルに永続化用デコレータ・アノテーションを持ち込まない（ヘキサゴナルの純粋性）
- PostgreSQL 16 のスキーマをバージョン管理し、Forward マイグレーション方式で運用できる

## 決定

- クエリ・永続化: **Kysely**（TypeScript の型でスキーマを表現する SQL ビルダー）
- マイグレーション: **node-pg-migrate**（`exports.up / down`、本番はダウンマイグレーション禁止の Forward 方式）
- トランザクション境界は Kysely の `transaction()` コールバックで明示する

### 代替案

- **TypeORM / MikroORM**: エンティティデコレータがドメインモデルに永続化関心を持ち込み、ヘキサゴナルの依存方向と衝突する。暗黙のクエリ生成は CQRS の読み取り最適化方針とも整合しない。却下
- **Prisma**: スキーマ定義・型生成は強力だが、独自 DSL への依存と生成クエリの制御性の低さが明示的 SQL 管理方針に合わない。マイグレーションも Prisma Migrate に束縛される。却下
- **生 pg + 手書き SQL**: 制御性は最大だが型安全性がなく、スキーマ変更時の破壊検知ができない。却下

## 影響

### ポジティブ

- スキーマ型とクエリが TypeScript の型検査で結びつき、カラム変更がコンパイルエラーとして検出される
- ドメイン層が永続化技術から完全に独立し、リポジトリアダプターに Kysely を閉じ込められる
- Read Model のクエリチューニングが SQL レベルで自由に行える

### ネガティブ

- ORM のような変更追跡・遅延ロードはなく、集約の再構築ロジックをリポジトリで明示的に書く必要がある
- Kysely のスキーマ型定義とマイグレーションファイルの二重管理（型生成の自動化で緩和）

## コンプライアンス

- dependency-cruiser ルール「domain / application が Kysely を直接 import しない（infrastructure の リポジトリアダプターのみ）」を CI で検証する
- マイグレーションは node-pg-migrate 記法であること、本番運用が Forward 方式であること（operation.md 6.3）をレビューで確認する

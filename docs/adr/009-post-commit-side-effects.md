# ADR-009: コミット後副作用（通知・イベント）はコマンド失敗として扱わない

集約の永続化コミット後に行う副作用（通知記録・ドメインイベント発行・購読側の状態更新）は、失敗してもコマンド自体の失敗として扱わず、冪等リスナーと at-least-once の再試行余地で結果整合を担保する。

日付: 2026-07-30

## ステータス

承認済み

## コンテキスト

IT4 のレビュー（architect M1/M5）で、`notify` / `emit` がコミット後の別処理であるにもかかわらず、失敗するとコマンド全体が失敗として表示される問題が指摘された。集約の状態は既にコミット済みのため、「状態は変わったのに画面はエラー」という不整合なユーザー体験と、リトライによる二重実行リスクを生む。

IT5 では Handling → Tracking / Booking のイベント連携（`HandlingActivityRegisteredEvent` 購読による貨物状態自動更新・MISROUTED 反映）が加わるため、購読実装前に共通方針の確立が必要となった（IT4 Try T2）。ADR-005 は「コミット後 emit・冪等リスナー・結果整合」を既に定めており、本 ADR はそれをコマンド境界の失敗セマンティクスまで具体化する。

## 決定

1. **コマンドの成否は集約の永続化コミットで確定する**。コミット後の副作用（通知記録・イベント発行・リスナー処理）の失敗は、コマンドのエラーレスポンス / エラーフラッシュにしない。
2. **副作用の失敗はエラーログ + 監視で検知する**。Application Service / Controller はコミット後副作用を try-catch で包み、失敗時は `Logger.error` に記録して処理を継続する。
3. **リスナーは冪等に実装する**（ADR-005 踏襲）。購読側は処理済み判定（対象レコードの存在・状態チェック）を行い、同一イベントの重複配信で二重更新しない。統合テストで「重複配信しても結果が変わらない」「リスナー失敗がコマンド結果へ波及しない」ことを検証する。
4. **at-least-once は発行のみの割り切りを維持する**。プロセスクラッシュによるイベント消失（結果整合の破れ）は ADR-005 どおり監視と手動リカバリで補い、Transactional Outbox は複数プロセス化の時点で別 ADR として判断する。

### 代替案

- **副作用失敗時にコマンドをロールバック**: コミット後のため不可能。コミット前に通知・購読処理を移すと、外部 I/O をトランザクションに巻き込みロック時間と失敗率が悪化する。却下
- **Transactional Outbox を今導入**: 配信保証は高まるがポーリング・リレー機構が初期スコープに過剰（ADR-005 の判断を維持）。却下（移行パスとして留保）
- **失敗を画面に警告表示（コマンドは成功扱い）**: ユーザーに委ねても対処できず、実装が煩雑。ログ + 監視で運用側が対処する方が一貫する。却下

## 影響

### ポジティブ

- コマンド結果が集約の状態と一致し、「保存されたのにエラー表示」という不整合が消える
- Tracking 購読（IT5）を安全に追加できる基準（冪等・非波及）がテスト可能な形で定まる

### ネガティブ

- 副作用の失敗がユーザーに見えないため、監視（エラーログ）への依存が強まる
- 通知記録の欠落がありうる（at-least-once ではなく at-most-once になるケース）。業務上クリティカルになった時点で Outbox へ移行する

## コンプライアンス

- コミット後副作用の try-catch + ログ記録をコードレビューで確認する
- 統合テストで「リスナー失敗がコマンド成功へ波及しない」「重複配信で冪等」を検証する（IT5 タスク 3.2/3.3）

# ADR-011: 認証境界を fail-closed（グローバルガード + 明示公開）へ反転する

認証を「デフォルト保護・明示公開」に反転する。グローバル `APP_GUARD`（AuthenticatedGuard）を全ルートに適用し、公開ルートは `@Public()` デコレータで明示的に除外する。

日付: 2026-07-30

## ステータス

承認済み

## コンテキスト

IT6 のアーキテクトレビュー（H1）で、認証境界が **fail-open** 構造であることが指摘された。認証はグローバルガードではなく各コントローラの `@UseGuards(AuthenticatedGuard, RolesGuard)` に依存しており、新しいコントローラでガードを付け忘れると意図せず全公開になる。実際に公開追跡ページ（US18）は「ガードを付けない＝公開」という opt-in 保護で成立しているが、この方式では付け忘れがそのまま情報公開事故になる。

現状の認証不要ルートは、ログイン（`/login`）・ログアウト・ヘルスチェック（`/health`）・公開追跡（`/public/tracking/*`）・静的アセットの 5 系統である。

## 決定

1. **`AuthenticatedGuard` をグローバル `APP_GUARD` として登録する**（`app.module.ts` の providers に `{ provide: APP_GUARD, useClass: AuthenticatedGuard }`）。全ルートがデフォルトで認証を要求する（fail-closed）。
2. **公開ルートは `@Public()` デコレータ（`SetMetadata('isPublic', true)`）で明示除外する**。`AuthenticatedGuard` は `Reflector` で `isPublic` メタデータを読み、真なら認証をスキップする。
3. **`RolesGuard` は従来どおり各コントローラの `@UseGuards` / `@Roles` で適用する**（ロール認可はルートごとに異なるため、グローバル化しない）。認証（グローバル・fail-closed）と認可（ルート単位）を分離する。
4. **公開に `@Public()` を付与するルートを最小に保つ**: `/login`・`/logout`・`/health`・`/public/tracking/*`・静的アセットのみ。付与は各ルートのレビュー対象とする。
5. **静的アセット（ServeStatic）はガードの管轄外**であることを確認し、必要なら除外パスを設定する。

### 代替案

- **現状維持（opt-in ガード）**: 付け忘れが公開事故に直結する構造的リスクが残る。却下。
- **RolesGuard もグローバル化**: ルートごとにロールが異なり、デフォルトロールの定義が不自然になる。認証と認可の関心を混ぜる。却下。

## 影響

### ポジティブ

- ガード付け忘れ＝認証必須（安全側）になり、新規ルート追加時の事故が構造的に防がれる
- 「どこが公開か」が `@Public()` の一覧で機械的に把握できる（レビュー・監査が容易）

### ネガティブ

- 既存の全コントローラの `@UseGuards(AuthenticatedGuard, ...)` から `AuthenticatedGuard` を外す移行が必要（RolesGuard は残す）
- `@Public()` の付与漏れがあると正当な公開ルートが 401/リダイレクトになる（回帰 E2E で担保）

## コンプライアンス

- 公開ルート（ログイン・ヘルス・公開追跡・静的）の回帰 E2E を全件 green にしてから後続タスクに進む
- `@Public()` の付与箇所をコードレビューで確認し、想定外の公開がないことを検証する

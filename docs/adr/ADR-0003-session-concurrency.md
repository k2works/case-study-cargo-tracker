# ADR-0003: 同一ユーザーの同時セッション数

同一ユーザーの同時セッション数を 1 とし、後続のログインが既存セッションを無効化する。セッションは DB（`sessions` テーブル）に保持する。

## ステータス

承認済み（2026-08-31・IT3）

## コンテキスト

[非機能要件](../design/non_functional.md) 4.1 は「同一ユーザーの同時セッション数: 1（後続ログインが既存セッションを無効化）」を要求する。一方、同じ節に次の懸念が併記されていた。

> 荷役作業員が部署共用アカウントを使う運用の場合、本要件は現場作業を阻害する。アカウント運用方針（個人 / 共用）を確定させ、共用運用なら本要件の緩和を ADR で判断すること

判断が必要な理由は 2 つある。

1. **実装への影響が大きい**: 同時セッション 1 を満たすには、ログイン時に既存セッションを検索して無効化する必要がある。ECS を複数タスクで運用する時点で、共有セッションストア（DB）が必須になる（[バックエンドアーキテクチャ](../design/architecture_backend.md)）
2. **後から緩める方が安全**: 制約を緩める変更（1 → N）は既存の利用者に影響しないが、締める変更（N → 1）は運用中のログインを切断する

## 決定

### 1. 同時セッション数 1 を実装する（非機能要件どおり）

共用アカウント運用の懸念は理解できるが、**現時点で共用運用が決まった事実はない**。決まっていない運用のために、監査証跡の前提（誰が操作したかを一意に特定できること）を先に手放すべきではない。

- 荷役作業員（`ROLE_HANDLER`）は**個人アカウント運用**を前提とする
- 実装は「ログイン成功時に、同一 `user_id` の既存セッションを削除してから新しいセッションを作る」

### 2. セッションストアは初期リリースから DB 実装とする

インメモリ実装では、ECS の別タスクが保持するセッションを無効化できない。ALB のスティッキーセッションは同一ユーザーを同一タスクへ固定するだけで、無効化の手段を持たない。

- ローカル・テストでもインメモリではなく **H2 の `sessions` テーブル**を使う。本番と同じ経路を検証するため
- 効果（`Session`）のハンドラを差し替えられる構造は維持する。性能が問題になった場合に ElastiCache 実装へ移行できる

### 3. 緩和が必要になった場合の条件を明示する

以下のいずれかが確認された時点で、本 ADR を改訂して緩和を判断する。

- 荷役作業員の共用アカウント運用が業務側で決定された
- 現場から「別端末でログインすると作業中の端末が切れる」という申告が実際に発生した

緩和する場合は、非機能要件 4.1 の改訂と、監査証跡の要件（操作者の特定）をどう満たすかをセットで決める。

## 影響

### 正の影響

- 監査証跡で操作者を一意に特定できる（[要件定義](../requirements/requirements_definition.md) の「業務データの保護・監査証跡の確保」）
- 認証情報が共有された場合に、同時利用が発覚しやすい（後からログインした側だけが使える状態になる）
- テストが本番と同じ DB セッションの経路を通る

### 負の影響

- **利用者は複数端末で同時に作業できない**。PC で作業しながらスマートフォンで確認する使い方はできない
- ログインのたびに DB の書き込みが 2 回（削除・作成）発生する。セッション数は同時利用者数と同じ規模のため、性能上の問題は生じない見込み
- ブラウザのタブを閉じただけではセッションが残るため、共用端末では明示的なログアウトが必要（[UI 設計](../design/ui_design.md) のログアウト導線で担保する）

### この判断を見直す条件

上記「3. 緩和が必要になった場合の条件」に記載。

## コンプライアンス

- ログイン成功時に、同一利用者の既存セッションが削除されること（`SessionTest.testLoginInvalidatesExistingSession`）
- セッションが DB に永続化されること（`sessions` テーブル）
- ログイン成功時にセッション ID が再生成されること（セッション固定攻撃対策。本 ADR とは別の要件）

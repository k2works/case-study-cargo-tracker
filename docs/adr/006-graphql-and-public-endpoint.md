# ADR-006: API 方式（GraphQL）と公開照会の分離

API は GraphQL（Sangria + circe）とし、ログイン無しの追跡照会は別エンドポイント・別スキーマ・別バンドル・別ターゲットグループに分離する。

日付: 2026-11-04

## コンテキスト

- 参照実装は GraphQL（Sangria）で、コマンド（Mutation）とクエリ（Query）が別のエンドポイント。
- 追跡照会はログイン無しで使え（US18）、追跡番号の推測と過負荷の標的になる（R-02）。
- Sangria のメンテナンス状況は採用時に確認が要る。技術スタックの確認では 4.2.x（参照実装は 4.2.4）。

## 決定

**GraphQL（Sangria + circe）を採り、Mutation と Query を別エンドポイント**にする。**公開の追跡照会は `/public/graphql` のような別エンドポイントで、公開項目だけの専用スキーマ**（内部スキーマから絞らず、公開用の型を別に定義）にする。クエリの深さ・複雑さを制限しイントロスペクションを無効にし、回数制限（WAF とアプリ）をかけ、存在しない番号と形式不正で応答を変えない。フロントエンドは公開照会を別のエントリ・別のバンドルにし、インフラは別のターゲットグループに置く。

### 変更箇所

- ヘルスチェックは回数制限・同時実行制限の対象外にする（過負荷で再起動を繰り返さない。NFR-A14）。
- フロントエンドは GraphQL のコード生成をスキーマの固定ファイルから行う（F3）。

### 代替案

- **REST**：コード生成と型付きの問い合わせの利点を失う
- **Caliban**：ZIO 前提のため、ZIO を採らない決定（ADR-007）と合わない（技術スタック 2.3 と同じ理由）
- **同一バンドル・同一スキーマで出し分け**：公開側に内部の項目や業務画面のコードが混ざるリスクがあるため却下

## 影響

### ポジティブ

- 公開項目を型で固定でき、過負荷・推測が業務側に波及しにくい。
- 参照実装の経験を使える。

### ネガティブ

- Sangria の保守状況に依存する（外部ライブラリの導入：R-01 の承認が要る）。
- エンドポイントとスキーマが増える。

## コンプライアンス

- A7：公開スキーマの項目一覧を固定するテスト。F7：公開バンドルが認証・業務画面のコードを含まない。I3：公開パスが別のターゲットグループ。I4：過負荷でヘルスチェックが 200 を返す。

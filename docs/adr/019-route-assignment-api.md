# ADR-019: 経路の割り当て API は候補の中身を丸ごと受け取り、確定時に成立を再検証する

`PUT /api/v1/bookings/{bookingId}/route` の契約を決める。経路設計者が選んだ候補を、どの形で受け取り、何を確かめ、何を発行するか。

日付: 2026-08-21

## ステータス

承認済み

## コンテキスト

IT4 で経路候補を算出できるようになり（[ADR-017](017-route-candidates-api.md)）、IT5 で選んだ候補を予約に割り当てる（[ADR-020](020-itinerary-assignment-transitions.md)）。その接続点となる API の形を決める必要がある。

決めることが 3 つある。

- **候補をどう指すか。** ID で参照するか、中身を丸ごと送るか
- **確定の時点で何を確かめるか。** 候補を出してから確定するまでに、航海スケジュールは変わりうる
- **`CargoRoutedEvent` を発行するか。** 設計には登場するが、イベント基盤（RabbitMQ）は IT6 である

1 つ目は [ADR-017](017-route-candidates-api.md) の帰結として決まる。あちらが「経路候補は永続化しない」と決めたため、**サーバ側に候補 ID で引ける実体が無い**。

## 決定

1. **候補の中身（区間の並び）を丸ごと受け取る。候補 ID では参照しない。**

   ```json
   PUT /api/v1/bookings/BKG-2026000001/route
   {
     "legs": [
       {
         "voyageNumber": "V0201",
         "loadUnLocode": "JPTYO",
         "unloadUnLocode": "CNSHA",
         "loadTime": "2026-09-02T09:00:00Z",
         "unloadTime": "2026-09-05T09:00:00Z"
       },
       { "voyageNumber": "V0202", "loadUnLocode": "CNSHA", "unloadUnLocode": "USLAX",
         "loadTime": "2026-09-06T09:00:00Z", "unloadTime": "2026-09-18T09:00:00Z" }
     ]
   }
   ```

   [ADR-017](017-route-candidates-api.md) が「候補は保存に見合わない」と決めたため、ID で引ける実体が無い。ID を発行するなら候補を保存することになり、あちらの決定を裏返す。**送る側が中身を持っているのだから、それをそのまま送る。**

   地点は UN/LOCODE で受け、名称はサーバがマスタから引く。画面が送った名称を信じると、地点名の直しがマスタと予約の 2 か所に分かれる。

2. **確定の時点で、選んだ経路がまだ成立することを確かめる。**

   候補を出してから確定するまでのあいだに、航海が更新・欠航・削除されることがある。**受け取った区間が、いまの航海スケジュールと一致するかを routingms に問い合わせる。** 一致しなければ **409** で断る（入力の誤りではなく、状態がその操作を許さない。[ADR-015](015-routing-requested-state.md) の先例に倣う）。

   > 中身を丸ごと受け取る形（決定 1）の代償がこれである。ID 参照ならサーバ側の実体を見れば済むが、こちらは**送られてきた内容が本物か**を確かめる必要がある。決定 1 と決定 2 は対になっている。

3. **`CargoRoutedEvent` を発行するコードは IT5 では書かない。** 依存（`spring-boot-starter-amqp`）と接続設定はすでに入っているため、ここで言う「IT6」は**発行するコードを書くこと**を指す。**発行しないことをここに明記する**のは、設計にイベントが描かれているためであり、書かないと「実装漏れ」と読まれる。追跡（trackingms）への連携は IT6 で足す。

### 代替案

- **候補に ID を振って参照させる**: API は小さくなるが、候補を保存することになる（[ADR-017](017-route-candidates-api.md) の裏返し）。1 回の探索で数十件出るものを、選ばれなかったぶんも含めて保存し、掃除の仕組みまで持つことになる
- **確定時に再検証しない**: 実装は単純だが、**欠航した航海の旅程が予約に入る**。荷役の担当者は来ない船を待ち、荷主には出ない便の予定が伝わる。しかも間違いに気づくのは出港予定日である
- **再検証を 400 で断る**: 入力の形式は正しいため、画面は「入力を直してください」と伝えることになる。直すべきは入力ではなく、経路をもう一度探すことである
- **IT5 でイベントも発行する**: 基盤ごと持ち込むことになり、US09 の受入基準と無関係な範囲が増える

## 影響

### ポジティブ

- 候補を保存しない方針が一貫する。探索結果の寿命は「画面に出ているあいだ」だけになる
- 出ない便の旅程が予約に入らない。しかも気づくのが確定の瞬間であり、出港予定日ではない

### ネガティブ

- **リクエストが大きくなる。** 積み替え 2 回で 3 区間、1 区間あたり 5 項目である。実用上の問題は無いが、ID 参照より冗長であることは記録しておく
- **確定のたびに routingms への呼び出しが増える。** 経路設計者の操作 1 回につき 1 回であり、頻度は低い
- **routingms が落ちていると確定できない。** 候補の算出も同じく落ちているため、業務としては同時に止まる。個別に縮退させる価値は無い
- **イベントを出さないため、追跡側は経路が決まったことを知らない。** IT6 まで、追跡番号の発行は経路の確定と連動しない

## コンプライアンス

**決定の数だけ検査を用意する。**

| 決定 | 検査 |
| :--- | :--- |
| 1. 中身を丸ごと受け取る | 区間の並びを送って旅程が保存されることを API のテストで固定する。**地点名はサーバがマスタから引く**ことを、リクエストに名称を含めない形で確かめる |
| 2. 確定時に成立を再検証する | **航海を消してから確定を試すと 409 になる**ことを固定し、再検証を外すと赤になることを確認する |
| 3. イベントを発行しない | メッセージ基盤の API を bookingms が**使っていない**ことを、アーキテクチャの検査（ArchUnit）で確かめる。依存は既に入っているため、検査できるのは使用のみである。IT6 で発行を足すときに、この検査を同じ変更で外す |

## 後日談（IT5 のクローズ）

レビューで 2 点が分かり、IT6 の kind 往復（タスク 0.1）でもう 1 点が分かった。

1. **接続先の既定値が bookingms 自身（8082）を指しており、上書きがリポジトリのどこにも無かった。** どの環境でも経路の確定だけが必ず失敗する状態だった。ACL の単体テストは別の URL で組み立てるため判別しない。既定値を直し、デプロイの設定にも配線した
2. **タイムアウトを置いていなかった。** 本 ADR のネガティブは「routingms が落ちていると確定できない」と書いたが、**「落ちている」と「遅い」は別の障害**である。応答が返らない状態では確定 1 件ごとにスレッドが埋まり、経路と無関係な予約一覧や荷主登録まで巻き込んで止まる。接続 2 秒・読み取り 5 秒を置いた。**再送はしない**（遅い相手に送り直すと詰まりが増える）

3. **サービス間の呼び出しに名乗りが無く、確定の瞬間だけ 403 になった。** 本 ADR は「サービス間の信頼はネットワーク境界（Gateway より内側）で担保する」として利用者ヘッダを伝播しない方針を採ったが、**相手が [ADR-007] のフィルタで利用者ヘッダを必須にしていること**と、`/api/v1/routes` が `ROLE_ROUTING` を要求していることを見落としていた。両側のテストが緑のまま、kind の統合環境で経路を確定した瞬間にだけ失敗した（コンシューマ側はスタブ相手、プロバイダ側の契約テストは**フィルタを通さないうえテスト自身が別の資格情報を書いていた**ため、どちらも判別しなかった）

   **決定を次のように補う。** ACL は呼び出し元の利用者ではなく**システム自身**（`system:bookingms`）を名乗る。ロールは付けない（付けると、bookingms の中で完結する再検証が呼び出し元のロールに依存する）。routingms は経路候補の参照に限り、**名簿に挙げた既知のサービス主体**を経路設計者と同じく通す。名簿に無い主体は従来どおり 403 で断る。この入口は参照のみで副作用が無い。**書き込みを伴う操作を同じ検査で守ってはいけない**

   | 決定 | 検査 |
   | :--- | :--- |
   | ACL はシステム自身を名乗り、ロールは付けない | コンシューマ側の契約テストで、利用者 ID ヘッダの値とロールヘッダの不在を固定する |
   | 既知のサービスは通す | プロバイダ側の契約テストを **[ADR-007] のフィルタを通したうえで**、コンシューマが実際に名乗る主体で流す |
   | 名簿に無い主体は通さない | 別のサービス名を名乗った要求が 403 になることを固定する（「`system:` で始まれば通す」形にすると、載せ忘れた主体ほど素通りする） |
   | 名乗らない要求は断る | ヘッダ無しの要求が 401 になることを固定する（これが無いと、フィルタを外しても緑のままになる） |

   接続先の環境変数（`APP_ROUTING_SERVICE_BASE_URL`）も、Heroku 側だけに配線し **kind の Kustomize に入れ忘れていた**。1 の直しが片側だけだったことになる。

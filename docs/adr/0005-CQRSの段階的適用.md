# ADR-0005: CQRS の段階的適用

コマンドとクエリをサービス層で分離する軽量な CQRS（単一データベース・単一スキーマ）を採用し、読み取り専用データベースやイベントソーシングは導入しない。将来の負荷増大時に段階的に強化する。

日付: 2026-07-08

## ステータス

2026-07-08 承認されました

## コンテキスト

設計レビュー（2026-07-04・指摘 #23）で、CQRS（コマンドクエリ責務分離）をどの深度で適用するかを ADR として明文化するよう求められた。architecture_backend.md は Booking / Tracking の読み書き負荷特性の違いに対応するため CQRS を採用する方針を示しているが、適用範囲（サービス分離のみか、読み書きデータベース分離やイベントソーシングまで踏み込むか）が未確定であった。

CQRS には段階がある。

| 段階 | 内容 | コスト |
| :--- | :--- | :--- |
| 1. サービス分離 | 同一 DB でコマンド／クエリのサービス・モデルを分離 | 低 |
| 2. 読み取りモデル分離 | クエリ専用のリードモデル（非正規化ビュー／別テーブル）を持つ | 中 |
| 3. 読み書き DB 分離 | 書き込み DB と読み取り DB を物理分離し同期する | 高 |
| 4. イベントソーシング | 状態を導出せずイベント列を真実源とする | 最高 |

本システムは業務系 Web アプリで画面数が限定的であり、初期フェーズでは段階 3・4 の運用コストに見合う負荷はない。ADR-0001（Dapper 集約永続化）・ADR-0002（UoW + post-commit イベント）で書き込み側の基盤は確立済みである。

## 決定

**段階 1（サービス分離）を採用する**。読み取りモデル分離（段階 2）は必要になったコンテキストで局所的に導入し、段階 3・4 は当面採用しない。

1. **コマンド側**: ドメインモデル（集約）を通じて状態変更する。不変条件の検証後、Dapper リポジトリ（手書き SQL）で永続化し、UoW のコミット後にドメインイベントを発行する（ADR-0001/0002）。
   - 命名: `<動詞><集約>CommandService`（例: `RegisterShipperCommandService`・`CreateEstimateCommandService`）
2. **クエリ側**: 集約を経由せず、クエリサービスが Dapper で SQL を発行し画面表示用 DTO へ直接射影する。ドメインモデルを通さない。
   - 命名: `Find<集約>QueryService`（例: `FindShipperQueryService`・`FindEstimateQueryService`）、DTO は `<集約>ListItem` / `<集約>Detail`
3. **データベースは単一・単一スキーマ**を共有する。読み取り専用 DB・マテリアライズドビュー・イベントストアは導入しない。
4. **段階的強化のトリガー**: 特定コンテキスト（想定は Tracking の 30 秒ポーリング・Booking の一覧）でクエリ性能が SLA を満たさなくなった時点で、そのコンテキストに限り段階 2（リードモデル）を導入する。段階 3・4 への移行が必要になった場合は本 ADR を置換する新 ADR で判断する。

IT1（Shipper・Estimation）で本方式を参照実装として確立済みである。

### 代替案

| 選択肢 | 却下理由 |
| :--- | :--- |
| CQRS を採用しない（単一サービスで読み書き） | 読み取り最適化（JOIN を含む DTO 直接射影）とドメイン整合の責務が混在し、Tracking の読み取り負荷に対応しづらい |
| 初期からイベントソーシング（段階 4） | 運用・学習コストが要件に見合わない。ADR-0002 でも Transactional Outbox は将来移行としている |

## 影響

### ポジティブ

- コマンド（整合性重視）とクエリ（表示最適化）の責務が明確に分離される
- 読み取りは集約再構築のオーバーヘッドなく DTO へ直接射影でき高速
- 追加インフラ（別 DB・イベントストア）不要で運用がシンプル

### ネガティブ

- コマンド側とクエリ側で類似のマッピングが二重に存在しうる（許容する）
- 単一 DB のため、極端な読み取り負荷にはスケール限界がある（段階 2 以降で対応）

## コンプライアンス

- コマンドサービスはリポジトリ + UoW を経由し、クエリサービスは集約を参照しないことをコードレビューで確認する
- ArchUnitNET でアプリケーション層がインフラ層をポート経由でのみ参照する規約（ADR 既定）を継続検証する

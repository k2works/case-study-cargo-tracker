# ADR-0003: 開発 SQLite / 本番 PostgreSQL の二方言運用

開発環境は SQLite、ステージング・本番・テストは PostgreSQL とする二方言構成を採用し、方言差異の混入を規約とテストで抑止する。

日付: 2026-07-04

## ステータス

2026-07-04 承認されました

## コンテキスト

開発環境の DB には SQLite（ファイルベース・セットアップ不要）を使用する方針が決定している。一方、データアクセスは Dapper の手書き SQL であり、設計レビュー（2026-07-04）で実行時 SQL に PostgreSQL 方言（`NOW()`、`RETURNING id`）が既に漏れていること、DbUp のプロバイダ別スクリプトはマイグレーションしか吸収できないことが指摘された。アーキテクトからは「開発も PostgreSQL に統一する A 案が最も安全」との意見があった。

検討した選択肢:

| 選択肢 | メリット | デメリット |
| :--- | :--- | :--- |
| A. 開発も PostgreSQL に統一 | 方言問題が消滅。開発 = CI = 本番で完全一致 | Docker 常時起動が必要。SQLite の軽量さを失う |
| B. 二方言を維持し、実行時 SQL から方言を排除 | 開発マシンで軽量・セットアップ不要 | 方言排除規約の徹底が必要。DbUp スクリプト 2 本保守 |

## 決定

**B 案（二方言維持）を採用する**。開発体験の軽さを優先するプロジェクト方針による。ただし以下の緩和策を必須とする。

1. **実行時 SQL の方言禁止規約**: リポジトリ・クエリサービスの SQL では以下を禁止する。
   - `NOW()` → 禁止。タイムスタンプは C# 側で `DateTimeOffset.UtcNow` を生成しパラメータで渡す
   - `RETURNING` → 禁止。採番が必要な INSERT は `SELECT` で取り直すか、アプリ側で ID（業務キー/GUID）を生成して渡す
   - `ILIKE`・配列型・JSONB・`ON CONFLICT` 等の PostgreSQL 固有構文 → 禁止
2. **方言検出テスト**: リポジトリアセンブリ内の SQL 文字列（`const string sql` 等）を走査し、禁止パターン（`NOW()` / `RETURNING` / `ILIKE` / `::` キャスト等）を検出する単体テストを CI に組み込む
3. **DDL はプロバイダ別に管理**: DbUp スクリプトは `Scripts/postgresql/` と `Scripts/sqlite/` を同一バージョン番号で並行管理する。PR レビューで両ディレクトリの同期を確認し、CI で「両ディレクトリのスクリプト本数・バージョン番号が一致すること」を検証する
4. **テストの正は PostgreSQL**: データアクセスの検証は Testcontainers（実 PostgreSQL）のみを根拠とする。SQLite での動作は開発時の利便性であり品質保証には使わない（test_strategy.md）
5. **既存設計の修正**: data-model.md のリポジトリ実装例から `NOW()` / `RETURNING` を排除し、本 ADR の規約に合わせる

## 影響

- 開発者はローカルで軽量に動作確認でき、Docker は本番相当検証（Docker Compose の PostgreSQL）と統合テスト実行時のみ必要
- 「ローカルで通ったが CI（PostgreSQL）で落ちる」リスクは残る。方言検出テストと Testcontainers の PR 時実行で早期検出する
- スクリプト二重管理のコストが継続的に発生する。ドリフトが頻発する場合は A 案（PostgreSQL 統一）への切替を再検討する

## コンプライアンス

- CI: 方言検出テスト + スクリプト同期検証 + Testcontainers 統合テストの 3 点で継続的に検証する
- 四半期ごとに二重管理コスト（スクリプト差分起因の障害・手戻り件数）をふりかえり、A 案への移行判断の材料とする

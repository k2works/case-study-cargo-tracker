# ADR-017: 料金の状態を支払いの状態と分ける

精算書に `charge_status`（DRAFT / CONFIRMED）を持たせ、既存の `payment_status`（PENDING / CONFIRMED / OVERDUE / REFUNDED）と**別の軸**として扱う。

日付: 2026-08-10

## ステータス

承認済み

## コンテキスト

US21 は料金の扱いを「算出 → 確認 → 確定」と定め、確定後は「確定」状態で登録されると書いている。

一方 `domain-model.md` の `Invoice` が持つ状態は `PaymentStatus` だけである。これは**支払いの状態**であり、料金そのものの状態ではない。

`PaymentStatus` を流用して料金の確定を表そうとすると、次の 2 つが同じ `PENDING` になる。

- 料金を確定したが、まだ入金されていない
- 料金がまだ確定していない（経理担当者が確認中）

US23 の受入基準は「支払い期限超過時、経理担当者に未払い通知が送信される」と定めている。**督促の対象は前者だけである。** 後者は請求書をまだ出していないのだから、督促しようがない。

## 決定

**料金の状態（`ChargeStatus`）を別に持つ。**

| 状態 | 意味 |
| :--- | :--- |
| `DRAFT` | 下書き。経理担当者が確認している最中である |
| `CONFIRMED` | 確定。**この時点で金額は動かない** |

`payment_status` はそのまま支払いの軸として残す。精算書の発行と入金の確認は US23（IT14）の領分である。

## 何がどこで守るか

| 守るもの | 守り手 |
| :--- | :--- |
| `ChargeStatus` が 2 値のいずれか | **DB の CHECK 制約**（`chk_invoice_charge_status`）＋ `InvoiceTest` |
| `CONFIRMED` の後に金額が動かない | **ドメイン**（`Invoice` が確定後の変更を拒む）＋ `InvoiceTest` |
| 料金の軸と支払いの軸を混ぜない | **DB のスキーマ**（`charge_status` と `payment_status` が別列）＋ `ChargeCalculationScenarioTest` |

## 根拠

- **督促の対象を選べる。** 「確定済みかつ支払期限超過」を SQL で絞れる
- **確定を意味のある操作にできる。** 確定後は `adjust` も UPDATE も拒める（ドメインと SQL の両方で守る）
- **状態を 1 つにまとめると、後から分けるほうが高くつく。** 既存の行がどちらの意味だったのかを、後からは判別できない

## 影響

### よくなること

- 請求対象一覧（未確定）と督促対象一覧（確定済み・期限超過）を別々に引ける
- 「確定済みは更新できない」を SQL の `WHERE charge_status = 'DRAFT'` で守れる。集約を通らない経路が生まれても金額が動かない

### 気をつけること

- **状態が 2 つになる。** 画面には「料金: 確定 / 支払い: 未入金」のように両方を出す必要がある。片方だけを出すと、経理担当者は残りの軸を推測することになる
- 遷移の組み合わせが増える。**`payment_status` が動くのは `charge_status = CONFIRMED` の後だけである**（US23 で実装する際にこの前提を守る）

## 代替案

| 案 | 却下の理由 |
| :--- | :--- |
| `PaymentStatus` に `DRAFT` を足す | 「料金は確定したが未入金」と「料金が未確定」を区別できるが、**支払いの状態に料金の話が混ざる**。`REFUNDED`（返金済み）と `DRAFT`（未確定）が同じ列に並ぶのは、読む人に 2 つの軸を暗記させる |
| 確定を `issued_at` の有無で表す | 発行日時は US23（精算書の発行）の概念であり、料金の確定とは時点が違う。**別の目的の列に意味を兼ねさせない** |
| 状態を持たず、確定を別テーブルの記録で表す | 1 件の精算書に対して 1 つの状態しか持たないのに、テーブルを分けるのは構造がデータより重い |

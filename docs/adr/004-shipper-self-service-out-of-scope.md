# ADR-004: 荷主セルフサービス機能を Phase 1 スコープ外とする

荷主（顧客）が Web ポータルから直接予約・追跡・問い合わせを行う「セルフサービス機能」は Phase 1 スコープ外とし、すべての操作は営業担当者・追跡管理者が代理で行う業務フローとして実装する。

日付: 2026-03-31

## ステータス

承認済み

## コンテキスト

本システムは国際貨物輸送管理のケーススタディであり、Jakarta EE 実装（`cargotracker`）の Spring Boot 移植を目的としている。エンドユーザーとしては以下の 2 種類が考えられる。

**社内ユーザー**（業務担当者）:

- 営業担当者: 貨物予約・ルート設計依頼
- 経路設計者: 最適ルートの設計・割り当て
- 追跡管理者: 追跡番号発行・ステータス更新
- 荷役作業員: 荷役イベント登録（バーコードスキャン）
- 経理担当者: 請求書発行・精算処理

**外部ユーザー**（顧客）:

- 荷主（Shipper）: 貨物の依頼元。予約・ステータス確認・請求書受け取り
- 荷受人（Consignee）: 配送先。到着通知・受け取り確認

**荷主セルフサービスとして考えられる機能**:

| 機能 | 説明 | 影響する画面・機能 |
|---|---|---|
| 荷主登録ポータル | 荷主が自分でアカウントを作成する | 荷主登録画面（新規追加） |
| 見積依頼フォーム | 荷主が見積もりを直接依頼する | 見積依頼画面（新規追加） |
| 予約ステータス確認 | 荷主が予約状況を確認する | 貨物詳細画面への荷主アクセス |
| 追跡番号照会（公開） | 荷主・荷受人が追跡番号で現在地を確認 | 公開追跡 API（部分的に対応済み） |
| 請求書ダウンロード | 荷主が請求書を直接ダウンロードする | 請求書発行画面への荷主アクセス |

**Phase 1 でのスコープ判断の背景**:

- **ケーススタディの目的**: 本プロジェクトは DDD + ヘキサゴナル + CQRS の実装パターン習得が主目的であり、荷主向け外部ポータルの追加はスコープを大幅に拡大する
- **認証・認可の複雑化**: 外部荷主のセルフ登録には、内部 RBAC（ROLE_SALES 等）とは別の認証フロー（メール確認、パスワードリセット等）が必要
- **マルチテナント化の課題**: 荷主ごとのデータアクセス制御（自分の貨物のみ閲覧可能）は Spring Security の追加設定が必要
- **UI/UX の追加工数**: 業務担当者向け UI と顧客向け UI は要件・デザインが異なり、別画面として設計・実装する必要がある

## 決定

**Phase 1 では荷主セルフサービス機能をスコープ外とし、以下の方針で代替実装する。**

### Phase 1 の代替実装

| 荷主の操作ニーズ | Phase 1 の対応 |
|---|---|
| 予約を依頼したい | 営業担当者が電話・メールを受けて代理で予約登録 |
| ステータスを確認したい | 追跡番号を使った公開追跡 API（認証不要・読み取り専用） |
| 見積もりを依頼したい | 営業担当者経由（システム外の業務フロー） |
| 請求書を受け取りたい | 経理担当者がシステムから印刷・PDF 出力して郵送・メール送付 |

### データモデルへの影響

`shipper` テーブルはシステムに登録された荷主マスタとして実装済み（ADR の影響外）。荷主のシステムログインは Phase 1 では不要なため、`users` テーブルとの外部キーは設けない。

```sql
-- Phase 1: shipper テーブルは管理データとして存在するが、ログイン機能なし
CREATE TABLE shipper (
    id         BIGSERIAL PRIMARY KEY,
    name       VARCHAR(200) NOT NULL,
    email      VARCHAR(255) UNIQUE NOT NULL,
    phone      VARCHAR(50),
    created_at TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
-- users テーブルとの外部キーは Phase 2 以降に追加
```

### Phase 2 以降の実装計画

荷主セルフサービスを実装する場合は以下の追加設計が必要。

1. **認証**: 荷主向けの `ROLE_SHIPPER` ロール追加 + メール確認フロー
2. **認可**: Spring Security の `@PreAuthorize("hasRole('SHIPPER') and #shipperId == authentication.principal.shipperId")` によるデータフィルタリング
3. **外部向け API**: 認証付き RESTful API（内部業務系と分離）
4. **荷主ポータル UI**: 業務担当者 UI とは別の Thymeleaf テンプレート群

### 変更箇所

| ファイル | 内容 |
|---|---|
| `docs/design/ui_design.md` | 荷主ポータル画面（見積依頼、自己登録）を Phase 2 として注記 |
| `docs/requirements/user_story.md` | 荷主セルフサービス関連ストーリーを Phase 2 に移動 |
| `shipper` テーブル | `users` テーブルとの外部キーなし（Phase 2 で追加） |

### 代替案

| 代替案 | 却下理由 |
|---|---|
| **Phase 1 から荷主セルフサービスを実装** | ケーススタディの目的（DDD パターン習得）に対してスコープが過大。荷主認証・認可・UI の追加工数が DDD コア実装の工数を上回る |
| **追跡番号照会のみ公開** | 追跡 API（`GET /tracking/{trackingId}`）は認証不要の公開 API として Phase 1 でも実装する。これはセルフサービスではなく「公開情報の提供」として扱う |
| **外部ポータルを別サービスとして分離** | Phase 1 のケーススタディでは単一 Spring Boot アプリとして実装する（マイクロサービス化は Phase 3 以降の検討） |

## 影響

### ポジティブ

- Phase 1 の実装スコープを絞り、DDD + ヘキサゴナル + CQRS のコアパターン習得に集中できる
- Spring Security の設計が単純化される（内部 RBAC のみ）
- 荷主向けの追加 UI・API が不要となり、開発・テスト工数が削減される

### ネガティブ

- 荷主が直接システムにアクセスできないため、営業担当者への業務集中が生じる
- Phase 2 で荷主セルフサービスを追加する際、`shipper` テーブルと `users` テーブルの関連付け・既存データのマイグレーションが必要
- 追跡番号照会（公開 API）は Phase 1 で実装するため、認証なし API のセキュリティ設計（レートリミット等）は Phase 1 から考慮すること

## コンプライアンス

- `users` / `user_roles` テーブルに `ROLE_SHIPPER` が含まれていないこと
- 業務担当者向け画面に荷主ログイン機能がないこと
- 追跡 API（`GET /tracking/{trackingId}`）が認証不要で動作すること
- UI 設計ドキュメントに「荷主セルフサービスは Phase 2」の注記があること

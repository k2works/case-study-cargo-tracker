# ADR-003: コマンドの冪等性と識別子

コマンドは冪等性キー + PostgreSQL の表で二重処理を防ぎ、集約 ID は ULID をクライアント／ゲートウェイが生成し、業務番号は集約 ID と分ける。

## コンテキスト

- 参照実装は再送すると別の ID で重複作成される（ユースケース内で ID を採番するため）。
- HTTP の再送や弱い回線（荷役作業員）で、予約・荷役記録が二重に登録されてはならない。
- 要件に一意性がある（航海番号 US24、追跡番号 US14・US18）。イベントソーシングでは複数集約にまたがる一意制約を単純には書けない。

## 決定

**クライアントが送る冪等性キー**を、コマンドの先頭で確かめる。同じキーの再送には最初の結果を返す。キーと結果は PostgreSQL の表（`platform.idempotency_key`）に保存し、保持は 7 日とする（NFR-D02）。**集約を新規作成するコマンドは、クライアントまたはゲートウェイが ULID の集約 ID を生成して渡す**。人が読む業務番号（予約番号・見積番号・請求番号）は集約 ID と分ける。航海番号は永続化 ID の元にし、追跡番号は追跡情報の永続化 ID そのものとして推測困難な乱数部（60 ビット以上。NFR-S30）を持つ形式にする。

### 変更箇所

- 同じキーで内容が違う要求は拒む（`request_hash`）。
- 追跡番号の形式と桁数は R-02 の承認時に確定する。
- 予約番号・見積番号・請求番号の採番は、採番集約か DB のシーケンスのいずれかを、ドメインモデルの Bolt 内で決める。

### 代替案

- **クライアント生成の集約 ID のみ**：新規作成の再送は防げるが、更新系コマンドの再送は防げない
- **サーバーがユースケース内で ID を採番（参照実装）**：再送で別集約ができるため却下

## 影響

### ポジティブ

- 再送・二重押下で二重登録が起きない。
- 集約自身が 2 回目の作成を拒める。

### ネガティブ

- 冪等性キーの表が RDS に増え、保持期間後の削除が要る。
- 復元（バックアップから）でキーを失うと、直後の再送が二重登録になりうる（OPR-B12）。

## コンプライアンス

- 二重送信・同じキーで内容違いの要求の検査（テスト戦略 L3・L5）。
- フロントエンドの Mutation は必ずキーを付ける（lint または共通フック。FE 4.2）。

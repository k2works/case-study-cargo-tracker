# ADR-022: サービス間のドメインイベント契約

bookingms から trackingms へ非同期でイベントを渡す（US14）ときに、何を発行するか・いつ発行するか・何を載せるか・受け取れなかったものをどうするかを決める。

日付: 2026-08-22

## ステータス

承認済み

## コンテキスト

IT6 で初めて**サービス間の非同期連携**を通す。これまで越境は REST 1 本（[ADR-019](019-route-assignment-api.md)）だけだった。

依存（`spring-boot-starter-amqp`）と RabbitMQ の接続設定はすでに入っているが、**発行するコードは 1 行も無い**（[ADR-019](019-route-assignment-api.md) 決定 3 で「IT5 では書かない」と決めた）。`ArchitectureTest` の `noEventPublishingRule` が「メッセージ基盤の API を使っていない」ことを検査している。

決めることが 6 つある。イベントは**受け手が読んだあと取り消せない**ため、あとで直すのが REST より高くつく。

- どのイベントを、いつ発行するか
- ペイロードに何を載せるか（ID だけか、内容も載せるか）
- スキーマの後方互換をどう保つか
- 受け取れなかったイベントをどうするか
- 順序保証を前提にするか
- コミットとの前後関係

加えて、**設計と計画が食い違っている**。`architecture_backend.md` の一覧と `domain-model.md` のシーケンスは `CargoBookedEvent` を**経路割り当ての直後**に発行し、trackingms が追跡番号を割り当てる形で描いている。一方 [ADR-021](021-shipper-notification-and-confirmation-transitions.md) は**採番するのは bookingms**と決めた。先に寄せる。

## 決定

### 1. `CargoBookedEvent` を廃止し、`TrackingNumberIssuedEvent` を発行する

一覧にある `CargoBookedEvent`（用途: 追跡番号の割り当てトリガー）は、**trackingms が採番する前提の設計**である。[ADR-021](021-shipper-notification-and-confirmation-transitions.md) で採番を bookingms に置いた以上、「割り当てを依頼する」イベントは要らない。

trackingms が要るのは「**この番号で追跡を始めよ**」であり、それが起きるのは追跡番号を発行したとき（US14）である。予約したときではない。予約の時点では番号が無く、追跡を作れない。

したがって `TrackingNumberIssuedEvent` を発行する。チャネル名は `cargoBookingChannel` を引き継ぐ（既存の設定を変えない）。

> **`CargoRoutedEvent`（旅程の同期）は IT6 では発行しない。** 追跡を作るのに旅程は要らず、旅程が要るのは荷役の照合（US15・IT7）である。**発行しないことをここに明記する**——書かないと「実装漏れ」と読まれる。[ADR-019](019-route-assignment-api.md) 決定 3 の検査は、この 1 種類の発行を許す形に絞る（丸ごと消さない）。

### 2. ペイロードには「相手が自分の集約を作るのに要るもの」を載せる

載せるのは `trackingNumber` / `bookingId` / `originUnLocode` / `destinationUnLocode` / `arrivalDeadline` / `occurredAt` である。

**ID だけにしない。** ID だけだと trackingms が bookingms へ問い合わせることになり、非同期にした意味が消える（同期の依存が戻り、bookingms が落ちていると追跡が作れない）。

**予約の全部も載せない。** 載せるほど受け手が Booking の言葉に縛られ、こちらの項目を変えるたびに向こうが壊れる。載せるのは「追跡を始めるのに要るもの」だけである。

### 3. 後方互換は「項目の追加だけ」

項目の削除・改名・意味の変更はしない。受け手は**知らない項目を無視する**（[ADR-019](019-route-assignment-api.md) の REST 契約と同じ）。

破壊的な変更が要るときは、**新しいイベント型を足して両方を出し**、受け手が移ってから古いほうを止める。イベントは受け手が読んだあと取り消せないので、REST のように「両側を同じ変更で直す」ことができない。

### 4. 受け取れなかったイベントは捨てず、デッドレターへ送る

再試行は 3 回、指数バックオフ（1 秒 → 2 秒 → 4 秒）。それでも駄目ならデッドレターキューへ送る。

捨ててはいけない。追跡が作られないと、**荷主は番号を渡されたのに追えない**。しかも bookingms 側は発行に成功しているので、どこにも異常が残らない。

**この経路を実際に通す**（成功基準 3）。「デッドレターの設定を書いた」ことと「落ちたイベントがそこへ届く」ことは別である（[IT5 の学び](../development/retrospective-5.md)と同じ形——安全装置は破るテストで固定する）。

### 5. 順序保証は前提にしない。受け手は冪等にする

IT6 は 1 種類しか出さないので順序は問題にならない。だが前提にすると、あとで複数のイベントを足したときに黙って崩れる。

受け手は**同じ追跡番号で 2 回来ても 1 件**にする。再試行がある以上、二重配送は起こる。

### 6. コミットしたあとに発行する

コミット前に出すと、**ロールバックした予約のイベントが飛ぶ**。存在しない予約の追跡ができ、荷主は追えるのに貨物が無い状態になる。

実装は**アダプタ側でコミット後に遅らせる**（`TransactionSynchronizationManager`）。ユースケースに「コミット後に呼べ」と作法を課すと、入口が増えた数だけ破られる。トランザクションの境目はインフラの関心である。

> **境目はユースケースに置く。** 置かないと、保存のトランザクションは `save` が戻った時点でコミット済みになり、発行の時点で同期が解除されている。つまり**この機構が一度も働かない**——結果の順序が正しいのは「たまたま save のあとに呼んでいる」からであり、決定が守られている根拠にはならない（IT6 のクローズレビューで見つけた）。

> **逆に、コミットは成功したが発行に失敗する窓は残る。** Transactional Outbox で塞げるが、IT6 では入れない。**残っていることをここに明記する**——書かないと、塞いだつもりで運用に入る。塞ぐのは、発行が増えて取りこぼしが見えるようになってからでよい。

### 7. 採番は bookingms が行う

[ADR-021](021-shipper-notification-and-confirmation-transitions.md) の決定に従う。イベントは**採番済みの番号を運ぶ**のであって、採番を依頼するのではない。

## 代替案

- **`CargoBookedEvent` を予約時に出し、trackingms が採番する**（設計どおり）: 一覧を変えずに済む。しかし採番が 2 つのサービスに散り、番号の形式を守る場所も 2 つになる。[ADR-011](011-booking-id-numbering.md) が予約番号で避けたのと同じ問題である
- **ペイロードを ID だけにする**: 契約が小さく、変更に強い。しかし受け手が同期で問い合わせることになり、非同期にした意味が消える
- **同期の REST で追跡を作る**: 実装が単純で、失敗が即座に分かる。しかし bookingms の確定処理が trackingms の可用性に縛られる。追跡は「あとから作られてよい」ものであり、予約の確定を止める理由が無い
- **失敗したイベントを再試行だけで済ませる（デッドレターを持たない）**: 設定が減る。しかし 3 回失敗したイベントは消え、どこにも残らない

## 影響

### ポジティブ

- 予約の確定が trackingms の可用性に縛られない
- 受け取れなかったイベントが残り、あとから直せる
- 採番の場所が 1 つに保たれる

### ネガティブ

- **設計の一覧から `CargoBookedEvent` が消える。** take-3 から引き継いだ名前であり、他の資料を読んだ人は探すことになる。一覧に「廃止」の行を残す
- **結果整合になる。** 追跡番号を発行した直後に追跡を照会すると、まだ無いことがある。US18（照会画面・IT8）までは画面から見えないため実害は無いが、IT8 で「作成中」の見せ方が要る
- **コミット後・発行前に落ちるとイベントが失われる。** Outbox を入れるまで残る窓である
- **デッドレターに溜まったイベントを戻す運用が要る。** IT6 では手動（運用手順書に載せる）

## コンプライアンス

**決定の数だけ検査を用意する。**

| 決定 | 検査 |
| :--- | :--- |
| 1. `TrackingNumberIssuedEvent` を発行する | 追跡番号を発行したときにだけ発行されることを固定する。**確定しただけでは発行されない**ことも対で確かめる（「出ること」だけを見ると、いつでも出す実装でも緑になる） |
| 2. ペイロードの項目 | コンシューマ（trackingms）が読む項目を**DTO の要素から導いて**突き合わせる（[IT6 タスク 0.3](../development/iteration_plan-6.md) で REST 契約に入れた形）。プロバイダ側にも同じ名簿を写す |
| 3. 項目の追加だけ | 受け手が**知らない項目を無視する**ことを固定する（余分な項目を含む JSON を流して壊れないこと） |
| 4. デッドレターへ送る | **受け手が例外を投げるイベントがデッドレターへ届く**ことを、実 RabbitMQ（Testcontainers）で確かめる。設定の存在ではなく到達を見る |
| 5. 冪等 | 同じイベントを 2 回流して追跡が 1 件であることを確かめる |
| 6. コミット後に発行 | **ロールバックしたトランザクションのイベントが飛ばない**ことをアダプタの単体テストで固定する。あわせて**本番の呼び出し形で同期が有効である**ことを実 DB のテストで固定する（境目が無ければ機構は素通りするため、片方だけでは守れない） |
| 7. 採番は bookingms | イベントのペイロードに採番済みの番号が入っていることを確かめる（空で送って相手に採番させていない） |

## 後日談（IT6 のクローズレビュー）

3 点が分かった。いずれも**全テストが緑のまま守られていなかった**ものである。

1. **決定 6 の機構が本番で一度も働いていなかった。** `@Transactional` はリポジトリの `save` にしか無く、発行の時点では同期が解除されていた。境目をユースケースへ引き上げ、「発行の時点でトランザクションが生きている」ことを実 DB のテストで固定した（外すと赤になることを確認）。

2. **往復テストがプロデューサの送る形を流していなかった。** 受け皿クラスをそのまま送っていたため、`__TypeId__` には**受け手のクラスパスに必ず存在する名前**が載っていた。本番で載るのは bookingms の型名であり、この違いはワイヤ上でしか出ない。JSON と `__TypeId__` を本番と同じ形で組み立てて流す形に直した。**相手の型はこちらのクラスパスに無くても読める**（`@RabbitListener` が推論した型を優先する）ことが、ACL の成り立つ根拠である。

3. **コンシューマ側の「知らない項目を無視する」が、テスト自身が寛容に設定した ObjectMapper に対する検査だった。** 本番の変換器を通す形に直した。プロデューサ側の契約テストが戒めていた罠を、コンシューマ側だけが踏んでいた。

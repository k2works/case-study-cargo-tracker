# ADR-0001: モジュール構成は垂直スライス（コンテキストファースト）を採用

名前空間・ファイル構成を境界づけられたコンテキスト単位の垂直スライスで編成する決定

日付: 2026-07-06

## ステータス

2026-07-06 承認済み

## コンテキスト

Cargo Tracker のバックエンドは F# で実装し、Booking・Routing・Tracking・Handling などの複数の境界づけられたコンテキスト（BC）と、Domain・Application・Infrastructure のレイヤー構造を持ちます。名前空間とプロジェクト内のファイル配置には次の 2 案があります。

- **案 A（垂直スライス / コンテキストファースト）**: `CargoTracker.{Context}.{Layer}`（例: `CargoTracker.Booking.Domain`）
- **案 B（レイヤーファースト）**: `CargoTracker.{Layer}.{Context}`（例: `CargoTracker.Domain.Booking`）

F# は .fsproj に記述されたファイル順で上から順にコンパイルされ、後方のファイルを前方から参照できないという特性があります。この特性をアーキテクチャ制約の静的な担保に活用できるかどうかが判断のポイントです。

## 決定

**案 A（垂直スライス / コンテキストファースト）を採用します。** 名前空間は `CargoTracker.{Context}.{Layer}` とし、レイヤーファースト（`CargoTracker.Domain.Booking`）は不採用とします。

根拠は以下のとおりです。

1. **F# のファイル順コンパイルによる依存方向の静的保証**: .fsproj 内をコンテキスト単位でまとめ、各コンテキスト内で Domain → Application → Infrastructure の順にファイルを並べることで、「Domain は Application を参照できない」「Application は Infrastructure を参照できない」というレイヤー依存方向がコンパイラレベルで保証されます。レイヤーファーストではコンテキスト間の依存がファイル順に現れず、この効果が得られません。
2. **境界づけられたコンテキストの独立性がファイル構成に現れる**: あるコンテキストの変更が他コンテキストに波及しないことがディレクトリ・ファイル順の構造から一目で分かり、将来のコンテキスト分離（別プロジェクト化・サービス分割）が容易になります。
3. **変更の局所性**: 機能追加はほぼ単一コンテキストのスライス内で完結するため、変更を楽に安全にできます。

## 影響

- **.fsproj のファイル順規約**: 「コンテキスト単位でまとめる」「コンテキスト内は Domain → Application → Infrastructure の順」「Shared（コンテキスト横断の共有型）は全コンテキストより前に置く」をファイル順規約として定めます。
- **ArchUnitNET ルールとの二重防御**: ファイル順による静的保証に加え、ArchUnitNET で「Domain 層は Infrastructure 層に依存しない」「BC 間は Shared 経由以外で参照しない」等のルールをテストとして記述し、二重防御とします（`docs/design/architecture_backend.md` 参照）。
- コンテキスト間で共有する型は `CargoTracker.Shared` に配置する必要があり、共有型の肥大化には ADR-0002 の Payload 方式で対処します。

## コンプライアンス

- ArchUnitNET によるアーキテクチャテストが CI で常時実行されること。
- コードレビューおよび `sbt`/`dotnet test` 相当のフルテストで .fsproj のファイル順規約違反（コンパイルエラー）が検出されること。

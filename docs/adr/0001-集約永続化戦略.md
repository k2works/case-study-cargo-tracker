# ADR-0001: Dapper による集約永続化戦略

Dapper（手書き SQL）で DDD 集約を永続化・再構築するための実装規約を定める。

日付: 2026-07-04

## ステータス

2026-07-04 承認されました

## コンテキスト

本システムのデータアクセスは Dapper 2.x + 手書き SQL である（tech_stack.md）。EF Core / JPA と異なり変更追跡（Change Tracking）が存在しないため、「集約ルート + 子コレクション」型の集約（`Cargo`↔`Leg`、`Voyage`↔`CarrierMovement`、`TrackingActivity`↔追跡/例外イベント、`Invoice`↔`invoice_line_item`）の保存と再構築をリポジトリが自前で設計する必要がある。設計レビュー（2026-07-04）で、この戦略が未定義のまま実装スケルトンが先行しており、実装者の場当たり判断を招くと指摘された。

## 決定

以下をリポジトリ実装規約とする。

1. **保存単位は集約全体**。リポジトリの公開メソッドは集約ルート単位（`SaveAsync(Cargo)`）とし、子エンティティだけを保存する公開メソッドは作らない。
2. **子コレクションは「全削除 → 再挿入」を既定戦略とする**。`UPDATE` 時は `DELETE FROM leg WHERE cargo_id = @Id` の後に現在のコレクションを一括 `INSERT` する。差分検出は行わない。
   - 根拠: 子コレクションは小規模（Leg は数件〜十数件）であり、差分検出の複雑さに見合わない。監査が必要な履歴系（`tracking_handling_event` 等）は追記専用（INSERT のみ・削除しない）とし、この戦略の対象外とする。
3. **再構築はマルチクエリ + 組み立て**。`QueryMultipleAsync` で集約ルートと子を 2 クエリで取得し、リポジトリ内でコンストラクタ（または再構築用ファクトリ `Cargo.Reconstitute(...)`）に渡して組み立てる。JOIN によるマルチマッピングは行数の重複が発生するため、1:N が 2 段以上ある場合は使用しない。
4. **`Cargo` 集約のリポジトリを参照実装とする**。他コンテキストのリポジトリは `CargoRepository` の構造（SaveAsync / FindByBookingIdAsync / 全削除再挿入 / Reconstitute）を踏襲する。
5. **接続は `IDbConnection`（接続ファクトリ）で注入する**。`NpgsqlConnection` 等の具象型をコンストラクタで受けない（開発環境 SQLite との両立、ADR-0003 参照）。

## 影響

- リポジトリの実装パターンが統一され、レビュー観点が明確になる
- 全削除 → 再挿入のため、子テーブルの `id` は安定しない。子エンティティを外部から参照する場合は業務キーを使う必要がある
- 楽観的ロック（`version` 列）は集約ルート表にのみ付与し、`UPDATE cargo SET ... , version = version + 1 WHERE id = @Id AND version = @ExpectedVersion` で競合を検出する（更新件数 0 なら競合例外）

## コンプライアンス

- 統合テスト（Testcontainers + PostgreSQL）で「保存 → 再構築 → 等価性検証」のラウンドトリップテストを各集約に必須とする（test_strategy.md）
- コードレビューで公開メソッドが集約ルート単位であることを確認する

# ADR-009: BC 間 ACL は同期・同一トランザクションで呼ぶ

境界付けられたコンテキスト間の連携を、ドメインイベントによる結果整合ではなく、ACL ポートの同期呼び出し（同一トランザクション）で行う。

日付: 2026-08-08

## ステータス

承認済み

## コンテキスト

IT6（US13 / US14 / US15）で BC 間 ACL ポートが 4 件になり、**1 つの操作が複数の BC に書き込む形**が実装に現れた。荷役の登録は荷役作業・追跡状態・予約の 3 つを 1 つのトランザクションで書く。

一方 `architecture_backend.md` の「イベント駆動設計」節は、`ApplicationEventPublisher` と `@TransactionalEventListener(AFTER_COMMIT)` による結果整合を実装方針としてコード例つきで規定していた。**実装と設計書で故障モードがまるで違う。**

- 結果整合: 荷役は成功し、追跡の更新は後から起きる（あるいは失敗して起きない）
- 同期・同一トランザクション: 両方成功するか、両方起きないか

この食い違いは IT6 のマルチパースペクティブレビュー（architect M2 / H3）で指摘された。**どちらが正しいかを決めずに実装が先行していた。**

さらに、同期を選ぶ場合には固有の危険がある。**楽観的ロックの失敗を握り潰すと、同期にした利点（片方だけ成功しない）がそのまま失われる。** IT6 のレビューでは実際に 3 か所で戻り値が捨てられていた。

## 決定

**BC 間 ACL は同期・同一トランザクションで呼ぶ。ドメインイベントによる結果整合は採らない。**

判断根拠は次のとおり。

- **片方だけ成功する状態が、この業務にはほぼ存在しない。** 「確定済みなのに追跡番号が無い」「荷役は記録されたのに輸送状態が動いていない」はいずれも業務上あり得ず、それを一時的にでも作ることに利益がない
- **荷役は本システムで最も頻度の高い操作である。** 結果整合を挟むと「登録したのに追跡に出ない」時間が現場に見える。現場はその時間を「壊れている」と受け取る
- 本システムは単一プロセス・単一データベースで動く。**分散していないところに分散システムの機構を持ち込むと、複雑さだけが増える**
- 結果整合が要るのは、BC が別プロセス・別データベースに分かれたときである。そのときは本 ADR を改訂する

### 同期を選ぶ以上、必ず守ること

1. **ACL アダプタは楽観的ロックの失敗を握り潰さない。** 戻り値 `boolean` で「他の更新が先行した」を返す契約であれば、呼び出し元は必ずその値を見る。捨てるなら同期にした意味が無い
2. **書き込みの後に失敗を返す経路は、例外で巻き戻す。** `@Transactional` の中で `return` を返すとコミットされる（Spring がロールバックするのは非検査例外のときだけ）。戻り値でエラーを返す設計と `@Transactional` は相性が悪い
3. **境界を越える値は素の値に限る。** ポートが運ぶ値はポートと同じパッケージに置く（ArchUnit ルール 4 の除外は ACL ポートのパッケージだけであり、そこが唯一の越境点である）

### 変更箇所

- `architecture_backend.md`: 「イベント駆動設計」節を、現状（未採用）と将来の方針に分けて記述する
- `domain-model.md`: BC 間 ACL ポート一覧に、同期・同一トランザクションで呼ぶことを明記する

### 代替案

| 代替案 | 却下理由 |
| :--- | :--- |
| ドメインイベント（AFTER_COMMIT）で結果整合にする | 単一プロセス・単一 DB で、片方だけ成功する状態に利益が無い。最高頻度の操作に最も重い機構を課すことになる |
| BC をまたぐ操作を作らない（1 操作 1 BC に限る） | 荷役の登録は、その性質上「荷役の記録」「輸送状態」「予約の進行」に同時に影響する。業務がまたいでいるものを実装だけで分けることはできない |
| Transactional Outbox パターン | 分散していない現時点では、テーブルと再送機構の運用コストに見合わない。将来 BC が別プロセスに分かれた時点で検討する |

## 影響

### ポジティブ

- 「登録したのに反映されていない」中間状態が構造的に発生しない
- 設計書と実装の故障モードが一致し、次に読む人が存在しない基盤の上に設計を積まなくなる
- 楽観的ロックの扱いが「守るべきこと」として明文化される

### ネガティブ

- **BC 間の結合が強い。** 相手の BC のトランザクションが長引くと、こちらも待つ
- BC を別プロセスに分ける将来の変更コストが上がる。そのときは本 ADR の改訂と、Outbox 等の導入がセットで必要になる
- 1 つのトランザクションが複数の集約を更新する。集約境界の原則からの逸脱であり、**「集約は 1 トランザクション 1 つ」という一般則をこのシステムでは採らない**ことを意味する

## コンプライアンス

- BC 間 ACL の実装（`*Adapter`）で、リポジトリの `boolean` 戻り値を捨てている箇所が無いこと（`grep` で数える）
- `@Transactional` を付けたメソッドで、書き込みの後に戻り値でエラーを返している箇所が無いこと
- ACL ポートが運ぶ値が、ポートと同じパッケージに定義されていること
- `architecture_backend.md` の「イベント駆動設計」節が、未採用であることを明示していること

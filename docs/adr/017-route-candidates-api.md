# ADR-017: 経路候補は複数を推奨順で返し、永続化しない

`GET /api/v1/routes/optimal`（単数の最適経路）を `GET /api/v1/routes`（複数候補）に改める。算出した候補は保存しない。到着期限は日付で受け取り、業務タイムゾーンの当日終わりまでとして扱う。

日付: 2026-08-21

## ステータス

承認済み

## コンテキスト

US08 の受入基準は「経路候補が**推奨順に並べられて**提示される」「経路候補ごとに**所要日数・経由港・費用・航海番号**が表示される」を求める。

しかし設計にある契約は `GET /api/v1/routes/optimal` で、**単数の `TransitPath` を返す形**である。所要日数・費用・経由港のフィールドを持たず、貨物種別のパラメータも無い（危険物・冷凍を運べる船は限られるのに、条件として渡していない）。この契約のままでは受入基準を満たせない。

保存先も決まっていない。`booking_db.route_candidate` は `estimate_id` を必須の外部キーに持ち、見積（US01・IT12）に紐づく候補のための表である。US08 の候補を入れる場所ではない。

さらに IT3 のクローズで、**画面が日付（`YYYY-MM-DD`）を送り、サーバが日時（`Instant`）で受け取る**食い違いが実バックエンドでだけ落ちた。到着期限も同じ形の項目であり、ここで型を決めておかないと同じ欠陥を繰り返す。

## 決定

### 1. 複数の候補を推奨順で返す

`GET /api/v1/routes?origin=&destination=&deadline=&cargoType=&maxTransshipments=`

- 候補ごとに **航海番号・区間・経由港・輸送日数・出発日時・到着日時・費用の概算・直行かどうか** を返す
- 並びは [ADR-018](018-route-search-rules.md) の推奨順。**画面は並べ替えない**
- **`origin` には任意の地点を指定できる。** 貨物の現在地を起点にした再設計（US28）を同じ入口で行うためである（既存の契約が持っていた性質を保つ）
- 候補が 0 件でも **200 と空の配列**を返す。「無い」は正常な結果であり、404 ではない。あわせて**どの条件が効いたか**を返し、画面が次の操作を出せるようにする

### 2. 候補は永続化しない

算出は都度行い、結果を保存しない。

- 候補は**航海スケジュールの写像**であり、スケジュールが変われば古くなる。保存すると「保存した時点では正しかった候補」を運用中に持ち続けることになり、どちらが正か分からなくなる
- 保存が要るのは**選んだあと**である。US09（経路の選択・確定）で `Cargo` の旅程として保存する。そこが唯一の正になる

### 3. 到着期限は日付で受け取り、業務タイムゾーンの当日終わりまでとする

- 画面は `deadline=2026-09-30`（日付）を送る。**サーバも日付として受け取る**
- 業務上「9 月 30 日まで」は「30 日中に着けばよい」を意味する。したがってサーバは業務タイムゾーンでの**その日の終わり**を期限の時刻とする
- 到着が期限ちょうどでも候補に出す（[ADR-018](018-route-search-rules.md)）

**日付を送って日時で受け取らない。** IT3 では文字列の前方比較で「たまたま動く」モックが単体も E2E も緑にし、実バックエンドでだけ落ちた。型は画面とサーバで 1 度突き合わせる。

### 代替案

- **`/optimal` を残して単数を返し続ける**: 受入基準（推奨順の一覧）を満たせない。画面側で複数回呼ぶ設計も考えられるが、条件の組み合わせを画面が発明することになる
- **候補を保存して ID で参照させる**: 画面の往復は楽になるが、古い候補を持ち続ける問題が生まれる。US09 で確定するまでの寿命は 1 回の画面操作であり、保存に見合わない
- **期限を日時で受け取る**: 業務が日付で考えているものを画面が時刻に変換することになり、変換の規則が画面側に散る（時差の分だけ当日が消える事故は、IT3 の教訓として記録済み）

## 影響

### ポジティブ

- 受入基準（推奨順・候補ごとの項目）をそのまま満たせる
- 保存しないため、スケジュール変更と候補の食い違いが構造的に起きない
- 期限の型が 1 箇所（日付 → 業務タイムゾーンの当日終わり）に決まる

### ネガティブ

- **同じ条件で 2 回呼ぶと、その間に航海が更新されていれば違う候補が返る。** 経路設計者が見ていた候補が消えることがある。US09 で確定するときに、選んだ経路がまだ成立するかを確かめる必要がある（IT5 で扱う）
- 候補の算出は毎回探索を走らせる。航海が増えると遅くなる。まずは絞り込みクエリで対応し、足りなくなったら考える
- `architecture_backend.md` の ACL 実装例（bookingms が `TransitPath` を直接デシリアライズする）は、この契約に合わせて書き直す必要がある。**bookingms 側は自分の DTO で受ける**（routingms の型を持ち込まない）

## コンプライアンス

決定の数だけ検査を用意する。

- **決定 1（複数候補・推奨順）**: API のテストで、複数の候補が推奨順で返ること・0 件で 200 と空配列になることを固定する
- **決定 2（永続化しない）**: `routing_db` のテーブル集合を固定する検査を置き、候補用のテーブルを足すと赤になるようにする
- **決定 3（期限は日付）**: 期限当日の遅い時刻に着く経路が候補に出ることを、業務タイムゾーンで検査する。あわせて画面が送る値の型をサーバの受け取り型と突き合わせる

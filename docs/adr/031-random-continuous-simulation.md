# ADR-031: ランダム実行は種から乱数器を作り直し、上限で業務を守る

バックエンドが乱数で業務シナリオを選んで流し続ける仕組みは、同じ種で同じ並びを
再現でき、実利用者の操作とヘルスチェックを劣化させない。

日付: 2026-09-01

## ステータス

**提案（決定 1〜6）**。IT15 で実装し、検査で固定する。

**いま守られているのは決定 5・6 だけである。** 決定 1〜4 は US37（継続実行）の実装と
同時に入る。コンプライアンス表で**まだ無い検査はバッククォートで囲んでいない**——
囲むと `AdrComplianceTableTest` が「実在する」と読み、無いものを在るように見せてしまう。
名前で追えない表は作文である。

## コンテキスト

[ADR-030](030-business-simulation-execution.md) で、予約から精算までの 1 本を自動で
流せるようになった。しかしその実行は**常に同じ 1 本の経路しか踏まない**。

実運用では複数の予約が並行して進み、荷役と精算と例外対応が同時に起きる。
IT15 の Phase 0 で、まさにその形の欠陥が 2 つ見つかった。

- 実行 ID の採番が「今日の件数 + 1」で、**同時に始めると衝突した**
- 経路割り当てが候補の先頭を無条件に選び、**別の実行が登録した航海に割り当てうる**

どちらも 1 件ずつ手で押しているあいだは起こりようがなく、ユニット・結合・E2E の
すべてが緑だった。**並行して動かして初めて出る欠陥がある**——US37 はそれを
リリース前に踏むための仕組みである。

ただし、負荷をかける側を自分で作るなら、**自分でクラスタを落とさない**ことを
先に決めておく必要がある。IT7 で、横断的な防御を一律に適用した結果、過負荷のとき
liveness が 503 を返して再起動ループになった。

> **決定ごとに「破られたら何が起きるか」を先に書く**（ADR-028〜030 と同じ）。

## 決定

### 決定 1: 乱数の種は実行に保存し、乱数器は種から作り直す

`simulation_run.seed` に種を残し、**実行のたびに種から乱数器を新しく作る**。
グローバルな乱数器を共有しない。

共有すると、並行実行の順序で取り出す値の並びが変わる。**同じ種を指定しても
再現できない**乱数実行は、落ちたときに報告する手段を持たない——「たまに落ちる
テストは 2 回目で追う」と決めても、追う手段が無ければ再実行して通ったことを
理由に見送ることになる。

**破られたら**: 落ちた実行を再現できない。US37 が「実運用に近い状態でしか出ない
欠陥を踏む」ための仕組みである以上、踏んだ欠陥を再現できなければ**踏んでいないのと
同じ**である。

### 決定 2: スケジューラは simulationms の中に置く

継続実行の刻みは simulationms 内のスケジューラで行う。外部のジョブ基盤を持ち込まない。

外に出すと、**停止・再現・上限の 3 つが別の場所で管理される**。管理者が画面で
「止める」を押したのに外のジョブが動き続ける、という状態を作らない。

**破られたら**: 止められない実行が残る。シミュレーションは業務データを作るため、
止められないことは実データが増え続けることを意味する。

### 決定 3: 同時実行数はセマフォで守り、ヘルスチェックは対象外にする

同時に走る実行の数はセマフォで、実行の間隔はスケジューラで守る。
**liveness / readiness の経路には掛けない。**

一律に掛けると、過負荷のときヘルスチェックが弾かれて Pod が再起動し、
**自分で自分を止める**。IT7 で実際に起きた形であり、IT3 の教訓がセマフォ経由で
同型に再現したものだった。

**破られたら**: 負荷をかけるほどクラスタが不安定になる。US37 の目的は
「実運用に近い状態を作る」ことであって、実運用を止めることではない。

### 決定 4: 停止は新規の開始だけを止める

停止の指示は**新しい実行を始めないこと**を意味する。進行中の実行は最後まで走らせる。

途中で中断すると、業務データが中途半端な状態で残る。[ADR-030](030-business-simulation-execution.md)
決定 5（巻き戻さない）と噛み合わない——巻き戻さないと決めた以上、中断した実行の
後始末をする場所が無い。

「止めた」と「止まった」を分けるため、状態に `STOPPING` を置く。分けないと、
進行中の実行が残っているのに停止済みと表示され、**統計が確定していない状態で読まれる**。

**破られたら**: 中途半端な貨物が実データに残る。シミュレーション由来なので業務は
止まらないが、「どこまで通ったか」を追う US35 の記録が実態と食い違う。

### 決定 5: 例外は実際に起きる操作で起こす

遅延・破損・誤配・税関保留・輸送中キャンセルを起こすための**専用 API は作らない**。
誤配は「予定と違う港での荷役を記録する」、遅延は「予定より遅い日時で記録する」——
実際に起きる操作をそのまま行う。

専用の入口を作ると、検知のロジックを迂回する。[ADR-026](026-misroute-detection-and-rerouting.md)
は誤配を荷役の記録そのものから検知すると決めており、専用 API はその検知を通らない
経路を新設することになる。[ADR-030](030-business-simulation-execution.md) 決定 2
（専用の書き込み経路を作らない）と同じ理由である。

**破られたら**: 「シミュレーションでは例外が起きるのに、実際の操作では起きない」
という状態を検出できなくなる。この仕組みを作る理由そのものが失われる。

### 決定 6: 二重実行の拒否は、手で押す実行にだけ効かせる

[US34-5](../requirements/user_story.md) の「同じシナリオが実行中なら断る」は、
**管理者が手で押す実行にだけ**適用する。継続実行では適用しない。

継続実行は同じシナリオを何本も並べて動かすため、そもそも噛み合わない。
US34-5 が守っているのは「押した人が、いま何が動いているか分からなくなる」ことであり、
継続実行にはその読み手がいない（開始したのはセッションであって、押した人ではない）。

**なお現状の拒否は同時開始で通り抜ける。** 実行中かを読んでから書くまでの隙間である
（Phase 0.10 で実測）。手で押す実行では 2 人の管理者が同時に押すことは起こりにくく、
起きても採番は衝突しないため実害は「2 本走る」ことに留まる。**部分 UNIQUE 索引で
守る道は取らない**——H2 が解釈せず（IT12 で実測）、ローカルの手軽な起動先が落ちる。

**破られたら**: 継続実行が 1 本目以降を開始できない。US37-1（並行して実行し続ける）が
成立しない。

## この決定の前提の外にあるもの

**種を記録すれば再現できる、という前提の外に「実データの状態」がある。**

同じ種で同じシナリオの並びは再現できるが、**そのとき業務データがどうなっていたかは
再現しない**。航海が登録済みか、通関が滞留しているか、前の実行が残した貨物があるかで
結果は変わる。種は「何を試みたか」を再現するのであって「何が起きたか」ではない。

落ちた実行を追うときは、種に加えて**そのときの実行 ID と工程の記録**（US35 が残す
もの）を併せて読む必要がある。種だけで追えると書くと、追えなかったときに
「再現性がない」と誤って結論づける。

## 影響

- `simulation_run` に `seed` と、継続実行との紐付けを足す。**既存行は種を持たない**ため、
  既定値で埋めてから NOT NULL にする（「不変条件の追加は既存行を壊す」）
- 継続実行のセッション（`simulation_session`）を新設する
- 実行は非同期になる（`202 Accepted` + 取得）。IT14 の同期実行は 14 工程で 8 秒かかり、
  継続実行では応答を待てない
- 例外シナリオは既存の業務 API だけで組み立てる。`BusinessGateway` の 1 ポートは変えない

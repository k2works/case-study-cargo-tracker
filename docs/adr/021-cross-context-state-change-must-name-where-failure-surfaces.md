# ADR-021: BC 越しに状態を変えるポートは、失敗が届く先を名簿に登録する

BC 境界を越えて状態を変える経路を、同期の ACL ポートにするかドメインイベントにするかは
「**できなかったことを誰がいつ知り、その人は動けるか**」で決める。
同期にする場合は、失敗が届く先を名簿に登録しなければ検査が落ちる。

日付: 2026-08-11

## ステータス

承認済み

## コンテキスト

ADR-009 は「状態の伝播はイベント、問い合わせとコマンドは同期」と決めた。
分類そのものは正しいが、**「状態の伝播」と「コマンド」の線引きが判断に委ねられている**。

IT14 でその曖昧さが実際の欠陥になった。入金確認の後に予約を `SETTLED` にする
`BookingSettlementPort.settle` は `boolean` を返す契約なのに、
**呼び出し側が戻り値を捨てていた**。結果として
「入金確認済みだが予約が精算済みでない」請求書がログにも画面にも残らない。

**その予約は精算後も引取記録を訂正できてしまう**
（US36 のガードが `booking_status` に依存しているため）。
テストは全緑、SonarQube も PASS のまま、レビューで初めて出た。

IT14 のふりかえり Try T1 は「戻り値を持つポートは、呼び出し側が使っているかを
実装時に確かめる」と定めた。**この基準は必要だが十分でない。**

- 戻り値を「ログに書く」だけでも「使っている」と言える
- 逆に、戻り値を使っていない同期ポートが必ず誤りとも限らない

**問うべきは戻り値の使われ方ではなく、失敗が人に届くかである。**

## 決定

**BC 越しに状態を変える経路は、次の 2 段で決める。**

1. **その越境は状態を変えるか。** 変えないなら問い合わせであり、同期の ACL ポートでよい
   （ADR-009 のとおり）
2. 変えるなら、**できなかったことを誰がいつ知り、その人は動けるか**

| 誰が知るか | 選ぶ形 | 失敗の届け先 |
| :--- | :--- | :--- |
| **いま操作している利用者**が知って、その場で手を打てる | **同期の ACL ポート** | **画面のメッセージ**（＋監査ログ） |
| 操作している人は何もできない（別の人・別の時間の仕事） | **ドメインイベント** | **ログ**＋**気づく手段**（一覧・カード） |

**「例外にしない」は「記録しない」ではない。** どちらを選んでも、
起きなかったことが消えてよいわけではない。

### いまの分類

| 経路 | 形 | 理由 | 失敗の届け先 |
| :--- | :--- | :--- | :--- |
| `BookingSettlementPort.settle` | **同期** | US23 の受入基準そのもの（「入金確認後、予約状態も精算済になる」）。経理担当者はその場で気づいて手を打てる | 請求書詳細の警告＋監査ログ |
| `InvoiceNotificationPort.notifyIssued` | **同期** | 「請求書が届いていない」と言われたときに答える記録。宛先が無いことは経理担当者が直せる | 請求書詳細の警告＋監査ログ |
| `TrackingPort.issue` | **同期** | 追跡番号を発行できたかは営業担当者の操作の結果そのもの | 画面のメッセージ |
| `CargoRouteAssignments.assign` | **同期** | 拒否の理由（端点不一致・状態不正）を経路設計者にその場で返す必要がある | 画面のメッセージ |
| **`CargoCancelledEvent`（US30）** | **イベント** | 承認するのは追跡管理者、請求するのは経理担当者である。**承認画面の前にいる人はキャンセル料について何もできない** | ログ＋請求対象一覧 |

### 何が守るか

**名簿である**（`CrossContextPortPolicyTest`）。
ACL ポートのうち問い合わせでないメソッドは、すべて名簿に
「なぜ同期か」と「失敗がどこに出るか」を書かなければ検査が落ちる。

C16（ダッシュボードの案内をロール列挙から名簿へ）と同じ形である。
**規律を人の記憶に預けず、構造で止める。**

## 根拠

- **ADR-009 の分類は残す。** 変えるのは「状態の伝播」と「コマンド」を分ける問いであり、
  分類の枠組みそのものではない
- **戻り値の有無は基準にならない。** `void` を返す同期ポートが誤りとは限らず、
  `boolean` を返すことが正しさを保証しない。**問いは人に届くかである**
- **イベントに寄せるほど良い、ではない。** IT14 の教訓は「失敗を見えるようにする」
  ことであり、同期をやめて画面のメッセージを消したら、直したはずのものを戻すことになる
- **名簿にすると、新しいポートを作った瞬間に問いが立つ。** レビューまで待たない

## 影響

- 既存の同期ポート 4 本はすべて同期のまま。**分類が変わるものは無い**
  （IT14 の是正で失敗はすでに画面に出ている）
- US30 の状態伝播は同期ポートを新設せず、`CargoCancelledEvent` で行う。
  **Booking → Billing の依存は増えない**（イベントは `shared` を経由する）
- 新しく状態を変える ACL ポートを足すと、名簿に書くまでテストが落ちる

## 代替案

- **`settle` / `notifyIssued` をイベントに変える。** 却下。ADR-009 の
  「状態の伝播」に字面は当てはまるが、**画面の警告が消える**。
  IT14 でわざわざ足した「気づく手段」を、整合性のために外すことになる
- **ArchUnit で「ACL ポートは値を返さねばならない」と縛る。** 却下。
  `boolean` を返しても捨てられるなら何も守っていない（IT14 がまさにそれだった）
- **Try T1 の運用（実装時に確かめる）のままにする。** 却下。
  **同じイテレーションの中で再発した前例がある**（T2 の日時の型）。
  規律だけに預けたものは、忙しい日に落ちる

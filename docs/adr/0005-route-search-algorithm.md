# 0005 経路探索アルゴリズム選定（DFS + 深さ制限）

US08（経路候補算出）の最大リスク要素について、IT3 着手前にアルゴリズムを暫定決定する。

日付: 2026-06-21

## ステータス

2026-06-21 提案されました（Spike 完了、IT3 US08 で本実装時に再評価）

## コンテキスト

US08「経路候補を算出する」は IT2 リリース計画 R7 で最大リスク要素と評価され（5 → 8 SP に上方修正）、IT2 末でスパイクを実施する申し送りとなっていた（`iteration_plan-2.md` タスク 4.x）。

- 入力: 登録済み `Voyage`（航海）の集合、出発地 / 目的地 `Location`、最早出発時刻
- 出力: 制約を満たす経路候補（`List[RoutingLeg]`）の列挙
- 制約: 区間連結（前到着地 == 次出発地、前到着時刻 ≤ 次出発時刻）、サイクル禁止、最大区間数（深さ制限）
- IT3 では危険物 / 冷凍貨物の対応航海フィルタ、料金 / 所要日数によるスコアリング、上位 N 件の選定が追加される

選択肢:

1. **DFS + 深さ制限**（採用）: 純関数で実装、テスト容易、IT3 で容易に拡張可能
2. **BFS**: 最短ホップ数の経路は得やすいが、時刻制約・複雑な枝刈りの導入で見通しが悪化
3. **Dijkstra / A***: 料金 / 所要時間の最短経路を直接得られるが、IT3 で要件確定する前にスコアリング設計を固定するのは尚早
4. **グラフ DB（Neo4j 等）**: 表現力は高いが Phase 2 のリリースペースに見合わず、技術スタック逸脱

## 決定

経路探索の初版アルゴリズムとして **DFS + 深さ制限**（`maxLegs = 3` を IT2 暫定値）を採用する。プロトタイプ `RouteCandidateSearchSpike` を `routing.application` パッケージに置き、純関数（`Voyage`・`Location` のみに依存）として実装する。

主要 API:

- `RouteCandidateSearchSpike.toRoutingLegs(voyages)`: `Voyage` の集合を辺リストに展開
- `RouteCandidateSearchSpike.search(legs, origin, destination, earliestDeparture, maxLegs)`: 全列挙

検証済み挙動（`RouteCandidateSearchSpikeSpec` 7 件）:

- 直行便を 1 候補返す
- 中継便の連結条件（区間時刻順）を満たす経路を発見
- 時刻逆転中継は除外
- 直行 / 中継の複数経路を同時列挙
- サイクル禁止（同一地点再訪を打ち切り）
- `maxLegs` 超過経路は除外
- 到達不能は空リスト

## 帰結

**ポジティブ**:

- 純関数なのでテスト容易（ScalaTest 7 ケースで主要分岐をカバー）
- IT2 で実装し IT3 US08 着手時のリスクを大幅に低減
- IT3 で容易に拡張可能（料金スコアリング・対応貨物種別フィルタを追加）

**ネガティブ / 制約**:

- 全列挙のため航海数が増えると経路数が指数的に膨らむ。IT2 暫定 `maxLegs = 3` で抑制
- IT3 で本実装する `RouteCandidateSearch` は本スパイクとは別クラスとし、スコアリング・上位 N 件選定を追加する
- `RoutingLeg` / `RouteCandidate` の最終的な型は `domain.model.valueobjects` に移動する可能性あり（IT3 で評価）

**IT3 への申し送り事項**:

1. 本スパイクを参照しつつ、`RouteCandidate` 型をドメイン側に格上げ
2. 危険物 / 冷凍貨物の対応航海フィルタを `Voyage` のメタデータとして追加（船名・運送会社・対応貨物種別カラム）→ データモデル追補 ADR で別途定義
3. 料金算出（US21）と連動した料金スコアリング
4. 上位 5 候補の選定ロジック
5. パフォーマンス試験（航海数 1000 件規模での経路探索 P95 < 3 秒、非機能要件）

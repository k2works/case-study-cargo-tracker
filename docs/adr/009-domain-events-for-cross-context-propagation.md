# ADR-009: BC 間の状態伝播はドメインイベントによる結果整合で行う

境界付けられたコンテキスト間で状態を伝播する連携を、同期呼び出しではなく、ドメインイベント（`AFTER_COMMIT`）による結果整合で行う。

日付: 2026-08-08

## ステータス

承認済み（**2026-08-08 改訂 1 回**）

> **改訂 1（2026-08-08）**: 当初は「BC 間 ACL は同期・同一トランザクションで呼ぶ」と決めた。
> **本改訂で判断を反転し、状態の伝播はドメインイベントによる結果整合とする。**
>
> 反転の理由は「**1 つの操作が 3 つの集約を 1 トランザクションで更新する形が、集約境界の
> 原則からの逸脱として重すぎた**」ことである。当初案はその逸脱を「業務上あり得ない中間状態を
> 作らないため」と正当化していたが、その代償として **BC 間の結合が強く、片方の遅延が
> もう片方を止める**構造を選んでいた。荷役は最も頻度の高い操作であり、**追跡や予約の
> 都合で荷役の記録が失敗してはならない**。順序が逆だった。
>
> 改訂前の記述は「代替案」の節に残す。**判断の経緯を追えるようにするためである。**

## コンテキスト

IT6（US13 / US14 / US15）で BC 間 ACL ポートが 4 件になり、**1 つの操作が複数の BC に書き込む形**が実装に現れた。荷役の登録は荷役作業・追跡状態・予約の 3 つを 1 つのトランザクションで書く。

一方 `architecture_backend.md` の「イベント駆動設計」節は、`ApplicationEventPublisher` と `@TransactionalEventListener(AFTER_COMMIT)` による結果整合を実装方針としてコード例つきで規定していた。**実装と設計書で故障モードがまるで違う。**

- 結果整合: 荷役は成功し、追跡の更新は後から起きる（あるいは失敗して起きない）
- 同期・同一トランザクション: 両方成功するか、両方起きないか

この食い違いは IT6 のマルチパースペクティブレビュー（architect M2 / H3）で指摘された。**どちらが正しいかを決めずに実装が先行していた。**

さらに、同期を選ぶ場合には固有の危険がある。**楽観的ロックの失敗を握り潰すと、同期にした利点（片方だけ成功しない）がそのまま失われる。** IT6 のレビューでは実際に 3 か所で戻り値が捨てられていた。

## 決定

**BC 間の「状態の伝播」はドメインイベントによる結果整合で行う。**

`ApplicationEventPublisher` で発行し、`@TransactionalEventListener(phase = AFTER_COMMIT)` かつ
`@Transactional(propagation = REQUIRES_NEW)` で購読する。

判断根拠は次のとおり。

- **1 つの操作が 3 つの集約を 1 トランザクションで更新する形は、集約境界の原則からの逸脱である。** 荷役の登録は荷役作業・追跡状態・予約に影響するが、それらは**別々に守るべき不変条件**を持つ。1 つのトランザクションに束ねると、集約が「一緒に守る単位」であるという前提が崩れる
- **荷役は本システムで最も頻度の高い操作であり、最も落としてはならない記録である。** 同期にすると、追跡や予約の都合（ロック競合・遅延）で**現場の作業記録そのものが失敗する**。順序が逆である。記録は必ず残り、反映は追って行われるのが正しい
- **発行側は購読側を知らない。** 荷役は「JPOSA で V001 に積み込んだ」という事実だけを伝え、それが輸送状態のどれに当たるか・輸送開始にあたるかは購読側が決める。同期呼び出しでは、発行側が相手の関心事（`markMisrouted` / `startTransportIfNotStarted`）を名前で知ることになっていた
- BC を将来別プロセスへ分けるときの変更が、購読の実装に閉じる

### 何をイベントにし、何を同期のままにするか

**すべての境界越えをイベントにするわけではない。** 分けるのは次の基準である。

| 種別 | 扱い | 例 |
| :--- | :--- | :--- |
| **状態の伝播**（起きた事実を他 BC が自分のモデルに反映する） | **ドメインイベント** | 荷役登録 → 追跡の輸送状態・予約の誤配と輸送開始 |
| **問い合わせ**（読むだけ。状態を変えない） | 同期（ACL ポート） | 予定ルートの参照（`CargoSnapshots`）、便の空き容量（`VoyageCapacityPort`） |
| **コマンド**（利用者の操作そのもので、可否をその場で返す必要がある） | 同期（ACL ポート） | 経路の割り当て（`CargoRouteAssignments`）、追跡番号の発行（`TrackingPort`） |

**コマンドをイベントにしない理由**は、拒否の理由を利用者に返せなくなるためである。経路の割り当ては「端点が予約と一致しない」「その状態では割り当てられない」を経路設計者にその場で伝える必要がある。イベントにすると、画面は「割り当てました」と表示した後に、どこにも表示されない失敗が起きる。

**問い合わせをイベントにしない理由**は、そもそも状態を変えないためである。

### イベントを選ぶ以上、必ず守ること

1. **購読は `AFTER_COMMIT` である。** コミット前に動くと、発行側が巻き戻ったときに購読側だけが残る
2. **購読側は新しいトランザクションで書く**（`REQUIRES_NEW`）。`AFTER_COMMIT` の時点で発行側のトランザクションは終わっており、そのままでは書き込みがコミットされない
3. **イベントが運ぶのは「起きた事実」であり、命令ではない。** 「輸送状態を進めよ」ではなく「積み込んだ」を伝える。命令を運ぶと、発行側が購読側の都合を知ることになる
4. **運ぶのは素の値だけ。** 発行側の型を載せると、購読する BC が発行側のドメインを参照することになる。イベントは `shared/domain/event` に置く
5. **購読側で楽観的ロックが失敗したら、ログに残す。** 結果整合では利用者の画面に返せないため、**そこが唯一「反映されなかった」ことを知る手段**になる。握り潰してはならない

### 変更箇所

- `handling/**`: 荷役の登録は荷役作業だけを書き、`HandlingActivityRegisteredEvent` を発行する
- `shared/domain/event/`: BC をまたぐイベントの置き場（共有カーネルではない）
- `tracking/interfaces/events/`・`booking/interfaces/events/`: 購読ハンドラ
- 削除: `TrackingEvents` / `HandlingProgressPort` とそのアダプタ（伝播が ACL ポートから消えた）
- `architecture_backend.md`: 「イベント駆動設計」節を採用済みとして記述する
- `domain-model.md`: ドメインイベント一覧と ACL ポート一覧の役割分担を明記する

### 代替案

| 代替案 | 却下理由 |
| :--- | :--- |
| **BC 間 ACL を同期・同一トランザクションで呼ぶ**（本 ADR の改訂前の決定） | 1 操作が 3 集約を 1 トランザクションで更新する形になり、集約境界の原則から逸脱する。かつ**最も頻度が高く最も落としてはならない荷役の記録が、追跡や予約の都合で失敗する**。中間状態を避ける利益より、記録が失敗する損失が大きい |
| すべての境界越えをイベントにする | 経路の割り当てのようなコマンドは、拒否の理由を利用者にその場で返す必要がある。イベントにすると失敗がどこにも表示されない |
| BC をまたぐ操作を作らない（1 操作 1 BC に限る） | 荷役の登録は、その性質上「荷役の記録」「輸送状態」「予約の進行」に同時に影響する。業務がまたいでいるものを実装だけで分けることはできない |
| Transactional Outbox パターン | 単一プロセス・単一 DB の現時点では、テーブルと再送機構の運用コストに見合わない。**BC が別プロセスに分かれた時点で必要になる**（本 ADR の次の改訂候補） |

## 何がどこで守るか

| 守るもの | 守り手 |
| :--- | :--- |
| 購読側は新しいトランザクションで書く（規則 2） | **`EventualConsistencyPropagationTest`**（IT15 で追加。既存 5 本の違反が判明した） |
| イベントが運ぶのは素の値だけ（規則 4） | **`PackageStructureTest.共有イベントは事実を運ぶレコードのみ`**＋`共有イベントのネストした型もレコード` |
| **購読は `AFTER_COMMIT` である（規則 1）** | **`EventualConsistencyListenerPhaseTest`**（IT16 で追加。下記） |
| イベントは命令ではなく事実を運ぶ（規則 3） | **守らない。** 命名の規律であり機械的に判定できない。レビューで見る |
| 購読側の楽観的ロック失敗をログに残す（規則 5） | **守らない。** ハンドラが握り潰しても検査は落ちない |

> **規則 1 に守り手が無かった。** IT15 で規則 2 の検査を書いたときに規則 1 を見ておらず、
> **「必ず守ること」と書いた 5 件のうち検査があったのは 2 件だけだった**。
> `@TransactionalEventListener(phase = AFTER_COMMIT)` を素の `@EventListener` に
> 戻しても、テストは緑のままだった。IT16 で検査を追加した。
>
> **規則 3・5 は「守らない」と明記する。** 書けない検査を書いたふりをするより、
> **どこが人の注意に預けられているかを名前で残す**ほうが安全である。

## 影響

### ポジティブ

- **1 トランザクション 1 集約に戻る。** 集約境界の原則からの逸脱が解消する
- **荷役の記録が、追跡や予約の都合で失敗しなくなる。** 最も頻度が高く最も落としてはならない操作が、他 BC から独立する
- 発行側が購読側を知らない。荷役は誰が何をするかを知らずに「起きた事実」だけを伝える
- BC を別プロセスへ分けるときの変更が、購読の実装に閉じる

### ネガティブ

- **「登録したのに反映されていない」瞬間が存在する。** 荷役を登録した直後に追跡を開くと、まだ前の状態が見えることがある。**この時間を短く保つのは運用の関心事**であり、利用者への説明（マニュアル）も必要になる
- **購読側の失敗が利用者の画面に返らない。** 楽観的ロックの衝突はログにしか残らない。ログを見る運用が要る
- 単一プロセス・単一 DB でありながら、分散システムの機構（イベント・結果整合）を持ち込むことになる。**再送・重複の扱いは現時点で持たない**（Outbox は将来の課題）
- 同一プロセスの `ApplicationEventPublisher` はプロセスが落ちるとイベントを失う。**荷役の記録は残るが反映されない**状態があり得る。復旧手段（再反映）は現時点で無い

## コンプライアンス

- BC 間で状態を伝播する経路が、ACL ポートの同期呼び出しではなくイベントであること
- 購読が `@TransactionalEventListener(AFTER_COMMIT)` かつ `@Transactional(REQUIRES_NEW)` であること
- イベントが `shared/domain/event` にあり、運ぶ値が素の値だけであること
- 購読側で楽観的ロックの失敗をログに残していること（握り潰していないこと）
- `architecture_backend.md` の「イベント駆動設計」節が、採用済みとして記述されていること

# ADR-014: ダッシュボードの件数は各 BC が自分で載せる

ダッシュボードに出す「気づくための件数」は、**共有の画面が全 BC を呼び集めるのではなく、各 BC が `@ControllerAdvice` で自分の分を載せる**。

日付: 2026-08-09

## ステータス

承認済み

## コンテキスト

ダッシュボード（`/`）は各ロールの作業入口である。ここには「放置するとコストが発生する」件数が並ぶ。

| ロール | 件数 | 出どころの BC |
| :--- | :--- | :--- |
| 追跡管理者 | 未解決の例外 / 通関で 3 日以上留置中 / 誤配 | Tracking / Handling / Booking |
| 管理者 | エスカレーション中の例外 / ロック中アカウント | Tracking / Security |
| 営業担当者 | 経路割り当て待ち / 追跡番号発行待ち | Booking |
| 経理担当者 | 支払期限超過 | Billing |

**件数は増え続ける。** IT10 で 2 つ、IT11 で 2 つ増えた。残りのイテレーションでも増える見込みがある。

### 素直に書くとどうなるか

ダッシュボードのコントローラは `shared` にある（`shared/infrastructure/web/DashboardController`）。ここで件数を集めると、**`shared` が全 BC のクエリサービスを import する**。

- `shared` は BC 間参照の検査（ArchUnit ルール 4）から**依存先として除外**されている。したがって**この結合は検査に映らない**
- 件数が増えるたびに `shared` のコンストラクタ引数が増える。**BC を 1 つ足すたびに共有クラスを触る**
- ADR-012 が「BC 間の参照は `infrastructure/acl` に閉じる」と決めた向きに反する。ダッシュボードは acl ではない

**`shared` は全 BC が依存してよい場所であり、そこに全 BC への依存を集めると、依存の向きの規律が中央で 1 か所だけ破れる。**

## 決定

**ダッシュボードに件数を載せるのは、その件数を持つ BC の責務とする。**

各 BC は `interfaces/web` に `@ControllerAdvice(assignableTypes = DashboardController.class)` を置き、`@ModelAttribute` で自分の件数をモデルに載せる。`shared` 側のコントローラは**どの BC が何を載せるかを知らない**。

```
tracking/interfaces/web/TrackingExceptionDashboardAdvice
  @ControllerAdvice(assignableTypes = DashboardController.class)
  @ModelAttribute("unresolvedExceptions")  → Tracking のクエリサービスを呼ぶ
```

### 3 つの規律

1. **ロールで出し分ける。** その件数を見ないロールでは**クエリを実行しない**。全ロールで走らせると、ログイン直後の 1 画面で使わない集計が並ぶ（IT10 のレビューで実際に指摘された）
2. **件数は次の行動へ繋ぐ。** 件数だけを出しても仕事は進まない。カードは必ず**対象の一覧へのリンク**を持つ
3. **テンプレートは属性が無い場合に耐える。** advice が無い BC の件数を参照しても画面が落ちないようにする（BC を外したときにダッシュボードごと壊さない）

## 根拠

- **依存の向きが `shared → BC` にならない。** `@ControllerAdvice` は Spring が実行時に結びつけるため、`shared` は各 BC を知らない。**知らないものは壊せない**
- **BC を足す・外すときに共有クラスを触らない。** 新しい BC は自分の advice を足すだけで済む
- **ADR-012 と同じ向きの判断である。** 「BC 間の結合は必要なら残すが、閉じ込める場所を決める」— ここでの閉じ込め先は各 BC 自身の `interfaces/web` である

## 検討した代替案

| 案 | 却下の理由 |
| :--- | :--- |
| `shared` のコントローラが全 BC のクエリサービスを呼ぶ | **`shared` が全 BC に依存する**。しかも ArchUnit の検査からは除外されているため、結合が育っても気づけない |
| ダッシュボード専用の ACL ポートを `shared` に定義し、各 BC が実装する | 形は正しいが、**件数 1 つにポートが 1 つ増える**。ポートは「BC 間で意味のある契約」に使いたい。表示のための集計は契約ではない |
| 各カードを htmx で個別に読み込む | 画面の応答は速くなるが、**リクエストがカードの数だけ増える**。件数はどれも 1 クエリで、まとめて出しても遅くない。速さの問題が出てから変える |

## 影響

- **正**: BC の追加・削除がダッシュボードに波及しない。ロール別の出し分けが BC の側で完結する
- **負**: 件数がどこから来るのかが 1 か所を読んでも分からない。**advice のクラス名に BC 名と対象を入れる**ことで補う（`TrackingExceptionDashboardAdvice`）
- **負**: `@ControllerAdvice` の結びつきはコンパイル時に検査されない。`assignableTypes` の指定を誤ると黙って効かなくなる。**ダッシュボードに件数が出ることをテストで固定する**（件数を 0 に潰すと赤になる形で書く。IT10 のレビューで、見出しの存在だけを見る偽の安全網を作っていた）

## 適用範囲

本 ADR は**ダッシュボードの件数**に限る。画面の本体（一覧・詳細）は従来どおり各 BC のコントローラが持つ。

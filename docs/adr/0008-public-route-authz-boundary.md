# ADR 0008: 公開照会ルートの認証境界分離と per-handler 認可方針（IT6）

## ステータス

承認（IT6 時点）

## コンテキスト

IT6 の US18（追跡情報の公開照会）で、**認証不要の公開ページ** `/public/tracking/{tracking_number}` を追加した。荷主・荷受人がログインせずに追跡番号で照会でき、URL を共有できることが要件である。

本システムの認可は [ADR-0002](0002-authentication-with-tower-sessions.md) 以来、tower-sessions ＋自前 RBAC で実装しており、各ハンドラが引数に `RoleGuard<R>`（型安全な認可）や `require_user` を取ることで認可を強制する **per-handler 方式**である。ルーター全体に認証ミドルウェアを掛ける方式ではない。

この方式で公開ルートを追加すると、次のトレードオフが顕在化する。

- 公開ルートは「ガード引数を意図的に外す」ことで実現する（`public_tracking` ハンドラは `RoleGuard`/`require_user` を取らない）。
- しかし同じ構造上、**認証必須のはずのハンドラでガード引数を書き忘れると、無防備なまま素通りする**。公開ルートが増えるほど、この「書き忘れ＝認可漏れ」の面積が広がる。

## 決定

### 1. 公開ルートは per-handler でガード引数を外して実現する（現状方式を継続）

`/public/tracking/{tracking_number}` は `RoleGuard`/`require_user` を取らないハンドラとして単一 Router に登録する。認証必須ルートは従来どおりハンドラ引数でガードを取る。IT6 時点ではルーター分割は行わず、既存方式との一貫性を優先する。

### 2. 「認証はハンドラ引数で強制し、公開ルートは意図的に引数を外す」ことを規約として明文化する

公開ルートの追加は例外的な操作であり、レビュー時に「なぜガードを外すか」を確認する。公開ルートのパスは `/public/` プレフィックスで統一し、公開意図をパスで表現する。

### 3. 認可漏れ検出の仕組みを IT7 以降の検討事項として記録する

per-handler 方式のリスク（ガード書き忘れ）に対し、以下を将来の対策候補として記録する。

- **ルーター構造での分離**: 認証必須グループと公開グループに Router を分割し、認証必須グループに `route_layer` でミドルウェアを適用する。境界が Router 構造で表現され、「書き忘れても素通りしない」安全側に倒れる。
- **テストによる網羅**: 全認証必須ルートに対し「未認証アクセスが 401/303 になる」ことを検証する横断テストを設け、公開ルートのみをホワイトリストとする。

> 本 IT では検出の仕組みは実装せず、規約として記録する。公開ルートが増えて認可漏れリスクが顕在化した時点で、上記のルーター分割へ移行する。

## 影響

- 公開照会が認証不要ルートとして提供され、US18 の「URL 共有」価値が成立する。公開ページには「ログイン不要で共有できる」旨と共有 URL を明示し、ユーザーが共有対象を誤認しないようにする。
- per-handler 認可のリスク（ガード書き忘れ）が「無自覚な穴」ではなく「既知のトレードオフ」として記録され、公開ルート増加時の移行基準（ルーター分割）が明確になる。
- セキュリティ境界に関わる意思決定が ADR として追跡可能になり、後続の認可設計変更の起点となる。

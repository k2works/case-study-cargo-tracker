# ADR-0002: Web・セキュリティ基盤の自作とその補償策

Flix にフレームワークが存在しないため、HTTP ルータ・HTML 生成・認証/セッション/CSRF・アーキテクチャ検査を JDK 標準 API の薄いラッパとして自作する。自作に伴うリスクは 4 つの補償策で管理する。

日付: 2026-08-03

## ステータス

2026-08-03 承認

## コンテキスト

[ADR-0001](ADR-0001-flix-adoption.md) で Flix を採用した結果、以下が存在しないことが確定した。

| 欠落 | 通常の選択肢 | Flix での可否 |
| :--- | :--- | :--- |
| Web フレームワーク | Spring Boot / Javalin | **なし** |
| テンプレートエンジン | Thymeleaf | Java 相互運用で呼べるが型検査の外に出る |
| ORM | JPA / MyBatis | アノテーション・XML を Flix から扱えず**実質使えない** |
| 認証・認可基盤 | Spring Security | **なし** |
| モックライブラリ | Mockito | **なし**（効果ハンドラで代替可能） |
| カバレッジ計測 | JaCoCo | **なし**（Flix ソース行にマップできない） |
| アーキテクチャ検査 | ArchUnit | **なし**（Flix のモジュール構造を検査できない） |

「車輪の再発明」は通常避けるべき投資である。とりわけ**認証・セッション・CSRF の自作は、実装欠陥が直接セキュリティ事故につながる**ため、既製フレームワークに任せるのが定石である。

しかし本プロジェクトでは、Flix を採用する目的（型と効果による安全性の検証）と、Flix にそれらが存在しないという事実が同時に成立している。Java 側にロジックを置いて回避する選択肢もあるが、それは「Flix で DDD を実装する」という検証目的そのものを損なう。

## 決定

### 1. 自作する。ただし範囲を JDK 標準 API の薄いラッパに限定する

| 自作するもの | 基盤 | 範囲の限定 |
| :--- | :--- | :--- |
| HTTP サーバ・ルータ | `com.sun.net.httpserver`（JDK 内蔵） | メソッド + パスパターンのディスパッチのみ。ミドルウェアは認可・CSRF・ロギングに限る |
| HTML 生成（`Html` DSL） | なし（Flix の ADT） | 要素・属性・テキスト・フラグメントの 5 ケースのみ。テンプレート言語は作らない |
| データアクセス | `java.sql`（JDBC） | `PreparedStatement` と `ResultSet` の手書きマッパー。クエリビルダは作らない |
| 認証・セッション・CSRF | `java.security.SecureRandom` + jBCrypt | セッション ID 発行・検証・失効、トークン検証のみ。OAuth・SAML は扱わない |
| アーキテクチャ検査（`arch-lint`） | Node.js | `use` / `import` 宣言と特定構文の走査。AST 解析は行わない |

**汎用化しない**ことを規律とする。「後で必要になるから今作る」を禁止し、必要になったイテレーションで拡張する（[開発戦略](../development/development_strategy.md) 2 節）。

### 2. テンプレートエンジンを使わない

Thymeleaf 等を相互運用で呼ぶと、テンプレート内の式が Flix の型検査の外に出る。画面層だけを型安全性の外に置く判断は、Flix を採用した目的と矛盾する。デザイナとの分業が発生しない本プロジェクトの体制を前提に、`Html` DSL を採用する。

### 3. リスクを 4 つの補償策で管理する

| リスク | 補償策 | 検証手段 |
| :--- | :--- | :--- |
| **セキュリティ実装の欠陥** | ① 自作範囲の限定（上表）<br>② OWASP ASVS L1 チェックリストによる四半期レビュー<br>③ セキュリティ回帰テストの必須化 | [テスト戦略](../design/test_strategy.md) 8.4 の 7 項目 |
| **カバレッジ計測不能による品質ゲートの空洞化** | 行カバレッジを品質ゲートに使わない。ビジネスルール ⇄ テストの対応表とストーリートレーサビリティ表で網羅を担保 | `docs/design/business_rule_traceability.md`、テスト戦略 5 章 |
| **`arch-lint` 自体のバグによるサイレントな規約違反** | 違反フィクスチャ（負例）と適合例（正例）によるメタテスト | `ops/scripts/arch-lint/fixtures/` |
| **自作分の見積もり誤差** | 技術ストーリー TS01-TS07 として独立に SP を計上し、ユーザーストーリーの裏に隠さない | [リリース計画](../development/release_plan.md) |

### 4. Maven 依存は 6 つに限定する

PostgreSQL Driver・H2・HikariCP・Flyway・jBCrypt・Jackson のみとする。追加時は「Flix 単一言語方針を崩さないか」を ADR で判定する。

### 5. セキュリティ機構の実装は第 2 段階に置く

最もリスクの高い認証機構を最初に踏まないよう、認証不要の公開追跡（US18）でウォーキングスケルトンを縦断してから認証に進む（IT1 → IT3）。

## 影響

### 正の影響

- Flix の型検査が画面生成まで届く（テンプレートの実行時エラーがなくなる）
- 効果ハンドラがテストダブルとして機能し、モックライブラリが不要になる
- フレームワークのバージョンアップに追従するコストがゼロになる
- ルーティング表・画面生成がすべて単体テスト可能になる

### 負の影響

- **技術ストーリーとして 44 SP（全体の 30%）を消費する**
- セキュリティ実装の欠陥リスクを恒常的に負う。補償策はリスクを下げるが、ゼロにはしない
- HTML の記述量が増える（`Components` モジュールで吸収する）
- 新規参加者に「なぜ自作しているか」の説明が毎回必要になる

### この判断が正当化される条件

**本 ADR は「Flix にエコシステムが存在しない」という制約下でのみ正当な投資である。**
本プロジェクトが実運用を見据えたシステムへ転用される場合、この判断は再度問い直す必要がある。

## コンプライアンス

- Maven 依存が 6 つを超えていないこと（`flix.toml` の `[mvn-dependencies]`）
- `arch-lint` の 9 規約に違反がないこと（CI で強制。規約の正典は [arch-lint 規約仕様](../design/arch_lint_rules.md)）
- `arch-lint` のメタテスト（負例の検出・正例の誤検出なし）が通ること
- セキュリティ回帰テスト 7 項目が CI で実行されていること（IT3 以降）
- `Html.RawUnsafe` の使用箇所が許可リストに含まれること（`arch-lint` 規約 7）
- `<form>` が `Components.form` 経由で生成されていること（`arch-lint` 規約 8）

## 補足（IT2）

補償策の 1 つである `arch-lint` について、運用の中で 2 度の是正を行った。**いずれも
「検査が存在すること」と「検査が効いていること」が別物であることを示している。**

| # | 是正 | 経緯 |
| :--: | :--- | :--- |
| 1 | 規約 5 を「ハンドラの**定義**」と「複数ハンドラの**合成**」に分離し、規約 6 を新設。SQL の規約は 9 へ移動 | IT1 のレビューで、旧規約 5 がアダプタ側のラップ関数（`withJdbcReadDb`）まで違反にすることが判明。偽陽性が続けば規約は無視されるようになる |
| 2 | 継続行を論理行へ畳んでから照合する方式へ変更し、複数行の負例フィクスチャを追加 | IT2 のレビューで、規約 5・8・9 が**実コードと同じ書き方の違反**（`"SELECT ... " +` で改行して連結）を検出できないことが判明（実測で検出 0 件）。メタテストが緑でも検査器を信用する根拠になっていなかった |

是正 2 を踏まえ、**フィクスチャは「規約に違反する最小の例」ではなく「このコードベースで
実際に書かれる形の違反」で作る**ことを補償策の運用規約に加える。

## 補足（IT3）: ロック・無効化の文言によるユーザー列挙を受容する

自作の認証機構では、**攻撃者に何も教えない**ことと**締め出された利用者を次の行動へ導く**ことが
正面から衝突する。IT3 のレビューで、この衝突が具体的な形で現れた。

| 立場 | 主張 |
| :--- | :--- |
| tester | `Locked`（一時ロック）と `Disabled`（無効化）で文言が異なるのは**ユーザー列挙の経路**である。存在するユーザー名を総当たりで判別できる。文言を統一すべき |
| user-representative | ロックと無効化は利用者の取るべき行動が違う（30 分待つ / 管理者に連絡する）。統一すると、締め出された利用者が**次に何をすればよいか分からなくなる**。本船作業直前の締め出しは業務を止める |

### 決定: 利用者側を採る。文言を分けたまま運用し、この受容を明示的に記録する

**根拠**:

1. **判別できるのは「そのユーザー名が存在し、かつロックまたは無効化されている」ことに限られる**。
   通常の認証失敗は `Locked` / `Disabled` のいずれでもなく、一律の文言（「ユーザー名または
   パスワードが正しくありません」）を返す。存在するだけのユーザー名は判別できない
2. ロックに至るには**そのユーザー名で 5 回連続の失敗**が要る。列挙のコストが高く、
   その過程でアカウントを実際にロックしてしまうため、攻撃として静かに進行しない
3. 本システムの利用者は**社内および契約済みの取引先に限られる**。ユーザー名の一覧は
   攻撃者にとって新規の情報になりにくい
4. 締め出された利用者が管理者へ辿り着けないことによる業務停止は、**確実に発生する損害**である。
   一方ユーザー列挙は、上記 1-3 の条件下では実害に結びつきにくい

### この受容が成り立たなくなる条件

次のいずれかが起きた場合、本決定を再検討する。

- 一般公開の登録（誰でもアカウントを作れる）を導入したとき。ユーザー名の一覧が価値を持つ
- パスワードスプレー攻撃（多数のユーザー名 × 1 パスワード）への対策を入れるとき。
  IP・セッション単位のスロットリングと合わせて文言設計を見直す（IT3 レビュー M12・IT5 以降）
- ロックの閾値を大きく緩めたとき。列挙のコストが下がる

### 補償

- 通常の認証失敗は**存否を漏らさない一律の文言**とし、`AuthServiceTest` で固定する
- 存在しない利用者でも BCrypt の照合を通し、**応答時間で存否が判別できない**ようにする（IT3 レビュー H3・対応済み）

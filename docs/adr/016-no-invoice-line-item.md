# ADR-016: 明細テーブルを作らず、料金調整を精算書の列で持つ

`data-model.md` が定義していた `invoice_line_item` を**作らない**。料金調整（減額・補償費用）は `invoice` の列で持つ。**種類が 3 つ以上に増えたら明細テーブルへ移す。**

日付: 2026-08-10

## ステータス

承認済み

## コンテキスト

`data-model.md` は Billing Context に 3 つのテーブル（`invoice` / `invoice_line_item` / `payment`）を定義しており、V1 のマイグレーションで 3 つとも作成済みである。

IT13 で US21（輸送料金を算出する）を実装するにあたり、`invoice_line_item` を使うかどうかを決める必要が生じた。`release_scope.md` のスコープ外表は、この判断を「Release 2.0 で必要性を判断する」として保留していた。

US21 / US22 / US23 の受入基準を読み直すと、次のことが分かった。

- 請求金額を説明するのに要求されているのは「基本料金・割引率・割引後料金・消費税・合計」だけである
- **明細行を要求する受入基準が 1 つも無い**
- ただし US21 の受入基準 6 は「例外が発生している場合、料金調整（減額・補償費用）の入力ができる」と定めており、**減額と補償費用は基本料金とは別の行として説明されるべきもの**である

`release_scope.md` の原則 3 は「要求元のないものは作らない」と定めている。

## 決定

**`invoice_line_item` を本リリースでは使わない。** 料金調整は `invoice` に 4 列（`adjustment_reduction_value` / `adjustment_compensation_value` / `adjustment_currency` / `adjustment_reason`）を足して持つ。

**移行の条件を先に決める**: 調整の種類が 3 つ以上に増えたら明細テーブルへ移す。

## 何がどこで守るか

| 守るもの | 守り手 |
| :--- | :--- |
| 料金調整は `invoice` の 4 列で持つ | **DB のスキーマ**（`V30__invoice_charge_status.sql`）＋ `InvoiceTest` |
| `invoice_line_item` を使わない | **守らない。** テーブルは `V1__init.sql` に存在したまま残っており、**マッパーから引いても検査は落ちない**（`MapperTableOwnershipTest` は所有 BC だけを見る） |
| **調整の種類が 3 つ以上に増えたら明細テーブルへ移す** | **守らない（守れない）。** 移行の条件であって現在の不変条件ではない。**列を足す変更のレビューで数える** |

> **移行条件を書いただけでは守られない。** 「3 つ以上に増えたら」は、
> 増やす人が本 ADR を読んで初めて働く。**読まれなければ 4 列が 6 列になるだけである。**

## 根拠

- **要求元のないものは作らない。** 明細行を要求する受入基準が無い状態で 2 つ目のテーブルを作ると、書き込む側と読む側の両方に「常に 1 行だけの明細」を扱うコードが生まれる
- **調整は 2 種類しかない。** 2 つの値を持つのに親子テーブルを用意するのは、構造がデータより重い
- **理由を必須にできる。** 4 列を `CHECK` で対にすると「調整があるなら理由がある」を DB が守れる。明細テーブルだと「理由の無い明細行」を作れてしまう

## 影響

### よくなること

- Billing の永続化が 1 テーブルで完結する。マッパーと復元の経路が 1 本になる
- 「調整があるなら理由がある」を DB の制約で守れる

### 気をつけること

- **調整の種類が増えると列が増える。** 3 つ目が要るという話が出た時点で明細テーブルへ移す。**「4 列で足りているから」と 5 列目を足さない**
- `data-model.md` には `invoice_line_item` の定義が残る。**作らない判断であって、設計から消したのではない**（US23 以降で必要になれば使う）

## 代替案

| 案 | 却下の理由 |
| :--- | :--- |
| `invoice_line_item` を使う | 明細行を要求する受入基準が無い。常に 1〜2 行だけの明細を扱うコードが両側に生まれる |
| `invoice_line_item` を削除する | **将来の判断を奪う。** US23（精算）で明細が要ると分かる可能性がある。作らないことと、設計から消すことは別である |
| 調整を JSON 列で持つ | 「理由があるか」を DB で守れない。列にすれば `CHECK` で対にできる |

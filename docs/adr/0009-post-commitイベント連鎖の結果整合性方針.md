# ADR-0009: post-commit イベント連鎖の結果整合性方針

1 つのドメインイベントが複数の post-commit ハンドラを各独立トランザクションで処理する構造において、部分適用（一部のハンドラのみ成功）による状態の恒久乖離を許容範囲に収めるための整合性方針を定義する。

日付: 2026-07-14

## ステータス

2026-07-14 承認されました（IT6 着手時・IT5 レビュー高優先 H1 への対応）

## コンテキスト

ADR-0002 で「ドメインイベントはコミット成功後にディスパッチし、各ハンドラは別トランザクションで永続化する」方針を定めた。IT5 で Tracking / Handling BC を立ち上げた結果、1 つのイベントが複数のハンドラを各独立 UoW でコミットする連鎖が実運用に入った。

- `HandlingActivityRegisteredEvent`（荷役登録）→ `SyncTrackingOnHandlingRegisteredHandler`（追跡状態同期）＋ `SyncBookingStatusOnHandlingRegisteredHandler`（予約状態同期）の 2 ハンドラが各独立 UoW でコミットする。
- `BookingConfirmedEvent`（予約確定）→ `IssueTrackingOnBookingConfirmedHandler` が別 UoW で追跡発行 → 状態遷移の 2 段書き込みの窓を持つ。

IT5 開発成果物レビュー（2026-07-13）で、複数エージェント（xp-programmer 高・xp-architect 高・xp-tester 中）が最重要テーマとして指摘した:

> 荷役確定後に Tracking / Booking 同期が失敗すると状態が恒久乖離（部分適用）する。補償・再試行・冪等・手動修復のいずれかを明文化しないと本番移行リスク。

現状は「at-least-once・冪等スキップで緩和」の割り切りだが、方針が ADR に明文化されておらず、可観測性（同期失敗の検知手段）もログ以外に無い。IT6 では `TrackingExceptionDetectedEvent`（例外検知 → 予約へ通知）が加わり post-commit 連鎖がさらに増えるため、例外実装の前提として整合性方針を確定する必要がある。

## 決定

### 1. 結果整合性（eventual consistency）を正式な整合性モデルとする

BC をまたぐ状態同期は、単一トランザクションの ACID ではなく **結果整合性**で扱う。イベント発行元のコミットを真実の源泉とし、下流ハンドラは非同期的に追随する。同期の一時的な乖離は許容し、最終的に整合すること（または検知・修復可能であること）を保証する。

### 2. ハンドラは冪等（idempotent）に実装する

各 post-commit ハンドラは、同一イベントで複数回実行されても副作用が 1 回分に収束するよう実装する。

- 状態遷移は「現在状態が期待どおりなら適用、そうでなければスキップ」（`if (cargo.BookingStatus == before) return;` 等の冪等スキップ）で表現する。
- これにより at-least-once（再試行含む）でも状態の二重適用を防ぐ。

### 3. 再試行と可観測性

- ハンドラ失敗はログに **同期失敗イベント（イベント種別・集約 ID・ハンドラ名・例外）** を WARN 以上で記録する。これを部分適用の一次検知手段とする。
- 当面は再試行を MediatR パイプライン内の限定回数リトライで扱い、恒久失敗はログに残して**手動修復**（運用手順）へエスカレーションする。
- 高信頼が必要になった時点で **Transactional Outbox パターン**へ移行する（ADR-0002 の将来方針を踏襲）。移行前の暫定水準であることを明記する。

### 4. 手動修復の再同期手段を用意する

部分適用が検知された場合に下流状態を発行元に合わせて再構築できるよう、同期ハンドラの処理は「発行元の現在状態から下流状態を導出する」冪等な形に保つ（差分適用ではなく状態導出）。これにより同一イベントの再投入または再同期コマンドで修復できる。

### 5. 適用範囲

本方針は BC をまたぐ post-commit イベント連鎖すべてに適用する。IT6 で追加する `TrackingExceptionDetectedEvent`（Tracking → Booking）も本方針（冪等・失敗ログ・状態導出）に従って実装する。

## 影響

### 良い影響

- 部分適用のリスクと対処（冪等・失敗ログ・手動修復・Outbox 移行）が明文化され、本番移行判断の基準が定まる
- 冪等スキップを標準パターンとすることで、再試行・イベント再投入が安全になる
- IT6 の例外イベント連鎖を同一方針の上に載せられる

### 悪い影響・残るリスク

- Transactional Outbox 未導入のため、プロセス障害でイベント発行自体が失われる窓は残る（at-least-once は再試行成功が前提）。本番移行前に Outbox 導入の要否を再評価する
- 手動修復は運用手順に依存する。再同期コマンドの整備は後続イテレーションの課題として残る
- 結果整合性のため、下流状態が一時的に古い値を返す瞬間を UI/API が観測しうる（追跡状態が数百 ms 遅れて更新される等）

## コンプライアンス

- post-commit ハンドラは冪等スキップを実装し、統合テストで「同一イベント 2 回処理で状態が二重適用されないこと」を検証する
- 同期失敗時に WARN ログが出力されることをテストまたはコードレビューで確認する
- 新規の BC 間 post-commit ハンドラを追加する際は、本 ADR の冪等・失敗ログ・状態導出に準拠する

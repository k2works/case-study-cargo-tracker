# ADR-0008: 外部経路サービスの契約方針

経路候補算出（US08）の「外部経路最適化サービス」連携について、当面は**ローカル算出（`VoyageRouteCandidateService`）を正式方針**とし、実 HTTP 外部サービスが存在する段階で WireMock.Net による契約テストを追加する。

日付: 2026-07-13

## ステータス

2026-07-13 承認されました

## コンテキスト

IT3（US08 経路候補算出）で、`IRouteCandidateService`（Routing BC 固有の出力ポート）を導入し、外部経路最適化システムとの ACL として位置づけた。計画では「外部経路サービス ACL を WireMock.Net でスタブ契約として先に固定し、ドメインをスタブ駆動で作り込む」方針だった。

しかし実装時点で以下が判明した。

- **実 HTTP の外部経路サービスが存在しない**。連携先の API 仕様・エンドポイントが未確定で、契約（リクエスト/レスポンス schema）を固定する対象がない。
- IT3 では暫定的に `VoyageRouteCandidateService`（登録済み航海群 `voyage`/`carrier_movement` から `RouteCandidateCalculator` で経路候補を純粋算出するローカル実装）を `IRouteCandidateService` の実装として用いた。算出ロジック（寄港地接続評価・時刻接続・期限フィルタ・直行優先ソート）は純粋ドメインサービスに凝集し、8 ユニットテストで網羅している。
- IT3 ふりかえり Try（T5）・IT4 ふりかえり Try（T6）で「外部経路サービスの契約方針を確定し ADR 化する」ことが繰り越されていた。

存在しない外部サービスに対して WireMock.Net 契約を先行実装すると、実仕様と乖離した契約を固定してしまい、実連携時に二重の手戻りが生じる。

## 決定

**当面はローカル算出（`VoyageRouteCandidateService`）を `IRouteCandidateService` の正式実装とする。** WireMock.Net による契約テストは、実 HTTP 外部サービスの API 仕様が確定した段階で追加する。

- `IRouteCandidateService`（出力ポート）は維持する。将来の外部サービス連携時は、この ACL の実装を差し替えるだけで済む（ヘキサゴナルアーキテクチャの利点）。
- ローカル算出は「登録済み航海スケジュールから制約を満たす経路を算出する」という業務要件を満たしており、MVP（Release 1.0）の受入条件を充足する。外部サービスは「より高度な最適化」を担う将来拡張と位置づける。
- 経路候補の費用・所要日数は暫定係数（基本輸送料金＋港湾利用料の概算）で算出し、UI では「概算」と明示する（IT4 レビュー M2 対応済み）。

### 実連携への移行トリガー

以下のいずれかが満たされた時点で、外部経路サービス連携を再検討し WireMock.Net 契約テストを導入する。

- 連携先の外部経路最適化サービスの API 仕様（エンドポイント・認証・リクエスト/レスポンス schema）が確定した
- ローカル算出では表現できない最適化要件（複数キャリア横断・動的運賃・積載最適化など）が業務要求として発生した

### 代替案

- **WireMock.Net 契約を先行固定する**: 実仕様が未確定なため、乖離した契約を作り込むリスクが高く却下。
- **ポート自体を廃止しローカル算出を直接呼ぶ**: 将来の外部連携時に ACL 再導入コストが生じ、BC 独立・差し替え容易性を損なうため却下。ポートは維持する。

## 影響

### 良い影響

- 存在しない外部サービスへの投機的な契約実装を避け、手戻りを防止する。
- `IRouteCandidateService` ポートを維持することで、実連携時は実装差し替えのみで移行できる。
- MVP（Release 1.0）を外部依存なしで完結でき、出荷を早められる。

### 悪い影響

- 経路候補の最適化はローカル算出の範囲に留まる（暫定係数の費用・所要日数）。高度な最適化は将来拡張となる。
- 外部連携時に契約テスト（WireMock.Net）を追加する作業が後続イテレーションに残る。

| # | 視点 | 指摘 | 対応 |

| H1 | programmer + architect（収束） | `status_before_exception` が永続化されず荷役履歴から再導出。US17 手動更新後の例外→解決で誤った状態に復帰する偽の安全網 | **対応済み**: `tracking_activities.status_before_exception` カラムを追加し集約状態として永続化。履歴再導出を廃止。US17 手動更新後の復帰を検証する回帰テストを追加 |

## 中・低優先度指摘の対応方針

**対応済み**:
- tech-writer 中: data-model の `escalation_flag` を US15→US20 に修正。

**次イテレーション対応（IT7 引き継ぎ）**:
- programmer 中: 荷役冪等ガードの DB unique index 裏付け（現状はアプリ層 `duplicate?` チェック。並行 POST の最終防衛として `(booking_id, event_type, event_completion_time, voyage_number)` に unique index + `RecordNotUnique` 捕捉を追加）。
- programmer 中 / user-rep H2: 例外登録・解決の precondition 拡充とセマンティクス見直し（CLAIMED 等の終端状態での例外登録可否、LOST 解決時に「発生前状態へ復帰」が業務的に適切か＝紛失は復帰ではなく補償完了として別状態が妥当かの検討）。
- architect 中: LOST エスカレーションの非トランザクション性（partial-apply）を ADR-0002 の受容範囲として明記し、将来 Outbox 移行対象とする（重大例外は臨界度が高い）。
- user-rep H3: 遅延対応の新到着予定日を構造化し、公開追跡の推定到着日へ反映（現状は自由テキスト `resolution_notes`）。
- tester 中 M3: ポーリングの条件付き GET（ETag/304 差分）は未実装（毎回全 partial 返却）。差分最適化は将来対応。
- tech-writer 中: 公開ページの例外時の問い合わせ導線・例外一覧の解決済み対応内容の後追い参照。

- ドメイン層（`ExceptionType`・`TrackingStatus`・`TrackingExceptionEvent`）は値等価・不変（`freeze`）・PORO 純粋性（Rails 非依存）を一貫維持。

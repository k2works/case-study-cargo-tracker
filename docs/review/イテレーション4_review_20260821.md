# イテレーション 4 開発成果物レビュー

- **対象**: IT4 の実装（US08 経路候補算出、8 SP。返済枠 8 件を含む）
- **レビュー日**: 2026-08-21
- **観点**: XP の 5 役割（programmer / tester / architect / technical-writer / user-representative）による並列レビュー

## エグゼクティブサマリー

**全緑のまま通っていた欠陥が 6 件見つかりました。** IT3 の教訓（安全装置は破るテストで固定する）を
DoD に入れて臨んだにもかかわらず、テスターが変異テストで実測すると、**4 つの安全装置が壊しても
赤にならない**状態でした。緑のテストは「壊れていないこと」を意味しません。

とくに重いのは 2 件です。

1. **すでに出港した便が候補に出ていました。** 航海スケジュールの一覧は IT3 で「既定は本日以降」に
   直したのに、経路探索には出発の下限がありませんでした。古い便ほど日数計算上は早く着くため
   **上位を占めます**。押さえられない船を前提にした経路が 1 位に出れば、経路設計者は以後この一覧を
   信用しません。**IT2・IT3 で同じ形の指摘（一覧は「毎朝どう使うか」から確かめる）を受けたのに、
   新しい画面で再発しました。**
2. **認可より先に型変換が走っていました。** 権限の無い営業担当者に 400 と
   `Parse attempt failed for value [not-a-date]` が返っていました。ADR-016 は IT4 でまさにこれを
   防ぐために起こした ADR であり、**その ADR を起こした同じイテレーションで、新しいエンドポイントが
   同じ欠陥を持っていました**。しかも MockMvc では再現せず、単体の検査は緑でした。

指摘件数: 高 14 件 / 中 20 件 / 低 15 件。

## 高優先度の指摘と対応方針

すべて IT4 のうちに対応しました。**壊すと赤になることを実測で確かめてから**採用しています。

| # | 指摘 | 視点 | 対応 |
| :--- | :--- | :--- | :--- |
| H1 | すでに出港した便が候補に出る | user-representative / tester | `Clock` を注入し、一覧と同じ「本日以降」に揃えた。境界のテストを追加 |
| H2 | 同じ航海が「直行」と「1 回積み替え」の 2 候補になる | programmer | 同じ船に乗り直す枝を刈った。1 本の航海は 1 区間で表す |
| H3 | 積み替えの最低 6 時間が探索側で無防備（壊しても緑） | tester | 探索側にも境界のテストを置いた |
| H4 | 積み替え上限の 2 つのガードが互いを隠す（どちらを壊しても緑） | tester | 条件側を単独で固定する検査を追加 |
| H5 | 積み替えの上限に上限が無い（外から任意に上げられる） | programmer / architect | 絶対の上限 3 を設けた。ADR-018 の決定 4 として起票 |
| H6 | ADR-018 に存在しない決定をコードが引用していた | programmer / architect | 既定値と絶対上限を分け、ADR・設計・画面を 1 つの値に揃えた |
| H7 | 認可より先に型変換が走る（実バックエンドでのみ再現） | architect | 値を `String` で受けてメソッド本体で変換。回帰は kind に対する検査に置いた |
| H8 | メタテストの必須規則に `validationAfterAuthorizationRule` が無い | architect | 名簿に追加。8 番目のサービスで落ちるようにした |
| H9 | ADR-018 決定 3 の「検査に落とせない」は誤り | technical-writer | 許可リスト方式で検査に落とした。ADR に誤りごと記録した |
| H10 | 期限を延ばす操作に荷主の合意が要ることが画面に無い | user-representative | 予約の期限といま探している期限の両方を残し、戻せるようにした |
| H11 | サーバが区別した理由を画面が捨てている | technical-writer / programmer | サーバの理由をそのまま見せる形にした |
| H12 | 期限を空にすると汎用エラーになり、次の操作へ繋がらない | programmer | 空なら探しに行かず、入力を促す |
| H13 | 「港湾制約を考慮する」という記述が 7 箇所に残っていた | architect / technical-writer | すべて決定を指す記述に書き換えた。US07 の受入基準には注記を添えた |
| H14 | 実バックエンドの検査が URL を手書きし、画面の組み立てを通らない | tester | 画面を操作して、実際に飛んだ問い合わせを見る形にした |

### 高優先度の対応で見つかった別の欠陥

- 画面が候補を並べ替えていないことを、**フィクスチャの並びが自然順と同じだったため誰も確かめていなかった**（tester M3）。推奨順と自然順を食い違わせて判別できるようにした
- デモ項目 5（寄港地と区間ごとの時刻を確かめる）の E2E が、**1 区間・寄港地ゼロの航海**を開いていた（tester M4）。途中に寄港する航海に変え、経由港と時刻まで見るようにした
- 実バックエンドの検査に固定の年月日が 4 箇所あり、その日を過ぎると原因と無関係なテストが同時に落ちる（tester M5）。業務タイムゾーンのヘルパに寄せた

## 視点別の要点

### programmer

制約の判断がドメインに集まっていること、SQL と集約の判定が食い違っていないことを確認。一方で
**同じ航海を積み替えとして二重に出す**欠陥と、**積み替え上限が外から任意に上げられる**問題を指摘。
モックがサーバより甘い箇所を 4 つ挙げた。

### tester

**変異テストを実際に走らせ、4 つの安全装置が壊しても緑であることを実測。** カバレッジは
`TransitPathFinder` で 96% line / 88% branch ありながら、3 種類の変異がすべて緑だった。
「この IT のカバレッジ数値は品質の根拠にならない」という指摘は正しい。

### architect

ADR-017・018 の決定が検査に落ちていることを確認する一方、**ADR-016 だけが決定は正しいのに
検査が空振り**していることを、実際の失敗モード（型変換）まで特定して指摘。設計への反映 16 件の
突合も行い、15 件反映済み・1 件部分的と判定した。

### technical-writer

**「否定の決定は検査に落とせない」という誤った一般則が定着しかけている**ことを、同じリポジトリの
実装（`RouteCandidatesAreNotPersistedTest`）を根拠に指摘。マニュアルの様式・キャプチャ・
ADR の構成を確認し、計画文書の同期漏れ（旧型名・DoD 未チェック・更新履歴）を挙げた。

### user-representative

**「朝いちばんに開いて仕事が前に進むか」で判断。** 3 クリックで候補が並ぶ導線と、候補ゼロの
作りを評価する一方、出港済みの便が混ざることで「順位を信用できない」と判定。受入基準 6 件のうち
5 件を達成、1 件（推奨順）を未達とした。**修正後は 6 件達成。**

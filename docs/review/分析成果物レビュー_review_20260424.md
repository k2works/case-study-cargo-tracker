## 総合評価

要件から設計までのカバレッジは広く、ドメイン分割・ユースケース粒度・品質属性の明文化は高水準です。
一方で、サービス構成・認証方針・DB 構成などのドキュメント間不整合が複数あり、実装着手時に設計判断が分岐するリスクがあります。
開発開始前に、高優先度 5 件の整合修正を行うことを推奨します。

## 改善提案（重要度順）

### 高

| # | 提案 | 指摘元 | 理由 | 対応方針 |
|---|------|--------|------|----------|
| H1 | インフラ構成図と環境定義を 7 サービス前提に統一する（`authms` / `handlingms` / `gatewayms` を含む） | xp-architect / xp-tester / xp-product-manager | `architecture_backend.md` と `architecture_infrastructure.md` のサービス一覧が不一致で、運用・テスト設計が成立しない | 修正する |
| H2 | ローカル開発 DB 記述を PostgreSQL 前提に統一する（MySQL 記述を除去） | xp-architect / xp-tester | `data-model.md` は PostgreSQL 前提だが、`architecture_infrastructure.md` のローカル構成が MySQL になっている | 修正する |
| H3 | 認証・権限モデルを最小権限で再定義する（`ROLE_OPERATOR` 一括権限を分割） | xp-product-manager / xp-user-representative / xp-tester | 営業・経理・荷役の権限分離がなく、業務統制と監査要件に抵触する可能性が高い | 修正する |
| H4 | 追跡照会の公開方針を要件・UI・非機能で統一する（認証必須 or 公開 API） | xp-interaction-designer / xp-architect / xp-tester | 「追跡照会のみ認証不要」と「ロール制御 UI」が混在し、実装時にセキュリティ設計が揺れる | 修正する |
| H5 | ユーザーストーリーと受入基準のトレーサビリティ表を追加する（US → UC → API / Test） | xp-tester / xp-product-manager | ストーリー数が多く、どの受入基準をどのテストで担保するか追跡できない | 修正する |

### 中

| # | 提案 | 指摘元 | 理由 |
|---|------|--------|------|
| M1 | `system_usecase.md` の高優先度偏重を再評価し、MUST/SHOULD を分離する | xp-product-manager | ほぼ全件が高優先度で、イテレーション計画の判断材料になりにくい |
| M2 | UC の一部を分割して INVEST を強化する（例: UC01, UC03） | xp-product-manager / xp-tester | 1 UC に分岐が多く、見積もり誤差とテスト複雑度が上がる |
| M3 | `location` 重複テーブルの同期戦略（ソースオブトゥルース、更新イベント、遅延許容）を明記する | xp-architect | Database per Service 方針自体は妥当だが運用ルールが未定義 |
| M4 | 非機能要件の SLO/SLA 指標を運用要件と 1 つの基準値に揃える | xp-architect / xp-tester | `non_functional.md` と `operation.md` で数値が近いが運用判断の基準が分散している |
| M5 | UI 設計のロール別ナビ制御を API 権限マトリクスと対応づける | xp-interaction-designer / xp-user-representative | 画面表示可否と API 実行可否の整合が文書上で追えない |

### 低

| # | 提案 | 指摘元 | 理由 |
|---|------|--------|------|
| L1 | 技術スタック表にバージョン確定日を追加する | xp-architect | 将来更新時に妥当性判断しやすくなる |
| L2 | 図中の用語（予約 ID / bookingId など）を表記統一する | xp-interaction-designer | 設計レビュー時の認知負荷を下げられる |
| L3 | 監視・運用の閾値に業務時間帯補正の注記を追加する | xp-user-representative | 夜間低負荷時の誤検知抑制に有効 |

## 矛盾事項

| # | 視点 A | 視点 B | 論点 | 推奨判断 |
|---|--------|--------|------|----------|
| 1 | UX 観点: 荷主・荷受人は追跡を手早く参照したい | セキュリティ観点: 原則 API は認証必須 | 追跡照会を公開するか | 追跡専用の限定公開 API（レート制限・監査ログ付き）を定義し、他 API は認証必須を維持 |
| 2 | PM 観点: 早期に価値提供したい | テスター観点: 要件粒度が大きく検証しにくい | ストーリー分割粒度 | 初回は業務フロー優先で残しつつ、実装前に受入基準ベースで 1 段階分割 |

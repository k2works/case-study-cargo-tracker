## S1: 列名の文字列で結果を読んでいた

R5 で N+1 を直したとき、まとめ引きの結果を `Map<Long, Map<String, Object>>` で受け、`"tracking_number"` というキーで値を取り出していた。

**列名の大文字小文字は DB で違いうる。** 違えば `null` になり、追跡番号が黙って空になる。承認する人は**どの貨物の話か分からなくなる**が、例外は出ない。

**推測せず実測した。**

| DB | 返ってきたキー |
| :--- | :--- |
| PostgreSQL 16 | `[tracking_number, id]` |
| H2（`h2-dialect` プロファイル） | `[tracking_number, id]` |

**いま壊れているわけではない。** それでも型（`HandlingTrackingNumberRow`）で受ける形に直した。静かに間違う経路は、落ちる経路より高くつく。

## S2: H2 のスモークが訂正の一覧を通っていなかった

`H2DialectSmokeTest` は「クエリが H2 でも解釈できる」ことを見る検査だが、**訂正・取り消しの一覧が対象に入っていなかった**。R5 でその経路の SQL を変えたにもかかわらず、両方向の方言差を見る網に掛からない状態だった。

経路を追加した。**ただしこの検査は「例外が出ないこと」しか見ない。** 行が 0 件なら中身が正しいかは分からない（S1 を実測で確かめたのはそのためである）。この限界は検査自身の Javadoc に書いた。

## S3: 列数の検査の対象範囲

`WideTableReadabilityTest` は `<thead>` を持つ表だけを数える。詳細画面の「項目名 / 値」の表は行ごとに `<th>` を置くため、`tracking/exception-detail.html` は `<th>` が 12 個あるが**横幅は 2 列**であり、横に送る必要が無い。

**見出し行を `<thead>` で書かない一覧を作ると、この検査からは外れる。** 見落としではなく決めごととして、検査の Javadoc に明記した。

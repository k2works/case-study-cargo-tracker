## 許容・保留（次イテレーション判断）

| 指摘 | 方針 |
| :--- | :--- |
| **取消が物理削除で改竄と是正を区別できない**（user-rep 高） | **許容**。取消は未精算（PENDING/OVERDUE）限定で、精算確定後は構造的に取消不能。よって「確定済み請求の事後改竄」は起こり得ず、対象は精算前の是正のみ。監査台帳（論理削除・操作ログ）の新規設計は影響が広く、次 IT の検討事項とする |
| **理由（reason）が任意入力**（user-rep 高） | **許容**。`description`（説明）が必須で理由の説明責任を担保しており、`reason` は補足的な監査コンテキスト。二重の必須化は入力負荷になるため任意を維持。data-model に設計意図を明記済み |
| **例外一覧の N+1**（`invoice_number_for_booking` を予約数ぶん呼ぶ）（programmer 中・tech-writer 低） | **保留**。例外件数は小規模。将来件数増加時にバルク取得 API（`invoice_numbers_for`）へ。コメントで明記 |
| **seq_number が位置ベース識別**（複数タブでの誤取消リスク）（programmer 低・architect 低） | **許容**。単一リクエスト内では安定。安定 ID 化は将来検討 |

## 良い点（維持）

- 符号規約を `InvoiceLineItem` に閉じる単一の真実点（T44 の実践）

- 正典 3 点（ADR・domain-model・data-model）の同期

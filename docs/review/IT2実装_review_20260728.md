# IT2 実装 マルチパースペクティブレビュー（2026-07-28）

対象: `apps/cargo-tracker`（IT2: US01 見積作成・US04/US05 貨物予約・US06 引き渡し）。
コミット範囲 `cc518678^..HEAD`（ブランチ `typescript/take-1`）。
前提: 全 189 テスト green・Playwright E2E 8 件 green・lint/typecheck/arch クリーン。

XP 5 視点（programmer / tester / architect / technical-writer / user-representative）で並列レビューを実施した。

## 総評

ヘキサゴナル層分離・BC 独立性（Booking→Shipper は ShipperExistenceChecker ACL 経由）・CQRS・ドメインイベントの骨格は設計と高水準で整合。一方で、(1) US04「見積情報との整合性確認」が未実装で見積→予約が分断、(2) 期限判定の日付粒度バグの入口、(3) エラー分類の一貫性欠如（Location/Estimation が plain Error）、(4) 荷主登録前提・UN/LOCODE の発見可能性欠如、が複数視点で収束して指摘された。

## 指摘一覧（優先度別）

### 高（クローズ前に対応）

| # | 指摘 | 視点 | 対応 |
| :--- | :--- | :--- | :--- |
| H1 | 期限判定が `getTime()` ミリ秒比較で、DATE 期限（当日00:00）vs 時刻付き ETA の粒度不一致。「当日着」を誤って刈るバグの入口。境界テストも欠落 | tester | **対応**（日付単位比較へ修正 + 境界テスト、Estimate 集約に集約） |
| H2 | 期限充足判定が service と controller で重複実装（DRY 違反・中核ドメインルール） | programmer | **対応**（Estimate.isDeadlineMet に集約） |
| H3 | Location/Estimation が plain Error を throw。controller で検証エラーと内部障害を区別できず、入力ミスが「予期せぬエラー」としてログ・画面に出る | programmer | **対応**（SharedValidationError 導入・Estimation に ValidationError パターン） |
| H4 | US05 危険物/冷凍の「申告欠落→エラー→非保存」の否定パスが HTTP 経路に無い（成功パスのみ） | tester | **対応**（統合テスト追加） |

### 低

- EventPublisher ポートの切り出し（IT4 購読実装とセット）、EstimateStatus.EXPIRED 未使用、findAll の N+1・未使用（→ 削除）、DI 配線スタイル不揃い、用語「荷主 ID/コード」二重化 → 一部対応（findAll 削除・用語補足）

## 良い点（維持推奨）

- ACL 境界の明快さ（Booking→Shipper 直接依存なし）、CQRS のコマンド/クエリ分離
- `CreateEstimateService` の `now?` 注入による決定論的テスト
- 状態遷移の不正パスのドメイン検証、テスト名が仕様として読める
- テストピラミッドの健全性（unit 厚め・統合は縦串・E2E は導線）

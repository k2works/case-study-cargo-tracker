## レビュー対象

- `docs/development/release_plan.md`（リリース計画: 31US・97SP・5 リリース）
- `docs/development/iteration_plan-1.md`（イテレーション 1 計画: US26/27/31/02・9SP）

## 総合評価

計画の骨格（一気通貫優先のリリース分割・US31 前倒し・US01 後置・依存順序の明示）は 5 視点すべてが支持しており、算術の整合（31US/97SP、明細と合計の一致）も検算済み。一方で、(1) 優先度列が正典 `user_story.md` と 6 件食い違いバッファ判断の根拠が崩れている、(2) イベントのコンシューマ側サービスが「主なサービス」列から落ちて SP 補正が構造的に漏れている（US15/US21/US28/US30）、(3) 計画が要求する品質ゲート（カバレッジ閾値・CI・TZ=UTC 実行）に実配線が無い、という 3 系統の欠陥があり、IT1 開始前の修正が必要。

### 評価サマリー

配分・合計の算術は完全に一致しており（31US / 97SP / リリース内訳・IT 別 SP・バーンダウンすべて整合）、リリース分割も「予約→追跡の一気通貫」という一本の背骨で説明できる良い計画です。一方で、リリース計画の優先度列が正典 `docs/requirements/user_story.md` の優先度と体系的にずれており（6 件）、特に正典「高」の US01 をフィーチャバッファ第 1 位に置いている点が最大の問題です。加えて IT4/IT5 の SP がベロシティ前提を超過しています。

### 良い点

- 合計の検算がすべて通る。US 数 7+11+4+5+4=31、SP 17+33+13+19+15=97、IT 別 SP 合計 97、リリース別 IT 割当もバーンダウン系列も一致。「合計は明細から導く」という take-6 の教訓が実際に守られている。
- 各リリースで「誰に何が届くか」が言える。ロール単位で受益者が特定できており、価値の届く単位になっている。
- US31 を Release 0.1 に前倒しした判断は妥当。根拠が具体的でコストベース。US01 を US21/US22 の後ろに置く依存判断も正典と整合。
- US14 を「最初のサービス間イベント」と位置づけ、KA/RR を高く振っているのは学習価値の使い方として正しい。
- IT1 の依存関係が明示され、4 ストーリーが「ログインして荷主を登録する」という 1 本のデモ動線に収まっている。

### 改善提案

- 【重要度: 高】優先度列を正典と突き合わせて修正する。US01（正典高→計画中）、US05・US10・US12（正典高→計画中）、US21・US22・US23（正典中→計画必須）。US01 は正典で「高」なのにバッファ後回し第 1 位で、判断の根拠が逆転。推奨は「US01 は正典どおり高だが依存順で最後に来るだけ」と整理し、バッファ第 1 位は US12 に譲る。優先度とスケジュール順序の混同を解消すること。
- 【重要度: 高】IT4（11SP）と IT5（12SP）をベロシティ前提に合わせて平準化する。IT5→IT6→IT7 方向に 3〜4SP を送り、IT7 を 8SP 前後に。計画時点で守れない数字を置くと初回の実績比較でベロシティ検証が機能しない。
- 【重要度: 中】US29 を 1.1 に置いた影響（1.0 では通関未済でも引取可能）をリリース 1.0 の「含まれる機能」に制約として明記し、1.0 は社内検証用と書く。
- 【重要度: 中】フィーチャバッファ SP の食い違い（17SP vs 15SP）を修正。
- 【重要度: 中】US31 の「通知される」と「同一メッセージ」の矛盾を「同一メッセージ優先・通知は別チャネル」で正典に注記して閉じる。
- 【重要度: 中】US31 の 2SP は過小の疑い。管理者解除の UI/API がタスクに無い。別ストーリー切り出し（推奨）か 3SP 化。
- 【重要度: 低】US27 の「ブラウザバックで戻れない」の充足手段を明示。
- 【重要度: 低】SP 補正の内訳（take-6 実績 X → 補正後 Y）を追跡可能にする。

### 懸念事項

- US26 と US31 は実質分離できず INVEST の Independent を意図的に諦めている。判断は支持するが、US31 を単独で先送りできないことをバッファ戦略に明記しておく。
- US02 の受入基準「荷主種別（個人/法人）を入力できる」が US03（IT2）と重なる。IT1 で種別セレクタだけ用意し法人固有項目を IT2 に回すと決めておく。
- バッファの成立条件（17SP のうち 9SP は確実に落とす前提）をステークホルダーに明示しないと、最終リリースで「見積機能がない」ことが不意打ちになる。
- IT1 は型の確立を含むため他 IT より 1 story 分軽くする方が実績データとして素直。

### スコープ外の発見

- 正典 `user_story.md` は 31 件中 26 件が「高」で優先度として機能していない。正典側の見直しか、リリース計画の優先度列への一本化かを決めるのが根本対処。
- US26 の「分割の経緯」注記は良い記録。他ストーリーの分割でも同形式を推奨。

### 評価サマリー

リリース分割とストーリー順序は設計の依存関係とよく整合し、過去 take の教訓が計画に織り込まれている点は水準が高い。一方で「主なサービス」列がイベントのコンシューマ側を落としており、SP 補正が構造的に漏れている。US15・US21・US28・US30 は計画が想定していないサービスにも変更が必要。IT1 の「型の確立」の中身が実装骨格の現状に対して薄く、US14 の 3SP はイベント基盤の初期構築を吸収できない。

### 良い点

- リリース境界がサービスの立ち上げ順と一致し、無理な分割になっていない。
- US31 を US26 と同時に作る判断・ロック状態のカラム永続化の明記は過去の失敗を回避できている。
- US18 の扱いは Gateway の「未登録は素通りさせない」設計と対になっている。
- US16→US29 のガード差し込みは同一 BC 内の別集約なので安全。

### 改善提案

- 【重要度: 高】US15 に bookingms の CargoSnapshot ACL（snapshot API 新設 + 契約テスト）が計上されていない。5SP→7SP 相当、または IT6 の独立タスクに。

## 総合評価

IT6 のふりかえり Try（安全装置を破るテスト・導線の機械検査・空虚なアサートの排除）が
実装とテストの両方に具体的な形で反映されており、**規律の水準は過去最高**である。
全 60 件の新規テストに「この式が偽になる入力」が付き、`NavigationReachabilityTest` は
3 IT 連続で再発した欠陥類型を機械検査へ落とした。

一方で、**防御を足したことが新しい単一障害点を作っていた**。同時実行の枠を
`/health/live` にも適用していたため、過負荷時に liveness が `503` を返し、
オーケストレータが「混んでいるだけで生きている」インスタンスを再起動する。
IT3 で DB について学んだ再起動ループが、セマフォ経由で同型再現していた。

また **IT7 で最も重い判断（Routing → Booking への ACL 方向反転）が ADR 化されず、
設計ドキュメントのイベントフロー図と実装が逆を向いていた**。
判断の理由はモジュールコメントに良質な形で書かれていたが、
コメントはコードと一緒に消える。ADR は決定が生き残るための形式である。

利用者代表からは「**この画面のまま日常業務は回らない**」という評価が出た。
理由は費用が無いことでも選択できないことでもなく、
**候補一覧に「もう出港した便」が混ざりうる**ことだった。

| # | 視点 A | 視点 B | 論点 | 判断 |

## 業務からの回答（利用者代表）

実装が「業務ルール未定義のため決めない」とした点に、利用者代表から回答があった。

| 事項 | 回答 | 反映 |
| :--- | :--- | :--- |

| 費用と経路確定の順序 | **確定は費用を見ずに行う操作ではない**。US09（選択・確定）と US01（見積）は、運賃が先か同時であるべき | ⏭️ IT8 の計画で順序を判断する |

| 入口を持たないロール | 荷役作業員・経理は**パイロット運用の対象から外す**という運用合意を明文化すべき | ⏭️ IT8 |

## 総合評価

IT1 の実装はヘキサゴナルアーキテクチャのレイヤー間依存ルールを概ね守り、値オブジェクトの型安全性・不変性の設計は良好です。一方、**3 つのユーザーストーリーすべてで受入条件と実装に乖離**が確認され、**Booking Context が Shipper Context の repository に直接依存**するアーキテクチャ違反が最大の技術的負債となっています。E2E テストの時限爆弾（2027 年問題）も CI/CD の信頼性リスクです。これらは IT2 で優先的に対処が必要です。

<summary>xp-programmer（高: 3 / 中: 2 / 低: 1）</summary>

### 評価サマリー
ドメインモデルの値オブジェクト設計と不変性の確保は良好ですが、**ユーザーストーリーの受入条件と実装の乖離**が複数箇所で確認され、また **Bounded Context 間の直接依存**がアーキテクチャ上の重大な問題として存在します。TDD サイクルを正しく回していれば受入条件の漏れは防げたはずであり、Red フェーズでの仕様の読み込みが不十分だった可能性があります。

### 良い点
- 値オブジェクトによる型安全性（`ShipperId`, `Email`, `DiscountRate` 等）
- 不変オブジェクト設計（`final` フィールドと必須項目の null チェック）
- `DiscountRate` のバリデーションをドメインオブジェクト内に閉じ込め
- `resolveCode` メソッドによる自動採番ロジックの分離
- `CorporateShipper` による法人荷主概念の型表現

### 改善提案
- 【高】Bounded Context 間の直接依存（`ShipperRepository` を Booking Context が直接利用）を ACL パターンで排除
- 【高】US02（住所欠落）/ US03（割引率 15% vs 30%）/ US04（寸法・個数・品名・希望引渡日欠落）の受入条件乖離を解消
- 【高】例外をドメイン固有例外クラスに置き換え（`EmailAlreadyRegisteredException`, `ShipperNotFoundException`）
- 【中】`CorporateShipper extends Shipper` を Composition に変更検討（種別増加時のクラス爆発回避）
- 【中】`resolveCode` で `UUID.randomUUID()` がハードコード → `ShipperCodeGenerator` インターフェース注入でテスト容易性向上
- 【低】`resolveCode` → `generateCodeIfAbsent` に改名

### 懸念事項
- メール重複チェックの競合状態（`findByEmail` と `save` の間に別トランザクションが割り込む可能性）
- UUID 先頭 8 文字の衝突確率（大量登録時に DB UK 制約が最終防衛線になっているか確認必要）

</details>

<summary>xp-tester（高: 3 / 中: 3 / 低: 1）</summary>

### 評価サマリー
ドメインモデル層のユニットテストは AAA パターンに従い、テスト名も仕様として読める良い基盤がある。一方、境界値テストの網羅性に複数の欠落があり、仕様と実装の乖離（`DiscountRate` 上限 15% vs US03 要件 30%）が未検出のまま。E2E テストのハードコード日付は時限爆弾であり、テストの信頼性を損なう。

### 良い点
- テスト名が仕様として読める（`shouldThrowWhenWeightIsZeroOrNegative` 等）
- AAA パターンの遵守
- テストピラミッドのバランスが概ね良好（ユニット〜E2E 各レイヤーにテスト存在）
- `Date.now()` による timestamp 付与でテスト間データ衝突を回避
- `ArgumentCaptor` による Cargo の中身検証

### 改善提案
- 【高】`DiscountRate`: 仕様（30%）vs 実装（15%）の乖離を検出するテストを追加（IT2 修正時の先行テスト）
- 【高】`booking.spec.ts` の `'2027-12-31'` / `'2027-06-30'` を `futureDate(daysFromNow)` ヘルパーに変更
- 【高】`CargoTest`: `Weight` 負値テストケース（`-0.001`）と最小正値テスト（`0.001` 成功）を追加
- 【中】`DiscountRate` 境界値テスト不足（下限 `0.0000` 成功・上限 `0.1500` 成功を追加）
- 【中】`RouteSpecification`: `LocalDate.now()` への直接依存を `Clock` 注入に変更
- 【中】`ShipperTest`: `Email` バリデーションの境界値（空文字、`@` のみ等）を追加
- 【低】`shouldThrowWhenBookingIdIsNull` が `NullPointerException` 期待 → `IllegalArgumentException` に統一検討

</details>

<details>
<summary>xp-architect（高: 3 / 中: 1）</summary>

### 評価サマリー
Booking Context から Shipper Context への依存が **2 種類の経路**で発生しており、ADR-010/011 が定めた「コンテキスト間の分離（shared domain 経由のみ）」ルールに違反しています。ヘキサゴナルアーキテクチャの層内ルールは正しく守られていますが、**境界づけられたコンテキスト間の結合**が最大の技術的負債です。

### 良い点
- ヘキサゴナルの層間依存は正しい（domain → infrastructure 依存なし）
- 値オブジェクトの設計品質が高い
- `Cargo` 集約のコンストラクタバリデーション
- `Location` を `shared.domain` に配置済み（共有カーネルの先例あり）
- `CargoAssembler` による DTO 変換の局所化

### 改善提案
- 【高】`ShipperId` を `shared.domain.model` に移動（ADR-010 との乖離解消）
- 【高】`ShipperRepository` 直接依存を ACL（`ShipperExistenceChecker` インターフェース）で分離
- 【高】ArchUnit テストにコンテキスト間分離ルール（`booking → shipper.domain.*` 禁止）を追加
- 【中】`IllegalArgumentException` 文字列マッチングをドメイン固有例外に置き換え

### スコープ外の発見
- `shared` と `shareddomain` のパッケージ命名不一致（ADR-010 は `shareddomain/`、実装は `shared.domain`）
- `allowEmptyShould(true)` の多用（パッケージ名タイポによるルール無効化を検知できない）
- `BookCargoCommand` が `application/internal/commandservices/` にある（ADR-010 では `domain/model/commands/` が正規位置）

</details>

### 評価サマリー
API の設計は RESTful の慣習に沿っており、エラーコードの体系化は良好です。一方、OpenAPI アノテーションが一切付与されておらず、Swagger UI から生成されるドキュメントは最低限の情報にとどまります。`private record` の重複定義も API ドキュメントの品質を下げています。

- `@DisplayName` 日本語テストがドキュメントとして機能
- Page Object パターンによるビジネス語彙でのテスト抽象化
- `@ConditionalOnProperty` による本番環境での Swagger UI 制御

### 改善提案
- 【高】`@Schema`, `@Operation`, `@ApiResponse` を各コントローラ・DTO に追加（条件付き必須ルール・バリデーション制約の文書化）
- 【高】`IdResponse` / `BookingIdResponse` / `ErrorResponse` の重複・非公開 record を共通化（OpenAPI スキーマに現れない、フィールド名不統一）
- 【中】`MethodArgumentNotValidException` のエラーレスポンスを構造化（フィールド名 + メッセージのリスト形式）
- 【中】`arrivalDeadline` の `@Future` が当日不可であることを `@Schema` で説明
- 【中】`cargoType` の有効値を `@Schema(allowableValues = ...)` で文書化
- 【低】`originUnlocode` / `destinationUnlocode` に UN/LOCODE の説明と例を追記

### スコープ外の発見
- `GlobalExceptionHandler`（`@RestControllerAdvice`）の不在（コントローラ増加時に同一パターンが増殖）
- 認証エラーのレスポンス形式が `ErrorResponse` と異なる可能性（Spring Security デフォルトレスポンス）

### 評価サマリー
荷主登録・予約登録の基本フローは動作しており、営業担当者として「荷主を登録して予約を作成できる」という最低限の業務は実施できます。しかし、**受入条件に含まれていた重要項目（住所、割引率の正しい上限、貨物詳細）が実装に反映されておらず**、本格的な業務利用には不十分です。

- 荷主登録から予約登録までの基本フローが一貫している

- 【中】状態・種別表示の日本語化（`PRELIMINARY` → 「仮受付」、`GENERAL` → 「一般」等）
- 【中】貨物詳細フィールドの追加（寸法・個数・品名・希望引渡日、US04 受入条件）
- 【中】重複メール登録時の既存荷主選択 UI（US02 受入条件 2 番）——現在はエラーメッセージのみで既存荷主へのリンクがない

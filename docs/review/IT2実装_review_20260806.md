# IT2 実装レビュー（2026-08-06）

## レビュー対象

- US04 貨物予約を登録する / US32 荷主情報を訂正する の実装一式
- Booking Context（`Cargo` 集約・`BookingStatus`・CQRS クエリ側）、Shipper Context の訂正、
  貨物予約 3 画面・荷主編集画面、マニュアル 04 章

**Agent ツールは使用していない。** 5 つの XP 視点（programmer / tester / architect /
technical-writer / user-representative）を順に当てて実施した。

## 総合評価

**受入基準は満たしており、遷移規則・楽観的ロック・監査ログはいずれも「働くこと」を
テストで確認できている。** 一方で、**ロールへの機能開放を、その前提が揃う前に行った**
欠陥が 1 件見つかった。IT1 の教訓（「安全装置は破るテストで固定する」）は守れたが、
**「開放してよいかを先に確かめる」という別の型の確認が抜けていた。**

### 高

| # | 提案 | 指摘元 | 理由 | 対応 |

| H1 | 貨物予約一覧を ROLE_SHIPPER に開放してはならない | architect / user-representative | **利用者アカウントと荷主を結びつける手段が無く、荷主から他社の予約まで見える。** `non_functional.md` は ROLE_SHIPPER を「自社予約・追跡（Phase 2）」と定めており、「自社の」を実現できない状態での開放は正典に反する | **IT2 内で修正済み。** 開放を取り消し、URL 直打ちでも 403 になることをテストで固定。**US34 を起票**（Release 2） |

## 良い点

- **遷移表の全 64 セルを網羅**し、拒否側を自動生成する形にした。状態が増えても書き忘れない
- **安全装置をすべて壊して確認した**（楽観的ロック・ArchUnit・依存検証・監査ログ・
  長さ検査の順序）。「入れたこと」で終わらせていない
- ADR の「〜しない」の棚卸しで、**9 件中 4 件が文章だけだった**ことを見つけてテストにした
- SonarQube のセキュリティホットスポットを抑止せず、**実際の欠陥（ReDoS）として直した**

## 反省

- **時間で守ろうとしたテストが、脆弱な実装に戻しても緑だった。** 分岐の結果で判定する形に
  書き直して初めて赤になった。「安全装置は破るテストで固定する」を、装置の側だけでなく
  **テストの側にも当てる**必要がある
- 置換で 1 つのテストを 3 つの入れ子クラスすべてに入れてしまい、そのうち 2 つは
  意味を成さないまま緑だった。**機械的な置換の結果を目で確かめる**

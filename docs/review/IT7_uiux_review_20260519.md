# IT7 UI/UX レビュー

## レビュー対象

- **S17**: 追跡詳細・管理（既存画面・例外機能追加）
- **S18**: 例外登録（新規画面）
- **S19**: 例外対応一覧（salt 図未作成）
- **関連ストーリー**: US19（遅延例外処理）、US20（破損・紛失例外処理）

## 総合評価

S17/S18 は既存画面パターンとの整合性が高く業務フローとも概ね一致しているが、**S19（例外対応一覧）の salt 図未作成**・**「対応入力 → 解決」UI の所在不明**・**S18 の種別別フォーム分岐の不足**という 3 点が IT7 着手前に解消すべき設計上の重大欠陥として確認された。また escalation 警告の強度が実業務の重大性に対して不十分であり、モバイル対応への配慮も欠落している。

## モダンデザイン準拠サマリー

| 評価項目 | 状態 | 備考 |
|---|---|---|
| カラーシステム | 要改善 | 例外履歴 RESOLVED / S18 警告への状態色トークン割り当てが未指定 |
| タイポグラフィ | 要改善 | 追跡番号と予約番号の主従関係が salt 図から不明 |
| Elevation & Surface | 要改善 | 例外履歴と追跡イベントの視覚分離が `---` 区切りのみ |
| コンポーネント一貫性 | OK | S17 のアクションボタン配置は他画面と一貫 |
| スペーシング | 要改善 | ボタン階層（Primary/Secondary/Danger）の割り当て未定義 |
| レスポンシブ / Adaptive | 要改善 | S18 がモバイル対応枠に含まれていない |
| ダークモード | 未対応 | プロジェクト方針として未定義のため許容 |
| 状態デザイン（空 / Loading / Error） | 要改善 | 例外履歴の空状態・S18 422 エラー時の表示先が未定義 |

## 改善提案（重要度順）

### 高（IT7 着手前に対応すべき）

| # | 提案 | 箇所 | 指摘元 | 理由 |
|---|------|------|--------|------|
| H-1 | S19 例外対応一覧の salt 図を作成する | S19 | 両エージェント | 追跡管理者の「未対応例外の見落とし防止」に必須。コレクションビューとして S16 と同パターンで設計する。必須カラム: 例外 ID / 追跡番号 / 種別バッジ / 発生日時 / 経過時間 / 発生場所 / 対応状態 / escalated フラグ。初期表示は「未対応のみ」フィルタ適用。タブに件数バッジ（例外対応(5)）を表示する |
| H-2 | 対応入力 → 解決 UI の所在を salt 図で明示する | S17 / S19 | インタラクションデザイナー | PATCH /exceptions/{exceptionId}/resolve に対応する画面が未定義。推奨案: S17 例外履歴テーブルの未解決行に [対応を入力] [解決] ボタンを追加し、モーダル（S17.modal-resolve）で解決処理を完結させる |
| H-3 | S18 の種別別フォーム分岐を明示する | S18 | インタラクションデザイナー | 「遅延」選択時に新しい到着予定日（ETA）入力欄、「破損」選択時に破損部位・写真添付欄が US19/US20 受入条件から必要。S20 と同じ `{(○○選択時) ...}` 表現で salt 図に追加する |
| H-4 | S18 紛失警告を二段階確認に強化する | S18 | 両エージェント | 現状の静的テキストは重大操作の確認表現として不十分。赤ボーダー + amber-50 背景 + 確認チェックボックス「紛失であることを確認しました（管理職に自動通知）」を必須化。通知先（誰に飛ぶか）を画面に明示する |
| H-5 | S18 のモバイル対応を設計に明示する | S18 | ユーザー代表 | 荷役作業員は現場（港湾・倉庫）でスマートフォンから破損等を記録する。1 カラム縦画面レイアウト・写真添付欄・UN/LOCODE の現在地サジェスト・発生日時デフォルト「現在時刻」が現場実務に必要 |

<summary>xp-interaction-designer（高: 5 / 中: 5 / 低: 3）</summary>

### 評価サマリー

S17/S18 は既存画面パターンとの整合性が高く骨格は妥当ですが、**S19 の詳細設計欠落・「対応入力 → 解決」UI の所在不明・S18 のステートフルなフォーム挙動（紛失警告・LOAD/UNLOAD 条件分岐）の表現不足** により、IT7 着手前に解像度を上げないと実装中に仕様の口頭追加が発生するリスクが高い状態です。

### 良い点

- S17 のアクションが「状態を更新／例外を記録／代替ルート要求」と業務オブジェクトの操作軸で並列化されており、OOUX アクション定義と一致
- S18 で「紛失選択時に escalation 通知の事前告知ブロックを出す」設計が US20 の `escalated=true` 自動付与を送信前に可視化している
- 画面遷移が「S16 → S17 → S18 → S17 戻し」と単純な往復構造で業務シナリオ D と 1:1 対応
- 例外履歴を S17 内にインラインで配置し、S18 から戻った直後に結果確認できる導線

### モダンデザイン準拠状況

- 本プロジェクトは Tailwind ベースの独自デザインシステムのため MD3 厳密準拠は評価対象外
- 例外履歴 RESOLVED 表示・S18 紛失警告への状態色トークン割り当てが未指定
- S17 のアクションボタン 3 つが同じ重みに見える（例外を記録は Danger 寄り Secondary が妥当）
- 例外履歴テーブルと追跡イベントの `---` 区切りのみの視覚分離は不十分

### 懸念事項

- アクセシビリティ宣言とのギャップ: S17 例外履歴の「色 + アイコン + ラベルの 3 重表現」が検証不能
- S18 で種別ラジオ変更時の動的フォーム展開後のフォーカス移動先が未定義（SR 利用者リスク）
- 例外登録 API が 422 を返すケースの表示先（S18 or S17）が未定義
- S19 の一覧 API（Query 側）が IT7 バックエンドスコープに入っているか未確認

### スコープ外の発見

- OOUX 整理表の TrackingActivity アクションに「代替ルート要求」が存在しない（業務オブジェクト定義側の更新が必要）
- シナリオ D と画面の整合性ガバナンスが弱い（validating-iteration-plan での三角検証を推奨）
- 追跡管理者が現場から S18 を使うユースケースがあれば、レスポンシブ方針表の S18 をモバイル対応枠に移すべき

<summary>xp-user-representative（高: 3 / 中: 4 / 低: 3）</summary>

### 評価サマリー

S17 の例外機能追加は業務フローに概ね沿っており実用的ですが、**S18 の「紛失選択時の escalation 警告」が静的テキストで弱く**、また **S19（例外対応一覧）の salt 図未作成**により業務上重要な「未対応例外の見落とし防止」要件が設計から欠落しています。

### 良い点

- S17 の操作ボタンが業務動詞で並んでおり、追跡管理者の作業単位と一致している
- S17 内に「例外履歴」と「追跡イベント」が同居しているのは正しい設計（別画面に飛ばないのが実務に合っている）
- S18 で例外種別をラジオボタンにしているのは正解（種別 3 つなら全選択肢を見える化する方が速い）
- 例外 ID（E-001）が履歴一覧で識別できるのは、追跡管理者間の口頭連携に有用

### モダンデザイン準拠状況（ユーザー視点）

- ラジオボタンによる種別選択は LINE や Slack の通報フォームと同様で違和感がない
- escalation 通知の警告表現が銀行アプリ・配送アプリの「重大操作確認」表現（赤背景 + 確認チェックボックス + 二段階確認）と比べて弱い

### 懸念事項

- 追跡 ID の表記方法（TRK と B- のどちらが主）は利用者役割によって異なる可能性がある
- 「代替ルート要求」と「例外を記録」のどちらを先に押すべきか迷う可能性がある
- 例外履歴・追跡イベントの時系列並び順（昇順か降順か）が不明
- escalation 通知の到達確認（通知失敗時に気づけない）

### スコープ外の発見

- 荷役作業員と追跡管理者の権限差によるボタン出し分けが設計に明記されていない
- オフライン環境（港湾現場の通信不安定）での下書き保存 → 通信回復後同期の検討
- 紛失 → 発見 → 通常輸送復帰の再開フローが存在しない

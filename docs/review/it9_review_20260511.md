# IT9 コードレビュー結果

## レビュー対象

- イテレーション: IT9（US10 経路条件再算出・US22 法人割引・US23 精算処理）
- 対象マイクロサービス: bookingms / billingms / frontend
- レビュー日: 2026-05-11

---

## 総合評価

IT9 は Phase 2 を完了する 21SP を 1 日で実装した。インサイドアウトアプローチを厳守し、ドメイン層の状態遷移ガード（`updateRouteSpec()` / `settle()` / `markOverdue()`）を正確に設計できている点は高く評価できる。一方、Invoice の再構成コンストラクタでのフィールド欠落・割引率の自動取得未実装（US22 受入条件 1 未充足）・境界値テストの不足など、**受入条件の完全性**と**ドメインモデルの整合性**に重要な課題が残っている。IT10 着手前に高優先度の指摘を解消する必要がある。

| # | 提案 | 箇所 | 指摘元 | 理由 |

## エージェント別フィードバック詳細

<details>
<summary>xp-programmer（高: 2 / 中: 2 / 低: 2）</summary>

### 評価サマリー
インサイドアウトアプローチが徹底されており、ドメイン層の状態遷移ガードの設計は正確。ただし Invoice の再構成コンストラクタでのフィールド欠落と toRecord() の税額計算ロジックは即座修正が必要。

### 良い点
- `Cargo.updateRouteSpec()` の CONFIRMED 以降変更不可ガードが状態遷移として適切に実装されている
- `Invoice.settle()` / `markOverdue()` のガード節（IllegalStateException）が正確に状態遷移を保護している
- `Money.ofJpy(toLong())` による回避は技術的な次善策として適切

### 改善提案
- 【重要度: 高】Invoice 再構成コンストラクタで discountRate / discountAmount / paidAt が復元されない。`reconstitute()` または DB 読み込み用コンストラクタにこれらのフィールドを追加する必要がある
- 【重要度: 高】`toRecord()` の taxAmount が `baseAmount.toLong() * TAX_RATE` で計算されており、割引後金額（finalAmount）が基準になっていない。精算書の税額が過大になる
- 【重要度: 中】`updateRouteSpec()` の変更不可判定が `status != PRELIMINARY && status != ROUTING` のブラックリスト方式。将来ステータスが追加された場合に漏れが生じるため `EnumSet.of(CONFIRMED, ARRIVED).contains(status)` のホワイトリスト方式を推奨
- 【重要度: 中】`applyDiscount()` の `discountRate` が `BigDecimal` 型で受け取られているが、0〜1 の範囲か 0〜100 の範囲かが不明瞭。ドキュメントに明記するか、型による制約を追加する

### 懸念事項
- Invoice の再構成コンストラクタ問題は、読み込んだ Invoice で `settle()` を呼んでも割引計算が再現できないため、精算フロー全体が機能しない重大なバグになる可能性がある

</details>

<summary>xp-tester（高: 2 / 中: 1 / 低: 1）</summary>

### 評価サマリー
ドメイン層のハッピーパステストは実装されているが、境界値・異常系テストが不足しており、ビジネスルールの違反が検知できない状態。

### 良い点
- `InvoiceTest` に `applyDiscount()` / `settle()` / `markOverdue()` の基本ケースが存在する
- `CargoTest` に `updateRouteSpec()` の正常遷移テストが存在する

### 改善提案
- 【重要度: 高】`applyDiscount()` の境界値テストが不足。`discountRate = 0`（割引なし）・`discountRate = 0.30`（最大 30%）・`discountRate = -0.01`（負の値 → 例外期待）・`discountRate = 1.01`（100%超 → 例外期待）を追加する
- 【重要度: 高】`markOverdue()` の異常系テストが不足。`status = PAID` の後に `markOverdue()` を呼ぶと例外が発生することを確認するテストを追加する
- 【重要度: 中】`updateRouteSpec()` で `status = CONFIRMED` の場合に例外が発生することのテストが不足
- 【重要度: 低】`PUT /api/booking/v1/cargos/{bookingId}/route-spec` の統合テストで deadline が過去日の場合のバリデーションテストがない

### 懸念事項
- 割引率の負の値・100%超が受け入れられる場合、負の請求額や過剰請求が発生する可能性がある

</details>

<details>
<summary>xp-architect（高: 2 / 中: 2 / 低: 0）</summary>

### 評価サマリー
マイクロサービス間の責務分離は適切に保たれているが、Money 値オブジェクトの制約回避（toLong() 変換）がドメインモデルの整合性を損なっている。IT10 前に解消が必要。

### 良い点
- billingms / bookingms の責務境界が明確に維持されている
- InvoiceRepositoryImpl での INSERT / SELECT / UPDATE が一貫して実装されている

### 改善提案
- 【重要度: 高】`Money.subtract(Money other)` を追加して `toLong()` 回避パターンを排除する。現状の回避策はドメインモデルの型安全性を損ない、将来の多通貨対応時に問題が生じる
- 【重要度: 高】Invoice の再構成コンストラクタでフィールドが欠落しているため、DB からの復元後に割引計算・精算処理が不整合になる。すべての永続化フィールドを再構成コンストラクタに含める必要がある
- 【重要度: 中】`InvoiceSettlePage` が毎回 `/calculate` を呼ぶことで Invoice が重複生成されるリスクがある。既存 Invoice を参照する `GET /api/billing/v1/invoices/{invoiceId}` エンドポイントを用意し、精算フローを参照→確認→決済の順序に明確化する
- 【重要度: 中】`Invoice.settle()` の前提として Invoice が存在している必要があるが、この順序制約がコードに暗黙的。アプリケーション層で順序ガードを明示する

### 懸念事項
- 現状の toLong() 変換は日本円（整数）には機能するが、多通貨や小数点以下の金額で精度が失われる

</details>

- 【重要度: 中】割引率の入力フィールドに「0〜30% の範囲で入力してください（法人のみ適用）」等のヒントテキストがない
- 【重要度: 低】US22 の受入条件「割引計算の根拠（割引率・基本料金・割引後料金）が精算書に記載される」が画面で確認しにくい。計算式を表示する補足テキストを追加する

### 評価サマリー
US22 の中核受入条件（割引率の自動取得）が未実装であり、個人荷主への割引非適用チェックもないため、US22 は受入条件を完全には満たしていない。

### 良い点

### 改善提案
- 【重要度: 高】US22 受入条件「荷主種別が法人の場合、割引率が自動的に取得・表示される」が未実装。現状は手動入力であり、営業担当者が正しい割引率を知らなければ機能しない
- 【重要度: 高】US22 受入条件「個人荷主の場合は割引が適用されない」の確認手段がない。個人荷主の貨物でも割引率を入力できてしまう

- 【重要度: 中】US23 受入条件「精算状態が精算済に更新される」の確認が画面でできない。精算後に状態が変わったことを示す表示が必要

### 懸念事項
- 割引率の自動取得が未実装の場合、US22 の受入条件 1 は未達成となり、イテレーション完了の判断を再検討する必要がある

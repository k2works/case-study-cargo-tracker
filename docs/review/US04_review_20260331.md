## 総合評価

ヘキサゴナルアーキテクチャの基本構造（ポート＆アダプター、ファクトリメソッド、値オブジェクト）は Shipper コンテキストとの一貫性を保ちながら正しく実装されており、72 テストが全件グリーンという安定した基盤が構築されています。

一方、**設計上の重大な問題が 3 件**確認されました。特に「DB 復元時に登録イベントが副作用として生成される」という問題は将来のバグの温床になります。また、**境界づけられたコンテキスト（BC）の分離が全層で破られており**、shipper コンテキストへの依存が booking の domain・application・web 全層に散在しています。

## 改善提案（重要度順）

### 🔴 高（早期対応すべき）

| # | 提案 | 箇所 | 指摘元 | 理由 |
|---|------|------|--------|------|
| H1 | `BookingRepositoryImpl.toBooking()` で `Booking.register()` を使わず `Booking.reconstitute()` を追加する | `BookingRepositoryImpl.java`, `Booking.java` | tester / programmer | DB 復元のたびに `BookingRegisteredEvent` が生成される設計上の副作用。将来的に重複イベント発行バグを引き起こす |
| H2 | `BookingController` が `BookingRepository` を直接使用しないよう `FindBookingUseCase` を導入する | `BookingController#detail()` | architect / programmer | UseCase を経由しない DB アクセスはレイヤー違反。ドメインロジックが Controller に漏れる起点になる |
| H3 | `booking.domain.ShipperId` を booking コンテキスト内で独自定義し、shipper コンテキストへのドメイン層依存を断ち切る | `Booking.java`, `BookingRegisteredEvent.java` | architect | BC 分離の根本問題。shipper の型変更が booking ドメイン全層に波及する |
| H4 | `ShipperVerificationPort` と `ShipperLookupPort` を booking コンテキスト内に定義し、ACL アダプター経由でのみ shipper コンテキストを参照する | `RegisterBookingUseCase`, `BookingController#lookupShipper` | architect | UseCase・Controller が他 BC の Repository を直接使用している。変更の影響が全層に波及する |
| H5 | `HomeController.login()` のパスワード漏洩リスクを排除し、プロファイル判定をポジティブ条件に変更する | `HomeController.java` | programmer | `devPassword` が HTML レスポンスに含まれる。プロファイル未設定環境でも認証情報が露出する |
| H6 | `BookingController` テスト（`@WebMvcTest`）を追加する | `BookingController.java`（テストなし） | tester | バリデーション失敗・荷主不存在・成功のリダイレクト分岐が全て未検証。Web 層テストが完全に欠落 |
| H7 | `List<Object> domainEvents` をマーカーインターフェース `DomainEvent` に変更し型安全性を確保する | `Booking.java`, `Shipper.java` | programmer / tester | 静的解析が機能しない。テストでのキャストが常に必要。Shipper と同時変更で一貫性を確保 |

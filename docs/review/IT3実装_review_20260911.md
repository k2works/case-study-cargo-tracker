## 総合評価

判定を純粋関数へ切り出す方針（`decide` / `isValidCsrf` / `cookieValue` / `isLocked`）が徹底され、
全ロール × 全要件のデシジョンテーブルをテストで固定できている。IT2 で指摘された構造的負債
（合成ルートの位置・`Principal` の置き場所・リクエスト組み立ての責務）も解消した。

一方で、**「テストが緑でも運用と安全性で破れる」欠陥が 5 件**見つかった。いずれも
実装としては動いており、テストも通っていたものである。

1. `user_roles` が複数行を許すため、**認可がリクエストごとに非決定的**になりうる
2. 環境判定が**フェイルオープン**で、本番の環境変数注入に失敗すると開発用の資格情報が画面に出る
3. 存在しない利用者でハッシュ照合を省いており、**応答時間の差でユーザー名の存否が判別できる**
4. `/health/live` が DB トランザクションを開き、**防ごうとした再起動ループを起こす**
5. BCrypt の計算中に DB コネクションを掴んでおり、**プール枯渇の第一候補**

利用者視点では「詰まったときの次の行動」が欠けていた（パスワード再設定・ロック時の連絡先・
別端末で締め出されたときの案内）。とくに**同時セッション 1 で締め出された利用者に
タイムアウトの文言を出すのは事実と違う案内**であり、障害報告につながる。

これらはすべてクローズ前に対応した。

## レビューを受けての気づき

**「テストが緑であること」と「運用で壊れないこと」は別の問題である。** 本イテレーションで
見つかった高優先度 5 件（非決定的な認可・フェイルオープン・タイミング差・liveness の DB 依存・
コネクション占有）は、すべてテストが緑のまま存在していた。いずれも「動作の正しさ」ではなく
**「壊れ方の設計」**に属する欠陥である。

自作の認証基盤では、正常系のテストをいくら足してもこの種の欠陥は見つからない。
**攻撃者視点（列挙・タイミング・注入）と運用視点（障害時・設定漏れ）を明示的に依頼する**
レビューの立て方そのものが、安全網の一部である。

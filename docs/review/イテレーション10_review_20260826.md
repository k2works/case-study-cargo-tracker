## 懸念事項（記録して次へ）

- **2 回目の誤配の扱いが決まっていない**（user-rep・architect）。`Misroute` は 1 件しか持たず、組み直した先でまた外れたときに 1 回目が残る。実務では「1 度外れた貨物は続けて外れる」ことが珍しくなく、**料金調整は回数で変わる**。IT11 で決める
- **誤配の記録を経理が読む手段がない**。28-8 の根拠は予約詳細にしか出ず、経理担当者は予約詳細を開けない。料金調整の実装は US21（Release 2.0）なので、そこで参照経路を作る
- **陸揚げ待ちの一覧は「未着手」を区別しない**（writer）。手配が済んだ行を消す手段がなく、件数が増えると「毎朝上から片付ける」使い方が破綻する
- **リスナー内の 2 ユースケース間にトランザクション境界がない**（architect）。IT9 の `CustomsStatusChanged` と同じ構造で、購読側で 2 つ目・3 つ目のユースケースを直列に呼ぶ形が定着しつつある
- **bookingms と trackingms が同じ `offRoute` を独立に消費**しており、片方だけ失敗する状態（予約は誤配だが例外は未起票／その逆）が起こりうる

## スコープ外の発見

- `AdvanceBookingUseCase.advance` の引数 5 つのうち 3 つが `String`。`handlingType` と `locationUnLocode` を取り違えてもコンパイルが通る
- `AssignmentResult.daysBeyondDeadline` が `Long`（null 可）で、REST 応答の都合が application 層まで染み出している
- `BookingStatus` の全値がラベル（`TURN_LABELS`）を持つことが検査されていない。IT10 でキャプチャを撮って初めて 3 つの欠落に気づいた
- モックの `daysBeyondDeadline` 計算が 0 を返し得る（本物は「超えないなら null」）→ 本 IT で 1 か所に寄せる際に修正済み

## このレビューが示したこと

**サービス単体・ドメイン層・実環境 API がすべて緑でも、画面から踏むと成立しない**という
IT9 と同じ形が、より深い場所で再発しました。今回の特徴は 2 つです。

1. **絞りが 3 か所に分かれていた**（高 6）。集約から期限検査を外した変更は正しかったが、
   その手前（SQL・探索の枝刈り）に同じ絞りが残っており、緩めたつもりが効いていなかった。
   ADR にその決定を書き、集約に検査も置いたのに、**実際には一度も通っていない経路**だった
2. **「事実」と「状態」を設計文書では正しく分けたのに、コードは事実側で分岐していた**（高 5）。
   `domain-model.md` は「状態は再設計で ROUTED へ戻る／事実は戻らない」と明記しており、
   実装のコメントも「状態ではなく事実を見る」と正しく書かれていた。**宣言が正しいまま
   使い方が誤っている**形で、コメントを読むだけでは気づけない

どちらも、実環境テストが API を直接叩いていたため空振りしていました（tester 高 2）。

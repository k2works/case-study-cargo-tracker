## 総合評価

IT4 は Routing→Booking の確定経路参照を SQL ベースの ACL（`ISelectedRouteLookup`）で実装し、ArchUnit に BC 独立ルールを追加、Cargo 集約の状態遷移をガード付きで凝集させるなど、ヘキサゴナル＋BC 独立の骨格を規律正しく守った質の高い実装である（全 198 テスト緑・警告 0）。一方で、(1) 確定経路が Routing の `selected_route_leg` と Booking の `leg` に二重永続化されながら「真実の源泉」が未明文化、(2) 経路選択がインデックス依存の再算出に立脚、(3) `BookingConfirmedEvent` のハンドラ未実装、(4) 実装済みだがテスト未整備の防御分岐（selectedIndex 範囲外・通知重複）、(5) 2 ロール引き継ぎでの営業担当者への文脈提示不足、が主要な改善対象である。

- 指摘件数: 高 7 件 / 中 5 件 / 低 6 件（重複統合後）

## 懸念事項

- **差し戻し時の Routing 側 SelectedRoute のライフサイクル欠落**（architect）：`Cargo.ReturnToRouting()` は Booking の `CargoItinerary` を null に戻すが、対応する Routing `selected_route`（予約単位 UNIQUE）を無効化する経路がない。「Routing に確定経路が残るが Booking に旅程がない」不整合期間が生じる。H1（真実の源泉）と対で整理が必要。
- **ACL の SQL とテーブルスキーマの結合**（architect）：`SelectedRouteLookup` は物理列名依存の生 SQL。Routing がテーブル構造を変えると Booking の ACL が静かに壊れる。ArchUnit は SQL 文字列を検出できないため統合テストでの回帰担保が必須。
- **通知の状態不変条件の非対称**（programmer）：`RouteNotification.Create` は `RouteProposed` 限定のため確定後（`Confirmed`）は通知不能。US12 の受入条件と照合し、理由をドメインコメントに残す。

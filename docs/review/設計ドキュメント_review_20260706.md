# F# 版設計ドキュメント レビュー結果（2026-07-06）

## レビュー対象

`docs/design/` 配下の F# 版設計ドキュメント一式（10 ファイル）

- architecture_backend.md / architecture_frontend.md / architecture_infrastructure.md
- domain-model.md / data-model.md / ui_design.md

レビュー方式: XP エージェント 5 体（xp-product-manager / xp-architect / xp-interaction-designer / xp-tester / xp-user-representative）による並列マルチパースペクティブレビュー。

## 総合評価

F# の型駆動設計（判別共用体 + スマートコンストラクタ + Railway Oriented Programming）による DDD/ヘキサゴナル/CQRS の移植方針は全エージェントから一貫して高評価であり、ドメインモデル単体の完成度・テスト戦略の規律・UI の OOUX 設計は実装着手に足る水準にある。一方で、(1) ドキュメント間の技術的整合性（DomainEvent 設計・モジュール構成・型定義がドキュメント間で矛盾）、(2) ユーザーストーリーの画面カバレッジ欠落（US12/13/14/16/17/21/22 の操作導線が UI 設計に無い）、(3) コア設計成果物へのトレーサビリティ断絶、の 3 系統の高重要度問題が検出された。いずれも実装前のドキュメント修正で解消可能であり、着手前に対応すべきである。

### 評価サマリー
F# の型駆動設計（DU + スマートコンストラクタ + ROP）による DDD/ヘキサゴナル/CQRS の移植方針は思想として一貫しており、ドメインモデル単体の完成度は非常に高い。ただしドキュメント間の技術的整合性に高重要度の不整合が複数存在し（特に domain-model.md と architecture_backend.md の間の DomainEvent 設計・モジュール構成・型定義の食い違い）、このまま実装に着手すると F# のファイル順コンパイル制約で手戻りが発生するリスクがある。

### 良い点
- 型駆動設計の徹底：`BookingState`/`PaymentState`/`CustomsStatus`/`ExceptionResolution` を「その状態で必要なデータのみ」を持つ DU で表現し nullable + 実行時検証を排除。C# 版対応表も移行意図が明確。
- ポートの関数化：単機能は関数型、複数操作は「レコード of 関数」の使い分け。DI コンテナ依存を排し、test_strategy.md のモックライブラリ不採用方針と整合。
- VoyageNumber のコンテキスト分離：各 BC 固有の単一ケース DU でコンテキスト跨ぎの取り違えをコンパイルエラー化。Shared Kernel 最小化として自然。
- 金額の整数管理：`Money`（最小通貨単位 + 通貨コード）を DB で `INTEGER + VARCHAR(3)` にマッピングし `NUMERIC` を回避。
- 二方言戦略の割り切り：SQL を ANSI 標準範囲に限定、DB テストは Testcontainers の実 PostgreSQL のみという現実的な回答。

### 改善提案
- 【重要度: 高】DomainEvent の設計がドキュメント間で矛盾し、F# のファイル順コンパイルで循環参照になる（domain-model.md は全 BC の具体型を直接参照する巨大 DU、architecture_backend.md は Payload レコード方式）。統一して ADR 化すべき。
- 【重要度: 高】モジュール構成・名前空間が 2 ドキュメントで逆（レイヤーファースト vs 垂直スライス）。F# では namespace 構成がファイル順・プロジェクト分割を規定するため一本化が必須。
- 【重要度: 高】参照されている ADR-0002/ADR-0003 が実在しない（docs/adr/ は index.md のみ）。起票すべき。
- 【重要度: 中】`TransportStatus` の DU ケースが domain-model Shared と backend で全く異なる。`TrackingStatus` との変換規則も未記述。
- 【重要度: 中】`Money` 型が int/int64・Currency/CurrencyCode で不一致。int64 に統一が妥当。
- 【重要度: 中】`BookingStatus`（backend/data-model）と `BookingState`（domain-model）の用語不統一。
- 【重要度: 中】`DomainError` のケースが不整合（4 ケース vs 階層型）。エラー合成境界を確定すべき。
- 【重要度: 中】Estimation Context が backend アーキテクチャに欠落。
- 【重要度: 中】`Cargo.book` のシグネチャ・戻り値が矛盾（6 引数 Result vs 2 引数生タプル）。
- 【重要度: 低】`Leg` が参照する `VoyageNumber` 型の帰属が未定義。
- 【重要度: 低】ドメインに存在しない DB カラム（cargo.weight・declared_value、invoice.tax_rate・tax_amount）の対応注記不足。

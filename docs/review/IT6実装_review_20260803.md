### 本レビューの依頼条件（IT5 ふりかえり Try T1）

IT5 のふりかえりで、**「Try を手順として書くと、その手順は守られるが同じ原理が及ぶ別の場所が漏れる」**
ことを最大の Problem として挙げた。そこで本レビューでは、5 視点すべてに対して
**各指摘について「この原理が及ぶ他の場所はどこか」を調べて書くこと**を必須条件とした。

この条件は実際に効いた。以下はいずれも「他の場所」の調査から出た成果である。

- `CAST` を含む SQL を全数確認し、無防備なのは検索の 2 箇所だけと確定できた
- 「認可はあるが導線が無い」ずれを全ルートで突合し、`/voyages` の 1 件と確定できた
  （同時に**逆向きのずれが 5 件**あることも判明した）
- 空虚なアサートを港コード判定の全箇所で走査し、1 件だけと確定できた
- doc コメントの誤配置を「空 `///` の 2 連続」で走査し、3 件見つけた

「他になし」と書けること自体に価値がある。**次に同じ疑いが出たとき、調査済みだと分かる。**

## 総合評価

Routing Context という新しい BC の立ち上げとして、**BC 独立性の規律はこれまでで最も守られた**
（`routing/**` から他 BC への参照は 0 件、`CargoCapability` / `VoyageError` を
コンテキスト固有型として意図的に分けた判断も根拠づけられている）。
画面も、区間の順序・港の選択式・差分の項目別表示・0 件の書き分けなど、
現場が引っかかる箇所を先回りできている。

一方で、**新規に導入した 2 つの安全装置（楽観的ロック・`X-App-Instance`）は、
いずれも「守りたいものを実際には守れていない」構造だった**。どちらも全緑のテストを
伴っており、IT5 ふりかえりの「緑のテストと壊れ方の設計は別物」がそのまま再現した。

さらに、**画面単体は正しいがロールをまたぐと切れる**欠陥が 3 件出た
（営業が航路一覧に到達できない・荷主に押せないボタンが出る・暫定運用が実行できない）。

高優先度 12 件のうち **10 件を本 IT で修正**し、2 件を IT7 へ送った。

## 特筆事項

### 1. 安全装置を入れたのに守れていない、が 2 件同時に出た

楽観的ロック（ADR-0008）も `X-App-Instance` も、**設計の意図は正しく、テストも緑**だった。
にもかかわらず、いずれも守りたいものを守れていなかった。

| 装置 | 意図 | 実際 |
| :--- | :--- | :--- |
| 楽観的ロック | 失われた更新を防ぐ | 逐次実行でしか成り立たない。`Stale` の扱いに至っては**1 回の衝突で無効化**される |
| `X-App-Instance` | 別インスタンスの応答を切り分ける | 期待値が無く、値を見ても判断できない |

共通しているのは、**「入れたこと」を検証するテストはあるが、「働くこと」を検証するテストが無かった**点である。
`testRejectsStaleUpdate` は逐次で、`testInstanceIdentifierDiffersPerStartup` は値が変わることしか見ていない。

IT5 の Try T4（観測手段を入れたらそれが働くことをテストで固定）を `X-Route` については実行したが、
**同じ原理が同じ IT で新設した他の装置に及んでいなかった**。Try T1 が指摘した形そのものである。

### 2. 「画面単体は正しいがロールをまたぐと切れる」が 3 件

`VoyagePages` は `canManage` でボタンを丁寧に出し分けている。その同じ判断が
`BookingPages` に及んでおらず、IT6 で荷主に一覧を開いた結果、**荷主が必ず見る画面に押せないボタン**が出た。
navbar の導線欠落も、運用手順の実行不能も、同じ「ロールをまたぐと切れる」形である。

記憶にある IT4 の教訓（ロール別の作業入口ナビ導線の欠落）が、形を変えて再発した。

### 3. 自分の書いたテストで同じ罠を踏んだ

tester が指摘した「ページ全体の部分一致で判定すると常に真になる」という欠陥を、
その修正として追加した `VoyagePagesTest` で**そのまま踏んだ**（検索フォームの
`<select>` が `value="GENERAL"` を持つため、`not contains "GENERAL"` が常に落ちる）。
セル単位の判定に直した。**原理を理解して書いても、同じ罠を踏む。**

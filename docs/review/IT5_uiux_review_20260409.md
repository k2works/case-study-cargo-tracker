# IT5 UI/UX レビュー（2026-04-09）

## レビュー対象

- **対象イテレーション**: IT5
- **対象ストーリー**: US09（経路選択・確定）・US10（経路条件再算出）・US11（経路情報を予約に紐付け）
- **レビュー日**: 2026-04-09
- **対象ファイル**:
  - `apps/cargo-tracker/src/main/resources/templates/booking/route.html`（経路割り当て画面）
  - `apps/cargo-tracker/src/main/resources/templates/booking/show.html`（予約詳細画面）
  - `apps/cargo-tracker/src/main/resources/templates/fragments/navbar.html`（ナビゲーション）

---

## 総合評価

経路割り当て画面（route.html）は「検索 → 選択 → プレビュー → 確定」という一貫した業務フローを 1 画面で完結させており、htmx による部分更新でページ遷移なしにプレビューできる設計は評価できる。一方で、**経路確定後の確認体験（US11-AC1）が完全に欠落**しており、予約詳細画面で確定済み経路情報を確認できない致命的な問題がある。加えて、レスポンシブ対応・アクセシビリティ・バリデーション・日時表示フォーマットなど複数の品質課題がある。

## エージェント別フィードバック詳細

<details>
<summary>xp-interaction-designer（高: 4 件 / 中: 5 件 / 低: 3 件）</summary>

**評価サマリー**: 経路割り当て画面は UI 設計ドキュメントのワイヤーフレーム仕様に概ね忠実に実装されており、オブジェクト中心設計の原則（一覧 → 選択 → アクション）に沿った自然なフローが実現されています。一方で、UI 設計仕様に含まれているいくつかの情報要素の欠落、アクセシビリティの細部の不備、htmx 部分更新時のユーザーフィードバック設計の不足が見られます。

**良い点**:
- オブジェクト中心の画面構造: 「経路検索条件」→「利用可能な航路」→「航路詳細」→「確定アクション」という視覚的階層が明確
- システムメタファーとの整合: 航海番号・UN/LOCODE・所要日数という海運ドメインの用語が一貫
- PRG パターンの適用: POST 後のリダイレクト設計（UI 設計仕様通り）
- Bootstrap 5 の適切な活用: card / table-hover / shadow-sm / badge が既存画面と一貫
- htmx による部分更新: ラジオボタン選択時に詳細を動的読み込みする良いインタラクションパターン
- 空状態の設計: 航路候補 0 件の場合の表示が実装されている
- 確認ダイアログの適切な使用: show.html の不可逆操作にモーダル確認を配置

**懸念事項**:
- htmx エラーハンドリングの不在: `htmx:responseError` の処理が定義されていない
- CSRF トークンと htmx の共存: htmx が POST フォーム送信時の CSRF ヘッダーを自動送信するかの確認が必要
- US10 受入条件「営業担当者に荷主との条件協議を依頼できる」の UI 未実装

**スコープ外の発見**:
- navbar.html でロールに応じたメニュー表示制御（`sec:authorize`）が未実装
- UI 設計仕様との不一致: container vs container-fluid の選択

</details>

<details>
<summary>xp-user-representative（高: 3 件 / 中: 4 件 / 低: 1 件）</summary>

**評価サマリー**: 経路選択画面の基本的な操作フロー（検索 → 選択 → プレビュー → 確定）は業務の流れに沿っており、htmx による部分更新で画面遷移なしにプレビューできる点は評価できます。しかし、**経路を確定した後の確認体験が完全に欠落している**ため、経路設計者は「本当に正しい航路が割り当てられたか」を画面上で検証できず、業務上の致命的な問題があります。

**良い点**:
- 検索 → 選択 → プレビュー → 確定の導線が 1 画面で完結している
- ラジオボタン + htmx プレビューの組み合わせが業務系 SaaS の一般的なパターンと一致
- 検索条件が出発地・目的地・希望着日の 3 項目にまとまっており過不足なし
- ナビゲーション順序が業務フロー順（IT4 申し送り反映済み）
- 不可逆操作へのモーダル確認が適切に配置されている

**懸念事項**:
- 経路の再割り当て時に旧 Leg データがどうなるか画面上で不明
- `PRELIMINARY` 状態で「予約確定」と「経路設計依頼」が並ぶことでロール混乱の可能性
- 検索条件の初期値が予約情報から自動セットされているかの確認が必要

**スコープ外の発見**:
- 状態遷移設計: `ROUTE_PROPOSED` が「依頼済み」と「割り当て済み」を兼ねているため、IT6 以降の状態細分化を検討すべき

</details>

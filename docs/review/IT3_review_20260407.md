# IT3 コードレビュー結果

## レビュー対象

- **イテレーション**: IT3
- **レビュー日**: 2026-04-07
- **対象ブランチ**: `java/take-2`（main との差分）
- **主要変更**: US01（輸送見積管理）・US06（経路設計依頼）の実装

## 総合評価

Booking コンテキストの `Cargo` 集約における不変オブジェクトによる状態遷移設計と、コンテキスト間の依存分離は高い水準で設計されています。新規追加の Estimation コンテキストは機能としては動作しているものの、パッケージ構成の不統一・ドメインモデルの原始型依存・設計ドキュメントへの未反映が課題です。また、状態遷移テストの全状態網羅が不十分であり、見積→予約への業務導線が未実装である点が最優先の改善項目です。

## エージェント別フィードバック詳細

<details>
<summary>xp-programmer（高: 3 / 中: 3 / 低: 2）</summary>

### 評価サマリー

ドメインモデルの不変性（immutable な状態遷移）と責務の分離は高い水準で設計されています。一方、Cargo の record ベースの State パターンにおけるファクトリメソッドの冗長性、EstimateService のハードコーディング、およびコマンドサービス内の変換ロジックの肥大化に改善の余地があります。

### 良い点

- Cargo の状態遷移が immutable: `confirm()`, `cancel()`, `assignToRouting()` が新しいインスタンスを返す設計
- `CANCELLABLE_STATUSES` の EnumSet による宣言的な状態定義
- ドメインイベントの発行と疎結合な受信（BookingEventLogger）
- コントローラの例外ハンドリングでビジネス例外とシステム例外を区別
- `ShipperExistenceChecker` による DIP 準拠の依存性逆転

### 改善提案（重要度: 高）

- **Cargo.java: 状態遷移ガード処理の重複（DRY 違反）**
  `confirm()` と `assignToRouting()` が同一ガードパターンを繰り返している。`requireStatus(BookingStatus required, String operationName)` メソッドへの抽出を推奨。

- **CargoBookingCommandService.java: bookCargo メソッドの肥大化**
  コマンドの変換・Cargo 組み立て・永続化が 1 メソッドに集中。CargoCommandAssembler または Cargo ファクトリメソッドへの責務分離を推奨。

- **EstimateService.java: マジックナンバー・マジックストリングのハードコーディング**
  `new BigDecimal("500")`, `"V001"`, `"SGSIN"` が直接埋め込まれている。`RouteCandidateProvider` インターフェースの抽出と、マジックナンバーへの命名を推奨。

### 懸念事項

- `UUID.fromString(command.bookingId())` が不正文字列で `IllegalArgumentException` を投げる。コントローラ層で捕捉されているか要確認。
- `cancel()` でキャンセル済み（CANCELLED）と非対応状態が同じエラーメッセージになる。

</details>

<details>
<summary>xp-tester（高: 3 / 中: 3 / 低: 2）</summary>

### 評価サマリー

テストピラミッドのバランスは良好で、ユニット/統合/E2E の各レイヤーが適切に分担されています。ただし、状態遷移テストにおいて**全状態の網羅が不十分**であり、`assignToRouting()` と `confirm()` の異常系カバレッジが明確に低い点が最大の懸念です。

### 良い点

- イミュータブルな Cargo 設計によるテストの独立性と予測可能性
- 4 層テストピラミッド（Domain → Application → Controller → E2E）の適切な分担
- 統合テスト（BookingThymeleafControllerTest）の品質: 実 DB + TRUNCATE による独立性確保
- E2E テストの Page Object パターン活用
- `cancel()` の状態遷移テストの网羅性（PRELIMINARY, CONFIRMED, CANCELLED, SETTLED）

### 改善提案（重要度: 高）

- **CargoTest: `assignToRouting()`/`confirm()` の全不許可状態が未テスト**
  ROUTE_PROPOSED, TRACKING_ISSUED, IN_TRANSIT 等からの遷移テストが欠落。`@ParameterizedTest` + `@EnumSource` で全状態を検証すべき。

- **CargoTest: `assignToRouting()` の属性保全テスト欠落**
  状態遷移後に `bookingId`, `weight`, `routeSpecification` 等が保全されているかの検証がない。

- **CargoBookingCommandServiceTest: イベント発行の `verify` がない**
  `assignToRouting` でイベントを発行しているが、テストに `verify(eventPublisher).publishEvent(any(BookingAssignedToRoutingEvent.class))` がない。

### テストピラミッド評価

| レイヤー | 評価 |
|---------|------|
| ユニット (Domain) | 良好。境界値テストあり。状態遷移网羅が弱い |
| ユニット (Application) | 良好。イベント検証漏れ |
| 統合 (Controller) | 優良。実 DB + セキュリティ付き |
| E2E (Playwright) | 主要フロー網羅。異常系が弱い |

</details>

### 評価サマリー

Booking コンテキストの不変集約・状態遷移・ドメインイベント導入は設計方針として堅実であり、コンテキスト間の依存分離も現時点では良好です。一方、新規 Estimation コンテキストにはパッケージ構成の一貫性の欠如と、ドメインモデルの成熟度に課題が見られます。

### 良い点

- Cargo 集約の不変性（副作用のない状態遷移）
- コンテキスト間の完全な依存分離（estimation → booking の import ゼロを確認）
- ACL パターンの一貫適用（`ShipperExistenceChecker` ポート + アダプター）
- ドメインイベントの record 採用（不変・軽量）
- ArchUnit によるアーキテクチャガードレールが機能中

- **Estimation パッケージ構成の不一致**: `application.internal.commandservices`, `interfaces.web` のサブパッケージ構成が未整備。Booking/Shipper との統一が必要。

- **Estimation ドメインモデルの原始型依存**: `cargoType: String`, `originUnlocode: String` が Booking の `CargoType` enum・`RouteSpecification` と不整合。

### 懸念事項

- Booking → Estimation 間のイベント連携設計が未定義（同期/非同期の選択、イベント変換方針）
- `findAll()` の N+1 問題（EstimateRepository が各 Estimate ごとに候補取得クエリを発行）

### 評価サマリー

見積機能と予約機能がそれぞれ単体としては動作しているが、「見積を確認してそのまま予約に進む」という営業担当者の最も基本的な作業動線がつながっていない。荷主から見積依頼を受け、ルート候補を提示し、予約に進む一連の業務フローが分断されており、実務での利用に支障をきたす。

- **見積詳細→予約作成への導線が欠落**
  荷主が見積を了承した後、見積詳細から予約作成フォームへの「この見積で予約する」ボタンが未実装。営業担当者は出発地・目的地・貨物種別・重量を再入力する必要があり、業務効率が著しく低下する。

- ルート候補が固定 2 件（SGSIN 経由 21 日 / HKHKG 経由 28 日）で実データと無関係。画面上でスタブであることが不明であり、荷主への誤った情報提供リスクがある。（スタブ実装として許容されているが、本番運用前に要対応）
- 「見積ステータス」の業務的意味が画面上で不明瞭（`CREATED` の表示が営業担当者にとって直感的でない）

4. **見積→予約の業務導線**（#7）: 営業担当者の核心的な作業フローの実現

5. **Estimation パッケージ構成の統一**（#3）: Booking/Shipper との整合
6. **Estimation ドメインモデルの値オブジェクト化**（#4）: `cargoType: String` の型安全化
7. **状態遷移ガードの DRY 化**（#8）: `requireStatus()` メソッドへの抽出

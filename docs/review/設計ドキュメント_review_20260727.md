# 設計ドキュメントレビュー（TypeScript 版設計一式）

- 実施日: 2026-07-27
- レビュー方式: マルチパースペクティブレビュー（XP エージェント 5 名並列）

## レビュー対象

`docs/design/` 配下の全 10 ドキュメント

- tech_stack.md / architecture_backend.md / architecture_frontend.md / architecture_infrastructure.md
- domain-model.md / data-model.md / ui_design.md
- test_strategy.md / non_functional.md / operation.md

## 総合評価

DDD + ヘキサゴナル + CQRS を NestJS で実現する設計思想、TSX SSR + htmx の技術選定、dependency-cruiser による構造検証、pg-mem / Testcontainers の使い分けなど、アーキテクチャの骨格は全エージェントから高評価でした。一方で、Java 版からの移植に起因する**ドキュメント間の構造的不整合**（BC 数の食い違い、US 番号の旧版凍結、割引率の数値矛盾、ロール名の不統一）が横断的に検出されており、実装着手前に「正典の一本化」が必須です。加えて、要件優先度「高」の例外処理（US19/US20）の UI 欠落と、要件にない割引ポリシー管理機能の混入（gold-plating）が、ビジネス価値との整合を損なう主要問題として複数エージェントから独立に指摘されました。

### 評価サマリー

アーキテクチャの方向性（DDD + ヘキサゴナル + CQRS を NestJS で実現、TSX SSR + htmx、ECS Fargate + RDS Multi-AZ）は妥当で、「変更を楽に安全に」を支える良い骨格。一方で致命的な問題は「ドキュメント間の構造的不整合」。BC の数と構成が文書ごとに食い違い（6/7/8）、backend のディレクトリ構成に別プロジェクト由来のコピペ残骸が混入。設計の正典が確立していないため、開発着手前に BC 定義の一本化が必須。

### 良い点

- dependency-cruiser の 4 ルールでヘキサゴナルの依存方向を構造的に強制し、CI で継続検出できる。
- EventEmitter2 の同期実行リスクを明記し、コミット後発行 / Transactional Outbox への移行余地まで示している。
- CQRS のクエリ側が Kysely で読み取り最適化 DTO を直接返す方針が一貫。
- pg-mem / Testcontainers の使い分けを 3 文書で揃えており健全。
- Money（最小通貨単位 INTEGER + ISO4217）、Location 共有カーネル限定の戦略的設計が堅実。

### 改善提案

- 【重要度: 高】BC 定義の正典化と、architecture_backend.md ディレクトリ構成のコピペ残骸（shipper コンテキスト、Booking 集約）除去。BC の数・名称・集約ルート名を全文書で一本化。
- 【重要度: 高】同一文書内にディレクトリ規約が 3 種類混在。アプリ名（apps/cargo-tracker vs apps/backend）も不一致。1 つに確定すること。

- 【重要度: 高】割引率上限が domain-model=30% / data-model=15% で不一致。
- 【重要度: 高】RBAC ロール名の不一致（ROLE_ACCOUNTANT vs ROLE_BILLING 等）。ロール正典表を定めて全文書を揃えること。

- 【重要度: 低】Alpine.js の tech_stack 未記載、infra 環境別設定表のローカル DB 記述の矛盾。

### 懸念事項

- 設計の正典不在が最大の懸念。正典 3 点（BC 定義・domain-model・data-model）の同期を DoD にすることを推奨。

## レビューの実施状況

**5 本すべてがクローズ開始から 10 分以内に返着しました。** IT7 では 1 時間半待って返らず自己レビューで補完しましたが、今回は全数が揃いました。**待つ価値がありました**——高優先度の指摘 14 件のうち、自己レビューでは見つけていなかったものが 12 件あります。

**3 人が独立に同じ 2 件を指摘しました**（レート制限が利用者の IP を数えていない・荷主の絞り込みがフェイルオープン）。複数の視点から同じ欠陥が見えるものは、実装の中心に近いところが壊れている兆候です。

## 高優先度の指摘と対応（14 件すべて対応済み）

| # | 指摘 | 指摘者 | 対応 |
| :--- | :--- | :--- | :--- |
| 1 | **荷主の絞り込みがフェイルオープン**。荷主 ID のヘッダが無ければ「全件可」。紐付けの無い `ROLE_SHIPPER` が 1 人でも作られると全社の追跡が見える | tester・architect・programmer | ロールを判断材料に加え、荷主を名乗るなら荷主 ID を必須に。**どちらか一方が欠けても広い側へ倒さない** |
| 2 | **レート制限が利用者の IP を数えていない**。nginx が中継するので gateway から見た接続元は常に 1 つ。全利用者が 1 つのバケツを共有し、攻撃者 1 人で公開照会を止められる | programmer・architect・user-representative | `X-Forwarded-For` の先頭を見る。**外れ（404）だけを数える**——総当たりは外れでしか進まないので、正しい番号を持つ荷受人は何度更新しても断られない |
| 3 | **例外の対応中に「押しても断られるボタン」が 6 個並ぶ**。集約は例外中の手動更新を無条件で断るのに、読み口は `canTransitionTo` だけで選択肢を作っていた | programmer | 判定を `TransportStatus#manualTransitionsFrom` の 1 か所に寄せ、集約も読み口もこれを呼ぶ |
| 4 | **開始イベントの再配送で現在の状態が巻き戻る**。upsert が `transport_status` を無条件で上書き | programmer | 開始時の値は挿入のときだけ書く。**開始 → 更新 → 開始の順序を踏む検査**を追加 |
| 5 | **一覧の並びが仕事の順序でない**。最終更新の新しい順は「さっき触ったもの」が上に来て、誰も触っていない＝いちばん危ないものが沈む | user-representative | 正典どおり到着予定が近い順に |
| 6 | **一覧が上限で無言に切れる**。追跡担当者は「一覧に出ていない＝無い」と読む | user-representative | 全件数を返して案内を出す |
| 7 | **現在地が更新のたびに消える**。場所は任意入力なので、空で 1 回更新すると消える | user-representative・programmer | 最後に場所が入っていたイベントを出す |
| 8 | **「誤配」「例外発生」を手で選べる**。例外発生は解決画面が無いあいだ行き止まり | technical-writer | 集約と読み口の両方で入口を絞る |
| 9 | **起きた日時を入れられない**（US17 §2 は「状態・位置・日時」）。出港は夜間で記録は翌朝 | user-representative | 「起きた日時」欄を追加（空なら業務時計で「いま」） |
| 10 | **荷主の画面に社内の担当者名が出る**（S41 の記録者列） | user-representative | 追跡担当者にだけ列を出す |
| 11 | **件数の指定が無検査**。負値がそのまま SQL に渡り 500 | programmer | 1〜200 に切り詰め |
| 12 | **マニュアルのボタン文言・導線が実物と違う**。業務フローが「未提供」のまま | technical-writer | 実物に合わせ、業務フローから 12 章へ繋いだ |
| 13 | **受け入れテストの「断られる」が判別しない**。2xx でないことしか見ておらず 404 でも 500 でも緑 | tester | 状態コードと理由まで見る |
| 14 | **受け入れテストが Gateway を通らない組合せで緑になる**。詳細を開くステップがロールを送っていなかった | tester | Gateway が実際に送る形にそろえた |

## 中・低の指摘（IT9 へ送るもの）

対応の価値はあるが、本 IT のストーリーの外か、正典の変更を伴うため次イテレーションに送ります。

| # | 指摘 | 指摘者 | 送る理由 |
| :--- | :--- | :--- | :--- |
| A | **追跡一覧が N+1**（1 行ごとに旅程と履歴を引く）。30 秒ごとに再実行される | architect・programmer | `data-model.md` は `current_unlocode` を列として定義済み。**投影で埋める**のが筋で、列の追加とイベントの扱いを含む |
| B | **遷移表の正典が手で書き写されている**。図が変わってもテストは追随しない | architect | `navigationMatchesUiDesign.test.ts` の先例に寄せて PlantUML を読む形にする |
| C | **ADR-0011 決定 3 の検査が文字列リテラル 1 本に依存**。別名のシーケンスや他モジュールの再実装は素通り | architect | ArchUnit で「実装クラスは 1 つだけ」を固定するほうが綴りに依存しない |
| D | **`shipper_id` が NULL の行に気づく手段が無い**。誰にも紐づかないまま一覧に出続ける | architect | NULL 行の解消と NOT NULL 化を IT9 の**行として立てる**（「余力次第」にすると固定化する） |
| E | **正規化が公開経路にしか掛からない**。小文字の追跡番号は S41 で見つからない | tester・programmer | 入口の形式検査とあわせて整理する |
| F | **衝突時の採り直しテストが判別しない**。`exists` の返事を無視する実装でも緑 | tester | 候補生成を差し替えられる形にする |
| G | **追跡番号の衝突検査が非同期の投影を見ている**。同時発行に対しては成立しない | programmer | 36^10 なので実害の確率は無視できるが、**コメントが実装より強い保証を主張している**ので直す |
| H | **`last_event_id` を書いているのに誰も読まない**。順序の入れ替わりで状態が巻き戻る | programmer | 「同じ／古いイベントなら更新しない」の判定に使うか、使わないなら消す |
| I | **一覧から貨物の見分けが付かない**。問い合わせは荷主名か予約番号で来る | user-representative | 列の追加と絞り込みは S40 の拡張として IT9 |
| J | **場所が自由入力**。打ち間違えても保存され、荷受人にも出る | user-representative | 港マスタからの選択にする（本 IT で 5 桁の形式ヒントのみ入れた） |
| K | **公開照会の「出発」が予定か実績か読めない** | user-representative | 「予定」と明示する表記の整理 |
| L | **ダッシュボードに追跡担当者・荷主の入口が無い** | user-representative | 「今日到着予定 N 件」などの受け皿。IT9 |
| M | **状態を更新しても荷主が気づけない**（US17 §4） | user-representative | 荷主のダッシュボードに「24 時間以内に変わった N 件」。送信基盤なしで満たせる |
| N | **デモ項目 3・8 に Cucumber が無い**（別の検査で担保） | tester | どの検査がどのデモ項目を担うかを完了報告書に明記した |

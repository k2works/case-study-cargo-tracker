# IT4 実装レビュー（2026-09-05）

## 実施の形

5 視点（programmer / tester / architect / technical-writer / user-representative）を並列で起動し、全員から結果を受け取りました。

| | IT2 | IT3 | IT4 |

なお、今回は結果が途中で切れませんでした（IT3 は 4 視点で切れました）。**表の最終行を確かめる手順は残します**（切れていないことを確認したうえで統合しています）。

## 高優先度の指摘と対応

### 1. 差分を確認したあとに入力を変えても更新できる（programmer・user）

`update` の `mutationFn` が押した瞬間に `payload()` を作り直していたため、**確認した内容と違うものが PUT され得ました**。US25 §受入基準 3（差分確認後に更新）が形だけになります。

差分を出した時点の入力を控え、更新はその控えを送る形にしました。あわせて、入力が変わったら差分を捨てて確認をやり直させます（運航変更の入力は、確認のあとにもう一桁直す操作が普通に起きます）。「差分を出したあとに入力を変えたら確認をやり直させる」テストを足しました。

### 2. 期限を過ぎた仮受付の予約が修正できない（programmer・user）

画面は `min` を既存期限まで緩めて「期限の過ぎた予約でも品名を直せる」と書いていましたが、集約は修正時も `arrivalDeadline.isBefore(today)` を断っていました。**画面のコメントと実装が逆**でした。

集約が受け付け時の期限を保持し、**期限を動かさない修正は期限が過去でも通す**形にしました。入力の誤りに気づくのはたいてい期限が近づいてからで、そのときには直せない、という状態を解消しています。

### 3. 更新済みの航海に登録イベントが読み直されると偽の重複が記録される（tester）

投影を読み直すと登録イベントがもう一度届きます。更新済みの行は中身が違うので「丸ごと比較」が一致せず、**「航海番号の重複」が偽で要確認一覧に積まれていました**。行は残るので画面は正常に見え、経路設計者の一覧にだけ身に覚えのない警告が残ります。

`updated_at` が入っている行は「登録イベントより新しい事実を持っている」と見なして止めます。「登録 → 更新 → 登録の読み直し」を踏むテストを足しました。

### 4. 認可の名簿検査にメソッドの次元が無い（architect・tester・programmer）

決定 6 で認可は（メソッド, 経路）の 2 次元になったのに、`EveryServiceEndpointIsRoutedAndProtectedTest` は `isDeclared(path)` しか見ていませんでした。**書き込みを足しても読み向けの広い宣言に吸われたまま緑**になります。

`isDeclared(method, path)` に変え、全メソッドについて宣言を要求する形にしました。あわせて「経路設計者は予約を読めるが書き換えられない」を検査に落としています（決定 6 に対応する検査）。使われていなかった 2 引数版 `isAllowed`（GET を既定にする紛らわしい API）は削除しました。

### 5. マイグレーションに導出がもう 1 本あり、一致を誰も確かめていない（architect）

R.1・R.2 は「導出が 2 本あって食い違った」ことへの返済でしたが、同じ導出が `V005` の SQL に再実装され、Java 版との一致は検査されていませんでした。区切り文字や桁数を変えると **CI は全緑のまま既存クラスタの行だけがずれます**（直したかった症状そのもの）。

実 DB に対して SQL の導出と `AttentionItemId.of(...)` を突き合わせる統合テストを置きました。区切りを 1 文字ずらすと赤になることを確認済みです。

### 6. 「対応する航海を探す」が貨物種別しか引き継がない（user）

行に出ている出発地・目的地・到着期限は引き継がれず、経路設計者は毎回打ち直していました。打ち間違えれば 0 件が出て「航海が無い」と読みます。

出発地・目的地・到着期限（出発日の上限として）まで引き継ぎます。翻訳表は `Record<CargoType, string>` の全数マップにして、種別が増えた瞬間に型で落ちるようにしました。

### 7. 「キャンセルしても変わらない」を受け入れテストが判別しない（tester）

差分の問い合わせだけを行い、**待たずに**詳細を読んでいたため、`/diff` が更新まで送る実装に壊れても投影が非同期な分だけ古い値が返り、緑のままでした。

「その時間のあいだ起きないこと」を確かめる形（`awaitWithin(..., expected=false)`）を足し、`updatedAt` が null のままであることも併せて見ます。

### 8. 「いつ直したか」が読み直しで動く（architect・tester）

投影が `clock.instant()` で `updated_at` を書いていたため、リプレイのたびに最終更新が現在時刻へ動きました。US25 の画面はこの値を「最終更新」として出すので、**読み直した日時が「直した日時」として利用者に見えます**。

更新時刻をイベントに持たせ、投影はそれを写すだけにしました。`ReplayIT` に「更新を読み直しても、いつ直したかは動かない」を足しています（予約側も同じ形に揃えました）。

### 9. 差分の表記だけが生の値（technical-writer）

`GENERAL / HAZARDOUS`、`JPTYO → USNYC（2026-09-10T09:00:00Z 〜 …）` と、画面の他のどこでも使っていない表記でした。**送信直前のいちばん慎重に読む場面でだけ表記が変わります**。一覧・詳細と同じラベル・UTC 表記に揃えました。

### 10. ユーザーマニュアルが IT4 分だけ未着手（technical-writer）

`docs/manual/index.md` の「画面を変えたらキャプチャを撮り直す」という宣言が、最初の適用機会で守られていない状態でした。**クローズの Q.3 で対応します**（章の追記・キャプチャ再生成・R.6 のキャプチャ重複解消を同じ変更で行う）。本レビューでは対応方針の確定までを結果とします。

### 一度だけ落ちたビルドについて

レビュー対応の途中で `TZ=UTC ./gradlew build` が 1 度だけ落ちました（`1 executed, 107 up-to-date`）。**再実行は緑で、その時点で報告が上書きされたため、落ちたタスクを特定できていません。** 全モジュールのテスト結果 XML に failures / errors はありません。

Axon Server コンテナの起動待ちは、同じ Docker で kind クラスタと SonarQube が動いていると伸びることが分かっており（`AbstractAxonIntegrationTest` に 6 分の猶予を置いた理由）、この日はその 3 つが同時に動いていました。**心当たりはありますが、確かめてはいません。** 2 度目を見たら追う対象として IT5 へ引き継ぎます（「たまに落ちるテストは 2 回目で追う」）。

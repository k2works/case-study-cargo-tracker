## 高

### H1. リプレイのたびに要確認一覧が増える（architect / tester）

**`ADR-0001` のコンプライアンス欄が「`ReplayIT` は未実装」のまま 2 IT 続いていました。** IT2 で投影が 3 つに増え（`shipper`・`cargo`・`shipper_contract_snapshot`）、投影が `attention_item` への書き込みという**副作用**を持つに至ったので、Reaction Handler を待たずに書きました。

**書いた時点で実在の欠陥が出ました。** 弾かれた登録を読み直すたびに要確認一覧が増えます。

| | |
| :--- | :--- |
| 場所 | `AttentionItemRecorder.java:32`（当時） |
| 原因 | 識別子が `UUID.randomUUID()`。同じ事実に毎回別の行を作る |
| なぜ気づけなかったか | `attention_item` は追記専用でリプレイでも消さない（`data-model.md`）。「行が増えない」ことを確かめる検査が投影テーブルにしか無かった |
| 業務での見え方 | 営業が毎朝見る要確認一覧が、同じ内容で読み直しの回数だけ膨らむ。件数が信用されなくなる |
| 対応 | **修正済み**（`5248a4c99`）。識別子を「何が・どの対象で・なぜ」から導き、`ON CONFLICT DO NOTHING`。上書きはしない（確認済みを消してしまう） |

**ArchUnit の `onlyInterfacesAndReactionSendCommands` はコンパイル時の依存しか見ておらず、実行時に呼ばれないことの保証ではありません。** ADR の表の 1 行が文章のまま残っていると、こういう形で欠陥が残ります。

### H2. 予約詳細のロール制御が到達性の検査から外れていた（user-representative）

| | |
| :--- | :--- |
| 場所 | `routes.tsx:51`・`routes.test.tsx` |
| 何が起きるか | 予約詳細（`/bookings/:bookingId`）はナビに載せないため、`routes.test.tsx` のロール別到達性（`NAVIGATION` を回す）の対象外だった。**外れた画面ほど権限の設定を間違えても気づけない** |
| 業務での見え方 | 一覧には出るのに開くと 403、あるいはその逆 |
| 対応 | **修正済み**。許可ロールを明示的に検査し、あわせて「一覧を開けるロールは詳細も開ける」ことを固定した。許可をずらすと赤になることを確認 |

## High

### H1. Handling → Tracking の書き込みが集約を通っていない（ADR-0012 の中心的主張が成立していなかった）

**指摘元**: architect ／ **返済済み**

`ApplyHandling.apply` は `findByTrackingNumber` で集約を読んで `case Some(_)` と**捨て**、
`TrackingRepo.updateTransportStatus(trackingNumber, status)` という**列単位のポート**を呼んでいた。
`TrackingModel` に遷移メソッドは存在せず、**集約は一度も通っていなかった**。

ADR-0012 は選択肢 B（直接 SQL）を「`TrackingActivity` の不変条件を保証できなくなる」として
却下している。アプリケーションサービスを 1 枚挟んでも、**保証されるものは選択肢 B と同じ**だった。
`ApplyHandling` のコメントが「遷移の妥当性は見ない」と宣言していたため、
**集約を通しても通さなくても同じ**という状態でもあった。

**規則が無いことと、規則を書く場所が無いことは違う**。US16（引取）で `CLAIMED` を足すとき、
規則を書く場所が要る。

**返済**: `TrackingModel.applyHandling` を追加し、ポートを `saveTransportStatus(activity)` へ
変えた（**集約型を引数に取る**——`(trackingNumber, status)` の 2 値を受ける形は、
ポートの型そのものが迂回を合法にする）。`findForUpdate` も追加した。

### H2. MISROUTED の統合テストが Booking 側を検証していなかった

**指摘元**: programmer・tester ／ **返済済み**

`testLoadAtUnplannedPortIsMisrouted` の doc は「**予約の経路状態が MISROUTED になること**まで
確かめる」と書いていたが、アサーションは Handling の履歴と Tracking の公開追跡だけで、
**Booking を一度も開いていなかった**。`BookingMisroutingReport` の経路を丸ごと削除しても
緑のままだった——ACL 3 本のうち 1 本が実質未検証だった。

**返済**: 予約詳細を開いて経路逸脱の表示と**旅程が消えていないこと**を確かめる
（`markMisrouted` は `saveItinerary` で書くため DELETE + INSERT を通る）。

### H3. 経路逸脱が経路設計者に届かない（H2 の返済で発覚）

**指摘元**: user-representative ／ **返済済み**

H2 のアサーションを足したところ**赤くなった**。予約詳細にも予約一覧にも
**経路状態を出す欄が無かった**——荷役作業員の画面には「経路設計者へご連絡ください」と出るのに、
受け手の側に受け皿が無い。逸脱は電話が鳴るまで放置される。

**返済**: 予約詳細に経路逸脱の警告を出し、経路設計者には**割り当て直しの導線**も添えた。
気付いても次の一手が分からなければ放置されるため。

### H4. 共有の `withPreparedStatement` を使わず、例外時にクローズしない私物コピーを新設していた

**指摘元**: programmer ／ **返済済み**

`SharedDbPool.withPreparedStatement` は `try/catch` で成功・失敗どちらでも `close()` を保証し、
既存 11 リポジトリすべてが使っている。IT10 で追加した 2 本（`JdbcTrackingRepo`・
`JdbcHandlingRepo`）だけが private な同名関数を定義し、**`try/catch` が無かった**。
例外が飛ぶ経路は実在した（H5）。

**返済**: 私物定義を削除し `SharedDbPool` を使う形へ揃えた。

### H5. 荷役日時の時刻部分が無検証で、DB 例外＝500 に直行していた

**指摘元**: programmer・tester ／ **返済済み**

`isDateTimeText` は長さ・`T` の位置・日付部しか見ておらず、`2026-08-01T99:99` が通って
`CAST(? AS TIMESTAMP)` で例外になっていた。**コメントは「規則は共有カーネルが持つ。
ここに書き写すと片方だけ緩む」と書きながら、実装が書き写していた**。

**返済**: `SharedCalendarText.isIsoDateTime` を直接呼ぶ形へ。
あわせて作業場所の**大文字化**も足した（他 3 BC は正規化しており、Handling だけ
`trim` のみで `jposa` が拒まれていた）。

### H6. ADR-0012 が自分の再検討条件に到達していることに気付いていなかった（2 件）

**指摘元**: architect・technical-writer ／ **返済済み**

- **ACL の本数**: ADR は「2 本 → 5 本。**境界に到達する**」と書いていたが、実際は **6 本**
  （US14 の `BookingTrackingNumberAssignmentAdapter` を数え落としていた）。
  同じ IT で更新した `arch_lint_rules.md` は 6 本と正しく書いており、**ADR と設計が矛盾**していた。
  6 本は再検討条件 4「6 本以上」に**既に該当**する。
- **集約の数**: US15 は 1 トランザクションで 3 集約（`HandlingActivity`・`TrackingActivity`・`Cargo`）を
  更新する。再検討条件 1「3 つ以上の集約」に**起票と同時に到達していた**——
  リスク節が US14 の 2 集約だけを数えていた。

**返済**: 両方を訂正し、「到達済み」と言い切った。あわせて
**本数は代理指標として機能していない**ことを記録した——6 本の内訳は
**書き込み 4 本のうち 3 本が Booking へ向いており**、「連携が増えた」のではなく
**`Cargo` がハブ化している**。IT11 では条件を「単一 BC へ向かう書き込みアダプタ数」へ
置き換えることを検討する。

### H7. 画面に Markdown の `**` がそのまま表示される

**指摘元**: technical-writer ／ **返済済み**

`Flash.handlingMessage` の MISROUTED の文言だけに `**` が混入しており、
荷役作業員には「`**貨物が予定と違う経路に乗っています**`」とアスタリスク付きで表示されていた。

**返済**: 除去した。

### H8. 荷役の記録が荷主の追跡タイムラインに出ない

**指摘元**: user-representative ／ **IT11 へ**

登録は `handling_activity` へ入るが、公開追跡のタイムラインが読むのは
`tracking_handling_event` で**別のテーブル**である。同期で更新されるのは輸送状態だけなので、
荷主にはバッジが変わるだけで**いつ・どこで積まれたかが出ない**。

US15 の「なぜ」は荷主がリアルタイムで確認できることであり、これは業務上の中核である。

**IT11 へ送る理由**: テーブルを 1 本に寄せるか追跡側へ 1 行足すかは設計判断であり、
`tracking_handling_event` の所有と `handling_activity` の関係を決める必要がある。
**US16 より先に扱う**——機能が入っているのに業務が回らない状態である。

### H9. 荷役履歴が全件無制限で、日次運用で使えない

**指摘元**: programmer・user-representative・tester ／ **IT11 へ**

`findAll()` は `WHERE` を持たず、`V12` が作った `idx_handling_activity_tracking` を使う SQL が
コードベースに存在しない。追跡管理者は「この番号の貨物は今どこか」に答えるために開くが、
**全貨物の荷役が時系列で混ざって**出る。1 日数十件で数日中に使えなくなる。

**IT11 へ送る理由**: 絞り込みの軸（追跡番号・判定・期間）を利用者代表と決める必要がある。
IT9 の経路割り当てで採った「上限 + 落とした件数を出す」形を踏襲する。

## 良かった点（維持する判断）

- **ADR を実装の前に決め、同一 IT で設計ドキュメントを是正した**。`domain-model.md` の
  イベント表を取り消し線で残し、未採用の理由と ADR へのリンクを添えた形は、
  将来「なぜイベントにしなかったのか」を確実に追える
- **アダプタが判断を持たない**。「ここで検証を書くと、集約の不変条件が 2 箇所になる」と
  書き、実装もそのとおりになっている
- **`matchesLeg` が航海番号で区間を特定してから港を比べる**。「同じ港を 2 度通る旅程で
  誤って一致する」を先に潰し、テストで固定している
- **`HandlingValidity` を `Bool` から 3 値へ格上げ**した判断。設計のデシジョンテーブルが
  警告と MISROUTED を書き分けている事実を型で受け止めている
- **`TrackingActivity` を導出型から永続化型へ是正**し、理由をコードに残した
- **`TestSql` の用途を「制約そのものを検証する場合だけ」に厳格に限定**した doc。
  安全装置検証のための抜け道が濫用に育つのを防いでいる
- **空振りを隠さず記録した**（`testConcurrentIssueProducesDistinctNumbers` の
  「このテストが識別できないこと（正直に書く）」節）。これがあったから
  「安全装置の検証水準がばらついている」という指摘（tester H3）が成立した
- IT9 レビュー H1 の返済（状態ごとの到達性・HTML のリンクを辿る形）が
  IT10 の新規テストにも引き継がれている

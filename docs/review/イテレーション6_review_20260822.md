# イテレーション 6 レビュー（2026-08-22）

## レビュー対象

- ブランチ `java/take-7`、差分 `485950a3f..80829fa19`（152 ファイル・8,727 追加・1,593 削除）
- US12（経路の通知）・US13（予約確定）・US14（追跡番号発行）・US32（ロック解除）
- 初のサービス間**非同期連携**（bookingms → RabbitMQ → trackingms）と **trackingms の初実装**
- 返済枠 11 件

## 総合評価

**非同期連携という最も壊れ方の見えにくい領域を、契約を両側に固定して実 RabbitMQ の往復と DLQ 到達まで通した**点は 5 視点すべてが評価しています。BC 独立性・ヘキサゴナルの守り・「安全装置は破るテストで固定する」の規律は、実装・ADR・設計書のいずれでも一貫していました。

一方で**高優先度の指摘が 9 件**あり、その大半が同じ形をしています——**決定はあるが、検査か配線が片側だけ**。これは IT6 自身が計画の欠陥表に挙げた 9 件と同じ性質であり、[ADR-019](../adr/019-route-assignment-api.md) 後日談 3 で踏んだ形の再発です。

**高優先度 9 件はすべてクローズ前に対応しました。**

## 対応した指摘（高優先度）

| # | 指摘（指摘元） | 何が起きていたか | 対応 |
| :--- | :--- | :--- | :--- |
| 1 | 戻した予約を経路設計者が触る前に通知できる（user-representative） | `notifyShipper` が `BookingStatus` だけを見ており、`returnToRouting` が `ROUTE_PROPOSED` に戻すため、**荷主が断った経路のまま通知済 → 確定にできた**。荷役はその予定で動き、荷主は違う話を聞く | 「いま経路が決まっている」（`ROUTED`）ことを見る。集約のテストで固定 |
| 2 | ADR-022 決定 6 が本番で一度も働いていない（architect・programmer） | `@Transactional` はリポジトリの `save` にしかなく、発行時には同期が解除済み。結果の順序が正しいのは「たまたま save のあとに呼んでいる」から | 境目をユースケースへ引き上げ、**発行時に同期が有効であること**を実 DB で固定（外すと赤） |
| 3 | 往復テストがプロデューサの送る形を流していない（tester・architect） | 受け皿クラスをそのまま送っていたため `__TypeId__` に**受け手のクラスパスに必ず存在する名前**が載る。本番との違いはワイヤ上でしか出ない | JSON と `__TypeId__` を本番と同じ形で組み立てて流す。相手の型がこちらに無くても読めることが ACL の根拠 |
| 4 | コンシューマ側の「知らない項目を無視する」が未検証（tester・programmer） | テスト自身が寛容に設定した `ObjectMapper` に対する検査で、**テストが本番より甘い** | 本番の変換器を通す形に直した |
| 5 | 新しい ArchUnit 規則が trackingms に適用されていない（architect・programmer） | `eventPublishingOnlyInMessagingInfrastructureRule` を呼ぶのは bookingms だけ。**AMQP に最も広く触っている trackingms が無検査**。メタテストの名簿にも無い | 必須規則を**手書きの名簿から公開規則を導く形**に変更。2 規則 × 全サービスの未適用が判明し配線 |
| 6 | 追跡番号の連番が 9999 を超えると重複しうる（programmer） | `LPAD` は**切り詰める**ため `-10000` は `-1000` になる。形式違反にならず、UNIQUE 制約に当たるまで気づけない | 連番を 9999 で循環させ、重複は制約が捕まえる形に。日次カウンタは IT7 の返済枠 |
| 7 | 追跡番号の日付が DB のタイムゾーンで決まる（programmer） | `CURRENT_DATE` はセッションの TZ（通常 UTC）。**日本時間 00:00〜09:00 の発行が前日の日付**になる | 日付はアプリが業務タイムゾーンの Clock から渡す。時刻源を 1 つに |
| 8 | 営業の朝の仕事が回らない（user-representative） | 「通知待ち」「返事待ち」を探す手段が画面に無い。経路が決まったことは営業に何も知らされず、一覧の「経路」列は通知前後で同じ | ダッシュボードに 3 つの入口（通知待ち・返事待ち・番号を伝える）と件数、一覧に「荷主へ通知」列を追加 |
| 9 | 廃止した `CargoBookedEvent` が設計書に 8 箇所残る（technical-writer） | ADR-022 が「寄せる」と宣言したのに 1 箇所しか寄せておらず、**同じファイルのサンプルコードが旧名で発行**していた | 全 8 箇所を修正。**廃止名が戻っていないことを検査するテスト**を追加（混ぜて赤になることを確認） |

あわせて、確定した予約に `[経路を見直す]` を出さない（押せるのに断られる操作を作らない）、判別しないテスト 3 本（確定・戻す・ロック解除）、マニュアルの追随漏れ 5 箇所も直しました。

## 次イテレーションへ送る指摘

対応しないと決めたもの、または IT7 で扱うものです。

| 指摘 | 判断 |
| :--- | :--- |
| **発行に失敗すると二度と発行できない**（architect） | 番号は保存済みで二重発行は拒否されるため、ブローカー障害時に「番号は渡されたのに追えない」が確実に起きる。**IT7 の返済枠**。ADR-022 のネガティブ（Outbox の窓）は、再実行手段とセットでないと運用で塞げない |
| **取りこぼしが見える手段が無い**（architect） | 発行済みだが追跡が無い予約を突き合わせる照会が無い。運用手順書の 1 タスクで足りる。**IT7** |
| **交換機に alternate-exchange が無い**（architect） | 「誰も受け取れなかった」メッセージは黙って消える。DLQ が守るのは「受け取ったが処理できなかった」だけ。**IT7 で ADR-022 決定 4 に一行足す** |
| **冪等が read-then-write**（tester） | いま単一コンシューマなので表面化しないが、並行化した瞬間に壊れる。**IT7** |
| **同じ遷移規則が集約・画面・モックの 3 か所にある**（programmer） | `Cargo` に可否の述語を置き、応答に載せて画面とモックが状態名を比較しない形へ。**IT7 の返済枠**（規模が大きく、IT6 のクローズで入れると回帰の確認が追いつかない） |
| **`booking-detail-page.tsx` が 610 行**（programmer） | 同じ IT で `route-design-page.tsx` を割った基準より大きい。可否述語の導入と同じ変更で分ける。**IT7** |
| **所要日数の丸めが 3 通り**（programmer） | 営業が荷主に伝える日数と経路設計画面が 1 日ずれる。**IT7** |
| **`CONFIRMED` の表示名が「確認済」**（technical-writer） | ボタン・マニュアル・ADR はすべて「確定」。表示名だけ違い、業務担当者は別のことが起きたと読む。**IT7 で「確定済」に揃える** |
| **通知の履歴が最新 1 件だけ**（user-representative・technical-writer） | 督促の判断材料が上書きで消える。**US19（通知基盤）と同時**（ADR-021 決定 2 の判断どおり） |
| **確定後の変更に出口が無い** | 船の欠航・数量変更は普通に起きるが、システム上は何もできない。**US30（IT9）まで運用ルールで吸収**。決めずに出すと現場は確定を後ろ倒しにする |
| **`ignoreFailures = true` で Checkstyle/SpotBugs が落ちない**（programmer） | 二重 import が検出されていた（今回手で直した）。**IT7 で方針を決める** |
| 契約の名簿・チャネル名が両側で自己完結（programmer・tester） | 共通のテスト用定義を両側が読む形へ。**IT7** |
| 追跡管理者のダッシュボードが全項目「準備中」（user-representative） | IT6 のスコープ外。利用者を割り当てる前に把握しておく |

## 総合評価

DDD + ヘキサゴナル + CQRS というアーキテクチャ選択、集約境界を不変条件から導く設計、enum 日本語ラベルの正典化、ArchUnit による構造の自動検証、JaCoCo 閾値の強制など、個々の設計判断は業務領域の性質から妥当に導かれており記述密度も実装に耐える水準にある。

一方で、**成果物全体を貫く問題は「正典（Single Source of Truth）が定まっていない」ことに集約される**。ADR が 1 本も存在しないまま複数文書が「詳細は ADR 参照」と決定を委譲し、その空白に文書間の分岐が入り込んでいる。US 採番・コンテキスト数・画面数・H2 の採否・共有カーネルの範囲・RTO/RPO・監査ログ保持年数・E2E ツール・ロールと画面の対応など、**実装着手をブロックする矛盾が 20 件以上**確認された。

加えて、業務観点では **ユーザーストーリー 27 本中 7 本分の画面が欠落**しており、特に荷主登録（US02/US03）が無いために最優先の予約フロー（US04）が成立しない。テスト観点では、楽観的ロック・認可マトリクスという「安全装置」が文言だけで検証対象が実在せず、E2E サンプルには常に緑になる空振りが埋め込まれている。

**設計の骨格は良い。壊れているのは骨格ではなく、骨格を一箇所に固定する仕組みである。**

## スコープ外の発見

- `data-model.md` **内部**で概念/論理 ER とテーブル定義が食い違う（`cargo` の `weight_kg` vs `weight`、`declared_value` の消失、`cargo_type` が VARCHAR(20)/(30)）。同一ファイル内の不整合であり実装前に是正が必要。
- `data-model.md` は「コンテキスト間に FK を設けない」と定めながら `cargo.shipper_id` と `leg.voyage_number` で自ら違反している。
- 概念データモデルは `users` / `user_roles` を「Shared Domain」、論理データモデルは「Security Context」に置く。Security は 7 コンテキストに存在しない区分であり「18 テーブル = 7 BC + Shared」という説明とも数が合わない。支援サブドメインとして `domain-model.md` に一行加えるのが自然。
- `RouteCandidate` は Estimation Context の `estimate_id` に従属し、**予約（Cargo）に紐づく経路候補の置き場が無い**。US09（候補から選択して確定）・US10（条件調整して再算出）は最優先ストーリー群であり実装着手時のブロッカーになる。
- `shipper` テーブルに住所カラムが無い（US02 の受入基準は住所入力を要求し、ドメインには `Address` VO がある）。メールアドレスに UNIQUE 制約も無く「同一メールアドレスが既に登録されている場合」を DB が保証しない。
- `escalationPolicy` が `test_strategy.md` のテスト例に登場するが `domain-model.md` のどのクラスにも存在しない（`TrackingExceptionEvent.escalationFlag` はある）。テスト例が設計より先行している。
- `/actuator/health` がレートリミット・サーキットブレーカーの対象外であることが明記されていない。**過負荷時に liveness プローブが 503 を返すと ECS が再起動ループに入る**。横断的な防御はヘルスチェックを除外する。
- 追跡 API のレートリミット到達時（429）のユーザー向けメッセージが未定義（エラーページ表は 400/403/404/500 のみ）。
- 公開追跡画面のフォーム送信先となる `/public/tracking`（パス変数なし）のエンドポイントが未定義。
- HikariCP 20 接続 × 最大 10 タスク = RDS `max_connections` 200 ちょうどで上限に張り付いている。`db.t3.medium`（バースト可能インスタンス）で 1,000 RPS を捌く前提も要検証。**追跡 API への負荷試験を IT の早い段階で 1 本入れる**ことを推奨（壊れるならここ）。
- `[📷 カメラスキャン]` の失敗時導線が未設計。港湾・倉庫ではラベル汚損・逆光・手袋操作が常態でスキャン失敗は日常。
- ROLE_HANDLER は現場でのモバイル利用が前提（セッション 2 時間の根拠）だが、荷役登録・一覧のモバイル最適化が未定義。モバイル要件は公開追跡画面にしか書かれていない。
- `test_strategy.md` に WireMock の記載があるが、過去の別言語版で WireMock 系ライブラリが依存関係のセキュリティ問題で見送られた経緯がある（ADR-0014 相当）。
- カバレッジのゲート値が JaCoCo 強制値と層別目標の二系統あり、後者が `non_functional.md` に一部しか転記されていない。**DoD は条件を書き写さず引用する**。
- `docs/article/source/rust/apps/cargo-tracker/target/` が未追跡のまま作業ツリーに存在。Rust のビルド成果物なので `.gitignore` へ追加すべき。
- `docs/design/` 全 10 ファイルが add 済み・未コミット。指摘反映の差分を追いやすくするため、レビュー反映前に一度コミットしておくとよい。

## 良い点（統合）

- **集約設計の根拠が不変条件で言語化されている** — Cargo に CargoItinerary を含める理由を `Leg[n].unloadLocation == Leg[n+1].loadLocation` の連結制約から説明している（Architect）。
- **コンテキスト間に DB 外部キーを張らない判断** — コンテキスト内は FK あり、間はアプリ層で保証と方針が一貫し、将来の分割余地を残している（Architect）。
- **ArchUnit による構造の自動検証** — 設計原則を文章でなくテストで固定する姿勢（Architect, Tester）。
- **H2 を明示的に不採用とし Testcontainers に一本化**（`test_strategy.md`）— 方言差による偽の安全網を排している（Tester）。※ただし H11 の通り他文書と衝突。
- **JaCoCo による閾値強制と段階的引き上げ方針** — 実測に追随させる手順まで書いており形骸化しにくい（Tester）。
- **enum 日本語ラベルの正典化** — ユーザーに見える言葉を一箇所に固定したユビキタス言語の実運用（PM, IxD）。
- **色のみに依存しない情報伝達を明記し、バッジ定義がラベル＋クラスの対で構成されている** — WCAG 1.4.1 への配慮が形だけで終わっていない（IxD）。
- **TransportStatus 全 9 値の表示規則を独立節で定義** — `EXCEPTION` / `UNKNOWN` という「例外的だが必ず起きる」状態の見せ方まで踏み込んでいる（IxD）。
- **例外業務が一覧・登録・解決の 3 画面で完結** — 解決フォームの「新到着予定日・対応方針・解決日時」は実務そのもの（User）。
- **荷役登録のカメラスキャン** — 港のヤードで手袋のまま 17 桁を打つのは無理であり必須（User）。
- **公開追跡ページで個人情報を非表示** — 荷主が取引先に URL を転送するのは日常茶飯事（User）。
- **スコープ外の混入を自己申告している**（`ui_design.md` ※1 の通関申告 US 未起票）— 隠さず明示する誠実さ（PM）。
- **US トレーサビリティマトリックス**（US → UC → BUC → ビジネス目標）が優先順位を議論する土台になっている（PM）。

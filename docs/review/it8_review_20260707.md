## 高優先の詳細

### H-01 ConfirmPayment 単一 Tx 未配線 (アーキテクト)

iteration_plan-8 で invoice 更新 + Cargo.Settled 連動は「単一 Tx」と明記され、
`ConfirmPaymentCommand.hs` の docstring も「Tx 境界は Interfaces 層が TxRunner で
囲む (T-01)」と記載。しかし `handlerConfirmPayment` は `Confirm.execute` を `liftIO`
で直接呼ぶのみで、`billingPageApp` に TxRunner が注入されていない
(`handlingPageApp` が `hpdTxRunner` を注入するのと対照的)。`updateInvoice` と
`markSettledByBookingId` が autocommit で独立コミットされ、後者失敗時に
invoice=Confirmed / Cargo=Confirmed の不整合が残留しうる。

- **対応方針**: IT9 で `billingPageApp` に TxRunner を注入し `handlerConfirmPayment`
  を `runTx` で包む。ConfirmPaymentCommand は `Monad m` 制約のまま TxRunner の m で
  実行可能。docstring の実装乖離も同時解消。

### H-02 OverdueCheckCommand 未配線 (ユーザー代表)

`OverdueCheckCommand` は実装・テスト済だが Main.hs で配線されておらず、起動する
エンドポイント / cron / バッチが存在しない。US23 受入基準 5「支払期限超過時、
経理担当者に未払い通知が送信される」が機能的に成立していない。

- **対応方針**: IT9 で起動主体を設計 (定期バッチ or 経理担当者向け手動トリガ
  エンドポイント)。設計判断を伴うため IT8 では対応せず、報告書・KPT に明示する。

### H-06 E2E 緩い正規表現 (テスター)

`toContainText(/[A-Z0-9]{8}/)` / `/TR[A-Z0-9]{6}/` はアンカーなしで追跡番号以外にも
偽陽性マッチし、フォーマット変更バグを検知できない。`data-testid` で要素特定 +
`toHaveText(/^TR[A-Z0-9]{6}$/)` の完全一致に改める (IT9)。

## IT8 内で即対応する指摘 (H-03/H-04/H-05/M-01/M-02)

軽微かつ低リスクで、GA 品質の一貫性に直結するものは本クロージング内で対応する。

- **H-03 割引式の二重定義**: Domain に `discountedAmount :: DiscountRate -> Money -> Money`
  を切り出し、`applyDiscount` と View の双方から呼ぶ
- **H-04 withCorrelationId の finally**: `Control.Exception.finally` で `action:end` を
  確実に出力
- **H-05 ADR-0016 Status**: 「提案」→「採用」に更新し実績表現へ
- **M-01 用語二分**: domain-model / data-model 側に「請求書 (Invoice) = 精算書」の
  対応注記を追加
- **M-02 消費税属性**: ui_design のオブジェクトモデルに「tax は IT8 未実装、
  invoice テーブルには列があるが集約は未使用」の注記を追加

## 良い点 (事実として記録)

- 全コマンドに対応する Spec が存在し TDD の痕跡が明確 (プログラマー / テスター)
- `sixDigitCodeFromInt` の純粋抽出 + hedgehog、`HandlingPageDeps` レコード化 (T7-F) は
  同型引数取り違え防止の正しい規律 (プログラマー)
- Cross-BC 3 port の Text-DTO 化で Rule 4 は良好に遵守、漏れなし (アーキテクト)
- Billing → Booking/Pricing/Notification の一方向依存で BC 境界は自然、DDD 的に妥当
  (アーキテクト)
- IORef fake の独立性は良好、決定論的ジェネレータ注入で再現性が高い (テスター)
- domain-model の実装差分注記による乖離管理は妥当 (アーキテクト)

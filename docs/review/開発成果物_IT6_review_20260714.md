# 開発成果物レビュー（IT6・US19/US20 追跡例外対応）

## レビュー対象

- 対象: IT6 実装（git 差分 `b81d04c3..HEAD` の apps/ 配下・26 ファイル・+1177 行）
- 範囲: Tracking BC の追跡例外対応（US19 遅延例外・US20 破損/紛失例外）＋ IT5 レビュー高優先 H1-H4 消化

- レビュー日: 2026-07-14
- レビュー種別: 正式（developing-review・XP 5 エージェント並列）

## 総合評価

IT6 は追跡例外対応をドメイン中核に凝集させた良質な実装で、ヘキサゴナルアーキテクチャの依存方向・BC 独立・単一未解決不変条件の三者整合（domain-model / UI / 通知）が高水準で保たれている。ADR-0009 の起票と ArchUnit ルール 5/6 の基準線固定、post-commit 失敗の可観測化（WARN ログ）も良い実践。全 255 テスト緑・0 警告・ドメイン被覆 96-98%。

一方、複数エージェントが共通して指摘した最重要テーマは **(A) 対応報告（ResolveException）の荷主通知が記録されない（受入基準の一部未達）** と **(B) ADR-0009 が要求する冪等性の統合テストが未整備で、通知テーブルに一意制約が無く at-least-once 再送で二重記録され得る** の 2 点である。加えて **(C) 設計ドキュメント（data-model の exception_notification 欠落・ui_design の例外登録ワイヤー乖離・「Booking が消費」の文書乖離）** のドリフトが継続している。変換ヘルパ重複負債（IT4 M1）は本 IT でも未返済・拡大した。

## 対応方針（高優先 2 件）

| 指摘 | 対応方針 |
|------|---------|
| H1（対応報告の荷主通知） | **IT7 着手時に対応**。`ResolveExceptionCommand` に解決通知の append-only 記録を追加（ExceptionNotification の Recipient.Shipper・種別=対応報告）。受入基準 AC4/AC5 の完全充足。低コストで価値大 |
| H2（変換ヘルパ集約） | **IT7 冒頭の負債返済枠で対応**。`Shared.Infrastructure.Persistence` に `DatabaseTimestamp`・`EnumDbCodec.ToScreamingSnake/FromScreamingSnake` を新設し Booking/Routing/Tracking の 8 箇所を一括巻き取り（部分適用禁止）。Row DTO 重複方針も ADR 検討 |

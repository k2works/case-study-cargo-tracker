# IT7 コードレビュー結果

## レビュー対象

- **イテレーション**: IT7（荷役拡張・例外処理）
- **レビュー日**: 2026-05-11
- **変更範囲**: US16（引取作業記録）・US05（危険物・冷凍貨物予約）・US19（遅延例外処理）

---

## 総合評価

IT7 では 3 つのユーザーストーリーすべてが計画 SP どおり完了し、テストカバレッジも trackingms 86%（目標 80% 達成）を達成した。ヘキサゴナルアーキテクチャの層分離、集約ルートを通じた状態管理、値オブジェクトのバリデーションといった基本設計は良好。

一方で、**型安全性の欠如**（String による exceptionType・status 管理）、**リポジトリの更新判定ロジックの脆弱性**（responseContent != null での判定）、**コントローラーの Map レスポンス**（DTO 未定義）、**UI の未実装部分**（対応内容更新画面、例外ページへの導線）が共通して複数エージェントから指摘された。

---

## エージェント別フィードバック詳細

<details>
<summary>xp-programmer（高: 3 / 中: 4 / 低: 2）</summary>

### 評価サマリー
全体として機能は正しく動作する設計になっているが、ドメインモデルの型安全性不足と永続化層の更新判定ロジックに脆弱性があり、今後の変更を安全に行うための改善が必要。

### 良い点
- HazmatInfo / TemperatureInfo が record + compact constructor でバリデーション付き Value Object として適切に設計されている
- TrackingActivity が集約ルートとして例外イベントのライフサイクルを管理し、`Collections.unmodifiableList` で不変性を保証
- TrackingExceptionService がドメインロジックを集約に委譲しており、サービスがシンプルに保たれている
- `respond()` メソッドがドメインの振る舞いとして状態遷移を内包

### 懸念事項
- TrackingActivity を介さずにエンティティの状態を変更するパターン（集約の整合性境界を破るリスク）
- insert/update 判定の 2 つの異なるヒューリスティクスが互いに非排他的
- TrackingExceptionEvent 単体のユニットテストが見当たらない
</details>

<details>
<summary>xp-tester（高: 3 / 中: 4 / 低: 2）</summary>

### 評価サマリー
カバレッジは trackingms 86%（良好）、bookingms 79%（目標 80% に僅かに未達）。テストピラミッドのバランスは適切で、モックの使い方も正しい。ただし、PUT エンドポイントの統合テスト不在と異常系の不足が目立つ。

### 良い点
- `@DirtiesContext` + `@Sql` で DB 状態リセットによるテスト独立性確保
- フロントエンドで hook のモックが適切、ユーザー操作を通じた振る舞い検証
- isPending 時のボタン無効化テストは UX 品質に直結

### 懸念事項
- status フィールドの文字列リテラルが typo による不整合リスク
- TrackingExceptionEvent 自体のユニットテストが不在
- フロントエンドで `as unknown as ReturnType<...>` キャストが多用され型安全性が低下
</details>

<details>
<summary>xp-architect（高: 2 / 中: 3 / 低: 2）</summary>

### 評価サマリー
ヘキサゴナルアーキテクチャの層分離は概ね守られており、集約ルートを通じた操作、ポート経由のリポジトリアクセスという基本構造は健全。ドメインモデルの型安全性とリポジトリの更新判定ロジックに改善の余地あり。

### 良い点
- `addException()` が集約ルートを経由し状態遷移を一箇所で制御
- `Collections.unmodifiableList()` で内部コレクションの漏洩を防止
- マイグレーションの外部キー制約でデータ整合性を DB レベルで担保

### 懸念事項
- 例外解消後の状態復元パス（EXCEPTION → 元状態）が未設計
- TrackingActivity が events と exceptions の 2 コレクションを毎回ロードする将来的なパフォーマンスリスク
- PUT エンドポイントの統合テスト不在
</details>

<details>
<summary>xp-technical-writer（高: 3 / 中: 2 / 低: 2）</summary>

### 評価サマリー
コード構造は明瞭でテストがユースケースの理解を助けているが、API 利用者が「コードを読まずに正しく使える」状態にはなっていない。入力値の制約が暗黙的で、exceptionType の取りうる値が不明、エラーレスポンスの形式が不文書。

### 良い点
- `respond()` メソッドが状態遷移を内部で管理し、呼び出し側が状態を意識不要（設計が良い）
- マイグレーション SQL のカラム定義が NOT NULL / DEFAULT を適切に使用
- テストの `@DisplayName` が日本語でシナリオの意図が読み取りやすい

### 懸念事項
- PUT エンドポイントの統合テスト不在のため、仕様が未確定
- レスポンスの `exceptions[].id` が新規作成直後に null になる可能性
</details>

<details>
<summary>xp-user-representative（高: 3 / 中: 4 / 低: 3）</summary>

### 評価サマリー
3 ストーリーとも基本的な業務フローをカバーし「まず使える」レベルに達している。ただし US19 の対応内容更新 UI 未実装は例外処理ワークフローが途中で切れるため業務上の影響が大きい。

### 良い点
- CLAIM 選択時の動的フィールド表示で入力ミスや混乱が減少
- 追跡番号保持のまま他フィールドをクリアする動作が現場フローに合致
- 危険物/冷凍の色分け（orange/blue）が視覚的に明確

### 懸念事項
- 例外記録後の状態遷移（EXCEPTION → 元状態への復元）が UI 上で不可逆に見える
- US19 例外記録ページへの導線が不明
- US05 で HEAVY 選択時に追加入力セクションがない
</details>

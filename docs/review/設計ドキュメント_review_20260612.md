## 総合評価

US01〜US25 のトレーサビリティが UI 設計とテスト戦略の双方で担保され、DDD + ヘキサゴナル + CQRS の意図が ArchUnit による機械検証まで含めて一貫した、完成度の高い設計ドキュメント群である。一方で、(1) ドキュメント間の不整合（TransportStatus の値集合、フロントエンドアーキテクチャからの Estimation Context 欠落）、(2) 並行性（lost update）の設計判断の欠落、(3) 現場業務の継続性（オフライン荷役登録・経理の月末一括処理・メンテナンス中の追跡照会継続）という 3 系統の問題が開発着手前に解消すべき課題として残っている。

## 矛盾事項

| # | 視点 A | 視点 B | 論点 | 推奨判断 |
|---|--------|--------|------|----------|
| 1 | セキュリティ（タイムアウトは無操作検出が目的） | UX（ポーリング中の画面注視はアクティブ利用） | htmx ポーリングを keep-alive と見なすか | ポーリングは keep-alive と**見なさない**（`lastAccessedAt` を更新しない専用エンドポイント or ヘッダー判定）。ユーザー操作（クリック・入力）のみ延長対象とし、警告バナーで延長を促す（H8 で明文化） |
| 2 | スコープ管理（入力値復元は Phase 2 で YAGNI 遵守） | 現場業務（荷役登録の入力消失は初期から実害大） | `sessionStorage` 退避の実装時期 | 全画面一律 Phase 2 は維持しつつ、**荷役作業登録のみ初期リリースで退避・再送を実装**する（H9。リスクの高い画面に限定投資） |
| 3 | SonarQube Quality Gate をマージブロックにする（non_functional.md） | Scala プラグインの保守リスクから一次防衛線は scalafmt/scalafix/scoverage（tech_stack.md） | 不安定な外部ツールをブロッキングゲートに据えるか | SonarQube は**可視化（非ブロッキング）に一本化**し、ブロッキングゲートは scalafmt/scalafix/scoverage/-Werror に限定する（アーキテクト懸念を採用） |

## 懸念事項（横断）

- **HikariCP × ECS の接続数が RDS 上限ピッタリ**（10 タスク × 20 = 200 = max_connections）。RDS 内部用接続を考慮し、プール縮小（例 15）か RDS Proxy を Auto Scaling max 10 運用の前提条件とすべき（アーキテクト）
- **`AuthenticatedAction` の毎リクエスト users テーブル参照**（`session_generation` / `lastAccessedAt` 検証）がステートレス水平スケールの利点を一部相殺する。認証経路の DB 負荷見積もりに織り込みが必要（アーキテクト）
- **`SyncDomainEventPublisher` の部分配信リスク**。購読者ごとの try/catch 隔離 + ログ化を設計に明記すべき（アーキテクト）
- **US15「即座に反映」と実際の最大 30 秒ラグ**の期待値ギャップはビジネス側との合意が必要（PM）
- **見積→予約の引き継ぎ「将来対応」**は営業の二度打ちを発生させ US01 の価値を半減させる。優先度の再検討余地（PM、インタラクションデザイナー、ユーザー代表の 3 者が指摘）
- **E2E の htmx ポーリング起因フレイキー対策**（リトライ方針）が未記載（テスター）
- **同時セッション数 1 と現場の複数端末運用**（共有端末 + 個人スマホ）の衝突可能性（ユーザー代表）

## スコープ外の発見

- `users` のパスワード過去 5 世代再利用禁止に対し `password_history` テーブルが未定義（PM）
- Flyway マイグレーションパスの表記ゆれ（`conf/db/migration/default/` / `conf/db/migration/`）（PM）
- operation.md の定常運用カレンダー（Gantt）が繰り返しタスクを長期単発タスクとして描画しており意図と図が不一致（アーキテクト）
- US13 の「経路設計中へ戻す（差し戻し）」ボタンが予約詳細の操作表に未反映（ユーザー代表、テスター L5 と関連）

### 評価サマリー

DDD・ヘキサゴナル・CQRS の意図が一貫して貫かれ、ドメイン層の純粋性を ArchUnit で機械的に守る設計は「変更を楽に安全にできる」基盤として高水準です。一方で、状態 enum・コンテキスト数・テーブル定義に複数ドキュメント間の実装非互換な不整合があり、Scala コード例にもコンパイルできないものが混在しているため、実装着手前の整合化が必要です。

### 良い点

- **依存方向の規律が機械化されている**（ArchUnit 4 ルールの CI 検証）。
- **トランザクション境界の明示化**（`DB.localTx` + イベントのコミット後発行）。
- **コンテキスト間を DB 外部キーで結合しない判断**（将来のサービス分割の切れ目を塞がない）。
- **VoyageNumber のコンテキスト別 opaque type 分離**。
- **テスト形状の選定根拠が明快**（「型で防げるものはテストしない」）。
- **Forward マイグレーション + Expand-Contract の採用**（Flyway Community の制約を正しく認識）。

### 改善提案

- 【重要度: 高】TransportStatus の値集合を統一する（architecture_backend.md と domain-model.md で非互換）。
- 【重要度: 高】TransportStatus（Shared）と TrackingStatus（Tracking 集約）の関係を定義する（同一 9 値の二重定義）。
- 【重要度: 中】Scala コード例のコンパイル可能性を是正する（`bookCargo` の Either 内包の型不整合・イベント発行位置の自己矛盾、`assignRoute` の `transitionTo` 版への統一）。
- 【重要度: 中】「将来追加予定カラム」と概念データモデルの混在を整理する（フェーズ凡例の導入）。
- 【重要度: 中】MDC のスレッドローカル問題を「注意」から「設計判断」（ADR 化）に格上げする。
- 【重要度: 低】コンテキスト数の表記をドキュメント横断で揃える。

### 懸念事項

- HikariCP × ECS タスク数 × RDS max_connections が上限ピッタリ（200 = 200）。RDS Proxy を前提条件化するかプール縮小を。
- ScalikeJDBC のブロッキング I/O 隔離が「方針」止まり（専用ディスパッチャーのスレッド数 ≒ プールサイズの整合ルール化を推奨）。
- クライアントサイド Cookie セッションでの同時セッション制御は毎リクエスト users 参照を生み、水平スケール利点を一部相殺。
- SonarQube Quality Gate のマージブロックと「一次防衛線は scalafmt/scalafix/scoverage」の矛盾。非ブロッキングへ一本化を。
- SyncDomainEventPublisher の部分配信リスク（購読者ごとの try/catch 隔離を明記すべき）。

### スコープ外の発見

- operation.md の Gantt 表記が誤用（繰り返し運用が長期単発タスクに見える）。
- 公開追跡の個人情報非表示要件と画面項目の突き合わせを UI レビューで推奨。

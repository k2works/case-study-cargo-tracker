# IT1 実装 マルチパースペクティブレビュー（2026-07-28）

対象コミット範囲: `a92834b3..HEAD`（US26/US27 認証、US02/US03 荷主登録、全ルートのプレースホルダ、CSS・シード・ログイン案内）。5 つの XP 視点（programmer / tester / architect / technical-writer / user-representative）で並列レビューを実施した。

## サマリー

- **クローズ前対応済み（高）**: email 一意制約欠如による重複登録の穴（H1）、法人割引率未入力時の内部例外露出（H2）、受入基準の未検証テスト 4 件を修正・追加。
- **次イテレーション対応（Try に反映）**: リポジトリポート抽象化（DIP）、ADR-0001 の RuboCop カスタム cop 未実装、Packwerk privacy、識別子 ShipperId/ShipperCode の確定、README 整備、ユビキタス言語ドリフト（利用者 ID / ロール表記）、荷主登録フォームの動的表示 UX。

## 視点別指摘と対応方針

### プログラマー（コード品質）

| # | 深刻度 | 指摘 | 対応 |
|:--|:--|:--|:--|
| H1 | 高 | `shippers.email` に一意制約がなく、find→save の TOCTOU で重複登録が成立 | **対応済み**: 一意インデックス追加 + `RecordNotUnique` を重複結果へ合流 |
| H2 | 高 | 法人で割引率未入力時 `BigDecimal("")` の内部例外がユーザーに露出 | **対応済み**: 日本語メッセージ「法人荷主には割引率が必須です」へ |
| M3 | 中 | 「一時ロック」の文言に対し自動解除機構がなく実質恒久ロック | 次 IT: ロック仕様（時限/恒久）を確定し文言か実装を整合 |
| M4 | 中 | Application 層が具象 `ActiveRecordShipperRepository` にデフォルト依存（DIP 逆流） | 次 IT: リポジトリポート抽象化・合成ルート注入 |
| M5 | 中 | `register_failure!` が increment→lock の 2 UPDATE で非アトミック | 次 IT: `with_lock` か単一 UPDATE 化 |
| M6 | 中 | `CorporateShipper.register` の `superclass.register` が二重生成で脆い | 次 IT: 検証分離で `Shipper.register` 直呼び |
| L7-L10 | 低 | ユーザー列挙タイミング差・memo 化・割引率整数固定など | 次 IT 以降で随時 |

### テスター（テスト品質）

- **受入基準の未検証 4 件**（US26 ロック/無効化拒否時の監査ログ、US27 ログアウトのログ記録）→ **対応済み**: authentication_service_spec・requests/authentication_spec にテスト追加。
- テスト構造・命名・factory trait は良質、テストピラミッドは健全と評価。
- 残: US27「ログアウト後に戻れない」の意味的検証はセッション破棄で担保済み（system spec でカバー）。

### アーキテクト（構造）

| 深刻度 | 指摘 | 対応方針 |
|:--|:--|:--|
| 高 | ADR-0001 の「ドメイン層 AR 依存禁止」を担保する RuboCop カスタム cop が未実装 | 次 IT: cop 実装 or ADR を「目視 + Packwerk」に改訂 |
| 高 | アプリ層→具象リポジトリの依存（ポート未定義） | 次 IT: `Shipper::Domain::ShipperRepository` ポート導入 |
| 中 | Packwerk privacy 未強制・`public/` 公開面未定義 | Booking→Shipper ACL 導入前に `enforce_privacy` 有効化 |
| 中 | 識別子ドリフト: 設計 `ShipperId`（Shared）vs 実装 `ShipperCode` | 次 IT: 越境識別子の正本を確定し ADR 追記 |

- 良好点: 認証を業務パック外に置いた関心分離、ドメイン層の Rails 非依存、スキーマ整合は設計に忠実。

### テクニカルライター（ドキュメント）

| 深刻度 | 指摘 | 対応方針 |
|:--|:--|:--|
| 高 | README が Rails 雛形のまま（起動・seed・テスト手順の入口なし） | 次 IT: README 整備 |
| 高 | 認証フィールド名が 3 通り（利用者 ID / ユーザー名 / メール）にドリフト | 次 IT: ui_design を「利用者 ID = username」に統一 |
| 中 | ui_design のロール（shipper/consignee）が 5 ロール RBAC と不一致 | 次 IT: ui_design を 5 ロール + 外部未認証で整理 |
| 中 | シードパスワードが 3 箇所ハードコード | 次 IT: dev 定数の一元化 |
| 低 | data-model のマイグレーション名・荷主コード桁が実装とずれ | 次 IT: data-model 修正 |

- 良好点: 日本語コメント（目的 + 対応 US）、ログイン画面のロール別アカウント案内は good example。

### ユーザー代表（業務利用）

- 法人契約情報フィールドが個人登録時も常時表示され認知負荷（高）→ 次 IT: 種別選択に応じた動的表示（Stimulus）。
- US02「既存荷主のどちらを使用するか選択」が実質「一覧へ戻る」だけ（高）→ 次 IT: 選択フローの充実。
- デモ項目 4 点は受入基準を満たすことを確認。

## 結論

高優先の**正しさに関わる不具合（H1/H2）と受入基準の未検証**はクローズ前に解消した。残る指摘は設計硬化・ドキュメント整備・UX 改善であり、いずれも IT1 のデモ価値を損なわないため、次イテレーションのふりかえり Try に反映して計画的に返済する。

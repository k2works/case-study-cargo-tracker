## 総合評価

**式を 1 か所に閉じる**（[ADR-028](../adr/028-settlement-and-quotation.md) 決定 6）という中心の
決定は、バックエンドでは構造として守られていた——`TransportCharge` が唯一の式であり、
見積も請求も必ずそこを通る。赤伝の一意制約を H2 と PostgreSQL の双方で成立させた作り
（`void_marker` と Flyway の Java マイグレーション）も、過去 IT の「方言差は両方向に起きる」
という学びの正しい適用である。

一方で、**自分で書いた 2 つの決定が噛み合っていない箇所**が中心部にあった。
精算の対象にはキャンセル済みの予約も並ぶ（[ADR-027](../adr/027-transport-charge-calculation.md)
決定 5）のに、予約は引取済からしか「精算済」へ進めない（ADR-028 決定 1）。この 2 つを繋いだ
結果、**キャンセル料の入金を永久に記録できない**経路ができていた。全テストが緑のまま、
実環境の E2E でも通らない——キャンセル済みの予約を精算する筋を、誰も 1 度も通していなかった。

**代替（メール・決済機関・未払い通知）の 3 件は業務として成り立つ**という評価を得た一方、
**検索が無いことは 2 度目の指摘**である（IT11 と同じ）。

## 中優先度（27 件）

対応した主なもの:

- ADR-028 のコンプライアンス表が挙げる **5 クラスすべてが実在しなかった**（architect）
  → 実体の名前に直し、**ADR が挙げる検査の実在を検査**にした（`AdrComplianceTableTest`）。
  この検査は ADR-027 でも 1 件（`TaxRateTest`）を見つけた
- ADR-028 決定 7 の「見積番号は年をまたぐと 1 に戻る」は実装と違う（architect）→ ADR を修正
- モックの `?? 1.0` が本物より甘い（programmer・tester）→ 断るようにした
- 見積との食い違い警告が、条件を直しても出し直されない（user）→ 判定し直す
- 全件の一覧で期限超過を見分けられない（user）→「（超過）」を出す
- 参照番号が任意であることがラベルに無い（writer）→「（任意）」を足した
- `domain-model.md` の料金式・`data-model.md`・ADR-028 の参照先（writer）→ 修正

**IT13 へ送るもの**（下記「残作業」に再掲）:

- `create` が候補を引き直すことによる外部呼び出しの多さ（architect）

# IT10 コードレビュー結果

**レビュー日**: 2026-05-12
**対象コミット**: a1ac7192（バックエンド）/ 348a63e8（フロントエンド）/ 46e98562（E2E）
**対象機能**: US01 輸送見積、US02 個人荷主登録、US03 法人荷主登録

---

## 総合評価

既存の bookingms アーキテクチャパターン（Hexagonal Architecture + DDD）に概ね沿った実装で、3 つのユーザーストーリーの基本的な業務フローはすべて実現されています。Command パターン、ファクトリメソッド、ドメイン層のバリデーション配置など、設計の一貫性が保たれています。

一方で、以下の問題が複数のエージェントで共通して指摘されました：

1. **ビジネスロジックのハードコーディング**（料金体系・ルート候補生成）
2. **入力値バリデーションの不足**（フロント・バックエンド双方）
3. **UX の改善余地**（LOCODE 入力補助・登録後フィードバック）

---

<details>
<summary>xp-programmer（高: 3 / 中: 2 / 低: 1）</summary>

### 評価サマリー
全体として DDD の集約パターンに沿った構造で、record による Command パターンも適切。ただし、ビジネスロジックのハードコーディングと ID 生成の非決定性に設計上の問題がある。

### 良い点
- Command を record で定義 — 不変性が保証され、意図が明確
- ファクトリメソッドパターン — `Shipper.createCorporate` / `createIndividual` で生成ロジックを集約内に閉じている
- バリデーションの配置 — 割引率の検証がドメイン層にある（正しい責務の場所）
- `replaceCandidates` の防御的コピー — `new ArrayList<>(candidates)` で外部からの変更を防いでいる
- 状態遷移がドメインに閉じている — `replaceCandidates` 内で `status` を自動設定

### 改善提案
- 【高】`generateCandidates` のマジックナンバーとハードコーディング
- 【高】`generateShipperCode` が `Math.random()` を使用
- 【高】`LocalDate.now()` の直接呼び出し
- 【中】`ShipperCommandService` の文字列比較による分岐
- 【中】フロントエンドのフォームバリデーション不在
- 【低】`RouteCandidate` のコンストラクタ引数の意味が不明

### 懸念事項
- テストファーストの証跡が差分に含まれていない
- `ShipperCommandService.register` に `@Transactional` がない可能性
</details>

### 評価サマリー
既存の bookingms アーキテクチャパターンに概ね沿った実装。Aggregate Root 設計、Port インターフェース分離など一貫性がある。ドメインロジックのアプリケーション層への漏出と Value Object の活用不足が変更容易性に影響する。

### 良い点

- `getCandidates()` の防御的コピー
- ファクトリメソッドの責務分離
- 集約間の参照が ID のみ（将来のサービス分割が容易）

### 改善提案
- 【高】`shipperCode` 生成のドメイン層への帰属が不明確
- 【高】`generateCandidates` ロジックのアプリケーション層への漏出
- 【中】`shipperType` が String（enum にすべき）
- 【中】`Shipper` に `equals`/`hashCode`/`toString` がない
- 【中】`RouteCandidate` は Entity ではなく Value Object が適切
- 【低】`Estimate.create()` の `cargoType` が String
- 【低】`setId` がドメインモデルに露出（技術的負債）

### スコープ外の発見
- `Cargo` のコンストラクタ数が多く Builder パターン検討余地あり
</details>

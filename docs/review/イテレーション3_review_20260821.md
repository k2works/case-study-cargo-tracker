### tester

### architect

### 改善提案

- **【重要度: 高】** `apps/backend/routingms/src/main/java/com/example/routingms/domain/model/VoyageDifference.java:39-40, 64-66`

  `describeInstant` が **1 区間目の出発日時しか比較していません**。比較項目は 船名 / 運送会社 / 貨物種別 / 寄港地 / 出発日時(先頭のみ) の 5 つで、**到着日時はどの区間についても一度も比較されない**し、2 区間目以降の出発日時も比較されません。

  結果、寄港地・船名・運送会社・貨物種別が同じまま時刻だけがずれた登録は `hasChanges() == false` になります。そして `voyage-register-page.tsx:240-286` は `hasChanges` が false のとき **「閉じる」ボタンしか出さない**（`voyage-register-page.test.tsx:200` がそれを固定している）ため、経路設計者は **画面から一切更新できません**。「変更はありません」と表示されて終わりです。

  これは US25 の最も一般的なケース（遅延・スケジュール改定による時刻の付け替え）そのもので、しかも `RegisterVoyageUseCaseTest` の 3 つの差分テスト（船名・寄港地・貨物種別）がいずれも時刻を動かしていないため、全緑のまま通っています。`describePorts` と同じ粒度で全区間の出発・到着を文字列化して比較する（例: `JPTYO 09-01 09:00 → CNSHA 09-03 18:00 → ...`）のが最小の修正です。先に「時刻だけを変えると差分が出る」赤いテストを置いてください。

- **【重要度: 中】** `apps/backend/bookingms/src/main/java/com/example/bookingms/interfaces/rest/CargoBookingController.java:100-112`

  `detail` は `requireSalesOrRouting` だけで、`visibleRoutingStatus`（同ファイル 195-201）のような引き渡し済みへの限定がありません。一覧では「経路設計者はまだ引き渡されていない予約を見る必要が無い」と明記して `ROUTING_REQUESTED` に絞っているのに、詳細は予約番号さえ分かれば任意の予約が開けます。予約番号は `V3__init_booking_cargo.sql:34,42` のとおり `LPAD(NEXTVAL(...), 6, '0')` の連番で、列挙は容易です。一覧の制限がそのまま迂回できるので、詳細側でも `ROLE_ROUTING` 単独の場合は `cargo.awaitingRouting()`（`Cargo.java:116`。判定はすでに集約にあります）で 404 に倒すべきです。

- **【重要度: 中】** `apps/backend/routingms/.../Voyage.java:86-93` と `VoyageMapper.java:29-42` — 同じ判断が 2 か所にあり、往復航海で答えが食い違う

  `Schedule.of` は同一港への再寄港を禁じていません（A→B→A→C は通る）。このとき `Schedule.callingOrderOf` は **最初の出現位置しか返さない**ため、`connects(B, A)` は `1 < 0` で false になります。一方で検索 SQL は `d.seq_number >= o.seq_number` を満たす区間の EXISTS で判定するため、同じ往復航海を **B→A の候補として返します**。

  往復は海運では常態であり、`Voyage` の javadoc が「判断を呼び出し側に散らかすと、画面と経路探索で別々の答えを出すようになる」と書いた事態が、SQL と集約のあいだで既に起きています。IT4 の経路候補算出は `connects()` を使う想定なので、「検索一覧には出るが経路として採用されない航海」という形で表れます。`callingOrderOf` を全出現位置を返す形にして「to のいずれかが from のいずれかより後」で判定し、往復航海を使った検査を `VoyageTest` と `VoyagePersistenceIntegrationTest` の両方に置くのが筋です（本番と検査で別の述語を持たせない、と同じ理由で SQL と集約でも別の述語を持たせない）。

- **【重要度: 中】** `apps/backend/shared/src/main/java/com/example/shared/auth/AuthenticatedUserFilter.java:29, 69-70`

  フィルタが `request.setAttribute(ATTRIBUTE, AuthenticatedUser.of(...))` で解決済みの利用者を後続に渡していますが、**この属性を読んでいる本番コードは 1 行もありません**（`grep "AuthenticatedUserFilter.ATTRIBUTE\|getAttribute("` で本番側 0 件）。全コントローラは `@RequestHeader` を 2 つずつ受け取って `AuthenticatedUser.of` を呼び直しています。結果として (a) 同じ解析が毎リクエスト 2 回走り、(b) 全エンドポイントのシグネチャに 2 引数のノイズが乗り、(c) 「渡している」つもりのコードが死んでいます。属性を消して意図をコメントから外すか、`HandlerMethodArgumentResolver` で `AuthenticatedUser` を直接引数に取れるようにして `@RequestHeader` の重複を消すか、どちらかに倒してください。後者なら認可の書き忘れも減ります。

- **【重要度: 低】** `apps/backend/routingms/.../AuthenticatedUserFilterRegistrationTest.java:35-36`

  正規表現 `new\s+AuthenticatedUserFilter\s*\(` は **インスタンス化されていること**しか見ておらず、`FilterRegistrationBean` として登録されていること・URL パターンが `/*` であること・順序が最優先であることは検査していません。テストの表示名は「登録している」と言っているので、宣言と検査内容にずれがあります。`FilterRegistrationBean<AuthenticatedUserFilter>` の Bean を返す `@Bean` メソッドの存在まで見るか、表示名を実態に合わせてください。

- **【重要度: 低】** `apps/backend/routingms/.../MyBatisVoyageRepository.java:44-51` / `RegisterVoyageUseCase.java:26-31`

  同一トランザクション内で `findByVoyageNumber` が 3 回走ります（ユースケースで 1 回、`save` の分岐で 1 回、`save` 末尾の読み戻しで 1 回）。動作は正しいですが、`Voyage.id()` を持っているのに使わずに毎回問い合わせている点は bookingms の `cargo.id() == null` 分岐と不揃いです。ユースケースが既存の `Voyage` を持っているのだから、`save` に渡す `Voyage` に id を載せて分岐する方が意図が読めます。

- **【重要度: 低】** `apps/backend/routingms/.../UserFacingMessage.java:22-23`

  最初の `": "` で無条件に切るため、診断情報を持たないメッセージでも文中に `": "` が現れれば途中で切れます。現在の文言では起きませんが、切る条件を「末尾側の `": "` 以降」あるいは例外側で診断情報を別フィールドに持つ形にした方が壊れにくいです。bookingms 側にも同じクラスがあり（`bookingms/.../UserFacingMessage.java`）、完全な重複です。共有カーネルの範囲を広げたくないという判断は理解できますが、`SharedKernelScopeTest` が枠を固定した今こそ、ADR で扱いを決める好機だと思います。

### 懸念事項

- **差分比較の網羅性を守る仕組みが無い。** 上記【高】の根本は、`Voyage` にフィールドを足しても `VoyageDifference` が追随しない構造にあります。IT4 以降で航海に属性が増えるたび同じ穴が空きます。「`Voyage` の全アクセサが差分比較に現れること」を検査するメタテスト（`SharedKernelScopeTest` と同じ発想）を置くか、差分算出を `Voyage` 自身の責務にして「比較に使う表現」を 1 か所に集約するのが安全です。

- **`Schedule.restore` は空リストを許すが、`origin()` / `destination()` / `callingPorts()` は `get(0)` を無防備に呼ぶ。** `VoyageResponse.from` も `carrierMovements().get(0)` を呼ぶため、区間が 0 行の `voyage` 行が 1 件でもあると一覧全体が 500 になります。`save` は `@Transactional` なので通常は起きませんが、`carrier_movement` の手動削除や別経路の投入で発生しうる状態です。「復元では検査しない」の原則は正しいので、検査ではなく **一覧側が壊れた行を飛ばして残りを見せる** 方向で守るのが良いと思います（1 行のために全員の画面が止まるのが最悪）。

- **`RegisterVoyageUseCase.register` の存在確認と `save` のあいだにトランザクション境界が無い。** `@Transactional` は `MyBatisVoyageRepository.save` にしか付いていないため、同じ航海番号の同時登録は `voyage_number` の UNIQUE 制約違反（500）として現れます。IT3 の規模では実害はありませんが、`ck_voyage_supported_cargo_types` や UNIQUE 違反を利用者向けの文言に変換するハンドラが無い点は将来の宿題です。

- **【重要度: 高】`VoyageMapper.java:80-86` — 一覧の既定に出港済みの航海が混ざります。** 並びは出発日の昇順なので、**過去の便が先頭を占めます**。経路設計者が朝いちばんに開いて最初に目に入るのが、もう出てしまった船です。既定は「本日以降の出発」に絞り、過去を見たいときだけ明示的に外せる形（「出港済みも含める」）にしてください。IT2 の予約一覧で同じ議論をしたはずです。
- **【重要度: 中】`booking-list-page.tsx:60-63` — 経路設計者にも「新規登録」ボタンが見えます。** `/booking/new` は営業限定（`App.tsx:34-47`）なので、押すと 403 です。共有画面に置くリンクはロールで出し分けてください。
- **【重要度: 中】営業側に「まだ引き渡していない予約」に気づく手段がありません。** 一覧に経路の状態列が無く（`booking-list-page.tsx:137-145`）、営業ダッシュボード（`dashboard-panels.ts:24-33`）にも未依頼の件数がありません。経路設計者側だけ気づける状態です。実務では「金曜に取った予約を月曜に渡し忘れる」が起きます。一覧に経路の状態列と「未依頼だけ」の絞り込みを足してください（`routingStatus` は URL には効くのに画面に入口がありません）。
- **【重要度: 中】`booking-detail-page.tsx:188` — 依頼ボタンの出し分けが集約の述語と別物です。** 画面は `routingStatus === 'NOT_ROUTED'` だけを見ますが、集約 `Cargo.requestRouting()` は `BookingStatus` も見ます（`Cargo.java:95-107`）。いまは仮受付しか無いので同じ結果ですが、US11（予約確定）・UC22（キャンセル）が入った瞬間に「押せるのに 409 で断られる」ボタンになります。API に「依頼できるか」を返させ、画面はそれを使ってください。
- **【重要度: 中】`voyage-list-page.tsx:203` — 通常時に件数が出ません。** 50 件で切ったときだけ総件数が出ます。「該当 12 件」は毎回見たい情報です。
- **【重要度: 低】航海の中身を見る画面がありません。** 一覧に出るのは出発地と目的地だけで、途中の寄港地・区間ごとの時刻が確認できません。乗り継ぎを含む経路を組むとき、経路設計者は「この船はどこを経由するか」を見ます。US08（IT4）の前に欲しいです。

### 懸念事項

- **過去日の航海を登録できてしまいます。** 送信前の検査（`voyage-register-page.tsx:75-115`）は区間の整合だけを見ており、「昨日出発」の航海が通ります。参照データなので過去の実績を入れる正当な理由もあり得ますが、いまは打ち間違い（年の入力ミス）と区別がつきません。少なくとも警告は欲しいです。
- **「変更はありません」で終わったあと、次の行動がありません**（`voyage-register-page.tsx:278-286`）。閉じるだけで、入力した内容はフォームに残ります。既に同じ内容が入っているのだから、その航海を一覧で見る導線を置いてください。
- **依頼の取り消しができません。** ADR-015 は却下も再依頼も無いと決めていますが、実務では「渡したあとで荷主から条件変更の連絡が来る」ことが普通にあります。予約の訂正（次 IT）と一緒に、依頼の差し戻しをどう扱うかを決めておく必要があります。いまは経路設計者が誤った内容で経路を組むまで止まりません。

### スコープ外の発見

- `CargoBookingController.java:71-78` の `/locations`・`/hazard-classes` は営業限定です。いまの画面構成では困りませんが、経路設計者向けに予約の絞り込み（出発地など）を足すときに 403 で詰まります。
- 予約一覧に「到着期限が近い」の目印がありません。経路設計者が待ち行列を見たとき、どれから手を付けるかは期限で決まります。US08 で経路候補を出すときには必ず必要になります。

# IT4 実装マルチパースペクティブレビュー統合レポート

対象: US09/US10/US11/US12/US13（Booking Context 経路確定・予約確定・通知基盤 ADR-0002）。
5 視点（programmer / tester / architect / technical-writer / user-representative）で並列レビューを実施。全対象 spec は green（233 例）。

## エグゼクティブサマリー

状態機械の集約集約・悲観ロックによる read-modify-write のアトミック化・値オブジェクトの不変性・PRG・ドメインイベントによる通知の疎結合と、XP/DDD の規律が効いた健全な実装。構造を覆す欠陥はない。一方で **受入基準に対する明確なギャップ 3 点**（US10 条件協議依頼の欠落・US12 通知が意図的操作でない・確定後キャンセル不可）と、**正典乖離 1 点**（ADR-0002「集約が発行」vs 実装のアプリサービス発行）、**軽微な堅牢性欠陥 1 点**（`satisfied_by?` が最終脚 `unload_time` nil で 500）を検出した。

## 高優先度の指摘と対応方針

| # | 視点 | 指摘 | 対応 |
|:--|:--|:--|:--|
| H1 | programmer/tester | `RouteSpecification#satisfied_by?` が最終脚 `unload_time` nil で `NoMethodError`（500・未 rescue） | **対応**: `CargoItinerary` に「最終脚 unload_time 必須」不変条件を追加＋境界 spec |
| H2 | user-rep/tester | US10「満たす経路がない場合の荷主との条件協議依頼」が未実装（受入基準未達） | **対応**: 候補ゼロ画面に「条件協議を依頼」→通知記録（CONSULTATION_REQUESTED）を実装 |
| H3 | user-rep | US12 通知が紐付けと同時に自動送信され、営業の確認→送信操作がない（受入基準ギャップ） | **対応**: 紐付けからイベント発火を分離し「荷主へ経路を通知する」ボタン（POST notify_route）で送信。イベント駆動（ADR-0002）は維持 |
| H4 | architect | ADR-0002 決定#1・domain-model「集約がイベント発行」と実装（アプリサービス発行）の正典乖離 | **対応**: 実装は DIP 上優秀のため**正典を実装に合わせ改訂**（ADR-0002・domain-model を「アプリサービスがコミット後に発行」へ） |
| H5 | technical-writer | cargos の consignee_name/email がデッドカラム（未入力・未使用）＋ドキュメント誤記 | **対応**: data-model に「将来 US 用の予約カラム」注記を追加し誤記修正 |

## 良い点

- `satisfied_by?` の `to_date <= arrival_deadline`：期限当日着を刈らない正しい日付比較（DATE 期限 vs TIMESTAMP 到着の既知バグを回避）。
- `with_locked_cargo`：ロック取得→ドメイン操作→同一トランザクション保存が明快で、二重遷移・二重通知の防止意図とコメントが一致。
- `BookingStatus`：FORWARD/BACKWARD/CANCELLABLE の宣言的テーブルで遷移規則が一望でき、値等価・freeze も適切。
- 通知結線のテスト分離（`rails_helper` の `before { reset!; install! }`）が優秀で、reset! ポリューションを封じている。
- Packwerk privacy/dependency 違反ゼロ・公開 API 経由の越境・notifiable_id を自然キー string 化した BC 非依存の判断が妥当。

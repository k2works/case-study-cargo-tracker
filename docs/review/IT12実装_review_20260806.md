## High（すべて返済済み）

### H1. 解決しても荷主の画面に「遅延が発生しています」が残り続けた

**指摘元**: user-representative ／ **返済済み**

`TrackingExceptionView` に「解決済みか」を載せていなかった。荷主から見ると
**対応が終わっても遅延が続いているように見える**。通知が将来リリースである以上、
公開画面が唯一の伝達手段であり、そこが実態と食い違っていた。

### H2. 解決の瞬間に対応方針が消えた

**指摘元**: tester ／ **返済済み**

解決フォームは対応方針を送らないため、`resolution_notes = ?` に素直に代入すると
`NULL` で塗り潰される。**公開画面のコメント自身が「解決した瞬間に理由が消えると
問い合わせが増える」と書いていた**そのものだった。

記録と解決を**別々の DB で確かめていた**ため、この連鎖を誰も通していなかった。
`COALESCE` で上書きしない形にし、1 本のテストで連鎖を通した。

### H3. 追跡管理者の画面に例外の内容が一切出なかった

**指摘元**: user-representative ／ **返済済み**

フォームだけがあり、**荷主の公開画面のほうが情報が多い**という逆転が起きていた。
追跡管理者は荷主からの問い合わせに答える立場であり、**荷主より情報が少ないと
答えられない**。

### H4. `escalated` を誰も読んでいなかった（4 イテレーション連続の同型）

**指摘元**: programmer・tester・user-representative（**3 視点一致**） ／ **返済済み**

`grep escalat` すると**書き込み側しか存在しない**。48 時間ルールは純関数の
ユニットテストしかなく、**業務に効いていることは 1 件も検証されていなかった**。
判定を `false` に固定しても全テストが緑だった。

IT9（行ロック）・IT10（UNIQUE）・IT11（時刻の逆行）に続き **4 度目**である。

追跡管理者の画面に出し、**判定を潰すと単体と HTTP の両方が赤くなることを実測**した。

### H5. `now` が常に `T00:00` で、時間単位の判定が最大 24 時間ずれていた

**指摘元**: programmer・tester ／ **返済済み**

`toEpochHours` は「日数だけでは 2 日ちょうどと 2 日 1 時間を区別できない」ために
作ったのに、比較の片側が常に 0 時だった。**閾値ちょうどを含めるか否かの議論が
入口で無効になっていた**。`Clock.now()`（分精度）を足した。

### H6. `resolvedAt = Some("")` という番兵

**指摘元**: programmer・tester ／ **返済済み**

`ExceptionRecord` の doc は「`resolvedAt` が入っていれば解決である——別の型にすると
『発生していない解決』が型として作れてしまう」と宣言していたが、
`withResolutionNotes` が `Some("")` を「解決でない」の合図に使っていた。
**宣言した不変条件を自分の手で破っていた**。

さらに解決の指示を作るために、集約が `description = ""`（`raiseException` 自身が
拒む値）を組み立てていた。和型（`ExceptionWrite`）にして分岐を網羅検査に載せた。

### H7. 未解決の例外が複数あると、解決が全行を巻き込んだ

**指摘元**: programmer・tester ／ **返済済み**

`WHERE resolved_at IS NULL` に単一行への絞り込みが無く、未解決行が 2 つあると
**両方に同じ解決日時・同じ対応方針**が入った。`resolveExceptionSql` の doc が
「解決済みの行を上書きすると過去の対応記録が消える」と警戒していたのと
同じ事故が、未解決行どうしで起きていた。

直近 1 行に限定し、あわせて**例外中の再発生を拒む**ようにした——
先に解決してから次を記録するのは業務としてもその順序である。

### H8. 新しい到着予定日が未検証のまま `CAST` に渡っていた

**指摘元**: programmer・tester ／ **返済済み**

集約は `revisedArrival` を一切見ておらず、`abc` を送ると型変換で例外になった。
**IT4 で同じ形を踏んでいる**（`SharedCalendarText` のコメントが記録している）。
画面の `type="date"` は UI の制約であって入口の防御ではない。

### H9. 対応内容が空でも成功として返り、既存の記録が消えた

**指摘元**: tester ／ **返済済み**

空のまま送ると `resolution_notes = NULL` で上書きされ、リダイレクトされた。
追跡管理者は記録できたと誤解する。

### H10. 例外が無い貨物にも「解決する」ボタンが出た

**指摘元**: programmer・tester ／ **返済済み**

ドメインに `hasActiveException` があるのに Read Model が運んでいなかった。
**押せるのに必ず失敗するボタン**であり、IT9 H1・IT10 M9 と同型である。

## v1.0.0 リリース判定

利用者代表の判定は「**指摘 1・2（H1・H3）は v1.0.0 必須**、指摘 4（M8）は運用手順で
当座しのげるが次リリース先頭、指摘 3（M7）は暫定運用を画面のヒントに明記すること」だった。

**H1・H3 を含む高 10 件は全件返済した。** 残るのは中 6 件・低 5 件であり、
いずれも「業務が回らない」形ではない。

> **M7（誤記録の取り消し）について**: 壊れる経路（引取済への荷役・例外の二重発生）は
> 塞いだが、**記録そのものを取り消す手段は無い**。これは v1.0.0 の既知の制約であり、
> 拒否メッセージで「追跡管理者へご連絡ください」と案内する運用で当座しのぐ。

## 良かった点（維持する判断）

- **`statusBeforeException` をカラムに永続化**し、`reconstruct` で未知値を既定値へ
  倒さず `None` にした判断は、「状態の再導出禁止」の教訓に正しく従っている（tester）
- **E2E が捕まえた `id` 重複を HTTP テストとして下の層に固定**し、
  「E2E でしか見えない形」をコメントに残した点は、テストピラミッドの正しい使い方（tester）
- **`hasClaim` は Handling が自分の記録だけで判定**して BC をまたがない。
  ユニットと HTTP の両方で「拒む」ことを実測しており、H4 と対照的に**外せば赤くなる**（tester）
- `nullableString` で `NULL` を `None` として読み、`status_before_exception` の意味
  （「例外中でない」）を守っている（programmer）

# IT4 実装レビュー（マルチパースペクティブ）

対象: IT4（US09 経路選択・確定、US10 条件調整、US11 経路紐付け、US12 荷主通知、US13 予約確定、US14 追跡番号発行）。

## クローズ内で対応した High 指摘

1. **ドメイン不変条件の欠落**（programmer H2 / user C2 の一部）: `Cargo.assignRoute` が旅程の端点一致（出発地・目的地）と到着期限内（日付単位比較）を検証していなかった。`expectedArrivalTime()` も未使用だった。ドメイン層に不変条件を追加し、不正な経路確定を集約で拒否するようにした（単体テスト 2 件追加）。
2. **POST でのクライアント値信頼**（programmer H1）: 経路確定 POST が `body.arrivalDeadline` / `body.cargoType` を信頼して候補を再解決し、期限超過・種別偽装の経路を紐付け可能だった。POST では永続化済みの予約条件のみで再解決するよう修正（ドメイン不変条件と二層防御）。
3. **越権遮断の検証欠落**（tester H3）: ロール制御が「営業→経路画面 403」の一方向のみだった。経路設計者が営業専用操作（confirm/notify/cancel/return-to-routing）を、営業が追跡番号発行を実行できないことを E2E で検証追加。
4. **期限当日着の境界値**（tester H1）: 過去の DATE 期限 vs TIMESTAMP 到着バグの再発防止として、期限当日（時刻付き）着は採用・翌日着は除外の境界テストを追加。
5. **US12/US14 通知記録の E2E 検証**（tester M1/M2）: 追跡番号発行時の通知記録（TRACKING_ISSUED）を E2E で検証追加。
6. **ラベルの語彙衝突**（tw1）: 候補選択ボタン「この経路で確定」を「この経路を割り当てる」に変更（ROUTE_PROPOSED 遷移であり CONFIRMED ではないため）。
7. **DRY 違反**（programmer M2）: `voyage.controller` の `hasTransit` / `hasAllTransit` 重複を統一。
8. **ui_design 正典ドリフト**（tw2/3/4/5）: 未実装のラジオ/htmx 部分更新記述・⚠ 警告・追跡表示ボタンを実装実態へ修正。キャンセル表示条件・ボタン文言の表記ゆれを是正。

## 次イテレーション引き継ぎ（IT5 で対応）

- **US12 通知先と通知内容**（user C1/C2）: 現状 `NotificationPort` の宛先が荷受人（consignee）メールになっている。US12/US14 の要件は荷主（shipper）への通知であり、荷主メール取得の ACL（`shipper` テーブル参照）が必要。また通知内容（経由港・所要日数・到着予定日・料金概算）の確認画面が未実装で、IT4 は「通知記録の登録」で受入基準を満たしている。荷主宛先化と通知確認画面を IT5 で対応する。
- **通知・イベントの原子性**（architect M1/M5）: `notify` / `emit` がコミット後の別処理で、失敗時にコマンド全体を失敗表示にする。Tracking Context 購読（IT5）着手前に、コミット後副作用を「コマンド失敗として扱わない」共通方針（冪等リスナー・アウトボックス）を確立する（ADR-005 と整合）。
- **共有 DB 直読の統制盲点**（architect M2）: `KyselyRouteCandidateReader` は Routing 所有テーブルを直読する（ADR-008 で承認済み）が、dependency-cruiser はコード import のみ検証し DB 結合を検出しない。ADR-008 に盲点である旨を追記し、スキーマ変更時の契約テスト方針を IT5 で検討。
- **`leg` 時刻カラムの NOT NULL 化**（architect L3 / programmer L2）: `load_time` / `unload_time` は書き込み時必ず値があるが nullable のため、reconstruct のフォールバックがデータ破損を隠蔽しうる。NOT NULL 化 migration を IT5 で実施。
- **US14 の貨物状態「受領待ち」**（user H3）: 要件の「貨物状態＝受領待ち（NOT_RECEIVED）」は Tracking Context の `TransportStatus` の領域。IT4 は BookingStatus=TRACKING_ISSUED まで。受領待ち状態は Tracking 実装（IT5-6）で表現する。
- **US10 の経由地追加による再算出**（user M2 / tester H2）: 条件調整は期限・貨物種別のみ。経由地追加は未対応。業務価値を見て IT5 以降で判断。
- **追跡番号採番の一意性強化**（programmer L1）: 48bit 採番 + DB 部分 UNIQUE で実害は極小だが、Tracking Context への採番主体移行（ADR-008）時に full UUID / 連番規則を再検討。
- **CargoRoutedEvent の at-least-once**（programmer L3）: 発行のみの割り切り。Tracking 購読実装時にアウトボックス等で担保。

# IT3 コードレビュー結果

## レビュー対象

- **イテレーション**: IT3（US09 経路割り当て / US11 経路紐付け / US13 予約確定）
- **対象コミット範囲**: `e3308189..7c5e2e35`
- **レビュー日**: 2026-05-08

---

## 総合評価

IT3 実装はヘキサゴナルアーキテクチャの依存方向が正しく守られており、ドメイン層の純粋性、イベント駆動連携の設計、テストカバレッジのバランスが高い水準にある。E2E テストと SonarQube Quality Gate をともに通過し、受入基準をすべて満たしている。主な改善ポイントは、DB 更新とイベント発行の原子性（`@Transactional` の欠如）、`cancel()` の状態ガード不足、API エラーレスポンスのボディ欠如の 3 点である。

---

## 改善提案（重要度順）

### 高（対応推奨）

| # | 提案 | 箇所 | 指摘元 | 理由 |
|---|------|------|--------|------|
| 1 | `assignRoute` に `@Transactional` を付与する | `CargoCommandService.java` | xp-programmer / xp-architect | `update` 成功後に `publishCargoRouted` が失敗した場合、DB とイベントの不整合が生じる |
| 2 | `cancel()` に状態ガードを追加する | `Cargo.java` | xp-programmer / xp-architect | `DELIVERED` / `SETTLED` 状態からのキャンセルが業務的に不正となる可能性がある |
| 3 | 状態遷移テストを網羅する（デシジョンテーブル） | `CargoTest.java` | xp-tester | CONFIRMED → assignRoute / cancel、CANCELLED → 各操作の不正遷移テストが欠如 |
| 4 | API エラーレスポンスにメッセージボディを追加する | `CargoController.java` | xp-technical-writer | `notFound()` / `badRequest()` がボディなしで返却され、API 利用者が原因を推測できない |
| 5 | 経路設計画面で予約情報を自動引き継ぎする | `RoutingDesignPage.tsx` | xp-user-representative | 予約詳細から遷移した際、出発地・到着地の再入力が不要であるべき |
| 6 | `confirmBooking` 前の確認ダイアログを追加する | `BookingDetailPage.tsx` | xp-user-representative | 確定は契約的意味を持つ操作であり、キャンセルと同等以上の確認が必要 |

### 中（対応推奨）

| # | 提案 | 箇所 | 指摘元 | 理由 |
|---|------|------|--------|------|
| 7 | `@ConditionalOnBean` を `@AutoConfigureAfter` で補強する | `MessagingConfiguration.java` | xp-architect | Bean 評価順序によっては NoOp が優先されるリスクがある |
| 8 | `cancel()` コマンドの idempotency を明確化する | `Cargo.java` | xp-programmer | すでに CANCELLED の場合の再キャンセル動作が未定義 |
| 9 | `assignRoute` に再割り当てのガードまたは説明を追加する | `Cargo.java` / Javadoc | xp-programmer | 既に ROUTE_PROPOSED の状態で再割り当てすると無条件に上書きされる |
| 10 | `CargoCommandService.assignRoute` の Javadoc にイベント発行を明記する | `CargoCommandService.java` | xp-technical-writer | 副作用（RabbitMQ 発行）を呼び出し元が把握できるよう Javadoc に追記 |
| 11 | `@DirtiesContext(BEFORE_EACH_TEST_METHOD)` を見直す | `CargoRoutedEventPublisherTest.java` | xp-tester | テスト数増加時にコンテキスト再生成コストが累積する |
| 12 | ROUTE_PROPOSED の表示名を業務用語に変更する | フロントエンド ラベル | xp-user-representative | 「提案済み」は荷主視点で違和感あり。「経路選択済み」など業務用語が望ましい |
| 13 | Controller のエラーハンドリングを `@ControllerAdvice` に集約する | `CargoController.java` | xp-programmer / xp-architect | try-catch が各エンドポイントに散在し、一貫性が低下する |

### 低（改善の余地あり）

| # | 提案 | 箇所 | 指摘元 | 理由 |
|---|------|------|--------|------|
| 14 | `NoOpCargoEventPublisher` クラスとインライン lambda を統一する | `MessagingConfiguration.java` / `NoOpCargoEventPublisher.java` | xp-architect / xp-technical-writer | 同じ責務を持つ実装が 2 箇所に存在する |
| 15 | `@Operation` / `@ApiResponse` アノテーションを追加する | `CargoController.java` | xp-technical-writer | Swagger UI に HTTP ステータスの条件が表示されない |
| 16 | `registerBooking` を コマンドオブジェクト化する | `CargoCommandService.java` | xp-programmer | 7 引数のメソッドは引数順序ミスのリスクが高い |
| 17 | `generateBookingId` の一意性確認を明記する | `CargoCommandService.java` | xp-programmer | UUID 12 文字切り詰めの衝突リスクを DB の UK 制約が守ることを明示 |
| 18 | ドメインモデルに状態遷移図（PlantUML）を追加する | `docs/design/domain-model.md` | xp-technical-writer | BookingStatus 8 状態の許可遷移が散逸するリスクがある |
| 19 | Testcontainers shared container を導入してテスト時間を短縮する | `CargoRoutedEventPublisherTest.java` | xp-tester | IT4 でテストが増えた際の実行時間増加対策 |
| 20 | UNLOCODE の入力を検索補完方式に変更する | `RoutingDesignPage.tsx` | xp-user-representative | JPTYO 等の暗記は実務では困難（IT3 スコープ外） |

## エージェント別フィードバック詳細

<details>
<summary>xp-programmer（高: 2 / 中: 4 / 低: 4）</summary>

### 評価サマリー
IT3 実装は、ドメインモデルの状態遷移ロジック、ヘキサゴナルアーキテクチャに基づくポート/アダプター分離、イベント駆動連携が整然と設計されており、全体的に高品質。

### 良い点
- 集約ルートの状態遷移ガード（`confirm()` が ROUTE_PROPOSED 以外からの遷移を拒否）
- `CargoItinerary` の `Collections.unmodifiableList` による不変性保証
- `CargoEventPublisher` ポートによるインフラ依存の排除
- テストのダブル設計（手書き Stub）でテストの意図が明確
- `CargoRoutedEvent`、`RouteCargoCommand` の record による簡潔な表現

### 改善提案
- **【高】`cancel()` の状態ガード欠如**: DELIVERED/SETTLED からのキャンセルを防ぐべき
- **【高】`assignRoute` のトランザクション境界**: `@Transactional` がなく DB とイベントの不整合リスク
- **【中】`assignRoute` の冪等性/再割当ガード**: ROUTE_PROPOSED 状態での再割り当てが無条件上書き
- **【中】`registerBooking` の引数過多**: 7 引数 → `BookCargoCommand` コマンドオブジェクト推奨
- **【低】`generateBookingId` の衝突リスク**: DB の UK 制約で守られていることを明示
- **【低】`MessagingConfiguration.jacksonMessageConverter` の条件理由をコメントで補足**

### スコープ外の発見
- `CargoController` の try-catch が各エンドポイントに散在 → `@ControllerAdvice` 集約を検討
- `Cargo` コンストラクタに null チェックの不整合（`specifyRoute` にはあるが初期コンストラクタにはない）
</details>

<details>
<summary>xp-tester（高: 2 / 中: 3 / 低: 1）</summary>

### 評価サマリー
テストピラミッドのバランスは良好で、ドメイン・統合・メッセージング連携の各レイヤーが適切にカバーされている。ただし、状態遷移カバレッジと統合テストの異常系に不足がある。

### 良い点
- テストピラミッドが健全（ドメインユニット → Controller 統合 → RabbitMQ 連携 → E2E）
- `shouldThrowWhenConfirmingNonRouteProposedCargo` で不正遷移を検証
- Testcontainers によるリアルな RabbitMQ テスト
- テスト名が仕様として読める（should 形式）

### 改善提案
- **【高】状態遷移テストの網羅性不足**: CONFIRMED → cancel、CANCELLED → 各操作の不正遷移テストが欠如
- **【高】Controller 異常系が薄い**: 不正リクエストボディ（null/空 legs）→ 400、状態不正 → 409/422 の検証なし
- **【中】`@DirtiesContext` の見直し**: `@Sql` でクリーンアップしているなら不要な可能性
- **【中】`5000` がマジックナンバー**: タイムアウト定数化と理由のコメント追加
- **【低】`shouldAssignRoute` が 2 つの観点を 1 テストで検証**: 状態遷移と itinerary 設定を分離推奨

### 懸念事項
- `receiveAndConvert` 5 秒タイムアウトが CI 負荷次第で flaky になり得る → `Awaitility` 検討
- `CargoRoutedEvent` の全フィールド検証がない（voyageNumber 等が未検証）
- `assignRoute` 後の DB 状態が Controller テストで検証されていない
</details>

<details>
<summary>xp-architect（高: 1 / 中: 3 / 低: 1）</summary>

### 評価サマリー
ヘキサゴナルアーキテクチャの依存方向が正しく守られており、ドメイン層の純粋性が高い。`assignRoute` の原子性欠如が現実的なリスク。

### 良い点
- 依存関係逆転の徹底（ArchUnit テストで自動検証）
- ドメインモデルの純粋性（Spring / RabbitMQ に依存なし）
- `CargoRoutedEvent` の record 採用（イミュータブル）
- `@ConditionalOnBean` / `@ConditionalOnMissingBean` による Graceful Degradation

### 改善提案
- **【高】`assignRoute` にトランザクション境界**: DB 更新後イベント発行失敗時の不整合防止
- **【中】`cancel` の状態遷移ガード**: DELIVERED/SETTLED からのキャンセルを防ぐべき
- **【中】`@ConditionalOnBean` を `@AutoConfigureAfter(RabbitAutoConfiguration.class)` で補強**
- **【低】`NoOpCargoEventPublisher` クラスとインライン lambda の重複解消**

### 懸念事項
- `@ConditionalOnBean(RabbitTemplate.class)` は Bean 定義処理順依存で不安定
- イベント発行がアプリケーション層の責務として将来的に肥大化するリスク（ドメインイベント蓄積パターン検討）
</details>

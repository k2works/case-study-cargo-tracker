# 開発成果物レビュー（IT5・US14-18 Tracking/Handling BC）

## レビュー対象

- イテレーション: IT5（US14 追跡番号発行 / US15 荷役登録 / US16 引取 / US17 状態手動更新 / US18 追跡照会）
- 差分: `git diff 76bdddf0..a251a4de -- apps/cargo-tracker/src apps/cargo-tracker/tests`（62 ファイル・約 2,462 行追加）

- 手法: XP 5 エージェント並列レビュー（xp-programmer / xp-tester / xp-architect / xp-technical-writer / xp-user-representative）

## 総合評価

IT5 は 4 つの境界づけられたコンテキスト（Booking / Routing / Tracking / Handling）の独立性を ACL（プリミティブ DTO ＋ SQL 直接参照）とドメインイベント（post-commit）で一貫して実現し、ドメインロジック（妥当性デシジョンテーブル・状態導出）が単体テストで意図明確に表現された良質な実装である。UnitOfWork のトランザクション解放後 publish（ADR-0006 の懸案解決）は変更を安全にする的確な判断で、5 エージェントが揃って高く評価した。

一方、**複数エージェントが共通して指摘した最重要テーマは「post-commit イベント連鎖の結果整合性が未整備（部分適用のリスク・ADR 未反映）」**である（xp-programmer 高・xp-architect 高・xp-tester 中）。加えて、荷主通知の全 US 未実装（xp-user-representative 高）、ArchUnit の Tracking/Handling BC 未検証（xp-architect 高）、CLAIM/UNLOAD の状態同期 E2E 未検証（xp-tester 高）が高優先で残る。設計ドキュメント（domain-model / data-model / ui_design）と実装の乖離も未是正で継続している。

なお、レビュー着手前の最重要課題「荷役登録→追跡/予約状態同期の実 MediatR 経由 E2E 皆無」はコミット `a251a4de` で是正済み（Receive→受領済、Load→積込済＋IN_TRANSIT を貫通検証）。本レポートはその上で残るギャップを対象とする。

## 懸念事項（横断）

- **post-commit 連鎖の可観測性（H1 関連）**: 部分適用時にログ以外の検知手段がなく、`IssueTrackingOnBookingConfirmedHandler` も別 UoW で追跡発行→状態遷移の 2 段書き込みの窓を持つ（冪等スキップで緩和）。リカバリ手順を本番移行前に決定すべき。
- **TrackingActivityRepository の全削除→再挿入**: `AddEvent`→`SaveAsync` が毎回全イベントを DELETE→INSERT。並行 read-modify-write で後勝ちによるイベント欠落の恐れ（L4 と関連）。
- **MISROUTED 判定の航海番号完全一致依存**: 入力ミスが即警告となり、誤警告頻発で作業員が警告を無視する習慣化リスク。運用開始後に誤警告率を観察。
- **到達不能な TransportStatus**: `OnboardCarrier`/`AwaitingClaim`/`Exception`/`Unknown` へ遷移する経路がコード上になく、`_ => false`/`_ => Unknown` フォールバックがどのテストでも到達しない（種別追加時のサイレント無効化リスク）。IT5 時点の到達可能状態を注記推奨。

## スコープ外の発見

- `booking_status = 'ROUTEPROPOSED'` → `'ROUTE_PROPOSED'` 修正（`RoutingRequestQueryService.cs:31`）は IT4 の永続化ドリフト是正に相当。良い修正だが US14-18 のスコープ外の付随変更。
- `ConsigneeConfirmation`（引取時の荷受人確認）は CommandService で必須検証されるが、`handling_activity` テーブル・`HandlingActivity` 集約に永続化されず検証のみで破棄。監査証跡としての妥当性を要確認。
- ArchUnit の BC ルールがホワイトリスト方式で、BC 追加のたびに追記が必要。「Shared 以外の他 BC 名前空間依存を一律禁止」の汎用ルール 1 本に寄せると統治漏れを構造的に防げる（将来のリファクタリング候補）。
- 公開追跡ページ（`PublicTrackingController`）は未認証到達と not-found のみ検証。実データでの公開表示内容（認証版と同等のタイムライン）は未検証（次 IT 補完余地）。
- US19（遅延例外処理・本 IT 対象外）実装時、MISROUTED を例外一覧へ流す動線を検討。

# Go 版設計ドキュメント レビュー結果（2026-07-11）

## レビュー対象

`docs/design/` 配下の Go 版設計ドキュメント 10 本

- tech_stack.md / architecture_backend.md / architecture_frontend.md / architecture_infrastructure.md
- domain-model.md / data-model.md / ui_design.md
- test_strategy.md / non_functional.md / operation.md

レビュー方式: XP エージェント 5 種（xp-product-manager / xp-architect / xp-interaction-designer / xp-tester / xp-user-representative）の並列レビュー

## 総合評価

Java/Spring 版の DDD + ヘキサゴナル + CQRS 思想を Go イディオム（手動 DI、interface = ポート、sqlc、自作ディスパッチャ、go-arch-lint）へ自然に読み替えた、実行可能性の高い設計一式である。移行マッピングの明快さ、testcontainers-go への一本化、ACL 5 ポートの契約テスト網羅は高く評価された。一方で、**並列移植の副作用としてドキュメント間の不整合（BC 数 5/7/8、TransportStatus・BookingStatus の列挙値、割引率上限 15%/30%、cargo テーブルの型矛盾、テンプレート命名・ロール名の揺れ）が多数検出され**、このまま実装に入るとコンテキスト境界とスキーマで確実に手戻りが発生する。加えて、現場で日常的に発生する例外系業務（荷役訂正・遅延例外登録・リルート）の画面が欠落している。方向性ではなく整合性と例外系の補完で解消できる。

## 主要な懸念事項（横断）

- **同期イベントディスパッチャの整合性**（PM / アーキテクト / テスター が共通指摘）: 「コミット後 Publish」方針での発行失敗・ハンドラ部分失敗時のリカバリ（再試行・ログ・手動再送）を運用要件に最低限定義する。不整合窓を実証する統合テストも持つ。Dispatcher シグネチャ（ctx 有無）も backend 側に統一。
- **公開追跡の負荷と SLA**: 追跡 API 1,000 RPS / 99.99% を共有 ECS/DB 構成で達成できるかは要検証。Read Replica / キャッシュ分離の観測ポイントとして意識する。
- **認可の実体はサーバー側ミドルウェアで担保**し、テンプレートのロール分岐は表示制御のみとすることを明記する。
- **WCAG 2.2「2.2.2 一時停止」**: 30 秒自動更新に一時停止手段がないと AA 準拠が崩れる可能性。
- **金額の丸め処理**: 端数を含む境界値テストで丸め規則を固定する。

### 評価サマリー
Java/Spring 版の DDD・ヘキサゴナル・CQRS 思想を Go スタックに忠実かつ現実的に移植した、完成度の高い設計一式です。技術選定の一貫性と移行マッピングの明快さは特筆に値しますが、ドキュメント間でコンテキスト数・enum 値・US カバレッジに不整合があり、「業務価値を過不足なく支えるか」の観点で修正が必要です。

### 良い点
- **移行判断の根拠が明快**：`tech_stack.md` の Spring→Go マッピング表（MyBatis→sqlc、ApplicationEventPublisher→自作ディスパッチャ、ArchUnit→go-arch-lint）が 1 対 1 で示され、「移してもビジネス機能を落とさない」ことが担保されている。DI コンテナ・HATEOAS・イベントソーシングを初期フェーズで見送る割り切りが YAGNI に沿って適切。
- **中核ドメインへの投資集中**：`domain-model.md` の象限図で Booking / Tracking / Routing を中核と位置づけ、複雑さの高い集約（Cargo の Leg 連結制約、TrackingActivity の例外復帰ロジック）に設計リソースを寄せている。ビジネス価値と設計投資の配分が合理的。
- **外部システム 5 ポートの ACL 抽象化**が一貫しており、税関・決済・港湾など変動リスクの高い外部依存をドメインから隔離できている。運用・テスト（httptest スタブ）まで一貫。
- **公開追跡ページ（/public/tracking）**は認証不要で荷主に URL 共有可能という、実際のビジネス価値（問い合わせ削減・荷主満足）を的確に捉えた追加。

### 改善提案
- 【重要度: 高】コンテキスト数の不整合を解消：`architecture_backend.md` は 6 コンテキストだが、`domain-model.md` は 8 コンテキスト（+ Shipper + Estimation）。Shipper（US22 法人割引の前提）と Estimation（US01）は業務価値上必須なので、`architecture_backend.md` 側を 8 コンテキストに揃え、コンテキストマップ・パッケージ構造・go-arch-lint ルールにも追記すべき。
- 【重要度: 高】enum 値の二重定義を統一：TransportStatus/TrackingStatus が `architecture_backend.md`（`IN_TRANSIT` / `CUSTOMS_INSPECTION` / `MISROUTED` を含む 9 値）と `domain-model.md`（`ONBOARD_CARRIER` / `CLAIMED` / `EXCEPTION` / `UNKNOWN` を含む 9 値）で値そのものが異なる。UI は `ONBOARD_CARRIER` 系を採用しており、`architecture_backend.md` だけ旧値。状態遷移は業務の背骨なので、ユビキタス言語として 1 つに統一し全 3 ドキュメントを揃えること。
- 【重要度: 中】US19〜US25 の画面トレーサビリティを明示：`ui_design.md` の画面一覧の対応 US は US18 までしか登場せず、US19（遅延例外）・US20（破損紛失）・US23（精算処理）・US24/US25（航海登録・更新）に対応する画面や操作の記載が薄い。画面追加か「今回スコープ外」の明示が必要。
- 【重要度: 中】貨物種別（CargoType）の値ゆれ：ドメインは 3 値だが、`ui_design.md` の登録フォームは 4 値（PERISHABLE 追加・接尾辞ずれ）、割引ポリシー画面では `DANGEROUS` 表記も混在。統一を。

### 懸念事項
- **同期イベントディスパッチャのトランザクション整合性**：「コミット成功・イベント発行失敗」で Tracking の状態が Booking に追従しない不整合が起こりうる。初期フェーズでも「発行失敗時のリカバリ（再試行・ログ・手動再送）」を運用要件として最低限定義しておくべき。
- **`domain-model.md` の Dispatcher シグネチャ不一致**：ドメインモデル側の `Handler func(e Event) error` に対し、backend 側は `Handler func(ctx context.Context, event Event) error`。backend 側（ctx あり）に統一すべき。

### スコープ外の発見
- **Shipper Context の集約設計**（`CorporateShipper` の embedding 表現）の永続化方針（同一/別テーブル）が `data-model.md` 側でどう表現されるか未確認。継承の永続化は移行時のリスクポイント。
- 参照元との突き合わせは未実施。enum・CargoType のゆれが「移植ミス」か「意図的変更」かは元設計と照合すると切り分けられる。

### 評価サマリー
Go スタックへの移植そのものは総じて質が高く、ヘキサゴナル+DDD+CQRS を Go のイディオムへ自然に読み替えており「変更を楽に安全にできる」構造の土台はできている。ただし Bounded Context の数（5/7/8）、TransportStatus の列挙値、割引率上限（15%/30%）、cargo テーブルの主キー型がドキュメント間・同一ドキュメント内で矛盾しており、このまま実装に入るとコンテキスト境界とスキーマで確実に手戻りが発生する。整合を取れば着手可能なレベル。

### 良い点
- Spring→Go 移行マッピング表が秀逸。Java 直訳を避けた判断が読み取れる。
- Go イディオムへの適合が適切（値オブジェクト = 非公開フィールド + `NewXxx`、オプション = ポインタ、継承 = embedding、enum = 型付き文字列定数）。
- テスト DB を testcontainers-go の実 PostgreSQL に一本化し H2 相当を排除した判断は実務的に正しい。
- go-arch-lint による依存方向の CI 強制が設計段階で組み込まれている。
- コンテキスト間に DB 外部キーを張らない判断は将来のサービス分割を妨げない正しい疎結合設計。
- 金額を INTEGER（最小通貨単位）+ 通貨コードで表現し浮動小数点誤差を排除。リスクの自己認識が随所にある。

### 改善提案
- 【重要度: 高】Bounded Context の数と一覧を全ドキュメントで統一（domain-model 8 BC / data-model 7 BC / architecture_backend 5 BC の三者三様。正典を domain-model に定める）。
- 【重要度: 高】cargo テーブルの主キー・外部キー型を統一（概念/論理は `booking_id VARCHAR(20)` / `shipper_id BIGINT`、テーブル定義は UUID。`shipper.id` は BIGSERIAL のため FK 型不一致でマイグレーション失敗。`weight_kg`/`weight` のカラム名割れも）。
- 【重要度: 高】TransportStatus の列挙値を一本化（Shared Kernel の共有型の値ずれはイベント同期時に不正値を生む。原典を確認して確定を）。
- 【重要度: 高】割引率の上限を統一（domain-model 30% / data-model CHECK 15%。プロダクトオーナー確認の上で確定）。
- 【重要度: 中】CSRF ライブラリ（nosurf）・validator・bluemonday を tech_stack.md に追記（Single Source of Truth の回復）。
- 【重要度: 中】Estimation Context のドメインイベント連携を明確化（独立して開発・デプロイできる純粋な追加コンテキストであることを明記）。

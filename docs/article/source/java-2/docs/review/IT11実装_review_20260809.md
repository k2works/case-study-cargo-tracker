## 総合評価

**IT10 のふりかえりで決めた Try が、実際にコードとして守られている。** 絶対日付を書かない・「エラーを出した」と「実行されなかった」を分ける・不在のアサートの前に開けたことを見る・出す／出さないを対で書く — これらは 5 視点のうち 3 つが「良い点」として独立に挙げた。

**一方で、コメントが実装より強い保証を主張している箇所が 3 件見つかった。** IT10 の Problem P3（「自分で書いた教訓を、書いた本人が同じ IT の中で繰り返した」）と同じ形が、別の顔で戻ってきている。

**そして最も重いのは、検査が守っている範囲の外で結合が増えたことである**（architect）。ArchUnit を 1 件も破らずに、BC 間の結合が SQL の層で 2 本増えた。

**高 14 件 / 中 17 件 / 低 12 件。高のうち 10 件を IT 内で対応した。**

## 視点別の要旨

### programmer

集約に判断を寄せる規律・結果整合・業務タイムゾーンの扱いは前 IT の教訓を反映している。一方で**ドメインが持つ述語をクエリ側で文字列比較として再実装**しており、ドメイン自身が「呼び出し側で『CLEARED なら』と書くな」と明記した規則をビューが破っていた。

### tester

受入基準 16 項目のうち **12 項目が実テストで押さえられ、4 項目が部分的または未達**だった。とくに「引き継がれる」「貨物 ID で検索」「不可への更新」は**通る道を押さえていなかった**。

### architect

イベントによる伝播（ADR-009）とダッシュボードの分散（ADR-014）は設計どおり。しかし **ADR-012 の規律が SQL の層で 2 か所破れている**。ArchUnit を 1 件も破らずに BC 間の結合が 2 本増えており、「検査が緑である」ことが「越境していない」ことの根拠になっていない。

### technical-writer

早見表 11 行の文言はすべて実コードに存在し、画像 43 件・アンカーもすべて解決した。一方で**マニュアルが「入力は保たれます」と実装より強い保証を先に主張していた**。これは記述の誤りではなく、**設計の欠陥をドキュメントが先に書いてしまった**形である。

### user-representative

US28 は 8 項目とも業務として成立している。US29 は **6 項目が成立、2 項目に穴**（引取拒否が申告のある貨物にしか効かない／荷受人が読める画面が無い）。加えて**通関「不可」がどこにも波及しない**のは輸入実務では見過ごせない。

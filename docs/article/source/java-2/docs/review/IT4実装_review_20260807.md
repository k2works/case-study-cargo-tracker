## 総合評価

**ドメインから固める順序は守られており、探索の不変条件は壊して赤を確認できている。**
一方で「**列や仕組みは用意したが、働いていない**」型の指摘が 2 件出た。IT3 で
「安全装置は破って赤を確認する」を規律にした結果、装置そのものの不在は減ったが、
**装置を置いた気になっている箇所**が残っていた。

---

## 高（クローズ前に対応）

### H1. 楽観的ロックの列を持ちながら使っていなかった（architect / programmer）

`booking_route_proposal` は `version` を持ち、`data-model.md` は「楽観的ロック（判断 8）」と
書いているのに、**更新の SQL が `WHERE` で見ていなかった**。2 人の経路設計者が同じ予約を
同時に算出すると、後の保存が前の候補を黙って消す。

**列があるのに見ていなければ、持っていないのと同じ**であり、次に読む人は守られていると
誤解する。IT2 で確立した `shipper` の書き方（`WHERE ... AND version = #{version}` /
`SET version = version + 1`）が踏襲されていなかった。

**対応**: 本 IT 内で修正済み。先に赤になるテスト（`同時に算出すると後の保存が拒否される`）を
書き、`WHERE` の `version` を外すと落ちることを実測してから採用した。
画面では 500 にせず「別の担当者が先に経路候補を算出しました」と表示する。

### H2. 予約詳細の戻り先が、開いたロールで使えなかった（user-representative）

経路設計者が予約詳細から「一覧に戻る」を押すと 403 になった。予約詳細は営業担当者と
経路設計者の両方が開くが、貨物予約一覧は営業担当者のものである。

IT3 のレビュー P2（画面から先への到達性）を受けて「開いた画面から次に何ができるか」は
確かめたが、**共有画面の中に元からあるリンク**が抜けた。

**対応**: 本 IT 内で修正済み。営業担当者には「一覧に戻る」、経路設計者には
「経路割り当て待ちへ戻る」と「経路を割り当て」を出す。全テンプレートの `th:href` を
洗い、2 ロール以上が開く画面は予約詳細だけであることを確認した。

## 視点別の所見

### programmer

- 探索・評価・費用がそれぞれ独立した部品になっており、テストが 1 つの関心事だけを見ている
- **逆走チェックのテストが最初は判別していなかった**ことを、自分で見つけて直している点は良い。「壊して赤」を実行しなければ気づけなかった
- H1 の見落としは、**新しい集約を作るときに既存集約の書き方を見に行かなかった**ことが原因である

### tester

- 受入基準とテストが 1:1 で対応している（`RouteAssignmentScreenTest` のコメント）
- 境界値（期限当日 23:59・経由回数ちょうど上限・所要日数の端数）が入っている
- `TZ=UTC` での実行も確認済み。IT3 の Try T2 が守られている
- **H1 の衝突は画面レベルのテストが無い**。並行リクエストを MockMvc で再現できないため、リポジトリのテストで固定した。この限界は記録に残す

### architect

- ACL の境界で BC の型を使わない形に直したのは正しい。**ArchUnit が設計の誤りを実際に捕まえた**
- `LocationMasterMapper` を `shared/infrastructure` へ移したのは妥当。共有カーネルの範囲（ADR-005）は `shared.domain.model` であり、技術基盤はその外である
- 探索対象の絞り込みを SQL に置いたことで、港と便が増えても一覧を開くだけで全件が載ることはない

### technical-writer

- マニュアルに**推奨順の決まり方**を表で書いたのは良い。順番の理由が分からないと、上から選んでよいのか判断できない
- 「候補ゼロ」と「期限内に着けない」の違いを本文で書き分けている
- 費用が概算であることを、画面・マニュアル・ADR の 3 か所に書いている

### user-representative

- 候補が並ぶだけでなく、**選べない理由が読める**ことが実務では効く
- H2 は「使ってみればすぐ分かる」種類の欠陥だった。**画面を開くだけでなく、置いてあるボタンを順に押す**確認が要る
- 確定できないことを画面に明記したのは誠実。空のボタンで匂わせるより良い

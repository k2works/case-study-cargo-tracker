# IT16 実装レビュー（途中レビュー）

日付: 2026-08-11
対象: IT16 の実装（C1 荷降し手配 ／ T1 ADR の守り手 ／ T2 catch の広さ ／ T4 名簿 ／ C2 貨物準備ヘルパー統合）
実施: **5 視点を逐次に実施**（`developing-review` のフォールバック。IT12 / IT15 と同じ形）

> **本レビューは実装の途中で回した**（Try T6）。IT14・IT15 と **2 IT 連続で落としていた**項目である。
> クローズ時ではなく途中で回すのは、**発見が遅いほど直す幅が広がる**ためである。

## 総合評価

**C1（US30 の未達受入基準）は満たされており、T1・T2・T4・C2 はいずれも「入れたこと」でなく「働くこと」まで確かめている。** 破壊検証は本 IT で 6 件行い、うち 2 件で空振り（守っているつもりの装置が働いていない状態）を見つけて埋めている。

**最大の問題は、IT16 自身が定めた Try を IT16 の実装が破っていることである。** T3 は「一覧を返すクエリサービスを書いたら、**その場で**問い合わせ回数のテストを書く（後から足すのではなく、一覧と同時に）」と定めている。C1 で `HandlingQueryService.findPendingDischarges` という**新しい一覧クエリを足しながら、`QueryCounter` のテストを書いていない**。

これは IT15 の P3（「C4 と同じ型を、C4 を返済した同じイテレーションで作った」）とまったく同じ形である。**規律を書いた当人が、書いた同じイテレーションで破った。**

## 視点別フィードバック

### xp-programmer（高 0 / 中 3 / 低 0）

**良い点**: 破壊検証を装置ごとに行い、空振りを 2 件見つけて埋めている。とくに C1 の「JOIN が守っていて規則が守っていない」の発見は、**テストが判別していないことをテストで示した**好例である。ADR-021 の名簿と SpotBugs の指摘に対し、**例外を足さず既存の形に合わせた**判断もよい。

**改善提案**: M4（`UUID.fromString` の重複）・M5（null 判定の二重）・M6（移行スクリプトの取りこぼし）。

**懸念**: 無し。

### xp-tester（高 2 / 中 0 / 低 0）

**良い点**: `DischargeOrderTest` は拒む側（承認していない・却下した）を持ち、さらに**破壊検証の空振りを受けて判別テストを追加**している。検査の追加ではメタテストを必ず添えており、「検査が働くこと」を確かめる規律が保たれている。

**改善提案**: H1（問い合わせ回数）・H2（並び順）。

**懸念**: **本 IT の Try を本 IT の実装が破った。** T3 は「一覧と同時に書く」と定めており、後から足すのは規律の骨抜きになる。

### xp-architect（高 0 / 中 0 / 低 2）

**良い点**: BC 独立性が保たれている。`ApprovedCancellations` は Handling が自分の型（`DischargeOrder`）を定義し、`booking_cancellation` の所有者である Booking がアダプタを実装する。**「もう降ろしたか」の判定を Handling 側に置いた**のは、ADR-015（マッパーは自分の BC のテーブルだけ）から導いた正しい分割である。マッパーをアダプタの内側に置いた是正も、集約の読み書きと ACL の読み取りを分ける効果がある。

**改善提案**: L2・L3。

**懸念**: 無し。

### xp-technical-writer（高 1 / 中 0 / 低 1）

**良い点**: ADR 19 件に守り手を書き出し、**検査の無い規則を「守らない」と名前で残した**のは、読み手に誤った安心を与えない。「荷降し」と「荷降し手配」の使い分けを 3 か所（要素表・用語集・画面）で明記したのも、IT15 の「キャンセル / 取り消し」と同じ扱いで一貫している。

**改善提案**: H3（マニュアル未更新）・L1。

**懸念**: 無し。

### xp-user-representative（高 0 / 中 3 / 低 0）

**良い点**: 手配が履歴より**上**に出るのは正しい。船が着く前に知らなければ降ろせない。行から荷役登録へ追跡番号を持ったまま進めるのも、番号を読んで打ち直す手間が無い。荷降しを登録すると手配が消えるのは、**毎朝読み飛ばす習慣を作らない**ために効く。

**改善提案**: M1（貨物種別）・M2（期限）・M3（行き止まり）。

**懸念**: 手配の一覧に**件数の上限が無い**。承認が溜まると画面が長くなるが、現時点では上限を設ける根拠（実データの規模）が無いため、要求が出てから対応でよい。

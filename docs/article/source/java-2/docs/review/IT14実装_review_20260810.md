## レビュー対象

- 差分: `git diff 076f38c53~1..70c6c854f -- apps/cargo-tracker/src e2e`（19 コミット・75 ファイル）
- 対象: US23（精算を処理する）と IT13 レビューの返済枠 8 件（C1〜C7 / C12 / C14 / C16）

## 総合評価

精算の 3 つの関心（発行・入金・期限）を値オブジェクトに切り出し、不変条件を集約に置き、拒む理由を業務の言葉で画面まで返す設計になっている。BC 依存の向きは本リポジトリで最も整った回で、`billing/` の本番コードは他 BC を 1 ファイルも import せず、越境は 6 つの ACL アダプタに閉じている。受入基準 5 項目はいずれも「その道を実行したテスト」を持ち、対応表が `SettlementScenarioTest` の Javadoc にある。

一方で、**「例外にしない」という判断が「記録もしない」に滑っていた**（予約を精算完了にできなかったことがどこにも残らない）、**期限のテストが CI では 1 日のうち 9 時間だけ落ちる**、**ADR-018 の「1 請求書 1 入金」が DB 制約になっていない**という、正しさに関わる指摘が出た。いずれも本イテレーション内で返済した。

## 矛盾事項

| # | 視点 A | 視点 B | 論点 | 判断 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | architect: `settle` / `notifyIssued` は**ドメインイベントであるべき**（戻り値を使っていない＝同期である必要がない） | 現行: 同期ポート | 状態伝播の方式 | **IT15 で ADR として起票する。** 本 IT では戻り値を使う形（記録する）に直して、同期である理由を一旦成立させた。イベント化は Booking → Billing の逆参照が生まれる前に行う |
| 2 | architect: Invoice 集約の責務は「広いが無理ではない」（軸をまたぐ不変条件が実在し、1 トランザクションでしか守れない） | programmer: 次の 1 機能で 500 行の上限に当たる | 集約の分割 | **分割しない。** 分割の合図は集約ではなくリポジトリ側に出る（すでに 4 メソッド）。5 本目が生えたら永続化の関心を見直す |
| 3 | user-rep: 荷主が自社の請求金額を確認できるべき | 現行: 請求書は ROLE_BILLING のみ | 見える範囲 | **IT15 で判断する。** 「他社の請求書を見せない」と「自社の請求書を見せる」は別である |

## スコープ外の発見

- **適格請求書（インボイス制度）の要件**が請求書の画面に無い（登録番号・税率ごとの区分記載）。荷主に渡す帳票を作る段で必ず問題になる（user-rep）
- **返金が業務としてどこにも定義されていない。** ADR-018 も マニュアルも「別の業務です」で止まっており、その別の業務が存在しない（user-rep）
- マニュアルのキャプチャに、別の場面として参照しているのに同一内容と見られるものがある（technical-writer）
- `.claude/agent-memory` に「戻り値を捨てている同期ポートは同期である必要がない」という判定基準を残す価値がある（architect）

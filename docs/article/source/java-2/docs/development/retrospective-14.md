## Keep（続けること）

### K1. 返済枠を先に片づけた

計画どおり**タスク 0（返済枠 26h 相当）を序盤で完済**した。IT13 のレビューで送った高 4 件（C1〜C4）は落とさず、C5 / C6 / C12 / C14 / C16 まで返した。**「余力次第」にしなかったこと**が効いている（`feedback_debt-allowance-defer-antipattern` の型を避けられた）。

### K2. 破壊検証が 6 件すべて赤になった

期限当日の扱い・一部入金の拒否・予約の精算・発行前の確定検査・引取日の記録・ダッシュボードの名簿。**「入れたこと」でなく「働くこと」を確かめる**規律が定着している。IT11 の「空振り 3 件」以降、2 IT 連続で空振り 0。

### K3. Checkstyle の制限を設計の合図として使い続けた

`Cargo` が 521 行に達したとき、コメントを削るのではなく**`reconstruct` の多重定義を `withX` に寄せて**減らした。`MyBatisBillingQueryService.toView` の循環的複雑度 14 は、**入金の 4 項目を `PaymentDetail` にまとめる**ことで解いた。どちらも「制限に当たったから直す」ではなく「制限が指した設計を直す」形になっている。

### K4. 数え上げてから壊す順序を守った

マニュアル 11.5〜11.7 に書いた守り（発行は 1 回だけ・期限は動かない・一部入金は不可・期限当日は対象外・入金確認で一覧から消える）を先に列挙し、そのうえで壊した。**列挙しなかったものは壊しようがない**という前提が共有できている。

### K5. ポートは使う側の BC が持つ、を守った

例外の記録が必要になったとき、Booking の `CargoExceptions` を使い回さず **Billing 側に `CargoExceptionRecordsPort` を新設**した。結果として `billing/` の本番コードは他 BC を 1 ファイルも import していない。

## Problem（問題だったこと）

### P1. 「例外にしない」が「記録しない」に滑っていた（最大の発見）

`settle` / `notifyIssued` はどちらも `boolean` を返す契約なのに、**呼び出し側が戻り値を捨てていた**。結果として「入金確認済みだが予約が `SETTLED` にならなかった請求書」がログにも画面にも残らない。**US36 の「精算済みには訂正・取り消しできない」は `booking_status` に依存している**ため、この不整合が起きた予約は精算後も訂正できてしまう。

「できなかったことを例外にしない」という判断自体は正しい。**そこから「だから何もしない」へ滑ったこと**が問題で、これは自分では気づけなかった（レビューで初めて出た）。

### P2. テストが CI の時間帯でだけ落ちる状態を作った

支払期限の境界テストで **DB の `CURRENT_DATE`**（UTC）を使い、判定は**アプリの業務タイムゾーン**（JST）で走らせていた。日本時間 0〜9 時に走らせると 1 本だけ落ちる。`CorrectionApprovalVisibilityTest` では同じ IT の中で `Clock` を注入していたのに、**新しく書いたテストには及ばなかった**。

`feedback_tests-must-use-the-same-clock` として記録済みの型が、**同じイテレーションの中で再発した**。

### P3. ADR に書いた不変条件を、また DB 制約にしていなかった

ADR-018 は「`payment` は 1 請求書 1 行として使う」と決めたのに `UNIQUE(invoice_id)` を置かなかった。**V31 で ADR-017 について同じ非対称を自分で咎めた直後**である。しかも壊れ方は静かではなく、`LEFT JOIN` により**締めの合計が二重計上**される。

### P4. 全緑からレビューが高 18 件を出した（6 IT 連続）

`./gradlew check` 緑・E2E 緑・SonarQube 87% の状態から、5 視点が高 18 件を出した。うち 13 件は正しさ・読み手に関わるもので、**自動チェックが原理的に見ない領域**（業務としてどう使うか、コメントと実装の一致、記録の有無）に集中している。

### P5. 「実装しなかった守り」の数え上げに漏れがあった

`SettleInvoiceCommandService` の Javadoc に「連絡先が未登録の荷主はいる」と書いたが、**`shipper.email` は NOT NULL であり到達不能**だった。数え上げの対象に Javadoc を含めていたのに、**その主張が成立するかまでは確かめていなかった**。

### P6. 利用者に見せる語の規則を、規則を書いた本人が破った

`BillingController` のコメントは「利用者に見せる語は請求書に統一する（H12）」と宣言している。ところが IT14 で足した画面は「精算書を発行」、マニュアルの節題も「精算書を発行する」だった。**同じ画面に「請求書詳細」と「精算書を発行」が同居していた**。

### 設計判断として持ち越すもの

- **`settle` / `notifyIssued` をドメインイベントにするか**（ADR として起票。Booking → Billing の逆参照が生まれる前に決める）
- **荷主が自社の請求書を見られるようにするか**（「他社を見せない」と「自社を見せる」は別）
- **返金をどう扱うか**（ADR-018 も マニュアルも「別の業務」で止まっており、その業務が存在しない）
- **適格請求書（インボイス制度）の要件**（登録番号・税率ごとの区分記載）。荷主へ渡す帳票を作る段で必要になる

### スコープ

IT15 は US30（キャンセル料の算定）5SP。**US21 の料金算出に依存する**ため、`Money` の減額まわりを触る際は本 IT で入れた `Adjustment` の適用順（基本料金 → 調整 → 割引 → 消費税）を壊さないこと。

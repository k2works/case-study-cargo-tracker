## エグゼクティブサマリー

**航海スケジュールを登録・検索でき、予約を経路設計者に引き渡せるようになった。**
Routing Context の `Voyage` 集約と `Schedule` の連結制約を確立し、経路候補算出（IT4）の
入力が揃った。**ROLE_ROUTER に開く最初の画面ができた**イテレーションでもある。

局面が序盤（アウトサイドイン）から中盤（インサイドアウト）へ切り替わった。
`Schedule` の連結制約は**行をまたぐため DB の CHECK 制約では守れず**、
画面から作っていれば「貨物が途中で消えるスケジュール」を登録できていた。
ドメインから先に固める意味が、最初のイテレーションで実証された。

**実バグを 3 件見つけた。** いずれも「テストは緑なのに動かない」種類である。

## 技術的成果

### Routing Context の確立

- `Voyage` 集約。**航海の端点（出発港・目的港）は `Schedule` から導き、保持しない**
  （同じ事実を 2 か所に持つと、区間を足したときに端点だけ古いままになる）
- `Schedule` が守るのは**区間をまたぐ 2 つの制約**である。連結（区間 n の到着港 =
  区間 n+1 の出発港）と時系列（着く前に次の船は出ない）。**どちらも DB の CHECK では
  守れない。** 制約を外すと 4 件落ちることを実測した
- `RoutingCargoType` は Routing が自前で持つ。Booking の `CargoType` と値は同じだが
  「この貨物は何か」と「この航海は何を運べるか」で意味が違う

### 港マスタ

`location` テーブルは**データが 1 件も無く**、`carrier_movement` の外部キーにより
航海スケジュールを 1 件も登録できない状態だった（計画時の突合で発覚）。
主要港 37 件を投入し、`data-model.md` が定めていた `country_code` / `time_zone` の
カラムも追加した。

### 検索（CQRS のクエリ側）

- 絞り込みはすべて SQL 側。航海の端点は結合で求め、航海ごとに区間を読み直さない
- **検索の日付境界**を実装した。上限をその日の 0 時にすると、**指定した日に出発する便が
  まるごと検索から消える**
- 貨物種別の判定は前後にカンマを付けて部分一致の誤検出を防ぐ

### CI が一度赤になった経緯

**ローカルは緑だったが CI（UTC）で 1 件落ちた。** 原因は、**直したはずの不具合
（UTC で業務日付を判断する）と同じ取り違えを、テストの側でしていた**こと。
同じ形が 4 ファイルに残っていた。`TZ=UTC` で回して CI と同じ条件の緑を確認してから
修正を確定した。

Trivy は Checkstyle の推移的依存に HIGH を 2 件検出した。**ビルドツール自身の依存も
スキャンの対象である。** アプリの実行時には載らないが、CI のビルド環境で実行される
コードであり、Checkstyle を 10.26.1 に上げ `plexus-utils` を修正版に固定した。

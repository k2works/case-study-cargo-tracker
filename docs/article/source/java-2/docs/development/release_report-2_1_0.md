## 技術的成果

### 最後の Bounded Context

`estimation` に集約 `Estimate`・値オブジェクト 5 種・ACL ポート 1 本・画面 3 枚を実装しました。これで **8 BC すべてが実装済み**になり、`package-info.java` だけのパッケージは無くなりました。

### ルート候補の出所を決着させた（ADR-023）

`domain-model.md` は「ルート候補はスタブ実装（固定値）で生成される。将来、外部ルーティングサービスとの連携時に置換予定」と書いていましたが、**ADR-006 は外部連携を採らないと決めており、その「将来」は来ません**。

一方 Routing には US08 で本物の探索が入っています。固定値を返す見積は、**画面は動くのに数字が現実と無関係**になり、荷主に渡る数字として成立しません。

Estimation が `RouteCandidateSource` ポートを持ち、Routing 側にアダプタを置く形に決着させました（ADR-023）。**この決着が見積もりを動かしました** —— スタブなら 3SP、独自の探索を作るなら 8SP、ACL なら 5SP。決めてから着手したため、見積もりは揺れませんでした。

### 読み取り側の規則の置き場（ADR-022）

整流（IT17）で、荷降し手配の「どれが残るか」という**規則**を application 層へ出し、「何回・どの SQL で引くか」だけを infrastructure に残しました。

### 期限切れの扱いを ADR-019 と区別した

ADR-019 は「期限超過は画面を開いた時点で判定する」と決めています。見積では逆に、**期限に間に合う候補が無い理由（便が無い / 期限が厳しい）を保存します**。同じ「期限」ということばで反対の扱いをするため、ADR-023 に両者を並べた表を入れました。

## Keep（続けること）

### K1. 返済枠を時間で先に確保する運用が 3 IT 目に入り、6 件を完済した

タスク 0 として 8 時間を先取りし、6 件すべてを実施した。**「余力次第」と書かなかったから
実施された**。ADR-008 が IT6〜IT8 で 3 IT 連続繰り越された過去と対照的である。

### K2. 依存の更新を機械で見えるようにしたら、25 件が未更新だった

「依存の更新を開始時に置く」は IT5 から 4 IT 続けていたが、**確かめる手段が無く目視に頼っていた**。
`dependencyUpdates` を入れた最初の実行で Spring Boot 4.0.6 → 4.1.0 を含む 25 件が出た。
**見落としても誰も気づかない規律は、いずれ守られなくなる。**

さらに棚卸しの過程で、**`micrometer-core` の上書きが古い方へ固定していた**ことが分かった。
`build.gradle` のコメントが「Boot が追いついたら削除すること。残すと今度は古い方に固定してしまう」
と警告していたとおりのことが、上書きを入れた 1 IT 後に起きていた。

### K3. T1（呼ばれないメソッドの検出）が機能の欠落を掘り当てた

26 件を検出し、うち `Shipper.changeContract` は**機能の欠落**だった。法人荷主の割引率を
打ち間違えると直す手段が無い状態で、US32 を完了扱いにしていた。
**定義済みで呼ばれないメソッドは配線漏れのサイン**という IT7 の教訓が、そのまま当たった。

### K4. 網羅 switch が、種別を増やした瞬間にコンパイルエラーで落ちた

`TrackingEventType` に 3 種別を足したとき、IT7 で入れた網羅テストが**コンパイルできずに
落ちた**。規律が人手から自動に移っていることの確認になった。

### K5. ArchUnit の新ルールを、実装者以外が壊して確かめた

アーキテクトのレビューが独立に検証し、**他 BC の ACL ポートを注入するとルール 4 は緑のまま
新ルールだけが赤**になることを実測した。ADR-012 が「0 件であることを検査で守る」と書いた
意図どおりに機能している。**自分で入れた検査を、自分以外が壊してみることの価値**が出た。

### K6. 5 視点のレビューがすべて回答を返した

IT7 は 5 視点中 4 視点が無回答で自分で代行した。今回は全視点が返り、**高優先度 11 件のうち
5 件は自分では見つけられなかったもの**である。とくに利用者代表の 3 件は、プログラマ・
テスターと同じ欠陥を別の入口から指しており、視点を分けることの効用がそのまま出た。

## Problem（問題点）

### P1. 「宣言と実装の食い違い」が本 IT でも 5 件出た（最も重い）

IT7 で 6 件出したこの形が、**自分で書いたばかりのコードに再び現れた**。

| # | 宣言 | 実装 |
| :--- | :--- | :--- |
| 1 | `relaxesAnything()`「緩めていない再算出は条件の記録を書き換えない」 | 書き換えていた（7 日延ばした事実が消える） |
| 2 | `MAX_EXTRA_DAYS`「画面の 1 クリックで到達してよい範囲ではない」 | 1 回ごとにしか効かず、14 回押せば 420 日 |
| 3 | `BookingNotification`「失敗も記録する」 | 本番に失敗記録の経路が無い |
| 4 | `TrackingActivity`「Setter を持たない。状態を変える手段は `recordEvent` に限る」 | `reroute` と `updateManually` を足して崩れた |
| 5 | 画面「取り消しの申請が必要です」 | 申請の手段が画面にもマニュアルにも無い |

**書いた本人が同じ IT の中で破っている。** コメントは書いた時点の意図であり、
その後の変更に自動では追随しない。

### P2. 「実装はあるが確かめていない」が 3 件（安全装置）＋ 4 件（レビュー指摘）出た

安全装置を壊す検証で 3 件が空振りし、レビューでさらに 4 件（E2E の空振り・空集合で真になる
アサーション・「古くない」しか見ない断言・理由を判別しないエラー確認）が出た。

**受け入れテストが通る経路で先に弾かれる条件は、集約の守りを判別しない。**
IT7 の P1 が「宣言と実装」だったのに対し、これは**その隣**にある。

### P3. 受入基準を 1 件、実装もテストもしないまま完了に向かっていた

US17「状態変更の種類に応じて荷主への通知が送信される」は、計画で
「US12 の通知記録の仕組みに載せる」と**明示的にコミットしていた**のに実装が無かった。
テスターの指摘で気づいた。**受入基準の 4 分の 1 である。**

計画に書いた「満たさないもの」の表は読み返したが、**「満たすと書いたもの」の表は
読み返していなかった。**

### P4. 新しい機能に、それを使う人の入口を作っていなかった

US12 は「予約詳細を開いた人が押す」機能に留まり、**通知すべき予約を見つける手段が無かった**。
経路を割り当てるのは経路設計者であり、営業に確定は伝わらない。
**「送ったつもり」を検知するという US12 の目的を、運用でいちばん壊す形**だった。

IT7 で「ロール別の到達性」、IT8 前半で「状態軸の到達性」を学んだが、
今回欠けていたのは**「その仕事がいつ発生したかを知る手段」**である。

### P5. ツールを上げた後にロックを作り直さず、CI だけが落ちた

Gradle wrapper を 9.7.0 へ上げる前にロックを再生成していた。9.7 はロックファイルに
案内行を書き足すため、CI が再生成して差分を検出した。
**ローカル緑・CI 赤の典型**であり、順序の問題である。

### ベロシティ

8 イテレーションの実績は **9 / 7 / 8 / 8 / 7 / 8 / 8 / 8** で、平均 **7.88SP**。
採用値 8SP との差は 0.12SP であり、**再調整はしない**。

**8 IT 連続で計画 SP = 実績 SP である。** ただしこれは「8SP に収まる量を計画している」
ことの結果でもあり、**上限は依然として測れていない**（IT1 からの持ち越しの問い）。

### レビューの重さについて

IT6 は 14 件、IT7 は 9 件、IT8 は 11 件。**IT8 で初めて 5 視点すべてが回答した**ため、
件数の比較には注意が要る（IT7 は 4 視点を自分で代行しており、自分の盲点は見つからない）。

**高優先度 11 件のうち 5 件は自分では見つけられなかったもの**であり、そのうち 3 件は
「自分が書いたコメントを自分で破った」形だった。**自分の宣言を自分で検算することの
難しさ**が、視点を分ける価値の中身である。

## Keep（続けること）

### K1. 安全装置を 7 つ壊して赤を確認した

IT2・IT3 から続く規律。**壊して赤を確認したのは 7 件。**

| 装置 | 壊し方 | 落ちた件数 |
| :--- | :--- | :--- |
| 経由回数の上限（枝刈り） | 判定を外す | 1 |
| 期限の日付単位比較 | 素朴な時刻比較に戻す | 1 |
| 逆走チェック（乗ってから降りる） | 探索の起点を 0 に戻す | 1 |
| 推奨順の直行優先 | 比較を外す | 1 |
| 所要日数の切り上げ | 切り捨てに戻す | 2 |
| 航海詳細の区間の並び | `ORDER BY` を逆順に | 2 |
| 経路提案の楽観的ロック | `WHERE` の version を外す | 1 |

### K2. 判別しないテストを、自分で見つけて直した

**逆走チェックのテストは、装置を外しても緑のままだった。** 出発地がそもそも航路上に
無いだけで、順序を見ているかを判別していなかった。乗る港と降りる港がどちらも航路上に
ある形（目的地に着いた後に出発地を出る航海）へ差し替えて、判別することを確かめた。

**「壊して赤を確認する」を実行しなければ、この空振りは見つからなかった。**
IT3 の Try がそのまま効いている。

### K3. ArchUnit が設計の誤りを実際に捕まえた

ACL ポートの戻り値に Routing の値オブジェクトを置いたところ、ルール 4 が
「booking が routing に依存している」と落ちた。**実装する側が相手のドメインを直接
参照するなら、ACL を置いた動機そのものが消える。** 境界は素の値にし、翻訳は
Routing 側で行う形に直した。

**ルールが「宣言」ではなく「検査」になっている**ことの価値が出た。

### K4. 着手前の突合が今回も効いた

計画時に設計側の欠落を 6 件見つけ、実装中にさらに 1 件（`booking_route_proposal` の
貨物種別・重量の列）が出た。とくに**費用に入力が無い**ことは、着手後に気づいたら
ADR を書く時間ごと計画外になっていた。

## Problem（問題点）

### P1. 「置いた気になっている装置」が 2 件あった（最も重い）

IT3 までで「装置の不在」は減ったが、**装置を置いた気になっている箇所**が残っていた。

| 内容 | 症状 |
| :--- | :--- |
| `booking_route_proposal` の `version` を `WHERE` で見ていなかった | 2 人が同時に算出すると、後の保存が前の候補を黙って消す |
| 読み戻しで貨物種別を落としていた | 危険物の予約に、扱えない便が「選択可」として並ぶ |

どちらも**保存のときだけ効く／宣言だけある**という共通点を持つ。
**新しい集約を作るとき、既存集約の書き方を見に行かなかった**ことが原因である
（`shipper` には楽観的ロックの正しい書き方がすでにあった）。

### P2. 利用者が押して初めて分かる欠陥を出した

**経路設計者が予約詳細から「一覧に戻る」を押すと 403 になった。**
IT3 の教訓（画面から先への到達性）を受けて新しく作った画面の出口は確かめたが、
**共有画面の中に元からあるリンク**は数えていなかった。

IT2 は「開けるか」、IT3 は「開いた先で何ができるか」、IT4 は
**「置いてあるボタンを実際に押せるか」**。同じ主題の 3 番目の変奏である。

### P3. 並行操作を画面レベルで検証できていない

H1 の衝突は、リポジトリのテストでは固定したが、**MockMvc では並行リクエストを
再現できず画面レベルのテストが無い**。「500 にしない」ことは実装で担保しているが、
自動では守られていない。

### P4. CI の Trivy がまた新しい HIGH を出した

micrometer-core に 2 件（DoS）。IT3 は Checkstyle の推移的依存、IT4 は Boot の
BOM が指すライブラリである。**依存の脆弱性は毎イテレーション出るものとして
扱うほうが実態に近い。**

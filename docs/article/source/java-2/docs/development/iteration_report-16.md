# イテレーション 16 完了報告書

日付: 2026-08-11
対象: **整流局面**（US30 の未達受入基準 ＝ #515 ／ 返済枠 C2〜C10 ／ ふりかえり Try T1〜T6）

## エグゼクティブサマリー

**US30 の唯一の未達受入基準を満たし、Release 2.0 の品質を確定させた。** 輸送中のキャンセルを承認すると陸揚げ地が決まるが、IT15 ではその記録が予約詳細と荷主通知にしか残らず、**実際に船から降ろす荷役作業員には何も届いていなかった**。荷役作業一覧の先頭に荷降し手配を出し、行から荷役登録へ追跡番号を持ったまま進めるようにした。

**本イテレーションの中心は「宣言されているのに、対象に届いていない規則」の是正である。** ADR 19 件に守り手を書き出したところ、**検査の無い規則が 13 件**見つかった。うち構造的に重い 2 件に検査を書き、残りは「守り手: 守らない」と名前で残した。

**新規ストーリーを持たない初めてのイテレーションである。** 計画 SP は 0 とした（US30 の未達分 2SP 相当は IT15 に計上済みであり、再計上すると二重計上になる）。

品質ゲートはローカルの `./gradlew check` 緑、E2E **21 本すべて緑**、テスト **1,410 件すべて緑**。返済枠 C1〜C10 の **10 件すべて**と Try T1〜T6 の **6 件すべて**を完了し、**落としたものは 0** である。

### ユビキタス言語

**「荷降し手配」と「荷降し（`UNLOAD`）」を分けた。** 前者は「ここで降ろせ」という**指示**、後者は現場が実際に降ろした**記録**である。同じ言葉が両方を指すと、一覧を見た作業員が「もう降ろしたのか」と読む。`domain-model.md`・`operation.md` の用語集・画面の 3 か所で使い分けを明記した。

## 課題と残作業

### 決着していない判断（**IT17 の着手前に決める**）

**荷役作業一覧を追跡管理者が開けるべきか。** `ui_design.md` は `ROLE_HANDLER, ROLE_TRACKER` とし、`SecurityConfig` は `ROLE_HANDLER` のみに絞って「現場が使う唯一の画面である」と理由を書いている。**どちらかが古い。**

C1 のテストで追跡管理者の到達性を主張したところ 403 で判明した。**認可を広げるのはテストで既成事実にしてよい変更ではない**ため実装は動かさず、両文書に食い違いを明記した。

**実測値を添えて送る**（ふりかえりの Try T1）。詳細は [ふりかえり](retrospective-16.md) を参照。

## 所感

**このイテレーションが繰り返し示したのは「記録は実態より小さい」ことである。**

| 項目 | 記録 | 実測 |
| :--- | :--- | :--- |
| C2 | 7 クラス | **39 クラス・41 箇所** |
| C3 | 2 件 | **21 件・最大 35 要素** |
| ADR の守り手 | — | **検査の無い規則 13 件** |

いずれも「落とす判断」がその小さい数字の上に立っていた。C2 は 2 度、C3 は 1 度、**「まだ小さい」という誤った前提で落とされている**。

**そして、検査を書く作業そのものが最も多く誤りを生んだ** — 自己参照 3 回、品質ゲート違反 3 回、名簿方式の穴 1 回。守るものを増やすと、守られる対象も増える。

## エグゼクティブサマリー

**貨物が予定と違う場所へ行ってしまったときに組み直せるようにし、通関という「止まる仕組み」を業務に載せた。** IT10 が作ったのは「予定どおり進まなくなったことを記録して伝える」までで、IT11 が足したのはその先である。誤配は記録して終わりではなく現在地から引き直さないと貨物は動かない。通関は下りるまで引き渡してはならない、業務上の唯一の「止まる仕組み」である。

**2 回続けて 10SP を達成した。今回は何も落としていない**（IT10 は計画どおり C9 を落として達成した）。ベロシティの平均は 8.27 に上がった。

**返済枠 7 件を IT 序盤の 7 コミットで完済した。** うち C18 は返済ではなく **US19 の受入基準の未達**であり、IT10 で残した唯一の未達項目が解消した。

そして、本 IT の最も重要な事実は次のものである。

> **IT10 の Try T1（破壊検証のリストを自分で作らない）を実行したら、IT10 とは正反対の結果が出た。** IT10 は「自分で選んだ 10 件が全部赤」で、選ばなかった 3 件が壊れていた。**IT11 は機械的に数え上げた 22 件のうち 3 件が空振りした。** 選び方を変えたら、見つかるものが変わった。

## 技術的成果

### 設計上の判断

| 判断 | 理由 |
| :--- | :--- |
| **US29 → US28 の順に実装する** | US28 は 4 つの BC にまたがる。**自動起票の作法を US29 で確立してから載せた** |
| **通関申告を独立した集約にする** | 申告のライフサイクルは荷役作業と独立に動く。引取の可否は同一トランザクションの読み取りで判定する（**当初「内部エンティティ」と書いたが実装と食い違っており、レビューで訂正した**） |
| **入力は追跡番号・保存は荷役作業への紐付け** | 申告は「どの通関作業でどの貨物を通したか」の記録である。列を NULL 可に緩めない |
| **承認を挟むのは誤配のときだけ** | 毎回挟むと現場の作業が倍になり、**警告そのものが読み飛ばされる** |
| **誤配の呼び名を `MISROUTED` に揃える** | 既に 2 か所で使われている。BC が違っても業務の言葉が違うわけではない |
| **留置の日数は業務日付単位・留置に入るたび数え直す** | 経過時間だと時差でずれる。最初の留置日から数え続けると再留置がいきなり警告になる |
| **対応が要る状態を状態自身に持たせる**（`needsAttention`） | 「留置だけ」を呼び出し側に書くと、**最も重い「不可」が最も静かになる**（実際にそうなっていた） |

### ADR

**ADR-014（ダッシュボードの件数は各 BC が自分で載せる）を起票した。** IT10 で確立しながら記録していなかった拡張点である。`shared` が全 BC のクエリサービスを参照する形を避けるという依存の向きの判断であり、ADR-012 の系列にある。

### マイグレーション

- `V23__exception_revised_arrival.sql` — 例外に新しい到着予定日（NULL 可）
- `V24__customs_status_history.sql` — 通関状態の変更履歴テーブル新設、`held_since`、`CUSTOMS_CLEARED` の CHECK

## 課題と残作業

### 正直な記録

**1. US28 の受入基準 1 項目が部分的である**（上記）。料金調整の根拠として営業担当者が誤配を追う手段が無い。IT12（C31）。

**2. 引取の拒否は「申告が登録されている貨物」にしか効かない。** 申告を出し忘れた輸入貨物は引取が通る。どの貨物に通関が要るのか（輸入／国内の区別）が現在のモデルに無く、判断を先送りした。IT12（C29）。

**3. BC 間の結合が SQL の層で 2 本増えた。** ArchUnit を 1 件も破らずに増えている。**検査が緑であることは、越境していないことの根拠にならない。** IT12（C28）。

### 落としたもの

**無し。** IT10 は計画どおり C9 を落として 10SP を達成したが、本 IT は計画したタスクをすべて実施した。

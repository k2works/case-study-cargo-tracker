## Keep（続けること）

### K1. 局面の名前ではなく条件でアプローチを選んだ

IT7〜IT12 はアウトサイドインだった。理由は「既存集約の組み合わせであり、新しい集約をできるだけ作らない」ことである。**IT13 はその条件を満たさない** — Billing は `package-info` のみで集約が 1 つも無く、ACL ポートを 3 つ同時に実装し、金額の丸め規則を確定させる必要があった。

中盤（IT3〜IT6）と同じ条件なので同じ選択をした。結果、**タスク 1 と 2（ドメインと永続化）を終えるまで画面もコントローラも 1 行も書いていない**。金額の丸めが画面の都合（カンマ区切り・切り上げ表示）に汚染されずに済んだ。

### K2. 設計書の計算例が「順序を決める必要性」を示せないことに気づいた

`domain-model.md` の計算例（基本料金 100,003 円・割引 15%・税 10%）では、**段階丸めと一括丸めの結果が一致する**。例をそのままテストにしても「順序を仕様として固定する必要がある」こと自体は示せない。

実際にずれる値を探して固定した（100,007 円で 93,505 と 93,506。一括丸めだと 1 円多く請求する）。**規則を決める必要性そのものをテストにした**のは本 IT の白眉である（テスターの評価）。

### K3. 検査が設計の合図を 11 回出し、すべて回避せず構造を直した

| 検査 | 回数 | 直した内容 |
| :--- | :--- | :--- |
| Checkstyle | 4 | パラメータ数超過 → `DetailContext` / `InvoiceParties` / `InvoiceAmounts`。ファイル 500 行超過 → テストクラスを関心で 2 回分割 |
| SpotBugs | 2 | ACL アダプタが Mapper 直参照 → 出力ポート経由。`RuntimeException` 再送出 → 計算してから代入 |
| ArchUnit | 3 | アプリ層 → インフラ層。共有イベントの名前検査。**表示名の変換をポートに載せたら BC 越境を捕まえた** |
| H2 スモーク | 1 | `UPDATE ... FROM` が PostgreSQL 固有 → 相関サブクエリ |
| Flyway | 1 | 既存テーブルの再作成 |

**制限に当たったのは合図である**を 11 回実践した。とくに ArchUnit が「表示名の変換を ACL ポートに載せた」のを捕まえたのは、レビュー指摘への対応中に出たもので、**急いでいるときほど検査が効いた**。

### K4. 返済枠を IT 序盤の独立コミットで先に着手した（8 IT 連続）

返済 7 件と運用要件 3 件を、ストーリー本体より先に片づけた。**「余力次第」にすると固定化する**という IT9 の教訓が 8 回続けて機能している。

### K5. マルチパースペクティブレビューが実バグを捕まえた

XP 5 視点の並列レビューで、**3 視点（programmer / technical-writer / user-representative）が独立に同じ箇所を指摘した**。視点の重なりは冗長ではなく確度である。実際に数値で再現でき、実バグだった。

## Problem（問題点）

### P1. 全緑の状態からレビューが高優先度を 13 件見つけた（5 IT 連続）

`TZ=UTC ./gradlew check` 全緑・E2E 17 本緑・SonarQube PASS の状態から、高優先度が 13 件出た。**5 イテレーション連続である。**

内訳を見ると、本 IT に固有の型が 2 つある。

**(a) 表示側だけが計算を持っていた（H1）。** 集約は正しく計算していたが、画面用の `InvoiceView` が「基本料金 − 割引額」で割引後料金を作り直していた。調整があると内訳が足し算にならない。**同じ計算に 2 つの答えを残した**形であり、これまで何度も戒めてきた型そのものである。

**(b) 調整ありのテストが個人荷主（割引 0%）しか無かった。** 割引と調整が同時にある組み合わせを踏んだテストが単体にも画面にも無く、判別できなかった。

### P2. 自分で書いた運用要件が実装で成立していなかった（H2）

タスク 0 で運用要件 R1 を定義し、「料金調整は例外の記録を見ながら判断する」と書いた。マニュアル 11.3 にも同じことを書いた。**しかし経理担当者は予約詳細を開けなかった**（403）。

**書いた側が確かめる側になると、成立を検査しない。** R1 を書いたのも、マニュアルを書いたのも、認可を設定したのも同じイテレーションの同じ担当である。利用者代表が「毎月どう使うか」から見て初めて出た。

### P3. コメントが主張する守りが実在しない形が 3 IT 連続で再発した

`BillableCargoAdapter` に「区間が 0 本の貨物は請求できない」と書きながら、その守りはどこにも実在しなかった（H3）。距離係数 0 が計算まで届き、画面には 500 が出る。

IT11（コメント）・IT12（マニュアル）に続き 3 回目である。**IT12 の Try T1「実装しなかった守りを数える」を実施し 3 件の穴を埋めたが、それはマニュアルの「〜できません」からの数え上げだった。** アダプタの Javadoc は数え上げの対象に入れていなかった。

### P4. 既存のテストが空振りしていた（H5）

「確定後は税率が変わっても金額が動かない」は、`reconstruct` に保存値そのものを渡していたため、**再計算する実装でも緑になった**。安全装置の破壊検証は 8 件すべて赤にできたが、**その検証は「作った守り」にしか向けていなかった**。

### P5. 破壊検証の判定を 2 回間違えた

`BUILD FAILED` をテストの赤と読んだが、コンパイルエラーでも同じ表示になる（**壊し方が下手なだけで「守れている」と読める**）。失敗の記録が stderr に出ることも見落とした。

### P6. E2E で「押したのに何も起きない」形を踏んだ

「この経路で確定」は `confirm()` を返すボタンで、`page.on('dialog', accept)` を張らないと **POST そのものが飛ばない**。画面にもサーバログにも痕跡が残らず、トレースの通信記録を見て初めて分かった。既存 spec には全て張ってあったが、新しい spec に写し忘れた。

### IT14 への申し送り

**US23（精算を処理する）は本 IT が作った土台の上に乗る。**

- `BookingSettlementPort` は未実装（`domain-model.md` の ACL ポート表）。精算完了時に予約を `SETTLED` へ遷移させる
- **ADR-017 の「`payment_status` が動くのは `charge_status = CONFIRMED` の後だけ」は口約束のまま。** DB 制約でも検査でもない（レビュー中）。US23 の実装時に固定すること
- **返金を伴う取り消しをどう扱うかが最初の設計判断になる。** US36 が「精算済みには訂正・取り消しできない」と定めており、`Money.subtract` も請求額を超える減額を拒んでいる
- `payment` テーブルは V1 で作成済み（本 IT では触っていない）

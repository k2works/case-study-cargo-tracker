## Keep（続けること）

### K1. 安全装置は必ず壊して確認した

IT1 の Try をそのまま実行した。本イテレーションで**壊して赤を確認した**のは 5 件。

| 装置 | 壊し方 | 結果 |
| :--- | :--- | :--- |
| 楽観的ロック（貨物・荷主） | 同じ version を読んだ 2 つの更新 | 後の 1 つが失敗する |
| ArchUnit ルール 4（BC 分離） | ドメインから他 BC の値オブジェクトを参照するプローブ | 落ちる |
| 依存検証 | `developmentOnly` を `runtimeOnly` に変更 | 落ちる |
| ArchUnit（ドメイン ↛ MyBatis） | 値オブジェクトに `@Mapper` | 落ちる |
| 遷移表 | 経路の無い予約を確定できる実装 | 4 件落ちる |

**「入れたこと」と「働くこと」は別**という IT1 の教訓が、手順として定着した。

### K2. 「宣言」の棚卸しが実際に穴を見つけた

ADR の「〜しない」9 件のうち、**4 件は文章だけで、破ってもビルドが緑**だった。
H2 を本番成果物から外す・WireMock を採用しない・JPA を採用しない・ドメインに MyBatis の型を
出さない。いずれも読めば守っている気になる宣言だった。

### K3. 受入基準を「満たせないから消す」ではなく「移し先を書く」形にした

US04 の 2 項目は消さずに移し先を表で明記した。**消すと、次に読む人には最初から
無かったように見える。**

### K4. SonarQube の指摘を抑止ではなく修正で解いた

セキュリティホットスポットは実際の欠陥（メールアドレス正規表現の ReDoS）だった。
権限が無くて API から特定できなかったため、ローカルコンテナの DB を読み取りのみで
参照して箇所を割り出した。**「見えないから保留」にしなかった。**

## Problem（問題点）

### P1. 前提が揃う前にロールへ機能を開放した（最も重い）

貨物予約一覧を ROLE_SHIPPER に開放したが、**利用者アカウントと荷主を結びつける手段が
無く、荷主から他社の予約まで見える状態だった。**

原因は、IT1 の教訓「ロール別の作業入口の欠落」を強く意識するあまり、
**「入口を作る」ことだけを確認し「開放してよいか」を確認しなかった**こと。
`non_functional.md` は ROLE_SHIPPER を「自社予約・追跡（Phase 2）」と明記しており、
正典を読めば分かった。

クローズ前のレビューで自分で見つけて修正したが、**受入基準にもテストにも
「見えてはならないもの」の観点が無かった。**

### P2. 時間で守ろうとしたテストが、脆弱な実装でも緑だった

ReDoS 対策（長さ検査を形式検査より先に）を経過時間のアサートで守ろうとしたが、
**順序を戻しても緑のまま通った。** 入力の形状が最悪ケースに当たらないと差が出ない。
分岐の結果（どちらの検査で落ちたか）で判定する形に書き直して初めて赤になった。

**K1 の規律をテストの側にも当てていなかった。**

### P3. 機械的な置換の結果を確認しなかった

1 つのテストを追加する置換が、同名のアンカーを持つ 3 つの入れ子クラスすべてに入り、
うち 2 つは意味を成さないまま緑だった。

### P4. 品質ゲートの前処理が手順から抜けていた

`sonar-local:check` は `sonar.java.libraries` が指す成果物を自分では作らない。
**手順書に「先に実行すること」と書くだけでは忘れられる**（実際に落ちた）。

### P5. 1 つ直すと別の指摘が出た

ReDoS 修正が S5998（上限の無い繰り返し）と S2629（ログレベルに関わらず整形が走る）を
新たに生んだ。**1 回のスキャンで終わりにできない**ことを、スキャンを 5 回まわして学んだ。

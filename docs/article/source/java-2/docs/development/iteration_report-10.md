## エグゼクティブサマリー

**輸送が計画どおりに進まなくなったときを扱えるようにした。** これまでの 9 イテレーションが作ってきたのは「うまくいく道」である。予約し、経路を割り当て、確定し、追跡番号を発行し、荷役を記録し、引き取る。IT10 で扱ったのは**その道から外れたとき** — 遅延・破損・紛失であり、これらは国際輸送では日常的に起きる。

**初めての 10SP を達成した。** ただしこれは「8SP が過小だった」ことを意味しない。計画に先に書いた順序どおり C9（3.0h 相当）を落として達成している。

**返済枠 9 件を IT 序盤の 5 コミットで完済した。** とくに C17（`data-model.md` の列が実スキーマにあるかの検査）は、有効化した時点で 12 件の乖離を出した。人が気づくのを 9 イテレーション待っていた乖離を、機械が 1 回で見つけている。

そして、本 IT の最も重要な事実は次のものである。

> **安全装置 10 件を破壊検証し、全件が赤になった。それでもレビューは高優先度の欠陥を 10 件見つけた。** 壊れていた装置のうち 3 つは、**破壊検証のリストに載せなかったもの**である。

## 技術的成果

### 設計上の判断

| 判断 | 理由 |
| :--- | :--- |
| **発生前の輸送状態を永続化する**（`status_before`） | 解決の復帰先を荷役の履歴から導き直すと、**例外の対応中に積込が記録された瞬間に誤った状態へ戻る**。ユニットテストは緑のまま通る |
| **例外を `TrackingActivity` の内部エンティティにする** | 例外は輸送状態を動かし、解決で元に戻す。別集約にすると状態を変える権限が 2 か所に分かれ、「解決したのに戻っていない」を作れる |
| **エスカレーションの要否は種別が持つ** | 呼び出し側から渡せる形にすると、紛失をエスカレーションせずに起票できる |
| **エスカレーションを管理者が見る画面で満たす**（ADR-006） | 外部へは送らない。**「送った」だけで誰も見ないなら意味が無い** |
| **発生と対応報告を別の通知種別にする** | 荷主にとって「起きた」と「片づいた」は別の知らせであり、同じ種別だと履歴で区別できない |
| **ダッシュボードの件数は各 BC が `@ControllerAdvice` で載せる** | `shared` が全 BC のクエリサービスを参照する形を避ける。**この拡張点は ADR 化していない**（IT11 / C25） |

### ADR

新規の ADR は起票していない。4 件の判断はいずれも既存 ADR（005 / 006 / 009 / 012）の適用である。**ADR-005 に `shared.application` の位置づけを追記した。**

### マイグレーション

`V22__tracking_exception_location.sql` — `tracking_exception_event.location_unlocode` の追加（**NULL 可のまま**）と、`booking_notification` の CHECK に `EXCEPTION_RESOLVED` を追加。

## このイテレーションの主題

**IT10 で扱ったのは「予定どおり進まなくなったことを記録して伝える」ことだった。IT11 で扱ったのは、そこから先の 2 つである。** ひとつは**組み直す**こと（誤配は記録して終わりではない）。もうひとつは**止める**こと（通関は業務上の唯一の「止まる仕組み」である）。

そしてふりかえりの主題は別にある。

> **IT10 の Try T1（破壊検証のリストを自分で作らない）を実行したら、IT10 とは正反対の結果が出た。** IT10 は「自分で選んだ 10 件が全部赤」で、選ばなかった 3 件が壊れていた。**IT11 は機械的に数え上げた 22 件のうち 3 件が空振りした。**
>
> **選び方を変えたら、見つかるものが変わった。**

## Keep（続けること）

### K1. 破壊検証のリストを自分で作らなかった（Try T1 の実行）

IT11 の差分から、`throw` 15 件・拒否の `return` 8 件・SQL の絞り込み 20 件・認可規則 15 件を**機械的に数え上げてから**壊した。

**空振りが 3 件出た。**

| 空振りした装置 | なぜ空振りしたか |
| :--- | :--- |
| 理由を必須にする検査 | **同じ検査が集約と値オブジェクトの 2 か所にあった。** 片方を壊しても、もう片方が拾う |
| 申告の重複登録を拒む | 拒否を書いただけで、**通る道を一度も試していなかった** |
| 通関の荷役だけを引き当てる | **荷役が 1 件も無い場合しか試していなかった。** 種別の条件を外しても、荷役ゼロなら結局拒否される |

**IT10 で「自分で選んだ装置しか検証していない」と書いた。IT11 は選ぶのをやめた。** その結果、IT10 では見つからなかった種類の欠陥（空振り）が見つかった。

### K2. やらなかったものを名前で記録した

数え上げ 58 件のうち実施は 22 件である。**やらなかったものを「一覧の絞り込み（`status` / `keyword`）と ID による単純な取得」と名前で書いた。** 理由も添えた（前者は検索のテストが通る道を押さえている、後者は取得できなければどのテストも成立しない）。

「全件やった」と書けない以上、**やらなかった範囲が読める形で残っていることが次の IT の入力になる。**

### K3. テストが 4 回、宣言と実装の食い違いを見つけた

| 見つかったもの | どう見つかったか |
| :--- | :--- |
| `BookingNotification.exception` が通関完了の種別を拒む | 通知が**黙って記録されない**まま緑だった。シナリオテストが落ちた |
| 画面は「現在地から再設計」と言うのに探索は元の出発地 | 超過日数のテストで**候補が 1 件も出ず**、食い違いが露見した |
| `test_strategy.md` が存在しないクラスを指す | 開始準備の突合 |
| 通関済が終端なら「解除して再留置」の経路が無い | テストを書こうとして**書けないことに気づいた** |

**4 件目は「テストを書こうとして書けなかった」という形である。** 実装が先にあり、テストがその矛盾を照らした。

### K4. 返済枠を IT 序盤の独立コミットで先に返した（5 IT 連続）

返済枠 7 件を最初の 7 コミットで完済した。**C21（複数例外）を先に返していなければ、US29 の通関留置と US28 の誤配がどちらも例外を自動起票するため、そこで詰まっていた。**

「余力次第」にしていたら、US29 の実装中に「1 件制限があるので誤配は起票できません」と書くことになっていた。

### K5. 「開けないこと」と「開けること」を対で書いた（Try T2 の実行）

通関の認可で、営業・荷主が 403 になることと、**追跡管理者が 200 で内容を読めること**を対で書いた。順序を入れ替えると赤になることも確認した。

IT10 は「403 を 2 件書いて 200 を 0 件」だった。今回は最初から対にしている。

## Problem（問題だったこと）

### P1. コメントが実装より強い保証を主張していた（3 件）

**これが本 IT の最大の問題である。** IT10 の P3（「自分で書いた教訓を、書いた本人が同じ IT の中で繰り返した」）が、別の顔で戻ってきた。

| 主張したコメント | 実装 |
| :--- | :--- |
| 「やめる側も同じ入力を持って戻る。**打ち直させると、入力し直すより承認を押すほうが楽になってしまう**」 | **追跡番号しか持ち回っていなかった。** 自分が警戒した誘因を、自分で作っていた |
| 「`HandlingActivity` の**内部エンティティ**。別集約にすると読んだ直後に留置へ変わっても止められない」 | **独立した集約だった。** しかも「避けた」と書いた形（引取側が通関を読みに行く）そのものになっていた |
| 「画面の出し分けは**同じ述語を使う**」 | **文字列比較で別の述語を再実装していた** |

**3 件とも、コメントを書いた本人が同じイテレーションで実装している。** 書いた時点では本当にそのつもりだったはずで、**「書いたから守られた」と思い込む形**である。

### P2. 検査が守っている範囲の外で、結合が 2 本増えた

ArchUnit のルールを **1 件も破らずに**、BC 間の結合が SQL の層で 2 本増えた（`BookingQueryMapper` → `handling_activity`、`CustomsListMapper` → `cargo` / `shipper`）。

**しかも同じイテレーションの中に、同じ問題への 2 つの答えが並んでいる。** 荷主名を引くのに、Tracking は ACL ポート（`CargoContacts`）を通し、Handling は SQL で JOIN した。**次に読む人はどちらの前例に従えばよいか判断できない。**

ADR-012 は「循環をインフラ層に閉じ込め、0 件であることを検査で守る」と決めた。**その「閉じ込め」は Java の依存についてしか成立していない。**

### P3. 「不可」がどこにも波及しなかった

通関状態を「不可」にしても、例外も通知も起きなかった。留置だけを拾っていたためである。

**留置は保管料だが、不可は積戻し・廃棄・関税の争いに発展する。最も重い状態が、最も静かだった。** 受入基準は「通関済」「留置」「不可」の 3 つを並べているのに、実装もテストも 2 つしか扱っていなかった。

### P4. 荷主が読む文面に「発生場所: null」が出ていた

自動起票（誤配・税関保留）は発生場所を持たない。文字列連結でそのまま出していた。

**C20 で「通知の本文を荷主に開放する」と決めた直後である。** 読めるようにした結果、読める形になっていないものが露見した。

### P5. 受入基準の 4 項目でテストが通る道を押さえていなかった

- 目的地・希望期限の**引き継ぎ**（目的地を取り違えても全テスト緑）
- 期限の超過日数の**算出**（単体テストは日数を手で渡していた）
- **貨物 ID** による検索
- 通関状態「**不可**」への更新

**「テストがある」と「その道が試されている」は別である。** 4 件とも、対応するコードは書かれていたが、通る経路を一度も実行していなかった。

### P6. マニュアルが実装より先に「保証」を書いた

「入力に戻る」で入力が保たれる、と手順書に書いた。**実装は保っていなかった。**

これは記述の誤りというより、**設計の欠陥をドキュメントが先に主張した**形である。手順書を直すのではなく実装を直した。

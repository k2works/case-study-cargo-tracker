# イテレーション 14 完了報告書

日付: 2026-08-10
対象: Release 2.0（精算）／US23 精算を処理する（5SP）

## エグゼクティブサマリー

**US23 を完了し、輸送料金の算出から精算完了までが 1 本につながった。** 経理担当者は請求対象の確認 → 料金の算出 → 確定 → 請求書の発行 → 督促 → 入金の確認まで、画面だけで月次の業務を回せる。入金を確認すると予約が「精算完了」になり、US36 の「精算済みには訂正・取り消しできない」が効き始める。

あわせて **IT13 レビューの返済枠 8 タスク（10 件）を完済**し、IT13 で送った高優先度 4 件（引取日・締めの件数と合計・例外の記録・N+1）に決着をつけた。

品質ゲートはローカル・CI・SonarQube のいずれも通過している（Quality Gate PASS。Bug 0 / Vulnerability 0 / Code Smell 0）。クローズ前のマルチパースペクティブレビューが高 18 件を出し、**うち 13 件を本イテレーション内で対応**した。

## 技術的成果

### ドメイン

- `Issuance`（発行日時＋支払期限）・`Payment`（入金の記録）・`PaymentMethod`・`PaymentStatus` を新設
- `Invoice.issue` / `confirmPayment` / `markOverdue`。**発行できるのは確定済みだけ**、**請求額どおりの入金だけを受ける**、**遅れても入金は入金**、**入金済みは督促に戻さない**
- 支払期限は**発行時に決めて保持**する（税率と同じ判断）。都度計算すると設定を変えた日に既発行分の期限が動く

### 越境

- ACL ポートを 3 本新設（`BookingSettlementPort` / `InvoiceNotificationPort` / `CargoExceptionRecordsPort`）。**ポートは使う側の BC が持つ**
- 結果として `billing/` の本番コードは**他 BC を 1 ファイルも import していない**

### 永続化

- `invoice.issued_at` / `due_date` / `payment_status` を使い始め、`payment` を `LEFT JOIN` で同時に読む
- 精算の更新を金額の更新と分け、`WHERE charge_status = 'CONFIRMED'` で守る
- ADR-017 の不変条件（V31 の `CHECK`）と ADR-018 の不変条件（V35 の `UNIQUE`）を**どちらも制約にした**

### 画面

- 請求書詳細に発行・入金確認・入金の記録・この貨物の例外・何日超過か
- 督促対象一覧は**請求書一覧の絞り込み**（`?status=OVERDUE`）。新しい画面を作らない
- ダッシュボードに「支払期限超過」のカード（行き先まで検査）

### ADR

| ADR | 判断 |
| :--- | :--- |
| ADR-018 | 一部入金を認めない（差額の扱いは業務であり、黙って受けると帳簿と合わない） |
| ADR-019 | 支払期限の超過は画面を開いたときに判定する（バッチは止まっても誰も気づかない） |

## レビュー結果

XP 5 視点の並列レビュー（[統合レポート](../review/IT14実装_review_20260810.md)）で **高 18 / 中 19 / 低 8 件**。

**高 13 件を本イテレーション内で対応した。** 主なもの:

- 「例外にしない」が「記録しない」に滑っていた（予約を精算完了にできなかったことがどこにも残らない）
- 期限のテストが CI（UTC）では 1 日のうち 9 時間だけ落ちる
- ADR-018 の「1 請求書 1 入金」が DB 制約になっていない（締めの二重計上として現れる）
- 楽観的ロックが「働くこと」を確かめていない
- 入金額・入金日時・支払方法・参照番号が画面のどこにも出ない
- 「利用者に見せる語は請求書に統一する」という規則を、規則を書いた本人が破っていた

**残る高 5 件は IT15 へ記名して送る**（期間・荷主の絞り込み、発行し忘れの検出、督促の導線と記録、テストヘルパーの重複、完全修飾名）。

# ADR-022: 読み取り側の「規則」は application 層に置き、「問い合わせ」は infrastructure に残す

CQRS の読み取り側で、業務の判断（どれを出すか・どうまとめるか）は application 層の純粋な関数に置く。何回・どの SQL で引くかは infrastructure の実装クラスに残す。

日付: 2026-08-11

## ステータス

承認済み

## コンテキスト

IT16 で荷降し手配の一覧（US30 / #515）を実装した。`MyBatisHandlingQueryService.findPendingDischarges` が次の 3 つを 1 つのメソッドで行っていた。

1. ACL ポート（`ApprovedCancellations`）から承認済みの手配を受け取る
2. 自分のマッパーで「すでに降ろした予約」をまとめて引く
3. **降ろし済みを落とし、同じ予約をまとめ、順序を保って返す**

3 が業務の規則である。ところがこれは **SQL を書くクラスの中にしか無かった**。確かめるには実 PostgreSQL を起動し、承認と荷降しをデータで作る必要があり、**規則そのものを直接壊すテストが書けなかった**。IT16 のクローズ前レビューで R3 として起票された。

一方、**クエリサービスの実装をまるごと application 層へ移す案**には別の代償がある。

- CQRS の読み取り側を MyBatis で書くのは本プロジェクトの設計である（`architecture_backend.md`「CQRS 適用方針」）。1 つだけ例外を作ると、**次に一覧を書く人がどちらに従えばよいか分からなくなる**
- ArchUnit ルール 3（アプリケーション層がインフラ層を直接参照しない）を満たすため、この一覧のためだけに出力ポートを 1 本増やすことになる

## 決定

**判断だけを動かす。問い合わせは動かさない。**

- **application 層**（`application/internal/queryservices/`）に、入力と出力だけを持つ純粋な関数を置く。ここにあるのは「降ろし済みは落とす」「同じ予約は 1 つにまとめる」「順序は保つ」という**業務の言葉で説明できる規則**だけである
- **infrastructure 層**（`infrastructure/repositories/`）は、ポートとマッパーから値を集め、規則に渡し、表示用へ変換する。**何回問い合わせるかはここが決める**

最初の適用は `DischargeOrderSelection`（荷降し手配）である。

### この分け方が効くかどうかの見分け方

読み取り側のメソッドを見て、次の両方が当てはまるときに分ける。

| 条件 | 意味 |
| :--- | :--- |
| 業務の言葉で説明できる判断がある | 「降ろし済みは落とす」は SQL の都合ではない |
| その判断を確かめるのに DB の起動が要る | 規則を壊すテストが書けない状態である |

**単に JOIN した結果を DTO に詰め替えるだけの一覧は分けない。** そこに判断は無く、分けると往復が増えるだけである。

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| 規則が問い合わせ側に書かれていない | **`ReadSideRuleLocationTest`**（IT19 で追加） | `infrastructure/repositories` の `*QueryService` にある**しきい値との比較**のみ。定数どうしの比較や Mapper の SQL は見ていない |
| 荷降し手配に残るものの規則 | **`DischargeOrderSelectionTest`**（IT17 の R3 で追加） | 規則の関数そのもの（DB を起動しない）。**落とすことと残すことの両方**を見る |
| 規則と画面のつながり | **`DischargeOrderTest`** | 実 PostgreSQL 上での画面までの経路 |
| 問い合わせ回数が件数に比例しない | **`DischargeOrderTest.手配が増えても問い合わせ回数は増えない`** | 手配 1 件と複数件での問い合わせ回数 |
| アプリケーション層がインフラ層を参照しない | **`PackageStructureTest`**（ArchUnit ルール 3） | Java のクラス参照のみ。**規則の関数が SQL を書き始めても落ちない** |
| 新しい一覧でこの分け方に従う | **守らない。** | **検査の外。** 「判断があるか」は機械的に判定できない。**一覧を足す変更のレビューで問う** |

## 影響

### ポジティブ

- **規則を DB 無しで壊せる。** 荷降し手配の規則は 7 本の単体テストで固定した。実 PostgreSQL を使うテストは、規則ではなく**画面までつながっていること**に集中できる
- 規則の置き場が読み手に分かる。「どれが出るのか」を調べる人は application 層を見ればよい
- CQRS の読み取り側を MyBatis で書く設計は変わらない。**例外を作っていない**

### ネガティブ

- クラスが 1 つ増える。判断の無い一覧にまで機械的に適用すると、**往復が増えるだけの層**になる
- 「判断があるか」の線引きは人が行う。検査に落とせない（上表に明記した）

## 検討したが採らなかった案

| 案 | 却下理由 |
| :--- | :--- |
| クエリサービスの実装ごと application 層へ移す | CQRS の読み取り側の書き方に例外ができ、次に書く人がどちらに従うか分からなくなる。この一覧のためだけに出力ポートを 1 本増やすことにもなる |
| そのまま infrastructure に置いておく | 規則を壊すテストが書けない状態が続く。IT16 のレビューで起票された問題がそのまま残る |
| 規則を集約（`HandlingActivity`）へ置く | 手配は Booking の承認から来る値であり、荷役の集約が守る不変条件ではない。集約に読み取りの都合を持ち込むことになる |

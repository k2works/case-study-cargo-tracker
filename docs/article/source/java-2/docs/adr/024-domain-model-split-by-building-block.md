# ADR-024: ドメインモデルを構成要素ごとのパッケージに分ける

## ステータス

承認済み（2026-08-12。IT19）

## コンテキスト

各 BC の `domain/model` は 1 つのパッケージにすべてを入れていた。実測で **140 クラス**あり、最大の Booking は 35 クラスが 1 階層に並んでいた。

パッケージを開いたとき、**どれが集約ルートでどれが値オブジェクトなのかは、クラスを開くまで分からない**。JIG のパッケージ図でも 1 つの箱になり、構成要素の別が読み取れない。

参照実装（`practical-ddd-in-enterprise-java` の `bookingms`）は `domain/model` を **aggregates / entities / valueobjects / commands** に分けている。

## 決定

**各 BC の `domain/model` を、DDD の構成要素ごとのサブパッケージに分ける。**

| サブパッケージ | 入れるもの |
| :--- | :--- |
| `aggregates` | 集約ルート |
| `entities` | 集約の内側で同一性を持つもの |
| `valueobjects` | 値オブジェクト・列挙・**識別子** |
| `commands` | 業務の要求を 1 つの型にまとめたもの（**該当が無ければ作らない**） |

**ドメインサービスと例外は `domain/model` 直下に残す。** どのサブパッケージにも属さないためであり、参照実装もサービスの置き場を持たない。該当するのは 6 クラス（`RouteSearchService` / `FreightEstimator` / `FreightChargeCalculator` / `DischargeCandidates` / `ClaimCodeMatch` / `InvalidBookingStatusTransitionException`）である。

**識別子は `valueobjects` に置く。** 識別子は値オブジェクトである。参照実装は `BookingId` を `aggregates` に置いているが、**それに倣うと集約ルートの数が読めなくなる**（下記「得たもの」が最初の 1 回で壊れた）。

**`entities` に置くのは同一性を持つものだけである。** レコードは値オブジェクトであり `valueobjects` に置く。

**サブパッケージにはすべて `package-info.java` を置く。** 説明の無いパッケージは JIG の図では名前だけの箱になる。

## 結果

### 得たもの

- **パッケージを開いた時点で構成要素が分かる。** 「この BC の集約ルートは何か」は `aggregates` を見れば足りる
- **JIG の用語集に構成要素ごとの説明が載る**（27 パッケージ分を追加）
- **集約ルートの数が目に見える。** Booking 3・Handling 3・Routing 2・Billing 2、他は 1 —— **多いことがひと目で分かる**

> **この 3 点は、最初に書いた分類のままでは得られなかった。** クローズ前レビューで
> 「識別子を `aggregates` に同居させたせいでルート数が読めない」「`entities` の 8 件中 6 件が
> record（＝同一性を持たない）」と指摘され、**同じイテレーションの中で分類を直した**。
> 直した結果、`entities` に残ったのは `ProposedRoute` と `TrackingExceptionEvent` の 2 つだけである。

### 失ったもの（**重要**）

**パッケージプライベートで守っていた境界が壊れた。**

分割前、集約の内側だけに開いていた操作は「同じパッケージにいること」で守られていた。javac が越境を止めていたのである。サブパッケージに分けると同じパッケージではなくなるため、**メソッドを `public` にせざるを得なくなった**。

| クラス | 置き場 | 開いた操作 | 本来呼んでよいもの | javac は止めていたか |
| :--- | :--- | :--- | :--- | :--- |
| `ProposedRoute` | `entities` | `of` / `withPriority` | `RouteSearchService` | **止めていた**（class） |
| `TrackingExceptionEvent` | `entities` | `raise` / `resolve` | 集約ルート（`TrackingActivity`） | **止めていた**（class） |
| `CargoProgress` | `valueobjects` | `withStatus` / `withRouting` / `issued` | 集約ルート（`Cargo`） | 止めていない（record） |
| `NotificationDelivery` | `valueobjects` | `succeeded` | 集約ルート（`BookingNotification`） | 止めていない（record） |

**実費は 4 メソッドである。** 当初この ADR は「7 メソッドを公開した＝コンパイラの保証をコメントへ格下げした」と書いていたが、クローズ前レビューで**後半の 2 クラスは `record` であり、正準コンストラクタが元から公開されている**ことが分かった。`new CargoProgress(...)` は分割前から誰でも書けたのであり、**そこに javac の保証は最初から無かった**。

**残る 4 メソッドについては、コンパイラによる保証をコメントによる約束へ格下げしたということである。** 各メソッドには「呼んでよいのは誰か」を書いたが、**書いてあることと守られていることは別である**（本プロジェクトが繰り返し踏んできた形そのものである）。

**この損失は IT20 で検査に落とした**（`EntityEncapsulationTest`。下記「何がどこで守るか」）。IT19 の時点では埋め合わせておらず、`iteration_plan-19.md` の「本 IT では扱わないもの」に **D5** として実測付きで記名して次のイテレーションへ送っていた。

> **この記名も、レビューで指摘されるまで存在しなかった。** 当初は「名前で記録した」と本文に書きながら、
> **どこにも記録が無かった**。ADR 自身が戒めている形をその ADR が踏んでいた。

### 変えなかったもの

- **集約の境界そのもの。** どのクラスがどの集約に属するかは変えていない
- **BC 間の規律。** ArchUnit のルール 4（BC 間でクラスを直接参照しない）はパッケージ階層が深くなっても効く
- **共有カーネルの検査。** 対象を `shared.domain.model` から `shared.domain.model..` に広げた（**サブパッケージへ移した瞬間、ルールは「何も検査していない」状態になった**。`allowEmptyShould(true)` を使っていなければ、これは赤で気づける）

### 副次的に返した負債

`Cargo` が分割の import で 500 行を超え、Checkstyle が赤になった。**IT15 から 4 イテレーション持ち越していた D1**（「次に `Cargo` を触る IT で引取まわりを切り出す」）をここで返し、`claimCode` / `consignee` / `claimedAt` を `CargoClaim` にまとめた（498 行）。

## 代替案

### 分けない（現状維持）

**採らなかった。** 140 クラスが 9 つのパッケージに平らに並ぶ状態は、新しく読む人に構成要素の別を伝えない。

### `entities` を作らず、集約ルートと同じパッケージに置く

**カプセル化を失わずに済む案である。** 採らなかったのは、参照実装の構成に揃えることを優先したためである。**失ったものの節に書いたとおり、この判断には 4 メソッド分の実費がある。**

分類を直した結果、`entities` に残るのは 2 クラスだけになった。**この案を採っていれば実費は 0 だった**ことになる。次に同じ判断をする人は、まずこの 2 クラスを見てほしい。

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| すべてのパッケージに説明がある | **`PackageInfoPresenceTest`**（IT19 で追加） | `.java` を置いたディレクトリに `package-info.java` があること。**中身が正しいかは見ない** |
| トップレベルは BC と 1 対 1 | **`PackageStructureTest.すべてのクラスはBC集合のいずれかに属する`** | クラスの所属パッケージのみ。**サブパッケージの名前は見ていない**（`aggregates` を `roots` と書いても落ちない） |
| 共有カーネルは Location と ShipperId だけ | **`PackageStructureTest.共有カーネルはLocationとShipperIdのみ`** | `shared.domain.model..` 配下の単純名。**サブパッケージへ移した瞬間に「何も検査していない」状態になり、赤で気づけた** |
| BC 間でクラスを直接参照しない | **`PackageStructureTest.コンテキスト間でクラスを直接参照しない`** | Java のクラス参照のみ。パッケージが深くなっても効く |
| `entities` の生成・変更を、契約した相手だけが呼ぶ | **`EntityEncapsulationTest.エンティティの生成と変更は契約した相手だけが呼ぶ`**（IT20 で追加） | 上の「失ったもの」の表を**（型・メソッド・呼んでよい相手）の 3 つ組**でそのまま検査する。**型名だけでは判定しない**（`ExceptionOccurrence.raise` や `TrackingExceptionCommandService.resolve` を誤検知するため）。**`reconstruct` は対象外**（復元は infrastructure が行う。除外理由は検査の Javadoc に書いてある）。テストクラスも除外しない |

> **この代償は IT20 で返した。** 4 メソッドそれぞれについて、許可外から呼ぶと赤になることを
> 確かめてある（破壊検証）。
>
> **一般化して「集約ルート以外は呼べない」と書かなかった。** そう書くと `ProposedRoute.of` を
> 集約ルートへ移すことになり、探索と提案の分離が壊れる（`of` の 6 引数はすべて探索の途中でしか
> 作れない）。**規則を一般化することは規則の書き換えである。**

## 正典への反映

- `docs/design/architecture_backend.md` —— パッケージ構成の正典。**IT19 以前は「`domain/model` フラット」に一本化していた**ため、本 ADR はその一本化を取り消す判断でもある。同じ変更で更新した
- `docs/design/domain-model.md` —— 変更なし（**集約の境界そのものは動かしていない**）

# ADR-018: 一部入金を認めない

入金は「請求額どおりか、そうでないか」の 2 値として扱い、請求額と一致しない入金は記録せず拒む。

日付: 2026-08-10

## ステータス

承認済み

## コンテキスト

US23 は「決済機関との連携により入金確認ができる」「入金確認後、精算状態が『精算済』に更新され予約状態も『精算済』になる」と定めている。

`data-model.md` の `payment` テーブルは 1 請求書に複数行を持てる構造であり、
**一部入金を受け付ける形にも読める**。しかし US23 の受入基準は
**部分的な状態を一切要求していない**。「精算済」か、そうでないかである。

一部入金を認めると、次のものが芋づるで要る。

- 未入金額（請求額 − 入金額の累計）
- 入金の履歴（いつ・いくら・何回目か）
- 一部入金中の督促（いくら足りないかを伝える文面）
- 過入金の扱い（返金は精算の取り消しを伴う別の業務である）

いずれも**要求元が無い**。`release_scope.md` の原則 3（要求元のないものは作らない）に反する。

## 決定

**請求額と一致しない入金は記録せず拒む。**

- 集約（`Invoice.confirmPayment`）が請求総額との一致を検査する
- 不足も過入金も同じく拒む
- `payment` テーブルは**1 請求書 1 行**として使う

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| 請求額と一致しない入金を記録しない（不足も過入金も） | **ドメイン**（`Invoice.confirmPayment`）＋ `SettlementTest` | **集約のメソッド経由の入金**のみ。SQL で直接書き換えれば通る |
| `payment` は 1 請求書 1 行 | **DB の一意制約**（`V35__payment_one_per_invoice.sql`） | **DB の一意制約**（経路によらず効く） |
| **返金の扱い** | **守らない。** | **決めていない。** 業務そのものが存在せず、守る対象が無い |

## 根拠

- **差額の扱いは業務である。** 不足は再請求、過入金は返金であり、どちらも人が判断して起こす別の行為である。**システムが黙って受けると帳簿と合わなくなる**
- **構造が許すことと、業務が許すことは別である。** テーブルが複数行を持てることは、複数行を作ってよい理由にならない
- **後から緩めるほうが安全である。** 認めない状態から認める状態へは移せるが、記録してしまった一部入金を後から意味づけ直すことはできない

## 影響

### よくなること

- 「精算済」の意味が 1 つに定まる。予約を `SETTLED` にしてよいかを迷わない
- 督促の対象が「入金がまだ無い請求書」だけになり、金額の計算が要らない

### 気をつけること

- **実際に一部入金が届いたときは運用で受ける。** 経理担当者が荷主に連絡し、差額の入金を待つか、請求そのものを見直す
- 一部入金を認める要求が出たら、本 ADR を置き換える。そのときは未入金額・入金履歴・督促文面を**同時に**設計する

## 代替案

| 案 | 却下の理由 |
| :--- | :--- |
| 一部入金を受け付け、未入金額を持つ | 要求元が無い。未入金額・履歴・督促・返金が芋づるで要る |
| 金額を検査せず記録だけする | **帳簿と合わない記録が残る。** 「入金確認済」が金額の一致を意味しなくなる |
| 過入金だけ認める | 返金の業務が無い状態で過入金を受けると、返す手段の無い預り金になる |

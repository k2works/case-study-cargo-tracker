# ADR-020: 請求書に種別を持たせ、二重請求は予約と種別の組で防ぐ

請求書に `invoice_type`（`TRANSPORT` / `CANCELLATION`）を持たせ、
二重請求を防ぐ一意制約を `booking_id` から
`(booking_id, invoice_type)` へ組み替える。

日付: 2026-08-11

## ステータス

承認済み

## コンテキスト

US30 は「キャンセル料が発生する場合、状態に応じた料率で算定され、
精算に引き渡される」と定めている。UC22 の拡張 4a1 は
「UC17 に引き渡す」と書くが、**UC17 は輸送料金の算出である**。

いまのスキーマは US30 を実装できない。V1 は次のように書いている。

```sql
-- UNIQUE 制約で二重請求を防止する
booking_id UUID NOT NULL UNIQUE,
```

**この判断は正しかった。** ただし、当時の世界に請求書は 1 種類しかなかった。
輸送料金の請求書が既にある予約には 2 枚目が入らないため、
**輸送中にキャンセルした荷主へキャンセル料を請求する手段がシステムに無い**。
イテレーション計画の構造的な穴 X1 であり、着手前の検証で見つかった。

取りうる形は 3 つあった。

| 形 | 問題 |
| :--- | :--- |
| キャンセル料を既存の請求書に**行として足す** | ADR-016 で明細行を持たないと決めている。加えて、輸送料金の請求書は既に発行・入金済みでありうる（**確定後の金額を動かせない**） |
| キャンセル料を**別テーブル**にする | 発行・支払期限・入金確認・督促がすべて二重に要る。US23 で作った仕組みを丸ごと写すことになる |
| 請求書に**種別**を持たせる | 一意制約の意味を変える必要がある |

## 決定

**請求書に種別を持たせ、一意制約を `(booking_id, invoice_type)` に組み替える。**

- `InvoiceType`（`TRANSPORT` / `CANCELLATION`）を Billing のドメインに置く
- `Invoice.cancellationFee(...)` はキャンセル料の請求書を作る。
  **`calculate` を通さない**（あちらは荷主種別から割引を決める道であり、
  通せば「割引 0% の法人」という嘘の記録が残る）
- `InvoiceRepository.findByBookingId` は**種別を渡させる**。予約だけでは 1 枚に定まらない
- 請求対象一覧の「請求済み」判定は `TRANSPORT` だけを数える。キャンセル料を請求したことは「輸送料金を請求済み」を意味しない

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| 予約と種別の組ごとに請求書は 1 枚 | **DB の一意制約**（`uq_invoice_booking_type`） | **DB の一意制約**（経路によらず効く） |
| 種別は 2 値のいずれか | **DB の CHECK 制約**（`chk_invoice_type`） | **DB の CHECK 制約**（実 PostgreSQL 上） |
| キャンセル料に割引・調整を適用しない | **ドメイン**（`Invoice.cancellationFee`）＋テスト | **集約のメソッド経由の生成**のみ |
| 料率 0 でキャンセル料の請求書を作らない | **ドメイン**（`cancellationFee` が拒む）＋テスト | **集約のメソッド経由の生成**のみ |
| 列が無かったころの行は輸送料金として読める | **ドメイン**（`InvoiceType.ofRestored`）＋テスト | **復元の経路**のみ（新規受け入れの経路とは別に検査する） |

## 根拠

- **二重請求の防止を捨てていない。** 防ぐ対象を「予約ごとに 1 枚」から
  「予約と種別の組ごとに 1 枚」へ狭めただけであり、
  輸送料金の請求書は依然として予約に 1 枚しか作れない
- **金額の性質が違うものを混ぜない。** 輸送料金は運んだことへの対価、キャンセル料は運ばなかったことへの対価である。同じ行に混ぜると、月次の締めで「輸送で得た売上」を数えられない
- **US23 の仕組みをそのまま使える。** 発行・支払期限・入金確認・督促はどちらの請求書にも同じように要る。別テーブルにすると、その全部を 2 度書くことになる
- **ADR-017 と同じ形である。** あちらは「料金の状態」と「支払いの状態」を混ぜないと決めた。ここは「請求書の進み方」と「請求書が何の対価か」を混ぜない

## 影響

- **マイグレーションが方言に分かれる。** V1 は制約に名前を付けずに書いたため、
  名前は DBMS が自動で決める（PostgreSQL は `invoice_booking_id_key`、
  H2 は `CONSTRAINT_74D6` のような通し番号）。
  名前を書き写せば片方でだけ落ちるため、**名前ではなく形で探して落とす**
  （「invoice の UNIQUE 制約のうち、列が `booking_id` 1 つだけのもの」）。
  `h2/` に初めてファイルが増えたのはこの理由であり、
  **スキーマが分岐したわけではない**
- 既存の行はすべて `TRANSPORT` として埋まる（キャンセル料はこの列と同時に生まれた）
- `findByBookingId` の呼び出し側は種別を渡すよう変わる（3 か所）

## 代替案

- **`booking_id` の一意制約を単に外す。** 却下。輸送料金の請求書を 2 枚作れてしまい、V1 が防いでいたものが消える
- **キャンセル料を金額 0 の調整として輸送料金の請求書に載せる。** 却下。確定・発行済みの請求書は動かせず（US21 の判断）、そもそも符号が逆である

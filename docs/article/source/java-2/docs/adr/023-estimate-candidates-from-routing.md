# ADR-023: 見積のルート候補は Routing の探索から作る

見積のルート候補を固定値のスタブで作らず、ACL ポートで Routing の探索に問い合わせて作る。

日付: 2026-08-12

## ステータス

承認済み

## コンテキスト

`domain-model.md` の Estimation Context は、ビジネスルール 6 として次のように書いていた。

> ルート候補はスタブ実装（固定値）で生成される。将来、外部ルーティングサービスとの連携時に置換予定

この記述は **Routing にまだ探索が無かった時期**のものである。IT18（US01）で見積を実装するにあたり、2 つの前提が崩れていることが分かった。

- **「将来の外部ルーティングサービス」は来ない。** ADR-006 で外部システムとは HTTP 連携しないと決めており、経路算出は内部シミュレーションで代替すると定めている
- **Routing には本物の探索がある。** US08（IT4）で `RouteSearchService` が入り、実在する航海から候補を推奨順で返す。概算費用も `FreightEstimator` が算出する（ADR-008）

**固定値を返す見積は、画面は動くのに数字が現実と無関係である。** 見積は荷主に渡る数字であり、営業担当者はそれを見て予算と納期を伝える。実在しない便の所要日数と費用を「概算」として提示することになる。

これは「動作するきれいなゴミ」（`docs/reference/よいソフトウェアとは.md`）そのものである。**技術的には完成しているが、誰の役にも立たない。**

## 決定

**見積のルート候補は、ACL ポート経由で Routing の探索から作る。**

- Estimation が `RouteCandidateSource` ポートを**所有する**（`estimation/application/internal/outboundservices/acl/`）
- アダプタは提供側に置く（`routing/infrastructure/acl/`）。既存の `RoutableBookingsAdapter` と同じ形である
- **BC 間で型を渡さない。** アダプタが Routing の `ProposedRoute` を Estimation の値に変換する（ADR-005 / ADR-012）
- 依存の向きはコンテキストマップの `estimation ..> routing : 航海スケジュールを参照` と一致する

### 候補が 0 件のときを区別する

US01 の受入基準 5 は「希望期限に間に合うルートが存在しない場合、その旨が通知される」と定めている。**「便が無い」と「期限に間に合わない」は別の事態であり、営業担当者が次に取る行動が違う。**

| 事態 | 営業担当者が次にすること |
| :--- | :--- |
| その区間を走る便が無い | 別の港を提案する・他社を当たる |
| 便はあるが期限に間に合わない | 荷主に期限の延長を相談する |

**まとめて「候補がありません」と出すと、どちらなのか分からない。** 区別して伝える。

### 期限切れは保存しない（ADR-019 との違い）

見積の `EXPIRED` は**読み出しのたびに導出する**。判定の形（画面を開いたときに・業務のタイムゾーンの今日で・当日は含めない）は ADR-019 と同じだが、**ADR-019 が状態を永続化するのに対し、こちらは永続化しない。**

| | ADR-019（請求書の超過） | 本 ADR（見積の期限切れ） |
| :--- | :--- | :--- |
| 状態が変わったこと自体に業務上の意味があるか | **ある**（督促の対象になる。誰にいつ督促したかを追う） | **無い**（期限を過ぎた見積は、ただ使えないだけである） |
| 状態に紐づく業務アクションがあるか | ある（督促の記録） | 無い |
| 永続化 | **する** | **しない** |

**保存しない状態は、保存し忘れという故障モードを持たない。** 一方で、保存する状態は「誰がいつその状態にしたか」を追える。見積の期限切れに追うべき履歴は無い。

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| 見積の候補が実在する便から来ている | **`EstimateRouteCandidateTest`**（IT18 で追加） | 実 PostgreSQL 上で、**登録した航海の番号が候補に出ること**。固定値なら落ちる |
| 「便が無い」と「期限に間に合わない」を区別する | **`EstimateRouteCandidateTest`** | 両方の状況を作り、**異なる案内が出ること**。片方だけでは常に同じ文言でも緑になる |
| BC 間で型を渡さない | **`PackageStructureTest.コンテキスト間でクラスを直接参照しない`** | Java のクラス参照のみ（ACL のパッケージは除外）。**SQL の越境は見ない**（ADR-015） |
| ポートを Estimation が所有する | **`PackageStructureTest`**（パッケージ構成） | クラスの所属パッケージのみ。**アダプタの置き場所そのものは見ていない** |
| 概算であることを画面に明示する | **守らない。** | **検査の外。** 表示文言を検査しておらず、ラベルを消しても落ちない（ADR-008 と同じ穴） |

## 影響

### ポジティブ

- **見積の数字が現実と繋がる。** 実在する便の番号・所要日数・概算費用が出る
- 探索の規則が 1 か所に留まる。便の追加やダイヤ変更が見積にもそのまま効く
- ADR-006 と矛盾しなくなる（来ない「将来の外部サービス」を前提にした記述が消える）

### ネガティブ

- **Estimation が Routing に依存する。** BC を別プロセスへ分けるときにポートの実装が要る（ただしこれは ACL を通しており、動かすのはアダプタだけで済む）
- **Routing の探索が変わると見積の数字も変わる。** これは意図どおりだが、「先週の見積と今日の見積で数字が違う」ことは起こりうる。**見積は保存した候補を表示する**（`route_candidate` テーブル）ため、作成済みの見積が書き換わることはない

## 検討したが採らなかった案

| 案 | 却下理由 |
| :--- | :--- |
| 固定値のスタブのまま（現記述） | 画面は動くのに数字が現実と無関係になる。ADR-006 により「将来の置換」も来ない |
| Estimation に独自の簡易探索を作る | 探索の規則が Routing と 2 か所に分かれる。便の追加・ダイヤ変更で**見積だけが古くなる** |
| Routing のクラスを直接参照する | ADR-012（BC 間の参照は ACL ポートのパッケージだけを通る）に反する |

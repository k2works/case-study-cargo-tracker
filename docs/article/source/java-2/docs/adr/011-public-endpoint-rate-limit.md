# ADR-011: 公開エンドポイントの防御を単一プロセス内のレートリミットで行う

認証を持たない相手へ開くエンドポイント（`/public/**`）の過剰なアクセスを、**アプリケーションのプロセス内で数えて制限する**。分散カウンタは導入しない。

日付: 2026-08-08

## ステータス

承認済み

## コンテキスト

US18（追跡情報を照会する）で、**本システムで初めて認証を持たない相手に画面を開いた**。

`/public/tracking` は荷主が取引先へ URL を転送する前提の画面であり、認証を課すとその価値が消える。一方で、この入口には 2 つの性質がある。

1. **追跡番号は推測できる形をしている。** `TRK-YYYYMMDD-NNNN` は日付＋連番であり、日付を決めれば連番は 4 桁しかない
2. **引き当てられたかどうかが応答から分かる。** 見つかれば状態が表示され、見つからなければメッセージが返る

存在の有無を区別できないメッセージにする対策は実装済みだが、**それは「どの番号か」を隠すだけであり、総当たりそのものは止まらない**。番号を順に試せば、実在する貨物とその輸送状態を端から収集できる。

`non_functional.md` §2.2 は「追跡 API は荷受人: 100 RPS/IP のレートリミットを設定する」と定めていたが、**IT6 終了時点で実装は存在しなかった**（`grep -rn "RateLimit"` が 0 件）。`ui_design.md` は 429 到達時の画面まで定めており、**設計だけが先行していた**。

### 選択肢

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| A | 実装しない（IT8 以降へ送る） | 公開エンドポイントを防御なしで開くことになる。**US18 と同時にしか判断できない** |
| B | **単一プロセス内で数える** | N 台構成では実効上限が N 倍になる。基盤の追加は不要 |
| C | 分散カウンタ（Redis / ElastiCache） | 上限を正確に守れる。**基盤（`architecture_infrastructure.md`）の判断が先に要る** |
| D | ALB / WAF のレート制限 | アプリを変えずに済む。**ローカル・開発環境では働かない**ため、動作を確かめられない |

## 決定

**B（単一プロセス内で数える）を採る。**

- `/public/**` に対して送信元 IP ごとに窓を持ち、窓の中の回数が上限を超えたら 429 を返す
- 上限と窓の長さは設定で外部化する（テストで到達できる値にするため）
- 429 には `Retry-After` ヘッダと、再試行の目安を書いた画面を返す

### N 倍になることを承知で採る理由

**「正確に守れないなら入れない」は、この場合には成り立たない。**

現状は上限が無限である。N 台構成で実効上限が N 倍になったとしても、無限よりは小さい。総当たりの速度を落とすことに意味があり、**完全に止めることだけが目的ではない**。

ただし**この限界を記録しないなら、入れないほうがまだよい**。記録が無ければ、次に読む人は「レートリミットがあるから守られている」と信じる。**設定したことと働いていることは別であり、働いていることと十分であることもまた別である。**

### ヘルスチェックを対象にしない

`/actuator/health` は**レートリミットの対象にしない**（`non_functional.md` §3.4）。

過負荷時にヘルスチェックまで制限されると、liveness プローブが 503 を返して ECS がタスクを再起動する。再起動により残ったタスクの負荷がさらに上がり、次のタスクも 503 を返す。**負荷を減らすための防御が、負荷を増やす再起動ループを引き起こす。**

他の実装（`flix/take-1` IT7）でこの故障モードを実測している。`flix/take-1` は IT3 で同じ教訓を得ていたにもかかわらず、IT7 でセマフォを入れた際に同型の障害を再現した。**横断的な防御を足すたびに、除外が要る対象を数え直す。**

除外は業務画面にも及ぶ。認証で守られており、ここまで制限すると繁忙期に現場が締め出される。

### 送信元ごとに数える

全体で 1 つの数え方にすると、**誰か 1 人の総当たりで全員が締め出される**。攻撃者が正規の利用者を締め出せる形は、防御ではなく攻撃の手段になる。

## 何がどこで守るか

| 守るもの | 守り手 | 対象範囲（何を見ているか） |
| :--- | :--- | :--- |
| `/public/**` に送信元 IP ごとの上限が効く | **`PublicRateLimitTest`** | **単一プロセス**で、テストが実際に叩いた経路のみ |
| **ヘルスチェックを対象にしない** | **`PublicRateLimitTest`**（`/actuator/health` と `/actuator/health/liveness` を明示的に叩く） | `/actuator/health` と `/actuator/health/liveness` の **2 経路**のみ。他の actuator 経路は見ていない |
| 業務画面を対象にしない | **`PublicRateLimitTest`** | テストが叩いた**業務画面**のみ |
| 上限と窓が設定で外部化されている | **設定値**（`application.yml`）＋ テストが到達できる値を使う | **設定値が読まれること**のみ。値の妥当性は見ない |
| **N 台構成では実効上限が N 倍になる** | **守らない。** | **守れない。** 単一プロセスで数える構造そのものの限界であり、検査で塞げない |

## 影響

### 良い影響

- 公開エンドポイントに上限ができ、総当たりの速度が落ちる
- 除外が効いていることをテストで固定した（除外を外すと 3 件が赤になることを実測）
- 上限を設定で変えられるため、運用中に調整できる

### 悪い影響・残る課題

| # | 内容 | 扱い |
| :--- | :--- | :--- |
| 1 | **N 台構成では実効上限が N 倍になる** | 基盤（Redis 等）を決めてから C 案へ移る。本 ADR の改訂候補 |
| 2 | ~~**プロキシの背後では送信元 IP が ALB のものになる**~~ | **IT8 で解消した**（下記「2026-08-08 の改訂」） |
| 3 | 窓の記録がプロセス内に残る | 窓を跨いだ入口で捨てる。**防御が別の障害（メモリ枯渇）を作らないため**である |
| 4 | 再起動で数え直しになる | 上記 1 と同じ性質であり、同じく C 案で解消する |

**課題 2 は本番で意味を持つ。** ALB の背後では全リクエストが同じ送信元に見え、上限が全体で共有される形になる。これは「誰か 1 人で全員が締め出される」形そのものであり、**本番投入前に解消しなければならない**。

## 2026-08-08 の改訂（IT8）: 信頼できるプロキシの段数を設定で持つ

**`ForwardedHeaderFilter` は使わない。** あれは「ヘッダを信じてリクエスト全体の見え方を差し替える」仕組みであり、リンクの生成やリダイレクトの絶対 URL にも影響する。**レートリミットが数える単位を決めたいだけ**であり、影響範囲が広すぎる。

代わりに `cargotracker.public-rate-limit.trusted-proxy-count` を置き、**その段数だけ `X-Forwarded-For` を右から遡った値**を実クライアントとして数える。

- **既定は 0 = ヘッダを一切信用しない。** 設定を忘れた環境が安全側に倒れる
- **右から数える。** ヘッダは「クライアントが名乗った値 + 各プロキシが追記した値」の並びであり、**左端は偽装できる**。信頼した段数だけ遡った位置が、偽装できない最も左の値になる
- ヘッダが無い・段数に足りないときは接続元にたおす。**プロキシ設定の誤りで制限が外れる**ほうが、厳しく数えるより危険である
- 段数は**環境の事実**であり、コードにも既定値にも書けない。環境ごとの設定で上書きする

**壊して確かめた**: 実装を左端採用に変えると「偽装された左端の値では回避できない」が赤になる。左右のどちらを採るかをテストが判別する。

**課題 1（プロセス内でしか数えない）は残る。**

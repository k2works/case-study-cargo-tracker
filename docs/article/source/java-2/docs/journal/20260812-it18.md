# 2026-08-12 IT18（見積コンテキスト）

## この日やったこと

US01「輸送見積を作成する」を実装し、**最後の未実装だった Estimation Context** を
立ち上げた。これで設計上の 8 BC がすべてコードとして存在する。あわせて IT17 の
ふりかえりで「育つ負債」と判定した C1（委譲アクセサ）・C2 を返した。

## 判断の記録

### ルート候補は自前で持たず、Routing に聞いた

見積は「この条件でいくらか」を答えるが、そのためには経路の候補が要る。
Routing には既に経路探索がある。**見積の中に 2 つ目の探索を作れば、同じ問いに
2 つの答えが出る**——荷主が見た見積の経路と、経路設計者が割り当てる経路が違う。

Estimation がポート（`RouteCandidateSource`）を持ち、Routing 側にアダプタを置いた。
ADR-023 として記録した。

### 期限切れの見積は保存しない、を ADR-019 と区別して書いた

ADR-019 は「期限超過は画面を開いた時点で判定する」と決めている。見積では逆に、
**期限に間に合う候補が無い場合はその理由（便が無い / 期限が厳しい）を保存する**。

同じ「期限」という言葉で反対の扱いをするので、ADR-023 に両者を並べた表を入れた。
書かなければ、次に読む人がどちらかに寄せてしまう。

### 候補が無いことを、次の行動に繋げた

「該当する便がありません」だけでは荷主は何もできない。理由ごとに次の一手
（別の港を検討する / 期限を延ばす）を出し分けた。

## 詰まったこと

### 「便がありません」のテストが、別の理由でも緑になっていた

破壊検証で見つけた。2 つの理由メッセージがどちらも「便」を含むため、
**片方を壊してももう片方の文字列で通ってしまう**。判別できない検査だった。

次の行動（「別の港」「期限の延長」）で判定するよう書き直した。

### 一覧のダッシュボードカードを消してもテストが通った

navbar に同じ文字列があった。`navbarOf()` で navbar を切り離してから
本文だけを見るようにした。

### H2 スモークの穴を 2 IT 続けて作った

IT17 の是正一覧、IT18 の見積一覧。どちらも実 DB のテストは緑で、
ローカル起動（H2）だけが落ちる形。**同じ形の穴を続けて作ったので、
ふりかえりの Try に載せた。**

## 学び

**記録した負債の数は、5 回連続で実態より小さかった。**

| 項目 | 記録 | 実測 |
| :--- | ---: | ---: |
| C2（貨物フィクスチャ） | 7 | 39 |
| C3（レコード） | 2 | 21 |
| R8（検査） | 8 | 10 |
| R7（列の多い一覧） | 1 | 13 |
| **C1（委譲アクセサ）** | **34** | **249** |

C1 は「34 個」として起票したが、着手時に数えたら 249 だった。**見積もりの精度の
問題ではない。数えずに書いていた。** 次からは起票のその場で数えた数を書く（Try T2）。

そして C1 は**育っていた**——レコードを分けるたびに委譲が増える形だったので、
落とし続ければ増え続けた。落とす順序は見積もりではなく「次の IT で対象が増えるか」
で決める。

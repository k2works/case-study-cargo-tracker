# 2026-08-09 開発ジャーナル

デプロイから始まり、IT11（US28 誤配 / US29 通関、10SP）と IT12（US35 引取確認コード / US36 訂正・取り消し、5SP）を計画からクローズまで通した。**Release 1.1（15 ストーリー・49SP）が完成した日である。** この日の裏テーマは「**緑であることは、守られていることの根拠にならない**」だった。ArchUnit が緑でも SQL は越境し、破壊検証が全件赤でも作らなかった守りは見えず、ローカルが緑でも CI は 3 回落ちた。

## ハイライト

- **Release 1.1 が完成した。** 累計 96SP。12 イテレーションの平均は 8.0SP（採用値 8SP と一致）
- **ArchUnit を 1 件も破らずに BC 間の結合が増えていた。** SQL の JOIN は Java の依存グラフに映らない。検査を作って測ったら、レビューの指摘 2 本に対し**実際は 9 本あった**（ADR-015）
- **3 イテレーション繰り越していた 4 件（C6 / C11 / C12 / C16）に決着をつけた。** IT12 の返済枠はストーリー本体と同規模（27h / 30h）だったが、8 タスク 12 件をすべて返し、1 つも落とさなかった
- **破壊検証 21 件が全件赤（空振り 0）でも、クローズ前の自己レビューが高 3 件を見つけた。** 破壊できるのは「作った守り」だけである
- **並列レビューが 25 分応答せず、フォールバック（逐次シミュレーション）に切り替えた。** その判断とリスクをレビューレポートに明記した

## Skill 実行の時系列

### 1. `operating-deploy` — アプリとドキュメントのデプロイ

Heroku Container Registry へアプリとドキュメントサイトを配置し、URL を開いて確認した。

### 2. `opening-iteration` — IT11 の開始準備

前 IT のふりかえり Try を計画に織り込み、`validating-iteration-plan` / `validating-design` を通してから GitHub とインデックスへ反映した。**返済枠 7 件を IT 序盤の独立コミットに割り当てる**形（5 IT 連続）を維持した。

### 3. `orchestrating-development` — IT11 の実装（US28 誤配 / US29 通関）

**ADR-014 を起票した。** ダッシュボードの件数を共有のダッシュボードが全 BC のクエリサービスから集めると、BC が増えるたびに 1 か所が太る。各 BC が `@ControllerAdvice` で自分の件数を載せる形にした。

**守りを数え上げてから壊した**（IT10 の Try T1）。22 件を機械的に数え、**3 件が空振り**した。IT10 は「自分で選んだ 10 件が全部赤」だったが、選ばなかった 3 件が壊れていた。**選び方を変えたら、見つかるものが変わった。**

### 4. `closing-iteration` — IT11 のクローズ

レビューが**高優先度 14 件**を出し、10 件を IT 内で対応した。うち 3 件は「**コメントが実装より多くを主張している**」形だった（「やめる側も同じ入力を持って戻る」と書いて追跡番号しか持ち回っていない、など）。これが IT12 の Try T1「『〜する』と書いたコメントは、その IT のうちに壊して赤にする」になった。

### 5. `opening-iteration` — IT12 の開始準備

返済枠が 27h、ストーリー本体が 30h。**同規模になった時点で「落とす順序」を計画に先に書いた**（0-8 → 0-7 → 0-5）。結果として 1 つも落とさずに済んだが、**判断を先送りしなかったことが効いた**。

### 6. `orchestrating-development` — IT12 の実装

#### 返済枠を最初の 8 コミットで完済した（T8。6 IT 連続）

US35 の着手は 9 コミット目である。

**C28（SQL の越境）が本 IT で最も学びが大きかった。** IT11 のレビューは「BC をまたぐ SQL が 2 本」と指摘した。検査を作って走らせたら 9 本あった（7 本は既存）。1 本を結果整合の写しで解消し、8 本を理由つきで登録した。**指摘の件数は「見つかった数」であって「ある数」ではない。**

フィクスチャは**実コードの形**（相関サブクエリ・複数 JOIN・別名付き）で作った。「最小の違反例」だけだと、メタテストが緑でも実コードの違反を見逃す。

#### Checkstyle が 3 回、設計の合図を出した

| 制限 | 対応 |
| :--- | :--- |
| `CorrectionRequest.reconstruct` が 13 引数 | `Details` / `Requester` / `Decision` に分割 |
| `SecurityConfig.filterChain` が 161 行 | 荷役まわりの規則をメソッドへ抽出 |
| `Cargo.reconstruct` が 8 引数（IT12 前半） | 流れるような `withClaimCode` を追加 |

**回避策を書かず、構造を変える契機として扱った**（IT7 から続く扱い方）。

#### E2E がユニット・統合をすり抜けた欠陥を見つけた

`critical-path` の E2E が C29（通関の要否）で落ちた。ユニットも統合も緑だったが、**画面を通した流れは荷降しから直接引取へ進んでいた**。「テストが緑」と「業務が通る」は別である。

### 7. `closing-iteration` — IT12 のクローズ

#### 並列レビューが応答しなかった

5 つの XP 視点を並列起動したが、**25 分待って 1 件も返らなかった**。`developing-review` のフォールバック（逐次シミュレーション）に切り替えた。**クローズを止め続けるより、検出力の低下を明記して進むほうがよい**と判断した。

#### 原因はクローズ後に分かった（追記）

**同名のエージェントが既に存在したため、私が起動したレビューは別名になり、催促は旧エージェント（IT7 担当）へ届いていた。** 返ってきたのは IT7 の所見である。

突合したところ **10 件中 9 件は後続イテレーションで返済済み**だった。残る 1 件（公開追跡の問い合わせ先がメールのみ）は、マニュアルが「連絡先は運用開始時に記載する」と定めているため、**運用が決めるべきことをコードで先取りしない**と判断して持ち越した。

**指摘のうち 2 件が、そのまま後続の設計になっていた。**

- 「案内だけ出して受け口が無いのは、これまで繰り返してきた形です」→ **US36（訂正・取り消し）の受け口**
- 「公開追跡に荷主名・品名・重量を足す提案が出たら止めてください」→ 個人情報を**型として持たない**設計と、応答本文を検査するテスト。US35 の引取確認コードも公開追跡には渡していない

**名前で相手を指すときは、その名前が誰を指しているかを確かめる。**

#### 自己レビューが高 3 件を見つけた

| # | 内容 |
| :--- | :--- |
| H1 | **訂正を承認しても記録が何も変わらない。** ドメインに `correcting()` はあったが、画面が直す内容を集めず、承認も適用していなかった。**マニュアルは「訂正は記録の中身を直します」と書いていた** |
| H2 | **記録を直す前に「承認済み」を書いていた。** 副作用が書けなくてもイベントを発行していた |
| H3 | **引取確認コードが経路設計者・追跡管理者にも見えていた。** どちらも引き渡しに関わらない |

**H1 は IT11 の Problem がドキュメントで再発した形である。** IT12 の Try T1 でコメント 10 件を数え上げて壊したが、**マニュアルを数え上げの対象に入れていなかった**。

#### クローズ中に CI が 3 回赤くなった

| # | 原因 | 気づき方 |
| :--- | :--- | :--- |
| 1 | `spotbugsTest` を見ておらず `spotbugsMain` だけで緑と判断 | CI のログ |
| 2 | **timestamptz を文字列で比較**し、CI（UTC）でだけ落ちた | CI のログ |
| 3 | SonarQube の同じ種類の指摘が、新しく書いた行で再発 | Quality Gate |

2 番目は 6 IT 前から記録している「業務日付を UTC で判断しない」の系である。**書くときには気づかず、CI が落ちてから思い出した。**

#### マニュアルの節番号を繰り下げてリンク 7 件を壊した

さらに、中黒を含む見出しのアンカーを**自分の推測で**書いた。`mkdocs build` は最初から「アンカーが無い」と警告していた。**生成する道具に聞けば済んだ。**

## 学び

- **検査が緑であることは、守られていることの根拠にならない。** ArchUnit と JIG は Java の依存グラフしか見ない。SQL・テンプレート・設定ファイルは検査の外にある。**検査そのものに「何を守っているか」を語らせる**（ADR-015 とそのメタテスト）
- **破壊検証には構造的な死角がある。** 壊せるのは「作った守り」だけで、**作らなかった守り**は数え上げの対象にならない。「21 件全部赤」は「守りが 21 件あって全部効いている」ことしか言っていない
- **宣言と実装の食い違いは、対象を変えて再発する。** IT11 はコメント、IT12 はマニュアルだった。数え上げの対象を「コード内のコメント」に限定すると、外側のドキュメントが同じ穴になる
- **人の目で数えた件数を総数だと思い込まない。** レビューの「2 本」に対し、機械的な検査は 9 本を見つけた
- **壊すタイミングが空振り率を変える。** IT11 は実装をまとめてから数え上げて 3 件空振り、IT12 は各コミットの中で「作った直後に壊す」を行って空振り 0 件だった
- **制限に当たったら回避策を書かず、構造を変える。** Checkstyle の引数制限・行数制限は 3 回とも設計の合図だった
- **ローカルの緑と CI の緑を混同しない。** 静的解析は本体とテストで別に走り、時刻の表記は JVM のタイムゾーンで変わる。**クローズ前は `TZ=UTC ./gradlew check` で確かめる**
- **静的解析の指摘は「同じ種類」を横断で潰す。** 1 件だけ直すと、次に書いた行で同じ指摘が出て往復が増える
- **アンカーの形は推測せず、生成する道具に聞く。** `mkdocs build` の警告を 0 にしてからコミットする
- **並列レビューが使えないときは、観点を明示的に切り替えて逐次で読む。** とくに「利用者視点でこの操作をしたら何が起きるか」を最後まで追う（H1 はこれで見つかった）
- **名前で相手を指すときは、その名前が誰を指しているかを確かめる。** 同名の担当が既にいると、催促は別人に届く。**返ってきた答えが噛み合わないときは、まず宛先を疑う**
- **「未達が無い」と「何も残っていない」は違う。** Release 1.1 は全ストーリー完了だが、**意図的に範囲を絞った 6 項目**（ADR-006 による通知の扱い、訂正の範囲、危険物クラスの検査深度、荷主紐付けの設定手段）を名前で残した

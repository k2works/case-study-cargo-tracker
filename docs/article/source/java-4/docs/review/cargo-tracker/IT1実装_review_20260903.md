## 視点別の所見

### programmer（コード品質）

集約・投影・クエリの責務は分かれており、不変条件は集約側にあります（`Shipper` の登録時検査）。今日の変更で色トークンを `styles.ts` に集約し、画面ごとにばらついていたクラス指定を 1 か所にしました。`catch` は概ね狭く、`ShipperDataCipher` の `catch (Exception)` は暗号処理の実装差を吸収する意図が書かれています。

指摘は L1・M6 の 2 件で、いずれも動作に影響しません。

### tester（テスト品質）

**デモ項目 7 件すべてに検査があります。ただし 7 件目は当初の記述が誤りでした**（H5）。デモ項目 7 の機能は `routes.test.tsx` の全ロール × 全ナビ項目の往復検査で固定されていますが、それを名前に掲げていた E2E は、その内容を検証していませんでした。

H1・H2 は品質ゲート側の欠陥ですが、**発見の筋はテスト観点**です。「緑に見えるが何も見ていない」検査は、テストコードだけでなく検査の配線にも生まれます。

### architect（設計整合）

ADR-0001 の決定 1〜6 は検査に落ちています（`BuildConventionTest`・`ArchRulesAreEffectiveTest`・`AuthIsNotEventSourcedTest`・`ContractEventGoldenTest`）。決定 5 の第 7 項だけが未実施で、ADR にもその旨が書かれています。

H3 は「検査を当てる範囲」の欠陥でした。規則そのものは実コードと同じ形の違反フィクスチャで赤を確かめており（タスク 2.2）、**規則の質ではなく適用範囲の担保**が弱い状態でした。

### technical-writer（ドキュメント）

手順書のコマンドは実在するタスク名と一致します（`k8s:setup`・`k8s:wait`・`portal:artifacts` を実行して確認）。マニュアルは 5 章で索引・`mkdocs.yml` と一致します。ドキュメントポータルから設計・ADR・運用手順・マニュアル・JIG・ER 図に到達できます。

## 高優先度の指摘と対応

### 1. 候補 20 件の打ち切りが「並べる前」に効いていた（tester・programmer）

**本 IT で最も重い欠陥です。** 目的地に着いた経路を 20 件見つけた時点で探索を止め、そのあとで推奨順に並べていました。返るのは「推奨順の上位 20 件」ではなく**「先に見つかった 20 件」**で、US08 §受入基準 4（所要時間の短い順）と §受入基準 5（直行便を優先）が破れます。

全候補を集めてから並べ、`limit(MAX_CANDIDATES)` を最後に効かせる形へ直しました。打ち切りは乗り継ぎの深さで持ちます。21 件以上の候補を持つグラフで「直行便が 1 位に出る」テストを足し、**元の実装に戻すと赤になる**ことを確かめています。

**この症状は、クラスタ E2E で一度実測していました。** `cluster.spec.ts` のコメントに「既存の 16 日の便 20 件に押し出された」と書きながら、原因を「同着の並び」と読んでテスト側を回避したため、実装の欠陥として残りました。ADR-0007 に「決定 2 の訂正」として、この誤診の経緯ごと記録しています。

### 2. 「知らない港は断る（422）」が実装されていなかった（architect・programmer）

`RoutingQueryHandler` の javadoc と `architecture_backend.md` の規則表が「知らない港・種別は断る」と書いていましたが、断っていたのは貨物種別だけでした。`Location.of()` は UN/LOCODE の**書式**しか見ないので、書式の正しい未登録港（`JPXXX` など）はそのまま探索に入り、**候補 0 件の正常応答**になります。港の打ち間違いは条件を変えても直らない入力誤りなので、画面は「到着期限を延ばすか、経由できる港を増やす」と案内し続けます。

投影に現れる港かどうかを見る判定を置き、未登録なら 422 で断るようにしました。統合テストで固定しています。

### 3. `findEdgesFrom` の javadoc が実装と矛盾していた（programmer）

「一覧と同じ `visible` を共有する」と書いてありましたが、XML 側は条件を書き直しており、しかもその XML のコメントは「**航海の出港ではなく区間の出発**で見る」と、意図的に違う判断であることを説明していました。javadoc が「書き直すな」と警告している事態が、その javadoc の直下で起きていた形です。実態（共有していないこと、なぜ違う判断なのか）を書く形に直しました。

### 4. 経路を確定したのに旅程が出ないことがある（user-representative）

確定後 S22 へ飛びますが、旅程は `routingStatus === 'ROUTED'` のときだけ問い合わせ、その予約の取り直しは「202（反映中）のときだけ」でした。確定前に予約は既に `ready` なので、投影が数秒遅れると `ROUTING_REQUESTED` のまま読み、旅程の見出しごと現れません。マニュアル 09 は「旅程の表に区間が積む順に出ます」と書いているので、**失敗したと読んでもう一度確定を押し、今度は状態の誤りで断られます**。

`ROUTED` になるまで取り直し、待っているあいだは「経路の反映を待っています」と出すようにしました。

### 5. マニュアル 09 と画面が、同じ状況で逆のことを言っていた（technical-writer）

候補 0 件で打ち切り警告が出たとき、マニュアルは「条件を変えても候補は増えません」、画面は「条件を絞ると別の候補が出ることがあります」と書いていました。実装を読む限りマニュアルが正しく、画面文言が誤りです。画面を 3 つの状態（0 件 / 0 件かつ打ち切り / 候補ありかつ打ち切り）で出し分け、両方を赤で固定しました。

### 6. 05 章のキャプチャに、IT5 で足したものが写っていない（technical-writer・user-representative）

**唯一の未対応の高です。** 05 章に新設した「旅程」「最終更新／修正履歴」が、キャプチャ（仮受付・未修正の予約）に写っていません。撮り直すには「経路確定済みかつ一度修正した予約」の見本データが要り、キャプチャ生成 spec の見本データ設計そのものを変えることになります。**IT6 で対応します**（マニュアル index.md が「古いキャプチャは、書いていないことよりも読者を迷わせます」と定めている方針に反する状態なので、先送りの理由をここに残します）。

### 7. 航海キャンセルに「今どれだけ巻き込むか」が出ない（user-representative）

**部分対応です。** 確認文は「経路候補に出なくなり、スケジュールも直せなくなります」だけで、その航海で既に経路を組んだ貨物の件数も予約番号も出ません。キャンセル後にその貨物へ辿り着く導線もありません（`VoyageCancelledEvent` は routingms 内で完結しています）。

件数と導線を出すには、bookingms 側で `VoyageCancelledEvent` を購読して「この航海に乗る予約」を引ける読み口が要ります。**IT6 の US11（経路紐付）と同じ範囲なので、そちらへ送ります。** 本 IT ではマニュアル 07 に「既に経路を組んだ貨物は自動では戻りません」という注意を足すに留めました。

## 本 IT のレビューから引くもの

**受入基準を破る実装が、全緑のまま残っていました。** 打ち切りの欠陥は単体・統合・受け入れ・クラスタ E2E のどれも赤にせず、しかもクラスタ E2E で症状を実測しながらテスト側を直して通していました。**「実環境で見つけた症状は、テストを直す前に実装を疑う」**を IT6 のふりかえりの Try に送ります。

**書いた保証が 3 件、空手形でした**（知らない港の 422・`visible` の共有・「設計し直す」シナリオ）。いずれも javadoc・規則表・テスト名という「読めば守られていそうな形」で書かれていました。IT4 の学び（[written-guarantees-need-a-red-test]）が本 IT でも同じ形で再現しています。

## 高

### H1. `Shipper` も `@EventTag` が無く、空のまま復元されていた（architect）

**IT2 で「`@EventTag` が無いと集約は空のまま復元される」と分かって ADR に書いた、その同じ変更で `Cargo` 側だけ直し `Shipper` 側が残りました。**

| | |
| :--- | :--- |
| 場所 | `ShipperRegisteredEvent.java:11`・`Shipper.java:24` |
| なぜ気づかなかったか | `Shipper` は static ハンドラしか無く、復元した状態を見る判断が 1 つも無かった。壊れていないのではなく、まだ触っていないだけだった |
| 何が起きるか | ADR-0003 決定 3 の `UpdateShipperContactCommand`（削除済みなら 409）を足した瞬間、`isShredded()` が常に true を返して守りが素通りする |
| 対応 | **修正済み。** `@EventTag` を付け、`register` をインスタンスのハンドラにし、`ShipperRestoreIT` で「同じ荷主 ID で 2 度は登録できない」を固定した |

### H2. `@EventSourced(tagKey)` と `@EventTag` の対応を検査する規則が無かった（architect）

H1 の原因です。ADR に「組み合わさると危険」と本文で書いても、集約を 1 つ足すたびに同じ失敗が起きます。

**対応: 修正済み。** `EventTagAccompaniesEventSourcedTest` が、`@EventSourced(tagKey)` の集約が `appender.append` で出すイベントを**全部拾ってから**タグの有無を見ます。「タグを持つイベントだけを探す」形にはしません。

### H3. `SharedKernelScopeTest#rejectsClassesOutsideTheScope` が何も判別していなかった（architect）

`rename()` はクラス群をそのまま返すだけで、フィクスチャは `resideInAPackage("...shared..")` に 1 件も一致しません。**緑だったのは違反を検出したからではなく、対象 0 件で ArchUnit が例外を投げたから**です。JavaDoc 自身が素通りを認めていました。

**対応: 修正済み。** このテストを削除し、判別している `discriminatesWhenScopeIsNarrowed` だけを残して理由を書きました。

### H4. ADR-0003 決定 6 が「消せない個人情報」を残していた（architect）

決定 6 は「API 応答に載せない」を選びましたが、**これは露出を止めただけ**でした。`attention_item.payload` にメールアドレスが平文・追記専用で残り続けます。鍵を破棄しても消えず、弾かれた荷主は `shipper` に行が無いので担当が辿り着けません。**ADR 自身が「いちばん気づきにくい形」と書いた状態そのもの**です。

**対応: 修正済み。** 投影が書く時点で重複相手の**荷主 ID だけ**を payload に入れ、メールアドレスを書かないようにしました。識別子は個人情報ではなく、鍵を破棄しても意味を持ちません。`ShipperProjectionIT` で「弾いた記録に個人情報を書かない」を固定しています。

### H5. US31 §受入基準 8 の中核が未検査だった（tester）

居ない利用者・パスワード誤り・無効化の 3 通りは比べていましたが、**ロック中と誤りを比べるテストが 1 本もありませんでした**。ロック中だけメッセージを変えても全緑になります。

計画（`iteration_plan-2.md` リスクと対策）が「4 経路を 1 つのテストで並べて完全一致を検査する」と宣言したのに、実施していませんでした。

**対応: 修正済み。** 4 経路を 1 つに並べ、ロック中だけメッセージを変えると赤になることを確かめました。

### H6. 登録直後の「受け付けました」が出ていなかった（user-representative）

`navigate` に `state: { justBooked: true }` を渡していましたが、**読む場所が 1 つもありません**でした。投影は非同期なので登録直後の一覧に自分の予約は無く、メッセージも出ません。営業は「登録できていない」と判断して二重に入力します。

`ui_design.md` の S10・S20 の salt には描かれていたので、正典との不一致でもありました。荷主一覧も同じ状態でした。

**対応: 修正済み。**

### H7. 一覧が 200 件で無音で切れていた（user-representative）

荷主・予約とも `page=0&size=200` 固定で、ページングも件数表示もありません。**荷主が 201 件目になった日、その荷主は予約登録の選択肢に出ず予約が取れなくなります。** 予約一覧の API は `total` を返しているのに画面に出しておらず、荷主一覧は `total` すら返していませんでした。

**対応: 修正済み。** クエリから直し、上限で切れていることを画面に出しました。`ui_design.md` の画面共通の規約にも足しています。

### H8. 到着期限が過去でも予約が通っていた（user-representative）

出発地と目的地が同じことは断るのに、期限が過去であることは断りません。年を打ち間違えた予約が仮受付として一覧に載り、経路設計者が「間に合う経路が 1 本も出ない」と気づくまで進みます。

**対応: 修正済み。** 集約で断り、画面にも `min` を入れました。**復元では検査しません**（受け付けたあとに期限を過ぎた予約が読めなくなる）。当日着は間に合う扱いなので、境目も固定しました。

## 次の IT までに決めたい業務ルール（user-representative）

- **期限に間に合うかの判定は港のローカル時刻で行う必要がある。** シンガポール・ニューヨーク着で最大 13 時間ずれます。入力は日付のままでよい
- **危険物かつ冷凍**の貨物（一部の化学品）が実務にある。現在の `CargoSpecification` は種別 1 つしか持てず表現できません

## 良い点（各視点から）

- **`AxonServerContainerIsBuiltInOnePlaceTest` の作り方**（architect）— `new AxonServerContainer` を含む行を全部拾ってから許可した 1 か所を除く。空振り防止まで入っている
- **crypto の共有カーネル移動が具体的な破綻に押されている**（architect）— 「billingms が持たないと氏名にエンベロープの JSON が入る」から動き、正典 3 点を同じ変更で更新した
- **「判別できない場所」を特定して層を移した記録が残っている**（tester）— `CargoTest.java:135-138` が、`disableAxonServer()` では守りを外しても緑になることを明記して実 Axon Server へ移している
- **予約一覧の既定条件が「今日やること」になっている**（user-representative）— 営業が毎朝上から片付けられる
- **受け入れ基準を黙って読み替えず、読み替えた事実を両方に書いた**（writer）— US31 §3・6 と §8 の矛盾を要件側に注記し、マニュアルで利用者の言葉に翻訳している

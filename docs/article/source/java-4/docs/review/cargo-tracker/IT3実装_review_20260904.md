## 高優先度の指摘と対応

### 1. サーバ側にロール認可が 1 つも無かった（programmer）

認証さえ通れば誰でも `POST /api/v1/routing/voyages`（航海登録）と `GET /api/v1/booking/bookings/routing-worklist`（全荷主の予約一覧）を叩けました。ロールの出し分けはフロントの `RequireRole` だけで、ブラウザを介さずに叩けば素通りします。

`BookingController` の Javadoc には「経路設計ロールへの開放は Gateway の**ルートとロール**で行う」と書いてあり、**前半だけが実装されていました**。書いただけで守った気になっていた形です。

対応: Gateway に経路 → 許すロールの宣言表を置き、宣言の無い `/api/` は通さない（[ADR-0006](../../adr/cargo-tracker/0006-role-authorization-at-the-gateway.md)）。宣言の抜けは検査が赤にする。認可を外すと 2 本が赤になることを確認。

### 2. 「丸ごと比べる」がヘッダだけだった（programmer）

`VoyageProjection.sameAsStored` は `voyage` の行（最初の出発と最後の到着）しか比べておらず、寄港地と受入貨物種別が入っていませんでした。同じ航海番号で「危険物も受ける」と申告した 2 件目がリプレイと判定され、そのまま追記されて**既存の航海の受入種別が黙って広がります**。要確認一覧にも載りません。

Javadoc に「項目ごとに比べない。別物が読み直し扱いで黙って捨てられる」と書いてあったのに、その事象そのものを起こしていました。

対応: 寄港地（順序込み）と受入貨物種別も比べる。再現テスト 2 本が修正前は赤。

### 3. 値オブジェクトが本番経路に載っていなかった（programmer）

`VoyageNumber` は 20 文字の上限を持ちますが、本番コードから一度も使われていませんでした。`Voyage.validate` は文字列の空白しか見ないので、21 文字の航海番号は集約を素通りしてイベントになり、投影の `VARCHAR(20)` で落ちて **Processing Group が止まります**。利用者には「登録したのに一覧に出ない」に見えます。

対応: 集約の検証を値オブジェクト経由にする。`Carrier` にも同型の穴があったので長さ検査を追加。

### 4. 記録した要確認項目を読み出す経路が無かった（architect）

routingms は航海番号の重複を `attention_item`（`ROLE_ROUTING` 宛）に記録しますが、それを読み出す REST がありませんでした。S70 は `/booking/attention-items` だけを叩いており、**弾かれた登録は誰にも見えないまま残ります**。`AttentionItemMapper.findOpenByRole` が定義済み未使用だったのが配線漏れのサインでした。

対応: `GET /api/v1/routing/attention-items` を追加し、S70 が両 BC を束ねる。画面レベルの検査を追加（供給元を booking だけに戻すと赤）。

### 5. 経路設計者が S70 に到達できなかった（technical-writer）

マニュアル 07 が「要確認一覧に残っている可能性があります」と誘導している先に、経路設計者は行けませんでした。ナビの許可は営業・経理・追跡のみ。一方、同じ `ui_design.md` の S02・S30・S32・S33 の salt は**サイドナビに「要確認」を描いており**、3 者が三様でした。

対応: ナビと正典の両方に経路設計を追加。

### 6・7. 正典の照合が片方向で、表示ロールを読んでいなかった（tester）

`navigationMatchesUiDesign.test.ts` は `NAVIGATION ⊆ 正典` しか見ておらず、**実装したのにナビへ足し忘れた画面**は緑のまま素通りしました。また画面 ID だけを取り、表示ロールの列を捨てていたため、**誤ったロールに開放しても検出しません**でした。

対応: 逆向き（実装した画面がナビに載っているか）と表示ロールの突合を追加。壊すと 2 本が赤。

### 8. 誤配案件が経路設計作業一覧に 1 件も出なかった（user-representative）

並び順は「誤配が先」、画面のコメントも「並び順は誤配が先」、`ui_design.md` も「誤配は含める」。ところが絞りは `booking_status = 'ROUTE_PROPOSED'` だけで、誤配になるのは輸送中なので**該当する行が存在しません**。文書・コメント・並び順の 3 つが揃って対応済みに見えていました。

誤配の再設計は急ぐ仕事で、S30 が唯一の入口です。ここに出ないと経路設計者は気づく手段を持ちません。

対応: 絞りを「設計待ち または 誤配」に直し、輸送中の誤配が出ることを検査で固定。

### 9. ダッシュボードの件数が経路設計者の仕事でなかった（user-representative）

経路設計者に「引き渡し待ちの予約が N 件」（＝まだ営業が引き渡していない予約）を出し、リンク先は `/bookings` でした。引き渡すのは営業の仕事（US06）なので、経路設計者はこの N 件に何もできません。逆に**営業にはこの件数が出ていない**ので、本来やるべき人が気づけませんでした。

対応: 件数を担当ごとに分ける。営業には「引き渡していない予約」、経路設計者には「設計を待っている予約」と S30 への導線。

### 10. 入力する日時がどの時刻帯か画面に無かった（user-representative）

`datetime-local` の入力を無条件に UTC として送っていますが、ラベルは「出発日時」だけでした。運送会社の公開スケジュールは港の現地時刻なので、日本の経路設計者が「10:00 出港」をそのまま入れると 9 時間ずれた航海が登録されます。**エラーは出ないので、荷主に誤った到着日を提示するまで誰も気づきません。**

対応: ラベルに `（UTC）` を明記し、換算が要ることを画面に出す。マニュアル 07 にも同じ注意を追加。

### 11. マニュアルが検査していない書式を規約として書いていた（technical-writer）

「IMO クラスは 1〜9、UN 番号は `UN` に続く 4 桁」と書いてあるのに、`HazardousDeclaration` は空白しか見ておらず `UN 1263` も `3.1` も通りました。表記ゆれは経路設計（受け入れ可否）と通関で効きます。

対応: 値オブジェクトに書式検査を実装（マニュアルの記述を正とした）。

## 中優先度（18 件・全件対応）

- 検査自身の穴 4 件: `throw new` の行頭形しか拾わない（`orElseThrow` が不可視）、修飾子の順序に依存（`static public` が素通り）、`*Controller.java` の `@RequestMapping` しか拾わない、公開経路の除外がテスト側にハードコード。いずれも壊して赤を確認
- 例外の対応表が 2 サービスに逐語コピー → 写しの有無を同型検査に足す（3 つ目のサービスで同じ失敗を繰り返さないため）
- 必須項目のエラー応答（US24 §受入基準 3 のサーバ側）にテストが 1 本も無かった → 追加（**文言でなく項目名でアサート**。既定文言はロケール依存）
- 多区間の寄港地が順序どおり読めることが受入層・E2E のどこにも無かった → 受け入れシナリオを追加（並びを逆にすると赤）
- US06 の成功経路が単体テストに無かった（クラスタ E2E だけ）→ 追加
- `Schedule` の同時刻の扱いが仕様か見落としか読めなかった → 許す判断を明示し、テストで固定
- 更新できなかったこと（0 件更新）を黙っていた → 警告を出す
- BC 境界の戻り値を `unknown[]` で素通しキャスト → 型を付ける
- 通信断で押しても何も起きないように見えた → フォールバック表示を追加
- 「設計済みも表示」の文言と実際の範囲が食い違っていた → 文言を実態に合わせる
- S30 に総数表示が無く、上限で無音で切れた → S32 と同じ扱いに
- 正典ドリフト 5 件（routing の `attention_item`・Flyway のロケーション・S33 の salt・S32 の時刻・S02 の salt・S30 の遷移先）→ 実装に合わせて更新し、ADR-0005 / ADR-0006 を起票

| 指摘 | 判断 |

| `Voyage.cancelled` が定義済み未使用（YAGNI） | US25（IT4）で使う。ただし「定義済み未使用は配線漏れのサイン」という指摘は正しく、今回その形で実欠陥（#4）が見つかった。US25 の計画に「投影とドメインのどちらが正か」を明記する |

## 良い点（維持したいところ）

- **「名簿の向き」への意識が広く行き渡っている。** 経路の検査・ES サービスの同型検査・遷移表の照合はいずれも「対象を全部拾ってから見る」形で、空振り検査が対になっている。今回の高優先度 2 件は、この方針が**ナビの規約テストにだけ**行き渡っていなかったという話
- **契約の往復を「届いた」で見た。** ゴールデン一致でなく購読側の表で確かめ、さらに「同じ表を見ているだけではない」ことを別テストで固定している。IT2 から 2 回繰り越した項目を実配送で閉じた
- **要確認の識別子を内容から導き、リプレイで増えない形にした。** 追記専用テーブルは投影と別の壊れ方をする
- **デモ項目と検査の対応を、テスト名でなくアサーションの中身で書いた**
- **索引・`mkdocs.yml`・実ファイルの 3 点が完全に一致している**
- **US32 の切り出しに出自と判断理由が残っている。** 「但し書きに畳むと『一部未達』が繰り返される」という理由づけが、リリース計画の SP・IT4 配分まで同じ変更で揃っている

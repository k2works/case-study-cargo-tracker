# リリース完了報告書 3.0 - Cargo Tracker（CQRS / Event Sourcing 版）

**報告書作成日**: 2026-09-16

## 概要

Cargo Tracker v3.0「運用と実演」のリリース完了報告書です。全 2 イテレーション（IT16〜IT17）、**19 ストーリーポイントを消化しきり**、「業務が端から端まで成立していること」を**システム自身が確かめられる**ようになりました。

**本リリースで新しい業務ロジックはほとんど足していません。** 作ったのは「業務が成立していることを確かめる手段」です——シナリオを 1 つ選ぶと予約から精算までの 13 工程が自動で通り、例外（遅延・破損・誤配・税関保留・輸送中キャンセル）は対応・解決・組み直し・承認まで通り、乱数で選んだシナリオを一定間隔で流し続けられます。**専用の書き込み経路は作りませんでした**（[ADR-0020] 決定 2）——作ると「シミュレーションは通るのに実際の操作は通らない」状態を検出できなくなるからです。

**あわせて荷主の入口を開きました。** 自社の予約一覧・進み具合・貨物の知らせです。知らせは**押し出さず読みに行く**形にしました（[ADR-0021]）——WebSocket や SSE は Gateway と認証をもう 1 本通すことになり、荷主が求めているのは「数分以内に気づける」ことだからです。

**局面は終盤（アウトサイドイン）のままです。** 新しいサービスは `simulationms` の 1 つで、**このサービスだけが Event Sourcing を使いません**（[ADR-0020] 決定 3）——シミュレーションは駆動役であって業務の文脈ではないからです。IT17 の時点で Axon 依存を完全に外し、規約検査で戻らないようにしました。

### 11 SP を落とさずに済んだ理由

IT17 は「US36 が作る貨物が US37 を確かめる材料になる」順序（US36 → US37 → US35）で組みました。**後のストーリーの前提を先のストーリーが作る**形にしたので、US35 の受け入れシナリオは US36 の継続実行がすでに流している経路をなぞるだけで済みました。順序が見積もりを縮めた例です。

## 主要な成果物

### 業務としてできるようになったこと

- **シナリオを 1 つ選ぶと、予約から精算までの 13 工程が自動で通る**（US33）。叩くのは人が使うのと同じ API で、Gateway の認可も同じ経路を通る
- **どの工程で何が起きたかが読める**（US34）。所要時間・生成した識別子・失敗の理由が工程ごとに残り、そこから業務画面へ行ける
- **例外シナリオが対応まで通る**（US35）。誤配は現在地からの経路を組み直して輸送が再開し、輸送中キャンセルは承認で指定した港での荷降しまで実行されて追跡が閉じる。**例外は手で起票せず、荷役や通関からシステムに起こさせます**——実物が断るからです
- **乱数で選んだシナリオを流し続けられる**（US36）。実行間隔・同時実行数・例外比率を設定でき、**種を指定すると同じ並びを再現できます**。流しているあいだも実利用者の操作は劣化しません
- **荷主が自社の貨物を見られる**（US37）。予約一覧・進み具合・貨物の知らせ。既読はサーバが持つので、端末を使い分けても同じ知らせが二度出ません

### 技術的な成果

- **8 つ目のサービス `simulationms`**。**Event Sourcing を使わない唯一のサービス**（[ADR-0020] 決定 3）で、IT17 で Axon 依存を完全に外し、ビルドファイルと本文から名簿を導く規約検査（**逆向きの検査つき**）で戻らないようにした
- **連鎖の待ちを「読み口の値」で宣言する形**（`ChainReadiness`）。工程ごとに「何が読めたら次へ進めるか」を宣言し、**待たない工程も宣言する**——既定を「待つ」にすると、読み口を持たない工程が上限まで待ってから失敗する
- **シミュレーション由来の印**（`simulated`）と、それを外す読み口の数え上げ（[ADR-0020] 決定 4）。乱数実行は大量にデータを作るので、混ざったままでは業務の一覧が使えなくなる
- **知らせの連番と既読位置**。`tracking_event` に順序を決める連番が無かったので `BIGSERIAL` を足した。**古い順に返す**——新しい順だと、上限で切ったときに出していない古い知らせまで既読になる

### ドキュメント

- ADR 2 件（0020 シミュレーションは駆動役であって Event Sourcing の文脈ではない・0021 知らせは押し出さず読みに行く）
- マニュアル 2 章（20 業務シミュレーションを流す・21 荷主が自社の貨物を見る）。あわせて **ch.00 の担当と画面の表**と **ch.01 の「いま使える範囲」**を実装に合わせ直した（5 章ぶん古かった）
- 正典（`domain-model` / `data-model` / `ui_design` / `architecture_backend`）に `SimulationSchedule`・`notice_read_position`・S92〜S94・S45/S46 を反映

## 総評

### よかったこと

**繰越ゼロが 13 回連続になりました。** とくに IT17 では、**6 IT 連続で起票されなかった S45・S46（荷主の自社予約）を行として立てて返しました**。着手して分かったのは、正典の「未実装」が「ルートだけが無い」ではなく読み口も一覧も実装 0 件だったことです——**落とした負債は育ちます**。

**実物を通すことでしか出ない欠陥を、毎 IT で捕まえました。** IT16 は 8 件（Dockerfile 7 本の写し忘れで全イメージが作れない、管理者が業務画面を開けないなど）、IT17 は 3 件（`users.shipper_id` を書く経路が存在せず荷主向けの画面がすべて空、監査の `reason` が短い、追跡番号が画面に出ない）。**どれも層ごとの検査はすべて緑でした。**

**外していない読み口を、表で数え上げて自覚的に残しました**（[ADR-0020] 決定 4）。IT16 で「未」3 件として残し、IT17 で閉じています。

### 学んだこと（次のリリースへ）

**確かめる側は、確かめられる側より丁寧に検査する必要があります。** 本リリースで作ったのは「業務が成立していることを確かめる手段」で、その手段自身がいちばん多くの欠陥を出しました——1 回目のポーリングで抜ける待ち、空集合で真になる述語、次に足したものが載らない手書きの名簿。**確かめる側が壊れていることは、誰も教えてくれません。**

**層をまたぐ性質は、どの層のテストも書きません。** IT17 の US36 §1（毎回ちがうシナリオを流す）は、乱数を集約が持ったため一度も働かないまま、層も受け入れ 18 本もクラスタ E2E 29 本も緑でした。集約にもサービスにも画面にも属さない性質なので、書く担当が決まらなかったのです。

**除外は、それを待ちに使っている場所を壊します。** 「シミュレーション由来を外す」承認待ち一覧を連鎖の待ちに使っていたため、**シミュレーション自身が出した申請が自分では見つけられず**、輸送中キャンセルのシナリオが必ず時間切れになりました。あわせて `EXISTS ... simulated = FALSE` は、写しが投影で届く前の一瞬、本物の申告まで一覧から消していました。**どちらもフルビルドと CI で初めて出ました。**

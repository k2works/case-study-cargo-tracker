## Keep（続けること）

### 壊して赤を見ることを全タスクで実施した

IT1 の Try 1 をそのまま実行しました。**ロック 3 通り・解除 2 通り・契約投影 2 通り・`@EventTag`・フロント 3 通り**を実際に壊し、すべて赤になることを確かめています。

とくに `@EventTag` の 1 件は、これをやらなければ**気づけませんでした**。付け忘れると集約が毎回空のまま復元されるのに、`AxonTestFixture` では判別できません。「入れた」と「働く」を分ける規律が、そのまま欠陥の発見になりました。

### クラスタに対する E2E を完了条件に入れた

イテレーションの途中でユーザーから追加された条件です。**単体テストもモックの E2E も通っていた欠陥**（S21 の荷主入力が UI 設計と食い違い、営業が UUID を書き写す形になっていた）を、実際に配ったもので初めて捕まえました。

「実際に配ったものが動くか」は、単体とモックのどちらも判別しません。

### デモ項目との対応をテスト名でなく本文で作った

IT1 の Try 9 です。IT1 は名前だけがデモ項目を謳うテストを数えていました。今回は各デモ項目について「何をアサートしているか」を計画に書いています。

### 返済枠を IT の序盤に置いた

IT1 の Try 2・3 です。持ち越し 9 件のうち 8 件を返しました。**「余力次第」にしなかったことが効いています**。落とした 1 件（契約テストの往復）も、理由（routingms が立つ IT3 のほうが検査対象が増える）と代替（`ShipperContractProjectionIT` で契約イベントが届くことを実測）を明記しました。

## Problem（うまくいかなかったこと）

### P1. 並列レビューの結果が、2 イテレーション連続でクローズの後に届いた

IT1 と同じです。5 エージェントを起動し、10 分後に全員 idle になり、催促にも応答がありません。逐次のフォールバックに切り替えてクローズまで進めた**直後に、5 通が一斉に届きました**。

**「2 回とも届かなかった」は誤りでした。2 回とも遅れて届いています。** 所要はおよそ 35〜40 分です。

| | IT1 | IT2 |
| :--- | :--- | :--- |
| 遅着分にしか無い指摘 | 8 件（うち高 3） | **14 件（うち高 6）** |

**IT2 の遅着分には、逐次レビューで見つけられなかった実欠陥が 6 件ありました。**

- `Shipper` にも `@EventTag` が無い（`Cargo` を直した同じ変更で片方だけ残った）
- 共有カーネルの検査が対象 0 件で「緑」になっていた
- ADR-0003 決定 6 が「消せない個人情報」を残していた
- US31 §受入基準 8 の中核（ロック中と誤りの比較）が未検査
- 登録直後の「受け付けました」を読む場所が無い
- 一覧が 200 件で無音で切れる（荷主が 201 件目になると予約が取れない）

**逐次レビューは 5 視点を「見た」だけで、並列ほど深く読めていませんでした。** 私が自分で書いたコードを自分で読むと、書いたときの前提をそのまま持ち込みます。IT1 の「自分で書いた対応表を自分で検証しても、同じ見落としをする」と同じです。

### P2. 設計と実装の食い違いが 5 件あった（すべて IT1 の実装に由来）

| # | 食い違い | 見つかり方 |
| :--- | :--- | :--- |
| 1 | ロックが 30 分（設計は 15 分） | US31 の着手時に `non_functional.md` と突き合わせた |
| 2 | 監査ログが理由を残せない形（設計は `event_type`/`reason`） | 同上 |
| 3 | REST が個人の契約情報を黙って捨てる | 個人の荷主の検査（IT1 レビュー M8）を足したら出た |
| 4 | 集約が断ると 500 | 同上 |
| 5 | S21 の荷主入力が ID 直接入力（設計は選ぶ） | **kind クラスタに対する E2E でのみ露見** |

**5 件とも IT1 のクローズ時点では緑でした。** 1・2 は正典と突き合わせなければ分からず、3・4 は「その経路を通るテストが 1 本も無かった」ために出ず、5 は「テストが ID を打っていた」ために出ませんでした。

共通するのは、**受入基準を満たすテストを書いたが、正典の数字・形と突き合わせていなかった**ことです。

### P3. 品質ゲートの配線が 2 件壊れていた

| # | 欠陥 | 結果 |
| :--- | :--- | :--- |
| 1 | `check` が `jacocoTestReport` を呼んでいなかった | Sonar が前のイテレーションのレポートを読み、新しいクラスを「未カバー」と数えた（実際 68〜97% を 28.6% と表示） |
| 2 | `sonar-local:scan` が TypeScript 用の引数で Java の設定を上書きしていた | Java のテストが「テスト」と見なされていなかった |

IT1 の P1（ゲートがフロントを見ていなかった・前回の解析結果を読んでいた）と**同じ種類**です。IT1 では「緑に見えて何も見ていない」、IT2 では「**赤く見えて実態と違う**」形でした。

**赤も疑う必要がある**というのが今回の学びです。赤を見て「カバレッジが足りない」と受け取ってテストを書き足していたら、配線の欠陥は残ったままでした。

### P4. Axon Server の待ち時間が 3 か所に散っていた

起動猶予を 3 分から延ばしたとき、`AbstractAxonIntegrationTest` だけを直し、`CucumberSpringConfiguration` と `AxonServerOutageIT` が別の定義を持ったままでした。**全体ビルドだけが落ち、単独実行では通る**形で出ました。

k8s 側（`startupProbe`）も 5 分のままで、こちらは**再起動ループ**になりました。業務サービスが軒並み繋がらなくなり、見えるのは「投影が進まない」です。

### P5. マニュアルが IT の途中で置き去りになった

貨物予約の章を書いたあとで S21 の荷主入力を変えたため、マニュアルが「荷主 ID を入力します」のまま残りました。レビューで見つけて直しています。

**画面を変えた IT でだけマニュアルを更新する運びだと、IT の途中の変更が取り残されます。**

## ADR-0001 決定 2 の発動条件（判定）

**発動しません。**

| 条件 | 判定 |
| :--- | :--- |
| IT2 終了時点で実績ベロシティが計画（9 SP）の 70%（6.3 SP）未満なら、`Quotation` と `Voyage` を状態保存に落とす | **実績 9 SP（100%）。発動条件を満たさない** |

`Cargo`（状態を持つ最初の集約）を Event Sourcing で書き切り、`@EventTag`・`@TargetEntityId`・インスタンスのコマンドハンドラという Axon 5 の作法も確定しました。**Event Sourcing の実装コストは見積もりの範囲に収まっています。**

ただし IT1・IT2 とも**基盤と持ち越しの返済が本体と同じかそれ以上の重さ**でした（IT2 は US 58h に対し返済枠・検査・マニュアルで 40.5h）。IT3 で routingms が立ち上がると 2 つ目のサービスの立ち上げコストが乗るので、**IT3 終了時点でもう一度ベロシティを見ます**。

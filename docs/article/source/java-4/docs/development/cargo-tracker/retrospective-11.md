## Keep

### Try T6 を 3 IT 目で達成した——「習慣にする」をやめたから

IT9・IT10 は「US を閉じるコミットに品質ゲートの結果を書く」を 2 IT 続けて守れませんでした。
IT10 のふりかえりで**手立てを変える**と決め、IT11 の序盤に `.gitmessage` を用意して
`commit.template` に設定しました。**書く欄が最初からあると、埋めないほうが不自然になります。**

同じ形で **Try T4（イメージは作成時刻で確かめる）も機械に移しました**。`k8s:images` が
最後にイメージの作成時刻を出すようにしたところ、**初回から www が 42 時間前のまま**である
ことを指摘しました。「気をつける」では出せなかった情報です。

### 読み口を先に決めてから記録を作った

IT10 の Problem P1 は「記録したが読めない」を 2 か所で作ったことでした。US20 §3
（管理職への escalation）は同じ形になりうる受入基準です。

今回は**読み口を先に決めました**——例外一覧（S42）を `ROLE_ADMIN` に開き、緊急なのに
知らせた記録が無い行に「未連絡」と出す。決めてから `ExceptionEscalatedEvent` を作ったので、
「記録して終わり」になりようがありませんでした。

副産物として**リンクの出し分け**という問題が出ました。管理者は S41 も S43 も開けないので、
一覧の行にリンクを出すと 403 に当たります。読む側と手を動かす側を同じ画面の中で分けました。

### 不変条件を「例外を許す」ではなく「別の規則」として立てた

US28 §6 のために `Cargo` 不変条件 5 を緩める必要がありました。`isSatisfiedBy` に
「誤配なら期限を見ない」という分岐を足すこともできましたが、**その分岐は増え続けます**。
代わりに `isSatisfiedByRedesign` という別の述語を立てました。

**緩めた側だけでなく、通常の設計で超過候補が出ないことも赤で固定しました。** tester が
「緩めた守りの反対側を毎回対で置いている」と評価した点です。

### クラスタ E2E が、また実欠陥を出した（Try T8 の 2 IT 目）

**投影が止まっていた**——誤配の自動起票で例外の識別子が投影の列幅を超え、書けない
イベント 1 つで Event Processor が止まっていました。画面には「反映されない」としか
出ません。集約のテストは投影の桁を知らないので、緑のまま通ります。

**例外一覧が荷主にも開いていた**——`/tracking/trackings/**` の広い宣言に吸われており、
他社の貨物の例外まで読めました。管理者に開く変更をしていなければ気づきませんでした。

**入力中にポーリングで入力欄が消える**——クローズの通しで見つけました。追跡管理者は
長い対応内容を書くので、書き終わる前に必ず当たります。

## Problem

### P1: 「片方にだけ書いた」形の欠陥を 3 件作った

レビューが出した高 9 件のうち 3 件が同じ形です。**同じ業務判断が 2 か所に要るのに、
後から足した経路にだけ書いていない。**

- 預かった荷役の適用が、その場で適用したときの後段（契約イベント・自動起票）を出さない
- 誤配の印を立てる経路だけで、降ろす経路が無い
- 取り消しが預かり中の荷役を外さない

**経路を増やしたとき、既存の経路がやっていることを数えていません。** IT10 の Try T2
（契約イベントを足したら、その状態へ入る経路を全部数える）は**出す側**しか数えて
おらず、**適用する側が 2 つになったこと**を見ていませんでした。

### P2: 緩めた守りの「反対側」を、軸ごとに数えていなかった

`isSatisfiedByRedesign` は期限の軸だけを緩めるつもりで、**端点の軸も一緒に外して**
いました。architect が「置き換えではなく削除されている」と指摘するまで気づいて
いません。「緩める側だけを検査すると緩みすぎに気づけない」は守ったのに、
**何を緩めたかを軸ごとに数えていなかった**わけです。

### P3: マニュアルが実装より先に「あるべき姿」を書いていた

15 章に「出発港は貨物の現在地に固定されます」と書きましたが、画面は編集可能な
絞り込み欄のままで、サーバだけが現在地を優先していました。**文章のほうが正しく、
実装が追いついていない**形です。writer が拾わなければ、利用者は入れても効かない欄に
値を書き続けます。

### P4: 重い検証を 1 本ずつ回せなかった（Try T3 が 2 IT 続けて未達）

走っているビルドの隣で別の Gradle を 3 度起こし、build ディレクトリを壊しました。
手順書（`operation.md` 9.2）には書きましたが、**書いただけでは守れませんでした**。
加えてこの環境では 10 分を超えるビルドが完走しないことが分かり、モジュールを分けて
5 回に分割する必要がありました。

### P5: 通しのクラスタ E2E が 6 回続けて別々の場所で落ちた

単独では全部緑なのに、通しでは毎回 1〜4 件落ち、落ちる場所が毎回違いました。
原因は 2 種類（一覧の表示上限・投影の反映待ちが 1 回だけ）で、**どちらも「自分の
データを名指しで探す」形**でした。6 回直してようやく通りました。

そして**この積み上がりは業務の問題でもあります**——未解決の誤配が経路設計作業一覧
（S30）の上限を食い、通常の設計依頼が沈みます。

### P6: user 視点のレビューが 1 時間返らなかった——そして高 3 件を持っていた

5 通のうち 4 通は 2 分以内に返りましたが、user 視点だけ返着せず、**再送を 2 度
依頼して 1 時間後に受領**しました。**無応答を「指摘なし」と読まなかったこと**で、
次の 3 件が拾えています。

- **輸送中の誤配では荷主へ超過を伝えた記録が残せない**（US28 §6 の後半が実質未達）
- **管理者が S42 で何もできない**（escalation の宛先が一番動けない）
- **「未連絡」の印は通常点かず、点いても消せない**（確かめる欄のつもりが飾りだった）

とくに 1 件目は受入基準そのものです。**「達成」と書いたものを、実務の目で
もう一度見る視点**が、他の 4 視点では出ませんでした。

### P7: 「開けない場所へ誘わない」が、行き止まりを作っていた

管理者に S42 を開いたとき、S41 を開けないので一覧の追跡番号からリンクを外しました。
**「共有画面のリンクもロールで出し分ける」という過去の教訓に従ったつもり**でしたが、
user は「escalation の宛先が一番動けない」と指摘しました。

正しい形は**リンクを外すことではなく、閲覧を開くこと**でした。教訓を当てはめる前に
「その人はそこで何をするのか」を問うべきでした。

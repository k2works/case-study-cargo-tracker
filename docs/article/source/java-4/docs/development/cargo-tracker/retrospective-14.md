## Keep

### 受け入れテストを「回した」ことで、実欠陥が 3 件出た

`請求の精算.feature`（9 シナリオ）と `輸送見積の作成.feature`（6 シナリオ）は
**書かれていたのにステップ定義が 1 つも無く**、それでも成功基準「デモ項目の受け入れテストが
すべて緑」は緑に見えていました（未定義のステップが落ちない設定だったため）。

レビューがこれを指し、**実際に回るようにしたら欠陥が 3 件出ました。**

1. **候補の経由港が候補ごとに違わない。** 画面が出発地と目的地を繋いでいたので、どの候補も
   同じ経路に見え、案を選び分けられなかった（US01 §受入基準 3 の未達）
2. **見積と異なる項目を画面が捨てていた。** サーバは応答に載せていたが、登録のあと誰にも
   伝わらない（不変条件 3）
3. **見積の貨物種別が素の `valueOf` で、知らない値が 500 になっていた**

**「受け入れテストがある」ことと「回っている」ことは別です。** 一覧の上では、どちらも同じに
見えます。

### レビューの遅着分を待ったら、中優先の指摘が 13 件届いた

programmer と architect の 2 本は長さ制限で切れて届きました。続きを求めて**1 時間半後に
返着**し、そこに `hasCandidate()` の Javadoc と実装の食い違い、危険物ガードが画面から
絶対に踏まれないこと、`invoice_notification` が正典に一切載っていないことが入っていました。

IT6 で「40 分待つ」、IT13 で「切れていたら続きを求める」と学んだことが、両方とも効きました。

### 正典を実装に合わせて直した（逆向きの修正）

これまでは「実装が正典を追い越したら正典を直す」形でしたが、今回は**正典のほうが実装より
細かい**ものが 2 件ありました。

- **Processing Group は「書くテーブルの単位」ではなくパッケージ**（Axon 5 に
  `@ProcessingGroup` が無い）。つまりリプレイと退避の単位が正典より粗い
- `invoice_notification` は実体だけが増え、ER にも表にも載っていなかった

どちらも**実装が自然**なので、正典の側を書き直しました。「正典が正しい」と決め打つと、
実装不能な正典が残ります。

## Problem

### BC をまたぐ配送だけが、どの検査にも掛かっていなかった

**この IT でいちばん重い欠陥です。** 入金を記録しても予約が精算済になりません
（US23 §受入基準 4）。入金は記録され、請求書は入金済になり、**billingms の側は
すべて正しく動いています**。bookingms が `PaymentRecordedEvent` を処理しないだけです。
ログにも要確認にも退避（`dead_letter_entry`）にも何も残りません。

**緑だった検査を並べると、なぜ気づけなかったかが見えます。**

- 集約の検査（`CargoSettlementTest`）——コマンドを直接渡すので緑
- 反応ハンドラの検査（`BookingReactionHandlerTest`）——イベントを直接渡すので緑
- 投影の検査（`InvoiceProjectionIT`）——billingms の中で完結するので緑
- 受け入れテスト（`請求の精算.feature`）——billingms 1 サービスで回すので緑
- ゴールデン JSON（`ContractEventGoldenTest`）——「形」は固定するが「届くか」は言わない

**すべて 1 つのサービスの中で完結しています。** 計画の T7 は「契約イベントなので
ゴールデン JSON **と Axon Server 経由の往復テスト**」を求めていましたが、
**往復テストが作られていませんでした**。クローズで書いたところ、ローカルでも
同じ症状を再現しました。

**IT13 までの契約は booking → tracking → handling → billing の一方向で、
billing から booking へ戻るのは IT14 が最初**です。向きが変わったときに、
それまでの検査の形がそのまま通用すると思い込みました。

### フルビルドが前のコミットから赤のままだった

成功基準「`TZ=UTC` でモジュールを分けて `build` が緑」は**事実に反していました**。
`:bookingms:build` と `:routingms:build` のカバレッジゲートが落ちており、
見積の値オブジェクト 6 クラスと `Cargo#settle`（分岐カバレッジ **0**）、
`CargoType#fromContractName` が未検査でした。

モジュール単位の `test` は緑だったので、**`build` を回すまで気づけません。**
IT12 で「ローカルの品質ゲートは CI と同じコマンドで」と学んだのに、それを
**IT を締める直前にしか実行していなかった**のが原因です。

### 列・読み口・画面が揃っているのに、書き込みだけが無かった

`quoted_amount` は列があり、`InvoiceRow` にあり、`InvoiceView` にあり、S61 が
「見積時の概算 → 請求 → 差額」の分岐まで用意していました。**`INSERT` 文だけが
その列を書いていませんでした。** さらに `InvoiceCalculation` が `null` を固定で渡しており、
差額行は本番で永久に出ません。

「記録と読み口は対で出す」（IT13 の Try T3）は**読み口の側ばかり見ていました**。
記録の側——実際に書いているか——も同じ検査で確かめる必要があります。

### 定義済み未使用が 5 件あり、うち 1 件は Javadoc が嘘をついていた

`Quotation#diffAgainst` は「不変条件 3 はこれが守る」と集約の Javadoc に書かれていましたが、
**本番から呼ばれておらず**、実際に守っているのは `application/QuotationDiff` でした。
`hasCandidate()` は Javadoc が「**期限に間に合う**候補があるか」なのに実装は総数を見るだけで、
テストは 1 件→真 / 0 件→偽 しか見ず**この食い違いを判別しませんでした**。

どちらも削除し、Javadoc を実際の守り手に向け直しました。**定義済み未使用は配線漏れの
サインです**（IT13 でも同じ形）。

### 集約の守りが画面から絶対に踏まれなかった

`QuotationController#hazardousOf` が空文字を `null` に寄せていなかったため、画面が送る
空文字は「入力された」ことになり、`HazardousDeclaration` が先に 422 を投げます。
集約の「危険物には危険物申告が必要です」は、**画面経由では一度も踏まれません**。

予約側の `CargoSpecificationAssembler` は同じ罠を警告するコメントまで持っていたのに、
**入口ごとに扱いが違っていました。**

### 比べ方は揃えたのに、見せ方は揃えていなかった

見積と予約の違いを知らせる行が、実データでは「重量: 1200.00 kg → 1500 kg」と
出ていました。**比較そのものは正しい**——`BigDecimal.compareTo` で桁を無視して
比べると、わざわざコメントまで書いてあります。揃えたのは比べ方だけで、**見せ方は
持っている桁をそのまま出していた**のです。

単体テストは `1200` を入れて比べていたので出ません。列から戻る値が
`BigDecimal(2)` だと知っているのは実データだけで、**クラスタで初めて出ました**。

**「同じものを扱う道が 2 本ある」と気づいたら、両方を揃えます。** 比べる道に
「数として比べる」と書いたなら、見せる道にも同じ注記が要ります。

### コミットの品質ゲート欄を、今回も埋めなかった

IT13 の Try T10 を立てたのに、クローズ中の 6 コミットは**すべて欄が空**でした。
IT13（11 件中 2 件）から改善していません。**テンプレートに欄があるだけでは埋まりません。**

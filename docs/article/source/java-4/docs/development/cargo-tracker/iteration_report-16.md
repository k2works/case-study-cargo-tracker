## エグゼクティブサマリー

**US33・US34 を完了し、8 つ目のサービス `simulationms` を立ち上げた。** 予約から精算までの 13 工程を、**人と同じ API を Gateway 経由で叩いて**自動実行する。専用の書き込み経路は作っていない（[ADR-0020] 決定 2）——作ると「シミュレーションは通るのに実際の操作は通らない」状態を検出できなくなるためである。引き継ぎ枠 2 件・負債枠 2 件も返済し、**繰越ゼロは 12 回連続**になった。

**この IT の収穫は、実物を通すまで出ない欠陥が 8 件出たことである。** 層ごとの検査はすべて緑だった。内訳はクラスタ E2E の**準備だけ**で 3 件（Dockerfile 7 本の写し忘れで全イメージが作れない・既存クラスタの DB 不足・管理者が業務画面を開けない）、受け入れスイートの実装で 5 件（識別子が列にあふれる・応答コードの無い失敗が成功として通る・発行直後の読み取り・状態コードの推測・必須項目の欠落）。

**クローズのレビューで高 8 件が出た。** うち 1 件は**この IT で作り込んだセキュリティの穴**である——`simulated` の印を誰でも立てられ、営業ロールの利用者が本物の荷主を業務の一覧から静かに消せた。ほか 2 件は受入基準が「書いてあるが満たしていない」状態（識別子からの行き先 3 つのうち 2 つが機能しない・経路設計の作業一覧に除外が無い）で、**受け入れ・往復・クラスタ E2E がすべて緑のまま**残っていた。高はすべてクローズ前に修正した。

## 技術的成果

### `simulationms`（8 つ目のサービス）

- **Event Sourcing を適用しない**（[ADR-0020] 決定 3）。実行の記録は業務の事実ではなく、監査もリプレイも要らない。加えて実行は数十秒走るので、コマンドバスをログとして使う形になる
- **段取りと経路を分けた。** どの工程をどの順に実行するかは `Scenario`、どの経路をどのロールで叩くかは `GatewayBusinessApi`。API を変えてもシナリオの定義は動かない
- **待ちは読み口の値で判別する**（`ChainReadiness`）。工程ごとに「何が読めたら次へ進めるか」を宣言し、**待たない工程も宣言する**

### 画面（S92・S93）

一覧に「どこまで進んだか」（成功した工程数 / 予定の工程数）を出す。開かないと分からない形にすると、走っている数十秒のあいだ何も判断できない。実行結果は工程ごとの成否・所要時間・生成した識別子・止まった理由を出し、識別子から業務画面へ行ける。

### 検査

- **名簿を数え上げる**（`DockerfilesCopyEveryModuleTest`）——`settings.gradle.kts` の include を出典に照合する。「足したら 8 か所を直す」という約束は、8 か所あるという事実そのものが忘れられる
- **8 サービスを単一 JVM で起動する受け入れスイート**（`simulationAcceptanceTest`）。確かめたいのが「端から端まで通ること」なので、1 つでも欠けると確かめたいものが無くなる
- **往復の契約テスト**が、発行側も集約も見逃した欠陥を捕まえた（暗号化の Converter が印を数え落としていた）

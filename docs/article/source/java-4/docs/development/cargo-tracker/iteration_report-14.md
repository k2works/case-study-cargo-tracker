## エグゼクティブサマリー

**業務の輪は、最後の一手前まで閉じました。** 見積を作り、その見積で予約し、輸送して引き取り、請求書を発行して入金を記録するところまでは通ります。**ただし入金が予約まで届きません**——`PaymentRecordedEvent` を bookingms が処理せず、予約は「引取済」のまま止まります（US23 §受入基準 4 の未達）。クローズのクラスタ確認で初めて分かりました。

**荷主が自分の請求書を読めるようになりました**（S62）。金額を出す唯一の荷主向け画面で、経理向けとは別の経路にしています——同じ経路にロールで分岐を足すと、載せ忘れた分岐ほど無防備になるためです。荷主は請求書番号を知らないので、予約から開ける導線を置きました。

**クローズで最も重かったのは「受け入れテストが書かれていたのに 1 つも回っていなかった」ことです。** `請求の精算.feature`（9 シナリオ）と `輸送見積の作成.feature`（6 シナリオ）にステップ定義が無く、成功基準「デモ項目の受け入れテストがすべて緑」は事実に反していました。実際に回したところ、**実欠陥が 3 件**出ました。

**フルビルドも前のコミットから赤のままでした。** `:bookingms:build` と `:routingms:build` のカバレッジゲートが落ちており、`Cargo#settle` は分岐カバレッジ 0 でした。モジュール単位の `test` は緑なので、`build` を回すまで気づけません。

**§4 が未達**です。§2 のスコープ外は計画の注 N9 で先に宣言したものですが、**§4 はクローズのクラスタ確認で初めて分かりました**。

**なぜ最後まで気づけなかったか。** 計画の T7 は「契約イベントなのでゴールデン JSON **と Axon Server 経由の往復テスト**」を求めていましたが、**往復テストが作られていませんでした**。ゴールデン JSON は「形」を固定しますが、「届くか」は何も言いません。集約の検査（`CargoSettlementTest`）も、反応ハンドラの検査（`BookingReactionHandlerTest`）も、受け入れテスト（`請求の精算.feature`）も、**すべて 1 つのサービスの中で完結している**ので緑でした。**BC をまたぐ配送だけが未検査**だったのです。

## 技術的成果

| # | 成果 | 内容 |
| :--- | :--- | :--- |
| 1 | **見積の集約と概算**（`Quotation`） | 候補 0 件でも作れる。比較は `QuotationTerms` の 1 か所で、集約と予約の受付の両方がそこを呼ぶ |
| 2 | **料率の出典を共有カーネルへ**（ADR-0016 補遺） | 見積と請求が同じ `cargo-rates.yml` を読む。**式は共有しない**（入力が違うので金額は一致しない）。同一性は `RateTableParityTest` が実ファイルを読んで固定 |

| 4 | **精算の連鎖**（billingms → bookingms） | 契約イベント `PaymentRecordedEvent`。**進めない状態は経理宛の要確認に出す**——退避すると、入金は記録されているのに予約だけ精算されないまま誰も気づかない |
| 5 | **概算を請求へ運ぶ**（契約イベント `CargoQuotedEvent`） | 追跡のイベントには載せない（trackingms は金額に関わらない）。S61 が「見積時の概算 → 請求 → 差額」を出す |
| 6 | **荷主の読み口**（S62） | 経理向けとは別経路。荷主 ID はサーバで突き合わせ、他社の請求書は 404（403 は存在を教える） |
| 7 | **ADR-0017**（`billing_status` が正） | 3 決定に 3 検査。`void_marker` は UNIQUE を成立させるための派生列 |
| 8 | **画面一覧に節が無い画面を検出する検査** | 3 IT 続いた文書の穴を機械に載せた。置いた瞬間に既存の 5 件を見つけた |

## レビュー結果

5 視点で並列にレビューしました。**高 9 件のうち 8 件をクローズ前に修正**し、1 件（`dead_letter_entry` の読み口が 0 件）は事実誤認として対応不要と判断しています（運用の gulp タスクと actuator の 2 つが既にあり、列名も実物と一致）。

**2 本が長さ制限で切れて届き、続きを求めて 1 時間半後に返着しました。** そこに中優先の指摘が 13 件入っており、`hasCandidate()` の Javadoc と実装の食い違い、危険物ガードが画面から絶対に踏まれないこと、`invoice_notification` が正典に一切載っていないことが含まれていました。**待った判断が正しかった**ことになります。

**レビューが指さなかったが、対応中に出たもの**として、フルビルドが前のコミットから赤のままだったことがあります。成功基準が事実に反していたのは受け入れテストとビルドの 2 か所で、**どちらも一覧の上では揃って見える形**でした。

# 2026-09-13 IT15 の開始と、精算の連鎖の修復

## この日やったこと

IT15（US30 キャンセル承認）の開始準備を通し、最優先タスク T-1
（IT14 から引き継いだ US23 §受入基準 4 の未達）を直しました。
**クラスタ E2E は 24 本すべて緑**になり、IT14 の唯一の未達が閉じました。

## 判断の記録

### 「届かない」と読んだ症状の実体は「書いていない」だった

IT14 のクローズ時、こう書き残していました——「入金は記録され請求書は入金済に
なるが、bookingms は `PaymentRecordedEvent` を処理せず、ログにも要確認にも退避にも
何も残らない。reaction の token は追いついているので**読んだが配送されていない**形
である。原因は Axon 5 のイベント配送にあると見ている」。

この読みは**間違っていました**。`org.axonframework.messaging.eventhandling` を
TRACE にして 1 度回すと、ログはこう言っていました。

- 予約側の Reaction Processor は購読の型一覧に `PaymentRecordedEvent` を**含んでいた**
- そのイベントを**受け取り**、退避キューを確かめ、ハンドラへ委譲していた
- `SettleBookingCommand` は通り、token も次へ進んでいた

つまり配送は最初から成立していて、集約は `BookingSettledEvent` を出していました。
欠けていたのは**その先**です。予約の投影は購読の型一覧に `BookingSettledEvent` を
持っておらず、`cargo_summary.booking_status` を `SETTLED` に書く相手が誰もいません
でした。営業の一覧が引取済のまま止まっていたのはそのためです。

**「token は追いついている」までは正しく観測できていたのに、そこから「配送の問題だ」
へ跳んだ**のが誤りでした。token が進むのは処理が成功したときも同じです。観測した
事実は「止まっていない」であって、「届いていない」ではありませんでした。だから
`@EventTag` を足す実験が空振りしたのも当然で、あれは**仮説が外れた証拠**として
読むべきものでした。

### 直した場所に検査を置き、往復と読み口を対にした

欠陥の形は既知のものです——**記録と読み口は対で出す**。IT10 で引取（`BookingDeliveredEvent`）に
同じ欠陥を出し、同じ言葉で戒めていました。にもかかわらず再発したのは、
**検査がその対を見ていなかった**からです。

- 集約テスト（`CargoSettlementTest`）は「引取済からだけ精算済へ進む」しか見ない
- 受け入れテストも billing の中で完結する
- 契約ゴールデン JSON はイベントの**形**しか固定しない

どれも 1 サービス・1 層の中を見ており、**層をまたいだ配線は誰の担当でもありません
でした**。そこで 2 本を対で置きました。`ContractEventRoundTripIT#paymentRecordedReachesBooking`
（BC をまたいで届くか）と `CargoSettlementProjectionIT`（届いた先が読み口に出るか）です。
どちらか片方では、今回の欠陥はまた素通りします。

### 誰も読まない列には書かない

`cargo_summary` には `settled_at` があり、`BookingSettledEvent` は請求書 ID も
入金額も運んでいます。「せっかくあるから書く」ことはできましたが、やめました。
`BookingView` にはその列を読む口が無く、**書いた値が正しいかどうかを確かめる手段が
無いまま増える**からです。同じ形で `delivered_at` がすでに残っています。
正典（`data-model.md`）に列がある以上いつかは使いますが、**読み口を作る IT で
書き手も一緒に作る**のが対の出し方です。

### 500 行の制限で理由を削らず、段で分けた

投影ハンドラを 1 本足したら `CargoProjection` が 525 行になりました。コメントを
削るのではなく、**輸送〜精算の段**（荷役・引取・その取り消し・誤配・精算）を
`CargoProgressProjection` へ分けました。同じパッケージに置いているのは意図的で、
Axon 5 では Processing Group がパッケージ名で決まります。分けても Processor も
退避先も予約ごとの順序も変わりません。切り口はテスト側（`CargoHandlingProjectionIT`・
`CargoSettlementProjectionIT`）と揃えました。

# 2026-09-04 IT2 の開発とクローズ

## この日やったこと

イテレーション 2（US31 アカウント保護・US03 法人荷主・US04 貨物予約、9 SP）の開発とクローズを通しました。前日の 9 月 3 日に開始準備（計画作成・整合性検証・GitHub 同期）を済ませています。

コミット 24 本、147 ファイル。**欠陥を 12 件見つけて直しました。**

## 判断と、その理由

### スパイクの結果が設計を変えた

IT1 から持ち越したスパイク（S3 へエクスポートした Event Store からの差分再投入）を Day 1 に置きました。稼働中の kind クラスタからエクスポートし、同じイメージの別インスタンスへ投入して確かめています。

**差分再投入は成立しました。** `minSequence` で切り出せ、投入したイベントは `id`・`dateTime`・`metaData`・`payload` が原本と完全一致します。

**しかし集約が復元できませんでした。** エクスポートに DCB のタグが含まれず、タグ無しで投入したイベントは集約のタグで検索すると 0 件になります。件数も内容も一致し、投影のリプレイも通るのに、集約だけが読めません。

これは「緑に見えるが何も見ていない」の変種で、**検証としては合格に見える**のが危険です。復元演習の合格条件に「復元した集約へコマンドを 1 本送って通ること」を足しました。

gRPC の API も調べ、読み出し側（`SourceEventsResponse` / `StreamEventsResponse`）がタグを含まないことを確かめています。REST の都合ではなく、**Axon Server から書いたタグを読み返す口が無い**という結論です。

### `@EventTag` は、書いてみるまで分からなかった

`Cargo`（状態を持つ最初の集約）で「同じ予約を 2 度受け付けない」を書いたら、`AxonTestFixture` でも実 Axon Server でも通りませんでした。

調べると、**イベント側に `@EventTag(key = ...)` が要る**。`@EventSourced(tagKey = ...)` は集約側の宣言でしかありません。付け忘れると集約は毎回空のまま復元され、状態を見る守りが丸ごと素通りします。

IT1 の `Shipper` は登録しかせず、**イベント列から復元した状態を見る判断が 1 つもありませんでした**。だから IT1 では出ませんでした。

さらに悪いことに、`AxonTestFixture` の `disableAxonServer()` ではタグ復元が働かないので、集約の単体テストでは判別できません。この 2 つが組み合わさると、守りを外しても緑のままです。実 Axon Server の統合テストに移し、`@EventTag` を外すと赤になることを確かめました。

### 受け入れテストを足したら、投影が止まっていた

US04 の受け入れシナリオを足したら、その前に走る「同じメールアドレスの荷主は要確認一覧に出る」の**後で投影が動かなくなっていました**。

原因は一意制約を例外で受けていたこと。PostgreSQL は制約違反でトランザクションを中断するので、`DuplicateKeyException` を捕まえても外側（投影とトークンの書き込み）が巻き添えになります。トークンが進まないため、**その 1 件で Processing Group 全体が止まり、以降のイベントが 1 件も反映されません**。

IT1 の受け入れテストはこれを見つけられませんでした。「要確認一覧に出る」ことだけを確かめていて、その後も投影が動き続けることを見ていなかったためです。要確認は別トランザクションで書くので、投影が死んでいても緑になります。

「重複で弾いたあとも投影は動き続ける」シナリオを足しました。

### クラスタに対する E2E が、モックの通す欠陥を捕まえた

イテレーションの途中でユーザーから「完了条件に kind ビルドと k8s での E2E も追加する」と言われ、DoD に入れて実際に通しました。

**S21 予約登録の荷主入力が UI 設計と食い違っていました。** 設計は「^山田商事 (SHP-000012)^」（選ぶ）ですが、実装は荷主 ID の直接入力です。単体テストもモックの E2E も通っていました。テストが ID を打っていたためです。営業は荷主一覧を開いて UUID を書き写すことになります。

実際に配ったものを踏んで初めて出ました。この 1 件だけでも、クラスタ E2E を入れた価値がありました。

**ただし終わりにだけ回したので、修正がクローズを押しました。** 次は途中で 1 度回します。

### 赤いゲートも疑った

SonarQube が `new_coverage` を 28.6% と出しました。各モジュールの JaCoCo は 68〜97% で合いません。

配線の欠陥が 2 件ありました。`check` が `jacocoTestReport` を呼んでおらず、Sonar が前のイテレーションのレポートを読んでいたこと。スキャンのラッパーが TypeScript 用の引数で Java の設定を上書きしていたこと。

**赤を鵜呑みにしてテストを書き足していたら、配線は壊れたままでした。** IT1 では「緑に見えて何も見ていない」欠陥を見つけましたが、今回は「赤く見えて実態と違う」形です。どちらも数字を疑うところから始まります。

### `ReplayIT` を、Reaction Handler を待たずに書いた

ADR-0001 のコンプライアンス欄が「`ReplayIT` は未実装」のまま 2 IT 続いていました。ADR は「最初の Reaction Handler を入れる変更で同時に書く」と定めており、IT2 でも Reaction Handler は入れていないので、条件としては未発動です。

しかし IT2 で投影が 3 つに増え、投影が `attention_item` への書き込みという**副作用**を持つに至りました。リプレイで何が起きるかは、Reaction Handler の有無に関わらず検査の対象です。

**書いた時点で実在の欠陥が出ました。** 弾かれた登録を読み直すたびに要確認一覧が増えます。識別子が `UUID.randomUUID()` で、同じ事実に毎回別の行を作っていました。`attention_item` は追記専用でリプレイでも消さないので、読み直しの回数だけ積み上がります。

**ADR の 1 行を「条件が来ていないから」と放置していたら、この欠陥は残りました。**

### 並列レビューが 2 回連続で返らなかった

IT1 と同じです。5 エージェントを起動し、10 分後に全員 idle、催促にも応答なし。

IT1 のふりかえりで書いた Try は「並列を使うなら、結果が届くまでクローズを確定しない」でした。今回それを守って待ちましたが、**最後まで届きませんでした**。

2 回とも届かない以上、Try の書き方が間違っていました。「届くまで待つ」ではなく「使わない」が正しい。逐次でも高 2・中 2 を出せています。

## 詰まったところ

### Axon Server の待ち時間が 3 か所に散っていた

起動猶予を 3 分から 6 分に延ばしたとき、`AbstractAxonIntegrationTest` だけを直しました。`CucumberSpringConfiguration` と `AxonServerOutageIT` が別の定義を持ったままで、**全体ビルドだけが落ち、単独実行では通る**形で出ました。原因を「環境の混雑」と読み違えて `--max-workers=1` を試し、それでも落ちてようやく散らばりに気づきました。

k8s 側（`startupProbe`）も 5 分のままで、こちらは再起動ループになりました。業務サービスが軒並み繋がらなくなり、見えるのは「投影が進まない」です。

Rule of Three は「重複コード」の話であって、**設定値には当てはまりません**。2 か所目が現れた時点で集めるべきでした。

### Axon Server は評価版で 12 時間で止まる

ユーザーからログを見せてもらって分かりました。`Trial access is limited to 12 hours. Shutdown scheduled at ...`。

止まると全サービスが繋がらなくなりますが、画面に出るのは「投影が進まない」です。`k8s:images` / `k8s:load` で毎回取り直し、`k8s:status` に停止予定時刻と残り時間を出すようにしました。

`kind load docker-image` は使えませんでした。公開イメージはマルチプラットフォームのマニフェストリストで配られており、`content digest ... not found` で失敗します。ノードの containerd に `crictl pull` で直接引かせる形にしました。

## 次に活かすこと

- **レビューは逐次を既定にする。** 並列は 2 IT 連続で返らなかった
- **受入基準を満たしたら、正典の数字・形とも突き合わせる。** 「5 回でロック」だけでなく「15 分」も見る。IT2 の食い違い 5 件のうち 2 件はこれで見つかった
- **入口で値を捨てる分岐を書いたら、捨てずに集約へ渡せないか考える。** 種別で分けて片方を `null` にする形は、黙って落とす経路になる
- **同じ設定が 2 か所に現れたら、その場で 1 か所に集めて検査を置く。** 3 か所目を待たない
- **クラスタ E2E をイテレーションの途中で 1 度回す**

# IT3 — 同じ日の続き

## 並列レビューは返らないのではなく、逐次に資源を奪われていた

前段で「レビューは逐次を既定にする。並列は 2 IT 連続で返らなかった」と書きました。**これは誤りでした。**

IT2 のふりかえりで「所要はおよそ 35〜40 分」と修正し、IT3 ではクローズ工程の**最初に**並列だけを起動しました。結果は **4〜6 分で全員から返着**。逐次のフォールバックを同時に走らせていたことが、遅延の原因だったと考えられます。

得られた指摘は高 11・中 18・低 9。**実欠陥 5 件はすべて並列レビューが見つけたもの**で、自分では 1 件も見つけていません。

## 「対応済みに見える」状態が 3 つ同時にあった

IT3 でいちばん学びが大きかったのはここです。

| 見かけ | 実際 |
| :--- | :--- |
| Javadoc「開放は Gateway の**ルートとロール**で行う」 | ルートだけ実装。**サーバ側の認可が 1 つも無い** |
| Javadoc「項目ごとに比べない。別物が読み直し扱いで黙って捨てられる」 | ヘッダしか比べておらず、**その事象そのものを起こしていた** |
| 並び順「誤配が先」＋コメント「誤配が先」＋正典「誤配は含める」 | 絞りが `ROUTE_PROPOSED` だけで**誤配は 1 件も出ない** |

IT2 で「『〜しない』コメントは赤で固定する」と決めました。今回破れたのは**肯定形**（「〜で行う」「〜まで比べる」）です。自分が書いた保証ほど疑いにくく、しかも文書・コメント・並び順の 3 つが揃うと「対応済み」に見えます。

**保証を書いたら、その変更の中でそれを破って赤を見る。書けないなら書かない。**

## 認可がまるごと無かった

`RequireRole` はフロントにあり、Gateway は JWT を検証してロールを後段へ伝えていました。**そこで止まっていました。** 認証さえ通れば誰でも航海を登録でき、全荷主の予約一覧を読めます。

`EveryServiceEndpointIsRoutedAndProtectedTest` は「認証で守られているか」しか見ておらず、この穴を見つける形になっていませんでした。**検査があると安心してしまう分、その検査が何を見ていないかを言えることが要ります。**

置き場所は Gateway の 1 か所にしました（ADR-0006）。宣言表を持ち、**宣言の無い経路は通しません**。載っていないものを許す形にすると、載せ忘れた経路ほど無防備になります。

## 記録したのに読めなかった

routingms は航海番号の重複を `attention_item` に記録しますが、読み出す REST がありませんでした。投影の単体テストは「行が入ったこと」しか見ないので緑です。

唯一のサインは `AttentionItemMapper.findOpenByRole` が**定義済み未使用**だったこと。IT2 で「定義済み未使用のドメインメソッドは配線漏れのサイン」と学びましたが、マッパーには適用していませんでした。同じことが `VoyageNumber`（20 文字の上限を持つのに本番から一度も呼ばれない）でも起きています。

## クラスタで配って初めて出たもの

E2E が 2 件出しました。ラベル「運送会社」が「運送会社コード」と前方一致で衝突して要素を特定できないこと、要確認一覧が 2 つの読み口を束ねるようになったのにキャプチャ側は片方しかモックしていなかったこと。

**どちらも単体テストは緑でした。** IT2 の「クラスタ E2E はモックが通す欠陥を捕まえる」がそのまま再現しています。ただし今回もクローズ前の 1 回だけで、途中では回せていません（2 IT 連続の未達）。

## 次に活かすこと

- **並列レビューはクローズの最初に起動し、逐次は走らせない**
- **レビュー結果が途中で切れていないか、表の最終行を確かめる**（5 通中 4 通が切れていた）
- **「〜する」と書いた保証も、その変更の中で赤を見る**
- **記録する先を足したら、読み口も同じ変更で足す**
- **件数や一覧を出すとき「これはその人の仕事か」を問う**
- **クラスタ E2E をイテレーションの途中で 1 度回す**（3 IT 連続の宿題）

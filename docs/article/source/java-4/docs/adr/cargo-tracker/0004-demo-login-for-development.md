# ADR-0004 開発環境のログイン画面に動作確認用の利用者を事前入力する

開発環境に限り、ログイン画面に動作確認用の利用者名とパスワードを事前入力し、担当（ロール）ごとの利用者を一覧して選べるようにする。既定は無効とし、ビルド時・起動時に明示的に有効化した成果物でのみ表示する。

日付: 2026-09-03

## ステータス

2026-09-03 提案されました

## コンテキスト

本システムは担当（ロール）によって見える画面が変わる。IT1 の時点で 7 ロールがあり、以降のイテレーションで各ロールの画面が増えていく。

IT1 の動作確認では次の手間が実際に発生した。

- クラスタでもローカルでも、利用者がひとりも入っていない状態から始まる。手順書に載せた `INSERT` 文を毎回貼り付けている
- どの利用者名がどの担当かが画面から分からない
- 無効化されたアカウントの挙動（`User.canSignInAt`）を試したくても、そのような利用者が存在しない

加えて、ログイン画面には CSS が一切当たっていなかった。ログイン後のシェル（`AppLayout`）は Tailwind が効いているのに、最初に見る画面だけが未装飾のまま残っていた。

一方で、認証情報が入力済みの画面を業務環境に出すことは避けねばならない。フロントエンドは SPA であり、この種の設定は**ビルド時に成果物へ焼き込まれる**。実行時の環境変数では取り消せないため、「本番のイメージにうっかり入る」経路を塞ぐ必要がある。利用者のシードも同じで、パスワードが分かっている利用者が業務環境の DB に入る経路を作ってはならない。

## 決定

1. **既定は無効とする。** 画面側は `VITE_DEMO_LOGIN_ENABLED=true` を**ビルド時に**渡した成果物でのみ、シード側は `cargo-tracker.demo-users=true` を渡した起動でのみ有効になる。**書き忘れたら安全側に倒れる**
2. **有効時は開発環境である旨を画面にはっきり表示する。** 事前入力していることを隠すと、本番同様の画面だと思い込まれる
3. **担当ごとの利用者を一覧し、選ぶと入力欄に反映する。** パスワードは一覧の全員で共通とし、その旨も画面に書く
4. **ログインできない利用者（`disabled01`）を一覧とシードの両方に用意する。** 一覧に載せる以上、実際にログインできないことまで確かめられなければ確認の役に立たない
5. **シードは Flyway の別ロケーション（`classpath:db/seed`）に置き、反復（`R__`）にする。** 業務のスキーマ（`db/migration`）と混ぜない。版付きにすると、あとから `db/migration` に新しい版を足したときに順序が前後して Flyway が止まる
6. **有効化するのは開発の 3 箇所だけとする。** ローカルの開発サーバ（`.env.development`）、ローカルのバックエンド起動（`dev:backend*` の起動引数）、kind クラスタ（フロントのイメージのビルド引数と authms の環境変数）

### 代替案

- **実行時の環境変数で画面を切り替える**: SPA では成果物に焼き込まれるため実現できない
- **シードを `db/migration` に置く**: すべての環境に入る。パスワードの分かっている利用者を業務環境へ持ち込むことになるので採らない
- **`cargo-tracker.production-like` を条件に流用する**: ローカルの kind クラスタはこれを `true` にしている（既知の JWT 鍵で起動しないため）。流用すると、まさに使いたい環境で無効になる。**別の目的には別のスイッチを置く**
- **一覧を出さず事前入力だけにする**: どの利用者名がどの担当かが分からないままなので、ロール別の確認という主目的が果たせない

## 影響

### ポジティブ

- 担当ごとの画面を、SQL を貼らずに切り替えて確認できる
- 無効化アカウントの挙動を画面から確かめられる
- 開発環境であることが画面から一目で分かる

### ネガティブ

- 開発環境の URL を知る第三者に、動作確認用の利用者名と共通パスワードが見える。開発環境には業務データを置かないことが前提になる
- ビルド成果物が環境ごとに変わる。「開発環境で動いたものをそのまま本番へ」という運用はできない

## コンプライアンス

決定ごとに検査を置く。文章のまま残る決定は守られない。

| 決定 | 検査 |
| :--- | :--- |
| 1（既定は無効） | `demoLogin.test.ts`（`demoLoginOf(undefined).enabled === false`。`"1"`・`"yes"` 等も無効）、`demoLoginIsOptIn.test.ts`（Dockerfile の `ARG` 既定・`.env` / `.env.production` に有効化が無いこと）、`AuthControllerIT`（既定のコンテキストに `DemoUserSeedConfiguration` が居ないこと） |
| 2（開発環境である旨） | `LoginPage.demo.test.tsx` |
| 3（選ぶと反映） | `LoginPage.demo.test.tsx`（一覧の利用者すべてが選べること） |
| 4（ログインできない利用者） | `demoLogin.test.ts`・`DemoAccountsMatchSeedTest`・`DemoUserSeedIT`（実際に 401 になること） |
| 5（シードの置き場） | `DemoUserSeedIT`（有効時に利用者が入り、共通パスワードで実際にログインできること） |
| 一覧とシードの一致 | `DemoAccountsMatchSeedTest`（画面の一覧とシードの SQL の顔ぶれが一致すること） |

**一覧とシードの一致を検査で固定するのは、食い違いが画面から決して分からないため。** 認証の失敗は理由を区別しない仕様なので、一覧に載っているのに DB に居ない利用者を選んだ人には「利用者名またはパスワードが正しくありません」としか出ない。

日付: 2026-08-22
対象: IT5（US09・US10・US11 と返済枠 9 件）の実装成果物（`git diff 2cc9246e9..5d83af8b9`・118 ファイル）

## 総合評価

ACL の型分離、ADR の決定ごとの検査、契約テストの双方向配置など、IT4 のふりかえりを反映した実装は水準が高い。一方で **高優先度の指摘が 12 件**出た。うち 5 件は「全テスト緑のまま業務が成り立たない」形であり、IT4 と同じ失敗の型（同じ規則が 2 か所にあって互いを隠す・踏まないパスは守られない）が再発している。

とくに重いのは次の 3 点。

1. **経路確定は実環境で必ず失敗する。** routingms の接続先の既定値が bookingms 自身を指しており、上書きがリポジトリのどこにも無い
2. **US10 の中心（期限を緩めて再算出）で見つけた経路は確定できない。** しかも返る理由は実際と違う（「航海スケジュールが変わっている可能性があります」）
3. **経路設計者の一覧が、割り当て済み・差し戻し済みの予約を落とす。** ADR-020 決定 3・決定 7 が詳細でだけ守られ、一覧では別の判定が書かれている

## エージェント別の要点

- **xp-programmer**: 「同じ規則が 2 か所にある」形が 3 種類（一覧と詳細の可視判定・期限判定の BC 間ずれ・出発下限）新たに入った。IT4 の Problem と Try 1 の再発
- **xp-tester**: 「実装を壊しても緑のまま」の穴が 6 か所。うち 1 件（モックの甘さ）はすでに実挙動としてバグが成立
- **xp-architect**: BC 独立性と ACL の設計は良質。同期呼び出しの「外側」（接続先・障害時の振る舞い）が設計の水準に追いついていない
- **xp-technical-writer**: 「まだできません」と書いた記述の棚卸しが仕組み化されていない。同型の取り残しが 4 件
- **xp-user-representative**: 中心の一本は業務に沿う。経路が組めない予約（＝いちばん手間のかかる予約）が業務として一周しない

# イテレーション 11 レビュー（US21・US22 精算管理）

- **実施日**: 2026-08-26
- **対象**: IT11 の全変更（`5a896cc0b..HEAD`。139 ファイル・10,468 行追加）
- **視点**: xp-programmer / xp-tester / xp-architect / xp-technical-writer / xp-user-representative
- **結果**: **高 11 件・中 20 件・低 10 件**。高 11 件はすべて対応済み

## 総合評価

新しい BC を立ち上げるイテレーションとして構造の質は高く、ADR-027 の各決定がコードの
コメントとテストに一対一で対応している。ACL の形（`RestRouteCandidateFinder` との相似）、
正典 3 点の同時更新、`application/port` に DTO を置いた ArchUnit 由来の判断、契約を
共有カーネルの 1 か所に置く形——過去 IT の教訓が反映されている。

一方で、**ADR-027 の決定が守られていない箇所が 3 件**あった。いずれも「決定を書いて
検査も置いたが、その決定が効く経路を通していない」形である（IT10 Try 2 の再発）。

- 決定 2（丸めは 1 か所）—— 画面が `Math.round` で税額を計算していた
- 決定 4（発行後は動かない）—— 金額を係数から毎回再計算していた
- 決定 4（同）—— 確定操作にトランザクション境界が無く、明細を欠いた請求書が残りうる

**経理担当者の視点からは「1 件の請求を作る流れは信頼できるが、精算業務としては未完成」**
という判定だった。探す・まとめる・出す・直すの 4 つが欠けている。

## 高優先度の指摘と対応（11 件）

| # | 指摘元 | 内容 | 対応 |
| :--- | :--- | :--- | :--- |

## 経理担当者からの申し送り（IT12 以降）

**「探す・まとめる・出す・直す」の 4 つが欠けている。**

| 優先 | 内容 |
| :--- | :--- |
| 高 | **取り消して出し直す（赤伝）**。桁違い・符号の逆は現実に起きる。「DB を直す」は監査に耐えない |
| 高 | **検索**（請求番号・荷主名・予約番号）と**発行月の絞り込み** |
| 高 | **請求書の印刷**。無いと数字を書き写して表計算で作ることになり、システムの金額と実際に送った請求書が食い違い始める |
| 高 | **輸出免税**。国際輸送の運賃は消費税が免除される。キャプチャに 37,800 円の消費税が乗っている |
| 中 | 確定ボタンの確認のひと手間・調整行の削除・過去の調整額の参照・「連絡済み」の記録・支払期限の表示 |

## 懸念事項（記録）

- **決定 4 に構造的な検査が無い**（architect）。`Invoice` に mutator が無いことは読めば
  分かるが、守る仕組みは規律だけ。IT12 で「取り消して出し直す」を入れるとき最も揺れる
- **`PaymentStatus` と「取消」の軸**（architect）。「金額を確定したか」を混ぜなかった判断と
  同じ理由で、「取消済み」も混ぜず別列にすると ADR-027 に追記しておくと IT12 で議論を
  繰り返さずに済む
- **基準運賃 50,000 円が暫定値であることが ADR-027 にしかない**（writer）。担当者が内訳を
  そのまま荷主に説明する前提なので、手引きにも 1 行要る
- **荷主へ連絡したかを残す場所が無い**（writer・user）。複数人運用で二重連絡か無連絡が起きる

## レビューの進め方について

**5 視点とも、最初は idle 通知だけで本文が届かなかった**（IT10 と同じ）。全員に再送を
求め、programmer → writer・tester・user → architect の順に届いた。architect は 4 度目の
督促で届いている。

**待った価値はあった。** programmer だけで打ち切っていれば、決定 4 が守られていない
3 件のうち 2 件（金額の再計算・トランザクション境界）を見逃していた。

# イテレーション 14 レビュー

| 項目 | 内容 |
| :--- | :--- |
| 対象 | US34（5 SP）・US35（3 SP）。simulationms の新設と、シミュレーション由来の識別・除外 |
| 実施日 | 2026-08-31 |
| 視点 | programmer / tester / architect / technical-writer / user-representative の 5 並列 |
| 結果 | **高 12 件**（10 件対応・2 件は IT15 へ明示的に送る）・中 30 件（8 件対応）・低 12 件 |

> **このイテレーションのレビューは、実装が「動く」ことと「壊れない」ことの差を突いた。**
> 実環境で 14 工程すべてが成功し、CI も SonarQube も緑だった状態から、
> **運用で確実に起きる壊れ方が 5 つ**見つかっている。

## 高優先度の指摘と対応

### 対応した（10 件）

| # | 視点 | 指摘 | 壊れ方 | 対応 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | programmer・tester・architect・user | **中断した実行が永久に「実行中」になり、そのシナリオが二度と実行できない** | 想定外の例外（名簿に無いロール・数値でない識別子）や Pod 再起動で工程を 1 つも記録せずに抜けると、二重実行の拒否が永久に効く。復旧手段が DB を手で触ることしか無い | 想定外の例外も工程の失敗として記録する＋15 分音沙汰の無い実行は実行中とみなさない。両方に検査を置いた |
| 2 | programmer | **`simulated` を要求本文だけで立てられる** | 営業が誤って（あるいは意図的に）送ると、その荷主の貨物は精算の締めに一生載らない。警告も出ず請求漏れとして残る | 設定で許した利用者だけが立てられるようにした（名簿は許可する側。載せ忘れは「動かない」側に倒れる）。残る穴（実在の営業利用者本人は今も送れる）は ADR に明記し IT15 へ |
| 3 | programmer・architect | **本番判定の名簿が fail-open** | 「本番相当」を名簿にすると、載せ忘れた環境で動く。環境を増やす人がこのクラスを開く理由が無い | 名簿を**許可する側へ反転**。未知のプロファイルは起動を失敗させる。`preprod`・`本番` でも落ちることを検査で固定 |
| 4 | programmer | **`app.simulation.enabled=false` が何も無効化しない** | 「安全側に倒したつもり」の環境が実行を受け付ける | 無効な環境では実行そのものを 503 で断るようにし、検査を置いた |
| 5 | programmer・tester | **「工程ごとにログインし直す」を固定する検査が何も固定していない** | ロールの値を比べるだけで、切符を使い回す実装に戻しても緑。ADR のコンプライアンス表はこの検査を名指ししていた | 2 工程を実際に流し、ログインが 2 回・別の利用者として飛ぶことを固定 |
| 6 | tester・programmer | **常に真の空振りアサート 2 件**（`Optional` に `isNotNull`／`isNotEqualTo(Optional)`） | 「それまでの記録は残る」「終わった実行は実行中でない」が何も守られていない | 判別する形に書き直した。書き直した結果、**共有 DB で他テストの実行が混ざって判定対象が入れ替わっていた**ことも露見し、シナリオ名をテストごとに分けた |
| 7 | tester | **引き継ぎの検査が受け取る側を見ていない** | `context.put` を消しても緑 | 受け取った側の context をアサートする形にした |
| 8 | tester・user | **識別子を全部リンクしても緑**／状態と終了時刻を画面が捨てていた | US35-4 の情報が画面に出ない | 繋がないことまで見る検査を追加。状態・終了時刻を見出し行に出した |
| 9 | tester | **モックが本物より甘い**（知らないシナリオを 201 で受ける／失敗した実行を一度も踏まない） | 断られたときの見え方・止まった理由の見え方が未検証 | モックを 400 で断る形にし、失敗した実行を置いて E2E で踏ませた |
| 10 | writer・programmer・architect | **ADR-030 のコンプライアンス表 決定 3 が「未実装」のまま** | ADR 自身が定める「承認済みの条件」を満たさない | 決定 3〜5 を実在する検査名で埋めた |

### IT15 へ明示的に送る（2 件）

| # | 視点 | 指摘 | 送る理由 |
| :--- | :--- | :--- | :--- |
| 11 | user・tester | **追跡管理者の未解決例外一覧に `SIM-` 由来が混ざる** | trackingms は荷主コードを持たず、問う経路の設計が要る。IT14 の当初計画から持ち越しとして ADR に明記済み。**当座の手当てとして、実行画面とマニュアルに「例外一覧には出る・追跡管理者に一報」を明記した**（伏せていたのを直した） |
| 12 | user・architect・programmer | **実行が同期 HTTP 1 本**（14 工程・最悪数分）で、進捗が見えない | `202 Accepted` + 既存の `GET /{runId}` への分割は US37（ランダム連続実行）で必ず要る。IT15 で設計ごと変える。現状は実測 8 秒で、実演には耐える |

## 中優先度（30 件・要約）

対応した 8 件は、シナリオ ID の日本語化・進捗の分母表示・工程数の表記統一（12/9 → 14）・
`SimulationUsers` の案内キー誤り・マニュアルの項目表と赤帯の説明・章一覧の欠落・
ui_design の画面詳細節と権限マトリクス行。

送るもの（主なもの）:

- `MyBatisSimulationRunRepository.scenarioOf` の全件読み（`findRecent(Integer.MAX_VALUE)`）。
  工程数は呼ぶ側から渡す形に直したため**実行開始のたびの全件読みは消えた**が、復元経路には残る
- `simulation_run.status` / `finished_at` が更新されない死んだ列。API は集約から導くため正しいが、
  **DB を直接見る人には全実行が実行中に見える**。IT15 で更新するか列を落とすかを決める
- 実行 ID の `COUNT(*)+1` 採番は、US37 の同時開始で UNIQUE 衝突する
- `SIM-` の判定が 3 か所（定数 1・SQL リテラル 2）。帯を変える日に片方が残る
- **識別子の種別が読めない**（user）。詳細画面は番号を素の文字列で出すだけで、
  何番号かは工程名から推測するしかない。現場では管理者が自分で開くのではなく
  **営業に番号を伝える**ため、種別の表示とコピーできる形が要る
- シナリオを選べない（実際は 1 本の決め打ち）。US34 の文面と画面の食い違い
- 一覧の絞り込み・終了時刻・全体所要が無い
- 決定 2 の検査に「HTTP を投げてよいのは誰か」が無い（別クラスが `RestClient` を直接使える）
- 決定 5 を守る検査が `@Transactional` の付け直しに反応しない

## 低優先度（12 件・要約）

`steps VARCHAR(500)` の余裕、`substring` がサロゲートペアを割りうる、`RestBusinessGateway` が
380 行で `call(...)`＋応答検査が 6 回反復（US37 で分割の潮時）、`BODY_LIMIT` の根拠コメントと
実際の列型（`TEXT`）の食い違い、マニュアルの見出し表記ゆれ、実行者がログイン名のまま。

## 良かった点（各視点から）

- **BC 独立性は物理的に断たれている**（`build.gradle` の依存が `shared` のみ）。層の配置と
  ArchUnit の適用漏れは無い（architect）
- 障害の伝播は工程単位に閉じており、再送なし・期限ありの方針は正しい（architect）
- ドメイン層の不変条件とコメントの質が高い（programmer）
- ロール別到達性（`ROLE_ADMIN` のみ・navbar とダッシュボードの両方に入口）は問題なし（user）
- 表記規約（ですます調・半角スペース・絵文字なし）は全ファイルで守られている（writer）
- `SIM-` の見え方の表が ADR と実装に一致している（writer）

# イテレーション 4 ふりかえり

対象: US08（経路候補算出）= 8 SP
期間: 2026-08-21（IT4）

## 実績

| 項目 | 計画 | 実績 |
| :--- | :--- | :--- |
| ストーリーポイント | 8 SP | 8 SP（100%） |
| 理想時間 | 121h（うち返済枠 28h・マニュアル 9h） | 計画どおり + レビュー手直し |
| ベロシティ | 8 SP（実効値） | **8 SP** |
| IT1〜IT4 の平均 | — | **8.75 SP / イテレーション** |

> ストーリー分は 8 SP / 79h = 1 SP あたり 9.9h で見積もり、そのとおりに収まった。IT3（6.9h）より
> 重い見積もりを立てたのは正しかった。US08 はグラフ探索と制約充足を含み、設計ドキュメントの
> 欠落が 16 件あった。

> **クローズ時のレビュー手直しは SP に計上していない。** 高優先度 14 件の対応に相応の工数が
> かかっている。IT3 に続き 2 回目であり、**もはや例外ではなく常態**である（Problem に記載）。

### 満たしていない受入基準

| 受入基準 | 扱い |
| :--- | :--- |
| 「経路候補ごとに**費用**が表示される」の**正しい料金** | 概算を出し、画面に概算と明記した。実料金は US21（IT11） |
| 「制約条件を考慮した」のうち**港湾制約** | **持たないと決めた**（[ADR-018](../adr/018-route-search-rules.md) の決定 3）。先送りではなく決着 |
| 候補の**選択・確定・予約への紐付け** | US09・US11（IT5）。IT4 は一覧の表示まで |

## Keep

### 設計ドキュメントの欠落を、着手前に 16 件洗い出した

`validating-iteration-plan` と `validating-design` を着手前に回したことで、実装を始める前に
16 件の欠落・矛盾が見つかった。**そのすべてを同じイテレーションのうちに反映した**（アーキテクトの
突合で 15 件反映済み・1 件部分的と確認）。IT3 は 6 件だったので、検証の網が広がっている。

とくに `RouteSpecification` が Booking Context に同名で存在することを着手前に見つけ、**改名を
決めてから実装した**のは効いた。IT5 の ACL で変換の両端が同じ名前になる事故を避けられた。

### 否定の決定を検査に落とす形を見つけた

「港湾制約を持たない」を、許可リスト方式（表と型が現れないことを検査する）で固定した。
ADR-018 は当初「否定の決定であり検査に落とせない」と書いていたが、**同じイテレーションの隣で
経路候補の非永続化を同じ方式で検査していた**。テクニカルライターがそれを突き合わせて指摘した。

**文章は読まれなければ効かないが、テストは読まれなくても効く。**

### 実バックエンドでだけ再現する欠陥を、見つけた場所に固定した

認可より先に型変換が走る欠陥は MockMvc では再現しなかった。単体の検査は緑のまま通る。
kind に対する検査へ回帰を置き、壊れた日付・未知の列挙値・数値でない上限のいずれでも
403 になることを固定した。

### 期限の型を先に決め、両端で確かめた

「期限は日付で受け取り、業務タイムゾーンの当日終わりまで」を ADR-017 の決定として先に置き、
画面・サーバ・モックの 3 つで端をそろえた。IT3 で実バックエンドでだけ落ちた形（日付を送り
日時で受ける）を繰り返さずに済んだ。

## Problem

### 4 つの安全装置が、壊しても赤にならなかった

IT3 の Try「安全装置は破るテストで固定する」を DoD に入れて臨んだにもかかわらず、テスターが
変異テストで実測すると次の 4 つが緑のままだった。

| 安全装置 | なぜ判別しなかったか |
| :--- | :--- |
| 積み替えの最低 6 時間（探索側） | 値オブジェクト側にも同じ検査があり、二重に見えた。実際は探索が先に弾くため値オブジェクトの検査に到達しない |
| 積み替え上限（探索側の打ち切り） | 条件側の判定が生きていれば結果が変わらない |
| 積み替え上限（条件側の判定） | 探索側の打ち切りが生きていれば結果が変わらない |
| 出発の下限 | そもそも実装されていなかった |

**「同じ規則を守る箇所が 2 つあると、互いを隠して両方とも無検査になる」**という形は、今回はじめて
言語化できた。カバレッジは `TransitPathFinder` で 96% line / 88% branch あったが、3 種類の変異が
すべて緑だった。**カバレッジは判別力の根拠にならない。**

### IT2・IT3 で指摘された「一覧は毎朝どう使うか」が、新しい画面で再発した

航海スケジュールの一覧は IT3 で「既定は本日以降」に直した。ところが IT4 の経路探索には出発の
下限が無く、**すでに出港した便を使った経路が候補の 1 位に出た**。古い便ほど日数計算上は早く着く
ため上位を占める。

同じ教訓を 3 回受けている（IT2 の荷主一覧・IT3 の航海一覧・IT4 の経路候補）。**画面ごとに学び直して
いる**。規約（`ui_design.md` の一覧規約）に書いたのは IT4 だが、書いた本人が同じ IT で破った。

### ADR に存在しない決定を、コードとドキュメントが引用していた

`RouteSearchSpecification` のコメントと `domain-model.md` が「3 回以上は候補にしない（ADR-018）」と
書いていたが、**ADR-018 にその決定は無かった**。しかも画面は 3 回を緩和の既定として勧めており、
規則と操作が食い違っていた。

IT3 の Try「ADR は決定の数だけ検査を用意する」は守った（決定に検査を付けた）が、**逆向き
（検査やコメントが、存在しない決定を引用する）は見ていなかった**。

### 認可の順序を決めた ADR を起こした同じ IT で、新しいエンドポイントが同じ欠陥を持った

ADR-016 は IT4 で「認可を入力検証より先に」を決め、ArchUnit の検査まで作った。その検査は
`@Valid` の有無しか見ないため、**`LocalDate` や列挙型で受け取ることによる型変換の失敗**を
素通りした。決定は正しく、検査は本命の失敗モードを外していた。

さらに ADR-016 は「適用漏れはメタテストが検出する」と書いたが、**メタテストの名簿に載せて
いなかった**。名簿方式を避けると書いた ADR が、名簿方式で漏れていた。

### レビューの手直しが 2 IT 続けて大きい

IT3 は高 11 件、IT4 は高 14 件。いずれも SP に計上していない。**「開発が終わってからレビューで
見つける」形が定着している**。ベロシティは計画どおりに見えるが、実際にはレビュー後の工数が
毎回上乗せされている。

### モックが 240 行のドメイン規則を写している

経路探索のモック（MSW）は、探索・推奨順・費用式・積み替え時間をサーバと同じ規則で書き直した
第二の実装になっている。**写しである以上、いつか必ずずれる。** 今回は「モックを本物より甘く
しない」ために意図して写したが、実物との突き合わせ（real-backend の検査）が候補の内容まで
見ていないため、ずれを捕まえる網は無い。

## Try

| # | 改善アクション | 期待効果 | 反映先 |
| :--- | :--- | :--- | :--- |
| 1 | **同じ規則を守る箇所が 2 つあるときは、片方ずつ壊して確かめる**。二重の守りは、互いを隠して両方とも無検査になる | 二重に見えて無防備、という形を作らない | IT5 の DoD |
| 2 | **カバレッジの数値を判別力の根拠にしない**。新しい安全装置は、必ず壊して赤を確認してから採用する（件数ではなく 1 つずつ） | 96% でも変異が全部緑、という状態を放置しない | IT5 の作業手順 |
| 3 | **一覧・候補を出す画面を作ったら、その場で「終わったものが混ざらないか」を確かめる**。規約に書くだけでは守られない。**チェックを DoD の独立項目にする** | 同じ教訓を 4 回目に持ち越さない | IT5 の DoD |
| 4 | **コードとドキュメントが ADR を引用したら、その決定が実在するか確かめる**。決定の数だけ検査を用意する（IT3 Try 7）の逆向きも見る | 存在しない決定を引用したまま運用しない | `creating-adr` の手順 |
| 5 | **横断的な規則（認可・検証の順序）を ADR にしたら、その規則が破られる経路を 2 つ以上挙げてから検査を書く**。1 つ塞いで満足しない | 決定は正しいが検査が本命を外す、を避ける | `creating-adr` の手順 |
| 6 | **メタテストの必須一覧に載せるところまでを「検査を作った」と呼ぶ**。規則を書いただけでは適用漏れを検出できない | 名簿方式を避けると書いた ADR が名簿で漏れる、を繰り返さない | IT5 の作業手順 |
| 7 | **実バックエンドでのみ再現する形（型変換・タイムゾーン・DB 方言）を、着手時にリストとして持つ**。MockMvc や MSW で再現しないものを先に知っておく | 「単体は緑・実物で落ちる」を減らす | IT5 の作業手順 |
| 8 | **モックがサーバの規則を写すときは、実物との突き合わせを同じ変更で用意する**。写しを増やすなら、ずれを捕まえる網も増やす | 第二の実装が黙ってずれる状態を作らない | IT5 の作業手順 |
| 9 | **レビュー手直しの工数を見積もりに入れる**。2 IT 続けて高 10 件超が出ている。返済枠と同じく、最初から枠を取る | ベロシティが「計画どおり」に見えて実は超過している状態をやめる | IT5 の計画 |

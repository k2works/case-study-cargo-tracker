# イテレーション 14 ふりかえり

| 項目 | 内容 |
| :--- | :--- |
| イテレーション | IT14（2026-11-16 〜 2026-11-29 想定・**Release 2.2**） |
| 対象 | US34（5 SP）・US35（3 SP）= **8 SP** |
| 実績 | **8 SP（達成率 100%）** |
| レビュー | [高 12 件・中 30 件・低 12 件](../review/イテレーション14_review_20260831.md)。高は 10 件対応・2 件は IT15 へ明示的に送った |

## Keep

### 1. 「確かめる仕組み」を、確かめられる形で作った

本 IT が作ったのは**業務そのものではなく、業務が通っているかを確かめる仕組み**である。
この種の仕組みは、作り方を誤ると**確かめているつもりで何も確かめていない**状態になる。

[ADR-030](../adr/030-business-simulation-execution.md) 決定 2 で先に「専用の書き込み経路を
作らない」と決め、**出口を 1 ポートに絞ってソースを読む検査で固定した**。ArchUnit では
文字列で書かれた URL の向き先が映らないため、型の依存を見る検査だけでは守れない性質だと
判断してのことである。検査が本当に赤くなることも、禁じた文字列を仮に入れて確かめた。

### 2. 実環境の枠が、また実環境でしか出ない欠陥を捕まえた

Phase 6.3（実環境で 1 本通す）で、**simulationms のマニフェストが `billing_db` を
向いていた**ことが分かった。写して作った manifest で接続先だけ直し忘れた形である。
ユニット・結合・モックはすべて緑だった。

止めたのは Flyway の検証（他サービスの履歴と食い違って落ちた）だが、**履歴が無い相手なら
他サービスのデータベースにテーブルを作っていた**。偶然に頼らず、マニフェストから接続先を
読んで自分の名前のデータベースを向いていることを確かめる検査（`ServiceDatabaseUrlTest`）に
落とし、壊すと赤くなることも確かめた。

IT5・IT12・IT13 の「接続先が localhost を向いていて実環境だけ 500」と**同じ族の欠陥**である。
族が同じなら検査も 1 か所にまとめられる、というのが今回の学びである。

### 3. 検査が実装より先に、8 回誤りを見つけた

| # | 捕まえた検査 | 何を見つけたか |
| :--- | :--- | :--- |
| 1 | `ArchitectureRuleCoverageTest` | 新サービスの ArchitectureTest 欠落 |
| 2・3 | `AuthenticatedUserFilterRegistrationTest` | フィルタ未登録、ヘッダ必須の検査そのものの欠落 |
| 4 | 方言スモーク | `TIMESTAMPTZ` を H2 が解釈しない。加えて `foreach` を含む動的 SQL が検査から漏れていたことも露見 |
| 5 | `jacocoTestCoverageVerification` | ドメイン層 90% 未達（未使用の `restore` を書いていた＝ TDD 違反） |
| 6 | `ServiceEndpointConfigTest` | Gateway の所在を渡す環境変数の命名（`APP_*_SERVICE_BASE_URL` に合わせて改名） |
| 7 | マニフェスト整合の検査 | マニュアル 15 章の欠落（メニューを足した時点で赤くなった） |
| 8 | `ServiceDatabaseUrlTest` | 上記 Keep 2 の接続先違い |

### 4. 決定を、実装しながら 1 つ改訂した

[ADR-030](../adr/030-business-simulation-execution.md) 決定 3 は当初「荷主コードの `SIM-` 帯
**と** `shipper.simulated` 列」だったが、**帯 1 本に絞った**。両方持つと食い違う行が生まれ、
どちらが正しいかを決める規則がまた要る。**決定は書いたあとも直せる**——直した理由を
ADR に残せば、後から読む人は「なぜ列が無いのか」を辿れる。

### 5. 負債を落とすときに、落とした先を ADR に書いた

追跡の未解決例外一覧からのシミュレーション由来の除外は**できていない**（trackingms は
荷主コードを持たない）。これを「対応済み」に丸めず、ADR とマニュアルの両方に
「今後の課題」として書き、IT15 の対象に入れた。マニュアルの表には
「未解決の例外：出ます（今後の課題）」と利用者向けの言葉でも書いている。

## Problem

### 1. ローカルで一部だけ測って、全部を測った気になった

Phase 3.1 で `./gradlew :simulationms:test --tests '*SimulationArchitectureTest*'` と
**絞って実行**し、緑を見て push した。`--tests` を付けると
`jacocoTestCoverageVerification` は走らない。**CI が新パッケージのカバレッジ 0.00 で落ちた**。

IT13 の Try 5'（品質ゲートの後に大きな変更を入れたら、ゲートを測り直す）と**同じ形**である。
今回は「一部だけ測って全部を測った気になる」版だった。

### 2. 足した項目が、それを知らない既存の呼び出しを 15 件まとめて壊した

`ShipperRequest` に `simulated` を**基本型の `boolean`** で足したところ、この項目を送らない
既存の荷主登録が `Cannot map null into type boolean` で 400 になった。
`ShipperControllerTest` が 15 件赤くなって気づいた。

**足す側の視点しか持っていなかった**。省略できる形（`Boolean`）にするという判断は、
「この項目を知らない呼び出しが既にいる」と考えて初めて出る。

### 3. kubectl の既定コンテキストが、運用タスクの向き先と違っていた

運用タスク（gulp）は `kind-cargo` を明示して使うが、素の `kubectl` は `docker-desktop` を
向いていた。**素の `kubectl apply -k` を打って、意図しないクラスタに 8 つ目のサービスを
作った**（気づいて削除した）。運用手順書のタスクを使っているうちは起きないが、
調査のために素のコマンドへ降りた瞬間に起きる。

### 4. シミュレーションが登録した航海は、荷主から辿れない

決定 3 は「貨物・請求書・追跡はすべて荷主から辿れる」を前提にしていたが、**航海だけは
荷主に紐づかない**。まっさらな環境では航海が 1 本も無く、無いと経路候補が 0 件になるため
シミュレーションが自分で登録する必要があり、その航海は経路設計者の一覧に並ぶ。

**前提の外にあるものが 1 つあった**。名前（`V-SIM-`）で見分けられるようにしたうえで、
「見えることを選んだ」と ADR に書いた。

### 5. 「動く」と「壊れない」の差が、レビューで 5 件出た

実環境で 14 工程すべてが成功し、CI も SonarQube も緑になった状態から、
**運用で確実に起きる壊れ方**が 5 つ見つかった。

| 何が起きるか | なぜ緑をすり抜けたか |
| :--- | :--- |
| 中断した実行がシナリオを永久にブロックする | 想定外の例外を投げるテストが無かった。正常系と「業務 API が断る」系しか踏んでいない |
| 由来のフラグを要求本文だけで立てられる | 「シミュレーションが立てる」経路しか考えず、**他の誰かが立てる**経路を考えていなかった |
| 本番判定が fail-open | 名簿を書いた自分は載せ忘れない。載せ忘れるのは**将来この場所を知らない人**である |
| 無効化の設定が何も無効化しない | 設定の名前が守っているつもりになっていた（起動時の検査にしか使っていない） |
| 決定を固定する検査が何も固定していない | ADR の表に名前を書き、名前の実在は機械で確かめたが、**中身が判別するか**は誰も見ていなかった |

**5 件のうち 4 件は、自分が書いたコメントや決定が「守られているつもり」だった箇所**である。
IT10 の教訓（コメントは仕様として読み、実装と突き合わせる）は、**自分が今書いたばかりの
コメント**にはまだ効いていない。

## Try

### 1. push 前は、必ず絞らずにビルドを回す（Problem 1）

`--tests` で絞った実行は**調査のためだけに使う**。push 前は `TZ=UTC ./gradlew build`
（フル）を回す。IT15 の DoD に「push 前のフルビルド」を明記する。

**期待効果**: カバレッジ検証・Checkstyle・ArchUnit が走らないまま緑と誤認する経路を塞ぐ。

### 2. 既存の呼び出しに項目を足すときは、送らない呼び出しを 1 つ書く（Problem 2）

API の要求に項目を足す変更では、**その項目を送らない要求のテストを同じ変更の中で足す**。
省略できる形にするか、既定値を持つかの判断が、そこで初めて必要になる。

**期待効果**: 「足した項目が既存の呼び出しを壊す」形を、赤で先に見つける。

### 3. 素の `kubectl` を打つ前に、コンテキストを確かめる（Problem 3）

調査で素のコマンドに降りるときは、まず `kubectl config current-context` を見る。
運用手順書に「素の kubectl を使う場合は `--context kind-cargo` を必ず付ける」を追記する。

**期待効果**: 意図しないクラスタへの適用を防ぐ。

### 4. 「族が同じ欠陥」は 1 つの検査にまとめる（Keep 2）

接続先の取り違え（相手サービスの所在・自分のデータベース）は 4 度出た。
`ServiceEndpointConfigTest` と `ServiceDatabaseUrlTest` の 2 本になっているので、
**次に同じ族が出たら 3 本目を作らず既存に足す**。

**期待効果**: 「どこを見れば接続先の約束が分かるか」を 1 か所に保つ。

### 5. 検査を書いたら、その場で壊して赤を見る（Keep 5）

ADR のコンプライアンス表に名前を書く検査は、**書いた直後に対象を壊して赤を確かめる**。
本 IT では `SimulationArchitectureTest` と `ServiceDatabaseUrlTest` でこれを行い、
行わなかった `logsInAgainForEachRole` が**何も固定していなかった**。差は工程 1 分である。

**期待効果**: 「表に名前がある」と「守られている」の差を、書いた本人がその場で潰す。

### 6. 前提の外にあるものを、決定のたびに 1 つ探す（Problem 4）

「すべて〜から辿れる」と書いたら、**辿れないものを 1 つ探してから決定を確定する**。
今回は航海がそれだった。ADR のテンプレートに「この決定の前提の外にあるもの」の欄を置く。

**期待効果**: 決定を書いた直後に例外を見つけられる（実装中に気づくより安い）。

# イテレーション 9 ふりかえり（KPT）

日付: 2026-08-25
対象: IT9（US29 通関申告の登録・管理／US30 輸送中の予約キャンセル承認、10 SP／返済枠 14 件）

## サマリー

計画 10 SP を達成し、**通関という関門が引取の前に立った**。US16 の引取は IT7 以来
「荷受人の確認」だけが歯止めで、通関書類は目視に委ねられていた。あわせて輸送中の予約に
承認フローが入り、船の上の貨物が行き先を失ったままキャンセルされる経路を塞いだ。

**返済枠は 14 / 14 完了**（3 IT 連続で全返済）。

本 IT で最も重かったのは、**サービス単体のテストが全部緑のまま、画面と実環境でだけ
成り立たない**欠陥が 5 件出たことである。

1. **営業の画面にキャンセル申請の入口が出なかった** — 集約に述語はあるのに、応答の操作
   一覧に載せていなかった。モックだけがその操作を返していた
2. **`/api/v1/cancellations` が Gateway のどこにも振られていなかった** — 画面からは 404、
   サービス側は無実。**本番プロファイルでは公開追跡とロック解除も同じ状態だった**
3. **E2E が新しいガードの手前で止まり、以前からの守りを踏まなくなっていた** — 通関ガードが
   先に立ったため、「荷受人の確認」を外しても緑のままになる状態になっていた
4. **US29-6（ダッシュボードの件数）が未達だった** — API もフックも用意されているのに、
   どこからも呼ばれていなかった。**受入基準に書いてあり、DoD にもチェックを付けていた**
5. **陸揚げ候補に通過済みの港が残っていた** — コメントは「次の寄港地」だが、実装は旅程の
   全区間から採っていた。船が二度と寄らない港での荷降しを承認できる

4・5 は**遅れて届いた 2 視点のレビュー**が見つけた。

## Keep（続けること）

### 1. 実環境で通す枠（Phase 6）を計画に置く

IT8 の Try がそのまま効いた。上の 1・2 は**この枠が無ければ IT10 以降に持ち越されていた**。
どちらも「API のテストは 200 を返すので緑」「サービスのテストは自分の中では正しいので緑」
であり、**画面と Ingress を通して初めて姿を現す**。

IT8 はこの枠で 1 件、IT9 は 3 件を捕まえた。**枠の価値は上がっている。**

### 2. ADR の決定ごとに検査を置き、1 件ずつ壊して赤を確認する

ADR-025 の 10 決定すべてで実施した（IT8 は 11 決定のうち 3 件が空振り）。**壊した記録を
表に残す**ことを完了条件にしたのが効いた——「検査名を書いた時点では未完了」と決めていな
ければ、また同じ空振りが残っていた。

### 3. 設計との突合を検査に落とす（返済枠 0.1）

`data-model.md` の DDL と Flyway のマイグレーションを突き合わせる検査は、**置いた直後に
13 件の実ドリフト**を指した。列挙して約束する形（IT8 は 13 件中 12 件が未反映）とは、
残るものが違う。

## Problem（問題だったこと）

### 1. 画面を通す検査が、API を通す検査より薄い

上の Keep 1 で捕まえた 3 件は、いずれも**画面を通していれば早く出た**。IT9 の受け入れ
テストは API を直接叩く形が中心で、画面から踏む形は限られていた。

`availableActions` に依存する画面は今後も増える。**サーバが値を載せ忘れると画面には何も
出ないが、API は 200 を返す**——この形は構造的に再発する。

### 2. 検査の入力を宣言し忘れると、壊しても緑になる

`BookingActionRosterTest` は画面の型とモックを読むが、Gradle の入力に宣言していなかった
ため、**モックだけを壊しても検査が動かなかった**。返済枠 0.1 で同じ落とし穴を踏み、
対処法まで分かっていたのに、**新しい検査を書くときに再現した**。

### 3. 型検査が何も見ていなかった

`tsc --noEmit` は、プロジェクト参照構成（`files: []` + `references`）では**何も検査せず
終了 0 を返す**。未定義の関数を呼んでも通る。IT9 のクローズで初めて気づいた。

**緑を見て安心していた分、検査が無いより危ない。** 型検査は `tsc -b` である。

### 4. 5 視点の結果を待たずに「クローズ完了」と宣言した

クローズのステップ 1 で 5 エージェントを並列起動したが応答が返らず、5 つの観点を単一の
レビュアーが順に通す形に切り替えてクローズを完了と宣言した。**その後、2 視点の結果が
遅れて届いた**（user-representative・tester）。

**そこに高 2 件が入っていた。**

- **US29-6（ダッシュボードに件数が現れる）が未達**。API もフックも用意されているのに、
  どこからも呼ばれていなかった。**定義済みで未使用のフックは配線漏れのサイン**である
- **陸揚げ候補に通過済みの港が残る**。コメントは「次の寄港地」だが、実装は旅程の全区間の
  荷降し地を候補にしていた。船が二度と寄らない港での荷降しを承認できる

どちらも単一レビュアーでは見つけられなかった。**独立した視点は、待てば働いた。**

宣言が早すぎたことのほうが問題である。「エージェントが返らない」は「結果が無い」では
なく「まだ来ていない」だった。

残る 3 視点は催促を含めて 2 度依頼しても応答が無く、そこで待つのを打ち切っている。
代わりに、**遅着分の指摘を手がかりに同じ観点で自分でも見直した**——「コメントが正しく
実装だけが違っていた」形を探し、「復元では検査しない」が宣言されているだけで検査が
無いことを見つけた（レビュー #24）。**遅れて届いた指摘は、それ自体の価値に加えて
「次にどこを見るか」を教える。**

### 5. 受入基準の達成を、DoD のチェックだけで判定していた

US29-6 は計画にも DoD にも書いてあり、チェックを付けた。**それを確かめる検査が無かった。**
書いてあることと、動いていることは別である。IT8 の教訓「DoD は条件を書き写さず引用する」
の次の段——**引用した条件を検査に結び付ける**——が要る。

### 6. 部分実行のあとにスキャンして、カバレッジが急落した

遅着レビューへの対応中、`--tests` で 1 クラスだけ実行した状態で SonarQube を回したところ、
**全体カバレッジが 91.4% → 54.3%** に落ちて品質ゲートが赤になった。JaCoCo のレポートが
その 1 クラス分しか無い状態で渡っていた。

**数字が動いたら、まず測り方を疑う。** 実装は何も変わっていなかった。フルの
`./gradlew build` で作り直したら 91.0% に戻っている。

### 7. 新しいガードが、以前からの検査を空振りにする

通関ガードを引取の手前に置いたことで、「荷受人の確認がない引取は断られる」テストが
**通関の段階で止まる**ようになった。テストは緑のまま（断られること自体は変わらない）
だが、**確かめたかった守りには一度も届いていない**。

守りを 1 段足すたびに、その後ろにあった守りの検査は同じ形で空振りしうる。

| 3 | **新しい検査コマンドを使い始めたら、一度壊して赤になることを確かめる**（Problem 3） | 何も見ていないコマンドを「緑」と読み違えない | IT10 の DoD |
| 4 | **ガードを 1 段足したら、その後ろにある守りの検査が今も踏まれているか確かめる**（Problem 7）。前提を作ってから確かめる形に直す | 守りを足すたびに、以前の守りが静かに無検査になるのを防ぐ | IT10 の進め方 |

## 次イテレーション（IT10）への引き継ぎ

1. **通関一覧を「毎朝の待ち行列」にする**（レビュー低 11・遅着 #18・[Issue #557](https://github.com/k2works/case-study-cargo-tracker/issues/557)）。
   未決着（審査中＋留置）を同時に見られるようにし、**表示件数と切り捨ての明示**
   （200 件で黙って切れる）も直す
2. **US30-10 の履歴が最新 1 件しか見えない**（遅着 #19・[Issue #556](https://github.com/k2works/case-study-cargo-tracker/issues/556)）。
   `decidedBy` / `decidedAt` は型にあるのに画面に出ておらず、却下後に再申請すると前回の
   却下理由が消える。**受入基準の一部未達**
3. **遅着分 #20〜#23**（予約詳細への導線・通関済からの巻き戻し・
   **荷役側の陸揚げ待ち**（[Issue #558](https://github.com/k2works/case-study-cargo-tracker/issues/558)）・キャンセル料の受け皿）
4. **テスト網羅性の上乗せ 3 件**（tester の指摘・IT10 の返済枠）
   - 再留置後の「4 日目以降は true」側の対を張り、`heldAt` の取り違えをより強く判別する
   - 即時確定パスで「通知しない／申請は保存される」ことを張り、承認確定との副作用の違いを守る
   - 2 回目の決定で内部状態が上書きされていないことまで見る（例外を投げつつ書き換える実装ミス）
5. **US33（荷主の担当者が自分の貨物だけを追跡する）の配置**。IT9 で起票した
   （[Issue #555](https://github.com/k2works/case-study-cargo-tracker/issues/555)）が、
   リリースへの配置は未定
6. **通知は依然として代替**（US29-4・US30-6・US30-7）。画面が「送られていない」と言う形で、
   仕組みでは埋めていない。**運用で回す約束が 3 つ増えた**——IT8 の分と合わせると負荷は
   軽くない。通知の仕組み（Release 2.0 以降）の優先度を上げる
7. **キャンセル料の算定は US21（Release 2.0）**。IT9 時点で billingms に受け口が無い
8. **陸揚げの作業指示は自動で作られない**（[ADR-025] 決定 5）。承認した追跡管理者から荷役の
   担当者へ連絡する運用ルールを添えている

# イテレーション 6 ふりかえり（KPT）

日付: 2026-08-23
対象: IT6（US12 経路の通知・US13 予約確定・US14 追跡番号発行・US32 ロック解除、9 SP／返済枠 12 件）

## サマリー

計画 9 SP を計画どおり達成し、**予約が業務として一周した**（提示 → 通知 → 確定 → 追跡番号の発行 → 追跡の開始）。あわせて**初のサービス間非同期連携**（bookingms → RabbitMQ → trackingms）と **trackingms の初実装**を通し、実 RabbitMQ での往復とデッドレターへの到達まで確かめた。

一方で、実装中に 9 件・クローズレビューで 9 件、**いずれも全テストが緑のまま潜んでいた欠陥**が出た。件数は IT5（12 件）より減ったが、**形が一つに揃っている**——決定はあるが、検査か配線が片側だけ。

もっとも重いのは [ADR-022](../adr/022-domain-event-contract.md) 決定 6（コミット後に発行する）で、**その機構が本番で一度も働いていなかった**。トランザクションの境目がリポジトリの `save` にしか無く、発行の時点では同期が解除済みだった。結果の順序が正しく見えていたのは「たまたま save のあとに呼んでいる」からであり、決定が守られている根拠ではなかった。

## Keep（続けること）

### 1. 実 RabbitMQ で往復させ、デッドレターへの到達まで見る（Try 1）

IT5 の Try 1 を成功基準 2・3 に据えた。設定の存在ではなく**到達**を見たことで、購読側で例外を握りつぶす実装に変えると赤になる形にできた。「デッドレターの設定を書いた」ことと「落ちたイベントがそこへ届く」ことは別である。

### 2. 契約の名簿を DTO から導く（Try 5）

項目名の名簿を手書きせず、`record` のコンポーネント名から導いた。手書きの名簿は、片側が項目を足しても赤にならない。同じ形を ArchUnit のメタテストにも広げ、**必須規則を公開メソッドから導く**ようにしたところ、2 規則 × 全サービスの未適用がその場で出た。

### 3. 壊して赤を確認する

IT6 では約 10 回の変異検査を行い、そのすべてで赤を確認した（ADR-021 決定 1・決定 3、ADR-022 決定 4・決定 6、契約の名簿、期限の判定、地点マスタの読み込み回数、廃止名の混入）。**決定 6 の欠陥は、この手順を「本番の呼び出し形」に対して行ったから出た**。

### 4. ADR に後日談を書き足す

ADR-019・ADR-021・ADR-022 に「後日談」の節を置き、**全テストが緑のまま守られていなかったもの**を決定と並べて残した。決定だけを読むと守られているように見えるため、破れた記録を同じ場所に置く。

### 5. 前 IT で「まだできません」と書いた箇所を機械的に棚卸しする（Try 6）

`grep` で拾う形を DoD に入れた。マニュアルの「訂正は次のリリース」など、使えるようになった後も残っていた記述を消せた。

## Problem（問題だったこと）

### 1. 決定はあるが、検査か配線が片側だけ ★最重要

18 件の欠陥の大半がこの形である。

- ADR-022 決定 6 の機構が一度も働いていない（境目がユースケースに無い）
- 新しい ArchUnit 規則を呼ぶのが bookingms だけ（**AMQP に最も広く触っている trackingms が無検査**）
- 往復テストが受け皿クラスをそのまま送っており、**プロデューサの送る形を流していない**
- コンシューマ側の「知らない項目を無視する」が、テスト自身が寛容に設定した `ObjectMapper` に対する検査だった
- 確定した予約の経路が `RoutingStatus` だけを見る差し替えで裏口から置き換えられた

**規則を足した変更で、それを適用する側をすべて洗い出していない。** ADR にコンプライアンス表を置く規律（IT5 Keep 1）は効いたが、表は「検査があるか」しか見ておらず「その検査がどこに適用されているか」を見ていなかった。

### 2. 「直したこと」と「実環境で動いていること」が別だと、クローズまで気づかない

追跡番号の日付を業務タイムゾーンから渡す修正は、コードもテストも緑だった。だが kind のイメージが修正前のままで、**デモを通すまで前日の日付が出ていた**。同じ形（同一タグのイメージは明示的に入れ替えないと差し替わらない）を、この IT で 2 度踏んでいる。

### 3. 品質ゲートの一部を、こちらの権限では閉じられない

SonarQube の新規違反はバックエンド・フロントエンドとも 0 にできたが、**セキュリティホットスポット 1 件のレビュー**は走査用トークンでは列挙も記録もできない（`Insufficient privileges`）。バックエンドのゲートは FAIL のままである。**閉じられないものを「閉じた」と書かない**ため、DoD は未チェックのまま残した。

### 4. 画面の分割基準が IT の中でぶれた

同じ IT で `route-design-page.tsx`（558 行）は割ったが、`booking-detail-page.tsx` は 610 行まで伸ばした。**割る基準を先に決めていない**ため、触った順で結果が変わっている。

### 5. 移行スクリプトが採番を巻き戻す形になっていた

`V7` は `DROP SEQUENCE` → `CREATE SEQUENCE START WITH 1` である。kind ではこの移行が今日はじめて走り、採番が 1 に戻った。番号は日付を含むため今回は衝突しなかったが、**同じ日に走れば発行済みの番号を再発行しうる**（UNIQUE 制約が捕まえる形にはなっている）。新しい DB では移行が発行より先に走るため、この露出はすでに過ぎている。

## 次イテレーションへの引き継ぎ

### 持ち越し（IT7 で扱う）

| # | 内容 | 理由 |
| :--- | :--- | :--- |
| 1 | **発行に失敗したイベントの再実行手段** | 番号は保存済みで二重発行は拒まれるため、障害時に「番号は渡されたのに追えない」が確実に起きる |
| 2 | **取りこぼしが見える照会**（発行済みだが追跡が無い予約） | 運用手順書の 1 タスクで足りる |
| 3 | **交換機の `alternate-exchange`** | DLQ が守るのは「受け取ったが処理できなかった」だけ。「誰も受け取れなかった」は黙って消える |
| 4 | **冪等を read-then-write からやめる** | 単一コンシューマのいまは表面化しないが、並行化した瞬間に壊れる |
| 5 | **遷移規則を集約の述語に一本化し、応答に載せる** | 集約・画面・モックの 3 か所にある |
| 6 | **`booking-detail-page.tsx`（610 行）の分割** | 5 と同じ変更で行う |
| 7 | **所要日数の丸めが 3 通り** | 営業が荷主に伝える日数と経路設計画面が 1 日ずれる |
| 8 | **`CONFIRMED` の表示名を「確定済」に揃える** | ボタン・マニュアル・ADR はすべて「確定」。表示名だけ「確認済」 |
| 9 | **`ignoreFailures = true` で Checkstyle / SpotBugs が落ちない** | 二重 import が検出されていた（今回は手で直した） |
| 10 | **契約の名簿・チャネル名が両側で自己完結** | 共通のテスト用定義を両側が読む形へ |
| 11 | **追跡番号の日次カウンタ** | いまは通算 9999 で循環する。1 日 9,999 件を超えたら作り替える |

### IT7 の着手前に決めること

- **SonarQube のセキュリティホットスポット 1 件を、利用者にレビューしてもらう。** IT6 のバックエンドのゲートはこれだけで FAIL のままである
- **追跡管理者のダッシュボードが全項目「準備中」。** 利用者を割り当てる前に、どの IT で埋まるかを示す
- **確定後の変更（欠航・数量変更）の出口。** US30（IT9）まで運用ルールで吸収すると決めたが、**決めたことを現場に伝えないと確定を後ろ倒しにされる**

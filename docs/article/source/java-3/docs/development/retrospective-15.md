# イテレーション 15 ふりかえり

| 項目 | 内容 |
| :--- | :--- |
| イテレーション | IT15（2026-11-30 〜 2026-12-13 想定・**Release 2.2 完了**） |
| 対象 | US36（3 SP）・US37（5 SP）= **8 SP** ＋ IT14 から送った負債 10 件（0 SP の返済枠） |
| 実績 | **8 SP（達成率 100%）** |
| レビュー | [高 10 件・中 5 件・低 2 件](../review/イテレーション15_review_20260901.md)。高は 9 件対応・1 件は IT16 へ |

## Keep

### 1. 実環境の枠が、また実環境でしか出ない欠陥を捕まえた

Phase 6.3（実環境で流す）で **5 つ**出た。いずれもユニット・結合・モック・E2E が
すべて緑の状態からである。

| 何が出たか | なぜ緑をすり抜けたか |
| :--- | :--- |
| 誤配の組み直しに、現在地からの航海が要る（409） | 元の航海が誤配した港からの区間を持たないことは、モックでは表れない |
| 航海番号が 20 文字を超えて 500 | 列の幅は実 DB にしか無い |
| 遅延の解決に新しい到着予定日が要る（400） | 集約の不変条件は、実際に呼んで初めて断られる |
| 冷蔵・危険物の予約に追加の入力が要る（23 件） | 乱数が種別を選ぶまで、一般貨物しか流していなかった |
| 航海が受け入れる貨物種別が固定で、候補 0 件（18 件） | 同上 |

IT14 の Keep 2（実環境の枠が欠陥を捕まえた）と同じ族である。**この枠は毎回働いている。**

### 2. 検査を 6 件すべて壊して、赤を見た

ADR-031 の決定 1〜6 について、実装を 1 つずつ壊して検査が赤くなることを確かめた
（IT14 Try 5）。所要は 1 件あたり 1 分である。IT14 では行わなかった
`logsInAgainForEachRole` が**何も固定していなかった**——その差がここで埋まった。

### 3. 「余力次第の返済枠」にしなかった

IT14 から送った負債 10 件を Phase 0 として**序盤に独立コミットで**片づけた。
うち 2 件（実行 ID の採番・追跡の例外一覧からの除外）は US37 の前提であり、
後回しにしていれば継続実行そのものが動かなかった。

「余力次第」にすると毎 IT 繰り越されて固定化する（ADR-0008 は 3 IT 連続で繰越）
——先に決めた順序が効いた。

### 4. 利用者代表のレビューが、受入基準の未達を 4 件見つけた

自分では緑だと思っていた 4 つが、**業務としては成立していなかった**。

- 一覧の分母が選択中シナリオ固定で、完了した誤配が「18 / 14 工程」と出る
- 実行間隔が保存・表示にしか使われず、1 本終われば 1 秒で次が始まる
- 設定を画面から変えられない（「設定でき」を満たしていない）
- 統計の「失敗した工程」から対象へ辿れない

**「実装した」と「その人の仕事が進む」は違う。** どれもテストは緑だった。

## Problem

### 1. 生成器が選んだ値が、どこにも届いていなかった

`ScenarioGenerator` は出発地・目的地・貨物種別・重量・期限を選んでいたのに、
`runForSession` は `scenario()` しか使わず、予約登録は固定値を送っていた。

**生成器だけを見るテストは緑のまま**である。`ScenarioGeneratorTest` は
「同じ種 → 同じ並び」も「割合が守られる」も確かめていたが、**その値が業務 API に
届いているかは誰も見ていなかった**。

利用者代表の言葉を借りれば、IT14 まで緑だった実行は「一般貨物・同じ港・同じ期限」の
1 本しか通しておらず、**冷蔵と危険物は一度も通っていなかった**。

IT12 の教訓「値は全層を生き延びるか確かめる」が、**自分が書いたばかりの値**には
効いていない。

### 2. IT14 の Try 2 を、同じ形で破った

契約に `simulated` を**基本型の `boolean`** で足したところ、この項目を送らない
既存の応答が「null を boolean に入れられない」で読めなくなった。

IT14 の Problem 2（`ShipperRequest` に `boolean simulated` を足して 15 件壊した）と
**同じ形**である。Try 2 は「項目を足すときは、送らない呼び出しのテストを同じ変更で
足す」だった。書いたのに守れていない。

今回は契約テストが捕まえたが、**捕まえたのは Try ではなく既存の検査**である。

### 3. リリース手順が 5 回とも「存在しない」状態だった

`ops/scripts/release.js` は書かれていたのに `gulpfile.js` が読み込んでおらず、
`npx gulp release:*` は「Task never defined」だった。

繋いだあと、さらに 4 つが連鎖して出た。

- 存在しない `deploy:prd` への依存で、gulpfile の読み込み自体が落ちる
- `npm run lint` がルートに無い（Missing script）
- `build -x test` で JaCoCo が実行データを持たず落ちる
- `npm run test:e2e` がルートに無い

**品質ゲートは一度も通ったことがなかった。** 「用意してある」ものが、実際には
一度も動いていない——スキルの手順に書いてあることと、動くことは別である。

### 4. 5 視点レビューのうち 4 つが返らなかった

programmer / tester / architect / technical-writer が 2 時間以上無応答だった
（3 度の催促にも反応なし）。担当分を自己レビューで代替したが、
**自分が書いたコードの自己レビューは弱い**——利用者代表が挙げた 7 件のうち
**6 件は自分では見つけられていない**。

IT13 の Try（レビューの結果を待たずにクローズしない）は守ったが、
**待っても来ない場合の手立てが無い**。

### 5. 実装の途中で、テストの前提を 2 度書き換えた

間隔を効かせたとき、既存の `ContinuousRunSchedulerTest` が固定時計で連続 tick する
前提だったため 2 件赤くなった。統計に見切りを入れたときも境目の解釈を取り違えた。

どちらも**実装が正しくなった結果**だが、テストを直す作業が「赤を緑にする」形に
見える瞬間がある。**直しているのが実装の誤りかテストの前提かを、その都度言葉に
していないと危うい。**

## Try

### 1. 生成した値は、届く先まで通すテストを同じ変更で書く（Problem 1）

値を作る仕組みを足したら、**その値が最終的にどこへ届くかを 1 本のテストで通す**。
生成器の単体テストだけでは、届いていなくても緑になる。

IT16 の DoD に「新しく生成する値は、業務 API に届くところまでのテストを同じ変更で
書く」を入れる。

**期待効果**: 「選んでいるのに使っていない」形を、実環境に出る前に捕まえる。

### 2. Try は DoD に書くだけでなく、変更のたびに読む（Problem 2）

IT14 の Try 2 を DoD に書いたのに、同じ形の欠陥を作った。**書いた Try は、
その形の変更をするときに読まなければ効かない。**

API の要求・応答・契約に項目を足す変更では、**コミット前に Try 2 を読む**。
DoD の確認はイテレーション末なので、そこでは遅い。

**期待効果**: 「書いたのに守れていない」を減らす。

### 3. 「用意してある」手順は、イテレーションの序盤に一度通す（Problem 3）

リリース手順・品質ゲート・運用タスクのように「あることになっている」ものは、
**使う日ではなく序盤に一度通す**。IT15 では末尾で初めて動かして 5 つ直した。

IT16 の Phase 0 に「使う予定の運用タスクを一度空打ちする」を入れる。

**期待効果**: 締めの直前に手順そのものを直す事態を避ける。

### 4. レビューが返らないときの手立てを決めておく（Problem 4）

待ち時間の上限を決め、超えたら**自己レビューで代替したことをレポートに明記する**。
今回そうしたが、その場で決めたので判断が遅れた。

IT16 では「1 時間で返らなければ自己レビューへ切り替え、その旨をレポートに書く」を
先に決めておく。**独立したレビューの方が強いことも併記する**——自己レビューは
見落とす前提で読まれるべきである。

**期待効果**: 待ちで止まらず、かつ弱さを隠さない。

### 5. テストを直すときは、直している対象を言葉にする（Problem 5）

既存テストが赤くなったら、**「実装の誤りを直している」のか「テストの前提が
古くなった」のか**をコミットメッセージに書く。書けないなら、まだ分かっていない。

**期待効果**: 「赤を緑にするためにテストを緩めた」形を自分で検出する。

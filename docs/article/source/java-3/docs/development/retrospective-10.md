## Keep（続けること）

### 1. 実環境で通す枠（Phase 6）が、今回も欠陥を捕まえた

IT9 で導入した枠が 2 回目も働いた。**サービス単体が全部緑でも実環境でだけ落ちる形**は
今回もあり、`dev:k8s:rollout:image` がタグ一致だと Pod を作り直さないことに気づけたのも
この枠のおかげである。

### 2. 「事実」と「状態」を別の軸に置いた設計判断

`Misroute` を `RoutingStatus` と別に持ったこと自体は正しく、`domain-model.md` にも
明記できた。状態フラグ 1 つで済ませていたら、料金調整の段で必ず揉めた。
**分けたこと自体は良かった**（分けたあとの使い方を誤ったのは Problem 3）。

### 3. `tsc -b` が型の欠落を捕まえた

IT9 の Try 3 で `tsc --noEmit` から替えた効果が出た。`RouteSearchCriteria` に `reroute` を
足し忘れたまま実装を進めたが、**vitest は 428 件すべて緑**で、`tsc -b` だけが落ちた。
型検査をしないテストは、この種の抜けを判別しない。

### 4. レビューの結果を待った（IT9 の Try 5）

5 視点とも最初は idle 通知だけで本文が届かず、全員に再送を求めた。**待った結果、高 8 件が
届いた**。そのうち 6 件は自分では見つけていなかった。IT9 で「待たずに打ち切った 2 視点に
高 2 件が入っていた」学びが、そのまま効いている。

### 5. 指摘を鵜呑みにせず確かめた

「日時が生の ISO で出ている」という中指摘は**誤り**だった（サーバが整形して返している）。
確かめずに直していたら、正しい実装を壊していた。ただし**それを固定する検査が無かった**ことは
本当だったので、検査を 1 本足した。

## Problem（困ったこと・繰り返したこと）

### 1. デモ項目に検査が対応していなかった（クローズ直前に発覚）

計画の「デモ項目 10 件」のうち 2 件（ダッシュボードの誤配件数から一覧へ／例外を解決しても
記録が残る）に、対応する検査が無かった。**実装はどちらも入っていた**ので実演では緑になり、
そのままチェックを入れていたら「見せられたから通った」で終わっていた。

IT9 の Try 6（受入基準ごとに検査 1 本）は守ったが、**その適用範囲を「受入基準」に限って
いた**。デモ項目は受入基準より具体的で、業務の通し方そのものである。

### 2. 絞りが 3 か所に分かれていて、緩めたつもりが効いていなかった

ADR-026 決定 4 に「期限で弾くと組み直す手段そのものが無くなる」と書き、集約から期限検査を
外し、その意図を Javadoc にも書き、検査も置いた。**それでも実際には一度も通っていない
経路だった**——期限による絞りは routingms 側にもう 2 つ（SQL の航海取得・探索の枝刈り）
あり、どちらも残っていた。

決定を書いて集約に検査を置いたことで「守った」と判断していた。**決定が効く経路を端から端まで
1 度も通していなかった**のが原因である。

### 3. 「事実」で分岐していた（宣言は正しいのに使い方が誤っていた）

`isMisrouted()` の Javadoc には「状態ではなく事実を見る」と正しく書いてあり、
`domain-model.md` にも「状態は戻る／事実は戻らない」と明記していた。**その正しい述語を、
状態で決めるべき 3 か所（バナー・操作一覧・ユースケースの分岐）に使っていた。**

結果、組み直したのに「組み直してください」と言われ続け、通常の割り当ての検証が二度と
適用されない状態になっていた。**コメントを読むだけでは気づけない形の誤り**である。

### 4. 画面から踏むテストが「着地点」を見ていなかった

IT9 の Try 1（応答の一覧に依存する画面を画面から踏む）は予約詳細の導線では守ったが、
その**遷移先**である経路設計画面には誤配のケースが 1 本も無かった。実環境テストも
`origin=SGSIN` を手で書いており、**画面が誤った origin を使っていても緑**だった
（判定をテスト側に書き直した形）。

### 5. ルートガードを通らないテストで「到達できる」と判断していた

予約詳細への導線 3 か所が 403 だった。画面単体のテスト（`renderWithProviders`）は
ルートガードを通らないため、**リンクが存在することは確かめられても、押せることは
確かめていない**。3 か所とも「行き止まりにしない」とコメントに書いてある場所だった。

### 6. ローカルで lint を回さずに push した

CI が `max-lines`（409 行 > 400）で落ちた。IT9 の学び「ローカルの品質ゲートは CI と同じ
コマンドで」を、**バックエンドでは守ったがフロントエンドでは守らなかった**
（`./gradlew build` は回したが `oxlint` は回していない）。

### 7. 実環境への反映が 2 度失敗した

`dev:k8s:images` を実行してもノード上のイメージが更新されず、`--tag` / `DEV_K8S_IMAGE_TAG`
のどちらでも `dev:k8s:rollout:image` がタグを切り替えなかった。コンテナ内の jar が 6 日前の
ままで、**最初の実環境確認が誤った赤を出した**。`kubectl set image` を直接使って進めた。

## 次イテレーション（IT11）への引き継ぎ

1. **レビューの低指摘 4 件**（[IT10 レビュー](../review/イテレーション10_review_20260826.md)）
   - 誤配バナーの港が UN/LOCODE のまま（他画面は港名を優先表示）
   - `RoutingStatus#visibleToRoutingPlanner` が否定リストで、値を足すと自動的に開く方向に倒れる。
     ADR-026 決定 2 は「述語がすべての値を明示的に扱う」と決めているが、検査になっていない
   - ADR-026 コンプライアンス表の決定 7 の行が、決定 5 の壊し方を記録している
   - trackingms の配線が完全修飾名だらけ（IT9 から伝播）
2. **2 回目の誤配の扱いを決める**。`Misroute` は 1 件しか持たず、組み直した先でまた外れたときに
   1 回目が残る。**料金調整は回数で変わる**ため、US21（Release 2.0）の前に決める必要がある
3. **誤配の記録を経理が読む手段がない**。予約詳細にしか出ず、経理担当者は開けない。
   料金調整の実装（US21）で参照経路を作る
4. **陸揚げ待ちの一覧が「未着手」を区別しない**。手配が済んだ行を消す手段がなく、件数が
   増えると「毎朝上から片付ける」使い方が破綻する
5. **購読側で 2 つ目・3 つ目のユースケースを直列に呼ぶ形が定着しつつある**。IT9 の
   `CustomsStatusChanged` と同じ構造で、トランザクション境界がない。順序をコメントで
   説明している以上、その順序を壊すと赤くなる検査が要る
6. **`BookingStatus` の全値がラベルを持つことが検査されていない**。IT10 でキャプチャを撮って
   初めて 3 つの欠落に気づいた
7. **通知は依然として代替**（US28-6・US29-4・US30-6・US30-7）。運用で回す約束が 4 つになった。
   通知の仕組み（Release 2.0 以降）の優先度を上げる
8. **`dev:k8s:rollout:image` の `--tag` が効かない**（Problem 7）。運用手順書の課題として起票する

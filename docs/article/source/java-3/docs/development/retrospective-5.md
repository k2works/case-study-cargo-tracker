# イテレーション 5 ふりかえり（KPT）

日付: 2026-08-22
対象: IT5（US09 経路の選択・US10 条件の調整・US11 予約への反映、8 SP／返済枠 9 件）

## サマリー

計画 8 SP を計画どおり達成し、**経路設計の往復が閉じた**（予約 → 候補 → 選択 → 確定 → 予約詳細に旅程）。IT4 から持ち越した返済枠 9 件もすべて消化した。

一方で、クローズのレビューで**高優先度 12 件**が出た。件数は IT4（14 件）とほぼ同じだが、**内訳の質が違う**。5 件は「全テスト緑のまま業務が成り立たない」形で、うち 1 件（接続先が bookingms 自身を指す）は**どの環境でも経路の確定が必ず失敗する**状態だった。

IT4 のふりかえりで書いた Try 9（レビュー手直しの枠を見積もりに入れる）は機能し、12h の枠に収まった。しかし**枠を取ったことで手直しが減ったわけではない**。減らすには、手直しの中身が生まれる仕組みに手を入れる必要がある。

## Keep（続けること）

### 1. ADR に「決定の数だけ検査を用意する」表を置く

ADR-019（決定 3）・ADR-020（決定 7）でコンプライアンス表を書き、決定ごとに検査を対応させた。**表があると、検査の無い決定が一目で分かる**。実際 ADR-019 決定 3（イベントを発行しない）は、表が無ければ「書かなかっただけ」で終わっていた。

### 2. 壊して赤を確認する

IT5 では 12 回の変異検査を行い、そのすべてで赤を確認した（常時 INSERT・荷主コード再採番・認可の順序・一覧の絞り込み・UTC への差し戻し・delete の省略・ADR-020 の決定 1〜5・契約テストの項目名／パラメータ名の改名）。**「消しても緑」だった 1 件**（探索側の出発下限）も、この手順があったから見つかった。

### 3. 「実バックエンドでしか再現しない形」を分けて置く

IT4 の Try 7 に従い、利用者を切り替える往復を `real-backend.spec.ts` に置いた。モックは読み直しで初期化されるため、モック側では書けない。

### 4. 据え置いた負債を、着手条件が来たら実際に返す

ADR-012 の `email` 値オブジェクト化（「荷主編集に着手するとき」）を US02 と同じ変更で解消した。**型を変えた瞬間に、検査を通していない値が届く経路が 4 箇所コンパイルエラーとして現れた**。据え置いていた間、その 4 箇所は「たまたま `register` を通っていた」だけだった。

### 5. レビューの指摘を検証してから受け入れる

「探索側の出発下限を消しても緑」という指摘を検証したところ、**無検査なのではなく観測できない最適化**（条件側が `collect` で必ず同じ判断をする）だった。指摘をそのまま受け入れて「テストを足した」ことにすると、実際より強く主張するテスト名が残る。

## Problem（問題だったこと）

### 1. 「踏まないパス」は守られていない ★最重要

接続先 URL の既定値が bookingms 自身（8082）を指し、上書きがリポジトリのどこにも無かった。**どの環境でも経路の確定だけが必ず失敗する**状態で、全テストが緑だった。

見逃した理由は 3 つ重なっている。

- ACL の単体テストは `MockRestServiceServer` に別の URL で bind するため、既定値を見ない
- 実バックエンド E2E は「候補が 0 件なら注釈を残して成功」で、**確定パスを一度も踏まずに緑**だった
- ADR-019 決定 2 の検査は、ユースケースのスタブ差し替えで満たされ、**実 HTTP を通っていない**

### 2. 同じ規則を守る箇所が 2 つあると、互いを隠す（IT4 の再発）

IT4 のふりかえりで最重要として挙げた形が、そのまま 3 種類再発した。

- 経路設計者に見せる範囲が、詳細（集約の述語）と一覧（コントローラの固定値）に別々にあり、**詳細だけを広げて一覧が古いまま**になった
- 到着期限の「当日」を、routingms は業務タイムゾーン、bookingms は目的地の暦で判断していた。**目的地が東京以外だと判定が食い違う**
- 出発希望日の下限が、探索側と条件側の 2 か所にあった（こちらは観測できない最適化と判明）

### 3. モックが本物より甘い（IT4 Try 8 が効かなかった）

`PUT /route` のモックが `NOT_ROUTED` だけを拒み、本物は `ROUTING_REQUESTED` / `ROUTED` **以外**を拒む。差し戻し中の予約をモックだけが通していた。IT4 で「写しを増やすならずれを捕まえる網も増やす」と書き、IT5 の計画にも 3h の枠を取ったが、**モックを足したときに本物と読み比べていなかった**。

`appliedCriteria.earliestDeparture` に至っては、**フロントの型が必須で宣言している項目がサーバに存在しなかった**。

### 4. 「まだできません」と書いた記述の棚卸しが仕組み化されていない

IT4 に書いた「次のリリースで使えるようになります」「IT4 は一覧の表示まで」「まだ働く場面が無い」が、使えるようになった後も 5 箇所残っていた（マニュアル 2 箇所・画面のコメント・集約のコメント・業務フローの対応表）。

### 5. 一部のユースケースがテスト後追いになった

`EditShipperUseCase` と `RequestConsultationUseCase` は、モックした Controller 経由でしか通っておらず、**カバレッジ低下が先に鳴って**から直接のテストを足した。Red 先行でなかった証拠がカバレッジ側から出た形になる。

### 6. 業務が一周しない導線が残っていた

「条件協議を依頼する」で営業へ差し戻せるようにしたが、**営業が返す操作を作っていなかった**。マニュアルは「決まったら経路設計者に伝える」とシステム外の運用に逃げていた。差し戻しは US10 の受入基準そのものなので、往復を閉じないと基準を満たしたことにならない。

## 次イテレーションへの引き継ぎ

### 持ち越し（IT6 で扱う）

| # | 内容 | 理由 |
| :--- | :--- | :--- |
| 1 | **kind 統合環境で成功基準 1 を通す**（予約 → 候補 → 選択 → 確定 → 旅程） | IT5 ではモック E2E と実バックエンド spec まで。接続先の欠陥が出た経緯からも、実環境で 1 往復させる価値が高い |
| 2 | **目的地が東京以外の予約で期限の判定を通す** | BC 間のタイムゾーン食い違いは直したが、実環境では確かめていない |
| 3 | 再検証失敗専用の例外型を作り、409 の射程を絞る | いまは `IllegalStateException` が「再検証の失敗」と「地点マスタの不備」の両方を運ぶ |
| 4 | 契約テストの項目名簿を DTO から導く | 手書きの名簿は、コンシューマ側が項目を足しても赤にならない |
| 5 | 地点マスタの N+1（確定 1 回あたり候補数 × 区間数 × 2 回） | 頻度は低いが、候補件数が増えると効く |
| 6 | `route-design-page.tsx`（502 行）・`mocks/handlers.ts`（1045 行）の分割 | US12 で同じファイルを触るときに行う |
| 7 | 個人事業主の法人成り（荷主の種別変更／統合） | 編集で種別を固定したため、実務で起きる形に手当てが無い |
| 8 | 予約の訂正（期限・出発希望日だけでも） | 条件協議の結果が「期限を延ばす」だった場合、予約を直せないと再依頼しても同じ結果になる |

### IT6 の着手前に決めること

- **イベント発行を足すとき、ADR-019 決定 3 の検査（`noEventPublishingRule`）を同じ変更で外す。** 外し忘れると、発行を足した瞬間に理由の分からない赤になる
- **経路の差し替えが荷主にどう伝わるか。** `[経路を見直す]` で差し替えられるが、営業が気づく手段が無い。US12（経路通知）と同じ IT で扱うか決める

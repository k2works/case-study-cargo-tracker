# ADR-013: フロントエンドは `pages/` を画面の入口、`features/` を業務単位の実装に分ける

`pages/` にはルーティングから直接指される画面コンポーネントだけを置く。データ取得・型・業務ロジックは `features/<コンテキスト>/` に置き、`pages/` はそれを組み立てる。`features/` から `pages/` を参照しない。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

IT1 の時点で `src/pages/` に 6 画面、`src/features/` に `auth/` と `booking/`（API 定義と型のみ）がある。両者の関係が明文化されておらず、次の判断ができない。

- 荷主一覧の取得フックはどちらに置くか
- 予約登録フォームの部品は画面ファイルに書くのか、`features/booking/` に切り出すのか
- `features/booking/types.ts` の型を `pages/` 以外から使うことはあるか

IT2 で画面が 4 つ増え（荷主登録の法人欄・予約一覧・予約登録・種別による出し分け）、IT3 以降でさらに増える。**画面を増やしてから決めると、決め直しの対象が増える**。

## 決定

1. **`pages/<画面名>-page.tsx` はルーティングの入口とする。** 1 ファイル 1 画面。責務は「`features/` のフックを呼び、レイアウトに配置する」ことに限る。ここに `fetch` や業務規則を書かない
2. **`features/<コンテキスト>/` に業務単位の実装を置く。** コンテキスト名はバックエンドのバウンデッドコンテキストに揃える（`auth` / `booking` / `routing` / `tracking` / `handling` / `billing`）。中身は次のとおり
   - `api.ts` — エンドポイントの呼び出し
   - `types.ts` — API の入出力の型
   - `queries.ts` — TanStack Query のフック（IT2 で新設）
   - `components/` — その業務でしか使わない部品（IT2 で新設。予約種別による出し分けなど）
3. **依存の向きは `pages/` → `features/` の一方向とする。** `features/` から `pages/` を import しない。逆流するとルーティングと業務実装が絡み、画面の付け替えができなくなる
4. **複数のコンテキストで使う部品は `components/ui/`、レイアウトは `components/layout/` に置く。** どちらにも属さない汎用処理は `lib/`
5. **この向きを検査で固定する。** `features/` 配下から `pages/` への import が無いことを、フロントエンドのテストとして書く。規則は、同じ変更で検査に落とさなければ守られない

### 代替案

- **画面ごとにディレクトリを切る（`src/booking/new/`）**: ルーティングと実装が 1 対 1 になり分かりやすいが、複数画面で共有する取得フック（荷主の一覧は登録画面でも予約画面でも要る）の置き場所が決まらない
- **`features/` を廃し `pages/` に集約する**: 画面が 6 のうちは成立するが、IT3 以降で 20 を超える。1 ファイルが肥大化する
- **バックエンドのコンテキストと揃えない（`shippers/` / `bookings/` のような画面群単位）**: 荷主と予約はいずれも booking コンテキストであり、分けるとバックエンドの変更が 2 箇所に散る

## 影響

### ポジティブ

- 画面を増やすときの置き場所を毎回考えなくてよい
- バックエンドのコンテキストとフロントの区分が対応し、変更が同じ場所に集まる

### ネガティブ

- IT1 の `pages/shipper-list-page.tsx` などから取得処理を `features/booking/queries.ts` へ移す作業が要る（IT2 のタスク 0.7 に含める）
- コンテキストにまたがる画面（ダッシュボード）は複数の `features/` を参照する。これは許容する（入口の責務のとおり）

## コンプライアンス

- `features/` から `pages/` への import が無いことをテストで検査する
- 検査を意図的に破ると赤になることを確認する
- `architecture_frontend.md` のディレクトリ構成を本 ADR に合わせる

## 備考

- 由来: IT2 の返済枠 M5（タスク 0.7）

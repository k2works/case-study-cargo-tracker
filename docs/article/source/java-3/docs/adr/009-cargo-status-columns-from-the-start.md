# ADR-009: 貨物の状態列は最初から NOT NULL で作り、料金列は算出できるまで NULL を許す

`cargo` の `transport_status` / `routing_status` は IT2 の時点で NOT NULL・既定値付きで作る。`booking_amount_value` / `booking_amount_currency` は、料金を算出する US18（IT11）まで NULL を許す。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

`data-model.md` の `cargo` は、輸送状況・経路状況・予約金額をいずれも NOT NULL としている。しかし IT2 で作るのは仮受付（`PRELIMINARY`）までであり、経路も配送も料金も存在しない。

素直に読むと「IT2 では nullable にしておき、値が入るようになったら NOT NULL を足す」となる。これは危険である。**不変条件を後から足すと、その規則が無かったころの行が読めなくなる**。IT2 で入った予約が IT11 のマイグレーションで NOT NULL 違反になり、移行スクリプトを書くか、既存行を捨てることになる。

一方で、両者は性質が違う。

- **輸送状況・経路状況**は、値が無いのではなく「まだ動いていない」という**状態がある**。`NOT_RECEIVED` / `NOT_ROUTED` は空欄ではなく、意味のある値である
- **料金**は、状態ではなく**計算結果**である。まだ計算していない金額に既定値（0 円）を置くと、「無料の予約」と区別がつかなくなる。0 円で請求される事故に化ける

## 決定

1. **`transport_status` は NOT NULL とし、既定値を `NOT_RECEIVED` とする。** `routing_status` も NOT NULL とし、既定値を `NOT_ROUTED` とする。いずれも IT2 の集約が明示的に設定する（DB のデフォルト値に頼らない。アプリ側で状態を持たないと、集約が自分の状態を答えられなくなる）
2. **`booking_amount_value` / `booking_amount_currency` は NULL を許す。** `data-model.md` の NOT NULL 記述を本 ADR に合わせて修正する
3. **料金の未算出は「NULL」で表し、0 で埋めない。** 画面では「未算出」と表示する。0 円と表示すると、算出漏れが無料の予約として通る
4. **IT11 で料金を算出できるようになっても、この列を NOT NULL にしない。** 見積の無い予約（US01 未実装期間に入った行）が残るため。「必ず値がある」ことは集約の不変条件ではなく、**料金を確定する遷移の事前条件**として表す

### 代替案

- **状態列も nullable にする**: 状態を持たない貨物が存在しうることになる。「経路が付いていない」と「経路状況が不明」の区別がつかず、一覧の絞り込みが書けない
- **料金列に 0 を入れる**: 未算出と無料が同じ表現になる。IT11 で区別する術がない
- **料金を別テーブルに分ける**: 1 対 1 のテーブルが増える。NULL 許容で足りる

## 影響

### ポジティブ

- IT2 で入った予約が、後続 IT のマイグレーションで読めなくなる事態を避けられる
- 未算出の料金が 0 円として通る事故を、型（NULL）の段階で塞げる

### ネガティブ

- 料金を表示する箇所すべてで NULL を扱う必要がある
- `data-model.md` を修正する（設計側の記述を狭める）

## コンプライアンス

- `cargo` のマイグレーションで、状態列が NOT NULL、料金列が nullable であることを確認する
- 仮受付の貨物を保存して読み戻す統合テストで、状態が `NOT_RECEIVED` / `NOT_ROUTED` であり料金が空であることを検証する
- IT11 の計画時に本 ADR を読み、NOT NULL 化しないことを確認する

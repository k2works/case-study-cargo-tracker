# ADR-010: 地点はサロゲート主キー + UN/LOCODE の一意制約で持ち、業務タイムゾーンを必須とする

`location` テーブルは `id`（BIGSERIAL）を主キー、`unlocode` を一意制約とする。`time_zone` は NOT NULL とする。マスタは bookingms が保持し、他サービスは自サービスのスキーマに同じ形で複製する。

日付: 2026-08-20

## ステータス

承認済み

## コンテキスト

地点（港湾）は booking / routing / tracking / handling の 4 コンテキストが参照する。共有カーネルの値オブジェクト `Location`（UN/LOCODE + 名称）は IT1 で定義済みだが、**テーブルとしての形はまだ決まっていない**。

IT2 で決めた形が IT3 以降で 4 サービスに複製されるため、ここで間違えると 4 箇所を直すことになる。決めるべき点が 3 つある。

**主キー**: UN/LOCODE は 5 文字の自然キーであり、そのまま主キーにできる。ただし UN/LOCODE は改訂されることがあり（統廃合・改称）、変わったときに全参照を追いかけることになる。

**タイムゾーン**: 到着期限（`spec_arrival_deadline`）は DATE 型であり、「いつまでに着けばよいか」を業務の暦で判断する。UTC で判断すると、時差の分だけ受付が拒否される時間帯ができる。判断に使う暦は「目的地の暦」であり、目的地の地点がタイムゾーンを持っていなければ決められない。

**保持者**: Database per Service のもとで、共通マスタをどこが持つか。

## 決定

1. **主キーはサロゲート（`id BIGSERIAL`）とし、`unlocode` に UNIQUE 制約を置く。** `cargo` からの参照は `unlocode`（VARCHAR(5)）で持つ。業務上の識別子で参照しつつ、コード改訂時にレコードの同一性を保てる
2. **`time_zone` は NOT NULL とする**（IANA タイムゾーン名。例: `Asia/Tokyo`）。到着期限の判断に必要であり、後から必須にすると既存行が読めなくなる。初期データの投入時点で全地点に設定する
3. **マスタの正は bookingms が持つ。** 予約時に出発地・目的地を選ぶのが最初の用途であり、そこが正になる
4. **他サービスは自サービスのスキーマに同じ形で複製する。** サービス間で JOIN しない（ADR-001）。複製の同期方法は IT3（routingms が地点を使い始める時点）で決める。IT2 では複製しない
5. **国コード（`country_code`）は `unlocode` の先頭 2 文字と重複するが、列として持つ。** 導出できることと、絞り込みに使えることは別である

### 代替案

- **`unlocode` を主キーにする**: 参照側の記述は素直になるが、コード改訂時に全参照を更新することになる。地点は長命なマスタであり、改訂は起こる前提で設計する
- **`time_zone` を nullable にする**: 到着期限の判断が「タイムゾーンがある地点だけ正しい」ことになる。どの地点で正しいかが利用者に分からない
- **地点マスタを専用サービスに切り出す**: サービスが 1 つ増える。4 コンテキストが参照するだけの参照系マスタであり、可用性の結合を増やす価値が無い

## 影響

### ポジティブ

- 到着期限を目的地の暦で判断できる（UTC 判断による誤った拒否を避けられる）
- UN/LOCODE の改訂に、参照を壊さず追随できる

### ネガティブ

- IT3 以降、4 サービスに同じテーブルが並ぶ。同期の仕組みが要る（IT3 で決める）
- `cargo` は `unlocode` で参照するため、外部キー制約は `location.unlocode` に対して張る（サロゲートキーへの FK ではない）

## コンプライアンス

- `location` のマイグレーションで、サロゲート PK・`unlocode` の UNIQUE・`time_zone` の NOT NULL を確認する
- 到着期限の検査を、目的地のタイムゾーンで行っていることをテストで固定する（UTC との差が出る時刻を含める）
- `TZ=UTC` でテストを実行しても緑であることを確認する

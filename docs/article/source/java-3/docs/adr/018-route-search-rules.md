# ADR-018: 経路候補の推奨順・費用の概算を決め、港湾制約は持たない

経路候補を「直行優先 → 到着の早い順 → 積み替えの少ない順」で並べる。費用は基本輸送料金と港湾利用料の概算で出す。港湾制約はモデルとして持たない。積み替えは既定 2 回・絶対上限 3 回とし、1 回あたり最低 6 時間を要するものとする。

日付: 2026-08-21

## ステータス

承認済み

## コンテキスト

US08（経路候補を算出する）の受入基準は「経路候補が推奨順に並べられて提示される」「直行便がある場合、最優先候補として提示される」「経路候補ごとに所要日数・経由港・費用・航海番号が表示される」を含む。しかし**推奨順の規則も費用の算出式も、設計ドキュメントのどこにも書かれていなかった**。

さらに、要件定義の「経路設計の制約条件」は**港湾制約**（港が該当する貨物の取扱いに対応しているか）を挙げているが、そのモデルは設計に存在しない。IT3 では `ui_design.md` に「US08 で必要性ごと判断する」と書いて先送りした。**判断を先送りし続けると、US28（誤配時の再設計）でまた同じ議論になる。**

費用については、運賃表も港湾利用料のマスタも存在しない。US21（輸送料金を算出する・IT11）まで実料金は出せない。

## 決定

### 1. 推奨順は「直行優先 → 到着の早い順 → 積み替えの少ない順」とする

1. **直行便を最優先で提示する。遅く着いても上に出す**（US08 の受入基準）。積み替えが無いことは、乗り継ぎ失敗も荷役による損傷も起きないという意味であり、経路設計者はまずそこを見る
2. 次に到着の早い順。荷主が待つ時間が短い
3. 到着が同じなら積み替えの少ない順。荷役のたびに損傷と遅延の危険が上がる

並べ方は 1 箇所（`RouteRecommendation.rank`）に置き、画面と API が別々に並べ替えない。

### 2. 費用は「区間 × 基本料金 + 輸送日数 × 日額 + 港数 × 港湾利用料」の概算とする

`区間数 × 200,000 円 + 輸送日数 × 30,000 円 + （経由港数 + 2）× 50,000 円`

**これは請求される金額ではない。**経路どうしを見比べるための目安であり、画面にも概算であると書く。**US21（IT11）で実料金に差し替える。**

日数を式に含めるのは、輸送日数が長いほど船と船倉を占有するためである。積み替えの待ち時間も日数に含める（[TransitPath の輸送日数](../design/domain-model.md)）。

### 3. 港湾制約はモデルとして持たない

- 対応できる貨物種別は**航海**が持つ（`Voyage.supportedCargoTypes`。IT3 / US24）。危険物・冷凍を運べるかは、港ではなく船と設備で決まる部分が大きい
- 港ごとの取扱い制限を持つには、港湾ごとの設備マスタと、それを維持する運用が要る。**維持されないマスタは、あるほうが危険である**（古い制限で正しい経路を落とす）
- **必要になる条件を決めておく**: 実際に「この港ではこの貨物を扱えない」ことが原因で経路が破綻した事例が出たときに、そのとき必要な粒度で持つ

### 4. 積み替えは既定で 2 回まで、絶対の上限を 3 回とする

荷役のたびに損傷と遅延の危険が上がるため、既定では 2 回までを候補にする。候補が見つからないときは経路設計者が緩められるが、**いくらでも緩められてはいけない**。探索は深さに対して指数的に広がるため、上限を外から任意に上げられると 1 回の問い合わせでサービスを止められる。業務としても 4 回以上の積み替えを提案する場面が無い。

**この決定は IT4 のレビューで足した。** それまで「3 回以上は候補にしない」という規則がコードのコメントと `domain-model.md` に書かれ、ADR-018 を引用していたが、**ADR には存在しない決定だった**。しかも画面は「3 回まで」を緩和の既定として勧めており、規則と操作が食い違っていた。

### 5. 積み替えには最低 6 時間を要する

降ろして、受け渡して、積む。0 にすると、机上では成立するが現場で実行できない経路を候補に出す。経路設計者はスケジュール表からそれを見抜けず、動かない予定が下流（荷役・追跡）へ流れる。

6 時間は業務上の判断であり、港ごとの実態を持っていない（決定 3 のとおり港湾のマスタを持たないため）。港ごとに変える必要が出たら、そのとき港のマスタに持たせる。

> **危険物の積み替えは 6 時間では回らない。** 積み替えのたびに書類と検査が入る。いまは全部一律なので、危険物の候補は机上で成立しても現場で崩れることがある（IT4 レビュー・利用者代表）。ここは次のイテレーション以降で扱う。

### 代替案

- **費用を出さない**: 受入基準が求めており、経路設計者が「安いほうを選ぶ」判断もできなくなる
- **費用の順で並べる**: 概算でしかない数字を判断の第一基準にすることになる。実料金が入る US21 で並び順を見直す
- **港湾制約を先送りする（IT3 と同じ）**: US28 でまた同じ議論になる。持たないと決めておけば、US28 は現在地起点の探索だけを考えればよい

## 影響

### ポジティブ

- 経路設計者が一覧を上から見て判断できる。並べ方が 1 箇所にあり、画面と API がずれない
- 港湾制約を持たないと決めたことで、US28（誤配時の再設計）は探索の起点だけを考えればよくなる

### ネガティブ

- **費用が実料金と食い違う。** 概算であることを画面に書くが、数字が出ている以上そのまま受け取られる危険はある。US21 で差し替えるまでの間、見積の根拠には使えない
- **港ごとの取扱い制限を見落とす。** 危険物を扱えない港を経由する経路が候補に出うる。運用上は経路設計者の目視確認に頼る（この運用条件を[リリース計画](../development/release_plan.md)の業務投入条件に含める）
- 積み替え 6 時間は一律であり、大きな港と小さな港を区別しない

## コンプライアンス

決定の数だけ検査を用意する。

- **決定 1（推奨順）**: `RouteRecommendationTest` で 3 段の順序を固定する。直行優先・同着時の積み替え優先のそれぞれを外すと赤になることを確認済み
- **決定 2（費用）**: `RouteRecommendationTest` で式を固定する。港湾利用料の項を落とすと赤になることを確認済み
- **決定 3（港湾制約を持たない）**: **否定の決定も検査に落とす。** 「書き忘れ」ではなく「足したこと」を検出すればよい（[ADR-017](017-route-candidates-api.md) 決定 2 と同じ許可リスト方式）。`RouteCandidatesAreNotPersistedTest` が、`routing_db` に港湾制約の表が現れないことと、routingms のドメインに `PortConstraint` / `PortCapability` の型が現れないことを検査する。**港湾制約の型を足すと赤になることを確認済み。** あわせて `ui_design.md` / `system_usecase.md` / `requirements_definition.md` / `business_usecase.md` / `user_story.md` の「港湾制約を考慮する」という記述を、この決定を指すよう書き換える（先送りの記述も、考慮すると読める記述も残さない）

  > **当初この節には「否定の決定であり検査に落とせない」と書いていた。誤りである。** 同じイテレーションの隣で、経路候補の非永続化を許可リストで検査していた。文章は読まれなければ効かないが、テストは読まれなくても効く。**否定の決定こそ検査に落とす。**

- **決定 4（積み替えの上限）**: `RouteSearchSpecificationTest` で境界（絶対の上限ちょうどは受け付ける・1 つ超えると断る）を固定する。**上限を外すと赤になることを確認済み。** あわせて、探索側の打ち切りと条件側の判定が互いを隠さないよう、条件側を単独で固定する検査を置く（経路を直接組み立てて探索を通さない）
- **決定 5（積み替え 6 時間）**: `TransitPathTest` で境界（ちょうど 6 時間は成立・5 時間 59 分は不成立）を固定する。**探索側にも同じ境界の検査を置く**（`TransitPath.of` の検査は、探索が先に弾くためその経路に到達せず、二重に見えて実は無防備だった）。どちらを外しても赤になることを確認済み

# ADR-001: バウンデッドコンテキスト単位のマイクロサービスアーキテクチャの採用

国際貨物輸送管理システムのバックエンドを、DDD のバウンデッドコンテキストを境界とした 7 つのマイクロサービス（gatewayms / authms / bookingms / routingms / trackingms / handlingms / billingms）として構成する。

日付: 2026-08-19

## ステータス

承認済み

## コンテキスト

- 国際貨物輸送は中核の業務領域であり、経路設計・積み替え・通関・例外処理など複雑なビジネスルールを持つ
- 金額を扱う請求（Billing）、監査記録が必要な荷役・通関・キャンセル承認、厳密な状態遷移（予約・輸送ステータス）が併存する
- コンテキストごとに読み書きの負荷特性が異なる（Tracking は参照が支配的、Handling は書き込み中心）
- 本プロジェクト（take-7）は take-3 のマイクロサービス設計を基礎とし、要件定義で追加された通関手続き（UC21）・予約キャンセル承認（UC22）・誤配検知（US28）・アカウント保護（US31）を反映する

## 決定

以下の組み合わせを採用する。

- **マイクロサービス**: 各バウンデッドコンテキスト（Auth / Booking / Routing / Tracking / Handling / Billing + API Gateway）を独立した Spring Boot アプリケーション・独立したデプロイ単位とする
- **ドメインモデル + ヘキサゴナルアーキテクチャ**: 各サービス内は domain / application / infrastructure / interfaces の 4 レイヤーで構成し、ドメインを技術的関心事から独立させる
- **CQRS**: コマンドは集約経由、クエリは MyBatis の読み取り最適化 SQL で DTO を直接返す
- **Database per Service**: 各サービスが専用 DB（PostgreSQL）を持ち、他サービスの DB に直接アクセスしない
- **イベント駆動**: サービス間の非同期連携は RabbitMQ + Spring Cloud Stream。同期連携は Booking → Routing の経路取得（ACL 経由の REST）のみに限定する
- **共有カーネル**: `Location`（UN/LOCODE）のみ共有ライブラリとして維持し、`VoyageNumber` 等は各コンテキスト固有型とする

### 代替案

- **モジュラーモノリス**: 単一デプロイで運用は簡単だが、本ケーススタディの目的（マイクロサービスの設計・運用の実践）に合致しない。コンテキスト間の独立デプロイ・スケール差別化ができない
- **イベントソーシング（Billing）**: 監査要件は満たしやすいが、初期フェーズには複雑すぎる。`Money` 値オブジェクト + 監査ログで代替し、必要になった時点で再検討する
- **すべて同期 REST で連携**: 実装は単純だが、サービス間の可用性が連鎖し、疎結合というマイクロサービスの利点を失う

## 影響

### ポジティブ

- コンテキストごとに独立したデプロイ・スケーリングができる（Tracking のみタスク数を増やす等）
- 境界が明示されるため、ACL・イベント契約を通じてモデルの汚染を防げる
- テスト戦略をサービス単位で最適化できる（Contract テストでサービス間契約を固定）

### ネガティブ

- 運用の複雑さが増す（サービス数分のビルド・デプロイ・監視）
- 結果整合性の考慮が必要（配送完了 → 精算開始などはイベント経由で遅延する）
- サービス間のスキーマ変更は後方互換の管理が必要

## コンプライアンス

- ArchUnit でレイヤー依存と BC 独立性（ACL ポートのみ越境可）を検証する
- Spring Cloud Contract でサービス間 API・イベントの契約を検証する
- CI はサービス単位のパスフィルタで独立ビルド・デプロイを維持する

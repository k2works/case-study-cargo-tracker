# ADR-005: 認証トークンは sessionStorage に保持する

ブラウザ側の JWT 保管場所を sessionStorage とし、明示ログアウトとタブのクローズで消える形にする。

日付: 2026-08-19

## ステータス

承認済み

## コンテキスト

IT1（US26・US27）でログイン・ログアウトを実装するにあたり、ブラウザが JWT をどこに置くかを決める必要が生じた。設計ドキュメントは「Zustand ストアに保存」とだけ定めており、保管先までは決めていなかった。

保管先の選択は業務の使い勝手とセキュリティの両方に効く。

- **メモリのみ**にすると、画面を再読み込みしたりブックマークから直接 URL を開いたりするたびにログインを求められる。IT1 の E2E で実際にこの形の失敗が現れた（担当外ロールの検証で `/booking/shippers` へ直接遷移したところ、認証が落ちて `/login` に飛んだ）。一覧を開いたまま更新する、別画面を新しいタブで開くといった日常的な操作が業務を止める
- **localStorage** にすると再読み込みには耐えるが、タブを閉じても端末に残る。共用端末（荷役現場の端末を含む）では、次に使う人がそのまま業務画面に入れてしまい、「ログアウトした」あるいは「閉じたから終わった」という利用者の理解が裏切られる

本システムは営業所・港湾の共用端末での利用を含み、ロールによって見える情報が異なる（US26 のロール別画面制御）。

## 決定

1. **JWT は sessionStorage に保持する。** Zustand の persist ミドルウェアを使い、保存するのはトークンと利用者情報（ID・表示名・ロール）だけとする
2. **明示ログアウト時は保存内容も消す。** ログアウト後はブラウザバックで業務画面に戻れないよう、遷移は履歴の置き換えで行う
3. **localStorage は使わない。** タブをまたいで持ち越さないことをテストで固定する

### 代替案

- **HttpOnly Cookie**: XSS でトークンを読み出せない点で最も強い。ただし Gateway・SPA・開発環境（Heroku の別オリジン）をまたぐ CSRF 対策とオリジン設定が増え、IT1 の範囲では投資に対して見合わない。将来、扱う情報の機微さが上がった段階で本 ADR を置換する候補とする
- **メモリのみ**: 最も残らないが、上記のとおり日常操作で業務が止まる。「安全だが使われない」形になり、結局は共用端末でログアウトせず放置する運用を招く
- **localStorage**: 実装は最も簡単だが、共用端末での持ち越しという本システムで最も現実的なリスクを増やす

## 影響

### ポジティブ

- 再読み込み・URL 直接入力でも作業が続く。営業担当者が一覧を開いたまま更新する使い方が成立する
- タブを閉じれば消えるため、共用端末で放置されたセッションが残らない
- 保管先が 1 箇所に決まり、「どこに置いてあるか」を追う必要がなくなる

### ネガティブ

- XSS があればトークンを読み出せる。依存パッケージの脆弱性検査と、ユーザー入力を DOM に直接挿入しない方針が前提になる
- 同じブラウザの別タブでは入り直しになる。複数タブで並行作業する利用者には手間が増える（この不便は共用端末の安全と引き換えに受け入れる）

## コンプライアンス

- `auth-store` のテストで次の 3 点を固定する。(a) ログインすると sessionStorage に保持される、(b) ログアウトすると消える、(c) localStorage には保存されない
- 保管先を変える変更は本 ADR の更新とセットで行う

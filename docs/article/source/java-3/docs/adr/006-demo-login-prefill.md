# ADR-006: 開発環境のログイン画面に動作確認用の利用者を事前入力する

開発環境に限り、ログイン画面に動作確認用の利用者 ID とパスワードを事前入力し、担当ごとの利用者を一覧する。既定は無効とし、ビルド時に明示的に有効化した成果物でのみ表示する。

日付: 2026-08-19

## ステータス

承認済み

## コンテキスト

本システムは担当（ロール）によって見える画面が変わる。IT1 の時点で 7 ロールがあり、以降のイテレーションで各ロールの画面が増えていく。

動作確認のたびに次の手間が発生していた。

- 画面を触るたびに利用者 ID とパスワードを打ち直す
- どの ID がどの担当かが画面から分からず、確かめるたびにシードの SQL（`V3__seed_users.sql`）を読みに行く
- 無効化されたアカウントの挙動（US31）を試したくても、そのような利用者が存在しない

一方で、認証情報が入力済みの画面を業務環境に出すことは避けねばならない。フロントエンドは SPA であり、この種の設定は**ビルド時に成果物へ埋め込まれる**。実行時の環境変数では取り消せないため、「本番のイメージにうっかり焼き込む」経路を塞ぐ必要がある。

## 決定

1. **既定は無効とする。** 事前入力は `VITE_DEMO_LOGIN_ENABLED=true` を**ビルド時に**渡した成果物でのみ有効になる。有効化を書き忘れたら安全側に倒れる
2. **有効時は開発環境である旨を画面にはっきり表示する。** 事前入力されていることを隠すと、本番同様の画面だと思い込まれる
3. **担当ごとの利用者を一覧し、選ぶと入力欄に反映する。** パスワードは一覧の全員で共通とし、その旨も画面に書く
4. **ログインできない利用者（`disabled01`）を一覧とシードの両方に用意する。** 一覧に載せる以上、実際にログインできないことまで確かめられなければ確認の役に立たない
5. **有効化するのは開発環境のビルドだけとする。** ローカルの開発サーバ（`.env.development`）、kind のイメージ（`dev:k8s:images`）、Heroku 開発環境のイメージ（`deploy:dev:push:frontend`）の 3 箇所で明示的に渡す

### 代替案

- **実行時の環境変数で切り替える**: SPA では成果物に埋め込まれるため実現できない。サーバー側で画面を組み立てる構成（take-6 の Thymeleaf）なら可能だった
- **開発環境専用のビルドを別に持たない（常に有効）**: 業務環境に認証情報が入った画面を出すことになる。論外
- **一覧を出さず事前入力だけにする**: どの ID がどの担当かが分からないままなので、ロール別の確認という主目的が果たせない

## 影響

### ポジティブ

- 担当ごとの画面を、シードの SQL を読まずに切り替えて確認できる
- 無効化アカウントの挙動を画面から確かめられる
- 開発環境であることが画面から一目で分かる

### ネガティブ

- 開発環境の URL を知る第三者に、動作確認用の利用者 ID と共通パスワードが見える。開発環境には業務データを置かないことが前提になる
- ビルド成果物が環境ごとに変わる。「開発環境で動いたものをそのまま本番へ」という運用はできない（もともと環境変数でビルドが変わる構成のため、新たな制約ではない）

## コンプライアンス

- **本番相当ビルドに認証情報が入らないことを E2E で検査する**（`e2e/production-build.spec.ts`）。ビルド時に埋め込まれる以上、成果物を配信して確かめるほかない。CI の `test:e2e:production` で実行する
- 既定が無効であることをユニットテストで固定する（`demoLoginOf(undefined).enabled === false`）
- 一覧の利用者が全業務ロールを覆うこと・ログインできない利用者が含まれることをテストで固定する
- `disabled01` が実際にログインできないことを authms の結合テストで確認する

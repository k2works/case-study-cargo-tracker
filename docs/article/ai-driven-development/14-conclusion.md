# 第 14 章：何が効き、何が効かなかったか

## この章の狙い

20 イテレーション・8 日・36 ストーリー・テスト 1,578 件の実績から、**AI と組んだ開発で何が品質を守り、何が守らなかったか**を総括します。

第 1 章で結論を先出ししました。ここでは根拠を添えて確定させます。

## 効いたもの

### 1. 手順を Skill として固定する

| 効果 | 根拠 |
| :--- | :--- |
| 8 日で 20 回転できた | 開始・終了を人間が指示していたら指示だけで日が終わる |
| 着手前の突合が実装をブロックする欠落を毎回検出 | IT4 で 6 件、IT7 で 13 件（うち 3 件がブロック） |
| 手順自体がふりかえりで育つ | CI 確認・SonarQube ゲート・途中レビューが後から工程になった |

**標準化して効いたのは実装ではなく、その前後です。** 56 Skill のうち実装は 2 つで、分析 14・計画 8 という配分がそれを示しています。

### 2. 破壊検証

| 効果 | 根拠 |
| :--- | :--- |
| 空振りが 19 イテレーションを通じて毎回検出された | IT4 で 1 件、IT5 で 2 件、IT11 で 3 件、IT16 で 3 件、IT19 で 5 件 |
| リストの作り方が結果を決めると分かった | 自分で選ぶと全部赤（IT10）、機械的に数えると 3 件空振り（IT11） |
| 壊すタイミングで空振りが 0 になった | 各コミットの中で「作った直後に壊す」（IT12） |

**「テストがある」と「テストが判別する」の差を、唯一実測できる手段**でした。

### 3. マルチパースペクティブレビュー

| 効果 | 根拠 |
| :--- | :--- |
| 全緑からの高優先度指摘が 7 IT 連続 | IT9〜IT15。IT14 は 18 件 |
| 利用者代表の指摘が一貫して重い | IT6・IT7 とも高 9 件中 6 件 |
| プローブを書くレビューは事実を持ってくる | IT20 で tester が実測 2 件を示した |
| 3 視点が独立に同じ箇所を指す | IT20 の U4 副作用。実装者には見えなかった |

**自動チェックが原理的に見ない領域**（業務としてどう使うか・コメントと実装の一致・記録の有無）を、レビューだけが見ました。

### 4. 規則を検査に落とす

| 効果 | 根拠 |
| :--- | :--- |
| 検査は実数を明らかにする | 指摘 2 本 → 実測 9 本（IT12）、指摘 1 組 → 実測 3 組（IT20） |
| 検査が設計を良くする | Checkstyle の上限が「不正な組み合わせを作れる値」をまとめる型を生んだ |
| 「守らない」の明記が実態を可視化 | ADR 19 件中 13 件が人の注意に預けられていた |

### 5. 返済枠を IT 序盤の独立コミット枠に置く

| 効果 | 根拠 |
| :--- | :--- |
| 6 IT 連続で機能 | 「余力次第」時代は 3 IT 連続で繰り越された（ADR-008） |
| 返済枠が本体と同規模でも落とさなかった | IT12：返済枠 27h / 本体 30h、落としたもの 0 |
| 猶予で優先順位を決める | IT20 の `Cargo` は猶予 0 行だった |

### 6. 返済専用の局面を置く

**SP 0 のイテレーションを 4 回（IT16・17・19・20）置きました。20 回のうち 5 分の 1 です。**

IT16・IT17 とも落としたものは 0 件で、局面の完了条件は「据え置きの表が空」＋**空を保つ検査つき**で定義されました。

## 効かなかったもの

### 1. ADR・コメント・案内文による規則の宣言

**主題 M2。20 イテレーションで一度も止まりませんでした。**

| IT | 形 |
| ---: | :--- |
| 6 | Javadoc が防ぐと宣言した故障モードを実装が守っていない |
| 7 | 画面のコメント・案内文・計画で **6 件** |
| 8 | **書いた本人が同じ IT の中で破る**（5 件） |
| 11 | コメントが実装より強い保証を主張（3 件） |
| 15 | **ADR-009 が 7 IT のあいだ半分だけ守られ、違反が 5 本増えた** |
| 17 | **「検査で固定した」と書いて検査が入っていなかった** |
| 19 | ADR が「名前で記録した」と書いて記録が無かった |
| 20 | 「是正はタスク 7」と書いてタスク 7 で是正しなかった |

対処は一貫して「**同じ変更の中で検査に落とす**」でした。落とせたものは止まり、文章のまま残ったものは再発しています。

**AI は文章を速く大量に書けるため、この失敗は人手の開発より高頻度で出ます。** 止められるのは個々の規則であって、「文章が実態を先回りする」という性質そのものではありません。

### 2. 件数・進捗の自己申告

**主題 M3。5 回連続でずれ、IT20 で 10・11 度目を数えています。**

| 項目 | 記録 | 実測 | 倍率 |
| :--- | ---: | ---: | ---: |
| 貨物フィクスチャ | 7 | 39 | 5.6 |
| レコード | 2 | 21 | 10.5 |
| **列の多い一覧** | **1** | **13** | **13** |
| 委譲アクセサ | 34 | **249** | 7.3 |

> **着手時に数え直す習慣は効いている**（毎回ここで気づく）。
> 効いていないのは**記録するときの数え方**である。
>
> — `retrospective-18.md` P2

**この失敗は M4 と連動します。** 小さく記録された負債は落とされ、落とされた負債は育ち、育ったことも小さく記録されます。

### 3. 「任意」と書いた工程

`closing-iteration` のステップ 8（ジャーナル）だけが「（任意）」で、**20 回のうち少なくとも 1 日ぶんが落ちました**。必須ステップの成果物は全 20 回分そろっています。

**規律の強さの差ではなく、必須か任意かの差でした。**

### 4. 記憶に書いただけの教訓

**効いた教訓はいずれも手順か検査の形に落ちたものです。**

| 教訓 | 落とし先 | 結果 |
| :--- | :--- | :--- |
| 返済枠を「余力次第」にしない | 計画のタスク 0（時間を先取り） | **6 IT 連続で機能** |
| 業務日付を UTC で判断しない | `Clock` 注入＋検査 | 機能（ただしテスト側への波及は遅れた） |
| 一覧は行をまとめて引く | **記憶のまま** | **返済した同じ IT で同型を再発**（IT15） |
| マニュアルの項目表を突き合わせる | Try に落とさなかった | **次の IT で再発**（IT7） |

## AI 駆動開発のアンチパターン

20 イテレーションから抽出した、繰り返し踏んだ形です。

| # | アンチパターン | 症状 |
| :--- | :--- | :--- |
| 1 | **宣言を成果と数える** | ADR・Javadoc・案内文を書いた時点で守った気になる |
| 2 | **起動を実行と数える** | レビューエージェントを起動したが 4 視点が無応答（IT7） |
| 3 | **目視の件数を実数と数える** | 指摘 2 本の裏に 9 本、記録 34 件の裏に 249 件 |
| 4 | **自分で選んだリストを網羅と数える** | 破壊検証 10 件全件赤、選ばなかった 3 件が壊れていた（IT10） |
| 5 | **規律の適用範囲を狭く取る** | 実装コードには当て、設定・CI・マイグレーションには当てない（IT1） |
| 6 | **検査を書きやすくするために設計を歪める** | 「集約ルート以外は呼べない」と一般化すると設計が壊れる（IT20 で回避） |
| 7 | **名簿方式で検査する** | 載せ忘れたものほど漏れる。3 IT 素通り（ADR-015） |
| 8 | **文章を実装より先に書く** | マニュアルが存在しない機能を約束する（IT1） |
| 9 | **受入基準の充足で完了とする** | 「3 件あります」と告げて、その 3 件へ行けない（IT9） |
| 10 | **手が空いたから前倒しする** | 根拠が変わらないのに判断を上書きする |

**1〜4 に共通するのは「実行したこと」と「働いたこと」を同一視する形**です。主題 M1 の一般形であり、対象がテスト・エージェント・検査・記録と移り変わりながら 20 イテレーション出続けました。

## AI 駆動開発の一般性と限界

### 一般化できること

**主題 M1〜M5 は構成に依存しません。**

エージェントメモリ（第 8 章）は同じ題材の他言語実装と共有されており、**Go 実装で得た「余力次第の返済枠は固定化する」という教訓が、Java 実装で 6 イテレーション連続の返済枠運用を支えました**。言語もフレームワークも違いますが、失敗の形は同じです。

蓄積された 49 件の教訓のうち、言語固有のもの（F# のレコードフィールド衝突、Haskell の qualified import）は少数派で、**大半は「緑と守られているは別」「文章と実装は別」の変奏**です。

### 一般化できないこと

| 限界 | 内容 |
| :--- | :--- |
| 単一構成 | モデル・ツール・言語がいずれも 1 通り。比較の根拠を持たない |
| 開発者 1 名 | 複数人での AI 運用（レビューの分担・コンフリクト）は観測されていない |
| 8 日 | 数か月スケールで出る劣化（依存の陳腐化・要員交代）は扱えない |
| 題材 | 業務システム。機械学習・リアルタイム制御には一般化できない |

**そして最も大きな限界は、記録されていない層があることです。** 第 4 章で見たとおり、**開発を実際に駆動していた Ralph Loop について、20 回のふりかえりは何も語っていません**。ふりかえりの対象になっていない仕組みは、良くも悪くもなりません。

## 結論

**AI 駆動開発で品質を守ったのは、AI を賢く使う工夫ではありませんでした。**

効いたものはすべて、**「実行したこと」を「働いたこと」に変換する仕組み**です。

- 破壊検証は、テストが判別することを実測に変えた
- レビューは、緑であることを他者の目に晒した
- 検査は、宣言を強制に変えた
- 返済枠は、意図を時間に変えた

効かなかったものはすべて、**文章のまま留まったもの**です。ADR に書いた規則、コメントに書いた保証、記録に書いた件数、記憶に書いた教訓 — いずれも書いた瞬間は正しく、そして追随しませんでした。

**AI は文章を速く大量に書きます。** だから AI 駆動開発の中心的な課題は「AI にどう書かせるか」ではなく、**書かせたものが働いていることをどう確かめ続けるか**です。

20 イテレーションで、この課題は解決していません。IT20 のふりかえりは、**その回に新しく足した安全装置そのものに過去の失敗が 3 種類再現した**ことを記録して終わっています。

**それでも、失敗の形は毎回小さくなりました。** 型 → メソッド → 呼び出しの形、と検査の粒度が細かくなったように、事故の粒度も細かくなっています。これが 8 日間で得られた実際の到達点です。

# 第 6 章：マルチパースペクティブレビュー

## 解こうとした問題

**自動チェックが原理的に見ない領域があります。**

前章の破壊検証を 19 イテレーション続け、`./gradlew check` 全緑・E2E 全緑・SonarQube Quality Gate PASS・CI 緑という状態を毎回作りました。**それでもレビューは毎イテレーション高優先度の指摘を出しました。**

> うち 13 件は正しさ・読み手に関わるもので、**自動チェックが原理的に見ない領域**
> （業務としてどう使うか、コメントと実装の一致、記録の有無）に集中している。
>
> — `retrospective-14.md` P4

## 仕組みの中身

`developing-review` Skill は、5 つの XP エージェントを **同一メッセージで並列起動** します。

| エージェント | 視点 | 着眼点 |
| :--- | :--- | :--- |
| `xp-programmer` | コード品質 | SOLID・DRY・命名・可読性・TDD サイクルの遵守 |
| `xp-tester` | テスト品質 | カバレッジ・境界値・エッジケース・テストの信頼性 |
| `xp-architect` | 設計整合性 | アーキテクチャとの整合・依存の方向・技術的負債 |
| `xp-technical-writer` | ドキュメント品質 | コメントの適切さ・README・機能の理解しやすさ |
| `xp-user-representative` | 利用者視点 | 業務フローとの整合・使い勝手・期待との一致 |

出典は `.claude/skills/developing-review/SKILL.md` です。

### 2 段階運用

20 イテレーションを通じて、レビューは 2 段階に定着しました。

| 段階 | タイミング | 目的 |
| :--- | :--- | :--- |
| **途中レビュー**（セルフレビュー） | 実装の途中で 1 度 | **その場で直せる幅のうちに**捕まえる |
| **クローズ前レビュー** | 品質ゲート通過後 | 5 視点の並列で、イテレーション全体を対象に |

途中レビューを入れる理由は明快です。

> **クローズ時のレビューでは、直す幅が広がっていた。** 途中で回したから、その場で直せた。
>
> — `retrospective-16.md` K1

## 実際に働いたか

### 全緑からの高優先度指摘が 20 イテレーション続いた

レビュー記録（`source/java-2/docs/review/`）から、高優先度の件数を並べます。

| IT | 高 | 特記 |
| ---: | ---: | :--- |
| 1 | 10 | **うち 4 件が「入っているつもりで働いていない安全装置」** |
| 2〜5 | 各 2 | すべて IT 内で対応 |
| 6 | 14 | 8 件を IT 内で対応。レビュー後に設計変更 |
| 7 | 9 | **エージェント 1 視点＋自己レビュー 4 視点**（後述） |
| 8 | 11 | 5 視点すべてが回答を返した |
| 9 | 9 | **全緑の状態から欠陥が出た**（画面から踏む経路・宣言と実装のずれ） |
| 10 | 10 | 破壊検証 10 件全件赤なのに、検証対象外の 3 件が壊れていた |
| 11 | 14 | 10 件を IT 内で対応 |
| 12 | 3 | 並列レビューが応答せず自己レビューで実施 |
| 13 | 13 | 9 件を IT 内で対応、4 件を IT14 へ記名 |
| 14 | **18** | 13 件を IT 内で対応、5 件を IT15 へ記名 |
| 15 | 5 | ADR-009 の違反が検査で判明 |
| 16 | 3（途中）＋ 2（クローズ） | **高 2 件はどちらも自分が書いた検査クラス自身の問題** |
| 17 | 1 | A1 の副作用（押すと 403 になるボタン） |
| 20 | 10 | **本 IT が新しく足した安全装置に、過去の失敗が 3 種類再現** |

**「全緑からレビューが高を出す」状態は IT9 から IT15 まで 7 イテレーション連続**で記録されています。

### 利用者代表の指摘が一貫して重かった

IT6・IT7 では**高優先度 9 件のうち 6 件が利用者代表**でした。

利用者代表が見つけたものの例です。

| IT | 指摘 |
| ---: | :--- |
| 9 | 「3 件あります」と告げながら、**その 3 件へ行く手段が無い** |
| 10 | 未解決の例外を 1 件に限る制約は、**遅延の対応中に破損が判明する実務**に合わない（代替案も同時に提示） |
| 13 | 経理担当者が**予約詳細を開けない**（403）。自分で書いた運用要件が成立していなかった |
| 18 | 貨物種別を変えると**入力済みの内容が全部消える** |
| 20 | 手持ちが全て期限切れの朝、条件を入れていないのに「条件を変えてお試しください」が出る |

**受入基準を満たすことは、AI にとって最も達成しやすい目標です。** 満たしたうえで業務が回らない、という形は自動チェックにも実装者にも見えません。

> **計画に書いた条件を満たすことと、業務が回ることは別である。**
>
> — `retrospective-9.md` P2

### プローブを書くレビューは、事実を持ってくる

IT20 のクローズ前レビューでは、tester が **3 種類のプローブを実際に書いて走らせました**。

| 見つけたもの | 実測の内容 |
| :--- | :--- |
| `EntityEncapsulationTest` がメソッド参照を素通り | `ProposedRoute::withPriority` を拾わず**緑のまま** |
| `RecentBusinessTime` の真夜中の順序崩れ | `hoursAgo(1)` と `hoursAgo(2)` が**どちらも 00:00 になり順序が消える** |

> どちらも読むだけでは見つからず、こちらの「破壊検証で 4 メソッドすべて赤を確認した」という
> 報告と矛盾しない形で潜んでいた。
>
> **「壊して赤」を実演したレビューは、意見ではなく事実を持ってくる。**
>
> — `retrospective-20.md` K3

**レビューの質は、コードを書くかどうかで決まります。** 読むだけのレビューは、実装者の報告と矛盾しない欠陥を見つけられません。

### 複数視点が独立に同じ箇所を指す

IT20 の U4 の副作用は、**利用者代表・アーキテクト・テクニカルライターの 3 視点が独立に同じ箇所を指しました**。実装者には見えていません。

**視点の分割は冗長ではありません。** 独立に到達したことが、その指摘の確度を上げます。

## 働かなかったケース

### 1. エージェントが回答を返さない

**AI 駆動開発に固有の失敗です。** 20 イテレーションで少なくとも 3 回起きています。

| IT | 症状 | 対処 |
| ---: | :--- | :--- |
| 7 | **5 視点中 4 視点が回答を返さなかった**（調査を終えたと見られる状態でアイドルに戻った） | 4 視点を順次自分で実施。高 3 件を追加検出 |
| 12 | 並列レビューが応答せず | 自己レビューで実施 |
| 15 | — | 5 視点を**逐次**で実施 |

> フォールバック手順に切り替えて 4 視点を自分で行い、高優先度 3 件を追加で見つけたため
> 結果的には成立したが、**「エージェントを起動した」ことと「レビューが行われた」ことは別である。**
>
> — `retrospective-7.md` P3

主題 M1 が、テストでも検査でもなく**エージェント実行**の側に現れた形です。**並列起動は安くありませんが、無応答は静かです。** 視点ごとに結果の有無を確認する手順が要ります。

### 2. 途中レビューが 2 イテレーション連続で落とされた

途中レビューは Try として決められましたが、**IT14・IT15 と 2 回連続で実施されませんでした**。IT16 で初めて実施したところ、**IT16 自身が定めた規則を IT16 の実装が破っている**ことが見つかっています。

**返済枠と同じく、「余力があれば」の位置に置かれた工程は落ちます**（主題 M4）。

### 3. 指摘は目視の上限を示す

IT11 のレビューは「BC をまたぐ SQL が 2 本」と指摘しました。**検査を作って走らせたら 9 本ありました**（7 本は既存）。

IT20 でも、キャプチャの重複についてレビューが指摘した 1 組に対し、検査を入れると既存 2 組が即座に出ています。

**レビューは「そこに問題がある」ことを教え、検査は「いくつあるか」を教えます。** 指摘の件数を実数と取り違えると、返済の判断を誤ります（主題 M3）。

### 4. 前 IT の指摘がそのまま再発する

IT7 では、IT6 のレビュー指摘が 2 件そのまま再発しました。

> **IT6 の Try には「マニュアルの索引 3 点同期」は入っていたが、
> 「項目表と付録 B」は入っていなかった。**
> ふりかえりで Try にしなかった指摘は、次の IT で同じように出る。
>
> — `retrospective-7.md` P2

**レビューで指摘され、その場で直したものは、Try にしない限り再発します。** 直したことと、次に書くときに思い出すことは別です。

## この規律のまとめ

| 効く条件 | 根拠 |
| :--- | :--- |
| 視点を分けて独立に走らせる | 3 視点が独立に同じ箇所を指した（IT20） |
| 途中とクローズ前の 2 段階で回す | 途中なら直す幅が狭い（IT16） |
| レビューアがプローブを書く | 読むだけでは報告と矛盾しない欠陥が残る（IT20） |
| 視点ごとに**結果が返ったか**を確認する | 起動したことと行われたことは別（IT7・IT12） |
| 指摘を Try に落とす | Try にしなかった指摘は次の IT で再発する（IT7） |
| 指摘の件数を実数と混同しない | 指摘 2 本 → 検査で 9 本（IT11・IT12） |

**自動チェックとレビューは代替関係ではありません。** 破壊検証は「いま知っている壊れ方」を確かめ、レビューは「知らない壊れ方」を持ってきます。20 イテレーションで、どちらか一方だけで済んだ回はありませんでした。

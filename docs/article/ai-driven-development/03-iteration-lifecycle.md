# 第 3 章：イテレーションのライフサイクル

## 解こうとした問題

**イテレーションは実装で終わりません。**

実装とレビューで達成感が出た後に、報告書・GitHub 同期・マニュアル更新・ドキュメント同期という事務作業が残ります。ここが抜けると、次のイテレーションの開始時に「何が終わっていて何が残っているか」が分からなくなります。

同じことが開始側にもあります。**計画を作っただけで着手すると、設計ドキュメントとの不整合がそのまま実装の手戻りになります。**

そこで開始と終了を、それぞれ 1 つの Skill として固定しました。

## 仕組みの中身

### `opening-iteration`（6 ステップ）

| # | ステップ | 内容 |
| ---: | :--- | :--- |
| 1 | 前イテレーションふりかえりの反映 | Try と持ち越し（返済枠）を計画に落とす |
| 2 | イテレーション計画の作成 | ストーリー・タスク・見積 |
| 3 | **詳細整合性検証** | 計画と上流設計（ユーザーストーリー・ドメインモデル・データモデル・UI 設計）の突合 |
| 4 | **横断整合性検証** | 開発戦略・過去の計画・設計トピックとの連続性 |
| 5 | GitHub 同期 | Issue・Milestone・Project |
| 6 | ドキュメント同期 | 索引の更新 |

**ステップ 3・4 がこの Skill の中心です。** 計画を書くこと自体は難しくありません。着手前に**上流の設計と突き合わせる**ことが、手戻りを防ぎます。

### `closing-iteration`（7 ステップ）

| # | ステップ | 内容 |
| ---: | :--- | :--- |
| 1 | マルチパースペクティブレビュー | XP 5 視点。高優先度は対応または方針明記 |
| 2 | 品質ゲート | 全テスト緑・Lint・カバレッジ |
| 2.5 | **CI 確認** | `gh run list` で対象ブランチの最新実行が success |
| 2.6 | **SonarQube Quality Gate** | Bug 0・Vulnerability 0・重複 3% 未満・カバレッジ目標 |
| 3 | 進捗反映 | `release_plan.md` / `iteration_plan-N.md` を実績で更新 |
| 4 | ふりかえり | KPT |
| 5 | 完了報告書 | `iteration_report-N.md` |
| 6 | GitHub 同期 | Issue クローズ・Project Status |
| 6.5 | ユーザーマニュアル更新 | UI 変更があれば本文・キャプチャ |
| 7 | ドキュメント同期 | `docs/index.md` / `mkdocs.yml` |
| （任意）8 | ジャーナル | 判断・詰まり・学び |

### 順序が意味を持つ

Skill 自身が注意事項として書いています。

> **順序を守る**: レビュー指摘の反映前に報告書を書くと、報告書が実態とずれる。
> 品質ゲートを通す前に GitHub をクローズすると、**緑でない成果を「完了」と宣言してしまう**。
>
> — `.claude/skills/closing-iteration/SKILL.md`

そして、抜けやすい場所も明示されています。

> **抜けやすいのはステップ 5-7**（報告書・GitHub・マニュアル・ドキュメント）。
> 実装とレビューで達成感が出た後の事務作業のため後回しにされやすい。
> **チェックリストで機械的に確認する。**

## 実際に働いたか

### 着手前の突合が、実装をブロックする欠落を毎回見つけた

| IT | 見つけた欠落 |
| ---: | :--- |
| 4 | 設計側の欠落 **6 件**（実装中にさらに 1 件） |
| 7 | 設計ドキュメント・スキーマ・シードデータの欠落 **13 件**（うち 3 件は実装をブロック） |
| 15 | 「作っても届かない」を **3 件** |
| 18 | `route_candidate` の所有 BC が**正典と検査の両方で誤っていた** |

IT4 の例が分かりやすい形です。**費用に入力が無い**ことを計画時に見つけました。

> 着手後に気づいたら **ADR を書く時間ごと計画外**になっていた。
>
> — `retrospective-4.md` K4

### 正典の食い違いを着手前に決着させると、見積が揺れない

IT18 で最も明確に効きました。`domain-model.md` が「ルート候補はスタブ実装」と書き、ADR-006 が外部連携を採らないと決めていた矛盾を、**着手前に決着**させています。

> 決着の内容は SP を動かした（スタブなら 3、独自の探索なら 8、ACL なら 5）。
> **決めてから着手したから、見積が揺れなかった。**
>
> — `retrospective-18.md` K1

**同じ 5SP でも、決めずに着手していれば実装中に 3〜8 の幅で振れていました。**

### CI 確認をステップに入れた効果

IT3 で「ローカル緑・CI 赤のままクローズに入りかけた」失敗から追加されたステップです。以降、CI が赤のままクローズされた回はありません。IT8 では Gradle のロックファイル差分で一度赤になりましたが、**クローズ前に検出して緑に戻して**います。

### 品質ゲートを「テスト緑」で終わりにしない

ステップ 2.6 の効果です。20 イテレーションを通じて SonarQube Quality Gate は PASS を維持し、Bug 0 / Vulnerability 0 / Code Smell 0 / 重複 0.24〜0.4% で推移しました。

**ただし本シリーズが繰り返し示すとおり、これは「守られている」ことを意味しません。** 全緑の状態からレビューが高優先度を出す状態が 7 イテレーション連続で記録されています（第 6 章）。

## 働かなかったケース

### 1. ステップの順序が守られても、工程の中身は保証されない

IT19 の失敗です。ステップ 6.5（マニュアル更新）は実施され、**本文は更新されました**。キャプチャは撮り直されていません。

> **文章は実装に追随していたので、本文だけ読むレビューでは緑に見える。**
> 画像の古さは人の目にしかかからない。
>
> — `retrospective-20.md` P4

**チェックリストは「やったか」を確認しますが、「正しくやったか」は確認しません。**

### 2. 「任意」の工程は落ちる

ステップ 8（ジャーナル）が 2026-08-08 に落ちました。**必須のステップ 1〜7 が生成する成果物は 20 回分そろっています。**

### 3. 突合は「両方が同じ間違いをしている」ケースを捕まえない

IT18 で見つかった限界です。

> IT17 で入れた「正典と検査の突合」は、**両方が同じ間違いをしているため検出できない**。
>
> — `retrospective-18.md` K2

**2 つの記述を突き合わせる検証は、第 3 の情報源（マイグレーションが作った実テーブル）を必要とします。**

### 4. 計画外の作業が工数を圧迫する

IT19 では計画 75h に対し実績 91h（**11h 超過**）で、計画外の 2 件が 16h を占めました。どちらも利用者の依頼で価値はありましたが、**計画の余白は 5h しかなく、超過が確定した時点で落とす順序を見直していません**。

**開始準備で計画を精緻にしても、途中で入る依頼は計画の外にあります。**

## この仕組みのまとめ

| 原則 | 根拠 |
| :--- | :--- |
| 着手前に**上流設計と突き合わせる** | 6 IT 連続で「作ったが使えない」を検出（IT7） |
| **正典の食い違いは着手前に決着させる** | 決めてから着手すると見積が揺れない（IT18） |
| 順序を守る（レビュー → 品質ゲート → 報告 → 同期） | 報告書が実態とずれるのを防ぐ |
| **ローカル緑を CI 緑と混同しない** | IT3 の教訓からステップ化 |
| 抜けやすい工程を**チェックリストで機械的に確認する** | 事務作業は達成感の後に来る |
| **「任意」の工程は落ちる前提で設計する** | ジャーナルが 1 日ぶん欠けた |

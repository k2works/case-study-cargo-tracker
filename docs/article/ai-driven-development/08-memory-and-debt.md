# 第 8 章：記憶と負債 — 失敗を資産にする

## 解こうとした問題

**AI エージェントはセッションをまたいで覚えていません。**

20 イテレーションを 8 日で回すあいだ、セッションは何度も切れます。前のセッションで学んだ「時間で守るテストは判別しない」「業務日付を UTC で判断しない」は、次のセッションの冒頭には存在しません。

そして本シリーズが繰り返し見てきたとおり、**同じ型の失敗は名前を変えて戻ってきます**。記憶が無ければ、20 回のふりかえりは 20 回とも独立した発見の場になり、蓄積しません。

もう 1 つ、記憶と対になる問題があります。**返済しなかった負債は据え置かれるのではなく、育ちます**（主題 M4）。

## 仕組みの中身

3 層で構成されています。

| 層 | 実体 | 粒度 | 寿命 |
| :--- | :--- | :--- | :--- |
| **エージェントメモリ** | 1 ファイル 1 教訓（`feedback_*.md`）＋索引 `MEMORY.md` | 汎化された教訓 | プロジェクトをまたぐ |
| **ジャーナル** | `docs/journal/YYYYMMDD.md` | その日の判断の物語 | プロジェクト内 |
| **ふりかえり** | `docs/development/retrospective-N.md` | KPT と Try | イテレーション |

### エージェントメモリ

1 ファイルに 1 つの事実を書き、フロントマターで種別を持ちます。本文は **教訓 → Why → How to apply** の 3 部構成です。実例を挙げます。

```markdown
---
name: feedback_debt-allowance-defer-antipattern
description: 「余力次第の返済枠」は毎 IT 繰越されて固定化する。
             返済枠は IT 序盤の独立コミット枠として先着手する
metadata:
  type: feedback
---

技術的負債の返済を計画に「返済枠（余力次第・超過時は次 IT へ繰越）」として
入れると、コア機能が優先され毎イテレーション繰越され続けて固定化する。

**Why:** 「余力次第」は実質「やらない」宣言に近い。コア US（受入基準あり）は
必ず優先され、余力枠は毎回削られる。負債は利子を生みながら残る。

**How to apply:** 返済枠を計画に入れるなら「余力次第」ではなく
**IT 序盤（Day 1-2）の独立コミット枠**としてスケジュールし、
コア US より先に着手する。[[feedback_ralph-loop-iteration]]
```

**`Why` と `How to apply` が必須**であることが要点です。「〜に気をつける」だけの記憶は次に読んでも行動が変わりません。`[[name]]` で相互にリンクします。

現在 **49 件**が蓄積されています。

### ジャーナル

ふりかえりや完了報告書とは目的が違います。

> コミットメッセージは「この変更が何を達成したか」を書きます。ジャーナルは
> **「なぜそうしたか、何を諦めたか、次回どう活かすか」** を書きます。
>
> **失敗の記録を省きません。** ジャーナルの価値の半分は「同じ罠に二度落ちない」ことにあります。
>
> — `journal/index.md`

各日に「裏テーマ」が付けられているのが特徴です。

| 日付 | 裏テーマ |
| :--- | :--- |
| 08-06 | 緑であることと働いていることは別 |
| 08-07 | 同じ型の失敗は繰り返す |
| 08-09 | 緑であることは、守られていることの根拠にならない |
| 08-11 | コメントや ADR が仕様を語りながら、実装が守っていない |
| 08-11（IT17） | 文章が実態を先回りする |
| 08-12（IT18） | 数えずに書いた記録 |
| 08-12（IT19） | 検査を足す回に、検査自身の穴を 3 つ作った |

**本シリーズの主題 M1〜M5 は、この裏テーマの列から抽出したものです。**

## 実際に働いたか

### 教訓が実装をまたいだ

本プロジェクトの記憶は、**同じ題材の他言語実装と共有されています**。49 件のうち多くは Go・Ruby・TypeScript・Flix・Haskell・F# の実装で得られたものです。

Java 実装のふりかえりが、他実装由来の記憶を名指しで参照しています。

| 参照された記憶 | 由来 | Java 実装での使われ方 |
| :--- | :--- | :--- |
| `feedback_debt-allowance-defer-antipattern` | **Go take-1**（ADR-0008 が 3 IT 連続繰り越し） | IT14 で「『余力次第』にしなかったことが効いた」と参照 |
| `feedback_tests-must-use-the-same-clock` | 別実装 | IT14 で**同じ型を再発させたときに名指しで記録** |
| `feedback_business-timezone-not-utc` | 別実装 | IT3 の業務タイムゾーン導入時に参照 |
| `feedback_comments-are-specs-verify-them` | — | IT20 で再現した失敗の由来として記録 |

**Go 実装で 3 イテレーション繰り越された負債の教訓が、Java 実装で 6 イテレーション連続の返済枠運用を支えました。** 言語もフレームワークも違いますが、失敗の形は同じです。

### 返済枠を「時間で先に確保する」

主題 M4 への対処が、この局面で最も明確に効いた規律です。

| 期間 | 運用 | 結果 |
| :--- | :--- | :--- |
| IT6〜IT8 | 「余力次第」 | **ADR-008 が 3 IT 連続で繰り越された** |
| IT7 以降 | **IT 序盤の独立コミット枠**として時間を先取り | 6 IT 連続で機能 |

> タスク 0 として 8 時間を先取りし、6 件すべてを実施した。
> **「余力次第」と書かなかったから実施された。**
>
> — `retrospective-8.md` K1

IT12 では運用が成熟の頂点に達しました。返済枠 27 時間（ストーリー本体 30 時間）で、**最初の 8 コミットがすべて返済枠**。ストーリーの着手は 9 コミット目です。**落としたものは 0 件**でした。

> 本 IT では返済枠が過去最大だったが、**落とす順序を計画に先に書いていた**ため、
> 判断を先送りせずに済んだ。
>
> — `retrospective-12.md` K1

### 落とす順序の決め方が 20 IT かけて変わった

| 時期 | 判断基準 |
| :--- | :--- |
| 初期 | 余力次第（＝実質やらない） |
| 中期 | 時間で先に確保し、**落とす順序を計画に書く** |
| IT16 | **実測が判明するたびに順序を組み替える**（落とさない対象を後ろに置かない） |
| IT19〜20 | **見積もりでなく「次の IT で対象が増えるか」で決める** |

最後の基準が、IT20 で `Cargo` を救いました。500 行・**猶予 0 行** — 次に 1 メソッド足せば Checkstyle が赤になる状態で、「余力があれば」に回していれば IT21 の最初の変更が止まっていました。

**負債の優先順位は「大きさ」ではなく「猶予」で測る。** 20 イテレーションかけて到達した結論です。

## 働かなかったケース

### 1. 記録は実態より小さい

**主題 M3 は最後まで解消しませんでした。** 5 回連続でずれ、IT20 では 10・11 度目を数えています。

| 項目 | 記録 | 実測 | 倍率 |
| :--- | ---: | ---: | ---: |
| C2（貨物フィクスチャ） | 7 | 39 | 5.6 |
| C3（レコード） | 2 | 21 | 10.5 |
| R7（列の多い一覧） | **1** | **13** | **13** |
| C1（委譲アクセサ） | 34 | **249** | 7.3 |

> **着手時に数え直す習慣は効いている**（毎回ここで気づく）。
> 効いていないのは**記録するときの数え方**である。
>
> — `retrospective-18.md` P2

**記憶の仕組みは「何を学んだか」を残しますが、「どれだけあるか」は残しません。** 数は書いた時点の目視であり、目視は必ず小さく出ます。対処として「返済枠を送るときは実測値を添える」「数を書くときは数えた方法も書く」という Try が出ましたが、**IT20 の計画自身がその Try を適用していませんでした**。

### 2. ジャーナルは手順に組み込まれていないと落ちる

**2026-08-08 のジャーナルがありません。** IT4〜IT10 を進めた日です。

> **書かなかったことも記録します** — ジャーナルは書いた日だけが残り、
> 書かなかった日の判断は追えなくなります。
>
> — `journal/index.md`

**`closing-iteration` が生成する完了報告書とふりかえりは全 20 回分そろっています。** 手順に組み込まれた記録は残り、そうでない記録は落ちました。これは規律の強さの差ではなく、**仕組みに載っているかどうか**の差です。

### 3. 返済したことと、次に書くときに思い出すことは別

IT15 で、N+1 の指摘を**返済した同じイテレーションで同じ形を作りました**。

> 「一覧を作るときは行をまとめて引く」は 2 イテレーション前に学んだはずだった。
> **返済したことと、次に書くときに思い出すことは別である。**
>
> — `retrospective-15.md` P3

**記憶に書いても、書く瞬間に参照されなければ効きません。** 効いた教訓（返済枠・タイムゾーン）はいずれも**手順や検査の形になったもの**で、記憶のまま留まったものは再発しています。

### 4. Try にしなかった指摘は再発する

> **IT6 の Try には「マニュアルの索引 3 点同期」は入っていたが、
> 「項目表と付録 B」は入っていなかった。**
> ふりかえりで Try にしなかった指摘は、次の IT で同じように出る。
>
> — `retrospective-7.md` P2

**レビューで指摘され、その場で直したものは、Try に落とさない限り再発します。**

### 5. 落とした負債は育つ

IT15 で落とした 4 件の育ち方です。

| 落とした項目 | 育ち方 |
| :--- | :--- |
| テストヘルパーの重複 | 対象が **5 → 7 クラス**に増えた |
| `InvoiceView` の引数整理 | 同じ形の `CancellationView` が **19 引数**で生まれた |

さらに IT16 で数え直したところ、テストヘルパーの重複は実測 **39 クラス・41 箇所**でした。**「5 → 7 に増えた」という記録を見て「まだ小さい」と判断していた**わけです。

**M3（記録が小さい）と M4（負債が育つ）は連動します。** 小さく記録された負債は落とされ、落とされた負債は育ち、育ったことも小さく記録されます。

## この規律のまとめ

| 原則 | 根拠 |
| :--- | :--- |
| 教訓は **Why と How to apply** つきで残す | 「気をつける」だけでは行動が変わらない |
| 記憶はプロジェクトをまたいで共有する | Go 実装の教訓が Java 実装で 6 IT 機能した |
| 教訓は**手順か検査の形にして初めて効く** | 記憶のまま留まったものは再発した（IT15） |
| 返済枠は **IT 序盤の独立コミット枠**に置く | 「余力次第」は 3 IT 連続で繰り越された |
| 落とす順序は「**次の IT で対象が増えるか**」で決める | `Cargo` は猶予 0 行だった（IT20） |
| 負債を送るときは**実測値を添える** | 数えずに送った負債は、次に読む人も数えない |
| 指摘は **Try に落とす** | Try にしなかった指摘は次の IT で再発する |
| 記録は**手順に組み込む** | 組み込まれていないジャーナルが 1 日ぶん落ちた |

**記憶の仕組みは、失敗を資産に変えました。** ただし変換できたのは、**手順か検査の形に落ちたものだけ**です。文章のまま残った教訓は、20 イテレーションを通じて何度も同じ顔で戻ってきました。

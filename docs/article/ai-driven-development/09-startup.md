# 第 9 章：立ち上げ（IT1〜IT3）— ウォーキングスケルトンを貫通させる

## この局面のゴール

**画面 → ドメイン → DB が実際に貫通することを、最初の 3 イテレーションで確かめる。**

設計ドキュメントで妥当と判断した構成が、コードとして成立するかはここで初めて分かります。基盤（Spring Security・MyBatis・Flyway・Testcontainers・Thymeleaf）が動くこと自体が成果物です。

| IT | 期間 | 対象 US | SP | 局面とアプローチ |
| ---: | :--- | :--- | ---: | :--- |
| 1 | 08-06 | US26 ログイン / US27 ログアウト / US31 アカウントロック / US02 荷主登録 | 9 | 序盤・アウトサイドイン |
| 2 | 08-06 | US04 貨物予約登録 / US32 荷主情報の訂正 | 7 | 序盤・アウトサイドイン |
| 3 | 08-06〜07 | US24 航海スケジュール登録 / US07 検索 / US06 経路設計者への引き渡し | 8 | **中盤・インサイドアウト**の初回 |

3 イテレーションとも計画 SP と実績 SP が一致しています。**ただしこの一致は、後述するとおり品質の指標になりません。**

## AI に何をさせたか

この局面で使った Skill は次の通りです。

| Skill | 役割 |
| :--- | :--- |
| `opening-iteration` | 計画作成・整合性検証・GitHub 同期（6 ステップ） |
| `developing-backend` | Red-Green-Refactor によるドメインからの実装 |
| `developing-review` | XP 5 エージェント（programmer / tester / architect / technical-writer / user-representative）の並列レビュー |
| `closing-iteration` | 品質ゲート・ふりかえり・完了報告書・ドキュメント同期（7 ステップ） |
| `creating-adr` | 設計判断の記録 |

**IT1 の時点では、この一連が「回ること」自体が未検証でした。** 20 イテレーションを 8 日で回せたのは、ここで手順が固定されたからです。

## 起きた失敗

### IT1：レビュー高 10 件のうち 4 件が「入っているつもりの安全装置」だった

IT1 で最も重い発見です。実装中はすべて緑で、**レビューが無ければ気づけませんでした**。

| 対象 | 実態 |
| :--- | :--- |
| 利用者シード | 全プロファイルに適用される場所にあった。ファイル冒頭の「本番では適用しない」というコメントは何も強制していない |
| アカウントロック | 失敗回数の更新が非原子で、**並行した試行ではロックが成立しない**。総当たり攻撃は逐次では来ない |
| ログアウトのテスト | 未認証状態から始めており、セッション破棄が壊れていても常に緑 |
| 脆弱性スキャン | Gradle の依存を見ておらず、**緑だったのは安全だからではなく何も検査していなかったから** |

> **共通するのは「宣言と実態がずれても誰も気づかない形になっていた」ことである。**
> コメントで宣言し、テストで緑にし、CI を通したが、そのどれもが対象を捉えていなかった。
>
> — `retrospective-1.md` P1

**規律そのものは最初からありました。** 「設定したことと働いていることは別」は掲げられていたのです。抜けていたのは適用範囲で、**規律を実装コードにだけ当て、設定ファイル・マイグレーションの配置・CI の定義という「コードでないもの」に同じ目を向けていませんでした**（主題 M1）。

### IT1：テストピラミッドが逆立ちしていた

`Clock` を注入する設計にしておきながら、**差し替えるテストを 1 本も書いていませんでした**。結果としてロック期限切れ後の振る舞いが完全に未検証で、「期限切れ後 1 回の打ち間違いで再び 30 分ロック」というバグが残りました。

実測でユニット約 9% / 統合約 91%。30 分待つ統合テストは書けないので、**書かれませんでした**。

> **テストが書きにくいのは設計の問題ではなく、テストレベルの選択の問題だった。**
>
> — `retrospective-1.md` P2

### IT1：マニュアルが実装に無い機能を約束していた

「管理者に連絡するとロックを解除できます」と案内していましたが、**解除の手段は存在しません**。「アクセスが拒否されました」というメッセージも実装に無く、実際は英語の Whitelabel Error Page でした。

**マニュアルを実装より先に書いた結果、「こうあるべき」が「こうなっている」として書かれていました**（主題 M2）。これは AI 駆動開発で特に出やすい失敗です。文章を書く速度が実装より速いためです。

### IT2：前提が揃う前にロールへ機能を開放した

貨物予約一覧を `ROLE_SHIPPER` に開放しましたが、**利用者アカウントと荷主を結びつける手段が無く、荷主から他社の予約まで見える状態でした**。

原因は皮肉なものです。IT1 の教訓「ロール別の作業入口の欠落」を強く意識するあまり、**「入口を作る」ことだけを確認して「開放してよいか」を確認しませんでした**。正典（`non_functional.md`）は `ROLE_SHIPPER` の範囲を「自社予約・追跡」と明記しており、読めば分かりました。

**受入基準にもテストにも「見えてはならないもの」の観点がありませんでした。** 到達性の確認は「見せる」と「見せない」の両方向に必要です。

### IT2：時間で守ろうとしたテストが、脆弱な実装でも緑だった

ReDoS 対策として「長さ検査を形式検査より先に行う」を入れ、経過時間のアサートで守ろうとしました。**順序を戻しても緑のまま通りました。** 入力の形状が最悪ケースに当たらないと差が出ないためです。

分岐の結果（どちらの検査で落ちたか）で判定する形に書き直して、初めて赤になりました。

> **K1 の規律をテストの側にも当てていなかった。**
>
> — `retrospective-2.md` P2

### IT3：CI が赤のままクローズに入りかけた

ローカルは緑でしたが、**CI（UTC）ではテストが 1 件落ちていました**。

原因は入れ子になっています。IT3 では「UTC で業務日付を判断すると、日本時間 0〜9 時に当日着の予約が拒否される」という実バグを見つけて直しました。ところが**同じ取り違えをテストの側でしていた**のです。ローカル（JST）では一致するため見えません。

さらに悪いことに、**同じ取り違えが 4 ファイルに残っていました**。1 か所直して満足し、他を探しませんでした。

### IT3：方言差を 2 回踏んでから対策した

PostgreSQL 固有の記述が H2 で動かない問題を、IT2 で 1 回（`setval`）、IT3 で 2 回（`INTERVAL 'N days'`・`LATERAL`）踏みました。

> **1 回目の時点で「同じ型の失敗が続く」と読めたはずである。**
>
> — `retrospective-3.md` P4

## どう直したか

失敗のたびに、**それが人の注意に依存しない形へ落とせるか**を判断しています。

| 失敗 | 落とし先 | 種別 |
| :--- | :--- | :--- |
| 「入れたつもり」の安全装置 | **破壊検証**を手順化（作った装置を壊して赤を確認する） | 運用 |
| マイグレーションの配置 | `MigrationLocationsTest` | 検査 |
| ADR の「〜しない」9 件 | うち 4 件は文章だけで、破ってもビルドが緑だった → 検査を追加 | 検査 |
| BC 分離・ドメインの独立 | ArchUnit ルール（プローブで落ちることを確認） | 検査 |
| 方言差 | `H2DialectSmokeTest`（全クエリサービスを H2 で実行し「解釈できるか」だけ見る） | 検査 |
| CI との環境差 | クローズ前に `TZ=UTC ./gradlew test` を 1 度回す | 運用 |
| マニュアルの先行 | キャプチャ生成が通ることを記述の前提にする（生成できない＝画面が無い） | 運用 |

### 破壊検証が手順として定着した

IT1 の Try「安全装置は壊して確認する」は、IT2 で 5 件、IT3 で 6 件と実行されました。

| IT | 壊した装置の例 | 結果 |
| ---: | :--- | :--- |
| 2 | 楽観的ロック / ArchUnit ルール 4 / 依存検証 / 遷移表 | すべて赤を確認（遷移表は 4 件落ちた） |
| 3 | 業務タイムゾーンの時計 / ページ送りの LIMIT / `Schedule` の連結制約 / 読み戻し順序 / H2 方言スモーク | すべて赤を確認（読み戻し順序は 6 件落ちた） |

**この習慣が、以降 17 イテレーションにわたって最も効いた規律になります**（第 5 章）。

### インサイドアウトへの切り替えが機能した

IT3 は局面が中盤に変わり、ドメイン層から作る方式に切り替えました。`Schedule` の連結制約（区間 n の到着港 = 区間 n+1 の出発港）と時系列制約は、**行をまたぐため DB の CHECK 制約では守れません**。

> 画面から作っていたら気づかないまま「貨物が途中で消えるスケジュール」を登録できていた。
>
> — `retrospective-3.md` K2

局面ごとにアプローチを変える設計（`development_strategy.md`）の意味が、切り替えた最初のイテレーションで実証されました。

### 実機で確かめる

MockMvc が緑でも、Playwright で実際の画面を確認しました。403 画面は **MockMvc が forward 先を描画しない**ため、テストだけでは中身を確認できません。実機確認がなければ「テストは緑だが画面は英語のまま」で終わっていました。

IT3 では、キャプチャを撮ろうとして `LATERAL` を H2 が解釈できず画面が 500 になることが発覚しています。**実バグ 3 件はいずれも「テストは緑なのに動かない」種類でした。**

## 残った未達

IT1 のふりかえりは持ち越し 8 件（C1〜C8）を名前つきで記録しています。荷主の編集機能・アカウントロックの解除手段・荷主コードの `MAX + 1` 採番による重複・重複メール競合時の 500 など、**いずれも「動いているが守られていない」種類**です。

このうち **C2（ロック解除の手段が無い）は「解除できない前提で運用する」と明記**されました。消さずに移し先を書く形は IT2 でも踏襲されています。

> **消すと、次に読む人には最初から無かったように見える。**
>
> — `retrospective-2.md` K3

### この局面で見えた計測の歪み

IT1 のふりかえりは、自らの実績値に注釈を付けています。

> レビュー指摘の修正・SonarQube の整備・脆弱性 30 件の解消は SP に計上していない。
> **IT1 の実績 9SP は「9SP 分の労力だった」ことを意味しない。**
>
> — `retrospective-1.md` P5

冒頭で「計画 SP と実績 SP の一致は品質の指標にならない」と書いたのはこのためです。**AI 駆動開発では計画外の作業が特に膨らみます** — レビューが多くの指摘を出し、その修正は SP に載らないからです。

## この局面の要点

1. **規律はあっても適用範囲が狭い。** IT1 の 4 件はすべて「コードでないもの」で起きた
2. **文章は実装を先回りする。** マニュアルが存在しない機能を約束した（M2）
3. **緑は根拠にならない。** 脆弱性スキャンが緑だったのは何も検査していなかったから（M1）
4. **同じ型の失敗が 2 回続いたら、その場で仕組みにする。** 3 回待たない（IT3 Try T5）

次章では、この手順のまま 7 イテレーションを走らせた IT4〜IT10 を扱います。**そこではジャーナルが 1 日ぶん欠落しています。**

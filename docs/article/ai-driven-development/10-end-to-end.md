# 第 10 章：一気通貫（IT4〜IT10）— 予約から追跡まで

## この局面のゴール

**予約 → 経路 → 確定 → 追跡番号 → 荷役 → 輸送中が一本つながること。**

IT6 で Release 1.0 が完成し、E2E がその 1 本を通しました。IT7 以降は幅を広げる局面に入り、公開追跡・法人荷主・例外処理が加わります。

| IT | 期間 | 対象 US | SP | 局面 |
| ---: | :--- | :--- | ---: | :--- |
| 4 | 08-07 | US08 経路候補の算出 | 8 | 中盤・インサイドアウト |
| 5 | 08-07 | US09 経路の選択・確定 / US11 予約への紐付け / US33 ロック解除 | 7 | 中盤 |
| 6 | 08-08 | US13 予約確定 / US14 追跡番号発行 / US15 荷役記録 | 8 | 中盤。**Release 1.0 完成** |
| 7 | 08-08 | US18 追跡照会 / US16 引取記録 / US03 法人荷主登録 | 8 | 終盤・アウトサイドイン |
| 8 | 08-08 | US17 状態の手動更新 / US10 再算出 / US12 荷主通知 | 8 | 終盤 |

**9 イテレーション連続で計画 SP = 実績 SP**（平均 7.89SP）です。

## AI に何をさせたか

前章の 5 Skill に加え、この局面で定着した運用が 2 つあります。

### 1. 着手前の突合（`opening-iteration` の検証ステップ）

IT7 では設計ドキュメント・スキーマ・シードデータの欠落を **13 件**見つけ、うち 3 件は実装をブロックするものでした。

| 欠落 | 見つからなかったら何が起きたか |
| :--- | :--- |
| `/tracking` の認可規則が設計と実装で食い違う | 発行待ち一覧（他社を含む確定済み予約）が荷主に見える |
| `ROLE_SHIPPER`・`ROLE_CONSIGNEE` の利用者が存在しない | 開いてよいと定めた画面を、誰も開けない |
| 引取確認を保存する列が無い | 引き渡し証明を記録する先が無い |

> **IT5 は「実行できる人」、IT6 は「実行する人の入口」、IT7 は「その人自体の不在」。**
> 6 IT 連続で「作ったが使えない」型であり、**着手前の突合でしか見つからない**。
>
> — `retrospective-7.md` K1

### 2. 返済枠を時間で先に確保する

IT2 で始めた「返済枠を『余力次第』にせず時間で確保する」が定着し、IT7 では 5 件を完済しました。IT8 のふりかえりはこう書いています。

> タスク 0 として 8 時間を先取りし、6 件すべてを実施した。**「余力次第」と書かなかったから
> 実施された**。
>
> — `retrospective-8.md` K1

## 起きた失敗

### 破壊検証は回数を重ねても、毎回別の場所で空振りする

この局面の破壊検証は 7 件（IT4）→ 11 件（IT5）→ 19 件（IT6）→ 11 件（IT7）→ 10 件（IT10）と規模を増しました。**それでも毎イテレーション空振りが出ています。** 重要なのは、空振りの理由が毎回違うことです。

| IT | 空振りの構造 | ふりかえりの言葉 |
| ---: | :--- | :--- |
| 4 | 判定を外しても緑。テストの入力が判別しない形だった | 「壊して赤を確認する」を実行しなければ見つからなかった |
| 6 | **入口は回したが、出口を回していない**。判定は 3 件壊したが、判定結果を「どこに書くか」は壊していない | 「共通するのは『入口は回したが、出口を回していない』こと」 |
| 7 | 入口と出口の両方を壊す形に拡張。荷役種別の網羅は**コンパイルエラー**で落ちた（実行時より強い） | — |
| 10 | **自分で選んだ装置しか検証していない**。10 件全件赤だったのに、検証対象に選ばなかった 3 つが壊れていた | 「リストを自分で作る限り、リストに載せなかったものは守られない」 |

IT10 の指摘が最も深いところを突いています。

> IT9 のふりかえりで「安全装置は入口と出口の両方を壊す」と書いたが、
> **そもそも安全装置として認識していないものは、入口も出口も無い。**
>
> — `retrospective-10.md` P1

**破壊検証は「テストが判別するか」は確かめられますが、「装置を数え落としていないか」は確かめられません。** この限界が、IT11 以降の「機械的に数え上げてから壊す」という次の形へつながります（第 11 章）。

### 「宣言と実装の食い違い」が 3 イテレーション連続で出た

主題 M2 が最も濃く出た区間です。**場所が毎回移動します。**

| IT | 件数 | 宣言の場所 |
| ---: | ---: | :--- |
| 6 | 1 | Javadoc（「1 つのトランザクションで書く」と宣言しながら、戻り値でエラーを返す設計と `@Transactional` が噛み合っていなかった） |
| 7 | **6** | 画面のコメント・利用者への案内文・イテレーション計画 |
| 8 | **5** | Javadoc・定数名・画面の案内文 |

IT7 の例です。

| 宣言した場所 | 宣言の内容 | 実際 |
| :--- | :--- | :--- |
| `handling/form.html` のコメント | 「予約の荷受人と違えば警告を出し、メモへの理由記入を求める」 | **照合は場所しか見ていない。メモ欄も無い** |
| `handling/form.html` の案内文 | 「荷受人へ事前に送付した確認コード」 | **送付する手段が無い**（ADR-006）。照合もしない |
| `iteration_plan-7.md` タスク 1-4 | 「作業日時の下限を追跡番号の発行日時とする」 | **実装していない** |
| `ClaimConfirmation.matchesConsignee` | 荷受人を照合するメソッド | **テストからしか呼ばれていない**（配線漏れ） |

IT8 では**同じ IT の中で自分が書いたコメントを自分で破って**います。

> **書いた本人が同じ IT の中で破っている。** コメントは書いた時点の意図であり、
> その後の変更に自動では追随しない。
>
> — `retrospective-8.md` P1

最後の 1 件（`matchesConsignee`）が突破口になりました。**「定義したがどこからも呼ばれないドメインメソッド」は配線漏れのサインであり、機械的に検出できます**。IT8 でこの検出を実装したところ **26 件**が出て、うち `Shipper.changeContract` は**機能の欠落**でした — 法人荷主の割引率を打ち間違えても直す手段が無い状態で、ストーリーを完了扱いにしていたのです。

### レビューエージェントが 5 視点中 4 視点で回答を返さなかった

**AI 駆動開発に固有の失敗です。** IT7 で `developing-review` を起動したところ、回答が返ったのは利用者代表のみで、残る 4 視点は調査を終えたと見られる状態でアイドルに戻り、レポートを返しませんでした。

フォールバックとして 4 視点を順次自分で実施し、高優先度 3 件を追加で見つけたため結果的には成立しました。教訓は一般化できます。

> **「エージェントを起動した」ことと「レビューが行われた」ことは別である。**
>
> — `retrospective-7.md` P3

これは主題 M1（緑であることは守られていることの根拠にならない）が、**テストではなくエージェント実行の側に現れた**形です。安全装置と同じく、**レビューもまた「実行した」ではなく「結果が返った」で確認する**必要があります。

### 「到達性」の観点が 5 段階に分化した

同じ「作ったが使えない」型の失敗が、毎イテレーション少しずつ違う顔で出続けました。

| IT | 欠けていた観点 |
| ---: | :--- |
| 2 | **ロール軸** — そのロールが開いてよいか（開放してよいかの確認漏れ） |
| 7 | **ロール別の作業入口** — そのロールがダッシュボードから到達できるか |
| 8 前半 | **状態軸** — その状態のレコードから開けるか |
| 8 後半 | **気づく手段** — その仕事がいつ発生したかを知る手段があるか |
| 9 | **次の行動** — 件数を出しても、そこから対象へ行けるか |

IT9 の例が分かりやすい形です。計画のデモ項目「差分と影響する予約の件数が出る」を文字どおり満たしましたが、**「3 件あります」と告げながらその 3 件へ行く手段がありません**。案内先の一覧には未割り当ての予約しか出ないため、案内どおりに動いた経路設計者は空の一覧を見て「連絡不要だった」と受け取ります。

> **計画に書いた条件を満たすことと、業務が回ることは別である。**
>
> — `retrospective-9.md` P2

**受入基準を満たすことは、AI にとって最も達成しやすい目標です。** だからこそ、受入基準の文言の外側にある「その人の 1 日」を誰かが確認する必要があります。この役割を担ったのが利用者代表のレビュー視点でした — IT6・IT7 とも**高優先度 9 件のうち 6 件が利用者代表**です。

### 集約の守りを単体で固定し、画面から踏んだときを確かめなかった

IT9 の最重要問題です。**出港済みの区間を直そうとした経路設計者は、エラー画面（500）に落ちていました。**

`Voyage.reschedule` の守り自体は単体テストで固定されています。しかしコントローラの `try` はコマンドの組み立てしか囲っておらず、集約が投げる例外が素通りしていました。

> 集約の単体テストは、**画面から踏んだときに何が起きるか**を判別しない。両方が要る。
> さらに悪いことに、**運航変更の連絡は航行が始まってから来ることのほうが多い**。
> この経路は例外的ではなく日常的である。
>
> — `retrospective-9.md` P1

### 環境依存の脆さを繰り返した

IT3 で「業務日付を UTC で判断しない」を本体に入れましたが、**テスト側には入っていませんでした**。IT9 の E2E は実行機のタイムゾーンで日時を組み立てており、開発機（JST）では 00:00〜09:00 だけ、**CI（UTC）では 1 日中**落ちます。

同じ IT で、航海テストの日付が絶対値（`2026-09-01`）で書かれ、その日を過ぎると一斉に落ちる状態も見つかりました。

## どう直したか

この局面の対処は、**規律そのものではなく「規律の適用範囲」を広げる**形が中心です。

| 失敗 | 直し方 |
| :--- | :--- |
| 例外は数えたが `boolean` の戻り値は数えていなかった（IT6 P2） | `grep` の対象を戻り値型にも広げ、3 件とも検出 |
| 呼ばれないドメインメソッド（IT7 P1） | **機械的な検出を実装** → 26 件検出、うち 1 件は機能の欠落 |
| 依存の更新が目視頼み（IT8） | `dependencyUpdates` を導入 → 初回実行で **25 件**が未更新と判明 |
| 上限に当たったときの回避（IT6・IT7） | **上限を緩めない。** 「別々に持つと不正な組み合わせを作れる値」をまとめる設計改善に使う |
| レビューエージェントの無応答（IT7） | フォールバック手順を明示し、視点ごとに結果の有無を確認 |

### 検査が設計を良くした例

Checkstyle のパラメータ数上限に 2 回当たり、**2 回とも型の導入で解決**しました。

| 型 | まとめた理由 |
| :--- | :--- |
| `ProposedRoute.Path` | 経由港はあるのに区間が 1 つ、という航海の上で成り立たない組み合わせを作れる |
| `CargoProgress` | 確定していないのに追跡番号がある、という組み合わせを作れる |
| `HandlingDetails` | 「受領なのに荷受人確認が付いている」という意味の定まらない組み合わせを作れる |

> **上限に当たったとき「引数をまとめる箱」を作ると、ただの回避になる。**
> 概念として意味のあるまとまりかどうかを毎回確かめた。
>
> — `retrospective-6.md` K3

ArchUnit も同様に設計の誤りを捕まえています。IT4 では ACL ポートの戻り値に相手 BC の値オブジェクトを置いたところルールが落ちました。

> **実装する側が相手のドメインを直接参照するなら、ACL を置いた動機そのものが消える。**
>
> — `retrospective-4.md` K3

**規則が「宣言」ではなく「検査」になっていることの価値**が、ここで実証されています（主題 M5）。

## この局面の要点

1. **破壊検証は「リストに載せた装置」しか守らない。** 数え上げの機械化が次の課題になった（IT10 P1）
2. **宣言と実装の食い違いは場所を移動する。** Javadoc → 画面の案内文 → 計画 → 定数名（M2）
3. **エージェントを起動したことと、レビューが行われたことは別。** AI 固有の M1
4. **受入基準を満たすことと業務が回ることは別。** 利用者代表の視点が高優先度指摘の 3 分の 2 を出した
5. **手順に組み込まれた記録は残り、そうでない記録は落ちる。** ジャーナルが 1 日ぶん欠けた

# 第 13 章：出荷と是正（IT18〜IT20）

## この局面のゴール

**最後の未実装 BC を立ち上げ、出荷し、育つ負債を止める。**

| IT | 期間 | 対象 | SP |
| ---: | :--- | :--- | ---: |
| 18 | 08-12 | US01 輸送見積（**最後の未実装 BC**）＋ 返済枠 C1 / C2 | 5 |
| 19 | 08-12 | Release 2.1 の出荷確定 ＋ 正典未達 2 件 ＋ Try 5 件 | **0** |
| 20 | 08-12〜13 | 育つ負債 2 件 ＋ 正典に残った未判断 | **0** |

IT18 で Estimation Context が実装され、**`package-info.java` だけのパッケージが無くなりました**。設計・テーブル・画面定義は揃っているのに実装だけが無い状態が、IT1 から 17 イテレーション続いていたことになります。

IT19 で `java/take-6/v2.1.0` を出荷確定。**以降は新規ストーリーがありません。** 達成は「育つ負債を止めたか」「未判断を減らしたか」で測ります。

## AI に何をさせたか

### 着手前に正典の食い違いを決着させる

IT17 の Try「正典が食い違ったら、決着させるまで次の IT に持ち込まない」が、IT18 で機能しました。

`domain-model.md` は「ルート候補はスタブ実装（固定値）で、将来外部ルーティングサービスと連携する」と書いていましたが、**ADR-006 は外部連携を採らないと決めており、その「将来」は来ません**。一方 Routing には US08 で本物の探索が入っています。固定値を返す見積は、画面が動くのに**数字が現実と無関係**になり、荷主に渡せません。

> 決着の内容は SP を動かした（スタブなら 3、独自の探索なら 8、ACL なら 5）。
> **決めてから着手したから、見積が揺れなかった。**
>
> — `retrospective-18.md` K1

### 実コードの違反を探してから検査を書く

IT19 の運用改善です。ADR-022 の検査は、先に**実際の違反を見つけてから**書きました。「規則を作って終わり」にならず、書いた瞬間に 1 件返せています。

### 育つ負債を「次の IT で対象が増えるか」で選ぶ

IT20 の主目的です。IT19 のふりかえりで決めた「落とす順序は見積もりでなく、**次の IT で対象が増えるか**で決める」を実行しました。

| # | 内容 | 実装前 | 結果 |
| :--- | :--- | :--- | :--- |
| D5 | ADR-024 の契約を検査にする | **検査の外**（コメントに書いただけ） | 完了 |
| D1 | `Cargo` の行数 | **500 行・猶予 0**（上限ちょうど） | 485 行・**猶予 15 行** |

> **`Cargo` は猶予 0 行だった。** 次に 1 メソッド足せば Checkstyle が赤になる状態であり、
> 「余力があれば」に回していれば IT21 の最初の変更が止まっていた。
>
> — `retrospective-20.md` K1

**負債の優先順位を「大きさ」ではなく「猶予」で測る**という判断が、20 イテレーション目にして確立しました。

## 起きた失敗

### 記録と実態のずれが 5 度目、そして 10 度目

主題 M3 は最後まで解消しませんでした。IT18 でふりかえり自身が集計しています。

| 項目 | 記録 | 実測 | 倍率 |
| :--- | ---: | ---: | ---: |
| C2（貨物フィクスチャ・IT16） | 7 | 39 | 5.6 |
| C3（レコード・IT16） | 2 | 21 | 10.5 |
| R8（検査・IT17） | 8 | 10 | 1.25 |
| R7（列の多い一覧・IT17） | 1 | 13 | 13 |
| **C1（委譲アクセサ・IT18）** | **34** | **249** | **7.3** |

> **着手時に数え直す習慣は効いている**（毎回ここで気づく）。
> 効いていないのは**記録するときの数え方**である。
>
> — `retrospective-18.md` P2

IT20 では 10・11 度目を数えています。しかも皮肉な形でした。

> 本 IT の Try「**数を書くときは数えた方法も書く**」が、**この計画自身には適用されていなかった**。
>
> — `retrospective-20.md` P5

### 検査を足すイテレーションなのに、その検査自身に穴があった

IT19 の最重要問題です。**クローズ前レビューが、本 IT で新しく足した検査に 3 つの穴を見つけました。**

| 検査 | 穴 |
| :--- | :--- |
| H2 スモークの載せ忘れ検査 | **型単位でしか見ておらず、メソッド 6 件を素通り** |
| ADR-022 の規則の置き場検査 | **数値リテラルしか拾わず、定数比較は素通り**。移設先がまさにその形だった |
| 型名の照合 | 部分一致で、接尾辞が重なる型を見分けられない |

> **「2 回続けて外したなら方式の問題」と書いて方式を変えたのに、
> 新しい方式の粒度が事故の粒度と合っていなかった。**
> IT17・IT18 で外したのは「新しいサービス」だったが、次に増えるのは「新しいメソッド」である。
>
> — `retrospective-19.md` P1

IT20 でも同型が再現します。**新しく足した安全装置そのものに、過去の失敗が 3 種類再現しました。**

| 装置 | 再現した失敗 |
| :--- | :--- |
| `EntityEncapsulationTest` | **メソッド参照を素通り**（形が違えば通る） |
| `EntityEncapsulationTest` | 契約表が**文字列の名簿**で、実在を誰も確かめていない |
| `RecentBusinessTime` | 真夜中の順序崩れを**直しきれていなかった**（01:00 で逆転） |
| `CargoMisrouteTest` | テスト名と検証内容が矛盾し、**欠陥を固定していた** |

> IT19 の Try「検査を書くときは過去に起きた事故の粒度で Red を作る」は、
> 型とメソッドの粒度までは効いた。**呼び出しの形**（直接呼び出し / メソッド参照 / リフレクション）
> の粒度には届かなかった。
>
> — `retrospective-20.md` P1

**粒度は事故のたびに細かくなり、常に一歩後ろにいます。** これは第 3 部を通じて一貫した構造です。

### ソースを読む検査が、ソースを入力にしていなかった

IT19 で見つかった、Gradle のビルドキャッシュに起因する空振りです。Javadoc だけを変えるとバイトコードが変わらず `compileJava` が UP-TO-DATE になり、**検査そのものが走らないまま緑**になりました。

> 破壊検証をしていなければ気づかなかった。
>
> — `retrospective-19.md` P3

### 「名前で記録した」と書きながら、記録が無かった

IT19 の ADR-024 は 2 か所で「次のイテレーションで ArchUnit ルールに落とす（**名前で記録した**）」と書いていましたが、`docs/development/` を grep しても **1 件もヒットしませんでした**。

> ADR 本文が最も強い言葉で戒めている形を、**その ADR 自身が踏んでいた**。
>
> — `retrospective-19.md` P5

IT17 の「検査で固定したと書いて検査が無かった」と同型です（主題 M2）。**AI に文章を書かせる限り、この形は繰り返されます。** 20 イテレーションで一度も止まりませんでした。

### 入力させたものを捨てていた

IT18 で、貨物種別を変えると**入力済みの内容が全部消える**画面を作りました。

> マニュアルの操作手順どおりに操作すると、**荷主と電話しながら打ち込んだ内容が種別選択の瞬間に全部消える**。
> テストは「危険物欄が出るか」しか見ておらず、**他の欄が残っているかを見ていなかった**。
>
> — `retrospective-18.md` P1

クローズ前レビューの利用者代表が見つけました。**「新しく出るもの」はテストされ、「消えないこと」はテストされない**という非対称です。

### 新しい既定が、新しい問題を作った

IT20 の U4（一覧の既定を「有効」に）は、U5（「何を直せばよいか分からない 0 件」をなくす）が解こうとした問題を新しく作りました。

**手持ちが全て期限切れの朝は、条件を 1 つも入れていないのに「条件を変えてお試しください」が出ます。**

> **利用者代表・アーキテクト・テクニカルライターの 3 視点が独立に同じ箇所を指した。** 実装者には見えなかった。
> **新しい既定は、それ自体が新しい状態を作る。**
>
> — `retrospective-20.md` P2

### マニュアルのキャプチャが 1 枚も更新されていなかった

IT20 の見落としです。計画には「マニュアル 12 章とキャプチャ再生成」と書かれ、**本文は更新されました**。キャプチャは撮り直されていません。本文が「表の上に該当 N 件と出ます」と書いているのに、画像にはそれが写っていません。

> **文章は実装に追随していたので、本文だけ読むレビューでは緑に見える。**
> 画像の古さは人の目にしかかからない。
>
> — `retrospective-20.md` P4

## どう直したか

### 規則を一般化せずに検査へ落とす

IT20 の最も良い判断です。ADR-024 の契約は「集約ルート以外は呼べない」と書けば 3 行で済みました。**そう書きませんでした。**

> ADR-024 が定めているのは**メソッドごとに呼んでよい相手を書き分けた表**であり、
> 一般化すると `ProposedRoute.of` を集約ルートへ移すことになって探索と提案の分離が壊れる。
>
> **（型・メソッド・呼んでよい相手）の 3 つ組**で書いたことで、
> `ExceptionOccurrence.raise` や `commandService.resolve` を誤検知せず、設計も変えずに代償を返せた。
>
> — `retrospective-20.md` K2

**検査を書きやすくするために設計を歪めない。** 規則の形をそのまま検査の形にする、という原則がここで確立しました。

### レビューアが実際にコードを書いて確かめた

IT20 のクローズ前レビューでは、tester が **3 種類のプローブを実際に書いて走らせ**、メソッド参照の素通りと真夜中の順序崩れを**実測で示しました**。

> どちらも読むだけでは見つからず、こちらの「破壊検証で 4 メソッドすべて赤を確認した」という
> 報告と矛盾しない形で潜んでいた。
>
> **「壊して赤」を実演したレビューは、意見ではなく事実を持ってくる。**
>
> — `retrospective-20.md` K3

**レビューの質は、コードを書くかどうかで決まります。** 読むだけのレビューは、報告と矛盾しない欠陥を見つけられません。

### 検査は同型の既存欠陥を掘り出す

IT20 でキャプチャの重複検査（md5）を入れたところ、**レビューが指摘した 1 組に加えて既存の 2 組が即座に出ました**。

> **検査は「今回の欠陥」を止めるだけでなく、同型の既存欠陥を掘り出す。**
> 手で数えていたら 3 組目は見つからなかった。
>
> — `retrospective-20.md` K4

第 11 章の「指摘は 2 本、検査は 9 本」と同じ構造です。**検査の価値は再発防止だけではなく、現在の実数を明らかにすることにあります。**

### 正典に残った未判断を決着させた

IT20 は `release_scope.md`「スコープ外」表の 5 行すべてを実態に合わせました。

| 対象 | 実装前 | 結果 |
| :--- | :--- | :--- |
| 返金 | 「Release 2.0 で判断する」 | **行わない**（`domain-model.md` は既に確定済み。追随の是正） |
| 多通貨 | 「保留」 | **単一通貨（JPY）で確定**（ADR-025。本 IT で唯一の新しい判断） |
| `invoice_line_item` | 「Release 2.0 で必要性を判断する」 | **作らない**。テーブルは作成済み・未使用と明記 |
| `cargo.declared_value` | 「要求元なし。落とす」 | 落とし済み（実測 0 件） |
| 見積の `EXPIRED` | 「要求元なし。**落とす**」 | **採用済み**（IT18）。**表だけが逆だった** |

**5 行のうち、新しい判断が必要だったのは 1 行だけ**でした。残る 4 行は、既に決まっていたか既に実装されていたのに、正典がそれに追随していなかったものです。

> ADR-025 が「**あとで判断すると書いた時点から、判断した気になっている時間が延び続ける**」と戒めた
>
> — `retrospective-20.md` P3

## 残った未達

IT20 は自分自身の Try も踏み外しています。`test_strategy.md` に「実装は 13 ルールあり本節は追随していない。**是正はタスク 7**」と自分で書きながら、**タスク 7 のコミットで是正せず完了扱いにしました**。ADR-025 が戒めた形を、同じイテレーションの中で踏んだことになります。

**20 イテレーション目でも、主題 M2 は止まっていません。**

## この局面の要点

1. **負債は「大きさ」でなく「猶予」で選ぶ。** `Cargo` は猶予 0 行だった
2. **検査の粒度は事故の粒度に一歩遅れる。** 型 → メソッド → 呼び出しの形
3. **規則を一般化せずに検査へ落とす。** 検査を書きやすくするために設計を歪めない
4. **プローブを書くレビューは、意見でなく事実を持ってくる**
5. **検査は同型の既存欠陥を掘り出す。** 指摘 1 組 → 実測 3 組
6. **「あとで判断する」と書いた瞬間から、判断した気になっている時間が延び続ける**

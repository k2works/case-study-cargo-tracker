## AI に何をさせたか

前章までの運用に加え、この局面で 2 つの転換がありました。

### 1. 破壊検証のリストを機械的に作る

IT10 の教訓「自分で選んだ装置しか検証していない」への対応です。**IT11 で選び方を変えた結果が、そのまま出ました。**

> **IT10 の Try T1（破壊検証のリストを自分で作らない）を実行したら、IT10 とは正反対の結果が出た。**
> IT10 は「自分で選んだ 10 件が全部赤」で、選ばなかった 3 件が壊れていた。
> **IT11 は機械的に数え上げた 22 件のうち 3 件が空振りした。**
>
> **選び方を変えたら、見つかるものが変わった。**
>
> — `retrospective-11.md`

**自分で選ぶと全部赤になり、機械的に数えると空振りが出る。** リストの作り方が結果を決めていたのであって、装置の品質が変わったわけではありません。

IT12 ではさらに一歩進み、**21 件を数え上げて全件壊し、空振り 0 件**を達成しました。IT11 との違いは壊すタイミングです。

> IT11 は実装をまとめてから数え上げたが、本 IT は**各コミットの中で「作った直後に壊す」**を行った。
> **間に合わせで足した検査が混ざる余地がない。**
>
> — `retrospective-12.md` K2

### 2. 局面の名前ではなく条件でアプローチを選ぶ

IT13 で Billing Context を立ち上げる際、直前 6 イテレーションのアウトサイドインから**インサイドアウトへ戻しました**。

> IT7〜IT12 はアウトサイドインだった。理由は「既存集約の組み合わせであり、新しい集約を
> できるだけ作らない」ことである。**IT13 はその条件を満たさない** — Billing は
> `package-info` のみで集約が 1 つも無く、ACL ポートを 3 つ同時に実装し、
> 金額の丸め規則を確定させる必要があった。
>
> — `retrospective-13.md` K1

結果、**タスク 1 と 2（ドメインと永続化）を終えるまで画面もコントローラも 1 行も書いていません**。金額の丸めが画面の都合（カンマ区切り・切り上げ表示）に汚染されずに済みました。

**局面の定義が「前回どうしたか」ではなく「いま条件が何か」で運用された**ことが、この判断の要点です。

## 起きた失敗

### ADR に「必ず守る」と書いた規則を、コードの半分が守っていなかった

**本シリーズで最も重い M5 の実例です**（IT15 P1）。

ADR-009 の規則 2 は「購読側は新しいトランザクションで書く（`REQUIRES_NEW`）」と明記しています。今回追加した購読先サービスは素の `@Transactional` でした。

> それだけなら「新入りの見落とし」で済むが、**検査を書いた瞬間、同じ違反が既存に 5 本ある
> ことが分かった**。5 本が宣言していて 5 本が宣言していない — つまり**ADR を書いた後も、
> 半分は守られないまま増え続けていた**。
>
> **「ADR に書いた」と「守られている」の間に何も無かった。**
>
> — `retrospective-15.md` P1

しかも故障は静かです。`AFTER_COMMIT` の時点で発行側のトランザクションは終わっており、**書き込みがコミットされないまま消えうる**。テストが緑なのは Spring の内部挙動に依存しているためで、依存していること自体が危険でした。

ADR-009 は 7 イテレーションのあいだ、**半分だけ守られながら違反を増やし続けて**いました。

### 検査が守っている範囲の外で、結合が増えた

IT11 では ArchUnit のルールを **1 件も破らずに**、BC 間の結合が SQL の層で 2 本増えました。

> ADR-012 は「循環をインフラ層に閉じ込め、0 件であることを検査で守る」と決めた。
> **その「閉じ込め」は Java の依存についてしか成立していない。**
>
> — `retrospective-11.md` P2

さらに悪いことに、**同じイテレーションの中に同じ問題への 2 つの答えが並んで**いました。荷主名を引くのに、Tracking は ACL ポートを通し、Handling は SQL で JOIN した。**次に読む人はどちらの前例に従えばよいか判断できません。**

IT12 で SQL 層の検査を作って走らせた結果は明快でした。

> IT11 のレビューは「BC をまたぐ SQL が 2 本」と指摘した。**検査を作って走らせたら 9 本あった**（7 本は既存）。
>
> — `retrospective-12.md` K3

**指摘は目視の上限を示し、検査は実数を示します。**

### 名簿方式の検査が、名簿に無いものを素通りさせた

IT15 で見つかった、**検査そのものの欠陥**です。`MapperTableOwnershipTest`（ADR-015）は所有表に無いテーブルを黙って通していました。

> **載せ忘れたものほど検査から漏れる**という反転した性質であり、
> `handling_correction` が IT12 から 3 イテレーション漏れていた。
> **検査を書くときに「知らない入力が来たらどうなるか」を考えていなかった。**
>
> — `retrospective-15.md` P4

主題 M1 が、テストでもエージェントでもなく **検査自身**に現れた形です。

### 「例外にしない」が「記録しない」に滑った

IT14 の最大の発見です。`settle` / `notifyIssued` はどちらも `boolean` を返す契約なのに、**呼び出し側が戻り値を捨てていました**。

結果として「入金確認済みだが予約が `SETTLED` にならなかった請求書」がログにも画面にも残りません。しかも US36 の「精算済みには訂正・取り消しできない」は `booking_status` に依存しているため、**この不整合が起きた予約は精算後も訂正できてしまいます**。

> 「できなかったことを例外にしない」という判断自体は正しい。**そこから「だから何もしない」へ
> 滑ったこと**が問題で、これは自分では気づけなかった（レビューで初めて出た）。
>
> — `retrospective-14.md` P1

### コメントが実装より強い保証を主張していた

主題 M2 が、この局面でも 3 イテレーション連続で出ました（IT11・IT12・IT13）。IT11 の 3 件が象徴的です。

| 主張したコメント | 実装 |
| :--- | :--- |
| 「やめる側も同じ入力を持って戻る。**打ち直させると、入力し直すより承認を押すほうが楽になってしまう**」 | 追跡番号しか持ち回っていなかった。**自分が警戒した誘因を、自分で作っていた** |
| 「`HandlingActivity` の内部エンティティ。別集約にすると読んだ直後に留置へ変わっても止められない」 | **独立した集約だった。** しかも「避けた」と書いた形そのものになっていた |
| 「画面の出し分けは同じ述語を使う」 | **文字列比較で別の述語を再実装していた** |

> **3 件とも、コメントを書いた本人が同じイテレーションで実装している。**
> 書いた時点では本当にそのつもりだったはずで、**「書いたから守られた」と思い込む形**である。
>
> — `retrospective-11.md` P1

IT13 では対象が Javadoc へ移ります。「区間が 0 本の貨物は請求できない」と書きながら、**その守りはどこにも実在せず**、距離係数 0 が計算まで届いて画面に 500 が出ました。

IT12 の Try「実装しなかった守りを数える」は実施されていましたが、**数え上げの対象がマニュアルの『〜できません』に限られており、アダプタの Javadoc は入っていませんでした**。規律はあり、適用範囲が狭い — 第 9 章から繰り返されている形です。

### 全緑からレビューが高優先度を出し続けた

この局面の一貫した事実です。

| IT | 品質ゲートの状態 | レビューが出した高優先度 |
| ---: | :--- | ---: |
| 13 | `TZ=UTC ./gradlew check` 全緑・E2E 17 本緑・SonarQube PASS | **13 件**（5 IT 連続） |
| 14 | 同上・E2E 19 本緑・新規カバレッジ 87.2% | **18 件**（6 IT 連続） |
| 15 | 同上・E2E 21 本緑・CI 緑 | **5 件**（7 IT 連続） |

IT14 の分析が的確です。

> うち 13 件は正しさ・読み手に関わるもので、**自動チェックが原理的に見ない領域**
> （業務としてどう使うか、コメントと実装の一致、記録の有無）に集中している。
>
> — `retrospective-14.md` P4

**自動チェックとレビューは代替関係ではありません。** 見ている領域が違います。

### 自分の catch が、自分のデバッグを 30 分止めた

IT15 の実務的な失敗です。「形式の違う ID を例外にしない」ための `try` を、**リポジトリの読み出しまで広げていました**。集約の復元が投げた例外がそこに吸われ、画面には 404「予約が見つかりません」だけが出ます。**ログにも何も残りません。**

9 本のテストが同じ 404 で落ち、デバッグ出力を仕込む往復をして初めて本当の例外が見えました。**catch を狭めた瞬間に 1 分で直りました。**

### 返済したことと、次に書くときに思い出すことは別

IT15 で、承認待ち一覧が 1 行ごとに予約を引き直していました。**IT13 レビューの N+1 指摘とまったく同じ形**で、しかも**その指摘を返済した同じイテレーションで作って**います。

> 待ち行列が伸びるほど遅くなる — いちばん混んでいるときに、いちばん遅い。
>
> — `retrospective-15.md` P3

## どう直したか

### 返済枠がストーリー本体と同規模になった

IT12 は、返済枠の運用が最も成熟した回です。

| 項目 | 値 |
| :--- | :--- |
| 返済枠 | 27 時間（8 タスク・12 件） |
| ストーリー本体 | 30 時間 |
| 落としたもの | **0 件** |
| 最初の 8 コミット | **すべて返済枠**（US35 の着手は 9 コミット目） |

> **「余力次第」にすると固定化する**という IT7 の学びが、6 イテレーション続けて機能している。
> 本 IT では返済枠が過去最大だったが、**落とす順序を計画に先に書いていた**ため、
> 判断を先送りせずに済んだ。
>
> — `retrospective-12.md` K1

3 イテレーション繰り越していた項目にも、ここで決着がつきました。

### しかし「落とした負債は育つ」

IT15 では返済枠 9 件のうち 4 件を落としました。落とす順序は計画どおりでしたが、**落としたことで対象が増えました**。

| 落とした項目 | 育ち方 |
| :--- | :--- |
| テストヘルパーの重複 | 対象が **5 → 7 クラス**に増えた |
| `InvoiceView` の引数整理 | 同じ形の `CancellationView` が **19 引数**で生まれた |

**負債は据え置かれるのではなく、育ちます**（主題 M4）。この観察が IT19 の Try「落とす順序は見積もりでなく、**次の IT で対象が増えるか**で決める」につながります。

### 対処の一覧

| 失敗 | 落とし先 |
| :--- | :--- |
| ADR-009 が半分守られていない | **検査を新設**し、既存違反 5 本を検出・修正 |
| BC をまたぐ SQL | **SQL 層の検査**を新設 → 9 本を検出（指摘は 2 本） |
| 名簿方式の素通り | 名簿に無い入力を**拒否する**形へ変更 |
| 戻り値を捨てる | 呼び出し側の記録を必須化 |
| 広すぎる `catch` | **解析だけを囲む**形へ狭める |
| CI の時間帯でだけ落ちるテスト | テストにも同じ `Clock` を注入 |
| ADR の不変条件が DB 制約になっていない | `UNIQUE` 制約を追加（`LEFT JOIN` で締めの合計が二重計上されていた） |

## 残った未達

Release 2.0 は完成しましたが、IT15 のデモ項目 18 件のうち **1 件が未達**で終わりました。さらに返済枠 4 件が落ち、宣言だけされて検査の無い規則が残りました。

**この 2 つが、次章「整流」という新しい局面を生みます。** 新規ストーリーを書かず、未達と負債と未検査の規則だけを扱う回です。

## この局面の要点

1. **破壊検証は「リストの作り方」で結果が変わる。** 自分で選ぶと全部赤、機械的に数えると空振りが出る
2. **作った直後に壊すと空振りが 0 になる。** まとめてから数えると間に合わせが混ざる（IT12）
3. **ADR は検査が無ければ半分しか守られない。** ADR-009 は 7 IT のあいだ違反を増やし続けた（M5）
4. **検査自身が M1 の対象になる。** 名簿方式は載せ忘れたものほど漏れる
5. **全緑からレビューが高を出す状態が 7 IT 連続。** 自動チェックとレビューは見ている領域が違う
6. **落とした負債は据え置かれず育つ。** 5 → 7 クラス、新たな 19 引数（M4）

# 実践 AI 駆動開発 — 執筆アウトライン

本ドキュメントは記事シリーズ **「実践 AI 駆動開発」** の計画書です。章立て・各章の主題・引用元・執筆順序を定めます。記事本文ではありません。

## 1. シリーズの位置づけ

| 項目 | 内容 |
| :--- | :--- |
| シリーズ名 | 実践 AI 駆動開発 |
| 記事ディレクトリ | `docs/article/ai-driven-development/` |
| 参照元実装 | `docs/article/source/java-2/apps/`（`java/take-6`） |

### 既存 2 シリーズとの関係

`docs/article/index.md` には既に 2 シリーズがあります。本シリーズは 3 本目として並びます。

| シリーズ | 問い |
| :--- | :--- |
| モノリスアーキテクチャ実装比較 | 同じ設計方針を違うランタイムに載せると何が分かれるか |
| 関数型ドメインモデリング | 業務ルールをどこまで型に埋め込めるか |
| **実践 AI 駆動開発（本シリーズ）** | **AI エージェントと組んだ開発で、何が品質を守り、何が守らなかったか** |

**題材とアーキテクチャは他 2 シリーズと同じです。** 違うのは軸で、本シリーズは**成果物ではなく開発プロセスそのもの**を扱います。「Cargo Tracker をどう作ったか」ではなく「**AI と作ると何が起きるか**」を書きます。

そのため、ドメインモデルやヘキサゴナルアーキテクチャの解説は既存シリーズへのリンクで済ませ、重複させません。

### この記事が扱わないこと

| 対象外 | 理由 |
| :--- | :--- |
| プロンプトエンジニアリングのテクニック集 | 単発の入力の工夫ではなく、20 IT 継続した運用を扱うため |
| ツールの機能紹介・設定手順 | 実装リポジトリの `.claude/` と `README.md` を参照すれば足りるため |

## 2. 通底する主題

20 イテレーションのふりかえり（`retrospective-1`〜`20`）とジャーナルを通読すると、**同じ形の失敗が名前を変えて繰り返されて**います。本シリーズの背骨はこれです。

| # | 主題 | 具体的に何が起きたか |
| :--- | :--- | :--- |
| M1 | **緑であることは、守られていることの根拠にならない** | 安全装置を入れたのに働いていない（IT1 で 4 件、IT11 で 22 件中 3 件空振り） |
| M2 | **書いたことと、していることは別** | ADR・Javadoc・遷移表が仕様を語り、実装が守っていない（IT15 で 3 か所同型） |
| M3 | **記録は実態より小さくなる** | 起票時の件数と実測が 5 回連続でずれた（C1 は記録 34 に対し実測 249） |
| M4 | **落とした負債は育つ** | 「余力次第」の返済枠は 3 IT 連続で繰り越された（ADR-008） |
| M5 | **規則は検査に落とさなければ守られない** | ADR-009 は 7 IT のあいだ半分守られず、違反が 5 本増えていた |

**AI 固有の失敗ではありません。** ただし AI は文章を速く大量に書くため、M2・M3 が人手より高い頻度で出ます。この非対称性が本シリーズの中心的な発見です。

## 3. 章構成

### 導入

### 第 1 部：仕組み — 何を用意したか

| 章 | タイトル | 主題 |
| :--- | :--- | :--- |
| 第 2 章 | Skill 体系で開発プロセスを固定する | 56 Skill の分類（分析／開発／レビュー／計画／運用）、Skill が「暗黙の手順」を明文化する意味、`CLAUDE.md` と Skill の役割分担 |
| 第 3 章 | イテレーションのライフサイクル | `opening-iteration`（6 ステップ）と `closing-iteration`（7 ステップ）。抜けやすい工程（完了報告書・GitHub 同期・ドキュメント同期）を手順に埋め込む |
| 第 4 章 | Ralph Loop と自律実行の境界 | Stop hook による継続実行、AI 単独で完結するタスクとそうでないタスクの切り分け、暴走させない歯止め |

### 第 2 部：規律 — 何が品質を守ったか

| 章 | タイトル | 主題 |
| :--- | :--- | :--- |
| 第 5 章 | TDD と「破壊検証」 | Red-Green-Refactor に加えて **作った安全装置を実際に壊して赤を確認する**。IT11（22 件中 3 件空振り）と IT12（21 件中 0 件空振り）の差は「壊すタイミング」だった（M1） |
| 第 6 章 | マルチパースペクティブレビュー | XP 5 エージェント（programmer / tester / architect / technical-writer / user-representative）の並列レビュー。途中レビューとクローズ前レビューの 2 段階運用。IT16 では途中レビューが**そのイテレーション自身の違反**を捕まえた |
| 第 7 章 | 規則を検査に落とす | ADR・コメント・遷移表は守られない。ArchUnit・自作 lint・QueryCounter へ落として初めて機能する（M2・M5）。IT20 の「（型・メソッド・呼んでよい相手）の 3 つ組」で一般化を避けた判断 |
| 第 8 章 | 記憶と負債 — 失敗を資産にする | エージェントメモリへの feedback 蓄積、ジャーナル（判断と学びの記録）、負債返済枠を IT 序盤の独立コミットに固定する運用（M4）。返済枠がストーリー本体と同規模になった IT12 |

### 第 3 部：実践記録 — 20 イテレーションで何が起きたか

局面ごとにまとめ、各章で 3〜5 イテレーションを扱います。

| 章 | タイトル | 対象 IT | 主題 |
| :--- | :--- | :--- | :--- |

## 4. 各章の構成（共通フォーマット）

イテレーション章（第 9〜13 章）は同じ構成で書きます。

1. **この局面のゴール** — 何を動く状態にするか
2. **AI に何をさせたか** — 使った Skill・分業の形
3. **起きた失敗** — 実際のふりかえりから、名前と件数つきで
4. **どう直したか** — 検査・運用・ドキュメントのどれに落としたか
5. **残った未達** — 次の局面へ持ち越したもの

仕組み・規律の章（第 2〜8 章）は次の構成です。

1. **解こうとした問題**
2. **仕組みの中身** — 実ファイルからの引用
3. **実際に働いたか** — イテレーション実績での検証
4. **働かなかったケース**

## 5. 引用元の対応

記事中のコード・設定の引用はすべて実ファイルから転記します。

| 章 | 主な引用元 |
| :--- | :--- |
| 第 2 章 | `java-2/CLAUDE.md`、`.claude/skills/*/SKILL.md` |
| 第 3 章 | `.claude/skills/opening-iteration/`、`closing-iteration/` |
| 第 4 章 | `java-2/README.md`（ralph-loop 導入手順）、`.claude/settings.json` |
| 第 5 章 | `docs/article/source/java-2/apps/` のテストコード、`retrospective-11.md`・`12.md` |
| 第 6 章 | `.claude/skills/developing-review/`、`docs/review/` |
| 第 7 章 | `apps/.../architecture/` の ArchUnit テスト、`docs/adr/` |
| 第 8 章 | `.claude/agent-memory/`、`docs/journal/` |
| 第 9〜13 章 | `docs/development/iteration_plan-N.md`・`iteration_report-N.md`・`retrospective-N.md` |
| 第 14 章 | 全ふりかえり、他言語 take のふりかえり |

**本シリーズは `docs/` こそが一次資料です。** 既存 2 シリーズは参照元の `docs/` を収録せず記事側に要点を反映する方針でしたが、本シリーズは読者が実際のふりかえり・計画・レビュー記録を突き合わせられることに価値があるため、**必要な範囲を `source/java-2/docs/` に収録します**（144 ファイル・2.7M）。

| 収録するもの | 内容 |
| :--- | :--- |
| `development/` | イテレーション計画 20・完了報告 20・ふりかえり 20・リリース計画／報告 |
| `journal/` | 開発ジャーナル（判断と学びの記録） |
| `review/` | マルチパースペクティブレビューの記録 |
| `adr/` | 設計判断の記録（第 7 章で「規則が守られなかった」実例として引用） |
| `design/` | 設計ドキュメント（正典ドリフトの検証対象） |
| `strategy/` | 開発戦略 |

| 収録しないもの | 理由 |
| :--- | :--- |
| `article/` | 参照元リポジトリ側の記事コピー。本リポジトリと重複する |
| `manual/` / `reference/` / `template/` / `assets/` | 本シリーズが引用しない |
| `requirements/` | 本リポジトリの `docs/requirements/` が US 採番の正典であり、そちらを参照する |

`.claude/skills/` も収録しません。**本リポジトリの `.claude/skills/` が同一の Skill 体系**であり、第 2〜4 章はそちらを引用します。

引用箇所は出典（ファイル名・IT 番号）を本文に明記します。

## 6. 執筆順序

| 順 | 対象 | 理由 |
| :--- | :--- | :--- |
| 1 | 第 1 章＋シリーズ index | 全体像を先に固定する |
| 2 | 第 9〜13 章（実践記録） | 一次資料が揃っており、事実の確定が先 |
| 3 | 第 2〜8 章（仕組み・規律） | 実践記録から「実際に効いた仕組み」を抽出して書く |
| 4 | 第 14 章（総括） | 全章の確定後 |
| 5 | `docs/article/index.md` への反映・MkDocs nav | 章が揃ってから一括 |

**第 3 部を先に書きます。** 仕組みの章を先に書くと「用意した仕組みの説明」に寄り、実際には働かなかったものを美化するためです。事実から先に固めます。

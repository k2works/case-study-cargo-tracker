# 第 2 章：Skill 体系で開発プロセスを固定する

## 解こうとした問題

**AI 駆動開発で最初に決めるのは「毎回どう頼むか」ではありません。「頼まなくても同じ手順が走る状態をどう作るか」です。**

毎回プロンプトで手順を指示していると、次の 3 つが起きます。

1. **指示の粒度がその日の集中力に依存する** — 疲れている日は「実装して」で終わる
2. **手順が改善されない** — 良い手順を思いついても、次回の自分に伝わらない
3. **抜けが発見されない** — 何をすべきだったかが定義されていないので、抜けが抜けとして見えない

20 イテレーションを 8 日で回すには、**手順そのものを成果物として扱う**必要がありました。

## 仕組みの中身

`.claude/skills/` に **56 の Skill** を置いています。1 Skill = 1 つの作業手順で、`SKILL.md` に発動条件と手順を書きます。

### 分類

| 分類 | 数 | 例 |
| :--- | ---: | :--- |
| オーケストレーション | 3 | `orchestrating-analysis` / `-development` / `-operation` |
| 分析 | 14 | `analyzing-requirements` / `-domain-model` / `-architecture` / `-test-strategy` |
| 開発 | 2 | `developing-backend` / `developing-frontend` |
| レビュー | 4 | `analyzing-review` / `developing-review` / `developing-uiux-review` / `operating-review` |
| 計画・進捗 | 8 | `opening-iteration` / `closing-iteration` / `planning-releases` / `validating-design` |
| 運用 | 9 | `operating-setup` / `-cicd` / `-deploy` / `-qt` |
| ドキュメント・Git | 10 | `creating-adr` / `creating-journal` / `git-commit` / `operating-docs` |
| 学習・共通 | 6 | `ai-agent-guidelines` ほか |

**分析 14・計画 8 という配分が特徴です。** 実装 Skill は 2 つしかありません。**AI 駆動開発で標準化して効くのは、コードを書く手順ではなく、その前後の手順**でした。

### `CLAUDE.md` との役割分担

| 場所 | 何を書くか |
| :--- | :--- |
| `CLAUDE.md` | **常に効く規範** — ペルソナ・言語・確認要否の境界・完了報告の様式 |
| Skill | **その作業のときだけ効く手順** — 発動条件つき |

`CLAUDE.md` で最も実務に効いたのは「確認要否の境界」です。

| 即座実行（確認不要） | 確認必須 |
| :--- | :--- |
| バグ修正・リファクタリング・性能改善 | 新規ファイル作成 |
| 既存ファイルの修正・更新 | 重要ファイルの削除 |
| 依存の追加・更新・削除 | アーキテクチャ・フォルダ構造の大規模変更 |
| 単体・統合テストの実装 | 新 API・外部ライブラリ導入 |
| 設定値変更・フォーマット適用 | 認証・認可の実装／スキーマ変更・マイグレーション |

**この境界が無いと、AI は 2 つの失敗のどちらかをします。** 全部確認して手が止まるか、確認せずに構造を変えるかです。境界を明文化すると、**確認は本当に判断が要るところにだけ発生します**。

20 イテレーションで実際に確認が入ったのは、認可の変更（IT16：`ui_design.md` と `SecurityConfig` の食い違い）のような**正典の判断が割れる場面**でした。

## 実際に働いたか

### 8 日で 20 回転できた

**これが最大の成果です。** 開始と終了を Skill で固定しなければ、この回数は回りません。イテレーションごとに「次に何をするか」を人間が指示していたら、指示だけで 1 日が終わります。

### 手順が改善され、次のイテレーションに引き継がれた

Skill は固定ではなく、ふりかえりの Try が反映されます。

| 発見 | Skill への反映 |
| :--- | :--- |
| 着手前の突合で欠落が 13 件見つかる（IT7） | `opening-iteration` のステップ 3・4（詳細／横断整合性検証） |
| 実装途中のレビューが自 IT の違反を捕まえる（IT16） | 途中レビューを工程として明示 |
| ローカル緑と CI 緑を混同する（IT3） | `closing-iteration` に「`gh run` で CI の実結果を確認」を追加 |
| テスト緑で品質ゲートを終わりにする | 「SonarQube Quality Gate PASS までを完了条件とする」を明記 |

**手順書が育つことで、同じ失敗が構造的に止まります。** 記憶（第 8 章）が「教訓として残す」のに対し、Skill は「次回自動的に実行される」形です。**効いた教訓はいずれも Skill か検査の形に落ちたもの**でした。

### 分析 Skill が「作ったが使えない」を先に潰した

第 10 章で見たとおり、着手前の突合は 6 イテレーション連続で「作ったが使えない」型の欠落を見つけています。

| IT | 見つけたもの |
| ---: | :--- |
| 5 | 実行できる人がいない |
| 6 | 実行する人の入口が無い |
| 7 | **その人自体が存在しない**（`ROLE_SHIPPER` の利用者が未作成） |

> 6 IT 連続で「作ったが使えない」型であり、**着手前の突合でしか見つからない**。
>
> — `retrospective-7.md` K1

## 働かなかったケース

### 1. Skill があっても実行されない工程がある

**途中レビューは IT14・IT15 と 2 イテレーション連続で落とされました。** 手順に書いてあっても、「余力があれば」の位置にあるものは落ちます。

同じことが `closing-iteration` のステップ 8（ジャーナル）でも起きました。

> ### （任意）ステップ 8: ジャーナル（`creating-journal`）
>
> — `.claude/skills/closing-iteration/SKILL.md`

**「（任意）」と書かれた唯一の工程が、20 回のうち少なくとも 1 日ぶん落ちました**（2026-08-08）。必須のステップ 1〜7 が生成する完了報告書とふりかえりは全 20 回分そろっています。

**規律の強さの差ではなく、必須か任意かの差です。**

### 2. Skill は「実行したこと」しか保証しない

`developing-review` は 5 エージェントを並列起動しますが、**IT7 では 4 視点が回答を返しませんでした**。Skill の手順どおりに起動しており、手順の側に落ち度はありません。

**手順が「起動する」までしか書いていないと、そこまでしか保証されません。** 結果の有無を確認する工程が要ります（第 6 章）。

### 3. 規約を書いた本人が読まずに作業する

IT6 の失敗です。`docs/manual/index.md` 自身が「章を追加したら 3 箇所を必ず揃える」と定めているのに、1 箇所が漏れました。

> **規約を書いた本人が、その規約を読まずに作業した。**
>
> — `retrospective-6.md` P5

**Skill は発動条件がマッチしたときにだけ読まれます。** 「章を追加する」という作業に Skill が紐づいていなければ、規約は文章として存在するだけです（主題 M5 と同じ構造）。

## この仕組みのまとめ

| 原則 | 根拠 |
| :--- | :--- |
| 手順そのものを成果物として扱う | 8 日 20 回転を可能にした |
| 標準化して効くのは**実装の前後** | 実装 Skill は 2、分析 14・計画 8 |
| `CLAUDE.md` に**確認要否の境界**を書く | 確認が本当に判断の要る場所にだけ発生する |
| ふりかえりの Try を**Skill に反映する** | 記憶のまま残った教訓は再発した |
| **「任意」と書いた工程は落ちる** | ジャーナルが 1 日ぶん欠けた |
| 手順は「起動する」でなく「**結果を確認する**」まで書く | レビューエージェントの無応答（IT7） |

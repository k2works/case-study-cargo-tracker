# 第 6 章：まとめ

本シリーズは、Cargo Tracker という**同じ業務**を 3 つの構成で実装したコードを読んできました。

| 章 | 構成 | 参照元 |
| :--- | :--- | :--- |
| 第 3 章 | モジュラーモノリス | `docs/article/source/java-2` |
| 第 4 章 | マイクロサービス + RabbitMQ（EDA） | `docs/article/source/java-3` |
| 第 5 章 | マイクロサービス + Axon Framework 5（CQRS/ES） | `docs/article/source/java-4` |

**3 つはいずれも動いている実装です。**段階的に育てた 1 つのコードベースの履歴ではなく、**独立した 3 本**です。だから「第 3 章の次に第 4 章へ進んだ」とは読めません。読めるのは、**同じ業務を別の前提で実装したときに何が変わるか**だけです。

この章では、その差分を 1 つの表に並べ、どれをいつ選ぶかを整理します。

## 3 つの実装アプローチの比較

### 構成の比較

| 観点 | モジュラーモノリス | EDA | CQRS/ES |
| :--- | :--- | :--- | :--- |
| デプロイ単位 | 1 つ | 8 サービス + 共有ライブラリ | 8 サービス + 共有ライブラリ |
| BC の単位 | トップレベルパッケージ | Gradle モジュール | Gradle モジュール |
| BC 間の境界 | ArchUnit で守る規律 | クラスパスが分かれる | クラスパスが分かれる |
| データベース | 1 つ（全 BC 共通） | サービスごと | サービスごと（**投影と Axon 管理表**） |
| BC 間の問い合わせ | ACL ポート（メソッド呼び出し） | ACL ポート（REST） | ACL ポート（Axon Query Bus） |
| BC 間の通知 | `ApplicationEventPublisher` | RabbitMQ | Axon Server（Event Bus） |
| 入口 | 画面（Thymeleaf + htmx） | REST + イベント購読 | REST + イベント購読 |
| Spring Cloud | 使わない | Gateway のみ | Gateway のみ |

第 4 章と第 5 章は、**この表ではほとんど同じ**です。サービス分割を揃えたのは意図的で、差分が永続化と読み書きの分離だけになるように選ばれています。

### 内側の比較

構成が同じでも、サービスの内側は別物です。

| 観点 | モジュラーモノリス | EDA | CQRS/ES |
| :--- | :--- | :--- | :--- |
| 書き込みの正典 | RDB の現在状態 | RDB の現在状態 | **イベント列（Event Store）** |
| 集約の永続化 | 集約単位で UPDATE | 集約単位で UPDATE | イベントを追記し、再生して復元 |
| 読み取り | 同じテーブルを SELECT | 同じテーブルを SELECT | **投影テーブル（結果整合）** |
| イベントの位置づけ | 保存のあとの通知 | 保存のあとの通知（契約） | **保存そのもの**（追記専用） |
| イベントの改名 | 自由 | 契約の変更（両側に契約テスト） | **Upcaster が要る**（過去は書き換えられない） |
| 調整役（サガ） | アプリケーション層のイベント購読 | メッセージハンドラ | Reaction Handler + `process_state` |
| 失敗の扱い | 捕まえて件数に記録する | 捕まえない（デッドレターへ） | 再試行 → 上限 → **補償と要確認一覧** |
| 不変条件の材料 | 集約 or DB の現在値 | 集約 or DB の現在値 | **集約だけ**（投影に尋ねられない） |

**「不変条件の材料」の行が、CQRS/ES を選ぶときに最も効きます。**投影は結果整合なので、「未決着のキャンセル申請は高々 1 件」のような判断を投影に尋ねると、追いついていないあいだは**申請できないと二重に申請できるの両方**が起こります。判断に要るものは集約が持つしかありません。第 3・4 章なら「テーブルを 1 本引けば済む」ことが、ここでは集約の設計に跳ね返ります。

### 保証を誰が引き受けるか

3 章を通して繰り返し現れたのは、**保証が消えるのではなく、引き受け手が移る**という形です。

| 保証 | モジュラーモノリス | EDA | CQRS/ES |
| :--- | :--- | :--- | :--- |
| コミット後に発行する | `@TransactionalEventListener(AFTER_COMMIT)` | 発行側で `afterCommit` を自作 | Axon の UnitOfWork |
| イベントの型が一致する | 同じ `record` を参照 | 契約テスト（両側に置く） | 契約テスト + Upcaster |
| 順序を守る | 同一トランザクション | 交換機とルーティングキー | Sequencing Policy（**列の切り方が被害の範囲**） |
| 一度だけ効く | トランザクション | べき等な購読 | `process_state` の段 |
| 集約の状態が正しい | DB の行 | DB の行 | **`@EventTag` が付いていること** |

いちばん下の行が、この方式の本質です。第 3 章なら集約の単体テストが落ちれば守りが壊れたと分かります。第 5 章では、`@EventTag` を付け忘れると集約は毎回空のまま復元され、**状態を見る守りが丸ごと素通りしてなお単体テストは緑**になります。しかも `AxonTestFixture` の `disableAxonServer()` ではタグによる復元が働かないので、単体テストでは原理的に判別できません。

**「緑に見えるが何も見ていない」テストが増える**——これが CQRS/ES の代金のうち、見積もりに現れにくい部分です。

## 適用判断の観点

### チーム規模と運用コスト

| 方式 | 動かすのに要るもの | 運用で見るもの |
| :--- | :--- | :--- |
| モジュラーモノリス | アプリ 1 つ + DB 1 つ | ログとメトリクス |
| EDA | サービス 8 つ + DB 8 つ + ブローカー | 上記 + キューの滞留・デッドレター |
| CQRS/ES | サービス 8 つ + DB 8 つ + Axon Server | 上記 + 投影の遅れ・トークンの位置・退避の再処理・**Event Store のバックアップと復元** |

**下に行くほど、業務が止まらなくても壊れている状態が増えます。**投影が止まっても書き込みは通り、画面だけが古くなります。Axon Server に繋がらなくてもアプリは起動します。**「起動した」「200 が返った」では健全性を判断できない**構成である、ということです。

小〜中規模のチームでは、まずモジュラーモノリスで境界を固定するほうが安全です。境界が正しいかどうかは、分ける前に確かめられます。

### 境界づけられたコンテキストの独立性

分けたあとに境界を直す費用は、方式ごとに桁が違います。

- **モジュラーモノリス**：パッケージの移動とリファクタリング。コンパイラが追随する
- **EDA**：契約の変更。発行側と購読側の両方を直し、両方に契約テストを置く
- **CQRS/ES**：**過去のイベントが読めるかどうかで縛られる**。クラスの移動・改名は Upcaster を伴い、パッケージ移動は「無料」ではない

境界が曖昧なまま CQRS/ES へ進むと、**間違った境界がイベントの型名として永久に残ります**。逆に言えば、境界が安定していることが前提条件です。

### 同期／非同期の整合性要件

- 即時整合を強く要求する領域は、同期コマンド中心の設計が適します。第 3 章の構成なら、1 トランザクションで済むことを分散させずに済みます
- 結果整合を許容できる通知・連携は、EDA で分離したほうが保守しやすくなります
- **イベント履歴そのものが業務の材料**である場合に、CQRS/ES の価値が最大化します

最後の点は言い換えが効きます。**「結果」だけでなく「経緯」を業務が読むか**です。第 5 章の実装は、履歴が業務として要る根拠を**例外処理・誤配・通関**（US19・US20・US28・US29）に置いています。逆に `authms` だけは状態保存のままです——現在状態だけが業務に要り、履歴は監査ログで足りるからです。

## 選び方

観点を 3 つ並べましたが、判断の順序は 1 つです。

1. **境界が安定しているか**を先に確かめる。安定していないなら、分ける前に直す。モジュラーモノリスはこれを安く確かめられる唯一の構成です
2. **プロセスを分ける理由があるか**を問う。デプロイ独立・チーム独立・スケール単位のどれかに実際の要求があるときだけ分けます。境界の表現のために分けるのは費用が合いません
3. **経緯を業務が読むか**を問う。読むなら CQRS/ES を検討します。読まないなら、履歴は監査ログで足ります

第 5 章の実装が `Quotation` と `Voyage` を「業務上は履歴が要らないのに」イベントソーシングにしたのは、**記事の比較のため**だと明記されています。実務でこれをやる理由はありません。そして同じ ADR が、**見直しの発動条件を数値で置いています**。

> **IT2 終了時点で実績ベロシティが計画の 70% 未満なら、`Quotation` と `Voyage` を
> 状態保存（MyBatis の UPDATE）に落とす。**

「工数の問題が出たら考える」では検知できません。**採用した方式を降りる条件を、採用するときに決めておく**——3 つの実装を並べて読んで、いちばん移植しやすい習慣はこれでした。

## 次の実装ステップ

読者が自分のコードベースで試すなら、次の順序を勧めます。

1. **境界の検査を書く**。ArchUnit で BC 間の依存方向と ACL ポートを固定します。これは 3 方式のどれでも要り、どれを選んでも無駄になりません
2. **イベントの契約を明文化する**。フィールド・意味・互換性を書き、発行側と購読側の両方に契約テストを置きます。プロセスを分けていなくても効きます
3. **投影を 1 本作って捨ててみる**。読み取り専用のテーブルを 1 つ作り、再構築の手順を運用に載せます。CQRS/ES の運用負荷のうち、**いちばん重い部分を先に測れます**
4. **そのうえで方式を選ぶ**。1〜3 を済ませた時点で、境界が安定しているか・分ける理由があるか・経緯を読むかの 3 問に答えられるようになっています

この順序を守ると、フレームワークの導入が目的化しません。**Axon を入れるかどうかは最後の判断であって、最初の判断ではない**——3 本のコードを並べて読んだ結論は、そこに尽きます。

# 第 6 章：まとめ

本シリーズでは、Cargo Tracker を同じ題材のまま 3 つの実装観点で整理しました。

1. Spring Platform × モジュラーモノリス
2. Spring Platform × EDA
3. Spring Platform × CQRS/ES（Axon）

ここでは、方式ごとの適用判断を最終的にまとめます。

## 3 つの実装アプローチの比較

| 観点 | モジュラーモノリス | EDA | CQRS/ES（Axon） |
| :--- | :--- | :--- | :--- |
| 配置単位 | 単一デプロイ | 単一デプロイ（イベント連携強化） | 構成次第（単一/分散） |
| 境界の表現 | BC パッケージ分割 + ACL | BC + イベント契約 | BC + コマンド/イベント/投影 |
| 書き込み正典 | RDB の現在状態 | RDB + イベント通知 | イベント列（Event Store） |
| 読み取りモデル | クエリサービス | クエリサービス + 非同期反映 | 投影（Projection）中心 |
| 運用負荷 | 低〜中 | 中 | 高 |
| 本リポジトリでの状態 | 実装済み | 実装済み | 構想段階（未導入） |

## 適用判断の観点

### チーム規模と運用コスト

- **小〜中規模チーム**では、まずモジュラーモノリスで境界を固定するほうが安全です。
- 非同期連携が増える段階で EDA を強めると、責務分離を保ったまま拡張できます。
- CQRS/ES は運用設計（イベント再生、投影再構築、監視）を伴うため、専任に近い運用能力が必要です。

### 境界づけられたコンテキストの独立性

- BC の責務が明確で、ACL ポートとイベント契約が安定しているほど、上位方式へ移行しやすくなります。
- 境界が曖昧なまま CQRS/ES へ進むと、イベントスキーマの変更コストが急増します。

### 同期／非同期の整合性要件

- 即時整合を強く要求する領域は、同期コマンド中心の設計が適します。
- 結果整合を許容できる通知・連携は、EDA で分離したほうが保守しやすくなります。
- イベント履歴そのものを監査・再計算に使う要件が明確な場合に、CQRS/ES の価値が最大化します。

## 現行実装への結論

Cargo Tracker の現行コードベースは、**モジュラーモノリス + EDA 実装済み、CQRS 分離済み、ES/Axon 未導入**という位置にあります。  
したがって最も現実的な進め方は、次の順序です。

1. 現行 EDA のイベント契約を安定化する
2. 投影モデルの再構築手順を先に運用化する
3. そのうえで Axon 導入を評価する

## 次の実装ステップ

1. BC ごとのイベント契約（フィールド、意味、互換性）の明文化
2. 代表ユースケースを 1 本選び、投影再生成を試行
3. Axon PoC でコマンドモデル 1 つを Event Sourcing 化し、運用負荷を計測

この順序を守ると、フレームワーク導入が目的化せず、ドメイン境界と運用可能性を両立した移行判断ができます。

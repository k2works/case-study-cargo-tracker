## Java 実装

### 5 イテレーション越しの負債返済

IT10 の成功基準を見ると、機能より先に負債返済が並んでいます。

| ID | 内容 | 起票 |
| :--- | :--- | :--- |
| H-1 | `assignItinerary` に `requireStatus(EnumSet.of(...))` パターンを適用（`cancel()` も統一） | IT5 |
| H-2 | `assignItinerary` 完了時に `CargoRoutedEvent` を発行（テストで明示） | IT5 |
| H-3 | `assignRoute` コントローラメソッドを `executeBookingCommand` パターンに統合 | IT5 |

H-1 は第 6 章で触れた「抽出したが全箇所に適用していない」問題です。IT5 で `requireStatus` を抽出してから、全メソッドへの適用完了まで **5 イテレーション**かかりました。

H-2 は「イベント発行の漏れ」です。経路が紐付いたのに `CargoRoutedEvent` が発行されていませんでした。第 7 章で述べた通り、イベント発行をアプリケーション層で明示的に呼ぶ設計では、この漏れがテストなしには検出されません。成功基準に「テストで明示」と書かれているのは、その反省です。

### 料金算出

US21 の実装は、意外なほど簡素です。

```java
// billing/domain/model/valueobjects/FreightCalculationResult.java
public record FreightCalculationResult(
        String bookingId,
        int baseFreight,
        int adjustmentAmount,
        String adjustmentReason,
        int finalAmount
) {
    public static FreightCalculationResult of(
            String bookingId, int baseFreight,
            int adjustmentAmount, String adjustmentReason
    ) {
        return new FreightCalculationResult(
                bookingId, baseFreight, adjustmentAmount, adjustmentReason,
                baseFreight + adjustmentAmount
        );
    }
}
```

```java
// billing/domain/model/services/FreightCalculationService.java
public class FreightCalculationService {

    public FreightCalculationResult calculate(Invoice invoice, int adjustmentAmount, String adjustmentReason) {
        return FreightCalculationResult.of(
                invoice.getBookingId(),
                invoice.getTotalAmountValue(),
                adjustmentAmount,
                adjustmentReason != null ? adjustmentReason : ""
        );
    }
}
```

料金算出＝「基本運賃 + 調整額」。重量による従量計算も、距離による計算も、危険物加算もありません。基本運賃は請求書が既に持っている値をそのまま使い、調整額は人間が入力します。

これは実装の手抜きではなく、**スコープの割り切り**として理解すべきものです。IT4 で経路候補の料金を「基本単価 × 所要日数」でハードコードしたのと同じ扱いで、料金体系そのものはこのケーススタディの主題ではありません。

ただし `FreightCalculationService` はドメインサービスとして切り出されており、料金ロジックを追加する場所は用意されています。現状は 1 行の足し算しかしていませんが、置き場所が決まっていることには意味があります。

**調整額の符号**に注目してください。`baseFreight + adjustmentAmount` なので、減額したければ負値を渡します。第 10 章で見た Ruby 実装の「補償費用の方向確定」問題と同じ論点で、Java 実装は「調整額は符号付き」という約束で処理しています。この約束はコードから読み取れますが、UI で経理担当者が入力するときにどちら向きに入れるべきかは自明ではありません。

### ドメインサービスをいつ使うか

`FreightCalculationService` は、このプロジェクトで唯一のドメインサービスです。他の業務ロジックはすべて集約のメソッドに置かれています。

料金計算をドメインサービスにした理由は、**複数の集約にまたがるため**です。料金は請求書（`Invoice`）と予約（`Cargo`）と例外記録（Tracking）の情報から決まり、どの集約のメソッドとしても自然でありません。

DDD においてドメインサービスは「どの集約にも属さない業務ロジック」の置き場所であり、この使い方は正しいものです。逆に言うと、**ドメインサービスが増えるのは集約の切り方を疑うサイン**です。このプロジェクトで 1 つしかないことは、集約の境界が業務と合っていることを示しています。

## 他言語ではどう書いたか

### 料金算出の扱い

US21 をどこまで作り込んだかは、実装ごとに差があります。

| 言語 | 料金算出の実装 |
| :--- | :--- |
| Java | 基本運賃 + 調整額 |
| Rust | `FreightCharge` 集約として独立。消費税計算あり |
| Ruby | 料金調整に取消・監査証跡を実装（IT9） |
| Go | 割引ポリシーを独立コンテキスト（`discountpolicy`）として分離 |
| Haskell | Billing Context の `Invoice` 集約に統合 |

Rust は料金を独立した集約（`FreightCharge`）にし、消費税をドメインに持たせています。Go は割引ポリシーを Billing とは別のコンテキストに切り出しており、ドメイン層カバレッジ 92.7% を単独で計測しています。

分割の是非は業務の複雑さ次第です。料金体系が単純なうちは Java のように請求書に統合するほうが素直で、体系が複雑化したときに切り出せばよい。ただし Rust・Go の分割は、**将来の複雑化を見越して先に境界を引く**という判断であり、モノリスにおいては安価な投資です（プロセス分割と違い、後から統合も分割も容易なため）。

Release 完了時点の各実装の規模を並べます。粒度が違うため直接比較はできませんが、傾向は読み取れます。

カバレッジの高い実装（Ruby 95.95%、TypeScript 94.05%、F# 89.0%）に共通するのは、**カバレッジ閾値を CI のハードゲートにしている**ことです。F# は「閾値 80% / ドメイン層 85%」と層別に設定しています。

Java の 80.9% は目標（80%）ぎりぎりで、ブランチカバレッジ 74% は目標未達のままリリースされました。C# 実装のふりかえりには「カバレッジ 85% CI ハードゲート化」が繰り越し項目として記録されており、同じ課題を抱えています。

**閾値を CI で強制していない実装は、目標を下回ったままリリースに至る**という相関がはっきり出ています。

### 例外系・境界値のテスト

最終イテレーション前後で各実装が集中的に追加したのは、例外系と境界値のテストです。

- **C#** — 「精算異常系テスト: MarkOverdue 境界・Overdue→Confirmed・存在しない精算書・二重発行」
- **Go** — 「支払期限 DATE/TIMESTAMP 境界バグ → 日付単位比較へ正規化・当日時刻付き境界テスト追加」
- **TypeScript** — 「サービス単体/境界値/端数テスト」
- **Ruby** — 「seq_number 境界バグ」の修正

すべて金額・日付・連番の**境界**に集中しています。正常系は早い段階で固まりますが、境界は最後まで残る。しかも境界のバグは、業務データが実際に境界に乗るまで顕在化しません（期限当日に到着する貨物、割引率 0% の法人、調整額 0 円の請求書）。

**リリース前に境界値テストをまとめて追加する**のは、全実装が共通して踏んだ工程です。であれば、機能実装と同時に境界を洗い出すほうが安い。境界値分析はテスト技法として古典的ですが、実践されているとは限らないことがこの 10 実装から見て取れます。

平均ベロシティ 9.8 SP/イテレーション。当初の想定（実効 10〜13 SP）の下限に収まりました。10 イテレーション中 9 回が目標達成で、外したのは IT4 の 1 回だけです。

ベロシティが安定していた理由の 1 つは、**部分完了を 0 点として扱った**ことです（IT4 の IT3-改善が 2 SP 予定で加算 0）。実態より高いベロシティを記録すると、次の計画が過大になり、以降ずっと外し続けます。

もう 1 つは、毎イテレーションに 2〜3 SP の改善枠を最初から積んでいたことです。IT2（4 SP）、IT3（3 SP）、IT5（改善込み）、IT6（3 SP）、IT10（3 SP）と、新機能だけで 10 SP を埋めていません。**改善を計画に載せる**ことが、ベロシティを安定させています。

ただし第 5 章で見た通り、載せた改善が必ず消化されたわけではありません。「改善枠を確保する」ことと「改善が実際に進む」ことの間には、まだ距離があります。

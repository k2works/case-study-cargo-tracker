## 25 テーブルと所有 BC

**テーブルには所有者がいます。** 一次資料はこれを正典として表にしています。

| BC | テーブル |
| :--- | :--- |
| **Booking** | `cargo` / `leg` / `booking_notification` / `booking_cancellation` |
| **Shipper** | `shipper` |
| **Routing** | `voyage` / `carrier_movement` / `booking_route_proposal` / `proposed_route` |
| **Tracking** | `tracking_activity` / `tracking_handling_event` / `tracking_exception_event` |
| **Handling** | `handling_activity` / `customs_declaration` / `customs_status_history` / `handling_correction` |
| **Billing** | `invoice` / `invoice_line_item` / `payment` / `invoice_reminder` |
| **Estimation** | `estimate` / `route_candidate` |
| **共有（所有者を持たない）** | `location`（共有カーネル。ADR-005）／ `users`・`user_roles`（支援サブドメイン。ADR-007） |

> 転記元：`docs/design/data-model.md`「テーブルの所有 BC（ADR-015 の正典）」

**所有とは「そのテーブルの SQL を書いてよい BC」のことです。** 他 BC のテーブルを読みたければ ACL ポートを通します。

### なぜ Java の検査だけでは足りないのか（ADR-015）

第 4 章で見た ArchUnit の BC 間参照禁止ルールは、**Java の型の依存しか見ません**。

```sql
SELECT c.booking_id, s.name
  FROM cargo c
  JOIN shipper s ON c.shipper_id = s.id
```

この SQL を Billing の MyBatis マッパーに書いても、**Java のコードとしては Billing のクラスしか登場しません**。ArchUnit は緑のまま通ります。しかし実態は Billing が Booking と Shipper のテーブルを直接読んでおり、**BC 分離は破れています**。

ADR-015 の決定はこうです。

> BC 間の結合は SQL の層でも検査する（ArchUnit は Java の依存しか見ない）

`MapperTableOwnershipTest` がマッパーの SQL をパースし、自分の BC が所有するテーブルだけを触っていることを検査します。例外は `ALLOWED` に**理由とともに**書きます。

**「黙って通すのではなく、名前で残す」**——第 6 章の名簿方式と同じ思想です。

### 正典が空白だった

**この所有の表そのものに事故がありました。** 一次資料が経緯を記録しています。

> ADR-015 は「テーブルの所有 BC の正典は `data-model.md` である」と定めていたが、
> **正典と名指しされた側が空白だった**。所有者を示していたのは検査コードの `OWNER` だけであり、
> **検査だけが正典で設計文書が無い**状態が IT12 から続いていた。
>
> 転記元：`docs/design/data-model.md`

**ADR が「あそこが正典だ」と宣言したのに、指された側に何も書かれていない**という状態が 4 イテレーション続きました。検査は動いており、SQL の越境は防がれていました。**壊れていたのは「なぜその所有なのか」を人が読める場所だけ**です。

この状態の危険は、**検査コードを誰も疑えなくなること**にあります。所有が正しいかを確かめる根拠が検査コード自身しかないため、検査が間違っていても検出できません。

### 実際に検査が間違っていた

そして間違っていました。

> **`route_candidate` の所有を Routing から Estimation に直した。**
> `route_candidate.estimate_id` は `estimate(id)` を参照しており、**ER 図もテーブル定義も
> 見積の子テーブルとして書いていた**。誤っていたのは本表と検査の名簿だけである。
>
> **正典と検査が一致するかを見る突合は、この誤りを検出できなかった。**
> 本表は検査の名簿から書き起こしており、**両方が同じ間違いをしていた**。
> 突合が守るのは「2 か所がずれないこと」であって「正しいこと」ではない。
>
> 転記元：`docs/design/data-model.md`

**突合検査の限界を明示した記録です。**

> **2 か所の一致は、正しさの証明ではない。片方をもう片方から書き起こしたなら、なおさら。**

正典を後から検査コードから書き起こしたため、**同じ誤りが 2 か所に複製されただけ**でした。気づいたのは Estimation を実装する段になってスキーマまで遡ったときです。

さらに名簿方式そのものの反転した性質も記録されています。

> **表に載っていないテーブルは検査が「分からない」として赤にする。** 名簿方式は
> **載せ忘れたものほど検査から漏れる**という反転した性質を持つため
> （`handling_correction` が 3 イテレーション素通りした）、
> **マイグレーションが作ったテーブルとの突き合わせ**も検査に含めている。

**名簿に載っていないものを「通す」設計だと、載せ忘れが最も危険な穴になります。** ここでは「載っていないものは赤」に反転させ、さらに**マイグレーションが作った実際のテーブル一覧**と突き合わせています。名簿の完全性を、名簿の外側から検査する形です。

## 集約とテーブルの対応

集約 13 個に対してテーブルは 25 件です。1 対 1 ではありません。

| 集約 | テーブル | 関係 |
| :--- | :--- | :--- |
| `Cargo` | `cargo` ＋ `leg` | 1 集約 : 2 テーブル（旅程の区間が子テーブル） |
| `Voyage` | `voyage` ＋ `carrier_movement` | 1 集約 : 2 テーブル |
| `BookingRouteProposal` | `booking_route_proposal` ＋ `proposed_route` | 1 集約 : 2 テーブル |
| `Estimate` | `estimate` ＋ `route_candidate` | 1 集約 : 2 テーブル |
| `TrackingActivity` | `tracking_activity` ＋ `tracking_handling_event` ＋ `tracking_exception_event` | 1 集約 : 3 テーブル |
| `Invoice` | `invoice` ＋ `payment`（＋ `invoice_line_item`） | 1 集約 : 2 テーブル（＋未使用 1） |
| `HandlingActivity` | `handling_activity` | 1 : 1 |
| `CustomsDeclaration` | `customs_declaration` ＋ `customs_status_history` | 1 集約 : 2 テーブル |
| `Shipper` | `shipper` | 1 : 1 |

**集約が複数テーブルに分かれるのは、集約の内側にコレクションがあるときです。** `Cargo` は `CargoItinerary`（旅程）を持ち、旅程は `Leg`（区間）のリストです。リストは行の集合になるので子テーブルになります。

**逆に、テーブルが集約をまたぐことはありません。** これは MyBatis を採用したことと関係します（ADR-004）。SQL を明示的に書くため、**集約をロードする SQL の範囲が集約境界そのもの**になります。ORM の遅延ロードで気づかないうちに境界を越えることがありません。

## BC 境界に外部キーを引かない（判断 5）

**同じ DB の中でも、BC をまたぐ参照には外部キー制約を付けません。**

| 参照 | FK |
| :--- | :--- |
| `leg.cargo_id` → `cargo.id`（BC 内） | **あり** |
| `carrier_movement.voyage_id` → `voyage.id`（BC 内） | **あり** |
| `handling_activity.booking_id` → `cargo.booking_id`（BC 間） | **なし** |
| `invoice.booking_id` → `cargo.booking_id`（BC 間） | **なし** |

根拠は一次資料にこうあります。

> DDD の境界付けられたコンテキスト間はイベント連携を前提とする疎結合設計であり、
> DB 外部キーによる強結合は将来のサービス分割を妨げる。整合性はアプリケーション層で保証する。

**モジュラーモノリスの設計として一貫しています。** 1 つの DB を共有していても、BC 間の参照は「別サービスへの参照」と同じ扱いにしています。

**代償は明確です。** 参照整合性は DB が保証しません。存在しない `booking_id` を持つ請求書を作ることが、DB のレベルでは可能です。これはアプリケーション層（ACL ポートによる存在確認）が守ります。

**この代償を払う価値があるかは、分割する予定があるかによります。** この題材は「将来のサービス分割を妨げない」ことを選びました。分割の予定が無いなら、FK を引いて DB に守らせるほうが安全です。

## 業務プリンシプルが物理設計に届いた例

第 1 章で予告した、部分インデックスの話です。

```sql
-- 未解決例外の一覧。追跡管理者が毎朝引く最重要クエリ（operation.md 業務運用）。
CREATE INDEX idx_tracking_exception_unresolved
    ON tracking_exception_event (tracking_id, occurred_at DESC)
    WHERE resolved_at IS NULL;

-- 通関で留置中の申告。3 日以上の留置は保管料が発生するため督促対象になる。
CREATE INDEX idx_customs_held
    ON customs_declaration (declared_at)
    WHERE status = 'HELD';

-- 経路未割り当ての予約。経路割り当て待ち一覧（ROLE_ROUTER の作業入口）で引く。
CREATE INDEX idx_cargo_unrouted
    ON cargo (arrival_deadline)
    WHERE routing_status = 'NOT_ROUTED';
```

> 転記元：`apps/cargo-tracker/src/main/resources/db/migration/postgresql/V101__partial_indexes.sql`

**3 本ともコメントが「誰が」「いつ」引くかを書いています。** ビジネスプリンシプルの「例外への迅速な対応」（第 1 章）と、組織マップの `ROLE_ROUTER`（第 2 章）が、そのまま `WHERE` 句になっています。

**さらに、この 3 本が `postgresql/` に隔離されていること自体が設計判断です。**

> 部分インデックスは H2 が解釈できないため `common/` に置けない。
> その結果、**ローカル（H2）ではこれらのインデックスが存在しない**。
> ローカルで一覧が速いことは本番で速いことを意味しないため、
> 効果は Repository テスト（実 PostgreSQL）と負荷試験で確認する。

**「ローカルで速いことは本番で速いことを意味しない」を SQL のコメントに書いています。** 環境差を隠さず、どこで検証するかまで書く形です。第 9 章で扱う DB 戦略（ADR-003）の帰結です。

### インデックスが 1 件も無かった時期がある

一次資料はこう記録しています。

> `non_functional.md` は公開追跡 API に p95 200ms を要求しているが、旧版のデータモデルには
> `CREATE INDEX` が 1 件も無く、**性能目標が物理設計として裏づけられていなかった**。

**非機能要件は、それを実現する物理設計と対にならないと宣言で終わります。** p95 200ms という数字は書かれていましたが、それを可能にする索引がありませんでした。

## 型の選択 — 4 つの判断

| # | 判断 | 根拠 |
| :--- | :--- | :--- |
| 金額 | `INTEGER`（最小通貨単位）＋ `VARCHAR(3)`（ISO 4217）。`NUMERIC` は使わない | 浮動小数点の精度誤差を排除。ドメインの `Money` 値オブジェクトに対応 |
| 列挙 | `VARCHAR(30)` ＋ CHECK 制約。PostgreSQL の `ENUM` 型は使わない | `ENUM` は値の追加に ALTER が必要でマイグレーションのリスクが高い |
| 識別子 | `BIGSERIAL` のサロゲートキー ＋ 業務キーに `UNIQUE` | FK を `BIGINT` に統一。**例外として `shipper.id` と `cargo.booking_id` は `UUID`**（アプリ側で採番） |
| 場所参照 | `location.unlocode`（5 文字の自然キー）を FK にする | UN/LOCODE は国際標準であり、それ自体が意味を持つ |

**金額の判断が ADR-025（単一通貨 JPY）と組み合わさっているのが面白い点です。** 通貨コードのカラムを持ちながら、実際には JPY しか入りません。**将来の複数通貨に備えた列を残しつつ、いま扱う値は 1 つに固定する**という形です。

`ENUM` を避ける判断も実践的です。第 8 章で見るとおり、この実装は 41 本のマイグレーションで列挙値を何度も追加しています。`ENUM` 型ならそのたびに型の ALTER が必要でした。

## 楽観的ロックと監査カラム

**全テーブルに `created_at` / `updated_at` があります。例外なしです。**

> 国際貨物輸送は規制上の監査要件が高く、全レコードの作成・更新タイムスタンプが必要。
> PostgreSQL のトリガーで自動更新する方法もあるが、**更新経路をアプリケーション側に集約したほうが
> 「いつ誰が更新したか」をコード上で追跡でき、テストからも制御しやすい**。

トリガーではなく MyBatis マッパー側で `CURRENT_TIMESTAMP` をセットしています。**ローカル（H2）と本番（PostgreSQL）で更新経路が変わらない**ことが理由に挙げられています。

**集約ルートのテーブルには `version` カラムがあります**（`cargo` / `shipper` / `voyage` / `tracking_activity` / `handling_activity` / `invoice` / `estimate`）。楽観的ロックです。

根拠の書き方が具体的です。

> 荷役登録イベントは `tracking_activity` と `cargo` の両方を更新する設計であり、
> 荷役は本システムで最も頻度の高い操作である。
> **最も頻度の高い操作が複数集約の同時更新を伴う以上、lost update は例外ではなく日常的に起きる。**

そして、この列が無かったことで起きていた問題も記録されています。

> `test_strategy.md` は統合テストの検証対象に楽観的ロックを挙げていたが、この列が無いため
> **検証対象が存在せず、テストが書けない状態**だった。**文言だけの安全装置は安全装置ではない。**

コンプライアンス欄にはこうあります。

> **安全装置は「入れたこと」ではなく「働くこと」を、実際に競合を起こすテストで固定する。**

**「2 スレッドから同じ `Cargo` を更新すると後勝ちが例外になる」統合テストを DoD に含める**と明記されています。ADR や設計判断に「どう検証するか」を書く運用は、第 10 章の主題です。

## 作ったが使っていないテーブル

`invoice_line_item` は **作成済みだが使われていません**。ADR-016 が「明細テーブルを作らず、料金調整を精算書の列で持つ」と決めたためです。副題は「要求元のないものは作らない」。

**最初のマイグレーション（V1）で作られており、後から DROP されていません。** テーブルの削除は既存データを失うため、慎重になるのは妥当です。ただし所有の表には載ったままで、**「あるが使わない」ことが表からは読み取れません**。

**使われていないものを消さない判断は正しくても、使われていないことを構造で示す手段が要ります。** 第 11 章でもう一度扱います。

## この章の要点

| 観察 | 内容 |
| :--- | :--- |
| テーブルには所有 BC がある | ArchUnit は Java しか見ない。**SQL の越境は別の検査が要る**（ADR-015） |
| 正典が空白だった | ADR が指した場所に何も無い状態が 4 イテレーション。**検査だけが正典**は疑えない |
| 突合の限界 | 片方をもう片方から書き起こした 2 か所の一致は、**同じ誤りの複製**でしかない |
| 名簿方式の反転 | 載せ忘れたものほど漏れる。**載っていないものを赤にし、外側から完全性を検査する** |
| 集約 : テーブル | 1 : N。集約の内側のコレクションが子テーブルになる。**テーブルが集約をまたぐことはない** |
| BC 間に FK なし | 疎結合を優先し、整合性はアプリケーション層で守る。**分割の予定があるかで判断は変わる** |
| 部分インデックス 3 本 | 業務プリンシプルと組織マップが `WHERE` 句になった。**ローカルには存在しない**ことも明記 |
| 安全装置 | **「入れたこと」ではなく「働くこと」を検査する。** 文言だけの安全装置は安全装置ではない |

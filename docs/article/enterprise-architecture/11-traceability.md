# 第 11 章：4 観点の貫通と、破れた箇所

| 項目 | 内容 |
| :--- | :--- |
| 観点 | 総括 |
| 前提 | 第 1〜10 章 |
| 主題 | 業務の能力は、どこまで実装の構造に貫通したのか |

## 1 本の縦串を通してみる

「例外への迅速な対応」というビジネスプリンシプル（第 1 章）を、下まで追いかけます。

| 層 | 対応物 | 出典 |
| :--- | :--- | :--- |
| **ビジネス** | ビジネスプリンシプル 4「例外への迅速な対応」 | `business_architecture.md` |
| **ビジネス** | ケイパビリティ L2「例外処理」（成熟度：中） | 同上 |
| **ビジネス** | 組織マップ：現場部門・運用部門（追跡管理者） | 同上 |
| **要件** | US19（遅延例外）・US20（破損・紛失）・US28（誤配） | `user_story.md` |
| **アプリケーション** | Tracking Context のエンティティ `TrackingExceptionEvent` | `tracking/domain/model/entities/` |
| **アプリケーション** | `CargoExceptionRaisedEvent` / `CargoExceptionResolvedEvent`（Tracking → Booking） | `shared/domain/event/` |
| **アプリケーション** | `CargoExceptions` ポート（Booking → Tracking の問い合わせ） | `booking/...outboundservices/acl/` |
| **データ** | `tracking_exception_event` テーブル（所有：Tracking） | `data-model.md` |
| **データ** | 部分インデックス `idx_tracking_exception_unresolved` | `db/migration/postgresql/V101` |
| **テクノロジー** | `MapperTableOwnershipTest` が Tracking 以外の SQL を拒む | ADR-015 |
| **テクノロジー** | 部分インデックスは PostgreSQL でのみ有効（ローカルには無い） | ADR-003 |

**業務のプリンシプルから、部分インデックスの `WHERE` 句まで繋がっています。**

そして繋がりを支えているのは、各段の**判断の記録**です。「なぜ Tracking が所有するのか」「なぜ部分インデックスなのか」「なぜローカルには無いのか」——それぞれの段に理由が残っています。

## 貫通した 5 つ

### 1. 組織の部門が、クエリの ORDER BY まで届いた

組織マップの「運用部門・経路設計」が `ROLE_ROUTER` になり、`findAwaitingRouting()` の既定ソート順が「希望期限の昇順」になりました。理由は「経路設計者が朝に見るのは、どれが一番切羽詰まっているか」です（第 2 章）。

**業務の担当者の 1 日の動きが、SQL のソート順を決めています。**

### 2. 顧客セグメントが、防御の仕組みまで届いた

BMC の顧客セグメントに「荷受人」が入っていたことが、**アカウントを持たない利用者**という要求になり、公開追跡画面（`PublicTrackingController`）と `PublicRateLimitFilter`（ADR-011）になりました（第 2 章・第 9 章）。

### 3. 業務の優先順位が、整合性モデルを決めた

ADR-009 の反転は、トランザクション理論ではなく**「荷役の記録は落としてはならない」という業務の優先順位**で決まりました（第 6 章）。

**技術的整合性より業務の優先順位が上位にある**ことを、ADR が明文で示した例です。

### 4. 「誰が動けるか」が、連携方式を決めた

ADR-021 の判断基準は「できなかったことを誰がいつ知り、その人は動けるか」でした（第 6 章）。同期にするかイベントにするかを、**業務担当者の可動域**で決めています。

### 5. ADR が検査になった

11 の規則が検査に落ちています（第 10 章）。**決定が実行されているかを、人間が確認する必要がありません。**

## 破れた 5 つ

**貫通しなかった箇所のほうが、参照する価値があります。**

### 1. UC 番号のトレーサビリティが切れた

要件定義とユーザーストーリーで、UC の採番が食い違ったまま両方が現役です（第 3 章）。

**切れた理由は、この規則が実装に届かなかったからです。** 実装は US 番号だけを参照し、UC 番号はどこにも現れません。第 10 章で見たとおり、この題材の検査はすべて**実装に届く規則**を対象にしています。

> **検査されていない対応関係は、いずれ切れる。そして切れても誰も痛まないため、切れたことに気づかない。**

**「痛まないから気づかない」が本質です。** 痛む規則（BC の分離・テーブルの所有）は、破ると実装が壊れるので気づきます。痛まない規則は、静かに切れます。

### 2. ガイディングプリンシプル「相互運用性」が降りきらなかった

「UN/LOCODE 等の国際標準に準拠し、外部システムとの連携を容易にする」というテクノロジーアーキテクチャのプリンシプルは、ADR-006 によって**連携の相手が存在しない**状態になりました（第 1 章・第 9 章）。

**ただし、この破れ方は健全です。**

- 判断が ADR-006 として**名前で残っている**
- 採用しない技術（WebClient・WireMock）が `tech_stack.md` に**明記されている**
- `verifyProductionDependencies` が**依存の混入を検査している**
- **復帰手順が `test_strategy.md` に残されている**

プリンシプルが降りなかったこと自体より、**降りなかったことをどう記録したか**が評価点です。

### 3. 正典が空白のまま 4 イテレーション

ADR-015 が「テーブルの所有 BC の正典は `data-model.md` である」と宣言したのに、指された側が空白でした（第 7 章）。

**ADR は、他のドキュメントを正典に指名できます。指名された側が応じたかは、ADR 自身には分かりません。**

そして空白を埋めるために検査コードから書き起こした結果、**同じ誤りが 2 か所に複製**されました。

> **突合が守るのは「2 か所がずれないこと」であって「正しいこと」ではない。**

**「正典」という言葉には、内容の正しさを保証する力がありません。** 保証するのは「他と食い違ったらこちらを採る」という優先順位だけです。

### 4. 設計と実配備が別のインフラを指している

`architecture_infrastructure.md` は AWS ECS Fargate / RDS Multi-AZ / Secrets Manager を前提に設計されています。実配備は Heroku Container Runtime で、プロファイルは `dev` です（第 9 章）。

**この差は文書のどこにも明示されていません。** 設計文書を読むと AWS で動いているように読めます。

**この題材を参照する読者への注意点として最も重要です。** 動いていることが検証されているのは次だけです。

| 項目 | 検証状態 |
| :--- | :--- |
| コンテナ化・非 root 実行・ヒープ追従 | 稼働中 |
| Flyway の環境別 locations | 稼働中 |
| ArchUnit / 独自構造テスト / 品質ゲート | ローカルビルドで稼働 |
| ECS Fargate / RDS Multi-AZ / ALB / Auto Scaling / Secrets Manager | **設計のみ** |
| GitHub Actions の CI/CD | **設計のみ**（java-2 配下にワークフロー定義なし） |
| 負荷試験による p95 200ms の裏づけ | **未確認**（コンプライアンス欄に手続きのみ） |

**設計文書は「そうする」を書き、実装は「そうした」を示します。** 両者を区別する印が無いことが、この題材の構造上の弱点です。

第 10 章で見た `AdrGuardScopeTest`（ADR が言う検査が実在するかを検査する）と同じ仕組みを、インフラ設計にも適用できていれば防げた種類の乖離です。**ただし、コードから確かめられないものは検査に落とせません。** ここが検査によるガバナンスの外縁です。

### 5. 使わないテーブルが残っている

`invoice_line_item` は ADR-016 が「作らない」と決めた後も、V1 で作られたまま残っています（第 7 章）。所有の表にも載っており、**表からは「あるが使わない」ことが読めません**。

**削除しない判断は妥当です。** 問題は、使わないことが構造に現れていないことです。

## 検査によるガバナンスの限界

第 10 章は「規則を検査に落とす」を主題としました。総括として、**落とせなかったものを整理します**。

| 落とせない対象 | 例 | なぜ落とせないか |
| :--- | :--- | :--- |
| 実装に現れない対応関係 | UC 番号と US 番号 | 検査する対象がコードに無い |
| コードの外の構成 | AWS の実配備 | ビルドから観測できない |
| 内容の正しさ | `route_candidate` の所有 | 検査は一致を見るのであって正しさを見ない |
| 作られなかったもの | 未実装のユースケース | 存在しないものは検査できない |
| 業務ルールの妥当性 | 割引率の上限 30% は妥当か | 業務部門にしか判断できない |

**検査が守れるのは「決めたことが守られているか」までです。** 決めたことが正しいかは守れません。

第 7 章の `route_candidate` はこの限界の実例でした。検査は動き、正典との突合も動き、それでも 5 イテレーション誤りが残りました。**気づいたのは、その BC を実装するために人がスキーマまで遡ったときです。**

> **検査は注意力を節約する道具であって、注意力の代替ではない。**

## 4 観点で切ることの効用

最後に、本シリーズの前提そのものを評価します。

### 効いたこと

**（1）変更の波及範囲が読めるようになる。**

「荷主に法人区分を追加する」なら、ビジネス層の顧客セグメント → Shipper BC の `ShipperType` → `shipper` テーブル → 割引の ACL、と辿れます。**テクノロジー層は動きません。**

「PostgreSQL 17 に上げる」なら、テクノロジー層とデータ層の方言だけが動きます。**BC の境界は動きません。**

**（2）判断の帰属が明確になる。**

「なぜ MyBatis なのか」はテクノロジーの判断ですが、根拠は「CQRS の読み取り最適化」というアプリケーション層の要求でした。**上の層が下の層の選択理由になっている**ことが、層を分けると見えます。

**（3）降りきらなかったものが可視化される。**

「相互運用性」というプリンシプルが実装に届かなかったことは、層を分けたからこそ検出できます。1 枚の図で描いていたら、そもそも並べて比較できません。

### 効かなかったこと

**（1）層をまたぐ判断が、どの層にも属さない。**

ADR-021（同期かイベントかを「誰が動けるか」で決める）は、業務の担当者の可動域という**ビジネス層の情報**を使って、**アプリケーション層の構造**を決めています。4 観点のどこにも収まりません。

**この題材で最も価値の高い判断が、観点の分類からはみ出しています。** 層の分割は分析の道具であって、判断の枠組みではありません。

**（2）データとアプリケーションの境目が曖昧。**

CQRS の読み取り側（第 8 章）は、アプリケーションの構造なのかデータの扱いなのか判然としません。本シリーズはデータ観点に置きましたが、`BookingView` の入れ子構造はアプリケーション観点の話です。

**（3）観点を分けると、縦の繋がりを別途書く必要がある。**

本章がそれです。**分割は統合の作業を生みます。**

## 読者への引き渡し

この題材から持ち帰れるものを、立場別に整理します。

| 立場 | 参照すべき箇所 |
| :--- | :--- |
| **アーキテクチャをレビューする** | 第 10 章の検査 4 層。**「その規則は何が守っているか」を各規則に問う** |
| **DDD を実務で適用する** | 第 4 章（境界の見つけ方）・第 6 章（連携方式の判断基準）。特に ADR-010 の「同じ概念の型が 1 BC 内に 2 つ現れたら、それは境界」 |
| **CQRS を導入する** | 第 8 章。**読み書きで変更の理由が違うから分ける**という説明の仕方 |
| **設計文書を運用する** | 第 7 章（正典の空白）・第 10 章（生成物との突き合わせ）・本章（設計と実配備の差） |
| **ビジネス分析から始める** | 第 2 章（ヒートマッピングがスコープを決める）・第 3 章（ケイパビリティ階層は BC の境界を決めない） |

## 結論

**業務の能力は、条件付きで実装の構造に貫通しました。**

貫通したのは、**実装に届く形で表現された規則**です。ロールはクエリのソート順になり、業務の優先順位は整合性モデルになり、ADR は検査になりました。

貫通しなかったのは、**実装に届かない規則**です。UC 番号の対応、AWS の構成、使わないテーブルの扱い——いずれも実装が参照しないため、ずれても誰も痛まず、痛まないため気づかれませんでした。

> **アーキテクチャは、実装が参照する形に翻訳された分だけ生き残る。**

4 観点で切ることの価値は、この翻訳がどこで止まったかを見えるようにすることにあります。**止まった箇所を名前で残せるなら、層を分けた甲斐があります。**

この題材は、止まった箇所の多くを ADR とコメントに残していました。残していなかったもの（設計と実配備の差）が、そのまま本シリーズの最大の注意事項になっています。

# エンタープライズアーキテクチャの 4 観点

## 概要

本シリーズでは、国際貨物輸送管理システム（Cargo Tracker）を **ビジネス・アプリケーション・データ・テクノロジー**という 4 つのアーキテクチャ観点から解剖します。

扱うのは「どう作ったか」の時系列ではありません。**完成した構造が、上から下までどう接続されているか**です。ビジネスケイパビリティは境界づけられたコンテキストに、コンテキストはテーブルに、テーブルは検査コードに——それぞれ対応しているはずです。**本当に対応していたのか**を、一次資料と実装の両方から確かめます。

**4 観点の分割は、それ自体が主張です。** アーキテクチャを 1 枚の図で語ると、業務の話と技術の話が同じ平面に置かれ、どちらの都合で決まった構造なのかが分からなくなります。層を分けて記述すると、**各層が上の層から何を受け取り、下の層へ何を渡したか**が追跡できるようになります。

## 4 観点の定義

本シリーズでは、以下の区分で 4 観点を使います。エンタープライズアーキテクチャの一般的なフレームワーク（TOGAF の BDAT）に沿った切り方です。

| 観点 | 問い | 本シリーズでの一次資料 |
| :--- | :--- | :--- |
| **ビジネスアーキテクチャ** | 誰にどんな価値を、どの能力で届けるのか | `docs/strategy/business_architecture.md`・`docs/requirements/` |
| **アプリケーションアーキテクチャ** | その能力をどう分割し、どう連携させるのか | `docs/design/architecture_backend.md`・`docs/adr/` |
| **データアーキテクチャ** | 業務の事実をどう表現し、誰が所有するのか | `docs/design/data-model.md` |
| **テクノロジーアーキテクチャ** | 何の上で動かし、構造をどう守り続けるのか | `docs/design/tech_stack.md`・`architecture_infrastructure.md` |

## 他 4 シリーズとの関係

同じ題材で 5 本のシリーズがあります。

| シリーズ | 軸 | 問い |
| :--- | :--- | :--- |
| [モノリスアーキテクチャ実装比較](../monolith-architecture/index.md) | 言語横断 | 同じ設計方針を違うランタイムに載せると何が分かれるか |
| [関数型ドメインモデリング](../functional-domain-modeling/index.md) | 型 | 業務ルールをどこまで型に埋め込めるか |
| [実践 AI 駆動開発](../ai-driven-development/index.md) | プロセス | AI と組んだ開発で、何が品質を守ったか |
| [XP によるドメイン駆動設計の実践](../xp-domain-driven-design/index.md) | 時間 | ドメインモデルは、どのプラクティスによって育つのか |
| **エンタープライズアーキテクチャの 4 観点（本シリーズ）** | **構造** | **業務の能力は、どこまで実装の構造に貫通しているか** |

参照元は XP／AI 駆動開発シリーズと同じ実装です。**違うのは切り口だけ**で、あちらが「20 イテレーションでどう変わったか」を追うのに対し、本シリーズは**変化を止めた断面**を見ます。

一方だけを読むなら、**アーキテクチャの評価・レビューを行う立場なら本シリーズ、開発の進め方を設計する立場なら XP シリーズ**です。

## 本シリーズが扱わないこと

- **イテレーションごとの変遷**。なぜその構造になったかの経緯は XP シリーズが扱います。本シリーズは ADR を「決定の記録」として引用するにとどめます
- **他言語実装との比較**。モノリスアーキテクチャ実装比較シリーズが扱います
- **AWS 上での実運用の実績**。`architecture_infrastructure.md` は ECS Fargate / RDS を前提に設計されていますが、**参照元が実際に配備されているのは Heroku のコンテナランタイムです**。設計と実配備の差は第 9 章で明示します
- **CI パイプラインの実物**。java-2 配下に CI 定義はありません。第 10 章で扱うのは **Gradle のタスクとして実在する検査**です

## 各章の読み方

各章は「**この観点が答える問い → 一次資料が示す設計 → 実装がどう応えたか → 一致しなかった箇所**」の順で書いています。

**設計どおりに実装されている箇所より、ずれている箇所のほうが情報量があります。** 一次資料の `data-model.md` が正典と名乗りながら空白だった期間、コンテキストマップに書かれていて実装に無いポート、ADR が決めた規則が検査に落ちていなかった期間——これらは同じ比重で扱います。

# 第 12 章：ふりかえりが設計を変えた

| 項目 | 内容 |
| :--- | :--- |
| 一次資料 | `development/retrospective-1..20.md`（KPT 20 本）／`journal/` |
| プラクティス | ふりかえり |
| 主題 | M4（設計の規則は、検査に落とさなければ守られない） |

## このプラクティスが解こうとした問題

前章までに出てきた検査は、どれも**最初から存在したものではありません**。`H2DialectSmokeTest` は 3 回踏んでから、`EntityEncapsulationTest` は ADR-024 の代償として、`DelegatingAccessorRatchetTest` は 4 度目の過小記録の後にできています。

**失敗を検査に変換する場所がふりかえりです。** 参照元は 20 回すべてで KPT を行い、Try が次のイテレーションの検査になる連鎖を残しています。

## どう実践したか

### Try に由来を書く

ふりかえりの Try は、**どの Problem から出たか**を列で持っています。

| # | 内容 | 期待する効果 | 由来 |
| :--- | :--- | :--- | :--- |
| T2 | **コミットメッセージに「検査で固定した」と書くときは、その検査を実行した出力を確認してから書く** | 文章が実態を先回りしない | P1 |
| T3 | **検査の失敗メッセージに由来（ADR 番号・IT の指摘番号）を必ず入れる** | 失敗を見た人が理由に辿り着ける | クローズ前レビュー（architect）＋実測 |
| T4 | **解析失敗で行を落とすときは、必ず気づく手段を残す**（ログ or 件数） | 「件数バッジと一覧の行数が合わない」に誰も気づけない状態を作らない | クローズ前レビュー（**3 視点が独立に指摘**） |
| T5 | **正規表現で識別子を扱うときは `\p{L}` を使う**（`\w` は日本語を拾わない） | このプロジェクトの識別子は日本語を含む | P4 |

> 出典：`retrospective-17.md`

**T3 が第 10 章の検査設計に効いています。** 「検査の失敗メッセージに由来を入れる」は、検査を書いた人以外がその赤を読めるようにするための規律です。実測では「由来つきのメッセージはまばらだった」と記録されています。

T4 の「3 視点が独立に指摘」という注記も重要です。**複数の視点が同じ場所を指したという事実自体が、優先度の根拠になっています。**

### 「余力次第」を禁じる

最も繰り返し現れる学びがこれです。

> **「余力次第」にすると固定化する**という IT9 の教訓が 8 回続けて機能している。
>
> — `retrospective-13.md`

同じ学びが別のイテレーションでも記録されています。

> 返済枠 9 件を最初の 5 コミットで完済した。（中略）「余力次第」にしていたら、**ADR-008 が IT6〜IT8 で 3 回繰り越された**のと同じ形になっていた。
>
> — `retrospective-10.md`

**返済枠をイテレーション序盤の独立したコミットに固定する**という運用がここから生まれました。IT12 では「最初の 8 コミットがすべて返済枠で、US35 の着手は 9 コミット目」と記録されています。

**順序が方針です。** 「余力があれば返す」は「返さない」と同じ意味になります。

### 落とすときは名前で残す

すべてを返せるわけではありません。落とす場合は記名します。

> C9 **日程が変わった区間に印を出し、遅延例外の登録へ導く** — **計画どおり最初に落とした。** IT11 の返済枠へ送る（「余力次第」にはしない）
>
> — `retrospective-10.md`

**「落とす」と「忘れる」を分ける唯一の方法が、行き先を書くことです。** 第 7 章の ADR-024 が D5 を次のイテレーションへ送った形と同じです。

ただし、この記名も万全ではありません。

> C6 / C7 / C8 / C11 / C12 / C16。**IT9 から 2 IT 連続で繰り越している。** IT11 の返済枠で C18〜C21 と合わせて優先順位を付け直す。
>
> — `retrospective-10.md`

記名しても繰り越しは起きます。**違うのは、繰り越されていることが見えるかどうか**です。

### 何も作らないイテレーションを 2 回置く

IT16・IT17 は新規ストーリーを持ちません。整流局面（第 4 章）です。

| 項目 | IT16 の実績 |
| :--- | :--- |
| 計画 SP / 実績 SP | 0 / 0（US30 の未達分は IT15 に計上済み。**二重計上しない**） |
| 返済枠 | **C1〜C10 の 10 件すべて完了**（落としたもの 0） |
| Try | **T1〜T6 の 6 件すべて完了** |
| 新設した検査 | **8 本**（いずれも破壊検証で赤） |
| テスト | 1,410 件すべて緑（IT15 から +33） |

> 出典：`retrospective-16.md`

**SP 0 のイテレーションで検査が 8 本増えました。** 第 10 章で扱った検査の多くがこの 2 イテレーションの産物です。

「いずれも破壊検証で赤」という記録も要点です。**検査を入れたら、それを実際に壊して赤くなることを確かめています。** 入れただけの検査は、働いているかどうか分かりません。

## モデルがどう変わったか

ふりかえりがモデルに与えた影響は、次の 3 経路です。

| 経路 | 実例 |
| :--- | :--- |
| **Problem → 検査** | 方言差 3 回 → `H2DialectSmokeTest`／過小記録 4 回 → `DelegatingAccessorRatchetTest` |
| **Problem → ADR の改訂** | IT6 レビューの指摘 → ADR-009 の判断反転（第 8 章） |
| **Try → 戦略ドキュメントの必須項目** | 期限当日の時刻付き到着 → 中盤ワークフローの必須境界値ケース（第 4 章） |

**設計ドキュメントは、ふりかえりを入力として書き換わっています。** ADR-009 が改訂 1 を持ち、改訂前の記述を代替案の節に残しているのはその痕跡です。

## 働かなかったケース

### 途中レビューを 2 回連続で落とした

IT16 の Keep に、こう書かれています。

> T6（実装の途中でレビューを 1 度入れる）は **IT14・IT15 と 2 IT 連続で落としていた**。IT16 で初めて実施したところ、**IT16 自身が定めた T3 を IT16 の実装が破っている**ことが分かった。
>
> C1 で `findPendingDischarges` という新しい一覧クエリを足しながら、`QueryCounter` のテストを書いていなかった。**Javadoc には「まとめて 1 回で引く」と主張が書かれているだけだった。**
>
> — `retrospective-16.md`

**同じイテレーションが定めた規則を、そのイテレーションの実装が破っています。** しかも破り方は本シリーズが何度も見た形 — Javadoc に主張を書いて、検査を書いていない（M3）。

そして**その規則を守れているかを確かめる仕組み（途中レビュー）自体が、2 回連続で落とされていました**。

### 文章が実態を先回りする

IT17 の T2 は「コミットメッセージに『検査で固定した』と書くときは、その検査を実行した出力を確認してから書く」です。

**この Try が必要になったということは、実行していない検査について「固定した」と書いたコミットが存在した**ということです。

第 7 章で見た ADR-024 の「当初は『名前で記録した』と本文に書きながら、どこにも記録が無かった」も同型です。**記録は、書いた瞬間に事実になったように見えます。**

### 20 回続けても同じ形が出た

最終イテレーション（IT20）の品質ゲートで 20 件のテストが落ちました（第 11 章）。原因は真夜中に壊れるテストヘルパーで、**6 か所に同じ書き方が散っていました**。

> **同じ間違いを 6 回書けるなら、7 回目も書ける。**
>
> — `RecentBusinessTime.java`

**20 回ふりかえっても、同じ形の失敗は最後まで出ます。** 変わったのは、それを見つけるまでの時間と、見つけた後に検査へ落とす速度です。

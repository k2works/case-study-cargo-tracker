# XP によるドメイン駆動設計の実践

## 概要

本記事では、国際貨物輸送管理システム（Cargo Tracker）を **20 イテレーションで設計しながら作り切った実績**を、XP のプラクティスの側から記録します。

扱うのは「DDD のパターンをどう適用したか」ではありません。**ドメインモデルは、どのプラクティスによって育ったのか**です。集約や値オブジェクトが最初から正しかったわけではなく、境界も一度で決まっていません。それらを動かし続けたのは、短いイテレーション・テストファースト・リファクタリング・継続的インテグレーション・ふりかえりという XP 側の規律でした。

**DDD のパターンは、その規律が働く「場所」を与えたにすぎない** — これが本シリーズの主張です。

## 他 3 シリーズとの関係

同じ題材で 4 本のシリーズがあります。

| シリーズ | 問い |
| :--- | :--- |
| [モノリスアーキテクチャ実装比較](../monolith-architecture/index.md) | 同じ設計方針を違うランタイムに載せると何が分かれるか |
| [関数型ドメインモデリング](../functional-domain-modeling/index.md) | 業務ルールをどこまで型に埋め込めるか |
| [実践 AI 駆動開発](../ai-driven-development/index.md) | AI と組んだ開発で、何が品質を守り、何が守らなかったか |
| **XP によるドメイン駆動設計の実践（本シリーズ）** | **ドメインモデルは、どのプラクティスによって育つのか** |

参照元の実装は [実践 AI 駆動開発](../ai-driven-development/index.md) と同じ `java/take-6` です。違うのは軸で、あちらが**誰が書いたか**（開発者 1 名＋ AI エージェント）を扱うのに対し、本シリーズは**どういう規律で書いたか**を扱います。開発者が AI であっても人であっても同じように働くプラクティスだけを追うため、Skill 体系や自律実行の話は出てきません。

**同じ事実が両シリーズに出てきます。** ADR-009 の 7 イテレーションの空白、委譲アクセサ 249 個、SP 0 の整流イテレーション — これらは重複ですが、扱いが違います。

| 事実 | 本シリーズでの扱い | AI 駆動開発シリーズでの扱い |
| :--- | :--- | :--- |
| ADR-009 が守られなかった | **設計判断がどう検査になったか** | なぜ AI だと文章が実態を先回りするか |
| 委譲アクセサ 249 個 | **負債をラチェットで凍結する判断** | 記録が実態より小さくなる頻度 |
| 整流イテレーション | **設計を腐らせないコスト** | ストーリーを書かない回を置く判断 |

どちらか一方だけ読むなら、**XP プラクティスの導入を検討しているなら本シリーズ、AI エージェントの導入可否を判断するなら AI 駆動開発シリーズ**です。

## この実績で検証できたこと、できなかったこと

**体制は開発者 1 名（＋ AI エージェント）です。** XP のプラクティスのうち、複数人を前提とするものはこの実績では検証されていません。第 1 章で示す拡張サークルオブライフの図には全プラクティスが並びますが、**本シリーズが根拠を持って語れるのはその一部です**。

| プラクティス | 本実績での扱い |
| :--- | :--- |
| テスト駆動開発／リファクタリング／シンプルな設計 | **検証済み**。第 2 部の中心 |
| 継続的インテグレーション | **検証済み**。第 11 章 |
| 小さなリリース／計画ゲーム | **検証済み**。6 リリース・ベロシティ実測（第 3 章） |
| ふりかえり | **検証済み**。KPT 20 回（第 12 章） |
| 受入テスト | **検証済み**（第 5 章） |
| **メタファー** | **未検証。** 一次資料にシステムメタファーの選定記録が無い |
| **ペアリング** | **未検証。** 1 名体制であり、代替として複数視点のレビューを回した |
| **共同所有** | **部分的。** コードの所有者が 1 名なので、争点が生じない |
| **オンサイト顧客** | **未検証。** 業務判断は要件ドキュメントと参考実装（Eclipse Cargo Tracker）から導いており、実在の業務部門に確認していない |
| **持続可能なペース** | **未検証。** 8 日で 20 イテレーションであり、人間のチームの持続性は測れていない |

**業務ルールの正しさをどう担保したかは、本シリーズの弱点です。** 「国連分類に 3.9 は存在しない」（第 6 章）のような判断は公開情報から導けますが、**業務部門に確認したわけではありません**。オンサイト顧客が実在する現場では、この部分の難しさが本シリーズの記述とは別物になります。

前提が違う読者向けの読み替えは、[第 13 章](13-conclusion.md) にまとめています。

## 通底する 5 つの主題

20 回分の計画・ふりかえり・ADR を「設計判断がいつ、何をきっかけに変わったか」という視点で通読すると、同じ形が繰り返し現れます。各章はこの 5 つのいずれかに帰着します。

| # | 主題 | 実際に起きたこと |
| :--- | :--- | :--- |
| M1 | **ドメインモデルは設計されるのではなく、イテレーションで育つ** | 7 つの BC は一度に立たなかった。Handling は ADR-010 で後から独立し、最後の Estimation が本格的に立ち上がったのは IT18 |
| M2 | **境界は最初から正しくない。動かして初めてずれが見える** | 共有カーネルを 2 要素に限定する判断も、BC 横断イベントも、越境の痛みが出てから決まった |
| M3 | **ユビキタス言語は、放っておくと実装から離れる** | 対訳表・Javadoc・遷移表が仕様を語り、実装が守っていない状態が繰り返し検出された |
| M4 | **設計の規則は、検査に落とさなければ守られない** | ADR-009 は 7 イテレーションのあいだ半分しか守られず、違反が 5 本増えていた |
| M5 | **リファクタリングの余地は、テストの厚みでしか買えない** | ドメインモデルの分割は、テスト 1,500 件超と ArchUnit の契約があって初めて実行できた |

## 各章の読み方

第 1 部・第 3 部は「このプラクティスが解こうとした問題 → どう実践したか → モデルがどう変わったか → 働かなかったケース」の順で書いています。

第 2 部はコード中心です。第 5・6 章は新しくモデルを作る話なので「扱う業務ルール → テストから始める → モデルに落とす → 後から効いた／効かなかった」、第 7・8 章は既にあるモデルを改変する話なので「扱う問題 → 何をしたか → 後から効いた／効かなかった」の順になります。

**うまくいった話だけを書きません。** 効かなかったプラクティス、降りきらなかった設計、3 イテレーション繰り越された返済枠も同じ比重で扱います。

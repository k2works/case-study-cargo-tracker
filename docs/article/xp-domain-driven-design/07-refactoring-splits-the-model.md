# 第 7 章：リファクタリングでモデルが割れる

| 項目 | 内容 |
| :--- | :--- |
| 対象 IT | IT19（分割）／IT20（代償の返済） |
| 対象 ADR | ADR-024（ドメインモデルを構成要素ごとのパッケージに分ける） |
| プラクティス | リファクタリング、シンプルな設計、テスト駆動開発 |
| 主題 | M5（リファクタリングの余地は、テストの厚みでしか買えない） |

## 扱う問題

19 イテレーション目の時点で、各 BC の `domain/model` は 1 つのパッケージにすべてを入れていました。実測 **140 クラス**、最大の Booking は **35 クラスが 1 階層**に並んでいます。

> パッケージを開いたとき、**どれが集約ルートでどれが値オブジェクトなのかは、クラスを開くまで分からない**。JIG のパッケージ図でも 1 つの箱になり、構成要素の別が読み取れない。
>
> — `adr/024-*.md`

これは動作の問題ではありません。テストは 1,500 件超が緑で、業務も正しく回っています。**読めないだけ**です。

**読めないだけの問題に手を入れられるかどうかが、テストの厚みで決まります。**

## 分割する

決定は単純です。

| サブパッケージ | 入れるもの |
| :--- | :--- |
| `aggregates` | 集約ルート |
| `entities` | 集約の内側で同一性を持つもの |
| `valueobjects` | 値オブジェクト・列挙・**識別子** |
| `commands` | 業務の要求を 1 つの型にまとめたもの（**該当が無ければ作らない**） |

> 出典：`adr/024-*.md`

得たものも記録されています。

- パッケージを開いた時点で構成要素が分かる
- JIG の用語集に構成要素ごとの説明が載る（27 パッケージ分）
- **集約ルートの数が目に見える。** Booking 3・Handling 3・Routing 2・Billing 2、他は 1 — 多いことがひと目で分かる

ただしこの 3 点は、最初の分類のままでは得られませんでした。

> クローズ前レビューで「識別子を `aggregates` に同居させたせいでルート数が読めない」「`entities` の 8 件中 6 件が record（＝同一性を持たない）」と指摘され、**同じイテレーションの中で分類を直した**。
>
> — `adr/024-*.md`

**参照実装に倣った分類が、この題材では目的を壊していました。** 参照実装は `BookingId` を `aggregates` に置いていますが、そのとおりにすると「集約ルートの数が目に見える」という得たかったものが最初の 1 回で消えます。**倣うべきは分類ではなく、分類の目的だった**ということです。

直した結果、`entities` に残ったのは `ProposedRoute` と `TrackingExceptionEvent` の **2 つだけ**になりました。

## 失ったもの

ADR の「失ったもの」節が本章の核心です。

> **パッケージプライベートで守っていた境界が壊れた。**
>
> 分割前、集約の内側だけに開いていた操作は「同じパッケージにいること」で守られていた。javac が越境を止めていたのである。サブパッケージに分けると同じパッケージではなくなるため、**メソッドを `public` にせざるを得なくなった**。

| クラス | 開いた操作 | 本来呼んでよいもの | javac は止めていたか |
| :--- | :--- | :--- | :--- |
| `ProposedRoute` | `of` / `withPriority` | `RouteSearchService` | **止めていた**（class） |
| `TrackingExceptionEvent` | `raise` / `resolve` | 集約ルート（`TrackingActivity`） | **止めていた**（class） |
| `CargoProgress` | `withStatus` / `withRouting` / `issued` | 集約ルート（`Cargo`） | 止めていない（record） |
| `NotificationDelivery` | `succeeded` | 集約ルート（`BookingNotification`） | 止めていない（record） |

> 出典：`adr/024-*.md`

**実費は 4 メソッドです。** 当初この ADR は「7 メソッドを公開した」と書いていましたが、レビューで後半 2 クラスは `record` であり正準コンストラクタが元から公開されていることが判明しました。`new CargoProgress(...)` は分割前から誰でも書けたのであり、**そこに javac の保証は最初から無かった**。

> **残る 4 メソッドについては、コンパイラによる保証をコメントによる約束へ格下げしたということである。** 各メソッドには「呼んでよいのは誰か」を書いたが、**書いてあることと守られていることは別である**。

**この一文が本シリーズの M4 そのものです。** ADR は自分が作った穴を、自分で名指ししています。

さらに ADR は、その記名すら最初は無かったことまで書いています。

> **この記名も、レビューで指摘されるまで存在しなかった。** 当初は「名前で記録した」と本文に書きながら、**どこにも記録が無かった**。ADR 自身が戒めている形をその ADR が踏んでいた。

## 代償を検査で返す

IT19 は代償を返さず、次のイテレーションへ **D5** として実測付きで送りました。IT20 で `EntityEncapsulationTest` が入ります。

```java
/**
 * <strong>{@code entities} の生成・変更メソッドを、呼んでよい相手だけが呼んでいること</strong>
 * （ADR-024 の代償を返す検査。IT20 / D5）。
 *
 * <p><strong>「集約ルート以外は呼べない」と一般化して書かない。</strong> そう書くと
 * {@code ProposedRoute.of} を集約ルートへ移すことになり、探索と提案の分離が壊れる
 * （{@code of} の 6 引数はすべて探索の途中でしか作れない）。ADR-024 が定めているのは
 * <strong>メソッドごとに相手を書き分けた表</strong>であり、規則を一般化することは
 * 規則の書き換えである。
 */
```

> 出典：`apps/.../test/.../EntityEncapsulationTest.java`

**「（型・メソッド・呼んでよい相手）の 3 つ組」で契約を書く**というのがこの検査の形です。「集約ルート以外は呼べない」という一般的で書きやすい規則を**あえて採らなかった**理由が、Javadoc に業務の言葉で残っています。

型名だけで判定しないことも明記されています。`raise` や `resolve` は他の型にも存在し、`ExceptionOccurrence.raise` は値オブジェクトです。**規則を広げると、守るべきでないものまで巻き込みます。**

## 後から効いた／効かなかった

### 効いた：分割が別の負債の返済を強制した

`Cargo` は分割に伴う import の増加で **500 行**（Checkstyle の `FileLength` 上限）を超え、赤になりました。

> **IT15 から 4 イテレーション持ち越していた D1**（「次に `Cargo` を触る IT で引取まわりを切り出す」）をここで返し、`claimCode` / `consignee` / `claimedAt` を `CargoClaim` にまとめた（498 行）。
>
> — `adr/024-*.md`

**上限は「いつか直す」を「今直す」に変える装置です。** 4 イテレーション繰り越されていた返済が、行数上限に触れた瞬間に実行されました。現在の `Cargo` は 485 行 — **猶予は 15 行**です。

### 効いた：分割で無効化されたルールが 1 本あった

> 共有カーネルの検査。対象を `shared.domain.model` から `shared.domain.model..` に広げた（**サブパッケージへ移した瞬間、ルールは「何も検査していない」状態になった**。`allowEmptyShould(true)` を使っていなければ、これは赤で気づける）
>
> — `adr/024-*.md`

**構造を変えると、構造を検査するルールの対象が消えます。** 対象が 0 件になった検査は、違反 0 件と区別がつきません。これは第 10 章で扱う「検査そのものを検査する」動機の一つです。

### 効かなかった：やらなくてよかった可能性

ADR は代替案の節で、自ら次のように書いています。

> 分類を直した結果、`entities` に残るのは 2 クラスだけになった。**この案を採っていれば実費は 0 だった**ことになる。次に同じ判断をする人は、まずこの 2 クラスを見てほしい。

`entities` を作らず集約ルートと同じパッケージに置いていれば、4 メソッドの公開も `EntityEncapsulationTest` も不要でした。**結果から見れば、参照実装への追従が 1 イテレーション分の代償を生んでいます。**

この記録が残っていること自体が、この ADR の価値です。

# 第 13 章：XP は DDD に何を与えたか

| 項目 | 内容 |
| :--- | :--- |
| 対象 | 全 20 イテレーション |
| 実績 | 7 BC ＋共有カーネル／テスト 1,578 件（＋ E2E 21 件）／ADR 25 件／v2.1.0 出荷済み |
| 主題 | 5 主題すべての決算 |

## 何が効いたか

### 短いイテレーションが、境界を動かす機会を作った

7 つの BC のうち、**最初の設計どおりだったものは一つもありません**。Handling は Tracking から独立し、共有カーネルは設計ドキュメント間で食い違ったまま始まり、BC 間の連携は同期から結果整合に反転しました。

これらはすべて「動かしてみて分かった」ことです（M2）。そして**動かす機会が 20 回あったから、20 回分の修正が入りました**。

| 判断 | いつ変わったか | きっかけ |
| :--- | :--- | :--- |
| 共有カーネルを 2 要素に限定 | IT1 | 設計ドキュメント間の食い違い |
| Handling を独立 BC に | IT6（ADR-010） | 実装したら同一 BC 内に対応する型が 3 組でき、言語が分岐していた |
| BC 間連携を結果整合に反転 | IT6（ADR-009 改訂 1） | 一気通貫を実装したら 3 集約が 1 トランザクションになった |
| ドメインモデルを building block で分割 | IT19（ADR-024） | 140 クラスが平らに並んで読めない |

**最後の 1 件が IT19 であることに注目してください。** 20 回のうち 19 回目で、まだモデルの構造が変わっています。

### テストの厚みが、リファクタリングの余地を買った

ADR-024 のパッケージ分割は、**140 クラスを動かす作業**でした。テスト 1,500 件超と ArchUnit の構造検査がなければ、この規模の移動は「動作を確かめられない変更」になります。

**リファクタリングの余地は、テストの厚みでしか買えません**（M5）。逆に言えば、テストを厚くしておかないと、読めないコードは読めないまま残ります。

### 規則を検査に落とした分だけが守られた

これが最も明快な結論です。

| 規則 | 検査 | 結果 |
| :--- | :--- | :--- |
| ADR-009 規則 2（新トランザクションで購読） | IT15 まで無し | **7 IT のあいだ半分だけ守られ、違反が 5 本増えた** |
| ADR-015（テーブルの所有 BC） | `MapperTableOwnershipTest` | 正典の表を読む形にして、片方だけ直すと赤 |
| ADR-022（読み側の規則の置き場） | `ReadSideRuleLocationTest` | しきい値比較を代理指標に |
| ADR-024（3 つ組の契約） | `EntityEncapsulationTest` | 一般化せず、表のまま検査 |

そして**検査を書くたびに、実数は指摘より多いことが分かりました**。

| 対象 | 指摘 | 実測 |
| :--- | ---: | ---: |
| BC をまたぐ SQL | 2 本 | **9 本** |
| ADR-009 規則 2 の違反 | 1 本 | **6 本** |
| 委譲アクセサ | 34 個 | **249 個** |

### ふりかえりが、失敗を検査に変換した

3 回踏んだ方言差、4 度目の過小記録、2 回連続で落とした途中レビュー — **繰り返しの検出がふりかえりの主な機能でした**。SP 0 のイテレーションを 4 回置いたのは、この変換に時間を確保した結果です。

## 何が効かなかったか

### 書いただけの規律

ADR・Javadoc・遷移表・コミットメッセージ — **文章はすべて「守った気になる」ための道具として機能しました**。

最も鋭い実例は、ADR-024 が自分自身について書いた一節です。

> **この記名も、レビューで指摘されるまで存在しなかった。** 当初は「名前で記録した」と本文に書きながら、**どこにも記録が無かった**。ADR 自身が戒めている形をその ADR が踏んでいた。

### 可視化

JIG は設計と実装の対を作りましたが、**乖離を赤くはしません**。`jigErd` に至っては CI から除外されており、実行するかどうかは人に委ねられています。

**見えるようにすることと、見ることは別です。**

### 検査の外に残った 13 件

IT16 の棚卸しで、ADR 19 件のうち**13 件が「守らない」に該当**しました。「イベントは命令ではなく事実を運ぶ」のような命名の規律は、機械では判定できません。

> 書けない検査を書いたふりをするより、**どこが人の注意に預けられているかを残す**ほうが安全である。
>
> — `retrospective-16.md` K4

**これは失敗ではなく限界の記録です。** ただし「人の注意に預けた」ものは、20 イテレーションのあいだ繰り返し破られました。

### 検査の運用ルールが、検査になっていなかった

**ラチェットの上限は 2 回引き上げられています。** 委譲アクセサの上限は 249 → **210**（IT18）→ **213**（IT19）→ **214**（IT20）と推移しました。

引き上げた理由は「負債が増えたから」ではありません。

> `Cargo` の引取まわりを `CargoClaim` へ切り出した結果、集約の外向き API がその 3 つへの委譲になった。**この 3 つは畳まない。** ここで止めているのは「レコードを分けるたびに増えるテンプレート互換の層」であり、**集約の入口を保つための委譲は別のものである**。
>
> — `DelegatingAccessorRatchetTest.java`

**数を数える検査は、数えている対象の意味を区別できません。** だから「上限を上げてよい条件」という運用ルールが要ります。それは Javadoc に書かれました。

そして IT20 のクローズ前レビューが、こう指摘しています。

> **ラチェット上限を上げた理由がコメントだけで検査になっていない**
>
> — `review/IT20クローズ_review_...md`

**検査の運用ルールが、検査になっていませんでした。** 20 回目にして、この記事の主題そのものが検査自身に跳ね返っています。

**それでも、緩めた記録は残り、レビューが追及しました。** 検査を消した記録は 0 件、緩めた記録は 2 件でいずれも理由つき — この対比が、規律が働いていたことの証拠です。

## イテレーションで育てられたもの、最初に決めるしかなかったもの

| 対象 | 進め方 | なぜ |
| :--- | :--- | :--- |
| 集約・値オブジェクト | **育てた** | テストがあれば作り直せる |
| BC の境界と越え方 | **育てた** | 越境の痛みが出るまで正しさが分からない |
| ユビキタス言語 | **育てた**（が、放っておくと離れた） | 業務の理解が進むと語彙が変わる |
| データモデル | **最初に全体を作った** | データが載ると移行コストが跳ね上がる |
| アーキテクチャの層構成 | **最初に決めた** | 全 BC が同じ形であることに価値がある |

**「変更コストが高いものを先に決める」というのが、この仕分けの唯一の基準です。** DDD のどのパターンを使うかではありません。

データモデルを先に作っても、初期スキーマは正しくありませんでした（`ALTER` 109 文）。**違うのは、間違いをどこで吸収するかです。**

## 残った未達

| 項目 | 状態 |
| :--- | :--- |
| `Cargo` の行数 | 485 行（上限 500）。**猶予 15 行**。第 7 章の「上限が返済を強制した」仕組みが、次の返済を待っている状態 |
| ADR の 13 件 | 検査の外。人の注意に預けたまま |
| `jigErd` | CI から除外。設計と実装の突合は手作業 |
| `domain-model.md` の BC 件数 | 本文が「6 つ」のまま（実際は 7 つ） |
| 委譲アクセサ | 上限で固定（ラチェット）。249 → 210 まで返したが、その後 214 まで戻した（理由つき） |

**最後の項目が象徴的です。** 249 個のうち返したのは 39 個で、残りは「増やすと落ちる」という形で凍結されています。返済ではなく**悪化の停止**であり、しかもその上限は 2 回引き上げられました（上記）。

## いくらかかったか

規律にはコストがあります。本実績で測れる範囲を示します。

| 項目 | 実績 |
| :--- | :--- |
| 規律のために止めた開発 | **20 イテレーション中 4 回**（IT16・IT17 の整流、IT19・IT20 の出荷と是正）。いずれも目標 SP 0 — **機能開発の 5 分の 1 を規律に充てた** |
| その 4 回で得たもの | 整流の 2 回で検査 **8 本**・返済枠 10 件・Try 6 件。出荷と是正の 2 回で ADR-024 の代償の返済（`EntityEncapsulationTest`）と `PackageInfoPresenceTest`・`ReadSideRuleLocationTest` |
| 検査 1 本の分量 | ArchUnit で書けるものは数十行。ドキュメントを読む検査（`DataModelDocumentSchemaTest`）はパーサを含めて 150 行程度 |
| 検査に落ちなかった規則 | IT16 の棚卸しで、**19 件中 13 件が「守らない」**（規則単位。ADR 単位ではない） |

**「機能開発の 5 分の 1 を止めて、規則の空白を埋めた」** — これがコストの言い方です。

そして**因果は逆から見るほうが明確です**。記事が詳しく扱った検査は、`MapperTableOwnershipTest` の正典突合が IT17、`PackageInfoPresenceTest` と `ReadSideRuleLocationTest` が IT19、`EntityEncapsulationTest` が IT20 — **すべて止めた回の産物**です。**止めていない 16 回で新設された検査は、ごく少ない。**

**逆に言えば、止めなければ埋まりませんでした。** 「余力次第」の返済枠は 3 イテレーション連続で繰り越されています（第 12 章）。

## 明日から試すなら

本シリーズの記録から導ける導入順序です。**検査を一気に入れることは勧めません。** 参照元も 15 イテレーションかけて少しずつ増やしています。

| 段階 | やること | 根拠 |
| :--- | :--- | :--- |
| 1. 棚卸し | 既存の ADR・設計ドキュメントに「守り手」列を足す。検査が無いものは**「守らない」と書く** | IT16 の実績。19 件中 13 件が「守らない」だった。**まず空白の量を知る** |
| 2. 1 本だけ検査にする | 最もよく破られている規則を 1 つ選び、検査にする。**入れたら実際に壊して赤を確認する** | ADR-009 は検査を書いた瞬間、指摘 1 本に対し実測 6 本が出た |
| 3. 悪化を止める | 返せない負債はラチェットにする（現在値を上限に固定。減らすのは自由、増やすと落ちる）。**上限は必ず機械で数え直した実測値にする** — 記録された件数を使ってはいけない | 委譲アクセサは記録 34 個に対し**実測 249 個**（過小記録は 4 度目）。返したのは 39 個で、残りは凍結 |
| 4. 順序を固定する | 返済枠をイテレーション**序盤の独立コミット**に置く。「余力次第」と書かない | 「余力次第」にした ADR-008 は 3 イテレーション繰り越された |

**1 と 2 だけなら 1 スプリントで試せます。** 効果の判定は簡単で、**指摘した件数と検査が出した件数が一致するかどうか**を見ます。一致しなければ、目視は少なく数えていたということです。

### レガシーへの適用

本実績はグリーンフィールドですが、**ラチェット（段階 3）は既存システムのための道具です。** 検査を後から入れると初日に数百件が赤になりますが、ラチェットなら現在値を上限にして「これ以上増やさない」だけを守れます。参照元も 249 個を返しきれず、この形で凍結しました。

**既存システムでは、段階 3 から始めて 2 へ戻るのが現実的です。**

## 前提が違うとき

本実績の前提は「開発者 1 名＋ AI・8 日・20 イテレーション・グリーンフィールド」です。読者の状況との差をどう読み替えるかを示します。

| 前提の違い | 何が変わるか |
| :--- | :--- |
| **イテレーションが長い**（2 週間×20 回＝10 か月） | 本シリーズの結論（規則は検査に落とせ）は**速度に依存しません**。ただし**空白の危険度は暦ではなく、その間に入った変更の量で決まります**。ADR-009 の違反 5 本は「7 日」ではなく「**7 イテレーション分の変更**」で増えました。イテレーションが長いほど 1 回あたりの変更量が大きいため、同じ「7 回ぶんの空白」はより多くの違反を抱えます |
| 人数が多い | **本実績では検証できていません。** 1 名体制では共同所有もペアリングも争点が生じません。ただし「書いたことと守られていることは別」は人数が増えるほど強く出るはずです |
| 既存システムがある | ラチェットから始める（上記）。**データモデルを先に全体設計する話は適用外です** |
| 業務が未知 | **データモデルを最初に全部作る判断は真似しないでください。** 本実績は Eclipse Cargo Tracker という参考実装があり、業務が既知でした。その条件が無いなら、スキーマも育てるしかありません |

## 次に同じ題材をやるなら

| 変える点 | 理由 |
| :--- | :--- |
| ADR を起票した同じ変更で検査を書く | 「後で検査を足す」は 7 IT の空白を生んだ |
| 検査対象が 0 件になったことを検出する | 構造変更はルールを静かに無効化する |
| `entities` パッケージを作らない | ADR-024 が自ら「この案を採っていれば実費は 0 だった」と書いている |
| 途中レビューを DoD に含める | 2 IT 連続で落とされた |

## 結論

**DDD は設計の語彙を与え、XP はそれを動かす力を与えました。**

境界づけられたコンテキストという概念があったから、Handling を独立させるという判断が言葉になりました。しかしその判断を引き起こしたのは、一気通貫を実装したという XP 側の出来事です。集約という概念があったから `Cargo` の責務を問えましたが、問う契機を作ったのは Checkstyle の 500 行という機械的な上限でした。

**どちらか一方では足りません。** 語彙だけあれば設計は美しく書けますが、書いたものが守られているかは分かりません。規律だけあれば動き続けますが、何を作っているかを言葉にできません。

そして本シリーズが 20 回の記録から取り出した最も実用的な一文は、これです。

**規則は、検査に落とさなければ守られない。** 落とせないものがあるなら、落とせないと書く。

# 第 6 章：値オブジェクトと不変条件

| 項目 | 内容 |
| :--- | :--- |
| 対象 US | US05（危険物・冷凍貨物の予約を登録する） |
| 対象 UC | UC03（貨物予約を登録する） |
| プラクティス | シンプルな設計、テスト駆動開発 |
| 主題 | M3（ユビキタス言語は、放っておくと実装から離れる） |

## 扱う業務ルール

危険物を輸送するには、危険物クラス・UN 番号・正式輸送品名の 3 項目が要ります。この 3 つは輸送書類にそのまま載り、**内容が誤っていれば積み込みを拒否され、税関で止まります**。

素直に実装すると、これは「入力フォームの必須チェック」になります。3 項目が空でなければ通す、というバリデーションです。実際に多くのシステムがそう作られています。

**参照元はこれを画面ではなく値オブジェクトに置きました。** その判断の中身が本章の主題です。

## テストから始める

危険物申告の受入基準は「危険物を選択した場合、危険物情報の入力が必須である」です。ここから素直に書ける Red は 2 種類しかありません — 3 項目が揃っていれば通る、欠けていれば落ちる。

しかし業務側の問いはもう一段あります。**「入っている」ことは「申告になっている」ことか？**

危険物クラス `3.9` は形としては正しく見えます。数字・ドット・数字であり、正規表現 `\d(\.\d)?` を通ります。**しかし国連分類に 3.9 は存在しません。** 存在しないクラスを書いた輸送書類は、申告が無いのと同じ結果になります。

この問いを立てた瞬間、テストは形式検証ではなく**実在検証**に変わります。

## モデルに落とす

```java
/**
 * 危険物申告（US05）。
 *
 * <p><strong>3 項目そろって初めて申告である。</strong> どれか 1 つでも欠けると
 * 法的要件を満たさず、**申告の無い危険物を預かった**のと変わらない。
 * 部分的に入った状態を作らせないため、値オブジェクトとしてひと組で持つ。
 *
 * <p><strong>「入っている」だけでは申告にならない。</strong> 危険物クラスと UN 番号は
 * 輸送書類にそのまま載る。存在しないクラスや桁の欠けた番号を書いた書類は、
 * <strong>申告が無いのと同じ結果</strong>（積み込み拒否・税関で止まる）になる。
 */
public record HazardousDeclaration(
        String hazardClass, String unNumber, String properShippingName) {
```

> 出典：`booking/domain/model/valueobjects/HazardousDeclaration.java`

3 項目を 1 つの型でひと組にしたのは、**部分的に入った状態を作らせない**ためです。個別のフィールドとして `Cargo` に持たせると「クラスだけ入っていて UN 番号が空」という状態が表現可能になります。表現可能な状態は、いつか作られます。

検証の中身が判断の記録になっています。

```java
/**
 * 国連分類のクラスと区分（実在するものだけ）。
 *
 * <p><strong>正規表現で「数字.数字」を通さない。</strong> {@code 3.9} は形は
 * それらしいが存在しない。<strong>存在しないクラスを書いた輸送書類は、
 * 申告が無いのと同じ結果になる。</strong>
 */
private static final java.util.Set<String> HAZARD_CLASSES = java.util.Set.of(
        "1", "1.1", "1.2", "1.3", "1.4", "1.5", "1.6",
        "2", "2.1", "2.2", "2.3",
        "3",
        "4", "4.1", "4.2", "4.3",
        "5", "5.1", "5.2",
        "6", "6.1", "6.2",
        "7", "8", "9");

/** UN 番号は {@code UN} ＋ 4 桁。**桁が欠けた番号は別の物質を指す。** */
private static final java.util.regex.Pattern UN_NUMBER =
        java.util.regex.Pattern.compile("UN\\d{4}");
```

> 出典：同上

**名簿方式（実在するものだけを列挙）と正規表現（形だけを見る）を使い分けています。** 危険物クラスは有限の実在集合なので名簿、UN 番号は 4 桁の任意の数字なので正規表現です。「桁が欠けた番号は別の物質を指す」という一文が、**なぜ長さを検証するのか**を業務の言葉で説明しています。

一方で、拒まないものも明示されています。

```java
// **小文字は拒まない。** 入力の揺れであって、別の物質を指すわけではない
unNumber = unNumber.toUpperCase(java.util.Locale.ROOT);
```

> 出典：同上

**「拒む／拒まない」を分ける基準は「結果が変わるか」です。** `un1263` と `UN1263` は同じ物質を指すので正規化して通す。`UN126` は別の物質を指すので拒む。この基準はコードの形からは読み取れないため、コメントとして残っています。

## もう一つの例：金額

第 4 章で、精算局面をインサイドアウトで進めた理由をこう引きました。

> **丸めと割引の規則は画面から下ろすと必ず表示都合が混ざる。**

その規則が置かれたのが `Money` です。Javadoc が仕様表そのものになっています。

```java
/**
 * 請求で扱う金額（US21。{@code domain-model.md}「金額の丸め規則」）。
 *
 * <p><strong>金額計算は法的・会計的な争いの対象になりうる。</strong> 丸めの規則と
 * 適用順序を仕様として固定する。順序が決まっていないと、
 * <strong>同じ入力でも実装者によって請求額が変わる</strong>。
 *
 * <table>
 *   <caption>丸め規則</caption>
 *   <tr><td>丸めモード</td><td>切り捨て（{@link RoundingMode#DOWN}）。
 *       <strong>荷主に不利な方向へ丸めない</strong></td></tr>
 *   <tr><td>丸めの単位</td><td>通貨の最小単位。<strong>最小通貨単位の整数で保持する</strong></td></tr>
 *   <tr><td>適用箇所</td><td>基本料金・割引後料金・消費税額の<strong>それぞれで丸める</strong>
 *       （段階丸め）。総額での一括丸めは行わない</td></tr>
 *   <tr><td>中間計算</td><td>丸める直前まで {@code BigDecimal} で保持する。
 *       {@code double} を使わない</td></tr>
 * </table>
 */
```

> 出典：`billing/domain/model/valueobjects/Money.java`

**「切り捨て」を選んだ理由が、技術ではなく立場で書かれています** — 「荷主に不利な方向へ丸めない」。丸めモードは技術的にはどれでも実装できますが、**誰が損をするかは業務の判断**です。

「それぞれで丸める（段階丸め）／総額での一括丸めは行わない」も同様です。どちらも実装可能で、結果が数円違います。**決めていなければ、実装者ごとに違う請求額になります。**

型を分けた理由も明記されています。

> **Routing の `Money` とは別の型である。** 概算費用（ADR-008）は経路候補の並べ替え用であり、請求額ではない。

**同じ「金額」でも、並べ替えの材料と請求額は別のものです。** BC をまたいで型を共有すると、経路探索の都合が請求に混ざります。第 8 章の共有カーネルを 2 要素に限定した判断と同じ形が、ここにも出ています。

## 後から効いた／効かなかった

### 効いた：不変条件をコンストラクタに置いたこと

`record` のコンパクトコンストラクタで検証しているため、**`HazardousDeclaration` 型の値が存在するなら、それは必ず妥当な申告です**。画面のバリデーションと違い、テストコードからも、DB からの復元経路からも迂回できません。

第 5 章で見た「受入テストは仕様の下限を守る道具であり、上限を決める道具ではない」の上限側が、ここに置かれています。

### 効いた：集約に置いた不変条件は画面をまたいで働く

同型の判断が経路割当にもあります。経路を割り当てるとき、**旅程の端点が予約の出発地・目的地と一致していること**、**到着予定が到着期限を超えていないこと**を確かめる必要があります。これを画面（コントローラ）に置くと、別の入口から同じ操作をしたときに素通りします。

参照元はこれを集約のメソッドに持たせています。**定義済みなのに呼ばれていないドメインメソッドは、配線漏れのサイン**でもあります。

### 効かなかった：Javadoc に書いた不変条件は守られない

同じ Javadoc が仕様を語っていても、それが検査されるとは限りません。IT15 のふりかえりには、遷移表・ADR・所有表の 3 か所で「**書いたことと、していることが別**」という同型の欠陥が同時に見つかった記録があります。

**この章のコード例が守られているのは、コンストラクタという実行される場所に書かれているからです。** 同じ内容を Javadoc にだけ書いていたら、守られていたかどうかは分かりません。「書いた場所が実行されるか」という基準は、第 10 章で ADR 全体に適用されます。

### 効かなかった：「多通貨対応」と書いてあるが、対応していなかった

`Money` は通貨を持ち、異なる通貨どうしの演算を `requireSameCurrency` で拒みます。設計ドキュメントには「多通貨対応」と書かれていました。**しかし実態は違いました。**

ADR-025（IT20）が、数え方まで含めて実測を残しています。

| 対象 | 実測 |
| :--- | ---: |
| `domain-model.md` の「多通貨対応」の記述 | **1 か所** |
| DB の通貨列（相異なる列名） | **9 個** |
| 通貨を跨ぐ演算の扱い | `requireSameCurrency` で**拒む**だけ |

> **「多通貨対応」と書いてあるが、対応してはいない。** 実装がしているのは「異なる通貨どうしの足し算・引き算を例外で止める」ことだけであり、**換算レートも、レートの有効期間も、表示通貨の選択も存在しない**。
>
> **この状態は「多通貨を保留している」のではなく、「単一通貨で動いている」。** 記述だけが別のことを言っている。
>
> — `adr/025-*.md`

しかも保留の判断自体が置き去りにされていました。スコープ定義は多通貨を「Release 2.0 の料金設計時に判断する」としていましたが、**Release 2.0 も 2.1 も出荷済み**です。判断されないまま 2 リリースが過ぎていました。

**通貨を持つ型を作ったことが、多通貨に対応したように見せていました。** 型は表現を守りますが、**機能があることの証拠にはなりません**。IT20 でこれを「単一通貨（JPY）で確定する」と決め直しています。

### 効かなかった：DATE と TIMESTAMP の境界

到着期限は日付（DATE）、到着予定は時刻付き（TIMESTAMP）で持っています。素朴に `isAfter` で比較すると、**期限当日の 14 時に着く便が「期限超過」として弾かれます**。値オブジェクトの中で型が揃っていても、**業務上の意味の粒度が違えば比較は誤ります**。

対処は日付単位での比較と、テストに「当日の時刻付き到着」を含めることでした。**型が守るのは表現であって、意味ではない** — 関数型ドメインモデリングシリーズが扱う「型に埋め込む」手法の境界がここにあります。

次章では、この値オブジェクトたちを抱えた `Cargo` が上限に達し、モデルが割れるまでを扱います。

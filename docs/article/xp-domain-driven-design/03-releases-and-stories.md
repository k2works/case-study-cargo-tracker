# 第 3 章：小さなリリースとイテレーション計画

| 項目 | 内容 |
| :--- | :--- |
| 一次資料 | `requirements/`（RDRA・UC・US）／`development/release_plan.md`／`iteration_plan-1..20.md` |
| プラクティス | 計画ゲーム、小さなリリース、オンサイト顧客 |
| 主題 | M1（モデルはイテレーションで育つ） |

## このプラクティスが解こうとした問題

第 2 章で業務領域の候補が出ました。次の問いは**どの順で作るか**です。

DDD はこの問いに答えを持ちません。「中核から作れ」という原則はありますが、中核は最も複雑で、最初に作るには足場が足りません。**順序を決めるのは計画ゲームの仕事です。**

## どう実践したか

### 要件は 4 段で降りる

業務の言葉は 4 つのドキュメントを通って実装単位になります。

| 段 | ドキュメント | 単位 | 数 |
| :--- | :--- | :--- | ---: |
| 1 | `requirements_definition.md`（RDRA 2.0） | システム価値・外部環境・境界・システム | — |
| 2 | `business_usecase.md` | アクター・目的リスト | — |
| 3 | `system_usecase.md` | ユースケース | UC01〜UC22 |
| 4 | `user_story.md` | ユーザーストーリー（受入条件つき） | US01〜US36 |

**UC が受入テストの単位、US がイテレーションの単位です。** 第 5 章のシナリオテストが「US13 / US14 / US15」と Javadoc に書いているのは、この対応があるからです。

### リリースを 6 つに割る

| リリース | 内容 | ストーリー数 | SP |
| :--- | :--- | ---: | ---: |
| Release 0.1 | 予約基盤（認証・荷主・予約） | 6 | 16 |
| Release 0.2 | 経路設計・予約確定 | 7 | 23 |
| Release 1.0 | 追跡（予約から追跡までの一気通貫） | 3 | 8 |
| Release 1.1 | 実運用に必要な補完 | 15 | 49 |
| Release 2.0 | 精算 | 4 | 16 |
| Release 2.1 | 見積 | 1 | 5 |

> 出典：`development/release_plan.md`

**Release 1.0 がわずか 3 ストーリー・8SP です。** 一気通貫を「予約から追跡まで線が通ること」と定義し、そこに必要な最小の 3 本だけを置いています。**線を通すことを、機能の量から切り離した**判断です。

Release 1.1 が最も大きい（15 ストーリー・49SP）のは、線が通った後に「実運用に必要な補完」が一気に見えたためです。**何が足りないかは、通してみるまで分からない**（M2 の計画側の現れ）。

### 業務領域の分類が着手順になる

第 2 章の quadrantChart と、実際にどのイテレーションでどの BC を触ったかを突き合わせます。

| 業務領域 | 分類（差別化・複雑さ） | 主に扱ったイテレーション |
| :--- | :--- | :--- |
| Booking | **中核**（0.75, 0.82） | IT2・IT3・IT5〜IT12・IT15・IT16 |
| Tracking | **中核**（0.82, 0.68） | IT6〜IT8・IT10・IT11 |
| Routing | 中核寄り（0.62, 0.60） | IT3〜IT5・IT8・IT9・IT18 |
| Shipper | 一般（0.65, 0.28） | IT1・IT2・IT7・IT13 |
| Billing | **補完**（0.30, 0.65） | IT7・IT13〜IT15・IT19 |
| Estimation | 補完寄り（0.50, 0.35） | IT2・IT18 |
| Handling | ADR-010 で独立 | IT6・IT7・IT11・IT12・IT16 |
| Shared | 汎用（0.18, 0.22） | 全期間（2 要素に固定） |

読み取れることが 4 つあります。

| 観察 | 内容 |
| :--- | :--- |
| **中核は長く触り続けた** | Booking は 20 回中 11 回登場する。**中核とは「一度で作り切らない領域」のこと**であり、分類は投資の総量ではなく**繰り返し回数**として現れた |
| **補完は後ろに寄せた** | Billing の本格着手は IT13、Estimation は IT18 |
| **序盤は最も単純な領域を選んだ** | IT1 は中核ではなく Shipper（複雑さ 0.28） |
| **汎用は増やさない対象として管理した** | Shared の**ドメインモデルは**全期間 2 要素のまま。分類は「作らない計画」にも使われた（ただし検査の外だった `shared.application` は別。第 8 章） |

**では、この四象限は書く価値があったのか。** 判定は「**順位は役に立ち、座標は役に立たなかった**」です。中核・補完・汎用という**順位**は着手順と繰り返し回数の両方に一致しました。一方で座標の数値（Booking 0.75, 0.82 など）が判断に使われた形跡はありません。第 2 章で触れたとおり、これは測定値ではなく見立てです。

**自分のプロジェクトで書くなら、順位だけ決めれば足ります。** 数値は見た目の精度を上げるだけで、根拠を強くしません。

3 つ目が重要です。IT1 のゴールは次のとおりでした。

> **ウォーキングスケルトンが通っている**: ログインして荷主を登録し、一覧で確認できる。Thymeleaf → Controller → Application → Domain → MyBatis → PostgreSQL が 1 本つながる
>
> — `iteration_plan-1.md`

**ウォーキングスケルトンは業務の難所ではなく、貫通のしやすさで選びます。** 荷主登録は業務ロジックがほぼ無く、それゆえ全レイヤーを通す作業に集中できます。中核の Booking から始めていたら、業務ルールの議論とレイヤー貫通の作業が同時に発生していました。

### ベロシティに計画を合わせる

計画 SP の配分理由が、そのまま `release_plan.md` に残っています。

> **8SP は 3 イテレーションの実測値であり、これに計画を合わせます。**
>
> **IT4 の開始準備で 8SP に再配分しました。** 旧 IT7（13SP）・旧 IT8（28SP）を IT7〜IT11 に割り直し、**イテレーション数を 8 から 11 に増やしました**。スコープを削らずに 8SP に収めるには、期間を伸ばす以外にありません。

**スコープではなく期間を伸ばしています。** これは計画ゲームの原則どおりですが、実際にイテレーション数を 8 → 11 に増やす判断が記録として残っているのは珍しい形です。

10SP に上げた 2 回についても、根拠と賭けであることが明記されています。

> **IT10・IT11 だけは 10SP です。**（中略）**例外対応・誤配・通関は既存集約の組み合わせであり新規スキーマが少ない**ため、2 件ずつで 10SP を試します。**超過は承知の上の賭けであり、IT9 終了時の実績で見直します。**

そして Release 2.0 で、その根拠を裏返しています。

> **Release 2.0 はその逆です。** Billing Context を新規に立ち上げ、`invoice` 系テーブルを新設し、ACL ポートを 3 つ実装します。**同じ 8SP でも中身が違う**ため、根拠を裏返して配分も裏返します。

**「新規 BC の立ち上げは同じ SP でも重い」** — これは 13 イテレーション回して得た知見であり、DDD の教科書には書かれていません。

## モデルがどう変わったか

**ストーリーの並び順が、BC の立ち上がる順序を決めました。**

| IT | ストーリー | 立ち上がった BC |
| :--- | :--- | :--- |
| IT1 | US26 / US27 / US31 / US02 | Shipper・Security |
| IT2 | US04 / US32 | **Booking** |
| IT3〜IT5 | US24 / US07 / US06 / US08 / US09 / US11 / US33 | **Routing** |
| IT6 | US13 / US14 / US15 | **Tracking・Handling** |
| IT13 | US21 / US22 | **Billing** |
| IT18 | US01 | **Estimation** |

**BC は「設計したから存在する」のではなく、「そのストーリーを実装したから立ち上がった」** — これが M1 の最も直接的な形です。Estimation は第 2 章のスコープで優先度 1 に含まれていましたが、実際に立ち上がったのは 18 回目です。

## データモデルだけは先に全体を作った

ドメインモデルがイテレーションで育ったのに対し、**データモデルは逆の進め方**をしています。

| 段階 | 実績 |
| :--- | :--- |
| 最初に全体を構築 | `V1__init.sql` の 1 本で **20 テーブルを一度に作成**。7 BC すべてを最初から張っている |
| 以後は差分で変更 | `V2`〜`V41` の 40 本。**新規テーブルは 5 本だけ**、残りは **`ALTER TABLE` 計 109 文** |
| 方言差の分離 | `common/`（41 本）と `postgresql/`（V101〜V104）・`h2/`（V103）に隔離 |

設計側も 2 段階です。`data-model.md` は概念データモデル（業務の関心事）を先に置き、そこから BC ごとの論理データモデルへ展開しています。

**なぜここだけ進め方が違うのか。**

| 観点 | 内容 |
| :--- | :--- |
| **スキーマは後戻りが高い** | 集約はテストがあれば作り直せるが、テーブルはデータが載った瞬間に移行コストが跳ね上がる。**変更コストが高い箇所を先に決める**という XP の判断 |
| **それでも初期スキーマは正しくなかった** | `V3__cargo_specification.sql` が `ALTER` 10 文、`V21__cargo_special_handling.sql` が 8 文、`V30__invoice_charge_status.sql` が 9 文 |
| **追加は「列」、分割は「テーブル」** | 後から増えた 5 テーブルはいずれも**新しい業務概念**（通知・通関履歴・是正・督促・キャンセル）。**テーブルが増えるときは、ドメイン側にも新しい概念が立っている** |

**先に全体を作っても、業務ルールが分かるのはイテレーションの中です。** 違うのは「どこで間違いを吸収するか」であり、データモデルはそれを `ALTER` 109 文で吸収しました。

**ただしこの判断には成立条件があります。** 本題材は Eclipse Cargo Tracker という参考実装を持ち、**業務が既知**でした。だから 20 テーブルを最初に張れます。業務が未知の新規事業で同じことをすると、`ALTER` では吸収しきれない構造の作り直しが起きます。**真似すべきは「先に全部作る」ことではなく、「変更コストが高いものを先に決める」という基準のほうです。**

## 働かなかったケース

### 合計を手で持つとずれる

> **合計は明細から導く値であり、手で持つと必ずずれる**（IT4 の教訓）。
>
> — `release_plan.md`

IT8 の開始準備で US35・US36 を追加した際、合計 SP とイテレーション数の両方を更新する必要がありました。**計画ドキュメントの数値は、実質的にコードと同じ整合性の問題を抱えます。**

### 未達を数え直すと実績が歪む

IT16 は新規ストーリーを持たず、計画 SP を 0 としています。その理由が明快です。

> IT16 の中心は US30 の未達受入基準であり、**その 2SP 相当は IT15 の US30 5SP にすでに計上されています**。ここで再び数えると二重計上になります。**未達を「完了扱いのまま追加で数える」ことのほうが、実績を歪めます。**

**未達をどう数えるかは、ベロシティの意味そのものに関わります。** ここで 2SP を計上すれば IT16 の見た目は良くなりますが、次の計画の基準が壊れます。

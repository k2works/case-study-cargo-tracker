# 記事

同一の題材（国際貨物輸送管理システム = Cargo Tracker）を素材にした 6 つの記事シリーズです。

いずれも DDD・ヘキサゴナルアーキテクチャ・CQRS によるモジュラーモノリスを、XP のイテレーション単位で追います。「何を作ったか」ではなく **各イテレーションで何を判断し、何を間違え、どう直したか** を記録することを主眼にしています。

### モノリスアーキテクチャ実装比較

Java（Spring Boot）実装の 10 イテレーションを骨格に、各章末で他 9 言語（C# / F# / Scala / Haskell / Flix / Rust / Go / Ruby / TypeScript）が同じユーザーストーリーをどう実装したかを比較します。

型システム・エコシステム・境界の防御手段の違いが、同じ要件に対してどう表れるかを横断的に扱います。

> [シリーズを読む](monolith-architecture/index.md)

### 関数型ドメインモデリング

F#（Giraffe）実装の 8 イテレーションを追い、**不正な状態を表現不可能にする**という設計手法が実際の業務システムでどこまで通用するかを検証します。

スマートコンストラクタ、和型による条件付き必須の排除、状態がデータを持つ状態機械、Railway Oriented Programming の 4 技法が中心です。手法が届かなかった領域も同じ比重で扱います。

> [シリーズを読む](functional-domain-modeling/index.md)

### 実践 AI 駆動開発

Java（Spring Boot）の別実装（`java/take-6`）を、**開発者 1 名と AI エージェントで 20 イテレーション作り切った実績**から追います。

扱うのは成果物ではなく開発プロセスです。Skill 体系・自律実行・破壊検証・マルチパースペクティブレビュー・規則の検査化・失敗の記憶という 6 つの仕組みが、実際に品質を守ったかを 20 回のふりかえりで検証します。**効かなかったものも同じ比重で扱います。**

> [シリーズを読む](ai-driven-development/index.md)

### XP によるドメイン駆動設計の実践

実践 AI 駆動開発と同じ実装（`java/take-6`）を、**設計の側から**追います。7 つの境界づけられたコンテキストは一度に立たず、共有カーネルは 4 要素から 2 要素に縮み、BC 間の連携は同期から結果整合に反転しました。

扱うのは「DDD のパターンをどう適用したか」ではなく、**モデルを動かしたのはどのプラクティスか**です。短いイテレーション・テストファースト・リファクタリング・継続的インテグレーション・ふりかえりが、集約と境界をどう書き換えたかを 20 回分たどります。**効かなかった規律も同じ比重で扱います。**

> [シリーズを読む](xp-domain-driven-design/index.md)

### エンタープライズアーキテクチャの 4 観点

同じ実装（`java/take-6`）を、**時間ではなく構造の断面**で切ります。ビジネス・アプリケーション・データ・テクノロジーの 4 観点で解剖し、業務ケイパビリティが Bounded Context に、コンテキストがテーブルに、テーブルが検査コードにどう対応したかを縦に追跡します。

扱うのは「完成した構造がどう接続されているか」です。貫通した箇所（組織の部門がクエリのソート順まで届いた）と、切れた箇所（UC 番号の対応、設計上の AWS 構成と実配備の差）を同じ比重で扱います。

> [シリーズを読む](enterprise-architecture/index.md)

### 実践 DDD in Spring Boot

同じ実装（`java/take-6`）を、**時系列そのまま**で追います。20 イテレーションを 1 章ずつ辿り、集約・値オブジェクト・リポジトリ・ドメインイベント・腐敗防止層を **Spring Boot のコードとしてどう書いたか**を示します。

上記 3 シリーズが 20 イテレーションを主題別に横串で束ねるのに対し、本シリーズだけが縦に読めます。「この順で作れば同じものが立つ」という経路を得たい場合はここから入ります。境界が動き、共有カーネルが縮み、同期の越境が結果整合に反転した過程も、**起きた順のまま**残します。

> [シリーズを読む](practical-ddd-spring-boot/index.md)

## 読む順序

- **多言語比較から入る** — 設計判断の幅を先に把握したい場合は [モノリスアーキテクチャ実装比較](monolith-architecture/index.md) から。第 1 章で全体像、第 12 章で総括が読めます
- **関数型設計から入る** — 型による設計に関心がある場合は [関数型ドメインモデリング](functional-domain-modeling/index.md) から。第 1 章に技法がまとまっています
- **両方を突き合わせる** — 上記 2 系列は相互に参照しています。同じ要件（貨物種別の条件付き必須、状態遷移、金額計算）を両シリーズで比較すると差が鮮明になります
- **作り方から入る** — 設計そのものより「どう進めたか」に関心がある場合は [実践 AI 駆動開発](ai-driven-development/index.md) から。第 1 章に体制と実績、第 14 章に総括があります
- **設計が動く過程を見る** — DDD と XP の関係に関心がある場合は [XP によるドメイン駆動設計の実践](xp-domain-driven-design/index.md) から。第 1 章に全体地図、第 13 章に決算があります。上記 AI 駆動開発シリーズと参照元が同じで、軸だけが違います
- **構造の断面から入る** — アーキテクチャのレビューや評価が目的なら [エンタープライズアーキテクチャの 4 観点](enterprise-architecture/index.md) から。時系列を追わずに全体構造を把握できます。第 10 章（検査の 4 層）と第 11 章（貫通と破れ）が中心です
- **実装の手順として読む** — 自分で同じものを作りたい場合は [実践 DDD in Spring Boot](practical-ddd-spring-boot/index.md) から。IT1〜IT20 を 1 章ずつ辿り、各章に Spring Boot の実コードが載っています

## 要件

各章が扱うユーザーストーリー（US01〜US23）と受入基準は、[要件](../requirements/index.md) を参照してください。記事側では要件の全文を再掲せず、イテレーションごとに対象ストーリーの ID と要点だけを示しています。

| ドキュメント | 内容 |
| :--- | :--- |
| [要件定義書](../requirements/requirements_definition.md) | システム価値・外部環境・境界・内部構造（RDRA 2.0） |
| [ビジネスユースケース](../requirements/business_usecase.md) | 業務視点のユースケース |
| [システムユースケース](../requirements/system_usecase.md) | システム視点のユースケース |
| [ユーザーストーリー](../requirements/user_story.md) | 各ストーリーの本文と受入条件（US01〜US31・US 採番の正典） |

10 実装はいずれもこの要件を正典としており、**US01〜US23 でストーリー ID が共通であることが言語横断比較の接続点**になっています。イテレーション数は言語ごとに 7〜12 と異なりますが、同じ US を軸に突き合わせられるのはこのためです。

両シリーズが扱うのもこの US01〜US23 です。US24 以降の扱いは次の通りです。

| 範囲 | 内容 | 記事での扱い |
| :--- | :--- | :--- |
| US24・US25 | 航海スケジュールの登録・更新 | ID の意味は実装間で一致するが、採否が分かれるため比較軸に含めない（F# シリーズでは IT3 の対象として扱う） |
| US26・US27・US31 | 認証（ログイン・ログアウト・アカウント保護） | 同上。US31 は US26 の分割により後から追加 |
| US28〜US30 | 誤配検知・通関申告・輸送中キャンセル | **10 実装の完了後に追加された要件**のため、いずれの実装にも含まれない |

なお **US ID の共通性が保証されるのは US01〜US23 の範囲まで**です。US24 以降には実装ごとのローカル採番が混在しており、たとえば Scala 実装の US28〜US30 は「法人荷主登録 UI・CSV 取込・監査ログ」を指し、上表の US28〜US30 とは別のストーリーです。実装リポジトリの US 番号を本表と突き合わせる際は注意してください。

# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、国際貨物輸送管理システム（Cargo Tracker）のアプリケーション開発環境をセットアップする手順を説明します。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 今日のソフトウェア開発の世界において絶対になければならない 3 つの技術的な柱があります。
> 三本柱と言ったり、三種の神器と言ったりしていますが、それらは
>
> - バージョン管理
> - テスティング
> - 自動化
>
> の 3 つです。
>
> — https://t-wada.hatenablog.jp/entry/clean-code-that-works

## 1. 前提条件

以下のツールがインストールされていることを確認してください。

| ツール | バージョン | 確認コマンド |
|--------|-----------|-------------|
| .NET SDK | 10.0.x (LTS) | `dotnet --version` |
| Docker | 最新 | `docker -v` |
| Docker Compose | v2.x | `docker compose version` |
| Git | 最新 | `git -v` |
| Node.js | v22.x LTS 以上 | `node -v` |
| npm | v10.x 以上 | `npm -v` |

### .NET SDK のインストール

.NET SDK 10.0 をインストールします。

```bash
# macOS（Homebrew）
brew install --cask dotnet-sdk

# バージョン確認
dotnet --version   # 10.0.x
```

公式サイトから直接ダウンロードする場合：

- https://dotnet.microsoft.com/download/dotnet/10.0

### Docker のインストール

Docker Desktop をインストールします。統合テスト（Testcontainers）と本番互換プロファイルで使用します。

- **Windows**: https://docs.docker.com/desktop/install/windows-install/
- **macOS**: https://docs.docker.com/desktop/install/mac-install/

```bash
# バージョン確認
docker -v

docker compose version
```

### Node.js のインストール

コミット前の品質チェック（husky + lint-staged）と運用タスクランナー（Gulp）に Node.js が必要です。

- https://nodejs.org/

```bash
# バージョン確認
node -v

npm -v
```

## 5. プロファイル構成

開発効率を高めるため、環境（`ASPNETCORE_ENVIRONMENT`）を使い分けます（ADR-0003 参照）。

| プロファイル | データベース | Docker | 用途 |
|-------------|------------|--------|------|
| Development | SQLite（ファイル DB: `cargo_tracker.db`） | 不要 | 日常開発・即座起動 |
| Production 互換 | PostgreSQL 16 | 必要 | 本番互換テスト・DbUp スクリプトの方言検証 |

### Development プロファイル（推奨：日常開発）

Docker なしで即座に起動できます。起動時に DbUp が `Scripts/sqlite/` のマイグレーションを自動適用します（DbUp の起動時配線は IT1 で実装予定。現時点ではスクリプトディレクトリのみ存在します）。

```bash
cd apps/cargo-tracker/src/CargoTracker.Web
dotnet run
```

### Production 互換プロファイル（本番互換）

```bash
# データベースコンテナを起動
cd apps/cargo-tracker
docker compose up -d db

# PostgreSQL 接続で起動（Scripts/postgresql/ が適用される）
cd src/CargoTracker.Web
ASPNETCORE_ENVIRONMENT=Staging dotnet run
```

## 6. 開発サーバーの起動

### タスクランナー経由（推奨）

```bash
# 開発サーバー起動（Development プロファイル）
npx gulp app:dev

# TDD モード（テスト自動再実行）
npx gulp app:tdd

```

> **Note**: Gulp タスクは `operating-script` スキルで整備します。未整備の場合は次項のビルドツール直接実行を使用してください。


## 8. テストの実行

### 全テスト実行

```bash
cd apps/cargo-tracker

# テスト実行（カバレッジレポート付き）
dotnet test --collect:"XPlat Code Coverage"
```

> **Note**: 統合テスト（リポジトリ・エンドポイント）は Testcontainers が実 PostgreSQL コンテナを自動起動するため、Docker Desktop の起動が必要です。

### テストの種類

| テスト種別 | ツール | 説明 |
|-----------|--------|------|
| 単体テスト | xUnit + Moq + FluentAssertions | ドメインロジックのテスト |
| 統合テスト | Testcontainers for .NET + WebApplicationFactory | 実 PostgreSQL を使用したテスト |
| アーキテクチャテスト | ArchUnitNET | レイヤー依存関係検証 |

### テストカバレッジ

```bash
# テストを実行してカバレッジレポートを生成
dotnet test --collect:"XPlat Code Coverage"
npx reportgenerator -reports:"**/coverage.cobertura.xml" -targetdir:"coverage-report"

# レポートの表示
# coverage-report/index.html
```

## 9. コード品質管理

### 静的コード解析ツール

| ツール | 目的 | コマンド |
|--------|------|---------|
| dotnet format | `.editorconfig` 準拠のフォーマット検証 | `dotnet format --verify-no-changes` |
| .NET Analyzers + StyleCop.Analyzers | コーディング規約・バグパターン検出（ビルド時） | `dotnet build` |
| coverlet | テストカバレッジ | `dotnet test --collect:"XPlat Code Coverage"` |

### 品質チェックの実行

```bash
cd apps/cargo-tracker

# 品質チェックのみ
dotnet format --verify-no-changes
dotnet build -warnaserror

# すべてのテストと品質チェック
dotnet format --verify-no-changes && dotnet build -warnaserror && dotnet test
```

### コード複雑度の基準

| 指標 | 閾値 | 説明 |
|------|------|------|
| 循環的複雑度 | 10 | 分岐・ループの複雑さ |
| ファイルサイズ | 500 行 | 1 ファイルの最大行数 |
| メソッドサイズ | 150 行 | 1 メソッドの最大行数 |
| パラメータ数 | 7 | メソッドの最大パラメータ数 |

### レポートの確認

品質チェック後、以下のディレクトリにレポートが生成されます。

| ツール | レポートパス |
|--------|-------------|
| coverlet | `**/TestResults/**/coverage.cobertura.xml` |
| ReportGenerator | `coverage-report/index.html` |
| テスト結果 | `**/TestResults/*.trx` |

## 12. Git 規約

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) に従います。

| タイプ | 説明 |
|--------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `chore` | ビルドプロセス・補助ツールの変更 |

### スコープ

境界付けられたコンテキストを示すスコープを使用します。

```
feat(booking): 貨物予約登録機能を追加
fix(tracking): 追跡ステータスの遷移エラーを修正
docs: セットアップ手順を更新
```

### Git Hooks（Husky + lint-staged）

コミット時に自動で品質チェックが実行されます。

#### セットアップ

`npm install` 実行時に Husky は自動的にセットアップされます（`prepare` スクリプト）。

```bash
# 手動でセットアップする場合
npx husky init
```

#### pre-commit フック

C# ソースファイルに変更がある場合、以下のチェックが自動実行されます。

| ツール | 目的 |
|--------|------|
| dotnet format | コーディング規約の検証 |
| dotnet build（Analyzers） | バグパターン検出 |

いずれかのチェックが失敗すると、コミットがブロックされます。

#### フックをスキップする場合

緊急時にフックをスキップしてコミットする場合（非推奨）：

```bash
git commit --no-verify -m "メッセージ"
```

> **Warning**: フックのスキップは緊急時のみ使用してください。品質チェックを通過しないコードはチームに影響を与える可能性があります。

## 14. CI/CD

CI/CD の構築は `operating-cicd` スキルで実施します。構築後、以下のワークフロー構成を予定しています。

### ワークフロー一覧

| ワークフロー | ファイル | トリガー | 説明 |
|-------------|----------|----------|------|
| Backend CI | `.github/workflows/backend-ci.yml` | `apps/cargo-tracker/**` 変更時 | 品質チェック・テスト・ビルド |
| Docker Publish | `.github/workflows/docker-publish.yml` | タグ push / 手動実行 | イメージを ECR に公開 |
| Docs Deploy | `.github/workflows/docs-deploy.yml` | main ブランチ push | MkDocs サイトをデプロイ |

### Backend CI

バックエンドの変更時に自動実行されます。

```
実行内容:

  1. .NET SDK セットアップ
  2. NuGet キャッシュ復元
  3. 品質チェック（dotnet format、Analyzers）
  4. テスト実行（単体・統合（Testcontainers）・アーキテクチャ）
  5. カバレッジレポート生成（coverlet）
  6. ビルド（dotnet publish）
  7. レポートアップロード
```

## トラブルシューティング

### dotnet コマンドが見つからない

**問題**: `.NET SDK` インストール後も `dotnet` が認識されない。

**解決策**: PATH を確認し、シェルを再起動します。

```bash
export PATH="$PATH:/usr/local/share/dotnet"
dotnet --version
```

### Testcontainers のテストが失敗する

**問題**: 統合テストで `Docker is not running` エラーが発生する。

**解決策**: Docker Desktop を起動してから再実行します。

```bash
docker info   # Docker が起動しているか確認
dotnet test
```

### ポート 8080 が使用中

**問題**: `Address already in use` エラーで開発サーバーが起動しない。

**解決策**: 使用中のプロセスを終了します（`killing-processes` スキル参照）。

```bash
lsof -i :8080
kill -9 <PID>
```

### pre-commit フックが失敗する場合

```bash
cd apps/cargo-tracker

# 品質チェックを手動実行してエラーを確認
dotnet format --verify-no-changes
dotnet build -warnaserror

# エラーを修正してから再度コミット
```

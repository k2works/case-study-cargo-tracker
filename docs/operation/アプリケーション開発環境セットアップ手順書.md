# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、国際貨物輸送管理システム（cargo-tracker）のアプリケーション開発環境をセットアップする手順を説明します。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 今日のソフトウェア開発の世界において絶対になければならない 3 つの技術的な柱があります。
> 三本柱と言ったり、三種の神器と言ったりしていますが、それらは
> バージョン管理・テスティング・自動化の 3 つです。
> — <https://t-wada.hatenablog.jp/entry/clean-code-that-works>

**本ドキュメントは手順であり、実施状況ではありません。** 現時点でどこまで整備されているかは [現在の整備状況](#現在の整備状況) を参照してください。

## 5. プロファイル構成

| プロファイル | データベース | Docker | 用途 |
|-------------|------------|--------|------|
| `local`（既定） | PostgreSQL 16（Docker Compose） | **必要** | 日常開発 |
| `e2e` | PostgreSQL 16（Docker Compose） | 必要 | E2E テスト（ポーリング間隔 5s） |
| `staging` / `production` | RDS PostgreSQL 16 | - | AWS 環境 |

> **インメモリ DB のプロファイルは用意しません。** ADR-003 により H2 を採用しないためです。方言差により「テストは通るが本番で壊れる」乖離が生まれることを避ける判断であり、その代償として**ローカル開発でも Docker が必須**になります。

### local プロファイル（日常開発）

```bash
# データベースを起動
docker compose up -d db

# アプリケーションを起動
cd apps/cargo-tracker
./gradlew bootRun --args='--spring.profiles.active=local'
```

### e2e プロファイル（E2E テスト実行時）

```bash
cd apps/cargo-tracker
SPRING_PROFILES_ACTIVE=e2e ./gradlew bootRun
```

`application-e2e.yml` で追跡画面のポーリング間隔を本番の 30 秒から 5 秒へ短縮します（[テスト戦略](../design/test_strategy.md) §3.4）。

## 8. テストの実行

テスト戦略の正典は [テスト戦略](../design/test_strategy.md) です。

## 12. Git 規約

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) に従います。

| タイプ | 説明 |
|--------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `chore` | ビルドプロセス・補助ツールの変更 |

### スコープ

境界付けられたコンテキストをスコープとして使用します。

```text
feat(booking): 貨物予約の登録を実装
fix(tracking): 誤配判定で期限当日の到着を誤って刈る問題を修正
docs: 設計ドキュメントの正典を一本化
```

### Git Hooks（Husky + lint-staged）

コミット時に自動で品質チェックが実行されます。

#### セットアップ

`npm install` 実行時に Husky が自動セットアップされます（`prepare` スクリプト）。

```bash
# 手動でセットアップする場合
npx husky init
```

#### pre-commit フック

Java ソースに変更がある場合、以下が自動実行されます。

| ツール | 目的 |
|--------|------|
| Checkstyle | コーディング規約の検証 |
| SpotBugs | バグパターン検出 |

いずれかが失敗するとコミットがブロックされます。

#### フックをスキップする場合

```bash
git commit --no-verify -m "メッセージ"
```

> **Warning**: フックのスキップは緊急時のみ使用してください。

### Backend CI に含めるステップ

[テスト戦略](../design/test_strategy.md) §7.1 のステージ別テスト戦略に対応させます。

```text
1. JDK 25 セットアップ
2. Gradle キャッシュ復元
3. 品質チェック（Checkstyle / SpotBugs）
4. テスト実行（ユニット + 統合 + 認可マトリクス + ArchUnit）
5. カバレッジ検証（jacocoTestCoverageVerification）
6. SonarQube 分析（Quality Gate）
7. ビルド（成果物生成）
8. レポートアップロード
```

- PR ジョブの目標時間は **5 分以内**
- E2E（クリティカルパス 3 本）は main マージ後に実行し、**15 分以内**
- 脆弱性スキャンは**導入失敗と検出が同じ赤にならないよう、スキャナの起動成否とスキャン結果を別ステップに分ける**

2. `docker-compose.yml` に `db`（postgres:16-alpine）と `adminer` を追加
3. Checkstyle / SpotBugs / JaCoCo の設定と閾値（`test_strategy.md` §6.3 の値）を `build.gradle` に反映
4. husky + lint-staged を導入し pre-commit で品質チェックを実行
5. `ops/scripts/app.js` を作成し Gulp タスク（`app:start` / `app:tdd` / `app:test` / `app:check`）を登録（`operating-script` スキル）
6. `.github/workflows/backend-ci.yml` を作成（`operating-cicd` スキル）

実装の着手順序は [リリーススコープ定義](../development/release_scope.md) の Release 1 に従います。

## トラブルシューティング

### テスト実行時に Testcontainers が起動しない

**問題**: 統合テストが Docker に接続できず失敗する。

```text
Could not find a valid Docker environment
```

**解決策**: Docker Desktop が起動しているか確認します。ADR-003 により H2 を使わないため、**Docker が起動していない状態で統合テストは実行できません**。

```bash
docker info
docker compose up -d db
```

### ポート 8080 が既に使用されている

**問題**: `bootRun` が `Port 8080 was already in use` で失敗する。

**解決策**: 使用中のプロセスを確認して停止します。PlantUML サーバーが 8080 を使う構成の場合は競合します。

```bash
lsof -i :8080
docker compose ps
```

### Flyway マイグレーションが失敗する

**問題**: 既存マイグレーションのチェックサム不一致でアプリが起動しない。

**解決策**: 既存マイグレーションファイルの編集は禁止です（Flyway のチェックサム検証）。開発中にスキーマをやり直す場合は DB を作り直します。

```bash
docker compose down -v   # ボリュームごと削除
docker compose up -d db
```

> **本番では Forward マイグレーション + Expand-Contract パターンで対応します。** Undo マイグレーション（`U` プレフィックス）は Flyway Community Edition では実行できません（[運用要件](operation.md) 参照）。

### pre-commit フックが失敗する場合

```bash
cd apps/cargo-tracker

# 品質チェックを手動実行してエラーを確認
./gradlew checkstyleMain spotbugsMain

# エラーを修正してから再度コミット
```

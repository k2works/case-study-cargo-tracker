# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、**国際貨物輸送管理システム (Cargo Tracker) Haskell 版** のアプリケーション開発環境をセットアップする手順を説明します。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 三本柱と言ったり、三種の神器と言ったりしていますが、それらは
>
> - バージョン管理
> - テスティング
> - 自動化
>
> の 3 つです。
>
> — https://t-wada.hatenablog.jp/entry/clean-code-that-works

GHC + Stack + Cabal + HLS (Haskell Language Server) を **GHCup** で一括インストールします。バージョン管理が容易です。

```bash

# プロジェクト用のバージョンに切替
ghcup install ghc 9.10.1
ghcup install stack 3.1.1
ghcup install cabal 3.12.1.0
ghcup install hls 2.9.0.0
ghcup set ghc 9.10.1

# バージョン確認
ghc --version
stack --version
cabal --version
haskell-language-server-wrapper --version
```

- https://www.haskell.org/ghcup/

## 5. プロファイル構成

開発効率を高めるため、複数のプロファイルを使い分けます。

| プロファイル | データベース | Docker | 用途 |
|-------------|------------|--------|------|
| local | PostgreSQL (Docker Compose) | 必要 | 日常開発・全環境同一 DB エンジン |
| test | PostgreSQL (testcontainers-hs) | 必要 | テスト実行時、spec ごとに独立コンテナ |
| product | PostgreSQL (本番相当 Docker) | 必要 | 本番互換テスト |

> **設計判断**: Java 版と異なり H2 などのインメモリ DB は使用しない。テストも Testcontainers の実 PostgreSQL を使用し、本番との差異を排除する。

### local プロファイル（推奨：日常開発）

Docker Compose で PostgreSQL を起動し、`stack run` でアプリを起動します。

```bash
# 1. PostgreSQL コンテナ起動
cd apps/cargo-tracker
docker compose up -d postgres

# 2. マイグレーション適用
APP_ENV=local dbmate up

# 3. アプリ起動
APP_ENV=local stack run cargo-tracker-exe
```

### product プロファイル（本番互換）

```bash
# データベースコンテナを起動
cd apps/cargo-tracker
docker compose up -d postgres

# product プロファイルで起動
APP_ENV=production stack run cargo-tracker-exe
```

## 8. テストの実行

### 全テスト実行

```bash
cd apps/cargo-tracker

# テスト実行（カバレッジレポート付き）
stack test --coverage

# カバレッジレポートの場所
stack hpc report --all
# → .stack-work/install/.../hpc/combined/all/hpc_index.html
```

### テストの種類

| テスト種別 | ツール | 説明 |
|-----------|--------|------|
| 単体テスト (例ベース) | hspec | ドメインロジック・状態遷移のテスト |
| プロパティテスト | hedgehog | スマートコンストラクタ・列挙型双方向変換の網羅検証 |
| 統合テスト (DB) | testcontainers-hs | 実 PostgreSQL でリポジトリ実装のテスト |
| 統合テスト (API) | hspec-wai | Servant API のエンドポイント検証 |
| アーキテクチャテスト | arch-check (自作) | レイヤー依存関係検証 (ADR 0002) |
| 契約テスト | hspec + WireMock | 外部 ACL ポートのスタブ検証 |
| E2E テスト | Playwright | 主要ユーザーシナリオ (TypeScript) |

### テスト実行の粒度

```bash
# Pre-commit (高速、Domain のみ)
stack test --test-arguments="--match Domain"

# 単体テスト全実行

# 統合テストのみ

# カバレッジレポート生成 + ブラウザで表示
```

| weeder | 未使用 export / 関数の検出 | `weeder` |
| hpc | テストカバレッジ | `stack test --coverage` |
| arch-check | アーキテクチャ規約検査 | `stack exec arch-check` |

### 品質チェックの実行

```bash
cd apps/cargo-tracker

# 品質チェックのみ
npm run lint               # HLint + fourmolu --mode check + weeder

# フォーマット自動適用
fourmolu --mode inplace src/ test/

# すべてのテストと品質チェック
npm run check              # lint + arch-check + stack test
```

| 1 モジュールの行数 | 500 行 | 推奨 |
| 関数の引数数 | 5 個 | 推奨 (それ以上はレコードに集約) |

## 11. 命名規則

プロジェクトの命名規則を定義します。

| 要素 | 規則 | 例 |
|------|------|-----|
| テーブル名 | snake_case (複数形は使わない) | `cargo`, `tracking_activity` |
| カラム名 | snake_case | `booking_id`, `created_at` |
| Haskell モジュール | PascalCase 階層 | `Cargotracker.Booking.Domain.Model.Aggregates.Cargo` |
| Haskell 型 | PascalCase | `Cargo`, `BookingStatus`, `DomainError` |
| Haskell 関数 | camelCase | `assignRoute`, `mkBookingId` |

| スマートコンストラクタ | `mkXxx :: a -> Either DomainError T` | `mkBookingId`, `mkUnLocode` |

| URL パス | kebab-case | `/api/v1/bookings/:id/route` |
| HTML id / class | kebab-case | `#status-container`, `.tracking-map` |

## 12. Git 規約

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) に従います。

| タイプ | 説明 |
|--------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `chore` | ビルドプロセス・補助ツールの変更 |

### スコープ

サブシステムまたは Bounded Context を示すスコープを使用します。

```
feat(booking): US04 貨物予約登録の実装
fix(tracking): TrackingStatus 遷移バグ修正
docs(adr): ADR 0003 を追加
test(it1): Cargo 集約の状態遷移テスト追加 (Red)
chore(deps): Servant を 0.20.2 に更新
```

### TDD コミット規律

- **Red コミットと Green コミットを分離** する。失敗するテストを先に追加してコミット (`test(...): ... (Red)`)、続けて実装でコミット (`feat(...): ... (Green)`)
- やむを得ず Red と Green を 1 コミットに含める場合、コミットメッセージに以下を明記:
  - `Red→Green サイクル: <テスト名> を先に追加し失敗を確認後、実装で Green に転じた`

### Git Hooks（Husky + lint-staged）

コミット時に自動で品質チェックが実行されます。

#### セットアップ

`npm install` 実行時に Husky は自動的にセットアップされます（`prepare` スクリプト）。

```bash
# 手動でセットアップする場合
npx husky init
```

#### pre-commit フック

ソースファイルに変更がある場合、以下のチェックが自動実行されます。

| ツール | 目的 |
|--------|------|
| fourmolu --mode check | フォーマット規約検証 |
| HLint | コーディング規約検証 |
| stack test --match Domain | ドメイン層単体テスト |

いずれかのチェックが失敗すると、コミットがブロックされます。

#### フックをスキップする場合

緊急時にフックをスキップしてコミットする場合（非推奨）：

```bash
git commit --no-verify -m "メッセージ"
```

> **Warning**: フックのスキップは緊急時のみ使用してください。品質チェックを通過しないコードはチームに影響を与える可能性があります。

### CI ジョブの内容

バックエンドの変更時に自動実行されます。

```
実行内容:

  1. 環境セットアップ (GHCup + GHC 9.10 + Stack)
  2. Stack キャッシュ復元 (~/.stack + .stack-work)
  3. アーキテクチャ規約検査 (arch-check + HLint)
  4. フォーマットチェック (fourmolu --mode check)
  5. デッドコード検出 (weeder)
  6. 単体テスト (hspec + hedgehog)
  7. 統合テスト (testcontainers-hs PostgreSQL + hspec-wai)
  8. カバレッジレポート生成 (hpc, 目標: Domain ≥ 95% / 全体 ≥ 85%)
  9. ビルド (stack build --pedantic)
  10. (main push 時) 負荷スモークテスト (k6, P95 < 500ms)
  11. レポートアップロード
```

### Docker Image Publish

タグ push 時または手動実行時に、Docker イメージをビルドして ECR に公開します。

```bash
# 手動実行
gh workflow run cd-staging.yml

# タグによる自動実行
git tag v1.0.0
git push origin v1.0.0

# イメージの取得
docker pull <account>.dkr.ecr.ap-northeast-1.amazonaws.com/cargo-tracker:latest
```

## トラブルシューティング

### Stack の初回ビルドが遅い

**問題**: `stack build` の初回実行が 30 分以上かかる。

```
Building all executables for `cargo-tracker' once. After a successful build of all of them, only specified executables will be rebuilt.
```

**解決策**: GHC とライブラリのコンパイル + キャッシュ整備のため、初回のみ時間がかかります。2 回目以降はキャッシュが効きます。
CI では `actions/cache` で `~/.stack` と `.stack-work` をキャッシュして対応しています。

```bash
# キャッシュサイズの確認
du -sh ~/.stack apps/cargo-tracker/.stack-work
```

### PostgreSQL 接続エラー

**問題**: `Connection refused: localhost:5432`

**解決策**: PostgreSQL コンテナが起動していない可能性があります。

```bash
cd apps/cargo-tracker
docker compose ps
docker compose up -d postgres

# 接続確認
docker compose exec postgres pg_isready -U cargo_tracker
```

### dbmate マイグレーション失敗

**問題**: `dbmate: relation "schema_migrations" already exists`

**解決策**: マイグレーション履歴テーブルが既存。状態を確認:

```bash
APP_ENV=local dbmate status
APP_ENV=local dbmate rollback   # 1 段階戻す
```

### HLint / fourmolu のバージョン違い

**問題**: ローカルと CI で警告内容が異なる。

**解決策**: GHCup でバージョンを固定:

```bash
ghcup install hls 2.9.0.0
cabal install hlint-3.8 fourmolu-0.16 weeder-2.9 --overwrite-policy=always
```

### pre-commit フックが失敗する場合

```bash
cd apps/cargo-tracker

# 品質チェックを手動実行してエラーを確認
npm run lint

# フォーマット自動修正
fourmolu --mode inplace src/ test/

# HLint の suggestion を適用
hlint --refactor=inplace src/

# エラーを修正してから再度コミット
```

### GHC バージョン不一致

**問題**: `stack build` で `GHC 9.10 required but found 9.8`

**解決策**: Stack の resolver と GHC バージョンを合わせる:

```bash
ghcup install ghc 9.10.1
ghcup set ghc 9.10.1
stack setup  # stack.yaml の resolver に合わせて再セットアップ
```

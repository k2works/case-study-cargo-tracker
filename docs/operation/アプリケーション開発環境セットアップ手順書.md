# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、国際貨物輸送管理システム（cargo-tracker）のアプリケーション開発環境をセットアップする手順を説明します。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 今日のソフトウェア開発の世界において絶対になければならない 3 つの技術的な柱があります。
> 三本柱と言ったり、三種の神器と言ったりしていますが、それらは
> バージョン管理・テスティング・自動化の 3 つです。
> — <https://t-wada.hatenablog.jp/entry/clean-code-that-works>

**本ドキュメントは手順であり、実施状況ではありません。** 現時点でどこまで整備されているかは [現在の整備状況](#現在の整備状況) を参照してください。

## 5. プロファイル構成

| プロファイル | データベース | Docker | 用途 |
|-------------|------------|--------|------|
| `local`（既定） | PostgreSQL 16（Docker Compose） | **必要** | 日常開発 |
| `e2e` | PostgreSQL 16（Docker Compose） | 必要 | E2E テスト（ポーリング間隔 5s） |
| `staging` / `production` | RDS PostgreSQL 16 | - | AWS 環境 |

> **インメモリ DB のプロファイルは用意しません。** ADR-003 により H2 を採用しないためです。方言差により「テストは通るが本番で壊れる」乖離が生まれることを避ける判断であり、その代償として**ローカル開発でも Docker が必須**になります。

### local プロファイル（日常開発）

```bash
# データベースを起動
docker compose up -d db

# アプリケーションを起動
cd apps/cargo-tracker
./gradlew bootRun --args='--spring.profiles.active=local'
```

### e2e プロファイル（E2E テスト実行時）

```bash
cd apps/cargo-tracker
SPRING_PROFILES_ACTIVE=e2e ./gradlew bootRun
```

`application-e2e.yml` で追跡画面のポーリング間隔を本番の 30 秒から 5 秒へ短縮します（[テスト戦略](../design/test_strategy.md) §3.4）。

## 7. Docker Compose のセットアップ

### データベースコンテナの起動

```bash
# データベースを起動
docker compose up -d db

# コンテナの状態確認
docker compose ps
```

### サービス構成

[インフラストラクチャ設計](../design/architecture_infrastructure.md) のローカル開発環境に対応します。

| サービス | イメージ | ポート | 用途 |
|---------|---------|--------|------|
| `db` | `postgres:16-alpine` | 5432 | アプリケーション DB（`postgres_data` ボリューム） |
| `adminer` | `adminer:5` | 8081 | DB 管理 UI |
| `mkdocs` | ローカルビルド | 8000 | ドキュメントサイト |
| `plantuml` | `plantuml/plantuml-server:jetty` | - | 図表レンダリング |
| `dev` | ローカルビルド | - | 開発用コンテナ |

初回起動時に `ops/docker/postgres/initdb/` の SQL が実行され、開発用（`cargo_tracker`）と E2E 用（`cargo_tracker_e2e`）の 2 つのデータベースが作成されます。**E2E がテストデータを投入・削除しても日常開発中のデータを壊さないよう分離しています。**

> **`container_name` は指定していません。** 本リポジトリは言語別の姉妹プロジェクトが多数あり、固定名にすると他プロジェクトの停止済みコンテナと名前が衝突して起動できなくなるためです。Compose のプロジェクト名によるネームスペースに任せます。

### Docker Compose の便利なコマンド

```bash
# データベースを起動
docker compose up -d db

# コンテナの停止と削除
docker compose down

# ログを確認
docker compose logs -f db

# データベースに接続
docker compose exec db psql -U cargo_tracker -d cargo_tracker
```

## 10. 設計ドキュメントの生成（JIG / jig-erd）

`docs/design/` は「**こう設計した**」を記述したドキュメントです。JIG と jig-erd はコードと DB スキーマから「**こう実装されている**」を生成します。

**両者を突き合わせることが目的です。** 設計書の図を手で更新し続けると、実装を変えたのに図だけ古いまま、という状態に必ずなります。生成物と比べれば、その乖離が目視ではなく差分として現れます。

### JIG（コードからの設計ドキュメント）

[JIG](https://github.com/dddjava/jig) はバイトコードから設計情報を可視化します。

```bash
cd apps/cargo-tracker

# JIG ドキュメントを生成（build/jig/ に出力）
./gradlew jigReports

# クリーンな状態から生成する場合
./gradlew clean jigReports

# ブラウザで開く
open build/jig/index.html
```

出力される主なドキュメント:

| ファイル | 内容 | 突き合わせ先 |
|---------|------|-------------|
| `index.html` | 全体のインデックス | - |
| `domain.html` | ドメインモデルの一覧（業務の概念とビジネスルール） | [ドメインモデル設計](../design/domain-model.md) |
| `package.html` | パッケージ関連図 | [バックエンドアーキテクチャ](../design/architecture_backend.md)「パッケージ構成」 |
| `usecase.html` | アプリケーション層の業務機能一覧 | [ユーザーストーリー](../requirements/user_story.md) |
| `inbound.html` / `outbound.html` | 入出力（Controller / Repository） | [バックエンドアーキテクチャ](../design/architecture_backend.md) |
| `glossary.html` | 用語集（Javadoc から抽出） | ユビキタス言語 |
| `insight.html` | 依存関係のインサイト | ArchUnit ルール（[テスト戦略](../design/test_strategy.md) §3.3） |

設定は `build.gradle` の `jig { ... }` ブロックにあります。`modelPattern = '.+'` で全パッケージを対象にしています。

> **JIG の警告は現時点では正常です。** 「SQL が見つかりませんでした」「Repository のメソッドが見つからない」等は、実装が未着手であることを示しています。実装が進むにつれて出力が充実します。

### jig-erd（DB スキーマからの ER 図）

[jig-erd](https://github.com/irof/jig-erd) は実際の DB スキーマから ER 図を生成します。

```bash
cd apps/cargo-tracker

# Testcontainers 上に Flyway でスキーマを構築し ER 図を生成
./gradlew jigErd

# 出力を確認（build/jig-erd/ に SVG が 3 種類）
open build/jig-erd/cargo-tracker-erd-detail.svg
```

| ファイル | 内容 |
|---------|------|
| `cargo-tracker-erd-overview.svg` | スキーマのみ |
| `cargo-tracker-erd-summary.svg` | スキーマ・テーブル |
| `cargo-tracker-erd-detail.svg` | スキーマ・テーブル・外部キーカラム |

- 実行には **Docker と Graphviz が必要**です
- 生成は `SchemaErdDocument` が担います。**検証を行わないため通常の `test` タスクからは除外**しています（テストではなくドキュメント生成であるため）
- 出力設定は `src/test/resources/jig.properties` にあります

> **jig-erd は関連に着目した「ざっくりした」ER 図です。** PK・データ型・制約は扱いません。それらの正典は [データモデル設計](../design/data-model.md) です。jig-erd で確認するのは**テーブルと外部キーの関係が設計どおりか**であり、カラム定義の詳細ではありません。

### 生成物は Git 管理外

`build/jig/` と `build/jig-erd/` は `.gitignore` で除外しています。**生成物をコミットすると、コードを変えたのに図が古いという状態がリポジトリに固定されます。** 必要なときに生成する運用とします。

```text
case-study-cargo-tracker-java-take-6/
├── .husky/                          # Git Hooks (Husky)
│   └── pre-commit                   # コミット前品質チェック
├── apps/

│       ├── Dockerfile

│       └── src/

│           │   ├── java/com/example/cargotracker/
│           │   │   ├── booking/     # Booking Context
│           │   │   ├── shipper/     # Shipper Context
│           │   │   ├── routing/     # Routing Context
│           │   │   ├── tracking/    # Tracking Context（handling/ を含む）
│           │   │   ├── billing/     # Billing Context
│           │   │   ├── estimation/  # Estimation Context
│           │   │   └── shared/      # 共有カーネル（Location・ShipperId）
│           │   └── resources/
│           │       ├── application.yml
│           │       ├── application-local.yml
│           │       ├── application-e2e.yml
│           │       ├── db/migration/            # Flyway マイグレーション
```

各 BC の内部は `domain/` `application/` `infrastructure/` `interfaces/` の 4 層で構成します。

| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `chore` | ビルドプロセス・補助ツールの変更 |

### スコープ

境界付けられたコンテキストをスコープとして使用します。

```text
feat(booking): 貨物予約の登録を実装
fix(tracking): 誤配判定で期限当日の到着を誤って刈る問題を修正
docs: 設計ドキュメントの正典を一本化
```

### Git Hooks（Husky + lint-staged）

コミット時に自動で品質チェックが実行されます。

#### セットアップ

`npm install` 実行時に Husky が自動セットアップされます（`prepare` スクリプト）。

```bash
# 手動でセットアップする場合
npx husky init
```

#### pre-commit フック

`.husky/pre-commit` が `npx lint-staged` を実行します。対象は `.lintstagedrc.mjs` で定義しています。

| 対象 | 実行内容 |
|------|---------|
| `apps/cargo-tracker/**/*.java` | `npm run app:lint`（Checkstyle + SpotBugs） |

いずれかが失敗するとコミットがブロックされます。**違反を混入させたコミットで実際に停止することを確認済みです。**

> **Markdown は対象にしていません。** 既存ドキュメントが markdownlint の既定ルール（MD013 行長・MD060 表スタイル）に多数抵触しており、対象にするとドキュメントを触るすべてのコミットが止まります。ルールセットを整備してから導入します。
>
> **lint-staged の設定を関数形式にしているのは意図的です。** lint-staged は既定でステージ済みファイル名をコマンド末尾に追記しますが、Gradle はファイル名を引数に取れません。関数で固定の文字列を返すことで追記を抑止しています。

#### npm スクリプト

ルートの `package.json` からアプリの主要タスクを実行できます。

| スクリプト | 内容 |
|-----------|------|
| `npm run app:start` | 開発サーバー起動（local プロファイル） |
| `npm run app:test` | テスト実行 |
| `npm run app:check` | テスト + 静的解析 |
| `npm run app:lint` | 静的解析のみ |
| `npm run app:build` | ビルド |
| `npm run app:jig` | JIG ドキュメント生成 |
| `npm run app:jig-erd` | ER 図生成 |

#### フックをスキップする場合

```bash
git commit --no-verify -m "メッセージ"
```

> **Warning**: フックのスキップは緊急時のみ使用してください。

### ArchUnit ルールの整備状況

[テスト戦略](../design/test_strategy.md) §3.3 が定める 6 ルールのうち、実装済みは 1 つです。

| ルール | 状況 | 理由 |
|-------|------|------|
| 5. トップレベルパッケージ = BC 集合 | ✅ 有効 | `package-info.java` が対象になるため検査できる |
| 1. ドメイン層 → インフラ層の依存禁止 | ⏳ 未有効 | 対象クラスが 0 件で `failOnEmptyShould` により失敗する |
| 2. ドメイン層の Spring アノテーション禁止 | ⏳ 未有効 | 同上 |
| 3. アプリケーション層 → インフラ層の直接参照禁止 | ⏳ 未有効 | 同上 |
| 4. BC 間のクラス直接参照禁止 | ⏳ 未有効 | 同上 |
| 6. 共有カーネルは 2 要素のみ | ⏳ 未有効 | 同上 |

**`allowEmptyShould(true)` で通すことはしません。** 何も検査していないルールを緑にすると、実装が入った後も検査されていないことに気づけなくなります。各ルールは対応する層の実装を追加するイテレーションで、**実際に違反を検出できることを確認したうえで**有効化します。

## トラブルシューティング

### テスト実行時に Testcontainers が起動しない

**問題**: 統合テストが Docker に接続できず失敗する。

```text
Could not find a valid Docker environment
```

**解決策**: Docker Desktop が起動しているか確認します。ADR-003 により H2 を使わないため、**Docker が起動していない状態で統合テストは実行できません**。

```bash
docker info
docker compose up -d db
```

### ポート 8080 が既に使用されている

**問題**: `bootRun` が `Port 8080 was already in use` で失敗する。

**解決策**: 使用中のプロセスを確認して停止します。PlantUML サーバーが 8080 を使う構成の場合は競合します。

```bash
lsof -i :8080
docker compose ps
```

### Flyway マイグレーションが失敗する

**問題**: 既存マイグレーションのチェックサム不一致でアプリが起動しない。

**解決策**: 既存マイグレーションファイルの編集は禁止です（Flyway のチェックサム検証）。開発中にスキーマをやり直す場合は DB を作り直します。

```bash
docker compose down -v   # ボリュームごと削除
docker compose up -d db
```

> **本番では Forward マイグレーション + Expand-Contract パターンで対応します。** Undo マイグレーション（`U` プレフィックス）は Flyway Community Edition では実行できません（[運用要件](operation.md) 参照）。

### pre-commit フックが失敗する場合

```bash
cd apps/cargo-tracker

# 品質チェックを手動実行してエラーを確認
./gradlew checkstyleMain spotbugsMain

# エラーを修正してから再度コミット
```

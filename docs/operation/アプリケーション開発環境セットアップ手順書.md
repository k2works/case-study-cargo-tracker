# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、**国際貨物輸送管理システム（case-study-cargo-tracker）** のアプリケーション開発環境をセットアップする手順を説明します。

本システムは **Axon Framework 5 + CQRS + Event Sourcing + Saga** を採用したマイクロサービス構成です。7 つのバックエンドサービス（authms / bookingms / routingms / trackingms / handlingms / billingms / gatewayms）+ フロントエンド（React SPA）+ Axon Server + PostgreSQL からなります。

### 整備状況の凡例

本ドキュメント内では各項目の実装ステータスを以下の記号で示します。

- ✅ 整備済み（実際に動作確認できる）
- 🚧 雛形のみ（`.gitkeep`、計画記載のみ）
- 📋 Phase 2 以降に実装予定

**IT1 完了時点で動かせる範囲**: `apps/backend/authms`（port 8081）、`apps/backend/bookingms`（port 8082）、`apps/frontend`（port 5173）。それ以外のサービス（routingms/trackingms/handlingms/billingms/gatewayms）は雛形（.gitkeep）配置のみで起動できません（ADR-0003 参照）。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 今日のソフトウェア開発の世界において絶対になければならない 3 つの技術的な柱があります。三本柱と言ったり、三種の神器と言ったりしていますが、それらは
>
> - バージョン管理
> - テスティング
> - 自動化
>
> の 3 つです。
>
> — <https://t-wada.hatenablog.jp/entry/clean-code-that-works>

### Gradle Wrapper の初回生成（クローン直後に 1 度だけ）

`apps/backend/` に `gradlew` / `gradlew.bat` / `gradle/wrapper/gradle-wrapper.jar` が無い状態でクローンした場合は、Docker 経由で Gradle 9.5 を起動して生成します（ホストに Gradle が未インストール、または Gradle 8 系で Java 25 をパースできない環境でも確実に動作）。

```powershell
# PowerShell（Windows）
docker run --rm `
  -v "${PWD}/apps/backend:/ws" `
  -w "/ws" `
  gradle:9.5.0-jdk25 `
  gradle wrapper --gradle-version 9.5 --distribution-type bin
```

```bash
# Git Bash / WSL / macOS / Linux
MSYS_NO_PATHCONV=1 docker run --rm \
  -v "$(realpath apps/backend):/ws" \
  -w "/ws" \
  gradle:9.5.0-jdk25 \
  gradle wrapper --gradle-version 9.5 --distribution-type bin
```

> **Phase 0 補足**: `apps/backend/bookingms/Dockerfile` は `gradle:9.5.0-jdk25` 公式イメージをビルダーに使うため、コンテナビルドだけなら wrapper 無しでも動作します。Wrapper はホスト側 `dev:bookingms` / `tdd:bookingms` の Gradle 実行で必要です。

## 5. プロファイル構成

開発効率を高めるため、複数のプロファイルを使い分けます。

| プロファイル | データベース | Axon Server | Docker | 用途 |
|-------------|------------|------------|--------|------|
| `local-h2` | H2（インメモリ） | Axon Server（dev mode）または Embedded EventStore | 不要 | 単体サービスの即座起動・TDD |
| `local-docker` | PostgreSQL（Docker） | Axon Server（Docker） | 必要 | 本番互換の結合確認 |
| `test` | Testcontainers（PostgreSQL + Axon Server） | 同上 | 自動起動 | 統合テスト実行 |

> **設計指針**: 集約の Event Store は Axon Server が必須。H2 は Read Model（Projection）と Auth DB の代替として使用。日常 TDD は単一サービス + H2 で完結させる。

### local-h2 プロファイル（推奨：単一サービスの TDD）

Docker なしで即座に起動できます（Axon Server は dev mode の埋め込みで代替）。

```bash
cd apps/backend/bookingms
./gradlew bootRun --args='--spring.profiles.active=local-h2'
```

### local-docker プロファイル（本番互換、二段構成）

`apps/docker-compose.yml` は Compose の `profiles` 機能で「基盤のみ」と「フル」を切り分けます。日常 TDD では基盤のみを Docker で起動し、対象サービスはホスト側で Gradle bootRun する構成を推奨します。

```bash
# 基盤のみ起動（推奨：日常 TDD）
docker compose -f apps/docker-compose.yml up -d axonserver postgresql

# 個別サービスを起動（例: bookingms）
cd apps/backend
./gradlew :bookingms:bootRun --args='--spring.profiles.active=local-docker'

# フル起動（compose で全 7 サービス + Frontend）
docker compose -f apps/docker-compose.yml --profile full up -d
```

> **Phase 0 注意**: `apps/docker-compose.yml` には現状 `bookingms` のみがアクティブで、他 6 サービス + Frontend は Phase 1 用のコメントアウトブロックに退避されています。Phase 1 で各サービスの最小骨格が揃った段階で順次アンコメントして `full` プロファイルへ移行します。

## 7. Docker Compose のセットアップ

### Compose ファイル構成

リポジトリには 2 つの compose ファイルがあります（ADR-0003 で分離）。

| ファイル | 役割 | 主な利用者 |
|---------|------|-----------|
| `apps/docker-compose.yml` | アプリ実行環境（Axon Server / PostgreSQL / 7 サービス / Frontend） | 開発者 |
| `docker-compose.docs.yml` | ドキュメントサイト（MkDocs）専用 | ドキュメント執筆 |

### `.env` の準備（必須）

`apps/docker-compose.yml` は `.env` からシークレットを読み込みます。**ハードコードは廃止されています**（ADR-0003）。

```bash
cp .env.example .env

# 最低限以下を設定してから compose を起動
#   POSTGRES_USER           : PostgreSQL ユーザー名
#   POSTGRES_PASSWORD       : PostgreSQL パスワード（必須、未設定だと起動失敗）
#   AXON_SERVER_HTTP_PORT   : 既定 8024
#   AXON_SERVER_GRPC_PORT   : 既定 8124
#   JWT_SECRET              : authms/gatewayms 連携時に必須
```

### サービスの起動

```bash
# 基盤のみ起動（推奨：日常 TDD）
docker compose -f apps/docker-compose.yml up -d axonserver postgresql

# Phase 0 で起動できる範囲を起動（基盤 + bookingms。compose 内アクティブ定義が bookingms のみ）
docker compose -f apps/docker-compose.yml up -d

# Phase 1 で残りサービスを compose にアンコメントしたら、起動範囲を `--profile full` で切り替える
# docker compose -f apps/docker-compose.yml --profile full up -d

# 状態確認
docker compose -f apps/docker-compose.yml ps
```

### 便利なコマンド

```bash
# Axon Server のログ確認
docker compose -f apps/docker-compose.yml logs -f axonserver

# PostgreSQL に psql で接続
docker compose -f apps/docker-compose.yml exec postgresql \
  psql -U "$POSTGRES_USER" -d booking_read_db

# 全コンテナ停止（ボリューム保持）
docker compose -f apps/docker-compose.yml down

# ボリュームも削除（Event Store と DB データを完全リセット、破壊的）
docker compose -f apps/docker-compose.yml down -v
```

> **重要 / セキュリティ**: compose の `AXONIQ_AXONSERVER_DEVMODE_ENABLED` はローカル開発限定の設定です。**ステージング・本番では必ず `false` にする**こと（認証が無効になります）。本書のステージング・本番向け手順書では `true` 設定は許可しません。

### docker-compose.yml の主要サービス（抜粋）

```yaml
services:
  axonserver:
    image: axoniq/axonserver:2026.0.0
    ports:
      - "${AXON_SERVER_HTTP_PORT:-8024}:8024"
      - "${AXON_SERVER_GRPC_PORT:-8124}:8124"
    environment:
      AXONIQ_AXONSERVER_DEVMODE_ENABLED: "${AXONIQ_AXONSERVER_DEVMODE_ENABLED:-true}"
      # 注意: DEVMODE はローカル限定。ステージング・本番では必ず false

  postgresql:
    image: postgres:16
    ports:
      - "${POSTGRES_PORT:-5432}:5432"
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?POSTGRES_USER not set in .env}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD not set in .env}
      POSTGRES_MULTIPLE_DATABASES: >-
        auth_db,booking_read_db,routing_read_db,
        tracking_read_db,handling_read_db,billing_read_db

  bookingms:
    build:
      context: ./backend
      dockerfile: bookingms/Dockerfile
    profiles: ["full", "booking"]
    depends_on:
      axonserver:
        condition: service_healthy
      postgresql:
        condition: service_healthy
    environment:
      SPRING_PROFILES_ACTIVE: local-docker
      AXON_AXONSERVER_SERVERS: axonserver:8124
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgresql:5432/booking_read_db
      SPRING_DATASOURCE_USERNAME: ${POSTGRES_USER}
      SPRING_DATASOURCE_PASSWORD: ${POSTGRES_PASSWORD}
```

実体は `apps/docker-compose.yml` を参照。すべてのシークレットは `.env` から読み込まれ、ハードコードは廃止されています（ADR-0003）。

詳細は [docs/design/architecture_infrastructure.md](../design/architecture_infrastructure.md) を参照。

### スコープ

```text
feat(bookingms): 予約集約のキャンセル機能を追加

refactor(design): Phase 1 レビュー指摘の反映
```

### Git Hooks（Husky + lint-staged）

`npm install` 実行時に Husky は自動的にセットアップされます（`prepare` スクリプト）。

```bash
# 手動セットアップ（必要時のみ）

```

#### pre-commit フック

ソースファイルに変更がある場合、以下のチェックが自動実行されます。

| 対象 | ツール |
|------|--------|
| Java | Checkstyle / SpotBugs |
| TypeScript | ESLint / Prettier |
| Markdown | markdownlint（テンプレートに準拠した整形ルール） |

いずれかのチェックが失敗するとコミットがブロックされます。

#### フックをスキップする場合（非推奨）

```bash
git commit --no-verify -m "メッセージ"
```

> **Warning**: フックのスキップは緊急時のみ。品質チェックを通過しないコードはチームに影響します。

### Docker イメージ Publish（GHCR）

タグ push 時または手動実行時に、Docker イメージをビルドして GHCR に公開します（ADR-0003）。CI では `secrets.GITHUB_TOKEN` で認証するため、リポジトリ側で追加シークレットの登録は不要です。

```bash
# タグによる自動実行
```

ローカルから手動 push する場合は Personal Access Token（`read:packages`, `write:packages`）を `.env` の `GHCR_USERNAME` / `GHCR_TOKEN` に設定し、`docker login ghcr.io` を実行してください。

## トラブルシューティング

### Axon Server に接続できない

**問題**: `bookingms` 起動時に `io.axoniq.axonserver.connector.client` 関連の接続エラーが出る

```text
io.netty.channel.AbstractChannel$AnnotatedConnectException: Connection refused: localhost/127.0.0.1:8124
```

**解決策**: Axon Server コンテナが起動・ヘルスチェック合格しているか確認

```bash
docker compose ps axonserver
docker compose logs axonserver | tail -50

# 起動していない場合
docker compose up -d axonserver
```

### PostgreSQL のマルチデータベースが作成されない

**問題**: `booking_read_db` などのデータベースが見つからない

**解決策**: `apps/ops/postgres/init-databases.sh` が `docker-entrypoint-initdb.d/` にマウントされているか確認。ボリュームを削除して再作成。

```bash
docker compose -f apps/docker-compose.yml down -v postgresql
docker compose -f apps/docker-compose.yml up -d postgresql
docker compose -f apps/docker-compose.yml exec postgresql \
  psql -U "$POSTGRES_USER" -l
```

### Java バージョン不一致でビルドが失敗

**問題**: `Unsupported class file major version` 等

**解決策**: Java 25 を使っているか確認。SDKMAN を使っている場合 `sdk use java 25-tem`。

```bash
java -version
./gradlew --version
```

### Frontend で API 502 / CORS エラー

**問題**: Vite 開発サーバから `/api/...` が 502 を返す

**解決策**: `vite.config.ts` の `server.proxy` で `localhost:8080`（gatewayms）に向ける。または gatewayms が起動しているか確認。

### フロントエンドから authms / bookingms への CORS エラー

**問題**: フロントエンド（localhost:5173）から API リクエスト時に CORS エラーが発生する

```text
Access to fetch at 'http://localhost:8081/...' from origin 'http://localhost:5173' has been blocked by CORS policy
```

**解決策**: 各サービスの `SecurityConfig` に `CorsConfigurationSource` Bean が正しく定義されているか確認。`allowedOriginPatterns` に `http://localhost:5173` が含まれている必要があります。

```java
// apps/backend/authms（または bookingms）/.../config/SecurityConfig.java
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    var configuration = new CorsConfiguration();
    configuration.setAllowedOriginPatterns(List.of(
            "http://localhost:3000",
            "http://localhost:5173",
            "https://*.herokuapp.com"
    ));
    configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    configuration.setAllowedHeaders(List.of("*"));
    configuration.setAllowCredentials(true);
    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", configuration);
    return source;
}
```

### フロントエンドから荷主 API が 404 になる

**問題**: 荷主一覧・登録 API が 404 を返す

**解決策**: フロントエンドの API クライアントが正しいサービスに向いているか確認。`bookingApiClient`（port 8082）を使用し、パスは `/api/v1/shippers` であることを確認。

```typescript
// 正しい実装: bookingApiClient + /api/v1/shippers
bookingApiClient.get<Shipper[]>('/api/v1/shippers')

// よくある誤り 1: authApiClient（port 8081）を使用
// よくある誤り 2: パスに /api/booking/ プレフィックスを付ける
```

### pre-commit フックが失敗する場合

```bash
cd apps/backend

# 品質チェックを手動実行してエラーを確認
./gradlew check -x test

# Frontend
cd ../frontend
npm run lint
```

エラー修正後に再度コミット。

# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、国際貨物輸送管理システム（Cargo Tracker F# 版）のアプリケーション開発環境をセットアップする手順を説明します。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 今日のソフトウェア開発の世界において絶対になければならない 3 つの技術的な柱があります。
> 三本柱と言ったり、三種の神器と言ったりしていますが、それらは
>
> - バージョン管理
> - テスティング
> - 自動化
>
> の 3 つです。
>
> — https://t-wada.hatenablog.jp/entry/clean-code-that-works

## 1. 前提条件

以下のツールがインストールされていることを確認してください。

| ツール | バージョン | 確認コマンド |
|--------|-----------|-------------|

| Docker Compose | v2.x | `docker compose version` |

.NET 10 SDK（LTS）をインストールします。

```bash
# macOS（Homebrew）
brew install --cask dotnet-sdk

# バージョン確認
dotnet --list-sdks
# 10.0.100 以上が表示されること
```

公式サイトから直接ダウンロードする場合：

- https://dotnet.microsoft.com/download/dotnet/10.0

Docker Desktop をインストールします。

- **Windows**: https://docs.docker.com/desktop/install/windows-install/
- **macOS**: https://docs.docker.com/desktop/install/mac-install/

```bash
# バージョン確認
docker -v

docker compose version
```

### Node.js のインストール

開発タスクランナー（Gulp）とドキュメントサイト運用に Node.js が必要です。

- https://nodejs.org/

```bash

```

## 5. プロファイル構成

開発効率を高めるため、環境別に設定を使い分けます。

| プロファイル | データベース | Docker | 用途 |
|-------------|------------|--------|------|
| Development | SQLite（ファイル DB） | 不要 | 日常開発・即座起動 |
| Production 互換 | PostgreSQL 16 | 必要 | 本番互換テスト |

### Development プロファイル（推奨：日常開発）

Docker なしで即座に起動できます。SQLite ファイル DB を使用し、起動時に DbUp がマイグレーションを適用します。

```bash
cd apps/cargo-tracker/src/CargoTracker.Web
dotnet run
```

### Production 互換プロファイル（PostgreSQL）

```bash
# PostgreSQL コンテナを起動
cd apps/cargo-tracker
docker compose up -d postgres

# PostgreSQL 接続で起動
cd src/CargoTracker.Web
ASPNETCORE_ENVIRONMENT=Staging dotnet run
```

## 8. テストの実行

### 全テスト実行

```bash
cd apps/cargo-tracker

# 全テスト実行（カバレッジ付き）
dotnet test --collect:"XPlat Code Coverage"
```

> **Note**: 統合テスト（Testcontainers）は Docker Desktop の起動が必要です。実 PostgreSQL 16 コンテナを自動起動して検証します。

### テストの種類

詳細は [テスト戦略](../design/test_strategy.md) を参照してください。

| テスト種別 | ツール | 説明 |
|-----------|--------|------|
| 単体テスト | xUnit + FsUnit + FsCheck | ドメインロジック・値オブジェクトのテスト（プロパティベース含む） |
| 統合テスト | Testcontainers for .NET | 実 PostgreSQL / SQLite 二方言のリポジトリテスト |
| アーキテクチャテスト | ArchUnitNET | レイヤー依存関係検証（4 ルール） |
| E2E テスト | Microsoft.Playwright | クリティカルパス 3 シナリオ |

### テストカバレッジ

```bash
# テストを実行してカバレッジレポートを生成
dotnet test --collect:"XPlat Code Coverage"

# HTML レポート生成（ReportGenerator）
dotnet tool run reportgenerator -reports:"**/coverage.cobertura.xml" -targetdir:"coverage-report"

# レポートの表示
# apps/cargo-tracker/coverage-report/index.html
```

カバレッジ目標: ドメイン層 85% 以上 / アプリケーション層 80% 以上（[テスト戦略](../design/test_strategy.md) 参照）

## 9. コード品質管理

### 静的コード解析ツール

| ツール | 目的 | コマンド |
|--------|------|---------|
| Fantomas | F# コードフォーマット | `dotnet fantomas .` |
| FSharpLint | Lint（コーディング規約検証） | `dotnet fsharplint lint CargoTracker.sln` |
| SonarQube | 静的解析・Quality Gate | `npx gulp sonar-local:check` |

### ツールのセットアップ（初回のみ）

Fantomas / FSharpLint は .NET ローカルツールとして管理します。

```bash
cd apps/cargo-tracker

# ツールマニフェストの復元
dotnet tool restore
```

### 品質チェックの実行

```bash
cd apps/cargo-tracker

# フォーマットチェック（CI と同一）
dotnet fantomas --check .

# Lint
dotnet fsharplint lint CargoTracker.sln

# すべてのテストと品質チェック
dotnet fantomas --check . && dotnet fsharplint lint CargoTracker.sln && dotnet test
```

### コード複雑度の基準

| 指標 | 閾値 | 説明 |
|------|------|------|
| 循環的複雑度 | 10 | 分岐・ループの複雑さ |
| ファイルサイズ | 500 行 | 1 ファイルの最大行数 |
| 関数サイズ | 150 行 | 1 関数の最大行数 |
| パラメータ数 | 7 | 関数の最大パラメータ数 |

### SonarQube（ローカル）

```bash
# SonarQube コンテナのセットアップ・起動
npx gulp sonar-local:setup

# スキャン + Quality Gate 確認
npx gulp sonar-local:check

# ダッシュボードを開く
npx gulp sonar-local:open
```

## 10. ディレクトリ構造

名前空間・レイヤー構成は [ADR-0001](../adr/0001-モジュール構成は垂直スライスを採用.md)（垂直スライス）に従います。

```
case-study-cargo-tracker/
├── apps/
│   └── cargo-tracker/
│       ├── CargoTracker.sln
│       ├── docker-compose.yml           # PostgreSQL 16（本番互換テスト用）
│       ├── .config/
│       │   └── dotnet-tools.json        # Fantomas / FSharpLint / ReportGenerator
│       ├── src/
│       │   ├── CargoTracker.Shared/     # 共有カーネル（Location, DomainEvent Payload, Ports）
│       │   ├── CargoTracker.Booking/    # 予約コンテキスト（Domain / Application / Infrastructure）
│       │   ├── CargoTracker.Shipper/    # 荷主コンテキスト
│       │   ├── CargoTracker.Routing/    # 経路コンテキスト
│       │   ├── CargoTracker.Tracking/   # 追跡コンテキスト
│       │   ├── CargoTracker.Handling/   # 荷役コンテキスト
│       │   ├── CargoTracker.Billing/    # 精算コンテキスト
│       │   ├── CargoTracker.Estimation/ # 見積コンテキスト
│       │   └── CargoTracker.Web/        # Giraffe ホスト（Api / Pages / CompositionRoot / Program.fs）
│       │       └── Scripts/
│       │           ├── postgresql/      # DbUp マイグレーション（PostgreSQL）
│       │           └── sqlite/          # DbUp マイグレーション（SQLite）
│       └── tests/
│           ├── CargoTracker.Tests/              # 単体テスト（xUnit + FsUnit + FsCheck）
│           ├── CargoTracker.IntegrationTests/   # 統合テスト（Testcontainers）
│           └── CargoTracker.ArchTests/          # アーキテクチャテスト（ArchUnitNET）
├── docs/                            # ドキュメント（MkDocs）
├── ops/                             # 運用スクリプト・Docker 設定
├── gulpfile.js                      # 開発タスクランナー
└── package.json                     # Node.js 依存関係
```

> **Note**: F# はファイル記述順にコンパイルされるため、各 `.fsproj` 内のファイル順は Domain → Application → Infrastructure の順を守ります（レイヤー依存方向の静的保証、ADR-0001 参照）。

## 12. Git 規約

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) に従います。

| タイプ | 説明 |
|--------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `chore` | ビルドプロセス・補助ツールの変更 |

### スコープ

境界づけられたコンテキストまたは領域を示すスコープを使用します。

```
feat(booking): 貨物予約登録機能を追加
fix(tracking): 追跡ステータスの導出誤りを修正
docs: セットアップ手順を更新
```

### コミット前チェック

コミット前に品質チェックを実行します。

```bash
cd apps/cargo-tracker

# フォーマット + Lint + テスト
dotnet fantomas --check . && dotnet fsharplint lint CargoTracker.sln && dotnet test
```

### Git Hooks（husky + lint-staged）

`npm install` 実行時に husky が自動セットアップされます（`prepare` スクリプト）。

コミット時、ステージされた F# ファイル（`apps/cargo-tracker/**/*.{fs,fsx}`）に対して以下が自動実行されます（`ops/scripts/precommit-fsharp.sh`）。

| ツール | 目的 | 備考 |
|--------|------|------|
| Fantomas | フォーマット自動修正 | 修正差分は lint-staged が自動で再ステージ |

> **Note**: FSharpLint は実行時間の都合（ソリューション単位で約 47 秒）から pre-commit には含めず、手動（`dotnet fsharplint lint CargoTracker.sln`）または CI で実行します。

緊急時にフックをスキップする場合（非推奨）：

```bash
git commit --no-verify -m "メッセージ"
```

## トラブルシューティング

### dotnet コマンドで SDK が見つからない

**問題**: `A compatible .NET SDK was not found` が表示される。

```
The command could not be loaded, possibly because:
  * You intended to execute a .NET application
```

**解決策**: .NET 10 SDK がインストールされているか確認し、`global.json` の SDK バージョン指定と一致させます。

```bash
dotnet --list-sdks
cat apps/cargo-tracker/global.json
```

### Testcontainers のテストが失敗する

**問題**: 統合テストで `Docker is not running` 等のエラーが発生する。

**解決策**: Docker Desktop を起動してから再実行します。

```bash
docker info   # Docker デーモンの稼働確認
dotnet test tests/CargoTracker.IntegrationTests
```

### ポート 8080 が使用中

**問題**: `Address already in use` で開発サーバーが起動しない。

**解決策**: 使用中のプロセスを終了します（`killing-processes` スキル参照）。

```bash
lsof -i :8080
kill -9 <PID>
```

### 品質チェックが失敗する場合

```bash
cd apps/cargo-tracker

# フォーマット違反を自動修正
dotnet fantomas .

# Lint エラーを確認して修正してから再度コミット
dotnet fsharplint lint CargoTracker.sln
```

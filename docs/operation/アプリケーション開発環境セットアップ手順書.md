# アプリケーション開発環境セットアップ手順書

## 概要

本ドキュメントは、国際貨物輸送管理システム（case-study-cargo-tracker）のアプリケーション開発環境をセットアップする手順を説明します。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> 今日のソフトウェア開発の世界において絶対になければならない 3 つの技術的な柱があります。
> 三本柱と言ったり、三種の神器と言ったりしていますが、それらは
>
> - バージョン管理
> - テスティング
> - 自動化
>
> の 3 つです。
>
> — https://t-wada.hatenablog.jp/entry/clean-code-that-works

### 環境の 3 段構え

本プロジェクトは環境を 3 段階で構成します。本書が対象とするのは **1 と 2** です。

| 段階 | 環境 | 基盤 | 用途 |
| :--- | :--- | :--- | :--- |
| 1 | 日常開発 | Gradle bootRun + H2（`local` プロファイル） | 単一サービスの TDD サイクル。Docker 不要で即座起動 |
| 2 | ローカル統合 | kind + Kustomize | 全 7 サービス + PostgreSQL + RabbitMQ の結合確認 |
| 3 | 開発 / ステージング / 本番 | Heroku / AWS ECS | [開発環境セットアップ手順書](開発環境セットアップ手順書.md) 以降を参照 |

| コマンド | 何をするか | いつ使うか |
| :--- | :--- | :--- |
| `npm run dev` | API をモック（MSW）した開発サーバを起動する | 画面だけを触るとき。バックエンドを起動しなくてよい |
| `npm run dev:api` | モックを使わず実バックエンドに繋ぐ開発サーバを起動する | モックを実物に差し替えて確かめるとき |
| `npm test` | ユニット・コンポーネントテストを 1 回実行する | 変更のたび |
| `npm run test:watch` | 同上を監視モードで実行する | TDD サイクル中 |

| `npm run lint` | oxlint を実行する | コミット前 |
| `npm run build` | 型検査 + 本番ビルド | デプロイ前・CI |
| `npm run test:e2e` | Playwright の E2E を実行する | 受け入れの確認 |

| `npm run test:e2e:real` | **実バックエンドに対する E2E**。kind の統合環境（`http://localhost`）に対して 1 本通す。事前に k8s の Gateway・authms・bookingms を起動する | モックで検証した機能を「動く」と言う前 |
| `npm run test:e2e:production` | **本番相当ビルドの検査**。動作確認用のログイン事前入力が焼き込まれていないことを確かめる | デプロイ前。**[ADR-006](../adr/006-demo-login-prefill.md) を守っているかを確かめる唯一の手段** |
| `npm run screenshots:manual` | ユーザーマニュアルの画面キャプチャを再生成する | 画面を変えたとき。PNG を手で差し替えない |
| `npx gulp manual:build` | マニュアルの Markdown を HTML に変換し `apps/www/manual` へ置く（**リポジトリルートで実行**） | キャプチャを撮ったあと。これを飛ばすと、読者が開く公開サイトのマニュアルだけ古いまま残る |

> `test:e2e:production` を飛ばすと、事前入力を有効にしたイメージを本番へ出しても誰も気づきません。

## 7. ローカル統合環境（kind + Kustomize）

全 7 サービスを結合して確認する場合は、kind クラスタ上に Kustomize でデプロイします。
Kustomize は素の Kubernetes マニフェストを base（共通の土台）と overlay（環境ごとの差分）に分けて合成します。

### 7.1 Kustomize ディレクトリ構成

```text
ops/k8s/kustomize/
├── base/
│   ├── kustomization.yaml      # 束ねる定義 + configMapGenerator + images
│   ├── namespace.yaml
│   ├── secret.yaml             # DB 認証（ローカル用）
│   ├── init-databases.sql      # 6 DB 作成（ConfigMap 化）
│   ├── postgres.yaml
│   ├── rabbitmq.yaml
│   ├── authms.yaml             # ┐
│   ├── bookingms.yaml          # │ サービスごとに Deployment + Service
│   ├── routingms.yaml          # │
│   ├── trackingms.yaml         # │
│   ├── handlingms.yaml         # │
│   ├── billingms.yaml          # ┘
│   ├── gatewayms.yaml
│   ├── frontend.yaml
│   ├── www.yaml                # ドキュメントポータル（apps/www）
│   └── ingress.yaml
└── overlays/
    ├── local/
    │   └── kustomization.yaml  # ローカル差分（replicas: 1、イメージタグ）
    └── ci/
        └── kustomization.yaml  # E2E 用差分
```

### 7.2 クラスタの作成

```bash
# Ingress 用のポートマッピングを持つクラスタを作成
# クラスタ名は kind-cluster.yaml の name（cargo）が使われる
kind create cluster --config ops/k8s/kind-cluster.yaml

# NGINX Ingress Controller の導入
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
kubectl -n ingress-nginx wait --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s
```

### 7.3 イメージのビルドとロード

```bash
# 全サービスの jar を一度にビルドし、サービスごとにイメージ化
cd apps/backend && ./gradlew bootJar -x test
for s in gatewayms authms bookingms routingms trackingms handlingms billingms; do
  docker build -t "cargo-$s:0.0.1" "$s"
done
cd ../frontend && docker build -t cargo-frontend:0.0.1 .
cd ../www && docker build -t cargo-www:0.0.1 .

# kind クラスタへイメージをロード（9 イメージ）
cd ../..
for s in gatewayms authms bookingms routingms trackingms handlingms billingms frontend www; do
  kind load docker-image "cargo-$s:0.0.1" --name cargo
done
```

### 7.4 デプロイと動作確認

```bash
# 合成結果の確認（クラスタに影響なし）
kubectl kustomize ops/k8s/kustomize/overlays/local

# 適用
kubectl apply -k ops/k8s/kustomize/overlays/local

# 10 Pod がすべて 1/1 Running になるまで待機（初回はイメージ取得を含め 3〜8 分）
kubectl -n cargo get pods -w

# フロントエンド（Ingress 経由）
curl -o /dev/null -w "%{http_code}\n" http://localhost/

# ドキュメントポータル（apps/www）
curl -o /dev/null -w "%{http_code}\n" http://localhost/docs-portal/

# 6 DB が作成されていること
kubectl -n cargo exec deploy/postgres -- \
  psql -U cargo_tracker -d postgres -tAc \
  "SELECT datname FROM pg_database WHERE datname LIKE '%_db' ORDER BY datname"

# RabbitMQ に各サービスが接続していること
kubectl -n cargo exec deploy/rabbitmq -- rabbitmqctl list_connections
```

> タスクランナーを使う場合は `npx gulp dev:k8s:up`（イメージ作成 → ロード → 適用 → 状態表示）で
> 7.3 と 7.4 をまとめて実行できます。ドキュメントポータルは `npx gulp dev:k8s:docs:open` で
> `http://localhost/docs-portal/` を開けます。

> ローカルでは PostgreSQL 1 台の中に各サービス専用のデータベース（auth_db〜billing_db）を作成します。
> Database per Service の論理分離は保ちつつ、開発の起動コストを抑えます。
> DB 起動待ちの再起動は `readinessProbe` の範囲で復帰させます（起動順序制御は作り込みません）。

### 7.5 クラスタの停止・削除

```bash
# デプロイのみ削除
kubectl delete -k ops/k8s/kustomize/overlays/local

# クラスタごと削除
kind delete cluster --name cargo
```

### テストの種類

テスト形状の設計方針は [テスト戦略](../design/test_strategy.md) を参照してください。

| テスト種別 | ツール | 対象 | 説明 |
| :--- | :--- | :--- | :--- |
| 単体テスト | JUnit 5 + Mockito + AssertJ | バックエンド | ドメインロジック（通関ガード・キャンセル承認・誤配検知・アカウントロック） |
| 統合テスト | Testcontainers（PostgreSQL / RabbitMQ） | バックエンド | 実 DB への SQL・イベント送受信 |
| アーキテクチャテスト | ArchUnit | バックエンド | レイヤー依存・BC 独立性（ACL ポートのみ越境可） |
| 契約テスト | Spring Cloud Contract | サービス間 | マイクロサービス間 API の契約 |
| コンポーネントテスト | Vitest + Testing Library | フロントエンド | React コンポーネント |
| API モックテスト | MSW | フロントエンド | API モックを使用した統合テスト |
| E2E テスト | Playwright | 全体 | kind + Kustomize（`overlays/ci`）上で主要シナリオを検証 |

### テストの規律

以下は過去の失敗から得た規律です。テストを書く際は必ず守ってください。

- **破壊検証**: 安全装置（通関ガード・アカウントロック・楽観的ロック）は「入れたこと」ではなく「働くこと」を検証する。実装を壊すと赤になるテストを対にする
- **分岐結果で判定**: 経過時間のアサートは脆弱な実装に戻しても緑になる。どの検査で落ちたか（分岐の結果）で判定する
- **同じ Clock**: 業務日付を扱うテストは本体と同じ `Clock`（業務タイムゾーン）を注入する。`LocalDate.now()` を直接呼ばない
- **CI（UTC）でも回す**: 日付判定を含むテストは `TZ=UTC` で一度実行して確認する
- **方言差の双方向スモーク**: 全クエリを PostgreSQL と H2 の両方で実行し、解釈できるかを確認する（「本番で緑・ローカルで赤」も同頻度で起きる）
- **本番経路の採番**: テストデータの ID は MAX+1 の自前採番をせず、本番と同じシーケンス経路で採番する

### テスト実行時の注意事項

- Testcontainers 使用時は Docker Desktop が起動している必要があります
- E2E テストは kind クラスタが必要です（`overlays/ci` を適用）。詳細は [E2E テストセットアップ手順書](E2Eテストセットアップ手順書.md) を参照してください

> **重要**: Port の追加や ADR の起票を伴う変更では、必ず `./gradlew test`（フル）を実行してください。
> レビューだけでは ArchUnit による構造的検証は代替できません。

## 10. 設計ドキュメント生成（JIG / jig-erd）

`docs/design` は「こう設計した」を、JIG と jig-erd の出力は「こう実装されている」を示します。
両者を突き合わせることで、設計と実装の乖離を目視ではなく生成物として検出できます。

> 生成物は `build/` 配下に出力され、Git 管理外です。コミットしません。

### 10.1 JIG（コードからの設計ドキュメント）

Java のバイトコードを解析し、パッケージ構造・ドメインモデル・使用箇所などを HTML で出力します。

```bash
npx gulp dev:jig          # 全サービス分を生成
npx gulp dev:jig:open     # 既定サービス（bookingms）のドキュメントを開く

# Gradle 直接実行
cd apps/backend
./gradlew jigReports              # 全サービス
./gradlew :bookingms:jigReports   # 個別サービス
```

出力先は各サービスの `build/jig/index.html` です（`shared` を含む 8 モジュール分）。

| 出力 | 内容 |
| :--- | :--- |
| `domain.html` | ドメインモデルの一覧と関連 |
| `usecase.html` | ユースケース（サービスメソッド）の一覧 |
| `package.html` | パッケージ関連図 |
| `inbound.html` / `outbound.html` | 入出力（Controller / Repository）の一覧 |
| `insight.html` | メトリクスに基づく気づき |

> 骨格の段階では「SQL が見つかりませんでした」「@Service がない」等の情報メッセージが出ます。
> 実装が進むにつれて出力が充実します。

### 10.2 jig-erd（実スキーマからの ER 図）

Testcontainers で PostgreSQL を起動し、Flyway が構築した**実際のスキーマ**から ER 図を生成します。
`docs/design/data-model.md` の ER 図は設計、jig-erd の出力は実装です。

```bash
npx gulp dev:jig-erd

# Gradle 直接実行
cd apps/backend
./gradlew jigErd              # DB を持つ 6 サービス分
./gradlew :bookingms:jigErd   # 個別サービス
```

出力先は各サービスの `build/jig-erd/` で、SVG が 3 種類（overview / summary / detail）生成されます。

**Database per Service のため、ER 図はサービスごとに分かれます。** サービスをまたぐ参照は
論理参照であり図には現れません。それが設計上正しい姿です（1 枚の全体 ER 図にはなりません）。

| 前提 | 確認コマンド |
| :--- | :--- |
| Docker（Testcontainers 用） | `docker info` |
| Graphviz | `dot -V` — 無ければ `brew install graphviz` |

`SchemaErdDocument` は検証を行わないドキュメント生成であるため、通常の `test` タスクからは
除外しています。`jigErd` タスクでのみ実行されます。

> **注意**: `jig.properties` の `jig.erd.filter.schema.pattern=public` は対象スキーマを
> public に限定する設定であり、Flyway 管理テーブルの除外ではありません。
> `flyway_schema_history` は図に現れます（実測）。

## 13. Git 規約

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) に従います。

| タイプ | 説明 |
| :--- | :--- |
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `chore` | ビルドプロセス・補助ツールの変更 |

### スコープ

サブシステムを示すスコープを使用します。

```text
feat(booking): 輸送中キャンセルの承認フローを追加
fix(tracking): 誤配検知が予定ルート外の荷役を拾わない問題を修正
docs: アプリケーション開発環境セットアップ手順書を作成
chore(setup): Gradle マルチプロジェクト基盤を構築
```

### Git Hooks（Husky + lint-staged）

コミット時に自動で品質チェックが実行されます。

`npm install` 実行時に Husky は自動的にセットアップされます（`prepare` スクリプト）。

Java ソースファイル（`apps/**/src/**/*.java`）に変更がある場合、Checkstyle・SpotBugs・テストが自動実行されます。いずれかが失敗するとコミットがブロックされます。

緊急時にフックをスキップする場合（非推奨）：

```bash
git commit --no-verify -m "メッセージ"
```

> **Warning**: フックのスキップは緊急時のみ使用してください。

## トラブルシューティング

### Gradle ビルドが失敗する

**問題**: Java バージョンが一致しない

```text
Unsupported class file major version 69
```

**解決策**: Java 25 がインストールされていることを確認

```bash
java -version
sdk use java 25-tem
```

### Gradle Wrapper が見つからない

**問題**: `gradlew: No such file or directory`

**解決策**: `apps/backend/` ディレクトリに移動してから実行

```bash
cd apps/backend
./gradlew build
```

### ポートが既に使用されている

**問題**: サービス起動時に `Port already in use` エラー

**解決策**: 使用中のプロセスを確認して停止

```bash
lsof -i :8082
kill -9 <PID>
```

### kind クラスタで Pod が Running にならない

```bash
kubectl -n cargo describe pod <Pod 名>
kubectl -n cargo logs <Pod 名>
```

| 症状 | 原因 | 対処 |
| :--- | :--- | :--- |
| `ImagePullBackOff` | イメージ未ロード | `kind load docker-image cargo-<svc>:0.0.1 --name cargo` |
| `CrashLoopBackOff`（DB 接続エラー） | postgres が未起動 | `readinessProbe` で自動復帰。数分待つ |
| Ingress にアクセスできない | Ingress Controller 未導入 | 7.2 の NGINX Ingress 導入手順を実行 |
| 正常起動しているのに再起動を繰り返す | exec probe の既定タイムアウト（1 秒）に診断コマンドが間に合わない | probe に `timeoutSeconds` を明示する（postgres / rabbitmq は設定済み） |

> **probe の注意**: ログ上は `Server startup complete` でも、liveness probe がタイムアウトすると
> 健全なコンテナが再起動ループに入ります。`kubectl describe pod` の Events で
> `Liveness probe failed: command timed out` が出ていないか確認してください。

### H2 Console に接続できない

`application.yml` で H2 Console が有効になっていることを確認します。

| 項目 | 値 |
| :--- | :--- |
| JDBC URL | `jdbc:h2:mem:booking_db` |
| User Name | `sa` |
| Password | （空欄） |

### pre-commit フックが失敗する場合

```bash
cd apps/backend
./gradlew checkstyleMain spotbugsMain
# エラーを修正してから再度コミット
```

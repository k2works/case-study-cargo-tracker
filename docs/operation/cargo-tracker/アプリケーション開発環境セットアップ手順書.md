# アプリケーション開発環境セットアップ手順書

## 概要

国際貨物輸送管理システム（Cargo Tracker）のアプリケーション開発環境をセットアップする手順です。

**この手順書に書かれている版とコマンドは、IT1 で実際に構築・実行して確認したものです。** 想定ではありません。版を上げるときは [技術スタック](../../design/cargo-tracker/tech_stack.md) の「バージョン管理方針」に従ってください。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> - バージョン管理
> - テスティング
> - 自動化
>
> — https://t-wada.hatenablog.jp/entry/clean-code-that-works

**Gradle は入れません。** リポジトリの Wrapper（`apps/cargo-tracker/backend/gradlew`、Gradle 9.5.0）が版を固定します。システムの Gradle を使うと版が食い違います。

### Java のインストール

Java 25 を入れます。Axon Framework 5 と Spring Boot 4 が要求する 17 以上を満たす最新 LTS です。

```bash
java -version
# openjdk version "25.0.2" のように表示されること
```

### Docker のインストール

- **macOS**: https://docs.docker.com/desktop/install/mac-install/
- **Windows**: https://docs.docker.com/desktop/install/windows-install/

```bash
docker -v
docker compose version
```

**Docker には十分なメモリを割り当ててください（8GB 以上を推奨）。** Axon Server は起動が遅く、機械が混んでいると Testcontainers の待ち時間を超えます。統合テストが「壊れた」ように見えて、実は待てば上がるだけ、という失敗が起きます。

**版が固定されている理由**（[ADR-0001](../../adr/cargo-tracker/0001-cqrs-es-with-axon-in-microservices.md)）:

- **Axon は 5.1.0-RC2 まで。** `axon-server-connector` が Maven Central に 5.0.0 と 5.1.0-RC2 しか公開されておらず、コアだけ上げると Axon Server に接続できません
- **Spring Boot は 4.0.6 まで。** Spring Cloud Gateway 5.0.x が Boot 4.0.x にしか対応せず、4.1 では起動しません
- **MyBatis は 4 系。** 3 系は Boot 3 向けで、Boot 4 では DataSource の自動設定に追随できず**黙って何もしません**

## 5. 依存ミドルウェアの起動

```bash
cd apps/cargo-tracker
docker compose up -d

# 起動確認
docker compose ps
```

DB とユーザーは `ops/k8s/base/postgres/init-databases.sql` が作ります。**この SQL は Kustomize と compose で共有しています。** 2 か所に持つと、片方だけ直したときに環境で食い違います。

```bash
# 6 つの DB ができていることを確認
docker exec cargo-tracker-postgres psql -U postgres -tAc \
  "SELECT datname FROM pg_database WHERE datistemplate=false ORDER BY 1"
# auth_db / billing_read_db / booking_read_db / handling_read_db /
# postgres / routing_read_db / tracking_read_db
```

### Axon Server の DCB について

compose は `AXONIQ_AXONSERVER_STANDALONE_DCB=true` を渡しています。**外さないでください。**

DCB が無効だと接続そのものが確立せず（実測は `AXONIQ-1302 default: not found in any replication group`）、しかも**アプリケーションは起動を止めずに無限再接続します**。起動時接続検査（後述）を入れているのはこのためです。

## 6. ビルドとテスト

```bash
cd apps/cargo-tracker/backend

# ビルド（ArchUnit・JaCoCo のレイヤー別閾値を含む）
./gradlew build

# 受け入れテスト（Cucumber・デモ項目の Gherkin）
./gradlew :acceptance-tests:test

# 契約テスト（ゴールデン JSON）
./gradlew :contract-tests:test

# 依存ミドルウェアを止める統合テスト（デモ項目 5）
./gradlew :bookingms:outageTest
```

`build` は Testcontainers で Axon Server と PostgreSQL を立てるため、**初回は 10 分程度かかります**。

### テストの種類

| 種別 | ツール | 対象 |
| :--- | :--- | :--- |
| 単体 | JUnit 5 + AxonTestFixture | 集約の不変条件 |
| 統合 | Testcontainers（Axon Server（DCB）+ PostgreSQL） | 投影・API・起動 |
| 契約 | ゴールデン JSON | 契約イベントの形（丸ごと一致） |
| 境界 | ArchUnit | レイヤー依存・共有カーネルの範囲・契約の名簿 |
| 受け入れ | Cucumber（日本語 Gherkin） | デモ項目 |
| E2E | Playwright | 画面からの到達性 |

### フロントエンド

```bash
cd apps/cargo-tracker/frontend
npm ci

npx tsc -b          # 型検査（--noEmit ではなく -b。参照構成では素通りする）
npm run lint        # ESLint（層をまたぐ import の禁止を含む）
npm run test        # Vitest
npm run test:coverage
npm run build
npx playwright install chromium
npm run e2e         # Playwright（到達性）
```

## 7. 開発サーバーの起動

### バックエンド

```bash
cd apps/cargo-tracker/backend
./gradlew :bookingms:bootRun     # 個別に起動
```

すべて起動する場合は jar をビルドして並べます。

```bash
./gradlew bootJar
for s in gatewayms authms bookingms routingms trackingms handlingms billingms; do
  java -jar $s/build/libs/$s-0.1.0-SNAPSHOT.jar &
done
```

**起動には 30〜60 秒かかります。** 起動時に Axon Server への接続と context の DCB を検査するためです。検査に落ちると**起動を止めます**（終了コード 1）。「繋がらないまま起動して、投影が永久に進まない」のを防ぐためです。

### フロントエンド

```bash
cd apps/cargo-tracker/frontend
npm run dev     # http://localhost:5173
```

`/api` は Vite の proxy が Gateway（8080）へ流します。フロントは各サービスの URL を知りません。

### 動作確認

```bash
# 全サービスの生死を 1 画面で
npx gulp ops:health

# 投影の進み具合（Processing Group ごとのトークン位置）
npx gulp projection:status
```

| サービス | URL |
| :--- | :--- |
| フロントエンド | http://localhost:5173 |
| API Gateway | http://localhost:8080 |
| Axon Server コンソール | http://localhost:8024 |
| ヘルスチェック | http://localhost:8080/actuator/health |

### 利用者の登録（初回のみ）

IT1 時点では利用者管理の画面がありません。検証用の利用者を直接入れます。

```bash
# BCrypt ハッシュを作る（例: パスワード secret1234）
# その後
docker exec cargo-tracker-postgres psql -U postgres -d auth_db -c \
  "INSERT INTO users (username, password_hash, display_name, enabled, failed_attempts, created_at, updated_at)
   VALUES ('sales01', '<ハッシュ>', '営業 太郎', TRUE, 0, now(), now());
   INSERT INTO user_roles (username, role) VALUES ('sales01','ROLE_SALES');"
```

## 8. kind（Kubernetes）での起動

```bash
npx gulp k8s:render     # マニフェストを描画して構文を確認（クラスタ不要）
npx gulp k8s:up         # kind クラスタを作って適用
npx gulp k8s:load       # イメージを載せ直して rollout restart
npx gulp k8s:down       # クラスタを消す
```

`k8s:load` が `rollout restart` まで踏むのは、**タグを据え置いたまま載せ直しても Pod は作り直されない**ためです。ここを飛ばすと、古いイメージのまま「反映した」と思い込みます。

## 12. CI

`.github/workflows/cargo-tracker.yml` が段ごとに分かれています。落ちた段で原因が分かるようにするためで、1 つにまとめるとログから探すことになります。

| ジョブ | 内容 |
| :--- | :--- |
| backend | `TZ=UTC ./gradlew build`（ArchUnit・JaCoCo 込み） |
| contract | 契約のゴールデン JSON |
| acceptance | デモ項目の Gherkin |
| frontend | 型検査・lint・単体・ビルド |
| e2e | Playwright（到達性） |
| docs | `gulp okf:check` |

**バックエンド系は `TZ=UTC` で回します。** ここで落ちるのは「テストが JVM 既定の `now()` を使っている」しるしで、本番でだけ時差の分ずれます。

## トラブルシューティング

### 起動が「Axon Server に 30 秒以内に接続できなかった」で止まる

依存ミドルウェアが起動していません。

```bash
cd apps/cargo-tracker && docker compose up -d && docker compose ps
```

**これは不具合ではなく設計です。** 繋がらないまま起動すると、投影が永久に進まないことに誰も気づけません。

### 統合テストが「Container startup failed / Timed out waiting for URL」で落ちる

機械が混んでいて Axon Server の起動が遅れています。Docker のメモリ割り当てを増やすか、他のコンテナを止めてから再実行してください。待てば上がります。

```bash
docker ps -a --format '{{.Names}}\t{{.Status}}'
```

### マイグレーションが走らないまま起動が成功する

`spring-boot-starter-flyway` が依存に入っているか確認してください。**`flyway-core` だけだと `FlywayAutoConfiguration` が classpath に無く、無音で何もしません。** Spring Boot 4 は自動設定をモジュールに分割しています。

### Mapper が「Invalid bound statement」で 500 になる

`application.yml` に `mybatis.mapper-locations` があるか確認してください。1 サービスで動いた設定を他が持っていない、という抜けは名乗り出ません。

### ログインできるのに業務画面がすべて 401 になる

フロントが `Authorization` を送っていない場合に起きます。`src/shared/api/client.ts` を確認してください。単体テストは `fetch` を差し替えるので判別できません。

### `npx tsc --noEmit` が何も検査しない

プロジェクト参照構成では `files: []` のため素通りします。**`npx tsc -b` を使ってください。**

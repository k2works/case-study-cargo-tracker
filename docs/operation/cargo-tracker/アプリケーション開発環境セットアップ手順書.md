# アプリケーション開発環境セットアップ手順書

## 概要

国際貨物輸送管理システム（Cargo Tracker）のアプリケーション開発環境をセットアップする手順です。

**この手順書に書かれている版とコマンドは、IT1 で実際に構築・実行して確認したものです。** 想定ではありません。版を上げるときは [技術スタック](../../design/cargo-tracker/tech_stack.md) の「バージョン管理方針」に従ってください。

テスト駆動開発（TDD）のゴールは **動作するきれいなコード** です。それを実現するためには [ソフトウェア開発の三種の神器](https://t-wada.hatenablog.jp/entry/clean-code-that-works) が必要です。

> - バージョン管理
> - テスティング
> - 自動化
>
> — https://t-wada.hatenablog.jp/entry/clean-code-that-works

### 環境の 3 段構え

本プロジェクトは環境を 3 段階で構成します。本書が対象とするのは **1 と 2** です。

| 段階 | 環境 | 基盤 | 用途 |
| :--- | :--- | :--- | :--- |
| 1 | 日常開発 | Gradle bootRun + docker compose（Axon Server・PostgreSQL） | 単一サービスの TDD サイクル |
| 2 | ローカル統合 | kind + Kustomize | 全 7 サービスの結合確認 |
| 3 | 開発 / ステージング / 本番 | — | 未整備。段階 2 が固まってから手順書を起こす |

**この構成には take-7 のような「Docker 不要の H2 プロファイル」がありません。** Event Store は
Axon Server であり、差し替えられる部品ではないためです（[ADR-0001](../../adr/cargo-tracker/0001-cqrs-es-with-axon-in-microservices.md) 決定 2）。
段階 1 でも Docker が要ります。

## 5. 依存ミドルウェアの起動

```bash
cd apps/cargo-tracker
docker compose up -d

# 起動確認
docker compose ps
```

DB とユーザーは `ops/k8s/base/postgres/init-databases.sql` が作ります。**この SQL は Kustomize と compose で共有しています。** 2 か所に持つと、片方だけ直したときに環境で食い違います。

```bash
# 6 つの DB ができていることを確認
docker exec cargo-tracker-postgres psql -U postgres -tAc \
  "SELECT datname FROM pg_database WHERE datistemplate=false ORDER BY 1"
# auth_db / billing_read_db / booking_read_db / handling_read_db /
# postgres / routing_read_db / tracking_read_db
```

### Axon Server の DCB について

compose は `AXONIQ_AXONSERVER_STANDALONE_DCB=true` を渡しています。**外さないでください。**

DCB が無効だと接続そのものが確立せず（実測は `AXONIQ-1302 default: not found in any replication group`）、しかも**アプリケーションは起動を止めずに無限再接続します**。起動時接続検査（後述）を入れているのはこのためです。

## 6. ビルドとテスト

```bash
cd apps/cargo-tracker/backend

# ビルド（ArchUnit・JaCoCo のレイヤー別閾値を含む）
./gradlew build

# 受け入れテスト（Cucumber・デモ項目の Gherkin）
./gradlew :acceptance-tests:test

./gradlew :contract-tests:test

# 依存ミドルウェアを止める統合テスト（デモ項目 5）
./gradlew :bookingms:outageTest
```

`build` は Testcontainers で Axon Server と PostgreSQL を立てるため、**初回は 10 分程度かかります**。

### テストの種類

| 種別 | ツール | 対象 |
| :--- | :--- | :--- |
| 単体 | JUnit 5 + AxonTestFixture | 集約の不変条件 |
| 統合 | Testcontainers（Axon Server（DCB）+ PostgreSQL） | 投影・API・起動 |
| 契約 | ゴールデン JSON | 契約イベントの形（丸ごと一致） |
| 境界 | ArchUnit | レイヤー依存・共有カーネルの範囲・契約の名簿 |
| 受け入れ | Cucumber（日本語 Gherkin） | デモ項目 |
| E2E | Playwright | 画面からの到達性 |

### テストの規律

以下は過去の失敗から得た規律です。テストを書くときは必ず守ってください。

- **破壊検証**: 安全装置（起動時接続検査・重複の記録・鍵の破棄）は「入れたこと」ではなく
  「働くこと」を検証する。実装を壊すと赤になるテストを対にする
- **分岐結果で判定**: 経過時間のアサートは脆弱な実装に戻しても緑になる。どの検査で落ちたか
  （分岐の結果）で判定する
- **同じ Clock**: 業務日付を扱うテストは本体と同じ `Clock`（業務タイムゾーン）を注入する。
  `LocalDate.now()` を直接呼ばない（ArchUnit が禁止している）
- **CI（UTC）でも回す**: 日付判定を含むテストは `TZ=UTC` で一度実行して確認する
- **本番と同じ形で立てる**: Axon Server は DCB を有効にして立てる。ここを緩めると、
  テストが緑でも本番だけ動かない

## 8. kind（Kubernetes）での起動

初めて立ち上げるときは `k8s:setup` を使います。`portal:artifacts` → `k8s:images` →
`k8s:up` → `k8s:load` → `k8s:wait` → `k8s:status` をこの順で踏みます。

```bash
npx gulp k8s:setup      # ゼロから立ち上げる（初回は 30 分程度）
npx gulp k8s:open       # port-forward を張って画面を開く（Ctrl+C まで転送が続く）
npx gulp k8s:down       # クラスタを消す
```

内訳のタスクは個別にも回せます。

```bash
npx gulp k8s:render     # マニフェストを描画して構文を確認（クラスタ不要）
npx gulp portal:artifacts  # ポータルが配る生成物（ドキュメント・マニュアル）を作る
npx gulp k8s:images     # 9 イメージ（7 サービス + フロントエンド + ポータル）を作る
npx gulp k8s:up         # kind クラスタを作って適用
npx gulp k8s:load       # イメージを載せ直して rollout restart
npx gulp k8s:wait       # 全 Pod が Ready になるまで待つ
npx gulp k8s:status     # Pod の状態を表示
npx gulp k8s:help       # コマンド一覧
```

コードを直してクラスタに反映したいだけなら `k8s:images` → `k8s:load` で足ります。

**`k8s:wait` を最後に置いているのは、`rollout restart` が投げるだけで待たないためです。**
待たずに一覧を出すと、立ち上げに成功していても最後の画面が `Init:0/1` と `Terminating` で
埋まり、失敗したように見えます。`k8s:wait` はリソースを依存の順（土台 → 業務サービス →
画面）に待ち、1 つずつ `Ready` を出します。落ちたものがあっても残りを続けて見るので、
どこまで上がったかが分かります。

> `kubectl wait --for=condition=Ready pod -l app=...` は使っていません。ラベルは
> **終了中の Pod にも一致する**ため、入れ替えの最中に張ると消えていく Pod を待ち続けて
> 必ずタイムアウトします。世代を見ている `rollout status` で待ちます。

`k8s:load` が `rollout restart` まで踏むのは、**タグを据え置いたまま載せ直しても Pod は作り直されない**ためです。ここを飛ばすと、古いイメージのまま「反映した」と思い込みます。

**`k8s:up` を単独で回してはいけません。** `k8s:up` が踏むのはクラスタ作成とマニフェストの
適用だけです。イメージが無いまま適用すると Pod は `ImagePullBackOff` で止まりますが、
`kubectl logs` が返すのは完了済みの init コンテナが残した「Axon Server を待っています」で、
原因がイメージ側にあることが読み取れません。`k8s:setup` はこの順序を落とせないようにするために
あります。

### イメージの作り方（`k8s:images`）

ビルドは各サービスの `Dockerfile` の中で行い、**ホストの `build/` は持ち込みません**（`.dockerignore`）。
持ち込むと、ローカルで何を回したかによってイメージの中身が変わります。

Gradle は入れず Wrapper を使います。イメージの中だけ別の版で組むと、ローカルで通ったビルドが
本番だけ落ちます。テストはイメージのビルドでは回しません——Testcontainers が Docker の中で
Docker を要求することになるためで、テストは CI が回します。

フロントエンドは Vite でビルドしたものを nginx が配ります。`npm run build` は `tsc -b` を
通ってから `vite build` に入る（`package.json`）ので、**型が壊れたイメージはできません**。

nginx は 2 つのことをしています。

- SPA のルーティングはクライアント側にあるので、存在しないパスは `index.html` に落とす。
  落とさないと、画面を開いたまま再読み込みしただけで 404 になります
- `/api/` を `http://gatewayms:8080` に中継し、**外から来た `X-Auth-*` を空にして渡す**。
  利用者の身元は Gateway だけが決めます（[ADR-0001](../../adr/cargo-tracker/0001-cqrs-es-with-axon-in-microservices.md) 決定 4）。
  Gateway 側でも必ず上書きしていますが、「上書きしているから大丈夫」を前提にすると、
  上書きを緩めた日に破れます

生死は `/healthz` で見ます。`index.html` を見ると、中身が壊れていても 200 が返ります。

### 起動の順序

全 Pod が上がるまで **5〜10 分** かかります。順序には理由があります。

1. `postgres` と `axonserver` が先に上がる
2. 業務サービスは `initContainer` で **Axon Server が応答するまで待つ**
3. フロントエンドは待たない。静的配信と `/api` の中継だけなので、後段が落ちていても
   画面は出る。出したうえで API のエラーを見せるほうが、白い画面より原因に近い

待たせているのは、業務サービスが起動時に接続を検査して繋がらなければ**起動を止める**
（`AxonServerStartupCheck`）ためです。待たずに一斉に立てると 7 サービスが落ちては再起動を
繰り返し、単一ノードの kind ではその CPU で Axon Server 自身の起動がさらに遅れます
（実測: CPU 681%、Axon Server の起動が 2 分超に延びて全体が上がらない）。

Deployment の更新戦略は `Recreate` です。既定の `RollingUpdate` だと新しい Pod が Ready に
なるまで古い Pod が残り、単一ノードでは JVM が 2 倍立ちます。

### 荷主ごとの鍵は Pod の寿命に載せない

bookingms の鍵置き場（[ADR-0003](../../adr/cargo-tracker/0003-crypto-shredding-for-personal-data.md)）は PVC に載せています。
**鍵を失うと暗号化済みの荷主データは二度と読めません**——破棄したのと同じことになります。
本番は KMS の実装を当てるので、この PVC はローカル・CI 限りです。

### 動作確認用の利用者

クラスタでも同じ利用者が入ります。`authms` の `CARGOTRACKER_DEMOUSERS=true`（マニフェスト）と、
フロントのイメージのビルド引数 `VITE_DEMO_LOGIN_ENABLED=true`（`k8s:images` が渡す）の 2 つが
揃って、ログイン画面に一覧が出ます。顔ぶれとパスワードは上の表と同じです。

入っているか確かめる:

```bash
kubectl --context kind-cargo-tracker -n cargo-tracker exec postgres-0 -- \
  psql -U postgres -d auth_db -c "SELECT username, enabled FROM users ORDER BY 1"
```

### 動いていることの確かめ方

`k8s:open` を別ターミナルで動かしたまま実行します。

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"sales01","password":"secret1234"}' | jq -r .token)

# 書き（コマンド → イベント）
curl -s -X POST http://localhost:8080/api/v1/booking/shippers \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"アクメ商事","email":"acme@example.com","shipperType":"CORPORATE",
       "contractNumber":"C-0001","discountRate":"0.05"}'

# 読み（投影）。返ってきた shipperId で引く
curl -s http://localhost:8080/api/v1/booking/shippers/<shipperId> \
  -H "Authorization: Bearer $TOKEN"
```

**読みでメールアドレスが返れば、鍵の読み書きまで通っています**（[ADR-0003](../../adr/cargo-tracker/0003-crypto-shredding-for-personal-data.md)）。
`null` なら鍵が読めていません。

### クラスタの中を見る（`k8s:open`）

**クラスタには Ingress がなく、Service はすべて ClusterIP です。** ホストからは何も見えないので、
`k8s:open` が `kubectl port-forward` を張ってから開きます。

| 転送先 | ローカルの URL |
| :--- | :--- |
| フロントエンド | http://localhost:3000 |
| API Gateway | http://localhost:8080 |
| Axon Server コンソール | http://localhost:8024 |

**画面を触るだけなら 3000 の 1 つで足ります。** クラスタのフロントエンドは自分の nginx で
`/api` を Gateway に中継するためです。5173 を避けているのは、ローカルの Vite 開発サーバと
取り違えないためです。

転送は **タスクが生きているあいだだけ** 有効です。バックグラウンドに逃がしていないのは、
切り忘れた転送が残ると「いまどのクラスタを見ているか」が分からなくなるためです。
終わるときは Ctrl+C を押します。

ローカルの Vite 開発サーバ（5173）も併用できます。`/api` が転送済みの Gateway に繋がります。

**`k8s:load` を実行すると転送は切れます。** `kubectl port-forward` は起動時の Pod に張り付くため、
Pod が作り直されると死にます。応答が空になったら `k8s:open` を起動し直してください。

**依存ミドルウェアを `docker compose` で上げたままだと同じポートを取り合います。** その場合
`k8s:open` は転送を張る前に止まり、どのポートが使用中かを表示します。
`docker compose down` してから実行してください。

## 10. 設計ドキュメント生成（JIG / jig-erd）

`docs/design` は「こう設計した」を、JIG と jig-erd の出力は「こう実装されている」を示します。
両者を突き合わせることで、設計と実装の乖離を目視ではなく生成物として検出できます。

> 生成物は `build/` 配下に出力され、Git 管理外です。コミットしません。

### 10.1 JIG（コードからの設計ドキュメント）

Java のバイトコードを解析し、パッケージ構造・ドメインモデル・使用箇所などを HTML で出力します。

```bash
./gradlew :bookingms:jigReports   # 個別
```

出力先は各サブプロジェクトの `build/jig/index.html` です（業務 8 + テスト専用 2 の 10 モジュール分）。

| 出力 | 内容 |
| :--- | :--- |
| `domain.html` | ドメインモデルの一覧と関連 |
| `usecase.html` | ユースケース（サービスメソッド）の一覧 |
| `package.html` | パッケージ関連図 |
| `inbound.html` / `outbound.html` | 入出力（Controller / Repository）の一覧 |
| `insight.html` | メトリクスに基づく気づき |

### 10.2 jig-erd（実スキーマからの ER 図）

Testcontainers で PostgreSQL を起動し、Flyway が構築した**実際のスキーマ**から ER 図を生成します。
`docs/design/cargo-tracker/data_model.md` の ER 図は設計、jig-erd の出力は実装です。

```bash
npx gulp dev:jig-erd

# Gradle 直接実行
cd apps/cargo-tracker/backend
./gradlew jigErd              # DB を持つ 6 サービス分
./gradlew :bookingms:jigErd   # 個別
```

出力先は各サービスの `build/jig-erd/` で、SVG が 3 種類（overview / summary / detail）生成されます。

**Database per Service のため、ER 図はサービスごとに分かれます。** サービスをまたぐ参照は
論理参照であり図には現れません。それが設計上正しい姿です（1 枚の全体 ER 図にはなりません）。

| 前提 | 確認コマンド |
| :--- | :--- |
| Docker（Testcontainers 用） | `docker info` |
| Graphviz | `dot -V` — 無ければ `brew install graphviz` |

生成を行う `SchemaErdDocument` は**何も検証しないドキュメント生成**であるため、通常の `test`
タスクからは除外しています（`jigErd` でのみ実行）。**Spring のコンテキストは起動しません**
——見たいのは Flyway が作るスキーマだけで、図を 1 枚描くために Axon Server まで立てる必要は
ないためです。

## 13. Git 規約

### コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) に従います。

| タイプ | 説明 |
| :--- | :--- |
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更 |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` / `ci` / `chore` | ビルド・CI・補助ツールの変更 |

スコープはサービス名（`booking`・`auth`・`gateway`・`frontend`・`ops`）です。

```text
feat(booking): 荷主の投影と要確認一覧を置く
fix(frontend): 型検査を通す
docs(adr): ADR-0001 決定 6 に再評価の発動条件を追記する
```

### Git Hooks（Husky + lint-staged）

`npm install` を実行すると、`prepare` スクリプトで Husky が自動的にセットアップされます
（`core.hooksPath` が `.husky/_` に設定されます）。

| フック | 何をするか |
| :--- | :--- |
| `pre-commit` | lint-staged 経由で、変更のあった層だけを検査する |
| `commit-msg` | Conventional Commits に従わないメッセージを弾く |

`pre-commit` の実体は `ops/hooks/` のスクリプトです。

| 変更ファイル | 実行される検査 |
| :--- | :--- |
| `apps/cargo-tracker/backend/**/*.java` | Checkstyle + SpotBugs（`ops/hooks/backend-check.sh`） |
| `apps/cargo-tracker/frontend/**/*.{ts,tsx}` | `tsc -b` + ESLint（`ops/hooks/frontend-check.sh`） |

**変更ファイルの一覧はスクリプトに渡していますが使いません。** Checkstyle も SpotBugs も
モジュール単位でしか走らないためで、lint-staged からは「Java が変わった」という合図として
呼ばれています。

緊急時にフックをスキップする場合（非推奨）:

```bash
git commit --no-verify -m "メッセージ"
```

## トラブルシューティング

### 起動が「Axon Server に 30 秒以内に接続できなかった」で止まる

依存ミドルウェアが起動していません。

```bash
cd apps/cargo-tracker && docker compose up -d && docker compose ps
```

**これは不具合ではなく設計です。** 繋がらないまま起動すると、投影が永久に進まないことに誰も気づけません。

### 統合テストが「Container startup failed / Timed out waiting for URL」で落ちる

機械が混んでいて Axon Server の起動が遅れています。Docker のメモリ割り当てを増やすか、他のコンテナを止めてから再実行してください。待てば上がります。

```bash
docker ps -a --format '{{.Names}}\t{{.Status}}'
```

### マイグレーションが走らないまま起動が成功する

`spring-boot-starter-flyway` が依存に入っているか確認してください。**`flyway-core` だけだと `FlywayAutoConfiguration` が classpath に無く、無音で何もしません。** Spring Boot 4 は自動設定をモジュールに分割しています。

### Mapper が「Invalid bound statement」で 500 になる

`application.yml` に `mybatis.mapper-locations` があるか確認してください。1 サービスで動いた設定を他が持っていない、という抜けは名乗り出ません。

### ログインできるのに業務画面がすべて 401 になる

フロントが `Authorization` を送っていない場合に起きます。`src/shared/api/client.ts` を確認してください。単体テストは `fetch` を差し替えるので判別できません。

### `npx tsc --noEmit` が何も検査しない

プロジェクト参照構成では `files: []` のため素通りします。**`npx tsc -b` を使ってください。**

### pre-commit フックが失敗する

どの検査で落ちたかは出力に出ます。手で再現してから直してください。

```bash
npx gulp dev:backend:check      # Checkstyle + SpotBugs
npx gulp dev:frontend:lint      # ESLint
```

### kind の Pod が Running のまま Ready にならない

まず何を待っているかを見ます。

```bash
kubectl --context kind-cargo-tracker -n cargo-tracker get pods
kubectl --context kind-cargo-tracker -n cargo-tracker describe pod <Pod 名>
kubectl --context kind-cargo-tracker -n cargo-tracker logs <Pod 名>
```

| 症状 | 原因 | 対処 |
| :--- | :--- | :--- |
| `Init:0/1` のまま | Axon Server がまだ上がっていない | 正常。`axonserver-0` が `1/1` になるまで待つ |
| `ErrImagePull` / `ImagePullBackOff` | イメージを作っていないか、kind に載せていない | `npx gulp k8s:images` → `npx gulp k8s:load`（初回なら `npx gulp k8s:setup`） |
| `error: context "kind-cargo-tracker" does not exist` | クラスタはあるが kubeconfig に context が無い（作成の中断、他のツールによる current-context の奪取） | `kind export kubeconfig --name cargo-tracker`。`k8s:up` は毎回これを踏むので、通常は起きない |
| ログが「Axon Server を待っています」で止まって見える | `kubectl logs` が**完了済みの init コンテナ**のログを返している。本体は別の理由で起動していない | `npx gulp k8s:status` で `STATUS` を見る。`Initialized: True` なら init は通っている |
| イメージのビルドが `exit code: 127` で落ちる | `gradlew` が CRLF でチェックアウトされ、shebang の行末に CR が残って `/bin/sh` を解決できない | `.gitattributes` の `gradlew text eol=lf` を効かせる。`rm gradlew && git checkout -- gradlew` で取り直す |
| `axonserver-0` が `Exit Code: 137` で再起動を繰り返す | liveness probe が起動を待ちきれずに殺している | 起動待ちは `startupProbe` に任せる（設定済み）。**`initialDelaySeconds` を伸ばして凌がない**——機械の混み具合で毎回変わる |
| gatewayms / authms が `CrashLoopBackOff` | 本番相当（`CARGOTRACKER_PRODUCTIONLIKE=true`）で開発用の JWT 既定鍵が配られている | マニフェストの鍵を変える。`ClusterJwtSecretTest` が同じ値を弾く |
| bookingms が `AccessDeniedException: /app/./.keys` | コンテナの `/app` が root 所有で、非 root の実行利用者が書けない | Dockerfile で `chown` 済み。イメージを作り直す |

> **`docker stats cargo-tracker-control-plane` で CPU を見てください。** 800% 近くに
> 張り付いているときは、遅いのではなく資源が足りていません。Docker への割り当てを増やすか、
> 他のコンテナを止めてから作り直します。

### `jigErd` が「dot: command not found」で落ちる

Graphviz が入っていません。

```bash
brew install graphviz && dot -V
```

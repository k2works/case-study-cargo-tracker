# 新サービス追加チェックリスト

新しいマイクロサービスを追加する際に、登録漏れによる E2E 失敗・デプロイ失敗を防ぐためのチェックリストです。

## 背景

IT2 で `bookingms` を追加した際、次の登録漏れが発生しました（[IT2 ふりかえり](../development/retrospective-2.md) Problem #1・#2）。

- **gatewayms の `local-h2` プロファイルに `bookingms` ルートが未登録**だったため、E2E 実行時に `/api/v1/shippers` が 404 となり原因特定に時間を要した。
- **`deploy:dev` の `SERVICES` / `DEPLOY_ORDER` に `bookingms` が未登録**だったため、Heroku デプロイスクリプトが当該サービスを対象にせず、レビューで初めて発覚した。

これらは「サービス追加時に更新すべき箇所」が一覧化されていなかったことが原因です。本チェックリストで再発を防ぎます。

IT7 で `billingms` を追加するにあたり、IT5/IT6 の追加（`trackingms` / `handlingms`）と本チェックリストを照合してドライラン検証を実施し、本版（IT7 改訂版）で **ポート番号一覧の最新化・Axon テーブル V1 SQL パターン・LocalH2SmokeTest パターン・cross-service イベント設計の確認章** を反映しました。

> **適用範囲**: 新しい **マイクロサービス**（Gradle サブモジュール）を追加する場合に使用します。既存サービス内へのエンドポイント追加（例: IT3 の `/api/v1/quotes`・`/api/v1/voyages/search` は既存 `bookingms`・`routingms` 内）は本チェックリストの対象外です（gatewayms のパスプレフィックスが既存ルートでカバーされているか確認するだけで足ります）。

## チェックリスト

### 1. アプリケーション本体

- [ ] `apps/backend/<service>ms/` に Gradle サブモジュールを作成
- [ ] `apps/backend/settings.gradle` に `include '<service>ms'` を追加
- [ ] `apps/backend/<service>ms/build.gradle` に Spring Boot + Axon + MyBatis 依存を設定
- [ ] ポート番号を採番（既存割当）

#### 既存ポート番号一覧（IT7 時点、`ops/scripts/heroku.js` を SSOT とする）

| サービス | ポート | 追加時期 |
| :--- | :--- | :--- |
| `gatewayms` | 8080 | IT1 |
| `authms` | 8081 | IT1 |
| `bookingms` | 8082 | IT2 |
| `routingms` | 8083 | IT1 |
| `trackingms` | 8084 | IT5 |
| `handlingms` | 8085 | IT5 |
| `billingms` | 8086 | **IT7（採番）** |
| `frontend` | 80 | IT1 |

新サービス追加時は **`ops/scripts/heroku.js` の `SERVICES` 配列を一次情報** として、未使用ポートを採番してください。

### 2. gatewayms ルーティング（4 プロファイルすべて）

`apps/backend/gatewayms/src/main/resources/` の **4 プロファイル全て** に新サービスのルートを追加します。1 つでも漏れると当該環境で 404 になります。**「local-h2 / heroku の 2 つだけ」では不足です（local-docker と application.yml も必要）。**

- [ ] `application-local-h2.yml`（ローカル H2・E2E 用、`uri: http://localhost:<port>`）
- [ ] `application-local-docker.yml`（Docker Compose 用、`uri: http://<service>ms:<port>`）
- [ ] `application-heroku.yml`（Heroku 用、`uri: ${<SERVICE>MS_URL}` 等）
- [ ] `application.yml`（デフォルト・共通設定、CORS / actuator など共通項目）

設定例（`application-local-h2.yml`）:

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: <service>ms
          uri: http://localhost:<port>
          predicates:
            - Path=/api/v1/<resource>/**
```

### 3. ローカル実行（Docker Compose）

- [ ] `apps/docker-compose.yml` にサービス定義（image / ports / depends_on / 環境変数）を追加
- [ ] ルートの `docker-compose.yml` にも必要なら追加
- [ ] 専用 Read Model DB（`<service>_read_db`）のコンテナ・初期化を追加
- [ ] Kafka を使う場合は `KAFKA_BOOTSTRAP_SERVERS` / `axon.kafka.consumer.event-processor-mode=tracking` などを各プロファイルに反映

### 4. デプロイ（`ops/scripts/heroku.js`）

- [ ] `SERVICES` 配列に `{ name: \`${PREFIX}-<service>ms\`, service: '<service>ms', port: <port>, type: 'backend' }` を追加
- [ ] `DEPLOY_ORDER` 配列に依存順序を考慮して `'<service>ms'` を追加
- [ ] `deploy:dev:setup` の Heroku アプリ作成手順ガイド（`heroku create ${PREFIX}-<service>ms --stack container`）に反映
- [ ] `deploy:dev:config` で他サービスのドメイン参照が必要なら追記
- [ ] `deploy:dev:build:backend` のサービスフィルタ（`SERVICES.type === 'backend'`）に新サービスが自動的に含まれることを確認
- [ ] `deploy:dev:help` のサービス一覧に追記（IT6 の事例：bookingms / trackingms / handlingms が一覧から漏れていた）

### 5. 品質管理（`apps/backend/sonar-project.properties`）

- [ ] `sonar.sources` に `<service>ms/src/main` を追加
- [ ] `sonar.tests` に `<service>ms/src/test` を追加
- [ ] `sonar.java.binaries` に `<service>ms/build/classes` を追加
- [ ] `sonar.java.test.binaries` に `<service>ms/build/classes` を追加
- [ ] `sonar.coverage.jacoco.xmlReportPaths` に `<service>ms/build/reports/jacoco/test/jacocoTestReport.xml` を追加

### 6. データベース・マイグレーション

- [ ] `apps/backend/<service>ms/src/main/resources/db/migration/` に Flyway マイグレーションを配置
- [ ] [データモデル設計](../design/data-model.md) の該当 Read Model テーブル定義と整合
- [ ] **Axon Framework が必要とするテーブル**（`V1__create_axon_tables.sql`）を配置。`tokenentry` / `sagaentry` / `associationvalueentry` / `domainevententry` / `snapshotevententry` の 5 テーブルが標準。
- [ ] Read Model テーブル定義は `V2__create_<context>_tables.sql` 以降に配置（schema 進化を理解しやすくする命名）
- [ ] H2 互換が必要な場合は `db/migration/h2/` 配下に並行配置（trackingms / handlingms 既存パターン）

Axon V1 マイグレーションのパターン例（PostgreSQL）:

```sql
CREATE TABLE IF NOT EXISTS tokenentry (
    processorname VARCHAR(255) NOT NULL,
    segment       INTEGER      NOT NULL,
    token         BYTEA,
    tokentype     VARCHAR(255),
    timestamp     VARCHAR(255),
    owner         VARCHAR(255),
    PRIMARY KEY (processorname, segment)
);
-- 同様に sagaentry / associationvalueentry / domainevententry / snapshotevententry も作成
```

### 7. テスト・疎通確認

- [ ] `<Service>MsLocalH2SmokeTest` を追加（`ApplicationContext` assertion パターン）
- [ ] `./gradlew :<service>ms:test` が PASS
- [ ] gatewayms 経由で `GET http://localhost:8080/api/v1/<resource>/...` が 200 を返す（404 でないこと）
- [ ] フロントエンド E2E（Playwright）で当該サービスのシナリオを追加・実行
- [ ] `./gradlew check`（全サービス）が PASS

LocalH2SmokeTest のパターン例（`<ServiceName>MsLocalH2SmokeTest.java`）:

```java
@SpringBootTest(
        webEnvironment = SpringBootTest.WebEnvironment.NONE,
        properties = {
                "axon.axonserver.enabled=false",
                "axon.kafka.publisher.enabled=false",
                "axon.kafka.fetcher.enabled=false"
        }
)
@ActiveProfiles("local-h2")
class XxxMsLocalH2SmokeTest {
    @Autowired
    private ApplicationContext context;

    @Test
    void localH2プロファイルでコンテキストを起動できる() {
        assertThat(context).isNotNull();
        assertThat(context.getBeanDefinitionCount()).isGreaterThan(0);
    }
}
```

このパターンは IT5 H6/H7 + IT6 で確立。SonarQube Quality Gate の `new_violations` 0 維持にも貢献します（空の `@Test` を Code Smell として検出される問題を回避）。

### 8. cross-service イベント設計の確認

新サービスが cross-service イベント連携を必要とする場合（多くは必要）、以下の ADR を確認・遵守してください。

- [ ] **ADR-0009 cross-service Saga**: Kafka tracking モードでイベントを購読する基本パターン
- [ ] **ADR-0011 Kafka tracking エラーハンドリング**: ホワイトリスト方式で例外を扱う方針
- [ ] **ADR-0012 cross-service 冪等性**: 集約発火型 + 投影フラグ列 + 待避テーブルの 3 規約
- [ ] **ADR-0014 @ProcessingGroup 命名規約**: `cross-` / `local-` / `outbound-` の 3 種類 prefix
- [ ] **ADR-0015 ShipperInfo ACL** （bookingms と連携する場合）: REST 同期 + Resilience4j + Caffeine cache + 手動入力 fallback の 3 層パターン
- [ ] **ADR-0016 @ProcessingGroup 一斉改名 + token 移行**: 改名適用と本番 token 移行手順
- [ ] 新サービス特有の cross-service 連携方針があれば、新規 ADR を起票（例: IT7 で billingms 用に ADR-0015 起票）

## IT3 での適用メモ

IT3（見積・航海検索・予約引渡し・予約確定）では **新規マイクロサービスは追加しません**。

- US01 見積は `bookingms` 内に `Quotation` 集約を追加（既存サービス拡張）
- US07 航海検索は `routingms` に検索クエリを追加（既存サービス拡張）
- gatewayms の `local-h2` ルートは `/api/v1/quotes/**`（bookingms）・`/api/v1/voyages/**`（routingms）を **すでにカバー済み**（追加不要）
- `deploy:dev` の `SERVICES` / `DEPLOY_ORDER`・sonar にも bookingms / routingms は登録済み

したがって IT3 ではセクション 6（`quotation` テーブルの Flyway マイグレーション）が主な作業で、サービス登録系（セクション 2・4・5）は確認のみで完了します。

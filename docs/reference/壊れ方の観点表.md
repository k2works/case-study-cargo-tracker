# 壊れ方の観点表

受入基準を書くとき、実装する前に機械的に当てるチェックリストです。

## なぜこの表が要るのか

IT3 のふりかえりで「テストが緑」と「運用で壊れない」の混同を Problem に挙げ、
Try として **「受入基準に『壊れ方』を 1 項目入れる」** を実行しました。
それでも IT4 のレビューで、**全テストが緑のまま 6 件の欠陥**が見つかりました。

原因を調べると、書いた壊れ方（重複時に 500 にしない、存在しない荷主で 500 にしない）は
**すべて実装・テストされていました**。残ったのは**書かなかった壊れ方**です。

> Try は「壊れ方を書く」ことしか求めておらず、**壊れ方を洗い出す方法**を与えていなかった。
> 思いついたものは書けるが、思いつかないものは書けない。
>
> — IT4 ふりかえり P1

この表は、その「洗い出す方法」です。**思いつきに頼らないこと**が目的であり、
網羅の保証ではありません。当てはまらない軸は「当てはまらない」と書いて飛ばします。

## 使い方

1. 受入基準を書いたら、4 軸をひとつずつ当てる
2. 各行について「起こり得るか」「起こったらどうなるか」「テストで固定するか」を決める
3. **飛ばした行は理由を書く**。無言で飛ばすと、次も同じところで落ちる
4. 決めた内容を受入基準またはイテレーション計画の「壊れ方の観点」節に残す

---

## 軸 1: 入力の境界

利用者・外部から来る値が、想定した範囲の**端と外側**にあるとき。

| # | 観点 | 実際に起きた例 |
| :--: | :--- | :--- |
| 1-1 | **負の値**。特に符号を含む文字列のパース | IT4: `-0.5` が `0.50%` になった（符号消失）。**同じバグを 2 箇所に作った** |
| 1-2 | 0 と、0 の周辺（`0`・`0.0`・`-0`） | |
| 1-3 | 上限・下限とその 1 つ外側 | IT4: 割引率の上限 30% |
| 1-4 | 空文字・空白のみ・未送信（キー自体がない） | |
| 1-5 | **全角数字・全角英字** | IT4: `Char.isDigit` が全角数字を通した |
| 1-6 | **非 ASCII 文字**が識別子として通る | IT4: `日本大阪港` が UN/LOCODE として通った |
| 1-7 | 単位付き文字列（`-25℃`・`10kg`）・区切り付き数値（`1,000`） | |
| 1-8 | 桁あふれ（`Int32` の範囲外）・極端に長い文字列 | |
| 1-9 | **形式は正しいが実在しない値** | IT4: `2026-02-30` が日付として通り、応答が返らなくなった |
| 1-10 | 大文字小文字の違い | IT4: メール一意制約が大小文字を区別し、重複登録できた |
| 1-11 | 前後の空白 | |

## 軸 2: 外部システムの壊れ方

DB・別コンテキスト・外部 API との境界。**アプリ側の想定と相手の実際が食い違う**とき。

| # | 観点 | 実際に起きた例 |
| :--: | :--- | :--- |
| 2-1 | **一意制約違反**（アプリの検査をすり抜けた同時登録・大小文字差） | IT4: メールの一意性 |
| 2-2 | 参照先が存在しない（FK 違反・マスタにないコード） | IT4: マスタにない港コードで応答が返らなくなった |
| 2-3 | **型変換・桁落ち**（`NUMERIC(10,3)` の往復・`Int64` ⇄ `Int32`） | |
| 2-4 | **DB 方言の差**（H2 と PostgreSQL） | IT4: `MERGE INTO ... KEY` は H2 のみ、`ON CONFLICT` は PostgreSQL のみ。**片方でしか動かない構文を書いた時点で、もう片方は検証されていない** |
| 2-5 | NULL と「値がない」の区別。部分的に NULL の行 | |
| 2-6 | **読めない行を黙って捨てていないか** | IT4: `decode` が読めない行を無言で除外していた |
| 2-7 | トランザクションが本当に効いているか | IT4: `ReadOnly` が `setReadOnly(true)` だけで、**何も守っていなかった** |
| 2-8 | 例外時に後処理が失われないか | IT4: `afterCommit` が例外時に失われる |
| 2-9 | 識別子の衝突確率（切り詰めたハッシュ・UUID の先頭 N 文字） | IT4: 荷主コードが約 77,000 件で 5 割衝突 |

## 軸 3: 表示経路

**ドメインが正しくエラーを返しても、利用者に届かなければ壊れている**のと同じ。

| # | 観点 | 実際に起きた例 |
| :--: | :--- | :--- |
| 3-1 | **エラーが画面に出るか**（各入力欄について） | IT4: 貨物種別の選択欄だけエラーが表示されなかった |
| 3-2 | **応答が返るか**（分岐の取りこぼしで無応答にならないか） | IT4: 実在しない日付・マスタ外の港で応答なし |
| 3-3 | **成功した結果を利用者が確認できるか**（発行された番号・保存された値） | IT4: 荷主コード・予約番号が発行後どこにも出ない |
| 3-4 | 入力値が再表示されるか（エラー時に打ち直しにならないか） | |
| 3-5 | **導線の着地先で意図した状態になっているか** | IT4:「既存の荷主を使う」の着地先で絞り込まれていなかった |
| 3-6 | 誤った安全側の既定値になっていないか | IT4: 未知の貨物種別が**危険物**として扱われた |
| 3-7 | 操作できない要素が見えていないか（403 になるボタン） | IT4: ROLE_SHIPPER に 403 になるボタンが見えていた |
| 3-8 | エスケープ漏れ（XSS） | |

## 軸 4: 並行

サーバは仮想スレッドで並行処理します。**逐次テストでは原理的に検出できない**種類です。

| # | 観点 | 実際に起きた例 |
| :--: | :--- | :--- |
| 4-1 | **応答の取り違え**（別の利用者の画面が返る） | IT4: 公開追跡が 1 度だけ 403 を返した（未解決） |
| 4-2 | セッション・共有状態の競合 | |
| 4-3 | 同一資源への同時書き込み（連打・二重送信） | |
| 4-4 | 状態遷移の二重実行 | |

> **軸 4 は「思い当たらない」で飛ばさない。**
> 逐次テストが全部緑でも何も言えていません。並行スモークを置くか、
> 「この経路に共有状態はない」ことを**構造で示す**かのどちらかにします。

---

## 飛ばしてよい場合

- その軸に該当する入力・境界が**存在しない**（例: 入力を取らない画面に軸 1 は当たらない）
- 別の層で**すでに構造的に排除されている**（型で表現済みなど）。この場合は**どこで排除されているかを書く**

「たぶん大丈夫」は理由になりません。IT4 の 6 件はすべて「たぶん大丈夫」だったものです。

## この表自体の更新

イテレーションのふりかえりで**新しい壊れ方**が見つかったら、この表に行を追加します。
表が育たないなら、それは学習が記録されていないということです。

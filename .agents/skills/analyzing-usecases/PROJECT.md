# analyzing-usecases — 本プロジェクトでの設定

SKILL.md の汎用手順に対する、国際貨物輸送管理システム固有の値と AI-DLC の規律です。食い違う場合は本ファイルを正とします。

## ファイルの置き場所と採番

| 成果物 | パス | 採番 |
| :--- | :--- | :--- |
| ビジネスユースケース | `docs/requirements/business_usecase.md` | BUC01〜 |
| システムユースケース | `docs/requirements/system_usecase.md` | UC01〜（**UC 採番の正典**） |
| ユーザーストーリー | `docs/requirements/user_story.md` | US01〜（**US 採番の正典**） |
| Unit 定義・ストーリーマップ | `docs/requirements/units.md` | U-01〜 |
| ドメイン用語集 | `docs/design/glossary.md` | — |
| リスク台帳 | `docs/requirements/risk_register.md` | R-01〜 |

要件定義書（`requirements_definition.md`）の図の中の別名（`as UC..`・`as BUC..`）は図ごとの局所的な識別子で、上の採番とは対応しない。本文で ID を書くときは上の正典に合わせる。参照実装（`docs/article/source/`）の採番（US36 まで、ADR-006 など）を持ち込まない（R-07）。

## 用語

- 文書を書く前に用語集を読み、同じ概念は用語集の表記で書く。AI は語のゆれ（例: 経路／ルート、仮受付／仮予約）を別の概念として扱いやすく、1 つのゆれがドメインモデルの重複エンティティになる
- 用語集に無い語（例: 経路の状態、管理職、貨物 ID）を使う必要があれば、使う前に用語集への追加を提案して承認を得る
- 状態名は要件定義書の状態モデルと用語集が正。ストーリーで新しい状態名を作らない（R-06）

## 受入条件の書式

- 各ストーリーの受入条件は Given/When/Then で一意に判定できる形にし、`AC-01` から番号を振る
- 元の基準に無い振る舞いを補った条件には「（AI の仮定）」と印を付ける
- 各ストーリーに「対応 UC」「Unit」「参照する成果物」「確認ポイント」「AI の仮定」の欄を置く
- 計算式・料率・項目・閾値が決まっておらず期待値が決まらない基準は、仮の値で埋めずに「確認ポイント」に書いて人に戻す
- 既存の文面を書き直すときは意味を変えない

## Unit 分解の条件

- Unit は「他の Unit の内部を変えずに開発・デプロイできるか」で切る。ユースケース・画面の境界とは一致させない
- 迷ったら小さく切らず、依存を共有するストーリーを同じ Unit にまとめる
- 新しいストーリーを作ったら、`units.md` のストーリーマップに配置する。どの Unit にも入らなければ「未配置」に書き、Unit の追加かスコープバッファかを人に判断してもらう
- Unit の境界の変更は設計判断のため、案を示して承認を得る
- 通知（インセプションデッキのスコープ 5）は現在ストーリーが無く、各ストーリーの受入条件に含まれている。通知のストーリーを足す場合は Unit の追加を検討する

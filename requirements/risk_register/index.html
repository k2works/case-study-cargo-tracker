    リスク台帳：国際貨物輸送管理システム¶

    AI に任せる範囲と、人の承認ゲートで止めるリスクを定義します。以降の AI 生成物（ストーリー・Unit・設計・コード・計画）はすべてこの台帳を前提にします。Unit 定義と各スキルの PROJECT.md はリスクを ID で参照し、本文をここに一元化します。

    組織のリスク台帳は存在しません（ケーススタディ）。「由来」欄は、インセプションデッキのリスク番号、CLAUDE.md の確認必須の操作、既存レビューのいずれに由来するかを示します。

    AI に渡せる範囲（In/Out）¶

    本プロジェクトはケーススタディ（架空の国際貨物輸送会社）であり、本番データ・実在する顧客情報・決済情報は存在しません。業務データとコードは原則 In です（AI-DLC 移行計画 の決定事項 1）。

    トピック In Out AI に任せる 備考
    要件・ユースケース・ストーリー ✓ 書き直し・欄の追加・Unit への配置 既存の文面の意味を変えない。曖昧なものは要確認として戻す
    ドメインモデル・設計 ✓ 初稿の生成、選択肢とトレードオフの提示 境界付けられたコンテキスト・Unit の境界・アーキテクチャ判断は人が決める（R-06, R-08）
    アプリケーションコード・テスト ✓ TDD による実装 技術スタック選定と ADR は人が承認する
    テストデータ ✓ 生成 荷主・港湾などは架空の値でよい。UN/LOCODE を使う場合は実在コードを使う（R-09）
    参照実装（docs/article/source/） ✓ 設計・実装のコンテキストとして読む 別プロジェクトの実装。採番（US36 まで）・スコープ・状態モデルを持ち込まない（R-07）
    外部システム（港湾管理・税関・決済機関・通知） ✓ ポート（インタフェース）・スタブ・契約テストの生成 実在機関の API 仕様を仮定で作らない（R-01）
    認証・認可 ✓ 方式承認後の設計と実装 方式の選択は確認必須（R-02）
    環境変数・接続情報（.env、.env.vault の復号鍵） ✓ — 開発・ステージング・本番の SSH 接続先を含む。AI は値を読まない・書かない。環境操作は docs/operation/ の手順書のタスク経由で行う（R-10）

    確認必須の操作¶

    CLAUDE.md の「確認必須」と同じ範囲です。該当するステップは計画に注記し、実行前に停止して人の承認を得ます。

    • 新規ファイル作成（承認済みの計画に無いもの）
    • ファイル削除（重要ファイル）
    • アーキテクチャ・フォルダ構造の大規模な変更
    • 外部 API・外部ライブラリの導入
    • 認証・認可の実装
    • データベースのスキーマ変更・マイグレーション
    • デプロイ設定・環境変数の変更・本番環境への操作

    リスク一覧¶

    ID リスク 由来 対策 承認ゲート
    R-01 外部システム（港湾管理・税関・決済機関・通知）の API 仕様が不明確で、AI が仕様を仮定して作り込む デッキ #1、確認必須（外部連携） 外部システムはポートとして定義し、スタブと契約テストで先行する。実仕様に見える項目・エンドポイントを創作しない 外部連携のポート定義と、実在サービス・ライブラリの導入時
    R-02 認証・認可（US26・US27・US31）の方式を AI が独断で選び、セキュリティ要件を満たさない 確認必須（セキュリティ） 方式（セッション／トークン、ロックアウト条件など）は選択肢を提示して人が決め、ADR に残す 認証・認可を含む Bolt のステップ計画と実装の各ステップ
    R-03 スキーマ変更・マイグレーションが検証なしに適用される 確認必須（データベース） マイグレーションはテストで検証し、適用前に人が差分を確認する スキーマ変更を含むステップで停止
    R-04 経路算出で、要件に無い制約条件を AI が推測で追加する、または既存の制約を落とす デッキ #6 制約条件は要件定義書「経路設計の制約条件」の 5 つを正とし、段階的に追加する。追加・変更はストーリーの受入条件に書いてから実装する 経路算出の制約条件を追加・変更するステップ
    R-05 危険物・冷凍・冷蔵貨物の規制要件を AI が創作する、または見落とす デッキ #7 規制は要件・受入条件に書かれたものだけを実装する。書かれていない規制は要確認として人に戻す 危険物・冷凍・冷蔵貨物を扱うストーリー（US05 など）の受入条件の承認時
    R-06 状態モデルが要件定義と乖離する（オリジナルの Cargo Tracker の TransportStatus 5 値を流用し、要件定義の 9 状態と合わない） 既存レビュー（ドメインモデル分析 2026-03-31） 貨物予約と追跡情報の状態は要件定義書の状態モデルを正とする。参照実装の列挙を持ち込まない ドメインモデル設計と状態を扱う Bolt
    R-07 参照実装（docs/article/source/）の採番・スコープ・用語が混入する 棚卸し（user_story.md の description に参照実装の US36 が残っていた） 採番は user_story.md、用語は docs/design/glossary.md を正とする。参照実装から持ち込む場合は差分を明示する ストーリー・Unit・設計の承認時
    R-08 リアルタイム反映の方式（イベント駆動など）やコンテキスト分割を AI が既成事実化する デッキ #3、確認必須（構造変更） 方式は PoC と ADR で人が決める。決まるまで AI は選択肢の提示に留める アーキテクチャ設計と構造変更を含むステップ
    R-09 UN/LOCODE などの国際標準のコード値を AI が創作する デッキ #4 標準コードは実在する値を使い、出典を示す。架空の港湾を使う場合は架空であることを明示する 港湾・都市コードを扱うデータモデルとテストデータの承認時
    R-10 環境変数・接続情報を AI が読み書きする、または手順書に無い独自スクリプトで環境を操作する 確認必須（本番環境）、CLAUDE.md の環境操作ルール .env・.env.vault の値に触れない。環境操作は運用手順書の定義済みタスクを使う デプロイ設定・環境変数の変更・本番操作のすべて

    デッキ #2（新規構築）と #5（荷役作業員の定着）は AI 生成物ではなく計画と UX の課題のため、この台帳では扱いません。前者はリリース計画の MVP ファーストとウォーキングスケルトン、後者は UI 設計で扱います。

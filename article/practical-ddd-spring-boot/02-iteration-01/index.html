    第 2 章：IT1 ウォーキングスケルトンを 1 本通す¶

    このイテレーションのゴール¶

    認証と荷主登録で「画面 → ドメイン → DB」を貫通させ、ウォーキングスケルトンを立ち上げる。

    幅を広げるのではなく、細くてもよいので端から端までつなげます。ログインして荷主を登録し、一覧で確認できれば達成です。その 1 本が通れば、Thymeleaf → Controller → Application → Domain → MyBatis → PostgreSQL のすべてが「動くことを確認済み」になります。

    このイテレーション終了時点のコンテキストマップ¶

    扱うユーザーストーリー¶

    ID ストーリー SP
    US26 システムにログインする 3
    US27 システムからログアウトする 1
    US31 認証失敗が続いたアカウントを保護する 2
    US02 荷主を登録する 3
    合計 9

    US26 / US27 / US31 は全機能の前提です。認証が無ければ、以降のどの画面もロール別の確認ができません。US02 は US04（貨物予約登録）の前提で、荷主 ID を作る手段が無ければ予約フローが成立しません。

    US04（貨物予約）は IT2 へ回しました。IT1 は認証基盤・Thymeleaf レイアウト・MyBatis マッパーの初出が同時に起きるため、地ならしの分を見込んで 9SP に抑えています（ベロシティの初期値は 12SP）。

    実装¶

    Security を共有カーネルに入れない¶

    最初の設計判断がここです。認証・認可は全 BC が使います。だからといって共有カーネルに入れると、共有カーネルは「みんなが使うもの置き場」になって際限なく太ります。

    security を支援サブドメインとして独立させました（ADR-007）。共有カーネル shared に入れてよいのは Location と ShipperId の 2 つだけ、という制約（ADR-005）を初回から守ります。

    ロック状態は集約が持つ¶

    US31（5 回連続失敗でロック）の実装で、最初に決めたことです。

    /**
 * 認証アカウント。
 *
 * <p>ロック状態は<strong>集約が保持する</strong>（US31）。失敗回数を認証ログから
 * 数え直す設計にすると、ユニットテストが緑でもリクエストをまたいだ時に誤判定する。
 * 「5 回連続失敗でロック」はリクエストを越えて成立しなければならない不変条件である。
 */
public final class UserAccount {

    /** ロックまでに許容する連続失敗回数。 */
    public static final int MAX_FAILED_ATTEMPTS = 5;

    /** ロックの継続時間。 */
    public static final java.time.Duration LOCK_DURATION = java.time.Duration.ofMinutes(30);

    失敗回数を認証ログから導出しない、という判断です。導出する設計は一見きれいで、単体テストも緑になります。しかし失敗の記録とロック判定が別のリクエストで起きたときに、状態が復元できません。集約が状態を持ち、その状態を永続化します。

    MAX_FAILED_ATTEMPTS と LOCK_DURATION を定数として集約に置いているのも同じ理由です。 アカウントの状態遷移は次のとおりです。このイテレーションで状態を持つのはアカウントだけで、荷主は状態を持ちません。

    この数字は業務ルールであり、SecurityConfig の設定値ではありません。

    このイテレーションのドメインモデル¶

    値オブジェクトで業務のことばを型にする¶

    Shipper 集約の値オブジェクトは 5 種類（ShipperCode / ShipperName / Email / Phone / Address）です。共有カーネルの ShipperId を識別子に使います。

    なぜ String のまま持たないのか。共有カーネルの package-info.java にそのまま書いてあります。

    /**
 * 共有カーネルコンテキストの値オブジェクトと列挙。
 *
 * <p><strong>同一性を持たない。</strong> 等価性は値で決まり、生成後は変わらない。
 * 業務のことばをここで型にする —— String と BigDecimal のまま持ち回ると、
 * 取り違えてもコンパイルが通る。
 */

    値オブジェクトは Java の record で書きます。コンパクトコンストラクタが検証の置き場になります。

    public record Email(String value) {

    private static final Pattern FORMAT =
            Pattern.compile("^[^@\\s]+@[^@\\s.]+(?:\\.[^@\\s.]+){1,10}$");
    private static final int MAX_LENGTH = 200;

    public Email {
        if (value == null) {
            throw new IllegalArgumentException("メールアドレスは必須です");
        }
        // **長さの検査を形式の検査より先に行う。** 逆にすると、上限をはるかに超える
        // 入力（数万文字）がそのまま正規表現に渡る。長さで先に落とせば、
        // 照合の対象は必ず 200 文字以内に収まる。
        if (value.length() > MAX_LENGTH) {
            throw new IllegalArgumentException("メールアドレスは " + MAX_LENGTH + " 文字以内です");
        }
        if (!FORMAT.matcher(value).matches()) {
            throw new IllegalArgumentException("メールアドレスの形式が不正です: " + value);
        }
    }
}

    この Email は最終形です。正規表現の形（ドメイン部のラベルからドットを除く）と検査の順序は、後のイテレーションで ReDoS 対策として直したものです。IT1 の時点では素朴な形式検査でした。

    Javadoc に「一意性は DB の UNIQUE 制約が最後の防波堤である」と書いています。画面の非同期チェックは同時登録の競合に無力なので、値オブジェクトが守るのは形式だけと決めています。守れないものを守るふりをしないことが重要です。

    データモデルは 20 テーブルを一括で作る¶

    このイテレーションで実装があるのは shipper と security だけです。しかし V1__init.sql は 20 テーブルすべてを作ります。

    location / users / user_roles / shipper / cargo / voyage / carrier_movement /
booking_route_proposal / proposed_route / leg / tracking_activity /
tracking_handling_event / tracking_exception_event / handling_activity /
customs_declaration / invoice / invoice_line_item / payment / estimate / route_candidate

    分析フェーズで data-model.md に概念データモデル・論理データモデル・テーブル定義まで引いてあり、それをそのまま DDL に落とした形です。invoice が使われるのは 13 回目、estimate は 18 回目のイテレーションです。

    テーブルには所有する BC があります。V1 の 20 テーブルを BC ごとに色分けすると、実装より先にスキーマだけが全体像を持っている状態が見えます。

    このイテレーションで足したのは V2__account_lock.sql（ロック列）だけでした。設計を先に引いておくと、ウォーキングスケルトンを通す回で DB 設計に時間を取られません。 IT1 のゴールに対しては、この進め方が効いています。

    代償は第 1 章「データモデリングをどう進めたか」に書いたとおりで、次のイテレーションで早速 1 つ目が出ます。

    ArchUnit を最初のイテレーションで有効にする¶

    このプロジェクトで最も効いた判断です。IT1 の時点で、実装が存在するようになったルールから順に有効化しました。

    @ArchTest
static final ArchRule ドメイン層はSpringに依存しない =
        noClasses()
                .that().resideInAPackage("..domain..")
                .should().dependOnClassesThat().resideInAPackage("org.springframework..")
                .because("ドメイン層は Spring フレームワークに依存してはならない");

    そして、有効化のたびに違反クラスを一時的に置いて、実際に赤くなることを確認しています。allowEmptyShould(true) は使いません。対象が 0 件のルールを緑にすると、実装が入った後も検査されていないことに気づけなくなります。

    この確認作業の副産物として、設計ドキュメント（test_strategy.md）に載っていたサンプルの ignoreDependency の引数の向きが逆であることも見つかっています。

    DDD の観点¶

    戦略的 DDD¶

    IT1 で引かれた境界は 3 つです — shipper（中核）・security（支援サブドメイン）・shared（共有カーネル）。

    このイテレーションの戦略的な判断は「入れない」判断でした。

    判断 内容
    security を共有カーネルに入れない 全 BC が使う ≠ 共有カーネル。認証・認可は業務の中核ではなく支援サブドメインである（ADR-007）
    shared を 2 要素に限る Location と ShipperId のみ（ADR-005）。上限を決めずに始めると共有カーネルは必ず太る

    共有カーネルは、複数の BC が同じモデルを共同所有するという約束です。共同所有はコストであり、変更するたびに全 BC の合意が要ります。だから小さく保ちます。ShipperId が入っているのは、荷主の識別子が全 BC を横断して現れるからで、Shipper そのものは入っていません。

    ACL はまだ登場しません。 BC が 1 つしかないため、越境がまだ発生していないためです（IT2 で最初の 1 本が通ります）。

    戦術的 DDD¶

    このイテレーションで導入された道具立ては 3 つです。

    道具立て 実装
    集約ルート Shipper（final かつ不変）・UserAccount
    値オブジェクト ShipperCode / ShipperName / Email / Phone / Address / ShipperId
    リポジトリ ShipperRepository（domain/repository）と MyBatisShipperRepository（infrastructure）

    UserAccount が状態を持つ集約であることが、このイテレーション最大の戦術的判断です。

    集約の定義は「不変条件を守る単位」です。「5 回連続失敗でロック」という不変条件は、リクエストをまたいで成立しなければ意味がありません。失敗回数を認証ログから数え直す設計は、その不変条件を集約の外へ出してしまいます。だから failedAttempts と lockedUntil を集約が持ち、そのまま永続化します。

    MAX_FAILED_ATTEMPTS = 5 と LOCK_DURATION = 30 分 を集約の定数として置いたのも同じです。この 2 つは業務ルールであって設定値ではありません。 application.yml に置くと、業務ルールがインフラの設定に漏れます。

    一方、Shipper は状態を持ちません。荷主は登録されたら登録されたままです。すべての集約が状態機械になるわけではないという当たり前のことが、最初の 2 集約で対照的に現れています。

    ユビキタス言語¶

    要件のことばがそのままクラス名になっています。 「荷主」＝ Shipper、「荷主コード」＝ ShipperCode、「利用者アカウント」＝ UserAccount。

    このイテレーションで確立したのは、ことばの置き場を Javadoc にするという運用です。

    /**
 * 荷主。Shipper Context の集約ルート。
 *
 * <p>他の境界付けられたコンテキストのクラスを直接参照しない。Booking からの参照は
 * {@code ShipperExistenceChecker} ACL ポートを経由する（{@code domain-model.md}）。
 */

    Javadoc に 業務の定義と、正典への参照 を書きます。ふりかえりの K2「判断の理由をコード内に残す」がこれにあたり、レビューの議論が「なぜそうしたか」から始められるようになりました。

    ことばが離れた箇所も 1 つ出ています。 ユーザーマニュアルが「管理者に連絡するとロックを解除できます」と書きましたが、解除の手段は実装にありません。マニュアルのことばだけが先に進んだ状態で、これは US33 として IT5 で実装されるまで残ります。ユビキタス言語は、コードと要件だけでなく 利用者に見せる文書とも一致していなければならない という最初の警告でした。

    設計判断¶

    ADR 決めたこと
    ADR-001 Java 25 LTS ＋ Spring Boot 4.x
    ADR-003 PostgreSQL を正、H2 はローカル補助
    ADR-004 MyBatis を採り、JPA を採らない
    ADR-005 共有カーネルは Location と ShipperId の 2 要素に限る
    ADR-007 認証・認可は支援サブドメイン（共有カーネルではない）

    US31 では受入基準そのものの矛盾も見つかりました。「ロックされたことが利用者に通知される」と「ロック中と誤りで同一メッセージを返す」は両立しません。同一メッセージを優先しています（通知するとアカウントの存在を第三者に教えることになるため）。受入基準の側を IT2 で修正する、という扱いにしました。

    このイテレーションの学び¶

    計画どおり 4 ストーリー 9SP を完了し、品質ゲートも全項目を満たしました（テスト 96 件緑・Checkstyle 0・SpotBugs 0・SonarQube PASS）。

    しかしクローズ時のレビューで高優先度 10 件が見つかりました。うち 4 件は「安全装置が入っているつもりで働いていなかった」ものです。実装中はすべて緑でした。

    学び 内容
    安全装置は破るテストで確かめる ArchUnit のルールも、ロックも、「入れた」だけでは働かない。違反を作って赤になることを確認して初めて有効になる
    判断の理由をコードに残す 「なぜロック状態を永続化するのか」を Javadoc に書いたことで、レビューの議論が「なぜそうしたか」から始められた
    実機で確かめる MockMvc が緑でも 403 画面の中身は確認できない（forward 先を描画しないため）。Playwright での実機確認で英語のデフォルト画面が出ていることが判明した
    生成物で乖離を検出する JIG が生成した CRUD 図から、荷主マッパーが丸ごと欠落していることが分かった

    問題も明確に残りました。

    • 境界値を単体で固定していなかった — Clock を注入する設計にしながら、差し替えるテストを 1 本も書いていない。ロック期限が切れた後の振る舞いが完全に未検証だった
    • マニュアルが実装に無い機能を約束していた — 「管理者に連絡するとロックを解除できます」と案内したが、解除の手段は存在しない（US33 として IT5 で実装されます）
    • 計画外の作業が実績に現れない — レビュー指摘の修正・脆弱性 30 件の解消は SP に計上していない。実績 9SP は「9SP 分の労力だった」ことを意味しない

    最後の点はベロシティの読み方に直結します。IT2 以降、返済の枠を計画の中に時間として確保する運用に変わります。

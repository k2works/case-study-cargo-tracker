    第 6 章：3 つの実装を同じ尺度で比べる¶

    ここまでで 3 本の実装を読みました。同じ業務（国際貨物輸送）を、違う前提で作ったものです。

    章 実装 参照元
    第 1〜3 章 モジュラーモノリス source/java-2/
    第 4 章 マイクロサービス + RabbitMQ source/java-3/
    第 5 章 マイクロサービス + Axon Framework 5（CQRS / Event Sourcing） source/java-4/

    各章はそれぞれの代金を、それぞれの言葉で書きました。この章がすることは、その言葉を揃え直すことだけです。

    尺度を先に決めます¶

    比較の章は、書き方を決めずに始めると印象の比較になります。「モノリスは単純」「マイクロサービスは複雑」は、どちらも測っていない文です。

    そこで軸を 3 つに絞り、それぞれについて「何を見れば決まるか」を先に決めます。

    軸 問い 何を見て決めるか
    1. 何を分けたか BC の境界は、何の単位として現れているか ビルドの構成・データベースの数・越境の手段
    2. 境界を直す費用 境界を引き直すとき、何が追随し、何が追随しないか 変更を止めるもの（コンパイラ・契約・過去のイベント）
    3. 守りが壊れたとき何が赤くなるか 不変条件や境界が破れたことを、何が知らせるか 実在する検査と、その検査が届かない範囲

    3 つ目は本シリーズ固有の軸です。一般的な比較記事は 1 と 2 を扱いますが、draft-2 の主題（M2：境界は宣言しただけでは守られない）に照らすと、守りが壊れたことに気づけるかどうかが方式の差として最も大きく出ました。

    軸にしなかったもの¶

    軸にしなかったもの 理由
    性能・スループット 3 本とも測っていない。 比較できる数字が参照元に無い
    チーム規模・開発速度 3 本とも同じ体制で作られている。分けて比べる材料が無い
    運用実績・障害の頻度 本番運用の記録が無い。kind クラスタでの E2E までが上限
    学習コスト 主観であり、参照元から読めない

    書けないものを書きません。これは draft-1 の第 5 章が構想で章を埋めた失敗（アウトライン §2 の P1）と同じ規律です。「運用負荷が高い」と一般論で書くことはできますが、それは 3 本を読んだ結果ではありません。

    この章のゴール¶

    1. 3 つの方式の差を、印象ではなく実在する成果物（ビルド構成・契約・検査）で言えること
    2. 方式を選ぶとき、どの順序で何を問えばよいかを説明できること
    3. この比較が何を確かめていないかを言えること

    軸 1：何を分けたか¶

    ビルドの構成に現れる¶

    モジュラーモノリスのビルド構成は 1 行です。

    rootProject.name = 'cargo-tracker'

    引用元: apps/cargo-tracker/settings.gradle

    include がありません。BC はトップレベルパッケージであって、ビルドの単位ではありません。第 3 章で「モジュラーモノリスのモジュールは Gradle のモジュールではない」と書いたのはこのことです。

    CQRS/ES 版は逆です。

    // 業務サブプロジェクト（9 つ）
include("shared")
include("gatewayms")
include("authms")
include("bookingms")
include("routingms")
include("trackingms")
include("handlingms")
include("billingms")
include("simulationms")

// テスト専用サブプロジェクト（業務サービスの数には含めない）
include("contract-tests")
include("acceptance-tests")

    引用元: apps/cargo-tracker/backend/settings.gradle.kts

    BC が独立したデプロイ単位である以上、ビルドの単位も分かれます。マイクロサービス版（java-3）も同じ形で、業務サービスの顔ぶれはほぼ同じです。

    分けたものを一覧にする¶

    モジュラーモノリス EDA CQRS/ES
    BC の実体 トップレベルパッケージ 独立した Spring Boot アプリケーション 独立した Spring Boot アプリケーション
    ビルドの単位 1 つ（include 無し） サービスごと サービスごと（+ テスト専用 2）
    データベース 1 つ（全 BC 共通） サービスごと サービスごと（投影と Axon 管理表）
    BC 間の通知 ApplicationEventPublisher RabbitMQ Axon Server
    BC 間の問い合わせ ACL ポート（メソッド呼び出し） REST（ACL 経由） Axon Query Bus（ACL 経由）
    集約の保存 現在状態を UPDATE 現在状態を UPDATE イベント列

    第 4 章と第 5 章はこの表でほとんど同じです。サービス分割を揃えたのが ADR-0001 決定 1 の意図であり、差分が集約の保存の行だけになるようにしてあります。

    この軸だけを見ると、大きな段差は 1 つしかありません——プロセスを分けたかどうか。イベントソーシングは、この軸にはほとんど現れません。

    軸 2：境界を直す費用¶

    ここで 3 本がはっきり分かれます。「境界を引き直す」とき、何が変更を止めるかが違うからです。

    モジュラーモノリス：コンパイラが追随する¶

    BC を分け直す作業は、パッケージの移動とリファクタリングです。参照元を直し忘れればコンパイルが通りません。ACL ポートの名簿も同じで、型が変われば呼び出し側が壊れます。

    止めるのはコンパイラだけなので、費用は 1 回きりです。

    EDA：両側を同じ変更で直せない¶

    プロセスが分かれた瞬間に、これが成り立たなくなります。

    破壊的な変更が要るときは、新しいイベント型を足して両方を出し、受け手が移ってから古いほうを止める。イベントは受け手が読んだあと取り消せないので、REST のように「両側を同じ変更で直す」ことができない。

    引用元: docs/adr/022-domain-event-contract.md（決定 3・設計文書からの引用）

    費用が 1 回きりでなくなります。新旧を並行して出す期間があり、その期間の長さは相手が移るまで決まりません。受け手が自分のチームでないなら、なおさらです。

    CQRS/ES：過去の自分も読み手になる¶

    イベントソーシングは、ここにもう 1 段積みます。受け手が他サービスだけでなく、将来の自分自身になるからです。

    規則 内容
    イベントは追記専用 フィールドの削除・型変更をしない。要るなら新しいイベント型を足す
    Upcaster で吸収 形を変えざるを得ないときは Upcaster を書き、旧形式のテストイベントを残す
    型名はメタデータに載る クラスの移動・改名は Revision と Upcaster を伴う。パッケージ移動は「無料」ではない

    引用元: docs/design/cargo-tracker/architecture_backend.md「イベント契約」（設計文書からの引用）

    最下段が効きます。モジュラーモノリスでは無料だった「パッケージを移す」が、ここでは移行作業になります。第 5 章で見たとおり、イベントに値オブジェクトを載せないのも同じ理由からです——あとで不変条件を足すと、過去のイベントが新しい検査を通らなくなります。

    費用を一覧にする¶

    何が変更を止めるか 費用の形
    モジュラーモノリス コンパイラ 1 回きり
    EDA 受け手（読んだあと取り消せない） 並行期間（相手が移るまで）
    CQRS/ES 受け手 + 過去のイベント 並行期間 + 移行コード（Upcaster は消えない）

    「間違った境界」の寿命が、下に行くほど延びます。モジュラーモノリスなら直せば消えます。CQRS/ES では、間違った境界がイベントの型名として残り続けます。

    軸 3：守りが壊れたとき何が赤くなるか¶

    本シリーズが一貫して追ってきた軸です。3 本とも「境界は宣言しただけでは守られない」と考えており、そのための仕組みを持っています。違うのは、その仕組みがどこまで届くかです。

    モジュラーモノリス：静的な依存で足りる¶

     * <p>{@code allowEmptyShould(true)} は使わない。**何も検査していないルールを緑にすると、
 * 実装が入った後も検査されていないことに気づけなくなる。**
 *
 * <p><strong>各ルールは違反を作って赤になることを確認済みである</strong>（ADR-005 の
 * コンプライアンス欄が定める手続き）。ADR-012 のルールは IT8 のレビューで、
 * 他 BC の ACL ポートを注入するとルール 4 は緑のまま**本ルールだけが赤**になることを
 * 実装者以外が確かめている。

    引用元: apps/cargo-tracker/src/test/java/com/example/cargotracker/PackageStructureTest.java

    2 つのことを言っています。「何も検査していないルールを緑にしない」ことと、「各ルールが違反を作って赤になることを確認済みである」こと。前者は第 5 章の actuallyInspectsAggregates と同じ考え方で、後者は java-4 の ArchRulesAreEffectiveTest（違反フィクスチャで規則が赤を出せることを固定する）と同じです。

    同じ規律が 3 本すべてに、別々の言葉で現れています。方式に依存しない部分だということです。

    そのうえで、モジュラーモノリスではこれで足ります。BC 間の参照は静的な依存であり、ArchUnit が見ている範囲に収まります。

    EDA：静的な依存では届かない¶

    プロセスが分かれると、依存グラフに現れないものが出てきます。

    /**
 * イベントが<strong>実際に届く</strong>ことを実 RabbitMQ で確かめる、往復テストの土台。
 *
 * <p>「発行するコードを書いた」「購読するコードを書いた」ことと、<strong>相手に届くこと</strong>は
 * 別である。交換機の名前・ルーティングキー・キューの結びつけ・変換器のどれか 1 つがずれると、
 * <strong>送り手はエラーにならないまま届かない</strong>。
 *
 * <p><strong>契約ごとにテストを分ける。</strong>1 つのクラスに 2 契約を入れていたが、
 * US17 で 3 契約目が入る。契約が増えるたびに同じクラスが伸びると、どの契約の何を
 * 確かめているのかが読めなくなる。土台だけを共有し、契約ごとの取り決めは各テストが持つ。
 */

    引用元: apps/backend/trackingms/src/test/java/com/example/trackingms/EventRoundTripTestBase.java

    「送り手はエラーにならないまま届かない」——コンパイラにも ArchUnit にも見えません。だから実 RabbitMQ の往復テストが要ります。第 4 章で見たとおり、契約テストも発行側と購読側の両方に置きます。片側だけでは守れないからです。

    CQRS/ES：単体テストでは判別できない¶

    もう 1 段進みます。集約の単体テストが緑でも、守りが外れていることがあります。

    @EventTag を付け忘れると集約は空のまま復元され、状態を見る守りが丸ごと素通りします。しかも AxonTestFixture の disableAxonServer() ではタグ復元が働かないので、集約の単体テストでは原理的に判別できません。

    対処は静的な走査です。そして、その走査が空振りしていないことを同じクラスが見ます。

        @Test
    @DisplayName("検査の対象が実在する（空振りしていない）")
    void actuallyInspectsAggregates() throws IOException {
        List<Aggregate> aggregates = eventSourcedAggregates();

        assertThat(aggregates)
                .as("@EventSourced(tagKey) の集約が 1 つも見つからないなら、"
                        + "上の検査は『守っている』ではなく『調べていない』")
                .isNotEmpty();
        assertThat(aggregates.stream().flatMap(a -> a.events().stream()).toList())
                .as("イベントを 1 つも拾えていないなら、appender.append の書き方が変わっている")
                .isNotEmpty();
    }
}

    引用元: apps/cargo-tracker/backend/shared/src/test/java/com/example/cargotracker/shared/conventions/EventTagAccompaniesEventSourcedTest.java

    java-2 の allowEmptyShould(true) は使わないという判断と、同じことをしています。違うのは重みです。モジュラーモノリスでは「実装が入った後も検査されていないことに気づけなくなる」という将来のリスクでしたが、ここでは今まさに守りが外れているのに緑という現在の問題です。

    さらに、ArchUnit が届かない範囲も名指しされています。

    ArchUnit の規則では代われない。CommandGateway の利用箇所をパッケージで限定する規則はコンパイル時の依存しか見ておらず、「リプレイの実行中に呼ばれない」という動的な保証は別物である。

    引用元: apps/cargo-tracker/backend/shared/src/test/java/com/example/cargotracker/shared/conventions/ReplayCheckAccompaniesReactionTest.java

    検知の手段を一覧にする¶

    守りが壊れたとき赤くなるもの 届かない範囲
    モジュラーモノリス コンパイラ・ArchUnit・集約の単体テスト —
    EDA 上記 + 契約テスト（両側）・実ブローカーの往復テスト 静的な依存に現れない配送
    CQRS/ES 上記 + 静的なソース走査・実 Axon Server の統合テスト・ReplayIT 集約の単体テスト（タグ復元が働かない）・リプレイ中の動的な保証

    この軸が、3 方式でいちばん差の大きい軸でした。しかも差は「検査が増える」だけではありません。CQRS/ES では、いちばん基本的な検査（集約の単体テスト）が判別力を失います。

    3 本に共通して現れたもの¶

    比べると差が目立ちますが、3 本すべてに現れた規律もあります。方式を選んでも捨てられない部分です。

    規律 java-2 での現れ方 java-3 での現れ方 java-4 での現れ方
    空振りする検査を作らない allowEmptyShould(true) を使わない 名簿を手で書かず DTO の要素から導く actuallyInspectsAggregates で対象が実在することを見る
    規則が赤を出せることを確かめる 各ルールで違反を作って確認（ADR-005 の手続き） 契約テストを両側に置く ArchRulesAreEffectiveTest が違反フィクスチャを食わせる
    決定を文章のまま残さない ADR の規則を ArchUnit に落とす ADR-022 の決定ごとに検査表を持つ AdrHasChecksTest が決定の数だけ検査を要求する
    無いものを無いと書く REST は無い・Mapper XML は無い Outbox は無い・イベントストアは無い Saga は無い・Deadline は無い・GA の connector は無い

    4 つ目が特に効きます。3 本とも「無いもの」を持っていて、そのどれもが将来足すかもしれないものです。無いと書いてあるから、読む側は「見落としたのか、決めて省いたのか」を区別できます。

    設計文書は 3 本とも実装から離れた¶

    M3（実装は設計文書を裏切る）は、方式に関係なく起きました。

    例 種類
    java-2 正典が interfaces/rest/ を規定するが全 BC に存在しない（第 3 章 D1） 設計が先、実装が追随しない
    java-2 ArchUnit の Javadoc が「ルール 5 のみ」のまま残っていた 実装が先、宣言が追随しない
    java-3 正典は Spring Cloud Stream、実装は素の AMQP（第 4 章） 設計が先、実装が追随しない
    java-4 設計が @Saga 前提で書かれていた（第 5 章） 設計が先だがコンパイラが止める
    java-4 「名簿は ArchUnit で固定する」と書いた検査が実在しなかった（第 5 章） 約束だけがあった

    java-2 の 2 例目は、当の Javadoc が自分で記録しています。

     * <p><strong>10 ルールすべてが有効であり、緑である</strong>（IT9 で本 Javadoc を実態に合わせた。
 * IT1 の記述が「ルール 5 のみを実装している」のまま残っていた —
 * <strong>実装はあるが宣言が古い</strong>形であり、IT8 のふりかえり P1 の裏返しである）。

    引用元: apps/cargo-tracker/src/test/java/com/example/cargotracker/PackageStructureTest.java

    「実装はあるが宣言が古い」——食い違いは設計文書の側からだけ起きるのではありません。そして java-4 の最後の例（約束だけがあった）が、いちばん見つけにくい形です。「検査で守る」と書いてある文書を読んだ人は、守られていると信じます。

    選ぶときの順序¶

    3 つの軸は同時に効くわけではありません。順序があります。

    1. 境界が安定しているか。安定していないなら分けません。軸 2 が示すとおり、間違った境界の寿命は方式で決まります。モジュラーモノリスはこれを安く確かめられる唯一の構成です
    2. プロセスを分ける理由があるか。デプロイ独立・チーム独立・スケール単位のどれかに実際の要求があるときだけ分けます。軸 1 が示すとおり、境界の表現のためだけなら分ける必要はありません——モジュラーモノリスでも ArchUnit が守れます
    3. 経緯を業務が読むか。「結果」だけでなく「どう至ったか」を業務が使うなら、イベントソーシングを検討します。読まないなら履歴は監査ログで足ります
    4. 軸 3 の検査を引き受けられるか。これが最後の関門です。CQRS/ES を選ぶなら、実 Axon Server の統合テストとクラスタでの E2E は選択肢ではなく必須になります。引き受けられないなら選びません

    4 を先に問わないことが大事です。1〜3 を飛ばして「Event Sourcing を入れるか」から始めると、境界が固まっていないまま型名が固定されます。

    この比較が確かめていないこと¶

    3 本は制御実験ではありません。

    限界 内容
    同時期ではない 3 本は別の時期に作られており、後のものほど前のものの知見を持っている
    完成度が違う java-2 は 20 イテレーションで v2.1.0 出荷済み、他の 2 本はイテレーションの本数が違う
    同じ人が作っている 方式の差と、作り手が学習した差を分離できない
    本番運用が無い 障害・スケール・運用負荷の実測が 3 本ともゼロ
    書籍の 4 アプローチのうち 2 つを扱っていない Jakarta EE / MicroProfile 版は参照元に無い。扱っていないものを評価しない

    特に 3 行目は、この章の結論の重みを決めます。「CQRS/ES は検査が多い」という観察は、方式がそれを要求したのか、それとも作り手が 3 本目で検査の書き方を覚えたのかを分離できていません。

    ただし軸 3 の中心（@EventTag の付け忘れ・単体テストで判別できないこと）は、Axon のスパイク結果として ADR に記録されており、学習の差では説明できません。分離できる部分とできない部分を、分けて読んでください。

    トレードオフ¶

    この章自体の書き方にもトレードオフがあります。

    軸を 3 つに絞ったことで失ったもの。性能・チーム規模・学習コストは、実務では選択を左右します。それらを落としたのは、参照元から読めないものを書かないためです。読者が自分の状況で選ぶときは、ここで扱った 3 軸に測れる材料を自分で足す必要があります。

    「どれが良いか」を書かなかったこと。3 本のうちどれが優れているかは書いていません。書けるのは「何が違うか」と「どの順序で問うか」までです。同じ業務を 3 通りに作れたという事実自体が、単一の正解が無いことを示しています。

    採用しなかった書き方。当初は 1 つの表に全項目を並べる案を採りかけました。やめたのは、軸ごとに段差の位置が違うからです——軸 1 の段差は「プロセスを分けたか」の 1 か所ですが、軸 2 と軸 3 は 3 段階です。1 つの表に潰すと、この違いが消えます。

    まとめ¶

    • 尺度を先に決めました。何を分けたか・境界を直す費用・守りが壊れたとき何が赤くなるか、の 3 軸です。性能やチーム規模を軸にしなかったのは、3 本とも測っていないからです
    • 軸 1（配置）の段差は 1 か所だけでした。プロセスを分けたかどうかで、イベントソーシングはこの軸にほとんど現れません
    • 軸 2（境界を直す費用）は 3 段階でした。コンパイラが止める → 受け手が読んだあと取り消せない → 過去のイベントも読み手になる。間違った境界の寿命が、方式で決まります
    • 軸 3（検知の手段）がいちばん差の大きい軸でした。しかも「検査が増える」だけではなく、CQRS/ES ではいちばん基本的な検査が判別力を失います
    • 3 本に共通する規律が 4 つありました。空振りする検査を作らない・規則が赤を出せることを確かめる・決定を文章のまま残さない・無いものを無いと書く。方式を選んでも捨てられません
    • 設計文書と実装の食い違いは、方式に関係なく起きました。向きは両方あり（設計が先・実装が先）、いちばん見つけにくいのは「検査で守る」と書いてその検査が無かった形です
    • この比較は制御実験ではありません。3 本は別の時期に同じ作り手が作っており、方式の差と学習の差を完全には分離できません。本番運用の記録もありません

    本シリーズはここで終わります。書籍の構造を実際に適用したら何が残り、何が変わったかを、3 通りの適用結果から報告しました。適用結果の側から書くとは、うまくいった設計だけでなく、写して失敗した記録と、まだ無いものを同じ比重で残すことです。

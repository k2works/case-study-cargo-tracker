    第 11 章：IT10 輸送料金算出とリリース 2.0¶

    このイテレーションのゴール¶

    IT9 申し送り事項（技術的負債 H-1〜H-3・H-5・H-6）を解消し、輸送料金算出（US21）を実装してすべての機能を完成させ、Release 2.0 のリリース準備を完了させる

    最終イテレーションです。目標 SP が 8 と最も少なく、うち相当量が技術的負債の返済に充てられています。

    項目 内容
    目標 SP 8
    実績 SP 8
    Java テスト 323 件（+8）
    Playwright E2E 98 件（+5）
    命令カバレッジ 80.9%
    ブランチカバレッジ 74%
    リリース Release 2.0

    扱うユーザーストーリー¶

    ID ストーリー SP
    US21 輸送料金を算出する 5
    IT9-改善 H-1〜H-3・H-5・H-6 の技術的負債返済 3

    Java 実装¶

    5 イテレーション越しの負債返済¶

    IT10 の成功基準を見ると、機能より先に負債返済が並んでいます。

    ID 内容 起票
    H-1 assignItinerary に requireStatus(EnumSet.of(...)) パターンを適用（cancel() も統一） IT5
    H-2 assignItinerary 完了時に CargoRoutedEvent を発行（テストで明示） IT5
    H-3 assignRoute コントローラメソッドを executeBookingCommand パターンに統合 IT5

    H-1 は第 6 章で触れた「抽出したが全箇所に適用していない」問題です。IT5 で requireStatus を抽出してから、全メソッドへの適用完了まで 5 イテレーションかかりました。

    H-2 は「イベント発行の漏れ」です。経路が紐付いたのに CargoRoutedEvent が発行されていませんでした。第 7 章で述べた通り、イベント発行をアプリケーション層で明示的に呼ぶ設計では、この漏れがテストなしには検出されません。成功基準に「テストで明示」と書かれているのは、その反省です。

    料金算出¶

    US21 の実装は、意外なほど簡素です。

    // billing/domain/model/valueobjects/FreightCalculationResult.java
public record FreightCalculationResult(
        String bookingId,
        int baseFreight,
        int adjustmentAmount,
        String adjustmentReason,
        int finalAmount
) {
    public static FreightCalculationResult of(
            String bookingId, int baseFreight,
            int adjustmentAmount, String adjustmentReason
    ) {
        return new FreightCalculationResult(
                bookingId, baseFreight, adjustmentAmount, adjustmentReason,
                baseFreight + adjustmentAmount
        );
    }
}

    // billing/domain/model/services/FreightCalculationService.java
public class FreightCalculationService {

    public FreightCalculationResult calculate(Invoice invoice, int adjustmentAmount, String adjustmentReason) {
        return FreightCalculationResult.of(
                invoice.getBookingId(),
                invoice.getTotalAmountValue(),
                adjustmentAmount,
                adjustmentReason != null ? adjustmentReason : ""
        );
    }
}

    料金算出＝「基本運賃 + 調整額」。重量による従量計算も、距離による計算も、危険物加算もありません。基本運賃は請求書が既に持っている値をそのまま使い、調整額は人間が入力します。

    これは実装の手抜きではなく、スコープの割り切りとして理解すべきものです。IT4 で経路候補の料金を「基本単価 × 所要日数」でハードコードしたのと同じ扱いで、料金体系そのものはこのケーススタディの主題ではありません。

    ただし FreightCalculationService はドメインサービスとして切り出されており、料金ロジックを追加する場所は用意されています。現状は 1 行の足し算しかしていませんが、置き場所が決まっていることには意味があります。

    調整額の符号に注目してください。baseFreight + adjustmentAmount なので、減額したければ負値を渡します。第 10 章で見た Ruby 実装の「補償費用の方向確定」問題と同じ論点で、Java 実装は「調整額は符号付き」という約束で処理しています。この約束はコードから読み取れますが、UI で経理担当者が入力するときにどちら向きに入れるべきかは自明ではありません。

    ドメインサービスをいつ使うか¶

    FreightCalculationService は、このプロジェクトで唯一のドメインサービスです。他の業務ロジックはすべて集約のメソッドに置かれています。

    料金計算をドメインサービスにした理由は、複数の集約にまたがるためです。料金は請求書（Invoice）と予約（Cargo）と例外記録（Tracking）の情報から決まり、どの集約のメソッドとしても自然でありません。

    DDD においてドメインサービスは「どの集約にも属さない業務ロジック」の置き場所であり、この使い方は正しいものです。逆に言うと、ドメインサービスが増えるのは集約の切り方を疑うサインです。このプロジェクトで 1 つしかないことは、集約の境界が業務と合っていることを示しています。

    他言語ではどう書いたか¶

    料金算出の扱い¶

    US21 をどこまで作り込んだかは、実装ごとに差があります。

    言語 料金算出の実装
    Java 基本運賃 + 調整額
    Rust FreightCharge 集約として独立。消費税計算あり
    Ruby 料金調整に取消・監査証跡を実装（IT9）
    Go 割引ポリシーを独立コンテキスト（discountpolicy）として分離
    Haskell Billing Context の Invoice 集約に統合

    Rust は料金を独立した集約（FreightCharge）にし、消費税をドメインに持たせています。Go は割引ポリシーを Billing とは別のコンテキストに切り出しており、ドメイン層カバレッジ 92.7% を単独で計測しています。

    分割の是非は業務の複雑さ次第です。料金体系が単純なうちは Java のように請求書に統合するほうが素直で、体系が複雑化したときに切り出せばよい。ただし Rust・Go の分割は、将来の複雑化を見越して先に境界を引くという判断であり、モノリスにおいては安価な投資です（プロセス分割と違い、後から統合も分割も容易なため）。

    最終的なテスト規模¶

    Release 完了時点の各実装の規模を並べます。粒度が違うため直接比較はできませんが、傾向は読み取れます。

    言語 テスト件数 カバレッジ 備考
    Java 323 + E2E 98 80.9%（命令） ブランチ 74%
    Haskell 889 examples — hspec の example 単位
    Flix 782 — arch-lint メタテスト 32 件を含む
    TypeScript 597 + E2E 8 94.05%（全体）／92.1%（新規） —
    Ruby 429 examples 95.95%（全体）／91.7%（新規） —
    F# 222 + 統合 149 + Arch 31 89.0%（全体）／88.8%（ドメイン層） —
    Go — 94.4%（Billing ドメイン層） 層別に計測
    Rust — — 97/97 SP 完了

    カバレッジの高い実装（Ruby 95.95%、TypeScript 94.05%、F# 89.0%）に共通するのは、カバレッジ閾値を CI のハードゲートにしていることです。F# は「閾値 80% / ドメイン層 85%」と層別に設定しています。

    Java の 80.9% は目標（80%）ぎりぎりで、ブランチカバレッジ 74% は目標未達のままリリースされました。C# 実装のふりかえりには「カバレッジ 85% CI ハードゲート化」が繰り越し項目として記録されており、同じ課題を抱えています。

    閾値を CI で強制していない実装は、目標を下回ったままリリースに至るという相関がはっきり出ています。

    例外系・境界値のテスト¶

    最終イテレーション前後で各実装が集中的に追加したのは、例外系と境界値のテストです。

    • C# — 「精算異常系テスト: MarkOverdue 境界・Overdue→Confirmed・存在しない精算書・二重発行」
    • Go — 「支払期限 DATE/TIMESTAMP 境界バグ → 日付単位比較へ正規化・当日時刻付き境界テスト追加」
    • TypeScript — 「サービス単体/境界値/端数テスト」
    • Ruby — 「seq_number 境界バグ」の修正

    すべて金額・日付・連番の境界に集中しています。正常系は早い段階で固まりますが、境界は最後まで残る。しかも境界のバグは、業務データが実際に境界に乗るまで顕在化しません（期限当日に到着する貨物、割引率 0% の法人、調整額 0 円の請求書）。

    リリース前に境界値テストをまとめて追加するのは、全実装が共通して踏んだ工程です。であれば、機能実装と同時に境界を洗い出すほうが安い。境界値分析はテスト技法として古典的ですが、実践されているとは限らないことがこの 10 実装から見て取れます。

    リリース時の未達¶

    Java 実装は Release 2.0 到達時点で、いくつかの未達を残しています。

    項目 状態
    US07 受入条件 6（貨物種別による航海の絞り込み） 未実装（IT4 で検出、IT10 まで放置）
    US18 受入条件 2（推定到着日の表示） 未実装（IT8 で検出、3 イテレーション持ち越し）
    メール通知（US17・US19・US20） 未実装（インフラ未整備）
    ブランチカバレッジ 80% 未達（74%）
    H2 → PostgreSQL 移行 未実施

    これらが未達として記録されていることには価値があります。Release 2.0 の完了報告書は、全機能完成を宣言しつつ、上記を残課題として明示しています。

    ただし記録するだけでは消化されません。第 5 章・第 7 章・第 10 章で繰り返し見た通り、「次のイテレーションで対応」とした項目の消化率は高くありませんでした。US07 の受入条件 6 は、検出から 6 イテレーション後のリリースまで一度も着手されていません。

    プロジェクト全体の実績¶

    イテレーション 目標 SP 実績 SP 累計
    IT1 10 10 10
    IT2 10 10 20
    IT3 10 10 30
    IT4 10 8 38
    IT5 10 10 48
    IT6 10 10 58
    IT7 10 10 68
    IT8 10 10 78
    IT9 12 12 90
    IT10 8 8 98

    平均ベロシティ 9.8 SP/イテレーション。当初の想定（実効 10〜13 SP）の下限に収まりました。10 イテレーション中 9 回が目標達成で、外したのは IT4 の 1 回だけです。

    ベロシティが安定していた理由の 1 つは、部分完了を 0 点として扱ったことです（IT4 の IT3-改善が 2 SP 予定で加算 0）。実態より高いベロシティを記録すると、次の計画が過大になり、以降ずっと外し続けます。

    もう 1 つは、毎イテレーションに 2〜3 SP の改善枠を最初から積んでいたことです。IT2（4 SP）、IT3（3 SP）、IT5（改善込み）、IT6（3 SP）、IT10（3 SP）と、新機能だけで 10 SP を埋めていません。改善を計画に載せることが、ベロシティを安定させています。

    ただし第 5 章で見た通り、載せた改善が必ず消化されたわけではありません。「改善枠を確保する」ことと「改善が実際に進む」ことの間には、まだ距離があります。

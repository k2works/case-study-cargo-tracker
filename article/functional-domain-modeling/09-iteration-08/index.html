    第 9 章：IT8 実務品質への引き上げ¶

    このイテレーションのゴール¶

    Release 1.1 の精算業務を実務品質へ引き上げる。IT7 で先送りした US21-23 の受入残（割引ポリシーマスタ接続・消費税/付加料金・支払期限・輸送実績表示・期限超過通知）を充足し、通知の実効化・決済 ACL の契約固定・Settled 同期のイベント駆動化・品質の穴埋めを行い、Release 1.1 を正式出荷可能な状態にする。

    新規ユーザーストーリーが 1 つもないイテレーションです。IT7 の受入残を消化し、型では守れない領域——外部連携・通知・可観測性——を固める回になります。

    項目 内容
    目標 SP 13（新規 US なし・IT6/IT7 の先送り項目を SP 換算）
    局面 終盤（強化・予備）・アウトサイドイン
    ユニットテスト 222 件緑（+11）
    統合テスト 149 件緑（+9）
    アーキテクチャテスト 31 件緑（+7）
    合計 402 件緑・失敗 0
    ビルド警告 0
    カバレッジ（全体 / ドメイン層） 89.0% / 88.8%
    ADR 0014 決済 ACL は PaymentGatewayPort と WireMock で契約固定する

    ユニットテストの増加（11 件）より統合テストとアーキテクチャテストの増加（16 件）が上回った唯一のイテレーションです。型で守れない領域を固める回であったことが、テストの内訳に出ています。

    扱う項目¶

    新規ストーリーの代わりに、受入残とレビュー指摘が並びます。

    分類 内容
    受入残 割引ポリシーマスタ接続・消費税/付加料金・支払期限・輸送実績表示・期限超過通知
    通知 MailSender 送信抽象・連絡先解決・通知失敗経路テスト
    外部連携 決済 ACL の契約固定
    BC 連携 Settled 同期のイベント駆動化

    型で守れない領域 1：外部システムとの契約¶

    決済機関との連携は、HTTP 越しの外部システムです。相手の応答形式は型システムの外にあります。

    対処はポートによる抽象化と、契約テストによる固定です。

    // src/CargoTracker.Web/PaymentGateway.fs
/// 決済機関との連携 ACL（US23・ADR-0014）。`PaymentGatewayPort` の実 HTTP アダプタ。
/// 契約は WireMock.Net で固定してテストする（BC 外部との腐敗防止層）。
module PaymentGateway =

    let stub (clock: Clock) : PaymentGatewayPort = ...

    let createHttp (client: HttpClient) (baseUrl: string) (clock: Clock) : PaymentGatewayPort = ...

    スタブと実 HTTP 実装が同じポート型を返します。第 2 章で見た通り、ポートが関数レコードなのでインターフェースを別途定義する必要がありません。

    エラーはドメインのエラー型に変換されます。

                        | ex -> return Error(BusinessRuleViolation("PaymentGatewayUnavailable", ex.Message))

    HttpRequestException や TaskCanceledException をそのまま上へ流さず、DomainError に写します。これが ACL（腐敗防止層）の本体です。外部システムの例外型がアプリケーション層に漏れると、決済機関を差し替えたときに広範囲が壊れます。

    ADR に書いたことを実装で変えた記録¶

    契約テストの実装には、率直な経緯が残っています。

    // tests/CargoTracker.IntegrationTests/PaymentGatewayContractTests.fs
// US23・ADR-0014: PaymentGatewayPort の実 HTTP アダプタ契約を固定する。
// 成功・決済拒否（4xx）・障害（5xx）の 3 系統を検証する。
//
// 契約スタブは .NET 標準の HttpListener によるインプロセス HTTP サーバで構成する。
// ADR-0014 は当初 WireMock.Net を想定したが、WireMock.Net が高深刻度の脆弱性を持つ
// 推移的依存（System.Linq.Dynamic.Core・Scriban.Signed 等）を多数引き込むため、
// セキュリティを優先し外部依存ゼロの HttpListener に切り替えた（同等の契約固定を実現）。

    ADR で「WireMock.Net を使う」と決めたが、依存関係の脆弱性を理由に標準ライブラリの HttpListener に切り替えた、という記録です。

    3 つの点で良い実践です。

    1. 判断の変更を記録した — なぜ ADR と実装が食い違うかが、実装側から辿れる
    2. 代替の等価性を明示した — 「同等の契約固定を実現」と書き、機能を落としていないことを示している
    3. 理由が具体的 — 「脆弱性がある」ではなく、どのパッケージがどう問題かまで書いてある

    検証する系統も明記されています。成功・決済拒否（4xx）・障害（5xx）の 3 系統。外部連携のテストで正常系だけを書くと、相手が落ちたときの挙動が未検証のまま本番に出ます。

    姉妹シリーズで見た通り、Rust 実装も同じ問題意識を持ち、ReqwestPaymentGateway を契約テスト済みにしたうえで既定はスタブとし、切り替えを合成ルートで行う設計にしています。

    型で守れない領域 2：通知が実際に届くか¶

    IT8 の成果に「通知の実効化」があります。

    2 通知の実効化 | MailSender 送信抽象・連絡先解決・通知失敗経路テスト | 完了

    3 点セットです。

    • MailSender 送信抽象 — 送信をポートにする
    • 連絡先解決 — 誰に送るかを決める仕組み
    • 通知失敗経路テスト — 送信が失敗したときの挙動を検証する

    姉妹シリーズの Java 実装は、この領域を最後まで実装しませんでした。

    US19・US20 の受入条件「荷主への通知が送信される」はメールインフラ未整備のため UI 上の通知記録のみで対応。

    メールサーバーがないから通知機能を作れない、という判断です。しかし送信をポートにすれば、実際に送らなくても「通知が発火すること」は検証できます。F# 実装が IT8 で行ったのはこれです。

    さらに「通知失敗経路テスト」が含まれている点が重要です。通知は失敗しうる副作用であり、失敗したときに業務が止まるのか続くのかは設計判断です。第 5 章で見た post-commit ディスパッチと同じ構造で、ここでも「確定済みの結果は巻き戻さない」方針が取られています。

    型で守れない領域 3：誰が起動するか¶

    IT7 の受入残に「期限超過通知」がありました。支払期限を過ぎた請求書を検出して経理に通知する機能です。

    これはユーザー操作で起きないイベントであり、起動主体を決める必要があります。

    姉妹シリーズでは、この問題が複数実装で同時に露見しました。

    実装 状態
    Haskell OverdueCheckCommand は実装・テスト済みだが Main 未配線（起動主体不在）
    Rust CheckOverdueService 未配線。レビューで 3 視点が重複指摘 → 手動駆動エンドポイント + 一覧ボタンで返済
    Java 一覧表示時に動的判定

    いずれもドメインロジックは正しく、テストも緑でした。誰も呼んでいないだけです。

    F# 実装が IT8 でこれを受入残として扱い、消化したのは、IT7 のクローズ時に「未達」として記録したからです。記録しなければ、緑のテストの下に隠れたままリリースされていました。

    Invoice.execute の MarkOverdue コマンドは、ドメインとしては IT7 から存在しています。

            | Pending dueDate, MarkOverdue now when now > dueDate ->
            Ok(
                { invoice with
                    Payment = Overdue dueDate },
                [ PaymentOverdue invoice.InvoiceId ]
            )

    now を引数で受けるため、時刻を注入すればテストできます（第 2 章の Clock ポート）。しかし「実際の now を誰が渡すか」は型の外側の問題です。

    型で守れない領域 4：アーキテクチャの維持¶

    アーキテクチャテストが 24 → 31 件に増えています。

    第 2 章で見た通り、ルールは [<Theory>] でコンテキストごとに展開されます。

    // tests/CargoTracker.ArchTests/ArchTests.fs
[<Theory>]
[<InlineData("Booking")>]
[<InlineData("Shipper")>]
[<InlineData("Estimation")>]
[<InlineData("Routing")>]
[<InlineData("Tracking")>]
[<InlineData("Handling")>]
[<InlineData("Billing")>]

    コンテキストは IT5 で 7 つに揃っているので、IT8 の増加分はルールそのものの追加です。同ディレクトリに MigrationComplianceTests.fs があり、DB マイグレーションの規約（方言の禁止パターンなど）も検証しています。

    F# のプロジェクト参照が防げるのはコンテキスト間の依存までであり、「ドメイン層に Donald が侵入していないか」「マイグレーションに NOW() を書いていないか」といったルールは別途テストが要ります。

    プロジェクト全体の実績¶

    IT8 完了時点の累計です。

    イテレーション 完了 SP 局面 アプローチ

    IT2 10 序盤 アウトサイドイン
    IT3 14 中盤 インサイドアウト
    IT4 12 中盤 インサイドアウト
    IT5 17 中盤 インサイドアウト

    平均ベロシティは 12.1 SP。リリースバーンダウンでは計画線と実績線が完全に重なっており、残 SP は 98 → 1 で着地しています。

    ベロシティの振れ幅は大きく（6〜17 SP）、IT5 の 17 と IT6 の 6 が両極です。IT5 でコンテキストを 2 つ立ち上げ、IT6 で負債を返す、という意図的な緩急がついています。

    カバレッジの推移も見ておきます。

    イテレーション 全体 ドメイン層
    IT2 91.9% 85.7%
    IT3 93.0% 88.4%

    姉妹シリーズの Java 実装が 93% → 80% と単調に低下したのに対し、89〜94% の帯に収まっています。ピークは IT4——ドメインが純粋関数の塊だった回です。

    IT8 で最低値（89.0%）になっているのは、この回の作業が外部連携・通知・合成ルートというテストしにくい領域に集中したためです。閾値（全体 80% / ドメイン層 85%）は維持されています。

    このイテレーションの学び¶

    型が守る領域と守らない領域の境界¶

    8 イテレーションを通して、境界がはっきりしました。

    型が守る 型が守らない
    値の妥当性（スマートコンストラクタ） 外部システムの応答形式
    条件付き必須（和型） 通知が実際に届くこと
    状態と付随データの整合（状態がデータを持つ） 誰がバッチを起動するか
    状態遷移の網羅（パターンマッチ） 永続化との往復での情報損失
    エラー処理の書き忘れ（Result） 業務用語と型名の一致

    右列を埋めるのが IT8 の仕事でした。新規ストーリーがゼロなのに 13 SP かかったのは、この領域が型の支援を受けられないためです。

    予備イテレーションを計画に入れる¶

    IT8 は「予備・強化イテレーション」として、リリース計画の段階から想定されていました。

    姉妹シリーズの Java 実装は、IT10 が結果的に負債返済イテレーションになりました。IT5 のレビュー指摘 H-1〜H-6 がリリース直前まで残り、最後に押し込む形です。

    計画に予備を置くのと、結果的に押し込むのとでは、受入残を正直に記録できるかどうかが変わります。予備があると分かっていれば「これは IT8 でやる」と書けますが、なければ「次で対応」という曖昧な記述になり、そのまま流れます。

    判断を変えたときは実装側に理由を残す¶

    ADR-0014 と実装の食い違い（WireMock.Net → HttpListener）は、実装のコメントに理由が書かれていました。

    ADR を書き換える方法もありますが、なぜ変えたかは変えた場所に書くのが実務的です。ADR は「そのとき何を決めたか」の記録であり、後から書き換えると決定の履歴が消えます。実装側に「ADR とは違う判断をした、理由はこれ」と残すほうが、両方の情報が保存されます。

    姉妹シリーズの Flix 実装のふりかえりには、逆の教訓が記録されています。

    設計図の向きを変えたら ADR。モジュールコメントで代替しない。ACL の方向反転が次のストーリーの設計をブロックした。

    こちらは設計の方向そのものを変えたケースで、ADR が要るという判断です。IT8 の WireMock 差し替えは、契約固定という目的も方式も変えず手段だけを替えたものなので、コメントで足ります。

    Bolt 計画 1 - ウォーキングスケルトン¶

    リリース計画の Bolt 1。この計画は 2026-11-04 に人（プロジェクトの担当者）が承認しました（/goal Bolt1 と、着手前ゲートの承認：ADR-001〜005・007〜009・011 と ADR-006 の API 部分、仮置き Q-1〜Q-3、対象外、AI の仮定をそのまま採用）。確認が要るステップ（新規ファイル・外部ライブラリ・スキーマ変更・認証）では、その都度停止して承認を得ます。

    1. Bolt の概要¶

    項目 内容
    Unit U-02 貨物予約
    ストーリー US02（AC-01・02）、US04（AC-01・02）
    ゴール 荷主を登録し、その荷主の貨物予約を「仮受付」で登録するまでを、UI・API・ドメイン・DB に最小の縦割りで通す
    確認したい仮説 選んだアーキテクチャ（Unit を最上位にしたモジュール、純粋なドメイン + イベントソーシング + CQRS）で、AI が規約どおりの縦割りを TDD で生成できるか。ゲート密度をどこまで下げられるか（リリース計画「ゲート密度」）
    テスト戦略 Standard（U-02。テスト戦略 4）
    ゲート密度 既定：各ステップでゲート。確認必須の操作（新規ファイル・構造・外部ライブラリ・スキーマ）を含むステップは必ず停止
    測るもの 承認ゲート通過数、変更依頼数、手戻り率、リードタイム（リリース計画「進捗の測り方」）。反映遅延の計測点が働くこと（実測の確定は別のスパイクとステージング）

    1.1 対象と対象外¶

    対象 対象外（理由）
    US02 AC-01：荷主を個人で登録し荷主 ID が発行される US02 AC-02 のうち「登録を続ける」の選択は、メール重複の扱い（Q2）の確認後に確定。重複の警告表示までを対象にする
    US02 AC-02：同じメールの荷主が登録済みなら既存の荷主を示す US03（法人）：Bolt 13
    US04 AC-01：荷主を選択する US04 AC-03（経路設計者への通知）：通知ポートのスタブが要り、US06 の通知と二重にならないか未確認（US06 の確認ポイント）。Bolt 4 で扱う
    US04 AC-02：貨物仕様・輸送条件を入力して登録し、予約番号が発行され「仮受付」になる（貨物種別は一般貨物のみ） US04 AC-04（見積との整合性）：判定不能（テスト戦略 11.3）。Bolt 9
    US05（危険物・冷凍・冷蔵）：Bolt 13
    認証・認可の実装：Bolt 2（R-02）。この Bolt では Principal を差し込めるスタブにとどめる

    2. 着手前の承認ゲート¶

    次が未承認のあいだは、ステップ 1 以降を始めません。レビューの指摘 H1・H6・H7 に当たります。

    2.1 承認する ADR（提案中のものを人が承認する）¶

    ADR 承認する内容 この Bolt で効く場所
    ADR-001 パターン・モジュール構成・Unit 間連携 モジュールの切り方、検査 A1〜A3
    ADR-002 イベントストアと配信（一次判断のみ：方式 A で始める。見直しは Bolt 4 の前） 永続化・投影の実装
    ADR-003 冪等性キーと識別子 registerShipper・registerBooking
    ADR-004 個人情報の扱い（荷主は CRUD） booking.shipper
    ADR-005 Clock ポート（業務タイムゾーンの基準は Bolt 1 では仮置き。US04 の基本形に期限と到着の比較は出てこない） Clock
    ADR-007 Scala 3.9 LTS・JDK 21・sbt、ZIO は採らない ビルド
    ADR-008 スキーマ構成と規約（R-03：スキーマ変更の前に承認） マイグレーション
    ADR-009 React + TypeScript + Vite、TanStack Query ほか フロントエンド
    ADR-011 テスト戦略 全ステップ

    ADR-006（GraphQL の API 方式）は、この Bolt で GraphQL を使うため、API 部分だけ承認する（公開照会の分離は Bolt 8）。ADR-010（クラウド）・012・013 は、この Bolt を止めない。

    2.2 事業側の確認（Bolt 1 を止める 3 点）¶

    # 論点 仮置きで進める場合
    Q-1 荷主のメールアドレスの重複：警告にとどめるか、一意制約にするか（domain-model Q2、data-model Q1） 警告にとどめる（US02 AC-02 の文面どおり）。一意制約にはしない
    Q-2 予約番号の形式（data-model Q3） 採番は platform.booking_number_seq、形式は BK- + 連番 6 桁の仮。整形は 1 箇所に隔離
    Q-3 「希望着日」と「希望期限」は同じか（domain-model 3.1） 同じとして扱う（用語集は「希望期限」）。列名は desired_deadline

    2.3 時間制限つきスパイク（Bolt 1 の外で、前に行う）¶

    # スパイク 時間の上限（案） 目的
    SP-1 同一集約への同時書き込み（NFR-A17、レビュー H1） 半日〜1 日 2 つのタスクで同じ集約にコマンドを送ったときの Journal の挙動を確かめ、クラスターモードの要否（BE-12）を判断する材料にする。結果は ADR-001・002・007 と NFR-A07 に反映
    SP-2 反映遅延の実測の準備（NFR-P10） 半日 LocalStack（方式 A）での測り方を決める。確定値はステージングで測る（ローカルでは SLO を確定できない）

    SP-1 の結果で、ステップ 4（アクター）の構成が変わる可能性があります。SP-1 は Bolt 1 の開始前に結論を出す。

    3. 入力となる成果物¶

    • 要件：US02・US04、Unit 定義 U-02、リスク台帳、用語集
    • 設計：ドメインモデル 5（Shipper・Booking）、データモデル 7（booking スキーマ）、UI 設計（SC-20〜22・25〜27）、バックエンド、フロントエンド、技術スタック、テスト戦略
    • ADR：001〜011

    4. ステップ計画¶

    各ステップは Red → Green → Refactor で進め、完了はテストで判定します。「確認」は人が停止して承認するステップです。承認前に実行しません。チェックボックスは完了で更新します。

    4.1 準備（環境・構造）¶

    • S1 ローカル環境の確認（2026-11-04 完了：JDK 21 は Corretto 21.0.x が利用可能（のち 2026-11-04 に JDK 25 へ変更。ADR-007 の更新を参照。イメージのベースは Temurin 21 の想定）、sbt は /usr/local/bin/sbt、Docker デーモンは稼働中。このマシンの既定の java は JDK 25（IntelliJ JBR）なので、sbt 実行時は JDK 21 を JAVA_HOME に指定する。PostgreSQL のコンテナは S9 のスキーマ承認後に compose で起動する。値は読んでいない）：Nix の Scala 開発シェル（scala_3・sbt）と Docker で PostgreSQL が起動することを確認する（方式 A の場合は LocalStack も）。環境変数・接続情報の値は読まない（R-10）。手順書に無い操作は operating-script でタスクにする　確認：環境操作
    • S2 sbt のマルチモジュールの骨格（2026-11-04 完了：承認済みの標準構成。Scala 3.9.0・sbt 1.12.15・sbt-scalafmt 2.6.2・scalatest 3.2.20・archunit 1.5.1。modules/architecture-tests の ModuleBoundariesSpec（A1 と層の向き。100 件）を先に書いて Red（build.sbt なし）→ Green。壊して赤：contract に domain への依存と参照を足すと「booking の contract は自 Unit の内側を参照しない」が FAILED、元に戻すと緑）：shared-kernel・booking（domain／use-case／contract／command-adapter／query-adapter）を空で作り、dependsOn で依存の向きを固定する。テストが先：A1（別 Unit の内側を参照しない）の検査が、わざと違反させると赤になる。ADR-007 の版を build.sbt に固定する　確認：新規ファイル・構造・外部ライブラリの導入（R-01）

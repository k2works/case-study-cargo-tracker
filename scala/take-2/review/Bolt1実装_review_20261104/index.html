    レビュー結果 - Bolt 1 ウォーキングスケルトンの実装¶

    レビュー対象¶

    未コミットの Bolt 1 実装一式（modules/、apps/local-server、apps/web、ops/scripts/ac-trace.cjs）。計画は Bolt 1 計画 の S26。

    総合評価¶

    層ごとの規律（純粋なドメイン、ポートとアダプター、認可を検証より先、Protobuf の旧版バイト列の固定、壊して赤）は高い水準で、5 視点とも骨格を評価している。一方、各層は緑のまま、層をまたぐと壊れる経路が複数の視点から独立に指摘された。最も重いのは次の 4 群。

    1. 書き込み側が受け付けるが、読み取り側が入れられない値がある（港の実在、重量・寸法の桁）。利用者には「受け付けました」と出て、一覧には永久に出ない。
    2. 冪等性が約束を満たさない経路がある（同時要求、成功後に保存が失敗した再送、「登録を続ける」の再送で毎回新しいキー）。
    3. 項目名がサーバーと画面で食い違う（港コード、寸法、荷主 ID）。モックが本物より甘く、テストは素通り。
    4. 営業の流れが途中で切れる（荷主詳細 → 予約登録の導線なし、荷主・予約の一覧が 100 件で切れ、新しい荷主が選べなくなる）。

    改善提案（統合・重要度順）¶

    高（Bolt 1 の完了前に対応方針を決める）¶

    # 提案 箇所 指摘元
    H1 書き込み側で港の実在を確かめる（出力ポート）。重量・寸法の精度と上限を列に合わせる。最小正値・最大桁・参照外の港でコマンドから投影まで通す回帰テスト RegisterBooking.scala、BookingValues.scala、V1__shipper_and_booking.sql アーキテクト・テスター・ライター
    H2 冪等性：同じキーの同時要求（荷主が 2 件できる）、成功後に保存が失敗した再送（INVALID_TRANSITION になる）。キーの事前予約か、ADR-003 に Bolt 1 の制約として明記。同時送信のテスト Idempotency.scala、PlatformAdapters.scala アーキテクト・テスター
    H3 「登録を続ける」の再送で毎回新しいキーになり、二重登録しうる。承知用のキーを保持する。通信エラー後の再送テスト ShipperRegisterForm.tsx:25-28 プログラマー・ライター・テスター
    H4 項目名の食い違い：港コードは portCode、荷主 ID は ulid、寸法は dimensions。呼び出し側が origin / destination / shipperId を決める。画面のモックを本物の応答の形から作る PortCode.scala、Ulid.scala、BookingRegisterForm.tsx:114-119 プログラマー・テスター・ライター
    H5 一覧の上限 100 件（古い順）で、新しい荷主が選べない。ホームの件数も 100 で頭打ち。検索して選ぶ UI と件数 Query Queries.scala:68-71、hooks.ts、Home.tsx 利用者代表・テスター・プログラマー
    H6 荷主詳細に「この荷主で予約を登録」（/bookings/new?shipperId=）。「既存の荷主を使う」の後も予約へ進めるようにする。ID が空のときのフォールバック ShipperDetail.tsx、ShipperRegisterForm.tsx:55 利用者代表
    H7 重複警告に既存の荷主（氏名・種別・住所）を出す（US02 AC-02「既存の荷主が表示され」） ShipperRegisterForm.tsx:51-62 利用者代表・テスター
    H8 待避先の行がリプレイのたびに増える。(projection_name, event_id) の一意制約と ON CONFLICT DO NOTHING。停止→再開で件数が増えないテスト EventProcessor.scala、V3__platform_tables.sql アーキテクト・テスター
    H9 起動手順が無く、マイグレーションを適用する手段も無い。E2eServer 相当を正式な開発用タスクにし（operating-script）、手順書とエラー文にタスク名を書く LocalServer.scala、docs/operation/ ライター
    H10 予約一覧の「予約を登録」が経路設計者・追跡管理者にも出て 403 になる。canOpen で出し分け BookingPages.tsx:37 利用者代表
    H11 個数の入力が parseInt で黙って丸まる（2.5 → 2、abc → 0）。文字列のまま送ってサーバーで判定 BookingRegisterForm.tsx:52 利用者代表・プログラマー・テスター・ライター

    中（対応推奨）¶

    # 提案 指摘元
    M1 要求のハッシュが toString（区切り文字の衝突、項目追加で保存済みキーが無効、120.5 と 120.50 が別扱い）。正規化した表現に プログラマー・アーキテクト・テスター
    M2 復元で不変条件を検査し直している。後の Bolt で厳しくすると過去のイベントが Malformed になる。復元用の構築子を分ける アーキテクト
    M3 認可が resolver と use-case に重なり、入力変換も先に走る。入力を文字列で受けて use-case の validate に寄せる プログラマー・アーキテクト
    M4 内部エラーを記録せず捨てている（相関 ID も無い） プログラマー・アーキテクト
    M5 集約レジストリの監督・passivation が無い。永続化失敗で全体が ask タイムアウトになりうる（SP-1 の観点に追加） アーキテクト・プログラマー
    M6 event-processor が command-adapter に依存。2 つ目の Unit の前にタグとコーデックを移す アーキテクト
    M7 ADR-005（now() 禁止）、NFR-S22（ログ走査）、A1 の空振り（allowEmptyShould）に検査を置く アーキテクト・テスター
    M8 認可の表が 3 か所。突き合わせるテストを置く アーキテクト・プログラマー
    M9 開発用認証 + 0.0.0.0 の組み合わせを起動時に拒む。ServerConfig.toString でパスワードを隠す。既定無効を fromEnv で固定するテスト アーキテクト・テスター
    M10 冪等性ストアのフェイクが本物と違う（上書き・期限なし）。「内容違い」のテストが予約 ID の違いで通ってしまう テスター
    M11 テストの隔離：ActorSystem と Journal の共有、Thread.sleep での「増えない」確認、永続化失敗の未検査 テスター
    M12 ac-trace が ignore( とコメントアウトを数える。テストと CI 呼び出しが無い。Gulp タスク化の規約 テスター・ライター・アーキテクト
    M13 適用済みマイグレーションの書き換え検査が無い テスター
    M14 画面：予約一覧に荷主名、結果に「仮受付」、反映待ちの文面、荷主取得失敗、予約詳細の荷主・寸法、履歴の日時を JST に 利用者代表・ライター
    M15 エラー文：サーバーの reason 文字列が画面に出る。理由コードにして文面は画面の表で作る。未ログイン時の案内に「Bolt」が出る ライター
    M16 反映待ちが一覧（上限 100）から探している。booking(id) で問い合わせる プログラマー・アーキテクト
    M17 読み取りモデルから書き込み側の表への外部キー（個人情報の削除方針で再検討） アーキテクト
    M18 設計書・計画の乖離：bolt_plan の冒頭が「草案」のまま、仮定 9 と S17 の矛盾、件数の食い違い、tech_stack.md の版（Flyway・TS・graphql）、ADR-002 の注記（S27 で反映） ライター・アーキテクト
    M19 重複コード（execute の骨格、二重解析、errorJson、フォームの共通部品）、文字列の直書き（'RECEIVED'、"INDIVIDUAL"）、Locale.ROOT プログラマー

    低¶

    文字数上限の境界値、docstrings.wrap = no、tsbuildinfo の無視、動詞の揺れ、ヘッダーのログアウト、行き止まり画面のリンク、MSW のスキーマ検証、必須の表示、起動失敗時の終了コード、Journal 再起動時の食い違いの注記、過去日付の引渡日（仕様要確認）など。詳細は各視点の原文を参照。

    矛盾事項¶

    # 論点 推奨判断
    1 冪等性の穴：キーの事前予約まで直すか、ADR-003 に Bolt 1 の制約として書いて SP-1 に回すか 荷主の重複は業務に直結。H3（再送のキー）は今直し、H2 の同時要求は事前予約を SP-1 の観点に入れて ADR に制約を明記する案を推奨
    2 港の入力を、実在確認の追加（ポート）で解くか、reference.port から選択肢を作る UI で解くか 両方必要（UI の選択は誤入力を減らすが、API は別に守る）。ポートを先に

    対応結果（2026-11-04、「推奨案で良い」の承認後）¶

    • 修正済み：H1、H3、H4、H6、H7、H8、H10、H11（テストを先に書き、H3 は壊して赤を確認。sbt 全体・vitest・E2E が緑）
    • 制約として記録：H2（ADR-003 に Bolt 1 の制約として追記。SP-1 の観点）、H5・H9（Bolt 計画 S26 に記録。次の Bolt の前）
    • 中・低：S27 / SP-1 / 次の Bolt

    対応方針の案（承認済み）¶

    • 今の Bolt 1 で直す（推奨）：H1、H3、H4、H6、H7、H10、H11（局所的で、E2E で壊れが見える）
    • 今の Bolt 1 で直すか、受け入れて記録するかを選ぶ：H2（同時要求）、H5（検索型の選択）、H8、H9

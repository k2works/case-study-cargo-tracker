## AI-DLC の規律（本プロジェクト固有）

### TDD の三原則をプロンプトに明示する

AI は一度にたくさん書けるため、放っておくとテストを書かずに実装し、失敗を確認せずに進み、テストが要求する以上の機能を先回りして実装する。ステップ計画を書くときも実装を指示するときも、次の三原則を必ず含める。

1. 失敗するテストを書くまで、プロダクションコードを書いてはならない
2. 失敗するテストは、失敗するのに十分なだけ書く
3. 現在失敗しているテストを成功させる以上のプロダクションコードを書いてはならない

Red では失敗を実行して確かめ、その出力を承認ゲートで示す。Green では最小限だけを書く。

### ステップ計画の置き場所と承認

- Bolt のステップ計画は `docs/development/bolt_plan-N.md`（N は `release_plan.md` の Bolt 番号）に書く。承認前に実装を始めない
- ゲート密度の既定は「各ステップでゲート」。Bolt 1（ウォーキングスケルトン）の結果で `release_plan.md` を見直すまで下げない
- ステップの完了報告には、作成・変更・削除したファイルの一覧を含める（ソース束縛レビュー）。人は `git diff --stat` と突き合わせる

### 受入条件からテストを書く

- テストは `user_story.md` の受入条件（`AC-01` など）に対応づけ、テスト名かコメントで AC 番号を示す。期待値は受入条件から取り、実装の出力をコピーしない
- 受入条件に「（AI の仮定）」や「要確認」が付いた振る舞いは、確認が取れるまで実装しない。計算式・料率・項目が未定義で期待値が決まらない場合（US01・US05・US21・US30 など）は、仮の値で実装せず人に戻す
- テスト戦略の水準は `release_plan.md` の Unit ごとの指定に従う（U-01・U-03・U-05 は Comprehensive、U-02・U-04 は Standard）

### ドメインモデルの規律

既存レビュー（`docs/review/ドメインモデル分析_review_20260331.md`）で、オリジナルの Cargo Tracker を分析したモデルが本プロジェクトの要件と合わないことが分かっている。AI は参照実装やオリジナルのモデルを「正解」として写しやすいため、次を守る。

- 予約状態・貨物状態・通関状態は要件定義書の状態モデルと用語集を正とする。参照実装（`docs/article/source/`）やオリジナルの列挙値（`TransportStatus` など）を持ち込まない（R-06・R-07）
- 識別子（予約番号・追跡番号など）は値オブジェクトにし、集約ルートにしない。識別子のためだけのリポジトリを作らない
- Unit（コンテキスト）の境界を越えて相手の型を直接参照しない。`units.md` の依存 DAG の向きに従い、問い合わせかイベントの契約で連携する
- 集約と値オブジェクトの間に循環依存を作らない
- 経路算出の制約条件は要件定義書の 5 つを正とし、追加・省略しない（R-04）

### 確認必須の操作

`risk_register.md` の「確認必須の操作」に該当するステップは、計画に注記し、実行前に停止する。本 Unit 群で特に起きやすいのは次のとおり。

- スキーマ変更・マイグレーション（R-03）
- 認証・認可の実装（R-02。U-01）
- 外部システム（港湾管理・税関・決済機関・通知）の連携。実仕様を仮定で作らず、ポートとスタブで進める（R-01）
- 依存ライブラリの追加（存在しない API を使う幻覚を防ぐため、追加は人が確認する）
- `.env`・`.env.vault` の値には触れない（R-10）

### 既存を参照させる

実装が始まったら、値オブジェクト・テストフィクスチャ・命名規則の置き場所をこの節に追記する。AI は既存を探さずに似た実装を新しく作りやすいため、新しく作る前にここを参照させる。

- （Bolt 1 のウォーキングスケルトン完了後に追記）

### 修正の反映先

人が AI の振る舞いを修正したら、全プロジェクト共通の規律は `CLAUDE.md`、本プロジェクトのバックエンド固有はこのファイル、特定の Unit・ストーリーの判断は `bolt_plan-N.md` の「AI の仮定」と `docs/journal/` に書く。

# AI-DLC 移行

XP ベースで運用してきたプロジェクトを **AI-DLC** の運用に移行し、移行後の適合性を検証する。日常の運用（Bolt 計画・ストーリー作成・実装）は各スキルが担い、本スキルは「一度きりの移行」と「適合しているかの確認」を担う。`migrating-okf` が文書のフォーマットを移行するのに対し、本スキルは **開発の進め方** を移行する。

移行の根拠は次のガイド。**作業前に必ず読む**。ガイドと本スキルが食い違う場合はガイドを正とする。

| ガイド | 本スキルで使う箇所 |
| :--- | :--- |
| `docs/reference/AI-DLC導入ガイド.md` | 第 3 章（10 原則）、第 4 章（成果物）、第 13 章（本プロジェクトへの導入ステップ） |
| `docs/reference/開発ガイド_AI-DLC版.md` | 活動ごとの AI と人の分担、ガイド対応表 |
| `docs/reference/リリース・イテレーション計画ガイド_AI-DLC版.md` | 第 1 章（Unit 分解・エントロピー評価・Bolt 計画）、第 5 章（リスク台帳）、第 8 章（計画スキルの読み替え） |
| `docs/reference/ユースケース作成ガイド_AI-DLC版.md` | 第 5 章（テンプレート）、第 10 章（Unit とストーリーマップ）、第 12 章（ブラウンフィールド） |
| `docs/reference/コーディングとテストガイド_AI-DLC版.md` | 基本原則（ガードレール化する規律）、本プロジェクトの開発スキルへの適用 |
| `docs/reference/AI-DLC用語集.md` | 用語の定義 |

同じディレクトリに `PROJECT.md` があれば必ず読む。対象プロジェクトの識別子・`docs/` と `apps/` の配置・既存の計画ファイル名・ガードレールの置き場所など、プロジェクト固有の値はそこにある。

## なぜ移行するのか

AI-DLC の核心は「AI が計画・分解・生成を担い、人が承認ゲートで検証・決定する」構図にある。ガイドを置き、CLAUDE.md に採用を書いただけでは、docs/ のストーリーは Unit にまとまっておらず、計画はストーリーポイントのままで、AI に渡せない範囲も決まっていない。そのままだと AI は既存の XP 版の成果物を読んで XP 版の振る舞いを続け、人は「AI-DLC を採用したはずなのに何も変わらない」と感じる。移行の本質はファイルの改名ではなく、**AI が読む成果物を AI-DLC の契約（Unit・受入条件・リスク・ガードレール）の形に揃えること** である。

移行そのものも AI-DLC の流儀で進める。計画を書き、人の承認を得てから 1 ステップずつ実行し、重要な判断（Unit の境界、AI に渡せない範囲、ゲート密度）は勝手にしない。

## モード

| モード | 用途 |
| :--- | :--- |
| `--plan` | 現状を棚卸しし、移行前の状態を測り、移行計画をチェックボックス付き Markdown で提示する。既存の成果物は変更しない |
| `--migrate` | 承認済みの移行計画を 1 ステップずつ実行する（既定） |
| `--check` | 移行後の適合性を検証し、不足を移行ステップに対応づけて報告する。ファイルは変更しない |

指定がなければ、移行済みの痕跡（`docs/requirements/<project>/units.md`）が無ければ `--plan` → 承認 → `--migrate`、あれば `--check` から始める。

## 進め方

### 1. 棚卸しと移行計画（`--plan`）

#### 1-1. 移行前の状態を測る

最初に検査スクリプトを実行し、ERROR と WARN の件数と主な項目を記録する。移行の前後を同じ物差しで比べられるようにするためで、計画の各ステップがどの不足を埋めるのかも、この結果と対応づけて書ける。

```bash
python .claude/skills/migrating-ai-dlc/scripts/aidlc_check.py --project <project>
```

#### 1-2. 棚卸し

次を調べ、現状を表にまとめる。

| 調査対象 | 見るもの | 判断 |
| :--- | :--- | :--- |
| `CLAUDE.md` | 「開発方法論：AI-DLC を採用する」節の有無、ペルソナの参照先 | 無ければ移行ステップに含める |
| `docs/reference/` | AI-DLC 導入ガイドと AI-DLC 版ガイド 4 本・用語集の有無 | 無ければ `npx boost --update` を先に案内し、移行は中断する |
| `docs/requirements/<project>/` | ユーザーストーリーの本数、受入条件を持つストーリーの本数（ストーリー単位で数える）、書式 | 受入条件が Given/When/Then でなければ書き直しの対象 |
| `docs/development/<project>/` | `release_plan.md`・`iteration_plan-N.md` の見積もり方式、進行中のイテレーション | 進行中のイテレーションは Bolt 計画に読み替える。完了済みは触らない |
| `docs/design/<project>/` | ドメインモデル・用語集・アーキテクチャ・ADR の有無 | 用語集が無ければ移行ステップで作る |
| `apps/<project>/` | コードの有無（ブラウンフィールドか）、テストの有無、フロントエンドの有無 | ブラウンフィールドなら静的・動的モデルへの昇格を含める。フロントエンドが無ければ `developing-frontend` は対象外 |
| `.claude/skills/*/PROJECT.md` | 既存のガードレール（命名規則・既存ユーティリティ・確認必須の操作） | TDD の三原則などの AI-DLC の規律が無ければ追記対象 |
| 組織のポリシー | AI に渡せないデータ・コード・鍵 | 分からなければ質問する。仮定で埋めない |

#### 1-3. 移行計画を書く

計画は `docs/development/<project>/aidlc_migration_plan.md` に書く。ファイル名は変えない。`--check` がこのパスで計画の有無を確かめる。

**計画に書くのは「何を・どの順で変え・どこで人の判断が要るか」まで** にする。Unit 定義、依存 DAG、ストーリーマップ、リスク台帳の表、エントロピー評価の表、静的・動的モデル、Bolt のステップといった **後続ステップの成果物は計画に書かない**。理由は 2 つある。

- 承認ゲートは誤りを早く刈り取るための損失関数で、1 つのゲートで判断するものは少ないほど効く。計画に Unit 案まで入れると、人は計画の承認と Unit 境界の承認を同時に求められ、ステップ 6 のゲートを経ずに境界が既成事実になる
- 計画が変更依頼で書き直されると、先に作った成果物の下書きはそのまま無駄になる。計画が短いほど承認までの往復も速い

棚卸しで気づいた候補（「決済は独立 Unit になりそう」「10 万円超の承認分岐は業務ルール候補」など）は、該当ステップの注記か要確認に 1 行で書けば足りる。

```markdown
# AI-DLC 移行計画：<project>

## 現状
- 検査結果（移行前）: ERROR 3 / WARN 9（主な項目: units.md 無し、risk_register.md 無し、CLAUDE.md の採用節無し）
- ストーリー: 12 本（受入条件あり 3 本、Given/When/Then 0 本）
- 計画: release_plan.md（ストーリーポイント）、iteration_plan-3.md 進行中
- コード: apps/<project>/（ブラウンフィールド、テスト 2 件、フロントエンド無し）
- ガードレール: developing-backend/PROJECT.md に命名規則のみ

## 移行ステップ
- [ ] 1. CLAUDE.md に AI-DLC 採用を明記する
- [ ] 2. AI に渡せる範囲（In/Out）とリスク台帳を作る ※組織ポリシーの確認が必要
- [ ] 3. ドメイン用語集を整備する
- [ ] 4. 既存コードを静的・動的モデルに昇格させる（ブラウンフィールド） ※業務ルール候補の確認が必要
- [ ] 5. ストーリーの受入条件を Given/When/Then に揃える
- [ ] 6. ストーリーを Unit にまとめ、依存 DAG とストーリーマップを作る ※Unit の境界は要承認
- [ ] 7. release_plan.md にエントロピー評価とスコープ・深さ・テスト戦略を加える
- [ ] 8. 進行中の iteration_plan-3.md を bolt_plan-3.md に読み替える ※ウォーキングスケルトンの選定は要承認
- [ ] 9. ガードレールを各スキルの PROJECT.md に書く
- [ ] 10. OKF を適用し、適合性を検証する（目標: ERROR 0）

## AI の仮定
- 決済は外部サービスのため AI に本番キーを渡さない（要確認）

## 要確認
- AI に渡せないデータ・鍵の範囲と、組織のリスク台帳の有無
```

`--plan` で作るのは計画ファイルと、その `index.md`・`log.md` への登録だけ。既存のストーリーや計画は変更しない。

### 2. 移行（`--migrate`）

承認された計画を 1 ステップずつ実行し、完了ごとにチェックボックスを更新する。成果物の書式は `references/artifact-templates.md` を使う。

#### ステップ 1：CLAUDE.md に AI-DLC 採用を明記する

`lib/assets/CLAUDE.md`（booster のテンプレート）と同じ「開発方法論：AI-DLC を採用する」節を、対象プロジェクトの `CLAUDE.md` に加える。ペルソナの参照先を `開発ガイド_AI-DLC版.md` にする。すでにあれば何もしない。

#### ステップ 2：AI に渡せる範囲とリスク台帳を作る

`docs/requirements/<project>/risk_register.md` を作る。組織のリスク台帳があればその ID と対応づける。本番データ・機密情報・鍵・決済など **AI に渡せないもの** と、**確認必須の操作**（新規ファイル・構造変更・外部連携・セキュリティ・データベース・本番環境）を列挙し、各リスクに `R-01` のような ID を振る。ここで決めた内容が以降のすべての AI 生成物の前提になるので、分からないことは質問して埋める。

#### ステップ 3：ドメイン用語集を整備する

`docs/design/<project>/glossary.md` が無ければ、既存のストーリー・ドメインモデル・コードの命名から用語を集めて作る。同じ概念が別の語で書かれていれば統一する。AI はユースケース内の語のゆれを別エンティティとして生成するため、用語集は Unit 分解の前に要る。

#### ステップ 4：既存コードを静的・動的モデルに昇格させる（ブラウンフィールドのみ）

`apps/<project>/` のコードから、静的モデル（コンポーネント・責務・関係）と動的モデル（主要ユースケースを実現する相互作用）を `docs/design/<project>/` に書く。コードに埋め込まれた条件分岐は業務ルール候補として別に列挙し、使われていない経路や不明な意図は推測せず「要確認」と印を付ける。人が検証してから次に進む。これを省くと AI は生のコードを読んで規約から外れた生成をする。

#### ステップ 5：受入条件を揃える

各ストーリーの受入条件を Given/When/Then で一意に判定できる形にする。「参照する成果物」「確認ポイント」「AI の仮定」の欄を加える（ユースケース作成ガイド AI-DLC 版 第 5 章のストーリー形式）。既存の文面の意味は変えない。曖昧で書き直せないものは「要確認」として人に戻す。

#### ステップ 6：Unit 分解・依存 DAG・ストーリーマップ

ストーリーを凝集度で **Unit** にまとめ、`docs/requirements/<project>/units.md` に書く。各 Unit には **目的・含まれるストーリー・NFR・リスク・測定基準・推奨 Bolt・エントロピー評価・AI の仮定** を置く。続けて Unit 間の依存 DAG と、ユースケース × Unit × ストーリーの対応表を書き、どの Unit にも入らないストーリーは「未配置」として列挙する。

- **Unit の条件** は「独立して開発・デプロイできる」こと。ユースケースの境界とは一致させない。境界は設計判断なので、案を示して人の承認を得る
- **リスク欄は台帳の ID で参照する**（例: `R-01（本番キーを渡さない）`）。ガードレールの本文は `risk_register.md` と各スキルの `PROJECT.md` に置き、units.md に書き写さない。AI は作業のたびに台帳と PROJECT.md を読むが、units.md に埋もれた禁止事項は Unit を読まない作業では見落とされ、二重管理にもなる。台帳がまだ無ければ暫定 ID（`R-P01` など）を振り、ステップ 2 で正式な ID に置き換えると「AI の仮定」に書く
- **AI の仮定** には、境界を決めるときに置いた前提（「与信チェックは注文処理側に置く」など）を書く。承認ゲートで人が確かめるべき点が明示される

書き終えたら `aidlc_check.py` を実行し、units.md に関する項目がすべて OK になったことを確かめて報告する。

#### ステップ 7：リリース計画の読み替え

`docs/development/<project>/release_plan.md` に、Unit ごとの **エントロピー評価**（意図の曖昧さ・構造的不確実性・検証の不確実性・リスク・未解決の仮定を LOW／MED／HIGH）と、**スコープ・深さ・テスト戦略** の選択を加える。ストーリーポイント欄は削除せず「参考」として残す。本番機能のテスト戦略は Standard 未満にしない。未配置のストーリーを計画に残す場合は、Unit を追加するかスコープバッファとして明記する。

#### ステップ 8：進行中のイテレーション計画を Bolt 計画に読み替える

進行中の `iteration_plan-N.md` から、同じ番号の `bolt_plan-N.md` を作る。Bolt ゴールに「確認したい仮説」を入れ、最初の Bolt を **ウォーキングスケルトン**（エンドツーエンドの最小の縦割り）にする。ゴールとステップが一致しているか（「API から DB まで通す」ならその層のステップが全部あるか）を確かめる。ゲート密度は「各ステップでゲート」を既定にし、ウォーキングスケルトンの結果で見直すと明記する。元の `iteration_plan-N.md` は `apply-okf` の deprecate で `replaced_by` を付け、削除しない。完了済みのイテレーション計画は触らない。

#### ステップ 9：ガードレールを書く

各スキルの `PROJECT.md` に、AI-DLC の規律をプロジェクト固有の形で書く。SKILL.md は booster の更新で上書きされるため、必ず `PROJECT.md` 側に置く。対象プロジェクトに無い層のスキル（フロントエンドが無ければ `developing-frontend`）は書かなくてよい。

| 置き場所 | 書く内容 |
| :--- | :--- |
| `developing-backend/PROJECT.md`、`developing-frontend/PROJECT.md` | TDD の三原則をプロンプトに明示すること、ステップ計画の置き場所、テストの命名規則、参照すべき既存実装・フィクスチャ、確認必須の操作 |
| `planning-releases/PROJECT.md` | Unit 定義・Bolt 計画の置き場所、エントロピー評価の運用、ゲート密度の既定 |
| `analyzing-usecases/PROJECT.md` | 用語集の場所、受入条件の書式、Unit 分解の条件 |
| `developing-review/PROJECT.md` | AI 生成コード固有の観点（先回り実装・同型テスト・過剰モック・既存の無視） |
| `ai-agent-guidelines/PROJECT.md` | 全行理解、仮の実装の明示、修正のガードレール反映先 |

既に人が AI を修正した記録（ジャーナル・レビュー指摘）があれば、それもガードレールに写す。

#### ステップ 10：OKF 適用と検証

作成・変更した文書に `apply-okf` を実行し（`apply docs --changed --by <agent>`）、`index.md`・`log.md` を更新する。`okf_apply.py` は git の差分から変更を判定するため、git 管理外のプロジェクトでは失敗する。その場合は `docs/reference/OKF導入ガイド_V0.2.md` §5 に沿ってフロントマター（`type`・`title`・`description`・`generated`、未レビューなら `status: draft`）を手で書き、`index.md`・`log.md` も既存の書式に合わせて更新し、完了報告にその旨を書く。

続けて本スキルの `--check` を実行し、不足があれば計画に戻る。移行計画の「AI の仮定」欄に残った未確認の仮定は、完了報告の要確認に載せる。

### 3. 検証（`--check`）

#### 3-1. 検査スクリプトを実行する

```bash
python .claude/skills/migrating-ai-dlc/scripts/aidlc_check.py --project <project> [--docs docs] [--apps apps] [--claude-md CLAUDE.md]
```

ERROR は移行が完了していない印、WARN は運用の中で埋めればよい印。報告には件数（`ERROR n / WARN n`）と各項目をそのまま載せる。

| 項目 | 判定 |
| :--- | :--- |
| CLAUDE.md に「AI-DLC を採用する」節がある | ERROR |
| AI-DLC 導入ガイド・AI-DLC 版ガイド 4 本・用語集が `docs/reference/` にある | ERROR |
| `units.md` がある | ERROR |
| 各 Unit に目的・ストーリー・NFR・リスク・測定基準・推奨 Bolt・エントロピー評価・AI の仮定がある | WARN |
| `units.md` に依存 DAG とストーリーマップがある | WARN |
| 未配置のストーリーが `release_plan.md` に割り当てられていない | WARN |
| `risk_register.md` があり、AI に渡せる範囲と確認必須の操作が書かれている | ERROR |
| `glossary.md` がある | WARN |
| 受入条件を持つストーリーの本数と、Given/When/Then の本数（ストーリー単位） | WARN（割合を報告） |
| `release_plan.md` にエントロピー評価とテスト戦略がある | WARN |
| `bolt_plan-N.md` に確認したい仮説・ゲート密度・ウォーキングスケルトンがあり、同じ番号の `iteration_plan-N.md` が deprecated になっている | WARN |
| ブラウンフィールドで静的・動的モデルがある | WARN |
| 移行で作った成果物に人の承認記録（`verified`）がある | WARN |
| 移行で作った成果物が各ディレクトリの `index.md` に登録されている | WARN |
| `aidlc_migration_plan.md` がある | WARN |
| 開発スキルの `PROJECT.md` に TDD の三原則がある（フロントエンドが無ければ `developing-frontend` は対象外） | WARN |

#### 3-2. スクリプトが見ない点を読んで確かめる

スクリプトはファイルとキーワードの有無しか見ない。ERROR 0 でも運用できる状態とは限らないので、次を実際に読んで確かめる。

- **成果物同士の矛盾**: 依存 DAG と Bolt の並び・リリース計画の順序が逆になっていないか。Bolt ゴールとステップが一致しているか。ストーリーの状態が文書間で食い違っていないか
- **契約としての中身**: リスク台帳に「In（AI に任せる範囲）」が書かれているか、確認必須の操作が CLAUDE.md より少なくないか。用語集で語のゆれが解消されているか
- **コードと契約の整合**（ブラウンフィールド）: 受入条件と既存実装の振る舞いが一致しているか。テストの無い先回り実装や未使用コードが残っていないか

#### 3-3. 報告する

不足ごとに、該当する移行ステップ番号と直し方を書く。`--check` ではファイルを変更しない。直すかどうかは人が決め、承認されたら `--migrate` の該当ステップで直す。

## 判断に迷いやすい点

- **Unit の境界**: ユースケース単位でも画面単位でもなく「独立してデプロイできるか」で切る。迷ったら小さく切らず、依存を共有する Unit を 1 つにまとめる方が安全。分割は後からできる
- **完了済みのイテレーション**: 読み替えない。過去の記録は当時の方法論のまま残す
- **ストーリーポイントの扱い**: 消さない。エントロピー評価を並記し、数 Bolt 回した後にどちらが予測に役立ったかで決める
- **ガードレールの粒度**: 「〜してはならない」を並べるより、なぜその規律が要るか（AI が先回りして実装する、既存を探さず重複を作る）を書く。理由が伝われば AI は類似の場面にも適用できる
- **AI に渡せない範囲が決まらない**: 移行を止めて質問する。ここを仮定で埋めると、以降のすべての生成物が組織ポリシーに反する可能性がある
- **計画に下書きを入れたくなったとき**: 入れない。気づいた候補は要確認に 1 行で残し、該当ステップのゲートで判断してもらう

## 完了報告

`--migrate` の最後に次を報告する。

```markdown
## AI-DLC 移行結果

- 対象: <project>（グリーンフィールド／ブラウンフィールド）
- Unit: <N> 件（ストーリー <M> 件を配置、未配置 <K> 件）
- 計画: release_plan.md にエントロピー評価を追加、iteration_plan-<N>.md → bolt_plan-<N>.md（ウォーキングスケルトン: <Unit 名>）
- ガードレール: <更新した PROJECT.md の一覧>
- 検証: 移行前 ERROR <n> / WARN <n> → 移行後 ERROR 0 / WARN <n>
- 要確認: <Unit の境界の判断、AI に渡せない範囲、未確認の仮定 など>
```

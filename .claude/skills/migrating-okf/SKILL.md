# OKF 移行

プロジェクトの Markdown ドキュメントを OKF（Open Knowledge Format）の**知識バンドル**に移行し、仕様バージョンアップに追従させる。

仕様の日本語リファレンスは `docs/reference/OKF導入ガイド_V0.2.md`。**作業前に必ず読む**。特に §4（コンセプト文書）・§5（来歴・信頼・ライフサイクル）・§11（適合性）・§13（バージョン間の変更点）・§14（導入手順）が本スキルの根拠になる。ガイドと本スキルが食い違う場合はガイドを正とする。

同じディレクトリに `PROJECT.md` があれば必ず読む。バンドルの置き場所・対象ディレクトリ・既定の `generated.by`・除外パターンなど、プロジェクト固有の値はそこにある。

## なぜ OKF に移行するのか

エージェントが繰り返し参照し、書き換えもする知識には「どこから来たか（来歴）」「誰が確認したか（信頼）」「まだ有効か（鮮度）」が要る。素の Markdown にはそれを置く場所がない。OKF は YAML フロントマターを持つ Markdown のディレクトリというだけの最小規約で、この 3 つを第一級にする。移行の本質はフォーマット変換ではなく、**各文書に「信頼してよい根拠」を持たせること**である。

## モード

| モード | 用途 |
| :--- | :--- |
| `--plan` | 対象文書を棚卸しし、バンドル構造と `type` 割り当て案を提示する。ファイルは変更しない |
| `--migrate` | 文書に OKF フロントマターを付与し、`index.md`・`log.md` を整備する（既定） |
| `--upgrade <version>` | 既存バンドルを指定バージョンの仕様に追従させる（例: `--upgrade 0.2`） |
| `--check` | バンドルの適合性を検証し、違反と警告を報告する |

指定がなければ、バンドルが未作成なら `--plan` → 確認 → `--migrate`、作成済みなら `--check` から始める。

## 進め方

### 1. 棚卸し（`--plan`）

1. 対象ディレクトリ（既定 `docs/`。`PROJECT.md` で上書き可）の `.md` を列挙する
2. 各文書を読み、次を判断する
   - **コンセプトにするか除外するか**。`index.md`・`log.md` は予約名なのでコンセプトにできない。テンプレート（`docs/template/`）や一時的なジャーナルは通常除外する
   - **`type`**。既存ディレクトリから素直に導く（例: `docs/adr/` → `ADR`、`docs/design/` → `Design`、`docs/operation/` → `Playbook`、`docs/reference/` → `Reference`）。中央登録はないので、説明的で一貫した値を選ぶことだけが要件
   - **`resource` の有無**。テーブル・API・ダッシュボードなど実在の資産を説明する文書だけに付ける
3. バンドル構造案を提示する。**既存ディレクトリ構造を尊重する**（移動はリンク切れと git 履歴の断絶を招く）。ガイド §14.2 の骨格はあくまで新規作成時の例
4. 提案を表にまとめ、ユーザーの確認を得てから `--migrate` に進む

### 2. 移行（`--migrate`）

各コンセプト文書に対して：

1. **フロントマターを付与する**。既存の見出し・本文はそのまま残す
   - `type`（必須）、`title`（既存の `# 見出し` から）、`description`（本文冒頭から 1 文に要約。無ければ書く）、`tags`
   - `generated: { by, at }`。`generated` は「**今の本文を誰がいつ書いたか**」を表す。フロントマターを付けただけで本文を変えていないなら、書いた人は変わっていないので、git log の著者から `human:<id>`、`at` は本文を最後に変えたコミットの日時にする。本文を書き換えた（要約を書き足した、構造化のため再構成した）なら本作業のエージェント（例: `claude-code/claude-fable-5`）と現在時刻。著者が git から辿れない（履歴が浅い、インポートされた文書）なら `generated` を省略し、レポートの要確認に載せる。移行しただけの文書にエージェントを著者として書くと、来歴が嘘になる
   - 既存のフロントマター（Wiki.js の `dateCreated`/`editor`/`published`、Jekyll の `layout` など）があれば**併合**する。意味が対応するキーは OKF に写し（`dateCreated` → `generated.at`）、ツール固有で意味を失うキーは削除し、削除したことをレポートに書く。判断がつかないキーは残す（未知キーは仕様上有効）
   - `status`。レビュー済みの安定文書は `stable`（省略可）、WIP は `draft`、置き換え済みは `deprecated`
   - `sources`。文書が根拠にしている外部資料・上流文書（要件定義→設計など）があれば登録し、`id` を付ける。本文中で根拠を示す箇所は `[^id]` 脚注に変える
   - `stale_after` は「定期的に見直すべき」文書（環境手順・技術スタック）にだけ付ける。全文書に一律付けると陳腐化警告がノイズになる
2. **リンクをバンドル相対（`/` 始まり）に揃える**。既存の相対リンクが壊れていなければ無理に変えなくてよい（相対も仕様上有効）
3. **本文を構造化する**。慣習見出し（`# Schema`・`# Examples`）が適用できる箇所だけ合わせる。文章を書き換えて意味を変えない。本文に NBSP（U+00A0）や全角スペースが混じっていることがあるので、文字列一致で編集する前に該当行を実際に読む
4. 各ディレクトリの `index.md` を生成・更新する。エントリにはフロントマターの `description` を反映する。バンドルルートの `index.md` のみ `okf_version: "0.2"` を持つフロントマターを置く
5. バンドルルートの `log.md` に移行エントリを追記する（`## YYYY-MM-DD` 見出し、新しい日付が上）
6. `scripts/okf_check.py --check` を実行し、違反ゼロを確認する

フロントマター付与の例：

**Input**（`docs/design/data-model.md` 冒頭）

```markdown
# データモデル設計

本ドキュメントは受注管理システムのデータモデルを定義する。要件定義書のユースケース一覧を基に...
```

**Output**

```markdown
---
type: Design
title: データモデル設計
description: 受注管理システムの概念・論理データモデルとテーブル定義。
tags: [design, data-model]
status: stable
generated: { by: human:k2works, at: 2026-06-10T09:12:00Z }   # 本文未変更なので git 著者と最終更新コミット
sources:
  - id: requirements
    resource: /requirements/requirements_definition.md
    title: 要件定義書
---

# データモデル設計

本ドキュメントは受注管理システムのデータモデルを定義する。要件定義書のユースケース一覧を基に...[^requirements]

[^requirements]: 要件定義書
```

### 3. バージョンアップ（`--upgrade <version>`）

仕様が改訂されたとき、既存バンドルを新バージョンに追従させる。

1. バンドルルート `index.md` の `okf_version` で現在バージョンを確認する（無ければ v0.1 相当とみなす）
2. ガイドの「vX.Y からの変更点」節（v0.2 なら §13）を読み、**破壊的変更**と**追加的変更**を分けて把握する
3. 破壊的変更を機械的に適用する。v0.1→v0.2 は `scripts/okf_check.py --upgrade 0.2` が対応している
   - `timestamp` → `generated: { by, at }`（`by` は git log の著者から推定。人なら `human:<id>`。推定できなければ `unknown/legacy` とし、レポートに列挙する）
   - 本文 `# Citations` リスト → フロントマター `sources`
4. 追加的変更は「付けられるところだけ」付ける。無いことも仕様上有効なので、根拠の無いフィールドを埋めるためにでっち上げない
5. `okf_version` を更新し、`log.md` に **Upgrade** エントリを追記する
6. `--check` で違反ゼロを確認する

将来のバージョン（v0.3 以降）でスクリプトが未対応なら、ガイドの変更点節を読んで変換規則を洗い出し、スクリプトに変換を追加してから適用する。手作業で全文書を直さない。

### 4. 検証（`--check`）

```bash
python .claude/skills/migrating-okf/scripts/okf_check.py --check <バンドルルート>
```

運用手順書に登録済みの Gulp タスク `gulp okf:check`（同じスクリプトを呼ぶ）でもよい。`gulp okf:help` に `okf:upgrade`・`okf:viz`（上流ツールでグラフ可視化）などの一覧がある。

検証内容はガイド §11 に対応する。

| レベル | 内容 |
| :--- | :--- |
| ERROR | 予約名以外の `.md` にフロントマターが無い / `type` が空 / `index.md`（ルート以外）にフロントマターがある / `log.md` の日付見出しが `YYYY-MM-DD` でない |
| WARN | `generated` が無い / `generated.by` の形式がアクター規約に合わない / 脚注ラベルに対応する `sources[].id` が無い / タイムスタンプに UTC オフセットが無い / バンドル内リンク切れ / `stale_after` を過ぎている |

検査はコードフェンスとインラインコードの中を無視する（仕様例のリンクや脚注を誤検知しないため）。ERROR は移行完了前に必ず解消する。WARN は仕様上は適合なので、内容を確認して意図的なら残してよい。リンク切れは「まだ書かれていない知識」でも有効だが、移行直後のリンク切れはたいてい単なるパス間違いなので直す。

## 判断に迷いやすい点

- **`verified` を付けてよいのは、実際に人またはプロセスが内容を確認したときだけ。** 移行作業でエージェントが読んだだけでは `verified` にしない。信頼ティアの意味が壊れる
- **`description` は検索スニペットと `index.md` に使われる。** 「〜について記述したドキュメント」のような自己言及ではなく、中身を 1 文で言う
- **`type` の数は絞る。** ディレクトリごとに 1 つが目安。文書ごとに新しい型を発明すると消費側のルーティングが効かない
- **本文の意味を変えない。** 移行は構造の付与であって推敲ではない。内容の誤りに気づいたらレポートに書き、別作業にする
- **mkdocs との共存。** フロントマターは MkDocs でもメタデータとして無害に扱われる。`docs/index.md` は MkDocs のトップページでもあるので、OKF の `okf_version` フロントマターを追加しても既存本文は残す

## 完了報告

`--migrate` / `--upgrade` の最後に次を報告する。

```markdown
## OKF 移行結果

- バンドル: <パス>（okf_version: <版>）
- コンセプト: <N> 件（type 別内訳）
- 除外: <N> 件（理由）
- 検証: ERROR 0 / WARN <N>
- 要確認: <generated.by を推定できなかった文書、リンク切れ、内容の疑義 など>
```
